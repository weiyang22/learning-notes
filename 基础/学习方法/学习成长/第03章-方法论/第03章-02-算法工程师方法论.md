## 0. 方法论全景图：四阶段 × 三角色

> 在展开每个方法前，先建立全局视角：算法工程师面对任何问题时，都会经过**四个阶段**（思考 / 分析 / 解决 / 归档）；同时扮演**三个角色**（技术执行 / 项目 Owner / 团队贡献者）。每个方法都对应一个或多个"阶段 × 角色"组合。

### 0.1 四阶段的关系

```text
  [思考问题]  ──→  [分析问题]  ──→  [解决问题]  ──→  [归档问题]
       ↑                                                  │
       └──────────────── 复盘反馈 ──────────────────────────┘
```

- **思考**：从模糊现象到清晰问题的过程。
- **分析**：把问题拆解为可验证的子问题。
- **解决**：把子问题的答案组合成可执行方案。
- **归档**：把过程和结果固化为可复用的知识。

> 💡 **核心原则**：**四阶段不可跳跃**。没有思考清楚就动手（"还没分析就写代码"）= 浪费；分析清楚没归档（"踩过的坑下次再踩"）= 无积累。

### 0.2 三角色在不同阶段的关注点

| 阶段     | 技术执行者             | 项目 Owner              | 团队贡献者            |
| :--- | :--- | :--- | :--- |
| **思考** | "这问题我能用模型 X 解吗？"  | "这问题是否值得作为项目做？"       | "这方法论值得团队复用吗？"   |
| **分析** | "输入输出 + 评估指标是什么？" | "投入产出比 + 风险点 + 资源需求？" | "团队其他人能学会吗？"     |
| **解决** | "跑通 baseline，调超参" | "管理时间盒 + 协调依赖方"       | "写文档 + 培训团队"     |
| **归档** | "记录我的踩坑"          | "沉淀项目案例 + 复盘"         | "输出方法论文档 / 内部分享" |

> 📌 **P6→P7 跃迁的本质**：从"只关注技术执行者列"到"能同时关注 Owner + 团队贡献者列"。

### 0.3 方法论的"骨架"——本文件的组织逻辑

本文件按四阶段顺序展开：思考 → 分析 → 解决 → 归档。在每一阶段，给出 3-6 个核心方法，每个方法按统一格式呈现：

```text
### 方法 N：[名称]
> 来源：[出处文档]
> 适用：[什么时候用]
> 结构：[怎么做]
> 案例：[真实例子]
> 反例：[什么时候不该用]
> 配套：[与其它方法的关系]
```

## 第一部分：思考问题

> **思考问题的目标**：从混乱的现象中，提炼出**清晰、可验证、有杠杆**的问题定义。这一步错了，后面所有工作都是无用功。

### 1. 五层 Why 模型（深度思考）

> **来源**：《教程-沟通思维职业篇》§1.1-1.5；《成长教程》§5.1
> **适用**：分析任何工作现象（实验结果、Bug、业务指标变化）；也可用于拆解论文核心创新。

#### 1.1 五层结构

| 层级 | 提问 | 输出 | 范例 |
| :--- | :--- | :--- | :--- |
| **L1 现象** | 发生了什么？ | 数据 / 观察 | "线上 CTR 从 5.2% 降到 4.8%" |
| **L2 机制** | 为什么有效 / 为什么会发生？ | 假设链条 | "新模型对长序列兴趣衰减，导致老用户 CTR 下降" |
| **L3 证据** | 怎么证明这个机制？ | 实验 / 数据 / 文献 | "分用户群分析：老用户 CTR -8%，新用户 CTR +3%" |
| **L4 抽象** | 本质是什么？一句话命名 | 可复用规律 | **"用户兴趣漂移导致长期 embedding 失效"**（命名：Interest Drift Decay） |
| **L5 推广** | 哪些场景也成立？ | 迁移建议 | "短视频 / 电商 / 广告都面临同样问题" |

#### 1.2 L4 命名：P6→P7 的分水岭

L4 必须给出**一句话命名**，且命名要满足三个标准：

| 标准 | 解释 | 范例 |
| :--- | :--- | :--- |
| **可识别** | 别人听到名字立刻知道是什么 | "维度坍缩" vs "embedding 不够用" |
| **可复用** | 能迁移到其它场景 | "兴趣漂移" → 也能用于电商 |
| **可操作** | 暗示了解决方案的方向 | "坍缩"暗示"加 uniformity"；"漂移"暗示"加时间衰减" |

> 📌 **为什么 L4 重要**：面试官、同事、未来的你，回看时能凭"名字"回忆起整套机制。没有 L4 命名的复盘只是流水账，有 L4 命名的复盘是知识资产。

#### 1.3 案例：从数据波动到 Insight

**L1 现象**：模型 AUC 提升 2%，但线上 CTR 反而下降 1%。
**L2 机制**：可能模型过拟合了某子群（用户群分布偏移）。
**L3 证据**：分用户群看，AUC 提升集中在头部用户（高频活跃），但尾部用户 AUC 下降。
**L4 抽象**：**"短视指标过拟合"**（指标漂移问题）。
**L5 推广**：所有"离线-在线不一致"问题都可归到这一类。

#### 1.4 反例：什么时候不要做五层

- 紧急线上故障（先止血，不做深度思考）
- 简单日常工作（写周报、做汇报——用模板即可）
- 创意发散阶段（先记录所有可能，再筛选）

### 2. 第一性原理（剥离表象到本质）

> **来源**：《成长教程》§1；《教程-理论技术工程篇》§1（隐含）
> **适用**：当面对一个看起来"理所当然"的设计，想知道它是否最优时。

#### 2.1 核心问题

- "这件事的本质是什么？"
- "如果从零开始，我会怎么设计？"
- "我现在的方案，与本质的最优方案，差多少？"

#### 2.2 案例：为什么推荐系统分召回 + 排序两阶段？

**表象答案**："业界都这样做。"
**第一性问题**："为什么不能端到端输出 top-K？"

**答案**：
- 计算复杂度：100 万物品端到端推理 = 100 万次 forward → 不可行
- 训练目标：点击率排序 vs top-K 排序优化目标不同
- 工程解耦：召回和排序可独立演进、独立上线

→ 结论：两阶段是**计算 + 目标 + 工程**三个约束的折中。当约束改变（如 OneRec 用生成式 + KV Cache），两阶段可被融合。

#### 2.3 第一性原理的常用提问模板

```text
1. 这个方案的核心假设是什么？
2. 如果假设不成立，方案还成立吗？
3. 有没有另一个领域用类似假设但解决了不同问题？
4. 如果去掉一半的工程复杂度，效果会怎样？
```

### 3. 模型思维 vs 编程思维（认知定位）

> **来源**：《成长教程》§5.4
> **适用**：判断自己当前工作是否在创造"杠杆价值"。

#### 3.1 两种思维对照

| 维度 | 编程思维 | 模型思维 |
| :--- | :--- | :--- |
| **起点** | API 文档 | 业务现象 |
| **过程** | 代码怎么写 → 程序跑通 | 如何抽象 → 指标提升 + 机制解释 |
| **产出** | 功能实现 | 问题定义 + 杠杆点 |
| **评价** | 跑通 / 不跑通 | 有效 / 无效，**为什么** |

#### 3.2 自检清单

```text
□ 我做的这件事，本质上是"把别人设计的模型跑起来"，还是"我定义了问题"？
□ 我能向不懂 ML 的产品经理解释清楚为什么我的方案有效吗？
□ 如果让我从零再做一次，我会用同样的方案吗？还是会有本质不同的设计？
□ 我产出的代码 / 模型，对团队其他人有什么可复用的价值？
```

> 📌 **P7 的标志**：80% 的时间在做模型思维工作（定义问题、设计实验、提炼机制），20% 在做编程思维工作（实现、调优）。

### 4. 杠杆识别：什么工作值得做

> **来源**：《成长教程》§0.1-0.2
> **适用**：决定时间投入方向。

#### 4.1 杠杆公式

$$\text{杠杆} = \frac{\text{影响人数} \times \text{影响深度} \times \text{可复用性}}{\text{投入时间}}$$

#### 4.2 高 / 低杠杆工作对照

| 高杠杆 | 低杠杆 |
| :--- | :--- |
| 设计一个可复用的训练框架 | 重复调一个超参 5 次 |
| 写一篇 1w+ 阅读的技术博客 | 写一份只能自己看的草稿 |
| 抽象出 3 个项目通用的方法论 | 重复第 3 个项目时还在重新摸索 |
| 带 2 个 P5 同学成长 | 自己包揽所有核心工作 |
| 把模型上线一次，沉淀 SOP | 每个模型独立上线，无规范 |

#### 4.3 决策流程

```text
对每个候选工作项：
1. 估算影响人数（1 / 10 / 100 / 1000+）
2. 估算可复用性（一次性 / 团队复用 / 行业复用）
3. 估算投入时间
4. 计算杠杆值，优先做高杠杆
5. 每周 review：上 80% 时间是否花在 top 20% 杠杆工作上？
```

## 第二部分：分析问题

> **分析问题的目标**：把模糊的问题拆成**可执行、可验证、有优先级**的子问题清单。这一步决定后续解决问题的效率。

### 5. 五段式叙述（最高频复用）

> **来源**：《成长教程》§4.1；《教程-沟通思维职业篇》§2.1-2.5
> **适用**：项目叙述、面试答题、实验复盘、博客写作（出现 7+ 次，是 5 份文档的"通用语法"）

#### 5.1 五段结构

```text
现象 ─→ 假设 ─→ 证据 ─→ 反例 ─→ 推广
（观察到） （猜测原因）（验证假设）（自找漏洞）（抽象升华）
```

#### 5.2 每段的写作规范

| 段 | 字数 | 关键问题 | 写作 tips |
| :--- | :--- | :--- | :--- |
| **现象** | 50-100 | 看到了什么数据 / 现象？ | 必须有**具体数字**；避免"效果不好"等模糊词 |
| **假设** | 50-100 | 为什么？机制是什么？ | 一个核心假设，不要多个并列 |
| **证据** | 100-200 | 怎么证明？ | 实验 / 数据 / 文献至少 2 类证据 |
| **反例** | 50-100 | 什么情况下假设不成立？ | 主动暴露漏洞，比被面试官抓到强 |
| **推广** | 50-100 | 这件事的更广意义？ | 抽象成可复用规律（带 L4 命名） |

#### 5.3 完整案例：Query 单独建模

**【现象】** 统一序列建模（Query + History 一起进 Transformer）后，AUC 反而下降 0.5%。我们怀疑 Query 信号被 History 噪声淹没。

**【假设】** Transformer 的 Attention 对 Query 和 History 一视同仁，Query 的高意图信号被长 History 的平均信号稀释（**Intent Dilution**）。

**【证据】**
1. Attention 可视化：Query token 的 attention weight 仅 5%，远低于 History 平均 12%。
2. 分用户群分析：长 History 用户群（>100）AUC 下降 0.8%，短 History 用户群 AUC 反而上升 0.2%。
3. 去掉 Query 让 Query 直接 concat 到 user embedding：AUC 回升 0.3%。

**【反例】** 在短视频场景，Query 是模糊的视频 ID，History 是细粒度的观看序列，Intent Dilution 不明显，统一建模反而有效。

**【推广】** **强意图信号需独立保护**——当输入包含强弱悬殊的信号时，弱信号需要"独立通路"避免被强信号平均。

#### 5.4 五段式的常见失败模式

| 失败 | 现象 | 修复 |
| :--- | :--- | :--- |
| **现象空泛** | "效果提升明显" | 强制要求具体数字 + 提升幅度 |
| **假设过多** | 列出 5 个并列假设 | 只保留一个核心假设，其它作为次级讨论 |
| **证据单薄** | 只引用一篇论文 | 至少 2 类证据（实验 + 数据 / 实验 + 文献） |
| **无反例** | 假设完美无缺 | 主动找反例——这是 P7 的标志 |
| **推广空洞** | "这个方法很重要" | 必须 L4 命名 + 给出迁移场景 |

### 6. STAR+ 法则（项目叙述）

> **来源**：《教程-沟通思维职业篇》§3.1-3.4
> **适用**：描述自己的项目、行为面试、简历项目叙述。

#### 6.1 五段结构

```text
S ─→ T ─→ A ─→ R ─→ Abstraction
（背景） （目标） （动作） （结果） （抽象）
```

#### 6.2 STAR vs STAR+ 的关键差异

| 段 | 标准 STAR | STAR+ |
| :--- | :--- | :--- |
| **S** | 业务背景 | + 业务规模（DAU / GMV / 流量级别） |
| **T** | 个人任务 | + 关键挑战（为什么难） |
| **A** | 做了什么 | + 技术动作清单（3-5 条分点） |

### 7. 深度递进三层（技术问答）

> **来源**：《教程-沟通思维职业篇》§4
> **适用**：面试回答"为什么 X 有效"

#### 7.1 三层结构

```text
L1 实验描述 ─→ L2 机制解释 ─→ L3 抽象推广
（结果是什么）  （为什么）      （还能用在哪）
```

#### 7.2 范例

**问题**："DIN 相比 DeepFM 提升的关键是什么？"

**L1（实验描述）**：DIN 在淘宝数据集上 AUC 比 DeepFM 高 3.2%，点击率提升 11.5%。

**L2（机制解释）**：DIN 用 Attention Pooling 给不同历史物品分配不同权重，让"用户刚浏览的相似物品"获得更高 attention，从而精准捕捉用户当前兴趣。DeepFM 用 Sum Pooling 平均所有历史，无法区分重要性。

**L3（抽象推广）**：**Attention Pooling 解决"序列中不同位置重要性差异"**——这一原则适用于所有"异构输入需要加权"的场景（如广告主-用户-商品三方匹配、新闻多源融合）。

#### 7.3 关键原则

- **永远不要停在 L1**——只说结果 = 不及格
- **L2 是必须的**——机制解释体现技术深度
- **L3 是专家与高级工程师的分水岭**——抽象推广体现认知高度

#### 8.3 案例：RankMixer 辅助 Tower 实验失败

**现象**：RankMixer 作为辅助 Tower 加到精排模型，AUC -0.3%（期望 +0.5%）。

**三个可能原因**：
1. **特征交互不充分**：RankMixer 的 Group-Level Interaction 没学到有意义的交叉。
   - 证据：可视化发现 attention 权重接近均匀。
   - 反驳：如果无效应该不影响 AUC，但实际下降。
2. **特征工程与主 Tower 不匹配**：辅助 Tower 输入的特征是主 Tower 的子集，可能存在 leakage 或缺失。
   - 证据：检查发现 1 个特征取值范围差异巨大（0-1 vs 0-10000）。
   - 反驳：单独跑辅助 Tower AUC 正常。
3. **梯度干扰**：辅助 Tower 的梯度影响主 Tower 的收敛。
   - 证据：主 Tower loss 曲线震荡。
   - 反驳：warmup 后震荡消失但 AUC 仍下降。

**倾向**：原因 2（特征不匹配）。

**验证**：对辅助 Tower 输入做 normalize，AUC 回升到 +0.1%。验证成功。

**后续**：特征输入前必须做对齐检查，建立"特征白盒"流程。

#### 14.2 每道防线的具体实现

**防线 1 SQL 强制**：

```sql
SELECT features.*, labels.label
FROM features
JOIN labels ON features.user_id = labels.user_id
WHERE labels.label_time >= features.feature_time  -- 关键
```

**防线 2 Temporal Snapshots**：

```python
# 特征表按天分区
```

```python
def assert_no_temporal_leak(df):
```

- 用过去 30 天数据切片作为"伪未来"评估

### 15. A/B 测试 SOP（统计严谨性）

> **来源**：《教程-理论技术工程篇》§9.4
> **适用**：任何线上实验设计

#### 15.1 5 个子流程

```text
1. 样本量计算
   ↓
2. 显著性检验（z-test）
   ↓
3. 多组实验校正（Bonferroni）
   ↓
4. A/A 测试（基线校验）
   ↓
5. 实时 p-value 监控
```

#### 15.2 样本量计算公式

$$n = \frac{(z_{\alpha/2} + z_{\beta})^2 \cdot (p_1(1-p_1) + p_2(1-p_2))}{(p_1 - p_2)^2}$$

- $z_{\alpha/2}$：显著性水平（默认 1.96，$\alpha=0.05$）
- $z_{\beta}$：统计功效（默认 0.84，$1-\beta=0.8$）
- $p_1, p_2$：两组转化率

**Python 实现**：

```python
def required_sample_size(p1, p2, alpha=0.05, power=0.8):
    from scipy.stats import norm
    z_alpha = norm.ppf(1 - alpha / 2)
    z_beta = norm.ppf(power)
    numerator = (z_alpha + z_beta) ** 2 * (p1 * (1 - p1) + p2 * (1 - p2))
    denominator = (p1 - p2) ** 2
    return int(numerator / denominator) + 1
```

#### 15.3 显著性检验实现

```python
def z_test_proportions(p1, n1, p2, n2):
    """两组转化率的 z-test."""
    from scipy.stats import norm
    p_pool = (p1 * n1 + p2 * n2) / (n1 + n2)
    se = (p_pool * (1 - p_pool) * (1/n1 + 1/n2)) ** 0.5
    z = (p1 - p2) / se
    p_value = 2 * (1 - norm.cdf(abs(z)))
    return z, p_value
```

#### 15.4 多组实验校正

```python
def bonferroni_correct(p_values, alpha=0.05):
    """对 K 组实验做 Bonferroni 校正."""
    K = len(p_values)
    adjusted_alpha = alpha / K
    return [p < adjusted_alpha for p in p_values]
```

> ⚠️ **警告**：当 K > 5 时，Bonferroni 太保守。考虑 Benjamini-Hochberg FDR 控制。

| **模型蒸馏** | 推理资源极紧 | 2-10x |

### 17. 听题三阶段 + 60-90-30 法则（面试答题）

> **来源**：《教程-沟通思维职业篇》§13
> **适用**：任何面试答题

#### 17.1 听题三阶段

```text
阶段 1：复述问题（30 秒）
   "我理解您的问题是 [复述] + [补充关键约束] + [确认细节]"
   → 让面试官知道你在听

阶段 2：拆解问题（1 分钟）
   "这个问题可以拆为 4 个子问题：1) ... 2) ... 3) ... 4) ..."
   → 展示结构化思维

阶段 3：列出大纲（30 秒）
   "我打算先讲 X，再讲 Y，最后讲 Z"
   → 让面试官跟上你的节奏
```

#### 17.2 60-90-30 法则

- **60%**：技术深度（核心知识点）
- **90 秒**：黄金开场（第一句话决定印象）
- **30%**：留白互动（问面试官"这个方向您想深挖吗？"）

#### 17.3 反例：被面试官打断

| 表现 | 修复 |
| :--- | :--- |
| 跑题（答非所问） | 听题三阶段 + 列出大纲 |
| 太空（无具体例子） | 每个论点配 1 个案例 |
| 太长（5 分钟还没讲完 1 个点） | 强制 5 分钟内讲完一个点 |
| 紧张卡壳 | 准备"我先想 10 秒"的过渡话术 |

### 18. "是的，而且..." 句式（被质疑时）

> **来源**：《教程-沟通思维职业篇》§13.4
> **适用**：被面试官挑战 / 质疑方案时

#### 18.1 标准模式

```text
承认质疑点 → 解释已考虑的方案 → 展示生产中的发现 → 转化为深度展示
```

#### 18.2 范例

**面试官**："你的方案在冷启动场景会失效吧？"

**错误回答**：
- "不会失效的。"（直接否定 = 防御性）
- "我不知道。"（放弃）

**正确回答**：

> "您说的对，冷启动确实是个挑战。我们在生产中发现，新用户冷启动的 CTR 比老用户低 40%。我们的解决方案是 [X]。但我们也发现一个有趣的现象 [Y]，这启发我们后续做了 [Z]。这个发现也写在我们的一篇内部分享里。"

**结构**：
- 承认质疑 → 展示已思考过
- 解释方案 → 体现执行力
- 展示发现 → 转化为深度展示
- 总结升华 → 给面试官追问机会

### 23. Anki 卡片 5 类与高质量卡片规则

> **来源**：《教程-沟通思维职业篇》§7.4

#### 23.1 5 类卡片

| 类型 | 范例问题 | 范例答案 |
| :--- | :--- | :--- |
| **概念卡** | "什么是 Attention？" | "QKV 三个向量通过 softmax 加权求和" |
| **公式卡** | "MHA 的公式是什么？" | $\text{Attention}(Q,K,V) = \text{softmax}(\frac{QK^\top}{\sqrt{d_k}})V$ |

#### 23.2 高质量卡片的 10 条规则

```text
1. 最小信息原则：一张卡片只问一个问题
2. 上下文独立：脱离笔记也能理解
3. 单点问题：不要"列举 X 的 Y 个特点"
4. 答案精确：避免"很多 / 一些"等模糊词
5. 反向思考：能问"为什么 X 不好"而不仅是"X 是什么"
6. 主动回忆：必须自问自答，不能复制
7. 间隔复习：每天 20 分钟，不超 30 张新卡
8. 持续更新：发现错误立即修改
9. 标签系统：用 Deck + Tag 分类
10. 关联卡片：用"参见 X"链接相关卡片
```

#### 23.3 常见错误

| 错误 | 表现 | 修复 |
| :--- | :--- | :--- |
| **卡片过大** | 一张卡片包含 5 个问题 | 拆成 5 张 |
| **答案模糊** | "主要是 X" | 强制具体数字 / 名称 |
| **过于简单** | "推荐系统是什么" | 改成 "DIN 的核心创新是什么" |
| **未应用** | 只输入不输出 | 每周用卡片回答 1 次 |

## 第五部分：方法论的元方法论

> 这一部分回答"如何设计自己的方法论"和"什么时候不要用方法论"——这是 P7+ 必备的元认知。

### 26. 如何设计自己的方法论

#### 26.1 设计原则

| 原则 | 解释 |
| :--- | :--- |
| **奥卡姆剃刀** | 框架越简单越好，少一个环节就少一个失败点 |
| **单一职责** | 一个框架解决一类问题，不要试图万能 |
| **可观察** | 框架的产出可以客观评估（不是"感觉"） |
| **可训练** | 能教会别人，能写明文档 |
| **熵减** | 框架用得越多越简单（不是越用越复杂） |

#### 26.2 设计流程

```text
Step 1：观察自己做某件事时的"重复动作"
   ↓
Step 2：提炼这些动作为 3-5 步
   ↓
Step 3：给每步命名（用动词）
   ↓
Step 4：写成模板
   ↓
Step 5：用 3 次迭代改进
   ↓
Step 6：分享给同事，让他们用，给反馈
```

#### 26.3 范例：我的"读论文方法论"

| 步骤 | 动作 | 输出 |
| :--- | :--- | :--- |
| 1. 速读 | 看 Abstract + Intro + Conclusion | 5 分钟判断"值不值得深读" |
| 2. 精读 | Method + Experiments | 2 小时 |
| 3. 复现 | 跑官方代码 / 自己实现 | 1-3 天 |
| 4. 提炼 | 写论文卡片（7 段模板） | 1 小时 |
| 5. 应用 | 找业务场景迁移 | 0.5-2 天 |
| 6. 输出 | 写博客 / 团队分享 | 2-4 小时 |

#### 26.4 检验方法论有效性的 3 个标准

1. **节省时间**：用方法论后，做这件事的时间减少 ≥ 30%
2. **提升质量**：产出物评分提升（可量化）
3. **可复用**：在第二个相似场景也适用

### 27. 方法论的适用边界（反方法论）

> **核心思想**：没有万能框架。每个方法都有适用边界，识别边界是高级用法。

#### 27.1 常见框架的适用边界

| 框架 | 适用 | 不适用 |
| :--- | :--- | :--- |
| **五段式** | 项目叙述 / 实验复盘 / 博客写作 | 紧急故障 / 简单日常任务 |
| **STAR+** | 面试 / 简历 / 跨团队沟通 | 内部周报 / 私下讨论 |
| **DDD** | 模型改动 / 新服务 | 配置微调 / Bug 修复 |
| **白盒 Review** | AI 生成代码 / 复杂模块 | 一行配置 / 注释 |
| **Bug Diary** | 重复性问题 / 团队共享 | 一次性 Bug |
| **Anki** | 长期记忆 / 面试准备 | 临时性任务 |
| **设计文档** | 跨团队 / 长期项目 | 个人 1 天可完成的工作 |

#### 27.2 "反方法论"的反例：过度使用

| 表现 | 后果 |
| :--- | :--- |
| **小任务也写 7 段文档** | 效率降低 50% |
| **所有沟通都用 STAR+** | 显得机械 |
| **任何改动都走 DDD** | 文档爆炸 |
| **所有问题都做五段式分析** | 浪费时间 |

#### 27.3 决策原则

```text
是否使用某方法论？
├── 这件事的影响范围？大 → 用
├── 投入时间？>1 人天 → 用
├── 可复用性？高 → 用
├── 是否紧急？紧急 → 简化用
└── 复杂度？高 → 用
```

### 28. 框架过载的 5 个信号

> 当你陷入"为方法论而方法论"时，效率反而下降。识别这 5 个信号。

#### 28.1 五个信号

| 信号 | 表现 |
| :--- | :--- |
| **写文档比做事情多** | 1 周写了 5 份文档，但只推进了 1 个项目 |
| **开会都在套框架** | 每次讨论都用"五段式 / STAR+ / DDD" |
| **为了完整而僵化** | 框架某环节不合适，但硬套 |
| **同事觉得你在表演** | 反馈"你说话太有套路了" |
| **自己感到疲惫** | 用框架比不用更累 |

#### 28.2 修复方法

1. **暂停一周**：不用任何框架，纯靠直觉做事
2. **回归本质**：问"我这样做是为了什么？"
3. **保留核心，舍弃繁文**：每个框架保留最关键的 1-2 步
4. **节奏化**：固定场景用框架（如：面试必用 STAR+），其它场景不用
5. **团队对齐**：和团队约定哪些场景用哪些框架

### 29. 跨团队协作 / 向上管理

**Action（是的，而且进阶版）**：
1. **承认现实**：我理解团队现在确实紧张
2. **展示价值**：这件事完成预计带来 [X] 的业务收益 + [Y] 的技术积累
3. **展示退路**：如果实在抽不出人，我可以用 [Z] 替代方案，但效果会打折到 [W]
4. **给出选择**：让 Leader 选（要资源 vs 接受降级方案）

**Result**：获得部分支持（1 人 2 个月），达成预期 70%。

##### 剧本 2：推动跨部门项目

**核心方法**：Stakeholder Map

| 角色 | 谁 | 关心什么 | 我的策略 |
| :--- | :--- | :--- | :--- |
| **决策者** | VP | 业务收益 | 汇报 ROI |
| **影响者** | 跨部门 Lead | 部门利益 | 找双赢点 |
| **受益者** | 业务方 | 解决痛点 | 联合提案 |
| **中立者** | 其他团队 | 不想被打扰 | 提前 sync，不打扰 |

**推进节奏**：
1. 与受益者联合提案 → 形成共识
2. 找影响者买账 → 谈双赢（"你帮我 X，我帮你 Y"）
3. 提交决策者审批 → 准备详细 ROI
4. 项目启动 → 中立者最小打扰

##### 剧本 3：接受 Critical Feedback

**错误反应**：
- 防御性反驳："但是..."
- 沉默不语
- 表面接受，实际不改

**正确反应（是的，而且）**：
1. 承认反馈点："您说的 X 确实是我的问题"
2. 解释上下文："当时我考虑的是 Y，但确实没考虑到 Z"
3. 展示行动："我已经做了 [W] 来改进 / 我打算 [V]"
4. 邀请跟进："您愿意下周再看一次吗？"

#### 29.2 跨团队沟通的 5 条黄金法则

1. **不要假设对方知道**：每次 sync 先讲背景
2. **不要假设对方关心**：每段先说"对你意味着什么"
3. **用对方语言**：业务方听业务语言，技术方听技术语言
4. **先给结论再给细节**：避免被细节追问偏
5. **明确下一步**：每次会议结束有"谁什么时候做什么"

## 29. 离线-在线一致性：搜推广的头号工程难题

> 📌 **一句话**：搜推广工程师的 80% 翻车都来自"离线涨指标、在线没效果甚至掉效果"。这不是玄学，是有清晰根因的工程问题。

### 29.1 离线-在线 Gap 的 5 大根因

```text
┌─────────────────────────────────────────────────────────┐
│  离线训练世界              在线推理世界                  │
│  ┌──────────┐             ┌──────────┐                  │
│  │ 曝光日志 │   ─────?──► │ 实时请求 │                  │
│  └──────────┘             └──────────┘                  │
│       ↑                         │                       │
│       │                         ▼                       │
│  ┌──────────┐             ┌──────────┐                  │
│  │ 完整特征 │             │ 部分特征 │                  │
│  └──────────┘             └──────────┘                  │
└─────────────────────────────────────────────────────────┘
         5 大 Gap 来源
```

| # | 根因 | 典型表现 | 检测方法 |
| :--- | :--- | :--- | :--- |
| 1 | **数据 Gap** | 离线用 30 天全量训练，在线只取最近 1 小时特征 | 分布对比（PSI / KS） |
| 2 | **特征 Gap** | 离线特征拼接有 200 个，在线 Pipeline 只拼到 150 个 | 特征覆盖率监控 |
| 3 | **服务 Gap** | 离线用 Python 算分，在线用 C++/Go 重写逻辑不一致 | 影子流量 + 打分比对 |
| 4 | **时延 Gap** | 离线模型无时延约束，在线 P99 必须 < 50ms | 推理链路 profiling |
| 5 | **偏差 Gap** | 离线用曝光样本训练，在线要预测"未曝光会不会点" | 位置偏差建模 + 反事实评估 |

### 29.2 离线-在线 Gap 的 3 类检测方法

#### A. 白盒检测（推荐，最高 ROI）

**做什么**：让离线和在线走完全相同的代码路径 + 相同特征 + 相同输入。

```python
# 影子打分模式：在线请求时，同步用离线模型的同一份特征算一遍分
def online_predict(user, item):
    features = online_feature_pipeline(user, item)  # 实时特征

    # 双跑打分
    score_online = online_model.predict(features)
    score_shadow = offline_model.predict(features)  # 影子打分

    # 上报一致性
    metric_client.report("score_diff",
                         abs(score_online - score_shadow),
                         tags={"model_version": "v123"})

    return score_online
```

**关键指标**：
- **打分一致率**：> 99.9%（小数点后 4 位）
- **特征覆盖率**：每个特征在离线/在线的覆盖率差异 < 0.5%
- **时延分布**：在线 P50 / P99 / P999 都要监控

#### B. 黑盒检测（必备，最低成本）

**做什么**：对比离线 AUC 和在线 CTR / CVR / RPM 的提升幅度。

| 离线 AUC 涨 | 在线 CTR 涨 | 结论 |
| :--- | :--- | :--- |
| +0.5% | +0.5% ~ +1% | 健康，理想情况 |
| +0.5% | +0.1% 或不变 | ⚠️ 有 Gap，查特征/服务 |
| +0.5% | -0.5%（掉） | 🔴 严重 Gap，必须回滚 |
| +1% | +2% | ✅ 真实收益超过离线预期 |
| +0.1% | +1% | ⚠️ 离线低估了收益，检查评估方法 |

#### C. 影子流量（必杀技，最严谨）

**做什么**：把 5%~10% 的真实流量用一个"影子模型"打分，但不出现在用户面前，纯粹用于比对。

```text
生产链路:
  用户 → 主模型 → 出参 → 用户看到

影子链路:
  用户 → 影子模型 → 出参(不展示) → 收集真实点击
```

**核心价值**：影子模型能拿到"在线真实分布"的反馈，但不影响业务。适合做：
- 新模型上线前的最后验证
- 多模型长期对比（哪个更稳定）
- 离线-在线 Gap 的根因定位

### 29.3 反穿越 4 道防线

> 💡 **"穿越"是什么？**
> 训练数据来自昨天，但训练时"看到"了今天才发生的行为（如点击/曝光），相当于数据穿越到了未来。模型会过拟合"未来信号"，在线效果必然差。

#### 防线 1：样本对齐（最基本）

```sql
-- 错误：训练时用了发生时间 > 样本时间 的特征
SELECT user_id, item_id, click_label,
       user_last_click_item  -- ❌ 这个特征可能来自未来
FROM exposure_log
WHERE date = '2024-01-01'

-- 正确：所有特征的时间戳 ≤ 曝光时间戳
SELECT user_id, item_id, click_label,
       user_last_click_BEFORE_exposure  -- ✅ 严格时序
FROM exposure_log t1
JOIN user_feature_history t2
  ON t1.user_id = t2.user_id
  AND t2.feature_time < t1.exposure_time
WHERE t1.date = '2024-01-01'
```

#### 防线 2：特征快照（解决"实时特征被回填"）

**问题**：实时特征系统（如 Redis）会持续更新。训练时如果从 Redis 取特征，可能拿到"未来"的值。

**解法**：训练时不用 Redis，用"特征快照"（每个曝光时刻的特征被持久化下来）。

```text
特征快照系统架构:

  在线服务 ──┬── 写 Redis（实时查询用）
            └── 写 Kafka → Flink → HDFS（训练用）

  训练时: 从 HDFS 读 t 时刻的快照，不碰 Redis
```

#### 防线 3：时间切分（防止"全局信息泄漏"）

```python
# 错误：用未来 7 天的样本作为验证集
train_data = day_1 ~ day_7
val_data = day_8 ~ day_14  # ❌ 但训练时全局 shuffle 了

# 正确：严格按时间切分
train_data = day_1 ~ day_7
val_data = day_8  # 单独 1 天，不用未来

# 更好：留 3 天 gap
train_data = day_1 ~ day_7
val_data = day_11  # 中间留 3 天 gap，防止有滞后反馈
```

#### 防线 4：因果特征识别（最难）

**核心**：识别哪些特征是"果"而不是"因"。

| 特征 | 类型 | 训练时能用？ |
| :--- | :--- | :--- |
| 用户历史点击数 | 因 | ✅ |
| 用户最近点击的 item | 因 | ✅ |
| 用户最近点击的 item **所属类目** | 因 | ✅ |
| **本曝光中 item 是否在第一位** | 果（位置决定） | ❌ |
| **本曝光中 item 是否被高亮** | 果（产品策略决定） | ❌ |
| **用户在本次 session 的累计点击** | 果（本次曝光才发生） | ❌ |

> ⚠️ **核心心法**：训练数据是"上帝视角"（你看到了曝光后的所有事），在线推理是"凡人视角"（只能看到曝光前的信息）。上帝视角的特征，模型学到的是"事后诸葛亮"，在线没用。

### 29.4 位置偏差建模（PAL / IPW / DLA）

> **位置偏差**：用户在第 1 位 / 第 2 位 / 第 3 位的点击率天然不同（位置越靠前，点击率越高），但这个差异不是 item 本身的偏好，是位置带来的。

#### 方法 1：PAL（Position-Aware Loss）

```python
# 思路：训练时把位置信息作为输入，预测时把位置置为"待评估位置"
class PAL_Model(nn.Module):
    def __init__(self):
        self.position_embedding = nn.Embedding(num_positions, dim)
        self.user_tower = UserTower()
        self.item_tower = ItemTower()

    def forward(self, user_feat, item_feat, position):
        user_vec = self.user_tower(user_feat)
        item_vec = self.item_tower(item_feat)
        pos_vec = self.position_embedding(position)

        # 融合位置信息
        combined = torch.cat([user_vec, item_vec, pos_vec], dim=-1)
        ctr = self.mlp(combined)
        return ctr

# 推理时：枚举所有候选位置，取期望
def predict_at_all_positions(model, user, item):
    scores = []
    for pos in range(num_positions):
        scores.append(model(user, item, position=pos))
    # 取平均或最大
    return torch.stack(scores).mean()
```

#### 方法 2：IPW（Inverse Propensity Weighting）

**核心**：对位置靠前的样本降权，对位置靠后的样本升权。

```python
# 位置 k 的曝光倾向性 P(k)
# 通常用经验值：P(1) > P(2) > ... > P(K)
# 或者用随机化实验测出来

propensity_k = {
    1: 0.9,   # 90% 的请求第 1 位会被用户看到
    2: 0.7,
    3: 0.5,
    ...
    K: 0.1,
}

# 训练时加权
loss_per_sample = bce_loss(pred, label) / propensity_k[position]
total_loss = loss_per_sample.mean()
```

#### 方法 3：DLA（Dual Loss Adaptation）

**核心**：用两阶段训练，第一阶段只学位置，第二阶段把位置信息从 item 表示中剥离。

| 方法 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- |
| PAL | 简单，能捕获位置×内容的交互 | 推理时要枚举位置，开销大 | 位置数 ≤ 20 |
| IPW | 推理无额外开销 | 倾向性估计误差会被放大 | 有随机化曝光数据 |
| DLA | 推理高效，效果好 | 训练复杂，需两阶段 | 大规模工业系统（推荐） |

### 29.5 选择偏差 / 曝光偏差

**选择偏差（Selection Bias）**：用户看到的 item 是上一轮模型挑出来的，模型学的是"被挑出来的 item 中用户喜欢哪些"，但在线推理时要预测"未曝光的 item 用户喜不喜欢"。

**曝光偏差（Exposure Bias）**：用户只对曝光过的 item 有反馈，没曝光的 item 没有任何信号。

**解法**：

1. **曝光模型 + 校准**：用单独的曝光模型预测 item 被曝光的概率，反向加权。
2. **全量排序学习（LTR）**：用 Listwise 损失（如 LambdaMART / ListNet）代替 Pointwise，让模型学到排序而非绝对分。
3. **生成式召回**：见 §37，让模型直接生成候选，绕开"曝光才有数据"的死循环。

### 29.6 反馈循环放大

**可怕的事实**：你的推荐结果 → 影响用户行为 → 用户行为喂给模型 → 模型又推荐类似内容 → 进一步影响用户 → ……

```text
推荐结果 ──→ 用户行为 ──→ 训练数据 ──→ 新模型 ──→ 推荐结果
   ↑                                                      │
   └──────────────────────────────────────────────────────┘
                    反馈循环
```

**4 大放大机制**（详细见 §36）：
1. **回音室效应**：用户只看到一类内容，逐渐失去其他兴趣
2. **马太效应**：热门 item 越来越热，长尾 item 越来越冷
3. **流量倾斜**：模型倾向于把流量给"已知表现好"的 item
4. **数据污染**：上一轮的错误推荐产生的点击，成为下一轮的"正样本"

> 🎯 **搜推广 P7 的核心能力**：能识别出"离线涨指标 ≠ 在线涨指标"的根因，并提出 1~2 道防线。这比写一个模型值钱 10 倍。

## 30. 多任务学习与多目标权衡

> 📌 **一句话**：搜推广的核心矛盾不是"模型不够强"，而是"目标太多，互相打架"。CTR 涨了，CVR 可能掉；时长涨了，留存可能掉；商业化涨了，用户体验可能掉。

### 30.1 MMoE vs PLE vs ESMM vs Shared-Bottom 选型

```text
                     ┌──────────────────────────┐
                     │   输入特征（共享）         │
                     └──────────┬───────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
   ┌─────────┐            ┌─────────┐            ┌─────────┐
   │ Expert 1│   ...      │ Expert K│            │ 任务 A  │
   └─────────┘            └─────────┘            └─────────┘
        │                       │                       │
        └──────────┬────────────┘                       │
                   ▼                                    │
              ┌──────────┐                              │
              │ Gate A   │──→ 任务 A 输出                │
              └──────────┘                              │
              ┌──────────┐                              │
              │ Gate B   │──→ 任务 B 输出                │
              └──────────┘                              │
              ...                                       │
```

| 架构 | 核心思想 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **Shared-Bottom** | 所有任务共享底层 | 简单，参数少 | 任务冲突严重时互相拖累 | 任务高度相关（如 CTR + CTR-related） |
| **MMoE** (Ma et al. 2018) | K 个 Expert + 每个任务一个 Gate | 软共享，缓解冲突 | Expert 数量难调，可能 collapse | 任务数 2~5 个，中等相关性 |
| **PLE** (Tang et al. 2020) | 任务专属 Expert + 共享 Expert | 进一步缓解负迁移 | 参数更多，结构复杂 | 任务数 5+，相关性差异大 |
| **ESMM** (Ma et al. 2018) | 建模 CTR → CTCVR → CVR 的全链路 | 解决 CVR 数据稀疏（曝光未点击就没 CVR 样本） | 假设强（曝光→点击→转化必须串联） | 电商 CVR 预估（推荐） |
| **AITM** | 任务自适应信息迁移 | 灵活，但调参难 | 训练不稳 | 探索性场景 |

#### 决策树：怎么选？

```text
任务数 ≤ 2 且高度相关？
  └─ Yes → Shared-Bottom（简单就好）
  └─ No ↓

任务存在严格级联关系（CTR → CVR）？
  └─ Yes → ESMM
  └─ No ↓

任务数 2~5？
  └─ Yes → MMoE
  └─ No ↓

任务数 > 5 且差异大？
  └─ Yes → PLE
  └─ No ↓
不确定 → MMoE（最常用 baseline）
```

### 30.2 Loss 加权 4 大方法

> **问题**：多任务训练时，每个任务的 loss 量级不同（CTR loss 可能是 0.5，CVR loss 可能是 0.05），直接相加会被 CTR 主导。

#### 方法 1：Uncertainty Weighting (Kendall et al. 2018)

```python
# 每个任务一个可学习权重
loss_total = (1 / (2 * sigma_a**2)) * loss_a + log(sigma_a) \
           + (1 / (2 * sigma_b**2)) * loss_b + log(sigma_b) \
           + ...
```

**核心**：模型自动学习每个任务的"噪声水平"，噪声大的任务权重自然小。

#### 方法 2：GradNorm

**核心**：让每个任务对共享层的梯度大小相当。

```python
# 每个任务的梯度范数 / 目标梯度范数 = 1
w_i = w_i * (avg_gradient_norm / task_i_gradient_norm) ** alpha
```

#### 方法 3：DWA（Dynamic Weight Averaging）

**核心**：根据每个任务当前的 loss 下降速度动态调整权重。

```python
# 第 t 轮，任务 i 的权重
w_i(t) = N * exp(r_i(t) / T) / sum_j exp(r_j(t) / T)
# r_i(t) = loss_i(t-1) / loss_i(t-2)  # 下降率
```

#### 方法 4：手动动态权重（工业界最常用）

```python
# 业务方说：CTR 和 CVR 都要涨，但 GMV 更重要
# 那就给 GMV（≈CTR×CVR×Price）更大权重

# 阶段 1（冷启动期）：w_ctr=1, w_cvr=0.5, w_gmv=0.3
# 阶段 2（成熟期）：w_ctr=1, w_cvr=1, w_gmv=2
# 阶段 3（瓶颈期）：w_ctr=0.8, w_cvr=0.8, w_gmv=3
```

| 方法 | 自动化程度 | 调参难度 | 推荐度 |
| :--- | :--- | :--- | :--- |
| Uncertainty Weighting | 高 | 中 | ⭐⭐⭐ |
| GradNorm | 高 | 高 | ⭐⭐ |
| DWA | 中 | 中 | ⭐⭐ |
| 手动动态权重 | 低 | 低 | ⭐⭐⭐⭐（工业界首选） |

### 30.3 业务指标拆解：CTR / CVR / GMV / 时长 / 多样性 / 留存

| 指标 | 业务含义 | 短期优化方法 | 长期风险 | 工程含义 |
| :--- | :--- | :--- | :--- | :--- |
| **CTR** | 用户对 item 的兴趣度 | 提高相关性、点击率模型 | 用户疲劳、标题党 | 主排序模型最常用目标 |
| **CVR** | 兴趣→行动的转化率 | 全链路优化、详情页推荐 | 数据稀疏（SSB 问题） | ESMM 架构 |
| **GMV** | 电商成交总额 | CTR × CVR × Price | 客单价高的商品被持续推，用户疲劳 | 需要多目标联合建模 |
| **时长** | 用户停留时间 | 推荐更吸引人的内容 | 标题党 / 擦边球内容增多 | 内容推荐核心 KPI |
| **多样性** | 推荐结果覆盖范围 | MMR / DPP 重排 | 与相关性负相关 | 召回层 + 重排层 |
| **留存** | 次日 / 7 日 / 30 日回访 | 长期兴趣建模 | 短期不掉，长期不一定涨 | 留存模型 + 后验评估 |

### 30.4 多目标 Pareto 前沿分析

> 🎯 **核心心法**：多目标没有"全局最优"，只有"Pareto 最优"——在不牺牲一个目标的前提下，另一个目标不能继续提升。

```python
# 画 Pareto 前沿
import numpy as np
import matplotlib.pyplot as plt

# 不同模型 / 超参下的 (CTR, 时长) 组合
results = [
    ("baseline", 0.05, 120),
    ("MMoE", 0.055, 125),
    ("PLE", 0.058, 122),
    ("uncalibrated", 0.062, 110),  # CTR 高，时长掉了
]

for name, ctr, time in results:
    plt.scatter(ctr, time, label=name)
    plt.annotate(name, (ctr, time))

plt.xlabel("CTR")
plt.ylabel("时长(min)")
plt.title("多目标 Pareto 前沿")
plt.legend()
plt.show()
```

**判断**：在 Pareto 前沿上的模型都是"值得考虑"的；不在前沿上的模型（如 CTR=0.062 但时长=110）应该被淘汰。

### 30.5 反例：多任务学习失败的 5 种常见情况

| # | 失败模式 | 症状 | 根因 | 修复 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **跷跷板效应** | CTR 涨 1%，CVR 跌 2% | 任务负相关，Shared-Bottom 强行共享 | 改 MMoE 或 PLE |
| 2 | **主任务压制辅任务** | CTR 涨明显，CVR 完全不动 | Loss 量级差异（CTR: 0.5 vs CVR: 0.05） | Uncertainty Weighting |
| 3 | **Auxiliary 任务拖累主任务** | 加了"用户活跃度"作为辅助任务，主任务反而掉 | 辅助任务太弱，或与主任务负相关 | 删辅助任务，或换相关性高的 |
| 4 | **任务定义不清** | 离线涨了 0.5%，业务方说"GMV 涨得不多" | 离线指标 ≠ 业务指标 | 重新对齐指标定义 |
| 5 | **Pareto 退化** | 新模型 CTR 涨了，但时长、留存都掉 | 单一目标优化，没有 Pareto 约束 | 多目标加权 / 加 Pareto 正则 |

> 🎯 **核心心法**：多任务学习不是"加任务就好"，90% 的情况是任务越多越糟。先看 2 个任务能不能涨，再考虑加第 3 个。

## 31. 冷启动与长尾处理

> 📌 **一句话**：搜推广系统永远有 3 类冷启动——新用户、新物品、新场景。冷启动不是"小问题"，是"系统性问题"。长尾 item 占据 SKU 的 80% 以上，决定了系统的多样性上限。

### 31.1 冷启动 3 类方案

#### A. 数据增强（最少改动）

**核心**：在没有行为数据的情况下，用"侧信息"（side information）造数据。

```python
# 用户冷启动：用"相似用户"的行为当作自己的
class ColdStartUserModel(nn.Module):
    def forward(self, user_features, similar_users_behaviors):
        # user_features: 注册信息（年龄、性别、城市、设备）
        # similar_users_behaviors: K 个相似用户的行为序列

        user_embedding = self.user_tower(user_features)
        behavior_embedding = self.attention_pool(similar_users_behaviors)

        combined = user_embedding + behavior_embedding  # 残差式
        return combined

# 物品冷启动：用物品的属性 + 文本描述
class ColdStartItemModel(nn.Module):
    def forward(self, item_id, item_attrs, item_text_embedding):
        # item_attrs: 类目、品牌、价格
        # item_text_embedding: BERT 编码的标题

        attr_vec = self.attr_mlp(item_attrs)
        text_vec = item_text_embedding

        # 物品 id embedding 在冷启动时不可用，只能 fallback
        return self.fusion_layer([attr_vec, text_vec])
```

#### B. 特征迁移（最常用）

**核心**：把热门 item / 老用户学到的知识，迁移到冷启动 item / 新用户。

```text
热门物品 ──→ 学到"商品知识" ──→ 迁移 ──→ 冷启动物品
活跃用户 ──→ 学到"用户兴趣" ──→ 迁移 ──→ 新用户

迁移方式:
  ① 共享 Embedding（热门和冷启动共享底层表示）
  ② 知识图谱（KGAT / KGIN）
  ③ Meta-learning（MAML 思路，参见 §31.4）
```

#### C. 模型架构（最彻底）

**核心**：设计专门的冷启动分支，绕过"必须有行为数据"的限制。

```text
推荐系统架构:
  ┌──────────────────────────────────────────┐
  │ 输入：用户 / 物品                          │
  └──────────────┬───────────────────────────┘
                 │
                 ▼
  ┌──────────────────────────────────────────┐
  │ 判断：是否冷启动？                          │
  └─────┬──────────────────────────┬─────────┘
        │ 是                        │ 否
        ▼                          ▼
  ┌────────────┐            ┌────────────┐
  │ 冷启动分支 │            │ 常规分支    │
  │ (side info)│            │ (行为序列)  │
  └─────┬──────┘            └─────┬──────┘
        │                         │
        └──────────┬──────────────┘
                   ▼
            ┌────────────┐
            │ 统一打分    │
            └────────────┘
```

### 31.2 长尾 Item 推荐的 5 种方法

#### 方法 1：重排序（DPP / MMR）

**Diversity-Enhanced Rerank**：在精排后用 DPP（Determinantal Point Process）或 MMR（Maximal Marginal Relevance）增加多样性。

```python
def mmr_rerank(candidates, top_k=10, lambda_param=0.5):
    selected = []
    while len(selected) < top_k:
        best_score = -inf
        best_item = None
        for item in candidates:
            if item in selected:
                continue
            relevance = item.predicted_score
            redundancy = max([sim(item, s) for s in selected], default=0)
            score = lambda_param * relevance - (1 - lambda_param) * redundancy
            if score > best_score:
                best_score = score
                best_item = item
        selected.append(best_item)
    return selected
```

#### 方法 2：探索策略（E&E 介入）

```python
# 在精排分上加一个"探索 bonus"
final_score = relevance_score + epsilon * exploration_bonus(item)
# exploration_bonus 可以是：item 被推的次数的倒数（推得越少，bonus 越大）
```

#### 方法 3：知识图谱（KGAT / KGIN）

**核心**：用 KG 推理出"长尾 item 与用户的隐式联系"。

```text
用户 A ──→ 点击过 ──→ iPhone 15 ──→ 品牌 ──→ Apple
                                          │
                                          ├──→ MacBook（长尾 item，用户没买过）
                                          ├──→ AirPods
                                          └──→ iPad
```

#### 方法 4：预训练 Embedding（LLM / 多模态）

**核心**：用 LLM / 多模态模型给所有 item 生成"语义 Embedding"，长尾 item 也能有高质量表示。

```python
# 用 GPT-4 / CLIP / 多模态模型给物品生成 embedding
item_embedding = clip_model.encode(image=item.image, text=item.title)

# 长尾 item 即使没有行为数据，也能基于内容相似度被推荐
similar_items = faiss_index.search(item_embedding, k=100)
```

#### 方法 5：强化学习（LinUCB / Contextual Bandit）

**核心**：把"推荐长尾 item"看作一个 Bandit 问题，主动探索。

```python
# LinUCB 的核心思想
class LinUCB:
    def __init__(self, alpha=1.0):
        self.A = np.eye(d)  # d x d
        self.b = np.zeros(d)

    def select_arm(self, context_features_per_arm):
        # 每个 item 当作一个 arm
        scores = []
        for arm in arms:
            A_inv = np.linalg.inv(arm.A)
            theta = A_inv @ arm.b
            ucb = theta @ arm.context + alpha * np.sqrt(arm.context @ A_inv @ arm.context)
            scores.append(ucb)
        return np.argmax(scores)
```

### 31.3 新用户 / 新物品 / 新场景的差异化处理

| 冷启动类型 | 数据稀缺度 | 主要策略 | 关键指标 | 常见失败 |
| :--- | :--- | :--- | :--- | :--- |
| **新用户** | 极高（无行为） | 注册信息 + 热门兜底 + 兴趣试探 | 次日留存 | 兴趣试探太激进（推的内容吓跑用户） |
| **新物品** | 高（无曝光无点击） | 内容 Embedding + 知识图谱 + 流量倾斜 | CTR / CVR | 流量倾斜太少（陷入"无曝光 → 无数据 → 无曝光"） |
| **新场景** | 中（新场景无历史，但用户和物品可能已知） | 跨场景迁移学习 | 场景渗透率 | 迁移学习负迁移（场景差异大，硬迁移伤主场景） |

### 31.4 Few-shot Learning / Meta-learning

#### MAML 思想在推荐中的应用

**核心**：学习一个"如何快速适应新任务"的初始化参数。

```python
# 推荐冷启动场景：
# Task = "给一个新用户做推荐"
# Support set = 这个新用户的前 3 次点击
# Query set = 这个新用户的后续曝光

# MAML 训练：在大量"新用户"任务上预训练，
# 让模型参数处于"快速 fine-tune 几次就能适应"的状态

for user_batch in meta_train_users:
    # 模拟新用户：只用前 K 次行为
    support = user_batch[:K]
    query = user_batch[K:]

    # 内循环：快速 fine-tune
    adapted_params = fast_adapt(model, support)

    # 外循环：在 query 上评估，反传更新 meta 参数
    meta_loss = compute_loss(adapted_params, query)
    meta_optimizer.zero_grad()
    meta_loss.backward()
    meta_optimizer.step()
```

#### Prototypical Networks 在推荐中的应用

**核心**：每个 item 学一个"原型向量"，新 item 用"相似物品的原型"插值。

```python
# 新物品的 embedding = K 个最相似物品的 embedding 加权平均
def cold_start_item_embedding(new_item, item_db):
    similar_items = find_top_k_similar(new_item, item_db, k=10)
    weights = softmax([sim(new_item, item) for item in similar_items])
    embedding = sum(w * item.embedding for w, item in zip(weights, similar_items))

```

### 31.5 反例：冷启动方案的常见失败模式

| # | 失败模式 | 症状 | 根因 | 修复 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **内容 Embedding 过度依赖** | 推的内容都长得很像 | 只用内容相似度，没有行为信号 | 加探索 + 用户反馈 |
| 2 | **冷启动分支拖累主分支** | 加了冷启动分支后，整体 AUC 反而掉 | 两个分支的输出没有正确融合 | 加门控（gate）机制 |
| 3 | **流量倾斜过度** | 给新物品 50% 流量，主指标掉 5% | 探索太激进 | 用 UCB / Thompson 渐进式探索 |
| 4 | **Meta-learning 难训练** | 离线涨 0.2%，在线没效果 | Meta 任务和真实任务分布差异大 | 让 meta 任务尽量贴近真实分布 |
| 5 | **侧信息用错** | 用"用户手机型号"做侧信息推"高端商品"，反而推错 | 侧信息和推荐目标相关性弱 | 重新筛选侧信息，加注意力 |

## 32. 探索与利用（E&E）

> 📌 **一句话**：E&E 是搜推广的"长期主义 vs 短期主义"问题。纯利用让你 1 个月见顶，纯探索让你 1 周掉 10%。平衡点需要精细调控。

### 32.1 E&E 问题的本质

```text
利用（Exploitation）：
  根据已有数据，选 CTR 最高的 item 推给用户。
  优点：短期收益最大。
  缺点：长尾 item 永远没机会曝光 → 数据稀疏 → 越推越偏。

探索（Exploration）：
  主动推一些"不确定但可能有价值"的 item。
  优点：发现新偏好，缓解马太效应。
  缺点：短期可能掉指标。

核心矛盾：
  - 探索太少 → 系统自我封闭
  - 探索太多 → 用户体验差
  - 平衡点 → 长期收益最大化
```

### 32.2 Bandit 四大算法

#### A. ε-greedy（最简单）

```python
def epsilon_greedy(item_scores, epsilon=0.1):
    if random.random() < epsilon:
        return random.choice(item_scores)  # 探索
    else:
        return max(item_scores, key=lambda x: x.score)  # 利用
```

**优点**：1 行代码就能写出来。
**缺点**：探索是"随机"的，不聪明；ε 难调。

#### B. UCB（Upper Confidence Bound）

```python
def ucb(item_rewards, item_counts, total_count):
    scores = []
    for item, rewards, count in zip(items, item_rewards, item_counts):
        if count == 0:
            return item  # 还没探索过的优先
        mean_reward = sum(rewards) / count
        confidence = math.sqrt(2 * math.log(total_count) / count)
        ucb_score = mean_reward + confidence  # 上界
        scores.append((item, ucb_score))
    return max(scores, key=lambda x: x[1])[0]
```

**核心**：被推得少的 item，置信区间宽，UCB 分高 → 自然被多推。
**优点**：理论保证（regret bound O(√T log T)）。
**缺点**：每个 item 必须有特征（context）。

#### C. Thompson Sampling

```python
def thompson_sampling(item_prior_alpha, item_prior_beta):
    # 每个 item 的 CTR 服从 Beta(α, β) 分布
    # 从后验采样一次，按采样值排序
    sampled_scores = []
    for item, alpha, beta in zip(items, item_prior_alpha, item_prior_beta):
        sample = np.random.beta(alpha, beta)
        sampled_scores.append((item, sample))
    return max(sampled_scores, key=lambda x: x[1])[0]

# 在线更新
def update(item, clicked):
    if clicked:
        item.prior_alpha[item] += 1
    else:
        item.prior_beta[item] += 1
```

**核心**：从后验分布采样，采样值高就推。
**优点**：天然支持概率性探索，效果通常比 UCB 好。
**缺点**：需要维护每个 item 的 α, β（空间开销）。

#### D. LinUCB（Contextual Bandit）

```python
class LinUCB:
    def __init__(self, d, alpha=1.0):
        self.d = d  # 特征维度
        self.alpha = alpha

    def select(self, arms_contexts):
        # 每个 arm 有自己的 (A, b)
        scores = []
        for arm, context in zip(arms, arms_contexts):
            A_inv = np.linalg.inv(arm.A)
            theta = A_inv @ arm.b
            p = theta @ context + self.alpha * np.sqrt(context @ A_inv @ context)
            scores.append((arm, p))
        return max(scores, key=lambda x: x[1])[0]

    def update(self, arm, context, reward):
        arm.A += np.outer(context, context)
        arm.b += reward * context
```

**核心**：每个 arm 维护一个岭回归模型，结合了 UCB 和个性化。
**适用**：新用户冷启动 / 新物品冷启动。

### 32.3 强化学习在推荐中的应用

> **核心区别**：Bandit 是"单步决策"（推一次 → 看一次反馈），RL 是"序列决策"（推一次 → 用户离开 → 整个 session 失败）。

| 算法 | 类型 | 适用场景 | 推荐系统应用 |
| :--- | :--- | :--- | :--- |
| **DQN** | Value-based | 离散动作 | 离散类目推荐 |
| **DDPG** | Actor-Critic | 连续动作 | 连续分数调整 |
| **PPO** | Policy-based | 通用、稳定 | 多目标加权策略 |
| **SAC** | Actor-Critic | 最大熵、探索友好 | 长期探索 |

#### 推荐系统中的 RL 框架

```python
# 推荐看作一个 MDP:
# State: 用户历史行为 + 上下文
# Action: 推荐结果列表
# Reward: 点击 + 长期价值

class RecEnv:
    def step(self, action):
        # action 是推荐列表
        user_click = simulate_user_click(action)
        reward = compute_reward(user_click, user.long_term_value)
        next_state = update_user_state(user, action, user_click)
        done = user.leaves or len(session) >= max_len
        return next_state, reward, done
```

**关键挑战**：
- **奖励稀疏**：用户可能看了 10 个 item 都不点
- **环境模拟难**：用户行为难以精确建模
- **稳定性差**：RL 在推荐中容易震荡

### 32.4 Contextual Bandit / Off-Policy Correction

#### Off-Policy Correction 核心

**问题**：用历史数据训练 Bandit，但历史数据是"旧策略"产生的，存在分布差异。

**解法**：
```python
# IPS（Inverse Propensity Scoring）核心思想
# 给"旧策略推过的样本"加权，让它看起来像"新策略的样本"

def ips_loss(new_policy_scores, old_policy_probs, new_policy_probs, rewards):
    importance_ratio = new_policy_probs / old_policy_probs  # 重要性权重
    weighted_reward = importance_ratio * rewards
    loss = -torch.mean(weighted_reward * torch.log(new_policy_scores))
    return loss

# SNIPS（Self-Normalized IPS）：加权归一化，更稳定
def snips_loss(new_policy_scores, old_policy_probs, new_policy_probs, rewards):
    importance_ratio = new_policy_probs / old_policy_probs
    numerator = torch.sum(importance_ratio * rewards * torch.log(new_policy_scores))
    denominator = torch.sum(importance_ratio)
    return -numerator / (denominator + 1e-8)
```

### 32.5 Diversity / Serendipity / Novelty 三大指标

| 指标 | 定义 | 计算方式 | 业务价值 |
| :--- | :--- | :--- | :--- |
| **Diversity** | 推荐结果的多样性 | 类目 / 内容相似度的负值 | 缓解回音室，提升长期留存 |
| **Serendipity** | 推荐结果让人惊喜 | (点击且与历史不相似) 的比例 | 用户"哇塞"感，情感连接 |
| **Novelty** | 推荐结果的新颖度 | item 流行度的负值（推冷门） | 缓解马太，给长尾曝光 |

```python
def compute_diversity(recommended_list, item_db):
    sims = []
    for i, item_i in enumerate(recommended_list):
        for j, item_j in enumerate(recommended_list):
            if i < j:
                sims.append(item_db.similarity(item_i, item_j))
    return 1 - np.mean(sims)

def compute_serendipity(user_history, recommended_list, item_db):
    surprises = []
    for item in recommended_list:
        if item.clicked:
            # 与用户历史最相似的 item 的相似度
            max_sim = max([item_db.similarity(item, h) for h in user_history])
            # 相似度低 + 点击 = 惊喜
            surprise_score = (1 - max_sim) * item.click_label
            surprises.append(surprise_score)
    return np.mean(surprises) if surprises else 0

def compute_novelty(recommended_list, item_popularity):
    # item 的流行度（被推次数）
    novelty = 1 / (item_popularity + 1)
    return np.mean([novelty[item.id] for item in recommended_list])
```

### 32.6 反例：纯利用 vs 纯探索的失败

| 失败模式 | 表现 | 后果 | 修复 |
| :--- | :--- | :--- | :--- |
| **纯利用** | 永远推 CTR Top 10 的 item | 长尾 item 饿死 → 系统多样性崩塌 → 用户疲劳 → 长期留存掉 | 加 ε-greedy 或 UCB |
| **纯探索** | 5% 流量随机推 | 主指标掉 8%，业务方拍桌子 | 用 Thompson Sampling 自动平衡 |
| **Bandit 收敛慢** | 新算法上线 1 个月还在"探索" | 业务方看不到收益 | 加先验（用热门 item 作为 warm-start） |
| **RL 训练不稳** | 不同 seed 结果差异巨大 | 无法上生产 | 用 PPO（最稳定），多次实验取平均 |

> 🎯 **核心心法**：E&E 不是"加一个 ε 就行"，是"探索预算如何在长期分配"。建议的入门配方：精排分 × 0.95 + 探索 bonus × 0.05。

## 33. 因果推断与去偏

> 📌 **一句话**：搜推广系统是"被你的推荐结果污染过的数据"训练出来的。学的是相关性，不是因果性。要去偏，必须引入因果推断工具。

### 33.1 因果图（Causal DAG）方法

```text
搜推广系统因果图（典型）:

用户兴趣 (U) ──→ 点击 (C) ──→ 转化 (Y)
  │              ↑
  │              │
  └──→ 曝光 (E) ─┘

推荐系统 (R) ──→ 曝光 (E)

混杂因子（Confounder）:
  - 时间（白天 vs 晚上点击率差异）
  - 位置（位置 1 天然点击率高）
  - 用户活跃度（活跃用户更可能点击）
```

**核心问题**：
- 你观察到"item A 在第 1 位的 CTR = 15%"，但这是因为"位置 1"而不是"item A"。
- 直接学 → 位置偏差被放大。
- 想去掉位置影响 → 因果推断。

### 33.2 Do-calculus 与反事实推断

#### Do-operator vs See-operator

```text
P(C | item=A, position=1)  ← "see"：观察到 item A 在位置 1 的点击率（混杂）
P(C | do(item=A), position=1)  ← "do"：强制把 item A 放到位置 1（干预）
```

**核心**：
- "See" 是观察：你看到的世界
- "Do" 是干预：如果你强制改变，会怎样
- **反事实**：如果当时没推 item A，推了 item B，会怎样？

#### Backdoor Adjustment（后门调整）

```python
# 想估计 "推 item A 的因果效应"
# 后门路径: A ← U → C （U 是混杂因子）
# 调整: P(C | do(A)) = Σ_u P(C | A, U=u) * P(U=u)

def causal_effect(item_A, user_features):
    total_effect = 0
    for user_segment in user_features.segments:
        # 在每个用户群体内估计条件概率
        p_click = p(click | item_A, user_segment)
        p_segment = p(user_segment)
        total_effect += p_click * p_segment
    return total_effect
```

### 33.3 IPS / Doubly Robust / SNIPS / DR 在推荐中的应用

| 方法 | 公式 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **IPS** | $\hat{V}_{IPS} = \frac{1}{n}\sum_i \frac{\pi_e(x_i)}{\pi_b(x_i)} r_i$ | 无偏估计 | 倾向性得分难估准，方差大 | 有随机化日志 |
| **SNIPS** | $\hat{V}_{SNIPS} = \frac{\sum_i w_i r_i}{\sum_i w_i}$ | 自归一化，更稳定 | 仍然依赖倾向性 | IPS 改进版（推荐） |
| **DR** | $\hat{V}_{DR} = \hat{V}_{DM} + (\hat{V}_{IPS} - \hat{V}_{DM-model})$ | 双鲁棒（任一估计无偏就无偏） | 实现复杂 | 工业级（推荐） |
| **DR with Clipping** | 加权截断防止极端权重 | 进一步降方差 | 引入偏差 | SNIPS 不够稳时 |

```python
# DR (Doubly Robust) 实现
def doubly_robust_estimate(policy_new, policy_old, rewards, predicted_rewards):
    """
    policy_new: 新策略对每个样本的倾向性
    policy_old: 旧策略对每个样本的倾向性（从日志得到）
    rewards: 实际观测到的奖励
    predicted_rewards: 直接方法预测的奖励
    """
    importance_ratio = policy_new / (policy_old + 1e-8)

    # DM 部分：直接方法
    dm_part = predicted_rewards.mean()

    # IPS 部分：加权
    ips_part = (importance_ratio * (rewards - predicted_rewards)).mean()

    # DR
    dr_estimate = dm_part + ips_part
    return dr_estimate
```

### 33.4 Counterfactual Evaluation

**核心**：用历史日志估计"如果当时用了新策略，会怎样"。

```python
# 反事实评估 pipeline
def counterfactual_evaluation(new_policy, historical_logs):
    estimated_rewards = []
    for log in historical_logs:
        # log 包含：context, action_old, reward_old, propensity_old

        # 1. 新策略在相同 context 下会推什么？
        action_new = new_policy.select(log.context)

        # 2. 新策略推这个 action 的概率
        propensity_new = new_policy.get_propensity(log.context, action_new)

        # 3. IPS 加权
        weight = propensity_new / (log.propensity_old + 1e-8)
        estimated_rewards.append(weight * log.reward_old)

    return np.mean(estimated_rewards)
```

**关键**：必须满足"新策略的倾向性 > 0"（否则那个 action 从未被旧策略推过，无法评估）。

### 33.5 长期效应 vs 短期效应

**最隐蔽的偏差**：模型优化了短期 CTR，长期留存可能掉。

```text
优化 CTR 的 3 个月:
  月 1: CTR +2%（推荐更吸引眼球的内容）
  月 2: CTR +1%（用户开始有点审美疲劳）
  月 3: CTR +0.5%（但留存掉了 -3%）

根因: 短期指标和长期指标不一致
解法:
  ① 多目标建模（短期 + 长期）
  ② 后验评估（上线 7/30 天后才算真赢）
  ③ 留存模型作为辅助任务
```

### 33.6 反例：相关性 ≠ 因果性的常见陷阱

| # | 陷阱 | 现象 | 真实原因 | 修复 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **买花的人更长寿** | 推花给老人 | 买花的人更注重健康（混杂） | 加健康相关特征 |
| 2 | **刷得久 = 喜欢** | 把时长当兴趣信号 | 用户开页面没关（背景运行） | 用有效交互时长 |
| 3 | **热门 item CTR 高** | 把热门当相关 | 位置偏置 + 曝光充分 | 去位置偏差 |
| 4 | **新算法指标涨** | 上线后第一天涨 3% | 数据新鲜度（最近的数据天然好预测） | 留 7 天再下结论 |
| 5 | **A/B 实验互相干扰** | 两个实验同时跑，效果抵消 | 流量层冲突 | 实验分层管理（见 §38） |

> 🎯 **核心心法**：搜推广的 90% "相关性" 都是 "位置偏置 + 曝光充分 + 时机巧合"。要去偏，必须用因果工具。

## 34. Embedding 优化全套方案

> 📌 **一句话**：搜推广的 Embedding 是"内存怪兽"。10 亿 item × 64 维 float32 = 256GB。优化 Embedding 是工业级系统的必修课。

### 34.1 量化（Quantization）

#### A. 标量量化（Scalar Quantization）

```python
# 把 float32 映射到 int8
def quantize_scalar(embedding):
    min_val = embedding.min()
    max_val = embedding.max()
    scale = (max_val - min_val) / 255
    zero_point = -min_val / scale

    quantized = np.round(embedding / scale + zero_point).astype(np.uint8)
    return quantized, scale, zero_point

def dequantize_scalar(quantized, scale, zero_point):
    return (quantized.astype(np.float32) - zero_point) * scale

# 压缩比: 4x（float32 → int8）
# 精度损失: 通常 < 1% AUC 损失
```

#### B. Product Quantization (PQ)

```python
# 把 64 维向量切成 8 个 8 维子向量
# 每个子向量用 K-means 聚类到 256 个 centroids
# 存的是 centroids 的 index（1 字节），不是向量本身

def product_quantize(embedding, num_subspaces=8, num_centroids=256):
    sub_vectors = np.split(embedding, num_subspaces)
    codes = []
    for sub in sub_vectors:
        # K-means 找最近的 centroid
        distances = np.linalg.norm(centroids[subspace] - sub, axis=1)
        codes.append(np.argmin(distances))
    return np.array(codes, dtype=np.uint8)  # 8 字节

# 压缩比: 64*4 / 8 = 32x
# 精度损失: 2-5% Recall 损失
```

#### C. INT4 / 二值化（极致压缩）

```python
# INT4: 每个值用 4 bit 表示
def quantize_int4(embedding):
    # 16 个 level: -8, -7, ..., 7
    quantized = np.round(embedding * 15).clip(-8, 7).astype(np.int8)
    # pack 2 个 int4 到 1 字节
    packed = (quantized[::2] & 0xF) << 4 | (quantized[1::2] & 0xF)
    return packed

# 压缩比: 8x（float32 → int4）
# 精度损失: 5-10%，但存储极小，适合端侧

# 二值化（Binary Embedding）:
def binarize(embedding):
    return (embedding > 0).astype(np.uint8)  # 1 bit per dim

# 压缩比: 32x
# 精度损失: 10-15%，但可以用 Hamming 距离快速计算
```

### 34.2 哈希（Hash Trick）

**核心**：把超高维稀疏特征映射到低维 Embedding。

```python
# 经典 Hash Trick
def hash_embedding(feature_id, embedding_dim=64):
    # 用 MurmurHash 或类似哈希函数
    h1 = mmh3.hash(str(feature_id), seed=1) % embedding_dim
    h2 = mmh3.hash(str(feature_id), seed=2) % embedding_dim
    return h1, h2

# 双 Hash（解决冲突）
class DoubleHashEmbedding:
    def __init__(self, dim=64):
        self.embedding = np.zeros((2, dim))  # 2 个独立 embedding

    def forward(self, feature_id):
        h1 = mmh3.hash(str(feature_id), seed=1) % 64
        h2 = mmh3.hash(str(feature_id), seed=2) % 64
        return self.embedding[0, h1] + self.embedding[1, h2]
```

| 哈希方案 | 冲突率 | 适用场景 |
| :--- | :--- | :--- |
| 单 Hash | 高（高维稀疏下冲突严重） | 低维 embedding（dim ≤ 64） |
| 双 Hash | 低（叠加缓解冲突） | 中等维度 |
| 复合 Hash | 极低 | 极高维稀疏（如用户 ID 拼接） |

### 34.3 检索：HNSW / IVF / Faiss / ScaNN / Milvus

#### HNSW（Hierarchical Navigable Small World）

```text
核心思想：
  构建多层图，每层是稀疏的"高速公路"，底层是稠密的"街道"
  查询时：从顶层快速定位 → 下到底层精确找

时间复杂度: O(log N)
召回率: 95%+
内存开销: 大（需要存图）
```

#### IVF（Inverted File Index）

```text
核心思想：
  K-means 把所有向量聚成 K 类
  查询时：先找到最近的几个 cluster → 在 cluster 内做精确 KNN

时间复杂度: O(N/K)  # 比全量快 K 倍
召回率: 80-90%（取决于 probe 的 cluster 数）
内存开销: 中
```

### 34.4 Embedding 爆炸问题

**场景**：10 亿 item × 64 维 float32 = 256GB，但单机内存可能只有 256GB。

**5 大方案**：

| 方案 | 压缩比 | 精度损失 | 实现复杂度 |
| :--- | :--- | :--- | :--- |
| **INT8 量化** | 4x | < 1% | 低 |
| **PQ 量化** | 16-32x | 2-5% | 中 |
| **二值化** | 32x | 10-15% | 低 |
| **分布式分片** | 1x（但分到多机） | 0% | 高 |
| **冷热分层**（热门在内存，长尾在 SSD） | 5-10x | < 2% | 高 |

```python
# 冷热分层示例
class TieredEmbedding:
    def __init__(self):
        self.hot_embedding = load_in_memory("hot_items.bin")  # 内存
        self.cold_embedding = load_on_disk("cold_items.bin")  # SSD

    def forward(self, item_id):
        if item_id in self.hot_embedding:
            return self.hot_embedding[item_id]
        else:
            # miss → 从 SSD 加载
            return self.cold_embedding[item_id]
```

### 34.5 端侧 Embedding 压缩

**场景**：手机端 / IoT 端 Embedding 受限（内存、带宽、电量）。

**方案**：

1. **联合压缩**：训练时就考虑量化（如 DoReFa、HAQ）
2. **混合精度**：重要维度用 INT8，次要维度用 INT4
3. **端云协同**：粗排在端侧（用小 Embedding），精排在云端（用大 Embedding）

```python
# 端云协同示例
class EdgeCloudRec:
    def forward(self, user_ctx):
        # 端侧：用小 Embedding（INT4）粗排
        candidates = edge_rerank(user_ctx, top_k=50)
        # 云端：上传 50 个候选 item id
        # 云端用大 Embedding（float32）精排
        final_scores = cloud_rerank(user_ctx, candidates)
        return final_scores
```

### 34.6 反例：Embedding 优化的常见错误

| # | 错误 | 后果 | 修复 |
| :--- | :--- | :--- | :--- |
| 1 | **量化后没重新评估** | INT8 后线上 CTR 掉了 3% | 必须做 AB 实验 |
| 2 | **IVF 的 nprobe 设太小** | 召回率只有 70% | 根据 recall-precision 曲线选 |
| 3 | **Hash 冲突导致相似 item 撞 Embedding** | 不相关 item 被推荐到一起 | 用双 Hash 或调大 dim |
| 4 | **冷热分层数据不一致** | 冷数据更新后线上看不到 | 严格的数据同步协议 |
| 5 | **端侧过度压缩** | 用户端体验明显差 | 端云分级，端侧保精度 |

## 35. 实时性与在线学习

> 📌 **一句话**：搜推广对实时性的要求是"分钟级可用新数据"。传统 T+1 训练在某些场景（如热点新闻、短视频）已经过时。

### 35.1 在线学习的本质

**传统 ML Pipeline**：收集数据 → 训练 → 上线（周期：天/小时）
**在线学习 Pipeline**：数据流式进来 → 模型实时更新（周期：秒/分钟）

```python
# FTRL（Follow The Regularized Leader）— 在线学习经典算法
def ftrl_update(weight, gradient, lambda1, lambda2, alpha, beta):
    """
    在线学习，参数 w_t 每次根据累积梯度更新
    """
    accumulated_grad += gradient
    accumulated_squared_grad += gradient ** 2

    sigma = (sqrt(accumulated_squared_grad) - sqrt(accumulated_squared_grad - gradient**2)) / alpha
    z = accumulated_grad - sigma * weight

    # L1 截断
    if abs(z) <= lambda1:
        new_weight = 0
    else:
        new_weight = -(z - sign(z) * lambda1) / (lambda2 + (beta + sqrt(accumulated_squared_grad)) / alpha)

    return new_weight

# Online SGD：最简单
for batch in stream:
    gradient = compute_gradient(model, batch)
    model.weights -= learning_rate * gradient
```

### 35.5 概念漂移（Concept Drift）检测

> **问题**：用户兴趣会随时间变化（季节、热点、生命周期），老模型的预测能力会下降。

```python
# 漂移检测方法 1：滑动窗口 AUC
def detect_drift_auc(model, recent_window=10000, threshold=0.02):
    recent_auc = compute_auc(model, recent_window)
    baseline_auc = compute_auc(model, recent_window * 5)  # 历史

    if baseline_auc - recent_auc > threshold:
        return "DRIFT_DETECTED"
    return "NORMAL"

# 漂移检测方法 2：特征分布对比
def detect_drift_psi(feature, recent_data, baseline_data, threshold=0.1):
    """PSI (Population Stability Index)"""
    recent_dist = compute_distribution(recent_data)
    baseline_dist = compute_distribution(baseline_data)

    psi = sum((recent_dist[i] - baseline_dist[i]) *
              log(recent_dist[i] / baseline_dist[i])
              for i in range(len(recent_dist)))

    return psi > threshold
```

| PSI 值 | 含义 |
| :--- | :--- |
| < 0.1 | 稳定 |
| 0.1 ~ 0.25 | 轻微漂移 |
| > 0.25 | 严重漂移，需要干预 |

## 36. 反馈循环与位置偏差

> 📌 **一句话**：搜推广系统的所有"看似自然"的偏差，几乎都是反馈循环的产物。能识别并打破反馈循环，是 P7 的核心能力。

### 36.1 Position Bias 建模（PAL / IPW / DLA）

详见 §29.4，此处补充工程化细节。

#### 工业级 PAL 实现

```python
class PositionAwareModel(nn.Module):
    def __init__(self, num_positions, embedding_dim):
        super().__init__()
        self.position_embedding = nn.Embedding(num_positions, embedding_dim)
        self.user_item_tower = UserItemTower(embedding_dim)

    def forward(self, user_feat, item_feat, position):
        base_score = self.user_item_tower(user_feat, item_feat)
        pos_emb = self.position_embedding(position)

        # 位置对 item 的影响建模为"加成"
        position_adjustment = self.position_mlp(torch.cat([
            base_score.unsqueeze(-1), pos_emb
        ], dim=-1))

        return base_score + position_adjustment

    def predict_unbiased(self, user_feat, item_feat):
        """推理时：枚举所有可能位置，取期望"""
        scores = []
        for pos in range(self.num_positions):
            scores.append(self.forward(user_feat, item_feat, position=pos))
        # 期望 = 平均（不同位置的中性化分数）
        return torch.stack(scores).mean(dim=0)
```

### 36.2 Selection Bias / Exposure Bias / Conformity Bias

| 偏差 | 定义 | 来源 | 影响 |
| :--- | :--- | :--- | :--- |
| **Selection Bias** | 训练数据只包含"被推荐系统选中的 item" | 反馈循环 | 模型学不到未曝光 item 的偏好 |
| **Exposure Bias** | 用户只对"曝光过"的 item 有反馈 | 系统选择 | 长尾 item 永远没数据 |
| **Conformity Bias** | 用户点击热门是因为从众，不是因为真的喜欢 | 社会效应 | 热门 item 的 CTR 被高估 |
| **Position Bias** | 位置靠前的天然 CTR 高 | UI 设计 | 模型学到"位置"而非"item" |

### 36.3 Feedback Loop 放大的 4 种机制

```text
┌─────────────────────────────────────────┐
│  反馈循环放大机制（4 种）                │
├─────────────────────────────────────────┤
│  ① 回音室效应（Echo Chamber）            │
│     用户只看一类内容 → 兴趣变窄           │
│     → 模型认为用户只喜欢这一类            │
│     → 推荐更窄 → 兴趣更窄                │
│                                         │
│  ② 马太效应（Matthew Effect）            │
│     热门 item 获得更多曝光               │
│     → 更多点击 → 数据更多                │
│     → 模型认为热门更好 → 更多曝光         │
│                                         │
│  ③ 流量倾斜（Traffic Concentration）     │
│     5% 的 item 拿走 80% 流量             │
│     → 长尾饿死 → 长尾越来越冷             │
│                                         │
│  ④ 数据污染（Data Contamination）        │
│     上一轮的错误推荐 → 用户错误点击        │
│     → 进入训练数据 → 模型学错             │
└─────────────────────────────────────────┘
```

### 36.4 离线评估的去偏方法

```python
# 反事实评估：估计"如果当时推的是 B 而不是 A"
def counterfactual_evaluation(log_data, new_policy, position_propensity):
    estimates = []
    for log in log_data:
        # log: context, item_A, label_click_A, position_A

        # 1. 计算新策略在相同 context 下推 item_A 的概率
        p_new = new_policy.get_propensity(log.context, log.item_A)

        # 2. 计算旧策略推 item_A 的概率（位置倾向性）
        p_old = position_propensity[log.position_A]

        # 3. IPS 加权
        weight = p_new / (p_old + 1e-8)
        estimates.append(weight * log.label_click_A)

    return np.mean(estimates)

# 双重稳健（DR）评估（更鲁棒）
def doubly_robust_evaluation(log_data, new_policy, old_propensity, base_model):
    estimates = []
    for log in log_data:
        # DM 部分：基础模型的预测
        dm_pred = base_model.predict(log.context, log.item_A)

        # IPS 部分
        p_new = new_policy.get_propensity(log.context, log.item_A)
        p_old = old_propensity[log.position_A]
        ips_weight = p_new / (p_old + 1e-8)

        # DR 组合
        dr_estimate = dm_pred + ips_weight * (log.label_click_A - dm_pred)
        estimates.append(dr_estimate)

    return np.mean(estimates)
```

### 36.5 长期 vs 短期效应

| 维度 | 短期指标 | 长期指标 |
| :--- | :--- | :--- |
| 时间范围 | 7 天内 | 30 / 90 / 180 天 |
| 典型指标 | CTR / CVR / 时长 | 留存 / LTV / 复购率 |
| 优化难度 | 容易（数据充足） | 难（数据稀疏） |
| 业务方关注 | 直接业务侧 | 战略层 |

**关键决策**：搜推广算法优化的"上限"是长期指标，下限是短期指标。只看短期 → 系统会塌缩；只看长期 → 业务方等不及。

## 37. 端到端生成式推荐

> 📌 **一句话**：2024-2025 是搜推广"端到端生成式"的元年。从召回 → 粗排 → 精排 → 重排的多阶段架构，被 OneRec / HSTU / MTGR 等模型挑战。

### 37.1 LLM4Rec 三大层级

| 层级 | 代表模型 | 思路 | 工业可用性 |

### 37.2 端到端生成式 vs 传统两阶段

```text
传统架构:
  召回 (亿级 → 千级)
    ↓
  粗排 (千级 → 百级)
    ↓
  精排 (百级 → 十级)
    ↓
  重排 (十级 → 最终)

  问题: 多阶段信息丢失 + 工程复杂

端到端架构:
  用户行为序列 → Transformer → Top-K 推荐

  优势: 信息无损 + 工程简化
  挑战: 推理慢 + 难以 debug
```

### 37.3 OneRec / OneSearch / HSTU / MTGR 范式

#### HSTU (Hierarchical Sequential Transduction Unit)

**Meta 2024** 提出，用于短视频推荐：

```python
class HSTU(nn.Module):
    def __init__(self, d, num_heads):
        super().__init__()
        self.attention = HSTUAttention(d, num_heads)  # 替代 Softmax Attention
        self.ffn = PointwiseFFN(d)

    def forward(self, sequence):
        # 序列：用户历史行为 [clicked_items, watched_videos, ...]
        x = self.attention(sequence)
        x = self.ffn(x)
        return x

# 核心创新: 把 Attention 改造为"排序敏感"
# 传统 Softmax: 输出概率分布
# HSTU: 输出加权 sum，保留原始排序信号
```

#### OneRec (KuaiShou 2024)

**核心**：单阶段生成式推荐，把召回+粗排+精排合一。

```text
OneRec 架构:
  输入: 用户行为序列 + 上下文
  Encoder: Transformer 编码用户兴趣
  Decoder: 生成 item id（用 Semantic ID）
  输出: Top-K item id（直接给用户）
```

#### MTGR (Multi-Task Generative Recommendation)

**核心**：一个生成式模型同时做 CTR / CVR / 时长预估。

### 37.4 Semantic ID（RQ-VAE）体系

**核心问题**：item id 是离散的（如 10 亿 item），Transformer 难以直接生成。

**RQ-VAE 解决方案**：
```python
# 用 RQ-VAE 把 item 编码成语义 ID（如 "A12-B45-C78"）
class RQVAE(nn.Module):
    def forward(self, item_embedding):
        # 1. VAE 编码
        z = self.encoder(item_embedding)

        # 2. 残差量化（多级 codebook）
        codes = []
        residual = z
        for codebook in self.codebooks:
            # 找最近的 code
            code_idx = nearest_neighbor(residual, codebook)
            codes.append(code_idx)
            residual = residual - codebook[code_idx]

        # codes 如 [12, 45, 78] → 语义 ID "12-45-78"
        return codes

# Transformer 就可以直接生成 codes
# codes → 解码回 item embedding → 找最近 item
```

**优势**：
- 语义相近的 item 共享前缀 → 推荐有连贯性
- 离散 codes 便于 Transformer 生成
- 冷启动友好（新 item 也能编码）

### 37.5 推理优化：KV Cache / Paged Attention / Prefix Caching / Speculative Decoding

#### KV Cache

```python
# Transformer 自回归生成时缓存 K/V
class GenerationWithKVCache:
    def __init__(self):
        self.kv_cache = {}

    def forward(self, input_ids, position):
        # 第一次: 全量计算
        if position == 0:
            output = full_forward(input_ids)
            self.kv_cache = output.kv
        # 后续: 只算新增 token，复用 cache
        else:
            new_input = input_ids[:, -1:]
            output = step_forward(new_input, self.kv_cache)
            self.kv_cache.update(output.new_kv)
        return output
```

#### Paged Attention（vLLM 核心）

**问题**：KV cache 内存碎片化（不同请求长度不同）。
**解法**：像操作系统虚拟内存一样分页管理。

```python
# vLLM 的 PagedAttention
# 每个请求的 KV cache 分成固定大小的"页"
# 页表管理映射关系
# 推理时按需加载页，内存利用率从 30% → 90%
```

#### Prefix Caching

```python
# 多个请求共享相同前缀（如 system prompt）
# 第一次请求算 prefix 的 KV，缓存
# 后续请求直接复用
prefix_kv = compute_kv(system_prompt)
for user_request in requests:
    # user_request: system_prompt + user_input
    # system_prompt 的 KV 直接复用
    output = generate(user_request, kv_cache=prefix_kv + new_kv(user_input))
```

#### Speculative Decoding

```python
# 用小模型草拟 N 个 token，大模型并行验证
small_draft = small_model.generate(input_ids, n=5)
big_verified = big_model.verify(input_ids + small_draft)
# 接受 big_verified 中正确的部分，拒绝并重新生成
# 提速 2-3x
```

```python
class MambaBlock(nn.Module):
```

### 38.2 A/B 测试的严谨性（详化版）

#### A/B 测试 5 大陷阱

| 陷阱 | 描述 | 修复 |
| :--- | :--- | :--- |
| **样本量不足** | 跑 1 天就下结论 | 用 power analysis 算最小样本量 |
| **时间窗口错** | 周一跑实验（流量异常） | 至少覆盖 1 个完整自然周 |
| **辛普森悖论** | 整体涨，分群跌 | 按用户群分桶看 |
| **AA 测试缺失** | 没有对照确认基线稳定 | 上实验前先跑 1-3 天 AA |
| **多重比较** | 同时跑 10 个实验，假阳 | Bonferroni 校正或分层 |

#### 工业级 A/B 测试框架

```python
class ABTestFramework:
    def __init__(self, num_buckets=100):
        self.num_buckets = num_buckets

    def assign_bucket(self, user_id):
        """通过 user_id 哈希分桶，确保同一用户始终在同一桶"""
        return hash(user_id) % self.num_buckets

    def is_in_experiment(self, user_id, experiment_config):
        bucket = self.assign_bucket(user_id)
        return experiment_config.bucket_start <= bucket < experiment_config.bucket_end

    def compute_significance(self, control_data, treatment_data):
        """计算 p-value 和置信区间"""
        from scipy import stats
        t_stat, p_value = stats.ttest_ind(control_data, treatment_data)

        # 置信区间
        diff = treatment_data.mean() - control_data.mean()
        se = np.sqrt(control_data.var()/len(control_data) + treatment_data.var()/len(treatment_data))
        ci_low = diff - 1.96 * se
        ci_high = diff + 1.96 * se

        return {
            'p_value': p_value,
            'significant': p_value < 0.05,
            'lift': diff / control_data.mean(),
            'ci': (ci_low, ci_high)
        }
```

### 38.4 灰度发布 / Rollback 机制

```python
class GradualRollout:
    def __init__(self, model_versions):
        self.model_versions = model_versions  # {'v1': 0.5, 'v2': 0.5}

    def ramp_up(self, new_version, target_ratio=1.0, step=0.1, interval='1d'):
        """渐进放量"""
        for ratio in np.arange(step, target_ratio + step, step):
            self.model_versions[new_version] = ratio
            # 其他版本按比例缩减
            self._rebalance()
            time.sleep(interval)  # 等待观察期

    def rollback(self, version):
        """回滚"""
        self.model_versions[version] = 0
        self._rebalance()
        # 自动通知相关人员
```

#### Q1: 推荐系统有哪些常见架构？

**3 分钟**：

#### Q2: DIN 的核心思想是什么？

**30 秒**：用 Attention 建模用户历史行为与候选 item 的相关性。

**3 分钟**：
- 传统 DNN 把用户历史行为做 sum pooling，所有历史等权。
- DIN 认为不同历史对当前 item 的重要性不同。
- 用 Attention：local activation weight = softmax(user_history × candidate_item)。
- 重要历史（如点击过同类商品）权重高。
- DIEN 进一步用 GRU 建模兴趣演化。

**5 分钟**：补充 DIN 的 attention 实现、训练 trick（自适应正则）、工业部署经验。

#### Q3: 推荐系统的冷启动怎么解决？

**30 秒**：新用户用注册信息 + 热门兜底，新物品用内容 Embedding。

**3 分钟**：
- 新用户：人口属性、注册兴趣、相似用户行为、热门/编辑推荐
- 新物品：内容 Embedding（文本/图像）、知识图谱、流量倾斜
- 新场景：跨场景迁移学习、Meta-learning

**5 分钟**：补充 Few-shot Learning / Meta-learning / MAML 在冷启动中的应用，以及工业级冷启动系统设计。

#### Q4: 推荐系统中的多任务学习怎么设计？

**30 秒**：MMoE（最常用）/ PLE / ESMM，根据任务相关性选。

**3 分钟**：
- Shared-Bottom：简单但任务冲突
- MMoE：Expert + Gate，软共享
- PLE：任务专属 + 共享 Expert
- ESMM：建模 CTR → CTCVR 全链路
- Loss 加权：Uncertainty Weighting / 手动加权

**5 分钟**：结合业务案例说明选型，给出 Pareto 前沿分析方法。

#### Q5: 推荐系统的"信息茧房"怎么解决？

**30 秒**：增加多样性和探索。

**3 分钟**：
- 多样性：DPP / MMR 重排
- 探索：E&E（UCB / Thompson Sampling）
- 长期信号：留存模型作为辅助
- 业务规则：强制插入多样性内容

#### Q6: 推荐系统怎么评估？

**30 秒**：离线 AUC + 在线 A/B + 后验指标（留存）。

**3 分钟**：
- 离线：AUC / LogLoss / GAUC / 多样性 / 覆盖率
- 在线：A/B 测试核心指标
- 后验：7 日 / 30 日留存、LTV

#### Q7: 推荐系统的特征工程有哪些常用方法？

**30 秒**：统计特征、序列特征、交叉特征、Embedding。

**3 分钟**：
- 统计：CTR / CVR（注意平滑）
- 序列：用户行为序列、N-gram
- 交叉：FM / DeepFM 自动交叉
- Embedding：item / user / context

#### Q8: 推荐系统中的位置偏差怎么建模？

**30 秒**：PAL / IPW / DLA。

**3 分钟**：
- PAL：把位置作为输入，推理时枚举所有位置
- IPW：对位置靠前的样本降权
- DLA：双阶段学习，先学位置再学内容

#### Q9: DIN 与 DIEN 与 SIM 的区别？

**30 秒**：DIN（attention）、DIEN（兴趣演化）、SIM（长序列）。

**3 分钟**：
- DIN：local activation，用 attention 加权历史
- DIEN：兴趣抽取 + 兴趣演化
- SIM：长序列（超长用户行为用 GSU + ESU）

#### Q10: 推荐系统的"双塔模型"是什么？

**30 秒**：用户塔 + 物品塔，各自编码后用内积打分。

**3 分钟**：
- 优点：离线预计算物品向量，线上只算用户向量
- 缺点：用户-物品特征无法交叉
- 改进：MV-DNN（多向量）、TDM（树形）

### 40.2 搜索系统（5 题）

#### Q11: 搜索系统的基本架构是什么？

**30 秒**：Query 理解 → 召回 → 排序 → 结果展示。

**3 分钟**：
- Query 理解：分词、改写、纠错、意图识别
- 召回：倒排索引、向量召回
- 排序：BM25 → Learning to Rank
- 结果展示：高亮、摘要

#### Q12: BM25 和 TF-IDF 的区别？

**30 秒**：BM25 加入了文档长度归一化和饱和函数。

**3 分钟**：
- TF-IDF：词频 × 逆文档频率
- BM25：TF-IDF + 文档长度归一化 + TF 饱和（防止长文档占优）

#### Q13: 搜索系统怎么评估？

**30 秒**：NDCG / MAP / MRR。

**3 分钟**：
- NDCG：归一化折损累积增益（最常用）
- MAP：平均精度均值
- MRR：倒数排名均值

#### Q14: 搜索和推荐的区别？

**30 秒**：搜索有明确意图（query），推荐没有。

**3 分钟**：
- 搜索：用户主动表达意图，结果与 query 相关性决定
- 推荐：用户被动接受，结果与用户兴趣相关
- 技术差异：搜索更依赖 NLP，推荐更依赖行为数据

#### Q15: 搜索系统中的 Learning to Rank 怎么实现？

**30 秒**：LambdaMART / RankNet / ListNet。

**3 分钟**：
- Pointwise：单个样本回归
- Pairwise：样本对比较（RankNet / LambdaRank）
- Listwise：整个列表评估（ListNet / LambdaMART）

### 40.3 广告系统（5 题）

#### Q16: 广告系统的核心模块有哪些？

**30 秒**：广告主 → 投放 → 召回 → CTR/CVR 预估 → 出价 → 拍卖 → 排序 → 展示。

**3 分钟**：
- 投放平台：广告主创建计划
- 召回：基于人群定向
- 预估：CTR / CVR 模型
- 出价：oCPC / oCPM
- 拍卖：GSP / VCG
- 排序：综合 score = bid × pCTR × q (quality)

#### Q17: 广告系统的拍卖机制是什么？

**30 秒**：GSP（广义二价拍卖）。

**3 分钟**：
- GSP：广告主按 score 排序，按下一名出价 + 0.01 收费
- VCG：按"对其他广告主的损失"收费（理论上更优）
- 实际工业界用 GSP 多（实现简单）

#### Q18: 广告 CTR 预估有什么特殊挑战？

**30 秒**：数据稀疏（广告曝光少）、冷启动（新广告）、季节性。

**3 分钟**：
- 数据稀疏：广告主少曝光 → 用跨广告迁移学习
- 冷启动：新广告 → 用创意内容 Embedding
- 季节性：电商大促、广告主预算波动

#### Q19: oCPC / oCPM 是什么？

**30 秒**：广告主给定转化出价，平台自动调整点击出价。

**3 分钟**：
- oCPC：按转化出价，按点击收费（CPC）
- oCPM：按转化出价，按千次曝光收费（CPM）
- 平台根据 CVR 预估自动调整出价，让广告主 ROI 稳定

#### Q20: 广告系统和推荐系统的区别？

**30 秒**：广告考虑广告主利益（出价），推荐只考虑用户体验。

**3 分钟**：
- 广告：score = bid × pCTR × quality（多目标）
- 推荐：score = pCTR（单目标 / 用户体验）
- 广告系统更复杂，需要兼顾广告主、平台、用户三方

### 40.4 多任务 / 多目标（5 题）

#### Q21: MMoE 的 Expert 数量怎么选？

**30 秒**：从 4-8 个开始，根据业务调。

**3 分钟**：
- 太少：表达能力不足
- 太多：训练不稳、过拟合
- 经验值：4-8 个

#### Q22: 多任务 Loss 加权的 4 种方法？

**30 秒**：Uncertainty Weighting / GradNorm / DWA / 手动加权。

**3 分钟**：见 §30.2。

#### Q23: ESMM 为什么能解决 CVR 数据稀疏？

**30 秒**：建模 CTCVR（点击+转化全链路），用点击样本监督 CVR 学习。

**3 分钟**：
- CVR 样本：曝光 + 点击 + 转化（最稀疏）
- CTCVR 样本：曝光 + 转化（较多）
- ESMM：CTCVR = CTR × CVR，CVR 通过 CTCVR 间接学习

#### Q24: 多目标 Pareto 前沿怎么分析？

**30 秒**：画图，找前沿上的点。

**3 分钟**：
- 不同模型 / 超参 → (指标 A, 指标 B) 散点图
- Pareto 前沿：前沿上的点都是"最优权衡"
- 业务方选择哪个点，看业务偏好

#### Q25: 多任务学习失败的常见原因？

**30 秒**：跷跷板、主任务压制、辅助任务拖累。

**3 分钟**：见 §30.5。

### 40.5 冷启动 / 长尾（3 题）

#### Q26: 新用户冷启动怎么做？

**30 秒**：注册信息 + 热门兜底 + 兴趣试探。

**3 分钟**：见 §31.3。

#### Q27: 新物品冷启动怎么做？

**30 秒**：内容 Embedding + 流量倾斜 + KG。

**3 分钟**：见 §31.3。

#### Q28: 长尾 item 推荐怎么提升多样性？

**30 秒**：重排序（DPP/MMR）+ 探索（E&E）+ 内容 Embedding。

**3 分钟**：见 §31.2。

### 40.6 工程 / 系统设计（5+ 题）

## 41. 跨域方法论迁移

### 41.1 视觉 → 推荐

#### Attention 机制迁移

```text
CV 中的 Attention (2017+):
  - Self-Attention 用于图像分类 (ViT)
  - Cross-Attention 用于检测 / 分割
  - 空间注意力 + 通道注意力 (SE-Net / CBAM)

推荐中的 Attention (2018+):
  - DIN: 候选 item 对历史行为的 attention
  - DIEN: 兴趣抽取 + 兴趣演化的 attention
  - SIM: 长序列的两阶段 attention (GSU + ESU)
```

**迁移的本质**：Attention 是一种"加权平均"，本质是"找重要信息"。视觉找重要的空间/通道，推荐找重要的历史/特征。

#### Contrastive Learning 迁移

```text
CV 中的 Contrastive Learning (2020+):
  - SimCLR: 同一样本不同增强 → 相似
  - MoCo: 维护负样本队列
  - BYOL: 不需要负样本

推荐中的 Contrastive Learning (2021+):
  - RecSys: 用户-物品点击 = 正样本，随机 = 负样本
  - 多视角对比（行为序列 vs 内容）
  - 长序列 vs 短序列对比
```

**迁移的本质**：对比学习的核心是"拉近相似、推远不相似"，在视觉和推荐中目标一致。

### 41.2 NLP → 推荐

#### LLM4Rec 迁移

```text
NLP 的 LLM 范式:
  - Pre-training: 大规模文本
  - Fine-tuning: 任务特定数据
  - Prompt: 任务模板

推荐的 LLM 范式:
  - Pre-training: 用户行为 + item 文本
  - Fine-tuning: 任务特定数据
  - Prompt: "推荐" + 用户历史 + 候选 item
```

**经典案例**：
- TALLRec：LLM 作为推荐系统的辅助特征
- P5：LLM 编码用户/物品，多任务 prompt
- InstructRec：LLM 直接生成推荐列表

#### Embedding 迁移

**核心**：把 BERT / Sentence-BERT 学到的文本 Embedding 用作 item 特征。

```python
# 用 BERT 给 item title 编码
item_text_embedding = bert_model.encode(item.title)

# 作为特征拼接到推荐模型
features = {
    'item_id_embedding': item_id_emb,
    'item_text_embedding': item_text_embedding,  # 来自 BERT
    'item_attr_embedding': item_attr_emb,
}
```

### 41.3 RL → 推荐

#### Bandit 算法迁移

```text
RL 中的 Bandit:
  - 多臂老虎机问题
  - 探索 vs 利用

推荐中的 Bandit:
  - 用户 = 老虎机
  - item = arm
  - 点击 = reward
```

**迁移案例**：
- LinUCB：每个 item 一个岭回归
- Thompson Sampling：每个 item 一个 Beta 分布
- Contextual Bandit：结合上下文（用户特征）

#### DQN / DDPG 迁移

**挑战**：推荐是"序列决策"（推一个 → 看反馈 → 推下一个），但奖励稀疏（用户可能没点击）。

**解法**：
- 状态：用户历史 + 上下文
- 动作：推荐列表
- 奖励：点击 + 长期价值

### 41.4 搜索 → 推荐

#### Learning to Rank 迁移

```text
搜索中的 LTR:
  - BM25 排序
  - LambdaMART
  - ListNet

推荐中的 LTR:
  - 把"候选 item 列表"看作"搜索结果"
  - 用户兴趣 = query
  - item 相关性 = ranking score
```

**核心思想**：推荐 = 给用户兴趣的"搜索"。

### 41.5 反例：不当迁移的代价

| 迁移 | 失败原因 | 教训 |
| :--- | :--- | :--- |
| **Transformer 直接用于推荐** | 用户行为序列太短（平均 50-100），Transformer 优势不明显 | 必须有长序列才有价值 |
| **Diffusion 用于推荐** | 生成式推荐需要语义 ID，Diffusion 难以生成离散 token | 离散生成用 RQ-VAE + AR 更合适 |
| **MoE 直接搬到推荐** | 推荐数据量比 NLP 小 100 倍，MoE 容易过拟合 | 必须小规模 + 强正则 |
| **对比学习无脑用** | 推荐中的"正样本"定义模糊（点过 = 正？） | 必须明确正样本定义 |

### 42.2 一次项目中同时用 5 个方法的范例

**项目背景**：电商推荐 CTR 涨 5%，但 GMV 没涨。

```text
方法 1: 5W1H 分析
  Why: CTR 涨但 GMV 不涨？
  What: 用户被吸引点了，但没有购买
  Where: 首页推荐
  Who: 主要影响新用户
  When: 上线后第 1 周明显
  How: 通过用户分群分析

方法 2: MECE 拆解
  GMV = DAU × 人均订单 × 客单价
  CTR 涨 → DAU 没涨 → 人均订单没涨 → 客单价没涨
  结论: CTR 涨了但"点击 → 加购"漏斗掉了

方法 3: 5Why 分析
  为什么 GMV 不涨？因为转化率掉
  为什么转化率掉？因为用户被"标题党"吸引，进来发现货不对板
  为什么货不对板？因为标题优化过度
  解决: 在精排里加"标题-详情匹配度"特征

方法 4: Pareto 分析
  80% 的 GMV 流失来自 20% 的"标题党"item
  针对这 20% item 单独做模型

方法 5: 闭环反馈
  上线后观察 7/30 天，确认 GMV 是否涨
  写复盘文档，给团队分享
```

```text
方法论链式调用示例:

项目启动

  → 用 MECE 拆解问题（方法 3）
  → 用费米估算评估量级（方法 4）
  → 用 DDD 设计架构（方法 12）
  → 用 TDD 实施（方法 9）
  → 用 SOP 上线（方法 38）
  → 用 A/B 测试验证（方法 38）

```

**核心**：方法论不是孤立的，是"链式调用"的组合拳。

### 43.2 方法论的"AI Resistance"评估

## 45. 框架过载的 7 个新信号（搜推广特化）

### 45.1 过度工程化

**症状**：
- 一个简单的 A/B 测试要写 10 份文档
- 一个召回优化要分 5 个项目阶段
- 团队 30% 的时间花在流程上

**判断标准**：如果流程的时间 > 实际项目的时间，就是过度工程化。

**解法**：区分"重要项目"和"日常迭代"。重要项目用全套方法论，日常迭代简化流程。

### 45.2 文档爆炸

**症状**：
- 一个项目有 20 份文档（需求、设计、评审、测试、上线、复盘……）
- 没人愿意写，但所有人都被要求写

**判断标准**：如果文档数量 > 实际需求 × 2，就是文档爆炸。

**解法**：合并同类文档（如设计 + 评审合并）、减少模板字段、允许"轻量级"文档。

### 45.3 流程僵化

**症状**：
- 所有项目必须按"立项 → 设计 → 开发 → 测试 → 上线"走
- 紧急 Bug 也必须走完整流程
- 创新项目被流程压死

**判断标准**：如果紧急情况下流程还必须走完，就是流程僵化。

**解法**：区分"标准流程"和"快速通道"。紧急 Bug / 创新项目走快速通道。

### 45.4 创新受阻

**症状**：
- 团队只做"业务方要求"的，不主动创新
- 创新提案被评审会拒绝
- 失败一次后再也没人敢试

**解法**：设立"创新预算"（如 20% 时间用于自由探索）、容忍失败。

### 45.5 团队疲劳

**症状**：
- 每周会议 > 10 小时
- 文档工作 > 30% 时间
- 工程师吐槽"流程比代码多"

**解法**：定期收集团队反馈、精简会议、允许"无文档"的快速迭代。

### 45.6 业务方困惑

**症状**：
- 业务方收到 5 份不同的指标报表
- 业务方搞不清"哪个指标是真的"
- 业务方和算法团队的会议变成"数字游戏"

**解法**：统一指标定义、单一可信来源、简化沟通。

### 45.7 自我感动

**症状**：
- 团队做了大量"看似严谨"的工作
- 但业务结果没变化
- 团队认为"我们做得很好，是业务方不懂"

**解法**：用业务结果反推方法论价值、定期做"价值回顾"。


## 📝 生成式推荐（GR）系统架构演进与核心攻坚方案

## 🎯 核心技术定位：从“判别式打分”到“生成式联合概率”

传统的推荐架构（召回 $\rightarrow$ 粗排 $\rightarrow$ 精排 $\rightarrow$ 重排）本质上是在做**孤立的判别式分类题**，计算的是 $P(\text{Click} | \text{User}, \text{Item})$。这种架构天然存在两个致命瓶颈：

1. **级联误差（Cascaded Error）**：上游为了截断耗时丢弃的样本，下游永远无法捕捉，造成严重的样本选择偏差（Selection Bias）。

2. **序列割裂**：无法真正建模用户在连续观看/刷新过程中，物品与物品之间的时序演序关系与联合概率分布。


**我们的目标**：将多阶段合并，引入生成式推荐（GR），直接端到端生成最符合用户心智流向的物品序列：

$$P(I_1, I_2, \dots, I_k | \text{Context}) = \prod_{i=1}^{k} P(I_i | I_{<i}, \text{Context})$$

## 🛠️ 三大核心技术攻坚模块（我的 CV 优势与 GR 结合点）

### 模块一：基于多模态残差向量量化（RVQ）的语义标记化（Tokenization）

> **痛点**：传统的随机整数 ID（Random Integer IDs）相互独立，会直接导致大模型（LLM）的 Embedding 空间坍塌，模型根本无法学习长尾和新物品的语义相似度。

- **我的解法（发挥 CV 优势）**：引入类似 SoundStream / EnCodec 的残差向量量化（Residual Vector Quantization, RVQ）技术。

    1. 利用我们现有的冻结多模态大模型（如 ViT / Video-LLM）作为 Backbone，提取视频/图文的原始高维稠密特征向量 $E \in \mathbb{R}^d$。

    2. 构建分层级联 Codebook（码本）。第一层量化提取**粗粒度语义**（如：美妆个护），计算残差；第二层量化提取**细粒度语义**（如：面部精华），再次计算残差；第三层量化提取**实例级商品特征**（如：特定品牌/质地）。

- **技术产出**：将全站千万级的 Item ID 压缩并转化为一个固定长度的离散 Token 序列（如：`[Token_14, Token_89, Token_204]`）。

- **业务价值**：即使大模型在自回归生成时最后一个 Token 预测发生轻微偏移，由于前两层粗/细粒度语义 Token 锁定，生成的依然会是同品类高质量内容，彻底解决长尾内容冷启动与语义丢失问题。


### 模块二：突破线上 30ms 延迟高墙（Ultra-Low Latency Inference）

> **痛点**：大模型自回归（Autoregressive）解码是 $O(N)$ 的时间复杂度。在国内大并发（高并发、QPS 极高）场景下，线上物理延迟预算通常只有 30 毫秒以内，自回归直接落地必死无疑。

- **我的解法**：根据业务场景，采用**双轨制工程优化**。

    1. **重排层切入（前中期方案）**：将 GR 限制在最末端 50-100 个候选集的重排阶段。在 C++ 侧构建内存常驻的**前缀树（Trie Tree）**。在 Beam Search 解码的每一步，利用 Trie 树对大模型输出的 Logits 进行强行 Mask，**只允许输出当前在架、合法的 Token 路径**。将搜索空间从万级瞬间收敛到个位数，耗时从 $>100\text{ms}$ 暴降至 $<15\text{ms}$。

    2. **主推荐流（长期方案）**：引入**非自回归生成（Non-Autoregressive Generation, NAG）**。利用 Masked Language Model 机制，输入用户行为序列后，一次性并行输出 6 个 `[MASK]` 位置的 Item Token。利用轻量级双向自注意力机制进行 1-2 轮的并行细化（Refinement），实现 $O(1)$ 的时间复杂度解码，完美承接线上高并发。


### 3. 模块三：基于 R-DPO（推荐直接偏好对齐）的多目标业务对齐

> **痛点**：大模型的底层 Loss 是交叉熵（Next-Token Prediction），它倾向于生成最容易被预测、或者高点击率的“点击类内容”，容易导致系统滑向低俗和标题党，无法对齐“人均观看时长、点赞、关注、GMV”等核心业务 KPI。

- **我的解法**：跳过复杂的强化学习显式奖励模型（Reward Model）训练，直接引入**推荐场景下的 DPO（Direct Preference Optimization）**。

    1. 从用户行为日志中构建三元组数据：$(\text{Context}, Y_w, Y_l)$。

        - $Y_w$（优质序列）：用户不仅点击，且完播、点赞或产生了高互动、长时长的物品序列。

        - $Y_l$（劣质序列）：用户点击后秒退（Bounce）、或者直接 Skip 掉的点击肉鸡序列。

    2. 利用以下损失函数直接微调（Fine-tune）我们的生成式推荐模型 $\pi_\theta$：

        $$\mathcal{L}_{\text{DPO}}(\theta; \pi_{\text{ref}}) = -\mathbb{E} \left[ \log \sigma \left( \beta \log \frac{\pi_\theta(y_w | x)}{\pi_{\text{ref}}(y_w | x)} - \beta \log \frac{\pi_\theta(y_l | x)}{\pi_{\text{ref}}(y_l | x)} \right) \right]$$

- **业务价值**：从数学底层约束模型，惩罚点击肉鸡序列的生成概率，激增高价值、长留存序列的展现机会，真正实现大模型技术向核心商业指标的对齐。
