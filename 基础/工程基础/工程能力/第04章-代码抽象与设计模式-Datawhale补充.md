## 二、核心补充内容

### 2.1 23 种 GoF 模式 × DL/搜推广工程映射表（sweetalk 目录 × 原文档工程视角）

把 sweetalk 的模式清单与本地工程场景对齐，形成"学习优先级"：

| 模式（分类） | 一句话 | 本地工程场景 | 优先级 |
| :--- | :--- | :--- | :--- |
| 工厂方法/抽象工厂（创建型） | 把"创建哪种模型/数据集"收敛到工厂 | `build_model(cfg)` / 数据集工厂（第06章配置系统） | ⭐⭐⭐ |
| 单例（创建型） | 全局唯一资源 | 训练器内的 tokenizer/词表缓存、日志句柄 | ⭐⭐⭐ |
| 建造者（创建型） | 分步组装复杂对象 | 多阶段构建特征配置/训练管线 | ⭐⭐ |
| 策略（行为型） | 算法族可替换 | 损失函数/采样策略/负采样器可插拔 | ⭐⭐⭐ |
| 观察者（行为型） | 事件驱动通知 | 训练钩子（epoch 结束→评估/上报） | ⭐⭐⭐ |
| 模板方法（行为型） | 父类定骨架子类填空 | `BaseTrainer.train()` 流程固定、子类覆写钩子 | ⭐⭐⭐ |
| 装饰器（结构型） | 不改原类加职责 | 计时/缓存/日志装饰数据集与算子 | ⭐⭐⭐ |
| 适配器（结构型） | 接口转换 | 不同特征存储/模型服务接口的统一层 | ⭐⭐ |
| 外观（结构型） | 子系统统一门面 | 特征平台 SDK 对上层暴露一个入口 | ⭐⭐ |
| 代理（结构型） | 控制访问 | 远程模型服务的本地桩/懒加载 Embedding 表 | ⭐⭐ |
| 组合（结构型） | 树形部分-整体 | nn.Module 树本身就是组合模式 | ⭐⭐ |
| 责任链（行为型） | 请求沿链传递 | 数据预处理管线/在线特征降级链 | ⭐⭐ |
| 状态（行为型） | 状态驱动行为切换 | 训练状态机（train/eval/patience 早停） | ⭐⭐ |
| 命令（行为型） | 请求对象化 | 实验任务队列（提交/撤销/重放） | ⭐ |

（其余 9 种：原型、享元、桥接、中介者、备忘录、迭代器、解释器、访问者、享元变体——在 DL 工程中出现频率低，学习时过一遍即可。）

### 2.2 "重构叙事"学习法（sweetalk docs 的特色）

sweetalk 沿用《大话设计模式》的"先写烂代码 → 重构出模式"叙事。应用到本地工程：

1. 先写一个"能跑"的 if-else 版本（如按模型类型分支的建图/建loss逻辑）；
2. 找出**变化轴**（哪些维度在频繁新增？模型种类？损失？采样策略？）；
3. 用对应模式把变化轴收敛（策略/工厂）；
4. 用"新增一个模型要改几处"作为重构收益的度量。

这个流程与本地第04章"代码抽象"的方法论一致，sweetalk 补的是每一步的**标准代码形态**。

### 2.3 三语言对照的价值点

同模式在 Python 与 C++ 的实现差异本身是学习材料：Python 用鸭子类型/装饰器即可实现"静态语言需要接口类"的结构（如策略模式无需显式 interface），而 C++ 的模板/CRTP 提供零开销抽象——在性能敏感的算子/数据通路侧（对应本地第07章性能剖析），这种差异决定实现选择。

## 三、可直接动手的实践

1. 从 sweetalk `python/` 目录取策略+工厂两个实现，改造成"损失函数注册表 + 配置驱动选择"的迷你框架；
2. 给本地任一训练脚本做一次 2.2 的重构演练，记录重构前后的"新增模型改动点数"；
3. 对照 nn.Module 与组合模式：画出自己项目里模型的 Module 树，标注哪几层用了模板方法/观察者（hook）。
