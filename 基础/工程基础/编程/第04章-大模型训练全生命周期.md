# 大模型生命周期工程实战全解

## 体系总览

下图展示了模型从零到生产、再到持续进化的完整轨迹：

```text
[前训练] → [后训练(SFT/RLHF/DPO)] → [部署推理]
    ↓              ↓                      ↓
  需断点续训     需断点续训              量化/压缩
    ↓              ↓
[增量更新(CPT/CFT)] ← 新数据到来 ← [生产环境]
```

下面以**前训练→后训练→断点续训→增量更新**为主线，加入**参数量与显存计算、数据缓存**等硬核细节，每一节都配有可运行的 PyTorch 代码。

## 第 1 章：前训练 —— 模型能力的“底座”

### 1.1 什么是前训练

前训练是指在大规模通用语料（几 GB ~ 几 TB）上，通过自监督任务学习通用语言/视觉表示的过程。

**典型范式**：
- **语言模型**：因果语言建模（GPT 系列，预测下一个 token）
- **掩码语言建模**：BERT 系列，随机遮盖部分 token 预测
- **图像**：MAE（掩码自编码器）、CLIP（图文对比）

前训练产出的“基座模型”，具备统计意义上的知识和泛化能力，但不一定遵循人类指令。

### 1.2 从零构建并前训练一个 GPT

以下代码演示了核心流程：构建 GPT 模型 → 准备数据 → 前训练循环。

```python
import torch
import torch.nn as nn
from torch.utils.data import DataLoader, Dataset

# 1. 构建 Causal Self-Attention 模块
class CausalSelfAttention(nn.Module):
    def __init__(self, embed_dim, num_heads):
        super().__init__()
        assert embed_dim % num_heads == 0
        self.embed_dim = embed_dim
        self.num_heads = num_heads
        self.head_dim = embed_dim // num_heads
        self.qkv = nn.Linear(embed_dim, 3 * embed_dim, bias=False)
        self.proj = nn.Linear(embed_dim, embed_dim, bias=False)

    def forward(self, x):
        B, T, C = x.shape
        qkv = self.qkv(x).reshape(B, T, 3, self.num_heads, self.head_dim)
        q, k, v = qkv.unbind(dim=2)  # 分割 Q, K, V
        # 使用 PyTorch 2.0+ 的 scaled_dot_product_attention
        y = nn.functional.scaled_dot_product_attention(q, k, v, is_causal=True)
        y = y.reshape(B, T, C)
        return self.proj(y)

# 2. 定义 GPT Block
class GPTBlock(nn.Module):
    def __init__(self, embed_dim, num_heads, ff_mult=4):
        super().__init__()
        self.ln1 = nn.LayerNorm(embed_dim)
        self.attn = CausalSelfAttention(embed_dim, num_heads)
        self.ln2 = nn.LayerNorm(embed_dim)
        self.mlp = nn.Sequential(
            nn.Linear(embed_dim, embed_dim * ff_mult),
            nn.GELU(),
            nn.Linear(embed_dim * ff_mult, embed_dim),
        )

    def forward(self, x):
        x = x + self.attn(self.ln1(x))   # Pre-Norm 残差
        x = x + self.mlp(self.ln2(x))
        return x

# 3. 完整 GPT 模型
class GPT(nn.Module):
    def __init__(self, vocab_size, embed_dim, num_heads, num_layers, max_seq_len):
        super().__init__()
        self.token_embed = nn.Embedding(vocab_size, embed_dim)
        self.pos_embed = nn.Embedding(max_seq_len, embed_dim)
        self.blocks = nn.Sequential(*[
            GPTBlock(embed_dim, num_heads) for _ in range(num_layers)
        ])
        self.ln_f = nn.LayerNorm(embed_dim)
        self.lm_head = nn.Linear(embed_dim, vocab_size, bias=False)

    def forward(self, x):
        B, T = x.shape
        pos = torch.arange(0, T, device=x.device).unsqueeze(0)
        x = self.token_embed(x) + self.pos_embed(pos)
        x = self.blocks(x)
        x = self.ln_f(x)
        return self.lm_head(x)

# 4. 训练循环
model = GPT(vocab_size=10000, embed_dim=512, num_heads=8, num_layers=6, max_seq_len=256)
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4, betas=(0.9, 0.95))
dataloader = DataLoader(MyTextDataset(), batch_size=32, shuffle=True)

for epoch in range(1):          # 示意：实际前训练需大量 epoch
    for batch in dataloader:
        x, y = batch[:, :-1], batch[:, 1:]    # 输入/目标错位一位
        logits = model(x)
        loss = nn.functional.cross_entropy(
            logits.reshape(-1, logits.size(-1)), y.reshape(-1)
        )
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
```

### 1.3 前训练中的参数量与显存计算

**Transformer 核心公式**（每个 Block）：

- 注意力 QKV 投影：`3 × d × d_model` + 输出投影 `d × d_model`
- FFN：`d × d_ff + d_ff × d`
- LayerNorm：`2 × d`

完整单层参数量：

```text
P_layer ≈ 4·d² + 2·d·d_ff + 4·d
```

**训练显存估算**：

| 组件 | FP32 | 混合精度(FP16权重+FP32优化器) |
| :--- | :--- | :--- |
| 权重 | P×4 | P×2 |
| 梯度 | P×4 | P×2 |
| 优化器(Adam) | P×8 | P×8 |
| **总计** | **P×16** | **P×12** |

换算工具代码：

```python
def estimate_memory(num_params, precision="fp16", training=True):
    bytes_per_param = {"fp32": 4, "fp16": 2, "int8": 1}
    b = bytes_per_param[precision]
    if training:
        total = num_params * (b + b + 8)   # weight + grad + optimizer
    else:
        total = num_params * b
    return total / (1024**3)               # 转换为 GiB

# 1B 参数 FP16 推理：
print(estimate_memory(1e9, "fp16", training=False))    # ≈ 1.86 GiB
# 1B 参数 FP16 训练：
print(estimate_memory(1e9, "fp16", training=True))     # ≈ 11.2 GiB
```

## 第 2 章：后训练 —— 让模型“对齐”人类偏好

前训练的模型会接话，但不懂“有用、无害、守规矩”。后训练解决这个问题，主要包括 SFT 和 RLHF/DPO 两条路径。

### 2.1 监督微调

使用高质量指令-回答对（人工或强模型生成）微调基座模型。以下代码演示最简单的 SFT 流程。

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

model = AutoModelForCausalLM.from_pretrained("pretrained-gpt-ckpt")
tokenizer = AutoTokenizer.from_pretrained("pretrained-gpt-ckpt")
optimizer = torch.optim.AdamW(model.parameters(), lr=5e-6)

# SFT 数据格式
instructions = ["翻译：Hello → ", "总结：这篇文章讨论了……"]
answers = ["你好", "文章讲的是……"]

for epoch in range(3):
    for instr, ans in zip(instructions, answers):
        full = instr + ans + tokenizer.eos_token
        inputs = tokenizer(full, return_tensors="pt")
        labels = inputs["input_ids"].clone()
        # 只对 answer 部分计算损失
        instr_len = len(tokenizer(instr)["input_ids"])
        labels[:, :instr_len] = -100

        outputs = model(**inputs, labels=labels)
        loss = outputs.loss
        loss.backward()
        optimizer.step()
        optimizer.zero_grad()
```

### 2.2 直接偏好优化

DPO 直接在偏好对上优化策略，不依赖显式奖励模型，训练更稳定。以下是最简实现：

```python
def dpo_loss(model, ref_model, chosen_inputs, rejected_inputs, beta=0.1):
    # 获取 chosen 和 rejected 的 log-prob
    with torch.no_grad():
        ref_chosen_logp = get_log_prob(ref_model, chosen_inputs)
        ref_rejected_logp = get_log_prob(ref_model, rejected_inputs)

    policy_chosen_logp = get_log_prob(model, chosen_inputs)
    policy_rejected_logp = get_log_prob(model, rejected_inputs)

    diff = (policy_chosen_logp - ref_chosen_logp) - (policy_rejected_logp - ref_rejected_logp)
    loss = -torch.log(torch.sigmoid(beta * diff)).mean()
    return loss
```

### 2.3 为什么引入强化学习

核心原因有三：

1. **损失函数不可微**：“无害”无法写成可微标量。
2. **多步决策**：链式推理、工具使用本质是序列决策，RL 天然适用。
3. **探索能力**：SFT 只能模仿，RL 能发现数据中不存在但更好的路径。

## 第 3 章：断点续训 —— 长时间训练的可靠性基石

### 3.1 为什么不能只保存权重

普通 `torch.save(model.state_dict(), ...)` **只保存了模型参数**，不包含优化器的动量、方差等状态。直接加载权重继续训练，优化器状态会被重置，导致初期训练不稳定甚至 NaN。

**必须打包保存的完整状态**：

```python
def save_full_checkpoint(model, optimizer, scheduler, scaler, epoch, step, path):
    checkpoint = {
        "model_state_dict": model.state_dict(),
        "optimizer_state_dict": optimizer.state_dict(),
        "scheduler_state_dict": scheduler.state_dict(),
        "amp_scaler": scaler.state_dict() if scaler else None,
        "epoch": epoch,
        "global_step": step,
        "rng_states": {
            "torch": torch.get_rng_state(),
            "cuda": torch.cuda.get_rng_state_all(),
        },
    }
    torch.save(checkpoint, path)
```

### 3.2 完整的分布式断点续训流程

在 PyTorch 分布式训练中（使用 `DistributedDataParallel`），`model` 被包装后结构发生变化，保存时需通过 `model.module` 获取原始模型。

```python
import torch.distributed as dist
import torch.nn as nn
from torch.nn.parallel import DistributedDataParallel as DDP

def save_ddp_checkpoint(model, optimizer, epoch, path, rank):
    if rank == 0:                         # 只在 rank 0 保存
        state = {
            "model": model.module.state_dict(),   # 解包 DDP
            "optimizer": optimizer.state_dict(),
            "epoch": epoch,
            "global_step": global_step,
        }
        torch.save(state, path)
    dist.barrier()                        # 等待保存完成

def load_ddp_checkpoint(model, optimizer, path, device):
    checkpoint = torch.load(path, map_location=device)
    model.module.load_state_dict(checkpoint["model"])
    optimizer.load_state_dict(checkpoint["optimizer"])
    epoch = checkpoint["epoch"]
    global_step = checkpoint["global_step"]
    return epoch, global_step
```

### 3.3 常见踩坑与解决方案

| 坑 | 原因 | 解决 |
| :--- | :--- | :--- |
| 续训后 loss 剧烈抖动 | 只恢复了权重，优化器状态丢失 | 必须同时恢复 `optimizer_state_dict` |
| 恢复后 loss 曲线与之前不一致 | 随机种子未恢复，数据遍历顺序变化 | 保存并恢复 `rng_states` |
| 混合精度续训直接 NaN | GradScaler 的 scale 被重置为 1 | 保存并恢复 `scaler.state_dict()` |
| 加载时 `RuntimeError: Error(s) in loading state_dict` | 模型结构不匹配 | 使用 `load_state_dict(..., strict=False)` |

## 第 4 章：增量更新 —— 模型在生产中持续进化

### 4.1 两层概念辨析

**增量更新**在工程中有两个含义：

**概念 1：断点续训后的继续训练（增量训练/分段训练）**：模型训到一半保存，之后加载 checkpoint 继续。这实际上就是第 3 章的断点续训。

**概念 2：在新数据上继续训练，保持旧知识（持续学习/Continual Learning）**：模型部署后，希望不断吸收新数据而不遗忘旧知识。核心挑战是**灾难性遗忘**。

以下聚焦于第 2 种概念的工业实践。

### 4.2 灾难性遗忘的本质

研究揭示：灾难性遗忘**不是模型“忘记”了旧能力**，而是旧能力在微调过程中被**新能力掩盖**（功能激活偏移）。

这一发现催生了“函数向量对齐”（Function Vector Guidance）等新方法：在微调新任务时，对齐旧任务对应的内部函数向量，显著降低遗忘。

### 4.3 增量更新策略全家桶

| 策略 | 原理 | 代码复杂度 | 防遗忘效果 |
| :--- | :--- | :--- | :--- |
| 经验回放 | 保留旧数据样本与新数据混合训练 | 低 | ★★★★ |
| 弹性权重巩固 | 给关键权重加“弹性惩罚”，限制变化幅度 | 中 | ★★★ |
| 参数隔离 | 不同任务使用不同子网络或掩码 | 高 | ★★★★★ |
| 函数向量对齐 | 对齐旧任务对应的内部函数向量 | 高 | ★★★★★ |
| 完全重训 | 新旧数据混合从零训练 | 低 | ★★★★★(但贵) |

### 4.4 经验回放实战代码

这是最实用、最稳定的增量更新方案。核心：**用 `register_buffer` 存储旧数据特征**，训练时与新数据混合回放。

```python
class IncrementalModel(nn.Module):
    def __init__(self, feature_dim, replay_buffer_size=500):
        super().__init__()
        self.encoder = nn.Linear(feature_dim, 128)
        self.classifier = nn.Linear(128, 10)

        # ---- 关键：用 register_buffer 存储旧数据缓存 ----
        # buffer 会随模型保存、随设备移动，但不参与梯度更新
        self.register_buffer(
            "replay_x",
            torch.zeros(replay_buffer_size, feature_dim)
        )
        self.register_buffer(
            "replay_y",
            torch.zeros(replay_buffer_size, dtype=torch.long)
        )
        self.replay_ptr = 0
        self.replay_full = False

    def update_replay_buffer(self, x, y):
        """添加新数据到回放缓存"""
        batch_size = x.size(0)
        for i in range(batch_size):
            self.replay_x[self.replay_ptr] = x[i]
            self.replay_y[self.replay_ptr] = y[i]
            self.replay_ptr = (self.replay_ptr + 1) % self.replay_x.size(0)
        if self.replay_ptr == 0:
            self.replay_full = True

    def get_replay_batch(self, batch_size=64):
        """从缓存中采样一批旧数据"""
        max_idx = self.replay_x.size(0) if self.replay_full else self.replay_ptr
        if max_idx == 0:
            return None, None
        indices = torch.randint(0, max_idx, (batch_size,))
        return self.replay_x[indices], self.replay_y[indices]

# 训练循环
model = IncrementalModel(feature_dim=100)
optimizer = torch.optim.Adam(model.parameters(), lr=1e-4)

for new_x, new_y in new_dataloader:
    # 1. 从回放缓存采样旧数据
    old_x, old_y = model.get_replay_batch(32)

    # 2. 新数据正常训练
    pred_new = model.classifier(model.encoder(new_x))
    loss_new = nn.functional.cross_entropy(pred_new, new_y)

    # 3. 与旧数据混合，防止遗忘
    if old_x is not None:
        pred_old = model.classifier(model.encoder(old_x))
        loss_old = nn.functional.cross_entropy(pred_old, old_y)
        loss = loss_new + 0.5 * loss_old
    else:
        loss = loss_new

    optimizer.zero_grad()
    loss.backward()
    optimizer.step()

    # 4. 更新回放缓存
    model.update_replay_buffer(new_x, new_y)

# buffer 随模型自动保存/加载
torch.save(model.state_dict(), "incremental_model.pt")
```

**为什么用 `register_buffer` 而非普通属性**？
- `model.state_dict()` 会包含它，保存/加载自动处理
- `model.to(device)` 会自动跟随迁移
- 优化器不会更新它（`requires_grad=False`）
- 可用 `model.replay_x.data` 手动更新

### 4.5 增量更新中的学习率策略

在旧 checkpoint 基础上追加新数据时，直接恢复旧的高学习率可能破坏已学好的特征。推荐做法：

```python
# 加载 checkpoint 后，从极小学习率重新 warmup
optimizer = torch.optim.AdamW(model.parameters(), lr=0)
scheduler = torch.optim.lr_scheduler.LambdaLR(
    optimizer,
    lr_lambda=lambda step: min(step / warmup_steps, 1.0) * 1e-6
    if step < warmup_steps else 1e-6
)
```

## 第 5 章：综合案例 —— 完整生命周期工程样板

以下代码将前述所有概念串联：前训练（带断点保护）→ 断点续训 → SFT → 增量更新。

```python
# ===================== 完整生命周期工程样板 =====================

def train_or_resume(model, optimizer, scheduler, dataloader,
                    total_steps, resume_path=None):
    """支持断点续训的通用训练循环"""
    global_step, epoch = 0, 0

    if resume_path and os.path.exists(resume_path):
        checkpoint = torch.load(resume_path)
        model.load_state_dict(checkpoint["model_state_dict"])
        optimizer.load_state_dict(checkpoint["optimizer_state_dict"])
        scheduler.load_state_dict(checkpoint["scheduler_state_dict"])
        global_step = checkpoint["global_step"]
        epoch = checkpoint["epoch"]
        print(f"[Resume] 从 step={global_step}, epoch={epoch} 恢复")

    model.train()
    while global_step < total_steps:
        for batch in dataloader:
            x, y = batch[:, :-1], batch[:, 1:]
            logits = model(x)
            loss = nn.functional.cross_entropy(
                logits.reshape(-1, logits.size(-1)), y.reshape(-1)
            )
            optimizer.zero_grad()
            loss.backward()
            torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
            optimizer.step()
            scheduler.step()

            global_step += 1
            # 每 1000 步保存断点
            if global_step % 1000 == 0:
                save_full_checkpoint(model, optimizer, scheduler,
                                     None, epoch, global_step,
                                     f"ckpt_step{global_step}.pt")

# 使用示例
model = GPT(vocab_size=10000, embed_dim=512, num_heads=8, num_layers=6, max_seq_len=256)
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)
scheduler = torch.optim.lr_scheduler.CosineAnnealingLR(optimizer, T_max=10000)
dataloader = DataLoader(MyTextDataset(), batch_size=32)

# 前训练（中断后可自动恢复）
train_or_resume(model, optimizer, scheduler, dataloader,
                total_steps=10000, resume_path="ckpt_step5000.pt")

# 后训练：SFT（同理支持断点续训）
# ... 加载 SFT 数据，小学习率 fine-tune
train_or_resume(model, optimizer, scheduler, sft_dataloader,
                total_steps=2000, resume_path="sft_ckpt_step1000.pt")

# 增量更新：加载之前的回放 buffer，混合新数据继续训练
incremental_model = IncrementalModel(feature_dim=100)
# buffer 已在 state_dict 中持久化
incremental_model.load_state_dict(torch.load("incremental_model.pt"))
# 用新数据继续更新...
```

## 第 6 章:数据流水线全解

### 6.1 数据预处理的工业实践

#### 6.1.2 高效的数据加载器

```python
import numpy as np
import torch
from torch.utils.data import Dataset, DataLoader
import mmap

class MmapGPTDataset(Dataset):
    """
    用 mmap 加载超大 token 文件, 不占内存
    """
    def __init__(self, bin_path, seq_len, num_samples=None):
        # mmap 打开二进制文件
        self.data = np.memmap(bin_path, dtype=np.uint16, mode='r')
        self.seq_len = seq_len
        self.num_samples = num_samples or (len(self.data) - 1) // seq_len

    def __len__(self):
        return self.num_samples

    def __getitem__(self, idx):
        start = idx * self.seq_len
        end = start + self.seq_len + 1

        # mmap 只读取这一段, 不加载整个文件
        chunk = np.array(self.data[start:end], dtype=np.int64)

        # GPT 训练: x 是前 seq_len 个 token, y 是后 seq_len 个 token(错位一位)
        x = torch.from_numpy(chunk[:-1])
        y = torch.from_numpy(chunk[1:])
        return x, y
```

```python
class PackedDataset(Dataset):
    """多文档打包训练(Falcon, Llama 风格)"""
    def __init__(self, token_files, seq_len):
        self.seq_len = seq_len
        # 把多个文档拼成连续的 token 序列, 用 <eos> 分隔
        all_tokens = []
        for f in token_files:
            tokens = np.load(f)
            all_tokens.extend(tokens.tolist())
            all_tokens.append(0)  # 0 作为 eos

        self.data = np.array(all_tokens, dtype=np.int64)

    def __getitem__(self, idx):
        start = idx * self.seq_len
        end = start + self.seq_len + 1
        chunk = self.data[start:end]
        return torch.from_numpy(chunk[:-1]), torch.from_numpy(chunk[1:])


# 避免 padding 浪费
# 假设样本平均长度 500, seq_len=2048
# 普通 padding: 每个样本浪费 1500 tokens
# Packed: 充分利用每个位置
# 节省 70%+ 训练时间
```

#### 6.1.4 数据混合(Mixture)与采样权重

```python
class MixtureDataset(Dataset):
    """
    多数据源按比例混合采样
    例: Common Crawl 60%, Wikipedia 20%, Books 20%
    """
    def __init__(self, datasets, weights):
        self.datasets = datasets
        self.weights = np.array(weights) / sum(weights)
        self.cumulative = np.cumsum(self.weights) * sum(len(d) for d in datasets)

    def __len__(self):
        return int(sum(len(d) for d in self.datasets))

    def __getitem__(self, idx):
        # 根据权重选择数据集
        rand = np.random.random() * self.cumulative[-1]
        dataset_idx = np.searchsorted(self.cumulative, rand)

        # 在该数据集中采样
        local_idx = np.random.randint(0, len(self.datasets[dataset_idx]))
        return self.datasets[dataset_idx][local_idx]
```

### 6.2 数据质量过滤

```python
import re
from urllib.parse import urlparse

class DataQualityFilter:
    """工业级数据质量过滤器"""

    def __init__(self):
        self.lang_detector = None  # fasttext 模型

    def filter(self, text):
        """返回 True 表示保留"""
        if not text or len(text) < 50:
            return False

        # 1. 去除 HTML 标签
        text_clean = re.sub(r'<[^>]+>', '', text)
        if len(text_clean) < 50:
            return False

        # 2. 去除过多特殊字符
        special_ratio = len(re.findall(r'[^\w\s]', text_clean)) / len(text_clean)
        if special_ratio > 0.3:
            return False

        # 3. 去除过多重复
        words = text_clean.split()
        unique_ratio = len(set(words)) / len(words)
        if unique_ratio < 0.3:
            return False

        # 4. 长度合理
        if len(words) > 50000:
            return False

        # 5. 平均句长合理
        sentences = re.split(r'[.!?。！？]', text_clean)
        avg_sentence_len = sum(len(s.split()) for s in sentences) / max(1, len(sentences))
        if avg_sentence_len < 3 or avg_sentence_len > 100:
            return False

        # 6. (可选) 语言检测
        if self.lang_detector and self.lang_detector.predict(text_clean)[0][0] != '__label__zh':
            return False

        return True


# 用法
filter = DataQualityFilter()
clean_docs = [doc for doc in raw_docs if filter.filter(doc)]
```

### 8.1 显存占用分析

```python
def detailed_memory_analysis(model, input_shape, dtype=torch.float32):
    """详细分析模型各部分显存占用"""

    # 1. 参数
    params_bytes = sum(p.numel() * p.element_size() for p in model.parameters())
    print(f"Parameters: {params_bytes / 1024**2:.2f} MB")

    # 2. 激活(估算)
    # 假设 seq_len=2048, batch=8, hidden=4096, layers=32
    seq_len, batch, hidden, layers = 2048, 8, 4096, 32
    # 单层激活: ~4 * batch * seq_len * hidden (4 路: Q, K, V, output)
    activation_per_layer = 4 * batch * seq_len * hidden * 2  # FP16
    total_activations = activation_per_layer * layers / 1024**2
    print(f"Activations (估算): {total_activations:.2f} MB")

    # 3. 优化器状态(Adam, FP32)
    optimizer_states = params_bytes * 2  # m, v
    print(f"Optimizer states (Adam, FP32): {optimizer_states / 1024**2:.2f} MB")

    # 4. 临时张量(框架开销, 临时计算)
    print(f"Framework overhead: ~500 MB")

    total = params_bytes * 4 + total_activations + 500  # 粗略
    print(f"Total estimated: {total / 1024**2:.2f} MB")
```

```python
from transformers import TextIteratorStreamer
from threading import Thread

def stream_generate(model, tokenizer, prompt, max_new_tokens=100):
    inputs = tokenizer(prompt, return_tensors="pt").to('cuda')
    streamer = TextIteratorStreamer(tokenizer, skip_prompt=True)

    generation_kwargs = dict(
        **inputs,
        streamer=streamer,
        max_new_tokens=max_new_tokens,
        do_sample=True
    )

    thread = Thread(target=model.generate, kwargs=generation_kwargs)
    thread.start()

    for text in streamer:
        yield text
```

```python
def compute_perplexity(model, eval_loader):
    """计算困惑度"""
    model.eval()
    total_loss = 0
    total_tokens = 0

    with torch.no_grad():
        for batch in eval_loader:
            x, y = batch
            x, y = x.cuda(), y.cuda()

            logits = model(x)
            loss = F.cross_entropy(
                logits.view(-1, logits.size(-1)),
                y.view(-1),
                reduction='sum'
            )

            total_loss += loss.item()
            total_tokens += y.numel()

    avg_loss = total_loss / total_tokens
    perplexity = math.exp(avg_loss)
    return perplexity
```

```python
    p_bar = (p1 + p2) / 2
    se_pooled = (2 * p_bar * (1 - p_bar)) ** 0.5
    se_unpooled = (p1 * (1-p1) + p2 * (1-p2)) ** 0.5

    n = ((z_alpha * se_pooled + z_beta * se_unpooled) / (p2 - p1)) ** 2
    return int(n) + 1


# 用法
# 新模型预期提升 2%
n = sample_size_calculator(baseline_rate=0.7, mde=0.02)
print(f"每组需要 {n:,} 个样本")
```

### 11.1 推理延迟与用户体验

**关键指标**:
- **TTFT (Time to First Token)**: 首 token 时间
- **TPS (Tokens Per Second)**: 每秒生成 token 数
- **总延迟**: TTFT + (max_tokens × TPS)

**用户容忍度**:
- TTFT < 200ms: 流畅
- TTFT 200-500ms: 略慢
- TTFT > 1s: 明显卡顿

**优化方向**:
- Prefill 阶段: 并行 attention, KV cache 预分配
- Decode 阶段: 投机解码(用小模型猜, 大模型验证)

### 11.2 长上下文支持

- GPT-3: 2048 tokens

- Claude: 200K tokens
- GPT-4 Turbo: 128K tokens

### 12.3 端到端生成式推荐:GR (Generative Recommendation)

```python
class GenerativeRecommender:
    """
    用 GPT 类模型直接生成推荐序列

    输入: 用户历史 + 上下文
    输出: 推荐商品 ID 序列
    """

    def __init__(self, base_llm, item_vocab):
        self.llm = base_llm
        self.item_vocab = item_vocab  # ID → 名称映射

    def recommend(self, user_history, context, top_k=10):
        # 1. 序列化输入
        prompt = self._format_prompt(user_history, context)

        # 2. 生成候选 ID 序列
        candidate_ids = self.llm.generate(prompt, max_tokens=100)

        # 3. 去重、过滤、排序
        unique_ids = self._deduplicate(candidate_ids)
        ranked_ids = self._rerank(unique_ids, user_history)

        return ranked_ids[:top_k]

    def _format_prompt(self, history, context):
        return f"""
你是推荐系统。根据用户的浏览历史和当前上下文, 推荐接下来用户可能感兴趣的 10 个商品(只输出商品 ID, 用逗号分隔)。

用户最近浏览: {[self.item_vocab[i] for i in history]}
当前上下文: {context}

推荐:
"""
```

### 12.4 Semantic ID (SID) 架构

**核心思想**: 把每个 item 编码为一串语义 token, 让推荐变成"序列生成"。

```python
class SemanticIDEncoder:
    """用 RQ-VAE 把商品编码为多级语义 ID"""

    def __init__(self, rqvae_model, num_levels=3, codebook_size=256):
        self.rqvae = rqvae_model
        self.num_levels = num_levels
        self.codebook_size = codebook_size

    def encode(self, item_embedding):
        """
        item_embedding: [D]
        返回: [num_levels] 语义 token 序列
        """
        # 残差量化
        semantic_ids = []
        residual = item_embedding

        for level in range(self.num_levels):
            # 找最近的 codebook entry
            distances = torch.norm(self.rqvae.codebooks[level] - residual.unsqueeze(0), dim=1)
            token = distances.argmin().item()
            semantic_ids.append(token)

            # 更新 residual
            residual = residual - self.rqvae.codebooks[level][token]

        return semantic_ids

    def decode(self, semantic_ids):
        """从语义 ID 重建 Embedding"""
        embedding = torch.zeros(self.rqvae.embedding_dim)
        for level, token in enumerate(semantic_ids):
            embedding += self.rqvae.codebooks[level][token]
        return embedding


# 推荐系统: 给定用户历史 (semantic ID 序列), 用 GPT 生成下一个 semantic ID
# 优势:
# - 语义可解释(token 有意义)
# - 长尾友好(用语义相似度而非 ID)
# - 可跨域推荐(语义是通用的)
```

### 12.5 HSTU (Hierarchical Sequential Transduction Unit)

Meta 2023 提出的统一召回+排序架构:

```python
class HSTUBlock(nn.Module):
    """Hierarchical Sequential Transduction Unit"""
    def __init__(self, dim, num_heads):
        super().__init__()
        self.dim = dim
        self.num_heads = num_heads

        # QKV 投影
        self.qkv = nn.Linear(dim, 3 * dim, bias=False)
        self.proj = nn.Linear(dim, dim, bias=False)

        # 相对位置偏置
        self.rel_bias = nn.Parameter(torch.zeros(num_heads, 1024))

    def forward(self, x):
        B, T, D = x.shape

        qkv = self.qkv(x).reshape(B, T, 3, self.num_heads, D // self.num_heads)
        q, k, v = qkv.unbind(dim=2)  # [B, T, H, D/H]

        # 注意力(去掉 softmax, 用 1/N 归一化)
        scores = torch.einsum('bthd,bshd->bhts', q, k) / (D // self.num_heads)

        # 加相对位置偏置
        scores = scores + self.rel_bias[:, :T, :T]

        # 直接用 scores 作为权重(不 softmax)
        out = torch.einsum('bhts,bshd->bthd', scores, v)
        out = self.proj(out.reshape(B, T, D))

        return out
```

**核心创新**:
- 去掉 softmax, 用 1/N 归一化, 避免稀疏激活
- 用相对位置偏置而非绝对位置
- 统一召回+排序

## 第 13 章:核心面试题(8 题)

### Q1: 大模型训练中 FP32 优化器和 FP16 权重各有什么作用?

**答**:
- FP16 权重: 节省一半显存, 加速矩阵乘。
- FP32 优化器(m, v): 防止 Adam 的更新量太小被 FP16 舍入。
- FP32 主权重: 防止更新时精度丢失。
- **三者缺一不可**,这就是"混合精度"的本质。

### Q2: 解释 LLaMA-2 的 RMSNorm?

**答**: RMSNorm 是 LayerNorm 的简化版, 去掉了均值中心化, 只用 RMS 缩放:
$$
\text{RMSNorm}(x) = \gamma \cdot \frac{x}{\sqrt{\frac{1}{D}\sum x_i^2 + \epsilon}}
$$
**优势**: 计算量减少 10-15%, 效果几乎不退化。

### Q3: 什么是 GQA (Grouped Query Attention)?

**答**: Multi-Query Attention(MQA)的改进,介于标准 MHA 和 MQA 之间:
- MHA: 每个 head 独立的 K, V(32 head 就有 32 套 K, V)
- MQA: 所有 head 共享 1 套 K, V(节省 32 倍)
- GQA: 4 个 head 共享 1 套 K, V(节省 8 倍, 效果接近 MHA)

LLaMA-2 70B 用 GQA。

### Q4: 如何评估一个 LLM 的真实能力?

**答**: 综合评估:
1. **困惑度(PPL)**: 基础语言能力
2. **多任务 benchmark**(MMLU, GSM8K, HumanEval): 各领域能力
3. **人类评估**: GPT-4-as-Judge, ELO rating
4. **A/B 测试**: 实际用户体验
5. **安全评估**: 偏见、毒性、隐私

**单一指标不够, 必须综合看**。

### Q5: 什么是 Rotary Position Embedding (RoPE)?

**答**: RoPE 是相对位置编码,通过旋转矩阵实现:
$$
\text{RoPE}(q_m, k_n) = q_m^T R(m-n) k_n
$$
其中 $R(m-n)$ 是相对位置 $m-n$ 的旋转矩阵。
**优势**:
- 显式表达相对位置
- 可外推到更长序列(只需训练时的 2-4 倍长度)
- LLaMA, GPT-NeoX 等都用

### Q6: 为什么大模型要 Pre-train + Fine-tune?

**答**:
- Pre-train: 学通用语言知识(语法、事实、推理), 数据量大, 成本高。
- Fine-tune: 学特定任务(对话、代码、推荐), 数据量小, 成本低。
- 类比: 教小孩先学所有知识(Pre-train), 再选专业(Fine-tune)。

### Q7: 大模型推理时 PagedAttention 是什么?

**答**: vLLM 提出的优化方案:
- **问题**: KV Cache 在传统连续分配中碎片化严重, 利用率低。
- **解法**: 类似操作系统的虚拟内存, 把 KV Cache 分成固定大小的"页", 按需分配。
- **效果**: 显存利用率提升 4 倍, 吞吐提升 5-10 倍。

### Q8: LLM 蒸馏怎么做?

**答**: 用大模型的输出去训练小模型。
- **Logit 蒸馏**: 让学生模型拟合教师模型的 logits 分布
- **Feature 蒸馏**: 让学生模型拟合教师模型的中间层特征
- **Instruction 蒸馏**: 用教师模型生成指令-回答对, 用 SFT 训练学生
- **效果**: 小模型(7B) 可以保留大模型(70B) 80-90% 的能力。

## 第 5 章：数据流水线设计 —— 从 Common Crawl 到可训练 token

### 5.1 数据工程先于模型工程

大模型训练中，模型结构通常不是第一个瓶颈，数据才是。

同样的参数规模、同样的训练 token 数量，数据质量差异可能造成显著的能力差距。

数据流水线的目标不是“尽可能多地下载文本”，而是建立可审计、可复现、可回滚的数据产品。

一个成熟的数据流水线至少要回答以下问题：

1. 这条文本来自哪里？
2. 它在什么时候被抓取或生成？
3. 是否包含重复内容？
4. 是否包含隐私、恶意代码或版权风险？
5. 清洗前后损失了多少内容？
6. 进入训练集后被采样了多少次？
7. 如果发现问题，能否定位到原始文档并删除？

数据流水线可以抽象为：

```text
原始来源
  ↓
抓取与落盘
  ↓
解析与规范化
  ↓
质量过滤
  ↓
安全与隐私过滤
  ↓
精确去重
  ↓
近似去重
  ↓
语言识别与分类
  ↓
分片与版本化
  ↓
Tokenizer
  ↓
Packing
  ↓
训练样本
```

每个阶段都应该有输入、输出、指标、错误样本和版本号。

不要把所有逻辑塞进一个“清洗脚本”。

清洗脚本一旦运行数小时，任何中途失败都会让排查成本急剧上升。

更稳妥的做法是每个阶段输出不可变的中间产物。

例如：

```text
s3://dataset/raw/crawl=2026-07-01/*.warc.zst
s3://dataset/parsed/parser=v3/*.jsonl.zst
s3://dataset/filtered/filter=v8/*.jsonl.zst
s3://dataset/dedup/dedup=v5/*.jsonl.zst
s3://dataset/tokens/tokenizer=qwen2/*.bin
```

### 5.2 Common Crawl 数据获取思路

Common Crawl 通常以 WARC、WAT 和 WET 等格式提供网页抓取结果。

WARC 保存较完整的抓取记录。

WET 更接近提取后的纯文本。

WAT 保存网页元数据和链接信息。

训练语料的第一原则是先确认数据许可和用途边界。

技术上能下载，不等于业务上可以直接用于训练。

工程上建议为每个数据源建立 source manifest：

```json
{
  "source_id": "commoncrawl-2026-06",
  "source_type": "common_crawl",
  "snapshot": "CC-MAIN-2026-06",
  "license_policy": "internal-review-required",
  "retrieved_at": "2026-07-10T08:00:00Z",
  "parser_version": "warcio-1.7",
  "hash_algorithm": "sha256",
  "owner": "data-platform"
}
```

下载阶段不要把所有内容直接读入内存。

WARC 文件可能达到数 GB，正确姿势是流式读取。

下面是一个最小的流式读取示例：

```python
from pathlib import Path
from warcio.archiveiterator import ArchiveIterator


def iter_warc_text(path: str):
    """逐条读取 WARC 中的响应正文，不把整个文件载入内存。"""
    with open(path, "rb") as stream:
        for record in ArchiveIterator(stream):
            if record.rec_type != "response":
                continue
            content_type = record.http_headers.get_header("Content-Type", "")
            if "text/html" not in content_type:
                continue
            payload = record.content_stream().read()
            yield {
                "url": record.rec_headers.get_header("WARC-Target-URI", ""),
                "payload": payload,
                "content_type": content_type,
            }
```

生产环境不应该忽略读取异常。

单个损坏记录不应导致整片数据任务失败。

但也不能静默丢弃，否则最终 token 数量无法解释。

推荐同时维护成功计数和失败计数：

```python
from collections import Counter

stats = Counter()
for item in iter_warc_text("part-000.warc"):
    try:
        text = item["payload"].decode("utf-8", errors="strict")
    except UnicodeDecodeError:
        stats["decode_error"] += 1
        continue
    stats["response_ok"] += 1
    process(text)

print(dict(stats))
```

对于超大规模数据，下载任务应使用可重试、可断点、可校验的对象存储客户端。

写入对象存储前先写临时 key。

上传完成并校验 checksum 后，再通过 rename manifest 的方式发布。

不要让训练任务读取一个仍在上传中的目录。

### 5.3 HTML 解析与文本规范化

网页文本通常包含导航、脚本、广告、评论区、重复页脚和模板噪声。

简单地删除所有 HTML 标签会把列表、标题和段落结构全部打碎。

文本规范化应该尽量保留语义边界。

常见处理步骤如下：

1. 删除 script、style、noscript 和模板节点。
2. 使用可读性算法提取主体内容。
3. 将标题、列表和段落转换为稳定的换行。
4. 解码 HTML entity。
5. 统一 Unicode 规范化形式。
6. 合并重复空白，但保留段落分隔。
7. 删除明显的 URL、邮箱和导航噪声。
8. 保留原始 URL 与解析器版本。

一个可运行的轻量解析器如下：

```python
import html
import re
import unicodedata
from bs4 import BeautifulSoup


def normalize_text(text: str) -> str:
    text = html.unescape(text)
    text = unicodedata.normalize("NFKC", text)
    text = text.replace("\r\n", "\n").replace("\r", "\n")
    text = re.sub(r"[ \t]+", " ", text)
    text = re.sub(r"\n{3,}", "\n\n", text)
    return text.strip()


def html_to_text(source: bytes) -> str:
    soup = BeautifulSoup(source, "html.parser")
    for node in soup(["script", "style", "noscript", "svg", "template"]):
        node.decompose()
    blocks = []
    for node in soup.find_all(["h1", "h2", "h3", "p", "li", "pre"]):
        value = normalize_text(node.get_text(" ", strip=True))
        if value:
            blocks.append(value)
    return "\n\n".join(blocks)
```

这个解析器适合教学和小规模验证，不等同于生产级网页抽取器。

生产环境需要保存 raw HTML 的 hash，以便解析器升级后重跑。

同一 URL 在不同时间抓取的内容应被视为不同版本。

不要用 URL 作为唯一主键。

推荐使用：

```text
record_id = sha256(source_id + warc_record_id + payload_hash)
```

### 5.4 质量过滤指标

质量过滤不应该只靠一个长度阈值。

过短文本可能是高价值 API 文档。

很长文本可能是循环生成的垃圾内容。

推荐组合多个弱特征，而不是依赖单一规则。

常用特征包括：

| 特征 | 含义 | 风险 |
| :--- | :--- | :--- |
| 字符数 | 文档长度 | 太短可能缺乏上下文 |
| token 数 | 模型视角长度 | 受 tokenizer 影响 |
| 字符类别比例 | 中英文、数字、符号比例 | 可发现乱码 |
| 行重复率 | 模板和刷屏检测 | 高重复通常是低质 |
| URL 密度 | 链接农场检测 | 过高可能是广告页 |
| 标点密度 | 结构和乱码线索 | 需按语言校准 |
| 词典覆盖率 | 自然语言程度 | 对专业文本不友好 |
| HTML 噪声率 | 页面抽取质量 | 可定位解析失败 |

定义重复行比例：

$$
R_{line}=1-\frac{|\text{unique lines}|}{|\text{all lines}|}
$$

定义符号比例：

$$
R_{symbol}=\frac{N_{symbol}}{N_{all\ characters}}
$$

一个简单的质量分数可以写成：

$$
Q=w_l f_{length}+w_r(1-R_{line})+w_c f_{charset}+w_s f_{structure}
$$

其中每个子分数都需要截断到 $[0,1]$。

不要把这个分数当作真实质量标签。

它只用于排序、抽样和人工复核。

可以先按质量分数分桶：

```python
from dataclasses import dataclass
import re


@dataclass
class Quality:
    chars: int
    line_repeat: float
    symbol_ratio: float
    score: float


def quality_score(text: str) -> Quality:
    lines = [line.strip() for line in text.splitlines() if line.strip()]
    chars = len(text)
    if not lines:
        return Quality(0, 1.0, 1.0, 0.0)
    line_repeat = 1 - len(set(lines)) / len(lines)
    symbols = len(re.findall(r"[^\w\s\u4e00-\u9fff]", text))
    symbol_ratio = symbols / max(chars, 1)
    length_score = min(chars / 500, 1.0)
    repeat_score = max(0.0, 1.0 - line_repeat * 2)
    symbol_score = max(0.0, 1.0 - max(symbol_ratio - 0.35, 0) * 2)
    score = 0.45 * length_score + 0.35 * repeat_score + 0.20 * symbol_score
    return Quality(chars, line_repeat, symbol_ratio, score)
```

不同语言必须使用不同阈值。

中文网页的标点、英文文档的代码符号和数学文档的 LaTeX 都会改变统计分布。

规则上线前至少要抽样查看：

1. 被保留的高分样本。
2. 被过滤的低分样本。
3. 分数边界附近的样本。
4. 每种语言各自的样本。
5. 每个来源各自的样本。

### 5.5 精确去重

精确去重用于消除字节级或规范化后完全一致的文档。

最简单的键是规范化文本的 SHA-256：

$$
key=SHA256(normalize(text))
$$

分布式流水线中不能把所有 hash 放进单机 Python set。

可以使用排序、外部存储或分布式键值系统。

教学版本如下：

```python
import hashlib


def text_hash(text: str) -> str:
    normalized = normalize_text(text)
    return hashlib.sha256(normalized.encode("utf-8")).hexdigest()


def exact_deduplicate(records):
    seen = set()
    for record in records:
        key = text_hash(record["text"])
        if key in seen:
            continue
        seen.add(key)
        record["exact_hash"] = key
        yield record
```

生产规模可以将 hash 写入按前缀分区的文件：

```text
hash=00/*.parquet
hash=01/*.parquet
...
hash=ff/*.parquet
```

同一分区内排序后使用唯一操作，即可减少内存压力。

精确去重应该先于近似去重。

否则大量完全重复的页面会浪费 MinHash 计算资源。

### 5.6 MinHash 与近似去重

近似去重用于发现轻微改写、模板页和复制粘贴文本。

将文本切分为 $k$-shingle：

$$
S_k(x)=\{x_i,x_{i+1},...,x_{i+k-1}\}
$$

两个文档的 Jaccard 相似度为：

$$
J(A,B)=\frac{|A\cap B|}{|A\cup B|}
$$

直接计算所有文档对的复杂度是 $O(N^2)$，不可接受。

MinHash 用多个哈希函数近似 Jaccard 相似度。

对每个文档生成签名：

$$
sig(x)=[min_{s\in S(x)}h_1(s),...,min_{s\in S(x)}h_m(s)]
$$

再用 LSH 将相似签名放入相同桶中。

以下代码演示字符 shingle 和签名计算：

```python
import hashlib


def shingles(text: str, size: int = 5):
    compact = " ".join(text.split())
    return {compact[i:i + size] for i in range(max(0, len(compact) - size + 1))}


def stable_hash(value: str, seed: int) -> int:
    payload = f"{seed}:{value}".encode("utf-8")
    return int.from_bytes(hashlib.blake2b(payload, digest_size=8).digest(), "big")


def minhash(text: str, num_perm: int = 64):
    values = shingles(text)
    if not values:
        return tuple([2**64 - 1] * num_perm)
    return tuple(min(stable_hash(item, seed) for item in values)
                 for seed in range(num_perm))


def signature_similarity(a, b) -> float:
    if len(a) != len(b):
        raise ValueError("signature length mismatch")
    return sum(x == y for x, y in zip(a, b)) / len(a)
```

这是教学实现，不应直接用于亿级文档的生产去重。

生产实现通常使用 Spark、Flink、Dataflow 或专用数据处理库。

一个重要的工程选择是“文档级去重”还是“段落级去重”。

文档级去重更保守，容易丢掉包含不同段落的页面。

段落级去重更细，但会破坏上下文和文档结构。

建议先文档级去重，再在训练采样阶段处理高频段落。

### 5.7 近重复的保留策略

发现近重复集合后，不要随机保留一条。

可以根据以下规则选择代表文档：

1. 质量分更高的优先。
2. 结构更完整的优先。
3. 来源可信度更高的优先。
4. 抓取时间更新的优先。
5. 语言标签更确定的优先。
6. 许可证信息更清晰的优先。

近重复集合可以表示为图。

文档是节点，相似度超过阈值的文档之间有边。

连通分量中的代表节点可以进入主训练集。

但阈值不能在所有领域统一。

新闻、代码、百科和论坛的天然重复率不同。

### 5.8 PII 与安全过滤

大模型数据处理必须把个人信息保护放在信任边界内。

常见 PII 包括：

- 手机号码。
- 电子邮箱。
- 身份证件号码。
- 银行卡号。
- API key 和访问令牌。
- 内网地址和数据库连接串。
- 未公开的个人住址。

正则表达式适合作为第一层高召回过滤器。

它不适合作为最终判定器。

示例：

```python
import re

EMAIL = re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.-]+\b")
PHONE = re.compile(r"(?<!\d)(?:\+?86[- ]?)?1[3-9]\d{9}(?!\d)")
SECRET = re.compile(r"(?i)\b(?:api[_-]?key|secret|token)\s*[:=]\s*[^\s]+")


def redact_pii(text: str) -> tuple[str, dict]:
    counts = {
        "email": len(EMAIL.findall(text)),
        "phone": len(PHONE.findall(text)),
        "secret": len(SECRET.findall(text)),
    }
    text = EMAIL.sub("[REDACTED_EMAIL]", text)
    text = PHONE.sub("[REDACTED_PHONE]", text)
    text = SECRET.sub("[REDACTED_SECRET]", text)
    return text, counts
```

不要把原始 PII 文本写入普通日志。

错误样本需要脱敏后再进入标注系统。

对密钥类数据，最好在下载后立刻扫描，而不是等到训练前。

代码数据还需要扫描私钥、云凭证和数据库 URI。

### 5.9 语言识别与混合比例

多语言模型要显式管理语言比例。

如果直接按网页数量采样，长文档和短文档会产生严重偏差。

更合理的统计单位是 token，而不是文档数。

对于语言 $l$，其训练采样概率可以定义为：

$$
P(l)=\frac{n_l^\alpha}{\sum_j n_j^\alpha}
$$

其中 $n_l$ 是语言 token 数，$0<\alpha<1$ 用于提高低资源语言比例。

当 $\alpha=1$ 时完全按数据量采样。

当 $\alpha<1$ 时会对大语言降权。

但过度上采样低资源语言会造成重复曝光和过拟合。

工程上需要同时记录：

```text
language=zh
raw_tokens=...
filtered_tokens=...
sampled_tokens=...
repeat_factor=sampled_tokens/filtered_tokens
```

语言识别错一条通常影响不大。

大量误判会改变混合数据的能力边界。

建议在每个语言桶中抽样人工审核。

### 5.10 Tokenizer 设计

Tokenizer 将字符序列映射为 token 序列。

训练成本通常按 token 计量，因此 tokenizer 直接影响成本和上下文长度。

同一段中文在不同 tokenizer 下可能对应完全不同的 token 数。

常见 tokenizer 方法包括 BPE、Unigram 和 WordPiece。

BPE 的核心操作是不断合并高频相邻符号对。

若词表为 $V$，序列 token 数为 $T$，则训练和推理的主要复杂度通常与 $T$ 成正比或更高。

tokenizer 评估至少包括：

1. 平均压缩率。
2. 各语言 token/字符比。
3. 代码和数学符号覆盖率。
4. 未知 token 比例。
5. 特殊 token 的边界行为。
6. 长文本编码速度。

压缩率可以写成：

$$
C=\frac{\text{原始字符数}}{\text{token 数}}
$$

但压缩率高不一定代表 tokenizer 更好。

边界错误会影响模型学习词法和格式。

### 5.11 Tokenizer 的最小训练示例

下面示例使用 Hugging Face tokenizers 训练一个 BPE tokenizer。

```python
from pathlib import Path
from tokenizers import Tokenizer
from tokenizers.models import BPE
from tokenizers.pre_tokenizers import ByteLevel
from tokenizers.trainers import BpeTrainer


def train_tokenizer(files, output: str):
    tokenizer = Tokenizer(BPE(unk_token="<unk>"))
    tokenizer.pre_tokenizer = ByteLevel(add_prefix_space=False)
    trainer = BpeTrainer(
        vocab_size=32000,
        min_frequency=2,
        special_tokens=["<pad>", "<bos>", "<eos>", "<unk>", "<|user|>", "<|assistant|>"],
    )
    tokenizer.train(files, trainer)
    tokenizer.save(output)
    return tokenizer


if __name__ == "__main__":
    paths = [str(path) for path in Path("clean_text").glob("*.txt")]
    tok = train_tokenizer(paths, "tokenizer.json")
    encoded = tok.encode("你好，世界。hello world")
    print(encoded.tokens)
    print(encoded.ids)
```

训练 tokenizer 的语料必须覆盖最终任务域。

如果后续大量加入代码、数学或中文数据，再训练一个全新词表会影响已有 checkpoint 的 embedding 对齐。

因此 tokenizer 版本是模型版本的一部分。

### 5.12 特殊 token 与对话模板

对话模型必须规定角色边界和停止条件。

常见角色包括 system、user、assistant 和 tool。

模板错误会导致模型学习到错误的对话边界。

不要在数据中混用多个模板而不记录来源。

建议将模板渲染写成纯函数：

```python
from dataclasses import dataclass


@dataclass
class Message:
    role: str
    content: str


def render_chat(messages: list[Message], add_generation_prompt=True) -> str:
    chunks = ["<|begin_of_text|>"]
    for message in messages:
        if message.role not in {"system", "user", "assistant", "tool"}:
            raise ValueError(f"unknown role: {message.role}")
        chunks.append(f"<|{message.role}|>\n{message.content}<|end|>")
    if add_generation_prompt:
        chunks.append("<|assistant|>\n")
    return "\n".join(chunks)
```

模板升级必须有兼容策略。

已经训练过的对话数据不能悄悄换模板后重新混合。

### 5.13 Sharding 与数据版本

训练输入应拆成多个大小相近的 shard。

每个 shard 记录：

```json
{
  "shard_id": "train-000123",
  "records": 1048576,
  "tokens": 183421337,
  "bytes": 734003200,
  "sha256": "...",
  "dataset_version": "clean-v8-dedup-v5",
  "tokenizer_version": "tok-v3",
  "created_at": "2026-07-12T10:00:00Z"
}
```

训练前读取 manifest，而不是扫描目录猜测文件。

manifest 能保证不同机器看到同一组输入。

如果某个 shard 损坏，任务可以精确定位和替换。

### 5.14 Token Packing

将短样本直接 padding 到最大长度会浪费大量计算。

Packing 将多个样本拼接到一个固定长度序列中。

对于因果语言模型，需要在样本边界插入 EOS 或构造 block diagonal attention mask。

简单的 EOS packing：

```python
from itertools import chain


def pack_sequences(sequences, max_length, eos_id):
    buffer = []
    for sequence in sequences:
        buffer.extend(sequence)
        buffer.append(eos_id)
        while len(buffer) >= max_length:
            yield buffer[:max_length]
            buffer = buffer[max_length:]
    if buffer:
        yield buffer + [eos_id] * (max_length - len(buffer))
```

如果不同样本之间不允许互相注意，需要额外的 attention mask。

只插入 EOS 而不做 mask 会让模型看到前一个样本的上下文。

这可能是可接受的，也可能造成任务边界污染。

选择取决于训练目标和数据类型。

### 5.15 数据缓存与吞吐

GPU 等待数据是最容易被忽略的训练成本。

应观测：

- dataloader 等待时间。
- CPU 解码时间。
- 网络读取吞吐。
- page cache 命中率。
- batch 组装时间。
- GPU utilization。

一个最小的计时器如下：

```python
import time


def timed_loader(loader):
    end = time.perf_counter()
    for batch in loader:
        data_time = time.perf_counter() - end
        start = time.perf_counter()
        yield batch, data_time
        compute_time = time.perf_counter() - start
        end = time.perf_counter()
        print({"data_s": data_time, "compute_s": compute_time})
```

生产环境可以把 token 数据保存为 mmap、Arrow、Parquet 或专用二进制格式。

格式不是目的，稳定吞吐和可复现才是目的。

### 5.16 数据流水线完整样板

下面代码把规范化、质量评分、脱敏和去重串起来。

```python
import json
from pathlib import Path


def build_clean_dataset(input_path: str, output_path: str):
    seen = set()
    counters = {}

    def inc(name):
        counters[name] = counters.get(name, 0) + 1

    with open(input_path, encoding="utf-8") as source, \
         open(output_path, "w", encoding="utf-8") as target:
        for line in source:
            inc("raw")
            record = json.loads(line)
            text = normalize_text(record.get("text", ""))
            if len(text) < 80:
                inc("too_short")
                continue
            quality = quality_score(text)
            if quality.score < 0.35:
                inc("low_quality")
                continue
            text, pii = redact_pii(text)
            key = text_hash(text)
            if key in seen:
                inc("exact_duplicate")
                continue
            seen.add(key)
            target.write(json.dumps({
                "text": text,
                "source": record.get("source", "unknown"),
                "quality": quality.__dict__,
                "pii": pii,
                "hash": key,
            }, ensure_ascii=False) + "\n")
            inc("kept")

    print(counters)


if __name__ == "__main__":
    build_clean_dataset("raw.jsonl", "clean.jsonl")
```

代码中的 `seen` 仅适合小规模验证。

生产任务需要替换为外部排序或分布式去重存储。

### 5.17 工业案例：LLaMA-3 风格的数据配比思路

LLaMA-3 代表了“扩大高质量公开数据并强化代码和多语言覆盖”的路线。

学习其工程思想时，不应机械复制具体数据规模。

真正值得借鉴的是：

1. 预训练数据有明确的质量筛选流程。
2. 训练不同阶段使用不同数据混合策略。
3. 代码和数学数据会单独评估，而不是只看总 loss。
4. tokenizer 和上下文长度升级需要配套训练计划。
5. 数据、模型和评测版本要绑定。

### 5.18 工业案例：Qwen 的多语言与代码数据

Qwen 系列体现了中文、英文、代码和数学混合数据的工程挑战。

中文数据并非只要增加网页数量就能提升能力。

更重要的是文档质量、领域覆盖、去重和 token 分配。

代码数据还需要：

- 语法解析。
- 编译或静态检查。
- 仓库级去重。
- 许可证过滤。
- 文档与实现配对。

### 5.19 工业案例：DeepSeek 的数据效率视角

DeepSeek 相关公开实践经常强调数据质量、训练效率和数据配比。

从工程角度看，可迁移的经验是：

1. 先建立小模型实验闭环，再扩大数据和模型。
2. 用 ablation 判断数据配比，而不是凭直觉加数据。
3. 对关键领域进行独立评测。
4. 将训练 token、有效 token 和重复 token 分开统计。
5. 训练效率和模型能力必须同时优化。

### 5.20 数据流水线失败案例

**失败案例一：重复网页导致 loss 看似下降。**

训练集包含大量相同模板页面。

训练 loss 很快下降，但验证集泛化很差。

根因是 token 数被重复内容虚高。

修复方法是增加精确去重、近似去重和文档级抽样检查。

**失败案例二：把测试集混入预训练。**

总训练指标正常，但 benchmark 分数异常高。

根因是数据来源没有做 split 级隔离。

修复方法是对评测集建立 hash 黑名单，并在数据发布时执行泄漏检测。

**失败案例三：过滤规则只支持英文。**

中文、日文和代码数据被误判为低质量。

根因是字符比例阈值没有按语言分桶。

修复方法是先语言识别，再使用语言专属质量模型。

### 5.21 数据工程面试题

**问题 1：为什么必须先精确去重再 MinHash？**

回答：精确重复的文档数量可能非常大，先去除能显著减少 shingle、签名和候选桶的计算量；同时避免一个完全重复的页面簇主导近似去重阈值。

**问题 2：为什么训练数据要用 token 统计而不是文档统计？**

回答：文档长度分布通常长尾严重，按文档数采样会让短文本和长文本贡献失真；训练成本、梯度更新次数和上下文覆盖都更接近 token 维度。

**问题 3：如何证明清洗没有误伤高价值数据？**

回答：保留规则版本、记录每个过滤原因、对每个语言和来源抽样人工审核，并比较过滤前后的能力评测与数据分布。

**问题 4：为什么 tokenizer 变了不能直接继续训练？**

回答：token id 到 embedding 的映射发生变化，旧 checkpoint 的 embedding 与 lm head 不再对应；除非做兼容扩词和权重迁移，否则会破坏已有参数语义。

**问题 5：如何处理训练数据删除请求？**

回答：为样本保存可追溯的来源和 hash，先从数据 manifest 中移除，再重建受影响 shard；若已训练进模型，还需要评估重训、遗忘或下游过滤策略的合规要求。

### 5.22 本章检查清单

- [ ] 每个数据源有 manifest 和许可证备注。
- [ ] 原始数据、中间数据和最终数据版本可追溯。
- [ ] 解析失败、编码失败和过滤原因有计数。
- [ ] 完全重复和近似重复分阶段处理。
- [ ] PII 与密钥扫描不写入明文日志。
- [ ] 不同语言使用独立质量分布和抽样策略。
- [ ] tokenizer 版本与模型 checkpoint 绑定。
- [ ] packing 后的有效 token 数可计算。
- [ ] 数据可以重跑、替换和回滚。

## 第 6 章：预训练监控与容错 —— 让长任务可观测、可恢复

### 6.1 训练不是一个 while 循环

小规模实验可以把训练理解为“取 batch、算 loss、反向传播、更新参数”。

当训练持续数小时、数天甚至数周时，训练系统更像一个分布式数据库任务。

它需要：

1. 状态持久化。
2. 运行时监控。
3. 失败自动恢复。
4. 异常样本隔离。
5. 资源和成本控制。
6. 版本和血缘追踪。

没有监控的训练，成功与失败都难以解释。

没有容错的训练，任何一次节点抢占都可能浪费大量算力。

### 6.2 训练状态的层次

完整训练状态至少分为四层：

```text
模型状态：参数、buffer、混合精度权重
优化状态：Adam 一阶矩、二阶矩、step
调度状态：学习率、warmup、梯度累积计数
数据状态：epoch、batch index、sampler、随机数
```

在分布式场景还要保存：

- world size。
- rank 拓扑。
- shard 划分方式。
- 版本号。
- 数据 manifest hash。
- tokenizer hash。
- 代码 commit。

如果恢复时这些信息不一致，训练可以“跑起来”，但结果可能不可复现。

### 6.3 核心指标分类

训练监控指标可以分成四类。

**优化指标**：

- train loss。
- validation loss。
- perplexity。
- gradient norm。
- update norm。
- learning rate。

**性能指标**：

- tokens per second。
- samples per second。
- MFU。
- GPU utilization。
- 显存占用。
- data loading time。

**稳定性指标**：

- NaN/Inf 次数。
- loss spike 次数。
- skipped step 次数。
- checkpoint 成功率。
- 节点重启次数。

**质量指标**：

- 领域验证集 loss。
- 代码执行通过率。
- 数学题准确率。
- 长上下文一致性。
- 安全拒答率。

不要只看训练 loss。

训练 loss 下降可能意味着数据泄漏、重复或过拟合。

### 6.4 Loss 与 Perplexity

因果语言建模的平均负对数似然为：

$$
L=-\frac{1}{T}\sum_{t=1}^{T}\log p_\theta(x_t|x_{<t})
$$

perplexity 定义为：

$$
PPL=\exp(L)
$$

如果使用不同 tokenizer，PPL 不能直接横向比较。

因为 token 的切分粒度不同，熵的测量单位不同。

跨 tokenizer 比较时可以同时报告 bits per byte 或 byte-level metric。

监控时建议同时记录：

```text
loss_mean
loss_std
loss_min
loss_max
valid_token_count
masked_token_count
ppl = exp(loss_mean)
```

### 6.5 Loss Spike 的定义

loss spike 没有唯一标准，需要结合历史窗口定义。

一种稳健的 z-score 规则是：

$$
z_t=\frac{L_t-\mu_{t-k:t-1}}{\sigma_{t-k:t-1}+\epsilon}
$$

当 $z_t>z_{threshold}$ 时触发告警。

但训练初期和学习率切换点通常天然波动较大。

因此阈值应该按训练阶段设置。

一个简单的滑动窗口检测器：

```python
from collections import deque
import math
import statistics


class LossSpikeDetector:
    def __init__(self, window=50, z_threshold=5.0):
        self.values = deque(maxlen=window)
        self.z_threshold = z_threshold

    def update(self, loss: float) -> dict:
        value = float(loss)
        finite = math.isfinite(value)
        result = {"loss": value, "finite": finite, "spike": False}
        if not finite:
            result["spike"] = True
            result["reason"] = "non_finite"
            return result
        if len(self.values) >= 10:
            mean = statistics.fmean(self.values)
            std = statistics.pstdev(self.values) or 1e-8
            z = (value - mean) / std
            result["z"] = z
            result["spike"] = z > self.z_threshold
            if result["spike"]:
                result["reason"] = "z_score"
        self.values.append(value)
        return result
```

只根据单个 batch 触发自动停止容易误报。

更稳妥的策略是连续两个或三个窗口异常才暂停。

### 6.6 梯度范数监控

梯度范数可以帮助区分数据异常和优化器异常。

常用的 L2 范数为：

$$
||g||_2=\sqrt{\sum_i g_i^2}
$$

PyTorch 提供了 `clip_grad_norm_`，它既可裁剪也可返回原始范数：

```python
import torch


def grad_norm(parameters):
    grads = [p.grad.detach() for p in parameters
             if p.grad is not None]
    if not grads:
        return 0.0
    total = torch.stack([
        g.float().norm(2) ** 2 for g in grads
    ]).sum()
    return float(total.sqrt().item())


loss.backward()
raw_norm = grad_norm(model.parameters())
clipped_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
optimizer.step()
```

梯度突然变大可能来自：

1. 学习率过高。
2. batch 中存在异常长序列。
3. loss mask 错误导致有效 token 数为零。
4. 混合精度溢出。
5. 某层权重初始化或归一化异常。
6. 数据中出现极端 token 模式。

### 6.7 Update-to-weight ratio

只看梯度范数还不够。

可以监控参数更新相对权重的比例：

$$
R=\frac{||\Delta W||_2}{||W||_2+\epsilon}
$$

如果 $R$ 长时间极小，可能学习率太低或梯度消失。

如果 $R$ 突然过大，可能导致模型破坏已学表示。

示例代码：

```python
@torch.no_grad()
def update_ratio(before, after):
    numerator = 0.0
    denominator = 0.0
    for old, new in zip(before, after):
        numerator += (new.float() - old.float()).pow(2).sum().item()
        denominator += old.float().pow(2).sum().item()
    return (numerator ** 0.5) / ((denominator ** 0.5) + 1e-12)
```

不需要每步保存全量参数。

可以每隔固定步数对少数代表层做采样。

### 6.8 学习率和有效 batch size

学习率日志必须包含 optimizer step，而不是只记录 dataloader step。

如果使用梯度累积：

$$
B_{effective}=B_{micro}\times N_{devices}\times K_{accumulation}
$$

一个常见错误是每个 micro batch 都调用 scheduler.step()。

这会让 warmup 实际缩短 $K$ 倍。

正确做法是每次真正更新参数后推进 scheduler。

```python
for micro_step, batch in enumerate(loader):
    with autocast_context():
        loss = model_loss(batch) / accumulation_steps
    scaler.scale(loss).backward()

    if (micro_step + 1) % accumulation_steps != 0:
        continue

    scaler.unscale_(optimizer)
    grad_norm_value = torch.nn.utils.clip_grad_norm_(
        model.parameters(), max_norm=1.0
    )
    scaler.step(optimizer)
    scaler.update()
    scheduler.step()
    optimizer.zero_grad(set_to_none=True)
```

### 6.9 混合精度与 NaN 传播

FP16 的指数范围小，更容易溢出。

BF16 的指数范围接近 FP32，通常更适合大模型训练。

无论使用哪种精度，都应该监控：

- 输入是否包含 NaN。
- logits 是否包含 Inf。
- loss 是否有限。
- 梯度是否有限。
- GradScaler 的 scale 是否不断下降。

一个通用检查器：

```python
import torch


def assert_finite(name, tensor):
    if not torch.isfinite(tensor).all():
        bad = (~torch.isfinite(tensor)).sum().item()
        raise FloatingPointError(f"{name} has {bad} non-finite values")


def check_model_finite(model):
    for name, parameter in model.named_parameters():
        assert_finite(f"parameter:{name}", parameter.data)
        if parameter.grad is not None:
            assert_finite(f"gradient:{name}", parameter.grad)
```

调试时可以只在异常 batch 上执行完整检查。

否则每层每步检查会增加明显开销。

### 6.10 原子 Checkpoint

checkpoint 写入失败时，最危险的情况不是任务立即报错，而是留下一个看起来完整但实际上截断的文件。

正确方案是临时文件加原子替换：

```python
import os
import tempfile
import torch


def atomic_torch_save(state, path: str):
    directory = os.path.dirname(os.path.abspath(path)) or "."
    fd, temporary = tempfile.mkstemp(prefix=".ckpt-", dir=directory)
    os.close(fd)
    try:
        torch.save(state, temporary)
        with open(temporary, "rb") as stream:
            os.fsync(stream.fileno())
        os.replace(temporary, path)
    except Exception:
        if os.path.exists(temporary):
            os.remove(temporary)
        raise
```

对象存储没有本地 POSIX rename 语义时，需要通过完成标记实现发布：

```text
checkpoint.step1000.parts/*
checkpoint.step1000.complete
```

加载器只接受存在 complete marker 的 checkpoint。

### 6.11 Checkpoint 内容设计

推荐的 checkpoint 结构：

```python
checkpoint = {
    "format_version": 3,
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),
    "scheduler": scheduler.state_dict(),
    "scaler": scaler.state_dict() if scaler else None,
    "global_step": global_step,
    "epoch": epoch,
    "micro_step": micro_step,
    "rng": capture_rng_state(),
    "data": {
        "manifest_hash": manifest_hash,
        "sampler_state": sampler.state_dict(),
    },
    "meta": {
        "git_commit": git_commit,
        "tokenizer_hash": tokenizer_hash,
        "world_size": world_size,
    },
}
```

不要把不必要的大型缓存塞入 checkpoint。

但用于复现训练顺序的 sampler 状态不能省略。

### 6.12 RNG 状态保存与恢复

随机状态至少包含 Python、NumPy、CPU torch 和 CUDA torch。

```python
import random
import numpy as np
import torch


def capture_rng_state():
    return {
        "python": random.getstate(),
        "numpy": np.random.get_state(),
        "torch": torch.get_rng_state(),
        "cuda": torch.cuda.get_rng_state_all() if torch.cuda.is_available() else None,
    }


def restore_rng_state(state):
    random.setstate(state["python"])
    np.random.set_state(state["numpy"])
    torch.set_rng_state(state["torch"])
    if state["cuda"] is not None and torch.cuda.is_available():
        torch.cuda.set_rng_state_all(state["cuda"])
```

分布式 dataloader 还需要保存 sampler epoch。

只恢复 torch seed 而不恢复数据 sampler，仍然可能读取不同 batch。

### 6.13 Checkpoint 保留策略

保存每一步 checkpoint 会产生过多对象和高昂存储成本。

常用保留策略是：

1. 保留最近 $N$ 个。
2. 保留验证集最优的 $K$ 个。
3. 保留每个训练阶段的里程碑。
4. 保留最终发布候选。

删除旧 checkpoint 前先检查是否有训练任务正在读取。

对象存储中的生命周期策略可以自动清理临时文件。

但不要让生命周期策略删除合规审计需要的版本。

### 6.14 断点续训中的数据位置

如果每次恢复都从 epoch 开头重新读取，模型会重复见到一段数据。

重复本身不一定错误，但会改变有效训练 token 数。

更严谨的方式是保存：

```text
epoch
shard_index
sample_index
micro_step
sampler_epoch
sampler_seed
```

对于流式数据，保存 byte offset 或 shard cursor。

对于 shuffle buffer，保存完整 buffer 很昂贵。

可以接受近似恢复，但必须在实验记录中注明“数据顺序非严格复现”。

### 6.15 DDP 训练中的保存协议

DDP 下通常只由 rank 0 负责写 checkpoint。

其他 rank 需要在保存前后通过 barrier 同步。

```python
import torch.distributed as dist


def save_rank_zero(state, path, rank):
    if rank == 0:
        atomic_torch_save(state, path)
    dist.barrier()


def load_before_training(model, optimizer, path, device):
    dist.barrier()
    checkpoint = torch.load(path, map_location=device, weights_only=False)
    model.load_state_dict(checkpoint["model"])
    optimizer.load_state_dict(checkpoint["optimizer"])
    dist.barrier()
    return checkpoint
```

如果 rank 0 写盘速度远慢于其他 rank，所有 rank 会在 barrier 等待。

可以使用独立保存进程或异步 checkpoint，但必须保证参数快照一致。

### 6.16 FSDP/分片状态的注意点

FSDP 将参数、梯度和优化器状态分片到多个 rank。

不能简单地对每个 rank 调用普通 `model.state_dict()` 并认为得到完整模型。

保存前需要选择 full、sharded 或 local state dict。

工程选择取决于：

- 是否需要单卡推理。
- checkpoint 大小。
- 保存速度。
- 恢复集群规模是否变化。
- 是否支持跨版本加载。

原则是发布 checkpoint 和训练 checkpoint 分离。

训练 checkpoint 可以是分片格式。

发布 checkpoint 通常需要额外导出成可推理格式。

### 6.17 异常处理策略

异常处理的目的不是吞掉所有错误。

应该区分：

| 错误类型 | 策略 |
| :--- | :--- |
| 瞬时网络错误 | 重试并退避 |
| 节点抢占 | 自动恢复 |
| 单个坏样本 | 记录并跳过 |
| CUDA OOM | 降低 batch 或终止 |
| loss NaN | 回滚 checkpoint |
| 模型结构错误 | 立即失败 |
| 数据 manifest 不一致 | 立即失败 |

“立即失败”比“静默继续”更安全。

例如加载了错误 tokenizer，训练继续跑几小时才发现，成本远高于启动时失败。

### 6.18 自动回滚训练循环

下面示例展示检测异常后回滚到最近健康 checkpoint。

```python
import copy
import math


def train_with_rollback(model, optimizer, scheduler, loader,
                        save_fn, load_fn, max_bad_steps=2):
    bad_steps = 0
    for step, batch in enumerate(loader):
        optimizer.zero_grad(set_to_none=True)
        loss = model_loss(model, batch)
        if not math.isfinite(float(loss.detach())):
            bad_steps += 1
            if bad_steps > max_bad_steps:
                load_fn()
                bad_steps = 0
            continue

        loss.backward()
        norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        if not math.isfinite(float(norm)):
            load_fn()
            continue
        optimizer.step()
        scheduler.step()
        bad_steps = 0
        if step % 100 == 0:
            save_fn(step)
```

示例省略了分布式同步和 AMP 细节，生产环境要让所有 rank 对异常做一致决策。

### 6.19 训练事件日志

结构化日志比拼接字符串更容易查询。

建议每个 step 记录一个事件：

```python
from dataclasses import asdict, dataclass
import json
import time


@dataclass
class TrainEvent:
    step: int
    loss: float
    lr: float
    grad_norm: float
    tokens: int
    elapsed_s: float
    checkpoint: str | None = None


def emit(event: TrainEvent):
    print(json.dumps({"time": time.time(), **asdict(event)}, ensure_ascii=False))
```

线上系统可以将事件写入 Prometheus、W&B、MLflow 或内部指标平台。

工具不是关键，字段定义和版本稳定才是关键。

### 6.20 性能指标 MFU

Model FLOPs Utilization 用于衡量实际训练吞吐接近硬件理论峰值的程度。

简化估算：

$$
MFU=\frac{F_{observed}}{F_{hardware\ peak}}
$$

其中每秒计算量可以估为：

$$
F_{observed}=tokens/s\times FLOPs/token
$$

不同模型结构对 FLOPs/token 的估算不同。

不要跨模型直接比较未经说明的 MFU。

还应同时看通信、数据和内存瓶颈。

### 6.21 训练吞吐的端到端测量

只用 GPU kernel 时间计算吞吐会高估系统性能。

端到端吞吐应从数据可用开始，到 optimizer step 完成结束。

```python
import time

start = time.perf_counter()
processed_tokens = 0
for batch in loader:
    tokens = batch["input_ids"].numel()
    loss = model(**batch).loss
    loss.backward()
    optimizer.step()
    optimizer.zero_grad(set_to_none=True)
    processed_tokens += tokens

elapsed = time.perf_counter() - start
print("tokens_per_second", processed_tokens / elapsed)
```

需要区分 warmup、稳定区间和保存 checkpoint 的区间。

### 6.22 工业案例：LLaMA-3 风格的长周期训练

大规模模型训练通常会经历多次数据、上下文和配方调整。

可迁移的监控方法是：

1. 每次配方变化都记录为阶段边界。
2. 阶段边界处单独比较 loss 和能力评测。
3. checkpoint 同时保存阶段 metadata。
4. 对长时间训练设置定期恢复演练。
5. 将训练日志与最终模型 artifact 绑定。

不要因为训练作业“已经连续运行很久”就跳过 checkpoint 校验。

### 6.23 工业案例：Qwen 风格的多阶段训练

多语言、代码和数学混合训练时，总 loss 可能掩盖单一领域退化。

监控应增加 domain-specific validation：

```text
val/general_loss
val/chinese_loss
val/english_loss
val/code_loss
val/math_loss
```

当数据配比改变时，重点观察领域 loss 的斜率，而不是只看当前绝对值。

### 6.24 工业案例：DeepSeek 风格的效率意识

训练效率不仅是 GPU utilization。

更完整的效率指标包括：

- 每美元有效 token。
- 每千 token 的验证收益。
- 每次 checkpoint 的恢复成本。
- 数据读取占总时间比例。
- 通信占总时间比例。

如果增加一倍算力只得到很小能力收益，问题可能在数据或优化配方，而不是 GPU 不够多。

### 6.25 失败案例：loss spike 后继续训练

某次训练在 step 120000 出现 loss 从 2.1 跳到 9.8。

团队只观察到后续 loss 又下降，于是认为是正常噪声。

最终模型在数学和代码上出现明显退化。

复盘发现异常 batch 来自损坏的 token shard，包含大量非法 token id。

正确做法是：

1. 保存异常 batch 的 shard 和 index。
2. 回滚到 step 119500 的健康 checkpoint。
3. 隔离问题 shard。
4. 修复数据后重新计算 manifest。
5. 对比回滚前后的领域评测。

### 6.26 失败案例：checkpoint 记录了模型但没有 optimizer

任务恢复后 loss 仍然下降，看起来没有报错。

但学习率和 Adam 动量不连续，导致后续训练的收敛路径发生变化。

这种问题最难发现，因为它不是立即崩溃。

解决办法是把“可加载”测试加入 checkpoint 发布流程：

```python
state = torch.load(path, weights_only=False)
assert "model" in state
assert "optimizer" in state
assert "global_step" in state
```

### 6.27 失败案例：只在 rank 0 检查 NaN

rank 0 的 loss 是有限值，但 rank 3 的梯度出现 Inf。

各 rank 继续 all-reduce 后，最终参数被污染。

异常检查必须在 all-reduce 前或同步后进行。

可以用布尔标量做全局 OR：

```python
flag = torch.tensor([int(local_bad)], device=device)
dist.all_reduce(flag, op=dist.ReduceOp.MAX)
if flag.item():
    rollback_every_rank()
```

### 6.28 监控系统面试题

**问题 1：为什么 loss 下降不能证明训练正常？**

回答：可能存在数据泄漏、重复数据、领域退化、评测 tokenizer 不一致或异常 batch 被平均掩盖；必须结合领域验证、梯度、吞吐和数据版本观察。

**问题 2：断点续训要保存哪些随机状态？**

回答：Python、NumPy、CPU torch、CUDA torch，以及分布式 sampler 的 epoch、seed 和位置；若使用随机 augmentation，还要保存其状态或接受近似复现。

**问题 3：如何设计 checkpoint 的原子发布？**

回答：先写临时文件或临时目录，完成 checksum 和可加载校验后，再原子 rename 或创建 complete marker；加载器只信任已发布标记。

**问题 4：loss spike 后应该立刻调小学习率吗？**

回答：先定位异常来源。若是数据坏样本，应隔离并回滚；若是优化不稳定，再调整学习率、梯度裁剪或精度配置。盲目调学习率可能掩盖数据问题。

**问题 5：为什么 scheduler step 位置重要？**

回答：梯度累积时只有真正更新参数才应推进调度器，否则实际 warmup 和衰减步数会与设计不一致。

### 6.29 本章检查清单

- [ ] 训练状态包括模型、优化器、调度器、scaler 和数据位置。
- [ ] checkpoint 有版本、manifest hash 和代码 commit。
- [ ] checkpoint 使用原子发布或 complete marker。
- [ ] loss、梯度范数、学习率和有效 token 可查询。
- [ ] NaN/Inf 能在 rank 间同步。
- [ ] 最近 checkpoint 和最佳 checkpoint 分开保留。
- [ ] 已验证 checkpoint 可以加载并继续训练。
- [ ] 至少演练过一次节点中断后的恢复。
- [ ] 领域验证集不会被总 loss 掩盖。

## 第 7 章：SFT、DPO 与 RLHF —— 后训练的完整工程流程

### 7.1 后训练的目标分解

前训练让模型学会“什么样的文本像自然文本”。

后训练让模型学会“在给定任务中怎样帮助用户”。

后训练通常同时优化四类目标：

1. 指令遵循。
2. 输出格式和风格。
3. 事实性与任务正确率。
4. 安全性、拒答边界和偏好一致性。

不要把“聊天更像人”作为唯一目标。

一个模型可能语言流畅，但事实错误、工具调用失败或拒绝策略混乱。

后训练应该有清晰的任务矩阵和评测集。

### 7.2 后训练数据的基本结构

监督数据常见格式：

```json
{
  "messages": [
    {"role": "system", "content": "你是一个严谨的助手。"},
    {"role": "user", "content": "解释梯度累积。"},
    {"role": "assistant", "content": "梯度累积是..."}
  ],
  "source": "human_verified",
  "domain": "education",
  "quality": 4,
  "license": "internal"
}
```

偏好数据常见格式：

```json
{
  "prompt": "如何处理异常梯度？",
  "chosen": "先检查数据、精度和梯度范数，再决定是否回滚。",
  "rejected": "直接把学习率乘以 0.1 就行。",
  "metadata": {"domain": "training", "annotator": "expert-01"}
}
```

对话模板应在训练前统一渲染。

不要让训练脚本在不同 worker 上使用不同模板版本。

### 7.3 SFT 的损失函数

给定输入 token $x_{1:T}$，因果语言模型的损失为：

$$
L_{SFT}=-\sum_{t=1}^{T}m_t\log p_\theta(x_t|x_{<t})
$$

其中 $m_t\in\{0,1\}$ 表示该位置是否参与损失。

指令微调通常只对 assistant token 计算损失。

这样可以避免模型被迫模仿用户问题和系统提示的表面分布。

但工具调用、结构化 JSON 和多轮上下文可能需要更细粒度的 mask。

### 7.4 正确构造 assistant mask

不能用字符串长度近似 token 长度。

必须对渲染后的 token 序列建立角色边界。

一个简化版本：

```python
from transformers import AutoTokenizer


def tokenize_sft(tokenizer, prompt: str, answer: str):
    prompt_ids = tokenizer(prompt, add_special_tokens=False)["input_ids"]
    answer_ids = tokenizer(answer, add_special_tokens=False)["input_ids"]
    eos_id = tokenizer.eos_token_id
    input_ids = prompt_ids + answer_ids + [eos_id]
    labels = [-100] * len(prompt_ids) + answer_ids + [eos_id]
    return {
        "input_ids": input_ids,
        "labels": labels,
        "attention_mask": [1] * len(input_ids),
    }
```

如果 prompt 中包含多个 assistant turn，需要为每个 assistant 区间设置 mask。

如果 answer 为空，应该在数据校验阶段拒绝该样本。

### 7.5 SFT 数据质量分层

SFT 数据的数量不是唯一指标。

可以将数据分为：

| 层级 | 特征 | 用途 |
| :--- | :--- | :--- |
| A | 专家编写并验证 | 核心能力和边界 |
| B | 强模型生成后人工审校 | 扩充覆盖 |
| C | 自动生成并规则过滤 | 长尾探索 |
| D | 未验证合成数据 | 小比例实验 |

高质量数据不应与低质量数据等权混合。

可以使用采样权重：

$$
P(i)=\frac{w_i}{\sum_jw_j}
$$

权重也可以进入损失：

$$
L=\frac{\sum_i w_iL_i}{\sum_iw_i}
$$

但样本权重过大容易让少量标注样本主导训练。

### 7.6 SFT 的学习率与训练轮数

SFT 通常使用明显小于前训练的学习率。

常见原则是：

1. 全参数微调用更小学习率。
2. LoRA 适当使用更高学习率。
3. 高质量小数据更容易过拟合。
4. 训练轮数要配合独立验证集。
5. 先冻结大部分参数是排查过拟合的简单手段。

不能直接照搬某个模型的学习率。

模型大小、数据量、batch size、序列长度和优化器都会改变稳定区间。

### 7.7 完整 SFT 训练样板

下面代码展示 tokenizer、collator、梯度累积和验证流程。

```python
import torch
from torch.nn.utils.rnn import pad_sequence
from torch.utils.data import DataLoader
from transformers import AutoModelForCausalLM, AutoTokenizer


class SFTCollator:
    def __init__(self, tokenizer):
        self.pad_id = tokenizer.pad_token_id

    def __call__(self, features):
        input_ids = [torch.tensor(x["input_ids"], dtype=torch.long)
                     for x in features]
        labels = [torch.tensor(x["labels"], dtype=torch.long)
                  for x in features]
        inputs = pad_sequence(input_ids, batch_first=True,
                              padding_value=self.pad_id)
        target = pad_sequence(labels, batch_first=True,
                              padding_value=-100)
        mask = inputs.ne(self.pad_id).long()
        return {"input_ids": inputs, "labels": target,
                "attention_mask": mask}


def run_sft(model, loader, optimizer, device,
            accumulation_steps=8, max_steps=1000):
    model.train()
    optimizer.zero_grad(set_to_none=True)
    for step, batch in enumerate(loader):
        if step >= max_steps:
            break
        batch = {k: v.to(device) for k, v in batch.items()}
        loss = model(**batch).loss / accumulation_steps
        loss.backward()
        if (step + 1) % accumulation_steps != 0:
            continue
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
        if step % 100 == 0:
            print({"step": step, "loss": float(loss) * accumulation_steps})
```

实际项目还需要 scheduler、AMP、checkpoint 和验证集。

但这段代码包含了 SFT 的核心数据流。

### 7.8 LoRA 的低秩适配

LoRA 将权重更新表示为低秩矩阵：

$$
W'=W+\frac{\alpha}{r}BA
$$

其中：

- $W$ 是冻结的预训练权重。
- $A\in\mathbb{R}^{r\times d}$。
- $B\in\mathbb{R}^{d'\times r}$。
- $r$ 是低秩维度。
- $\alpha$ 是缩放系数。

LoRA 主要节省优化器状态和梯度显存。

它不一定减少前向传播中的基础权重显存。

### 7.9 手写 LoRA Linear

```python
import torch
import torch.nn as nn


class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, rank=8, alpha=16, dropout=0.05):
        super().__init__()
        self.base = base
        for parameter in self.base.parameters():
            parameter.requires_grad_(False)
        self.scale = alpha / rank
        self.dropout = nn.Dropout(dropout)
        self.a = nn.Parameter(torch.empty(rank, base.in_features))
        self.b = nn.Parameter(torch.zeros(base.out_features, rank))
        nn.init.kaiming_uniform_(self.a, a=5**0.5)

    def forward(self, x):
        base_output = self.base(x)
        update = self.dropout(x) @ self.a.t() @ self.b.t()
        return base_output + self.scale * update
```

初始化 $B=0$ 可以让初始 LoRA 输出等价于基础模型。

这样训练一开始不会突然改变模型行为。

### 7.10 QLoRA 的核心思路

QLoRA 使用量化基础模型加低秩适配器。

基础模型通常以 4-bit 权重保存并计算，LoRA 参数保持较高精度。

需要注意：

1. 量化误差会影响最终上限。
2. 训练计算通常仍需要 BF16/FP16。
3. optimizer 只更新 LoRA 参数。
4. 合并 adapter 前要验证量化和非量化推理一致性。

QLoRA 不是“4-bit 梯度训练所有权重”。

它的关键是冻结量化基础权重，只训练可学习的低秩分支。

### 7.11 LoRA 参数量估算

对一个 $d_{out}\times d_{in}$ 的线性层，LoRA 参数量为：

$$
P_{LoRA}=r(d_{in}+d_{out})
$$

当 $r\ll d$ 时，参数量显著小于原始矩阵：

$$
\frac{P_{LoRA}}{P_W}=\frac{r(d_{in}+d_{out})}{d_{in}d_{out}}
$$

但 target modules 选择会影响效果。

只给 attention 的 Q、V 加 LoRA 可能不足以改变复杂任务行为。

给 q、k、v、o 和 MLP 投影加 LoRA 更全面，但显存和训练时间会上升。

### 7.12 Preference Learning 的基本设定

对同一个 prompt，提供一个 chosen 回答和一个 rejected 回答。

目标是让模型提高 chosen 的相对概率：

$$
\pi_\theta(y^+|x)>\pi_\theta(y^-|x)
$$

仅仅比较序列总 log probability 会偏好短回答。

因此通常需要按有效 token 数做长度归一化，或使用更稳健的序列级目标。

不同任务的长度偏差不同，必须在验证集上检查。

### 7.13 DPO 推导

DPO 假设最优策略可以写成参考策略和奖励的关系：

$$
\pi^*(y|x)\propto\pi_{ref}(y|x)\exp\left(\frac{r(x,y)}{\beta}\right)
$$

由此可得到隐式奖励差：

$$
\hat r_\theta(x,y)=\beta\left(\log\pi_\theta(y|x)-\log\pi_{ref}(y|x)\right)
$$

DPO 损失为：

$$
L_{DPO}=-\log\sigma\left(\beta\left[(\log\pi_\theta(y^+|x)-\log\pi_{ref}(y^+|x))-(\log\pi_\theta(y^-|x)-\log\pi_{ref}(y^-|x))\right]\right)
$$

### 7.14 正确计算序列 log probability

只对 response 部分计算 log probability。

```python
import torch
import torch.nn.functional as F


def sequence_logp(logits, labels, response_mask):
    shifted_logits = logits[:, :-1]
    shifted_labels = labels[:, 1:]
    shifted_mask = response_mask[:, 1:].float()
    token_logp = F.log_softmax(shifted_logits, dim=-1)
    gathered = token_logp.gather(
        dim=-1, index=shifted_labels.unsqueeze(-1)
    ).squeeze(-1)
    numerator = (gathered * shifted_mask).sum(-1)
    denominator = shifted_mask.sum(-1).clamp_min(1.0)
    return numerator / denominator
```

如果使用平均 log probability，chosen 和 rejected 的 mask 必须正确。

如果使用总 log probability，最好对长度分桶评估。

### 7.15 完整 DPO loss

```python
import torch
import torch.nn.functional as F


def dpo_loss(policy, reference, batch, beta=0.1):
    policy_chosen = policy(
        input_ids=batch["chosen_ids"],
        attention_mask=batch["chosen_mask"],
    ).logits
    policy_rejected = policy(
        input_ids=batch["rejected_ids"],
        attention_mask=batch["rejected_mask"],
    ).logits

    with torch.no_grad():
        ref_chosen = reference(
            input_ids=batch["chosen_ids"],
            attention_mask=batch["chosen_mask"],
        ).logits
        ref_rejected = reference(
            input_ids=batch["rejected_ids"],
            attention_mask=batch["rejected_mask"],
        ).logits

    pi_pos = sequence_logp(policy_chosen, batch["chosen_ids"],
                           batch["chosen_response_mask"])
    pi_neg = sequence_logp(policy_rejected, batch["rejected_ids"],
                           batch["rejected_response_mask"])
    ref_pos = sequence_logp(ref_chosen, batch["chosen_ids"],
                            batch["chosen_response_mask"])
    ref_neg = sequence_logp(ref_rejected, batch["rejected_ids"],
                            batch["rejected_response_mask"])

    logits = beta * ((pi_pos - ref_pos) - (pi_neg - ref_neg))
    loss = -F.logsigmoid(logits).mean()
    accuracy = (logits > 0).float().mean()
    return loss, {"preference_accuracy": float(accuracy.detach())}
```

参考模型通常冻结，不需要对其计算梯度。

如果显存有限，可以提前计算参考模型 log probability。

### 7.16 DPO 的 beta 和 KL 约束

$\beta$ 控制偏好目标相对参考策略的强度。

$\beta$ 太大，模型可能过度追逐偏好对。

$\beta$ 太小，更新过弱，偏好信号不明显。

观察指标包括：

- DPO loss。
- preference accuracy。
- chosen/rejected logp。
- policy-reference gap。
- 生成长度变化。
- 通用能力回归。

训练 loss 下降但 preference accuracy 不升，可能是 batch 构造或 mask 错误。

### 7.17 Reward Model

RLHF 的奖励模型接收 prompt 和回答，输出标量奖励。

给定 chosen 和 rejected，常用 Bradley-Terry 损失：

$$
L_{RM}=-\log\sigma(r_\phi(x,y^+)-r_\phi(x,y^-))
$$

```python
import torch
import torch.nn.functional as F


def reward_pair_loss(chosen_reward, rejected_reward):
    margin = chosen_reward - rejected_reward
    loss = -F.logsigmoid(margin).mean()
    accuracy = (margin > 0).float().mean()
    return loss, accuracy
```

奖励模型最容易学到标注偏差。

例如更长、更客气或更格式化的回答可能得到更高分，即使事实不正确。

因此奖励模型必须配合独立事实性评测。

### 7.18 PPO 的概念结构

经典 RLHF 流程为：

```text
SFT policy
  ↓
采样回答
  ↓
Reward model 打分
  ↓
加入 reference KL 惩罚
  ↓
PPO 更新 policy/value
```

PPO 的 clipped surrogate objective：

$$
L^{CLIP}=E_t\left[min(r_t(\theta)A_t,clip(r_t(\theta),1-\epsilon,1+\epsilon)A_t)\right]
$$

其中：

$$
 r_t(\theta)=\frac{\pi_\theta(a_t|s_t)}{\pi_{old}(a_t|s_t)}
$$

PPO 工程复杂度高，涉及 rollout、优势估计、value head 和 KL 控制。

### 7.19 KL 惩罚

为了避免策略偏离 SFT 模型太远，通常加入 KL 惩罚：

$$
R'=R-\beta_{KL}D_{KL}(\pi_\theta||\pi_{ref})
$$

token 级近似可以使用 log probability 差：

```python
@torch.no_grad()
def approx_kl(policy_logp, ref_logp, mask):
    diff = policy_logp - ref_logp
    return (diff * mask).sum() / mask.sum().clamp_min(1)
```

KL 过大通常说明更新太激进或奖励模型被钻漏洞。

### 7.20 RLOO 与 GRPO 的简化理解

RLOO 使用同一个 prompt 的多个回答估计 leave-one-out baseline。

GRPO 通过组内相对奖励减少 value model 依赖。

组内优势可以写成：

$$
A_i=\frac{r_i-mean(r_{1:G})}{std(r_{1:G})+\epsilon}
$$

```python
import torch


def group_advantage(rewards):
    mean = rewards.mean(dim=1, keepdim=True)
    std = rewards.std(dim=1, keepdim=True, unbiased=False)
    return (rewards - mean) / (std + 1e-6)
```

这类方法对可验证奖励任务特别有用，例如数学答案、代码测试和格式检查。

### 7.21 可验证奖励

奖励函数可以由程序直接验证：

```python

def math_reward(prediction: str, answer: str) -> float:
    pred = normalize_answer(prediction)
    gold = normalize_answer(answer)
    return 1.0 if pred == gold else 0.0


def code_reward(output: str, tests: list[str]) -> float:
    result = run_in_sandbox(output, tests, timeout=2)
    if result.timeout:
        return 0.0
    return result.passed / max(result.total, 1)
```

执行代码必须在隔离沙箱中完成。

不能让训练进程直接执行不可信生成代码。

奖励设计还需要防止模型输出硬编码答案、绕过测试或利用评测漏洞。

### 7.22 SFT → DPO 的完整流水线

```python
from copy import deepcopy
import torch


def train_sft_then_dpo(base_model, sft_loader, pref_loader, device):
    model = base_model.to(device)
    sft_optimizer = torch.optim.AdamW(
        [p for p in model.parameters() if p.requires_grad], lr=2e-5
    )

    for batch in sft_loader:
        batch = {k: v.to(device) for k, v in batch.items()}
        loss = model(**batch).loss
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        sft_optimizer.step()
        sft_optimizer.zero_grad(set_to_none=True)

    reference = deepcopy(model).eval()
    for p in reference.parameters():
        p.requires_grad_(False)
    dpo_optimizer = torch.optim.AdamW(
        [p for p in model.parameters() if p.requires_grad], lr=5e-7
    )

    for batch in pref_loader:
        batch = {k: v.to(device) for k, v in batch.items()}
        loss, metrics = dpo_loss(model, reference, batch)
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        dpo_optimizer.step()
        dpo_optimizer.zero_grad(set_to_none=True)
        print(metrics)
    return model
```

示例省略了 padding、AMP 和分布式封装。

但训练阶段的依赖关系是完整的：先 SFT，再固定 reference，再用偏好对更新 policy。

### 7.23 对齐数据的泄漏与污染

偏好数据可能来自模型生成结果。

如果 chosen 和 rejected 使用了同一个评测问题，可能造成 benchmark 泄漏。

数据集拆分要按 prompt 或任务模板分组，而不是随机按行拆分。

否则同一个问题的不同答案会同时进入 train 和 validation。

### 7.24 拒答数据的设计

安全对齐不是把所有敏感问题都回答成同一句话。

高质量拒答应包含：

1. 清楚说明不能提供什么。
2. 避免复述危险细节。
3. 在安全范围内提供替代帮助。
4. 对合法边界问题保持可用。

拒答数据需要覆盖“应该拒答”和“不应该拒答”的对比样本。

否则模型可能学成过度拒答。

### 7.25 工具调用后训练

工具调用数据通常包含结构化 action：

```json
{
  "tool": "search",
  "arguments": {"query": "大模型训练监控"}
}
```

训练时需要同时监督：

- 是否调用工具。
- 工具名称是否正确。
- 参数 JSON 是否可解析。
- 观察结果后是否继续行动。
- 最终答案是否引用工具结果。

只监督最终自然语言答案，工具调用格式可能不稳定。

### 7.26 结构化输出约束

对于 JSON 输出，训练和推理最好都做 schema 校验。

```python
from dataclasses import dataclass
import json


@dataclass
class ToolCall:
    name: str
    arguments: dict


def parse_tool_call(text: str) -> ToolCall:
    payload = json.loads(text)
    if not isinstance(payload.get("name"), str):
        raise ValueError("tool name must be string")
    if not isinstance(payload.get("arguments"), dict):
        raise ValueError("arguments must be object")
    return ToolCall(payload["name"], payload["arguments"])
```

训练数据中要统计 JSON parse rate。

### 7.27 后训练评测矩阵

建议至少包含：

| 维度 | 指标 |
| :--- | :--- |
| 指令遵循 | exact match、judge score |
| 事实性 | citation accuracy、QA accuracy |
| 推理 | 数学、代码、逻辑 |
| 格式 | JSON parse rate、schema pass rate |
| 安全 | refusal precision、unsafe completion rate |
| 通用 | 通用语言和知识基准 |
| 回归 | 旧版本固定测试集 |

单一自动评测分数不能作为发布条件。

### 7.28 工业案例：LLaMA-3 风格的多阶段后训练

大模型常采用多阶段 SFT、偏好优化和安全训练。

可迁移的工程原则是：

1. 每一阶段都保存独立 checkpoint。
2. 每一阶段都有输入数据版本。
3. 偏好优化后必须做通用能力回归。
4. 安全训练不能覆盖所有普通帮助能力。
5. 发布候选需要经过人工红队。

### 7.29 工业案例：Qwen 风格的中文与工具能力

中文对话、代码和工具调用的格式边界可能不同。

工具数据中应特别检查：

- 中文参数是否被截断。
- 日期、金额和单位是否正确。
- 多工具调用是否保持顺序。
- 工具返回错误后是否能恢复。

### 7.30 工业案例：DeepSeek 风格的推理后训练

可验证奖励对数学和代码任务特别有效。

但推理奖励不能只鼓励输出更长的思维文本。

应区分：

```text
答案正确
推导有效
格式满足要求
成本可接受
```

如果奖励只看最终答案，模型可能学会猜测。

如果奖励只看解释长度，模型可能产生无效冗余。

### 7.31 失败案例：SFT 把 prompt 也算进 loss

模型出现复述用户问题、泄露系统提示和角色混乱。

根因是 labels 没有对 prompt 区域设置 -100。

修复后重新训练，并增加多轮角色边界测试。

### 7.32 失败案例：DPO chosen/rejected 方向写反

训练 loss 正常下降，但模型更偏向 rejected。

排查方法是计算：

```text
preference_accuracy = P(logit > 0)
```

如果长期低于 0.5，优先检查样本方向、mask 和 reference logp。

### 7.33 失败案例：奖励模型被长度欺骗

生成越长奖励越高，模型开始输出大量重复解释。

根因是标注者偏好和奖励模型把长度当作质量代理。

修复方法包括长度分桶、重复惩罚、事实性样本和独立 judge。

### 7.34 失败案例：过度拒答

安全训练后模型对普通医学、代码和历史问题也拒答。

根因是拒答正例多、合法边界负例少。

修复方法是构建成对边界数据，并评估 refusal precision 和 recall，而不是只看拒答率。

### 7.35 后训练面试题

**问题 1：SFT 为什么只对 answer 计算 loss？**

回答：prompt 是条件，不是需要模型复述的目标；mask prompt 可以让梯度集中在回答质量和任务行为上，同时减少模型复制用户输入。

**问题 2：DPO 与 RLHF 的核心区别是什么？**

回答：DPO 直接在偏好对上优化策略与 reference 的相对 log probability，不显式训练奖励模型和在线 rollout；RLHF 通常包含奖励模型、采样和策略优化，工程复杂度更高但可处理更一般的序列奖励。

**问题 3：为什么 DPO 需要 reference model？**

回答：reference 提供锚点和隐式 KL 约束，避免策略为了满足偏好对而大幅偏离基座或 SFT 模型。

**问题 4：如何识别奖励模型被 reward hacking？**

回答：同时观察人工质量、事实性、长度、重复率、格式通过率和独立奖励；如果奖励上升但真实任务下降，说明代理目标被利用。

**问题 5：什么时候更适合 LoRA？**

回答：数据量有限、显存有限、需要多任务 adapter 或希望保留基础模型时优先考虑 LoRA；如果需要全局能力重塑或大规模持续预训练，可能需要全参数或更广泛参数更新。

### 7.36 本章检查清单

- [ ] SFT 的 prompt 和 answer mask 经单元样本验证。
- [ ] 对话模板有版本号且训练前统一渲染。
- [ ] 训练、验证和 benchmark 按 prompt 去重拆分。
- [ ] LoRA 的 target modules 和可训练参数量可审计。
- [ ] DPO 的 chosen/rejected 方向和 response mask 已校验。
- [ ] preference accuracy 与通用能力同时监控。
- [ ] 奖励模型有独立事实性和长度偏差评测。
- [ ] 代码奖励在隔离沙箱中运行。
- [ ] 安全训练有过度拒答回归测试。
- [ ] 每个后训练阶段都能独立回滚。

## 第 8 章：工业案例、发布门禁与面试题 —— 从实验到稳定系统

### 8.1 为什么还需要发布工程

模型训练完成不等于模型可以发布。

从实验 checkpoint 到生产服务，中间还要经过格式转换、推理验证、容量评估和安全门禁。

一个能在单机上生成文本的模型，不一定能在生产中稳定服务。

工业化的目标是把“模型好不好”转化为可重复的发布判断。

建议把发布过程拆成以下阶段：

```text
训练完成
  ↓
checkpoint 完整性检查
  ↓
离线能力评测
  ↓
安全与合规扫描
  ↓
推理格式转换
  ↓
单卡正确性验证
  ↓
并发与延迟压测
  ↓
灰度发布
  ↓
线上反馈闭环
```

每一步都应该有明确的输入、输出和失败处理。

### 8.2 模型 artifact 的组成

模型 artifact 不只是 `pytorch_model.bin`。

推荐至少包含：

```text
config.json
model.safetensors 或分片权重
tokenizer.json
tokenizer_config.json
special_tokens_map.json
generation_config.json
chat_template.jinja
model_card.md
training_manifest.json
evaluation_report.json
license.txt
```

缺少 tokenizer 或 chat template，生产服务可能产生完全不同的行为。

缺少训练 manifest，后续无法追溯数据和配方。

### 8.3 Artifact 完整性校验

发布前先做文件和结构校验。

```python
import hashlib
import json
from pathlib import Path


REQUIRED = [
    "config.json",
    "tokenizer.json",
    "tokenizer_config.json",
]


def sha256_file(path: Path) -> str:
    digest = hashlib.sha256()
    with path.open("rb") as stream:
        for block in iter(lambda: stream.read(1024 * 1024), b""):
            digest.update(block)
    return digest.hexdigest()


def validate_artifact(directory: str):
    root = Path(directory)
    missing = [name for name in REQUIRED if not (root / name).exists()]
    if missing:
        raise FileNotFoundError(f"missing files: {missing}")
    config = json.loads((root / "config.json").read_text())
    for key in ["vocab_size", "hidden_size", "num_hidden_layers"]:
        if key not in config:
            raise ValueError(f"config missing {key}")
    return {path.name: sha256_file(path) for path in root.iterdir()
            if path.is_file()}
```

校验结果应写入发布记录。

不要只在发布机器上人工检查文件名。

### 8.4 权重格式与安全加载

优先使用 safetensors 等不会执行任意 Python 对象的权重格式。

加载来自不可信来源的 pickle checkpoint 存在代码执行风险。

如果必须加载旧格式，应在隔离环境中转换，并使用最小权限。

加载时要明确 `map_location` 和 dtype。

```python
import torch


def load_state(path: str, device="cpu"):
    return torch.load(path, map_location=device, weights_only=True)
```

不同 PyTorch 版本对 `weights_only` 的支持可能不同。

生产代码应固定运行时版本并加入兼容测试。

### 8.5 推理正确性检查

转换到量化、张量并行或推理引擎后，先做小规模一致性检查。

比较内容包括：

1. tokenizer 输出是否一致。
2. 输入长度和 attention mask 是否一致。
3. logits top-k 是否近似一致。
4. 贪心生成是否一致。
5. 采样分布是否在可接受范围内。
6. stop token 是否正确。

量化后不应要求浮点 logits 完全相等。

但 top-k、格式和任务正确率应该有阈值。

### 8.6 生成函数的最小验证

```python
import torch


@torch.inference_mode()
def generate_text(model, tokenizer, prompt, max_new_tokens=64):
    inputs = tokenizer(prompt, return_tensors="pt")
    inputs = {k: v.to(model.device) for k, v in inputs.items()}
    output = model.generate(
        **inputs,
        max_new_tokens=max_new_tokens,
        do_sample=False,
        pad_token_id=tokenizer.eos_token_id,
    )
    return tokenizer.decode(output[0], skip_special_tokens=True)


def smoke_test(model, tokenizer):
    cases = [
        "用一句话解释梯度累积。",
        "输出 JSON：{\"ok\": true}。",
        "Write a short Python function.",
    ]
    for prompt in cases:
        text = generate_text(model, tokenizer, prompt)
        assert text.strip(), prompt
        print({"prompt": prompt, "output": text[:200]})
```

冒烟测试不能替代完整评测。

它只负责尽早发现模型无法加载、输出为空或 stop token 错误。

### 8.7 发布门禁设计

门禁应该区分硬门禁和软门禁。

硬门禁失败时禁止发布：

- 权重无法加载。
- tokenizer 缺失。
- 核心安全测试失败。
- JSON schema 通过率低于最低阈值。
- 关键任务比基线退化超过阈值。
- artifact checksum 不一致。

软门禁失败时进入人工审核：

- 某领域轻微退化。
- 延迟略高于目标。
- 生成风格改变。
- 某些长尾问题表现不稳定。

### 8.8 评测报告的结构

一个可审计的评测报告应该包含：

```json
{
  "model_id": "candidate-2026-07-17",
  "base_checkpoint": "pretrain-step-900000",
  "data_version": "sft-v12-dpo-v4",
  "tokenizer_version": "tok-v3",
  "benchmarks": {
    "general": {"score": 0.72, "baseline": 0.70},
    "code": {"score": 0.61, "baseline": 0.60},
    "safety": {"unsafe_rate": 0.01, "baseline": 0.02}
  },
  "runtime": {
    "p50_ms": 180,
    "p95_ms": 430,
    "tokens_per_second": 95
  },
  "decision": "review"
}
```

评测脚本版本也要记录。

同一个 benchmark 如果提示模板变化，分数就不再可比。

### 8.9 成本模型

粗略训练成本可以写为：

$$
C_{train}=N_{GPU}\times t_{hour}\times price_{GPU}\times utilization\_factor
$$

其中利用率因子包含空转、故障、保存和数据等待。

有效 token 成本为：

$$
C_{token}=\frac{C_{train}}{N_{effective\ tokens}}
$$

推理成本还要考虑输入和输出 token：

$$
C_{infer}=C_{input}+C_{output}+C_{overhead}
$$

不要只用 GPU 租赁价格做预算。

网络、对象存储、日志、人工标注、重试和评测都是真实成本。

### 8.10 容量规划

服务容量至少受以下因素限制：

- 单请求显存。
- KV cache。
- 最大上下文长度。
- 并发请求数。
- batch 合并策略。
- 生成 token 速度。
- P99 延迟目标。

KV cache 的内存与层数、头数、序列长度和 batch 大小相关。

简化表达：

$$
M_{KV}\propto B\times T\times L\times n_{kv}\times d_{head}\times bytes
$$

使用 GQA 或 MQA 可以减少 KV 头数。

但模型结构和 checkpoint 必须匹配，不能在部署阶段随意修改。

### 8.11 延迟分解

端到端延迟可以拆成：

```text
排队时间
+ tokenizer 时间
+ prefill 时间
+ decode 时间
+ detokenize 时间
+ 网络传输时间
```

prefill 通常与输入长度相关。

decode 通常与输出 token 数和 KV cache 访问相关。

只报告平均延迟会掩盖长上下文请求的尾延迟。

### 8.12 压测脚本

```python
import concurrent.futures
import statistics
import time


def one_request(client, prompt):
    start = time.perf_counter()
    response = client.generate(prompt)
    elapsed = (time.perf_counter() - start) * 1000
    return {"ms": elapsed, "ok": bool(response)}


def load_test(client, prompts, workers=8):
    with concurrent.futures.ThreadPoolExecutor(max_workers=workers) as pool:
        results = list(pool.map(lambda p: one_request(client, p), prompts))
    latencies = [item["ms"] for item in results]
    latencies.sort()
    p95 = latencies[int(len(latencies) * 0.95) - 1]
    return {
        "count": len(results),
        "success_rate": sum(x["ok"] for x in results) / len(results),
        "p50_ms": statistics.median(latencies),
        "p95_ms": p95,
        "max_ms": max(latencies),
    }
```

压测要固定 prompt 长度分布和输出长度上限。

否则不同测试之间无法比较。

### 8.13 灰度发布

灰度发布可以按用户、流量比例、地域或业务场景分组。

灰度期间同时记录：

- 失败率。
- 用户重试率。
- 平均输出长度。
- 工具调用成功率。
- 负反馈率。
- 安全拦截率。
- 成本变化。

模型分流必须保留 request 到 model version 的映射。

否则线上问题无法回放。

### 8.14 线上反馈的闭环

线上反馈不要直接全部回流训练。

正确流程是：

```text
线上请求
  ↓
隐私脱敏
  ↓
质量抽样
  ↓
问题分类
  ↓
人工或规则验证
  ↓
构造训练/评测数据
  ↓
离线实验
  ↓
小流量验证
```

用户点赞不等于事实正确。

用户点踩也不一定说明模型错误，可能是用户目标不明确或产品交互不合理。

### 8.15 数据回流的去重

生产反馈可能包含同一个模板问题的大量副本。

回流前要对 prompt、上下文和回答做精确与近似去重。

同时要防止把模型自己的错误回答重复训练成“事实”。

每条反馈最好带有人工标签：

```text
correct
incorrect
unsafe
format_error
irrelevant
ambiguous
```

### 8.16 工业案例：LLaMA-3 风格的模型家族

模型家族通常包含多个尺寸、上下文长度和部署版本。

发布工程要保证：

1. 每个尺寸有独立评测报告。
2. tokenizer 和 chat template 行为一致。
3. 量化版本有独立质量基线。
4. 不同尺寸的能力差异有文档说明。
5. 用户知道何时选择大模型或小模型。

不能因为同一个系列名称相同，就假设所有版本行为一致。

### 8.17 工业案例：Qwen 风格的中文生产服务

中文生产服务特别容易遇到：

- 全角半角混用。
- 日期和金额格式不一致。
- 中文标点导致 JSON 解析失败。
- 多语言 prompt 切换后的 tokenizer 长度变化。
- 中文安全规则误报或漏报。

上线前应把中文格式、代码、工具和安全分别建立回归集。

### 8.18 工业案例：DeepSeek 风格的推理模型服务

推理模型的服务成本通常更受输出长度影响。

需要同时管理：

- 最大推理 token。
- 最终答案长度。
- 中间推理是否暴露给用户。
- 长回答的事实性。
- 超时和取消请求。

如果只追求 benchmark 分数而忽略输出成本，线上单位请求成本可能不可接受。

### 8.19 工业案例：领域模型持续更新

领域模型通常不是每天从零训练。

更常见的路线是：

```text
通用基座
  ↓
领域继续预训练
  ↓
领域 SFT
  ↓
偏好优化
  ↓
线上错误样本回流
  ↓
小批量增量更新
```

每轮增量更新都需要固定通用回归集。

否则领域能力上升可能伴随基础能力下降。

### 8.20 失败案例：量化后格式能力退化

量化模型的通用问答看起来正常，但 JSON 输出经常缺括号。

根因是量化误差对低概率结构 token 的影响更明显。

修复方法：

1. 为结构化输出建立专项评测。
2. 比较量化前后的 token-level logit。
3. 选择更合适的量化配置。
4. 使用 constrained decoding 作为安全边界。
5. 必要时对 adapter 或输出头做精度保留。

### 8.21 失败案例：灰度期间无法定位版本

用户反馈模型“突然变笨”，但日志只有请求 ID，没有 model version。

根因是分流层没有把版本写入请求上下文。

修复方法是将以下字段写入不可变日志：

```text
request_id
model_id
adapter_id
quantization
prompt_template_version
tokenizer_version
```

### 8.22 失败案例：训练回流污染

线上用户的问题和错误答案未经审核就加入 SFT。

模型随后更高概率生成同样的错误。

修复方法是将线上日志先作为候选评测集，只有经过验证的样本才进入训练集。

### 8.23 失败案例：只看平均延迟

平均延迟为 200 ms，但长上下文请求 P99 超过 20 秒。

根因是请求长度分布没有纳入压测。

修复方法是按输入 token 和输出 token 分桶报告 P50、P95、P99。

### 8.24 发布前一页清单

**数据**：

- [ ] 训练和评测数据版本锁定。
- [ ] 评测集没有训练泄漏。
- [ ] 线上回流数据已脱敏和审核。

**模型**：

- [ ] checkpoint 可加载。
- [ ] tokenizer 和 chat template 完整。
- [ ] 权重 checksum 已记录。
- [ ] 生成冒烟测试通过。

**能力**：

- [ ] 通用能力不低于基线门槛。
- [ ] 核心领域指标达到目标。
- [ ] 结构化输出通过率达标。
- [ ] 工具调用回归通过。

**安全**：

- [ ] 高风险测试集通过。
- [ ] 过度拒答未超标。
- [ ] PII 输出有拦截策略。
- [ ] 生成内容有审计日志。

**系统**：

- [ ] P50、P95、P99 延迟达标。
- [ ] 并发压测通过。
- [ ] OOM 和超时有降级策略。
- [ ] 灰度和回滚开关可用。

### 8.25 常见面试题：从零训练大模型需要哪些状态

回答可以按四层组织：

1. 模型参数和 buffer。
2. 优化器和混合精度状态。
3. 学习率、梯度累积和 global step。
4. dataloader、sampler 和随机数状态。

分布式场景再补充 rank、world size、分片信息和数据 manifest。

### 8.26 常见面试题：如何估算训练显存

先区分推理和训练。

推理主要是权重、KV cache 和临时激活。

训练还包含梯度、优化器状态、激活和通信 buffer。

Adam 混合精度训练通常要考虑 FP16/BF16 权重、FP32 master weight、梯度和一阶二阶矩。

公式只是初估，最终还要通过实际 batch、序列长度和并行策略验证。

### 8.27 常见面试题：loss 突然变成 NaN 怎么排查

推荐顺序：

1. 确认输入、labels 和 attention mask。
2. 检查 loss 是否包含有效 token。
3. 检查 logits、梯度和参数的有限性。
4. 查看最近学习率和梯度范数。
5. 定位异常 shard 和 batch。
6. 回滚到最近健康 checkpoint。
7. 分别测试 BF16/FP16、裁剪和学习率。

不要第一步就把学习率改小。

### 8.28 常见面试题：为什么训练集 loss 降了但能力没提升

可能原因包括：

- 数据重复。
- 训练集和任务分布不匹配。
- tokenizer 统计改变。
- 评测泄漏或评测错误。
- 模型只学会格式而没有学会任务。
- 过拟合。
- 总 loss 掩盖了关键领域退化。

应通过小规模 ablation、领域验证集和人工样本复盘定位。

### 8.29 常见面试题：DPO 为什么可能导致通用能力下降

DPO 会强化偏好数据中的行为分布。

如果偏好数据过窄、过度风格化或存在事实错误，策略可能偏离 reference。

因此需要控制 beta、混合保留数据、监控 KL，并在通用回归集上评估。

### 8.30 常见面试题：LoRA 为什么节省显存

LoRA 冻结基础参数，只为低秩矩阵保存梯度和优化器状态。

可训练参数从完整矩阵规模降到 $r(d_{in}+d_{out})$。

但基础权重仍需参与前向计算，推理显存不一定按同样比例减少。

### 8.31 常见面试题：如何设计数据版本

数据版本不能只用日期命名。

至少要包含来源快照、解析器版本、过滤规则、去重版本、tokenizer 版本和 manifest hash。

发布训练集时保存样本数量、token 数、过滤统计和抽样样本。

### 8.32 常见面试题：如何判断是否应该继续训练

可以观察三个信号：

1. 验证 loss 是否仍在有效下降。
2. 关键能力是否随 token 增长获得收益。
3. 边际 token 的成本是否值得能力提升。

如果训练 loss 仍降但能力和领域指标停滞，继续增加相同数据通常不是最佳选择。

### 8.33 常见面试题：如何避免灾难性遗忘

可以采用经验回放、混合旧数据、降低学习率、LoRA、EWC、参数隔离和定期全量重训。

实际工程中先使用旧数据回放和固定回归集。

只有当任务冲突严重且收益明确时，再引入更复杂的参数隔离方法。

### 8.34 常见面试题：为什么需要独立的验证集

训练 loss 只反映模型是否拟合当前 batch。

验证集用于判断泛化、过拟合和数据配方效果。

如果验证集来自相同重复文档，指标也会失真。

因此验证集需要独立来源、独立 hash 检查和固定版本。

### 8.35 常见面试题：如何判断模型真的学会了工具调用

不能只看生成文本像不像工具调用。

要验证：

1. action JSON 可解析。
2. 工具名存在且参数 schema 正确。
3. 工具返回错误时模型能恢复。
4. 最终答案使用了观察结果。
5. 不需要工具时不会滥用工具。

### 8.36 常见面试题：如何设计线上回滚

模型、adapter、tokenizer、模板和路由配置都要可版本化。

回滚不能只替换权重文件。

发布系统应支持按版本切换，并保留旧版本最小容量。

回滚后还要检查缓存、日志和用户会话是否与旧模板兼容。

### 8.41 最小可复现性检查

```python

def reproducibility_check(run_a, run_b, tolerance=1e-5):
    assert run_a["config_hash"] == run_b["config_hash"]
    assert run_a["manifest_hash"] == run_b["manifest_hash"]
    for left, right in zip(run_a["losses"], run_b["losses"]):
        assert abs(left - right) < tolerance
```

GPU kernel、并行归约和随机数据增强可能让严格 bitwise 复现很难。

可以把目标分为：

1. 完全复现。
2. 统计复现。
3. 指标区间复现。

### 8.42 长上下文专项验证

长上下文模型要评估：

- 位置编码外推。
- 中间信息召回。
- 多段文档一致性。
- 长输入下的吞吐和显存。
- 截断策略。

不能只把 `max_seq_len` 配大，就认为模型获得了稳定长上下文能力。

### 8.43 多模态扩展的接口

如果生命周期扩展到视觉、音频或视频，数据流水线要额外管理：

- 媒体编码格式。
- 分辨率和采样率。
- 模态对齐时间戳。
- 缺失模态。
- 版权和隐私。
- 图像文本去重。

核心思想不变：原始数据、规范化数据、token 或 embedding、训练 manifest 都要版本化。

### 8.44 训练系统的最小 SLO

可以为训练平台定义：

| SLO | 示例目标 |
| :--- | :--- |
| checkpoint 成功率 | ≥ 99.9% |
| 自动恢复成功率 | ≥ 99% |
| 数据读取错误率 | ≤ 0.01% |
| GPU 空转比例 | ≤ 10% |
| 训练日志延迟 | ≤ 60 秒 |
| 发布回滚时间 | ≤ 10 分钟 |

这些目标需要结合团队和成本调整。

SLO 的价值是让“训练稳定”可以被讨论和改进。

### 8.45 复杂度控制原则

不是所有训练项目都需要 RLHF、FSDP、近似去重和在线回流。

建议遵循从简单到复杂的路线：

1. 单机小模型验证数据和损失。
2. 单机多卡验证吞吐和 checkpoint。
3. 分布式验证恢复和扩展性。
4. SFT 验证任务行为。
5. DPO 或可验证奖励验证偏好收益。
6. 灰度验证线上指标。

每一步只引入解决当前瓶颈所需的复杂度。

### 8.48 训练项目启动前的十个问题

### 8.51 结语

大模型训练不是一次性的“跑脚本”，而是一条从数据到模型、从模型到服务、再从服务回到数据的闭环。

真正可靠的系统不追求每一个组件都复杂。

它追求每一个关键状态都可观察、每一次变化都可解释、每一次失败都可恢复。

当你能够回答“数据从哪里来、参数如何变化、异常如何回滚、指标如何证明收益、线上问题如何回流”时，才真正掌握了大模型训练全生命周期。

## 深度扩展 · 多视角系统展开(续)

### 110. 第04章-大模型训练全生命周期 - 最佳实践 视角

**核心议题**: 本节从最佳实践视角切入,系统展开 "第04章-大模型训练全生命周期" 的相关讨论。

**1. 背景与动机**

任何技术或方法的出现都不是孤立的,而是回应特定历史条件下的具体问题。"第04章-大模型训练全生命周期" 的发展也不例外。要理解它,必须回到它出现的那个时间点,看清它要解决的真实问题是什么。当时的主流方案有哪些不足? 它的提出填补了哪些空白? 这些问题的回答,决定了我们今天该如何使用它。

从知识论角度看,**技术演进是问题驱动的**——不是先有方案再找问题,而是先有问题再有方案。这个观察可以帮助我们避免"拿着锤子找钉子"的陷阱,真正把方法用对地方。

历史维度上,我们看到三个规律:

1. **从特殊到一般**: 早期方法往往针对特定场景,后期抽象出通用框架。学习的认知规律也是先掌握具体案例,再抽象出一般模式。这种"自下而上"的学习方式,在机器学习模型的设计里反复出现。

2. **从手工到自动**: 经验规则逐步被数据驱动的方法取代。在早期,很多 AI 系统依赖人工编写的规则。统计学习方法的崛起让"从数据中学习"成为可能。深度学习进一步把特征工程也自动化了。今天的大模型时代,我们看到端到端学习从感知扩展到了推理与生成。

3. **从局部到全局**: 关注单个组件,演进到关注整个系统。早期模型评估只关注单点指标,现在更关注全链路的协同效应。这种"系统视角"的转变,与软件工程从单体架构到微服务架构的演进高度相似。

**2. 最佳实践视角的展开**

从最佳实践视角出发,我们可以把 "第04章-大模型训练全生命周期" 拆解为以下几个层次:

**第一层: 概念层** —— 这是最抽象的层次,定义了我们要研究的对象是什么。例如,"推荐系统"在概念层是一个"为用户从物品集合中筛选合适物品"的问题。这个层次的特点是清晰、稳定、不易变化。一个好的概念定义应该具备几个特征:可操作性、可测量性、可扩展性。

**第二层: 模型层** —— 把概念实例化为数学模型。同一概念可以有不同的模型化方式,例如"推荐系统"可以是协同过滤、矩阵分解、深度学习等。模型的选择决定了后续算法的空间,也决定了能利用的归纳偏置(比如序列模型擅长捕捉时序依赖,图模型擅长建模关系结构)。模型选型是工程实践中最重要的决策之一。

**第三层: 算法层** —— 在选定模型下,具体的求解方法。这一层最活跃,新算法层出不穷。同一模型往往有多种算法,各有优劣。例如同样是优化深度网络,可以选择 SGD、Adam、L-BFGS 等不同算法。算法的选择要考虑收敛速度、数值稳定性、计算成本等多个维度。

**第四层: 工程层** —— 算法落地的实现细节,包括数据流水线、训练框架、推理优化、监控告警等。工程层是研究到生产的桥梁,决定了一个方法能否真正用起来。一个在论文里表现很好的算法,如果不能高效实现、不能稳定运行、不能快速迭代,就没有实际价值。工程能力是把研究转化为生产力的关键。

**第五层: 业务层** —— 在具体业务场景中的表现。同一技术在不同业务里效果差异巨大,因为业务目标、数据分布、用户行为都有差异。从业务视角看技术,我们必须回答几个问题:这个技术解决了什么业务问题?投入产出比如何?长期可持续吗?技术评估必须与业务目标对齐,否则容易陷入"技术自嗨"的陷阱。

**3. 数学形式化(简洁版)**

虽然我们强调最佳实践视角,但数学形式化提供了共同语言。机器学习的核心问题可以表达为:给定输入样本,学习一个映射函数,使得函数输出与真实目标的差距最小化。这个抽象捕捉了分类、回归、生成等大多数任务的本质。
