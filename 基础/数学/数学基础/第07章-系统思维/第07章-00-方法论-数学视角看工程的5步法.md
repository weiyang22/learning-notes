# 0.1 方法论:数学视角看工程的 5 步法

> **写给每天和模型、数据、指标打交道的工程师的话**:
>
> 这是整个 **7-系统思维文件夹的"宪法"**。后面 15 个案例 (DLRM、MMoE、GR、HSTU、RLHF、PPO、GRPO、Exploration、DreamerV3、Diffusion、VAE、Hinton KD、Feature Distillation、Transformer 注意力、RoPE) 都用这同一个 5 步法拆解。
>
> 你有没有过这种时刻:
>
> - **线上 AUC 涨了 0.5%,但业务指标没动**。你不知道该不该上线。
> - **训练 loss 在掉,但测试 loss 在涨**。你不知道这是过拟合还是分布漂移。
> - **同事甩给你一篇 arXiv 论文,说"这个 SOTA 我们能不能用"**。你读完不知道作者为什么这么做,也不知道能不能落地。
> - **A/B 实验跑了 2 周,实验组胜出,但 PM 问"为什么是这个方案"**, 你只能说"感觉效果好一点"。
> - **review 会上,leader 问"这背后的数学依据是什么"**, 你给不出比"经验"更深的回答。
>
> 这些时刻的共同点: 你**有数据、有代码、有实验**, 但**没有一套把"工程现象"翻译成"数学命题"的方法**。
>
> 5 步法就是这套方法。它的本质是一句话: **"把工程问题用数学重新问一遍, 看会不会有更深的答案"**。
>

> - 数学模型求解出来, 怎么回到工程验证? 验证失败时, 是模型错了, 还是验证错了?
> - 算法的"有效边界"在哪里? 什么时候该换方法?
> - 5 步法每一步的"反模式"是什么? 怎么识别?
>

> - 2-线代 给了**矩阵、特征值、SVD** 的工具

> - 4-离散数学 给了**群、图、组合** 的抽象
> - 5-信息论 给了**熵、互信息、率失真** 的视角

## 1. 直觉引入:为什么需要"数学视角"

### 1.1 工程问题的"复杂性诅咒"

工程师每天的工作流,长这样:

```text
真实生产环境
   ↓
看到现象 (线上指标掉了 / 离线 AUC 涨不动)
   ↓
动手实验 (调参 / 改特征 / 换模型)
   ↓
看指标 (涨了 / 跌了)
   ↓
再调 / 上线 / 回滚
   ↓
   ...循环
```

这套流程**有效**,但它有 4 个根上的盲区:

1. **没有"问题定义"**: 看到指标掉了, 直接动手调参。但"为什么掉"没想清楚, 调的可能不是真正的原因
2. **没有"理论下界"**: 看到一个方案涨了 1%, 但不知道这个数据集的"理论上限"是 5% 还是 0.5%, 不知道还有多少空间
3. **没有"反面证据"**: 一个方案在 1 个数据集上有效, 不能推广。数学上要问"什么时候会失效"
4. **没有"可复用的洞察"**: 每次遇到新问题都从头试。数学上可以把"这类问题"统一处理

**反面案例**: 某大厂推荐团队, 2022 年花 3 个月做特征工程, 离线 AUC +0.3%, 上线后业务指标反而 -0.5%。事后复盘: 团队只盯着离线指标, 没分析"离线 AUC 与线上业务"之间到底是什么关系, 也没考虑特征分布随时间漂移 (covariate shift)。

**正面案例**: 同一团队, 2023 年用 5 步法重新拆解了"长尾内容冷启动"问题:
- 第 1 步: 观察到长尾内容曝光率 < 5%, 但消费意愿高 → 现象
- 第 2 步: 假设"长尾内容的 embedding 不准", 形式化为矩阵分解的欠秩问题 → 数学
- 第 3 步: 用加权 ALS 替代标准 SGD, 推导 O(k log n) 复杂度 → 求解
- 第 4 步: 离线 NDCG +8%, A/B 业务 +2.1% → 验证
- 第 5 步: 数学洞察 = "信息瓶颈", 长尾内容的信息量大于头部, 应当分桶处理 → 反向思考

3 周解决问题, 上线 6 个月仍有效。**区别就是"有没有用数学问一遍"**。

### 1.2 5 步法的必要性

5 步法不是新发明。它是把**科学方法**(现象 → 假设 → 实验 → 结论) **工程化**(每步有具体的"产出物"和"判停标准"), 同时把**数学建模**(假设 → 形式化 → 求解) **嵌进来**。

```text
科学方法 (200 年前)        数学建模 (100 年前)        5 步法 (现在)
─────────────              ─────────────             ──────────
现象                        假设                      ① 现象观察
   ↓                          ↓                          ↓
假设                        形式化                    ② 数学建模
   ↓                          ↓                          ↓
实验                        求解                      ③ 求解与算法
   ↓                          ↓                          ↓
结论                        验证                      ④ 工程验证
                                                        ↓
                                                    ⑤ 数学洞察 (反向)
```

**5 步法和传统工程方法的核心区别**:

| 维度 | 传统工程方法 | 5 步法 |
| :--- | :--- | :--- |
| 起点 | "调一下试试" | "先看清现象" |
| 模型 | 黑盒 (e.g. "深度学习就是好") | 显式 (写出 $f(x)$ 的形式) |
| 优化 | 试错 (网格搜索) | 推导 (有理论复杂度) |
| 验证 | "AUC 高就行" | 多指标 + 失败案例 |
| 沉淀 | "经验" | "可复用的数学洞察" |
| 复用 | 一案一议 | 一类问题统一解 |

### 1.3 一个 30 秒的直觉案例:DLRM 为什么不用 MLP

为了让 5 步法不再抽象, 先用一个 30 秒的小例子走一遍。

**现象**: Meta 2019 年发现, 纯 MLP 推荐模型在稀疏类别特征 (用户 ID、商品 ID) 上表现差。
**建模**: 把"类别特征 → 分数"形式化为双线性 $\langle \mathbf{e}_u, \mathbf{e}_i \rangle$, 其中 $\mathbf{e}_u, \mathbf{e}_i \in \mathbb{R}^d$。
**求解**: 训练就是学习 embedding, 复杂度 $O(d \cdot |\text{unique IDs}|)$。
**验证**: 在 Meta 1B 样本上 AUC 涨 5%, 推理延迟 30ms。
**洞察**: 推荐本质是"矩阵分解 + 浅层交叉", MLP 深了反而过拟合; 信息瓶颈 $I(\text{特征}; \text{label})$ 决定模型容量上限。

30 秒读完, 你已经看到了 5 步法的"骨架"。下面 8 节, 我们把这个骨架放大, 配上详细的工程案例和数学工具。

```text
  反直觉实验                ↓                     ↓
  ↓                        必要的简化              数值稳定性
  表层 vs 深层              ↓                     ↓
  差异                      "建模" 完成             "算法" 给出
       │                        │                      │
       └────────────────────────┼──────────────────────┘
                                ↓
                          ④ 工程验证
```

**5 步的关键判停标准**:

| 步骤 | 输入 | 输出 | 判停标准 |
| :--- | :--- | :--- | :--- |
| ① 现象观察 | 真实生产数据 | 1 段现象描述 + 1 张表 | 能用一句话说清"反直觉"在哪 |
| ② 数学建模 | 现象描述 | 1 组公式 + 1 张假设清单 | 假设可证伪 (能在数据上检验) |
| ③ 求解与算法 | 模型 + 数据规模 | 1 个算法伪代码 + 复杂度表 | 能在 $O(\text{工程预算})$ 内跑出 |
| ④ 工程验证 | 算法 + 离线评估脚本 | 1 张离线表 + 1 份 A/B 报告 | 业务指标 +0.5% 以上, 且无负向 |
| ⑤ 数学洞察 | 全部 | 1 段"反例"分析 + 1 张推广边界 | 能说出"什么情况下这方法失效" |

### 2.2 每步的"产出物"和"反模式"

**① 现象观察**:
- **正确**: "长尾内容曝光率 < 5%, 但消费完成率是头部内容的 1.8 倍"
- **反模式**: "感觉推荐效果不好" (无法验证)
- **反模式**: "领导说要把这个指标搞上去" (没有客观测量)

**② 数学建模**:
- **正确**: "假设 = embedding 欠秩, 模型 = 矩阵分解 $R \approx U V^T$, 损失 = 加权 Frobenius 范数"
- **反模式**: "用深度学习" (没有具体形式, 无法求解)
- **反模式**: "直接套用 ResNet-50" (没考虑推荐数据的稀疏性)

**③ 求解与算法**:
- **正确**: "加权 ALS, 每次迭代 $O(|\text{edges}| \cdot d)$, 收敛 $O(\log(1/\epsilon))$"
- **反模式**: "用 PyTorch 跑 100 个 epoch" (没有复杂度意识)
- **反模式**: "用 Adam 调一下" (没有分析优化景观)

**④ 工程验证**:
- **正确**: "离线 AUC + 1.2%, Recall@50 + 3%, 推理 35ms, A/B 业务 + 0.8%"
- **反模式**: "AUC 涨了" (只看一个指标, 没看延迟、内存、长尾)
- **反模式**: "线下 0.5% 提升, 应该上线" (没做 A/B, 风险高)

**⑤ 数学洞察**:
- **正确**: "长尾内容 = 信息瓶颈的极限情况, 信息量大于头部; 模型容量应当按信息量分配, 而不是按样本量"
- **反模式**: "模型效果不错" (没有反例, 没有边界)
- **反模式**: "下一步做更多特征" (没有理论指导)

- **小问题 / 时间紧**: 传统方法更快
- **大问题 / 想突破**: 5 步法更稳
- **多次迭代**: 5 步法的洞察会越积越多, 边际成本下降

## 3. 第 1 步: 现象观察 (Observation)

### 3.1 直觉:为什么"看现象"是 5 步法最难的一步?

现象观察**看着简单**, 但它是 5 步法里**最容易被跳过、最容易做错**的一步。原因有三:

1. **数据噪声掩盖信号**: 真实生产数据的信噪比常常 < 0.1, 工程师看到的"涨/跌"可能是噪声
2. **确认偏误 (confirmation bias)**: 工程师倾向于找"支持自己假设"的数据
3. **观测成本高**: 真正的反直觉实验可能要花几周搭建, 工程师倾向于"看几个指标"就开干

**关键原则**: **现象观察的核心不是"看指标", 而是"看出反直觉"**。反直觉 = "你以为 A 导致了 B, 但数据说不是"。

### 3.2 现象观察的 4 个层次

```text
层次 4: 反直觉 (counter-intuitive)    ← 真正能驱动的洞察
       ↓
层次 3: 关联 (correlation)            ← 相关不等于因果
       ↓
层次 2: 趋势 (trend)                  ← 涨/跌本身
       ↓
层次 1: 数字 (raw metric)             ← 工程师最容易停留的地方
```

**例子**: 推荐系统的点击率 (CTR) 指标。

| 层次 | 观察 | 价值 |
| :--- | :--- | :--- |
| 1. 数字 | "今天 CTR = 3.2%" | 低, 无法判断好坏 |
| 2. 趋势 | "CTR 跌了 5%" | 中, 知道有变化 |
| 3. 关联 | "跌的 5% 集中在新用户" | 高, 知道在哪 |
| 4. 反直觉 | "新用户 CTR 跌, 但他们的平均使用时长涨" | 极高, 颠覆"CTR 跌 = 业务差"的假设 |

**层次 4 的反直觉**: 新用户 CTR 跌, 但使用时长涨。这说明新用户**看到了更感兴趣的内容** (每次点击更深), 而不是"东西更差"。这时候 CTR 跌**反而是好事**。

### 3.3 离线 vs 在线指标的差异

**经典陷阱**: 离线 AUC 涨, 在线业务跌。这背后有 3 个原因:

1. **分布漂移 (covariate shift)**: 离线训练数据和线上数据分布不同
2. **位置偏置 (position bias)**: 离线评估假设所有位置等价, 线上位置差异巨大
3. **反馈延迟 (delayed feedback)**: 离线用"是否点击"做标签, 线上有"未点击但满意"的隐式反馈

```text
   离线 (Offline)              线上 (Online)
   ────────────                ───────────
   数据: 训练集 / 验证集       数据: 实时流
   标签: 已有 (历史)            标签: 实时 (有延迟)
   评估: AUC, NDCG, ...        评估: 点击率, 时长, GMV
   优势: 可复现                 优势: 反映真实用户
   劣势: 脱离生产               劣势: 噪声大, 难复现
```

**判停标准**: **离线指标只用于"排序候选", 线上指标用于"拍板"**。两者背离时, 优先信线上 (但要排除 bug、流量异常等干扰)。

### 3.4 工程实例:一个反直觉的实验

**场景**: 某电商搜索, 工程师 A 发现"加入购物车率"跌了 8%, 怀疑是排序模型问题。

**层次 1 数字**: "购物车率 12% → 11%" (确实跌了)
**层次 2 趋势**: "持续跌了 2 周" (持续性确认)
**层次 3 关联**: "主要跌在'美妆'类目" (定位)
**层次 4 反直觉**: "但美妆类目 GMV 涨 5%, 客单价涨 12%" (颠覆!)

**结论**: 购物车率跌**不是 bug**, 而是"用户直奔高客单商品, 跳过加购" (奢侈品 / 高端美妆直接买, 不需要加购)。这反而是好事。

**5 步法的下一步**: 进入第 2 步 (数学建模) 时, 工程师已经知道"加购率不是好目标, 客单价 + GMV 才是", 建模时就不会再优化"加购率"。

### 3.5 现象观察的 5 个判停问题

在进入第 2 步之前, 工程师必须能回答这 5 个问题:

1. **数字**: 这个现象的**数值**是什么? (e.g. CTR 跌 5%)
2. **时间**: 持续多久? 是突变还是渐变?
3. **群体**: 在哪些用户/内容/场景上发生? 是否有共同特征?
4. **对照**: 和"应该的样子"差多少? (基线 / 去年同期)
5. **反直觉**: 我的第一反应是什么? 数据是不是反过来?

第 5 个问题是核心。**反直觉 = 新洞察的入口**。

## 4. 第 2 步: 数学建模 (Modeling)

### 4.1 直觉:建模 = "用数学重新问一遍"

5 步法里, **数学建模**是把"工程现象"翻译成"数学命题"的关键一步。它的本质是**两件事**:

1. **写假设**: 用数学符号表达"我假设问题是这样"
2. **选工具**: 根据假设, 选对应的数学分支 (概率 / 优化 / 信息论 / ...)

**关键原则**: **"假设" 比 "公式" 重要 10 倍**。一个写错的公式可以调, 一个写错的假设会让整个 5 步法走偏。

### 4.2 建模的 4 步流程

```text
工程现象                         数学命题
───────                         ────────
"长尾内容曝光低"     ──────>     假设: 长尾内容的 embedding 维度不够
                            ↓
                       形式化: $R = U V^T$,  $U, V$ 秩 $r$ 不足
                            ↓
                       选工具: 矩阵分解 (2-线代) + 加权正则 (6-最优化)
                            ↓
                       模型: $\min_{U,V} \sum_{(u,i) \in \Omega} w_{ui} (R_{ui} - \langle \mathbf{u}, \mathbf{v} \rangle)^2 + \lambda (\|U\|_F^2 + \|V\|_F^2)$
```

**4 步流程**:
1. **列假设**: "我假设" + 1 句话
2. **写形式**: 用变量 / 函数 / 集合表达
3. **选工具**: 数学分支 (概率 / 优化 / 信息论 / 几何)
4. **建损失**: 写出具体的目标函数

### 4.3 选择数学工具:4 大类

| 工具类 | 核心问题 | 典型应用 |
| :--- | :--- | :--- |
| **概率统计** | "数据从哪个分布来" | 推荐 (伯努利), 风控 (高斯), NLP (语言模型) |
| **矩阵 / 张量** | "维度之间怎么交互" | 推荐 (矩阵分解), CV (SVD), 图 (邻接矩阵) |
| **优化理论** | "目标函数长什么样" | 凸优化 (L2 回归), 非凸 (神经网络), 离散 (组合优化) |
| **信息论** | "信号 vs 噪声" | 压缩, 蒸馏, 异常检测, 强化学习 |

**选择标准**:
- 数据稀疏 → 概率 / 张量
- 维度高 → 矩阵 (SVD、PCA)
- 目标非凸 → 优化理论 (凸松弛, 信赖域)
- 涉及压缩 / 蒸馏 / 决策 → 信息论

### 4.4 必要的定理引用

建模时, **至少引用一条定理**作为"理论的护城河"。否则你的模型就是个"经验公式", 经不起推敲。

**例子**:
- 用矩阵分解 → 引用 **Eckart-Young 定理** (最优低秩近似的存在性)
- 用 KL 散度做蒸馏 → 引用 **Gibbs 不等式** ($D_{\mathrm{KL}}(P \| Q) \ge 0$, 等号 iff $P = Q$)
- 用 Adam → 引用 **Robbins-Monro 条件** (SGD 收敛性)
- 用 PPO → 引用 **信赖域定理** (TRPO 的单调改进)

```text
建模 = 假设 + 形式化 + 工具 + 定理
                  ↑
              最容易忘
```

**反面案例**: 某团队 2023 年用"自定义损失函数"做推荐, 上线后效果波动大。复盘: 损失函数没有理论保证 (不是凸的, 也没有单调性), 训练结果依赖随机种子。"看起来效果不错" 其实是过拟合。

### 4.5 简化的代价:什么时候"过度简化"会反咬一口?

**简化原则**: **能省则省, 但不能省错**。

简化有两种:
- **合理的简化**: 假设独立 (e.g. i.i.d.), 假设同分布, 假设凸性
- **危险的简化**: 假设高斯 (实际是长尾), 假设独立 (实际有相关性)

**判断方法**: 简化后, 用 **bootstrap** 或 **残差分析** 检查"被忽略的部分是不是有结构"。如果有, 简化错了。

**例子**: 推荐数据用 i.i.d. 假设, 实际上**用户行为有序列依赖**。简化后, 残差在时间维度上有自相关。**结论**: 简化错了, 需要加序列模型 (GR / HSTU 案例)。

### 4.6 建模的 5 个判停问题

在进入第 3 步之前, 工程师必须能回答:

1. **假设**: 我假设问题是什么样的? (一句话)
2. **形式化**: 用什么变量 / 函数表达? (公式)
3. **工具**: 用了哪些数学分支? (e.g. 概率 + 优化)
4. **定理**: 引用了哪条定理? (作为理论护城河)
5. **简化**: 简化了什么? 这个简化会反咬吗? (残差分析)

第 5 个问题最难, 但**最重要**, 它是后续"翻车"的最常见原因。

## 5. 第 3 步: 求解与算法 (Solving)

### 5.1 直觉:从模型到代码的"最后一公里"

第 2 步给出**目标函数**, 第 3 步给出**算法**。这一步本质是:

1. **推导**: 怎么从 $\min f(x)$ 走到 $x_{t+1} = g(x_t)$?
2. **复杂度**: 这个算法在 $N = 10^9$ 的数据上要跑多久?
3. **数值稳定性**: FP32 会不会爆? 梯度会不会消失?
4. **对比**: 和现有方案比, 优势在哪?

**关键原则**: **算法选错了, 模型再漂亮也没用**。一个 $O(N^2)$ 的算法在 10 亿样本上跑一年, 没人会等。

### 5.2 推导:从公式到更新规则

```text
目标函数                              更新规则
────────                              ────────
$\min_x f(x)$                ────>   $x_{t+1} = x_t - \eta \nabla f(x_t)$ (SGD)

$\min_x \|Ax - b\|^2$        ────>   $x = (A^T A)^{-1} A^T b$ (正规方程)

$\min_{U,V} \|R - UV^T\|^2$  ────>   $u_i \leftarrow (\sum_j v_j v_j^T + \lambda I)^{-1} \sum_j r_{ij} v_j$ (ALS)

$\min_\theta \mathbb{E}_{x \sim p}[\log q_\theta(x)]$  ────>  $\theta \leftarrow \theta + \eta \nabla_\theta \log q_\theta(x)$ (MLE)
```

**反面案例**: 某团队用 Adam 优化矩阵分解, 跑得比 SGD 还慢。复盘: 矩阵分解是凸问题, 用一阶方法即可, Adam 的自适应反而引入噪声。**没有"对所有问题都好"的算法**。

### 5.3 复杂度分析:必填项

每个算法必须给出**时空复杂度**:

| 算法 | 时间复杂度 | 空间复杂度 | 适用规模 |
| :--- | :--- | :--- | :--- |
| SGD | $O(N d / \epsilon)$ | $O(d)$ | $N \le 10^{10}$ |
| 矩阵分解 (ALS) | $O(\|\Omega\| \cdot d \cdot k)$ | $O((M+N) d)$ | $M, N \le 10^8$ |
| Adam | $O(N d / \epsilon)$ (常数大) | $O(d)$ | 同 SGD |
| L-BFGS | $O(N d \cdot \log(1/\epsilon))$ | $O(d \cdot m)$ | $N \le 10^7$ |
| 二阶方法 | $O(d^3)$ per step | $O(d^2)$ | $d \le 10^4$ |

**说明**:
- $N$: 样本数
- $d$: 参数维度
- $\epsilon$: 收敛精度
- $|\Omega|$: 观察到的 (user, item) 对数
- $m$: L-BFGS 保留的历史梯度数

**判停标准**: **算法总时间 = 复杂度 × 硬件 FLOPS, 必须在工程预算内** (e.g. 1 天内能训完)。

### 5.4 数值稳定性

**3 个常见数值问题**:

1. **梯度爆炸**: 深层网络, 梯度 $\to \infty$ → 解决: 梯度裁剪 (gradient clipping)
2. **梯度消失**: 深层 + sigmoid, 梯度 $\to 0$ → 解决: ReLU, 残差连接, LayerNorm
3. **下溢 / 溢出**: $\log p$ 中 $p \to 0$ → 解决: log-space 计算, FP64

```text
数值稳定性 checklist:
□ 梯度有界吗?  (clip 到 $\|g\| < c$)
□ 中间量有界吗? (e.g. $\log(\text{sum}) \to \log(\text{sum} + \epsilon)$)
□ 用了 FP64 吗? (e.g. KL 散度, log-likelihood)
□ softmax 有减 max 吗? (避免 $e^x$ 爆炸)
```

**例子**: 矩阵分解中 $R_{ui} = \langle u_i, v_j \rangle$ 可能上亿 (e.g. 大规模 embedding 点积), 必须用 **log1p** 或 **binned** 处理。直接用 FP32 算点积, 数值不稳定。

### 5.5 与现有方案对比

每个新算法都该**和 baseline 对比**:

| 维度 | 新算法 | baseline |
| :--- | :--- | :--- |
| 收敛速度 | $O(\log(1/\epsilon))$ | $O(1/\epsilon)$ |
| 最终精度 | +1.2% AUC | 0 (基线) |
| 推理延迟 | 35ms | 30ms |
| 训练时长 | 8h | 24h |
| 内存 | 16GB | 12GB |
| 实现难度 | 中 | 低 |

**判停标准**: 至少在 **2 个维度**有显著优势, 才能"替换" baseline; 否则是"加一种选择"。

### 5.6 第 3 步的 5 个判停问题

1. **推导**: 怎么从公式到更新规则? (写出主要步骤)
2. **复杂度**: 时间 / 空间复杂度? 在工程预算内吗?
3. **稳定性**: 数值稳定吗? 哪些量会爆?
4. **对比**: 和 baseline 比, 优势在哪?
5. **复现**: 别人能按我写的复现出来吗? (伪代码 / 开源代码)

第 5 个问题最容易被忽略。一个"只在作者机器上跑通"的算法, 没有工程价值。

## 6. 第 4 步: 工程验证 (Validation)

### 6.1 直觉:验证 = "真的有效吗?"

**第 3 步给算法, 第 4 步给"证据"**。这一步的本质是: **用数据证明"这个算法在真实场景下比 baseline 好"**。

**关键原则**: **离线指标不等于线上指标, 单一指标不等于业务效果**。验证要"多维度"。

### 6.2 离线指标:可复现但脱离生产

| 任务 | 常用指标 | 含义 |
| :--- | :--- | :--- |
| 分类 | AUC, log-loss, F1 | 排序质量 |
| 回归 | RMSE, MAE | 预测误差 |
| 排序 | NDCG@K, MAP@K, Recall@K | 排序质量 |
| 生成 | BLEU, ROUGE, PPL | 生成质量 |
| 多任务 | 任务加权 AUC | 多目标平衡 |
| 蒸馏 | Top-1 一致率, 互信息 | 师生一致性 |

**判停标准**:
- AUC 提升 > 0.5% → 显著
- NDCG@50 提升 > 1% → 显著
- log-loss 降低 > 0.5% → 显著

低于这些, 大概率是噪声。

### 6.3 在线 A/B:反映生产但难复现

```text
A/B 实验的标准流程:
─────────────
1. 切流量 (1%, 5%, 10% 三档)
2. 跑实验 (至少 7 天, 覆盖工作日 + 周末)
3. 监控核心指标 (CTR, GMV, 留存, 延迟, 错误率)
4. 显著性检验 (p-value, 置信区间)
5. 决策: 上线 / 放量 / 回滚
```

**3 个关键监控**:

1. **核心业务指标**: CTR / GMV / 时长 (这是 PM 关心的)
2. **护栏指标 (guardrail)**: 延迟 / 错误率 / 公平性 (不能为了涨指标而崩其他)
3. **长尾指标**: 少数群体 / 小流量内容 / 异常场景 (防止"只优化头部")

**反面案例**: 某短视频产品 2023 年 A/B 实验, 算法涨了 1.2% 时长, 上线后发现**长视频 (P50 以上的视频) 播放量跌了 8%**。这是"护栏指标"没监控到, 导致头部涨了, 长尾崩了。

### 6.4 失败案例与教训

**每个验证都必须有"失败案例"部分**。失败案例 = 边界条件 = 推广的禁区。

**例子: 矩阵分解的失败模式**:

| 失败模式 | 触发条件 | 现象 | 修复 |
| :--- | :--- | :--- | :--- |
| 嵌入崩溃 | 训练数据有偏 | 所有 embedding 接近 | 加熵正则 |
| 数值爆 | 嵌入维度太大 | 梯度 NaN | 维度截断 + 梯度 clip |
| 冷启动 | 新 item 没有交互 | embedding 随机 | 用 side info (text, image) |
| 过拟合 | 训练时长太长 | 训练 AUC 涨, 测试 AUC 跌 | early stopping |

**判停标准**: **至少列 3 个失败模式**, 并给出"触发条件"和"修复方案"。否则这个验证不完整。

### 6.5 第 4 步的 5 个判停问题

1. **离线**: 哪些离线指标? 涨多少? 是否显著?
2. **在线**: A/B 跑了多久? 多少流量? 显著性如何?
3. **业务**: 核心业务指标涨多少? 护栏指标有没有崩?
4. **长尾**: 长尾场景 (少数群体 / 小流量) 表现如何?
5. **失败**: 至少 3 个失败模式, 怎么识别和修复?

第 5 个问题最难, 但**最体现工程深度**。一个只会报"涨了 1%"的验证, 是不合格的验证。

## 7. 第 5 步: 数学洞察 (Insight)

### 7.1 直觉:洞察 = "把这个案例变成方法"

**第 5 步是 5 步法的"灵魂"**。前 4 步解决"一个问题", 第 5 步解决"一类问题"。

**关键原则**: **数学洞察 = 反向思考 + 反例 + 推广边界**。不是"总结", 是"反问"。

### 7.2 5 步法的"反向"过程

```text
前 4 步:                              第 5 步:
─────                                 ─────
① 现象: "A 现象"                     ① 现象的"反面"是什么?
② 建模: "我假设 H"                   ② H 在什么情况下不成立?
③ 求解: "我用了算法 S"               ③ S 在什么情况下失效?
④ 验证: "我得到结果 R"               ④ R 的"反例"是什么?
```

**关键问题**:
- 这个方法的"**反面**"是什么? (什么情况下会失败)
- 这个方法的"**极限**"是什么? (再优化能到多少)
- 这个方法的"**推广边界**"是什么? (能用到哪些其他问题)

### 7.3 为什么有效:数学的"必要条件"

**第 5 步的第一步**: 用数学解释"为什么这个算法有效"。

```text
算法有效的 4 个数学依据:
─────────────
1. 假设匹配: 算法的"前提条件"和数据的"真实分布"匹配
2. 优化景观: 损失函数的几何 (凸性 / 平滑性) 利于该优化器
3. 信息保留: 算法保留 / 提取了关键信息 (互信息、熵)
4. 复杂度匹配: 算法的样本复杂度低于数据规模
```

**例子**: 为什么 DLRM 有效?
- 假设匹配: 推荐 = 矩阵分解 + 浅层交互, DLRM 的结构刚好匹配
- 优化景观: 浅层 MLP + 嵌入, 损失面相对平滑
- 信息保留: 类别特征的 embedding 保留 ID 信息, 数值特征保留 scale 信息
- 复杂度匹配: 一次前向 $O(d^2)$, 在 10 亿样本上 8 小时能训完

### 7.4 反面:什么时候会失效?

**第 5 步的第二步**: 找"反例"。

**反面案例: DLRM 什么时候失效?**
- **数据极端长尾**: embedding 学不到, 推荐退化为头部内容
- **特征强相关**: 双线性假设不成立, 效果不如 FM / DeepFM
- **目标非加性**: e.g. 转化 (conversion) 受时间影响大, 双线性捕捉不到
- **推理延迟敏感**: DLRM 推理 30ms, 比双塔模型 (10ms) 慢, 实时性差

**意义**: 知道反面, 才能**正确地选择**用 DLRM 还是别的方法。

### 7.5 极限:再优化能到多少?

**第 5 步的第三步**: 算"理论上限"。

**方法**:
- **信息论上界**: 特征与标签的互信息 $I(X; Y)$ (e.g. $\le H(Y)$, 即"不能比标签的信息量还高")
- **贝叶斯最优**: 假设我们知道真实分布, 能达到的最优精度
- **PAC 学习界**: 样本复杂度 $N \ge O(\text{VC dim} / \epsilon)$

**例子**: 某推荐任务理论上限 = AUC 0.85, 实际能到 0.83, 距离 0.02。这 0.02 的 gap 是"模型没榨干", 还是"特征不够"? 算出来才能决定下一步动作。

### 7.6 推广边界:能用到哪些其他问题?

**第 5 步的第四步**: 把"一个案例"变成"一类问题"。

**例子**: DLRM 的"信息瓶颈 + 矩阵分解"思路可以推广到:
- **广告 CTR**: 用户 × 广告 × 上下文的"三重矩阵分解"
- **短视频推荐**: 用户 × 视频 × 创作者, 加时间维度
- **电商多目标**: 用户 × 商品 × 店铺 × 类目, 加分层结构
- **风控**: 用户 × 行为 × 设备, 加时间序列

**判停标准**: 至少列出 3 个"可推广的场景", 并指出"需要调整的部分"。

### 7.7 第 5 步的 5 个判停问题

1. **为什么**: 这个算法为什么有效? (4 个数学依据至少 2 个)
2. **反面**: 什么情况下会失效? (至少 3 个反例)
3. **极限**: 再优化能到多少? (理论上限 vs 实际)
4. **推广**: 能用到哪些其他问题? (至少 3 个场景)
5. **沉淀**: 这个洞察能写进"方法库"吗? (一句话总结)

第 5 个问题最容易被跳过。**没有沉淀的洞察, 只是"这一次的经验", 不能变成"下一次的方法"**。

## 9. 误区 + 互引

### 9.1 三大常见误区

#### 误区 1: ❌ "数学建模 = 套用公式"

**反例**: 工程师遇到新问题, 直接套用"矩阵分解"或"Transformer", 没考虑**假设是否成立**。

**真相**: 建模的核心是**假设**, 不是公式。一个写错公式的模型可以调, 一个写错假设的模型, 整个 5 步法走偏。

**判断**: 建模前, 必须能用一句话说清"我假设问题是这样"。如果说不清, 假设还没想明白, 别急着用公式。

**真实案例**: 某团队直接套用 Transformer 做长尾推荐, 失败。复盘: Transformer 假设"序列位置信息有用", 但长尾 item 几乎没有序列数据, 假设不成立, Transformer 反而学到噪声。

#### 误区 2: ❌ "工程验证只看 AUC"

**反例**: 离线 AUC 涨 1%, 直接上线。结果线上业务指标跌 3%。

**真相**: 验证要看**多维度**: 离线指标 + 线上 A/B + 业务核心 + 护栏 + 长尾 + 失败案例。**AUC 涨不代表业务涨**。

**判断**: 任何"上线决定"必须基于**至少 3 个独立维度**的证据。单一指标的涨/跌, 95% 是噪声。

**真实案例**: 某搜索团队 2022 年优化 AUC 涨 1.5%, 上线后商家投诉"我的商品被埋了", 复盘发现护栏指标 (商家多样性) 崩了, 只看 AUC 没看到这点。

#### 误区 3: ❌ "数学洞察 = 总结"

**反例**: 验证完写一句"模型效果不错, 提升了 1%"。这就是"总结", 不是洞察。

**真相**: 数学洞察 = **反向思考 + 反例 + 推广边界**。具体三件事:
1. **反向**: "什么情况下这个方法失效?"
2. **反例**: "给我一个数据, 让这个方法失败"
3. **推广**: "这个思路能用到哪些其他问题?"

**判断**: 写完一段"洞察", 问自己: "如果一个新同学看这段, 他能避开未来的 3 个坑吗?" 能, 就是洞察; 不能, 就是总结。

**真实案例**: 某团队 2023 年做完"长尾内容优化"项目, 写报告时只说"效果不错, 上线了"。2024 年另一个团队做类似项目, 重新踩了"长尾 embedding 欠秩"的坑, 浪费 3 个月。**这就是"没有沉淀" 的代价**。

## 4.1 第 1 步深度展开:问题的数学抽象

### 4.1.1 抽象层次的金字塔

```text
真实业务问题 (Concrete)
   ↓ 业务约束识别
业务需求 (Requirements)
   ↓ 关键变量提取
数学对象 (Objects)
   ↓ 关系建模
数学结构 (Structure)
   ↓ 公理化
形式系统 (Formal System)
```

### 4.1.2 三种典型抽象范式

#### 范式 A:优化问题抽象

**业务语言**: "我们想让推荐点击率最高,同时保证多样性。"

**数学抽象**:
$$
\begin{aligned}
\max_{\theta} \quad & \mathbb{E}_{x \sim \mathcal{D}} [R(\theta; x)] \\
\text{s.t.} \quad & \text{Diversity}(\theta) \geq \delta \\
& \text{Fairness}(\theta) \geq \epsilon \\
& \theta \in \Theta
\end{aligned}
$$

**关键概念解释**:
- $\theta$: 模型参数(待求解)
- $\mathcal{D}$: 数据分布
- $R$: 奖励函数(点击率代理)
- $\delta, \epsilon$: 业务约束阈值
- $\Theta$: 参数可行域

#### 范式 B:动态系统抽象

**业务语言**: "用户兴趣会随时间漂移,系统需要自适应。"

**数学抽象** (差分方程):
$$
\begin{cases}
h_{t+1} = f_\theta(h_t, x_t) \\
y_t = g_\theta(h_t)
\end{cases}
$$

其中:
- $h_t$: 隐状态(用户兴趣的数学表征)
- $x_t$: 当前观测(行为)
- $f_\theta$: 状态转移函数
- $g_\theta$: 输出函数

#### 范式 C:博弈论抽象

**业务语言**: "平台、用户、广告主三方利益冲突,需要平衡。"

**数学抽象** (Stackelberg 博弈):
$$
\begin{aligned}
\text{平台 (Leader):} \quad & \max_{\pi} U_P(\pi, \sigma_U^*, \sigma_A^*) \\
\text{用户 (Follower):} \quad & \sigma_U^* = \arg\max_{\sigma_U} U_U(\pi, \sigma_U, \sigma_A^*) \\
\text{广告主 (Follower):} \quad & \sigma_A^* = \arg\max_{\sigma_A} U_A(\pi, \sigma_U^*, \sigma_A)
\end{aligned}
$$

### 4.1.3 抽象质量的自检清单

```markdown
## 数学抽象自检表

- [ ] **可证伪性**: 抽象后的模型能给出可被实验反驳的预测?
- [ ] **可计算性**: 给定输入,能用算法在有限时间算出解?
- [ ] **可解释性**: 参数/变量是否有清晰业务含义?
- [ ] **可推广性**: 同一抽象能否套用到类似业务?
- [ ] **可简化性**: 是否能用更少变量刻画本质?
```

## 4.3 数学建模的常见陷阱

### 4.3.1 陷阱 1:奥卡姆剃刀遗忘

**现象**: 模型越复杂越好

**反例**: 用 1000 万参数的 Transformer 拟合 100 个样本的正弦曲线

**准则**: 模型参数应与数据规模匹配
$$
\text{经验法则: } N \geq 10 \cdot p
$$
其中 $N$ 为样本数,$p$ 为参数个数。

### 4.3.2 陷阱 2:分布漂移忽视

**现象**: 训练数据和测试数据分布不一致

**数学刻画**:
- 训练分布 $P_{\text{train}}(x, y)$
- 测试分布 $P_{\text{test}}(x, y)$
- 漂移度量: KL 散度 $\text{KL}(P_{\text{train}} \| P_{\text{test}})$

**应对**:
1. 域适应(Domain Adaptation)
2. 持续学习(Continual Learning)
3. 在线学习(Online Learning)

### 4.3.3 陷阱 3:奖励黑客(Reward Hacking)

**现象**: 智能体学到"最大化代理奖励"的捷径,但真实目标失败

**经典案例**: CoastRunners 游戏中,智能体发现反复撞船得分最高,而不是比赛

**数学刻画**:
$$
\text{真实目标: } R^* = \mathbb{E}[r_{\text{real}}]
$$
$$
\text{代理奖励: } \hat{R} = \mathbb{E}[\hat{r}]
$$
$$
\text{黑客条件: } \max \hat{R} \neq \max R^*
$$

**应对**:
1. 多奖励信号
2. 人类反馈(RLHF)
3. 约束优化(CMDP)

### 4.3.4 陷阱 4:维度诅咒

**现象**: 高维空间中,数据稀疏,距离度量失效

**数学刻画**:
- 高维空间体积集中在边角
- 局部邻域失去意义
- 距离比 $\frac{d_{\max}}{d_{\min}} \to 1$

**应对**:
1. 降维(PCA / t-SNE / UMAP)
2. 哈希化(LSH)
3. 学习有用表征(对比学习)

## 4.4 数学验证的 5 种方法

### 4.4.1 理论验证

**核心**: 通过数学证明验证模型性质

**例:证明排序模型的单调性**
$$
\text{若 } x_i > x_j \text{ 且 } \theta > 0, \text{ 则 } f(x_i; \theta) > f(x_j; \theta)
$$

验证方法: 对 $f$ 求偏导,确认符号。

### 4.4.2 数值验证

**核心**: 通过数值实验验证理论预测

```python
import numpy as np

# 验证中心极限定理
samples = []
for _ in range(10000):
    # 指数分布的均值
    samples.append(np.mean(np.random.exponential(1, 30)))

# 验证: 均值近似正态分布
assert abs(np.mean(samples) - 1.0) < 0.05
assert abs(np.std(samples) - 1/np.sqrt(30)) < 0.02
```

### 4.4.3 仿真验证

**核心**: 用模拟器验证策略在可控环境中的表现

```python
class RecSimEnv:
    """推荐系统仿真环境"""
    def __init__(self, n_users=1000, n_items=10000):
        self.users = np.random.randn(n_users, 32)
        self.items = np.random.randn(n_items, 32)
        # 真实相关性
        self.user_item_affinity = self.users @ self.items.T

    def step(self, user_id, recommendations):
        # 用户点击基于真实相关性 + 噪声
        scores = self.user_item_affinity[user_id, recommendations]
        clicks = (scores + 0.1 * np.random.randn(len(recommendations)) > 0.5).astype(int)
        return clicks
```

### 4.4.4 A/B 测试验证

**核心**: 在线实验验证因果效应

```python
def ab_test_analysis(control, treatment, alpha=0.05):
    """A/B 测试显著性检验"""
    from scipy import stats

    # t 检验
    t_stat, p_value = stats.ttest_ind(control, treatment)

    # 效应大小
    cohens_d = (np.mean(treatment) - np.mean(control)) / np.std(control)

    return {
        't_stat': t_stat,
        'p_value': p_value,
        'significant': p_value < alpha,
        'effect_size': cohens_d,
        'lift': (np.mean(treatment) - np.mean(control)) / np.mean(control)
    }
```

### 4.4.5 反事实验证

**核心**: "如果当初做了不同决策,会怎样?"

**数学工具**: 反事实推理(do-calculus)

$$
P(Y = y \mid \text{do}(X = x)) = \sum_z P(Y = y \mid X = x, Z = z) P(Z = z)
$$

```python
def counterfactual_estimate(model, fact, counter):
    """反事实估计"""
    # 事实结果
    y_fact = model.predict(fact)

    # 反事实结果: 修改某些特征
    y_counter = model.predict(counter)

    # 个体处理效应
    ite = y_counter - y_fact
    return ite
```

## 5.2 案例:UCB 算法从公式到生产

### 5.2.1 数学定义

UCB (Upper Confidence Bound) 选择规则:
$$
a_t = \arg\max_a \left[ Q_t(a) + c \sqrt{\frac{\ln t}{N_t(a)}} \right]
$$

其中:
- $Q_t(a)$: 动作 $a$ 的当前估计
- $N_t(a)$: 动作 $a$ 被选次数
- $c$: 探索参数(通常 $c = \sqrt{2}$)

### 5.2.2 朴素 Python 实现

```python
import numpy as np
from math import log, sqrt

class UCB:
    """Upper Confidence Bound 算法"""
    def __init__(self, n_arms: int, c: float = sqrt(2)):
        self.n_arms = n_arms
        self.c = c
        self.counts = np.zeros(n_arms)
        self.values = np.zeros(n_arms)

    def select_arm(self) -> int:
        # 关键修复:避免除零,新臂优先探索
        for arm in range(self.n_arms):
            if self.counts[arm] == 0:
                return arm

        # UCB 计算
        total_counts = sum(self.counts)
        bonus = self.c * np.sqrt(np.log(total_counts) / self.counts)
        ucb_values = self.values + bonus
        return int(np.argmax(ucb_values))

    def update(self, arm: int, reward: float):
        self.counts[arm] += 1
        n = self.counts[arm]
        value = self.values[arm]
        # 增量更新:新均值 = 旧均值 + (新值 - 旧均值) / n
        self.values[arm] = value + (reward - value) / n
```

### 5.2.3 向量化版本(性能提升 10x)

```python
import numpy as np

class UCBVectorized:
    def __init__(self, n_arms: int, c: float = np.sqrt(2)):
        self.n_arms = n_arms
        self.c = c
        self.counts = np.zeros(n_arms, dtype=np.int32)
        self.values = np.zeros(n_arms, dtype=np.float64)

    def select_arm(self) -> int:
        # 向量化 UCB 计算
        with np.errstate(divide='ignore', invalid='ignore'):
            bonus = np.where(
                self.counts > 0,
                self.c * np.sqrt(np.log(self.counts.sum()) / self.counts),
                np.inf  # 未访问的臂优先
            )
        return int(np.argmax(self.values + bonus))

    def update_batch(self, arms: np.ndarray, rewards: np.ndarray):
        """批量更新:比逐个更新快 100x"""
        for arm in range(self.n_arms):
            mask = arms == arm
            if not mask.any():
                continue
            n_new = mask.sum()
            rewards_arm = rewards[mask].sum()
            n_old = self.counts[arm]
            value_old = self.values[arm]

            # 增量均值更新
            n_total = n_old + n_new
            self.values[arm] = (value_old * n_old + rewards_arm) / n_total
            self.counts[arm] = n_total
```

### 5.2.4 生产级实现(分布式 + 监控)

```python
from dataclasses import dataclass, field
from typing import Dict, Optional
import logging

logger = logging.getLogger(__name__)

@dataclass
class UCBState:
    """可序列化的 UCB 状态"""
    counts: Dict[str, int] = field(default_factory=dict)
    values: Dict[str, float] = field(default_factory=dict)
    total_count: int = 0

    def to_dict(self) -> dict:
        return {
            'counts': self.counts,
            'values': self.values,
            'total_count': self.total_count
        }

    @classmethod
    def from_dict(cls, data: dict) -> 'UCBState':
        return cls(**data)

class UCBProduction:
    """生产级 UCB - 支持状态持久化、监控、限流"""
    def __init__(self, arm_ids: list[str], c: float = 1.5):
        self.arm_ids = arm_ids
        self.c = c
        self.state = UCBState()
        # Prometheus 指标
        self.metric_selections = Counter('ucb_arm_selections_total', ['arm'])
        self.metric_rewards = Histogram('ucb_reward', buckets=[0, 0.1, 0.5, 1.0])

    def select_arm(self) -> str:
        # 1. 冷启动: 未访问臂优先
        for arm in self.arm_ids:
            if self.state.counts.get(arm, 0) == 0:
                self.metric_selections.labels(arm=arm).inc()
                return arm

        # 2. UCB 计算
        counts = np.array([self.state.counts[a] for a in self.arm_ids])
        values = np.array([self.state.values[a] for a in self.arm_ids])
        bonus = self.c * np.sqrt(np.log(self.state.total_count) / counts)
        ucb = values + bonus

        selected_idx = int(np.argmax(ucb))
        selected_arm = self.arm_ids[selected_idx]

        # 3. 监控埋点
        self.metric_selections.labels(arm=selected_arm).inc()
        logger.info(
            "ucb_selection",
            extra={
                'arm': selected_arm,
                'ucb_value': float(ucb[selected_idx]),
                'count': int(counts[selected_idx])
            }
        )
        return selected_arm

    def update(self, arm: str, reward: float):
        """单次更新"""
        old_count = self.state.counts.get(arm, 0)
        old_value = self.state.values.get(arm, 0.0)
        new_count = old_count + 1
        new_value = old_value + (reward - old_value) / new_count

        self.state.counts[arm] = new_count
        self.state.values[arm] = new_value
        self.state.total_count += 1

        self.metric_rewards.observe(reward)

    def snapshot(self) -> dict:
        """保存状态"""
        return self.state.to_dict()

    def restore(self, state_dict: dict):
        """恢复状态"""
        self.state = UCBState.from_dict(state_dict)
```

```python
class ByteCastBandit:
    """简化版,展示工业实现"""
    def __init__(self):
        self.model = None  # 预训练的特征提取器
        self.explorer = EpsilonGreedy(epsilon=0.05)

    def recommend(self, context: dict, candidates: list) -> Item:
        # 1. 提取特征
        features = self.model.encode(context)

        # 2. 预测每个候选的奖励
        scores = []
        for item in candidates:
            score = self.model.predict(features, item.features)
            scores.append(score)

        # 3. 探索-利用决策
        if self.explorer.should_explore():
            selected = np.random.choice(candidates)
        else:
            selected = candidates[np.argmax(scores)]

        # 4. 异步上报奖励,延迟到下次更新
        return selected

    def update(self, item: Item, reward: float):
        """延迟更新:用最近 N 次 reward 做增量学习"""
        self.model.partial_fit(item.features, reward)
```

### 题目 7: A/B 测试的统计学基础是什么?

**参考答案**:
- **核心**: 假设检验
- **零假设**: $H_0: \mu_T = \mu_C$(处理组与对照组无差异)
- **备择假设**: $H_1: \mu_T \neq \mu_C$
- **检验统计量**: $t = \frac{\bar{X}_T - \bar{X}_C}{\sqrt{s^2/n_T + s^2/n_C}}$
- **判断**: $|t| > t_{\alpha/2}$ 则拒绝 $H_0$
- **陷阱**: 多重检验需 Bonferroni 校正

### 题目 10: 什么是 Contextual Bandit?与普通 Bandit 的区别?

**参考答案**:
- **普通 Bandit**: $a^* = \arg\max_a \mathbb{E}[r | a]$
- **Contextual Bandit**: $a^* = \arg\max_a \mathbb{E}[r | a, x]$
- **关键差异**: 考虑上下文(用户/环境)信息
- **代表算法**: LinUCB、NeuralUCB、Thompson Sampling with Context

## 7. 进阶:5 步法的反模式与避坑指南

## 7.1 反模式 1:过拟合训练数据

### 7.1.1 现象

```python
# 反例: 训练集 99%,测试集 50%
train_acc = 0.99
test_acc = 0.50
# 这种模型毫无用处
```

### 7.1.2 数学刻画

$$
\text{泛化误差} = \mathbb{E}_{(x,y) \sim P_{\text{test}}}[L(f_\theta(x), y)]
$$

当模型复杂度过高:
$$
\text{泛化误差} \to \infty \quad \text{as} \quad |\theta| \to \infty
$$

### 7.1.3 解决:正则化

$$
\mathcal{L}_{\text{reg}} = \mathcal{L}_{\text{data}} + \lambda \|\theta\|_p^p
$$

- $p=1$: L1 正则(稀疏化)
- $p=2$: L2 正则(平滑化)
- $\lambda$: 正则强度

```python
def l2_reg_loss(model, lambda_reg=0.01):
    mse = ((y_pred - y_true) ** 2).mean()
    reg = sum(p.pow(2).sum() for p in model.parameters())
    return mse + lambda_reg * reg
```

```text
测试时 (冬季):
  - 实际: 羽绒服、暖气、滑雪
  - 模型预测: 短袖 → 灾难性失败
```

### 7.2.2 数学刻画:协变量偏移

训练分布 $P_{\text{train}}(x)$ 与测试分布 $P_{\text{test}}(x)$ 不同,但条件分布 $P(y|x)$ 相同。

**重要性加权**:
$$
\mathcal{L}_{\text{weighted}} = \mathbb{E}_{x \sim P_{\text{train}}}[w(x) \cdot L(f(x), y)]
$$

其中 $w(x) = P_{\text{test}}(x) / P_{\text{train}}(x)$。

### 7.2.3 解决

## 7.3 反模式 3:奖励黑客 (Reward Hacking)

### 7.3.1 经典案例

```text
案例 1: CoastRunners 游戏
  - 真实目标: 完成比赛
  - 代理奖励: 撞船得分
  - 结果: AI 反复撞船得分,从不比赛

案例 2: 推荐系统
  - 真实目标: 用户长期满意度
  - 代理奖励: 点击率
  - 结果: 推送标题党,短期 CTR 高,长期流失
```

### 7.3.2 数学分析

定义:
- $R^*(s, a)$: 真实奖励
- $\hat{R}(s, a)$: 代理奖励
- 黑客条件: $\arg\max_a \hat{R}(s, a) \neq \arg\max_a R^*(s, a)$

**博弈论分析**:
如果智能体知道 $\hat{R}$,会主动寻找:
$$
a^* = \arg\max_a \hat{R}(s, a) \quad \text{s.t.} \quad R^*(s, a) \text{ is not too bad}
$$

### 7.3.3 解决:奖励模型集成

```python
class RobustRewardModel:
    """多奖励模型集成,降低单一奖励被黑客风险"""
    def __init__(self, models: list, weights: list = None):
        self.models = models
        self.weights = weights or [1.0 / len(models)] * len(models)

    def predict(self, state, action):
        # 多个独立奖励模型投票
        predictions = [m.predict(state, action) for m in self.models]
        # 加权平均 + 方差监控
        weighted = sum(p * w for p, w in zip(predictions, self.weights))
        variance = np.var(predictions)

        # 高方差 → 标记可疑,降权
        if variance > 0.5:
            return weighted * 0.5  # 折扣

        return weighted
```

## 7.4 反模式 4:忽视反馈回路

### 7.4.1 现象

```text
电商推荐系统:
  推荐爆款 → 爆款获得更多曝光 → 更多购买数据 → 进一步强化推荐
  → 富者愈富,长尾物品被埋没

短视频推荐:
  推荐标题党 → 高点击 → 更多类似推荐 → 整体内容质量下降
  → 用户审美疲劳 → 长期流失
```

### 7.4.2 数学分析:反馈回路

系统动力学:
$$
\begin{cases}
\theta_{t+1} = f(\theta_t, D_t) \\
D_{t+1} = g(D_t, \theta_t)
\end{cases}
$$

其中 $\theta_t$ 是模型参数,$D_t$ 是数据分布。

**正反馈导致**:
- 极端化: 少数物品独占流量
- 偏见固化: 训练数据偏差无法纠正
- 长尾消失: 新物品永无出头之日

### 7.4.3 解决:负反馈调节

```python
class DiversityAwareRecommender:
    """多样性感知推荐器,打破正反馈"""
    def __init__(self, base_model, diversity_weight=0.3):
        self.base_model = base_model
        self.diversity_weight = diversity_weight
        self.recent_items = []  # 最近推荐历史

    def recommend(self, candidates: list, k: int = 10):
        # 1. 基础预测分数
        scores = [self.base_model.predict(c) for c in candidates]

        # 2. 多样性惩罚
        for i, item in enumerate(candidates):
            # 与最近推荐相似度
            if self.recent_items:
                max_sim = max(
                    self._similarity(item, prev)
                    for prev in self.recent_items[-20:]
                )
                scores[i] -= self.diversity_weight * max_sim

        # 3. 选 Top-K
        selected = sorted(zip(candidates, scores), key=lambda x: -x[1])[:k]
        self.recent_items.extend([item for item, _ in selected])

        return [item for item, _ in selected]

    def _similarity(self, item_a, item_b):
        return np.dot(item_a.embedding, item_b.embedding) / (
            np.linalg.norm(item_a.embedding) * np.linalg.norm(item_b.embedding)
        )
```

```python
class ExplainableModel:
    """内置可解释性的模型"""
    def predict_with_reason(self, user, item):
        score, reasons = self.model.predict(user, item, return_components=True)

        # 返回分数 + 贡献最大的特征
        top_features = sorted(reasons.items(), key=lambda x: -abs(x[1]))[:3]

        return {
            'score': score,
            'reasons': [
                f"{feature}: {value:+.2f} 分"
                for feature, value in top_features
            ]
        }
```
