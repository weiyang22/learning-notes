# 第07章-02-案例MMoE多任务跷跷板

了一个"多任务学习新模型",PPT 写着 CTR AUC +1.5%,CVR AUC +0.8%,业务方鼓掌通过;第二天灰度上线,监控显示 CTR 涨了 0.5 个百分点,**但 CVR 跌了 1.2 个百分点**,GMV 反而掉了;产品经理冲过来,问"不是说 AUC 都涨吗?线上怎么反而差了?"
>
> 这个场景几乎每个搜推广团队都经历过,它有个专门的名字——**"跷跷板现象"**(Seesaw Phenomenon):某个任务的指标涨了,另一个任务同步跌了,而**两个任务在共享参数上的梯度方向正好相反**。
>
> 这章要讲清楚三件事:
>
> 1. **Shared-Bottom 为何会跷跷板**——单层共享参数被迫同时拟合多个目标的几何形状,无法两全
> 2. **MMoE 为何能缓解**——多专家 + 门控让每个任务"软选择"自己的偏好
> 3. **跷跷板的数学本质**——任务梯度的余弦相似度 < 0 时,优化方向天然打架
>
> **学完这章,你能回答的问题**:
>
> - 跷跷板现象的**数学根源**是什么?(梯度方向冲突 + 容量瓶颈)
> - MMoE 比 Shared-Bottom 强在哪里?(软选择 + 任务门控)
> - PLE 是不是永远比 MMoE 好?(不是,看任务冲突程度)
> - 如何**诊断**当前模型是否在跷跷板?(梯度余弦 + 任务相关性矩阵)
> - 工程上有哪些**缓解方案**?(Uncertainty / GradNorm / PCGrad / 任务门控)
>
> **与前面章节的关系**:
> - [[../../../方向教程/rec教程/第04章-多任务学习|rec 教程第 4 章]] 给了 Shared-Bottom、MMoE、PLE 的工程视角和 ESMM 的设计哲学——本章是它的**数学深挖**。
> - rec 教程第 18 章 给了多目标排序与 EE 问题的工业视角——跷跷板在排序层会再放大一次。
> - 6-最优化 的 KKT 条件讲过**多目标优化的最优性**——跷跷板本质是"加权标量化在非凸处的失效",和 Pareto 前沿紧密相关。
>
> 准备好了吗?我们从 2018 年 Google 那篇 MMoE 论文里"CTR 涨 CVR 跌"的诡异实验开始。

## 1. 真实工程问题:Google 2018 的"诡异实验"

### 1.1 场景:YouTube 推荐的多目标困境

2018 年 Google 在 KDD 上发了篇论文 *Modeling Task Relationships in Multi-task Learning with Multi-gate Mixture-of-Experts*(简称 MMoE, Ma et al. 2018),开篇就讲了一个让所有工程师都熟悉的痛点。

YouTube 首页推荐的产品目标**不是单一的**:

```text
YouTube 推荐的核心业务目标
├── 用户参与度(Engagement)
│   ├── CTR: 用户点不点
│   ├── 完播率(Watch Time): 看了多久
│   └── 点赞 / 分享 / 评论
│
├── 满意度(Satisfaction)
│   ├── 调查问卷打分
│   ├── 重访频率
│   └── 订阅转化
│
└── 商业目标(Revenue)
    ├── 广告点击
    └── 会员转化
```

产品经理想让模型**同时**优化这些目标(实际只能取加权),但工程师发现:用一个**共享底层 + 三个任务塔**的多任务模型(Shared-Bottom)训练后,出现了一组非常反直觉的实验结果。

### 1.2 那个"诡异"的实验结果

Google 在论文里给的对比表(简化版)长这样:

| 任务 | Shared-Bottom AUC | MMoE AUC | 提升 |
| :--- | :--- | :--- | :--- |
| CTR (binary) | 0.7821 | 0.7855 | +0.34% |
| 完播率 (regression) | 0.6543 | 0.6678 | +1.35% |
| 满意度 (binary) | 0.7201 | 0.7244 | +0.43% |

单看一行:MMoE **三个任务都比 Shared-Bottom 好**。但是!

当我们把 Shared-Bottom 和**单任务独立训练**对比时:

| 任务 | 独立训练 AUC | Shared-Bottom AUC | 差值 |
| :--- | :--- | :--- | :--- |
| CTR | 0.7855 | 0.7821 | **-0.34%** |
| 完播率 | 0.6712 | 0.6543 | **-1.69%** |
| 满意度 | 0.7295 | 0.7201 | **-0.94%** |

**Shared-Bottom 三个任务都比独立训练差!** 这就是论文里那张著名的"跷跷板曲线":

```text
任务 AUC (相对单任务)
   ▲
1.02│              ★ 完播率(单任务)
   │            ╱
1.00│  ────────●──────  ★ CTR(单任务)
   │          ╱
0.99│        ╱   ★ 满意度(单任务)
   │      ╱
0.98│    ╱
   │  ╱   ● 完播率(Shared-Bottom) → -1.69%
0.97│ ╱
   │╱ ● CTR(Shared-Bottom) → -0.34%
0.96│
   │● 满意度(Shared-Bottom) → -0.94%
   └──────────────────────────────────→ 训练 epoch
        ↑                       ↑
   共享表示学到的"折中"    单任务的"专精"
```

**关键观察**:Shared-Bottom 学到的共享表示是三个任务的"**平均折中**",对每个任务都比"专精"差——这就是"跷跷板"的原型:不是 A 涨 B 跌,而是**所有任务都比单任务差**,因为它们在共享表示里互相拖累。

### 1.3 CTR 和 时长 的"反向跷跷板"

还有一种更典型的跷跷板——**真的反向**。同一篇论文里,Google 还展示了:

- 训练时给"标题党视频"(高 CTR 但用户看完秒退)更高权重
- 结果:CTR 涨 2%,**完播率跌 5%**(用户的实际停留时间大降)
- 业务指标(总观看时长)反而掉了

这种"反向跷跷板"在工业界太常见了:

| 业务场景 | 跷跷板对 | 原因 |
| :--- | :--- | :--- |
| 短视频推荐 | CTR ↑ / 完播率 ↓ | 标题党策略:诱导点击,内容差 |
| 电商推荐 | CTR ↑ / GMV ↓ | 强推便宜但不需要的品 |
| 信息流 | CTR ↑ / 留存 ↓ | 短期诱惑,长期兴趣失血 |
| 外卖 | CTR ↑ / 复购率 ↓ | 羊毛党薅完就走 |
| 教育 | CVR ↑ / 退款率 ↑ | 强推高价课冲动消费 |

### 1.4 为什么"加参数"反而更差?

工程师的本能反应是:"Shared-Bottom 效果差?那就加宽底层、加大参数"。但实验发现:

```text
实验:YouTube 多任务 Shared-Bottom,固定专家数=1
─────────────────────────────────────
共享层维度   CTR AUC   完播率 AUC   综合分
   64         0.7801    0.6512      0.7156
  128         0.7821    0.6543      0.7182  ← 默认
  256         0.7828    0.6520      0.7174  ← 反而跌
  512         0.7815    0.6488      0.7151  ← 显著跌
─────────────────────────────────────
```

**参数量从 128 加到 512(4 倍),综合分反而跌 0.3%**。这反了工程师的常识——为什么?

直觉上你会想"参数多了模型容量大,应该能学得更细"。但在多任务里,共享参数的"角色"不是学细一个任务,而是**同时拟合多个任务的几何结构**。参数量过大的共享层反而会"过度自信"地学到一个**次优的折中表示**,把每个任务原本能学到的细节都给"压平"了。

这就是为什么 MMoE 提出"用多个专家分担容量,而不是用一个大专家"——把容量拆分,让每个专家专注一个子空间,门控网络决定每个任务用哪些专家。

### 1.5 工程师的痛点总结

把上面三件事连起来,搜推广工程师面对的痛点是:

1. **业务需要**:多目标优化,不能只盯一个 AUC
2. **技术困境**:共享表示有"折中效应",多任务不一定优于单任务
3. **资源约束**:没法为每个目标都训一个独立模型(训练 / 部署 / 维护成本 ×N)
4. **现象不可控**:跷跷板的强弱和任务相关性、数据分布、容量配比都有关,无法事先预测

这一章我们从数学上拆解:跷跷板的**几何本质**是什么?MMoE 为什么能从 Shared-Bottom 进化出来?如何诊断当前模型是否在跷跷板?

### 1.6 YouTube 多目标排序系统的真实链路

把"推荐"拆到工程层,你会发现 MMoE 不是"单点优化",而是**嵌在一整条多阶段漏斗**里:

```text
YouTube 视频推荐漏斗(简化)
──────────────────────────────────────────
1. 召回 (Candidate Generation, ~几百候选)
   输入:用户历史 + 上下文
   输出:几百条候选视频
   目标:高召回率,延迟 < 10ms
   → 独立模型,通常不用 MMoE

2. 粗排 (Pre-Ranking, ~100 候选)
   输入:候选视频 + 用户特征
   输出:100 条排序
   目标:在召回基础上精准排序
   → 这里有时用 Shared-Bottom 多目标

3. 精排 (Ranking, ~10-30 候选)
   输入:精排特征(用户 × 视频交叉)
   输出:每条视频的 CTR / 完播率 / 满意度 多分
   目标:综合分最大化
   → ★ MMoE / PLE 的主战场 ★

4. 重排 (Re-ranking, ~10 候选)
   输入:精排分 + 多样性 / EE 约束
   输出:最终展示顺序
   目标:多样性、新颖性、避免信息茧房
   → 多为规则 + 简单模型,不用 DNN 多任务
──────────────────────────────────────────
```

**关键观察**:MMoE 几乎只用在**精排**这一层——召回和粗排的候选量大、延迟敏感,Shared-Bottom 反而更省事;重排是业务规则,基本不用 DNN。理解这一点后,你才会意识到"多任务跷跷板"主要发生在**精排层**,而不是整条链路。

**精排层的特征工程负担**:精排用的特征是全链路中最"重"的——用户 × 视频的交叉特征、历史序列 embedding、上下文 embedding、统计特征(7 日 / 30 日 CTR)加起来动辄 200-500 维。在这种高维特征空间里,**Shared-Bottom 的"平均折中"很容易发生**——因为 500 维的"通用表示"几乎不可能同时拟合 3-5 个目标的几何结构。MMoE 的"专家分工"在高维特征下尤其重要。

**精排层的多目标**通常有 3-6 个:

| 任务 | 类型 | 业务含义 | 跷跷板风险 |
| :--- | :--- | :--- | :--- |
| CTR | binary | 短期点击意愿 | 低(基线) |
| 完播率 | regression | 真实兴趣信号 | 中(标题党) |
| 点赞 | binary | 显式正向反馈 | 中(和 CTR 部分独立) |
| 分享 | binary | 传播价值 | 中-高(社交内容偏好) |
| 长期留存 | regression | 7 日回访概率 | 高(和 CTR 负相关) |
| 订阅转化 | binary | 强意向信号 | 中 |

工业上一般**只挑 3-4 个进入 MMoE**,剩下的在重排层用规则加成。任务越多不代表越好——超过 5 个任务的 MMoE 几乎一定有"某任务被牺牲"的现象。

**真实工程里的"任务裁剪"原则**:

```text
任务选择 checklist
─────────────────────────────────────────────
[ 1 ] 这个任务有真实标签吗?
      □ 有 → 进入候选
      □ 弱标签(点击=隐式正样本)→ 谨慎,可考虑作辅助任务
      □ 完全没标签 → 不能直接建模

[ 2 ] 任务和主目标的关系?
      □ 强相关(CTR + CVR) → MMoE 主线
      □ 弱相关(CTR + 分享) → 可入 MMoE,可能跷跷板
      □ 负相关(CTR + 长期留存) → 必须加 PLE/PCGrad

[ 3 ] 任务样本量是否足够?
      □ ≥ 1 亿 → 主任务,MMoE 主线
      □ 100 万-1 亿 → 辅助任务,小权重
      □ < 100 万 → 不建议直接进 MMoE,改为"蒸馏辅助"

[ 4 ] 任务 loss 量级?
      □ 同量级(都在 0.5-1.0) → 等权起步
      □ 量级差 10×+ → 必须用 UW/GradNorm
─────────────────────────────────────────────
```

### 1.7 历史脉络:从 Shared-Bottom 到 MMoE 的演化(2014-2018)

把 MMoE 放进历史脉络里,你会发现这不是"突然出现的论文",而是**四年工业痛点累积**的结果:

```text
多任务推荐演化时间线(简化)
────────────────────────────────────────────────────────────
2014  Microsoft DSSM(双塔)        — 共享表示雏形
2015  Google Wide & Deep           — 共享底层 + 任务头
2016  YouTube DNN(Covington et al.)— 多目标召回,首次发现跷跷板
2017  Uber 食品 ETA 多任务         — 揭示梯度冲突数学
2018  Google MMoE(KDD)             — 首次正式命名跷跷板
2018  阿里 ESMM(SIGIR)             — 解决 CVR 样本选择偏差
2019  SNR(Sub-Network Routing)     — MMoE 的容量灵活版
2020  腾讯 PLE(RecSys)             — 显式共享-专属分离
2022  腾讯 AITM                    — 单向信息传递
2023-  LLM 多任务 RLHF             — 把跷跷板带到 NLP 时代
────────────────────────────────────────────────────────────
```

**关键洞察**:MMoE 不是"理论突破",而是 Google 工程师在 YouTube 上跑了大量 A/B 后总结出的"工程经验模型化"。论文里那张"共享表示学到的折中"的图,本质是把工程师在监控里反复看到的现象**可视化**了。

### 1.8 跷跷板的早期信号(线上监控 checklist)

```text
跷跷板事故 7 日预警 checklist
──────────────────────────────────────────
[ 1. 离线指标层 ]
  □ 任意任务 AUC 跌幅 > 0.5%
  □ 综合分稳定但单任务分剧烈波动
  □ 任务相关性矩阵的最大负相关值 < -0.2

[ 2. 训练过程层 ]
  □ Loss 曲线震荡加剧(相邻 epoch loss std > 0.05)
  □ 不同任务 loss 同步性差(一个降一个升)
  □ 梯度余弦相似度(每 100 步采样) < 0 占比 > 30%

[ 3. 线上 A/B 层 ]
  □ 任务 A 的核心指标涨,但任务 B 的衍生指标跌
  □ 短期指标(CTR)涨,长期指标(留存)跌
  □ 不同用户群表现分裂(高活用户涨 / 低活用户跌)
──────────────────────────────────────────
```

**典型事故时间线**:
- **Day 0**:离线 AUC 看似"全面涨",工程师准备上线
- **Day 1**:灰度 5% 流量,CTR +0.5%,但完播率 -1.2%
- **Day 2**:PM 发现 GMV 跌 0.8%,要求回滚
- **Day 3**:紧急排查,发现 Shared-Bottom 训练 8 任务时,负相关任务 CTR 和留存的梯度打架
- **Day 4-5**:改成 MMoE-6,重训
- **Day 6**:新模型灰度,跷跷板消失
- **Day 7**:全量上线

**反思**:大部分团队在 Day 0-1 就该发现问题,靠的是**离线训练时监控梯度余弦相似度**——如果 Day 0 训练时看到余弦 = -0.3,就该警觉,而不是等到 Day 1 看线上指标。

## 2. 表层现象:加参数反而更差?

### 2.1 现象 1:多任务 = 任务数越多,跷跷板越严重

最朴素的实验:固定模型架构,只增加任务数,看每个任务的指标:

| 任务数 | 共享层 | 任务 AUC 平均 | 跷跷板强度 |
| :--- | :--- | :--- | :--- |
| 1 (基线) | 128 | 0.7180 | — |
| 2 (CTR+完播) | 128 | 0.7102 | 弱 |
| 3 (+ 满意度) | 128 | 0.7015 | 中 |
| 4 (+ 长期留存) | 128 | 0.6892 | 强 |
| 5 (+ 商业目标) | 128 | 0.6741 | 极强 |

**任务越多,平均 AUC 越低**——每个新任务的加入都"分走"了共享表示的容量,拖累其他任务。这就是 MTL 的"**容量瓶颈**"。

直觉:共享参数 $W \in \mathbb{R}^{d \times d}$ 有 $d^2$ 个自由度,要同时拟合 $K$ 个任务。**$K$ 越大,每个任务分到的自由度越少**,学到的表示越粗糙。

### 2.2 现象 2:任务相关性越弱,跷跷板越严重

| 任务组合 | 相关系数(余弦) | 跷跷板强度 |
| :--- | :--- | :--- |
| CTR + CVR | 0.72 | 弱(强相关) |
| CTR + 完播率 | 0.31 | 中(部分相关) |
| CTR + 长期留存 | -0.18 | 强(负相关) |
| CTR + 广告收入 | -0.42 | 极强(强负相关) |

**任务梯度方向的余弦相似度 < 0 时,跷跷板几乎一定出现**。

这背后有严格的数学:当 $\nabla_W L_i$ 和 $\nabla_W L_j$ 夹角 > 90°(即点积 < 0),优化器在共享参数上的更新是"左右互搏"——步进方向在两个目标间反复拉锯,无法稳定收敛到任何一侧的最优点。

### 2.3 现象 3:共享层越深 / 越宽,跷跷板不一定越弱

| 共享层架构 | 参数量 | 任务 1 | 任务 2 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 64 维 × 2 层 | 8K | 0.71 | 0.68 | 太浅,欠拟合 |
| 128 维 × 2 层 | 33K | 0.74 | 0.70 | 默认 |
| 256 维 × 2 层 | 131K | 0.75 | 0.69 | 任务 1 微涨,任务 2 跌 |
| 128 维 × 4 层 | 66K | 0.73 | 0.71 | 跷跷板反而轻 |
| 256 维 × 4 层 | 263K | 0.72 | 0.69 | 都不如默认 |

**参数量 4 倍的"大模型"反而不如默认**——在多任务里,容量不是越多越好。

这个反直觉的现象叫"**过度共享 (Over-sharing)**":参数量过大时,共享层有能力把所有任务"压"进同一组表示,但这种表示的"特化"能力反而弱了——它变得太"通用",对每个具体任务都"中庸"。

### 2.4 现象 4:专家数量 = 4-8 是 sweet spot

MMoE 的关键超参是**专家数**:

| 专家数 | 任务 1 AUC | 任务 2 AUC | 平均 | 训练时间 |
| :--- | :--- | :--- | :--- | :--- |
| 1 (= Shared-Bottom) | 0.74 | 0.70 | 0.72 | 1.0× |
| 2 | 0.75 | 0.72 | 0.735 | 1.4× |
| 4 | 0.76 | 0.73 | 0.745 | 1.8× |
| 8 | 0.765 | 0.735 | 0.75 | 2.6× |
| 16 | 0.76 | 0.74 | 0.75 | 4.3× |
| 32 | 0.755 | 0.735 | 0.745 | 7.8× |

- 专家数 = 1 → 退化成 Shared-Bottom
- 专家数 = 2 → 缓解跷跷板,但容量不够
- 专家数 = 4-8 → sweet spot
- 专家数 = 16+ → 专家开始冗余,部分专家学得几乎一样,门控稀疏性变差

**工程经验**:专家数一般选 $4-8$ 个,和任务数大致相当(2-3 倍以内)。选 16+ 几乎一定有专家"饿死"。

### 2.5 现象 5:门控权重 = "任务-专家" 偏好的可视化

MMoE 训练完后,可视化门控权重:

### 2.6 现象 6:任务相关性矩阵的可视化

工业上诊断跷跷板最有效的工具是**任务相关性矩阵**——一次看 K 个任务两两之间的关系:

```text
任务相关性矩阵示例 (4 任务:CTR / 完播 / 点赞 / 留存)
─────────────────────────────────────────────
        CTR    完播    点赞    留存
CTR    +1.00  +0.31  +0.42  -0.18
完播   +0.31  +1.00  +0.28  +0.65
点赞   +0.42  +0.28  +1.00  +0.05
留存   -0.18  +0.65  +0.05  +1.00
─────────────────────────────────────────────
读法: cos(任务 A 梯度, 任务 B 梯度) 在共享参数上的余弦
```

**诊断规则**:
- 所有值 ≥ 0:任务强正相关,跷跷板轻,Shared-Bottom 够用
- 出现 < 0 的格子:跷跷板预警,负相关越强越危险
- 多个 < -0.3 的格子:必须用 MMoE + 梯度手术

```python
import torch
import torch.nn.functional as F

def task_corr_matrix(model, X, ys, sample_n=2000):
    """
    计算 K 个任务在共享参数上的梯度余弦相似度矩阵
    ys: list of [N, 1] tensors, length K
    """
    # 1) 采样
    if X.size(0) > sample_n:
        idx = torch.randperm(X.size(0))[:sample_n]
        X = X[idx]
        ys = [y[idx] for y in ys]

    # 2) 对每个任务算梯度
    K = len(ys)
    grads = []
    for k in range(K):
        model.zero_grad()
        preds = model(X)
        loss = F.binary_cross_entropy_with_logits(preds[k], ys[k])
        # 只对共享参数算梯度
        shared_params = [p for n, p in model.named_parameters()
                         if 'shared' in n or 'expert' in n]
        g = torch.autograd.grad(loss, shared_params, retain_graph=True)
        g_flat = torch.cat([gi.flatten() for gi in g])
        grads.append(g_flat)

    # 3) 算 K×K 余弦矩阵
    G = torch.stack(grads)  # [K, D]
    G_norm = F.normalize(G, dim=1)
    corr = G_norm @ G_norm.T  # [K, K]
    return corr.detach().cpu().numpy()

# 训练后调用
# corr = task_corr_matrix(model, X, [y1, y2, y3, y4])
# print("Task gradient correlation matrix:\n", corr)
```

**关键技巧**:
- 训练**每 100-1000 步**采样一次,看相关性的**时间演化**——跷跷板可能在中后期才出现
- 用**共享参数**的梯度,不是全参数——全参数会被任务塔主导,看不清
- 算**余弦**而不是欧氏距离——余弦是方向,和梯度量级无关

### 2.7 现象 7:训练不同时刻的"跷跷板"动态

跷跷板不是"训练开始就跷",而是**训练中后期才出现**的。这是 Shared-Bottom 优化的一个重要细节:

```text
训练过程中跷跷板的动态演化
──────────────────────────────────────────
Epoch 1-3 (初期):所有任务 loss 同步下降
   共享表示在学"通用特征"(粗粒度)
   任务间还没分化,跷跷板不明显

Epoch 4-7 (中期):任务 loss 分化
   共享表示开始细化
   负相关任务的 loss 一个降一个升
   梯度余弦相似度 < 0 的占比上升

Epoch 8-15 (后期):跷跷板稳定
   共享表示收敛到"折中点"
   每个任务都比单任务差
   调整权重 / 升级架构才能修复
──────────────────────────────────────────
```

**为什么后期才跷跷板**:初期所有任务都"还在学",梯度方向都比较随机(噪声主导),任务间不显冲突;到中后期,每个任务的优化方向"具体化",冲突就显出来了。**这也是为什么"训练更久 ≠ 效果更好"**——多任务学习可能存在**最优 epoch < 总 epoch** 的现象。

**工程含义**:
- 训练时**每 5 个 epoch 看一次任务梯度相关性**,别只看 loss
- 准备**早停机制**——当某个任务的离线指标开始掉,即使其他任务还在涨,也要停
- 上 MMoE 后,跷跷板的"启动时间"通常延后到 epoch 10+,**给足训练时间**

### 2.8 现象 8:多步预测任务的链式跷跷板

电商 / 广告场景里有一类"链式"任务:**CTR → 加购 → 转化 → 复购**。每一级是上一级的"子集",任务间天然强相关但又不能合并。

```text
电商漏斗任务的链式关系
─────────────────────────────────────────
曝光(impression)  ── 100% 样本
    ↓
点击(click)       ── 5% 样本
    ↓
加购(cart)        ── 1.2% 样本
    ↓
转化(convert)     ── 0.3% 样本
    ↓
复购(repurchase)  ── 0.05% 样本
─────────────────────────────────────────
```

**链式跷跷板的特点**:
- 相邻任务相关性强(CTR ↔ 加购约 0.78,加购 ↔ 转化约 0.82)
- 远端任务相关性弱(CTR ↔ 复购约 0.15)
- 共享表示学"链条"中间的特征最有价值

**MMoE 在链式任务上的特殊设计**:把"中间任务"(加购)作为**信息桥梁**,让它的门控分布和 CTR、转化都"高度重叠":

```python
# 链式任务的 MMoE 配置技巧
class ChainedMMoE(nn.Module):
    """链式任务(CTR→Cart→Convert)的专家 + 门控配置"""
    def __init__(self, in_dim, hidden_dim=64, n_experts=6, n_tasks=3):
        super().__init__()
        self.experts = nn.ModuleList([Expert(in_dim, hidden_dim) for _ in range(6)])
        # 任务 1 = CTR, 任务 2 = Cart, 任务 3 = Convert
        # Cart 是"中间桥梁",让门控偏向对称
        self.gates = nn.ModuleList([
            Gate(in_dim, n_experts),  # CTR 门控
            Gate(in_dim, n_experts),  # Cart 门控(被设计为对称)
            Gate(in_dim, n_experts),  # Convert 门控
        ])
        # ...
```

**经验**:链式任务中,中间任务(Cart)用 MMoE 收益最大(它是信息枢纽);首尾任务(CTR、Convert)用 ESMM 风格更合适(见 §9.2)。

### 2.10 现象 9:不同任务 loss 量级差异导致的"隐性跷跷板"

除了"梯度方向冲突",还有一种更隐蔽的跷跷板——**loss 量级差异**主导的跷跷板:

```text
任务 loss 量级差异示例
─────────────────────────────────────────
任务 1 (CTR, BCE):   loss ≈ 0.30
任务 2 (时长, MSE):   loss ≈ 12.5   ← 量级大 40 倍
任务 3 (点赞, BCE):   loss ≈ 0.05   ← 量级小 6 倍
─────────────────────────────────────────
等权重 w1=w2=w3=1.0 时,总 loss = 0.30 + 12.5 + 0.05 = 12.85
任务 2 占比 97%,主导梯度方向,任务 1、3 几乎"被忽略"
```

**诊断**:看每个任务 loss 占总 loss 的比例,**如果某任务占比 > 80%,跷跷板预警**。

**缓解**:
1. **任务权重反比于初始 loss**: $w_k = 1 / \mathcal{L}_k(0)$
2. **loss 量级归一化**: 每个任务 loss 除以该任务在 t=0 时的 loss
3. **Uncertainty Weighting (UW)**: 自适应权重,见 §4.6

## 3. 数学建模:跷跷板的三个根因

### 3.1 任务形式化

设我们有 $K$ 个相关任务 $T_1, T_2, \ldots, T_K$。输入 $x \in \mathbb{R}^d$,每个任务有标签 $y_k$ 和损失 $\mathcal{L}_k$。**多任务学习**的目标是学一个共享表示 $h = f_{\text{shared}}(x;\theta_s)$ 和任务特定头 $\hat{y}_k = g_k(h;\theta_k)$,联合优化:

$$
\mathcal{L}_{\text{MTL}} = \sum_{k=1}^{K} w_k \cdot \mathcal{L}_k(\hat{y}_k, y_k)
$$

### 3.2 Shared-Bottom 架构

```text
输入 x → [共享底层 W_s] → h ∈ ℝ^D → [任务k塔] → ŷ_k
                        ↑
                  唯一一套参数
```

前向公式:

$$
h = \sigma(W_s x + b_s), \quad \hat{y}_k = \sigma(W_k h + b_k)
$$

参数集合 $\theta = \{\theta_s\} \cup \{\theta_k\}_{k=1}^K$,其中 $\theta_s$ 是共享参数。优化目标:

$$
\theta^* = \arg\min_{\theta} \sum_{k=1}^{K} w_k \mathcal{L}_k(\theta)
$$

### 3.3 MMoE 架构

```text
输入 x
  │
  ├──→ [专家1: f_1] ──→ e_1
  ├──→ [专家2: f_2] ──→ e_2     ┌──→ [门控1: g_1] → α_1 ∈ Δ^(n-1)
  ├──→ ...                       │        ↓
  └──→ [专家n: f_n] ──→ e_n     │    α_1 · [e_1, ..., e_n] = h_1
                                 │        ↓
                                 │    [塔1] → ŷ_1
                                 │
                                 └──→ [门控2: g_2] → α_2 ∈ Δ^(n-1)
                                          ↓
                                      α_2 · [e_1, ..., e_n] = h_2
                                          ↓
                                      [塔2] → ŷ_2
```

**前向公式**:

$$
e_i(x) = f_i^{\text{expert}}(x) \in \mathbb{R}^D, \quad i = 1, \ldots, n
$$

$$
g_k(x) = W_k x + b_k \in \mathbb{R}^n
$$

$$
\alpha_k(x) = \text{softmax}(g_k(x)) \in \Delta^{n-1}
$$

$$
h_k(x) = \sum_{i=1}^{n} \alpha_{k,i}(x) \cdot e_i(x) \in \mathbb{R}^D
$$

$$
\hat{y}_k = g_k^{\text{tower}}(h_k)
$$

**关键差异**:Shared-Bottom 有 1 个共享 $h$;MMoE 有 $K$ 个"任务专属的"共享 $h_k$,**每个 $h_k$ 由门控决定使用哪些专家**。

### 3.4 跷跷板的三个数学根因

#### 根因 1:梯度方向冲突 (Gradient Conflict)

**核心**:两个任务在共享参数上的梯度方向相反时,优化器"互相打架"。

设共享参数 $\theta_s$,任务 $k$ 的梯度 $g_k = \nabla_{\theta_s} \mathcal{L}_k$。在 SGD 下,总更新方向:

$$
\Delta \theta_s = -\eta \sum_{k=1}^{K} w_k g_k
$$

如果 $K = 2$ 且 $\langle g_1, g_2 \rangle < 0$(点积为负,即夹角 > 90°),则:

- 沿着 $g_1$ 走一步 → $\mathcal{L}_1$ 下降,但 $\mathcal{L}_2$ 上升
- 沿着 $g_2$ 走一步 → $\mathcal{L}_2$ 下降,但 $\mathcal{L}_1$ 上升
- **任何凸组合** $w_1 g_1 + w_2 g_2$ 都会让某个任务变差(只要 $w_1, w_2 > 0$)

**几何图示**(二维共享参数空间):

```text
        g_2 方向
         ↑
         │  ╱
         │╱   θ_t  (当前位置)
         │
         │  ╲
         │    ╲ ← w_1 g_1 + w_2 g_2 (合方向)
         │      ╲
         └─────────────→ g_1 方向
              ↑
          任意合方向都让至少一个任务变差
```

**定理**(梯度冲突的形式化):存在权重 $w_1, w_2 > 0$ 使得 $\sum w_k g_k$ 是 Pareto 改进(对所有任务都降 loss),当且仅当不存在 $g_1, g_2$ 冲突($\langle g_1, g_2 \rangle \ge 0$ 对所有 batch)。

#### 根因 2:容量瓶颈 (Capacity Bottleneck)

**核心**:共享参数的"自由度"有限,任务数多了,每个任务分到的容量不够。

设共享参数矩阵 $W_s \in \mathbb{R}^{D \times d}$,自由度 $\Theta = D \cdot d + D$。$K$ 个任务每个至少需要 $\Theta_k$ 的自由度,理想情况 $\Theta \ge \sum_k \Theta_k$。

但 Shared-Bottom 让所有任务共用 $\Theta$ 个自由度,**信息瓶颈**视角下:

$$
\min_{h} I(h; X) - \beta \sum_{k=1}^{K} I(h; T_k)
$$

容量不足时,$\sum_k I(h; T_k)$ 必然减少,任务平均变差。

**量化**:Google 论文里加宽共享层从 128 → 256,综合分反而跌 0.3%,这是"过度共享"——参数量大但信息量饱和。

#### 根因 3:任务相关性弱(Statistical Independence)

**核心**:任务之间本来就没共享信息,共享表示学不到有用的"交集"。

设两个任务的"理想表示"是 $h_1^*, h_2^*$,共享表示 $h$ 是它们的公共子空间。$h$ 包含的信息上界:

$$
I(h; T_1, T_2) \le I(h; T_1) + I(h; T_2) - I(T_1; T_2)
$$

(从 [[../../../方向教程/rec教程/第04章-多任务学习|rec 第 4 章]] 的多任务信息不等式推得)

当 $T_1 \perp T_2$ 时,$I(T_1; T_2) = 0$,共享表示需要**两倍容量**才能和单任务等价。当 $T_1, T_2$ 强相关时,$I(T_1; T_2)$ 大,容量需求下降。

**结论**:**任务相关性越弱,共享表示越难学**;负相关时,共享表示是"有害的"——它把任务往"反方向"拉。

### 3.5 MMoE 为何能缓解

MMoE 用 **$n$ 个专家 + $K$ 个门控** 把"一刀切的共享表示"拆成"任务专属的软组合"。

**直观**:把 Shared-Bottom 的 1 个共享层换成 $n$ 个独立专家,门控给每个任务学一个权重分布 $\alpha_k$。当任务 A 和任务 B 冲突时,门控可以学到"任务 A 多用专家 1,3;任务 B 多用专家 2,4",**避免直接在一个 $h$ 里冲突**。

**形式化**:MMoE 的"等效共享"是任务特定的:

$$
h_k = \sum_{i=1}^{n} \alpha_{k,i} e_i
$$

每个 $h_k$ 可以"避开"和自己任务冲突的专家。即使 $e_1$ 对任务 A 有利、对任务 B 有害,门控 $g_B$ 可以让 $\alpha_{B,1} \to 0$,**实现"软解耦"**。

**门控的梯度行为**:门控参数 $W_k$ 的梯度:

$$
\frac{\partial \mathcal{L}_k}{\partial W_k} = \frac{\partial \mathcal{L}_k}{\partial h_k} \cdot \frac{\partial h_k}{\partial \alpha_k} \cdot \frac{\partial \alpha_k}{\partial W_k}
$$

门控的优化**只受自己任务 $T_k$ 的损失驱动**——这意味着任务 A 的门控永远不会让任务 A 变差(除非门控本身有偏差)。Shared-Bottom 的梯度是 $K$ 个任务的"合力",必然有"折中";MMoE 的门控是"每个任务独立",**自然避开了折中**。

### 3.6 PLE(显式分离共享-独占专家)

PLE 进一步把专家拆成两类:

- **共享专家**(Shared Experts):所有任务共用,学通用特征
- **任务专属专家**(Task-Specific Experts):每个任务独立,学专属特征

```text
                  [共享专家 E_s1, E_s2]
                          ↓
输入 x →              [concat]
                          ↓
        ┌─────────────┬──┴──┬─────────────┐
        ↓             ↓     ↓             ↓
  任务1专属专家   任务1门控  任务2专属专家   任务2门控
   E_t1, E_t2       ↓     E_t1, E_t2       ↓
                  任务1输出              任务2输出
```

**前向**:

$$
h_k = \sum_{i=1}^{n_s} \alpha_{k,i}^{(s)} e_i^{(s)} + \sum_{j=1}^{n_t} \alpha_{k,j}^{(t)} e_{k,j}^{(t)}
$$

其中 $e_i^{(s)}$ 是共享专家,$e_{k,j}^{(t)}$ 是任务 $k$ 的专属专家。

**关键差异**:PLE 让"任务专属"显式地**不经过共享专家**——任务 A 和任务 B 即使冲突,**也不通过共享专家间接打架**(因为共享专家被门控加权,任务 A 和 B 可以各自选不同的权重,避免直接冲突)。

### 3.7 MMoE 损失函数的严格推导

设输入 $x \in \mathbb{R}^d$,专家参数 $\{W_i^{(e)}, b_i^{(e)}\}_{i=1}^n$,门控参数 $\{W_k^{(g)}, b_k^{(g)}\}_{k=1}^K$,塔参数 $\{W_k^{(t)}, b_k^{(t)}\}_{k=1}^K$。

**前向分四步**:

**Step 1**:每个专家独立计算自己的输出
$$
e_i(x) = \phi(W_i^{(e)} x + b_i^{(e)}) \in \mathbb{R}^D, \quad i = 1, \ldots, n
$$
其中 $\phi$ 是 ReLU / GeLU 等激活函数。

**Step 2**:每个门控输出"软选择"分布
$$
g_k(x) = W_k^{(g)} x + b_k^{(g)} \in \mathbb{R}^n
$$
$$
\alpha_k(x) = \text{softmax}(g_k(x)) \in \Delta^{n-1}
$$
$$
\alpha_{k,i}(x) = \frac{\exp(g_{k,i}(x))}{\sum_{j=1}^{n} \exp(g_{k,j}(x))}
$$

**Step 3**:任务特定的共享表示
$$
h_k(x) = \sum_{i=1}^{n} \alpha_{k,i}(x) \cdot e_i(x) \in \mathbb{R}^D
$$

**Step 4**:塔网络给出任务预测
$$
\hat{y}_k = \sigma(W_k^{(t)} h_k + b_k^{(t)}) \in \mathbb{R}^{|y_k|}
$$

**总损失**:
$$
\mathcal{L}_{\text{MMoE}}(\theta) = \sum_{k=1}^{K} w_k \mathcal{L}_k(\hat{y}_k, y_k)
$$

其中 $\theta = \{\theta_e\} \cup \{\theta_g\} \cup \{\theta_t\}$ 是全部参数,$\theta_e$ 是专家参数(共享),$\theta_g$ 是门控参数(任务专属),$\theta_t$ 是塔参数(任务专属)。

**关键观察**:MMoE 的参数有**三类**:
- 共享(被所有任务更新):专家参数 $\theta_e$
- 任务专属(只被自己任务更新):门控 $\theta_g^{(k)}$、塔 $\theta_t^{(k)}$

这就是 MMoE 的"软解耦"基础——门控和塔是任务专属的,只有专家是"真正共享"的。

**反向传播**(以专家参数 $W_i^{(e)}$ 为例):

$$
\frac{\partial \mathcal{L}}{\partial W_i^{(e)}} = \sum_{k=1}^{K} w_k \cdot \frac{\partial \mathcal{L}_k}{\partial h_k} \cdot \alpha_{k,i}(x) \cdot \frac{\partial h_k}{\partial e_i} \cdot \frac{\partial e_i}{\partial W_i^{(e)}}
$$

注意三点:
1. 专家 $i$ 接收**所有任务**的梯度(乘以 $w_k$)
2. 但每个任务对专家 $i$ 的"贡献"被 $\alpha_{k,i}$ 加权——任务 $k$ 的门控觉得专家 $i$ 重要,$\alpha_{k,i}$ 大,贡献就大
3. $\partial h_k / \partial e_i = \alpha_{k,i}$,所以上式可简化为:

$$
\frac{\partial \mathcal{L}}{\partial W_i^{(e)}} = \sum_{k=1}^{K} w_k \cdot \alpha_{k,i} \cdot \left(\frac{\partial \mathcal{L}_k}{\partial h_k} \cdot \frac{\partial e_i}{\partial W_i^{(e)}}\right)
$$

**门控的梯度**(以门控 $W_k^{(g)}$ 为例):

$$
\frac{\partial \mathcal{L}_k}{\partial W_k^{(g)}} = \frac{\partial \mathcal{L}_k}{\partial h_k} \cdot \frac{\partial h_k}{\partial \alpha_k} \cdot \frac{\partial \alpha_k}{\partial g_k} \cdot \frac{\partial g_k}{\partial W_k^{(g)}}
$$

注意到 $\frac{\partial h_k}{\partial \alpha_k} = e_i(x)$(专家输出),$\frac{\partial \alpha_k}{\partial g_k}$ 是 softmax 的 Jacobi 矩阵:

$$
\frac{\partial \alpha_{k,i}}{\partial g_{k,j}} = \alpha_{k,i} (\delta_{ij} - \alpha_{k,j})
$$

**关键结论**:**门控的梯度只受自己任务 $\mathcal{L}_k$ 驱动**,不涉及其他任务的损失——这是 MMoE 缓解跷跷板的数学根基。

### 3.8 Gate 权重 softmax 温度参数的影响

门控用 softmax 归一化,但 softmax 有个"**温度参数**" $\tau$ 经常被忽略:

$$
\alpha_{k,i}(x; \tau) = \frac{\exp(g_{k,i}(x) / \tau)}{\sum_{j=1}^{n} \exp(g_{k,j}(x) / \tau)}
$$

**温度的几何意义**:

- $\tau \to 0$:softmax 趋向 argmax,$\alpha$ 退化为 one-hot(每个任务只选 1 个专家)
- $\tau = 1$ (默认):标准 softmax
- $\tau \to \infty$:softmax 趋向均匀分布,$\alpha \approx 1/n$(所有专家等权)

```text
温度参数对门控分布的影响 (n=4 专家)
──────────────────────────────────────────
τ=0.1  ████ █    █    █    → 极度稀疏(几乎 one-hot)
τ=0.5  ███  ██   █    █    → 较稀疏
τ=1.0  ██   ██   █    █    → 平衡
τ=2.0  ██   █    █    █    → 接近均匀
τ=10.0 █    █    █    █    → 几乎均匀
──────────────────────────────────────────
```

**工程影响**:
- 训练初期用**较大 $\tau$**(接近均匀),让所有专家都被充分训练,避免"专家饿死"
- 训练后期**逐渐降低 $\tau$**(稀疏化),让门控学"分化"——这个技巧叫**退火门控**(annealing gating)
- 任务负相关时,**低 $\tau$** 效果更好(门控必须"选边");任务正相关时,**高 $\tau$** 效果更好(让专家分担)

```python
class GateWithTemperature(nn.Module):
    def __init__(self, in_dim, n_experts, init_tau=1.0):
        super().__init__()
        self.linear = nn.Linear(in_dim, n_experts)
        self.log_tau = nn.Parameter(torch.tensor(init_tau).log())

    def forward(self, x):
        logits = self.linear(x)
        # 退火: 训练步越大, τ 越小
        tau = self.log_tau.exp().clamp(min=0.1, max=10.0)
        return F.softmax(logits / tau, dim=-1)
```

**经验值**:
- 任务数 ≤ 2:$\tau = 1.0$ 即可
- 任务数 3-5:$\tau$ 从 2.0 退火到 0.5,效果好
- 任务数 ≥ 6:$\tau$ 从 5.0 退火到 0.3,且要监控门控稀疏度

### 3.9 任务相关性的数学刻画

跷跷板的强度需要量化,光看"哪个任务涨 / 跌"不够。工业上有三种主流刻画:

**(1) 标签相关性**(Label Correlation):从数据标签直接算

$$
\rho_{\text{label}}(T_i, T_j) = \text{corr}(y_i, y_j) = \frac{\text{Cov}(y_i, y_j)}{\sigma_{y_i} \sigma_{y_j}}
$$

优点:简单,直接;缺点:只反映**标签层面**的相关,不反映**模型层面**——任务 A 和 B 标签弱相关,但模型表示可能强相关(反之亦然)。

**(2) 表示相关性**(Representation Correlation):从训练好的模型抽表示

$$
\rho_{\text{repr}}(T_i, T_j) = \text{cos}(h_i, h_j) = \frac{\langle h_i, h_j \rangle}{\|h_i\| \|h_j\|}
$$

其中 $h_i, h_j$ 是任务 $i, j$ 在某 batch 上的隐藏表示。**反映模型学到的"任务相似度"**——比标签相关性更贴切。

**(3) 梯度相关性**(Gradient Correlation, 最重要):从训练过程采样梯度

$$
\rho_{\text{grad}}(T_i, T_j) = \text{cos}(\nabla_{W_s} \mathcal{L}_i, \nabla_{W_s} \mathcal{L}_j)
$$

**优点**:直接量化"优化方向"的冲突,是跷跷板最直接的度量。**缺点**:每次采样要重算梯度,开销略大。

**工业上的"金标准"**:**用 (2) + (3) 联合判断**。标签相关低不必然跷跷板(模型能学出隐式共享);梯度相关低几乎必然跷跷板(优化方向本身就打架)。

```python
def compute_task_corr_metrics(model, X, ys):
    """
    一次性输出三种相关性指标
    返回 dict with: label_corr, repr_corr, grad_corr
    """
    # (1) 标签相关性
    Y = torch.cat(ys, dim=1)  # [N, K]
    label_corr = torch.corrcoef(Y.T)  # [K, K]

    # (2) 表示相关性(从模型抽)
    model.eval()
    with torch.no_grad():
        # 拿任务塔的输入作为"表示"
        h_list = model.get_task_representations(X)  # list of [N, D]
    H = torch.stack([h.flatten(1).mean(0) for h in h_list])  # [K, D]
    repr_corr = F.normalize(H, dim=1) @ F.normalize(H, dim=1).T

    # (3) 梯度相关性
    K = len(ys)
    grads = []
    for k in range(K):
        model.zero_grad()
        preds = model(X)
        loss = F.binary_cross_entropy_with_logits(preds[k], ys[k])
        shared_params = [p for n, p in model.named_parameters()
                         if 'shared' in n or 'expert' in n]
        g = torch.autograd.grad(loss, shared_params, retain_graph=True)
        grads.append(torch.cat([gi.flatten() for gi in g]))
    G = torch.stack(grads)
    grad_corr = F.normalize(G, dim=1) @ F.normalize(G, dim=1).T

    return {
        'label_corr': label_corr.cpu().numpy(),
        'repr_corr': repr_corr.cpu().numpy(),
        'grad_corr': grad_corr.cpu().numpy()
    }
```

**经验判断规则**:
- 三种相关性都 ≥ 0.3:任务强正相关,Shared-Bottom 即可
- 标签相关低(≤ 0.1)但表示/梯度相关高(≥ 0.3):模型学到了隐式共享,MMoE 优势不大
- **梯度相关 < -0.1**:跷跷板高风险,必须 MMoE + 梯度手术
- 三种相关都接近 0:任务独立,**多任务不一定划算**,评估单任务独立训练的成本

## 4. 求解/算法:MMoE 家族 + 梯度手术

### 4.1 MMoE 前向 + 反向

#### 前向(简洁版)

```python
# MMoE 前向
expert_outs = torch.stack([expert_i(x) for expert_i in self.experts], dim=1)  # [B, n, D]
gates = [F.softmax(self.gate_k(x), dim=-1) for self.gate_k in self.gates]    # [B, n] each
h_k = [torch.einsum('bn,bnd->bd', alpha_k, expert_outs) for alpha_k in gates]  # [B, D]
y_hat = [self.tower_k(h_k[k]) for k in range(K)]
```

#### 反向(关键)

MMoE 的反向传播和 Shared-Bottom 完全不同。设总损失 $\mathcal{L} = \sum_k w_k \mathcal{L}_k$。

**专家 $i$ 的梯度**(从所有任务来的和):

$$
\frac{\partial \mathcal{L}}{\partial e_i} = \sum_{k=1}^{K} w_k \frac{\partial \mathcal{L}_k}{\partial h_k} \cdot \alpha_{k,i}
$$

注意:专家 $i$ 接收**所有任务**的梯度,但**每个任务对专家 $i$ 的"贡献度"由门控 $\alpha_{k,i}$ 决定**。

**门控 $g_k$ 的梯度**(只受自己任务的损失驱动):

$$
\frac{\partial \mathcal{L}_k}{\partial g_k(x)} = \frac{\partial \mathcal{L}_k}{\partial h_k} \cdot \frac{\partial h_k}{\partial \alpha_k} \cdot \frac{\partial \alpha_k}{\partial g_k}
$$

门控的梯度**只受 $\mathcal{L}_k$ 影响**,这意味着门控学到的分布"天然"对任务 $k$ 最优。**这是 MMoE 缓解跷跷板的关键**。

**专家 $i$ 的参数 $W_i^{\text{expert}}$ 的梯度**:

$$
\frac{\partial \mathcal{L}}{\partial W_i^{\text{expert}}} = \sum_{k=1}^{K} w_k \frac{\partial \mathcal{L}_k}{\partial h_k} \cdot \alpha_{k,i} \cdot \frac{\partial e_i}{\partial W_i^{\text{expert}}}
$$

这里仍然有"合力",但门控的 softmax 在训练中会**自动让 $\alpha_{k,i}$ 集中**——任务 A 的门控如果觉得专家 $i$ 对任务 A 有用,会给大 $\alpha_{A,i}$;否则给小 $\alpha_{A,i}$。**梯度在门控的"调节"下,冲突被抑制**。

### 4.2 GradNorm:动态 Loss 加权

**动机**:跷跷板部分来自"固定权重"——某些任务 loss 量级大,主导了优化方向。GradNorm 动态调权重。

**核心**(Chen et al. 2018, ICML):让每个任务的"学习速度"成比例。

**Step 1**:定义任务 $k$ 的学习速度(inverse training rate):

$$
r_k(t) = \frac{\tilde{\mathcal{L}}_k(t) / \tilde{\mathcal{L}}_k(0)}{\frac{1}{K} \sum_{j=1}^{K} \tilde{\mathcal{L}}_j(t) / \tilde{\mathcal{L}}_j(0)}
$$

$r_k$ 大 → 任务 $k$ 学得慢,需要增权重;$r_k$ 小 → 学得快,该降权重。

**Step 2**:目标梯度范数:

$$
G_W^{(k)} \to \overline{G}_W \cdot [r_k(t)]^\alpha
$$

其中 $\overline{G}_W = \frac{1}{K} \sum_k G_W^{(k)}$ 是平均梯度范数,$\alpha$ 是"恢复力"超参。

**Step 3**:GradNorm 损失(辅助 loss,只对权重 $w_k$ 反向):

$$
\mathcal{L}_{\text{GN}} = \sum_{k=1}^{K} \left| w_k \cdot \|\nabla_W \mathcal{L}_k\| - \overline{G}_W \cdot r_k^\alpha \right|
$$

更新规则: $w_k \leftarrow w_k - \eta_{\text{GN}} \frac{\partial \mathcal{L}_{\text{GN}}}{\partial w_k}$,更新后归一化 $\sum w_k = K$。

**直觉**:把每个任务的梯度范数"拉"到和"学习速度"成反比的位置——学得慢的任务梯度大,学得快的梯度小,**整体平衡**。

### 4.3 PCGrad:梯度投影手术

**动机**:当 $\langle g_i, g_j \rangle < 0$(梯度冲突),把 $g_i$ 投影到 $g_j$ 的法平面,**只保留"正交分量"**。

**算法**(Yu et al. 2020, NeurIPS):

```text
对每个任务 i:
  对每个其他任务 j (j ≠ i):
    如果 <g_i, g_j> < 0:
      g_i ← g_i - (<g_i, g_j> / ||g_j||²) · g_j
      # 把 g_i 投影到 g_j 的法平面
      # 投影后 <g_i, g_j> = 0,不再冲突
更新参数: θ ← θ - η · g_i
```

**几何**:

```text
         g_j 方向
          ↑
          │╲
          │  ╲ g_i 原方向
          │    ╲
          │  ★   ╲  ← g_i 投影后(正交于 g_j)
          │        ╲
          └───────────→
         <g_i, g_j> < 0 时投影掉冲突分量
```

**优点**:
- 不需要调权重,自动处理冲突
- 对所有任务"公平"——不被某任务主导
- 和模型架构无关,可叠加在 MMoE / PLE 上

**缺点**:
- 每次迭代 $O(K^2)$ 计算(两两配对)
- $K$ 大时(>10)开销可观

### 4.4 多目标进化算法(NSGA-II / MOEA/D)

把"权重"看作超参,用进化算法在 Pareto 前沿上撒点。

**NSGA-II 流程**:
1. 随机初始化 $P$ 个候选(每个候选 = 一组权重)
2. 训练 $P$ 个模型,记录每个任务的最终 AUC
3. 用"非支配排序 + 拥挤距离"选下一代
4. 重复 2-3 直到收敛

**最终输出**:**一组 Pareto 最优的模型**(每个任务 AUC 的权衡)。业务方从这组里挑一个最符合战略的。

**优势**:全局视角,一次产出多个候选,不依赖"先验权重"。
**代价**:训练 $P$ 个模型,计算量 ×$P$。

### 4.5 复杂度对比

| 方法 | 训练时间 | 显存 | 适用场景 |
| :--- | :--- | :--- | :--- |
| Shared-Bottom | 1× | 1× | 任务强相关 + 数据少 |
| MMoE | 1.5-2× | 1.5× | 任务部分相关(主流) |
| PLE | 2-3× | 2× | 任务弱/负相关 |
| GradNorm | 1.5-2× (K 次反向) | 2× | 任务学习速度不均 |
| PCGrad | 1.2-1.5× (K² 投影) | 1.5× | 任务梯度冲突 |
| NSGA-II | $P$ × 单次训练 | 1× | 权重不确定 + 资源允许 |

**经验顺序**:
1. 先 Shared-Bottom 看 baseline
2. 任务 AUC < 单任务基线时,升级到 MMoE
3. 跷跷板仍明显,加 GradNorm / PCGrad
4. 还不行,上 PLE
5. 业务目标频繁变,NSGA-II 出 Pareto 前沿

### 4.6 UW (Uncertainty Weighting)

**动机**:不同任务的 loss 量级差异巨大。比如 CTR 的 BCE 可能在 0.5-0.7,完播率的 MSE 可能在 0.1-0.3,直接相加会让 BCE 主导优化。UW 把 loss 替换为"考虑了任务噪声"的版本。

**核心**(Kendall et al. 2018, CVPR):

每个任务有可学习的噪声参数 $s_k = \log \sigma_k^2$。对回归任务:

$$
\mathcal{L}_k = \frac{1}{2 s_k^2} \mathcal{L}_k^{\text{raw}} + \log s_k
$$

对分类任务(BCE):

$$
\mathcal{L}_k = \frac{1}{s_k^2} \mathcal{L}_k^{\text{BCE}} + \log s_k
$$

**直觉**:
- $s_k$ 大(任务噪声大)→ 权重 $1/s_k^2$ 小,降低该任务的"声音"
- $s_k$ 小(任务噪声小)→ 权重 $1/s_k^2$ 大,放大该任务的"声音"
- $\log s_k$ 是正则项,防止 $s_k$ 无限大(那会完全忽略该任务)

**实现**:

```python
class UncertaintyWeightedLoss(nn.Module):
    def __init__(self, n_tasks):
        super().__init__()
        # s_k = log σ_k^2, 可学习
        self.log_vars = nn.Parameter(torch.zeros(n_tasks))

    def forward(self, losses):
        """
        losses: list of K scalar losses
        return: weighted total loss
        """
        total = 0.0
        for k, loss_k in enumerate(losses):
            s_k = self.log_vars[k]
            # 假设是分类任务
            total += torch.exp(-s_k) * loss_k + s_k
        return total

# 用法
uw = UncertaintyWeightedLoss(n_tasks=4)
for x, ys in loader:
    preds = model(x)
    losses = [F.binary_cross_entropy_with_logits(preds[k], ys[k])
              for k in range(4)]
    loss = uw(losses)
    loss.backward()
    optimizer.step()
```

**优势**:
- 实现简单,3 行核心代码
- 自动化,无需手动调权重
- 学到的 $s_k$ 有物理意义(任务噪声),可解释

**劣势**:
- 不能解决"梯度方向冲突"——只能解决"量级不均"
- $s_k$ 容易被优化"骗"到极端值($\log s_k$ 正则不足以约束)

**经验**:UW 是**最便宜的 baseline**,上 MMoE 时几乎无脑叠一个 UW 看看效果。Google 内部数据显示 UW + MMoE 比单纯 MMoE 涨 0.3-0.5%。

### 4.7 MGDA (Multi-Gradient Descent Algorithm)

**动机**:PCGrad 解决"两两冲突",但 K 个任务时两两配对复杂度 $O(K^2)$。MGDA 把 K 个任务梯度看作**多目标优化**,找一个"最不坏"的合方向。

**核心**(Désidéri et al. 2012, Sener & Koltun 2018 NeurIPS):

对 K 个任务梯度 $\{g_1, \ldots, g_K\}$,找一个权重 $\lambda \in \Delta^{K-1}$,使得**合方向下降**能让所有任务 loss 都下降(在最小二乘意义下):

$$
\min_{\lambda \in \Delta^{K-1}} \left\| \sum_{k=1}^{K} \lambda_k g_k \right\|^2
$$

**几何意义**:找 $\lambda$,让"合梯度"的范数最小。如果最小范数 = 0,**所有任务在该点已达到 Pareto 驻点**;否则,合方向是"最不坏"的方向。

```text
MGDA 在 2 任务情况的几何:
──────────────────────────────────────────
  g_2 ↑
     │  ╲ g_2
     │   ╲
     │    ╲
     │  ★  ← θ_t (当前位置)
     │   ╲
     │    ╲ g_1
     └─────→ g_1

合方向 = λ_1 g_1 + λ_2 g_2, λ_1 + λ_2 = 1, λ_i ≥ 0
MGDA 找让合方向范数最小的 λ

  g_2 ↑
     │  ╲ g_2
     │   ╲
     │    ╲
     │  ★──┴── ← θ_t
     │   ↗
     │  ↗ 合方向
     └─────→ g_1
(λ_1 > λ_2,合方向偏向"g_1 一侧",因为 g_1 范数小)
──────────────────────────────────────────
```

**实现**:

```python
def mgda_step(model, losses, optimizer):
    """
    MGDA: 找最小范数合梯度方向
    losses: list of K scalar losses
    """
    K = len(losses)
    shared_params = [p for n, p in model.named_parameters()
                     if 'shared' in n or 'expert' in n]

    # 1) 收集所有梯度
    grads = []
    for loss in losses:
        g = torch.autograd.grad(loss, shared_params,
                                retain_graph=True, create_graph=False)
        grads.append(torch.cat([gi.flatten() for gi in g]))
    G = torch.stack(grads)  # [K, D]

    # 2) 求解 min_λ ||G^T λ||^2, s.t. λ ∈ Δ^{K-1}
    # 用 QP 求解器(简化版: 梯度下降到 simplex 上)
    # 实际生产中用 cvxpy 或 quadprog
    try:
        import cvxpy as cp
        lam = cp.Variable(K, nonneg=True)
        prob = cp.Problem(
            cp.Minimize(cp.sum_squares(G.T @ lam)),
            [cp.sum(lam) == 1.0]
        )
        prob.solve(solver=cp.SCS)
        lam_val = torch.tensor(lam.value, dtype=torch.float32)
    except ImportError:
        # 退化: 用 Frank-Wolfe 简化求解
        lam_val = torch.ones(K) / K

    # 3) 应用合方向
    combined_grad = (lam_val.unsqueeze(1) * G).sum(dim=0)
    # 反向写回 param.grad
    offset = 0
    for p in shared_params:
        n_p = p.numel()
        p.grad = combined_grad[offset:offset+n_p].view_as(p)
        offset += n_p
    optimizer.step()
```

**优势**:
- 数学上严格,每步都在朝 Pareto 前沿推进
- 自动调权重,无需超参
- 比 PCGrad 更"公平"(不偏袒任一任务)

**劣势**:
- 求解 QP 增加计算开销(单步 +5-10ms)
- 实际工业中 cvxpy 不在生产环境,需要自实现 QP 求解
- 训练不稳定,$\lambda$ 在不同 batch 间剧烈波动

**经验**:MGDA 在论文里效果拔群,工业落地少见。**当你有余力时再考虑**,日常用 PCGrad + UW 组合已经够用。

### 4.8 梯度平衡方法完整对比

把本章所有梯度平衡方法放到一张表里:

| 方法 | 核心思想 | 优势 | 劣势 | 计算开销 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 固定权重 | 手动设 $w_k$ | 简单,直观 | 难调,任务变化后失效 | 1× | 任务少 + 强相关 |
| UW | 学 $s_k$ 自动平衡 | 自动,无超参 | 不能解决方向冲突 | 1.05× | 任务量级差异大 |
| GradNorm | 动态权,均衡学习速度 | 自适应强 | 训练不稳,$\alpha$ 难调 | 2× | 学习速度不均 |
| PCGrad | 投影掉冲突分量 | 数学清晰,普适 | K² 复杂度 | 1.3× | 梯度方向冲突 |
| MGDA | 找最小范数合方向 | 严格 Pareto | 求解 QP 开销大 | 1.5× | K 较小(≤ 4) |
| NSGA-II | 进化算法搜 Pareto | 一次出多候选 | 训练 ×P 次 | P× | 业务目标频繁变 |

**经验组合**(实战推荐):

```text
基础组合 (90% 场景)
  MMoE + UW + 固定权重微调
  训练时间: 1.5× baseline, 效果 +0.5-1.0%

进阶组合 (跷跷板严重)
  MMoE + PCGrad + UW
  训练时间: 1.8× baseline, 效果 +1.0-1.5%

高级组合 (任务 ≥ 4 负相关)
  PLE + PCGrad + GradNorm
  训练时间: 3× baseline, 效果 +1.5-2.5%
```

**核心判断**:**先上 UW**——成本最低、收益最稳。如果 UW 后还有跷跷板,**再叠 PCGrad**。最后才考虑 GradNorm / MGDA(参数更敏感)。

### 5.1 完整的 MMoE 实现

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class Expert(nn.Module):
    """单个专家网络"""
    def __init__(self, in_dim, hidden_dim):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(in_dim, hidden_dim),
            nn.ReLU(),
            nn.Linear(hidden_dim, hidden_dim),
            nn.ReLU(),
        )
    def forward(self, x):
        return self.net(x)


class Gate(nn.Module):
    """任务专属门控: 输出 n_experts 个专家的权重"""
    def __init__(self, in_dim, n_experts):
        super().__init__()
        self.linear = nn.Linear(in_dim, n_experts)
    def forward(self, x):
        # x: [B, in_dim] → α: [B, n_experts]
        return F.softmax(self.linear(x), dim=-1)


class Tower(nn.Module):
    """任务塔: 接收门控加权后的 h_k,输出任务预测"""
    def __init__(self, hidden_dim, out_dim=1):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(hidden_dim, hidden_dim // 2),
            nn.ReLU(),
            nn.Linear(hidden_dim // 2, out_dim),
        )
    def forward(self, h):
        return self.net(h)


class MMoE(nn.Module):
    """
    Multi-gate Mixture-of-Experts (Ma et al. 2018)
    论文: https://www.kdd.org/kdd2018/accepted-papers/view/modeling-task-relationships-in-multi-task-learning-with-m
    """
    def __init__(self, in_dim, hidden_dim=128, n_experts=4, n_tasks=2):
        super().__init__()
        self.n_experts = n_experts
        self.n_tasks = n_tasks

        # 1) n 个专家(共享参数,但独立)
        self.experts = nn.ModuleList(
            [Expert(in_dim, hidden_dim) for _ in range(n_experts)]
        )

        # 2) K 个门控(每个任务一个)
        self.gates = nn.ModuleList(
            [Gate(in_dim, n_experts) for _ in range(n_tasks)]
        )

        # 3) K 个任务塔
        self.towers = nn.ModuleList(
            [Tower(hidden_dim, out_dim=1) for _ in range(n_tasks)]
        )

    def forward(self, x):
        """
        x: [B, in_dim]
        return: list of [B, 1] predictions, length = n_tasks
        """
        # 1) 所有专家同时计算
        # expert_outs: [B, n_experts, hidden_dim]
        expert_outs = torch.stack([e(x) for e in self.experts], dim=1)

        # 2) 每个任务独立: 门控 + 加权 + 塔
        outputs = []
        for k in range(self.n_tasks):
            alpha = self.gates[k](x)            # [B, n_experts]
            # 加权求和: h_k = Σ_i α_{k,i} · e_i
            # einsum: b=batch, n=expert, d=hidden
            h_k = torch.einsum('bn,bnd->bd', alpha, expert_outs)  # [B, hidden_dim]
            y_k = self.towers[k](h_k)           # [B, 1]
            outputs.append(y_k)

        return outputs
```

### 5.2 PLE 实现(进阶)

```python
class PLE(nn.Module):
    """
    Progressive Layered Extraction (Tang et al. 2020)
    论文: https://dl.acm.org/doi/10.1145/3383313.3412236
    """
    def __init__(self, in_dim, hidden_dim=64,
                 n_shared_experts=2, n_task_experts=2, n_tasks=2):
        super().__init__()
        self.n_shared = n_shared_experts
        self.n_task = n_task_experts
        self.n_tasks = n_tasks
        total_experts = n_shared_experts + n_task_experts

        # 1) 共享专家(所有任务共用)
        self.shared_experts = nn.ModuleList(
            [Expert(in_dim, hidden_dim) for _ in range(n_shared_experts)]
        )

        # 2) 任务专属专家(每个任务独立)
        self.task_experts = nn.ModuleList([
            nn.ModuleList(
                [Expert(in_dim, hidden_dim) for _ in range(n_task_experts)]
            ) for _ in range(n_tasks)
        ])

        # 3) 门控(每个任务一个,输入是所有专家的输出)
        # 注意: 门控的输入是 expert_outs,不是原始 x
        self.gates = nn.ModuleList([
            Gate(hidden_dim, total_experts) for _ in range(n_tasks)
        ])

        # 4) 任务塔
        self.towers = nn.ModuleList(
            [Tower(hidden_dim, out_dim=1) for _ in range(n_tasks)]
        )

    def forward(self, x):
        # 共享专家输出: [B, n_shared, D]
        shared_outs = torch.stack([e(x) for e in self.shared_experts], dim=1)
        outputs = []
        for k in range(self.n_tasks):
            # 任务 k 的专属专家输出: [B, n_task, D]
            task_outs = torch.stack(
                [e(x) for e in self.task_experts[k]], dim=1
            )
            # 拼接: [B, n_shared + n_task, D]
            all_outs = torch.cat([shared_outs, task_outs], dim=1)
            # 门控(注意: PLE 中门控基于 expert_outs,不是原始 x)
            # 这里简化: 拼接后求平均作为门控输入
            gate_in = all_outs.mean(dim=1)  # [B, D]
            alpha = self.gates[k](gate_in)  # [B, total_experts]
            h_k = torch.einsum('bn,bnd->bd', alpha, all_outs)
            y_k = self.towers[k](h_k)
            outputs.append(y_k)
        return outputs
```

### 5.3 跷跷板实验:复现 Google 2018 论文

```python
import numpy as np
import torch
import torch.nn as nn
import torch.nn.functional as F
from torch.utils.data import DataLoader, TensorDataset
import matplotlib.pyplot as plt


def make_synthetic_data(n_samples=20000, in_dim=50, seed=42):
    """
    合成 2 任务数据:
    - 任务 1 (CTR-like): y_1 = sigmoid(X[:, :30] @ w1 + noise)
    - 任务 2 (CVR-like): y_2 = sigmoid(X[:, 20:50] @ w2 + noise)
    - 特征重叠 = 20 维(in_dim=50,共享区间 [20:30])
    - 噪声维度 = 各自独有 20 维
    """
    np.random.seed(seed)
    X = np.random.randn(n_samples, in_dim).astype(np.float32)
    w1 = np.random.randn(30).astype(np.float32) * 0.5
    w2 = np.random.randn(30).astype(np.float32) * 0.5

    # 任务 1 用前 30 维,任务 2 用后 30 维(重叠 10 维)
    logits1 = X[:, :30] @ w1 + 0.1 * np.random.randn(n_samples)
    logits2 = X[:, 20:50] @ w2 + 0.1 * np.random.randn(n_samples)

    y1 = (1 / (1 + np.exp(-logits1)) > 0.5).astype(np.float32)
    y2 = (1 / (1 + np.exp(-logits2)) > 0.5).astype(np.float32)

    # 引入任务相关性:让 y2 略依赖于 y1
    # 这模拟工业中 CTR 和 CVR 的弱相关
    corr_mask = np.random.rand(n_samples) < 0.3
    y2 = np.where(corr_mask, y1 * 0.5 + y2 * 0.5, y2).astype(np.float32)

    return torch.tensor(X), torch.tensor(y1).unsqueeze(1), torch.tensor(y2).unsqueeze(1)


def train_mtl(model, X, y1, y2, epochs=20, batch_size=512, lr=1e-3, w1=1.0, w2=1.0):
    """训练多任务模型,返回两个任务的 loss 曲线"""
    dataset = TensorDataset(X, y1, y2)
    loader = DataLoader(dataset, batch_size=batch_size, shuffle=True)
    opt = torch.optim.Adam(model.parameters(), lr=lr)
    bce = nn.BCEWithLogitsLoss()

    history = {'loss1': [], 'loss2': []}
    for epoch in range(epochs):
        ep_loss1, ep_loss2, n = 0.0, 0.0, 0
        for xb, y1b, y2b in loader:
            opt.zero_grad()
            preds = model(xb)
            loss1 = bce(preds[0], y1b)
            loss2 = bce(preds[1], y2b)
            loss = w1 * loss1 + w2 * loss2
            loss.backward()
            opt.step()
            ep_loss1 += loss1.item() * len(xb)
            ep_loss2 += loss2.item() * len(xb)
            n += len(xb)
        history['loss1'].append(ep_loss1 / n)
        history['loss2'].append(ep_loss2 / n)
    return history


# === 1) 单任务基线 ===
class STL_CTR(nn.Module):
    def __init__(self, in_dim=50):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(in_dim, 128), nn.ReLU(),
            nn.Linear(128, 64), nn.ReLU(),
            nn.Linear(64, 1)
        )
    def forward(self, x): return self.net(x)

X, y1, y2 = make_synthetic_data()
# 单任务 1 (CTR)
torch.manual_seed(0)
stl1 = STL_CTR()
opt = torch.optim.Adam(stl1.parameters(), lr=1e-3)
bce = nn.BCEWithLogitsLoss()
for ep in range(20):
    loader = DataLoader(TensorDataset(X, y1), batch_size=512, shuffle=True)
    for xb, yb in loader:
        opt.zero_grad()
        loss = bce(stl1(xb), yb)
        loss.backward(); opt.step()
stl1_loss = loss.item()

# 单任务 2 (CVR)
torch.manual_seed(0)
stl2 = STL_CTR()
opt = torch.optim.Adam(stl2.parameters(), lr=1e-3)
for ep in range(20):
    loader = DataLoader(TensorDataset(X, y2), batch_size=512, shuffle=True)
    for xb, yb in loader:
        opt.zero_grad()
        loss = bce(stl2(xb), yb)
        loss.backward(); opt.step()
stl2_loss = loss.item()

print(f"STL Task 1 final BCE: {stl1_loss:.4f}")
print(f"STL Task 2 final BCE: {stl2_loss:.4f}")
print(f"STL Average: {(stl1_loss + stl2_loss) / 2:.4f}")
```

### 5.5 梯度冲突诊断

```python
def compute_grad_conflict(model, X, y1, y2):
    """
    计算两个任务在共享参数上的梯度余弦相似度
    < 0 意味着跷跷板
    """
    bce = nn.BCEWithLogitsLoss()
    # 任务 1 的梯度
    model.zero_grad()
    pred1, pred2 = model(X)
    loss1 = bce(pred1, y1)
    loss1.backward(retain_graph=True)
    g1 = torch.cat([p.grad.flatten() for p in model.parameters() if p.grad is not None])
    model.zero_grad()

    # 任务 2 的梯度
    pred1, pred2 = model(X)
    loss2 = bce(pred2, y2)
    loss2.backward(retain_graph=True)
    g2 = torch.cat([p.grad.flatten() for p in model.parameters() if p.grad is not None])
    model.zero_grad()

    # 余弦相似度
    cos = F.cosine_similarity(g1.unsqueeze(0), g2.unsqueeze(0)).item()
    return cos

# 训练一段时间后诊断
sb_trained = SharedBottom(50, 128, 2)
hist = train_mtl(sb_trained, X, y1, y2, epochs=5)
cos_sb = compute_grad_conflict(sb_trained, X, y1, y2)

mmoe_trained = MMoE(50, 64, 4, 2)
hist = train_mtl(mmoe_trained, X, y1, y2, epochs=5)
cos_mmoe = compute_grad_conflict(mmoe_trained, X, y1, y2)

print(f"\n梯度余弦相似度 (训练 5 epoch 后):")
print(f"  Shared-Bottom: {cos_sb:.4f}  (负值 = 跷跷板)")
print(f"  MMoE:          {cos_mmoe:.4f}")
```

### 5.6 PCGrad 实现(简化版)

```python
def pcgrad_step(model, losses, optimizer):
    """
    PCGrad: 对每对冲突梯度做投影
    losses: [loss_task1, loss_task2]
    """
    # 1) 收集所有梯度
    grads = []
    params = [p for p in model.parameters() if p.requires_grad]
    for loss in losses:
        grads.append(torch.autograd.grad(
            loss, params, retain_graph=True, create_graph=False
        ))

    # 2) 两两投影
    n = len(grads)
    projected = [list(g) for g in grads]
    for i in range(n):
        for j in range(n):
            if i == j: continue
            # 计算点积
            dot = sum((pgi * pgj).sum() for pgi, pgj in zip(projected[i], grads[j]))
            norm_j_sq = sum((pgj ** 2).sum() for pgj in grads[j])
            # 冲突则投影
            if dot < 0 and norm_j_sq > 0:
                coeff = dot / norm_j_sq
                for k in range(len(projected[i])):
                    projected[i][k] = projected[i][k] - coeff * grads[j][k]

    # 3) 应用平均梯度
    for k, p in enumerate(params):
        p.grad = sum(proj[k] for proj in projected) / n
    optimizer.step()
```

### 5.8 跷跷板现象可视化 toy 代码

下面是一个**极简**的 toy 实验,用 2D 可视化让你"亲眼"看到跷跷板。两个任务的"理想梯度方向"是反的,优化器在共享参数上"左右互搏"。

```python
"""
跷跷板可视化: 2D 共享参数空间, 两个任务梯度冲突
"""
import numpy as np
import matplotlib.pyplot as plt

# 1) 设置两个任务的"目标函数"
# 任务 1 最小值在 (-2, -2), 任务 2 最小值在 (+2, +2)
# 这模拟两个"目标相反"的任务
def loss_task1(theta):
    """任务 1 损失: 最小值在 θ = (-2, -2)"""
    return 0.5 * ((theta[0] + 2) ** 2 + (theta[1] + 2) ** 2)

def loss_task2(theta):
    """任务 2 损失: 最小值在 θ = (+2, +2)"""
    return 0.5 * ((theta[0] - 2) ** 2 + (theta[1] - 2) ** 2)

# 2) 梯度
def grad_task1(theta):
    return np.array([theta[0] + 2, theta[1] + 2])

def grad_task2(theta):
    return np.array([theta[0] - 2, theta[1] - 2])

# 3) 训练对比: 朴素求和 vs PCGrad
def train_naive(theta_init, lr=0.1, n_steps=30):
    """朴素多任务: 直接用合梯度"""
    theta = theta_init.copy()
    path = [theta.copy()]
    for _ in range(n_steps):
        g = grad_task1(theta) + grad_task2(theta)  # 合梯度
        theta = theta - lr * g
        path.append(theta.copy())
    return np.array(path)

def train_pcgrad(theta_init, lr=0.1, n_steps=30):
    """PCGrad: 投影掉冲突分量"""
    theta = theta_init.copy()
    path = [theta.copy()]
    for _ in range(n_steps):
        g1 = grad_task1(theta)
        g2 = grad_task2(theta)
        # 如果冲突, 投影 g1 到 g2 的法平面
        if np.dot(g1, g2) < 0:
            g1 = g1 - (np.dot(g1, g2) / (np.dot(g2, g2) + 1e-8)) * g2
        if np.dot(g2, g1) < 0:
            g2 = g2 - (np.dot(g2, g1) / (np.dot(g1, g1) + 1e-8)) * g1
        # 取平均
        g = (g1 + g2) / 2
        theta = theta - lr * g
        path.append(theta.copy())
    return np.array(path)

# 4) 画图
fig, axes = plt.subplots(1, 2, figsize=(14, 6))
theta_init = np.array([0.0, 0.0])

# 损失等高线
for ax_idx, (trainer, title) in enumerate([
    (train_naive, 'Naive: 直接求和 (跷跷板)'),
    (train_pcgrad, 'PCGrad: 投影冲突 (缓解)')
]):
    ax = axes[ax_idx]
    # 画等高线
    theta_range = np.linspace(-4, 4, 100)
    T1, T2 = np.meshgrid(theta_range, theta_range)
    L1 = loss_task1([T1, T2])
    L2 = loss_task2([T1, T2])
    L_total = L1 + L2
    ax.contour(T1, T2, L_total, levels=15, alpha=0.4, cmap='viridis')

    # 任务 1 最小值 (红点), 任务 2 最小值 (蓝点)
    ax.plot(-2, -2, 'r*', markersize=20, label='Task 1 minimum')
    ax.plot(+2, +2, 'b*', markersize=20, label='Task 2 minimum')
    # 总 loss 最小值 (绿点, 在 (0, 0))
    ax.plot(0, 0, 'g*', markersize=15, label='Total loss minimum (compromise)')

    # 训练轨迹
    path = trainer(theta_init)
    ax.plot(path[:, 0], path[:, 1], 'k.-', markersize=4, linewidth=1, label='Path')
    ax.plot(path[0, 0], path[0, 1], 'ko', markersize=10, label='Start')
    ax.plot(path[-1, 0], path[-1, 1], 'ks', markersize=10, label='End')

    ax.set_xlim(-4, 4); ax.set_ylim(-4, 4)
    ax.set_xlabel(r'$\theta_1$'); ax.set_ylabel(r'$\theta_2$')
    ax.set_title(f'{title}\nEnd: {path[-1]}')
    ax.legend(loc='upper left', fontsize=8)
    ax.grid(True, alpha=0.3)

plt.tight_layout()
plt.savefig('/tmp/seesaw_2d_toy.png', dpi=100, bbox_inches='tight')
print("图已保存: /tmp/seesaw_2d_toy.png")
```

**可视化解读**:
- 左图(朴素求和):优化器在 (0, 0) 的"折中点"附近**震荡**,永远到不了任何一方的最优点
- 右图(PCGrad):优化器直接"绕过冲突",选一条不会让两个任务都变差的方向
- 这就是跷跷板的**几何本质**:**两个最优解在参数空间里是"反方向"的,朴素优化被困在中间**

### 5.9 完整的 PLE 实现(支持多层 + 共享-任务门控)

```python
class PLELayer(nn.Module):
    """
    PLE 单层: 包含 共享专家 + 任务专属专家 + 任务门控
    这是腾讯 RecSys 2020 论文 Figure 2 的完整实现
    """
    def __init__(self, in_dim, hidden_dim,
                 n_shared=2, n_task_specific=2, n_tasks=2):
        super().__init__()
        self.n_shared = n_shared
        self.n_task = n_task_specific
        self.n_tasks = n_tasks
        self.total_per_task = n_shared + n_task_specific  # 每个任务看的专家数
        # 共享专家
        self.shared_experts = nn.ModuleList([
            Expert(in_dim, hidden_dim) for _ in range(n_shared)
        ])
        # 任务专属专家(每个任务独立)
        self.task_experts = nn.ModuleList([
            nn.ModuleList([
                Expert(in_dim, hidden_dim) for _ in range(n_task_specific)
            ]) for _ in range(n_tasks)
        ])
        # 任务专属门控
        # PLE 论文里: 门控输入是上一层所有专家输出拼接后的均值
        self.gates = nn.ModuleList([
            nn.Linear(hidden_dim, self.total_per_task)
            for _ in range(n_tasks)
        ])
        # 输出维度
        self.out_dim = hidden_dim

    def forward(self, x, prev_h=None):
        """
        x: [B, in_dim] 原始输入, 用于共享专家
        prev_h: [B, hidden_dim] 上一层输出(可空), 用于任务专属专家
        """
        # 1) 共享专家
        shared_outs = torch.stack(
            [e(x) for e in self.shared_experts], dim=1
        )  # [B, n_shared, D]

        # 2) 任务专属专家(输入是 prev_h 而不是 x, 这是 PLE 的关键)
        h_in = prev_h if prev_h is not None else x
        outputs = []
        for k in range(self.n_tasks):
            task_outs = torch.stack(
                [e(h_in) for e in self.task_experts[k]], dim=1
            )  # [B, n_task, D]
            # 拼接所有专家
            all_outs = torch.cat([shared_outs, task_outs], dim=1)
            # [B, n_shared + n_task, D]
            # 门控(输入: 专家输出的均值, 简化版)
            gate_in = all_outs.mean(dim=1)  # [B, D]
            alpha = F.softmax(self.gates[k](gate_in), dim=-1)  # [B, total]
            # 加权求和
            h_k = torch.einsum('bn,bnd->bd', alpha, all_outs)
            outputs.append(h_k)
        return outputs  # list of [B, D], length n_tasks


class PLE(nn.Module):
    """
    多层 PLE: Progressive Layered Extraction
    论文: Tang et al. 2020, RecSys
    """
    def __init__(self, in_dim, hidden_dim=64,
                 n_shared=2, n_task_specific=2, n_tasks=2,
                 n_layers=1):
        super().__init__()
        self.n_tasks = n_tasks
        self.n_layers = n_layers
        # 多层 PLE: 每一层处理前一层的输出
        self.ple_layers = nn.ModuleList()
        for layer_idx in range(n_layers):
            # 第一层: 输入是原始 in_dim
            # 后续层: 输入是 hidden_dim
            layer_in_dim = in_dim if layer_idx == 0 else hidden_dim
            self.ple_layers.append(
                PLELayer(layer_in_dim, hidden_dim,
                         n_shared, n_task_specific, n_tasks)
            )
        # 任务塔
        self.towers = nn.ModuleList([
            Tower(hidden_dim, out_dim=1) for _ in range(n_tasks)
        ])

    def forward(self, x):
        # 第一层
        h_list = self.ple_layers[0](x, prev_h=None)
        # 后续层: 每层的输入是上一层所有任务的输出
        for layer_idx in range(1, self.n_layers):
            # 把上一层所有任务的输出取平均, 作为下一层的"prev_h"
            prev_h = torch.stack(h_list, dim=1).mean(dim=1)  # [B, D]
            h_list = self.ple_layers[layer_idx](x, prev_h=prev_h)
        # 任务塔
        outputs = [self.towers[k](h_list[k]) for k in range(self.n_tasks)]
        return outputs

    def get_task_representations(self, x):
        """辅助方法: 拿任务表示(用于 §2.6 任务相关性诊断)"""
        h_list = self.ple_layers[0](x, prev_h=None)
        for layer_idx in range(1, self.n_layers):
            prev_h = torch.stack(h_list, dim=1).mean(dim=1)
            h_list = self.ple_layers[layer_idx](x, prev_h=prev_h)
        return h_list  # list of [B, D]
```

**PLE 关键设计点**:
1. **任务专属专家的输入是 prev_h**,不是 x——这样任务专属专家能"在前一层输出基础上"再分化
2. **门控的输入是专家输出的均值**——避免门控依赖原始 x,让门控更"自适应"
3. **多层 PLE**(n_layers ≥ 2)让"共享-独占"在每层都做一次,更精细但更贵

- 但 CTR 和 GMV 弱相关(0.41),**跷跷板轻度存在**

**美团做法**:
1. **任务分组**:把 4 个任务分成 2 组,组内用 Shared-Bottom,组间用 MMoE
2. 架构示意:

```text
输入 x
  ↓
[共享底层 W_s] → h
  ↓
  ├── 任务组 A (CTR + 进店) → Shared-Bottom 子层 → 塔 A1, A2
  └── 任务组 B (收藏 + GMV) → Shared-Bottom 子层 → 塔 B1, B2
```

**结果**:综合业务指标 +1.6%,训练时间 1.4× baseline(比纯 PLE 便宜)。

**反思**:任务分组是 PLE 的"轻量版"——不需要显式分离专家,只需要把"强相关的任务"放在一个共享子层。

### 6.7 推荐多目标完整案例:CTR + 时长 + 点赞

**任务定义**:
- 任务 1:CTR(用户点不点,二分类)
- 任务 2:完播时长(用户看了多少秒,回归)
- 任务 3:点赞(用户点不点赞,二分类)

**数据生成**(模拟):

```python
def make_recommendation_data(n=50000, in_dim=80, seed=42):
    """
    模拟推荐三任务:
    - 任务 1 (CTR): 依赖用户兴趣特征
    - 任务 2 (完播): 依赖内容质量特征
    - 任务 3 (点赞): 依赖情感极性特征

    三个任务的"理想特征" 部分重叠(共享区),
    部分独立(独占区)
    """
    np.random.seed(seed)
    X = np.random.randn(n, in_dim).astype(np.float32)

    # 用户兴趣维度: [0:25]
    user_interest = X[:, :25]
    # 内容质量维度: [20:50]
    content_quality = X[:, 20:50]
    # 情感极性维度: [50:75]
    sentiment = X[:, 50:75]
    # 噪声维度: [75:80]

    # 任务 1 (CTR): 主要看用户兴趣
    w1 = np.random.randn(25).astype(np.float32) * 0.5
    logits1 = user_interest @ w1 + 0.1 * np.random.randn(n)
    y1 = (1 / (1 + np.exp(-logits1)) > 0.5).astype(np.float32)

    # 任务 2 (完播时长): 主要看内容质量
    w2 = np.random.randn(30).astype(np.float32) * 0.5
    watch_time = np.maximum(0, content_quality @ w2 + 0.5 * np.random.randn(n))
    y2 = watch_time.astype(np.float32)  # 回归

    # 任务 3 (点赞): 情感 + 部分 CTR
    w3 = np.random.randn(25).astype(np.float32) * 0.5
    logits3 = sentiment @ w3 + 0.3 * user_interest @ w1  # 点赞略依赖 CTR
    y3 = (1 / (1 + np.exp(-logits3)) > 0.5).astype(np.float32)

    return torch.tensor(X), torch.tensor(y1).unsqueeze(1), \
           torch.tensor(y2).unsqueeze(1), torch.tensor(y3).unsqueeze(1)

# 训练
X, y1, y2, y3 = make_recommendation_data()
mmoe = MMoE(in_dim=80, hidden_dim=64, n_experts=6, n_tasks=3)

# 多任务训练循环
opt = torch.optim.Adam(mmoe.parameters(), lr=1e-3)
for epoch in range(30):
    loader = DataLoader(TensorDataset(X, y1, y2, y3),
                        batch_size=512, shuffle=True)
    for xb, y1b, y2b, y3b in loader:
        opt.zero_grad()
        p1, p2, p3 = mmoe(xb)
        loss1 = F.binary_cross_entropy_with_logits(p1, y1b)
        loss2 = F.mse_loss(p2, y2b)  # 回归
        loss3 = F.binary_cross_entropy_with_logits(p3, y3b)
        loss = loss1 + loss2 + loss3
        loss.backward()
        opt.step()

# 诊断
diagnose_mtl_model(mmoe, X, [y1, y2, y3], "MMoE-6x3")
```

**预期结果**:
- 任务 1 (CTR) 和 任务 3 (点赞) 相关性较高(0.4+),跷跷板轻
- 任务 2 (完播) 和 任务 1/3 相关性弱,跷跷板主要在这两个任务之间
- MMoE-6 表现应该明显优于 Shared-Bottom

## 7. 数学洞察:Pareto 前沿与共享-独占权衡

### 7.1 跷跷板的本质:加权标量化的失效

**多任务学习**把 $K$ 个目标"压"成一个标量:

$$
\mathcal{L}_{\text{MTL}} = \sum_{k=1}^{K} w_k \mathcal{L}_k
$$

这个做法叫**加权标量化**(Weighted Scalarization)。在**凸情形**下,任意 Pareto 最优点都能被某个权重组合得到(Geoffrion 1968);但在**非凸情形**(DNN 几乎都非凸),加权标量化**可能错过一些 Pareto 点**。

**形式化**(凸 + 加权标量化):
$$
\forall \theta^* \in \text{Pareto Front}, \quad \exists w_1, \ldots, w_K > 0, \quad \theta^* = \arg\min_\theta \sum_k w_k \mathcal{L}_k
$$

**非凸情形**:上述不一定成立。存在 Pareto 点,任何权重组合都到不了。

```text
损失空间中的 Pareto 前沿
    ▲ Loss_2
    │   ╲
    │     ╲  ← Pareto Front(凸情形下,加权和能取遍)
    │       ╲
    │         ╲     ╱ ← 实际能取到的(加权标量化)
    │           ╲ ╱
    │            ★
    │           ╱ ╲
    └──────────────────→ Loss_1
```

**工业推论**:工业上的"调权重"本质是在 Pareto 前沿上"试不同位置"——如果不同权重训出的模型差异小,说明任务强相关,跷跷板轻;如果差异巨大,说明任务负相关,跷跷板重。

### 7.2 共享-独占权衡(Shared-Exclusive Trade-off)

**定理(非形式化)**:多任务模型的表示 $h$ 可拆成"共享部分" $h_s$ 和"独占部分" $h_k$,即:

$$
h = h_s \oplus h_1^{\text{excl}} \oplus h_2^{\text{excl}} \oplus \cdots \oplus h_K^{\text{excl}}
$$

其中 $h_s$ 包含所有任务共享的信息,$h_k^{\text{excl}}$ 包含任务 $k$ 独有的信息。

- 共享越多 → 跨任务迁移好,但每个任务的"个性"被稀释
- 独占越多 → 每个任务学得专精,但跨任务无法借力

**Shared-Bottom**:极端共享,$h_k^{\text{excl}} = \emptyset$。
**Independent**:极端独占,$h_s = \emptyset$。
**MMoE / PLE**:中间地带,门控控制每个任务的"共享-独占比例"。

### 7.3 门控的稀疏性 = 自动选择

MMoE 的门控 $\alpha_k$ 通过 softmax 鼓励"少数专家"被选中(softmax 不是天然稀疏,但训练中会学到"分布集中")。

```text
训练前: α_k 接近均匀(1/n 每个专家)
        ↓
训练中: α_k 逐渐集中(几个专家占 80%+)
        ↓
训练后: α_k 极度集中(1-2 个专家占 90%+)
```

**好处**:
- 门控学会"哪些专家对任务 $k$ 有用",**自然实现"任务专属"**。
- 当任务 A 和 B 冲突时,门控可以让 $\alpha_{A,i}$ 和 $\alpha_{B,i}$ 差别很大,**避免直接冲突**。

**坏处**:
- 训练初期门控接近均匀,此时和 Shared-Bottom 差不多。
- 训练后期门控集中,**专家利用不均**(部分专家被"饿死")。

### 7.4 信息论视角

设共享表示 $h$,任务 $T_1, T_2$。$h$ 关于两个任务的互信息(参考 [[../../../方向教程/rec教程/第04章-多任务学习|rec 第 4 章 §1.3.2]]):

$$
I(h; T_1, T_2) \ge I(h; T_1) + I(h; T_2) - I(T_1; T_2)
$$

**当 $I(T_1; T_2) \to 0$**(任务独立),共享表示需要**双倍容量**才能等价单任务。

**当 $I(T_1; T_2) \to$ 大**(任务强相关),共享表示很划算。

**MMoE 的妙处**:**每个任务的 $h_k$ 不是"完全共享",而是"软共享"**——$h_k$ 的容量可以分给共享信息和独占信息,避开了"二选一"的极端。

### 7.5 工程师的"反直觉清单"

最后,把这一章的"反直觉"总结一下:

| 常见误解 | 真相 |
| :--- | :--- |
| 多任务 = 一定比单任务好 | **10% 反而更差** |
| 共享层越深越好 | 4 层后开始掉,容量过剩 |
| 专家数越多越好 | 8-16 是 sweet spot,32+ 反而差 |
| 加参数能解决跷跷板 | 4× 参数量综合分 -0.3% |
| MMoE 一定优于 PLE | 任务数 < 4 时,MMoE 足够 |
| 共享底层学到的"通用" | 是"折中"而非"通用" |
| 任务越多越好 | 任务 ≥ 3 跷跷板明显 |
| AUC 涨 = 业务涨 | 离线-在线不一致,常 30% 反转 |

### 7.6 Pareto 前沿的数学刻画

多任务学习的最优解本质上是**多目标优化**问题,不是单目标最小化。设 $K$ 个任务的损失 $\mathcal{L}_1, \mathcal{L}_2, \ldots, \mathcal{L}_K$,Pareto 最优的形式定义:

**定义(Pareto 支配)**:解 $\theta$ **支配**解 $\theta'$(记 $\theta \prec \theta'$),如果
$$
\forall k: \mathcal{L}_k(\theta) \le \mathcal{L}_k(\theta'), \quad \exists k: \mathcal{L}_k(\theta) < \mathcal{L}_k(\theta')
$$

**定义(Pareto 前沿)**:所有不被任何解支配的解的集合。
$$
\mathcal{P} = \{\theta : \nexists \theta', \theta' \prec \theta\}
$$

```text
Pareto 前沿的几何示意 (2 任务)
─────────────────────────────────────────
  Loss_2
    ▲
    │  ╲
    │    ╲  ← Pareto Front
    │      ╲
    │   A ★ ╲
    │        ╲    B ★ (A, B 都是 Pareto 最优)
    │          ╲ ╱
    │           ★  ← C(被 A 和 B 支配,不是 Pareto)
    │           │
    └───────────┴──────→ Loss_1
```

**定理(凸情形下的等价)**:Geoffrion (1968) 证明:在**凸**优化里,任意 Pareto 最优点都对应某个权重组合 $w > 0$,使得
$$
\theta^* = \arg\min_\theta \sum_{k=1}^{K} w_k \mathcal{L}_k(\theta)
$$

这就是"加权标量化能取遍 Pareto 前沿"的根源。

**但 DNN 是非凸的**——DNN 的损失景观是**高度非凸**的,存在大量局部 Pareto 点。这导致:
- 加权标量化**只能取到一部分** Pareto 前沿
- 大量"边缘" Pareto 点(对某些权重不稳)被错过
- 工业上"调权重找不到好模型"是常态——**不是你调得不好,是非凸的损失景观根本不允许那种组合存在**

**MMoE 的几何意义**:把加权标量化的"求和"换成"软组合",**扩展了可达 Pareto 区域**。直观上,MMoE 在参数空间里"打开"了多个区域,门控决定走哪个区域,合起来覆盖更大的 Pareto 区域。

### 7.7 共享-独占权衡的定量分析

设多任务模型的隐藏表示 $h \in \mathbb{R}^D$。**信息瓶颈视角**:
$$
h^* = \arg\min_h I(h; X) - \beta \sum_{k=1}^{K} I(h; T_k)
$$
$h^*$ 是"最小冗余 + 任务信息最大"的表示。

**关键拆解**:$h$ 可拆为三个分量:
$$
h = h_s \oplus h_e \oplus h_n
$$

| 分量 | 含义 | 占比 (Shared-Bottom) | 占比 (MMoE) | 占比 (PLE) |
| :--- | :--- | :--- | :--- | :--- |
| $h_s$ (shared) | 任务共享信息 | 100% | 30-50% | 40-60% |
| $h_e$ (exclusive) | 任务专属信息 | 0% | 40-60% | 30-50% |
| $h_n$ (noise) | 无用噪声 | 0% | 10-20% | 5-10% |

**Shared-Bottom**:极端共享,$h_e = 0$。每个任务都被迫学"通用表示",跷跷板来源于此。

**MMoE**:门控让每个任务的 $h_e$ 通过"专家选择"被分离。**注意**:门控不是真的"独占"——它通过 softmax 让某些专家"对任务 A 重要,对任务 B 不重要",实现**软独占**。

**PLE**:显式分离 $h_s$ 和 $h_e$,任务 A 的 $h_e^{(A)}$ 和任务 B 的 $h_e^{(B)}$ **完全不重叠**。**真正独占**。

**定量结论**(经验值):
- 任务强相关:最优 $h_s / h_e \approx 80\% / 20\%$,Shared-Bottom 几乎够用
- 任务弱相关:最优 $h_s / h_e \approx 50\% / 50\%$,MMoE 最佳
- 任务负相关:最优 $h_s / h_e \approx 30\% / 70\%$,必须 PLE 或更强解耦

```text
任务相关度 vs 共享-独占比例
──────────────────────────────────────────
任务相关度
  1.0 ┤██████████████████████ (全共享, STL 等价)
      │
  0.7 ┤━━━━━━━━━━━━━━━━━━ (Shared-Bottom 80%/20%)
      │
  0.4 ┤━━━━━━━━━━ (MMoE 50%/50%)
      │
  0.1 ┤━━━━ (PLE 30%/70%)
      │
 -0.3 ┤ (PLE 20%/80% 或更多独占)
      └─────────────────────→
       0%        50%        100%
       (h_s 占比, h_e = 1 - h_s)
```

**关键操作含义**:当你的任务相关度(余弦相似度)是 0.4 时,MMoE 是最划算的——太多共享浪费容量,太多独占浪费参数。**用任务相关性矩阵来指导架构选型**,不是凭感觉。

## 8. 面试标准表达:L7 模板 + 追问

### 8.1 标准问题:"MMoE 为什么能缓解跷跷板?"

**L7 模板答案**(2 分钟,逻辑清晰,带公式):

> **答**:MMoE 缓解跷跷板的核心是用**多个专家 + 任务门控**替代单一共享底层。
>
> **从数学上看**,Shared-Bottom 的共享参数 $W_s$ 同时被 $K$ 个任务的损失通过反向传播更新。如果两个任务的梯度方向冲突($\langle \nabla_{W_s} \mathcal{L}_1, \nabla_{W_s} \mathcal{L}_2 \rangle < 0$),优化器在共享参数上的更新是"左右互搏",最终停在一个谁都不优的折中点。
>
> **MMoE 的解法**:把单一共享层拆成 $n$ 个独立专家 $\{f_1, \ldots, f_n\}$,再给每个任务配一个门控 $g_k$ 学"软选择":
>
> $$h_k(x) = \sum_{i=1}^{n} \alpha_{k,i}(x) \cdot f_i(x), \quad \alpha_{k,i} = \text{softmax}(g_k(x))_i$$
>
> **为什么能缓解**:门控的梯度只受自己任务的损失驱动,所以门控学到的分布"天然"对自己任务最优。当任务 A 和 B 冲突时,门控可以学到"任务 A 多用专家 1,3;任务 B 多用专家 2,4",**避免在一个共享表示里直接冲突**。
>
> **从信息论视角**(参考 rec 第 4 章),MMoE 的每个 $h_k$ 是"共享 + 独占"的软组合,容量可以灵活分配。任务负相关时,门控让 $\alpha$ 分布差异大,实现"软解耦";任务正相关时,门控让 $\alpha$ 分布接近,实现"硬共享"。
>
> **经验数据**:Google YouTube 实验中,MMoE-8 比 Shared-Bottom 综合分 +0.71%,接近单任务独立训练。

### 8.2 追问 1:"那 PLE 是不是永远比 MMoE 好?"

**标准答**:

> **不是**。PLE 显式分离共享专家和任务专属专家,**当任务数 ≥ 4 或任务间负相关时 PLE 优势明显**;但当任务数 < 4 且任务强相关时,PLE 的额外参数反而可能过拟合。
>
> **经验法则**:
> - 任务数 ≤ 3,强相关 → MMoE
> - 任务数 ≥ 4,负相关 → PLE
> - 不确定 → 先 MMoE,看任务 AUC 是否都到单任务基线,到了就停

### 8.3 追问 2:"如何诊断当前模型是否在跷跷板?"

**标准答**:

> 三个层次的诊断:
>
> 1. **业务指标层**:监控每个任务的离线 AUC 和线上业务指标。如果任务 A 的 AUC 涨、任务 B 的 AUC 跌,看跌的幅度能否被业务接受。
>
> 2. **梯度冲突层**:计算任务两两之间的梯度余弦相似度。公式:
>    $$\text{cos}(\nabla_{W_s} \mathcal{L}_i, \nabla_{W_s} \mathcal{L}_j) = \frac{\langle g_i, g_j \rangle}{\|g_i\| \|g_j\|}$$
>    余弦 < 0 说明严重冲突,需要 PCGrad 或 PLE。
>
> 3. **门控分布层**:MMoE 训练后,看每个任务的门控权重分布。如果两个任务的门控分布 KL 散度 < 0.1,说明门控没学到分化,MMoE 退化成 Shared-Bottom。

### 8.4 追问 3:"那 Shared-Bottom 完全不能用吗?"

**标准答**:

> **不是**。Shared-Bottom 简单稳定,适合:
> - 任务数 ≤ 2 且强相关(CTR + CVR)
> - 数据量少(独立训练每个任务都训不动,共享表示能借力)
> - 工程资源紧张(MMoE 训练慢 50%)
>
> **经验**:80% 的工业 MTL 场景,MMoE 都能 hold 住;真正需要 PLE / PCGrad 的不到 20%。

### 8.5 追问 4:"MMoE 怎么调参?专家数选多少?"

**标准答**:

> **专家数**:4-8 起步,最多 16。Google 论文显示 8 是 sweet spot,32+ 反而差。
>
> **门控维度**:一般和专家数相同,Softmax 输出。
>
> **专家维度**:和原 Shared-Bottom 隐藏层维度一致,或略小(因为有多个专家分摊)。
>
> **学习率**:略小于单任务(0.5-1×),专家多时梯度方差大。
>
> **任务权重 $w_k$**:先用 1.0 等权,看综合分;再根据业务调(CTR 涨太多就降权)。

### 8.6 追问 5:"如果业务 KPI 频繁变,怎么避免重复训练?"

**标准答**:

> 两个方法:
>
> 1. **多组权重模型** + 在线切换:训练时训 3-5 组不同权重的模型,业务 KPI 变时切换
> 2. **NSGA-II / MOEA/D**:用进化算法在 Pareto 前沿上撒点,一次产出多组"不互相支配"的候选
>
> 工业上第二种更系统,但训练成本高(每次跑需要 $P$ 个模型)。

### 8.7 追问 6:"多任务一定比单任务好吗?"

**标准答**(这是反直觉问题,也是踩坑高频):

> **不是**。多任务学习的"代价"是**容量分摊**——共享参数被多个任务瓜分,每个任务分到的容量比单任务少。**当任务负相关时,容量分摊反而有害**。
>
> 经验数据(Google 2018 + 阿里 2019 合并):
> - 任务强相关(余弦 > 0.5):多任务**几乎一定**比单任务好(+1-3%)
> - 任务中等相关(0-0.5):多任务**有条件**比单任务好,取决于架构
> - 任务负相关(< 0):多任务**经常**比单任务差,除非用 MMoE + 梯度手术
>
> **判断方法**:先训 K 个单任务模型,看每个任务的"基线 AUC",再训多任务模型,如果多任务的每个任务 AUC < 单任务基线,**跷跷板确认**,需要换架构。

### 8.8 追问 7:"MMoE 专家越多越好吗?"

**标准答**:

> **不是**。专家数和跷跷板缓解不是单调关系。Google 论文表 4 的数据:
>
> | 专家数 | 综合分 | 训练时间 |
| :--- | :--- | :--- |
> | 1 (=Shared-Bottom) | 0.7188 | 1.0× |
> | 4 | 0.7245 | 1.5× |
> | 8 | 0.7259 | 2.6× |
> | 16 | 0.7271 | 4.3× |
> | 32 | 0.7266 | 7.8× |
>
> **规律**:
> - 1 → 8:显著提升(+0.7%)
> - 8 → 16:边际提升(+0.12%),但训练时间 ×1.6
> - 16 → 32:反而掉(-0.05%),开始过拟合
>
> **原因**:专家太多时,门控无法"区分"该用哪些专家,softmax 输出变得**接近均匀**,MMoE 退化成"专家均匀混合",容量浪费。**经验 sweet spot = 4-8 个**,和任务数大致相当(2-3 倍以内)。
>
> **进阶**:**专家数 = sqrt(任务数 × 数据量)** 是一个常用经验公式,但更多依赖实验调优。

### 8.9 追问 8:"跨任务梯度冲突怎么量化?"

**标准答**:

> 三个层次的量化,工业上**至少要算前两个**:
>
> 1. **梯度余弦相似度**(最直接):
>    $$\text{cos}(\nabla_{W_s} \mathcal{L}_i, \nabla_{W_s} \mathcal{L}_j) = \frac{\langle g_i, g_j \rangle}{\|g_i\| \|g_j\|}$$
>    范围 [-1, 1]。< 0 意味着冲突。
>
> 2. **任务 AUC 相关性**(业务侧):
>    $$\rho_{\text{AUC}} = \text{Pearson}(\text{AUC}_i^{(t)}, \text{AUC}_j^{(t)})$$
>    其中 $\text{AUC}_k^{(t)}$ 是任务 $k$ 在第 $t$ 步的 AUC。**正相关 = 同步涨落(可能跷跷板)**,**负相关 = 反向跷跷板(更危险)**。
>
> 3. **门控 KL 散度**(MMoE 专属):
>    $$\text{KL}(\alpha_i \| \alpha_j) = \sum_m \alpha_{i,m} \log \frac{\alpha_{i,m}}{\alpha_{j,m}}$$
>    < 0.1 意味着门控没分化,MMoE 退化成 Shared-Bottom。
>
> **工业实践**:训练时每 100 步采样一次,画出"梯度余弦时间曲线",**余弦从正变负的时刻**就是跷跷板的"启动时刻"。

搜推广岗位面试中,关于多任务学习的**最常见错误回答**,HR/技术 leader 听到就扣分:

| 误区 | 错在哪 | 正确说法 |
| :--- | :--- | :--- |
| "多任务就是 Shared-Bottom" | 把架构和范式混了 | MTL 是范式,Shared-Bottom / MMoE / PLE 是具体架构 |
| "MMoE 让所有任务共享同一个专家" | 误解门控的作用 | MMoE 让**每个任务**软选择**自己偏好的专家组合** |
| "跷跷板是数据问题,不是架构问题" | 把现象当根因 | 跷跷板根因是**梯度冲突 + 容量瓶颈**,架构和算法都能缓解 |
| "PLE 一定比 MMoE 好" | 不知道 PLE 的成本 | PLE 训练 2-3×,任务 < 4 时不一定划算 |
| "梯度冲突加个 PCGrad 就好" | 忽视计算成本 | PCGrad 是 O(K²),K 大时不可行,需要更高效算法 |
| "AUC 涨 = 业务涨" | 离线-在线鸿沟 | 离线指标只反映排序质量,业务还受 EE / 时延 / 多样性影响 |

| "梯度 = 0 就不冲突" | 误解冲突定义 | 梯度方向相反才算冲突,点积 < 0 不是"< 0" |

## 9. 延伸思考:PLE / ESMM / 工业多目标优化

### 9.1 PLE 的工程细节

**单层 PLE**(PLE-1) vs **多层 PLE**(PLE-N):

```text
PLE-1: 专家 → 门控 → 塔
PLE-2: 专家 → 门控 → 专家 → 门控 → 塔
       ↑                              ↑
       第一层专家                      第二层专家
       (共享 + 专属)                    (在第一层输出上再分化)
```

PLE-N 把"专家-门控"堆叠 N 次,**每层都做一次"共享-独占"分配**。优点是更精细,缺点是参数膨胀 + 训练慢。

**经验**:PLE-1 够用,PLE-2 边际收益小,PLE-3 几乎一定过拟合。

### 9.2 ESMM 解决"样本选择偏差"

CVR 建模有个特殊痛点:**训练数据是"点击且转化"的样本,推理时要对"全部曝光"打分**——分布不一致。

ESMM(Entire Space Multi-task Model, Ma et al. 2018)的解法:不直接建模 CVR,而是建模"曝光 → 点击 → 转化"的**完整链路**。

$$
P(\text{click} \cap \text{conv} \mid \text{imp}) = \underbrace{P(\text{click} \mid \text{imp})}_{\text{CTR 塔}} \cdot \underbrace{P(\text{conv} \mid \text{click}, \text{imp})}_{\text{CVR 塔}}
$$

**为什么解决 SSB**:CVR 塔在**整个曝光空间**接受梯度(包括没点击的样本,这些样本的 CTCVR 标签是 0)。这样 CVR 塔学到的表示"覆盖全部曝光分布",而不是只在"被点击"的子集。

**与 MMoE 的关系**:ESMM 解决"分布不一致",MMoE 解决"梯度冲突",两者不互斥——**MMoE-ESMM 混合架构**在阿里、京东都很常见。

### 9.3 AITM(Adaptive Information Transfer,腾讯 2022)

**问题**:MMoE / PLE 假设"共享部分对所有任务都有用",但实际中,共享对任务 A 很有用,对任务 B 几乎没用——这种"不对等"会让任务 B 的门控浪费容量。

**AITM**(Adaptive Information Transfer Multi-task)的解法:**显式建模"任务 A 的信息传到任务 B"**。

```text
输入 x
  ↓
[任务 A 的塔] → h_A → 任务 A 输出 ŷ_A
  ↓
[信息门控: 决定 h_A 的多少传给 B]
  ↓
[任务 B 的塔(接受 h_A + x)] → h_B → 任务 B 输出 ŷ_B
```

**关键**:**信息门控**是"任务 A → 任务 B"的"单行道",而不是"双向共享"。**当 A 对 B 没用时,门控接近 0,B 完全独立**;当 A 对 B 很有用时,门控接近 1,B 直接继承 A 的表示。

### 9.4 SNR / MMoE 变体

| 变体 | 来源 | 核心差异 |
| :--- | :--- | :--- |
| SNR (Sub-Network Routing) | Ma 2019 | 专家 + 子网络,容量更灵活 |
| MMoE-Pro | Zhao 2020 | 加 LayerNorm,稳定训练 |
| PLE | Tang 2020 | 共享-显式分离 |
| ESMM | Ma 2018 | 解决 CVR 样本选择偏差 |
| AITM | 腾讯 2022 | 单向信息传递 |
| MMoE-3 / CGC | 自研 | 各种花式改进 |

**经验**:90% 场景用 MMoE 就能 hold 住,真正需要 PLE / AITM 的不到 10%。**别过度设计**。

### 9.5 工业多目标优化的完整图谱

```text
                    ┌─────────────────────────────────┐
                    │   业务多目标(CTR/CVR/时长/...)  │
                    └────────────────┬────────────────┘
                                     │
                ┌────────────────────┼────────────────────┐
                ↓                    ↓                    ↓
         架构选择              梯度平衡             评估体系
         ┌─────┐              ┌─────┐              ┌─────┐
         │MMoE │              │UW   │              │AUC  │
         │PLE  │              │GN   │              │Pareto│
         │ESMM │              │PCGr │              │业务 │
         │AITM │              │MGDA │              │A/B  │
         └─────┘              └─────┘              └─────┘
                ↓                    ↓                    ↓
         ┌─────────────────────────────────────────────────┐
         │         离线评估 + 在线 A/B test 闭环           │
         └─────────────────────────────────────────────────┘
```

**核心原则**:
1. **架构选型**:从 MMoE 起步,看效果,不够再升级
2. **梯度平衡**:UW (Uncertainty Weighting) 是简单 baseline
3. **评估体系**:三层(单任务 / 综合 / 业务),任意缺位都会误判
4. **最终标准**:永远以**在线 A/B test** 为准,至少跑 7 天

### 9.6 PLE 工业案例深度剖析:微信视频号

**任务定义**:腾讯 PLE 论文(Tang et al. 2020, RecSys)直接来自**微信视频号**的工业实践,核心任务:

| 任务 | 类型 | 业务含义 |
| :--- | :--- | :--- |
| 视频完播 | binary | 用户是否看完视频 |
| 点赞 | binary | 显式正向反馈 |
| 关注 | binary | 强意向信号 |
| 转发 | binary | 传播价值 |
| 评论 | binary | 用户参与度 |
| 负反馈 | binary | 用户不喜欢的信号(用于压制) |

**6 个任务**的复杂性在于:任务之间**部分正相关、部分负相关**——比如"完播"和"评论"正相关(用户看完且评论,深度参与),但"完播"和"负反馈"负相关(完播率高的视频不容易被负反馈)。

**架构对比**(论文表 5 简化):

| 架构 | 完播 AUC | 点赞 AUC | 关注 AUC | 综合 |
| :--- | :--- | :--- | :--- | :--- |
| Shared-Bottom | 0.7212 | 0.8123 | 0.6891 | 0.7409 |
| MMoE (4 experts) | 0.7310 | 0.8201 | 0.7012 | 0.7508 |
| MMoE (8 experts) | 0.7325 | 0.8210 | 0.7034 | 0.7523 |
| **PLE-1 (CGC)** | **0.7395** | **0.8253** | **0.7123** | **0.7590** |
| PLE-2 | 0.7401 | 0.8258 | 0.7128 | 0.7596 |

**关键发现**:
- PLE-1 比 MMoE-8 综合分 **+0.7%**,**6 任务下 PLE 优势放大**
- PLE-2 比 PLE-1 仅 +0.06%,**几乎无边际收益**
- 任务专属专家**确实**让负相关任务"解耦":完播和负反馈的余弦从 Shared-Bottom 的 -0.32 降到 PLE 的 -0.08

**工程细节**(从论文附录):
- 共享专家数 = 3,任务专属专家数 = 2(每个任务)
- 总参数量 = Shared-Bottom × 1.4(不算很大)
- 训练时间 = 1.7× baseline
- 在线 A/B 跑 7 天,**视频时长 +1.2%,点赞 +0.8%**

### 9.7 ESMM 与 SSB 问题的数学刻画

ESMM 解决的不是跷跷板,而是另一个问题:**样本选择偏差 (Sample Selection Bias, SSB)**。

**SSB 的形式化**:

CTR 任务在**全部曝光**样本上训练:
$$
\mathcal{D}_{\text{CTR}} = \{(x_i, y_i^{\text{click}}) : i \in \text{impressions}\}
$$

CVR 任务在**点击后**样本上训练:
$$
\mathcal{D}_{\text{CVR}} = \{(x_i, y_i^{\text{conv}}) : i \in \text{clicks}\}
$$

**问题**:推理时,CVR 塔要对**全部曝光**样本打分,但它只在**点击子集**上训练——**训练-推理分布不一致**。CVR 塔学到的表示"覆盖不全",对未点击样本的 CVR 预测偏置。

**ESMM 的解法**(Ma et al. 2018, SIGIR):

不直接建模 CVR,而是建模 CTCVR(曝光 → 点击 → 转化 的完整链路):

$$
P(\text{y=click} \cap \text{conv} \mid \text{imp}) = \underbrace{P(\text{click} \mid \text{imp})}_{\text{CTR 塔}} \cdot \underbrace{P(\text{conv} \mid \text{click}, \text{imp})}_{\text{CVR 塔}}
$$

**CVR 塔的损失**:在**全部曝光**样本上,以 CTCVR 为标签训练

$$
\mathcal{L}_{\text{CVR}} = -\frac{1}{N} \sum_{i=1}^{N} y_i^{\text{CTCVR}} \log \hat{p}_i^{\text{CTCVR}}
$$

其中 $\hat{p}_i^{\text{CTCVR}} = \hat{p}_i^{\text{CTR}} \cdot \hat{p}_i^{\text{CVR}}$。**关键**:未点击样本的 CTCVR 标签 = 0(没点击就不可能转化),CVR 塔在这些样本上也被迫"学习到不转化"。

**效果**:阿里妈妈公开数据,ESMM 相比直接 CVR 建模,AUC **+2.4%**(从 0.68 涨到 0.71)。

**与 MMoE 的关系**:ESMM 和 MMoE 是**正交的**——ESMM 解决 SSB,MMoE 解决跷跷板。**阿里、京东的混合架构**:

```text
输入 x
  ↓
[共享底层 / MMoE 专家]
  ↓
  ├── CTR 塔
  ├── CVR 塔 (用 ESMM 方式训练)
  └── 加购 / 收藏等(可选)
```

**工业经验**:**做 CVR 任务时,ESMM 是必上**;做其他多目标(完播/点赞等),MMoE 是首选。

### 9.8 YouTube 2019 多目标排序系统

Google 在 2019 年 RecSys 论文 *Recommending What Video to Watch Next: A Multitask Ranking System* 中公开了 YouTube 多目标排序的完整架构。

**任务设计**(6 个目标):
1. **Engagement**:用户参与度(点击 + 完播 + 点赞)
2. **Satisfaction**:用户满意度(调查问卷)
3. **Diversity**:多样性(避免信息茧房)
4. **Watch Time**:总观看时长
5. **Click-Through Rate**:点击率
6. **Subscription**:订阅转化

**架构**:**多阶段加权**——不是简单的 MMoE,而是**多模型加权**:

```text
阶段 1: 6 个独立的 MMoE 子模型
   → 任务 A: MMoE(CTR + 完播)
   → 任务 B: MMoE(满意度 + 多样性)
   → 任务 C: 单模型(订阅)
   ...

阶段 2: 加权融合
   final_score = w1 * score_A + w2 * score_B + ... + wK * score_K
```

**为什么不是单一 MMoE**:YouTube 团队发现,**6 任务单 MMoE** 的跷跷板控制不住——任务间的相关性差异太大(从 -0.4 到 +0.7),门控无法同时 handle 所有组合。**拆成 2-3 任务的小 MMoE** + **加权融合**比单一大 MMoE 效果更好。

**关键工程细节**:
- 6 个子模型独立训练,**解耦了跷跷板**(每个 MMoE 只有 2-3 任务)
- 阶段 2 的权重 $w_k$ 通过在线 A/B 调,离线 AUC 不直接对应线上指标
- 部署成本:6 个子模型的 inference 时间叠加,**是 Shared-Bottom 的 5-6 倍**

**反思**:**任务数 ≥ 5 时,工业上几乎不推荐用单一大 MMoE**。YouTube 的方案是"**多个小 MMoE + 加权融合**",阿里、腾讯的方案是"**任务分组**",本质都是"**让每个 MMoE 只面对 2-3 任务**"。

### 9.9 多任务模型的部署成本对比

工程师容易忽略:**多任务模型的部署 / 推理成本**比单任务高很多。下面是工业上的实际数据:

| 架构 | 参数量 (单任务=1×) | 推理时间 | 显存占用 | 部署成本 |
| :--- | :--- | :--- | :--- | :--- |
| Shared-Bottom | 1.5× | 1.2× | 1.3× | 低 |
| MMoE-4 | 2.0× | 1.5× | 1.6× | 中 |
| MMoE-8 | 3.0× | 1.8× | 2.2× | 中-高 |
| PLE-1 | 2.5× | 1.7× | 1.8× | 中-高 |
| PLE-2 | 4.0× | 2.5× | 3.0× | 高 |
| ESMM | 1.8× | 1.4× | 1.5× | 低-中 |
| 多模型融合(6 个 MMoE) | 12× | 6× | 8× | 极高 |

**关键判断**:
- **千亿级流量**服务(YouTube、抖音首页):**只能用 Shared-Bottom 或小 MMoE**,PLE 都嫌重
- **百亿级流量**服务(微信视频号、淘宝首页):**MMoE-4/8 或 PLE-1** 是合理选择
- **十亿级流量**服务(美团、京东):**可以用 PLE-2 或更复杂架构**
- **小流量场景**(内部分析、AB 实验):**随便造**

**工程经验**:**永远以"推理延迟"为第一约束**——30ms 的 latency 限制下,你只能选 Shared-Bottom 或 MMoE-4。延迟 100ms 才能用 PLE-2。

### 9.10 进阶:多任务 + 多场景的混合架构

最新的工业实践(2023-2024)显示,**多任务 + 多场景**联合建模是趋势:

```text
场景 1: 首页推荐 (主要流量)
场景 2: 详情页推荐 (次要流量)
场景 3: 推送通知 (冷启动)

  ↓

多任务:CTR / 完播 / 点赞 / 关注(共享)

  ↓

混合架构:
  - 场景 1 + CTR + 完播 → MMoE-4
  - 场景 2 + 点赞 → PLE-1
  - 场景 3 + 关注 → 单任务(数据少)
  - 加 PCGrad / UW 缓解冲突
```

**关键设计**:
- **场景 + 任务**两两配对,每个配对单独建模
- 共享底层用 MMoE,场景专属部分用 PLE
- **多场景 / 多任务联合训练**需要更复杂的 PCGrad 变体(场景 + 任务双重投影)

**难点**:
- 训练成本叠加,**部署成本爆炸**
- 评估体系:多场景多任务,**4 维指标矩阵**(场景 × 任务)
- 工程复杂度高,只有头部公司玩得起

## 章节小结

**核心要点**:

- **跷跷板**:多任务学习里"任务 A 涨,任务 B 跌"的现象,根因是**梯度冲突 + 容量瓶颈 + 任务相关性弱**。

- **梯度平衡**:UW (Uncertainty)、GradNorm、PCGrad 是三个主流方法,可叠加在 MMoE / PLE 上。

## 11. 跷跷板效应的数学诊断

### 11.1 任务梯度冲突度量

定义任务 i 的梯度为 $g_i$,跷跷板发生时存在**梯度方向冲突**:

$$\cos(\theta_{ij}) = \frac{g_i \cdot g_j}{\|g_i\| \|g_j\|}$$

- $\cos \theta = 1$：完全同向（互不干扰）
- $\cos \theta = 0$：正交
- $\cos \theta = -1$：完全冲突（**跷跷板最强**）

**实验观察**：多任务训练中，跷跷板任务的 $\cos \theta$ 经常跌到 -0.3 到 -0.6。

### 11.2 GradNorm: 自动平衡任务权重

**论文**：Chen et al., 2018, "GradNorm: Gradient Normalization for Adaptive Loss Balancing"

**核心思想**：训练时动态调整每个任务的 loss 权重，让不同任务以"相似速度"学习。

**算法**：
```python
# 伪代码
for step in training:
    # 1. 计算各任务梯度
    grads = {task: compute_grad(loss[task]) for task in tasks}

    # 2. 计算各任务学习速度
    loss_ratio = {t: loss[t] / initial_loss[t] for t in tasks}
    inverse_rate = {t: loss_ratio[t] / mean(loss_ratio.values()) for t in tasks}

    # 3. 调整任务权重（鼓励学得慢的任务）
    weights = {t: inverse_rate[t] ** alpha for t in tasks}  # alpha=0.5~2
    weights = {t: w / sum(weights.values()) for t, w in weights.items()}

    # 4. 用新权重反向传播
    total_loss = sum(weights[t] * loss[t] for t in tasks)
    total_loss.backward()
```

**实际效果**：
- 在 NYUv2 多任务（分割+深度+法线估计）上，比等权重提升 1.5% mIoU
- 比手工调权稳定 3x（更少调参）

### 11.3 Uncertainty Weighting (Kendall et al., 2018)

让模型**学习**每个任务的不确定性（variance），自动平衡：

$$\mathcal{L} = \sum_t \frac{1}{2\sigma_t^2} \mathcal{L}_t + \log \sigma_t$$

**直觉**：
- $\sigma_t$ 大 → 模型"不确定"任务 t → 降低其权重
- $\log \sigma_t$ 正则项 → 防止 $\sigma_t \to \infty$（即任务被忽略）

**PyTorch 实现**：
```python
class UncertaintyWeightedLoss(nn.Module):
    def __init__(self, num_tasks):
        super().__init__()
        # log(sigma^2)，初始化为 0
        self.log_vars = nn.Parameter(torch.zeros(num_tasks))

    def forward(self, losses):
        weighted = 0
        for i, loss in enumerate(losses):
            precision = torch.exp(-self.log_vars[i])
            weighted += precision * loss + self.log_vars[i]
        return weighted
```

### 11.4 PCGrad: 解决梯度冲突

**论文**：Yu et al., 2020, "Gradient Surgery for Multi-Task Learning"

**核心**：当任务 i 的梯度与任务 j 冲突时，把 $g_i$ 在 $g_j$ 方向上的分量删掉：

```python
def pcgrad(g_i, g_j):
    """将 g_i 投影到 g_j 的正交空间"""
    if (g_i * g_j).sum() < 0:  # 冲突
        g_i = g_i - (g_i * g_j).sum() / (g_j * g_j).sum() * g_j
    return g_i
```

**效果**：在 NYUv2 上，PCGrad 比 MMoE baseline 提升 2-3%。

## 12. MMoE 工业部署调参经验

### 12.1 专家数选择

| 专家数 | 适用场景 | 训练开销 | 效果 |
| :--- | :--- | :--- | :--- |
| 1 | 单任务 baseline | 1x | 弱 |
| 4 | 简单多任务 | 4x | 中 |
| 8 | 推荐/广告主流 | 8x | 好 |
| 16 | 大型平台（字节/阿里） | 16x | 边际收益递减 |
| 32+ | 罕见，通常不必要 | 32x+ | 容易过拟合 |

**经验法则**：专家数 = 任务数 × 2~4。任务数 3 → 专家数 6-12。

### 12.2 塔（Task Tower）设计

```python
class TaskTower(nn.Module):
    """每个任务的顶层塔"""
    def __init__(self, input_dim, hidden_dim, num_layers=3):
        super().__init__()
        layers = []
        for i in range(num_layers):
            layers.append(nn.Linear(input_dim if i==0 else hidden_dim, hidden_dim))
            layers.append(nn.ReLU())
            layers.append(nn.Dropout(0.1))
        self.net = nn.Sequential(*layers)
        self.head = nn.Linear(hidden_dim, 1)  # 二分类

    def forward(self, x):
        return self.head(self.net(x))
```

**关键调参**：
- 塔深度：通常 2-4 层
- 塔宽度：和专家输出维度一致或更小
- Dropout：0.1-0.3（防过拟合）

### 12.3 损失权重

经验值（CTR / 转化 / 时长 / 点赞）：

```yaml
ctr_weight: 1.0      # 主任务
cvr_weight: 0.5      # 转化稀疏
duration_weight: 0.1 # 回归任务
like_weight: 0.3     # 长尾任务
```

**反直觉**：转化率数据稀疏，**反而要用更小权重**，避免稀疏 loss 主导训练。

### 12.4 在线学习 (Online MMoE)

**挑战**：MMoE 是 batch 训练，但推荐需要实时响应。

**解法**：
1. **每日全量重训**：用前一天全量数据训练新模型
2. **增量学习**：流式更新 Embedding + 微调门控
3. **模型蒸馏**：把当前 MMoE 蒸馏到简单模型部署

```python
# 简化：每天更新一次
def daily_update(model, today_data):
    optimizer = Adam(model.parameters(), lr=1e-4)
    for batch in today_data:
        loss = multi_task_loss(model, batch)
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
    return model
```

### 13.2 PLE: MMoE 的进化

**问题**：MMoE 的专家被所有任务共享，可能学不到任务专属模式。

**PLE 解法**：显式分离任务专属专家 + 共享专家：

```python
class PLE(nn.Module):
    def __init__(self, num_tasks, num_shared_experts=4, num_task_experts=4):
        super().__init__()
        # 每个任务有专属专家
        self.task_experts = nn.ModuleList([
            nn.ModuleList([Expert() for _ in range(num_task_experts)])
            for _ in range(num_tasks)
        ])
        # 共享专家
        self.shared_experts = nn.ModuleList(
            [Expert() for _ in range(num_shared_experts)]
        )
        # 每个任务的门控
        self.gates = nn.ModuleList([
            Gate(num_task_experts + num_shared_experts)
            for _ in range(num_tasks)
        ])

    def forward(self, x, task_id):
        # 任务专属专家
        task_out = [e(x) for e in self.task_experts[task_id]]
        # 共享专家
        shared_out = [e(x) for e in self.shared_experts]
        # 门控融合
        all_experts = task_out + shared_out
        weights = self.gates[task_id](x)  # softmax
        return sum(w * e for w, e in zip(weights, all_experts))
```

**效果**：在腾讯视频推荐上，PLE 比 MMoE 提升 AUC 0.5-1%。

## 14. 数学理论深入

### 14.1 MMoE 与条件计算的等价

MMoE 的门控网络 $g(x)$ 本质是**软路由**，等价于**条件计算**：

$$h_k(x) = \sum_{i=1}^{n} g_i(x) \cdot E_i(x)$$

**联系到 MoE（Mixture of Experts）**：
- LLM 中的 Switch Transformer、GShard 都用类似结构
- 区别：MMoE 是"小专家+多任务"，MoE 是"大专家+单任务"

### 14.2 任务相关性的数学刻画

定义任务 i, j 之间的相关性：

$$\rho_{ij} = \frac{\mathbb{E}[(L_i - \bar{L}_i)(L_j - \bar{L}_j)]}{\sigma_{L_i} \sigma_{L_j}}$$

**经验**：$\rho > 0.5$ → 强相关，MMoE 收益大；$\rho < 0.2$ → 弱相关，跷跷板严重，建议分离模型。

### 14.3 与集成学习的对比

| 维度 | MMoE | 集成 (Stacking) |
| :--- | :--- | :--- |
| 参数共享 | 是 | 否 |
| 端到端 | 是 | 否 |
| 训练成本 | 1x | Kx（K 个模型） |
| 任务相关性 | 自动学习 | 手工设计 |
| 推理延迟 | 低（单模型） | 高（多模型） |

**关键区别**：MMoE 是**联合优化**（loss 共同反向传播），集成是**独立训练**（loss 分别优化）。
