# 社招 1 年经验算法/AI 工程师简历模板与制作手册

> 简历是你**视频版的自我介绍** —— 招聘方花 7-30 秒判断要不要继续看。本手册把"算法岗 1 年经验"最容易踩的坑、最该突出的亮点、最优的工具链, **浓缩成一份可直接 copy 使用的简历制作 SOP**。

## 0. 前言: 为什么 1 年经验的简历更"难写"

### 0.1 三个事实

1. **2026 年中国算法岗投递量同比增长 340%, HC 仅增长 12%** — 卷度创新高。
2. **HR 平均阅读时间从 2023 年的 11 秒缩短到 7 秒** — 信息密度要求越来越高。
3. **1 年经验最容易"被刷掉"**, 不是因为能力不够, 而是"和 5 年资深候选人比看不出亮点"。

### 0.2 本手册的 5 个核心承诺

1. **明确告诉 HR / 面试官"你做了什么 + 结果 + 你的成长"**, 而不只是"参与了什么"
2. **每条项目 bullet 都有量化指标**, 满足大厂 ATS 评分权重（数据量化 × 1.3）
3. **针对 1 年经验的特殊策略**: 突出成长性、潜力、学习能力, 而不是比深度
4. **配套 Markdown + LaTeX 双模板**, 可直接 fork 改造
5. **附 5 份已实证有效的真实 GitHub Pages 简历范例** + 拆解

### 0.3 路径图

## 1. HR / 技术 Leader 第一视角

> "知己知彼" — 先搞清楚他们**怎么看**, 你才知道**怎么写**。

### 1.1 HR 平均阅读时间: 7-30 秒

| 场景 | 时长 | 触发决策 |
| :--- | :--- | :--- |
| HR 桌面扫描 | **7 秒** | 决定是否送技术评估 |
| 技术 leader 细读 | 30-60 秒 | 决定是否约面试 |
| 面试前 5 分钟回看 | 1-2 分钟 | 准备提问 |

> **7 秒 = 看 4 行**：姓名 / 公司 / 工作年限 / 最近一段成就。所以"最近一段工作"必须**放在第一眼看到的位置**。

### 1.3 必看模块视线扫描路径

```text
[视线时间占比]

👁 0.5s  → 个人信息 + 工作年限 + 期望岗位
```

> 总结：80% 决策来自**前 5 行**。

### 1.4 资深面试官的 3 个"死亡信号"（TrueSight 15 年视觉算法面试官视角）

1. **堆砌名词，缺乏上下文**: 罗列 SOTA 模型，没说在哪数据集、什么硬件、什么效果
2. **成果模糊，缺乏量化**: "提升了准确率" —— 没有 mAP / FPS 都是耍流氓
3. **缺乏落地闭环**: 只懂调参，不懂量化、算子融合、端侧部署

### 1.7 "逆向" 视角: 大厂 HR 实际怎么读简历

```python
def hr_reads_resume(resume):
    """
    模拟 HR 7 秒阅读路径
    """
    # 0-1s: 工作年限 + 最近公司
    if resume.work_years < 2:
        # 1 年经验需要更多亮点补偿
        check_highlights(resume)

    # 1-3s: 头部 4-5 行
    if not has_clear_position_intent(resume):
        return REJECT  # 没写期望岗位 = 不认真

    # 3-5s: 最近 1 段工作
    if resume.recent_job.duration < 1_year:
        return REJECT  # 1 年跳 2 次的简历

    # 5-7s: 量化数字
    if count_quantified_bullets(resume) < 3:
        return REJECT  # 至少 3 条量化

    # 决定: 送技术评估
    return PASS
```

### 1.10 算法岗招聘方特别在意的 5 件事

[腾讯面鬼仔经验](https://www.nowcoder.com/discuss/887282797973372928) + [TrueSight 视觉算法面试官](https://tsight.io/articles/12883418) + [面试狗·腾讯算法岗](https://interviewdog.cn/prep/tencent-algorithm.html) 综合：

1. **算法理解深度**: 不是问 SOTA, 是问"为什么这版模型在你的场景下有效"
2. **数据敏感度**: 你怎么分析 bad case? 怎么定位问题?
3. **工程实现能力**: 训练 pipeline / 部署 / 监控是否齐全
4. **业务 sense**: 你的优化是不是真的带来业务价值, 不是自嗨
5. **论文 / 项目真实性**: 是否能讲清楚 motivation / 创新点 / 局限

### 1.13 算法岗招聘的"潜规则"

| 潜规则 | 应对 |

## 2. 简历结构与模板

> "结构 = HR 7 秒视线扫描路径"。这一章给出**可直接 fork 改造**的标准结构。

### 2.1 标准 6 大板块（社招 1 年经验）

```text
1. 个人信息（顶部一行，必备）
   ├─ 姓名 + 期望岗位
   ├─ 电话 + 邮箱
   └─ GitHub / 博客（可选）

2. 技术栈（分组清晰，必备）
   ├─ 编程语言（精通 / 熟悉 / 了解 三档分开）
   ├─ 深度学习框架
   ├─ LLM / RAG / Agent（按方向）
   └─ 工程化 / 工具链

3. 工作经历（倒序，必备，2-3 段）
   ├─ 公司 · 职位 · 时间
   └─ 项目 bullets（每条 STAR + 量化）

4. 项目经历（独立项目，可选补充）
   ├─ 项目名 + 时间
   └─ 技术栈 + 角色 + 量化

5. 教育背景（必备，1-2 行）
   ├─ 学校 · 专业 · 时间
   └─ GPA / 排名 / 相关课程

6. 论文 / 专利 / 竞赛 / 开源（按强度选填）
   ├─ 论文：venue + 排序 + 角色
   └─ 竞赛：Top % + 团队规模
```

### 2.2 1 年经验推荐结构（精简版）

```text
【顶部 1 行】  姓名 · 期望岗位 · 联系方式 · GitHub
【第 2 段】    技术栈（按方向分组, 4-6 行）
【第 3 段】    工作经历（1 段公司, 3-5 个项目 bullets）
【第 4 段】    重点项目（1-2 个独立项目, 2-4 个 bullets）
【第 5 段】    教育背景（学校 · 时间 · 排名）
【第 6 段】    论文 / 竞赛 / 开源（可选）
【第 7 段】    自我评价（1-3 行, 不要空话）
```

## 3. STAR 法则 + 量化指标

> 这一章是**最重要的章节** —— 让流水账变成"业绩证明"。

### 3.1 STAR 法则定义

```text
S (Situation) 项目背景     - 业务问题 + 数据规模 + 现状痛点
T (Task)        具体职责    - 你的角色 + 目标
A (Action)      具体做法    - 模型/工程/部署方案
R (Result)      量化结果    - 离线/线上指标 + 业务收益
```

### 3.2 3 个典型改写样例

#### 案例 1: 推荐系统

**❌ 差：流水账式**

> 参与推荐系统项目，负责特征工程和模型调参，使用 XGBoost 和 LightGBM。

**✅ 好：STAR + 量化**

> **项目：信息流推荐排序优化（2024.06 - 2024.12）**
> - **S**：某百万 DAU 内容平台 CTR 长期低于行业均值 15%，需优化召回排序两阶段。
> - **T**：独立负责排序侧多目标模型迭代。
> - **A**：基于 **XGBoost + DeepFM** 构建多目标融合排序模型，引入 32 维用户长短期兴趣特征；引入 **ItemCF 负采样**缓解曝光偏差。
> - **R**：离线 AUC +0.023（0.781→0.804），线上 A/B 实验 CTR **+7.2%**（p<0.01），用户次日留存 **+3.1%**，2 个月后全量上线，覆盖日均请求 2000 万+。

#### 案例 2: LLM 推理

**❌ 差："假大空"**

> 优化了模型推理速度，提升了系统性能。

**✅ 好：硬件 + 量化 + 业务**

> 通过 **TensorRT FP16 量化** + **动态批处理**（max_batch=32），LLM 推理延迟从 180ms 降至 **65ms**（↓64%），客服机器人并发从 500 QPS 提升至 **1400 QPS**，支撑双 11 峰值无降级。

#### 案例 3: 团队协作

**❌ 差："打杂感"**

> 与团队协同发布产品。

**✅ 好：领导力 + 量化**

> 带 **4 人** 小组负责数据 pipeline，主笔季度 OKR，模型上线 **Doubao 1.5** 主对话版本。

### 3.3 量化指标的 4 个维度

```text
每条 highlight 至少包含 1 个数字, 最好 2-3 个:

时间维度    训练时长 / 收敛步数 / latency / 周期
规模维度    模型大小 / GPU 数 / tokens 量 / QPS / DAU
质量维度    精度 / 召回 / winrate / 稳定性
影响维度    上线产品 / 业务线接入 / 团队规模
```

### 3.4 量化指标公式

**改写对比表 — 模糊 vs 量化**:

| 模糊写法（差） | 量化写法（好） |
| :--- | :--- |
| 优化了模型推理速度 | 推理吞吐 +35%（38% → 51% MFU on 8K H100 集群） |
| 主导大模型训练项目 | 主导 100B 参数 MoE 端到端训练, crash rate 60% → 24%, 恢复时间 4h → 25min |
| 参与数据 pipeline 工作 | 设计去污染 + 去重三阶段, 处理 4T+ tokens 中文语料, 下游任务 +4.2 pp on MMLU |
| 与团队协同发布产品 | 带 4 人小组负责数据 pipeline, 主笔季度 OKR, 模型上线 Doubao 1.5 主对话版本 |
| 推动技术指标提升 | 落地 DPO + 拒绝采样, winrate 较 SFT baseline +18 pp（人评 3000 条） |

### 3.5 收益换算公式

```text
商业收益 = (实验组指标 - 对照组指标) × 业务基数 × 货币化系数

例：CTR +2.3%（绝对值）× 日均 GMV 1.2 亿 × 365 × 货币化系数 0.04
     ≈ 年收益 4.02 亿元
```

每条性能提升要回答 4 件事：**基准值→优化后值→相对提升→业务翻译**。

### 3.7 7 类证据的写法（AI Agent / RAG 项目）

```text
1. 场景：为什么要做？
2. 架构：系统如何组织？ (Planner / Retriever / Tool Executor / Evaluator)
3. 数据：用什么验证？ (自建 300 条业务 QA 集)
4. 指标：怎么衡量成功？ (Recall@5 / Faithfulness / P95)
5. 优化：做了哪些动作？ (混合检索 + rerank + 缓存 + fallback)
6. 取舍：为什么这样设计？ (牺牲部分召回换取低延迟)

```

### 3.8 量化时常见的"无数字"症状

| 症状 | 改善 |
| :--- | :--- |
| "提升准确率" | → "准确率 78% → 84%, AUC +0.06" |
| "减少延迟" | → "推理延迟 180ms → 65ms, QPS 500 → 1400" |
| "提升业务" | → "CTR +7.2%, 年化收益 4 亿+" |
| "优化系统" | → "GPU 利用率 38% → 51%, 月节省成本 30 万" |
| "管理团队" | → "带 4 人小组, 完成 3 个上线项目" |

### 3.9 "伪量化" 陷阱

❌ **数字但无意义**:
- "优化 1000 行代码"（与价值无关）
- "完成 50+ PR"（质量未知）
- "服务 1 万用户"（基数太小）

✅ **真正的量化**:
- "将模型 AUC 从 0.781 提升至 0.804, 带来年化 4 亿 GMV 收益"
- "推理服务 P99 延迟从 180ms 降至 65ms, 节省 30% GPU 成本"

### 3.13 量化指标的"诚实底线"

### 5.6 算法岗项目"模型 / 数据 / 效果"三件套

```text
模型: 用了什么模型? 为什么?
  - 选 XGBoost 而非 NN: 树模型可解释 + 小数据更稳定
  - 选 LLaMA-7B 而非 GPT-4: 开源可微调, 数据隐私可控

数据: 用了什么数据? 多大?
  - 100 万用户行为序列, 平均长度 50
  - 自建 300 条金融 QA 测试集 (含 hard cases)

效果: 达到了什么效果?
  - 离线 AUC 0.804, 线上 CTR +7.2%
  - 引用正确率 88%, 用户满意度 +23 pp
```

## 6. 1 年经验特殊关注

> 这一章是**整份手册的核心** — 1 年经验区别于"5 年资深候选人"的策略。

### 6.1 1 年项目如何写得"有亮点"而不是"打杂"

**三个关键动作**:

```text
1. 挖掘项目 "亮点 + 难点 + 待优化点"
   - 让面试官相信你通过上一段工作掌握了下一段工作所需技能
   - "亮点" 证明你能解决别人不能解决的问题
   - "待优化点" 以项目负责人身份叙述 (只有负责人才会想到下一步)

2. 以项目负责人视角重写
   - 不论你是否真负责人, 能思考 "之后如何优化" 就把自己放在更高位置
   - 证明责任心

3. 写 "成长点"
   - 1 年经验本身处于新人角度, 需体现学习能力与潜力
   - 以心得体会、事后总结的形式呈现
```

### 6.2 简历分块顺序: 按个人优势排

```text
简历分块顺序按个人优势排:
- "论文 → 实习 → 竞赛"
- "论文 → 竞赛 → 实习"
- 每块最前的项目最可能被问, 要写得最熟
```

### 6.3 学历 / 论文 / 竞赛排名的加权

```text
- 985 / C9 / Top2: 学校放最前 (这是优势)
- 双非 / 专升本: 必须靠项目 + 竞赛 + 开源补位
- 1 年经验: 学校仍是重要信号, 但项目 + 量化更重要
```

### 6.4 跳槽原因怎么写才不尴尬

| 去向 | 安全话术 |
| :---: | :--- |
| 大厂 → 小公司 | "大平台晋升较慢, 螺丝钉和天花板效应明显, 所以想去小而精的平台更好的发挥个人价值" |
| 小平台 → 大厂 | "小公司有发展的局限性, 想到大的公司扩宽视野, 发挥能力" |
| 给钱少 / 晋升慢 | **绝对不能说**, 改为: "想挑战一下更大的平台" |
| 组织架构调整 / 业务裁撤 | 实话实说, 加一句: "调整后的岗位和我想要的职业发展路线不太一致" |
| 工作内容简单 / 打杂 | "想趁着年轻多做有挑战性的工作" |

### 6.5 期望薪资怎么写

```text
1. 不要在简历上写期望薪资
   - 简历只用于"过筛", 不是谈薪
   - 期望写在 HR 沟通时, 给自己谈判空间

2. 行业基准 (1 年经验, 2026 年):
   - 字节 / 腾讯: 30-50K/月 (16-20 薪)
   - 阿里 / 美团: 28-45K/月 (16 薪)
   - 拼多多: 35-55K/月 (18-20 薪, 加班多)
   - 小红书 / B 站: 30-45K/月 (14-16 薪)
   - 创业公司 (B 轮+): 25-40K/月 + 期权

3. 期望薪资区间计算:
   - 现有 base × 1.2 - 1.5
   - 加入大厂溢价 +20%
   - 跨城市搬家 +5-10%
```

### 6.6 1 年经验标准缺点回答

```text
"由于之前的工作偏执行性, 所以导致自己对于项目的全局性把握的不够。
 在未来的工作中, 我也将多加思考这方面的内容。"
```

(主推 / 1-3 年经验通用)

### 6.7 1 年经验"成长性"的具体体现

```text
✅ 体现 1: 难度递进的项目
- 第一个项目: 执行工程师任务, 实现 X
- 第二个项目: 独立完成 Y 模块
- 第三个项目: 主导 0 到 1 项目 Z

✅ 体现 2: 技术深度递进
- 初期: 使用 XGBoost
- 中期: 改造 XGBoost + 引入自定义特征
- 后期: 自研模型架构

✅ 体现 3: 业务理解递进
```

### 6.8 "项目打杂感"的 5 个修复法

```text
1. 包装法: 把"协助"改成"参与", 把"参与"改成"独立负责"
2. 深度法: 加技术细节 (用了什么算子 / 什么优化)
3. 量化法: 加数字 (耗时 / 数据量 / 性能)
4. 业务法: 加上线 / 业务收益
```

### 6.11 1 年经验"简历陷阱"

```text
❌ 项目: "协助 XX 模块" (体现不出贡献) → 改 "独立完成"
❌ 期望薪资: 写太高 (显得没诚意) / 写太低 (显得没自信)
```

```text
2. 有新 offer 护航: 不要裸辞
3. 目标公司清楚: 不是 "想看看机会", 而是 "想加入 XX 公司做 XX"
4. 节奏稳: 不急不躁, 不仓促决定
```

### 6.14 "1 年经验" 反向建议

## 8. ATS 优化

> "ATS = 机器过筛"。这一章教你过机器, 再过 HR。

### 8.1 现代 ATS 三层解析模型

```python
# 来源: 2026 ATS 解码报告

ATS_PARSING_LAYERS = {
    "Layer 1": "关键词存在 (keyword presence) → 基础门槛",
    "Layer 2": "语义上下文 (semantic context)   → NLP 看'用法'",
    "Layer 3": "影响力量化 (impact quantification) → 数字 / 百分比 / 时间"
}
```

### 8.2 9 元素 ATS 风险矩阵

| 元素 | ATS 风险 | 建议 |
| :---: | :---: | :--- |
| 单栏文本 + 标准 bullet | ✅ 0 | 主用 |
| 表格 | ⚠️ 中-高 | 表格内不放成就 bullet |
| 多栏布局 | ❌ 高 | 投 ATS 不用 |
| 文本框 | ❌ 高 | 不用 |
| 图表 / 图片 | ❌ | 装饰可用, 关键信息不放图里 |
| Icon | ⚠️ 低-中 | 装饰别太多 |
| 颜色 / 字体 | ✅ 低 | 不影响解析 |
| 链接 | ⚠️ 低 | URL 文本被读 |
| 页眉 / 页脚 | ❌ 高 | 联系方式别放那 |

### 8.3 ATS 友好的 5 条铁律

```text
1. PAR 格式: Problem-Action-Result, 每条 bullet 三件套
2. 数字嵌入: 关键词附近必须有数字
3. 禁用模糊词: "显著提升" → 必须换数字
4. 文件名规范: "Lin-Zixuan-CV.pdf" 而非 "林子轩简历.pdf"
5. PDF 体积 ≤ 500KB
```

### 8.4 关键词提取 (JD 反推)

```python
def extract_jd_keywords(jd_text):
    """从 JD 提取关键词, 用于简历匹配"""
    import re
    # 必出现 (must-have)
    must = re.findall(r"\b(Python|PyTorch|TensorFlow|Java|C\+\+|SQL)\b", jd_text)

    # 加分项 (nice-to-have)
    nice = re.findall(r"\b(Docker|K8s|CUDA|Triton|vLLM|RAG|LLM|Agent)\b", jd_text)

    # 软技能
    soft = re.findall(r"\b(沟通|协作|抗压|责任心|主动)\b", jd_text)

    return {
        "must_have": list(set(must)),
        "nice_to_have": list(set(nice)),
        "soft_skills": list(set(soft)),
    }
```

### 8.5 关键词嵌入位置

```text
关键词必须出现在 3 个位置:
1. 技能栈区域 (按方向分组)
2. 项目 bullet 中 (关键词 + 数字)
3. Summary / 自我评价中 (1-2 个核心方向)
```

```text
ML 类: PyTorch / TensorFlow / sklearn / XGBoost / LightGBM
LLM 类: Transformers / vLLM / SGLang / LangChain / LangGraph / DPO / RLHF
```

### 8.7 ATS 友好度自检清单

```text
✅ 标准字体 (思源黑体 / 微软雅黑 / 宋体)
✅ 关键词出现在标题 / 项目 bullet / 技能区三处

❌ 避免: 复杂表格 / 图片嵌入 / 页眉页脚 / 双栏排版
```

### 8.8 1 年经验简历的 ATS 优化重点


## 附录 D: FAQ (15 个高频问题)

**Q1: 我应该用 Markdown 还是 LaTeX 写简历?**

A: 看个人喜好。
- **Markdown**: 上手快, 工具链简单 (Pandoc + Typst), 适合不碰 LaTeX 的同学
- **LaTeX**: 排版天花板, 学术 / 工程师友好, 适合追求完美的同学
- **YAML 数据驱动** (rendercv): 适合多份简历统一管理
- 现实: 90% 用 Markdown 也能拿到大厂 offer, 关键是内容, 不是格式

**Q2: 简历应该多长?**

A: 1 年经验强制 1-1.5 页。
- 应届 / 1 年: 1 页
- 1-3 年: 1-1.5 页
- 3-5 年: 1.5-2 页
- 5 年以上: 2 页
- **不要超过 2 页** (3+ 年经验), HR 没有耐心

**Q3: 工作 1 年想跳, 怎么解释跳槽原因?**

A: 参考 §6.4。**绝对不要说**: 老板不好 / 工资低 / 同事差 / 加班多。**安全话术**: 想挑战更大的场景 / 想长期发展 / 想接触更复杂的业务。

**Q4: 简历里要不要放照片?**

A: **看公司文化**:
- 外企 / 港企: 通常要放
- 国企 / 银行: 通常要放
- 互联网大厂 (字节 / 阿里): 不放
- 创业公司: 看情况
- 默认: **不放**, ATS 不读, 浪费空间

**Q5: GitHub 不到 1k stars, 还要不要放?**

A: **看相关性**:
- 强相关 (面试算法岗, 项目类似): 放, 加 stars 数
- 弱相关 (完全不同领域): 不放
- 默认: **不放**, 或者一句话"项目见 GitHub"

**Q6: 期望薪资要不要写在简历?**

A: **不要**, 写在 HR 沟通时。简历只用于过筛, 不是谈薪。

**Q7: 没论文, 怎么补?**

A: 1 年经验没论文很正常。
- 优先: Kaggle / 天池 / Datawhale (Top 5%-10%)
- 次选: 技术博客 / 开源项目 (1k+ stars)
- 替代: 公司内部技术沉淀 (PPT / Wiki / 文档)

**Q8: 双非本科, 简历怎么补救?**

A: 双非 1 年经验过筛率 10-20%, 需要更亮眼:
- **必须有 Kaggle Top 5%**
- **必须有 GitHub 1k+ stars**
- **必须有量化数字**
- **必须针对 JD 调关键词**
- 教育背景放最后 (不要显眼)

**Q9: 应该海投还是精投?**

A: **精投优先**。
- 海投: 每天 10-20 份, 转化率 < 5%
- 精投: 每天 3-5 份, 针对 JD 调, 转化率 15-25%
- 1 年经验建议 80% 精投 + 20% 海投

**Q10: 内推真的比海投好吗?**

A: **是的**, 转化率高 2-3 倍:
- 内推: 35% 面试通过率 / 20% 录用率
- 海投: 18% 面试通过率 / 10% 录用率
- 内推 = HR 信任度 + 候选人主动性强 + 直接送到技术 Leader

**Q11: 1 年经验跳槽会不会被认为"不稳"?**

A: 会, 但可以应对:
- 强调"想长期发展"
- 强调"已规划好未来 3 年"
- 强调"业务匹配度"
- 1 年经验跳槽在算法岗不算罕见 (大厂平均司龄 2-3 年)

**Q12: 简历里的"参与"和"独立负责"到底怎么写?**

A: **主动词严格分级**:
- 主导 (Led / Drove / Headed): 0 到 1, 团队 leader
- 独立负责 (Independently owned): 一个人扛
- 主要负责 (Primarily responsible): 多个人, 你占比最大
- 参与 (Contributed / Participated): 协作, 不主导
- 协助 (Assisted / Helped): 边角料

**Q13: 推荐系统的项目怎样写最有亮点?**

A: **量化 + 业务**:
- 数据规模 (100 万 DAU, 2000 万 PV)
- 模型指标 (AUC +0.023)
- 业务指标 (CTR +7.2%, CVR +4.8%)
- 工程指标 (延迟 180ms → 65ms)
- 上线范围 (全量 / 灰度 / 试验)

**Q14: LLM 项目怎样写最有亮点?**

A: **链路 + 评测 + 成本**:
- 训练 / 微调 (LoRA + DPO + Ray 分布式)
- 推理 (vLLM + TensorRT)
- 评测 (自建测试集 + GPT-4 胜率)
- 成本 (单条推理成本 $0.003)

**Q15: 投递多久没回复应该放弃?**

A: **7 天**:
- 3 天内没回复: 简历被筛的概率 70%
- 7 天内没回复: 简历被筛的概率 95%
- 7 天后主动询问: 礼貌但不一定有效
- 14 天后: 视为已放弃, 准备下一家

## 附录 E: 面试反问 5 个加分题

> 面试结束前, HR / 面试官都会问"你有什么问题想问?" — 这是**加分**的机会。

### E.1 反问 5 道题 (按优先级)

**1. 关于团队**:
> "您团队目前最希望解决的 1 个技术问题是什么? 如果我入职, 第一个月应该聚焦在哪?"

体现: 你关心业务, 想马上产生价值, 不是来"养老"。

**2. 关于岗位**:
> "这个岗位未来 1 年的成长路径是什么? 团队对新人的期望是什么?"

体现: 你有长期规划, 不是干一票就走。

**3. 关于技术栈**:
> "团队目前使用的 LLM 训练 / 推理框架是什么? 有考虑过迁移到 vLLM / SGLang 吗?"

体现: 你懂技术, 对行业趋势敏感。

**4. 关于业务**:
> "团队最近上线的最重要功能是什么? 上线后效果怎么样?"

体现: 你关注业务落地, 不是只懂算法。

**5. 关于团队文化**:
> "团队的 code review / 知识分享机制是怎样的?"

体现: 你关心 engineering culture, 愿意成长。

### E.2 反问的"雷区"

```text
❌ "这个岗位薪资多少?" (HR 面再问)
❌ "团队加班严重吗?" (HR 不喜欢)
❌ "我什么时候能晋升?" (显得急功近利)
❌ "我能远程办公吗?" (1 年经验不适合问)
❌ "我没什么问题了" (没准备 = 不感兴趣)
```

### E.3 反问的话术模板

**关于团队**:
> "您团队目前最希望解决的 1 个技术问题是什么?"

**关于成长**:
> "这个岗位未来 1 年的成长路径是什么?"

**关于技术**:

### E.4 反问的"加分项"

### F.2 Python 完整评分脚本

```python
#!/usr/bin/env python3
"""score_resume.py - 简历评分 (8 大厂通用)"""
import re
import sys

def score_resume(resume_text: str) -> dict:
    """返回 4 个维度的分数 (0-100)"""
    scores = {}

    # 1. 关键词密度 (25 分)
    keywords = ["Python", "PyTorch", "TensorFlow", "SQL", "Git", "Linux",
                "CUDA", "Docker", "K8s", "推荐", "搜索", "LLM", "RAG"]
    kw_count = sum(1 for kw in keywords if kw in resume_text)
    scores["关键词"] = min(100, kw_count * 8)

    # 2. 数字量化 (25 分)
    numbers = re.findall(r"\d+\.?\d*%?", resume_text)
    scores["数字量化"] = min(100, len(numbers) * 2)

    # 3. STAR / PAR 完整 (25 分)
    # 简化: 检测动词
    action_verbs = ["主导", "独立", "负责", "设计", "实现", "优化",
                     "构建", "搭建", "推动", "参与"]
    verb_count = sum(1 for v in action_verbs if v in resume_text)
    scores["STAR"] = min(100, verb_count * 10)

    # 4. 排版 / 结构 (25 分)
    # 简化: 检测段落数
    sections = ["教育背景", "工作经历", "项目经历", "技术栈", "自我评价"]
    sec_count = sum(1 for s in sections if s in resume_text)
    scores["结构"] = min(100, sec_count * 20)

    # 总分
    scores["总分"] = sum(scores.values()) // 4

    return scores


if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("用法: python score_resume.py resume.pdf")
        sys.exit(1)

    import subprocess
    text = subprocess.run(["pdftotext", sys.argv[1], "-"], capture_output=True, text=True).stdout

    scores = score_resume(text)
    print(f"=== 简历评分 ===")
    for k, v in scores.items():
        bar = "█" * (v // 5)
        print(f"  {k:10s}: {v:3d} {bar}")
```

对 "社招 1 年经验算法/AI 工程师简历模板与制作手册" 常见的误解包括:

1. **"模型越复杂越好"**: 实际上,简单模型 + 好数据往往优于复杂模型 + 烂数据。这条法则在实践中反复被验证。

2. **"训练 loss 越低越好"**: 训练 loss 低不代表泛化好,可能过拟合。要看验证集表现,做误差分析。

3. **"指标好就等于业务好"**: 离线指标与在线业务有 gap,必须做 A/B 测试。指标可以被优化,但业务目标很难直接优化。

4. **"新方法一定比旧方法好"**: 新方法通常针对特定场景,在你的场景未必更好。要谨慎评估,先复现,再改进。

5. **"开源即用"**: 开源代码与你的数据/工程栈往往有 gap,需要适配。盲目复用经常踩坑,要理解代码再做改动。
