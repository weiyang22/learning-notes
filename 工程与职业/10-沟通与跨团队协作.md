# 10-沟通与跨团队协作

> **定位**: 算法工程师的"软实力手册", 把"沟通能力"从"软技能"变成"硬通货"
> **适用**: 算法工程师 / 研究员, 想搞清楚"怎么让别人听懂 + 接受 + 行动"
> **风格**: 场景 + 模板 + 案例 + 检查表, 一份文档讲透"沟通怎么练"

## 0. 一句话总结

**算法工程师 80% 时间是沟通**: 写文档 / 评审 / 拉通 / 答辩 / 培训. P5 看技术, P6 看执行, P7+ 看沟通. 本文用 12 大场景 + 模板 + 案例, 让你从"不会说话"到"沟通高手".

## 1. 为什么沟通重要

### 1.1 算法工程师的工作 80% 是沟通

```text
算法工程师的时间分配:
- 模型设计: 10%
- 写代码: 10%
- 实验调优: 10%
- 写文档: 20%
- 会议评审: 20%
- 跨团队沟通: 20%
- 答辩 / 培训: 10%
```

**真相**: 沟通能力决定你能走多远.

```text
P5 → P6: 技术 + 执行
P6 → P7: 系统设计 + 沟通
P7 → P8: 影响力 + 跨部门
P8 → P9: 行业领导 + 沟通
```

### 1.2 跨团队协作的挑战

**4 大挑战**:

1. **目标不一致**: 算法想 AUC, 工程想稳定, PM 想上线
2. **语言不通**: 算法讲 loss, 工程讲 latency, PM讲 业务指标
3. **优先级冲突**: 算法想做实验, 工程想 release, 数据想清洗
4. **责任边界模糊**: 谁来负责, 怎么兜底

## 2. 与产品经理协作

### 2.1 理解需求

**3 个常见误区**:

```text
误区 1: "PM 不懂技术"
正确: PM 懂业务, 不懂技术是算法的事
       算法要把技术翻译成业务

误区 2: "PM 需求总是变"
正确: PM 需求是基于业务理解的, 不是瞎变
       算法要主动追问, 不是被动接受

误区 3: "PM 拍脑袋"
正确: PM 是有数据 + 用户反馈 + 业务理解
       算法要参与决策, 不是被动执行
```

**5 个关键问题**:

```text
1. 这个需求的业务背景是什么? (为什么做)
2. 成功标准是什么? (OEC 是什么)
3. 优先级是多少? (为什么这个先)
4. 时间要求是什么? (什么时候上线)
5. 不做什么? (排除范围)
```

### 2.2 拆解需求

**5W1H 拆解法**:

```text
W (What):   做什么? (功能定义)
W (Why):    为什么做? (业务价值)
W (Who):    谁做? (谁负责)
W (When):   何时做? (时间节点)
W (Where):  在哪做? (哪个模块 / 业务)
H (How):    怎么做? (技术方案)
```

**示例**:

```text
PM 需求: "我们想做个新功能, 提升推荐效果"

算法拆解:
- W: 提升 CTR / GMV / 时长 (明确指标)
- W: 业务方反馈用户停留下降
- W: 算法 + 工程 + 数据
- W: 1 个月上线
- W: 抖音 Feeds
- H: DIN 改造 DIEN + 推理优化
```

### 2.3 量化影响

**3 个量化维度**:

```text
1. 业务影响: CTR / GMV / DAU / 时长 (核心)
2. 技术影响: AUC / 延迟 / 吞吐 (辅助)
3. 范围影响: 用户数 / 业务数 / 团队数 (扩展)
```

**表达模板**:

```text
"这个优化预计能:
- 业务上: CTR +1%, GMV +3%
- 技术上: AUC +0.5%, p99 延迟 ↓10ms
- 范围上: 影响 8 亿用户, 全公司 3 个业务复用"
```

### 2.4 案例: 业务沟通失败

**背景**: 某算法工程师和 PM 沟通需求, 结果 PM 觉得算法不配合.

**失败原因**:

```text
1. 算法只讲技术方案 (AUC +0.5%), 不讲业务
2. 算法没参与业务讨论, 觉得"PM 让我做我就做"
3. 算法没追问需求细节, 结果做出来 PM 不满意
4. 算法上线后没主动同步结果, PM 不知道进展
```

**正确做法**:

```text
1. 算法要理解业务 (参加业务会议)
2. 算法要把技术翻译成业务 (用业务指标表达)
3. 算法要主动追问需求 (5W1H)
4. 算法要主动同步进展 (周报 + 关键节点)
5. 算法要有不同意见 (技术不可行时及时说)
```

## 3. 与后端 / 客户端协作

### 3.1 接口设计

**3 大原则**:

```text
1. 简洁: 接口最小化, 不暴露内部实现
2. 稳定: 接口向后兼容, 不要频繁变更
3. 可测: 接口可独立测试, 不要依赖全局状态
```

**RESTful 接口示例**:

```text
GET /v1/recommend?user_id=123&scene=feeds&count=20
→ 返回: { "items": [{"id": "v1", "score": 0.95}, ...] }

POST /v1/feedback
→ 请求: { "user_id": "123", "item_id": "v1", "action": "click" }
→ 返回: { "status": "ok" }
```

**接口版本管理**:

```text
/v1/recommend    (旧版本, 维护)
/v2/recommend    (新版本, 推荐)
/v3/recommend    (实验版本, 灰度)
```

### 3.2 性能与功能平衡

**性能 vs 功能 trade-off**:

```text
PM: "我要加 5 个新特征"
算法: "可以, 但延迟会增加 5ms"
工程: "P99 约束是 30ms, 加不了"
PM: "那能不能不加"
算法: "可以, 但 AUC 会降 0.3%"
...
最终方案: 加 3 个核心特征, AUC +0.2%, 延迟 +3ms
```

**3 个常见冲突**:

```text
冲突 1: 算法要 AUC, 工程要延迟
  → 解决方案: 用知识蒸馏 + 模型量化

冲突 2: 算法要复杂模型, 客户端要小包
  → 解决方案: 服务端计算, 客户端只展示

冲突 3: 算法要实时, 工程要稳定
  → 解决方案: 异步化 + 缓存
```

### 3.3 联调排期

**联调流程**:

```text
W1: 接口设计 + 文档 (算法 + 后端)
W2: 接口实现 + 联调环境 (后端)
W3: 接口联调 (算法 + 后端 + 客户端)
W4: AB 实验 + 调优 (算法)
W5: 全量上线 (所有)
```

**排期模板**:

```text
| 任务 | 负责人 | 开始 | 结束 | 依赖 |
|------|-------|------|------|------|
| 接口设计 | 算法 | W1D1 | W1D3 | - |
| 接口实现 | 后端 | W1D4 | W2D5 | 接口设计 |
| 联调 | 算法 + 后端 | W3D1 | W3D5 | 接口实现 |
| AB 实验 | 算法 | W4D1 | W4D5 | 联调 |
| 全量上线 | 所有 | W5D1 | W5D2 | AB 通过 |
```

## 4. 与数据团队协作

### 4.1 特征工程

**特征 pipeline**:

```text
原始数据 → 清洗 → 加工 → 特征化 → 存储 → 服务
  │         │       │       │        │       │
  日志    去重   聚合    Embedding   Hive   在线
```

**特征分类**:

```text
1. 用户特征: 性别 / 年龄 / 城市 / 兴趣
2. 物品特征: 类目 / 标签 / 价格 / 销量
3. 行为特征: 点击 / 收藏 / 购买 / 时长
4. 上下文特征: 时间 / 地点 / 设备 / 网络
5. 交叉特征: 用户 × 物品, 时间 × 类目
```

**特征责任划分**:

```text
数据团队: 原始数据采集 + 离线计算
算法团队: 特征设计 + 特征工程
工程团队: 在线服务 + 监控
```

### 4.2 数据质量

**数据质量 5 维度**:

```text
1. 准确性: 数据是否正确
2. 完整性: 数据是否缺失
3. 一致性: 多源数据是否一致
4. 时效性: 数据是否及时
5. 唯一性: 数据是否重复
```

**数据质量监控**:

```python
# 数据质量检查脚本
def check_data_quality(df):
    issues = []

    # 缺失率检查
    null_rate = df.isnull().mean()
    high_null = null_rate[null_rate > 0.1]
    if len(high_null) > 0:
        issues.append(f"高缺失率: {high_null.to_dict()}")

    # 分布检查
    for col in df.select_dtypes(include='number'):
        mean, std = df[col].mean(), df[col].std()
        if std == 0:
            issues.append(f"常量列: {col}")
        if abs(mean) > 100 * std:
            issues.append(f"异常均值: {col}")

    # 时效性检查
    if 'timestamp' in df.columns:
        latest = df['timestamp'].max()
        if latest < pd.Timestamp.now() - pd.Timedelta(hours=1):
            issues.append(f"数据延迟: {latest}")

    return issues
```

## 5. 与运维 / SRE 协作

### 5.1 模型部署

**部署流程**:

```text
1. 算法提交模型 (权重 + 配置)
2. 工程打包镜像 (Docker)
3. SRE 部署到测试环境
4. 算法验证 (AB 测试)
5. SRE 灰度上线 (1% → 10% → 50% → 100%)
```

**部署检查清单**:

```text
- [ ] 模型文件 md5 一致
- [ ] 配置文件正确
- [ ] 特征 pipeline 验证
- [ ] 监控指标配置
- [ ] 告警规则配置
- [ ] 应急预案准备
- [ ] 回滚方案确认
```

### 5.2 监控告警

**监控 3 层**:

```text
1. 业务层: CTR / GMV / DAU / 时长
2. 模型层: AUC / 预测分布 / 特征覆盖率
3. 系统层: P99 / QPS / 错误率 / CPU / GPU
```

**告警规则**:

```yaml
# prometheus 告警示例
- alert: HighP99Latency
  expr: latency_p99 > 30ms
  for: 5m
  severity: warning

- alert: ModelAccuracyDrop
  expr: auc < 0.7
  for: 1h
  severity: critical

- alert: HighErrorRate
  expr: error_rate > 0.01
  for: 5m
  severity: critical
```

### 5.3 应急响应

**应急响应流程**:

```text
1. 告警触发 (Prometheus)
2. oncall 收到 (PagerDuty / 钉钉)
3. 5 分钟内响应 (排查)
4. 15 分钟内确认 (根因)
5. 30 分钟内缓解 (降级 / 回滚)
6. 1 小时内恢复 (修复)
7. 24 小时内复盘 (RCA)
```

**应急手段**:

```text
降级: 切到简单模型 (LR)
限流: 降级 50% 流量
回滚: 切到上一个稳定版本
熔断: 暂停某服务
切流: 切到备用集群
```

## 6. 跨业务线协作

### 6.1 模型共享

**共享模式**:

```text
模式 1: 完全共享 (一个模型, 多业务)
  - 适用: 业务相似 (Feeds / 直播 / 极速版)
  - 优点: 维护成本低, 数据多
  - 缺点: 业务特性难体现

模式 2: 部分共享 (底座共享, 业务塔独立)
  - 适用: 业务差异较大
  - 优点: 兼顾共享 + 业务特性
  - 缺点: 复杂度高

模式 3: 完全独立 (每个业务一个模型)
  - 适用: 业务差异巨大
  - 优点: 灵活
  - 缺点: 维护成本高
```

### 6.2 特征共享

**特征共享原则**:

```text
1. 通用特征 (用户基础属性) → 全公司共享
2. 业务特征 (业务行为) → 业务内共享
3. 敏感特征 (涉及隐私) → 严格权限
```

**特征平台**:

```text
公司级特征平台 (Feast):
- 离线特征: Hive / Spark 计算
- 在线特征: KV / HBase 存储
- 特征服务: gRPC / RESTful
- 特征监控: 数据漂移 / 缺失率
```

### 6.3 复用与独立

**复用 vs 独立 决策树**:

```text
Q1: 业务相似吗?
  ├── 完全相似 → 完全复用
  ├── 部分相似 → 部分复用
  └── 完全不同 → 完全独立

Q2: 团队预算够吗?
  ├── 够 → 独立
  └── 不够 → 复用

Q3: 时间紧吗?
  ├── 紧 → 复用
  └── 不紧 → 独立

Q4: 有平台支持吗?
  ├── 有 → 复用
  └── 没有 → 独立
```

**示例**:

```python
"""
OneRec 模型架构
================
基于 HSTU 的端到端生成式推荐架构.

参考:
- HSTU (Meta, 2024)
- OneRec (快手, 2024)

作者: 张三
创建: 2026-08-15
"""

class OneRec(nn.Module):
    def __init__(self, config):
        """
        初始化 OneRec 模型.

        Args:
            config: 模型配置, 包含 hidden_size, num_layers 等
        """
        super().__init__()
        # Token Embedding
        self.token_embedding = nn.Embedding(
            config.vocab_size, config.hidden_size
        )
        # Transformer 层
        self.layers = nn.ModuleList([
            TransformerBlock(config) for _ in range(config.num_layers)
        ])

    def forward(self, input_ids):
        """
        前向计算.

        Args:
            input_ids: [batch_size, seq_len]

        Returns:
            logits: [batch_size, seq_len, vocab_size]
        """
        # Embedding
        x = self.token_embedding(input_ids)
        # Transformer
        for layer in self.layers:
            x = layer(x)
        return x
```

```text
1. 结果 (30 秒): 一句话讲清楚结果
   "本周 OneRec 上线测试, CTR +1.2%"

2. 过程 (3 分钟): 关键节点 + 决策
   "测试中发现 X 问题, 通过 Y 解决..."

3. 展望 (1 分钟): 下一步 + 风险
   "下周预计全量上线, 需要关注延迟问题"
```

**汇报禁忌**:

```text
❌ 念 PPT
❌ 长篇大论
❌ 没有结论
❌ 没有数据
❌ 抱怨
❌ 推卸责任
```

## 10. 冲突管理

### 10.1 技术分歧

**3 种处理方式**:

```text
1. 数据说话: 用实验结果决策
2. 妥协方案: 各退一步, 找中间方案
3. 升级: 找更高层决策
```

**示例**:

```text
A 主张: "用 Self-Attention"
B 主张: "用 Cross-Attention"
A 的论据: "表达更强"
B 的论据: "延迟更优"
数据说话: 实验对比, AUC +0.3% vs 延迟 +5ms
决策: 取决于 P99 约束
```

### 10.2 资源冲突

**资源冲突场景**:

```text
- GPU 不够, 算法要跑实验, 工程要 serving
- 工程师不够, 多个项目并行
- 数据不够, 多个模型都想用
```

**解决方案**:

```text
1. 优先级排序 (OEC 优先)
2. 资源共享 (时分复用)
3. 公平调度 (轮流使用)
4. 资源扩展 (申请更多)
```

### 10.3 优先级分歧

**优先级决策树**:

```text
Q1: 哪个对业务影响最大?
  → 业务影响最大的优先

Q2: 哪个时间最紧?
  → 时间紧的优先 (避免延期)

Q3: 哪个 ROI 最高?
  → ROI 高的优先

Q4: 哪个涉及合规 / 安全?
  → 合规 / 安全优先
```

## 11. 真实案例

### 11.1 与 PM 沟通失败案例

**背景**: 算法工程师做完了, PM 不满意.

**问题**:

```text
1. 算法没问清楚需求就开做
2. 算法做完没主动同步
3. 算法用技术语言汇报, PM 听不懂
4. 上线后业务效果不好, PM 抱怨
```

**正确做法**:

```text
1. 需求阶段: 主动问 5W1H
2. 开发阶段: 每周同步进展
3. 汇报阶段: 用业务指标, 不用 AUC
4. 收尾阶段: 总结经验教训
```

### 11.2 跨团队合作成功案例

**背景**: OneTrans 项目跨 4 个团队.

**成功因素**:

```text
1. 早期拉通: 设计阶段就拉齐 4 个团队
2. 明确责任: 每个团队有明确接口人
3. 周会同步: 每周固定时间, 所有人参加
4. 文档先行: 设计文档评审通过后才动手
5. 风险预警: 提前暴露问题, 不藏着
6. 复盘总结: 项目结束做复盘
```

### 11.3 紧急故障协作案例

**背景**: 模型上线后 CTR 跌 10%.

**应急流程**:

```text
1. 发现: 监控告警 (5 分钟)
2. 拉群: 算法 + 工程 + SRE (3 分钟)
3. 排查: 数据 + 模型 + 服务 (20 分钟)
4. 决策: 回滚 / 修复 (10 分钟)
5. 执行: 回滚到上一版本 (5 分钟)
6. 验证: CTR 恢复 (10 分钟)
7. 复盘: RCA 报告 (24 小时)
```

**根因**: 特征 pipeline 配置错误, 导致缺失关键特征.

**教训**:

```text
1. 上线前必须全链路验证
2. 配置变更要走 code review
3. 关键路径必须有护栏指标
4. 回滚必须能在 5 分钟内完成
```

## 12. 与 RL/GR 团队协作

### 12.1 RL 团队

**协作场景**:

```text
1. 算法团队用 RL 做长期价值优化
2. 工程团队需要支持 RL 训练 / 推理
3. 数据团队需要支持 RL 数据流
```

**协作要点**:

```text
- RL 训练需要模拟环境, 数据团队支持
- RL 上线要谨慎, 有护栏指标
- RL 训练成本高, 需要算力支持
```

### 12.2 GR 团队

**协作场景**:

```text
1. 算法团队用生成式推荐 (HSTU / OneRec)
2. 工程团队需要支持 SID 生成 + 检索
3. 数据团队需要支持多模态特征
```

**协作要点**:

```text
- SID 生成要稳定, 离线在线一致
- 检索引擎要支持大规模 (Faiss / Milvus)
- 多模态特征需要 GPU 资源
- 推理延迟要严格控制
```

## 附录 C · 沟通失败案例集 (10 案例)

## C.1 需求理解错误

**场景**: 算法做了 PM 不要的功能.

**失败原因**:
- 算法没问清楚就开做
- 算法假设了 PM 的需求
- 算法没主动确认

**正确做法**:
- 主动问 5W1H
- 用自己的话复述需求, 确认理解
- 留出"需求澄清"环节

## C.2 跨团队责任不清

**场景**: 故障时, 算法说工程负责, 工程说数据负责.

**失败原因**:
- 责任边界没明确
- 接口人没确定
- 文档没记录

**正确做法**:
- 项目初期明确 RACI
- 每周同步
- 文档记录责任划分

## C.3 会议低效

**场景**: 1 小时会议, 30 分钟闲聊, 30 分钟正事.

**失败原因**:
- 没有议程
- 没有主持人
- 没有结论

**正确做法**:
- 提前发议程
- 主持人控制节奏
- 明确决策和行动项

## C.4 文档缺失

**场景**: 新人接手, 不知道怎么干.

**失败原因**:
- 没有 onboarding 文档
- 没有 runbook
- 没有架构图

**正确做法**:
- 新人必读文档清单
- runbook (操作手册)
- 架构图 + 数据流图

## C.5 沟通语言不通

**场景**: 算法讲 loss, PM 听不懂.

**失败原因**:
- 用技术语言沟通
- 没翻译成业务
- 高估对方技术背景

**正确做法**:
- 用业务指标 (CTR / GMV)
- 少用 jargon
- 多用图表

## C.6 时区沟通失败

**场景**: 海外团队, 中国同事下班前发消息, 美国同事早上看到.

**失败原因**:
- 没约定沟通时间
- 没文档化决策
- 没异步工具

**正确做法**:
- 约定 sync 时间
- 文档化所有决策
- 异步为主

## C.7 跨文化冲突

**场景**: 中国同事很直接, 国外同事觉得太 aggressive.

**失败原因**:
- 文化差异
- 没意识到
- 没调整

**正确做法**:
- 了解对方文化
- 调整沟通风格
- 多用 "please" / "thank you"

## C.8 紧急情况沟通失败

**场景**: 故障时, oncall 没及时响应.

**失败原因**:
- 告警没收到
- 责任人不清楚
- 升级路径不明

**正确做法**:
- 告警机制 (PagerDuty)
- 明确 oncall 排班
- 清晰升级路径

## C.9 文档评审走过场

**场景**: 评审会没人看, 走个过场.

**失败原因**:
- 时间紧, 没提前看
- 文档质量差
- 没激励评审

**正确做法**:
- 提前 24 小时发文档
- 文档质量检查清单
- 评审纳入 OKR

## C.10 拒绝需求不当

**场景**: 算法拒绝 PM 需求, PM 觉得算法不配合.

**失败原因**:
- 直接说"做不了"
- 没给替代方案
- 没解释原因

**正确做法**:
- 解释原因
- 提供替代方案
- 共同决策

## 扩展 A · 沟通与跨团队协作 的可执行手册（2026-07-24）

### A.1 使用规则

1. 先选一个对象，不要同时打开整章；
2. 先写假设和约束，再选择方法或工具；
3. 每次只改变一个主要变量，保留原始证据；
