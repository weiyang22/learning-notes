# 9-项目展示与技术影响力

> **定位**: 算法工程师的"硬通货手册", 把"做过的项目"变成"升职加薪的资本"
> **适用**: 算法工程师 / 研究员, 想搞清楚"怎么把项目讲好"
> **风格**: 场景 + 模板 + 案例 + 检查表, 一份文档讲透"项目怎么秀"

---

## 0. 一句话总结

**项目展示 = 你的职场简历**. 不会讲 = 没做. 会讲 = 加倍. 本文用 STAR + PPT 模板 + 24 篇论文实战案例, 让你从"做了说不出来"到"说得出来还做得好".

---

## 1. 为什么项目展示重要

### 1.1 晋升的硬通货

**真相**: 70% 的晋升失败不是能力不够, 是"不会讲".

```text
晋升失败的 5 大原因:
1. 项目做得不错, 但讲不清楚 (40%)
2. 业务结果不清晰 (25%)
3. 数据不可信 (15%)
4. 评委挑战 (10%)
5. 其他 (10%)
```

**为什么**:
- 评委不了解你, 只能从"你说的"判断
- 时间有限 (通常 30 分钟), 必须精炼
- 表达 = 影响力的核心

### 1.2 求职的核心

**真相**: 面试 90% 是项目展示.

```text
面试评分:
- 项目展示: 40%
- 算法题: 30%
- 系统设计: 20%
- 行为面试: 10%
```

**为什么**:
- 项目展示是面试官了解你的核心窗口
- 不会讲 = 做了等于没做
- 讲得好 = 能力 +10%

### 1.3 行业影响力的基础

**真相**: 行业影响力 = 1 个有影响力的项目 × 100 次分享.

```text
行业影响力公式:
影响力 = 项目影响力 × 传播次数

举例:
- 一个 OneTrans 项目, 价值 100
- 如果只在团队内讲: 影响力 = 100 × 5 = 500
- 如果在 KDD 讲: 影响力 = 100 × 1000 = 100,000
```

## 2. 项目展示的 4 类场景

### 2.1 晋升答辩

**特点**:
- 时间紧 (30 分钟)
- 评委多 (3-5 个)
- 评委不一定懂你的业务
- 必须讲结果 + 业务影响

**关键点**:
- 业务结果量化 (CTR +X%, GMV +Y%)
- 跨团队影响 (被 N 个团队复用)
- 创新性 (新模型 / 新方法)
- 个人贡献清晰

### 2.2 求职面试

**特点**:
- 时间紧 (15-20 分钟)
- 面试官关心"能不能干活"
- 必须讲结果 + 个人能力

**关键点**:
- STAR 法则 (Situation/Task/Action/Result)
- 个人贡献清晰 (不是团队)
- 业务结果量化
- 与目标岗位相关

### 2.3 行业分享

**特点**:
- 时间 30-60 分钟
- 受众是行业同行
- 必须讲方法 + 思考

**关键点**:
- 行业痛点 (受众关心的)
- 解决思路 (你的创新)
- 实验设计 (严谨)
- 反思与展望

### 2.4 内部技术分享

**特点**:
- 时间 30-60 分钟
- 受众是公司内同行
- 必须讲结果 + 经验

**关键点**:
- 业务背景
- 技术方案
- 实验结果
- 经验教训

## 3. 项目选择策略

### 3.1 选择标准

**3 大标准**:

| 标准 | 权重 | 说明 |
|------|------|------|
| **影响** | 40% | 业务结果 + 复用范围 |
| **难度** | 30% | 技术新颖 + 复杂 |
| **通用性** | 30% | 可推广 + 可借鉴 |

**具体问题**:
1. 这个项目影响了多少人? 多少业务?
2. 业务结果量化了吗? (CTR +X% / GMV +Y%)
3. 技术有什么创新? (新模型 / 新方法)
4. 别人能复用吗? (怎么复用)
5. 你的个人贡献是什么? (不是团队的)

### 3.2 5 类典型项目

#### 类型 1: 新模型上线

**特点**:
- 业务提升明确
- 技术难度中等
- 个人贡献清晰

**适合场景**: 晋升答辩 + 求职面试

**示例**:
- OneTrans 异构 Transformer 上线
- DIN 改造 DIEN 上线
- MMoE 多任务模型上线

#### 类型 2: 工程平台建设

**特点**:
- 长期价值高
- 影响范围广
- 个人贡献明确

**适合场景**: 晋升答辩 (P7+)

**示例**:
- 特征平台 v2.0
- 训练平台 Triton
- 推理优化 vLLM 集成

#### 类型 3: 架构升级

**特点**:
- 技术难度高
- 业务影响大
- 风险高, 收益大

**适合场景**: 晋升答辩 + 行业分享

**示例**:
- 召回架构升级 (双塔 → HSTU)
- 排序架构升级 (DIN → OneTrans)
- GR 架构升级 (DLRM → 生成式)

#### 类型 4: 业务增长

**特点**:
- 业务结果突出
- 技术含量中等
- 业务 owner 感

**适合场景**: 晋升答辩 + 求职面试

**示例**:
- 新业务 0→1 算法建设
- 直播推荐 GMV +50%
- 跨境电商新场景

#### 类型 5: 行业输出

**特点**:
- 行业可见度高
- 长期价值高
- 个人品牌

**适合场景**: P8+ 晋升

**示例**:
- 1 篇顶会论文
- 1 个开源项目
- 1 次行业大会演讲

## 4. 晋升答辩 PPT 模板 (10 页)

```text
页 1: 封面

```

### 4.2 项目背景 (第 4 页)

**模板**:
```markdown
## 项目 X: XXX

### 业务背景
- 业务: 抖音 Feeds
- 规模: 8 亿 DAU, 日均 100 亿次曝光
- 现状: 现有架构是 X, 存在 Y 问题

### 核心痛点
- 痛点 1: 用户兴趣建模不够精准
- 痛点 2: 模型迭代成本高
- 痛点 3: 长尾物品曝光不足

### 业务机会
- 如果解决, 预计提升: CTR +X%, GMV +Y%
- 投入: N 人月, M GPU 月
```

### 4.3 目标与挑战

```markdown
## 项目 X: XXX - 技术方案

### 方案思路
- 调研了 24 篇规模化排序论文
- 决定借鉴 LLM 的异构参数化思想
- 设计 OneTrans 统一架构

### 关键技术
1. **Unified Tokenizer**: 所有特征 token 化
2. **Mixed Parameterization**: 序列共享 Q/K/V/FFN, 非序列 token-specific
3. **Pyramid Schedule**: 浅层宽, 深层窄
4. **Cross-Request KV Cache**: 跨请求共享

### 与 baseline 对比
| 指标 | DIN | DIEN | OneTrans |
|------|-----|------|----------|
| AUC | 0.745 | 0.752 | **0.768** |
| 延迟 (P99) | 28ms | 32ms | **27ms** |
| 训练时间 | 6h | 8h | **5h** |
```

### 4.5 实施过程

```markdown
## 项目 X: XXX - 实施过程

### 时间线
- W1-W2: 调研 + 选型

- W5-W8: 工程化 + 部署
```

## 5. 求职简历的项目展示

### 5.1 STAR 法则

```text
S (Situation):  业务背景 (3 句)
T (Task):       我的职责 (2 句)
A (Action):     我做了什么 (5-7 句, 具体)
R (Result):     量化结果 (3 句)
```

**示例**:
```markdown
S: 抖音电商需要给 10 亿用户推商品, 召回通道只有协同过滤, 新品 0 曝光.
T: 我负责召回通道扩充, 主攻向量召回.
A: 我调研了 Faiss / Milvus, 设计了双塔模型 (User Tower + Item Tower),
   训练用了 100 亿样本, 负采样 1:5, 用了 temperature-scaled softmax,
   部署用了 Faiss IVF-PQ 索引 (10 亿向量).
R: 召回 hit rate 提升 15%, 新品曝光从 0 → 30%, GMV 提升 8%.
```

### 5.2 项目分类

**简历上通常分 3 类**:

#### 类别 1: 主导项目 (1-3 个)

```markdown
### 抖音 Feeds 推荐系统升级 (2024-2025)
主导推荐架构升级, 借鉴 LLM 异构参数化, 设计 OneTrans.
- **技术**: 异构 Transformer + KV-Cache + Pyramid Schedule
- **业务**: CTR +14.6%, GMV +13.1%, p99 -3.6%
- **影响**: 全公司 4 个业务线复用
```

#### 类别 2: 参与项目 (2-3 个)

```markdown
### 美团外卖多场景排序 (2023-2024)
参与多任务架构, 用 MMoE + PLE 解决任务冲突.
- **技术**: MMoE + PLE + 多任务调优
- **业务**: CTR 不降, GMV +3%, 任务冲突消失
```

#### 类别 3: 个人项目 / 开源 (1-2 个)

```markdown
### EasyRec 推荐框架 (开源)
维护 1 个开源推荐框架, Star 500+.
- 30+ contributors, 50+ 业务使用
- https://github.com/alibaba/EasyRec
```

### 5.3 数据呈现

**数据呈现 4 原则**:

1. **量化**: 用数字, 不用形容词
   - ❌ "显著提升"
   - ✅ "+14.6%"

2. **对比**: 用 baseline, 不用绝对值
   - ❌ "CTR 9.4%"
   - ✅ "CTR +14.6% (从 8.2% 到 9.4%)"

3. **业务**: 用业务指标, 不用技术指标
   - ❌ "AUC +0.5%"
   - ✅ "GMV +13.1%"

4. **范围**: 用影响范围, 不用局部
   - ❌ "这个团队用得不错"
   - ✅ "全公司 4 个业务线复用"

## 6. 案例库 (基于 24 篇 GenRec 论文)

> 用 24 篇论文作为案例, 演示"项目展示"怎么做. 每个项目都有 STAR 模板 + PPT 模板.

### 6.1 OneRec 项目的展示模板 (快手)

#### STAR 案例

```markdown
S: 快手电商有 3 亿用户, 1000 万商品, 传统多阶段 (召回+粗排+精排) 架构维护成本高, 信息断裂严重.
T: 我负责设计端到端生成式推荐架构, 减少阶段, 提升效果.
A: 我调研了 24 篇 GR 论文 (HSTU / OneRec / TIGER), 借鉴 NLP 的 Encoder-Decoder 范式:
   - 用 SID (Semantic ID) 表示商品
   - 用 Transformer 作为生成式模型
   - 用 beam search 解码 Top K
   - 用 constrained decoding 保证有效性
R: 在线 A/B 实验: CTR +5.2%, GMV +3.8%, 维护成本 ↓50%.
   推广到 3 个业务线 (电商 / 本地生活 / 海外).
```

#### PPT 5 页结构

```text
页 1: 项目名称 + 一句话
页 2: 业务背景 + 痛点 (传统架构)
页 3: OneRec 架构 (SID + Transformer + Beam Search)
页 4: 实验结果 (CTR / GMV / 维护成本)
页 5: 复用 + 反思 + 展望
```

#### 关键展示点

1. **创新性**: 端到端生成式, 不是小修小补
2. **业务结果**: CTR +5.2%, GMV +3.8%
3. **复用性**: 3 个业务线复用
4. **方法论**: 跨论文对比 + 借鉴 NLP

### 6.2 HSTU 项目的展示模板 (Meta)

#### STAR 案例

```markdown
S: Meta 推荐有 10B 用户, 长行为序列 (10K+), 现有 DLRM 序列建模不够.
T: 我负责设计新一代序列建模架构, 满足 scaling law.
A: 我设计了 HSTU (Hierarchical Sequential Transduction Unit):
   - 稀疏 attention (替代 self-attention)
   - 共享参数 (跨用户 / 跨物品)
   - 1.5T 参数规模化训练
   - M-FALCON 微批处理推理
R: 比 DLRM 在线 +12%, 比 Transformer 节省 100x 训练 cost.
   Meta 内部 5 个产品线复用.
```

#### 关键展示点

1. **规模**: 1.5T 参数, 业界最大
2. **创新**: 稀疏 attention + 共享参数
3. **业务**: +12% 在线
4. **效率**: 节省 100x 训练 cost

### 6.3 RL 项目的展示模板 (RecSys)

#### STAR 案例

```markdown
S: 推荐系统只优化短期 CTR, 但用户长期价值 (LTGM) 被忽略, 长期留失率上升.
T: 我负责引入强化学习, 优化长期价值.
A: 我调研了 Bandit / PPO / DPO 方案, 设计了混合架构:
   - 短期目标: 用 CTR 排序
   - 长期目标: 用 DPO 训练
   - 探索利用: UCB + Thompson Sampling
   - 在线学习: FTRL 增量更新
R: 7 日留存 +2%, LTGM +5%, CTR 持平.
   用户体验主观评分 +10%.
```

#### 关键展示点

1. **问题**: 长期价值 vs 短期 CTR
2. **方案**: 强化学习 (Bandit + DPO)
3. **业务**: 7 日留存 +2%
4. **创新**: 短期 + 长期混合

### 6.4 STCA 项目的展示模板 (字节)

#### STAR 案例

```markdown
S: 抖音 Feeds 用户行为 10K+, 标准 Self-Attention 计算不可行 (单卡 OOM).
T: 我负责长序列建模, 满足 P99 < 30ms 约束.
A: 我分析了 Self-Attention 二次复杂度的本质, 设计了 Cross-Attention 替代:
   - Target-History Cross-Attention O(L·d)

R: 端到端带宽 ↓84%, 吞吐 2.2×, PS CPU 减半, 替换 TWIN-10K 检索增强层.
```

#### 关键展示点

1. **挑战**: 10K 长序列, Self-Attention OOM
2. **创新**: Cross-Attention 替代
3. **工程**: 端到端带宽 ↓84%
4. **复用**: 替换原 TWIN-10K 层

### A.1 使用规则

1. 先选一个对象，不要同时打开整章；
