# 04-如何理解设计取舍 - 工业推荐的核心 Trade-off 矩阵

> **核心**: 没有"最优"架构, 只有"在某种约束下的最优"
> **框架**: 5 个核心取舍维度 × 决策树
> **案例**: 24 篇论文的取舍分析 + 3 个深度案例

---

## 0. 一句话总结

**设计取舍 = 在多个互相冲突的目标间找平衡**. 工业推荐有 5 个核心维度, 每个维度都有明确的取舍方向. 理解取舍 = 理解为什么方案"长成那样".

---

## 1. 工业推荐的 5 个核心取舍维度

### 1.1 维度 1: 效果 vs 效率 (Quality vs Efficiency)

| 维度 | 追求效果 | 追求效率 |
|------|---------|---------|
| **指标** | AUC / NDCG / 业务指标 | MFU / FLOPs / 延迟 / 内存 |
| **典型选择** | Attention, 大模型 | Token Mixer, 量化, 剪枝 |
| **代表论文** | HSTU, OneTrans | RankMixer, NEZHA |

**典型取舍**:
- 用 Token Mixer 替代 Attention: 损失全局建模, 提升 MFU 10x
- 用 INT8 量化: 精度损失 1%, 显存减少 4x
- 用 grouped GEMM: 实现复杂, 训练快 2x

### 1.2 维度 2: 通用性 vs 专用性 (General vs Specific)

| 维度 | 追求通用性 | 追求专用性 |
|------|-----------|-----------|
| **指标** | 跨场景泛化能力 | 单一场景最优 |
| **典型选择** | LFM, MTGR, OneRec | TokenMixer-Large, SMES |
| **代表论文** | LFM4Ads, MTGR | STORE, SORT |

**典型取舍**:
- 用 LFM 跨广告 + 内容: 跨任务负迁移风险
- 用单一业务专用模型: 资源浪费, 难维护

### 1.3 维度 3: 复杂度 vs 可维护性 (Complexity vs Maintainability)

| 维度 | 追求性能 | 追求可维护 |
|------|---------|-----------|
| **指标** | AUC, 业务 | 代码简洁, 易调试 |
| **典型选择** | 多模块组合, MoE | 单一大模型 |
| **代表论文** | MTmixAtt, TokenMixer-Large | OneRec V2 |

**典型取舍**:
- 用混合 MoE (共享 + 场景): 性能好, 代码复杂
- 用单一 Decoder: 代码简单, 容量上限受限

### 1.4 维度 4: 创新 vs 稳健 (Innovation vs Stability)

| 维度 | 追求新颖 | 追求稳健 |
|------|---------|---------|
| **指标** | SOTA, 论文 novelty | 风险可控, 可解释 |
| **典型选择** | 新架构, 新范式 | 在 SOTA 基础上微调 |
| **代表论文** | HSTU, TIGER | MDL (基于已有方案) |

**典型取舍**:
- 用全新 GR 范式: 风险大, 收益可能巨大
- 用 prompt tuning: 风险小, 收益有限

### 1.5 维度 5: 长尾 vs 头部 (Long-tail vs Head)

| 维度 | 关注长尾 | 关注头部 |
|------|---------|---------|
| **指标** | 覆盖率, 多样性 | 头部物品 CTR |
| **典型选择** | Memory Network, 探索 | MoE, 个性化 |
| **代表论文** | MSN (PKM), TIGER | HSTU, OneTrans |

**典型取舍**:
- 用 Memory Network: 个性化强, 适合长尾
- 用 MoE: 头部表现好, 长尾一般

## 2. 取舍分析框架

### 2.1 显式取舍 vs 隐式取舍

**显式取舍**: 作者在论文中明确说 "我们牺牲了 X 换取了 Y"

**隐式取舍**: 作者没说, 但架构选择暗含了取舍
- 例: 用 Token Mixer, 牺牲了全局建模, 换取了 MFU
- 例: 用 per-token MoE, 牺牲了通用性, 换取了参数效率

### 2.2 跨章取舍

一个选择可能影响多个维度:
- 选择 Token Mixer → 损失全局建模 (效果↓) + 提升 MFU (效率↑) + 代码更复杂 (可维护↓)

### 2.3 取舍决策树

```text
                    ┌─ 业务是头部还是长尾?
                    │
        ┌───────────┴──────────┐
        │                      │
    头部为主                长尾为主
        │                      │
        v                      v
    优先效果              优先多样性
        │                      │
        v                      v
    选 MoE / 大模型       选 Memory / 探索
        │                      │
        └──────────┬───────────┘
                   │
                   v
            是否有强延迟约束?
                   │
           ┌───────┴────────┐
           │                │
       有 (≤50ms)         无
           │                │
           v                v
      优先 NEZHA        优先 HSTU / GR
      投机解码          全栈 GR
           │                │
           └───────┬────────┘
                   │
                   v
            是否有跨场景需求?
                   │
           ┌───────┴────────┐
           │                │
       是                否
           │                │
           v                v
      选 OneRec          选 TokenMixer-Large
      / LFM4Ads         单一场景优化
```

## 4. 深度案例

### 4.1 案例 1: TokenMixer-Large 的取舍分析

**选择**: 在 TokenMixer 基础上, 用 Mixing-and-Reverting + Per-token MoE

**显式取舍** (作者明确说明):
- 牺牲: 一些通用性 (Per-token MoE 路由引入额外假设)
- 换取: 支持 7B-15B 深度稳定训练

**隐式取舍** (架构暗含):
- 牺牲: 训练稳定性 (深层训练本身就更难)
- 换取: 容量大幅提升 (15B 参数)

**效果**:
- 在线: +2.0% ADSS, +2.98% GMV, +1.4% 营收
- 工程师视角: 实现复杂, 但落地明确

### 4.2 案例 2: OneTrans 的取舍分析

**选择**: 序列 + 特征交互统一到一个 Transformer

**显式取舍**:
- 牺牲: 一些灵活性 (不能分别调优序列 vs 交互)
- 换取: 端到端优化 + 信息双向流动

**隐式取舍**:
- 牺牲: 工程复杂度 (异构参数化难实现)
- 换取: 训练 / 推理效率 (单一模型)

**效果**:
- 在线: +5.68% gmv/u (Feeds)
- 工程师视角: 复杂但有效

### 4.3 案例 3: MTGR 的取舍分析

**选择**: 保留 DLRM 交叉特征 + 用 HSTU 框架

**显式取舍**:
- 牺牲: 纯 GR 的简洁性
- 换取: 保留交叉特征带来的大幅性能提升

**隐式取舍**:
- 牺牲: 一些扩展性 (GR 与 DLRM 混合架构)
- 换取: 工业落地友好 (兼容现有 DLRM)

**效果**:
- 在线: +1.22% conversion (美团外卖)
- 工程师视角: 实用主义, 不追求理论纯粹

## 5. 工程师 vs 研究者的取舍偏好

| 维度 | 工程师 | 研究者 |
|------|--------|--------|
| **效果 vs 效率** | 优先效率 (生产约束) | 优先效果 (SOTA) |
| **通用 vs 专用** | 优先专用 (业务对症) | 优先通用 (普适性) |
| **复杂度 vs 可维护** | 优先可维护 (团队维护) | 优先性能 (技术新颖) |
| **创新 vs 稳健** | 优先稳健 (可上线) | 优先创新 (理论价值) |
| **长尾 vs 头部** | 优先头部 (业务大头) | 优先长尾 (公平性) |

**启示**:
- 工业论文通常在效率 / 可维护 / 稳健维度上更强
- 学术论文通常在效果 / 通用 / 创新维度上更强
- **优秀的工业研究者** 能在两者间找到平衡

## 6. 面试中的取舍讨论

### 6.1 常见面试题

1. "为什么不用 attention 替代你的 token mixer?"
2. "为什么不用更大的模型?"
3. "为什么不 end-to-end 训练?"
4. "推理延迟能接受吗?"

### 6.2 回答模板

```text
1. 明确取舍维度 (效率 vs 效果)
2. 说明当前选择的优势
3. 诚实承认代价
4. 给出未来改进方向
5. 用数字证明 (MFU, 延迟等)
```

**示例**:
> "我们用 Token Mixer 替代 Attention, 牺牲了一些全局建模能力, 换取了 MFU 从 4.5% 提升到 45%. 在我们的场景下, 长序列建模比全局 attention 更重要, 所以这个取舍是值得的."

## 10. 详细取舍分析: 24 篇论文 × 5 维度

### 10.1 TokenMixer-Large (ByteDance)

**显式取舍**:
- 牺牲: 通用性 (Per-token MoE 对场景敏感)
- 换取: 7B-15B 深度的稳定训练

**隐式取舍**:
- 牺牲: 实现复杂度 (Mixing-and-Reverting + MoE)
- 换取: 容量 + 效率双提升

**最终效果**:
- 在线 +2.98% GMV (电商), +2.0% ADSS (广告)
- 7B 模型 + INT8 量化部署

**5 维度评分**:
```text
效果: ●●  (中, 因为牺牲了通用性)
效率: ●●● (强, MFU 高)
通用: ●   (弱, 强场景化)
复杂: ●●● (高, 工程复杂)
创新: ●●● (强, Mixing-and-Reverting 新)

```

## 11. 如何在实施前估算取舍

### 11.1 4 个估算步骤

```text
Step 1: 列出候选方案 (3-5 个)
Step 2: 对每个方案, 在 5 维度上打分 (1-3)
Step 3: 加权求总分 (根据业务权重)
Step 4: 选 1-2 个最优方案
```

### 11.2 估算示例: 长序列建模方案选择

**候选方案**:
- A: Standard Attention (O(L²))
- B: Sparse Attention (O(L log L))
- C: Linear Attention (O(L))
- D: Mamba/SSM (O(L))

**5 维度评分**:

| 方案 | 效果 | 效率 | 可维护 | 通用 | 创新 | 加权总分 |
|------|------|------|--------|------|------|---------|
| A    | 3    | 1    | 3      | 3    | 1    | 11 |
| B    | 3    | 2    | 2      | 2    | 2    | 11 |
| C    | 2    | 3    | 3      | 2    | 2    | 12 |
| D    | 2    | 3    | 1      | 2    | 3    | 11 |

**结论**: C (Linear Attention) 加权最高, 是当前场景的最优选择

### 11.3 估算的 5 个陷阱

1. **维度权重不明确**: 不同场景权重差异大
2. **评分主观**: 评分应该基于历史数据, 不是直觉
3. **忽略长期成本**: 只看短期收益, 忽略长期维护成本
4. **忽略团队能力**: 再好的方案, 团队不会做也不行
5. **忽略业务时机**: 太超前的方案, 落地困难

### 11.4 取舍的"5 年后"视角

**问题**: 5 年后看, 当初的取舍还对吗?

**案例**: 2020 年, 很多团队选择 "小模型 + 复杂特征工程"
- 2020: 这个取舍是对的 (大模型还没成熟)
- 2025: 这个取舍可能是错的 (大模型已经证明效果更好)

**启示**: 取舍要保留"未来调整"的空间, 不要把所有资源都押在一个方向。

## 12. 糟糕取舍的失败案例

> 4 个真实 (虚构) 案例, 展示糟糕取舍的后果。

### 12.1 案例 1: "为了 1% 效果, 牺牲 50% 维护性"

**背景**: 团队引入 5 种新组件, AUC 提升 1%, 但代码量翻倍
**后果**: 6 个月后, 没人能完整讲清楚架构, 新人上手 3 个月
**教训**: 复杂度边际收益递减, 1% 效果不值得 50% 维护成本

### 12.2 案例 2: "为了 SOTA, 牺牲业务价值"

**背景**: 团队花 3 个月在公开数据集刷到 SOTA, 但生产数据 AUC 不涨
**后果**: 业务方不满, 项目被砍
**教训**: 公开数据集 SOTA ≠ 业务价值

### 12.3 案例 3: "为了通用, 牺牲场景最优"

**背景**: 团队用 LFM 跨 10 个场景, 每个场景 AUC 都不如专用模型
**后果**: 业务方投诉, 退回专用模型
**教训**: "跨场景" 不是越多越好, 要看场景相似度

### 12.4 案例 4: "为了稳健, 牺牲创新"

**背景**: 团队 5 年都在 SOTA 基础上微调, 不敢尝试新架构
**后果**: 竞品 (字节/快手) 推出 GR 范式, 落后一代
**教训**: 过度稳健 = 落后, 要保留 10-20% 资源探索新方向

### 12.5 失败案例的 5 个共性

| 共性 | 描述 |
|------|------|
| **单一指标优化** | 只看一个指标, 牺牲整体 |
| **过度复杂** | 5 个组件堆叠, 边际收益递减 |
| **脱离业务** | 学术 SOTA 不等于业务价值 |
| **过度保守** | 5 年没创新, 落后一代 |
| **忽略维护** | 性能好但团队维护不了 |

## 13. 如何向非技术 stakeholder 解释取舍

### 13.1 为什么需要解释

- 业务方不懂技术细节, 但需要理解 "为什么这么做"
- 老板关心 ROI, 不关心 AUC
- PM 关心业务影响, 不关心架构

### 13.2 翻译模板

```text
技术语言 → 业务语言

"AUC 提升 1%" → "用户点击率提升 1%, 约等于每月 X 万元 GMV"

"MFU 提升 10x" → "GPU 成本降低 90%, 每月节省 X 万元"

"延迟从 100ms 降到 30ms" → "用户看到推荐的速度快 3 倍, 用户体验提升"

"模型从 1B 扩到 7B" → "对用户兴趣的理解更深, 但需要 7x GPU 成本"

"scaling 实验" → "在更大的规模下验证效果, 为未来 3 年做准备"
```

### 13.3 5 个具体场景的翻译

| 技术方案 | 业务翻译 |
|---------|---------|
| 用 Token Mixer | "我们用更高效的架构, 同样效果但成本降低 50%" |
| 用 MoE 扩展参数 | "我们用稀疏激活, 模型容量提升 7x, 但推理成本不变" |
| 用 GR 范式 | "我们用统一架构, 召回+排序都用一个模型, 维护成本降低" |
| 用 Quantization | "我们用 INT8 量化, 显存减半, 服务器数量减半" |
| 用 Speculative Decoding | "我们用投机解码, 用户看到的推荐速度提升 30x" |

### 13.4 解释的 3 条原则

1. **用业务指标**: GMV / CTR / 延迟 / 成本, 而不是 AUC / MFU
2. **用对比**: "原来 X, 现在 Y, 业务影响 Z"
3. **诚实承认代价**: "我们牺牲了 X, 换取了 Y"

## 14. 量化取舍分析: 5 个方法

### 14.1 方法 1: 成本-收益矩阵

```text
高收益高成本: 大模型 (HSTU 1.5T)
高收益低成本: TokenMixer-Large (7B, 效率高)
低收益高成本: 过度工程化
低收益低成本: 不做
```

### 14.2 方法 2: ROC 曲线分析

- 假设 5 个方案, 各自在 "效果 vs 效率" 平面上的点
- 画 ROC 曲线, 找 Pareto front
- 选择 Pareto front 上的方案

### 14.3 方法 3: 边际收益分析

- 每次改进 (新增组件 / 增加参数) 的边际收益
- 当边际收益 < 阈值时, 停止改进

**例子**: TokenMixer-Large
- 1B → 4B: +1% AUC
- 4B → 7B: +0.5% AUC
- 7B → 15B: +0.2% AUC
- → 7B 是最优 (边际收益临界点)

### 14.4 方法 4: 多目标优化

- 把 5 个维度转化为权重
- 用 NSGA-II 等多目标优化算法
- 找 Pareto 最优解

### 14.5 方法 5: A/B 测试验证

- 把多个方案同时 A/B
- 看实际业务指标
- 选择综合指标最好的

## 15. "违反"常见取舍的成功案例

> 大多数情况下, 一些取舍是"常识"。但有些方案, 通过创新方法, 成功"违反"了常识。

### 15.1 "违反" 1: 用更复杂架构, 反而更快

**常识**: 复杂架构 = 慢
**违反**: TokenMixer-Large 用 MoE 扩展参数, 但用稀疏激活保持推理速度
**关键**: 稀疏激活让"复杂"不等于"慢"

### 15.2 "违反" 2: 跨场景反而提升单场景

**常识**: 通用 = 单场景弱化
**违反**: LFM4Ads 用 LFM 跨广告+内容, 每个场景都提升
**关键**: 跨场景有"协同效应"时, 通用反而更好

### 15.3 "违反" 3: 增加参数, 推理更快

**常识**: 大模型 = 慢
**违反**: HSTU 的稀疏 attention + 大参数, 反而比小模型快 (因为更好地捕捉长依赖, 减少重排)
**关键**: 架构创新让"大"不等于"慢"

### 15.4 "违反" 4: 增加复杂度, 反而更好维护

**常识**: 复杂 = 难维护
**违反**: OneRec 用端到端 GR, 统一架构反而比"分离架构"更好维护
**关键**: 统一的"复杂度"比"分离的多模块"更容易维护

### 15.5 "违反" 5: 创新方案, 反而更稳健

**常识**: 新方案 = 高风险
**违反**: TIGER 的"生成式检索", 在冷启动上比传统双塔更稳健
**关键**: 新方案针对的是"传统方案的痛点", 所以反而更稳健

### 15.6 违反取舍的 3 个条件

1. **找到"传统方案"的痛点**: 你的方案要解决一个真问题
2. **有技术创新**: 不是简单堆砌, 而是有真正的创新
3. **验证有效**: 用实验证明你的方案在多个维度上都好

## 16. 取舍的 5 个反模式

### 16.1 反模式 1: "过度优化单一维度"

**症状**: 只看 AUC, 不看延迟 / 成本
**后果**: 上线困难
**修正**: 用 5 维度框架评估

### 16.2 反模式 2: "默认当前范式"

**症状**: 因为"大家都这么做", 所以也这么做
**后果**: 错过范式转换
**修正**: 每年至少 1 次范式扫描

### 16.3 反模式 3: "复杂度爆炸"

**症状**: 5 个组件堆叠, 每个都说有用
**后果**: 维护成本指数增长
**修正**: 复杂度收益递减原则

### 16.4 反模式 4: "过度通用"

**症状**: 一个模型服务 10 个业务
**后果**: 每个业务都不是最优
**修正**: 通用 vs 专用要权衡

### 16.5 反模式 5: "只看短期"

**症状**: 优化 1 个项目, 不看长期影响
**后果**: 技术债累积
**修正**: "5 年视角"原则

## 17. 决策树: 5 类典型场景的取舍指南

### 17.1 场景 1: "我有一个新想法, 但和当前架构不兼容"

**取舍**:
- 选项 A: 改造当前架构, 集成新想法
- 选项 B: 在新模块独立实验, 验证有效再集成
- 选项 C: 抛弃新想法, 继续优化当前架构

**决策**: B 通常最优 (PoC 验证)

### 17.2 场景 2: "老板要业务指标, 但优化空间有限"

**取舍**:
- 选项 A: 强优化, 牺牲长期可维护性
- 选项 B: 渐进优化, 接受短期有限
- 选项 C: 寻找新方向, 用创新换收益

**决策**: B 通常最优 (可持续)

### 17.3 场景 3: "竞品做了 GR, 我们要不要跟?"

**取舍**:
- 选项 A: 立即跟进, 投入大量资源
- 选项 B: 调研 + 评估, 决定是否适合
- 选项 C: 等竞品验证, 再决定

**决策**: B 通常最优 (避免盲目)

### 17.4 场景 4: "我们的模型越来越大, 推理太慢"

**取舍**:
- 选项 A: 量化 (INT8 / INT4)
- 选项 B: 蒸馏 (大模型教小模型)
- 选项 C: 投机解码 (NEZHA 方案)
- 选项 D: 架构改造 (用更高效的架构)

**决策**: 视场景而定, 通常 A + B 组合

### 17.5 场景 5: "团队有 5 个研究方向, 资源只够 2 个"

**取舍**:
- 选项 A: 按 ROI 排序, 选 Top 2
- 选项 B: 按"对核心硬核的贡献"排序
- 选项 C: 按"团队能力匹配度"排序

**决策**: A + B 组合

## 21. 取舍的"暗黑模式": 5 类隐藏取舍

> 有些取舍是"显式"的, 作者会写在论文里。但有些取舍是"隐藏"的, 作者不说但实际做了。

### 21.1 隐藏取舍 1: "数据集取舍"

**现象**: 论文选了对方法有利的数据集
**例子**: TIGER 在 Amazon Reviews 上的提升, 可能因为数据集稀疏
**识别**: 主动看数据集的统计特性 (用户数 / 物品数 / 稀疏度)

### 21.2 隐藏取舍 2: "baseline 取舍"

**现象**: 论文选了对自己有利的 baseline
**例子**: 论文不报告弱 baseline 的结果
**识别**: 自己实现最强的 baseline, 不要信论文的 baseline

### 21.3 隐藏取舍 3: "超参取舍"

**现象**: 论文只报告最优超参的结果, 不报告平均
**例子**: 某个组件在精心调参后 +2%, 但在普通调参下可能 +0.5%
**识别**: 自己做 sensitivity analysis, 不要信论文的"最优超参"

### 21.4 隐藏取舍 4: "评估指标取舍"

**现象**: 论文选了对方法有利的指标
**例子**: 论文报告 NDCG, 但 NDCG 对长尾物品更敏感
**识别**: 看多个指标 (AUC / NDCG / Recall / Hit Rate)

### 21.5 隐藏取舍 5: "工程实现取舍"

**现象**: 论文的方法依赖特殊硬件 / 框架
**例子**: 某个 MoE 实现只在 H100 上高效
**识别**: 看方法对硬件的依赖, 评估自己的硬件能否跑

### 21.6 暗黑模式的应对

- **永远自己验证**: 不要完全信论文
- **看多个数据集**: 不要只用一个数据集
- **看多个指标**: 不要只看一个指标
- **看完整代码**: 论文没说清的实现细节, 看代码

## 22. 取舍的"动态调整"

> 取舍不是一次性的, 而是动态的。随着业务 / 技术 / 团队的变化, 取舍也要调整。

### 22.1 触发取舍调整的 5 类事件

1. **业务变化**: 新业务 / 新场景 / 新用户群
2. **技术变化**: 新硬件 / 新框架 / 新算法
3. **团队变化**: 新人加入 / 老人离开
4. **竞争变化**: 竞品推出新方案
5. **成本变化**: GPU 价格 / 带宽成本

### 22.2 调整的 5 步流程

```text
1. 触发事件: ...
2. 现状评估: 当前取舍是什么?
3. 重新评估: 5 维度评分是否变化?
4. 决策: 调整 / 不调整
5. 实施: 渐进调整, 不是翻天覆地
```

### 22.3 案例: TokenMixer-Large 的取舍动态调整

**初始取舍** (2024 Q1):
- 维度: 效果 vs 效率 → 偏向效率 (MFU 高)
- 决策: 用 Token Mixer, 不用 Attention

**触发事件** (2024 Q3):
- 业务变化: 抖音需要更长历史 (从 1K 到 10K)
- 技术变化: Flash Attention 2.0 发布, 速度提升 2x

**重新评估**:
- Token Mixer + 长序列: 效果提升但效率下降
- Attention + 长序列: 效果更好, 效率也够 (因为 Flash Attention 2.0)

**决策**: 维持 Token Mixer (因为已有 7B 部署), 但在下一版本考虑 attention 混合

**启示**: 取舍不是一次性的, 要持续评估

## 23. 取舍的"团队维度"

> 取舍不只是技术决策, 也是团队决策。

### 23.1 团队能力 vs 取舍

- 团队擅长 ML → 优先复杂模型
- 团队擅长工程 → 优先优化效率
- 团队小 → 优先简洁方案
- 团队大 → 优先通用方案

### 23.2 团队发展阶段 vs 取舍

| 团队阶段 | 推荐取舍 |
|---------|---------|
| **初创 (1-5 人)** | 优先简洁, 用 1 个模型服务所有 |
| **成长 (5-20 人)** | 优先专业化, 分场景分任务 |
| **成熟 (20+ 人)** | 优先统一, 跨场景跨任务 |

### 23.3 团队技术栈 vs 取舍

- 团队熟悉 PyTorch → 优先 PyTorch 生态方案
- 团队有 CUDA 经验 → 优先定制 kernel
- 团队用 Triton → 优先 Triton 优化

### 23.4 取舍的"组织级"考虑

- 跨团队复用 → 优先通用方案
- 团队隔离 → 优先专用方案
- 跨团队协作 → 优先标准化

## 24. 5 个"反直觉"取舍

> 下面 5 个取舍, 反直觉但有效。

### 24.1 反直觉 1: "用更大的模型, 推理更快"

**直觉**: 大模型慢
**事实**: HSTU 1.5T 反而比小模型快 (因为更好地捕捉长依赖, 减少重排)
**条件**: 当小模型需要更多"修复"操作时

### 24.2 反直觉 2: "用更复杂的架构, 更好维护"

**直觉**: 复杂难维护
**事实**: OneRec 统一架构反而比分离架构好维护
**条件**: 当"分离"导致接口混乱时

### 24.3 反直觉 3: "用更多的训练数据, 反而更稀疏"

**直觉**: 数据多 = 稠密
**事实**: 大数据下, 个性化反而更稀疏 (每个用户的偏好更精准)
**条件**: 当数据规模超过阈值时

### 24.4 反直觉 4: "用 MoE, 总参数大但推理快"

**直觉**: MoE 参数大 = 慢
**事实**: MoE 只激活部分参数, 推理 FLOPs 与小模型相当
**条件**: 当路由开销 < 节省的 FLOPs 时

### 24.5 反直觉 5: "用 quantization, 推理精度涨"

**直觉**: 量化损失精度
**事实**: 适度量化 (INT8) 反而可能涨精度 (因为正则化效果)
**条件**: 当模型过拟合时

5. 下季度要调整哪些取舍?

### 25.4 案例: 字节 5 年取舍演进

| 年份 | 关键取舍 | 当时理由 | 5 年后看 |
|------|---------|---------|---------|
| 2020 | DLRM 范式 | LLM 不成熟 | 错误 (错过 LLM) |
| 2021 | 双塔召回 | 简单稳定 | 错误 (GR 取代) |
| 2022 | Token Mixer | 效率高 | 正确 (HSTU 借鉴) |
| 2023 | GR 范式 | 跟 Meta | 正确 (字节核心) |
| 2024 | 15B 参数 | scaling law | 待验证 |

**启示**: 即使是顶级团队, 也有 ~50% 的取舍在 5 年后看是错的。

## 26. 取舍的"哲学层"

> 最后谈谈取舍的"为什么"。

### 26.1 取舍 = 价值观的体现

- 选效率 = 重视工程 / 重视落地
- 选效果 = 重视研究 / 重视创新
- 选通用 = 重视整体 / 重视复用
- 选专用 = 重视场景 / 重视精准
- 选稳健 = 重视风险 / 重视团队
- 选创新 = 重视未来 / 重视突破

### 26.2 不同角色的取舍偏好

| 角色 | 优先取舍 |
|------|---------|
| **工程师** | 效率 > 效果, 稳健 > 创新 |
| **研究者** | 效果 > 效率, 创新 > 稳健 |
| **PM** | 通用 > 专用, 业务 > 技术 |
| **老板** | 性价比 > 极致, ROI > 性能 |

### 26.3 优秀的取舍 = 兼顾

- 工程师 + 研究者: 既看效率, 又看效果
- 短期 + 长期: 既看眼前, 又看未来
- 局部 + 全局: 既看自己, 又看团队
- 业务 + 技术: 既看指标, 又看架构

### 26.4 取舍的"动态最优"

- 没有永远的"最优", 只有"当前最优"
- 3 个月看一次, 持续调整
- 不要陷入"沉没成本"陷阱

---

## 27. 一句话总结 (4 次)

> **设计取舍 = 在多目标冲突中找平衡**.

> **没有"最优"架构, 只有"在某种约束下的最优"**.

> **理解取舍 = 理解为什么方案"长成那样"**.

> **取舍 = 价值观 + 当前约束 + 5 年后视角**.

## 30. 常见错误案例 (6 个)

### 30.1 错误 1: "只看收益, 不看成本"

**症状**: 提案只写"提升 5%", 不写"代价是什么"。

**解决**: 强制"成本 3 问":
1. 算力 +X 倍?
2. 延迟 +Y ms?
3. 维护成本 +Z 倍?

### 30.2 错误 2: "只看平均, 不看长尾"

**症状**: 整体 +3%, 但头部 +5%, 长尾 -2%。

**解决**: 必报"分桶结果" (头部/中部/长尾)。

### 30.3 错误 3: "只看技术, 不看业务"

**症状**: 技术最优解, 业务无法上线。

**解决**: 业务约束写在第一行, 技术方案围绕业务。

### 30.4 错误 4: "只看论文推荐, 不看自己场景"

**症状**: 论文说"用 A", 我也用 A, 但我的场景不适合 A。

**解决**: 决策树第一问"业务约束是什么"。

### 30.5 错误 5: "只看短期, 不看长期"

**症状**: 短期 +2%, 但 6 个月后变成 -1% (数据漂移)。

**解决**: 必配"长效指标" (7 日留存 / LTGM)。

### 30.6 错误 6: "只听一方, 不听多 stakeholder"

**症状**: 只听 mentor 的, 没听 PM / 工程 / 运维。

**解决**: 重大决策必开 3 方对齐会。

### 32.2 取舍账本脚本

```python
# tradeoff.py
def tradeoff_score(plan, weights):
    # plan: dict with effect, cost, latency, maintain
    # weights: dict with same keys
    score = sum(plan[k] * weights[k] for k in plan)
    return score

# 例子
plan_a = {"effect": 2, "cost": 1.5, "latency": 30, "maintain": 2}
plan_b = {"effect": 3, "cost": 3.0, "latency": 50, "maintain": 3}
plan_c = {"effect": 1.5, "cost": 1.0, "latency": 20, "maintain": 1}
weights = {"effect": 0.4, "cost": 0.2, "latency": 0.2, "maintain": 0.2}

for p, name in [(plan_a, "A"), (plan_b, "B"), (plan_c, "C")]:
    print(f"Plan {name}: {tradeoff_score(p, weights):.2f}")
```
