# 05-如何设计实验 - 离线 + 在线 + 消融的完整框架

> **核心**: 一个方案"有效"需要 4 层证据: 离线 baseline / 在线 A/B / 消融 / Scaling
> **目的**: 把"我做了个东西"变成"我证明了一个东西"
> **案例**: 用 TokenMixer-Large 等 24 篇论文演示

---

## 0. 一句话总结

**实验设计 = 离线验证 + 在线 A/B + 消融归因 + Scaling 验证**. 4 层证据链缺一不可, 共同构成"我真的有效"的完整证明.

---

## 1. 实验设计的 4 类目标

### 1.1 验证有效性 (Does it work?)

**问题**: 我的方案在标准任务上比 baseline 好多少?

**指标**: AUC, NDCG, Recall@K, Logloss

**方法**: 标准数据集 + 强 baseline 对比

**示例** (HSTU):
- 公开数据集: +65.8% NDCG vs SASRec/BERT4Rec
- 工业数据集: +12.4% online

### 1.2 理解机制 (How does it work?)

**问题**: 哪些组件是关键的? 为什么有效?

**指标**: 消融后的 AUC delta

**方法**: 逐个组件去掉, 看损失

**示例** (TokenMixer-Large):
- Mixing-and-Reverting 去掉: -X% AUC (关键)
- Per-token MoE 去掉: -Y% AUC (重要)

### 1.3 量化收益 (How much gain?)

**问题**: 在生产环境能带来多少业务价值?

**指标**: CTR, CVR, GMV, RPM, 时长

**方法**: 在线 A/B 测试

**示例** (SORT, AliExpress):
- 在线 A/B: +6.35% 订单, +5.47% GMV, -45% 延迟

### 1.4 探索极限 (Where does it break?)

**问题**: 在什么规模 / 数据 / 场景下会失效?

**指标**: 不同参数 / 数据规模下的表现

**方法**: Scaling 实验

**示例** (HSTU):
- 1.5T 参数仍然有效
- Scaling 跨 3 个数量级

## 2. 离线实验设计

### 2.1 数据集选择

| 来源 | 优点 | 缺点 |
|------|------|------|
| **公开数据集** | 可复现, 易对比 | 规模小, 场景单一 |
| **工业数据集** | 真实场景, 大规模 | 不公开, 无法对比 |

**24 篇论文的数据集策略**:
- 全部使用工业数据集
- 部分 (如 Wukong) 也用 6 个公开数据集做对比
- 公开数据集用于 sanity check, 工业数据用于效果验证

### 2.2 数据划分

```text
时间分割:
  Train: 30 天前 - 7 天前
  Val:   7 天前 - 3 天前
  Test:  3 天前 - 今天

用户分割:
  Train users: 80%
  Val users:   10%
  Test users:  10%
```

**注意事项**:
- 严格时间分割 (避免数据穿越)
- 用户内 split (避免用户泄漏)

### 2.3 Baseline 选择

**三类 baseline**:
1. **弱 baseline**: 简单模型 (LR, FM)
2. **强 baseline**: 之前的 SOTA (DCN, AutoInt, DIN)
3. **同期 baseline**: 同时期 SOTA (MMoE, PLE)

**24 篇论文的 baseline 矩阵**:
| 论文 | 主要 baseline |
|------|-------------|
| TokenMixer-Large | RankMixer, Wukong, HiFormer, DHEN |
| HSTU | SASRec, BERT4Rec, GRU4Rec |
| MTGR | DLRM, HSTU |
| NEZHA | TAO, ... |

### 2.4 评估指标

| 指标 | 适用 | 含义 |
|------|------|------|
| **AUC** | 二分类 | 区分正负样本能力 |
| **GAUC** | 排序 | 用户内 AUC 加权 |
| **NDCG@K** | 排序 | 考虑位置折扣 |
| **Recall@K** | 检索 | 召回覆盖率 |
| **Logloss** | 校准 | 概率预测质量 |
| **CTR** | 业务 | 点击率 |
| **CVR** | 业务 | 转化率 |
| **GMV** | 业务 | 总交易额 |
| **RPM** | 广告 | 千次展示收入 |

## 3. 在线 A/B 实验设计

### 3.1 实验单位

| 单位 | 适用 | 注意事项 |
|------|------|---------|
| **用户 (UID)** | 个性化推荐 | 用户可能被分到不同实验 |
| **请求 (Request)** | 实时决策 | 同用户不同请求可能不同 |
| **物品 (Item)** | 内容排序 | 罕见 |

**24 篇论文**: 全部用 **用户级** A/B 实验

### 3.2 流量分配

| 流量 | 阶段 | 时长 |
|------|------|------|
| 1% | 初始灰度 | 1-3 天 |
| 5% | 监控稳定性 | 3-7 天 |
| 10% | 显著性检验 | 7-14 天 |
| 50% | 风险可控 | 14-30 天 |
| 100% | 全量 | 30+ 天 |

**24 篇论文的流量策略**:
- TokenMixer-Large: 7B 在线, 多种流量
- OneTrans: A/B 测试后全量
- STCA: 抖音全流量
- HSTU: 1.5T 全量

### 3.3 实验时长

| 类型 | 时长 | 注意事项 |
|------|------|---------|
| 短期 (1-7 天) | 新奇效应可能虚高 | 需要重复验证 |
| 中期 (1-4 周) | 平衡新奇和学习效应 | 大多数论文用这个 |
| 长期 (1-3 月) | 季节性 / 长期效应 | 重要决策需要 |

### 3.4 护栏指标

**核心指标** (越升越好): CTR, CVR, GMV
**护栏指标** (不能下降): 用户留存, 多样性, 公平性

**示例** (TokenMixer-Large):
- 核心: ADSS, GMV
- 护栏: 用户活跃天数 (没下降)

### 3.5 显著性检验

**统计方法**:
- t 检验: 连续指标
- 卡方检验: 离散指标
- 序检验: 多层实验

**24 篇论文**: 大多数直接报告百分比, 隐含假设"指标差异显著" (但没给 p-value)

## 4. 消融实验设计

### 4.1 组件消融

```text
完整模型 = A + B + C + D
去掉 A → AUC X%
去掉 B → AUC Y%
去掉 C → AUC Z%
去掉 D → AUC W%

结论: 最重要的是 B (去掉后损失最大)
```

**24 篇论文的消融示例**:
- TokenMixer-Large: 去掉 Mixing-and-Reverting, 去掉 Per-token MoE
- HSTU: 去掉 Pointwise Projection, 去掉 Gated MLP
- LFM4Ads: 去掉 User Tower, 去掉 Mix Tower

### 4.2 超参数消融

- 学习率: [1e-5, 1e-4, 1e-3]
- batch size: [256, 1024, 4096]
- 序列长度: [1K, 5K, 10K]
- 专家数量: [4, 8, 16, 32]

**24 篇论文**: 部分论文 (如 LFM4Ads) 有详细超参数消融

### 4.3 数据规模消融

- 训练数据: [10%, 50%, 100%]
- 用户数: [1M, 10M, 100M]
- 物品数: [100K, 1M, 10M]

### 4.4 消融的 8 个陷阱

1. **一次改太多变量**: 不知道哪个变了
2. **消融不完整**: 只消融明显组件, 隐藏组件没消融
3. **不消融 baseline**: 不知道 baseline 是否可优化
4. **消融不报告指标范围**: 只报 best, 不报 std
5. **消融基于过拟合配置**: 在最优配置上消融, 可能在其他配置上结论反转
6. **不消融正则项**: 学习率 / weight decay 等
7. **消融顺序不当**: 应该从大组件消融, 再到小组件
8. **不在生产数据上消融**: 公开数据集的消融结论可能不适用于生产

## 6. 实战: TokenMixer-Large 实验设计分析

### 6.1 数据集

- 离线: 抖音广告 / 电商 / 直播生产数据 (具体规模未公开)
- 在线: 三种业务流量

### 6.2 Baseline

- RankMixer-1B (广告)
- RankMixer-150M (电商)
- RankMixer-500M (直播)
- 之前 SOTA (Wukong, HiFormer, DHEN)

### 6.3 主要结果

| 场景 | 离线 AUC | 在线增益 |
|------|---------|---------|
| Feed Ads | +0.35% | **+2.0% ADSS** |
| E-Commerce | +0.51% | **+1.66% Order, +2.98% GMV** |
| Live Streaming | +0.7% UAUC | **+1.4% 营收** |

### 6.4 消融

作者隐含说明了几个组件的关键性:
- Mixing-and-Reverting: 关键 (深层稳定)
- Inter-Residual: 重要
- Per-token MoE: 重要

### 6.5 Scaling

| 场景 | 离线参数 | 在线参数 |
|------|---------|---------|
| Feed Ads | 15B | 7B |
| E-Commerce | 7B | 4B |
| Live Streaming | 4B | 2B |

## 7. 实验报告常见错误

### 7.1 错误 1: 报告"我们的方法更好" 但没说"在什么设置下"

**修正**: 明确说明 baseline 配置, 训练时长, 数据量

### 7.2 错误 2: 只报 best, 不报方差

**修正**: 跑 3-5 次, 报告均值和标准差

### 7.3 错误 3: 在线 A/B 时间太短

**修正**: 至少 7 天, 重要决策 30 天

### 7.4 错误 4: 消融不报告 baseline 的对应消融

**修正**: 同时消融 baseline, 看消融是否公平

### 7.5 错误 5: 只在公开数据集测, 不在生产测

**修正**: 公开 + 生产都测

```text
| 样本数 | AUC |
|--------|-----|
| 100M | 0.80 |
| 1B   | 0.83 |
| 10B  | 0.85 |
| 100B | 0.86 |

## 3. Scaling Law
- 公式: AUC = 0.78 + 0.02 * log(N) + 0.01 * log(D)
- N: 模型参数
- D: 数据量

## 4. 最优 Scaling
- 计算最优 (FLOPs 最少, 效果不降): 7B + 10B
- 收益递减点: 7B (再扩收益 < 1%)

- 资源充足: 15B
- 资源一般: 7B
- 资源紧张: 1B (用蒸馏)
```

## 11. A/B 测试详细规划指南

### 11.1 实验单位的选择

| 单位 | 适用 | 优缺点 |
|------|------|--------|
| **用户 (UID)** | 个性化推荐, 长期效果 | 个体稳定, 但样本少 |
| **请求 (Request)** | 实时决策, 短期效果 | 样本大, 但有用户串扰 |
| **物品 (Item)** | 内容排序 | 罕见使用 |

**24 篇论文**: 全部用 UID 级

### 11.2 样本量计算

**公式**:
```text
n = (Z_α/2 + Z_β)² × 2σ² / δ²

Z_α/2: 1.96 (α=0.05 双尾)
Z_β: 0.84 (power=0.8)
σ: 指标标准差
δ: 期望提升 (越小, 样本量越大)
```

**例子**:
- 指标 CTR 标准差 = 0.01
- 期望提升 1% (相对)
- 需要样本量: 10 万用户/天

### 11.3 流量分配策略

**单层实验**:
- 实验组 10% / 对照组 90% (节省资源)
- 实验组 50% / 对照组 50% (加快显著性)

**多层实验** (实验互不干扰):
- 层 1 (召回): 实验组 50%
- 层 2 (粗排): 实验组 10%
- 层 3 (精排): 实验组 10%

**互斥实验**:
- 同一层, 实验组之间互斥
- 用户在层 1 只能进 A 或 B

### 11.4 显著性检验方法

| 检验 | 适用 | 公式 |
|------|------|------|
| **t 检验** | 连续指标 (CTR, GMV) | t = (μ1 - μ2) / √(σ²/n) |
| **卡方检验** | 离散指标 (点击次数) | χ² = Σ(O - E)² / E |
| **Mann-Whitney U** | 非正态数据 | 排序比较 |
| **序检验** | 多层实验 | Bonferroni 校正 |

**p-value 解读**:
- p < 0.01: 极显著
- 0.01 ≤ p < 0.05: 显著
- p ≥ 0.05: 不显著

### 11.5 新奇效应 (Novelty Effect)

**定义**: 用户对新方案的短期好奇, 导致短期指标虚高

**例子**:
- A/B 第 1 天: +5% CTR
- A/B 第 7 天: +2% CTR
- A/B 第 30 天: +1.5% CTR (稳定)

**应对**:
- 长期 A/B (至少 14 天)
- 看第 7-14 天的指标, 而不是第 1 天
- 长期护栏指标更重要

### 11.6 季节性 / 长效效应

**定义**: 实验期内的特殊事件 (大促, 节假日, 季节变化)

**例子**:
- 6.18 大促期间: CTR 普遍上涨
- 春节前后: 用户行为变化大

**应对**:
- 避免在大促 / 节假日做 A/B
- 长期 A/B (1-3 个月)
- 对比同期历史数据

### 11.7 A/B 测试的 8 个陷阱

1. **流量太小**: 显著性不足
2. **时间太短**: 新奇效应未消退
3. **大促期间**: 异常数据
4. **不分组对照**: 混淆变量
5. **指标太多**: 多重比较问题
6. **互斥冲突**: 用户进了多个实验
7. **特征穿越**: 离线训练时用了未来信息
8. **Novelty 没考虑**: 短期虚高, 长期下降

## 12. 消融实验设计深入

### 12.1 消融的 5 个层次

| 层次 | 内容 | 例子 |
|------|------|------|
| **L1 模块消融** | 去掉整个模块 | 去掉 MoE |
| **L2 子模块消融** | 去掉模块的某个组件 | 去掉 MoE 的 load balance loss |
| **L3 超参消融** | 改变关键超参 | 专家数 8 vs 16 |
| **L4 数据消融** | 改变训练数据 | 用 50% 数据 |
| **L5 初始化消融** | 改变初始化 | 不同随机种子 |

### 12.2 消融顺序

```text
从大到小:
1. 先消融模块 (L1): 找关键模块
2. 再消融子模块 (L2): 找模块内关键组件
3. 再消融超参 (L3): 找关键超参
4. 最后消融数据 (L4): 看数据规模影响
```

### 12.3 消融报告模板

```text
| 消融 | AUC | Δ | 备注 |
|------|-----|---|------|
| 完整 | 0.85 | - | - |
| 去掉 Mixing | 0.80 | -5.9% | 关键 |
| 去掉 Reverting | 0.81 | -4.7% | 关键 |
| 去掉 Inter-Residual | 0.83 | -2.4% | 重要 |
| 去掉 MoE | 0.84 | -1.2% | 重要 |
| 去掉 Aux Loss | 0.848 | -0.2% | 可选 |

结论: Mixing + Reverting 是核心, 其他是补充
```

### 12.4 消融的 8 个陷阱 (重复说明 + 扩展)

| 陷阱 | 描述 | 解决 |
|------|------|------|
| **一次改太多** | 同时去掉 3 个组件 | 每次只去 1 个 |
| **不消融 baseline** | baseline 没消融 | baseline 也消融 |
| **只消融大组件** | 跳过小组件 | 全部组件都消融 |
| **不报告方差** | 只报 best | 报告 mean ± std |
| **过拟合配置** | 在最优超参上消融 | 多组超参下消融 |
| **不消融正则** | 跳过 LR / WD | 也消融超参 |
| **顺序不当** | 小组件先消融 | 大组件先消融 |
| **不在生产测** | 公开数据消融 | 生产数据也消融 |

### 12.5 消融中的"反直觉"现象

**现象**: 去掉某个组件后, AUC 反而上升

**可能原因**:
1. 该组件是有害的 (考虑移除)
2. 该组件与某超参耦合 (重新调参)
3. 训练数据本身的问题 (过拟合到特定 pattern)
4. 该组件在长序列才有用, 短序列看不出

**应对**:
- 不要立刻移除"看起来没用"的组件
- 多次运行, 看是否稳定
- 在不同数据集 / 场景下复现

## 13. 公平对比的 5 个原则

### 13.1 原则 1: 同样的训练数据

**含义**: baseline 和我们的方法用同样的数据
**反例**: baseline 用 100B 数据, 我们用 10B 数据 → 不公平

### 13.2 原则 2: 同样的训练时长

**含义**: 都训练到收敛, 或都训练固定时长
**反例**: baseline 训练 1 天, 我们训练 7 天 → 不公平

### 13.3 原则 3: 同样的超参调优时间

**含义**: baseline 和我们都调优到最优
**反例**: baseline 用默认超参, 我们精心调优 → 不公平

### 13.4 原则 4: 同样的评估指标

**含义**: 用同一个评估脚本, 同一个数据集划分
**反例**: baseline 用 AUC, 我们用 NDCG → 不公平

### 13.5 原则 5: 同样的硬件

**含义**: 在同样的 GPU / 同样的 batch size 下跑
**反例**: baseline 用 V100, 我们用 H100 → 不公平

### 13.6 公平对比的 8 个常见错误

| 错误 | 修正 |
|------|------|
| baseline 用老代码 | 用最新代码复现 |
| baseline 默认超参 | 精心调优 baseline |
| 我们用更多数据 | 同样数据 |
| 我们训练更久 | 同样时长 |
| 我们用更强 GPU | 同样硬件 |
| baseline 用 weak 版本 | 用最强版本 |
| 数据集划分不同 | 同样划分 |
| 评估脚本不同 | 同一脚本 |

## 14. 实验常见错误详解

### 14.1 错误 1: 数据穿越 (Data Leakage)

**含义**: 训练时用了未来信息

**例子**:
- 用第 30 天的标签, 训练第 1 天
- 用同一用户的未来行为
- 用全局统计 (包含测试集)

**检测方法**:
- 离线 AUC 远超在线 → 可能数据穿越
- 训练集和测试集分布差异大 → 可能泄漏

### 14.2 错误 2: 用户泄漏 (User Leakage)

**含义**: 同一用户既在训练集又在测试集

**例子**:
- 随机划分数据集 (没按用户)
- 跨场景用同一样本

**检测方法**:
- 检查用户 ID 是否跨集
- 用 GroupKFold

### 14.3 错误 3: 标签泄漏 (Label Leakage)

**含义**: 用了包含标签的特征

**例子**:
- 用了"点击数"作为特征预测点击率
- 用了"购买时间"作为特征预测购买

**检测方法**:
- 仔细审视每个特征的定义
- 训练时移除可疑特征, 看 AUC 变化

### 14.4 错误 4: 过拟合测试集

**含义**: 反复调参直到测试集上 AUC 高

**例子**:
- 调了 100 次超参, 每次看 test AUC
- 最终的 AUC 是过拟合的

**检测方法**:
- 用 val set 调参, 只用 test set 一次
- 多次运行不同 seed

### 14.5 错误 5: 不公平 baseline

**含义**: baseline 用弱版本

**例子**:
- baseline 用论文中的数字, 不自己复现
- baseline 用 5 年前的代码

**检测方法**:
- 自己实现最强 baseline
- 用开源实现 (如有)

### 14.6 错误 6: 报告"全网最佳"但不报告方差

**含义**: 跑 100 次, 报 best

**修正**: 报告 mean ± std (至少 3 次)

### 14.7 错误 7: 在线 A/B 短期

**含义**: 只跑 1-3 天

**修正**: 至少 7 天, 重要决策 30 天

### 14.8 错误 8: 不报告失败案例

**含义**: 只展示成功的实验

**修正**: 报告所有实验, 包括失败的

## 15. 统计显著性深入

### 15.1 p-value 的正确解读

**p < 0.05**:
- 含义: 在 5% 显著性水平下拒绝零假设
- 解读: 差异不太可能是随机产生的
- 注意: 不等于"差异很大", 只等于"差异存在"

**p > 0.05**:
- 含义: 不能拒绝零假设
- 解读: 差异可能是随机产生的
- 注意: 不等于"没有差异", 可能样本不够

### 15.2 显著性 vs 重要性

**显著性**: 差异是否存在 (统计学)
**重要性**: 差异有多大 (业务)

**例子**:
- 显著性: p < 0.01 (差异存在)
- 重要性: +0.1% CTR (业务无感)

**结论**: 显著性高, 重要性低, 业务上不需要应用

### 15.3 效应量 (Effect Size)

**Cohen's d**:
- d = (μ1 - μ2) / σ
- d > 0.8: 大效应
- d > 0.5: 中效应
- d > 0.2: 小效应

**CTR 例子**:
- μ1 = 5.0%, μ2 = 5.1%, σ = 0.5%
- d = 0.1 / 0.5 = 0.2 (小效应)
- 业务含义: 提升太小, 不值得全量

### 15.4 置信区间 (Confidence Interval)

**定义**: 真实提升可能落入的范围

**例子**:
- 报告: +2% CTR (95% CI: [1.5%, 2.5%])
- 解读: 真实提升很可能在 1.5%-2.5% 之间

**比单点报告更可信**

### 15.5 多重比较 (Multiple Comparisons)

**问题**: 实验多个指标, 至少一个会"偶然显著"

**修正**:
- Bonferroni 校正: p < 0.05/N (N 个指标)
- 控制 FDR (False Discovery Rate)

**例子**:
- 实验 10 个指标
- Bonferroni: p < 0.005 才算显著

### 15.6 序检验 (Sequential Testing)

**场景**: 持续监控 A/B 实验, 看到 p < 0.05 立即停止

**问题**: 多次检验累积 α 错误

**修正**:
- mSPRT (mixture Sequential Probability Ratio Test)
- Always Valid Inference

**工具**: Optimizely / Eppo 提供

### 15.7 24 篇论文的统计严谨性

| 论文 | p-value 报告 | 样本量计算 | 多次运行 |
|------|-------------|-----------|---------|
| HSTU | 否 | 否 | 否 |
| TokenMixer-Large | 否 | 否 | 否 |
| TIGER | 部分 | 否 | 部分 |
| LFM4Ads | 是 | 是 | 是 |

**观察**: 工业论文普遍缺乏严格的统计报告, 多凭经验判断。

## 16. 在约束下设计实验

> 实际工作经常遇到"资源不够 / 时间不够"的情况。

### 16.1 资源约束下的实验设计

**约束 1: 只有 1 张 GPU**
- 策略: 用小模型 + 小数据 + 快速 PoC
- 替代方案: 用 100M 参数 + 10M 样本, 验证假设

**约束 2: 只有 1 周时间**
- 策略: 减少实验数量, 选最关键 3 个
- 替代方案: 1 个离线 + 1 个在线 + 1 个消融

**约束 3: 没有生产流量**
- 策略: 用历史数据做 replay
- 替代方案: 用 30 天历史数据模拟

**约束 4: 团队只有 2 个人**
- 策略: 1 个人做实验, 1 个人分析
- 替代方案: 不要并行 5 个项目

### 16.2 时间约束下的优先级

**1 周能做的实验**:
- 1 个离线 PoC
- 1 个 baseline 对比
- 1 个超参扫描 (3-5 个点)

**1 个月能做的实验**:
- 1 个完整离线 (含消融)
- 1 个小流量在线 A/B
- 1 个 Scaling 实验

**3 个月能做的实验**:
- 1 个完整研究项目 (4 层证据链)
- 1 个上线方案

### 16.3 紧急情况下的实验设计

**场景**: 上线前发现 bug, 需要快速验证修复

**策略**:
- 1 小时: 单元测试 + 集成测试
- 1 天: 小流量 1% A/B
- 3 天: 5% A/B 验证
- 7 天: 10% A/B 显著性检验

**原则**: 不要跳步骤, 但可以缩短每步的时长

### 16.4 跨团队协调的实验设计

**问题**: 实验涉及 5 个团队 (算法 / 工程 / 产品 / 运营 / 数据)

**策略**:
- 算法: 设计实验
- 工程: 实现 + 部署
- 产品: 业务指标定义
- 运营: 流量协调
- 数据: 数据回流

**协调机制**:
- 每周同步会 (30 分钟)
- 共享实验文档
- 明确每个团队的 SLA

## 17. 实验设计的"反模式"

### 17.1 反模式 1: "盲目跑大量实验"

**症状**: 跑 100 个实验, 报告最好的 5 个
**问题**: 多重比较, 假阳性
**修正**: 先有假设, 再跑实验

### 17.2 反模式 2: "不报告负面结果"

**症状**: 只展示成功的实验
**问题**: 信息不完整, 别人无法学习
**修正**: 报告所有实验, 包括失败的

### 17.3 反模式 3: "调优到 test set"

**症状**: 反复调参, 直到 test AUC 高
**问题**: 过拟合 test set
**修正**: 用 val set 调参, test set 只用一次

### 17.4 反模式 4: "只用一个指标"

**症状**: 只看 AUC
**问题**: 其他指标可能下降
**修正**: 用多指标 (AUC + NDCG + Recall + 多样性)

### 17.5 反模式 5: "短期 A/B"

**症状**: 跑 1-3 天就下结论
**问题**: 新奇效应 / 季节性
**修正**: 至少 14 天

### 17.6 反模式 6: "不公平对比"

**症状**: baseline 用弱版本
**问题**: 我们的优势被夸大
**修正**: 自己实现最强 baseline

### 17.7 反模式 7: "线上线下不一致"

**症状**: 离线 AUC 涨, 在线 CTR 跌
**问题**: 数据 / 服务 / 特征不一致
**修正**: 定期对齐离线 + 在线

### 17.8 反模式 8: "忽略护栏"

**症状**: 只看核心指标, 不看护栏
**问题**: 用户体验变差, 长期掉留存
**修正**: 强制要求报告护栏指标

## 18. 实验报告的 10 个最佳实践

1. **明确说明 baseline**: 至少 3 个 baseline
2. **报告 mean ± std**: 至少 3 次运行
3. **公开数据集 + 工业数据**: 双重验证
4. **完整的消融表**: 每个组件都消融
5. **Scaling 验证**: 至少 4 个参数规模
6. **在线 A/B**: 至少 14 天
7. **护栏指标**: 至少 3 个护栏
8. **失败案例**: 报告失败的实验
9. **代码开源**: 长期价值
10. **数字 + 故事**: 不只是数字, 还有"为什么"

## 扩展 A · 实验设计框架 的可执行手册（2026-07-24）

> 本扩展围绕“用离线、在线、消融和Scaling四层证据回答方案是否有效、为何有效及何时失效”补充决策表、练习卡和复盘证据。它不替代正文，而是把正文转化为可以执行、检查和复用的工作单元。

### A.1 使用规则

1. 先选一个对象，不要同时打开整章；
2. 先写假设和约束，再选择方法或工具；
3. 每次只改变一个主要变量，保留原始证据；
4. 结论必须连接到一个指标、一个链接或一个可运行的最小例子；
5. 没有通过验证的内容，标记为“待证据”，不要写成确定事实。

### A.2 核心对象与证据门槛

| 编号 | 对象 | 首要动作 | 最小产出 | 状态 |

### 21.1 练习 1: 设计 1 个完整 A/B 实验

**目标**: 从假设 → 实验设计 → 上线, 完整走 1 遍。

```text
Day 1  写假设
  "在 [场景] 下, [方法 A] 比 [方法 B] 在 [指标] 上提升 ≥ [N]%"

Day 2  设计实验
  - 流量: 10% 实验, 10% 对照 (互斥)
  - 周期: 7 天 (含工作日 + 周末)
  - 护栏: CTR / 延迟 / 错误率
  - 显著性: p-value ≤ 0.05

Day 3-4  实现 + 灰度
  - 1% → 5% → 10%
  - 监控: 实时指标 + 异常告警

Day 5-7  收集数据
  - 每天 check 一次
  - 异常立即停止

Day 8  分析
  - 主指标 + 护栏
  - 显著性检验
  - 决策: 上线 / 回滚
```

**验收**: 1 份完整实验报告, 含假设、设计、结果、决策。

### 21.5 练习 5: 写 1 份统计显著性报告

**目标**: 严格计算显著性。

```python
from scipy import stats

# 实验组 vs 对照组
exp = [0.052, 0.053, 0.051, 0.054, 0.052]  # CTR
ctrl = [0.050, 0.051, 0.049, 0.050, 0.051]

# t 检验
t, p = stats.ttest_ind(exp, ctrl)
print(f"t={t:.3f}, p={p:.3f}")

# 效应量 (Cohen's d)
import numpy as np
d = (np.mean(exp) - np.mean(ctrl)) / np.sqrt((np.var(exp) + np.var(ctrl)) / 2)
print(f"Cohen's d = {d:.3f}")
```

## 23. 常见错误案例 (6 个)

### 23.1 错误 1: "训练/测试集划分错误"

**症状**: 离线 AUC 0.85, 在线 CTR 0.05 (远低于 baseline)。

**根因**: 用户内未 split, 同一用户同时出现在 train/test。

**解决**: 用 GroupKFold 按用户 split, 严禁未来信息穿越。

### 23.2 错误 2: "特征穿越 (Feature Leakage)"

**症状**: 离线 +5%, 在线 +0%。

**根因**: 训练时用了"用户当天行为", 在线拿不到。

**解决**: 严格时间窗, 训练时只能用"过去 X 天"。

### 23.3 错误 3: "没有对照组"

**症状**: 新方法 +3%, 但 baseline 同期也是 +3% (节假日)。

**根因**: 没有同时跑对照。

**解决**: 实验组 + 对照组同时上线, 时间窗完全对齐。

### 23.4 错误 4: "显著性不够"

**症状**: 实验 +1%, 但 p-value 0.3。

**根因**: 样本量太小, 流量太小。

**解决**: 用 [[05-如何设计实验]] 算最小样本。

### 23.5 错误 5: "新奇效应未识别"

**症状**: 上线第 1 周 +5%, 第 4 周变 0%。

**根因**: 用户"新鲜感", 不是真提升。

**解决**: 至少跑 2-4 周, 观察趋势。

### 23.6 错误 6: "辛普森悖论"

**症状**: 总体 +2%, 但每个用户群都 -1%。

**根因**: 加权方式错了 (新用户拉低老用户)。

**解决**: 必报"分桶结果"。

```python
from scipy import stats
import numpy as np

def ab_test(exp, ctrl, alpha=0.05):
    # t 检验
    t, p = stats.ttest_ind(exp, ctrl)
    # 效应量
    pooled_std = np.sqrt((np.var(exp) + np.var(ctrl)) / 2)
    d = (np.mean(exp) - np.mean(ctrl)) / pooled_std
    # 置信区间
    se = pooled_std * np.sqrt(1/len(exp) + 1/len(ctrl))
    ci_low = np.mean(exp) - np.mean(ctrl) - 1.96 * se
    ci_high = np.mean(exp) - np.mean(ctrl) + 1.96 * se
    return {
        "t": t, "p": p, "significant": p < alpha,
        "cohens_d": d, "ci": (ci_low, ci_high)
    }

# 例子
exp = np.random.normal(0.052, 0.005, 10000)
ctrl = np.random.normal(0.050, 0.005, 10000)
print(ab_test(exp, ctrl))
```

### 25.3 样本量计算

```python
# sample_size.py
from scipy import stats
import math

def required_sample_size(baseline_rate, mde, alpha=0.05, power=0.8):
    # 计算 A/B 测试所需样本量 (每组)
    p1 = baseline_rate
    p2 = baseline_rate + mde
    z_alpha = stats.norm.ppf(1 - alpha/2)
    z_beta = stats.norm.ppf(power)
    p_pooled = (p1 + p2) / 2
    n = ((z_alpha * math.sqrt(2 * p_pooled * (1 - p_pooled))
         + z_beta * math.sqrt(p1*(1-p1) + p2*(1-p2))) / mde) ** 2
    return int(math.ceil(n))

# 例子: 基线 CTR 5%, 想检测 1% 提升
print(required_sample_size(0.05, 0.01))
```
