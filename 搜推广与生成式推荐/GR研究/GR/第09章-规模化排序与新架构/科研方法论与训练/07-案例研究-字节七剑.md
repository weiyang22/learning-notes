# 第09章-07 - 案例研究: 字节七剑规模化排序全链路

> **研究问题**: 字节跳动如何在 18 个月内连续发表 7 篇规模化排序架构论文, 形成"Token Mixer / 异构 Transformer / Memory" 三派并行的技术体系?
>
> **研究方法**: 把 7 篇论文视为**同一研究问题的不同切片**, 通过对比它们的问题定义、方案解构、设计取舍, 提炼出字节研究风格的**共性模式**.
>
> **样本论文**: TokenMixer-Large, OneTrans, STCA, MDL, MixFormer, MSN, HyFormer

---

> **字节七剑的真正核心不是"哪个架构最好", 而是"如何在工业约束下做架构探索 — 渐进式 + 工程化 + 多场景验证"**.

## 3. 案例 1: 问题发现 — 字节共性问题地图

### 3.1 五大共性问题

| 问题 | 描述 | 受影响的论文 |
|------|------|------------|
| **Q1: 长序列** | 用户行为序列长达 10K, 标准 self-attention O(L²) 不可行 | STCA, OneTrans, HyFormer |

| **Q5: 工业约束** | 推理延迟 < 30ms, QPS 1万+, 显存 80GB 限制 | ALL 7 篇 |

### 4.2 Token Mixer 派

#### TokenMixer-Large

**架构图**:
```text
Input Tokens (序列 + ID + 上下文)
            │
            ▼
   ┌─────────────────────────┐
   │  Tokenization Layer     │  ← 特征 → Token
   └─────────────────────────┘
            │
            ▼
   ┌─────────────────────────┐
   │  TokenMixer-Large       │  × N 层
   │  Block                  │
   │  ┌───────────────────┐  │
   │  │ Mixing            │  │  ← 核心创新 (取代 self-attention)
   │  │ & Reverting       │  │
   │  └───────────────────┘  │
   │  ┌───────────────────┐  │
   │  │ Per-token SwiGLU  │  │
   │  └───────────────────┘  │
   │  ┌───────────────────┐  │
   │  │ Residual + LN     │  │
   │  └───────────────────┘  │
   │  ┌───────────────────┐  │
   │  │ Interval Residual │  │  ← 跨层残差
   │  └───────────────────┘  │
   │  ┌───────────────────┐  │
   │  │ Residual Loss     │  │  ← 辅助损失
   │  └───────────────────┘  │
   └─────────────────────────┘
            │
            ▼
   ┌─────────────────────────┐
   │  Sparse Per-token MoE   │  ← 稀疏扩展
   │  (Token-Parallel)       │
   └─────────────────────────┘
            │
            ▼
        Output Logits
```

**核心组件详解**:
- **Mixing & Reverting**: 把 token reshape 后 MLP, 再 revert 回去 → 避免信息损失
- **Per-token SwiGLU**: 每个 token 独立 FFN, 增加非线性
- **Residual + LN**: 标准残差
- **Interval Residual + Auxiliary Loss**: 跨层信息流 + 辅助梯度
- **Sparse Per-token MoE**: 每 token 路由到专属 expert

#### RankMixer (前身)

- Token Mixer 范式奠基
- MFU 4.5% → 45%
- 100× 参数扩展同延迟

### 4.3 异构 Transformer 派 (3 篇)

#### OneTrans

**架构图**:
```text
                ┌─────────────────────────┐
                │  Unified Tokenizer      │
                └─────────────────────────┘
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
   ┌─────────────────────┐    ┌─────────────────────┐
   │  S-token (序列特征) │    │ NS-token (非序列)   │
   │  Shared Q/K/V/FFN   │    │ Per-token Q/K/V/FFN │
   └─────────────────────┘    └─────────────────────┘
              │                           │
              └─────────────┬─────────────┘
                            ▼
                 ┌─────────────────────┐
                 │ Mixed               │
                 │ Parameterization    │
                 │ (异构参数化)         │
                 └─────────────────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Pyramid Schedule    │  ← 逐层剪枝
                 └─────────────────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Cross-request       │  ← O(1) 推理
                 │ KV Caching          │
                 └─────────────────────┘
```

#### HyFormer

**核心**: Global Tokens + 交替 Query Decoding

```text
非序列特征 → Global Tokens
序列特征   → 长行为序列

每个 Block:
  Layer 1: Query Decoding (Global Tokens → 序列 K/V)
  Layer 2: Query Boosting (Global Tokens ← 序列输出)
  交替进行
```

#### MixFormer

**核心**: 完全统一 Transformer, 移除序列 vs 稠密的硬边界

#### MDL

**核心**: 场景 / 任务 token 化 (类似 LLM soft prompting)

```text
特征 → Feature Tokens
场景 → Scenario Tokens
任务 → Task Tokens

三层交互:
  1. Feature self-attn
  2. Domain-feature attn (Domain Tokens 激活 Feature Tokens)
  3. Domain-fused aggregation
```

### 4.4 Memory 派

#### MSN

**核心**: PKM (Product-Key Memory) 记忆网络

```text
DLRM/SMoE 模型
            │
            ▼
   ┌─────────────────────────┐
   │  Memory Gating          │  ← 动态检索个性化表征
   └─────────────────────────┘
            │
            ▼
   ┌─────────────────────────┐
   │  PKM (Product-Key)      │  ← 亚线性检索
   │  ┌─────────┬─────────┐  │
   │  │ Subkey1 │ Subkey2 │  │
   │  │  检索    │  检索    │  │
   │  └────┬────┴────┬────┘  │
   │       └────┬────┘       │
   │            ▼            │
   │     Memory Slot Value   │
   └─────────────────────────┘
            │
            ▼

```

**关键工程优化**:
- Query & key LayerNorm
- 学习率 warm-up
- Key embedding 过参数化 (防 collapse)
- Sparse-Gather + AirTopK 算子

### 4.5 STCA — 长序列派 (独立分支)

**核心**: O(L) 目标-历史交叉注意力

```text
User History: 10K tokens
Candidate: 1 token (target)

传统: O(L²) self-attention (100M FLOPs)
STCA: O(L · d_h) cross-attention (1.3M FLOPs) ← 75× 加速
```

### 5.3 关键发现

1. **没有"最好"架构, 只有"最合适"**: 字节同时存在 3 派, 恰好对应不同的 (D1, D2, D3, ...) 组合
2. **多业务统一用异构 Trans** (MDL), 单场景规模化用 Token Mixer (TokenMixer-Large)
3. **超长序列必须 STCA** 类 (O(L) attention)
4. **Memory 是补丁, 不是替代** (MSN 部署在 SMoE 之上)

## 6. 案例 4: 工程创新 — 字节杀手锏

### 6.1 三大工程创新

| 创新 | 来源 | 关键指标 |
|------|------|---------|
| **Request-Level Batching (RLB)** | STCA / OneTrans / MixFormer | 带宽 ↓84%, 吞吐 2.2× |
| **Cross-Request KV Caching** | OneTrans / LONGER | 推理 O(m·L) → O(1) |
| **Length Extrapolation** | STCA | 训练 2K, 推理 10K, ρ=5× |

### 6.2 RLB 详解

**核心思想**: 多目标 / 多请求共享用户侧编码

```python
def request_level_batching(user_features, candidates_list):
    """多目标共享用户侧"""
    # 1 次用户侧前向
    user_repr = user_encoder(user_features)  # O(1) per user

    # 多个候选共享
    scores = []
    for candidates in candidates_list:  # batched
        scores.append(cross_attention(user_repr, candidates))

    return scores  # 总计算: O(1) user + O(T) candidate
```

**字节的实践** (来自 STCA):
- 端到端带宽 ↓84%
- PS CPU 减半
- 吞吐 2.2×

### 6.3 Cross-Request KV Caching 详解

**核心思想**: 跨请求 / 跨候选缓存用户 KV

```python
class CrossRequestKVCache:
    def __init__(self, max_size=10000):
        self.cache = {}
        self.max_size = max_size

    def get_or_compute(self, user_id, model):
        if user_id in self.cache:
            return self.cache[user_id]  # O(1) 复用

        # 首次计算用户 KV
        user_features = fetch_user_features(user_id)
        user_kv = model.encode_user(user_features)

        # LRU 缓存
        if len(self.cache) >= self.max_size:
            self.cache.popitem()
        self.cache[user_id] = user_kv

        return user_kv

# 推理时
user_kv = cache.get_or_compute(user_id, model)  # O(1)
for candidate in candidates:  # 并行
    score = model.cross_attention(user_kv, candidate)  # O(L)
```

**字节的实践** (来自 OneTrans):
- 单次请求推理从 O(m·L) 降到 O(1)
- p99 延迟 ↓3.91%

### 6.4 Length Extrapolation 详解

**核心思想**: 训练短序列, 推理长序列

```python
import torch
from torch.distributions import Beta

class LengthExtrapolationSampler:
    """训练时采样短序列, 推理时用长序列"""
    def __init__(self, alpha=0.1, beta=1.0, max_train_len=2048):
        self.dist = Beta(alpha, beta)
        self.max_train_len = max_train_len

    def sample_train_length(self):
        """从 Beta 分布采样训练长度"""
        return int(self.dist.sample() * self.max_train_len)

    def train_step(self, model, batch):
        # 随机采样短序列 (从分布)
        for sample in batch:
            train_len = self.sample_train_length()
            sample['history'] = sample['history'][:train_len]
        return model(batch)

    def inference_step(self, model, batch):
        # 推理时用完整长度 (10K)
        return model(batch)

# 字节 STCA: 平均 2K 训练, 10K 推理
```

**收益**: STCA 用 1/3 训练成本捕获 ~80% 的 10K 收益

### 6.5 工程创新的共性

> **字节的工程创新全部围绕"让大模型能在生产环境跑起来"**, 不是"加速训练". 论文的 RLB/KV/Length 都是为了让大模型满足工业延迟约束.

```text
    │   解决方案:
    │   ├─ Mixing-and-Reverting (修复残差)
    │   ├─ Interval Residual + Auxiliary Loss (稳定梯度)
    │   ├─ Sparse Per-token MoE (完整稀疏化)
    │   └─ Token-Parallel (工程并行)
    │
    ▼
    Scaling Law 验证:
    ├─ 0.5B: AUC 0.6250
    ├─ 1B: AUC 0.6280
    ├─ 2.1B: AUC 0.6320
    ├─ 5B: AUC 0.6355
    ├─ 9B: AUC 0.6380
    ├─ 15B: AUC 0.6395
    └─ 拟合 alpha_N = 0.093, R² = 0.987
```

### 7.2 关键决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 离线最大规模 | 15B | 边际收益 < 0.5% 但算力翻倍 |
| 在线最大规模 | 7B | 比 15B 节省 50% 算力, 损失 0.1% AUC |
| 训练数据 | 100B 样本 | Chinchilla 最优 |
| 训练长度 | 2K | Length Extrapolation 推理 10K |
| 是否蒸馏 | 是 | 大模型离线 → 小模型在线 |

### 7.3 字节的 Scaling 经验总结

**经验 1: 先验架构, 再做 Scaling**
- TokenMixer 架构本身就比 self-attention 更易扩展 (MFU 45%)
- 如果架构弱 (例如 Hiformer MFU 17%), 即使 scaling 也追不上

**经验 2: 离线和在线解耦**
- 离线 15B 用于蒸馏 / 特征
- 在线 7B 用于实时服务
- **不要硬塞 15B 上线** (延迟爆炸)

**经验 3: Scaling 必须配合工程优化**
- 没有 RLB, 7B 模型在线延迟爆炸
- 没有 KV 缓存, 推理 O(m·L) 不可行
- 没有 Length Extrapolation, 训练成本失控

## 14. 每篇论文的详细复盘

> 7 篇论文逐一复盘: 解决了什么问题, 怎么解的, 关键创新点是什么.

### 14.1 TokenMixer-Large 复盘

**问题**: RankMixer 1B 之后 scaling 停滞 (4 大瓶颈).

**解法**:
1. **Mixing-and-Reverting**: token reshape → MLP → revert, 修复信息损失
2. **Interval Residual**: 跨层残差, 让梯度直达
3. **Auxiliary Loss**: 每层加辅助 loss, 强化学习信号
4. **Sparse Per-token MoE**: 每 token 路由到专属 expert
5. **Token-Parallel**: 新 CUDA kernel, MFU 从 17% 升到 45%

**效果**:
- 离线 15B 模型 +2% ADSS, +2.98% GMV
- 在线 7B 模型 (蒸馏自 15B)
- 抖音 Ads / 电商 / 直播 三场景全量

**关键洞察**:
> **离线做最大, 在线蒸馏压缩** — 这是字节的核心 scaling 哲学.

**面试要点**:
- 为什么 Mixing-and-Reverting 有效? (答: 修复残差路径, 避免信息瓶颈)
- 7B vs 15B 如何选? (答: 7B 推理快, 15B 蒸馏教师)
- Per-token MoE 与普通 MoE 区别? (答: 路由粒度更细, 1 个 token 1 个 expert)

### 14.2 OneTrans 复盘

**问题**: 序列建模和特征交互分离架构 → 信息双向断裂.

**解法**:
1. **Unified Tokenizer**: 所有特征 token 化
2. **Mixed Parameterization**: 序列共享 Q/K/V/FFN, 非序列 token-specific
3. **Pyramid Schedule**: 逐层剪枝 (深层窄, 浅层宽)
4. **Cross-Request KV Caching**: 跨请求共享 KV, O(m·L) → O(1)

**效果**:
- Feeds +5.68% gmv/u
- Mall +3.67% gmv/u
- p99 延迟 ↓3.91%

**关键洞察**:
> **统一架构不等于所有参数共享** — 异构参数化才是关键.

**面试要点**:
- 为什么序列特征要共享? (答: 序列同质, 共享提升效率)
- 为什么非序列 token-specific? (答: ID 特征差异大, 独立保留表达)
- Cross-Request KV Cache 如何不影响精度? (答: 用户 KV 复用, 与候选独立计算)

### 14.3 STCA 复盘

**问题**: 长序列 (10K) 标准 self-attention $O(L^2)$ 不可行.

**解法**:
1. **Target-History Cross-Attention**: $O(L \cdot d)$ 而非 $O(L^2)$
2. **Request-Level Batching (RLB)**: 多请求共享用户侧编码
3. **Length Extrapolation**: 训练 2K, 推理 10K (Beta 分布采样)

**效果**:
- 端到端带宽 ↓84%
- 吞吐 2.2×
- PS CPU 减半

**关键洞察**:
> **不要做 self-attention, 做 cross-attention** — 推荐系统的"目标"是 1 个, 不是 $L$ 个.

**面试要点**:
- 为什么 O(L) cross-attention 不会丢信息? (答: 用户历史里只有少数与目标相关, cross-attention 直接关注相关部分)
- RLB 与 KV Cache 的区别? (答: RLB 是请求级共享, KV Cache 是请求内复用)
- Length Extrapolation 为什么能泛化? (答: Beta 分布覆盖不同长度, 训练时见过)

### 14.4 MDL 复盘

**问题**: 多场景多任务, 业务差异大, 单一模型难以通用.

**解法**:
1. **Scenario Tokens**: 每个场景一个 token (类似 LLM soft prompt)
2. **Task Tokens**: 每个任务一个 token
3. **3 层交互**: Feature self-attn → Domain-feature attn → Domain-fused aggregation

**效果**:
- 抖音搜索 +0.0626% LT30
- 多场景统一架构

**关键洞察**:
> **场景和任务可以 token 化, 让模型自己学习迁移** — 这是 LLM 范式对推荐的迁移.

**面试要点**:
- Scenario Token 与 Prompt 的区别? (答: Token 在内部 embedding 空间, Prompt 在外部输入)
- 3 层交互为什么必要? (答: 分离场景识别 / 特征交互 / 场景融合 三个阶段)
- 多场景迁移的极限? (答: 5-10 个场景内有效, 太多会冲突)

### 14.5 MixFormer 复盘

**问题**: 序列特征 vs 稠密特征的硬边界, 无法统一建模.

**解法**:
1. **完全统一 Transformer**: 移除序列 vs 稠密的硬边界
2. **Token 类型**: 用户序列 / 上下文 / 候选 都视为 token
3. **缩放**: 序列长度与稠密维度共同 scaling

**效果**:
- 抖音 Feeds 活跃天数提升
- 多场景统一

**关键洞察**:
> **"一切皆 token"** — 这是 NLP Transformer 思想的最彻底贯彻.

**面试要点**:
- 与 OneTrans 区别? (答: MixFormer 是完全统一, OneTrans 是异构参数化)
- Token 类型如何区分? (答: Type embedding 类似 BERT 的 segment id)
- 完全统一有没有代价? (答: 失去异构的 inductive bias, 需要更多数据)

### 14.6 MSN 复盘

**问题**: 现有模型对超长历史的"个性化表征"利用不充分.

**解法**:
1. **PKM (Product-Key Memory)**: 亚线性检索的记忆网络
2. **Memory Gating**: 动态决定检索哪些记忆
3. **稀疏优化**: Sparse-Gather + AirTopK 算子

**效果**:
- 部署在 SMoE 模型之上, 增量提升
- 不替换原有模型, 而是"补丁"

**关键洞察**:
> **Memory 是补丁, 不是替代** — 大模型 + Memory 是组合, 不是革命.

**面试要点**:
- PKM 的两个 Subkey 检索机制? (答: 各自检索 top-k, 然后求交集)
- Memory Gating 如何避免检索噪声? (答: 门控网络学习"是否需要"记忆)
- 为什么不直接用更大模型? (答: 大模型记忆是隐式的, 显式 Memory 更可控)

### 14.7 HyFormer 复盘

**问题**: 序列特征与非序列特征的注意力交互不充分.

**解法**:
1. **Global Tokens**: 非序列特征压缩为少量 Global Tokens
2. **交替 Query Decoding + Boosting**: 双向信息流
3. **70 天 30 亿样本训练**

**效果**:
- 抖音搜索 CTR 全量部署
- 提升搜索精度

**关键洞察**:
> **Global Tokens 是"信息瓶颈", 但又是"注意力枢纽"**.

**面试要点**:
- 为什么 Global Tokens 数量通常 < 10? (答: 太多会失去瓶颈作用)
- 双向信息流为什么必要? (答: 单向会让 Global Token 信息滞后)
- 与 MixFormer 区别? (答: MixFormer 是 token-level 统一, HyFormer 是 token 间的双向流动)

## 16. 技术决策的 WHY 分析

> 为什么字节选 TokenMixer 而非标准 Transformer? 为什么 OneTrans 要做异构参数化? 本节剖析每个关键技术决策的 WHY.

### 16.1 为什么 TokenMixer 派而非 Attention 派?

| 决策点 | 选项 | 选择 | WHY |
|--------|------|------|-----|
| **核心算子** | Self-Attention / Cross-Attention / Token Mixer | Token Mixer | 推荐数据是"异构 token 集合", 不是"序列", attention 不适配 |
| **Scaling 行为** | 平方复杂度 / 线性复杂度 | 线性 (Token Mixer) | 在线延迟 < 30ms 硬约束, 必须避免平方 |
| **MFU** | 4.5% (Attention) / 45% (Token Mixer) | 45% | 字节 GPU 集群成本高, 必须高 MFU |
| **异构特征融合** | 分别建模 / 统一建模 | 统一 (Token Mixer) | 异构融合是推荐的核心难点 |

### 16.2 为什么 OneTrans 选异构参数化?

**WHY #1**: 序列特征 (用户历史) 与非序列特征 (用户属性) 信息密度不同.
- 序列: 长但稀疏, 共享权重能减少参数量
- 非序列: 短但稠密, token-specific 保留表达力

**WHY #2**: 异构参数化能让**两个塔同时 scaling**, 不会相互拖累.
- 如果全部共享 → 序列变长时, 非序列表达被稀释
- 如果全部独立 → 序列无法利用参数效率

**WHY #3**: 工业部署友好.
- 共享部分可以预计算 + 缓存
- 独立部分可以并行计算

### 16.3 为什么 STCA 选 Cross-Attention 而非稀疏 Attention?

| 方案 | 复杂度 | 效果 | 工程难度 |
|------|--------|------|---------|
| **Longformer (稀疏 attention)** | $O(L \sqrt{L})$ | 损失全局信息 | 中 |
| **Linformer (低秩 projection)** | $O(L \cdot k)$ | 损失长程依赖 | 低 |
| **STCA (cross-attention)** | $O(L \cdot d)$ | 保留全部 | **低** |
| **Mamba (SSM)** | $O(L)$ | 序列建模能力 | 高 |

字节选 STCA 因为:
- 工程难度最低 (复用现有 attention kernel)
- 效果最好 (不丢信息)
- 与 RLB (Request-Level Batching) 完美兼容

### 16.4 为什么 MDL 选 Scenario Token 而非网络分组?

**选项 A**: 网络分组 (每个场景一个子网络)
- 缺点: 参数膨胀, 难扩展

**选项 B**: Scenario Token (一个网络 + 场景 token)
- 优点: 参数共享, 自动迁移
- 缺点: 场景冲突时需要调参

字节选 B 因为业务场景太多 (>10 个), 网络分组不现实.

### 16.5 为什么 MSN 选 Memory 而非更大模型?

| 方案 | 复杂度 | 效果 | 风险 |
|------|--------|------|------|
| **更大模型 (15B → 30B)** | $O(N^2)$ | 边际收益 0.1% | OOM, 部署难 |
| **长序列 (10K → 100K)** | $O(L^2)$ | 离线 GPU 撑不住 | 工程难 |
| **Memory (PKM 检索)** | $O(\sqrt{N})$ | 显式可控 | 中等 |

字节选 Memory 因为: **大模型记忆是隐式的, 显式 Memory 更可控**.

```text
1. Introduction (2 页)
   ├── 业务背景 (具体数字)
   ├── 现有方法的局限 (3-4 个问题)
   ├── 我们的贡献 (3-4 个 bullet)
   └── 与业界方法的区别

2. Method (3-4 页)
   ├── 整体架构图
   ├── 核心创新 (1-2 个)
   ├── 工程优化 (kernel / 推理)
   └── 与已有方法的对比

3. Experiments (3-4 页)
   ├── 数据集 (脱敏)
   ├── Baseline (5-10 个 SOTA)
   ├── 主要结果 (在线 + 离线)
   ├── 消融实验 (2-3 个关键组件)
   └── Scaling 验证

4. Deployment (1-2 页)
   ├── 工程实现
   ├── 在线 A/B 数字
   ├── 性能数据 (延迟 / QPS / MFU)
   └── 经验教训

5. Related Work (1 页)

6. Conclusion (0.5 页)
```

### 19.4 复用字节模式的 4 个陷阱

| 陷阱 | 表现 | 避免 |
|------|------|------|
| **业务脱离** | 论文很美但业务无感 | 选真实业务问题 |
| **过度工程** | kernel 太复杂, 维护难 | 简化到能跑即可 |
| **数据吹牛** | 描述规模但无 scaling 实验 | 必有 scaling 验证 |
| **在线失败** | 离线好但在线无效 | 早 A/B, 早发现 |

## 24. 常见错误案例 (5 个)

### 24.1 错误 1: "只看论文, 不看团队"

**症状**: 读懂了 TokenMixer, 但不知道是哪个团队做的。

**解决**: 必查作者团队 + 部门 + 业务背景。

### 24.2 错误 2: "只学技术, 不学风格"

**症状**: 复现了论文, 但不知道"为什么字节这么做"。

**解决**: 必读团队博客 / 演讲 / 内部分享。

### 24.3 错误 3: "只看 SOTA, 不看演进"

**症状**: 只读最新一篇, 不知道前面 6 篇的脉络。

**解决**: 按时间线读, 画出演进图。

### 24.4 错误 4: "忽略业务约束"

**症状**: 觉得"字节方法好", 但忽略"我们没那个算力"。

**解决**: 必读"工业约束"章节 (算力 / 数据 / 延迟)。

### 24.5 错误 5: "盲目崇拜"

**症状**: 字节做什么就抄什么, 没自己的判断。

**解决**: 必做"批判性阅读", 找 3 个弱点。

```python
# bytedance_seven.py
papers = {
    "TokenMixer": {"year": 2024, "type": "基础架构", "scale": "大集群"},
    "OneTrans": {"year": 2024, "type": "排序统一", "scale": "大集群"},
    "STCA": {"year": 2024, "type": "稀疏 attention", "scale": "大集群"},
    "MDL": {"year": 2024, "type": "多视角蒸馏", "scale": "大集群"},
    "MixFormer": {"year": 2023, "type": "蒸馏统一", "scale": "中等"},
    "MSN": {"year": 2023, "type": "难负样本", "scale": "中等"},
    "HyFormer": {"year": 2023, "type": "异构融合", "scale": "中等"},
}

def analyze_bytedance_style(papers):
    by_year = sorted(papers.items(), key=lambda x: x[1]["year"])
    print("字节七剑时间线:")
    for name, info in by_year:
        print(f"  {info['year']}: {name} ({info['type']})")

    # 统计
    types = [p["type"] for p in papers.values()]
    print(f"
类型分布: {dict((t, types.count(t)) for t in set(types))}")

analyze_bytedance_style(papers)
```
