# 第09章-09 - 案例研究: 其他厂商八强规模化排序研究 (v2.0)

> **研究问题**: 在阿里九章 + 字节七剑之外, 还有 6 家头部厂商 (腾讯 / 快手 / 小红书 / 京东 / Meta / 美团) 各自有 1-2 篇代表性论文. 这些论文有什么**独特问题**和**独特方案**?
>
> **核心论点 (One-Line)**: 这 6 家公司的研究风格**高度差异化**, 没有"统一范式". 腾讯做 Foundation Model Transfer, 快手做稀疏 MoE, 小红书做沉默门控, 京东做 LLM 推理增强, Meta 做全球异构架构 + Scaling Law, 美团做全景序列建模 + AutoToken. **学习这 8 篇论文的关键不是抄方案, 是看懂"在不同业务约束下应该做什么不同的事"**.
>
> **样本论文 (8 篇)**:
> - **腾讯** LFM4Ads — 广告 Foundation Model
> - **快手** SMES — 稀疏 MoE 多任务
> - **小红书** LASER — 沉默门超长序列
> - **京东** OxygenREC — 推理 + GR
> - **Meta** InterFormer + Kunlun — 异构 + Scaling
> - **美团** HoMer + MTmixAtt — 全景序列 + AutoToken

> **腾讯走 Foundation Model Transfer, 快手走稀疏 MoE 路由, 小红书走沉默门控超长序列, 京东走 LLM 增强推理, Meta 走异构 Transformer + Scaling Law, 美团走全景序列 + 自动 Token 设计. 6 家没有"标准答案", 但每家的论文都对自己业务约束做了极致适配. 学习这 8 篇, 学的是"业务约束 → 方法选择"的能力, 不是具体 trick**.

## 3. 案例 1: 各家独特的问题发现

### 3.1 腾讯: 广告主 / 内容双场景

#### 3.1.1 业务背景

腾讯广告主要服务:

- **朋友圈广告** (微信生态)
- **视频号广告** (短视频内嵌)
- **视频号小店广告** (电商类)

这 3 个子业务的特征差异巨大:

| 业务线 | 用户状态 | 核心目标 | 优化指标 |
|--------|---------|---------|---------|
| 朋友圈 | 静态(看图文) | 点击 → 转化 | CTR, CVR, GMV |
| 视频号 | 动态(看视频) | 完播 → 互动 | Watch Time, ADSS |
| 视频号小店 | 电商(看商品) | 加购 → 转化 | GMV, RPM |

#### 3.1.2 腾讯的核心痛点

```text
┌─────────────────────────────────────────────────────────┐
│  痛点: 3 个业务线, 9 种特征, 7 种任务目标                    │
│                                                         │
│  现有做法: 每个业务训练独立模型, 共 9 个                    │
│            工程成本高 (训练 / 推理 / 维护 × 9)                │
│            数据利用率低 (每业务只能用自己数据)                │
│                                                         │
│  问题: 如何用一个 Foundation Model 解决 3 个业务?           │
└─────────────────────────────────────────────────────────┘
```

#### 3.1.3 LFM4Ads 的洞察

LFM4Ads 把广告推荐建模为 **三个表征 (UR + IR + CR)** 的统一学习:

- **UR (User Representation)**: 用户特征
- **IR (Item Representation)**: 物品特征
- **CR (Cross Representation)**: 用户 × 物品交叉 (核心创新)

CR 是关键 — 通常 CR 只能在样本级 (一次 user-item pair) 学, LFM4Ads 通过 **时序 EMA 聚合** 把样本级 CR 折叠为可迁移的用户/物品级 CR.

#### 3.1.4 腾讯的对外表述

> "腾讯广告推荐的本质, 是 **理解用户 × 物品** 的关系. 这个关系既随用户历史变, 也随物品上下文变. 我们用一个 Foundation Model 同时建模这 3 个跨业务共性的关系, 然后下游业务微调."

**这是腾讯式研究的代表** — **从业务本质抽出共性, 然后用一个 Foundation Model 解决**.

### 3.2 快手: 多任务负载均衡

#### 3.2.1 业务背景

快手首页推荐服务 **50+ 任务目标**, 包括:

- **CTR / CVR / GMV** (传统电商)
- **Watch Time / 完播率 / 点赞 / 评论 / 收藏 / 关注** (短视频)
- **直播打赏 / 连麦转化 / 直播间时长** (直播)
- **关注转化 / 拉黑 / 不感兴趣** (负反馈)
- **50 种以上** (随业务演化)

#### 3.2.2 核心痛点

```text
┌─────────────────────────────────────────────────────────┐
│  痛点: 50+ 任务, MMoE 类的模型严重任务失衡                 │
│                                                         │
│  现象 1: 主任务 (CTR) 占 GPU 80%+                       │
│          副任务 (拉黑) 几乎没学习                         │
│  现象 2: 任务之间相互负迁移                              │
│  现象 3: 新任务上线, 老模型需要重新训练                     │
│                                                         │
│  问题: 如何让 50+ 任务均衡学习, 且支持灵活加新任务?        │
└─────────────────────────────────────────────────────────┘
```

#### 3.2.3 SMES 的洞察

**稀疏 MoE (Sparse MoE)** + **渐进式专家路由**:

- 50+ 任务共享一组 **专家 (experts)**
- 每个任务**渐进式**选专家 (先选 2 个, 再选 4 个, ...)
- **专家负载均衡**, 避免主导专家
- **增量添加新任务**容易 (注册任务即可)

```python
# SMES 伪代码
def smes_routing(task_emb, expert_outputs):
    # task_emb: 当前任务嵌入
    # expert_outputs: 所有 expert 的输出 (B, E, D)
    route = softmax(task_emb @ W_gate)  # (B, E)
    # 渐进路由: top-k
    k = min(self.k, E)  # 渐进
    topk_idx = topk(route, k=k)
    output = sum(route[:, i] * expert_outputs[:, i] for i in topk_idx)
    return output
```

#### 3.2.4 快手式研究

> "快手的研究始终围绕 **多任务** 这个核心. 我们不是研究新的 attention, 而是研究'如何让 50+ 任务都学好'. SMES 是这个方向的最新进展."

**这是快手式研究的代表** — **任务路由** 而非架构创新.

### 3.3 小红书: 长序列 + 沉默门

#### 3.3.1 业务背景

小红书的用户结构独特:

| 用户类型 | 占比 | 特征 |
|---------|------|------|
| **活跃用户** | ~60% | 每日刷小红书, 行为序列长 |
| **沉默用户** | ~40% | 1 周以上未登录, 行为序列稀疏 |
| **新用户** | ~10% | 7 日内注册, 行为几乎为 0 |

#### 3.3.2 核心痛点

```text
┌─────────────────────────────────────────────────────────┐
│  痛点: 40% 用户行为序列稀疏 (< 5 条), 长序列建模失效       │
│                                                         │
│  现有做法 1: 截断到固定长度, 沉默用户序列全 pad             │
│  问题 1: 沉默用户的"沉默"信号被丢弃了                    │
│                                                         │
│  现有做法 2: 单独做沉默用户建模                           │
│  问题 2: 工程复杂, 模型分裂                              │
│                                                         │
│  问题: 如何让沉默信号成为"信息", 而不是"噪声"?            │
└─────────────────────────────────────────────────────────┘
```

#### 3.3.3 LASER 的洞察

**沉默门 (Silence Gate)** — 用一个 sigmoid 门来**激活/沉默** 序列:

```python
# LASER 沉默门
def silence_gate(seq):
    # seq: 用户行为序列 (B, L, D)
    # 计算每条行为的"重要性"分数
    importance = sigmoid(seq @ W_g + self.bias)  # (B, L, 1)
    # 沉默的用户权重低, 活跃的用户权重大
    weighted = seq * importance
    # 但同时保留"沉默 = 信息"信号
    silence_signal = mean(1 - importance)  # (B, 1)
    return weighted, silence_signal
```

**关键洞察**: "沉默"不是一个 0/1 的开关, 而是**梯度可微**的信号. 算法可以学到"沉默用户的特定模式".

#### 3.3.4 小红书式研究

> "小红书有 40% 的沉默用户, 这是小红书的'特色'. 我们不把他们当'低质用户', 而是当'另一种用户'. LASER 让沉默信号本身成为信息."

**这是小红书式研究的代表** — **从业务独特性找洞察**.

### 3.4 京东: 推理 + GR

#### 3.4.1 业务背景

京东自营电商的决策周期**长**:

```text
浏览 → 加购 → 1 日复访 → 3 日复访 → 7 日复访 → 30 日复访 → 转化
```

- 用户可能 7 天后才买
- 模型要"有远见"

#### 3.4.2 核心痛点

```text
┌─────────────────────────────────────────────────────────┐
│  痛点: 用户决策周期长, 短期信号弱, 长期价值难捕捉            │
│                                                         │
│  现有做法 1: 多任务学习 (CTR + CVR + GMV)                 │
│  问题 1: CVR 样本选择偏差 (点击后才转化)                  │
│                                                         │
│  现有做法 2: 多步建模 (CTR → CTCVR → CVR)                 │
│  问题 2: 误差累积                                       │
│                                                         │
│  问题: 如何让模型"会推理", 处理长决策链路?                 │
└─────────────────────────────────────────────────────────┘
```

#### 3.4.3 OxygenREC 的洞察

**Fast-Slow Thinking** + **GR (Generative Recommendation)**:

- **Fast Thinking**: 快速响应短期信号 (CTR)
- **Slow Thinking**: 用 LLM 推理长期价值 (7 日 GMV)
- **GR**: 用生成式模型直接生成"用户下一步动作"

```python
# OxygenREC 伪代码
def oxygen_rec_forward(user, item):
    # Fast: 短期预测
    fast_score = self.fast_tower(user, item)  # CTR 概率

    # Slow: 用 LLM 推理长期价值
    slow_score = self.llm_reason(
        prompt=f"用户最近 30 天行为: {user.history}, 商品: {item.name}",
        temperature=0.7
    )  # 未来 30 天购买概率

    # 加权
    final = 0.7 * fast_score + 0.3 * slow_score
    return final
```

#### 3.4.4 京东式研究

> "京东的用户决策周期长, 这是我们和其他电商 (淘宝 / 拼多多) 不同. 我们需要模型'会推理', 看到短期信号时, 也要考虑长期价值. LLM 的'思考'能力是核心."

**这是京东式研究的代表** — **用 LLM 增强传统推荐系统**.

#### 4.1.2 关键创新: 时序 EMA 聚合 CR

```python
# LFM4Ads 关键模块
class LFM4Ads(nn.Module):
    def __init__(self):
        self.user_tower = UserTower()
        self.item_tower = ItemTower()
        self.mix_tower = MixTower()
        self.ema_alpha = 0.95  # 时序 EMA 系数

    def forward(self, user_hist, item):
        # 1. 三塔独立计算
        user_emb = self.user_tower(user_hist)
        item_emb = self.item_tower(item)
        # 样本级 CR
        cr_sample = self.mix_tower(user_hist, item)  # [B, D]

        # 2. 时序 EMA 聚合: 把样本级 CR 折叠为 user/item 级 CR
        with torch.no_grad():
            # 按用户聚合
            user_cr_ema = self.user_cr_ema * self.ema_alpha + cr_sample * (1 - self.ema_alpha)
            # 按物品聚合
            item_cr_ema = self.item_cr_ema * self.ema_alpha + cr_sample * (1 - self.ema_alpha)

        # 3. 联合表征
        final = user_emb + item_emb + user_cr_ema + item_cr_ema
        return final
```

LFM4Ads 提供了**3 种粒度**的迁移方式:

| **模块级** | 拿中间层输出 + 微调 | 中等投入 |
| **模型级** | 整模型 + 业务 head | 最深度迁移 |

### 4.3 LASER — 小红书沉默门超长序列

#### 4.3.1 核心创新: Silence Gate

```python
class SilenceGate(nn.Module):
    def __init__(self, dim):
        super().__init__()
        self.gate = nn.Linear(dim, 1)
        self.bias = nn.Parameter(torch.zeros(1))

    def forward(self, seq):
        # seq: (B, L, D)
        score = torch.sigmoid(self.gate(seq) + self.bias)  # (B, L, 1)
        # 沉默用户的 score 自然低, 但仍保留非零梯度
        weighted = seq * score
        # 沉默信号本身
        silence_strength = 1 - score.mean(dim=1, keepdim=True)  # (B, 1, 1)
        return weighted, silence_strength
```

**关键洞察**: `silence_strength` 特征作为**输入到下一层**, 让"沉默"成为信息.

### 4.8 MTmixAtt-AutoToken — 美团自动 Token 设计

#### 4.8.1 AutoToken 核心

AutoToken 让**每个用户动态选择 token 数量**:

```python
class AutoToken(nn.Module):
    def __init__(self, max_k=64):
        super().__init__()
        self.k_controller = nn.Sequential(
            nn.Linear(D, 64),
            nn.ReLU(),
            nn.Linear(64, 1),
            nn.Sigmoid()
        )
        self.max_k = max_k

    def forward(self, user_seq):
        # 1. 计算每条行为的重要性
        importance = self.k_controller(user_seq)  # (B, L, 1)

        # 2. 学习 token 数量
        k_frac = importance.mean(dim=1)  # (B, 1)
        k = (k_frac * self.max_k).long()  # 每个用户 k 不同

        # 3. 选 top-k 行为
        topk_val, topk_idx = topk(importance.squeeze(-1), k=k)

        # 4. 稀疏 attention
        pruned_seq = user_seq.gather(1, topk_idx.unsqueeze(-1).expand(-1, -1, D))
        output = self.attention(pruned_seq)
        return output
```

#### 4.8.2 训练: REINFORCE

k 的选择本身用 REINFORCE 学习:

```python
# RL 训练
def reinforce_train(model, batch):
    # 1. 前向
    output = model(batch)
    reward = compute_business_metric(output, batch.target)

    # 2. 策略梯度
    log_prob = model.get_token_log_prob()
    loss = -reward.detach() * log_prob

    return loss.mean()
```

- 推理延迟 -3 ms (因为 token 数自适应)

```python
class AutoTokenRLTrainer:
    def __init__(self, model):
        self.model = model
        self.reward_baseline = 0.0

    def train_step(self, batch):
        # 1. 策略梯度
        output, k_log_prob = self.model(batch, return_k=True)
        reward = self.compute_business_metric(output, batch.target)

        # 2. REINFORCE 更新 k
        advantage = reward - self.reward_baseline
        self.reward_baseline = 0.95 * self.reward_baseline + 0.05 * reward

        loss = -advantage.detach() * k_log_prob
        loss.backward()

        # 3. 正常更新模型参数
        self.optimizer.step()
```

业界没有 Meta/Google 那种"一个架构 serve 所有". 大部分公司是"业务驱动 → 定制方案".

**行动**: 不要试图"找最好的架构", 而要"找最适合我的业务的架构".

### 启示 3: 长序列 + 长决策 + 多场景 = 三大挑战

8 篇论文里有 **6 篇** 直接处理这三大挑战. 这三者是 2026 年推荐排序的核心战场.

**行动**: 如果你的业务有这些挑战, 优先读 LASER / OxygenREC / HoMer.

京东 OxygenREC 用 LLM 做推理, Meta InterFormer/Kunlun 用纯 Transformer.

**两种路线都没错**, 但**对延迟要求严格**的业务不适合 LLM.

**行动**: 评估你的业务延迟预算, 再决定是否上 LLM.

### 启示 5: 任务路由 (MoE) 是多任务的标准武器

6/8 都用 MoE. **MoE 是工业界的事实标准**, 不是学术创新.

**行动**: 如果你有 5+ 任务, 第一选择是 MoE.

### 启示 6: 沉默用户不是噪声, 是信号

LASER 把"沉默"作为可微信号, 这是工业界对"沉默数据"的反思.

**行动**: 当你有沉默用户时, 不要"丢弃", 而要"建模型".

### 启示 7: 跨场景 / 跨业务统一建模是终极目标

6/8 是为了"跨场景/跨业务统一". 这是工业界的"圣杯".

**行动**: 如果你公司的多个业务有重叠用户, 一定要考虑统一建模.

### 启示 8: Scaling Law 是 2026 年议程

Meta / 美团 / 阿里都在做 Scaling Law. **2026 年新论文几乎都需要有 Scaling 实验**.

**行动**: 即使你的模型只有 1B 参数, 也要补一组 Scaling 实验.

### 启示 9: AutoML 在工业界的崛起

```python
import matplotlib.pyplot as plt
import numpy as np

def plot_radar(company, scores):
    categories = list(scores.keys())
    values = list(scores.values())
    angles = np.linspace(0, 2 * np.pi, len(categories), endpoint=False).tolist()
    values += values[:1]
    angles += angles[:1]
    fig, ax = plt.subplots(figsize=(6, 6), subplot_kw=dict(projection='polar'))
    ax.plot(angles, values)
    ax.fill(angles, values, alpha=0.25)
    ax.set_xticks(angles[:-1])
    ax.set_xticklabels(categories)
    ax.set_title(company)
    plt.savefig(f"{company}_radar.png")
```
