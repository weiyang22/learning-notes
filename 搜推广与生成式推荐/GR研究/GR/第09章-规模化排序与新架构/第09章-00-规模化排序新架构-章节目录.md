## 3. 三大设计模式

### 3.1 模式 A: Token 混合代替注意力 (Token Mixer)
- **核心**: 用 MLP/reshape 替换 self-attention, 显著提升 MFU
- **代表**: RankMixer (字节 2025), TokenMixer-Large (字节 2026), HHFT (阿里 2025)
- **代价**: 损失全局上下文建模能力, 需配合其他模块 (如 STCA 的 target→history 注意力)

### 3.2 模式 B: 异构参数化 (Heterogeneous Parameterization)
- **核心**: 序列特征共享参数 (类似 LLM), 非序列特征 token-specific 参数
- **代表**: HiFormer (Google 2023) → OneTrans (字节 2025) → MixFormer/HyFormer (字节 2026) → HHFT (阿里 2025)
- **优势**: 语义保持 + 参数高效 + 扩展性强

### 3.3 模式 C: 稀疏激活 (Sparse Activation) 规模化
- **核心**: 用 MoE/记忆网络/Memory 把总参数做大但单次激活保持小
- **代表**:
  - **MoE**: SMES (快手 2026 渐进专家), MTmixAtt (美团 多重专家), TokenMixer-Large (字节 Per-token MoE)
  - **Memory**: MSN (字节 PKM)
  - **生成式检索**: HSTU → MTGR → OneRec 系列

## 4. 共同系统创新 (4 大杀手锏)

| 创新 | 核心思想 | 适用论文 |
|------|---------|----------|
| **Request-Level Batching (RLB)** | 多目标共享用户侧编码 | STCA, OneTrans, MixFormer, HyFormer |
| **Cross-Request KV Caching** | 跨请求缓存用户 KV, O(1) 推理 | OneTrans, LONGER |
| **Length Extrapolation** | 训练用短序列, 推理用长序列 | STCA (5× 外推) |
| **Context Parallelism (CP)** | 长序列切分到多 GPU, jagged tensor | HSTU-CP (Meta RecSys'25) |

## 40. 重要定义 / 术语表

### 40.1 GR (Generative Recommendation)

```text
定义: 把推荐任务建模成"序列生成"任务
核心: 输入历史行为, 输出下一行为 (item / action)
与传统区别:
  - 传统: 分类 (CTR / 排序)
  - GR: 生成 (类似 LLM)
优势:
  - 统一架构
  - 多任务
  - 长序列
  - 跨业务
劣势:
  - 工程门槛
  - 推理延迟
  - 训练成本
代表: HSTU, TIGER, MTGR, OneTrans
```

### 40.2 SID (Semantic ID)

```text
定义: item 的语义化 token 化表示
作用: 把 item 从"ID"变成"token", 才能用 LLM-style 训练
方法:
  - VQ-VAE (基础)
  - RQ-VAE (残差, 主流)
  - (后续: 多模态, 跨域)
例子:
  - item 123 → "12_345_67"
  - 这是 SID
代表: RQ-VAE, TIGER (用 SID)
```

### 40.3 LLM4Rec (LLM for Recommendation)

```text
定义: 用 LLM 的能力做推荐
思路:
  - 把推荐任务变成 NLP 任务
  - 用 LLM 统一多任务
  - 用 LLM 的能力做 zero-shot
代表: P5, M6-Rec, TallRec, InstructRec, ChatRec
```

### 40.4 Scaling Law (标度律)

```text
定义: 模型性能 vs 规模 (参数/数据/算力) 的关系
公式: y = a * x^b + c (幂律)
结论:
  - Kaplan: 持续 scaling
  - Chinchilla: compute-optimal (N:D = 1:20)
对 RecSys 启示:
  - 持续 scaling 有效
  - 数据与模型平衡
代表: Kaplan, Chinchilla, UniScale
```

### 40.5 多任务 (Multi-task)

```text
定义: 多个任务 (CTR/CVR/...) 共享模型
优势:
  - 知识共享
  - 减少参数
  - 一致性强
挑战:
  - 任务冲突
  - Loss 加权
方法:
  - Shared-Bottom
  - MMoE / PLE
  - 多专家 (STORE)
```

### 40.6 跨域 (Cross-domain)

```text
定义: 多个域 (淘宝/天猫/...) 知识共享
优势:
  - 跨域迁移
  - 冷启动友好
挑战:
  - 域差异
  - 评估复杂
方法:
  - 共享 embedding
  - 跨域 attention
  - 元学习
```

### 40.7 蒸馏 (Distillation)

```text
定义: 大模型 (教师) → 小模型 (学生)
目的: 简化部署, 减少推理成本
方法:
  - 软标签 + 硬标签
  - 蒸馏温度
  - 多 teacher
代表: MixFormer, EST, MDL
```

### 40.8 稀疏 Attention (Sparse Attention)

```text
定义: 不是所有 token 都 attend
目的: 长序列加速
方法:
  - 聚类稀疏 (STCA)
  - 滑窗 (Longformer)
  - 全局 + 局部 (BigBird)
优势:
  - 加速 10x+
  - 长序列 (50K+)
```

### 40.9 异构 (Heterogeneous)

```text
定义: 不同类型的数据 / 模型
场景:
  - 多模态 (图/文/视频)
  - HF + LF 数据
  - 异构专家
方法:
  - 异构 attention
  - 异构 expert
  - 路由
代表: HyFormer, HHFT, HeMix
```

### 40.10 跨业务 (Cross-business)

```text
定义: 多个业务 (淘宝/天猫/闲鱼) 共享模型
优势:
  - 减少开发成本
  - 知识共享
方法:
  - 业务塔
  - 共享 + 业务 expert
代表: STORE, MTGR
```

## 41. 常见问题 (FAQ)

### 41.1 "GR 是什么?"

```text
GR = Generative Recommendation
= 把推荐任务建模成序列生成任务

类似:
  - NLP 的 GPT
  - 输入: 历史行为序列
  - 输出: 下一行为 (item / action)

区别于:
  - 传统推荐: DLRM (分类)
  - 序列推荐: DIN (注意力)
  - GR: 生成式
```

### 41.2 "SID 是什么?"

```text
SID = Semantic ID
= item 的语义化 token 表示

作用:
  - 把 item 从"ID"变成"token"
  - 才能用 Transformer / LLM-style 训练

例子:
  - 视频 123 → "12_345_67"
  - 这个 "12_345_67" 就是 SID

方法:
  - RQ-VAE (残差量化)
  - 多个残差层
  - 每层选最近的 code
```

### 41.3 "LLM4Rec 是什么?"

```text
LLM4Rec = LLM for Recommendation
= 用 LLM 做推荐

思路:
  - 把推荐变 NLP 任务
  - 用 LLM 统一多任务
  - zero-shot 能力

代表:
  - P5 (T5 推荐)
  - M6-Rec (M6 推荐)
  - TallRec (微调 LLM)
```

### 41.5 "GR 与 LLM 推荐的区别?"

```text
GR:
  - 序列生成 (item → SID → next SID)
  - 训练: Next SID prediction
  - 推理: beam search

LLM4Rec:
  - 文本生成 (用户行为 → 文本 → 推荐)
  - 训练: Next token
  - 推理: 生成文本

关系:
  - GR 是子集
  - LLM4Rec 是扩展
  - GR 强调"统一架构"
  - LLM4Rec 强调"通用能力"
```

### 41.6 "GR 适合我的业务吗?"

```text
适合:
  - 信息流 (字节)
  - 短视频 (快手)
  - 多业务 (阿里 / 美团)
  - 大规模 (亿级)

不适合:
  - 极小业务 (10万用户)
  - 单一场景 (单品类电商)
  - 实时性要求极高 (< 10ms)

判断:
  - 用户数 ≥ 1000 万 → 适合
  - 序列长度 ≥ 100 → 适合
  - 多任务 → 适合
  - 跨业务 → 适合
```

### 41.7 "GR 的最大挑战?"

```text
1. 工程门槛
   - 大集群
   - 复杂部署

2. 推理延迟
   - GR 生成慢
   - 需要优化

3. 数据需求
   - 长序列
   - 多任务标签

4. 评估难
   - 离线 + 在线
   - 业务指标
```

### 41.8 "GR 与 Scaling Law 关系?"

```text
GR 需要 Scaling:
  - 大模型 (HSTU 10B+)
  - 大数据 (10B+ 序列)
  - 大集群

Scaling 是 GR 的支撑:
  - 没有 scaling, GR 无法实用
  - Kaplan: 持续 scaling 有效
  - Chinchilla: compute-optimal

对 RecSys 启示:
  - 推荐需要 scaling
  - UniScale 是 RecSys scaling
```

### 41.9 "GR 与多模态?"

```text
多模态 GR:
  - 输入: 视频 / 图像 / 文本
  - 输出: 下一行为
  - 融合: 多模态 attention

代表:
  - HyFormer (字节)
  - (未来: 多模态 SID)

趋势:
  - 多模态是 2025 重点
  - GR + 多模态融合
```

### 41.10 "GR 与端侧?"

```text
端侧 GR:
  - 模型小 (< 1B)
  - 实时响应
  - 隐私保护

挑战:
  - 模型压缩
  - 推理加速
  - 量化

代表:
  - TokenMixer (字节)
  - (未来: 端侧 GR 专用)

趋势:
  - 端侧是 2025-2026 重点
  - 模型小型化
```
