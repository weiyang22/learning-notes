
## 1. 三大架构派系深度对比

### 1.1 Token Mixer 派 (注意力替代)

**核心思想**: 用 MLP/reshape 替换 self-attention, 提升 MFU, 降低显存

| 论文 | 关键改进 | 在线增益 | 部署规模 |
|------|---------|----------|----------|
| **RankMixer (字节)** | MLP-Mixer 风格 token 混合 + per-token FFN | +1.08% in-app time | 1B 模型, 抖音全量 |
| **TokenMixer-Large (字节)** | Mixing-and-Reverting + Per-token MoE | +2.98% GMV | **15B (offline) / 7B (online)** |
| **HHFT (阿里)** | 异构 Transformer 编码 (含 mixer 思想) | +0.6% GMV | 300M, 淘宝搜索 |
| **FuXi-α (华为)** | 多通道自适应注意力 | +5.10% listening | 华为音乐 |

**代表架构模式**:
```python
# 伪代码: Token Mixer Block (RankMixer / HHFT 风格)
def token_mixer_block(x):
    # Multi-head token mixing (替代 attention)
    split_x = split_heads(x)            # [B, H, T, D/H]
    mixed = mlp_mixer(split_x)            # O(T·D²), no attention
    x = revert(x, mixed)                 # 残差 + 信息回流

    # Per-token FFN
    x = per_token_swiglu(x)              # 每个 token 独立 FFN
    return residual_norm(x)
```

**优势**:
- MFU 4.5% → 45% (RankMixer)
- 100× 参数扩展, 同样延迟
- 硬件友好 (无 attention softmax)

**劣势**:
- 损失全局上下文建模
- 需配合其他模块 (如 STCA 的 target→history 注意力)

### 1.2 异构 Transformer 派 (共享 + 独立参数)

**核心思想**: 序列特征共享参数 (类似 LLM), 非序列特征 token-specific 参数

| 论文 | 异构粒度 | 在线增益 | 部署规模 |
|------|---------|----------|----------|
| **Hiformer (Google)** | 特征对变换矩阵 M_{i,j} | +2.66% 参与度 | Google Play |
| **OneTrans (字节)** | 序列共享 / 非序列独立 | +5.68% gmv/u | 抖音 Feeds/Mall |
| **MixFormer (字节)** | 完全统一 Transformer | 活跃天数 + | 抖音 |
| **HyFormer (字节)** | 全局 Token + 交替 Query 解码 | 显著 + | 抖音搜索 |
| **InterFormer (Meta)** | Interaction / Sequence / Cross 三子架构 | +0.15% NE + 24% QPS | Meta Ads |

**代表架构模式**:
```python
# 伪代码: 异构 Transformer (OneTrans 风格)
def heterogeneous_block(seq_tokens, nonseq_tokens):
    # 序列特征: 共享 Q/K/V/FFN (类似 LLM text tokens)
    seq_out = shared_transformer(seq_tokens)    # 单组权重

    # 非序列特征: 每个 token 独立权重
    nonseq_out = per_token_transformer(nonseq_tokens)  # 每 token 独立 QKV/FFN

    # 合并 + 残差
    return combine(seq_out, nonseq_out)
```

**优势**:
- 语义保留 (非序列 token 维持各自意义)
- 参数高效 (序列 token 共享)
- 扩展性强 (加新序列 token 不需要新参数)

**劣势**:
- 工程复杂 (两类 token 需要不同 kernel)
- 异构参数化对训练稳定性有挑战

### 1.3 稀疏激活派 (MoE / Memory)

**核心思想**: 总参数做大但单次激活保持小

| 论文 | 稀疏化机制 | 在线增益 | 部署规模 |
|------|-----------|----------|----------|
| **Wukong (Meta)** | FM stack (FM + linear) | (离线) | 637B+ params |
| **HSTU (Meta)** | Stochastic-length sparsity | +12.4% online | **1.5T params** |
| **MTGR (美团)** | HSTU + 保留 DLRM 交叉特征 | +1.31% CTR | 美团外卖 |
| **TokenMixer-Large (字节)** | Per-token MoE | +2.98% GMV | 15B 离线 |
| **SMES (快手)** | 渐进专家路由 (PER) + MTLB | +0.31% watch time | 4 亿 DAU |
| **MTmixAtt (美团)** | 多重 MoE (共享 + 场景特定) | +3.62% 支付 PV | 1B params |
| **MSN (字节)** | Product-Key Memory (PKM) | 显著 + | 抖音搜索 |
| **Kunlun (Meta)** | GDPA + HSP + MoE | +1.2% topline | Meta Ads |

**代表架构模式**:
```python
# 伪代码: Sparse MoE Block (SMES 风格)
def smes_block(x, scenario):
    # Stage 1: 任务共享 experts
    shared_score = sum_weighted([router(x, t) for t in tasks])
    shared_experts = top_k(shared_score, K_s)

    # Stage 2: 任务自适应 experts
    adaptive_experts = []
    for t in tasks:
        adaptive_experts.append(top_k(router(x, t) & ~shared_experts, K_a))

    # 去重激活
    activated = unique(shared_experts + adaptive_experts)

    # 计算
    return moe_forward(x, activated)
```

**优势**:
- 参数容量大, 推理成本相对低
- 个性化强 (per-token / per-scenario)
- Scaling law 验证充分 (HSTU, Wukong)

**劣势**:
- 工程复杂 (专家路由, 负载均衡)
- 通信开销大 (专家可能分布在不同 GPU)
- 训练稳定性挑战

## 3. 四大系统级创新 (通用杀手锏)

### 3.1 Request-Level Batching (RLB)

**核心思想**: 多目标 / 多请求共享用户侧编码

**使用论文**: STCA, OneTrans, MixFormer, HyFormer, HoMer

**架构模式**:
```python
# 伪代码: RLB
def request_level_batching(user_features, candidates_list):
    # 一次用户侧前向传播
    user_repr = user_encoder(user_features)  # O(1) per user

    # 多个候选共享用户表征
    scores = []
    for candidates in candidates_list:  # batched
        scores.append(cross_attention(user_repr, candidates))

    return scores  # 总计算: O(1) user + O(T) candidate
```

**收益**:
- STCA: 带宽 ↓84%, 吞吐 2.2×
- OneTrans: p99 延迟 ↓3.91%
- 整体: 跨论文平均提速 2-3×

### 3.2 Cross-Request KV Caching

**核心思想**: 跨请求 / 跨候选缓存用户 KV, O(1) 推理

**使用论文**: OneTrans, LONGER

**架构模式**:
```python
# 伪代码: Cross-Request KV Cache
def cached_inference(user_id, candidates):
    if user_id in cache:
        user_kv = cache[user_id]  # 复用
    else:
        user_kv = compute_user_kv(user_id)
        cache[user_id] = user_kv

    # 所有候选共享同一 user_kv
    scores = batched_cross_attn(user_kv, candidates)
    return scores
```

**收益**: 单次请求推理从 O(m·L) 降到 O(1)

### 3.3 Length Extrapolation (训练短, 推理长)

**核心思想**: 训练用短序列, 推理用长序列, 用外推能力

**使用论文**: STCA (5× 外推), LONGER (5000 token)

**架构模式**:
```python
# 伪代码: Length Extrapolation
def train_with_short_infer_long(model):
    # 训练: 随机短序列 (从 Beta(α, β) 采样)
    train_seqs = sample_from_beta(alpha=0.1, beta=1)  # 平均 2K

    # 推理: 长序列 (10K)
    test_seqs = full_length_sequences()  # 10K

    # 模型通过 RoPE 或 ALiBi 等机制自然外推
    return model
```

**收益**: STCA 用 1/3 训练成本捕获 80% 的 10K 收益

### 3.4 Context Parallelism (长序列切分)

**核心思想**: 长序列切分到多 GPU, 用 jagged tensor 支持变长

**使用论文**: HSTU-CP (Meta RecSys'25)

**架构模式**:
```python
# 伪代码: Jagged Tensor Context Parallelism
def cp_forward(sequence_jagged, cp_size):
    # 序列切分到 CP GPUs
    shards = jagged_all_gather(sequence_jagged, dim=seq_length)
    shards = even_split(shards, cp_size)

    # 各 GPU 独立 attention
    local_attn = []
    for gpu_id in range(cp_size):
        local_attn[gpu_id] = attention(shards[gpu_id])

    # Ring-based 通信汇总
    output = ring_gather(local_attn)
    return output
```

**收益**: HSTU-CP 支持序列长度 **3K → 16K** (CP=8), 缩放因子 1.33-1.55×

### 7.2 三大趋势预测

#### 趋势 1: **GR (生成式推荐) 全面取代 DLRM**

**预测**: 2026-2027 年, NTP + RL + 推理 将成为推荐训练标准范式

**预测**: 2027-2028 年, "One Model for All" 成为可能

### 16.1 模式 1: Token Mixer

**核心思想**: 用 MLP/reshape 替换 self-attention, 提升 MFU, 降低显存。

**代表论文**: RankMixer, TokenMixer-Large, HHFT, HeMix, FuXi-α (华为)

**架构模式**:
```python
# Token Mixer Block (RankMixer / HHFT 风格)
def token_mixer_block(x):
    # 1. Multi-head token mixing (替代 attention)
    split_x = split_heads(x)            # [B, H, T, D/H]
    mixed = mlp_mixer(split_x)            # O(T·D²), no attention
    x = revert(x, mixed)                 # 残差 + 信息回流

    # 2. Per-token FFN
    x = per_token_swiglu(x)              # 每个 token 独立 FFN
    return residual_norm(x)

# TokenMixer-Large (深层 + 残差修复)
def token_mixer_large_block(x, layer_idx):
    # 1. Mixing (MLP)
    mixed = mlp_mixer(x)

    # 2. Reverting (修复跨层 residual 错配)
    x = revert(x, mixed, layer_idx)

    # 3. Inter-Residual (稳定深层梯度)
    if layer_idx % N == 0:
        x = inter_residual(x)

    # 4. Sparse Per-token MoE (大模型扩展)
    x = sparse_per_token_moe(x)

    return residual_norm(x)
```

**优势**:
- MFU 大幅提升 (4.5% → 45% in RankMixer)
- 100× 参数扩展, 同样延迟
- 硬件友好 (无 attention softmax)

**劣势**:
- 损失全局上下文建模
- 需配合其他模块 (如 STCA 的 target→history 注意力)

**适用场景**: 算力瓶颈 + 短序列 (< 1K) + 单业务

### 16.2 模式 2: 异构 Transformer

**核心思想**: 序列特征共享参数 (类似 LLM), 非序列特征 token-specific 参数。

**代表论文**: HiFormer, OneTrans, MixFormer, HyFormer, FAT, MGDIN, HoMer, Kunlun

**架构模式**:
```python
# 异构 Transformer Block (OneTrans 风格)
def heterogeneous_block(seq_tokens, nonseq_tokens, layer_idx):
    # 1. 序列特征: 共享 Q/K/V/FFN (类似 LLM text tokens)
    seq_out = shared_transformer(seq_tokens)    # 单组权重

    # 2. 非序列特征: 每个 token 独立权重
    nonseq_out = per_token_transformer(nonseq_tokens)  # 每 token 独立 QKV/FFN

    # 3. 跨 token 交互 (不同 layer 不同方式)
    if layer_idx % 2 == 0:
        out = cross_attention(seq_out, nonseq_out)
    else:
        out = additive_fuse(seq_out, nonseq_out)

    return residual_norm(out)

# InterFormer (双向 Cross)
def inter_former_block(seq, nonseq, direction):
    if direction == "seq_to_nonseq":
        # 序列 → 非序列 attention
        return cross_attn(nonseq, seq, seq)
    elif direction == "nonseq_to_seq":
        # 非序列 → 序列 attention
        return cross_attn(seq, nonseq, nonseq)
```

**优势**:
- 语义保留 (非序列 token 维持各自意义)
- 参数高效 (序列 token 共享)
- 扩展性强 (加新序列 token 不需要新参数)

**劣势**:
- 工程复杂 (两类 token 需要不同 kernel)
- 异构参数化对训练稳定性有挑战

**适用场景**: 多模态特征 (序列 + 画像 + 上下文) + 中长序列 (1K-5K)

### 16.3 模式 3: 稀疏 MoE

**核心思想**: 总参数做大但单次激活保持小。

**代表论文**: SMES, MTmixAtt, EST, TokenMixer-Large (Per-token), Wukong, Kunlun (event-level)

**架构模式**:
```python
# Sparse MoE Block (SMES 风格, 渐进专家路由)
def smes_block(x, scenario):
    # Stage 1: 任务共享 experts
    shared_score = sum_weighted([router(x, t) for t in tasks])
    shared_experts = top_k(shared_score, K_s)

    # Stage 2: 任务自适应 experts
    adaptive_experts = []
    for t in tasks:
        adaptive_experts.append(top_k(router(x, t) & ~shared_experts, K_a))

    # 去重激活
    activated = unique(shared_experts + adaptive_experts)

    # 计算 + MTLB 负载均衡损失
    out = moe_forward(x, activated)
    return out

# MTmixAtt (多重 MoE, 自动特征分组)
def mtmix_att_block(x, n_groups=None):
    if n_groups is None:
        # AutoToken: 自动分组
        n_groups = auto_token_count(x)

    outputs = []
    for group in range(n_groups):
        # 共享 expert + 场景特定 expert
        shared = moe_forward(x, k=shared_k)
        scenario = moe_forward(x, k=scenario_k)
        outputs.append(shared + scenario)

    return aggregate(outputs)
```

**优势**:
- 参数容量大, 推理成本相对低
- 个性化强 (per-token / per-scenario)
- Scaling law 验证充分 (HSTU, Wukong)

**劣势**:
- 工程复杂 (专家路由, 负载均衡)
- 通信开销大 (专家可能分布在不同 GPU)
- 训练稳定性挑战

**适用场景**: 大模型 (10B+) + 多任务多场景 + 算力充足

### 16.4 模式 4: Memory 替代 MoE

**核心思想**: 用 Product-Key Memory (PKM) 或类似机制替代 MoE, 获得稀疏激活但更稳定。

**代表论文**: MSN (字节)

**架构模式**:
```python
# PKM (Product-Key Memory) Block
def pkm_block(x, n_keys=256, n_values=512, top_k=8):
    # 1. 双路 key 索引
    key_a = linear_a(x)  # [B, T, n_keys]
    key_b = linear_b(x)  # [B, T, n_keys]

    # 2. 笛卡尔积 → n_keys × n_keys 候选 value
    score = key_a.unsqueeze(-1) + key_b.unsqueeze(-2)  # [B, T, n_keys, n_keys]
    score = score.view(B, T, -1)  # [B, T, n_keys * n_keys]

    # 3. top-k 选 value
    top_scores, top_indices = topk(score, k=top_k)

    # 4. 查 value 表
    value_table = parameter([n_keys * n_keys, n_values])  # 稀疏参数
    values = value_table[top_indices]  # [B, T, top_k, n_values]

    # 5. 加权求和
    out = (values * top_scores.unsqueeze(-1)).sum(dim=-2)
    return residual_norm(out)
```

**优势**:
- 稀疏激活, 但比 MoE 更稳定
- 双路索引避免冲突
- 适合长尾物品 (Memory 容量大)

**劣势**:
- Memory 大小需要调优
- 训练不稳定 (PKM 在 NLP 中已较少用)

**适用场景**: 长尾物品多 + Memory 可容纳 + 中等规模 (1-5B)

### 16.5 模式 5: 长序列处理

**核心思想**: 用全局 Token、Length Extrapolation 或 Context Parallelism 处理 10K+ 序列。

**代表论文**: STCA, LONGER, HSTU-CP, HyFormer, LASER, Kunlun (Sliding Window)

**架构模式**:
```python
# STCA: O(L) target→history 交叉注意力
def stca_attention(target, history):
    # target: [B, 1, D] (单个目标)
    # history: [B, L, D] (L 长序列)

    # 1. Cross attention O(L) 而非 O(L²)
    # 标准 self-attention 是 O(L²)
    # target → history 是 O(L)
    scores = target @ history.transpose(-1, -2)  # [B, 1, L]
    attn = softmax(scores, dim=-1)
    out = attn @ history  # [B, 1, D]
    return out

# HSTU-CP (Jagged Tensor Context Parallelism)
def cp_forward(sequence_jagged, cp_size):
    # 序列切分到 CP GPUs
    shards = jagged_all_gather(sequence_jagged, dim=seq_length)
    shards = even_split(shards, cp_size)

    # 各 GPU 独立 attention
    local_attn = []
    for gpu_id in range(cp_size):
        local_attn[gpu_id] = attention(shards[gpu_id])

    # Ring-based 通信汇总
    output = ring_gather(local_attn)
    return output

# HyFormer 全局 Token
def global_token_block(history, n_global=64):
    # 1. 压缩到 n_global 个全局 token
    global_tokens = compress(history, n_global)  # [B, n_global, D]

    # 2. 双向 attention
    history_out = self_attention(history, kv=global_tokens)  # 历史关注全局
    global_out = self_attention(global_tokens, kv=history)  # 全局关注历史

    # 3. 拼接
    return concat(history_out, global_out)
```

**优势**:
- 处理 10K+ 序列
- STCA: 2.2× 吞吐, -84% 带宽
- HSTU-CP: 序列 3K → 16K
- HyFormer 全局 Token: O(N) 复杂度

**劣势**:
- 工程复杂 (CP 需要 jagged tensor)
- 全局 Token 可能丢失细节

**适用场景**: 长期用户行为建模 + 10K+ 序列 + 大模型

```python
def mdl_block(x, scenarios):
```

### 16.7 模式 7: GR + RL

**核心思想**: 用 RL (DPO/GRPO/HEPO/SA-GCPO) 对齐 GR 模型与长期价值。

**代表论文**: OxygenREC, OneRec V1/V2/Think, GPR, HiGR, MTGR

**架构模式**:
```python
# GR + DPO (OneRec V1)
def gr_dpo_loss(y_pos, y_neg, ref_logits):
    # 1. GR 模型输出 policy logits
    policy_logits = gr_model(y_pos)
    ref_policy_logits = ref_model(y_pos)

    # 2. DPO loss (隐式奖励)
    pos_ratio = policy_logits / ref_policy_logits
    neg_ratio = gr_model(y_neg) / ref_model(y_neg)

    loss = -log_sigmoid(beta * (log(pos_ratio) - log(neg_ratio)))
    return loss

# GR + GRPO (OneRec-Think)
def gr_grpo_loss(prompts, K=4):
    # 1. 同 prompt 采样 K 个 response
    responses = sample(gr_model, prompts, K)

    # 2. 计算每个 response 的奖励
    rewards = reward_model(responses)

    # 3. 组内归一化优势
    advantages = (rewards - rewards.mean()) / (rewards.std() + 1e-8)

    # 4. GRPO 损失
    loss = -mean(min(ratio * advantages, clip(ratio, 1-eps, 1+eps) * advantages))
    return loss

# GR + HEPO (GPR, 层次增强)
def hepo_loss(y_hierarchy, ref_logits):
    # 1. 多 token (层级) 价值对齐
    #   token 1: 大类 (一级类目)
    #   token 2: 中类 (二级类目)
    #   token 3: 小类 (三级类目)

    # 2. 各级 token 各自的 DPO/GRPO 损失
    l1 = gr_loss(y_hierarchy[:, 0])
    l2 = gr_loss(y_hierarchy[:, 1])
    l3 = gr_loss(y_hierarchy[:, 2])

    # 3. 加权求和 (层次权重)
    return alpha1 * l1 + alpha2 * l2 + alpha3 * l3
```

**优势**:
- 对齐长期价值 (CTR / 时长 / GMV)
- 层次对齐 (HEPO) 提升多 token 质量
- 与 SFT 配合而非替代

**劣势**:
- 奖励函数难设计 (reward hacking)
- 训练不稳定 (多任务 + RL)
- 计算成本高

**适用场景**: 端到端 GR + 长期价值优化

### 16.8 模式 8: 端到端 GR

**核心思想**: 检索 + 排序 统一为单个 GR 模型, 直接生成候选 ID。

**代表论文**: SORT, OxygenREC, OneRec V1/V2/Think/Foundation, GPR, HiGR, NEZHA

**架构模式**:
```python
# 端到端 GR (OneRec 风格)
def end_to_end_gr(user_history, candidates):
    # 1. 用户历史编码 (Encoder)
    user_repr = encoder(user_history)  # [B, D]

    # 2. 候选生成 (Decoder 自回归)
    candidate_ids = []
    for step in range(max_steps):
        # 上一步生成的 token 作为输入
        prev_ids = torch.tensor(candidate_ids) if candidate_ids else None

        # Decoder 输出
        logits = decoder(user_repr, prev_ids)  # [B, V]

        # 采样 (推理) / 贪心 (训练)
        next_id = sample(logits) if training else greedy(logits)
        candidate_ids.append(next_id)

    return candidate_ids

# NEZHA 投机解码加速
def nezha_speculative(user_history, draft_model, target_model):
    # 1. 小模型快速 draft
    draft_ids = draft_model.generate(user_history, n=5)

    # 2. 大模型并行 verify
    accepted = []
    for i in range(len(draft_ids)):
        target_logits = target_model.forward_one(user_history, draft_ids[i])
        draft_prob = draft_model.get_prob(draft_ids[i])
        target_prob = softmax(target_logits)[draft_ids[i]]

        # 接受概率
        accept_prob = min(1, target_prob / draft_prob)
        if random() < accept_prob:
            accepted.append(draft_ids[i])
        else:
            accepted.append(sample(target_logits))
            break

    return accepted
```

**优势**:
- 检索 + 排序统一 (节省召回成本)
- 受益于 LLM scaling law
- 推理增强 (Think, NEZHA) 提升质量

**劣势**:
- 训练成本高 (LLM 级)
- 推理延迟要求高 (NEZHA 投机解码才能 < 30ms)
- 冷启动仍需传统召回兜底

**适用场景**: 端到端重塑推荐 + LLM 资源充足 + 长期价值导向

## 17. 工业落地的 6 大共性挑战 (200+ 行)

> 24 篇论文揭示的工业落地共性挑战, 不分派系不分公司, 是 2025-2026 规模化推荐的核心难题。

### 17.1 挑战 1: 长序列的算力瓶颈

```text
问题: 10K+ 序列, 标准 self-attention O(N²) 不可接受
  - 10K × 10K = 1亿 entries, 单 batch 显存爆炸
  - 工业序列: 用户行为数百到数千, 部分长尾用户 10K+

现有方案 (从 24 篇提炼):
  - STCA: O(L) target→history 交叉注意力
  - HSTU-CP: Jagged Tensor Context Parallelism
  - LONGER: 全局 Token 压缩
  - HyFormer: 全局 Token + 交替 Query
  - LASER: SeqVault + 门控分段
  - Kunlun: Sliding Window Attention

未来趋势: 进一步压缩 + 系统优化 + CP/DP/TP 协同
```

### 17.2 挑战 2: MFU 偏低

```text
问题: 推荐模型 MFU 普遍 17-30%, 远低于 LLM 的 40-60%
  - 异构特征 (稀疏 ID + 稠密数值)
  - 不规则 shape (变长序列, jagged tensor)
  - 小 embedding + 大 FFN 比例失衡

现有方案:
  - RankMixer: 4.5% → 45% (Token Mixer 派)
  - OneRec V2: 28.8% 推理 MFU
  - Kunlun: 17% → 37% (GDPA + HSP + CompSkip)
  - HHFT: ~30% (300M 小模型)
  - HeMix: ~28% (800M 小模型)

关键洞察:
  - Token Mixer 是 MFU 提升的最大杠杆
  - 系统优化 (GDPA 类的 FlashAttention 融合) 是普适手段
  - 小模型 + 异构 比大模型 + Dense 更易达到高 MFU
```

### 17.3 挑战 3: 推理延迟约束

```text
问题: 线上 < 50ms p99, GR 模型替换 DLRM 必须维持延迟
  - DLRM: ~30-50ms (100 候选)
  - GR (LLM-style): 数百 ms (直接生成)
  - 必须用 NEZHA 投机解码 + 预计算 + KV 缓存

现有方案:
  - NEZHA: 1000ms → <30ms (投机解码)
  - OneTrans: 跨请求 KV 缓存, p99 ↓3.91%
  - STCA: 2.2× 吞吐
  - SORT: -45% 延迟
  - Action Token (GenRank): 94.8% 训练加速

关键洞察:
  - 投机解码是 GR 落地的核心
  - KV 缓存 + RLB + 预计算 是普适优化
  - 端到端 GR 必须 < 50ms, 否则业务不能接受
```

### 17.4 挑战 4: 业务多样性与冷启动

```text
问题: 同一公司多业务线, 冷启动持续存在
  - 字节: 抖音 Feeds/Mall/搜索/广告/直播/电商 - 6+ 业务
  - 阿里: 淘宝搜索/广告/电商 + AliExpress + 高德 - 6+ 业务
  - 美团: 外卖/闪购/酒旅 + 首页
  - 冷启动: 新用户 / 新物品

现有方案:
  - MDL: 场景 token 化 (场景作为模型输入)
  - SMES: 渐进专家路由 (多任务)
  - EST: Enhanced Sparse (场景特定 expert)
  - CDNet: 跨域 Network
  - OneMall: 跨场景电商 GR
  - LFM4Ads: 三塔 (UR + IR + CR)

关键洞察:
  - 多业务模型共享底层, 业务特定上层
  - 场景 token 化是字节系的方案
  - 跨域知识迁移 (CDNet) 是阿里系的方案
  - 冷启动需要兜底通道 (规则 / Bandit / 元学习)
```

### 17.5 挑战 5: 训练稳定性

```text
问题: 大模型 + 异构 + MoE 训练不稳定
  - Loss spike / 收敛慢 / 训练崩溃
  - 专家路由冷启动
  - 异构参数化梯度不一致

现有方案:
  - TokenMixer-Large: Inter-Residual + 辅助损失
  - SMES: MTLB (Multi-Task Load Balancing)
  - Switch Transformer: 容量因子 + 辅助损失
  - OneRec: 23.7% MFU 训练稳定
  - AdamW + warmup + cosine decay

关键洞察:
  - Inter-Residual 是 TokenMixer-Large 训练稳定的关键
  - MoE 必须有负载均衡损失 (aux loss)
  - 异构架构需要分组学习率 (shared 慢, per-token 快)
```

### 17.6 挑战 6: 长期价值对齐

```text
问题: 推荐优化短期点击 vs 长期用户价值
  - CTR 优化 → 信息茧房
  - 用户 7/30 日留存下降
  - GMV 短期增长但用户长期流失

现有方案:
  - RL 训练 (DPO/GRPO/HEPO/SA-GCPO)
  - 奖励函数: 时长 + GMV + 多样性 + 留存
  - OneRec V2 GBPO: 用户反馈 + 时长
  - OxygenREC SA-GCPO: 格式 + 排序 + 多样性
  - Multi-Token Prediction (MTP, GPR) + HEPO: +17.9% MTP gain

关键洞察:
  - RL 是长期价值对齐的核心手段
  - 奖励函数需要精心设计 (避免 hacking)
  - 多 token 预测 + 层次对齐 是未来方向
```

### 23.7 补充: 决策树

```text
我要做 GR 项目 →

├─ 信息流 / 短视频 → 字节思路 (TokenMixer + 蒸馏)

├─ 本地生活 → 美团思路 (MTGR + 多任务)
└─ 多元 → 腾讯思路 (稳健架构)

算力?
├─ 超大 (10K GPU) → HSTU / OneTrans
├─ 大 (1K GPU) → STORE / MTGR
├─ 中 (100 GPU) → MixFormer / EST
└─ 小 (10 GPU) → MSN / 蒸馏

数据规模?
├─ 10B+ → GR 范式
├─ 1B-10B → 统一架构
├─ 100M-1B → 蒸馏
└─ <100M → 经典推荐

延迟要求?
├─ ≤10ms → 蒸馏 / 量化
├─ ≤50ms → 中等模型
└─ ≤200ms → 大模型
```
