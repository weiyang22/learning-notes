### 2.1 百度（Baidu）— 3 篇

#### 2.1.1 GRAB: An LLM-Inspired Sequence-First Click-Through Rate Prediction Modeling Paradigm
- **arXiv**: [2602.01865v2](https://arxiv.org/abs/2602.01865)
- **公司 / 作者**：Baidu Search Ads CTR Ranking Team（Shaopeng Chen, Chuyue Xie, Huimin Ren, Shaozong Zhang 等）
- **发表**：2026-02（已全面生产部署）
- **核心问题**：传统 DLRM 在长序列建模与泛化能力上达到瓶颈；现有 GR 模型忽略数据异质性导致性能受限
- **方法（2-3 句）**：
  1. **Causal Action-aware Multi-channel Attention (CamA)**：在 user behavior 序列中同时建模时间动态与具体 action 信号
  2. **Sequence-Then-Sparse (STS) Training**：解耦 dense params 与 sparse embedding 的优化梯度冲突
  3. 端到端生成式框架，把所有训练分布式打包到序列化序列中
- **结果**：
  - Offline: 在 Baidu 工业数据集上比 DIN/SIM-Soft/TWIN/HSTU/LONGER 提升 0.19% 相对 AUC
  - Online A/B: 主流量 10% × 一个月，CPM +3.05%、CTR +3.49%，与原 DLRM 推理成本持平
- **Scaling 行为**：模型 AUC 随 dense 参数（Transformer 层数 / 头数 / 维度）和行为序列长度单调近乎线性提升，无饱和
- **Why it matters**：百度首次完整公开**生产级 CTR 生成式排序**全链路——CamA + STS + L20/H20 推理优化，补充了百度在第9章的空白。

---

#### 2.1.2 COBRA: Sparse Meets Dense — Unified Generative Recommendations with Cascaded Sparse-Dense Representations
- **arXiv**: [2503.02453v1](https://arxiv.org/abs/2503.02453) / NeurIPS 2025
- **公司 / 作者**：Baidu Inc.（Yuhao Yang, Zhi Ji, Zhaopeng Li 等）
- **核心问题**：纯稀疏 Semantic ID（如 TIGER）损失细粒度相似度建模，纯 dense retrieval 存储 / 算力代价大
- **方法（2-3 句）**：
  1. **Cascaded Organized Bi-Represented generAtive retrieval**：先生成 sparse ID 作 coarse sketch，再以 sparse ID 为条件生成 dense vector 作 fine detail
  2. 端到端训练，通过对比学习动态 refinement dense 表示
  3. **BeamFusion** 推理机制：把 beam search 概率与 dense KNN 分数融合，控制多样性
- **结果**：
  - Offline：Recall@500 提升 42.2%（去除 dense），Recall@800 提升 36.1%（去除 BeamFusion）
  - Online A/B：百度广告平台（≥2 亿日活）Conversion +3.60%、ARPU +4.15%
- **Why it matters**：直接与字节的 Kuaishou 双向竞争，统一召回+粗排的尝试，工业级 Sparse+Dense 范式典范。

---

#### 2.1.3 LASAR: Latent Adaptive Semantic Aligned Reasoning for Generative Recommendation
- **arXiv**: [2605.10207v1](https://arxiv.org/abs/2605.10207)
- **公司 / 作者**：Beihang University + Baidu（Yiwen Chen, Fuwei Zhang, Deqing Wang 等）
- **核心问题**：现有 GenRec 仅基于浅层文本特征（TIGER RQ-VAE 量化），缺乏 latent semantic 信息，难做 reasoning
- **方法**：在 latent space 用 LLM（Beihang）做"adaptive semantic aligned reasoning"，将 latent reasoning 与 SIDs 对齐
- **Why it matters**：是百度+北航首个 LLM reasoning 与 GenRec 融合的论文，预示 GR 进入 Reasoning 时代。

### 2.2 京东（JD.com）— 4 篇

#### 2.2.1 OxygenREC: An Instruction-Following Generative Framework for E-commerce Recommendation
- **arXiv**: [2512.22386v1](https://arxiv.org/abs/2512.22386)
- **公司**：JD.com（Xuegang Hao, Ming Zhang, Alex Li 等 30+ 作者）
- **核心问题**：传统 GR 缺乏复杂意图的演绎推理能力；现有方案多场景各自训练，资源利用低
- **方法**：
  1. **Fast-Slow Thinking** 框架：Fast path 处理常规，Slow path 调 LLM 推理
  2. 单 backbone 多场景服务（多任务生成）
  3. World knowledge 注入，deductive intent reasoning
- **结果**：京东核心推荐场景全量部署，订单量与 GMV 显著提升
- **Why it matters**：京东 Oxygen AI 全栈首次完整公开，是国内为数不多的**单一 backbone + LLM 推理 + 多场景**实践。

---

#### 2.2.2 GenR-PO: Generative Retrieval with Preference Optimization for E-commerce Search
- **arXiv**: [2407.19829v2](https://arxiv.org/abs/2407.19829)
- **公司 / 作者**：JD.com + Tsinghua SIGS（Mingming Li, Huimu Wang, Zuxu Chen 等）
- **核心问题**：E-commerce 短查询转长 item title 生成困难；noise 标题、长尾查询、可解释性差
- **方法**：
  1. **Multi-span Identifier**：把 query-to-title 任务转换为 query-to-multi-span，简化生成
  2. SFT + DPO 偏好对齐，约束 beam search 保证 span 在 inventory 中
- **结果**：JD 真实数据集 + 在线 A/B，长尾 query 转化收益显著
- **Why it matters**：京东搜索的 GR-first 范式；与字节 OneSearch、快手 OneSearch 形成对比。

#### 2.2.3 GRAM: Generative Retrieval and Alignment Model
- **arXiv**: [2504.01403](https://arxiv.org/abs/2504.01403) / WWW 2025
- **公司**：JD.com（Pang Ming, Yuan Chunyuan, He Xiaoyu 等）
- **核心问题**：Sparse ID 缺乏 LLM world knowledge，product-based identifier 与 query 词分布错位
- **方法**：
  1. 联合训练 query + product 文本 → 生成共享 text identifier codes，co-alignment 策略
  2. query-product 评分机制 + 实时缓存 → 取代传统召回 + 粗排
- **结果**：5% 流量 A/B（JD 搜索广告），GMV / CTR 显著正收益，每日数亿次检索调用
- **Why it matters**：JD 落地大模型时代召回的标志性论文，与字节 OneSearch 不同路线。

---

#### 2.2.4 OCP: Orthogonal Constrained Projection for Sparse Scaling in Industrial Commodity Recommendation
- **arXiv**: [2603.18697v1](https://arxiv.org/abs/2603.18697)
- **公司**：JD.com
- **核心问题**：当 Item-ID 词表从 1.78 亿扩到 10 亿时，sparse embedding 会出现 collapse、overfitting 长尾
- **方法**：对 embedding 投影施加**正交约束 (Orthogonality)**，减少与高基数特征的共线性
- **结果**：
  - JD.com 5 天 A/B：UCXR **+12.97%**，订单量 +13.07%，GMV +8.95%
  - 同时适用于 OxygenREC 生成式检索 + 传统 DLRM 排序
- **Why it matters**：罕见的"工程级 sparse scaling 实战论文"，填补第09章对**sparse scaling 上限**探讨的空白。

#### 2.2.5 (JDRec 2024 AAMAS)
- **arXiv**：AAMAS 2024
- **公司**：JD.com + Tsinghua
- **核心问题**：组合式推荐中的 list 评估偏差
- **方法**：Actor-Critic 强化学习框架 + bootstrap 初始化
- **结果**：CTR +2.6%，平台价值 +5.03%
- **Why it matters**：JD 排序阶段强化学习在线部署代表作；与字节 OneRec DPO 形成对照。

### 2.6 B站（Bilibili）— 1 篇

#### 2.6.1 Constraint-Aware Generative Re-ranking for Multi-Objective Optimization in Advertising Feeds
- **arXiv**: [2603.04227v1](https://arxiv.org/abs/2603.04227)
- **公司 / 作者**：Bilibili Inc.（Chenfei Li, Hantao Zhao, Weixi Yao, Ruiming Huang, Rongrong Lu 等）
- **核心问题**：广告 feeds 的 constrained combinatorial optimization（收入 + 用户体验），并避免生成式 reranking 的高延迟
- **方法**：
  1. **CGR（Constraint-Aware Generative Re-ranking）**：把 constrained optimization 转为 bounded autoregressive decoding
  2. 生成与 reward 估计网络合一
  3. **Constraint-aware Reward Pruning**：在 decoding 中嵌入约束剪枝
- **结果**：
  - Offline：NDCG@10 比 PRM 提升 2-3%
  - Online A/B：日请求超 10 亿，推理延迟降低 **85%** 以上
- **Why it matters**：B站首篇 GenRec 广告重排论文，"约束 + 列表生成" 的工程范式，补充了第9章对约束型广告 GenRec 的空白。

## 3. 国际公司新论文（14 篇）

### 3.1 Google / YouTube（Alphabet）— 5 篇

#### 3.1.1 PLUM: Adapting Pre-trained Language Models for Industrial-Scale Generative Recommendations (YouTube)
- **arXiv**: [2510.07784v1](https://arxiv.org/abs/2510.07784)
- **公司**：Google / YouTube（R. He, Lukasz Heldt, Lichan Hong, Raghunandan H. Keshavan, Shifan Mao, Nikhil Mehta 等）
- **核心问题**：如何把 LLM 预训练红利迁移到工业级 GR
- **方法**：
  1. **SIDv2** 增强版 item tokenization
  2. **Continued Pre-training (CPT)** 在领域数据上
  3. SFT 对齐生成式检索
  4. 推理：1024 TPU v6e 训练 MoE-110M/370M/900M/3B 系列
- **结果**：
  - 训练成本与 production Transformer (LEM) 相当（100x dense param 但更快收敛）
  - 4.2B total params / 900M activated 达到最佳
  - Online 部署在 YouTube 长期视频 + Shorts 检索
- **Why it matters**：YouTube 首次完整公开 LLM-CPT 用于 GR 的工程细节，是 LinkedIn LiGR 的对手方法。

#### 3.1.2 STATIC: Vectorizing the Trie — Efficient Constrained Decoding for LLM-based Generative Retrieval
- **arXiv**: [2602.22647v1](https://arxiv.org/abs/2602.22647)
- **公司**：Google / YouTube
- **核心问题**：TPU/GPU 上的 constrained decoding 在 trie 遍历时有严重 latency penalty
- **方法**：把 prefix tree 拍扁为静态 CSR（Compressed Sparse Row）矩阵，做全向量化稀疏矩阵运算
- **结果**：
  - 20M vocabulary 约束下 latency overhead 仅 **0.033ms/step（+0.25%）**
  - 比 CPU trie **948× speedup**，比 binary-search baseline **47-1033× speedup**
  - Online：+5.1% 7-day fresh video views，+2.9% 3-day fresh views
- **Why it matters**：YouTube 公开 constraint-aware decoding 的硬件-软件协同最佳实践，工业级可复用。

#### 3.1.3 Self-Evolving Recommendation System: End-to-End Autonomous Model Optimization with LLM Agents (YouTube)
- **arXiv**: [2602.10226v1](https://arxiv.org/abs/2602.10226)
- **公司**：Google / YouTube
- **核心问题**：传统 A/B 工程师迭代太慢，需 LLM Agent 自主发现结构创新
- **方法**：
  1. **Offline Agent**（Inner Loop）：proxy metric 假设生成
  2. **Online Agent**（Outer Loop）：DAG 异步部署 + 业务指标验证
  3. Closed-loop "Think-Code-Verify"
  4. 基于 Gemini 2.5 Pro family 的 MLE Agent
- **结果**：YouTube 多个场景成功上线
- **Why it matters**：AI Agent for RecSys 的标志性论文，预示 Agent-as-MLE 工作流。

#### 3.1.4 LRF: Learned Ranking Function with Long-Term Rewards (YouTube)
- **arXiv**: [2408.06512](https://arxiv.org/abs/2408.06512)
- **核心问题**：slate optimization for long-term user satisfaction
- **方法**：MDP + Cascade Click Model + constrained optimization (dynamic linear scalarization)
- **结果**：YouTube Watch Page 首发，Home + Shorts 跟进；top-line +0.66%
- **Why it matters**：长 reward slate 优化的早期名作，可与第9章 HisRec、RL 应用对照。

#### 3.1.5 Beyond Item Dissimilarities: Diversifying by Intent in Recommender Systems (YouTube)
- **arXiv**: [2405.12327](https://arxiv.org/abs/2405.12327) / KDD 2025
- **核心问题**：用户长期兴趣被"短视重复"压制，缺乏 user intent 级别的多样化
- **方法**：posterior 信念更新 intent，序列选择确保 intent 多样性
- **结果**：YouTube 多场景 live exp，DAU + 整体享乐度 ↑
- **Why it matters**：YouTube 多样性 + 长 reward 的最佳实践。

### 3.2 Amazon — 3 篇

#### 3.2.1 Rufus: Amazon Generative AI-Powered Shopping Assistant
- **来源**：Amazon Science Blog 2024-10 + AWS ML Blog
- **作者**：Amazon Rufus Team
- **核心问题**：电商"买什么"问答 + product compare + recommendation
- **方法**：
  1. **Custom LLM specialized for shopping**（训练数据：Amazon 全 catalog + 评论 + Q&A + Web）

### 4.1 DIN: Deep Interest Network for Click-Through Rate Prediction
- **arXiv**: [1706.06978](https://arxiv.org/abs/1706.06978) / AAAI 2018
- **公司 / 作者**：Alibaba Group（Guorui Zhou, Chengru Song 等）
- **核心问题**：固定长度 user representation 是 embedding&MLP 瓶颈，无法捕捉用户多兴趣
- **方法**：**Local Activation Unit** — 用候选 ad 计算与历史行为的 attention 权重，自适应生成 user 兴趣向量；同时引入 mini-batch aware regularization + Dice 激活
- **结果**：阿里展示广告 CTR **+10.0%**、RPM **+3.8%**（30 天 A/B）
- **Why it matters**：CTR 行为序列建模奠基之作，几乎所有后续 GR 都依赖 DIN 的 target-attention 思路。

### 4.2 DIEN: Deep Interest Evolution Network for Click-Through Rate Prediction
- **arXiv**: [1809.03672](https://arxiv.org/abs/1809.03672) / AAAI 2019
- **公司**：Alibaba（Guorui Zhou 等）
- **核心问题**：用户兴趣是 latent 的，并会随时间漂移
- **方法**：
  1. Interest Extractor（GRU + auxiliary loss：用下一行为监督当前 hidden state）
  2. Interest Evolving Layer（**AUGRU**：attention 注入 GRU 更新门）
- **结果**：CTR **+20.7%**（淘宝显示广告）
- **Why it matters**：把 target attention 扩展到序列演变，是 BST/SIM/MIM 共同祖先。

### 4.3 SIM: Search-based User Interest Modeling (Alibaba 2020)
- **公司**：Alibaba（Qi Pi 等）
- **核心问题**：DIN/DIEN 受限于短行为序列

- **Why it matters**：后续 TWIN、SDIM 的直接祖先。

### 4.4 TWIN V1 & V2: Two-stage Interest Network (Kuaishou)

- **V2 arXiv**：[2407.16357](https://arxiv.org/abs/2407.16357) / CIKM 2024

- **KDD 2025**（引用页 DOI）
- **核心问题**：LLM-based GR 推理慢
- **方法**：Register tokens 减少 KV cache + 复用
- **Why it matters**：KDD 2025 工业 GR 加速模型，对照 LinkedIn LiGR。

---

### 5.2 SIGIR 2025

#### 5.2.1 SETRec: Order-agnostic Identifier for LLM-based Generative Recommendation
- **arXiv**: [2502.10833](https://arxiv.org/abs/2502.10833) / SIGIR 2025
- **核心问题**：现有 token-sequence ID 存在 local optima + 生成慢
- **方法**：**Set Identifier** 范式 — 每个 item 表示为 order-agnostic tokens 集合（CF + 语义）
  1. Sparse attention mask（删除 token 间 attention）
  2. Query-guided simultaneous generation
- **结果**：4 数据集平均 **15×, 11×, 18×, 8× 速度提升**，Qwen 1.5B-7B 持续 scaling
- **Why it matters**：从"序列 token"到"集合 token"的设计升级，预示 GR ID 范式下一步演进。

#### 5.2.2 Fast: Unified Search and Recommendation Framework Based on Multi-Scenario Learning
- **SIGIR 2024**（已收录 24 篇之外）由 JD.com Liu Jinhan 等
- **方法**：全局标签空间多任务层（GLMT）+ S&R 视图分场景
- **结果**：京东 7Fresh UCVR +2.85-3.35% / UCTR +1.05-1.17%
- **Why it matters**：京东搜索推荐统一建模原始论文。

#### 5.2.3 Towards Principled Learning for Re-ranking in Recommender Systems
- **SIGIR 2025**（Ant Group）
- **方法**：引入 Convergence Consistency + Adversarial Consistency 两条原则
- **Why it matters**：Re-ranking 训练原则化的代表性探索。

## 9. 引用与延伸（按主题分）

### 9.1 GenRec 基础

> **TIGER (NeurIPS 2023)** → HSTU (ICML 2024) → COBRA / SETRec / DeepInterestGR → OneRec-V2 / PLUM / PinRec / LiGR
> 这是从"单品语义 ID"到"端到端生成 + LLM 化 + 多场景化"的完整演进路径。

### 9.2 GenRec + RL

> OneRec V1 (DPO) → OneRec V2 (GBPO + 真实反馈) → DeepInterestGR (Interest-Aware Reward) → IntSR (动态负采样)
> RLHF 路线：从纯 RM → 真实用户反馈 → 自我演进。

### 9.3 GenRec + 跨场景

> LASAR / IntSR (S+R 统一) / USR / GRAM / Semantic IDs for Joint S&R
> 多家公司共同探索 Joint S&R。

### 9.4 稀疏 scaling

> DCN (Google 17') → DeepFM (Huawei 17') → xDeepFM (MSRA 18') → Wukong (Meta 24') → OCP (JD 26') → Embedding Collapse (24')
> "sparse embedding 是不是 GenRec 的天花板"，这是 GenRec 时代核心张力之一。

### 9.5 多目标 / 多任务

> ESMM (Alibaba 18') → MMoE (Google 18') → PLE (Tencent 20') → HeMix / CDNet（第9章）→ Wukong → LiRank
> 多目标"和谐"问题是工业难点。

### 9.6 LLM 迁移

> TIGER → PLUM (LLM-CPT) → STATIC (TPU trie) → LASAR (Latent reasoning) → SETRec (Order-agnostic) → Self-Evolving (Agent)
> 2025-2026 的 GenRec 已经从"用 transformer"演进到"训练 LLM-as-MLE"。

### 9.7 端到端

> OneRec V1 (MoE encoder-decoder) → OneRec V2 (Lazy decoder) → Feed SR (LinkedIn interleave) → PLUM (CPT+SFT) → RaG (Video-Gen)
> "端到端 + RL + LLM 对齐"是长期主线。

### 9.8 推理与硬件协同

> M-FALCON (Meta) → LoRA / Quantize → STATIC (Google TPU trie) → Continuous batching (Rufus) → Parallel decoding (Rufus)
> 工业 GR 的"每秒 QPS × 万亿参数"挑战还未结束。

## 附录 A: 端到端生成式推荐 vs DLRM 的本质差异

### 1. 架构差异

```text
DLRM 范式 (传统):
[用户特征] + [物品特征] + [上下文] -> [特征交叉] -> [MLP] -> [CTR]
                         ↑
              [Embedding Lookup] -> [向量]

[用户行为序列] -> [DIN/SIM] -> [用户兴趣]
              ↓
            [与候选拼接] -> [预测]

端到端生成式范式:
[用户历史] + [候选] -> [统一 Transformer] -> [CTR/CVR/...]
                                  ↑
                          [SID Embedding]

所有特征都通过 Transformer 学习交互, 没有显式的特征交叉 / 注意力池化.
```

### 2. 训练目标差异

**DLRM**:
- 主损失: BCE on CTR label
- 辅助: 各种正则化
- 无序列建模目标

**端到端生成式**:
- 主损失: BCE
- 辅助: Next SID prediction (类似 GPT 的 next token)
- 多任务: CTR + CVR + 长期价值

### 3. 推理差异

**DLRM**:
- 用户侧: 一次前向得到用户表示
- 物品侧: 一次前向得到物品表示
- 点积相似度
- 延迟低

**端到端生成式**:
- 用户侧: 一次 Transformer 前向
- 物品侧: 预计算 SID Embedding
- 注意力机制
- 延迟较高, 需要优化

### 4. 数据效率差异

**DLRM**:
- 100B 样本足够
- 数据越多越好, 但有 diminishing returns

**端到端生成式**:
- 100B 样本不够
- 需要 1T+ 样本才能发挥威力
- Scaling law 明显

## 附录 D: 端到端推荐系统的训练稳定性

### 训练不稳定的常见原因

1. **梯度爆炸**: 深层 Transformer, 序列很长
2. **Loss spike**: 数据分布突变
3. **NaN/Inf**: 数值不稳定

### 解决策略

1. **梯度裁剪**: torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
2. **学习率 warmup**: 前 N 步从 0 升到目标
3. **Mixed precision**: bf16 训练
4. **梯度累积**: 等效大 batch
5. **Loss spike 处理**: 检测到 spike 时跳过该 batch
6. **EMA**: 参数指数滑动平均

### 训练监控 checklist

- 训练 loss 曲线平滑
- 验证 loss 跟着下降
- 梯度 norm < 阈值
- 学习率按 schedule 变化
- 显存利用率 < 95%
- GPU 利用率 > 70%

## 附录 E: 推理优化关键技术

### 1. KV-Cache
- 已生成的 KV 缓存, 只算新 token
- 显存: O(L * N * D)
- 优化: MQA / GQA / MLA

### 2. 投机解码 (Speculative Decoding)
- 小模型 draft, 大模型 verify
- 加速 2-3x, 质量保持

### 3. 连续批处理 (Continuous Batching)
- 请求级别动态调度
- 吞吐提升 10-20x

### 4. 量化 (INT8 / INT4)
- INT8: 4x 显存, 精度损失 <1%
- INT4: 8x 显存, 精度损失 ~2%
- GPTQ / AWQ / SmoothQuant

### 5. PagedAttention (vLLM)
- 分页管理 KV 显存
- 碎片化优化

## 附录 F: 业务落地常见问题

### Q: 我的业务数据量不够 100B, 还能用端到端推荐吗?
A: 可以. 用更小的模型 (100M-1B), 更短的序列 (100-300), 仍然能跑. 关键是统一架构, 不一定是 scaling.

### Q: 端到端推荐对工程师要求更高吗?
A: 是的. 需要懂 Transformer 原理, 分布式训练, 推理优化. 建议团队至少 2-3 个 LLM 背景的工程师.

### Q: 怎么评估端到端推荐效果?
A: 用 offline AUC + online A/B test. offline 提升 0.3-1% AUC 通常对应 online 1-5% CTR 提升.

### Q: 端到端推荐的 ROI 如何?
A: 大型业务 (>1B 用户) ROI 显著. 小型业务 ROI 不明显, DLRM 足够.

### Q: 推理延迟如何保证?
A: 用 INT8 量化 + 投机解码 + 连续批处理. 典型 P99 50-100ms.

## 附录 J: 工业实践 FAQ

### Q1: DLRM 还能用多久?
A: 至少 5 年. 大部分公司仍在用 DLRM 变体. 端到端是趋势但不是必须.

### Q2: HSTU 和 OneTrans 哪个更好?
A: 各有所长. HSTU 是 Meta 的工业方案, OneTrans 是字节的. 选适合你业务的.

### Q3: 端到端推荐的工程难点?
A: 训练资源, 推理延迟, 冷启动. 用量化 + cache + 蒸馏解决.

### Q4: RL 在推荐中必须用吗?
A: 不是必须. 但 RL 优化长期价值有理论优势. 业务规模大时 ROI 显著.

### Q5: 多模态推荐必须用吗?
A: 不是必须. 但物品有图像 / 视频时, 多模态提升明显.

### Q6: 如何判断是否需要迁移到端到端?
A: 当 DLRM 优化空间 < 0.1% AUC, 或者训练数据 > 100B, 或者业务要求长期价值.
