## 0. 一句话总结

> **LLM 与 GenRec 必将融合,但融合不是"用 LLM 替代 GenRec",而是"LLM 增强 GenRec 的认知层 + GenRec 提供 LLM 的工业层";最终目标是统一的"基础智能 + 业务表征"模型,3-5 年内见到原型。**

## 1. 为什么需要融合

### 1.1 单一范式的局限

#### 1.1.1 LLM 单独的局限

| 局限 | 描述 | 影响 |
| :--- | :--- | :--- |
| 无法实时更新 | 训练一次数月 | 用户兴趣变化追不上 |
| 输出长 | 数十-数千 token | 推荐链路容不下 |
| 成本高 | 单 token $0.001 | 千亿请求不可承受 |
| 业务信号弱 | 主要是文本 + 通用 | 推荐指标不优 |
| 私有知识 | 互联网数据 | 用户行为缺失 |
| 冷启动 | 新场景缺乏 | 需要快速适应 |

LLM 的根本问题:**通用智能强, 但业务决策弱**。

#### 1.1.2 GenRec 单独的局限

| 局限 | 描述 | 影响 |
| :--- | :--- | :--- |
| 理解力弱 | 不擅长语义推理 | 难处理多义 / 上下文 |
| 创意缺乏 | 只能基于历史 | 难推荐新兴趣 |
| 自然语言交互 | 不支持 | 用户不能"说话"推荐 |
| 跨场景 | 局限于单一业务 | 跨业务难以统一 |
| 解释性弱 | 模型黑盒 | 不能给出"为什么推荐 X" |
| 上下文利用 | 仅行为数据 | 文本搜索 query 丢失 |

GenRec 的根本问题:**业务决策强, 但通用智能弱**。

#### 1.1.3 互补性

| 维度 | LLM 优势 | GenRec 优势 |
| :--- | :---: | :---: |
| 语义理解 | ✓✓✓ | ✓ |
| 推理能力 | ✓✓✓ | ✗ |
| 多轮交互 | ✓✓ | ✗ |
| 实时决策 | ✗ | ✓✓✓ |
| 业务 ROI | ✗ | ✓✓✓ |
| 在线延迟 | ✗ | ✓✓✓ |
| 数据效率 | ✗ | ✓✓✓ |
| 跨任务 | ✓✓✓ | ✓ |

互补结果是: **LLM 做"思考", GenRec 做"行动"**。

### 1.2 业务侧推力

#### 1.2.1 用户的统一体验诉求

现代用户希望:

- "我搜了 X, 给我推 X 相关 + 我可能也喜欢的" → **搜索 + 推荐统一**
- "为什么给我推这个?" → **可解释**
- "我想要类似但更便宜的" → **多轮对话**
- "我换新手机了, 怎么还推荐老视频" → **实时理解**

LLM 能理解语义, GenRec 能给出精准结果。**只有融合, 才能完整满足**。

#### 1.2.2 公司的成本压力

维持两套独立系统 (LLM 服务 + GenRec 服务):

- 两套 GPU 集群
- 两套人才
- 两套运维
- 不能复用成果

融合后:

- 共享 GPU 推理框架
- 共享人才
- 跨任务迁移
- 模型可复用

**ROI 显著提升**。

#### 1.2.3 监管的压力

欧盟 AI Act / 美国相关法规要求:

- 可解释性 (LLM 优势)
- 数据保护 (GenRec 优势)
- 多场景统一治理

融合后才能整体合规。

### 1.3 技术侧的推力

#### 1.3.1 架构趋同

| 维度 | LLM | GenRec |
| :--- | :---: | :---: |
| 主架构 | Transformer | Transformer |
| 训练目标 | Next token | Next SID |
| 优化方法 | AdamW | AdamW |
| 推理框架 | vLLM | 自研 (但相同思路) |

**架构趋同 → 容易融合**。

#### 1.3.2 数据趋同

- LLM 开始加入行为数据 (RLHF)
- GenRec 开始加入文本 / 图像 embedding
- 多模态数据是融合的天然土壤

#### 1.3.3 计算范式趋同

- LLM 用 speculative decoding, GenRec 用 trie
- LLM 用 prefix caching, GenRec 用 cross-request KV
- LLM 量化 INT4, GenRec 量化 INT8

工程范式趋同, 融合有共同的工具基础。

### 1.4 不融合的"半融合"陷阱

如果融合得太浅 (只是把两个模型串起来), 会带来:

| 陷阱 | 表现 | 解决 |
| :--- | :--- | :--- |
| 工程复杂 | 两套独立系统 | 共享基础设施 |
| 维护成本翻倍 | 团队 / 监控 / 故障 | 团队融合 |
| 性能瓶颈 | 两套串联延迟 | 一体化推理 |
| 收益不明 | 业务 lift 不显著 | 明确业务目标 |

融合必须**深度**, 不是简单"LLM 套 GenRec"。

## 2. 当前融合尝试

### 2.1 LLM-as-Feature-Encoder

#### 2.1.1 思路

用 LLM 把文本 / 多模态输入编码成向量, 作为 GenRec 的额外特征输入。

#### 2.1.2 公式

$$
\mathbf{x}_\text{enhanced} = [\mathbf{x}_\text{behavior}; \text{LLMEncode}(\mathbf{x}_\text{text})]
$$

其中 LLMEncode 是 frozen LLM (通常是 1B-7B)。

#### 2.1.3 案例

| 公司 | 实现 |
| :--- | :--- |
| 阿里妈妈 | 用 Qwen 编码 query / item 文本 |
| 美团 | 用 LLM 编码商品详情 + 评论 |
| 字节抖音 | 用 LLM 编码视频标题 / 描述 |
| 小红书 | 用 LLM 编码笔记文本 |
| 京东 | 用 LLM 编码商品描述 + 评论 |

#### 2.1.4 工程细节

- **冻结 LLM**: 不参与 GenRec 训练, 节省算力
- **离线编码**: 提前算好, 在线只读
- **轻量 Adapter**: 在 GenRec 内加一层 MLP 适配

#### 2.1.5 收益

- +0.5-1.5% 业务 lift
- 几乎不需要推理时间增加 (因为离线)
- 工程简单

#### 2.1.6 局限

- LLM 编码静态, 不能实时更新
- 文本信号权重低, 行为信号主导
- 没用到 LLM 的"推理"能力

### 2.2 LLM-as-Reranker

#### 2.2.1 思路

用 GenRec 召回候选, 用 LLM 重排。

#### 2.2.2 公式

$$
\text{final\_items} = \text{Reranker}(\text{LLM}, \text{GenRec}(\text{candidates}))
$$

#### 2.2.3 案例

| 公司 | 实现 |
| :--- | :--- |
| 字节 | 用豆包对召回候选重排 |
| 阿里 | 用 Qwen 对搜索结果重排 |
| 美团 | 用自研 LLM 对本地服务候选重排 |
| Reddit | 用 LLM 对帖子重排 |

#### 2.2.4 工程模式

```text
GenRec Recalls (1000)
  ↓
GenRec Ranker (top 50)
  ↓
LLM Reranker (top 10)
  ↓
最终推荐
```

LLM 的输入:

```text
[system]: 你是推荐系统助手
[user]: 用户历史行为: A B C
        候选: [X, Y, Z, ...]
        请按相关性排序并解释
[assistant]: 推荐 X (用户最近喜欢 X 类)
```

#### 2.2.5 收益

- +1-3% 业务 lift (取决于场景)
- LLM 加解释, 可解释性提升
- 用户满意度上升

#### 2.2.6 局限

- LLM 推理慢 (< 100ms 难保证)
- 候选过多时 prompt 太长
- LLM 可能跟 GenRec 重复工作

### 2.3 LLM-as-Reasoner (OneRec-Think)

#### 2.3.1 思路

LLM 做推理, GenRec 做决策。这是 OneRec-Think 的核心。

#### 2.3.2 OneRec-Think 架构

```text
输入: 用户行为 + 上下文
  ↓
LLM Reasoner (慢, 离线)
  ├── 分析用户兴趣
  ├── 生成推理路径 (CoT)
  ├── 输出结构化信号
  ↓
GenRec Predictor (快, 在线)
  ├── 接收 LLM 信号 + 用户实时特征
  ├── 输出推荐
```

#### 2.3.3 公式

$$
\mathbf{r}_\text{enhanced} = [\mathbf{r}_\text{GenRec}(\mathbf{x}); \text{Proj}(\text{LLM Reasoner}(\mathbf{x}))]
$$

#### 2.3.4 SA-GCPO 训练

OneRec-Think 用了 SA-GCPO (Self-Ask Guided Reinforcement Policy Optimization):

- LLM 自问自答生成推理路径
- GCPO: 用 GenRec 业务信号做 RL
- 共同训练 LLM + GenRec

#### 2.3.5 效果

- 业务 lift 显著 (单点 +1-3% 估)
- 推理路径提升可解释性
- 慢 LLM 离线化, 不影响在线延迟

#### 2.3.6 工程细节

| 段 | 时间 | 系统 |
| :--- | :---: | :--- |
| LLM 推理 | 10-30s | 离线 |
| 信号传输 | 0.1s | 特征平台 |
| GenRec 推理 | 10-30ms | 在线 |

LLM 推理时段长没关系, 只要它在"离线"。

### 2.4 GenRec-as-Plugin-for-LLM

#### 2.4.1 思路

把 GenRec 当作 LLM 的"工具", 让 LLM 在需要时调用。

#### 2.4.2 实现模式

```text
LLM Agent
  ├── 思考: 用户可能想要什么?
  ├── 工具调用: GenRec.predict(user_id, history)
  │     → 返回 [item_a, item_b, item_c]
  ├── 思考: 用户兴趣是音乐, 生成解释
  ├── 输出: 给用户推荐 + 解释
```

#### 2.4.3 案例

| 公司 | 实现 |
| :--- | :--- |
| 字节 | 豆包 + 抖音推荐融合 |
| 阿里 | 通义 + 淘宝推荐融合 |
| 百度 | 文心 + 搜索融合 |
| Meta | LLaMA + News Feed 探索 |
| Anthropic | Claude + 第三方 Rec API |

#### 2.4.4 优势

- LLM 可以决定"何时调 GenRec"
- 灵活的 agent 行为
- 易于跨业务复用

#### 2.4.5 局限

- LLM Agent 行为难以控制
- 多次 LLM 调用增加延迟
- 工具调用协议标准化

## 3. 端到端 LLM 推荐

### 3.1 整体 LLM 处理推荐

#### 3.1.1 极致设想

让一个 LLM 完全独立完成:

```text
输入: 用户 query + 历史 + 上下文 (文本形式)
  ↓
LLM 处理
  ├── 理解用户意图
  ├── 检索相关 item
  ├── 排序
  ├── 生成推荐文本
  ↓
输出: 推荐列表 + 解释
```

#### 3.1.2 案例: ChatGPT 推荐

2024 年起, ChatGPT 已经能给出推荐:

```text
User: 我喜欢科幻电影, 推荐 5 部
ChatGPT: 1. 黑客帝国 ...
        2. 银翼杀手 ...
        ...
```

但这是 **LLM 自身知识推理**, 不是基于实时数据。

#### 3.1.3 案例: Perplexity / 搜索答案

Perplexity 是 LLM + 搜索融合:

```text
User: 2024 年 LLM vs GenRec 进展如何?
Perplexity:
  生成答案
  + 引用 [1] / [2] / [3]
```

这是搜索 + LLM 融合。

#### 3.1.4 案例: ChatGPT 推荐新闻 (探索)

部分新闻 App 试用过 ChatGPT 推荐:

```text
User: 我想看科技新闻
ChatGPT: 推荐 3 条
        1. AI 最新进展 ...
        2. 量子计算 ...
        3. 苹果公司新闻 ...
```

效果: 用户满意度 +10-20%, 但推荐精准度不如 GenRec。

### 3.2 全 LLM 推荐面临的问题

| 问题 | 描述 |
| :--- | :--- |
| 实时性 | LLM 无实时数据 |
| 千亿物品 | 词表太小 |
| 业务信号 | LLM 不知道 CTR |
| 推理成本 | 无法承担 |
| 冷启动 | LLM 不知道新物品 |

### 3.3 半融合方案

业界共识:**半融合 > 全融合**

| 模式 | LLM 占比 | GenRec 占比 | 典型场景 |
| :--- | :---: | :---: | :--- |
| 全 GenRec | 0% | 100% | 现有工业 |
| LLM-as-Feature | < 10% | 90%+ | 文本融合 |
| LLM-as-Reranker | 10-30% | 70%+ | 重排序 |
| LLM-as-Reasoner | 30-50% | 50%+ | CoT + 决策 |
| LLM-as-Agent | 50-90% | 10-50% | 探索场景 |
| 全 LLM | 100% | 0% | 极端实验 |

工业上目前主流是 **LLM-as-Feature** 或 **LLM-as-Reranker**。

### 3.4 端云协同方向

LLM 端侧 + GenRec 云端协同:

```text
端侧 (手机):
├── 小型 LLM (1-3B INT4)
├── 本地历史缓存
└── 用户意图理解

云端:
├── GenRec 主模型
├── Trie 字典
├── 实时特征
└── 大型 LLM (推理 / 解释)
```

未来 3-5 年看好。

## 4. 推理增强 GenRec

### 4.1 LLM 生成 CoT 推理

#### 4.1.1 思路

用 LLM 为每个推荐生成解释链, GenRec 用此作为额外信号。

#### 4.1.2 数据示例

```text
用户看了: 科幻片 A, 喜剧片 B
LLM 推理:
  1. 用户对科幻和喜剧都感兴趣 (混合兴趣)
  2. 最近科幻片评分高, 用户可能倾向科幻
  3. 但 Comedy B 是热门, 也可能想继续

推荐结果: 科幻片 C (高分) + 喜剧 D (热门)
```

#### 4.1.3 工程实现

LLM 离线生成 CoT (每天批量), GenRec 在线消费。

#### 4.1.4 收益

- 推荐准确度 +1-2%
- 可解释性强
- 用户信任提升

### 4.2 LLM 生成 query 理解

#### 4.2.1 思路

用户搜索 query 由 LLM 处理, 提取意图、扩展、改写, 给 GenRec 用。

#### 4.2.2 数据示例

```text
原始 query: "笔记本 推荐"
LLM 处理:
  - 扩展: 高性能笔记本 / 入门笔记本 / 商务笔记本
  - 改写: "2025 年最新笔记本电脑推荐"
  - 意图: 购买决策
GenRec: 用扩展后的 query 推荐
```

#### 4.2.3 案例

| 搜索引擎 | 实现 |
| :--- | :--- |
| Google | LLM 改写 query (LLM4Search) |
| Bing | LLM 辅助搜索意图 |
| 百度 | 文心辅助 query 理解 |
| 阿里 | 通义辅助搜索扩展 |

### 4.3 案例: OxygenREC

#### 4.3.1 Fast-Slow Thinking

OxygenREC (京东) 把 LLM reasoning 与 GenRec 完全解耦:

```text
Slow Path (离线):
  ├── LLM reasoning (CoT 生成)
  ├── 用户深层兴趣挖掘
  └── 结构化信号给 Fast Path

Fast Path (在线):
  ├── 接收 slow 信号
  ├── GenRec 实时融合
  ├── < 30ms p99
  └── 输出推荐
```

#### 4.3.2 SA-GCPO 训练

OxygenREC 用 SA-GCPO 联合训练:

- Slow Path: LLM-guided policy
- Fast Path: GenRec policy
- 共同通过业务 RL 信号对齐

#### 4.3.3 业务效果

多场景 GMV 显著提升 (具体公开数字未给, 主比较矩阵记录)。

### 4.4 案例: OneRec-Think

#### 4.4.1 多阶段推理

OneRec-Think 用 LLM 做"多阶段推理":

1. **意图识别**: LLM 分析用户当前需求
2. **兴趣匹配**: LLM 在历史中找到相关兴趣
3. **过滤 / 排序**: GenRec 在 LLM 框架下做
4. **生成解释**: LLM 输出推荐理由

#### 4.4.2 工程上

LLM 在 **near-line** (近线) 阶段工作:

- 触发时机: 用户有明显行为变化时
- 延迟容忍: 秒级
- 输出: 结构化兴趣标记

#### 4.4.3 业务效果

快手内部 +N% 提升 (具体数字未公开)。

### 4.5 案例: DeepInterestGR

#### 4.5.1 LLM 深度兴趣挖掘

DeepInterestGR 是 "Multi-LLM 兴趣挖掘 + GR" 方案:

1. 多 LLM 并行挖掘不同维度兴趣
2. 离线整合兴趣
3. 在线 GR 用兴趣结构推荐

#### 4.5.2 关键技术

| 阶段 | 技术 |
| :--- | :--- |
| 离线 LLM 兴趣挖掘 | Multi-LLM ensemble |
| 兴趣结构化 | LLM 输出 JSON |
| 兴趣整合 | 跨 LLM 一致性 |
| 在线推理 | GR 用兴趣 + 行为 |
| 评估 | 业务 AB |

## 5. 共同 Scaling Law

### 5.1 数据 / 模型 / 计算 scaling

#### 5.1.1 共同 Scaling 的目标

```text
数据 ──┐
       ├──> 共同 scaling 协调
模型 ──┤
       ├──> 业务 / 通用 双指标
计算 ──┘
```

LLM 的 Chinchilla 和 GenRec 的 HSTU / Wukong 都证明: **数据 × 模型 × 计算** 的乘积决定效果。

#### 5.1.2 LLM Scaling Law

$$
L_\text{LLM} \propto N^{-0.34} D^{-0.28}
$$

(参 Chinchilla)

#### 5.1.3 GenRec Scaling Law

(UniScale 等论文)

$$
L_\text{GenRec} \propto N^{-\alpha_\text{rec}} D^{-\beta_\text{rec}}
$$

其中 $\alpha_\text{rec}, \beta_\text{rec}$ 与 LLM 不同。

#### 5.1.4 共同 Scaling Law 的拟合

如果想要一个统一模型同时服务 LLM + GenRec, 需要新的 Scaling Law:

$$
L(N, D, T_\text{llm}, T_\text{rec}, \text{task}) \to \text{loss}
$$

其中 $T_\text{llm}, T_\text{rec}$ 是不同任务子集占比, $\text{task}$ 是任务类型。

这是一个**开放的工程问题**, 需要大量实验拟合。

### 5.2 跨任务 / 跨场景

#### 5.2.1 LLM 的跨任务泛化

LLM 在同一模型下能处理:

- 对话
- 摘要
- 翻译
- 编程
- 数学
- 推理

LLM 的"涌现"实现了多任务统一。

#### 5.2.2 GenRec 的跨场景泛化

GenRec 在同一模型下:

- 多业务
- 多场景
- 多任务 (CTR + CVR + GMV)

但 "跨业务统一" 在 GenRec 中仍有挑战。

#### 5.2.3 融合后的跨任务

统一模型应当能处理:

| 任务类型 | 例 |
| :--- | :--- |
| 通用对话 | "今天天气如何" |
| 推荐 | "我可能喜欢什么" |
| 搜索 | "查找 X" |
| 写作 | "写一封邮件" |
| 推理 | "解这道题" |
| 任务规划 | "安排我的行程" |

这是 Foundation Model 的全部愿景。

#### 5.2.4 跨场景 scaling 挑战

- 数据异构 (文本 vs 行为)
- 评估标准不同 (perplexity vs AUC)
- 推理要求不同 (ms vs s)
- 商业化路径不同

需要新算法 / 架构 / 工程方案。

## 6. Token 统一

### 6.1 LLM token + GenRec item ID

#### 6.1.1 当前现状

| 项 | LLM token | GenRec SID |
| :--- | :--- | :--- |
| 来源 | BPE / WordPiece | RQ-VAE |
| 词表大小 | 32K-128K | 16K-256K (每个层次) |
| 语义 | 子词 | 物品聚类码 |
| 长度 | 数十-数千 | 1-3 |

#### 6.1.2 统一挑战

| 挑战 | 描述 |
| :--- | :--- |
| 词表对齐 | 文本 token ≠ 物品 ID |
| Embedding 共享 | 不同空间 |
| 长度差异 | LLM 长, GR 短 |
| 训练目标 | NTP vs Next SID |

### 6.2 统一词表

#### 6.2.1 思路

构建一个"超级词表", 包含:

- 文本子词 (BPE / SentencePiece)
- 物品 ID (RQ-VAE)
- 用户特征 (特殊 token)
- 时间 / 上下文 (特殊 token)
- 工具 / 函数调用 (function tokens)

#### 6.2.2 主流工作

| 工作 | 描述 |
| :--- | :--- |
| TST (Token + Side info) | 物品带文本描述 token |
| 阿里 EasyRec-token | 引入 item 作为 token |
| 字节 TokenMixer-v2 | 部分统一词表 |
| Meta Llama-4 (传说) | 加入视觉 token |

#### 6.2.3 工程挑战

- 词表太大 → softmax 计算量大
- 多义词 → 训练需要大量数据
- 性能 trade-off → 单一词表可能不如分词表

#### 6.2.4 经验阈值

经验上:

- 100K token 词表 → 实用
- 1M token 词表 → 实验
- 10M+ token → 难训练

实际融合会用**分层 / 组合词表**。

### 6.3 统一 Embedding

$$
\mathbf{e}[\text{token}] \in \mathbb{R}^d
$$

所有 token 共享同一个 $d$ 维 embedding 空间。这样:

- Attention 可在统一空间运算
- 跨词表迁移容易
- 多任务训练自然

这是 LLaMA / Qwen 实际上已经在做的("全词表共享 embedding")。

### 6.4 多模态 token

未来词表还会有:

- 图像 patch token
- 视频 keyframe token
- 音频 token
- 物品视觉 token

这是 **多模态原生** 的方向。

## 7. 训练范式统一

### 7.1 共同预训练

#### 7.1.1 共同预训练目标

需要一种 loss 同时优化 LLM 和 GenRec 任务:

$$
L = \lambda_\text{llm} L_\text{llm} + \lambda_\text{rec} L_\text{rec} + \lambda_\text{joint} L_\text{joint}
$$

其中:

- $L_\text{llm}$ = next token prediction
- $L_\text{rec}$ = next SID prediction
- $L_\text{joint}$ = 联合任务 (RAG, Agent 等)

#### 7.1.2 联合数据混合

预训练数据应该是:

- 50% 文本 (通用能力)
- 30% 行为 (推荐)
- 10% 代码 (编程)
- 10% 多模态

混合比例用 scaling 实验确定。

#### 7.1.3 典型做法: Curriculum Learning

```text
阶段 1: 文本 pretrain (large, classical)
  ↓
阶段 2: 通用微调 (SFT)
  ↓
阶段 3: 添加 GenRec 任务 (loss 加权)
  ↓
阶段 4: RLHF (通用对齐)
  ↓
阶段 5: 业务 RL (GenRec 对齐)
```

### 7.2 共同微调

#### 7.2.1 SFT 融合

SFT 数据混合:

- 对话数据
- 推荐指令 ("请推荐我可能喜欢的内容")
- 搜索指令 ("查找 X")
- 任务指令 ("写 / 解 / 总结")

用统一格式 (类似 ChatML) 训练。

#### 7.2.2 RLHF / RL 融合

- 通用 + 业务反馈
- 多目标优化 (CTR / GMV / 用户满意度)

### 7.3 共同训练框架

```text
共同训练框架:
├── 数据层 (文本 + 行为 + 多模态)
├── 模型层 (Transformer + Unified Token)
├── 优化层 (AdamW + LR scheduler)
├── 分布式 (DDP / TP / PP + 稀疏优化)
├── 评估层 (perplexity + AUC + 业务)
└── 部署层 (vLLM + Trie 扩展)
```

主流框架: PyTorch + FSDP + Megatron-LM 风格。

### 7.4 LoRA / PEFT 融合

LLM 和 GenRec 可用 LoRA 协同微调:

- 主模型 frozen
- LoRA 适配新业务
- 多业务 LoRA 共享

这是工业推荐团队的实际做法。

## 8. 推理范式统一

### 8.1 自回归生成

#### 8.1.1 共同的推理范式

LLM 与 GenRec 都用自回归生成:

$$
y_t = \arg\max_v p_\theta(v | x, y_{<t})
$$

差别只在:

- LLM: $v$ 来自文本词表
- GenRec: $v$ 来自 SID 词表 + Trie 约束

#### 8.1.2 共同推理框架

工程上, vLLM / SGLang 等可以扩展到 GenRec:

- KV Cache 共享
- Continuous Batching
- Speculative Decoding (GenRec 不太需要)
- Constrained Decoding (GenRec 必须)

未来框架可能:

```text
vLLM + GenRec Extensions:
├── 通用 LLM 推理
├── Constrained Decoding (TRIE)
├── Cross-request KV (GenRec)
├── Fast-Slow Routing
└── Unified Continuous Batching
```

### 8.2 共享推理框架

#### 8.2.1 多模型服务架构

```text
统一推理服务:
├── 模型路由: 根据任务 / 输入选择模型
│   ├── 文本任务 → LLM
│   ├── 推荐任务 → GenRec
│   ├── 混合任务 → LLM + GenRec 协同
├── 推理引擎:
│   ├── Prefill (compute-bound)
│   ├── Decode (memory-bound)
│   └── Trie-aware (constrained)
├── 调度:
│   ├── Continuous Batching
│   ├── Priority Queue
│   └── Fast-Slow Split
```

#### 8.2.2 Fast-Slow 推理模式

借鉴 OxygenREC 的设计:

```text
请求进来
  ↓
Fast Path: < 50ms (GenRec 在线)
  └── p99 < 50ms, 80% 流量
  ↓
Slow Path: 1-10s (LLM 推理)
  └── 5-20% 流量 (复杂 / 解释 / 端到端)
```

LLM 推理在 slow path, 不影响 GenRec 主链延迟。

### 8.3 边缘 / 端侧融合

#### 8.3.1 端侧约束

| 设备 | 内存 | 可行模型 |
| :--- | :---: | :--- |
| 手机 | 8GB | 1B-3B LLM + 端侧 GR 字典 |
| 高端机 | 16GB | 3B-7B LLM + GR 字典 |
| 笔记本 | 32GB+ | 7B+ LLM + GR 完整 |

#### 8.3.2 端侧融合模型

未来:

```text
端侧模型:
├── LLM (基础智能): 1B-3B INT4
├── GenRec 排序: 100M-500M INT8
├── 共享 tokenizer
├── 共享 vocabulary (item + text)
└── 联合推理
```

端侧模型解决隐私 + 离线可用 + 个性化。

## 13. 挑战与风险

### 13.1 技术挑战

#### 13.1.1 统一的损失函数

LLM loss (perplexity) 和 GenRec loss (NDCG) 量纲不同, 简单加权可能失衡。

解决:

- Pareto 多目标学习
- 自适应权重
- 多任务梯度 surgery

#### 13.1.2 实时性不匹配

LLM 慢 (秒级), GenRec 快 (毫秒级)。

解决: Fast-Slow 解耦。

#### 13.1.3 数据异构

文本 vs 行为数据格式 / 量级 / 质量差异大。

解决: 联合 embedding + 多阶段训练。

#### 13.1.4 评估标准不一致

通用 benchmark vs 业务指标。

解决: 多维评估体系。

### 13.2 工程挑战

| 挑战 | 描述 |
| :--- | :--- |
| 集群异构 | GPU 集群 + 推荐系统 |
| 调度复杂 | 多服务 + 多业务 |
| 监控复杂 | 双系统监控 |
| 回滚难 | 错误排查跨系统 |

解决: 统一架构师 + 标准化。

### 13.3 业务挑战

- **多业务冲突**: 各业务 KPI 冲突
- **资源分配**: 谁优先
- **责任划分**: 出了问题谁负责
- **商业化路径**: 收入统计复杂

解决: 业务治理委员会。

### 13.4 监管挑战

- **EU AI Act**: 多任务 AI 系统分类难

## 18. 附录 C · 代码模板

### 18.1 Fast-Slow GenRec + LLM 协同

```python
class FastSlowRecSystem:
    def __init__(self):
        self.fast_rec = GenRecModel("genrec_v3.pt")
        self.slow_reasoner = LLMReasoner("reasoner_qwen_v2.pt")
        self.feature_store = FeatureStore()

    def predict(self, user_id, history):
        # 1. 拉特征
        user_feat = self.feature_store.get(user_id)

        # 2. 慢路径 (异步, 离线)
        if self._need_slow_reasoning(user_id):
            slow_signal = self.slow_reasoner.reason(user_id, history)
            # 缓存到 feature store
            self.feature_store.update_slow_signal(user_id, slow_signal)
        else:
            slow_signal = self.feature_store.get_slow_signal(user_id)

        # 3. 快路径
        scores = self.fast_rec.predict(
            history, user_feat, slow_signal
        )

        # 4. Trie 查表 + 业务规则
        items = self.trie.beam_search(scores, beam_size=4)
        items = self.business_rules(user_id, items)

        return items

# 总延迟:
#   Fast Path: 5-30ms
#   Slow Path: 1-10s (异步, 不阻塞)
```

### 18.2 LLM-as-Reranker

```python
class LLMReranker:
    def __init__(self):
        self.genrec = GenRecModel()
        self.llm = vLLM("qwen2.5-7b-instruct")

    def rerank(self, user_id, candidates):
        # 1. GenRec 召回 + 粗排 (top 50)
        scores = self.genrec.predict(user_id)
        top_50 = scores.topk(50)

        # 2. 构造 LLM prompt
        prompt = self._build_rerank_prompt(
            user_id, top_50
        )

        # 3. LLM 重排
        ranked = self.llm.generate(
            prompt,
            response_format=json_schema,
            max_tokens=200,
        )

        return ranked
```

### 18.3 共同训练 Loop

```python
class UnifiedTrainer:
    def __init__(self):
        self.model = UnifiedFoundationModel()
        self.tasks = {
            "lm": LMTask(),
            "rec": RecommendationTask(),
            "search": SearchTask(),
            "agent": AgentTask(),
        }

    def train_step(self, batch):
        # Multi-task loss
        losses = {}
        for task_name, task in self.tasks.items():
            if task.should_train(batch):
                losses[task_name] = task(self.model, batch)

        # 加权求和
        total_loss = sum(
            w * losses[k] for k, w in self.loss_weights.items()
        )

        total_loss.backward()
        self.optimizer.step()
```

## 26. 附录 J · 融合的"不归路"清单

### 26.1 不可走的方向

#### 26.1.1 不归路 1: 用 LLM 完全替代 GenRec

LLM 推理慢, 无法适应实时推荐。

#### 26.1.2 不归路 2: 用 GenRec 完全替代 LLM

GenRec 不能做开放式对话 / 写作。

#### 26.1.3 不归路 3: 简单串联两个独立系统

简单串联会导致:
- 延迟叠加 (50ms + 500ms = 550ms)
- 维护成本翻倍
- 业务 lift 不显著

#### 26.1.4 不归路 4: 强行统一所有训练数据

文本 + 行为数据混训容易失焦, 分阶段训练更好。

#### 26.1.5 不归路 5: 跳过业务 AB 直接融合上线

任何融合都需 AB 实验, 否则风险大。

### 26.2 慎行方向

| 方向 | 风险 |
| :--- | :--- |
| 大规模联合训练 (100B+) | ROI 不确定 |
| 激进上线统一模型 | 系统风险 |
| 跨业务强行复用 | 业务冲突 |
| 实时融合推理 | 延迟风险 |

## 29. 附录 M · 概念辨析 (融合方向)

### 29.1 关键概念区分

| 概念 A | 概念 B | 区别 |
| :--- | :--- | :--- |
| LLM-as-Feature | LLM-as-Reranker | Feature 是输入, Rerank 是输出 |
| Fast-Slow | Cascade | Fast-Slow 是并行, Cascade 是串联 |
| Self-Evolving | Online Learning | Self-Evolving 用 LLM 调优, Online 更简单 |
| Foundation Model | Multi-task | Foundation 是单一大模型, Multi-task 可以分多个 |
| Token 统一 | 词表共享 | Token 统一还含 Embedding 统一 |
| RLHF | RL for Rec | RLHF 是 LLM 对齐, RL for Rec 是业务反馈 |

### 29.2 关键术语

| 术语 | 含义 |
| :--- | :--- |
| Foundation Model | 基础模型, 大规模多任务 |
| Joint Pretraining | 共同预训练 |
| Knowledge Distillation | 知识蒸馏 |
| Self-Evolving | 自我演化 |
| Fast-Slow Routing | 快慢路径分流 |
| Cross-task Transfer | 跨任务迁移 |
| Constrained Decoding | 约束解码 |
| Online Learning | 在线学习 |
