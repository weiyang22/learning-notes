# 1. 在线服务的时延预算

> **本章定位**: 工业级推荐系统的时延要求
> **预计时长**: 45 分钟

---

## 1.1 典型时延预算

| 阶段 | P99 时延 |
| :--- | :--- |
| 召回 (Annoy/FAISS) | 5-10 ms |
| 粗排 | 10-20 ms |
| 精排 | 20-50 ms |
| **总计** | **< 100 ms** |

---

## 1.2 SID 在时延预算中的位置

```text
用户请求 (5ms)
  ↓
召回 (5-10ms) ← SID 查表 (μs 级)
  ↓
粗排 (10-20ms) ← SID Embedding
  ↓
精排 (20-50ms) ← SID Embedding + Cross Attention
  ↓
返回结果 (1ms)
```

SID 查表是**最快的环节**(μs 级)。

---

## 1.3 离线 vs 在线 SID

| 维度 | 离线预计算 | 在线推断 |
| :--- | :--- | :--- |
| 时延 | 0 (查表) | 5-20ms (encoder) |
| 灵活 | 低 (固定 SID) | 高 (query-aware) |
| 适合 | 大量物品 | 少量物品 |

---

## 1.4 为什么时延如此关键(业务视角)

时延不只是体验问题,直接影响收入:
- 经典结论:每增加 100ms 时延,电商转化率可下降约 1%(Amazon)、搜索使用率下降(Google)。
- 推荐是**长链路**(召回→粗排→精排→重排),每一环都在抢时延预算,任何一环超时会触发**降级**(返回缓存/简单模型),伤害效果。
- 所以 SID 设计的第一约束往往不是"效果多好",而是"能否在预算内算完"。

---

## 1.5 P99 而非平均:长尾时延才是杀手

工业只看 **P99/P999**,不看平均。原因:
- 一次请求要 fan-out 到成百上千个下游(多路召回、多分片),**最终时延 = 最慢那个分片**(木桶效应)。
- 单机 P99=10ms,fan-out 100 路后整体 P99 可能被拖到几十 ms。
- 优化长尾手段:超时熔断(hedged request)、冗余请求取最快、尾延迟感知调度。

---

## 1.6 SID 服务的时延优化手段

| 手段 | 作用 |
| :--- | :--- |
| **离线预计算 SID** | item SID 提前算好入库,线上 μs 级查表 |
| **在线只算 query/user SID** | 只有少量动态实体需在线 encoder(见 1.3) |
| **ANN 索引(HNSW/IVF-PQ)** | 亚线性检索,见 [07-03](第07章-03-ANN索引与SID检索.md) |
| **批处理 + GPU** | 精排合批摊薄开销 |
| **缓存热门 query 的 SID/结果** | 命中即 0 计算 |
| **量化/蒸馏 encoder** | 在线 encoder 更快 |

```python
# 混合策略: item 走离线查表, query 走在线 encoder + 缓存
def get_sids(query, item_ids):
    q_sid = sid_cache.get(query) or online_encoder(query)   # 在线(带缓存)
    item_sids = [offline_sid_table[i] for i in item_ids]     # 离线查表(μs)
    return q_sid, item_sids
```

## 1.9 P99/P999 时延理论深度

### 1.9.1 为什么工业只看 P99,不看平均

平均时延(Mean)是个"骗子":它对短时延非常敏感,但忽略了长尾。例如:

- 100 个请求,99 个 5ms,1 个 5000ms
- 平均时延 = (99 × 5 + 5000) / 100 = 54.95ms
- 但 P99 = 5000ms

平均告诉我们"通常不错",P99 告诉我们"有人遭殃"。

工业推荐系统每天处理 10 亿+ 请求,即使 P99 = 1000ms,意味着每天有 **1000 万** 用户等待 1 秒以上 — 这部分用户转化率会暴跌(Google 数据:搜索时延从 100ms 升到 400ms,流量降 0.6%)。

**统计意义**:

```text
Mean(均值): 一阶矩, μ
P50: 中位数, 50% 分位
P95: 95% 分位
P99: 99% 分位, 1% 的请求超过此值
P999: 99.9% 分位, 0.1% 超过
Pmax: 最慢的请求

工业"护栏指标"通常选 P99 或 P999
```

### 1.9.2 P99 的数学性质

假设请求时延 $X$ 服从对数正态分布(实际场景中常见):

$$
X \sim \text{Lognormal}(\mu, \sigma^2), \quad P(X > t) = 1 - \Phi\left(\frac{\ln t - \mu}{\sigma}\right)
$$

其中 $\Phi$ 是标准正态 CDF。

**P99 的解析式**:

$$
P_{99} = \exp(\mu + 2.33 \sigma)
$$

(因为 $\Phi^{-1}(0.99) \approx 2.33$)

**关键观察**: $P_{99}$ 对 $\sigma$ 极敏感。如果平均时延固定,标准差 $\sigma$ 翻倍, P99 翻 $e^{2.33 \sigma} / e^{2.33 \sigma/2}$ 倍 — **远大于平均**。

**这就是为什么优化长尾 = 降低方差, 而非降低均值**。

### 1.9.3 实际时延分布:重尾 (Heavy Tail)

实际请求时延往往不是对数正态,而是**重尾分布** (Power Law):

$$
P(X > t) \sim t^{-\alpha}, \quad \alpha \in [1, 2]
$$

这种分布下,均值和方差都可能不收敛,只能看分位数。

**常见来源**:
- GC 暂停 (Java/Python)
- 磁盘 IO 抖动
- 跨机房网络抖动
- 第三方 API 慢响应

**应对**:超时熔断、冗余请求、降级。

## 1.10 Fan-out 系统的时延木桶效应

### 1.10.1 数学建模

假设请求要 fan-out 到 $n$ 路并行召回, 每路独立,P99 = $t_p$:

$$
P_{99,\text{total}} = P\left( \max_{i=1}^{n} X_i > T \right) = 1 - P(X_1 \leq T, \ldots, X_n \leq T)
$$

如果每路独立且同分布:

$$
P_{99,\text{total}} = 1 - [P(X \leq T)]^n
$$

**反推**: 如果要求整体 P99 = 100ms, fan-out 100 路, 每路的 P99 是多少?

设每路 P99 = $t_p$,则整体 P99 = $t$ 当 $1 - (1 - 0.01)^n \cdot [P(X \leq t) / P(X \leq t_p)]^n$ ...

简化:如果每路 i.i.d.:

$$
P(\text{任一路} > t) = 1 - P(X \leq t)^n
$$

要保证整体 P99 = 100ms, 100 路 fan-out, 设每路 P_{99.99} ≈ 100ms(因为 0.99 ≈ 1 - (1-0.0001)^{100})。

也就是说,**fan-out 把 P99 指标推得越来越严**。

### 1.10.2 工业实践

```text
请求 → 召回 100 路 → 粗排 → 精排 → 重排 → 返回
   ↑     ↑
   P99   每路独立 P99
   5ms   10ms × 100 路
          整体 P99 接近 10ms (最慢的那路)
```

**优化手段**:

| 手段 | 描述 | 收益 |
| :--- | :--- | :--- |
| **超时熔断** | 给每路设超时(如 5ms), 超时立即降级 | 避免被拖死 |
| **冗余请求** | 同路发 2 份, 取最快响应 | 降 P99 ~30% |
| **分层调度** | 重要路 (i2i) 高优先级, 次要路 (u2i) 后跑 | 关键路径优先 |
| **批量合并** | 把多 query 合并为单次 ANN 检索 | 摊薄 QPS |
| **预加载** | 热门 query/user 的 SID 提前加载到本地缓存 | 命中 0 ms |

## 1.11 SID 服务的完整时延拆解

```text
┌────────────────────────────────────────────────────────────┐
│ 用户请求 (1ms 网络)                                         │
├────────────────────────────────────────────────────────────┤
│ 召回阶段 (5-10ms)                                           │
│  ├─ query 解析 (0.5ms)                                      │
│  ├─ query SID 编码 (1-3ms, GPU) [若在线]                   │
│  ├─ FAISS 检索 (3-5ms, nprobe=32)                          │
│  └─ 返回 top-1000 候选 (0.5ms)                              │
├────────────────────────────────────────────────────────────┤
│ 粗排阶段 (10-20ms)                                          │
│  ├─ 加载候选 SID embedding (1ms, 内存查表)                  │
│  ├─ 加载候选 ItemID embedding (2ms, 内存查表)               │
│  ├─ 双塔打分 (5-10ms, GPU batch)                            │
│  └─ 取 top-100 (0.5ms)                                     │
├────────────────────────────────────────────────────────────┤
│ 精排阶段 (20-50ms)                                          │
│  ├─ 加载 user history (5ms, Redis/HBase)                    │
│  ├─ 加载 cross features (5ms)                               │
│  ├─ DLRM/DIN forward (15-30ms, GPU)                        │
│  └─ 取 top-50 (1ms)                                        │
├────────────────────────────────────────────────────────────┤
│ 重排阶段 (5-10ms)                                           │
│  ├─ 多样性约束 (MMR/DPP) (3ms)                              │
│  ├─ 业务规则过滤 (1ms)                                      │
│  └─ 返回 top-20 (1ms)                                      │
├────────────────────────────────────────────────────────────┤
│ 总计: 41-91 ms (P99)                                        │
└────────────────────────────────────────────────────────────┘
```

**关键观察**: SID 在整个链路中贡献的时延几乎为零(查表 μs 级),它解决的是**召回质量**, 不是时延。这是 SID 最重要的工程优势之一。

## 1.12 时延与吞吐的"U 形曲线"

系统设计有个核心矛盾:**时延 vs 吞吐**。

```text
高吞吐 ─────────── / ─────────── 低时延
                  / \
                 /   \
                /     \
               /       \
              /  最优    \
             /   工作点    \
            /               \
   单请求处理           批处理
   (P99 10ms)         (P99 100ms 但 QPS 100x)
```

**现象**:
- 单请求处理: P99 低 (10ms), 但 QPS 低 (100)
- 批处理 1000: P99 高 (100ms), 但 QPS 高 (10K)

**工业选择**:
- 用户请求类 (个性化推荐): 走低时延, 牺牲一些吞吐
- 离线计算类 (批 Embedding 算 SID): 走高吞吐, 时延无所谓

## 1.13 时延的"分层 SLA"设计

工业系统通常把请求分成多档 SLA, 不同档走不同链路:

| 档位 | 时延预算 | 适用场景 | 退化策略 |
| :--- | :--- | :--- | :--- |
| **L0 (极速)** | < 30ms | 首页首屏推荐 | 只走 1 路召回 + 简化模型 |
| **L1 (标准)** | < 100ms | 一般推荐位 | 完整 100 路召回 + 精排 |
| **L2 (深度)** | < 500ms | 用户主动刷新 | 多路召回 + 重排 + 业务规则 |
| **L3 (后台)** | < 5s | 个性化首页生成 | 全量用户历史 + 多模型融合 |

**SID 在不同档的作用**:

- L0: 离线 SID 查表(μs)
- L1: 离线 SID 查表 + 在线 query encoder(5ms)
- L2: 同 L1 + 多路召回
- L3: 离线预计算

## 1.14 时延优化的常见误区

### 1.14.1 误区 1: "GPU 一定能加速"

不一定。GPU 加速有 kernel launch overhead (~10μs), 小模型(< 1ms 计算) 上 GPU 可能反而慢。

**判断标准**: 单次计算 > 100μs 才用 GPU;否则 CPU。

### 1.14.2 误区 2: "缓存越多越好"

缓存有代价:
- 内存占用
- 失效一致性
- 命中率衰减(长尾)

**经验**: 缓存命中率 > 80% 才值得做, 否则直接算更省事。

### 1.14.3 误区 3: "P50 优化就是时延优化"

错。优化 P50 不代表优化 P99。P50 优化降的是"常态", P99 优化降的是"长尾"。

工业里,**专门有 P99 优化工程师**, 解决"为什么最慢那 1% 那么慢"。

### 1.14.4 误区 4: "减少网络跳数 = 减少时延"

不一定:
- 多一跳可能引入重试/熔断逻辑, **反而降 P99**
- 多一跳可能让服务就近, **降 P50**

**判断标准**: 用 trace 看真实分布, 而不是看代码。

## 1.15 时延 vs 准确率的权衡

时延和效果不总是正相关。有时候**算得快但算错了**,反而更糟。

| 策略 | 时延 | 效果 | 适用 |
| :--- | :--- | :--- | :--- |
| 暴力精确召回 | 50ms | 100% | 离线评估 |
| ANN 近似召回 | 5ms | 95% | 线上默认 |
| 简化模型 + ANN | 2ms | 85% | 首屏极速档 |
| 缓存热门结果 | 0.5ms | 90% (缓存场景) | 热点用户 |

**经验值**: 时延每降 50%, 效果降 5-10%, 是工业甜点。降 90% 时延 (1s → 100ms), 效果可能降 30%, 这就是首屏 vs 个性化首页的差别。

## 1.16 SID 在时延优化中的"杠杆点"

虽然 SID 本身时延很低, 但 SID 化可以**间接降低其他环节时延**:

| 杠杆点 | 说明 | 收益 |
| :--- | :--- | :--- |
| **降低召回候选量** | SID 召回更精准, top-100 候选足够, 不需要 top-1000 | 精排时延 -50% |
| **降低精排输入维度** | SID 5 维 vs ItemID Emb 128 维 | 精排 forward -60% |
| **预排序** | 用 SID 之间的相似度预排, 跳过无关候选 | 召回后处理 -30% |
| **缓存友好** | SID 是离散 token, 缓存 key 自然 | 缓存命中率 +20% |

**典型案例**: 一个 DLRM 系统上线 SID 后, 整体 P99 从 120ms 降到 75ms (主要是精排 forward 加速)。

## 1.17 时延监控与告警

### 1.17.1 核心监控指标

```yaml
必监控:
  - P50 / P95 / P99 / P999 时延
  - QPS (每秒请求数)
  - 错误率 (5xx, timeout)
  - 各阶段拆解时延 (trace)

可选监控:
  - CPU / 内存 / 显存
  - GC 暂停时间
  - 网络 RTT
  - 上游依赖时延
```

### 1.17.2 告警阈值

| 指标 | 警告 | 紧急 |
| :--- | :--- | :--- |
| P99 时延 | > 100ms (基线 +20%) | > 150ms (基线 +50%) |
| 错误率 | > 0.1% | > 1% |
| QPS 突降 | < 80% 基线 | < 50% 基线 |
| P999 时延 | > 300ms | > 500ms |

### 1.17.3 P99 异常的快速诊断流程

```text
1. 看 P50: P50 也涨了 → 全局性问题 (网络/上游)
   P50 不涨 P99 涨 → 长尾问题 (某个下游慢)
2. 看 trace: 找出 P99 请求的瓶颈环节
3. 看上游: 是否上游某服务整体慢?
4. 看资源: CPU/内存/磁盘 IO 是否饱和?
5. 看新版本: 是否刚发了新版?
```

## 1.18 SID 服务的容量评估

### 1.18.1 假设条件

```text
DAU: 1000 万
人均请求: 50 次/天
峰值 QPS: 100K (假设 10x 平均)
召回路数: 100 路
SID 编码 (在线部分): 5ms/请求
FAISS 检索: 5ms/请求
```

### 1.18.2 容量计算

```text
单实例处理能力:
  CPU 编码服务: ~200 QPS (5ms/请求)
  GPU 编码服务: ~2000 QPS (含 launch overhead)
  FAISS CPU 检索: ~500 QPS (nprobe=32)
  FAISS GPU 检索: ~10K QPS

需要实例数 = 峰值 QPS × 单次耗时 / (1000 × 实例核数)
  编码服务: 100K × 5 / (1000 × 1) = 500 核 → 16 个 32 核实例
  FAISS 检索: 100K × 5 / (1000 × 1) = 500 核 → 16 个 32 核实例
  或: 100K / 10K = 10 个 GPU 实例 (单卡)

总计: 16 CPU 实例 + 10 GPU 实例 (含 2x buffer)
```

### 1.18.3 成本估算

```text
CPU 实例 (32 核 64GB): ~$500/月
GPU 实例 (A10): ~$2000/月

每月成本: 16 × $500 + 10 × $2000 = $28,000
每千次请求成本: $28K / (1000万 × 50 / 1000) = $0.056

参考: Google 内部指标, 每千次搜索成本 < $0.01
优化空间: 提升缓存命中率 / 优化 GPU 利用率
```

## 1.19 时延优化的"分层套路"

按优先级排序, 投入产出比从高到低:

### 1.19.1 第 1 层: 缓存 (投入产出比最高)

```text
- 热门 query/user 的 SID 缓存 (命中率 30-50%)
- 热门 item 的召回结果缓存 (命中率 50-70%)
- 特征缓存 (命中率 70-90%)

收益: P99 降 30-50%
成本: Redis 集群
```

### 1.19.2 第 2 层: 批处理

```text
- 精排模型 batch_size=64 → 256 (4x 吞吐)
- 召回结果批量传给粗排

收益: 吞吐 ×4, 时延 +20-50%
成本: 增加 batch 等待延迟
```

### 1.19.3 第 3 层: 模型优化

```text
- 蒸馏 (大模型 → 小模型, 5-10x 加速)
- 量化 (fp32 → int8, 2-3x 加速)
- 稀疏化 (剪枝, 1.5-2x 加速)

收益: 时延 -50%
成本: 模型重训 + 精度损失
```

### 1.19.4 第 4 层: 架构优化

```text
- 多级缓存 (L1 本地内存 / L2 Redis)
- 预加载 (启动时加载热门)
- 异步化 (同步 → 异步 pipeline)

收益: 时延 -30%
成本: 架构复杂
```

### 1.19.5 第 5 层: 硬件升级

```text
- CPU → GPU (10-100x 加速)
- HDD → SSD → NVMe (10-100x IO 加速)
- 普通网卡 → RDMA (10x 网络加速)

收益: 视场景
成本: 设备投入
```

## 1.20 SID 与其他时延优化技术的配合

### 1.20.1 SID + 缓存

```python
class SIDCache:
    """SID 服务的多级缓存"""
    def __init__(self, redis_client):
        self.redis = redis_client
        self.local_cache = LRUCache(maxsize=10_000)

    def get_item_sid(self, item_id, version):
        # L1: 本地缓存
        key = f"{version}:{item_id}"
        sid = self.local_cache.get(key)
        if sid is not None:
            return sid

        # L2: Redis
        sid = self.redis.get(key)
        if sid is not None:
            self.local_cache[key] = sid
            return sid

        # L3: 数据库
        sid = self.db.query(f"SELECT sid FROM item_sids_{version} WHERE item_id={item_id}")
        self.redis.setex(key, 3600, sid)
        self.local_cache[key] = sid
        return sid
```

### 1.20.2 SID + 预排序

```python
def fast_prerank(candidates, query_sid, top_k=100):
    """用 SID 之间的相似度预排序, 减少送精排的候选"""
    scores = []
    for cand in candidates:
        # SID Hamming 距离作为粗打分
        dist = hamming(query_sid, cand.sid)
        scores.append(-dist)  # 距离越小分越高
    # 取 top_k
    sorted_idx = np.argsort(scores)[:top_k]
    return [candidates[i] for i in sorted_idx]
```

**收益**: 召回 top-1000 → 精排 top-100, 精排时延 -90%。

### 1.20.3 SID + 模型蒸馏

```python
# 蒸馏: 大 encoder → 小 encoder
class DistilledEncoder(nn.Module):
    """小 encoder 直接预测 SID (跳过 K-Means 查表)"""
    def __init__(self, dim_in=768, dim_hidden=256, K=5, C=256):
        super().__init__()
        self.backbone = nn.Sequential(
            nn.Linear(dim_in, dim_hidden),
            nn.ReLU(),
            nn.Linear(dim_hidden, dim_hidden),
            nn.ReLU(),
        )
        # 每层一个分类头
        self.heads = nn.ModuleList([
            nn.Linear(dim_hidden, C) for _ in range(K)
        ])

    def forward(self, x):
        h = self.backbone(x)
        sids = [head(h).argmax(dim=-1) for head in self.heads]
        return torch.stack(sids, dim=-1)
```

**收益**: 跳过 K-Means 查表, 单次编码 < 1ms。

## 1.22 时延优化的"反模式"

### 1.22.1 反模式 1: 盲目加机器

症状: 时延高 → 加机器 → 没用。

原因: 时延高可能是:
- 锁竞争 (单线程瓶颈)
- 同步 IO (CPU 空闲但等 IO)
- GC 频繁 (内存碎片)

加机器不解决这些问题。

### 1.22.2 反模式 2: 过度并行化

症状: 启了 100 线程 → 性能更差。

原因: 线程切换开销 + 缓存失效。

**经验**: CPU 密集任务, 线程数 = CPU 核数; IO 密集任务, 线程数 = CPU 核数 × 2-4。

### 1.22.3 反模式 3: 过早优化

症状: 系统还活着, 先花 3 月优化时延。

原因: 业务还没起来, 优化了没人用。

**建议**: 先跑通 → 监控 → 看真实瓶颈 → 优化。YAGNI。

### 1.22.4 反模式 4: 忽略冷启动

症状: 系统重启后 10 分钟慢。

原因: 缓存未热 + 索引未加载 + JIT 未编译。

**解法**: 预热 (warm-up traffic) + lazy loading。

## 1.23 时延的"预热" 与 "冷启动"

### 1.23.1 服务的冷启动

新实例启动 → 加载模型 → 加载索引 → JIT 编译 → 接受流量。

**典型耗时**:
- 模型加载: 10-30s
- FAISS 索引加载: 30-300s (取决于规模)
- JIT 编译: 5-30s

**工业解法**:

```python
# 1. 启动后先做 warm-up 请求
def warmup():
    for _ in range(100):
        encode_sid(dummy_embedding)
    for _ in range(100):
        faiss.search(dummy_query, k=10)

# 2. 健康检查返回 ready 才接流量
@app.get("/ready")
async def ready():
    if not model_loaded or not index_loaded:
        raise HTTPException(503)
    return {"status": "ready"}

# 3. 滚动部署: 先启动新实例 → 切流量 → 关老实例
# 而不是先关老实例再起新实例
```

### 1.23.2 索引的冷启动

FAISS 索引从磁盘加载到内存, 1 亿向量可能要 5-10 分钟。

**工业解法**:
- mmap 加载 (内存映射, 按需分页)
- 多 shard 并行加载
- 启动前预下载到本地 NVMe
- 灰度加载 (先加载 10%, 流量切 10%, 再加载更多)

## 1.24 SID 服务的灰度发布与时延

灰度时, 要保证**新旧版本同时在线**, 时延会翻倍吗?

**答案**: 不一定, 看架构。

```text
架构 A: 副本式 (推荐)
  旧版本: 实例 1-10 (10 个, 100% 流量)
  新版本: 实例 11-15 (5 个, 5% 流量)
  → 时延不变 (新旧独立)

架构 B: 单实例双版本 (不推荐)
  旧版本 + 新版本共存同一实例
  → 时延 +50-100% (内存翻倍, 索引翻倍)
```

**工业经验**: 永远用架构 A (副本式), 不要用架构 B。

## 1.26 一些冷门但重要的时延概念

### 1.26.1 Tail at Scale (Dean & Barroso 2013)

Google 经典论文, 提出"tail-tolerant system design"。

核心观点: 单机 P99 = 100ms 不代表整体 P99 = 100ms, fan-out + 网络 + 上游依赖会让 P99 雪崩。

**应对**:
- Hedged requests (冗余 + 取最快)
- Tied requests (同步锁)
- Gradient-based shedding (动态降级)

### 1.26.2 The Tail at Scale:Implications

```text
单实例 P99 = 100ms
100 实例 fan-out
理论整体 P99 = ?

如果 100 实例独立同分布:
P(max > t) = 1 - (1 - 0.01)^{100} ≈ 1 - 0.366 = 0.634
即 63% 请求整体超过某阈值

要让整体 P99 = 100ms:
单实例 P_{99.99} = 100ms
```

这就是为什么 Google 的基础设施追求 **P99.99** 而非 P99。

### 1.26.3 工业实践: tail-tolerant 设计

```python
async def hedged_request(query, timeout_ms=10):
    """Hedged request: 主请求 + 备份请求, 取最快"""
    primary_task = asyncio.create_task(async_query(query))
    await asyncio.sleep(timeout_ms / 2)  # 等一半时间
    if not primary_task.done():
        # 启动备份
        backup_task = asyncio.create_task(async_query(query))
        done, pending = await asyncio.wait(
            [primary_task, backup_task],
            return_when=asyncio.FIRST_COMPLETED,
            timeout=timeout_ms / 1000,
        )
        for p in pending:
            p.cancel()
        return done.pop().result()
    return await primary_task
```

**收益**: P99 降 30-50%, 但 QPS 略降 (重复请求)。

## 1.29 时延的"分层 SLA"与服务降级

### 1.29.1 多档 SLA 设计

```python
class AdaptiveSIDService:
    """自适应 SLA: 根据当前负载选择降级策略"""
    def __init__(self):
        self.primary_encoder = FullEncoder()
        self.fallback_encoder = DistilledEncoder()
        self.cache = LRUCache()

    def encode(self, emb, sla="L1"):
        if sla == "L0":  # 极速档
            # 只走缓存, 没有就走默认值
            cached = self.cache.get(tuple(emb[:8]))
            return cached or DEFAULT_SID

        elif sla == "L1":  # 标准档
            # 缓存 → 蒸馏 encoder → 全量 encoder
            cached = self.cache.get(tuple(emb[:8]))
            if cached:
                return cached
            try:
                return self.fallback_encoder(emb)
            except TimeoutError:
                return DEFAULT_SID

        else:  # 深度档
            return self.primary_encoder(emb)
```

### 1.29.2 服务降级触发条件

```python
def should_degrade(metrics):
    """判断是否要降级"""
    if metrics['p99_latency_ms'] > 150:
        return "L1 → L0"
    if metrics['error_rate'] > 0.05:
        return "L1 → 缓存 only"
    if metrics['qps_drop_pct'] > 0.5:
        return "L1 → L2"  # 上游挂了, 不接新请求
    return None
```

## 1.33 工业时延优化的"段子手"案例集

### 1.33.1 案例 1: 一个 P99 = 2000ms 的服务如何优化到 50ms

某电商搜索服务, P99 时延 2000ms (2 秒!), CTR 比预期低 30%。

**诊断**:
```text
trace 分析发现:
  - 99% 请求在 100ms 内返回
  - 1% 请求卡在"特征加载"环节 2 秒
  - 根因: 某些长尾 user 的特征在 HBase, 首次访问要扫全表
```

**优化**:
1. 特征预热: 热门 user 特征预加载到 Redis
2. 长尾兜底: 找不到特征时返回默认值, 不阻塞
3. 异步化: 特征加载异步并行, 不阻塞主流程

**结果**: P99 从 2000ms → 80ms, CTR +25%。

### 1.33.2 案例 2: 某新闻推荐服务的"GC 雪崩"

某新闻推荐服务, 每天上午 9 点 P99 从 50ms 飙到 5000ms, 持续 30 分钟。

**诊断**:
```text
9 点是用户高峰期, 新请求涌入 → 对象分配激增 → Minor GC 频繁 → Major GC 暂停 5 秒
```

**优化**:
1. 改用 G1GC (减少 STW)
2. 对象池化 (复用对象, 减少分配)
3. Off-heap 缓存 (大对象放堆外)

**结果**: P99 稳定在 80ms, 无明显雪崩。

### 1.33.3 案例 3: 某视频推荐服务的"冷启动慢"

某视频推荐服务, 新实例启动后前 100 个请求要 5 秒。

**诊断**:
```text
启动流程:
  1. 加载模型 (10 秒)
  2. 加载 FAISS 索引 (20 秒)
  3. JIT 编译 (5 秒)
  4. 第一次请求: 索引未热, 全磁盘 IO
```

**优化**:
1. 模型 + 索引用 mmap (无需全加载)
2. 启动后立即跑 1000 个 dummy 请求做 warm-up
3. 健康检查 /ready 返回 200 才接流量
4. 滚动部署: 先起新实例 → 切流量 → 关老实例

**结果**: 启动到接流量 < 30 秒, 无慢首请求。

## 1.34 时延优化的"反直觉"现象

### 1.34.1 现象 1: "系统更快 = QPS 下降"

直觉: 系统优化 → QPS 更高。

现实: 优化后单请求处理更快, 但请求太快会让**队列堆积**反而 QPS 下降。

**举例**: 系统处理时间从 10ms 降到 1ms, 但如果上游突发流量 (10K QPS), 服务器瞬间被淹没, 大量请求被丢弃。

**解法**: 限流 (rate limiter) + 队列管理。

### 1.34.2 现象 2: "P99 越低, 总成本可能越高"

直觉: P99 低 = 服务快 = 资源利用率高 = 成本低。

现实: 优化 P99 需要冗余 (hedged requests), **资源消耗翻倍**。

**举例**: hedged requests 让 P99 降 30%, 但 QPS 容量降 30% (重复请求)。

**判断标准**: 业务 ROI, 不是技术指标。

### 1.34.3 现象 3: "加缓存后 P99 反而上升"

直觉: 缓存 = 更快 = P99 更低。

现实: 缓存击穿 / 雪崩时, P99 会爆。

**举例**:
- 缓存 key 过期, 大量请求穿透到 DB → DB 雪崩
- 缓存节点挂掉, 流量打到另一个节点 → 该节点压力激增

**解法**:
- 缓存预热
- 多级缓存 (L1 + L2)
- 缓存 key 不在 TTL 同时过期 (加随机抖动)

### 1.34.4 现象 4: "异步化一定能降时延"

不一定:
- 异步化适合 IO 密集 (网络/磁盘)
- CPU 密集任务异步化, 反而增加调度开销

**判断标准**: 任务是否是 IO 密集? 是 → 异步化; 否 → 同步。

## 1.35 时延的"理论极限": 光速与内存墙

物理上, 时延有理论极限:

| 操作 | 理论极限 |
| :--- | :--- |
| 内存访问 (L1 cache) | 1 ns |
| 内存访问 (DRAM) | 100 ns |
| SSD 随机读 | 100 μs |
| NVMe SSD 随机读 | 20 μs |
| 同城网络 RTT | 0.5 ms |
| 跨城网络 RTT | 10 ms |
| 跨国网络 RTT | 100 ms |
| 光纤 1 米 | 5 ns |

**含义**:
- 单机 SID 查表理论极限 < 1 μs
- 跨城 SID 编码服务理论极限 > 10 ms (网络)

工业系统一般工作在理论极限的 **10-100x** (即 10x-100x 的优化空间)。

## 1.37 时延 vs QPS 的"Little's Law"

Little's Law 是排队论的基石:

$$
L = \lambda W
$$

- $L$: 系统中平均请求数 (队列长度)
- $\lambda$: 到达率 (QPS)
- $W$: 平均处理时间 (时延)

**应用**:
- 如果 P99 时延 = 100ms, QPS = 1000, 则队列长度 = 1000 × 0.1 = 100 个请求在排队
- 如果 QPS 升到 2000, 队列长度 = 200, **P99 会雪崩**

**工业意义**: **扩容不是按 CPU 利用率, 是按队列长度**。

```python
def should_scale_up(metrics):
    """基于 Little's Law 的扩容判断"""
    avg_latency = metrics['p50_latency_s']
    qps = metrics['qps']
    queue_length = qps * avg_latency

    if queue_length > 1000:  # 队列太长, 扩容
        return True
    if metrics['cpu_utilization'] > 0.7:
        return True
    return False
```

## 1.38 时延优化的"预算分配"

一个 100ms P99 的预算怎么分?

```text
用户网络 (前端到后端):   5 ms  (5%)
├─ 边缘网络:            2 ms
└─ 入口网关:            3 ms

业务请求 (后端):       95 ms  (95%)
├─ 召回:               10 ms  (10%)
├─ 粗排:               15 ms  (15%)
├─ 精排:               50 ms  (50%)
└─ 重排:               20 ms  (20%)
```

**经验分配**:
- 精排占大头 (50%), 因为模型大
- 召回 + 粗排合计 25%, 因为 ANN
- 重排 20%, 多样性约束 + 业务规则

**SID 在分配中的位置**: 召回内部, 占 1-3ms (查表), 几乎不占预算。

## 1.39 时延优化的"长尾"分布建模

实际请求时延往往是 bimodal (双峰):

```text
                    ╱╲
                   ╱  ╲          ← 主峰 (正常请求, ~95%)
                  ╱    ╲
                 ╱      ╲
                ╱        ╲  ╱╲
               ╱          ╲╱  ╲    ← 长尾峰 (异常请求, ~5%)
              ───────────────────────→ 时延
              1ms  10ms  100ms  1000ms
```

**含义**: 优化手段要**分别针对两个峰**:
- 主峰: 优化单请求处理时间 (缓存, 模型压缩)
- 长尾峰: 优化异常处理 (超时, 重试, 熔断)

## 1.40 时延优化的"工程经验清单"

## 1.41 SID 服务与边缘计算

边缘计算 (Edge Computing) 是把计算推到用户身边 (CDN 节点, 5G MEC)。

**SID + 边缘的好处**:
- SID 查表推到边缘 → 用户请求 → 边缘 SID 服务 → 返回结果
- 时延: 5ms (边缘 RTT) vs 50ms (中心 RTT)
- 离线 SID + 在线 query encoder 都可以推到边缘

**挑战**:
- 边缘资源有限 (CPU/内存)
- SID 数据库太大 (10GB) → 放不下
- 解法: 只在边缘放热门 10% SID, 长尾走中心

## 1.47 时延与"可观测性"的"三位一体"

**指标 (Metrics)**:
- 聚合数据 (P99, QPS, 错误率)
- 适合监控 / 告警

**日志 (Logs)**:
- 详细事件 (请求详情, 错误堆栈)
- 适合事后分析

**链路 (Traces)**:
- 跨服务调用链
- 适合找瓶颈

**SID 服务的"三位一体"埋点**:

```python
from prometheus_client import Counter, Histogram
from opentelemetry import trace
import logging

# Metrics
ENCODE_COUNT = Counter('sid_encode_total', 'Total SID encoding requests')
ENCODE_LATENCY = Histogram('sid_encode_duration_seconds', 'SID encoding latency')
ERROR_COUNT = Counter('sid_encode_errors_total', 'Total SID encoding errors')

# Trace
tracer = trace.get_tracer(__name__)

# Log
logger = logging.getLogger(__name__)

@app.post("/encode_sid")
async def encode_sid(req: EncodeRequest):
    with tracer.start_as_current_span("encode_sid") as span:
        ENCODE_COUNT.inc()
        start = time.time()
        try:
            with tracer.start_as_current_span("rq_encode"):
                sid = rq_model.encode(req.embedding)
            ENCODE_LATENCY.observe(time.time() - start)
            span.set_attribute("sid", sid.tolist())
            logger.info(f"encoded item {req.item_id}", extra={
                "latency_ms": (time.time() - start) * 1000,
                "sid": sid.tolist(),
            })
            return {"sid": sid.tolist()}
        except Exception as e:
            ERROR_COUNT.inc()
            logger.exception(f"encode failed for item {req.item_id}")
            raise
```

## 1.48 实时计算与时延:SID 服务的"流式"思考

## 1.54 总结: 时延优化的"心法"

最后 5 条心法, 浓缩所有内容:

1. **先看 P99, 再看平均** — 平均骗人, 长尾是杀手。
2. **缓存为王** — 命中率 > 80% 是工业甜点。
3. **离线能算的不要在线算** — SID 查表是 μs 级, 在线 encoder 是 5ms 级。
4. **P99 优化 = 降低方差** — 不是降均值, 是让最慢变快。
5. **优化 ROI 优先, 不要过早优化** — YAGNI (You Aren't Gonna Need It)。

## 1.55 常见时延相关 Bug

### 1.55.1 Bug 1: 时区导致的数据错位

现象: 某些时间段请求时延高。

原因: 时区转换用了 timezone(), 内部调用慢。

解法: 用 timezone 缓存, 或用 UTC 时间。

### 1.55.2 Bug 2: 浮点精度导致 NaN

现象: 偶尔返回 None。

原因: 浮点除 0, 出现 NaN。

解法: 除法前判断, 或用 np.errstate。

### 1.55.3 Bug 3: 字符串拼接累积内存

现象: 长时间运行后 OOM。

原因: 字符串拼接产生新对象, 旧对象没释放。

解法: 用 io.StringIO 或 join。

### 1.55.4 Bug 4: 全局变量被多线程污染

现象: 偶发性错误。

原因: 多个请求共享全局状态。

解法: ThreadLocal 或 request context。

### 1.55.5 Bug 5: 日志太多拖慢服务

现象: 服务慢, 但 CPU 不高。

原因: 大量 IO 操作 (写日志)。

解法: 异步日志, 或采样日志 (1/100)。

## 1.60 进阶时延: 跨数据中心部署的"全局时延"

### 1.60.1 跨数据中心部署的时延挑战

大型推荐系统通常跨多个数据中心部署, 用户请求路由到最近的机房:

```text
用户
 ├→ 北京机房 (北方用户)
 ├→ 上海机房 (华东用户)
 └→ 广州机房 (南方用户)
```

**机房间时延**:
- 同城机房 (北京 A - 北京 B): 0.5-1ms
- 同城异区 (北京 - 上海): 5-15ms
- 跨大区 (北京 - 广州): 20-40ms

### 1.60.2 SID 服务的多机房部署策略

**方案 1: 全量复制 (推荐)**
```text
每个机房有完整 SID 数据库副本
- 优点: 用户请求总在最近机房, 时延最低
- 缺点: 数据同步复杂, 一致性难保证
```

**方案 2: 主从部署**
```text
主机房: 全量 SID 数据库
从机房: 部分热门 SID (top 10%) + 长尾回源
- 优点: 数据一致性好
- 缺点: 长尾 SID 时延高 (回源 10-30ms)
```

**方案 3: 就近写**
```text
每个机房写自己的 SID, 异步同步到其他机房
- 优点: 写时延低
- 缺点: 跨机房读可能读到旧数据
```

### 1.60.3 SID 数据同步的实现

```python
class SIDDBReplication:
    """SID 数据库跨机房同步"""
    def __init__(self):
        self.local_db = ...  # 本地
        self.remote_dbs = {dc: ... for dc in ['beijing', 'shanghai', 'guangzhou']}
        self.kafka_producer = KafkaProducer(...)

    def put(self, item_id, sid):
        """写入本地 + 异步广播"""
        self.local_db.put(item_id, sid)
        # 异步发到 Kafka, 其他机房订阅
        self.kafka_producer.send('sid_updates', {
            'item_id': item_id,
            'sid': sid,
            'source_dc': 'local',
            'timestamp': time.time(),
        })

    def on_update(self, message):
        """收到其他机房的更新"""
        if message['source_dc'] == 'local':
            return  # 自己发的, 忽略
        self.local_db.put(message['item_id'], message['sid'])
```

**一致性保证**:
- 写入: 同步写本地 (强一致)
- 读取: 读本地 (最终一致, 通常延迟 < 1s)
- 全局视图: 不强求 (跨机房一致性代价高)

## 1.61 时延与"一致性"的张力 (CAP 三角)

CAP 定理: 一致性 (C), 可用性 (A), 分区容忍 (P), 只能三选二。

**SID 服务在 CAP 中的取舍**:
- **C (Consistency)**: 所有机房看到一致的 SID
- **A (Availability)**: 任何机房故障, 服务不挂
- **P (Partition tolerance)**: 机房间网络故障不挂

**实际选择**:
- 跨机房部署: 必须 P (网络分区不可避免)
- 二选一: 选 A + 弱 C (最终一致)

**结论**: SID 服务是 **AP 系统**, 优先可用性, 容忍短暂不一致。

## 1.62 时延优化的"控制论"视角

把时延优化想成"控制系统":

```text
         ┌─────────┐
         │         │
请求 →  [Controller] → 系统行为 → 监控 → [反馈]
         │         │       │
         │         │       ↓
         │         │   [P99/QPS/Error]
         │         │
         └─────────┘
              ↑
         控制信号 (扩缩容/降级/限流)
```

### 1.62.1 经典控制: PID

```text
输出 = Kp * 误差 + Ki * 积分 + Kd * 微分
```

应用: 自动扩缩容 (HPA)。

### 1.62.2 工业实践: 自适应限流

```python
class AdaptiveRateLimiter:
    """基于时延的自适应限流"""
    def __init__(self):
        self.target_p99_ms = 100
        self.current_qps = 1000
        self.smoothing = 0.1

    def on_metrics(self, p99_ms, qps):
        """根据 P99 调整限流"""
        if p99_ms > self.target_p99_ms * 1.2:
            # P99 太高, 降低 QPS
            self.current_qps *= (1 - self.smoothing)
        elif p99_ms < self.target_p99_ms * 0.8:
            # P99 健康, 提升 QPS
            self.current_qps *= (1 + self.smoothing)
        # 边界
        self.current_qps = max(100, min(self.current_qps, 100000))

    def allow(self):
        """判断是否允许请求"""
        return random.random() < self.current_qps / self.measured_qps
```

## 1.63 时延优化的"博弈论"视角

时延优化本质是**资源分配的博弈**:

```text
资源 (CPU/内存/网络) 是有限的
需求 (QPS/用户数/功能) 是无限的
时延是资源分配的"目标函数"
```

**博弈策略**:

| 策略 | 描述 | 适用 |
| :--- | :--- | :--- |
| **公平分配** | 每个请求同等资源 | 一般场景 |
| **优先级** | VIP 请求优先 | 高价值用户 |
| **SLA 分级** | 不同档位不同资源 | 多档服务 |
| **优胜劣汰** | 慢请求超时丢弃 | 保护系统 |
| **排队论** | M/M/c 队列模型 | 经典方法 |

## 1.64 经典排队论模型 (M/M/c)

**M/M/c 队列**:
- M: 泊松到达 (Markov)
- M: 指数服务时间
- c: c 个服务台

**核心公式**:

利用率:
$$
\rho = \frac{\lambda}{c \mu}
$$

平均等待时间:
$$
W_q = \frac{P_0 \cdot (c\rho)^c}{c! (1-\rho)^2} \cdot \frac{1}{\mu}
$$

**应用**: SID 服务容量评估

```text
例: 100 QPS, 单实例处理 50 QPS (服务率 μ=50)
需要 c = 2 个实例

利用率 ρ = 100 / (2 × 50) = 1.0 (危险! 已满载)
建议 c = 3 个实例, ρ = 0.67 (健康)
```

## 1.65 时延优化的"信息论"视角

### 1.65.1 信息熵与时延

请求时延分布的**熵**反映了时延的不确定性:

$$
H(X) = -\sum_i p_i \log_2 p_i
$$

- 低熵 = 时延集中 = 好
- 高熵 = 时延分散 = 差

**优化方向**: 降低熵 → 让时延更可预测。

### 1.65.2 信道容量与吞吐

把推荐系统想成"信道", 容量 (capacity) 是最大吞吐:

$$
C = B \log_2(1 + S/N)
$$

类比: SID 服务容量 ∝ 1 / 时延。

**含义**: 时延越短, 容量越大。

## 1.66 时延的"经济学"视角

### 1.66.1 时延成本

```text
时延 100ms → 用户流失 1% → 损失收入 X
时延 500ms → 用户流失 5% → 损失收入 5X
时延 1000ms → 用户流失 10% → 损失收入 10X
```

**结论**: 时延优化的 ROI 与用户价值正相关。

### 1.66.2 时延 vs 准确率的成本

```text
效果提升 1% (NDCG) → 收入 +A%
时延增加 100ms → 收入 -B%

净收益 = A - B

SID 服务的杠杆: 时延几乎不增加, 效果显著提升 → 净收益最大化
```

## 1.67 时延优化的"陷阱"

### 1.67.1 陷阱 1: 优化错指标

现象: 优化了 P50, 但 P99 没变。

原因: 优化错位置, 真正的瓶颈在 P99 请求。

### 1.67.2 陷阱 2: 优化时机不对

现象: 上线时优化, 但 QPS 没起来, 优化白做。

原因: 过早优化 (premature optimization)。

### 1.67.3 陷阱 3: 优化后回退

现象: 优化后效果好, 但三个月后效果消失。

原因: 数据分布漂移, 优化针对的是旧数据。

### 1.67.4 陷阱 4: 优化变负优化

现象: 加了缓存, 系统更慢。

原因: 缓存命中率低, 维护缓存的开销 > 缓存收益。

### 1.67.5 陷阱 5: 优化了不该优化的

现象: 优化了边角功能, 核心功能慢。

原因: 没找对瓶颈, 在错的位置优化。

## 1.69 时延优化的"前沿技术"

### 1.69.1 eBPF / XDP

Linux 内核技术, 在网络层做时延优化, 不需要改应用代码。

应用: 网络包处理加速 (10x), 时延 -30%。

### 1.69.2 DPDK

用户态网络栈, 绕过内核, 时延 -50%。

应用: 高频交易系统, 工业推荐用得少。

### 1.69.3 RDMA

远程直接内存访问, 跳过 CPU, 时延 -80%。

应用: GPU 集群通信, 大模型推理。

### 1.69.4 Persistent Memory (PMem)

内存 + 存储的混合, 时延介于两者之间。

应用: 大索引加载 (FAISS), 启动时间 -50%。

### 1.69.5 CXL (Compute Express Link)

新一代内存互联协议, 时延 -30%, 带宽 +5x。

应用: 大模型推理 (CPU + GPU 共享内存)。

## 1.71 时延与"工作生活平衡"

最后一点非技术性提醒:

**时延优化是"长期主义", 不是"立竿见影"**。

- 一个优化可能要 1-3 个月才有显著效果
- 优化的效果可能需要 1-2 年才能完全显现
- 但**累积效果惊人**: 5 年下来, 系统可能从 P99=500ms 优化到 P99=50ms

**给初学者的建议**:
- 不要想着一周优化 50%, 不现实
- 每月优化 5%, 持续 12 个月, 就是 +80% 的优化
- "持续的小改进" 比 "一次大重构" 更稳
