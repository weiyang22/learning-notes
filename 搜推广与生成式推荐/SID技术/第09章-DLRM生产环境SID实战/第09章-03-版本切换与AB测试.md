## 3.2 AB 测试指标

| 类型 | 指标 | 说明 |
| :--- | :--- | :--- |
| **核心** | CTR / CVR / 时长 | 新版本是否提升业务目标 |
| **召回质量** | Recall / 覆盖率 | 是否召回更多相关物品 |

## 3.3 SID 版本切换的特殊难点

换 SID 版本比换普通模型更麻烦,因为 **SID 是一整套离散编码,牵一发动全身**:

- **索引重建**:新 SID → 整个 ANN 索引/倒排要重建,不能热切。
- **双版本并存**:灰度期新旧 SID 同时在线,存储/内存翻倍。
- **下游耦合**:召回/排序/缓存都依赖 SID,需协同切换,否则版本错配。
- **不可逆性**:用户行为已按新 SID 积累后,回滚会丢一段数据一致性。

**安全切换流程**:
```text
离线训练新 SID → 离线评估(碰撞率/覆盖率/下游AUC)
  → 影子流量(旁路打分, 不影响线上, 对比一致性)
  → 小流量灰度(1%→5%→20%→50%)
  → 每档观察核心+护栏指标, 达标才放量
  → 全量 + 保留回滚点(旧索引不立即删)
```

## 3.4 分流的正确姿势

```python
import hashlib
def stable_bucket(user_id, salt="sid_exp_2026"):
    # 用稳定 hash(非 Python 内置 hash, 它跨进程不稳定)
    h = hashlib.md5(f"{salt}:{user_id}".encode()).hexdigest()
    return int(h, 16) % 100
```

- **稳定分桶**:同一用户始终在同一组(用 md5 而非 `hash()`,后者跨进程不稳定)。
- **正交实验**:不同实验用不同 salt,避免相互干扰。
- **holdout**:留一小撮永不实验的对照组,衡量长期累积影响。

## 3.6 AB 实验的"统计学基础"

### 3.6.1 假设检验

AB 实验的本质是**假设检验**:

- **零假设 (H0)**: 新版本与旧版本效果相同
- **备择假设 (H1)**: 新版本效果 ≠ 旧版本

**判断流程**:
```text
1. 收集数据 (新版本 vs 旧版本)
2. 计算检验统计量 (t / z / chi-square)
3. 计算 p 值 (观察到的差异在 H0 下的概率)
4. p < 0.05 → 拒绝 H0, 接受 H1
5. p ≥ 0.05 → 不能拒绝 H0, 差异可能为噪声
```

### 3.6.2 t 检验 vs z 检验

| 检验 | 适用 | 公式 |
| :--- | :--- | :--- |
| **t 检验** | 小样本 (n < 30), 总体方差未知 | $t = \frac{\bar{X} - \mu_0}{s / \sqrt{n}}$ |
| **z 检验** | 大样本 (n ≥ 30), 总体方差已知 | $z = \frac{\bar{X} - \mu_0}{\sigma / \sqrt{n}}$ |

工业推荐系统一般样本量很大, 用 **z 检验**。

### 3.6.3 双侧 vs 单侧检验

- **双侧**: 新版本效果可能更好或更差 (工业默认)
- **单侧**: 只关心新版本是否更好 (省钱但有偏)

工业推荐一般用双侧, 防止"事后选择性报告"。

### 3.6.4 显著性 ≠ 业务显著

```text
统计显著: p < 0.05 (差异不是噪声)
业务显著: 差异 > 业务阈值 (如 CTR 涨 0.5%)
```

两者都要看。

## 3.7 AB 实验的"样本量计算"

### 3.7.1 公式

$$
n = \frac{2 \sigma^2 (z_{\alpha/2} + z_\beta)^2}{\delta^2}
$$

其中:
- $\sigma$: 标准差
- $z_{\alpha/2}$: 显著性水平对应的 z 值 (α=0.05 → 1.96)
- $z_\beta$: 统计功效对应的 z 值 (β=0.2 → 0.84)
- $\delta$: 最小可检测差异 (MDE)

### 3.7.2 工业实例

CTR 实验:
- 当前 CTR = 5%
- 标准差 σ ≈ 0.05 (CTR 方差)
- 期望检测 Δ = 0.5% (CTR 涨 0.5%, 即 5.0% → 5.5%)
- α = 0.05, β = 0.2

$$
n = \frac{2 \times 0.05^2 \times (1.96 + 0.84)^2}{0.005^2} = \frac{2 \times 0.0025 \times 7.84}{0.000025} = 1568
$$

每组需要 ~1600 用户。总共 3200 用户。

**实际**: 工业一般会用百万级用户, 远超最小样本量, 因为还要做分桶对比。

### 3.7.3 MDE (Minimum Detectable Effect)

```text
MDE = z * sqrt(2 * σ² / n)

n=10000, σ=0.05, z=2.58 (α=0.01)
MDE = 2.58 * sqrt(2 * 0.0025 / 10000) = 0.0018 (0.18%)
```

**含义**: 1 万用户可以检测 0.18% 的 CTR 差异。

## 3.8 AB 实验的"分桶策略"

### 3.8.1 用户级分桶 (最常用)

```python
def user_bucket(user_id, salt):
    """用户级稳定分桶"""
    h = hashlib.md5(f"{salt}:{user_id}".encode()).hexdigest()
    return int(h, 16) % 100

def assign_group(user_id, traffic_split, salt):
    bucket = user_bucket(user_id, salt)
    cumulative = 0
    for group, ratio in traffic_split.items():
        cumulative += ratio * 100
        if bucket < cumulative:
            return group
    return list(traffic_split.keys())[-1]
```

**优势**:
- 同一用户始终在同一组 (体验一致)
- 跨进程一致 (md5)

### 3.8.2 请求级分桶

```python
def request_bucket(request_id, salt):
    """请求级分桶 (适合短期实验)"""
    ...
```

**适用**: 短期实验 (如新功能), 但用户体验不连续 (同一用户可能看到不同版本)。

### 3.8.3 时间分桶

```python
def time_bucket(timestamp, hour_windows):
    """时间分桶 (如一天内不同小时)"""
    ...
```

**适用**: 短期测试, 防止用户跨组看到不同版本。

### 3.8.4 分桶的"陷阱"

- **新用户 / 老用户**: 老用户有历史, 行为稳定, 适合实验; 新用户行为随机, 干扰大
- **跨设备**: 一个用户在多个设备, 应保持分桶一致
- **跨实验**: 多个实验同时进行, 用不同 salt 避免互相污染

## 3.9 AB 实验的"指标体系"

### 3.9.1 OEC (Overall Evaluation Criterion)

OEC 是实验的"北极星指标", 单一目标函数。

```text
OEC = 0.5 × CTR + 0.3 × CVR + 0.2 × 时长
```

或更复杂的:

```text
OEC = (点击 - 误点击) × 时长 × CVR × 长期价值
```

### 3.9.2 多维度指标

不能只看一个指标, 要看多个:

| 维度 | 指标 | 关注点 |
| :--- | :--- | :--- |
| **业务** | CTR / CVR / GMV | 直接业务影响 |
| **用户** | 留存 / 满意度 | 长期价值 |
| **系统** | P99 时延 / 错误率 | 稳定性 |
| **公平** | 长尾物品曝光 | 生态健康 |
| **多样性** | 品类熵 / 基尼 | 用户体验 |

### 3.9.3 护栏指标 (Guardrails)

护栏指标是**不能破**的指标, 破了就回滚:

| 护栏 | 阈值 |
| :--- | :--- |
| P99 时延 | < 200ms (基线 2x) |
| 错误率 | < 0.5% (基线) |
| 长尾物品曝光 | 不跌 > 20% |
| 客诉 | 不增 > 5x |

### 3.9.4 反指标 (Counter Metrics)

反指标是"看似正面但实际负面"的指标:

- **CTR 涨但时长跌**: "标题党"
- **CVR 涨但 GMV 跌**: "高客单价低转化率"
- **召回涨但多样性跌**: "推荐同质化"

要警惕反指标。

## 3.10 AB 实验的"实施流程"

### 3.10.1 实验设计阶段

```text
1. 明确假设
   - 新版本预期提升 X%
   - 这是科学假设, 不是愿望

2. 确定 OEC + 护栏指标
   - 主指标: CTR / CVR / GMV
   - 护栏: 时延 / 错误率 / 多样性

3. 计算样本量
   - 基于 MDE + α + β
   - 工业一般多算 2x buffer

4. 设计分组
   - 实验组: 新版本
   - 对照组: 旧版本 (5-10%)
   - Holdout: 永不实验 (1-2%)

5. 设计时长
   - 至少 7 天 (覆盖工作日 + 周末)
   - 大型实验 14-30 天

6. 注册实验
   - 实验名 / 假设 / OEC / 护栏 / 时长
   - 不可中途修改
```

### 3.10.2 实验执行阶段

```text
1. 配置分流
   - md5(salt:user_id) 分桶
   - 配置到流量分发系统

2. 监控实时指标
   - 核心指标每 1 小时看一次
   - 护栏指标实时监控

3. 处理异常
   - 护栏破 → 立即停止
   - 核心指标显著恶化 → 评估后停止

4. 不修改实验
   - 实验期间不修改配置
   - 不引入其他变量

5. 记录问题
   - 任何异常都记录
   - 复盘材料
```

### 3.10.3 实验分析阶段

```text
1. 数据清洗
   - 剔除异常用户 (机器人 / 测试账号)
   - 剔除异常时间段 (系统故障)

2. 显著性检验
   - t 检验 / z 检验
   - 计算置信区间

3. 分桶对比
   - 按用户活跃度 / 物品热度
   - 找到主要贡献群体

4. 多指标综合
   - OEC 是否涨
   - 护栏是否破
   - 反指标是否变

5. 决策
   - 通过: 推全量
   - 失败: 回滚
   - 模糊: 延长实验 / 重新设计

6. 复盘
   - 写实验报告
   - 沉淀经验
```

### 3.10.4 实验上线后

```text
1. 全量
   - 推 100% 流量
   - 旧版本保留 7 天 (回滚点)

2. 长期监控
   - 7 日 / 30 日指标
   - 长期 LTV

3. 写经验
   - 实验报告
   - 知识库
```

## 3.11 SID 灰度发布的"特殊细节"

### 3.11.1 SID 灰度的"额外检查点"

普通模型灰度只需要看预测效果, SID 灰度还要看:

```text
SID 特有检查:
  - 重建 MSE 漂移
  - 碰撞率变化
  - 码本利用率
  - 新旧 SID 召回重合度
  - 索引重建耗时
  - 双版本内存占用
```

### 3.11.2 SID 灰度的"延迟效应"

SID 改变后, 用户行为按新 SID 积累, **但用户历史用旧 SID**。

```text
切 SID 前: 用户 A 看了物品 [3, 5, 2, 7, 9] (旧 SID)
切 SID 后: 物品 [3, 5, 2, 7, 9] 可能是不同物品
         但用户历史还是这串数字
         模型 "看不懂"
```

**对策**:
- 短期: 双版本并行, 模型兼容两套
- 中期: 重训模型用新 SID
- 长期: 历史行为用新 SID 重新编码

### 3.11.3 SID 灰度的"回滚窗口"

普通模型回滚几秒就行, SID 回滚要保留:

```text
旧索引 / 旧码本 / 旧 SID 表 / 旧模型 至少 7 天
```

**原因**: 用户行为用旧 SID 积累, 一旦切回必须还能用。

## 3.12 AB 实验的"分桶一致性"

### 3.12.1 为什么分桶要稳定?

```text
同一用户必须始终在同一组
否则:
  - 用户体验不连续 (一会新版本, 一会老版本)
  - 指标对比失真 (数据污染)
```

### 3.12.2 md5 vs Python hash()

```python
import hashlib
import sys

user_id = "12345"

# Python 内置 hash (跨进程不稳定!)
print(hash(user_id))  # 在不同进程可能不同

# md5 (稳定)
h = hashlib.md5(f"salt:{user_id}".encode()).hexdigest()
print(int(h, 16) % 100)  # 跨进程一致
```

**事故案例**: 某公司用 `hash()` 分桶, Python 进程重启后用户分桶变了, 实验数据全乱了。

### 3.12.3 多实验的"正交性"

多个实验同时进行, 要保证分桶**正交**:

```python
def experiment_a_bucket(user_id):
    return hashlib.md5(f"exp_a:{user_id}".encode()).hexdigest()

def experiment_b_bucket(user_id):
    return hashlib.md5(f"exp_b:{user_id}".encode()).hexdigest()
```

不同 salt = 不同分桶, 实验互不干扰。

### 3.12.4 实验的"互斥"与"正交"

- **互斥**: 一个用户只能在一个实验组 (简单清晰)
- **正交**: 一个用户可以同时在多个实验 (复杂但灵活)

工业默认: **正交** (用不同 salt), 因为实验多。

## 3.13 AB 实验的"陷阱"

### 3.13.1 陷阱 1: 用户跨组

现象: 同一个用户在新旧版本都出现。

原因: 分桶函数不稳定 (Python hash) 或 cookie 丢失。

**对策**: 用 md5 稳定分桶。

### 3.13.2 陷阱 2: 短期效应

现象: 第 1 天 CTR 涨 5%, 第 7 天 CTR 跌 2%。

原因: "新奇效应", 用户对新鲜感反应, 不是真提升。

**对策**: 至少跑 7 天。

### 3.13.3 陷阱 3: 网络效应

现象: 实验组用户分享给对照组用户, 污染数据。

原因: 社交网络。

**对策**: 实验设计时考虑, 用地理 / 时段分桶。

### 3.13.4 陷阱 4: 数据泄露

现象: 离线 / 在线指标不一致。

原因: 离线用未来信息。

**对策**: 严格时序划分。

### 3.13.5 陷阱 5: 实验污染

现象: 同时跑多个实验, 互相干扰。

原因: 分桶不独立。

**对策**: 正交分桶 + 实验注册系统。

## 3.15 AB 实验的"高级主题"

### 3.15.1 多变量实验 (Multivariate Testing)

不止一个变量, 多个变量同时实验:

```text
变量 A: SID 版本 (v1 / v2)
变量 B: 精排模型 (DLRM / DIN)
变量 C: 召回通路 (3 路 / 5 路)

实验设计: 2 × 2 × 2 = 8 组
```

**挑战**:
- 样本量需求增大
- 交互作用复杂

**适用**: 想同时优化多个组件。

### 3.15.2 多臂老虎机 (Multi-Armed Bandit)

不固定分桶, 动态调整流量:

```python
class BanditRouter:
    """多臂老虎机: 动态调整流量"""
    def __init__(self, arms, epsilon=0.1):
        self.arms = arms  # ['v1', 'v2']
        self.epsilon = epsilon
        self.counts = {a: 0 for a in arms}
        self.rewards = {a: 0 for a in arms}

    def select(self):
        """epsilon-greedy 选择"""
        if random.random() < self.epsilon:
            return random.choice(self.arms)
        else:
            # 选择平均 reward 最高的 arm
            avg_rewards = {a: self.rewards[a] / max(self.counts[a], 1) for a in self.arms}
            return max(avg_rewards, key=avg_rewards.get)

    def update(self, arm, reward):
        self.counts[arm] += 1
        self.rewards[arm] += reward
```

**适用**: 长期优化, 不需要严格显著性。

### 3.15.4 Switchback 实验

按时段切换版本 (如每天切一次):

```python
def switchback_assign(timestamp, treatment_period='day'):
    """Switchback 分桶"""
    if treatment_period == 'day':

```

```text
2. 分流规则: md5 稳定分桶
3. 实时指标: QPS / CTR / 时延
4. 显著性检验: 自动计算 p 值
5. 报警: 护栏破 → 通知
6. 实验报告: 自动生成
7. 历史回溯: 之前的实验数据
```

## 3.17 实验的"伦理与合规"

### 3.17.1 用户知情

部分实验需要用户知情:
- A/B 实验: 通常不需要 (用户不知情)
- 收集用户数据: 需要隐私政策
- 影响用户行为: 一般无要求

### 3.17.2 公平性

实验不能歧视特定群体:
- 实验组 / 对照组要平衡
- 不同群体的指标都要看
- 不能故意"伤害"对照组

### 3.17.3 不可逆操作

有些操作不可逆, 谨慎:
- 删除用户数据 (谨慎)
- 永久改模型权重 (可逆)
- 推送通知 (不可逆)

## 3.18 AB 实验的"长期实践"

### 3.18.1 实验"疲劳"

长期看, 用户的"新奇感"消退, 实验效果可能变差。

**对策**:
- 定期重新设计实验
- 关注长期指标 (LTV / 留存)

### 3.18.2 实验"漂移"

随着时间, 旧实验的分桶可能漂移:
- 用户行为变化
- 数据分布变化
- 模型本身漂移

**对策**:
- 定期重新校准
- 监控实验组的代表性

### 3.18.3 实验"通胀"

AB 实验做多了, 显著性阈值要调整:

```text
多次检验 (m 次):
  p_corrected = 1 - (1 - p)^m

例: 5 个指标都 p=0.05 → 综合 p = 0.23 (不显著)
```

**对策**: Bonferroni 校正 / FDR 控制。

## 3.19 AB 实验的"反模式"

### 3.19.1 反模式 1: 实验太多

现象: 同时跑 50 个实验, 结果混乱。

原因: 想"快"。

**对策**: 集中资源做重要实验。

### 3.19.2 反模式 2: 实验太长

现象: 实验跑 6 个月, 期间产品都变了。

原因: 想"严谨"。

**对策**: 7-30 天为限。

### 3.19.3 反模式 3: 只看单一指标

现象: CTR 涨就推, 忽略其他指标。

原因: 简化决策。

**对策**: 多指标综合判断。

### 3.19.4 反模式 4: 不做显著性检验

现象: 看 CTR 涨 0.5% 就推。

原因: 偷懒。

**对策**: 强制 p < 0.05 + 多次实验验证。

### 3.19.5 反模式 5: 事后选择性报告

现象: 跑了 10 个指标, 只报告涨的那个。

原因: 想"赢"。

**对策**: 实验前确定指标, 实验后报告全部。

```python
class ABExperiment:
    """完整的 AB 实验系统"""
    def __init__(self, config):
        self.config = config
        self.metrics_collector = MetricsCollector()

    def assign(self, user_id):

                self.stop()
                return

            # 3. 检查显著性 (可选)
            if day >= 3:  # 至少 3 天数据
                sig = self.check_significance()
                if sig['p_value'] < 0.001 and abs(sig['effect_size']) > 0.005:
                    logger.info(f"Strong significance at day {day}")
                    # 可以提前结束 (但一般不)

    def collect_daily_metrics(self):
        """收集每日指标"""
        # 从数据库 / 日志系统读
        ...

    def check_guardrails(self, metrics):
        """检查护栏指标"""
        return any(
            metrics[k] > self.config.guardrails[k]
            for k in self.config.guardrails
        )

    def check_significance(self):
        """检查显著性"""
        treatment = self.metrics_collector.get_treatment_metrics()
        control = self.metrics_collector.get_control_metrics()

        from scipy.stats import ttest_ind
        t_stat, p_value = ttest_ind(treatment, control)

        effect_size = np.mean(treatment) - np.mean(control)
        return {
            'p_value': p_value,
            'effect_size': effect_size,
            'significant': p_value < 0.05,
        }

    def generate_report(self):
        """生成实验报告"""
        sig = self.check_significance()
        return {
            'experiment_name': self.config.name,
            'duration': self.config.duration_days,
            'treatment_size': self.metrics_collector.get_treatment_n(),
            'control_size': self.metrics_collector.get_control_n(),
            'treatment_mean': np.mean(self.metrics_collector.get_treatment_metrics()),
            'control_mean': np.mean(self.metrics_collector.get_control_metrics()),
            'p_value': sig['p_value'],
            'effect_size': sig['effect_size'],
            'significant': sig['significant'],
            'guardrails_breached': self.check_guardrails(...),
            'recommendation': self.make_recommendation(sig),
        }

    def make_recommendation(self, sig):
        """决策"""
        if sig['p_value'] > 0.05:
            return "Inconclusive - extend experiment or fail"
        elif sig['effect_size'] > 0:
            return "Ship - significant positive effect"
        else:
            return "Rollback - significant negative effect"
```

```python
class RolloutController:
    """灰度发布控制器"""
    def __init__(self, config):
        self.config = config
        self.current_stage = 0
        self.metrics = MetricsCollector()

    def get_traffic_pct(self):
        """获取当前流量比例"""
        return self.config.rollout_stages[self.current_stage].traffic_pct

    def should_advance(self):
        """判断是否进入下一阶段"""
        stage = self.config.rollout_stages[self.current_stage]
        if not stage.duration_hours:
            return False

        elapsed = self.metrics.elapsed_hours()
        if elapsed < stage.duration_hours:
            return False

        # 检查所有护栏 + 核心指标
        metrics = self.metrics.get_current()
        for m in stage.metrics_to_check:
            if not self.check_metric(m, metrics):
                return False
        return True

    def advance(self):
        """进入下一阶段"""
        self.current_stage += 1
        new_pct = self.config.rollout_stages[self.current_stage].traffic_pct
        self.update_traffic_pct(new_pct)
        notify(f"Advanced to stage {self.current_stage}, traffic={new_pct*100}%")

    def rollback(self, reason):
        """回滚"""
        self.update_traffic_pct(0)
        self.current_stage = -1
        notify_urgent(f"Rollback triggered: {reason}")
```

```python
import hashlib
import time
import json

from dataclasses import dataclass, field
from typing import Dict, List, Optional, Tuple
from enum import Enum
from datetime import datetime, timedelta

logger = logging.getLogger(__name__)

# 数据模型
# ============================================================================

class StageStatus(Enum):
    """灰度阶段状态"""
    PENDING = "pending"
    RUNNING = "running"
    ADVANCING = "advancing"
    COMPLETED = "completed"
    ROLLBACK = "rollback"


@dataclass
class RolloutStage:
    """灰度阶段配置"""
    name: str
    traffic_pct: float
    duration_hours: int
    min_sample_size: int
    check_metrics: List[str]
    promotion_criteria: Dict[str, float]  # {metric: min_threshold}


@dataclass
class ExperimentConfig:
    """实验配置"""
    experiment_id: str
    experiment_name: str
    salt: str
    control_version: str
    treatment_version: str
    stages: List[RolloutStage]
    guardrails: Dict[str, float]
    notification_channels: List[str]
    holdout_pct: float = 0.01


@dataclass
class MetricsSnapshot:
    """指标快照"""
    timestamp: float
    experiment_id: str
    stage: str
    n_control: int
    n_treatment: int
    metrics: Dict[str, float]
    p_values: Dict[str, float]
    effects: Dict[str, float]


# ============================================================================
# 分流器
# ============================================================================

class TrafficSplitter:
    """流量分流器"""
    def __init__(self, config: ExperimentConfig):
        self.config = config

    def bucket(self, user_id: int) -> int:
        """稳定分桶"""
        h = hashlib.md5(
            f"{self.config.salt}:{user_id}".encode()
        ).hexdigest()
        return int(h, 16) % 100

    def is_holdout(self, user_id: int) -> bool:
        """是否在 holdout 组"""
        return self.bucket(user_id) < self.config.holdout_pct * 100

    def get_group(self, user_id: int, stage_traffic_pct: float) -> str:
        """根据阶段流量比例, 决定用户在哪组"""
        bucket = self.bucket(user_id)

        # holdout 组在最前面
        if bucket < self.config.holdout_pct * 100:
            return "holdout"

        # 实验组和对照组
        adjusted_bucket = bucket - int(self.config.holdout_pct * 100)
        adjusted_total = 100 - int(self.config.holdout_pct * 100)

        if adjusted_bucket < stage_traffic_pct * adjusted_total / 100:
            return "treatment"
        return "control"

    def get_sid_version(self, user_id: int, stage_traffic_pct: float) -> str:
        """根据用户 ID 和当前阶段, 返回 SID 版本"""
        group = self.get_group(user_id, stage_traffic_pct)
        if group == "treatment":
            return self.config.treatment_version
        return self.config.control_version


# ============================================================================
# 指标收集器
# ============================================================================

class MetricsCollector:
    """指标收集器"""
    def __init__(self):
        self.data = []  # List[MetricsSnapshot]

    def record(self, snapshot: MetricsSnapshot):
        """记录一个快照"""
        self.data.append(snapshot)

    def get_by_group(self, group: str) -> List[MetricsSnapshot]:
        """获取某个组的快照"""
        return [s for s in self.data if s.get("group") == group]

    def get_latest(self, stage: Optional[str] = None) -> Optional[MetricsSnapshot]:
        """获取最新快照"""
        relevant = [s for s in self.data if stage is None or s.stage == stage]
        return max(relevant, key=lambda s: s.timestamp) if relevant else None

    def compute_aggregate(self, group: str, metric: str) -> Tuple[float, int]:
        """计算某组某指标的聚合"""
        relevant = [
            s.metrics[metric] for s in self.data
            if s.metrics.get(metric) is not None
        ]
        if not relevant:
            return (0.0, 0)
        return (sum(relevant) / len(relevant), len(relevant))


# ============================================================================
# 显著性检验
# ============================================================================

class SignificanceTest:
    """显著性检验"""

    @staticmethod
    def welch_t_test(treatment: List[float], control: List[float]) -> Dict:
        """Welch's t-test (不需要方差齐性)"""
        from scipy.stats import ttest_ind

        t_stat, p_value = ttest_ind(treatment, control, equal_var=False)

        mean_t = sum(treatment) / len(treatment)
        mean_c = sum(control) / len(control)
        effect_size = (mean_t - mean_c) / (
            (sum([(x - mean_t) ** 2 for x in treatment]) / len(treatment) +
             sum([(x - mean_c) ** 2 for x in control]) / len(control)
        ) ** 0.5

        return {
            't_stat': t_stat,
            'p_value': p_value,
            'effect_size': effect_size,  # Cohen's d
            'significant': p_value < 0.05,
            'mean_treatment': mean_t,
            'mean_control': mean_c,
        }

    @staticmethod
    def compute_power(n_t: int, n_c: int, effect_size: float, alpha: float = 0.05) -> float:
        """计算统计功效 (power)"""
        from scipy.stats import norm

        se = (1 / n_t + 1 / n_c) ** 0.5
        z_alpha = norm.ppf(1 - alpha / 2)
        z_beta = (effect_size / se) - z_alpha
        power = norm.cdf(z_beta)
        return power

# 灰度控制器
# ============================================================================

class RolloutController:
    """灰度发布控制器"""

    def __init__(
        self,
        config: ExperimentConfig,
        splitter: TrafficSplitter,
        metrics: MetricsCollector,
    ):
        self.config = config
        self.splitter = splitter
        self.metrics = metrics
        self.current_stage_idx = 0
        self.stage_start_time = None
        self.status = StageStatus.PENDING
        self.traffic_router = None  # 实际流量路由

    def start(self):
        """启动灰度"""
        if self.status == StageStatus.RUNNING:
            return
        logger.info(f"Starting rollout: {self.config.experiment_name}")
        self.current_stage_idx = 0
        self.stage_start_time = time.time()
        self.status = StageStatus.RUNNING
        self.update_traffic_split()

    def update_traffic_split(self):
        """更新流量分配"""
        if not self.config.stages:
            return
        current_stage = self.config.stages[self.current_stage_idx]
        if self.traffic_router:
            self.traffic_router.set_traffic_pct(
                self.config.treatment_version,
                current_stage.traffic_pct,
            )
        logger.info(
            f"Stage {self.current_stage_idx + 1}/{len(self.config.stages)}: "
            f"traffic_pct={current_stage.traffic_pct}"
        )

    def check_promotion(self) -> Tuple[bool, str]:
        """检查是否可以进入下一阶段"""
        if self.status != StageStatus.RUNNING:
            return False, "Not running"

        current_stage = self.config.stages[self.current_stage_idx]

        # 1. 时间检查
        elapsed = (time.time() - self.stage_start_time) / 3600
        if elapsed < current_stage.duration_hours:
            return False, f"Only {elapsed:.1f} hours elapsed, need {current_stage.duration_hours}"

        # 2. 样本量检查
        snapshot = self.metrics.get_latest(current_stage.name)
        if not snapshot:
            return False, "No metrics yet"
        if snapshot.n_treatment < current_stage.min_sample_size:
            return False, f"Insufficient treatment samples ({snapshot.n_treatment})"

        # 3. 护栏检查
        for metric, threshold in self.config.guardrails.items():
            if snapshot.metrics.get(metric, 0) > threshold:
                logger.warning(f"Guardrail breached: {metric}={snapshot.metrics[metric]} > {threshold}")
                return False, f"Guardrail breached: {metric}"

        # 4. 推广条件检查 (每个核心指标都满足)
        for metric, min_threshold in current_stage.promotion_criteria.items():
            if snapshot.metrics.get(metric, 0) < min_threshold:
                return False, f"Promotion criteria not met: {metric}={snapshot.metrics[metric]} < {min_threshold}"

        return True, "Ready to advance"

    def advance(self) -> bool:
        """进入下一阶段"""
        can_advance, reason = self.check_promotion()
        if not can_advance:
            logger.info(f"Cannot advance: {reason}")
            return False

        self.current_stage_idx += 1
        if self.current_stage_idx >= len(self.config.stages):
            self.status = StageStatus.COMPLETED
            logger.info(f"Rollout completed: {self.config.experiment_name}")
        else:
            self.stage_start_time = time.time()
            self.update_traffic_split()
        return True

    def rollback(self, reason: str):
        """回滚"""
        logger.warning(f"Rolling back: {self.config.experiment_name}, reason={reason}")
        self.status = StageStatus.ROLLBACK
        if self.traffic_router:
            self.traffic_router.set_traffic_pct(
                self.config.treatment_version, 0.0
            )
        self._notify_rollback(reason)

    def _notify_rollback(self, reason: str):
        """通知回滚"""
        for channel in self.config.notification_channels:
            # 发送通知
            logger.info(f"Notify {channel}: Rollback reason={reason}")


# ============================================================================
# 实验分析器
# ============================================================================

class ExperimentAnalyzer:
    """实验分析器"""

    def __init__(self, metrics: MetricsCollector):
        self.metrics = metrics

    def generate_report(self, experiment_id: str) -> Dict:
        """生成实验报告"""
        snapshots = [s for s in self.metrics.data if s.experiment_id == experiment_id]

        if not snapshots:
            return {}

        report = {
            'experiment_id': experiment_id,
            'n_snapshots': len(snapshots),
            'duration_days': (
                max(s.timestamp for s in snapshots) -
                min(s.timestamp for s in snapshots)
            ) / 86400,
        }

        # 各指标汇总
        for metric in ['ctr', 'cvr', 'p99_latency', 'gmv']:
            t_metrics = [s.metrics[metric] for s in snapshots
                         if 'treatment' in s.metrics.get('_group', '') and metric in s.metrics]
            c_metrics = [s.metrics[metric] for s in snapshots
                         if 'control' in s.metrics.get('_group', '') and metric in s.metrics]

            if t_metrics and c_metrics:
                sig = SignificanceTest.welch_t_test(t_metrics, c_metrics)
                report[metric] = {
                    'treatment_mean': sig['mean_treatment'],
                    'control_mean': sig['mean_control'],
                    'effect_size': sig['effect_size'],
                    'p_value': sig['p_value'],
                    'significant': sig['significant'],
                }

        return report
```

## 3.27 AB 实验的"数学原理" (深入)

### 3.27.1 中心极限定理

样本均值的分布近似正态, 即使原始分布不是:

$$
\bar{X} \sim \mathcal{N}(\mu, \sigma^2 / n)
$$

这是 t 检验和 z 检验的理论基础。

### 3.27.2 大数定律

样本量越大, 样本均值越接近总体均值:

$$
\bar{X} \to \mu \text{ as } n \to \infty
$$

工业实践中, 大样本量是 AB 实验可靠性的基础。

### 3.27.3 第一类和第二类错误

| 错误类型 | 描述 | 工业对应 |
| :--- | :--- | :--- |
| **第一类 (α)** | H0 真但拒绝 H0 (误报) | 假阳性, 把无效改动推上线 |
| **第二类 (β)** | H0 假但没拒绝 (漏报) | 假阴性, 错过好改动 |

工业 α 通常 0.05, β 通常 0.2 (功效 80%)。

### 3.27.4 p 值的"误读"

p 值经常被误读, 工业一定要清楚:

| 常见误解 | 正确理解 |
| :--- | :--- |
| p < 0.05 = 实验有效 | p 是"在 H0 下观察到这个结果的概率", 不是"实验有效的概率" |
| p 越小越好 | 不是, p 受样本量影响 |
| p > 0.05 = 实验无效 | 不一定, 可能样本量不够 |

### 3.27.5 置信区间

95% CI 表示"真实值有 95% 概率落在这个区间内":

$$
\bar{X} \pm 1.96 \times \frac{\sigma}{\sqrt{n}}
$$

**判断**: 实验组与对照组 CI 重叠 → 差异不显著; 不重叠 → 显著。

### 3.27.6 效应量 (Effect Size)

Cohen's d (标准化均值差):

$$
d = \frac{\bar{X}_T - \bar{X}_C}{s_{\text{pooled}}}
$$

- d < 0.2: 极小
- 0.2 ≤ d < 0.5: 小
- 0.5 ≤ d < 0.8: 中
- d ≥ 0.8: 大

工业推荐: |d| > 0.1 通常有意义 (大样本 + 严格阈值)。

工业推荐系统的"双盲":
- 用户: 不知道自己在实验组 (天然满足)
- 开发: 实验期间不分析数据 (难做到)

## 3.39 AB 实验的"统计学再深入"

### 3.39.1 贝叶斯 AB 测试

传统频率派 vs 贝叶斯:

**频率派**: p < 0.05 拒绝 H0
**贝叶斯**: P(Better than A | data) > 0.95

```python
import pymc as pm
import numpy as np

def bayesian_ab_test(treatment, control):
    """贝叶斯 AB 测试"""
    with pm.Model() as model:
        # 假设先验
        mu_t = pm.Normal('mu_t', mu=0.05, sigma=0.01)
        mu_c = pm.Normal('mu_c', mu=0.05, sigma=0.01)
        sigma = pm.HalfNormal('sigma', sigma=0.01)

        # 似然
        obs_t = pm.Normal('obs_t', mu=mu_t, sigma=sigma, observed=treatment)
        obs_c = pm.Normal('obs_c', mu=mu_c, sigma=sigma, observed=control)

        # 采样
        trace = pm.sample(2000, return_inferencedata=True)

        # 概率: P(mu_t > mu_c | data)
        prob_better = (trace.posterior['mu_t'] > trace.posterior['mu_c']).mean()

        return {
            'prob_better': prob_better,
            'mu_t_mean': trace.posterior['mu_t'].mean(),
            'mu_c_mean': trace.posterior['mu_c'].mean(),
        }
```

**优势**: 给出"实验效果更好的概率", 更直观。

### 3.39.2 序贯检验 (Sequential Testing)

不固定样本量, 边收集边判断:

```python
class SequentialTester:
    """序贯检验: 不固定样本量, 边走边看"""
    def __init__(self, alpha=0.05, beta=0.2):
        self.alpha = alpha
        self.beta = beta

    def check(self, treatment_data, control_data):
        """每收集一批数据, 检查一次"""
        n_t = len(treatment_data)
        n_c = len(control_data)

        if n_t < 30 or n_c < 30:
            return {'decision': 'continue'}

        # 计算检验统计量
        t_stat, p_value = self.welch_t(treatment_data, control_data)

        # 序贯检验的"墙" (Wald boundaries)
        upper_bound = self.alpha_boundary(n_t, n_c)
        lower_bound = -upper_bound

        if t_stat > upper_bound:
            return {'decision': 'reject', 'p_value': p_value}
        elif t_stat < lower_bound:
            return {'decision': 'accept_baseline', 'p_value': p_value}
        else:
            return {'decision': 'continue'}

    def alpha_boundary(self, n_t, n_c):
        """序贯检验的显著性边界, 比固定样本量更严"""
        # O'Brien-Fleming 边界
        return 3.0 / np.sqrt(min(n_t, n_c) / 100)
```

**优势**: 可能提早结束实验。

### 3.39.3 异方差检验 (Heteroscedasticity)

如果两组方差差异很大, 用 Welch's t-test 而非 Student's t-test:

```python
from scipy.stats import ttest_ind

# Student's t-test (假设方差齐性) ❌
# Welch's t-test (不假设方差齐性) ✓
t_stat, p_value = ttest_ind(treatment, control, equal_var=False)
```

### 3.39.4 非正态数据的处理

如果数据明显非正态 (如重尾):

```python
# 1. 用非参数检验 (Mann-Whitney U)
from scipy.stats import mannwhitneyu
u_stat, p_value = mannwhitneyu(treatment, control, alternative='two-sided')

# 2. 数据变换 (取 log / sqrt)
treatment_log = np.log(treatment + 1)

# 3. Bootstrap 检验
def bootstrap_test(treatment, control, n_bootstrap=10000):
    n_t = len(treatment)
    diffs = []
    for _ in range(n_bootstrap):
        t_sample = np.random.choice(treatment, n_t, replace=True)
        c_sample = np.random.choice(control, len(control), replace=True)
        diffs.append(t_sample.mean() - c_sample.mean())
    return np.percentile(diffs, [2.5, 97.5])
```

### 110. 3-版本切换与AB测试 - 工业实践 视角

**1. 背景与动机**

任何技术或方法的出现都不是孤立的,而是回应特定历史条件下的具体问题。"3-版本切换与AB测试" 的发展也不例外。要理解它,必须回到它出现的那个时间点,看清它要解决的真实问题是什么。当时的主流方案有哪些不足? 它的提出填补了哪些空白? 这些问题的回答,决定了我们今天该如何使用它。

从知识论角度看,**技术演进是问题驱动的**——不是先有方案再找问题,而是先有问题再有方案。这个观察可以帮助我们避免"拿着锤子找钉子"的陷阱,真正把方法用对地方。

历史维度上,我们看到三个规律:

1. **从特殊到一般**: 早期方法往往针对特定场景,后期抽象出通用框架。学习的认知规律也是先掌握具体案例,再抽象出一般模式。这种"自下而上"的学习方式,在机器学习模型的设计里反复出现。

2. **从手工到自动**: 经验规则逐步被数据驱动的方法取代。在早期,很多 AI 系统依赖人工编写的规则。统计学习方法的崛起让"从数据中学习"成为可能。深度学习进一步把特征工程也自动化了。今天的大模型时代,我们看到端到端学习从感知扩展到了推理与生成。

3. **从局部到全局**: 关注单个组件,演进到关注整个系统。早期模型评估只关注单点指标,现在更关注全链路的协同效应。这种"系统视角"的转变,与软件工程从单体架构到微服务架构的演进高度相似。

**2. 工业实践视角的展开**

从工业实践视角出发,我们可以把 "3-版本切换与AB测试" 拆解为以下几个层次:

**第一层: 概念层** —— 这是最抽象的层次,定义了我们要研究的对象是什么。例如,"推荐系统"在概念层是一个"为用户从物品集合中筛选合适物品"的问题。这个层次的特点是清晰、稳定、不易变化。一个好的概念定义应该具备几个特征:可操作性、可测量性、可扩展性。

**第二层: 模型层** —— 把概念实例化为数学模型。同一概念可以有不同的模型化方式,例如"推荐系统"可以是协同过滤、矩阵分解、深度学习等。模型的选择决定了后续算法的空间,也决定了能利用的归纳偏置(比如序列模型擅长捕捉时序依赖,图模型擅长建模关系结构)。模型选型是工程实践中最重要的决策之一。

**第三层: 算法层** —— 在选定模型下,具体的求解方法。这一层最活跃,新算法层出不穷。同一模型往往有多种算法,各有优劣。例如同样是优化深度网络,可以选择 SGD、Adam、L-BFGS 等不同算法。算法的选择要考虑收敛速度、数值稳定性、计算成本等多个维度。

**第四层: 工程层** —— 算法落地的实现细节,包括数据流水线、训练框架、推理优化、监控告警等。工程层是研究到生产的桥梁,决定了一个方法能否真正用起来。一个在论文里表现很好的算法,如果不能高效实现、不能稳定运行、不能快速迭代,就没有实际价值。工程能力是把研究转化为生产力的关键。

**第五层: 业务层** —— 在具体业务场景中的表现。同一技术在不同业务里效果差异巨大,因为业务目标、数据分布、用户行为都有差异。从业务视角看技术,我们必须回答几个问题:这个技术解决了什么业务问题?投入产出比如何?长期可持续吗?技术评估必须与业务目标对齐,否则容易陷入"技术自嗨"的陷阱。

**3. 数学形式化(简洁版)**

虽然我们强调工业实践视角,但数学形式化提供了共同语言。机器学习的核心问题可以表达为:给定输入样本,学习一个映射函数,使得函数输出与真实目标的差距最小化。这个抽象捕捉了分类、回归、生成等大多数任务的本质。

进一步,优化目标通常加入正则化项来控制模型复杂度,平衡经验风险与模型容量。统计学习理论给出了泛化误差的上界,告诉我们模型越复杂并不一定越好——**奥卡姆剃刀**在数学上有严格的形式化。

偏差-方差分解是另一个核心框架:误差可以分解为模型偏差(欠拟合)、方差(过拟合)和不可约噪声三部分。理解这个分解有助于诊断模型表现、选择合适复杂度。

在数值稳定性方面,有几个常见陷阱: 浮点数精度有限、Log-Sum-Exp 计算要减去最大值、Softmax 在大数值下会溢出。这些工程细节常常决定一个模型能否在生产环境稳定运行。

**4. 信息论视角**

信息论为"3-版本切换与AB测试" 提供了统一的视角:**学习的本质是从数据中提取与目标相关的信息**。

互信息衡量知道一个变量后,另一个变量不确定性减少的量。在机器学习中,它被广泛用于特征选择、表示学习、多模态对齐等场景。

KL 散度衡量两个概率分布的距离,在交叉熵损失、变分推断、策略梯度等场景无处不在。需要注意它是**不对称**的——不同方向有不同的解释。

信息瓶颈原则指出,我们应该寻找既紧凑又预测性强的表示。这一思想影响了大量表示学习方法的设计,包括对比学习、自监督学习、多模态预训练等。

**7. 实践建议**

结合 "3-版本切换与AB测试" 的特点,实践中有以下建议:

1. **数据优先**: 数据质量决定上限,模型只是逼近这个上限。把 50% 的时间投入到数据理解和清洗上,这条经验被无数实践证明。数据问题往往比模型问题更关键,但也更容易被忽视。

2. **基线先行**: 先用最简单的方法(如逻辑回归、规则)做基线,确认增益是来自方法还是数据。没有强基线的"创新"往往不靠谱。很多看似 fancy 的方法,在强基线面前提升有限。

3. **迭代式改进**: 不要追求一步到位,而是 baseline → 简单改进 → 高级方法 → 调优。每一步都用验证集确认有提升。每一步的提升幅度通常递减,要预期边际收益下降。

4. **失败案例分析**: 重点看模型做错的样本,往往能发现系统性问题。错误样本里藏着模型没学会的知识。把这些样本按错误类型分类,可以发现模型的薄弱点。

5. **A/B 测试**: 在生产环境做对照实验,用业务指标而非离线指标评估。离线指标只是手段,业务指标才是目的。指标可以被优化,但业务目标很难直接优化。

6. **监控与回滚**: 上线后持续监控关键指标,异常时快速回滚。任何线上系统都必须考虑"最坏情况",并预先设计好应对方案。

**8. 常见误解**

对 "3-版本切换与AB测试" 常见的误解包括:

1. **"模型越复杂越好"**: 实际上,简单模型 + 好数据往往优于复杂模型 + 烂数据。这条法则在实践中反复被验证。

2. **"训练 loss 越低越好"**: 训练 loss 低不代表泛化好,可能过拟合。要看验证集表现,做误差分析。

3. **"指标好就等于业务好"**: 离线指标与在线业务有 gap,必须做 A/B 测试。指标可以被优化,但业务目标很难直接优化。

4. **"新方法一定比旧方法好"**: 新方法通常针对特定场景,在你的场景未必更好。要谨慎评估,先复现,再改进。

5. **"开源即用"**: 开源代码与你的数据/工程栈往往有 gap,需要适配。盲目复用经常踩坑,要理解代码再做改动。

在数值稳定性方面,有几个常见陷阱: 浮点数精度有限、Log-Sum-Exp 计算要减去最大值、Softmax 在大数值下会溢出。这些工程细节常常决定一个模型能否在生产环境稳定运行。

**7. 实践建议**

结合 "3-版本切换与AB测试" 的特点,实践中有以下建议:

1. **数据优先**: 数据质量决定上限,模型只是逼近这个上限。把 50% 的时间投入到数据理解和清洗上,这条经验被无数实践证明。数据问题往往比模型问题更关键,但也更容易被忽视。

2. **基线先行**: 先用最简单的方法(如逻辑回归、规则)做基线,确认增益是来自方法还是数据。没有强基线的"创新"往往不靠谱。很多看似 fancy 的方法,在强基线面前提升有限。

3. **迭代式改进**: 不要追求一步到位,而是 baseline → 简单改进 → 高级方法 → 调优。每一步都用验证集确认有提升。每一步的提升幅度通常递减,要预期边际收益下降。

4. **失败案例分析**: 重点看模型做错的样本,往往能发现系统性问题。错误样本里藏着模型没学会的知识。把这些样本按错误类型分类,可以发现模型的薄弱点。

5. **A/B 测试**: 在生产环境做对照实验,用业务指标而非离线指标评估。离线指标只是手段,业务指标才是目的。指标可以被优化,但业务目标很难直接优化。

6. **监控与回滚**: 上线后持续监控关键指标,异常时快速回滚。任何线上系统都必须考虑"最坏情况",并预先设计好应对方案。

**8. 常见误解**

对 "3-版本切换与AB测试" 常见的误解包括:

1. **"模型越复杂越好"**: 实际上,简单模型 + 好数据往往优于复杂模型 + 烂数据。这条法则在实践中反复被验证。

2. **"训练 loss 越低越好"**: 训练 loss 低不代表泛化好,可能过拟合。要看验证集表现,做误差分析。

3. **"指标好就等于业务好"**: 离线指标与在线业务有 gap,必须做 A/B 测试。指标可以被优化,但业务目标很难直接优化。

4. **"新方法一定比旧方法好"**: 新方法通常针对特定场景,在你的场景未必更好。要谨慎评估,先复现,再改进。

5. **"开源即用"**: 开源代码与你的数据/工程栈往往有 gap,需要适配。盲目复用经常踩坑,要理解代码再做改动。
