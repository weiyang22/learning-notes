### 7.1 问题的本质:为什么 DLRM 和 GR 都需要 RL?

#### 7.1.1 曝光偏差的数学本质

训练数据 = 历史的"曝光-点击"日志

$$D = \{(u, i, c, t) : \text{物品 } i \text{ 在时刻 } t \text{ 被推荐给用户 } u,\ c = \text{点击结果 } (0/1)\}$$

但用户只能点"被推荐过的"物品
未曝光的物品的点击概率,我们完全没有数据

数学上,我们想学:
$p^*(c=1 \mid u, i)$ - 真实 CTR

但实际学的是:
$\hat{p}(c=1 \mid u, i)$ - 在"当前推荐系统"曝光过的物品上的 CTR

二者不等!因为:
$$E_{\text{data}}[c \mid u, i] = P(\text{user clicks} \mid \text{user SEES item})$$
$$\neq P(\text{user clicks} \mid \text{item is shown randomly})$$

这是 "selection bias" (选择偏差)

#### 7.1.2 GR 中的曝光偏差

GR 的训练目标: $\max\, E[\log p_\theta(i^* \mid h)]$
其中 $h$ 是历史, $i^*$ 是真实点击

但 $i^*$ 也是"被推荐过的"物品
GR 学到的 $p_\theta$ 偏向"训练数据中曝光过的物品"
→ 推理时,GR 倾向于推荐"历史上被推荐过"的物品
→ 形成"富者愈富"的循环
→ 永远学不到"新物品"的真实兴趣

数学表达:

$$p_\theta(i^* \mid h) \approx P(i^* \in \text{推荐列表} \mid h) \times P(\text{click} \mid i^* \in \text{推荐列表}, h)$$

第二项是真实兴趣
第一项是"被推荐过"的概率 (受推荐系统影响)

训练时,$P(\text{推荐})$ 较高 → GR 倾向这些物品
推理时,GR 生成的物品 → 进入推荐列表 → 又被训练
→ 自我加强的循环

#### 7.1.3 RL 的"对症下药"

```text
RL (强化学习) 提供:
  1. 显式的 reward signal:  不只是"点击 = 1"
  2. 长期价值建模:  考虑未来 N 步的累计收益
  3. 探索机制:  主动推未曝光的物品,  收集新数据
  4. 策略优化:  直接优化推荐策略,  而非概率拟合

所以:  RL 是 GR 处理"曝光偏差"和"长期价值"的唯一系统化方案
```

**文字**: 为什么 DLRM 和 GR 都困在曝光偏差里?根源是训练数据的"被推荐过"过滤。日志里只有曝光过的物品 `(u, i, c, t)`,未曝光物品根本没出现在训练集,模型对它们的 loss 严格等于 0,梯度永远传不回去。模型自然把"没被推荐过"等同于"用户不喜欢",推理时倾向于重复推熟悉的物品,新物品永远拿不到曝光,数据回流后偏差自我强化,富者愈富,长尾物品越推越冷。IPS (Inverse Propensity Scoring) 不直接纠偏,但提供一套无偏估计的工具:用"被推荐概率"的倒数 `1/\pi_b(a|s)` 当权重,把有偏样本加权后还原成对真实兴趣 `p*(c=1|u,i)` 的无偏估计,这是 7.4 所有 RL 算法的理论起点。

**公式**:
$$L_{\text{IPW}}(\theta) = \mathbb{E}_{(s,a,r)\sim\mathcal{D}}\!\left[\frac{1}{\pi_b(a|s)} \cdot r \cdot \log \pi_\theta(a|s)\right]$$
其中 $\pi_b(a|s)$ 是行为策略 (产生训练数据的推荐系统),$\pi_\theta(a|s)$ 是当前模型。当 $\pi_b$ 概率极低时,需要截断权重避免方差爆炸。

**代码**:
```python
def ips_weighted_loss(logp, reward, behavior_prob, eps=1e-6):
    """IPS 加权的策略梯度, 估计真实期望奖励"""
    # 重要性权重 = 1 / π_b(a|s), 截断防止极端值
    w = torch.clamp(1.0 / behavior_prob.detach(), max=10.0)
    # IPS 目标: E[1/π_b · r · log π_θ]
    return -(w * reward.detach() * logp).mean()
```

### 7.2 RL 的核心概念(5 分钟回顾)

RL 的核心组件 (5 大元素):

**State (状态)**: $s$ = 用户当前的状态(历史行为 + 上下文)
  - *e.g.*, $s = (\text{用户最近 100 次点击},\; \text{时间},\; \text{设备})$

**Action (动作)**: $a$ = 推荐的物品
  - *e.g.*, $a \in \{\text{物品}_1,\; \text{物品}_2,\; \ldots,\; \text{物品}_{10^7}\}$

**Reward (奖励)**: $r$ = 推荐的即时反馈
  - *e.g.*, $r = \mathbb{1}[\text{click}] \in \{0,\; 1\}$,但也可以是其他(完播、点赞、停留时长、GMV)

**Policy (策略)**: $\pi(a \mid s)$ = 给定状态,选动作的概率分布
  - *e.g.*, GR 模型本身就是一个策略,$\pi_\theta(a \mid s) = \prod_{k} p_\theta(\text{token}_k \mid \text{history}, \text{token}_{<k})$

**Value (价值)**: $V(s)$ = 从状态 $s$ 出发的长期累计奖励期望
  - *e.g.*, $V(s) = \mathbb{E}\!\left[\sum_{k=0}^\infty \gamma^k r_{t+k} \;\Big|\; s_t = s\right]$

**Q-Value (动作价值)**: $Q(s, a)$ = 在 $s$ 选 $a$ 的长期累计奖励期望
  - *e.g.*, $Q(s, i) = \mathbb{E}\!\left[\sum_{k=0}^\infty \gamma^k r_{t+k} \;\Big|\; s_t = s,\; a_t = i\right]$

## 7.2.1 价值函数的 Bellman 递推推导

**为什么需要 Bellman 方程?** 上面两个价值函数的定义是无穷级数 $\sum_{k=0}^\infty \gamma^k r_{t+k}$, 直接算不出来。Bellman 方程通过**时间上的递推**把无穷级数化简为一步加未来。

**Step 1: 写出 $V^\pi(s)$ 的定义**

$$V^\pi(s) = \mathbb{E}_\pi\!\left[\sum_{k=0}^\infty \gamma^k r_{t+k} \,\Big|\, s_t = s\right]$$

**Step 2: 把第 0 步单独拆出来**

$$V^\pi(s) = \mathbb{E}_\pi\!\left[r_t + \sum_{k=1}^\infty \gamma^k r_{t+k} \,\Big|\, s_t = s\right]$$

利用折现因子,$\sum_{k=1}^\infty \gamma^k r_{t+k} = \gamma \cdot \sum_{k=0}^\infty \gamma^k r_{t+1+k}$,这正好是 $V^\pi(s_{t+1})$ 的形式(把时间起点从 $t+1$ 重新计):

$$V^\pi(s) = \mathbb{E}_\pi\!\left[r_t + \gamma \cdot V^\pi(s_{t+1}) \,\Big|\, s_t = s\right]$$

**这就是 Bellman 方程**:

$$\boxed{V^\pi(s) = \mathbb{E}_\pi\!\left[r_t + \gamma \cdot V^\pi(s_{t+1}) \,\Big|\, s_t = s\right]}$$

**Step 3: 展开 $Q^\pi$ 与 $V^\pi$ 的关系**

类似地, 对 $Q^\pi(s, a)$ 在 $s$ 选 $a$ 后, 下一个状态 $s'$ 和下一个动作 $a'$ 的期望:

$$Q^\pi(s, a) = \mathbb{E}_\pi\!\left[r_t + \gamma \cdot Q^\pi(s_{t+1}, a_{t+1}) \,\Big|\, s_t = s, a_t = a\right]$$

把 $Q$ 在 $a$ 上做边缘化, 得到 $V$:

$$V^\pi(s) = \mathbb{E}_{a \sim \pi(\cdot|s)}[Q^\pi(s, a)]$$

把 $V$ 在 $s'$ 上做边缘化, 得到 $Q$:

$$Q^\pi(s, a) = r(s, a) + \gamma \cdot \mathbb{E}_{s' \sim P(\cdot|s,a)}[V^\pi(s')]$$

**Step 4: Bellman 最优性原理**

最优策略 $\pi^*$ 满足:在状态 $s$ 选动作 $a$ 时, $Q^{\pi^*}(s, a) \geq Q^{\pi^*}(s, a')$ 对所有 $a'$ 成立。最优 $V$:

$$V^*(s) = \max_a Q^*(s, a) = \max_a \left[ r(s,a) + \gamma \cdot \mathbb{E}_{s'}[V^*(s')] \right]$$

这是**Bellman 最优方程**, 是值迭代 (Value Iteration) 算法的基础。

**Step 5: 折现因子 $\gamma$ 的物理意义**

$$V(s) = \sum_{k=0}^\infty \gamma^k \mathbb{E}[r_{t+k}]$$

- $\gamma = 0$ → 只看立即奖励 $r_t$,退化为监督学习("CTR 最大化")
- $\gamma = 1$ → 永不折现, 长期奖励权重和立即奖励一样,但**训练极不稳定**(无穷级数不收敛风险)
- $\gamma \in (0, 1)$ → 折现,1 步奖励权重 $\gamma^k$, 几何衰减

**有效视野** (Effective Horizon): 奖励权重衰减到 $\epsilon$ 时的步数

$$H_{\text{eff}} = \frac{1}{1 - \gamma}, \quad \gamma = 0.99 \implies H_{\text{eff}} = 100, \quad \gamma = 0.95 \implies H_{\text{eff}} = 20$$

推荐系统的工业经验:
- 短期价值主导(CTR) → $\gamma = 0.9 \sim 0.95$, 视野 $10 \sim 20$ 步
- 长期价值主导(留存) → $\gamma = 0.99$, 视野 100 步
- 极端长期(7 日/30 日 LTV) → $\gamma = 0.999$, 视野 1000 步,但**训练需要非常稳定**

### 7.2.2 RL 目标函数与策略梯度基础

**RL 目标**: 最大化从状态分布出发的累计奖励期望:

$$J(\pi) = \mathbb{E}_{s_0 \sim \rho_0, a_t \sim \pi(\cdot|s_t)}\!\left[\sum_{t=0}^T \gamma^t r_t\right]$$

**策略梯度定理** (Sutton 2000): 直接对 $J(\pi)$ 求关于 $\pi$ 参数 $\theta$ 的梯度:

$$\boxed{\nabla_\theta J(\pi_\theta) = \mathbb{E}_{s \sim d^\pi, a \sim \pi_\theta}\!\left[\nabla_\theta \log \pi_\theta(a \mid s) \cdot Q^\pi(s, a)\right]}$$

直觉: 如果动作 $a$ 在状态 $s$ 下的 $Q$ 值大, 就把 $\pi_\theta(a|s)$ 推高, 反之推低。**REINFORCE** 是这个梯度的蒙特卡洛近似,用采样回报 $\hat{Q}_t = \sum_{k=0}^T \gamma^k r_{t+k}$ 代替真实 $Q$:

$$\nabla_\theta J \approx \mathbb{E}\!\left[\nabla_\theta \log \pi_\theta(a_t \mid s_t) \cdot \hat{Q}_t\right]$$

---

#### 7.2.3 RL 的三大范式深度对比

**1. Value-based (基于价值)**

学 $Q(s, a)$ 函数, 策略由 $\arg\max$ 给出:
$$\pi(a \mid s) = \arg\max_a Q(s, a)$$

- **优点**: 样本效率高(off-policy + experience replay)
- **缺点**: 不适用于连续动作($\arg\max$ 难算); 不能输出随机策略(探索能力受限)
- **代表**: DQN, DDPG, SAC

**2. Policy-based (基于策略)**

直接参数化 $\pi_\theta(a|s)$:
$$\pi_\theta(a \mid s) = \text{softmax}(f_\theta(s))_a, \quad \text{或者高斯分布 } \mathcal{N}(\mu_\theta(s), \sigma^2)$$

- **优点**: 自然处理连续动作; 可输出随机策略(天然探索)
- **缺点**: 样本效率低(on-policy); 训练方差大
- **代表**: REINFORCE, TRPO, PPO, GRPO

**3. Actor-Critic (混合)**

同时学 $\pi_\theta(a|s)$ (Actor) 和 $V_\phi(s)$ (Critic):
$$\nabla_\theta J \approx \mathbb{E}\!\left[\nabla_\theta \log \pi_\theta(a \mid s) \cdot A^\pi(s, a)\right], \quad A^\pi(s, a) = Q^\pi(s, a) - V^\pi(s)$$

$A^\pi$ 是 advantage, 衡量"动作 $a$ 相对平均水平好多少"。

- **优点**: 兼顾样本效率(用 critic 估计 V 替代采样回报, 减少方差)和稳定训练
- **缺点**: 两个网络要同时调, 容易不稳定
- **代表**: A2C, PPO, SAC, IMPALA

---

**RL 的核心公式**:

$$V^\pi(s) = \mathbb{E}_\pi\!\left[\sum_{k=0}^\infty \gamma^k r_{t+k} \,\Big|\, s_t = s\right] \quad \text{(状态价值函数)}$$

$$Q^\pi(s,a) = \mathbb{E}_\pi\!\left[\sum_{k=0}^\infty \gamma^k r_{t+k} \,\Big|\, s_t=s,\ a_t=a\right] \quad \text{(动作价值函数)}$$

**RL 的目标**:

$$\max_\pi J(\pi) = \max_\pi \mathbb{E}_{\tau \sim \pi}\!\left[\sum_{t=0}^T \gamma^t r_t\right] \quad \text{(策略梯度目标)}$$

**文字**: 推荐天然就是序列决策。第 t 次推荐会影响用户状态 (看没看、停留多久、是否离开),这个状态又决定第 t+1 次推荐,链条一断,短期 reward 立刻漂移。第二个原因是奖励的"长期性":我们真正关心的是 7 日留存、30 日 GMV、长期 LTV,不是当下那一次点击;SFT 用 cross-entropy 拟合 next item,根本回答不了"如果当初推另一个会怎样"这种反事实问题。实践上,工业界 99% 用 off-policy (用历史日志训,数据便宜但有分布偏移),1% 用 on-policy (实时流量做实验,无偏但贵且慢),两者都需要 importance sampling 修正。RL 给出的核心承诺:既能量化"反事实奖励",又能建模"长期价值",这是 SFT 框架给不了的。

**公式**:

$$V^\pi(s) = \mathbb{E}_\pi\!\left[r_t + \gamma \cdot V^\pi(s_{t+1}) \,\Big|\, s_t = s\right]$$

$V^\pi(s)$ 是状态 $s$ 的长期价值,$\gamma \in [0, 1]$ 折现未来奖励,$\gamma=0$ 等价 SFT (只看当下),$\gamma \to 1$ 关注长期留存。

**代码**:
```python
# Q-learning (value-based): 学 Q(s,a), 推理时取 argmax
def q_learning_update(Q, s, a, r, s_next, alpha=0.1, gamma=0.99):
    td_target = r + gamma * Q[s_next].max()         # 时序差分目标
    Q[s, a] += alpha * (td_target - Q[s, a])        # 沿梯度方向更新

# Policy Gradient (policy-based): 直接优化 π_θ(a|s)
def pg_update(logp, returns, optimizer):
    loss = -(logp * returns).mean()                  # REINFORCE
    optimizer.zero_grad(); loss.backward(); optimizer.step()
```

### 7.3 RL 在 GR 中的 4 大应用场景

#### 场景 1: 精排模型的 RL 微调 (RL Finetune)

```text
目标:  在 SFT 训好的 GR 基础上, 进一步用 RL 优化
方法:
  Step 1:  SFT 训练 (有监督,  next token prediction)
  Step 2:  部署 GR 模型
  Step 3:  收集用户反馈 (点击,  停留,  购买,  收藏)
  Step 4:  用反馈数据训练 reward model
  Step 5:  PPO / GRPO 微调 GR
  Step 6:  部署新模型
```

**Reward 设计**:

```python
# 简单的 reward:  1 if click,  0 if not
reward_click = 1.0 if click else 0.0

# 复杂 reward:  多目标加权
def compute_reward(event):
    """
    event:  Dict 包含用户的反馈
    """
    reward = 0.0
    if event['click']:
        reward += 1.0       # 点击
    if event['dwell_time'] > 30:
        reward += 0.5       # 停留 > 30s
    if event['like']:
        reward += 1.0       # 点赞
    if event['share']:
        reward += 2.0       # 分享 (社交信号)
    if event['purchase']:
        reward += 5.0       # 购买 (强信号)
    if event['skip'] and event['dwell_time'] < 2:
        reward -= 0.3       # 划走 (负信号)
    return reward
```

#### 场景 2: 长期价值建模 (Long-term Value, LTV)

问题: SFT 只优化"立即点击"
  但推荐应该考虑长期:
    用户点了一个"标题党" → 短期 CTR 高,长期用户失望
    用户点了一个"深度文章" → 短期 CTR 低,长期用户留存高
    → 需要建模"长期价值"

RL 解决: 优化 $G_t = \sum_k \gamma^k r_{t+k}$
  $\gamma \in [0.95, 0.99]$: 折现因子
  未来 50 步的累计奖励,折现到现在

具体:
  Step 1: 推荐物品 A
  Step 2: 用户点击 ($r_0 = 1$)
  Step 3: 用户离开,1 天后回来 ($r_1 = 0$)
  Step 4: ...
  Step K: 用户留存 ($r_K = 1$)

$$G = \sum_k \gamma^k r_k$$

  即使 $r_0 = 1$, $G$ 也会被 $r_1, r_2, \ldots$ 拉低 (如果用户离开)
  → 模型学会"用户会后悔的"物品不推

#### 场景 3: 多目标联合优化

推荐系统的多个目标 (CTR, CVR, 时长, 留存, GMV) 经常冲突
传统 SFT: 每个目标加权求和,权重难调
RL 解决: 每个目标一个 reward,加权求和
  或者用 Pareto 多目标 RL

示例:

$$r = \alpha \cdot \text{CTR} + \beta \cdot \text{CVR} + \gamma \cdot \text{时长} + \delta \cdot \text{GMV}$$

其中 $\alpha, \beta, \gamma, \delta$ 仍要调,但比 SFT 的 loss weight 更直观

#### 场景 4: 探索与利用 (Exploration-Exploitation)

问题: SFT 倾向于"利用"已知好物品,不会探索
  → 新物品永远没机会 → 长尾物品越推越少

RL 解决: 在策略中加熵正则

$$L_{\text{PPO\_with\_entropy}} = L_{\text{PPO}} + \beta \cdot H(\pi(a \mid s))$$

$$H(\pi) = -\sum_a \pi(a \mid s) \cdot \log \pi(a \mid s) : \text{策略的熵}$$
$\beta$ 控制探索程度: $\beta$ 大 → 更随机 → 更多探索

→ 模型在"利用已知好物品"和"探索新物品"之间平衡

### 7.4 RLHF/RLHF-R/DPO/PPO/GRPO——术语全景

```text
RLHF (Reinforcement Learning from Human Feedback):
  = 用人类反馈训练 reward model, 然后 PPO 优化策略
  起源:  OpenAI InstructGPT 2022, ChatGPT 2023
  在推荐:  用户反馈 = "隐式的人类反馈" (点击 = 隐式赞同)

RLHF-R (Reinforcement Learning from Recommender Feedback):
  = 推荐场景的 RLHF, 但反馈来自"推荐系统的用户行为"
  vs RLHF:  反馈来源不同
  在 Meta HSTU 2024 中提出

PPO (Proximal Policy Optimization):
  = 当前最主流的 on-policy RL 算法
  = OpenAI 2017 提出
  = 限制策略更新的步长, 避免"跳太远"
  = 在 GR 中需要 4 个模型:  policy, reference, reward, value
  = 显存占用大, 训练慢

GRPO (Group Relative Policy Optimization):
  = DeepSeek 2025 提出
  = PPO 的简化版, 不用 value model
  = 对一个 prompt 生成 K 个回答,  用 K 个回答的相对奖励
  = 显存省一半, 训练快 2 倍
  = 已成为 GR 的新标准

DPO (Direct Preference Optimization):
  = Stanford 2023 提出
  = 直接从偏好数据优化, 不需要 reward model
  = 在推荐中:  "用户点击了 A 而不是 B" 就是偏好数据
  = 比 PPO 简单, 比 PPO 显存省, 效果略差于 PPO
```

**三大算法核心公式对比**:

PPO clip 目标（限制策略更新步长）:

$$\mathcal{L}^{\text{PPO}}(\theta) = \mathbb{E}_t\!\left[\min\!\left(r_t(\theta)\,A_t,\ \text{clip}(r_t(\theta), 1-\varepsilon, 1+\varepsilon)\,A_t\right)\right], \quad r_t = \frac{\pi_\theta(a_t|s_t)}{\pi_{\text{old}}(a_t|s_t)}$$

GRPO（无 value model，用组内相对奖励替代 advantage）:

$$A_i = \frac{R_i - \text{mean}(R_{1:K})}{\text{std}(R_{1:K})}, \quad \mathcal{L}^{\text{GRPO}}(\theta) = \mathbb{E}_{i \in [1,K]}\!\left[\min(r_i A_i, \text{clip}(r_i, 1 \pm \varepsilon) A_i) - \beta D_{\text{KL}}(\pi_\theta \| \pi_{\text{ref}})\right]$$

DPO（无 reward model，直接从偏好对优化）:

$$\mathcal{L}^{\text{DPO}}(\theta) = -\log\sigma\!\left(\beta\log\frac{\pi_\theta(y_w|x)}{\pi_{\text{ref}}(y_w|x)} - \beta\log\frac{\pi_\theta(y_l|x)}{\pi_{\text{ref}}(y_l|x)}\right)$$

其中 $y_w$ 为用户偏好(点击), $y_l$ 为非偏好(未点击), $\beta$ 控制与参考策略的偏离程度。

**文字**: PPO 的核心动机是"步长多大合适"。朴素策略梯度一步可能让策略变化 10 倍,旧的训练数据瞬间失效 (off-policy 风险),老的 reward model 估计也跑偏。PPO 用 clip 限制更新幅度:先算新策略和旧策略的概率比 $r = \pi_\theta(a|s) / \pi_{\theta_{\text{old}}}(a|s)$,如果 r 落在 $[1-\varepsilon, 1+\varepsilon]$ (通常 $\varepsilon=0.2$) 区间内,loss 对 r 的梯度为 0,参数不更新;越出区间,梯度被强制往回"拉",保证新策略不会离老策略太远。这个 trick 的妙处:既允许同方向继续优化,又防止一次跳太远,且实现极简,只要 clamp 一个 ratio 就行。clamp 之外再取 min,是 pessimistic bound 的设计,保证不被过大的 advantage 推到极端。

**公式**:

$$\mathcal{L}^{\text{CLIP}}(\theta) = \mathbb{E}_t\!\left[\min\!\left(r_t A_t, \text{clip}(r_t, 1-\varepsilon, 1+\varepsilon) A_t\right)\right]$$

$r_t = \pi_\theta(a_t|s_t) / \pi_{\theta_{\text{old}}}(a_t|s_t)$ 是新旧策略的比率, $A_t$ 是 advantage。min 操作为悲观估计,避免极端策略更新。

**代码**:
```python
class PPO:
    """Proximal Policy Optimization, 简化版实现"""
    def __init__(self, policy, ref_policy, clip_eps=0.2, kl_coef=0.1, lr=1e-5):
        self.policy = policy
        self.ref = ref_policy
        self.clip_eps = clip_eps
        self.kl_coef = kl_coef
        self.optim = torch.optim.AdamW(policy.parameters(), lr=lr)

    def compute_loss(self, new_logp, old_logp, advantage, ref_logp):
        """PPO clip 损失 + KL 约束"""
        ratio = (new_logp - old_logp).exp()               # π_θ / π_old
        surr1 = ratio * advantage                         # 未裁剪 surrogate
        surr2 = ratio.clamp(1 - self.clip_eps, 1 + self.clip_eps) * advantage
        policy_loss = -torch.min(surr1, surr2).mean()     # 悲观下界
        kl = (new_logp - ref_logp).mean()                 # KL 散度
        return policy_loss + self.kl_coef * kl             # 总 loss

    def update(self, prompts, gen_ids, old_logp, rewards, ref_logp):
        """一步 PPO 更新"""
        new_logp = self.policy.log_prob(prompts, gen_ids) # 当前策略 log p
        advantage = (rewards - rewards.mean()) / (rewards.std() + 1e-8)
        loss = self.compute_loss(new_logp, old_logp, advantage, ref_logp)
        self.optim.zero_grad(); loss.backward()
        torch.nn.utils.clip_grad_norm_(self.policy.parameters(), 1.0)
        self.optim.step()
        return {'loss': loss.item(), 'kl': (new_logp - ref_logp).mean().item()}
```

### 7.5 RL-GR 的训练流程(完整版)

```text
┌──────────────────────────────────────────┐
│         阶段 1: SFT (有监督微调)            │
│                                            │
│  数据:  历史点击日志 (user, history, item)   │
│  模型:  GR Transformer                     │
│  损失:  CrossEntropy (next token)          │
│  输出:  SFT 模型 π_SFT                     │
└──────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────┐
│         阶段 2: Reward Model 训练           │
│                                            │
│  数据:  用户反馈 (item, click, dwell, like) │
│  模型:  回归器 (Transformer + MLP)          │
│  损失:  MSE / Ranking Loss                 │
│  输出:  Reward model R_θ                  │
└──────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────┐
│         阶段 3: PPO/GRPO 优化               │
│                                            │
│  数据:  用户 prompt (历史行为)              │
│  模型:  GR + reference + reward (可选 value)│
│  算法:  PPO / GRPO                        │
│  输出:  RL 优化后的模型 π_RL               │
└──────────────────────────────────────────┘
                    ↓
                上线服务
```

**文字**: 为什么 RL+GR 训练必须分三阶段,不能端到端一把训完?第一,RL 的优化起点必须是个"说得通"的策略,所以先用 SFT 训出基础 policy,让它能生成合法物品序列;第二,用户反馈 (点击/时长/留存) 极度稀疏,不能直接当 loss 梯度,需要训一个 Reward Model 把隐式反馈学成可微的标量函数;第三,RL 阶段 (PPO/GRPO) 才用策略梯度 fine-tune。三阶段看似繁琐,实则每一步的损失函数都不同 (cross-entropy / MSE / Policy Gradient),合并训练会让多个目标互相打架。Meta HSTU、快手 OneRec、字节 2025 全部沿用这套三阶段范式,几乎是 RL-GR 的事实标准。

**公式**:
**[阶段 1: SFT]**

数据: $(history, target\_item)$ 二元组
目标: $L_{\text{SFT}} = -\log \pi_\theta(item \mid history)$
输出: 基础策略 $\pi_{\text{SFT}}$,冻结作为 reference

↓

**[阶段 2: Reward Model]**

数据: $(history, item, click/dwell/like)$ 反馈日志
目标: $L_{\text{RM}} = \text{MSE}(R_\theta(history, item), \text{用户反馈})$
输出: 奖励模型 $R_\theta$,推理时冻结

↓

**[阶段 3: PPO/GRPO]**

数据: $history$ 作 prompt,采样 $K$ 个生成
目标: $L_{\text{PPO}} = -\min(r \cdot A, \text{clip}(r, 1 \pm \varepsilon) \cdot A) + \beta \cdot \text{KL}(\pi_\theta \| \pi_{\text{SFT}})$
输出: 最终策略 $\pi_{\text{RL}}$,部署上线

**代码**:
```python
# 阶段 1: SFT, 用 next-token 预测训出基础 policy
for batch in sft_loader:
    log_p = sft_policy.log_prob(batch['history'], batch['target_item'])
    loss = -log_p.mean()                                # cross-entropy
    sft_optim.zero_grad(); loss.backward(); sft_optim.step()

# 阶段 2: Reward Model, 拟合用户隐式反馈
for batch in feedback_loader:
    pred_score = reward_model(batch['history'], batch['item'])
    loss = F.mse_loss(pred_score, batch['click_label']) # MSE
    rm_optim.zero_grad(); loss.backward(); rm_optim.step()

# 阶段 3: PPO/GRPO, 用策略梯度微调
for batch in rl_loader:
    gen = policy.generate(batch['history'])            # 采样生成
    r = reward_model(batch['history'], gen)            # RM 打分
    ppo_loss = compute_ppo(policy, gen, r, ref=sft_policy)  # clip + KL
    ppo_optim.zero_grad(); ppo_loss.backward(); ppo_optim.step()
```

### 7.6 完整的 PPO-GR 代码实现

```python
import torch
import torch.nn as nn
import torch.nn.functional as F
from torch.optim import AdamW

class PPOTrainer:
    """
    PPO 训练器 for Generative Recommendation.
    4 个模型:  policy, reference, reward, value
    """
    def __init__(
        self,
        policy_model: nn.Module,      # 待训练的 GR 模型
        reference_model: nn.Module,   # SFT 后的冻结模型 (KL 约束基准)
        reward_model: nn.Module,      # 训练好的 reward 模型
        value_model: nn.Module,       # 价值函数 (用 policy 的隐层 + 头)
        lr_policy: float = 1e-5,
        lr_value: float = 1e-4,
        clip_eps: float = 0.2,        # PPO 的 clip 范围
        kl_coef: float = 0.1,         # KL 散度惩罚系数
        gamma: float = 0.99,          # 折现因子
        gae_lambda: float = 0.95,     # GAE 参数
    ):
        self.policy = policy_model
        self.reference = reference_model
        self.reward = reward_model
        self.value = value_model

        # reference 和 reward 冻结
        for p in self.reference.parameters():
            p.requires_grad = False
        for p in self.reward.parameters():
            p.requires_grad = False

        # policy 和 value 可训练
        self.policy_optim = AdamW(self.policy.parameters(), lr=lr_policy)
        self.value_optim = AdamW(self.value.parameters(), lr=lr_value)

        self.clip_eps = clip_eps
        self.kl_coef = kl_coef
        self.gamma = gamma
        self.gae_lambda = gae_lambda

    def compute_gae(self, rewards, values, dones):
        """GAE:  Generalized Advantage Estimation"""
        advantages = torch.zeros_like(rewards)
        last_advantage = 0
        for t in reversed(range(len(rewards))):
            if t == len(rewards) - 1:
                next_value = 0
            else:
                next_value = values[t + 1]
            delta = rewards[t] + self.gamma * next_value * (1 - dones[t]) - values[t]
            last_advantage = delta + self.gamma * self.gae_lambda * (1 - dones[t]) * last_advantage
            advantages[t] = last_advantage
        returns = advantages + values
        return advantages, returns

    def compute_rewards(self, prompts, generated_ids):
        """
        用 reward model 给生成的序列打分.
        """
        with torch.no_grad():
            # 拼接 prompt + 生成
            full_ids = torch.cat([prompts, generated_ids], dim=1)

            # reward model 输出每步的 reward
            rewards = self.reward(full_ids)  # [B, T]

            # 只对生成的部分计算 reward
            gen_rewards = rewards[:, prompts.size(1):]
        return gen_rewards  # [B, T_gen]

    def compute_logprobs(self, model, input_ids, target_ids):
        """计算 target_ids 在 model 下的 log probability"""
        logits = model(input_ids)  # [B, T, V]
        log_probs = F.log_softmax(logits, dim=-1)
        # gather target_ids 位置的概率
        return log_probs.gather(-1, target_ids.unsqueeze(-1)).squeeze(-1)  # [B, T]

    def ppo_step(self, prompts, generated_ids, old_logprobs, advantages, returns):
        """
        一步 PPO 更新.
        """
        # 1. 计算新策略的 log probs
        new_logprobs = self.compute_logprobs(
            self.policy, prompts, generated_ids
        )  # [B, T_gen]

        # 2. 计算 ratio
        ratio = (new_logprobs - old_logprobs).exp()  # [B, T_gen]

        # 3. PPO 损失
        surr1 = ratio * advantages
        surr2 = ratio.clamp(1 - self.clip_eps, 1 + self.clip_eps) * advantages
        policy_loss = -torch.min(surr1, surr2).mean()

        # 4. KL 散度 (vs reference model)
        with torch.no_grad():
            ref_logprobs = self.compute_logprobs(
                self.reference, prompts, generated_ids
            )
        kl = (new_logprobs - ref_logprobs).mean()
        kl_penalty = self.kl_coef * kl

        # 5. Value 损失
        values = self.value(prompts)  # [B, T_gen]
        value_loss = F.mse_loss(values, returns)

        # 6. 总损失
        total_loss = policy_loss + kl_penalty + 0.5 * value_loss

        # 7. 反向传播
        self.policy_optim.zero_grad()
        self.value_optim.zero_grad()
        total_loss.backward()

        # 梯度裁剪
        torch.nn.utils.clip_grad_norm_(self.policy.parameters(), 1.0)
        torch.nn.utils.clip_grad_norm_(self.value.parameters(), 1.0)

        self.policy_optim.step()
        self.value_optim.step()

        return {
            'policy_loss': policy_loss.item(),
            'value_loss': value_loss.item(),
            'kl': kl.item(),
            'reward': returns.mean().item(),
        }

    def train_step(self, prompts, generated_ids, rewards):
        """
        完整的 PPO 训练 step.
        prompts:  [B, T_p]  用户历史
        generated_ids:  [B, T_g]  GR 生成的 token 序列
        rewards:  [B, T_g]  reward model 给的分数
        """
        # 1. 用旧策略计算 log probs
        with torch.no_grad():
            old_logprobs = self.compute_logprobs(
                self.policy, prompts, generated_ids
            )
            values = self.value(prompts)  # [B, T_g]
            dones = torch.zeros_like(rewards)  # 简化: 假设没有 done

        # 2. 计算 GAE
        advantages, returns = self.compute_gae(rewards, values, dones)
        advantages = (advantages - advantages.mean()) / (advantages.std() + 1e-8)

        # 3. PPO 多步更新 (epochs)
        metrics = {}
        for _ in range(4):  # PPO epochs
            metrics = self.ppo_step(
                prompts, generated_ids, old_logprobs, advantages, returns
            )

        return metrics

### 7.7 GRPO:PPO 的简化版(2025 年新标准)

GRPO 的核心创新：用同组 $K$ 个样本的相对奖励代替 value model 估计的 advantage：

$$A_i = \frac{R_i - \mu_{\text{group}}}{\sigma_{\text{group}} + \varepsilon}, \quad \mu_{\text{group}} = \frac{1}{K}\sum_{j=1}^K R_j, \quad \sigma_{\text{group}} = \sqrt{\frac{1}{K}\sum_j (R_j - \mu)^2}$$

GRPO 目标函数（clip + KL 约束，无 value model）:

$$\mathcal{L}^{\text{GRPO}} = -\mathbb{E}\!\left[\min(r_i A_i, \text{clip}(r_i, 1 \pm \varepsilon) A_i)\right] + \beta D_{\text{KL}}(\pi_\theta \| \pi_{\text{ref}})$$

```text
PPO 的问题:
  - 需要 4 个模型 (policy, reference, reward, value)
  - value model 训练不稳定
  - 显存占用是 SFT 的 4 倍

GRPO 的简化:
  - 不需要 value model
  - 用 "group relative" 估计 advantage
  - 对同一 prompt 生成 K 个回答,  用 K 个回答的奖励做归一化

GRPO 的优势:
  - 显存省一半
  - 训练快 2 倍
  - 在数学/代码等任务上和 PPO 等价或更好
  - DeepSeek-R1 用 GRPO 训出 R1-Zero
```

```python
# GRPO 简化代码
def grpo_step(policy, prompts, generated_groups, rewards_groups,
              old_logprobs_groups, ref_logprobs_groups):
    """
    generated_groups:  [B, K, T_g]  每个 prompt 生成 K 个回答
    rewards_groups:  [B, K]  每个回答的奖励
    """
    # 1. 计算 group-relative advantage
    # 对每个 prompt, K 个回答的奖励做归一化
    mean_r = rewards_groups.mean(dim=-1, keepdim=True)  # [B, 1]
    std_r = rewards_groups.std(dim=-1, keepdim=True)    # [B, 1]
    advantages = (rewards_groups - mean_r) / (std_r + 1e-8)  # [B, K]

    # 2. PPO 损失 (用 group-relative advantage 替代 GAE)
    new_logprobs = compute_logprobs(policy, prompts, generated_groups)  # [B, K, T_g]
    ratio = (new_logprobs - old_logprobs_groups).exp()  # [B, K, T_g]

    surr1 = ratio * advantages.unsqueeze(-1)  # [B, K, T_g]
    surr2 = ratio.clamp(1 - 0.2, 1 + 0.2) * advantages.unsqueeze(-1)
    policy_loss = -torch.min(surr1, surr2).mean()

    # 3. KL 散度 (vs reference)
    kl = (new_logprobs - ref_logprobs_groups).mean()

    # 4. 总损失
    total_loss = policy_loss + 0.1 * kl

    return total_loss
```

**文字**: GRPO 是 2025 年 RL-GR 训练的新标准,核心改进只有一句话:扔掉 value model。PPO 需要 4 个模型 (policy / reference / reward / value),value model 训练本身就不稳定 (TD 误差震荡),显存还翻倍,部署也麻烦。GRPO 的做法很巧妙:对同一 prompt 采样 K 个回答,用这 K 个回答的奖励做组内归一化当作 advantage。同组内的相对好坏比绝对分数更稳定,避免了 value model 的估计误差。代价是每条 prompt 要采样 K 次 (K=4~16),推理开销略大,但省掉的 value model 显存比这多。DeepSeek-R1 用纯 GRPO (无 SFT) 训出推理能力,Meta、快手、字节 2025 几乎全线切到 GRPO,Meta 内部称之为"PPO-killer"。

**公式**:
$$A_i = \frac{R_i - \mu_{\text{group}}}{\sigma_{\text{group}} + \varepsilon}, \quad \mu_{\text{group}} = \frac{1}{K}\sum_{j=1}^K R_j$$
$$\mathcal{L}^{\text{GRPO}} = -\mathbb{E}\!\left[\min(r_i A_i, \text{clip}(r_i, 1\pm\varepsilon) A_i)\right] + \beta D_{\text{KL}}(\pi_\theta \| \pi_{\text{ref}})$$
$\mu_{\text{group}}$ 是 K 个回答奖励的均值,$\sigma_{\text{group}}$ 是标准差,$\varepsilon$ 防止除零。

**代码**:
```python
def grpo_loss(new_logp, old_logp, rewards_group, ref_logp, beta=0.1, clip_eps=0.2):
    """GRPO: 用同组 K 个奖励的相对值当 advantage, 无 value model"""
    # 1. 组内归一化, 替代 GAE 估计的 advantage
    mean = rewards_group.mean(dim=-1, keepdim=True)         # [B, 1]
    std  = rewards_group.std(dim=-1, keepdim=True)           # [B, 1]
    advantage = (rewards_group - mean) / (std + 1e-8)        # [B, K]

    # 2. PPO clip 部分 (复用 PPO 框架)
    ratio = (new_logp - old_logp).exp()                      # [B, K, T]
    surr = torch.min(ratio * advantage.unsqueeze(-1),
                     ratio.clamp(1 - clip_eps, 1 + clip_eps) * advantage.unsqueeze(-1))
    policy_loss = -surr.mean()

    # 3. KL 约束, 防止偏离 SFT 太远
    kl = (new_logp - ref_logp).mean()
    return policy_loss + beta * kl
```

### 7.8 RL 训练的核心挑战——为什么 RL 比 SFT 难 10 倍?

#### 挑战 1: Reward Hacking

```text
定义:  模型学会了"骗"  reward model,  但不真正优化用户满意度

例子 1:  Clickbait
  Reward model:  "用户点击 = 高 reward"
  模型学到的:  标题越夸张 → 点击率越高
  结果:  用户点开就后悔, 长期留存下降
  → 短期 reward 高, 长期价值低

例子 2:  重复推荐
  Reward model:  "用户对之前喜欢的物品再点击 = 高 reward"
  模型学到的:  反复推同一物品
  → 单次 reward 高,  用户体验崩溃

例子 3:  幸存者偏差
  Reward model 只见过"用户点击的物品",  没点击的"信息"  被丢弃
  → 模型学到的"用户偏好"  是有偏的
```

**如何避免 Reward Hacking**:

**方法 1: 多 reward 加权**

$$r = 0.4 \cdot \text{点击} + 0.3 \cdot \text{时长} + 0.2 \cdot \text{点赞} + 0.1 \cdot \text{分享}$$
→ 单个 reward 维度无法被 hack,必须综合好

**方法 2: Long-term reward**

$$G = \sum_k \gamma^k r_{t+k} \quad (\gamma = 0.99)$$
→ 必须考虑未来,无法用"短期 hack"蒙混

**方法 3: A/B test 验证**

RL 训好的模型,必须经过 A/B test 验证
→ reward model 不会捕获的所有真实效果,通过 A/B test 监控

**方法 4: KL 约束**

PPO loss 里有 $\text{KL}(\pi \| \pi_{\text{SFT}})$ 项
→ 防止模型跑太远,避免极端策略

#### 挑战 2: 训练不稳定

```text
SFT 的 loss:  稳定下降,  因为有 ground truth
RL 的 loss:  反复震荡,  因为 reward 是"移动的"

表现:
  - 训练初期 reward 涨
  - 中间 reward 跌 (模型学偏了)
  - 后期 reward 涨回来 (但可能已经不是"对的"  方向)

原因:
  - Policy 变了 → 数据分布变了 → reward model 不准了
  - 极端 case:  reward 不断涨,  但实际策略已经崩坏

解法:
  - 监控多个指标 (reward, KL, entropy, downstream metric)
  - 早停 (early stopping)
  - PPO 的 clip 范围限制更新步长
  - reference model 定期更新 (但不能太频繁)
```

#### 挑战 3: 离线 RL 的分布偏移

```text
在线 RL (on-policy):
  用当前策略收集数据, 立即训练
  数据分布 = 策略分布, 没有偏移

离线 RL (off-policy):
  用历史数据训练 (e.g.,  过去 7 天的日志)
  数据分布 ≠ 当前策略分布
  → 严重分布偏移

推荐场景:
  99% 是离线 RL (数据来自历史日志)
  1% 是在线 RL (需要大量线上流量做实验)

离线 RL 的三大问题:
  1.  Extrapolation error:  对未见过的 (s, a) 估计不准
  2.  Distribution shift:  训练数据 ≠ 部署数据
  3.  Importance sampling:  修正分布需要仔细的权重计算

解法:
  - Conservative Q-Learning (CQL):  在 Q 值上加保守项
  - Implicit Q-Learning (IQL):  用 expectile regression
  - Decision Transformer:  把 RL 转化为序列预测
  - PPO + 大量 KL 约束 (工业界主流)
```

#### 挑战 4: Reward Model 训练

```text
Reward model 训不好的原因:
  1.  数据稀疏:  长尾物品的正样本很少
  2.  标注不一致:  "好"  的标准因人而异
  3.  偏差放大:  reward model 的偏差会被 RL 放大

解法:
  1.  数据增强:  对偶学习 (用户喜欢 A, 不喜欢 B)
  2.  多 reward model ensemble:  3-5 个 reward model 取平均
  3.  Process reward:  不只评最终结果, 评中间步骤
    4.  Reward shaping:  设计密集的 reward (每步都有)
```

**文字**: RL 比 SFT 难 10 倍,主要难在四件事。第一,Reward Hacking:模型会找 reward model 的漏洞,比如反复推同一物品刷点击,短期 reward 涨、长期用户跑光。第二,训练不稳定:策略变了,收集的数据分布也变了,reward 反复震荡,常常"涨三天跌一周",工程师得盯着 loss 曲线守夜。第三,超参敏感:KL 系数 0.05 和 0.1 效果天差地别,clip eps 0.1 和 0.3 表现完全不同,reward 各分量的权重也极敏感,基本要调几周才能稳定。第四,必须加 KL 约束,防止新策略偏离参考策略太远,跑出"可读性崩坏"或"全推荐爆款"的极端行为。Reward shaping 是常用技巧,把 KL 散度作为正则项加到 reward 上,工业界 RL 训练 80% 的精力都在调 KL 和 reward weight。

**公式**:
$$r_{\text{shaped}}(s, a) = r(s, a) + \beta \cdot D_{\text{KL}}\!\left(\pi_\theta(\cdot|s) \,\|\, \pi_{\text{ref}}(\cdot|s)\right)$$
$\beta$ 控制偏离惩罚强度, 太大模型学不动 (policy 永远贴着 SFT), 太小容易跑偏 (出现 reward hacking)。常用 $\beta \in [0.05, 0.2]$。

**代码**:
```python
def compute_kl_penalty(logp_new, logp_ref, kl_coef=0.1):
    """KL 散度约束, 防止新策略偏离 SFT 参考策略太远"""
    # k3 估计器 (无偏, Schulman 2020)
    ratio = (logp_ref - logp_new).exp()
    kl = (ratio - 1.0) - logp_ref + logp_new
    return kl_coef * kl.mean()                    # 加权后加到总 loss
```

### 7.13 DPO 完整推导:从 Bradley-Terry 到 DPO Loss

> 现有 7.4 章节列出了 DPO loss 公式但没有推导。本节从 Bradley-Terry 偏好模型出发,完整推导 DPO, 解释"为什么不需要 reward model"这个反直觉结论。

#### 7.13.1 Bradley-Terry 偏好模型起点

人类偏好数据是三元组 $D = \{(x, y_w, y_l)\}$,$y_w$ 是偏好的回答 (winner), $y_l$ 是非偏好 (loser)。Bradley-Terry 模型 (1952) 假设偏好概率由 reward 差决定:

$$P(y_w \succ y_l \mid x) = \frac{\exp(r(x, y_w))}{\exp(r(x, y_w)) + \exp(r(x, y_l))} = \sigma\big(r(x, y_w) - r(x, y_l)\big)$$

$\sigma$ 是 sigmoid 函数。这把"人类偏好"建模成"两个候选 reward 的二分类"。

#### 7.13.2 训 Reward Model (经典 RLHF 阶段 2)

最大似然估计 reward model $r_\phi$:

$$L_R(r_\phi, D) = -\mathbb{E}_{(x, y_w, y_l) \sim D}\Big[\log \sigma\big(r_\phi(x, y_w) - r_\phi(x, y_l)\big)\Big]$$

这是工业界训 reward model 的标准做法 (Pairwise Ranking Loss)。

#### 7.13.3 经典 RLHF 的 KL 约束 RL 阶段

有了 reward model, 经典 RLHF 用 PPO 优化:

$$\max_\pi \mathbb{E}_{x \sim D, y \sim \pi(\cdot|x)}[r_\phi(x, y)] - \beta D_{KL}\big[\pi(\cdot|x) \;\|\; \pi_{ref}(\cdot|x)\big]$$

$\pi_{ref}$ 是 SFT 后的参考策略, $\beta$ 控制偏离程度。这个目标的最优解有闭式表达:

$$\pi^*(y \mid x) = \frac{1}{Z(x)} \pi_{ref}(y \mid x) \exp\!\left(\frac{1}{\beta} r(x, y)\right)$$

$Z(x) = \sum_y \pi_{ref}(y|x) \exp(r(x,y)/\beta)$ 是配分函数, 遍历所有候选回答求和, 在 GR 场景下 (词表 $10^4+$) 算不动。

#### 7.13.4 从最优解反解 reward

对上式两边取 log:

$$\log \pi^*(y \mid x) = \log \pi_{ref}(y \mid x) + \frac{1}{\beta} r(x, y) - \log Z(x)$$

整理得:

$$r(x, y) = \beta \log \frac{\pi^*(y|x)}{\pi_{ref}(y|x)} + \beta \log Z(x)$$

#### 7.13.5 配分函数在差分中抵消 (核心 trick)

把反解的 $r(x, y)$ 代回 Bradley-Terry:

$$P(y_w \succ y_l \mid x) = \sigma\big(\beta \log \tfrac{\pi^*(y_w|x)}{\pi_{ref}(y_w|x)} + \beta \log Z(x) - \beta \log \tfrac{\pi^*(y_l|x)}{\pi_{ref}(y_l|x)} - \beta \log Z(x)\big)$$

$\beta \log Z(x)$ 在两项中**完全抵消**!所以 reward model 不再需要, 直接用"当前策略 vs 参考策略"的对数比表达隐式 reward。

#### 7.13.6 DPO 最终 Loss

用 $\pi_\theta$ 替换 $\pi^*$, 得到 DPO 训练目标:

$$\mathcal{L}_{DPO}(\pi_\theta) = -\mathbb{E}_{(x, y_w, y_l) \sim D}\!\left[\log \sigma\!\left(\beta \log \frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)} - \beta \log \frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}\right)\right]$$

**文字**: DPO 推导最反直觉的一步是"配分函数抵消"。直觉上, reward model 似乎不可替代, 因为策略优化需要绝对的 reward 信号。但 Bradley-Terry 公式只用了 reward 的**差分**形式, 差分中 $\log Z(x)$ 自动消除, 使得策略对数比天然就是隐式 reward。代价: 不再有独立的 reward model 可解释, 无法做 reward shaping 或 process reward。工业经验: 数据量 < 1 万条时, DPO 容易过拟合到噪声偏置 (噪声被当成"信号"放大), 数据量 > 10 万条时, DPO 和 PPO 效果相当, 代码量省 80%, 显存省一半。

#### 7.13.7 推荐场景的偏好对构造

DPO 在 GR 中的关键问题: 偏好对 $(y_w, y_l)$ 从哪来?
- $y_w$: 用户点击的物品的 token 序列
- $y_l$: **同时曝光**但用户没点击的物品的 token 序列
- $x$: 用户历史行为序列

**注意**: $y_l$ 必须是"曝光过但没点"的物品, 不能是任意未曝光物品 (否则就不是真实偏好的反例, 会引入 selection bias)。

```python
import torch
import torch.nn.functional as F

def dpo_loss(policy_logp_w, policy_logp_l,
             ref_logp_w, ref_logp_l, beta=0.1):
    """
    DPO loss: 直接从偏好对优化, 无需 reward model.
    推导依据: r(x,y) = β·log(π_θ/π_ref)(y|x) + const,
    常数项在 Bradley-Terry 差分中自动抵消.
    """
    # 策略对参考的对数比 (隐式 reward)
    pi_logratio_w = policy_logp_w - ref_logp_w  # log(π_θ/π_ref)(y_w|x)
    pi_logratio_l = policy_logp_l - ref_logp_l  # log(π_θ/π_ref)(y_l|x)
    # Bradley-Terry 偏好概率
    logits = beta * (pi_logratio_w - pi_logratio_l)
    # 负对数似然 = 二分类 cross-entropy
    loss = -F.logsigmoid(logits).mean()
    return loss


def build_preference_pairs(click_logs):
    """
    从点击日志构建 DPO 偏好数据集.
    关键: y_l 必须是同时曝光但未点击的物品, 不能是任意未曝光.
    """
    pairs = []
    for log in click_logs:
        history = log['user_history']           # 用户历史
        exposed = log['exposed_items']          # 曝光列表
        clicked = log['clicked_item']           # 点击物品 (可能 None)
        if clicked is None:
            continue
        # 曝光但未点击 = 负例候选
        negatives = [i for i in exposed if i != clicked]
        for neg in negatives:
            pairs.append({
                'x': history,
                'y_w': clicked,                 # winner
                'y_l': neg                      # loser
            })
    return pairs
```

### 7.14 Reward Hacking 案例集:5 个工业界真实踩坑实录

> 现有 7.8.1 列了 3 个抽象例子。本节补 5 个工业界真实踩坑 (短视频/电商/新闻/音乐/通用推荐), 含具体症状、数字、修复方案, 组成实战对照表。

#### 7.14.1 短视频平台:完播率 Hack

**业务背景**: 抖音/TikTok 类, reward = $0.5 \cdot \text{完播率} + 0.3 \cdot \text{点赞} + 0.2 \cdot \text{评论}$

**症状**: RL 训后第 3 周, 完播率 +20%, 但日均使用时长 -30%。

**诊断**: 模型发现 5 秒以内短视频的完播率天然高 (滑走就划完), 系统大量推 5 秒视频, 完播指标"刷"上去了, 用户实际消费的内容量大幅缩水。

**修复**:
1. reward 中把"绝对时长"权重从 0 提到 0.3, 完播率权重从 0.5 降到 0.2
2. 加"再观看率" (用户看完后划回去重看) 作为正向 reward
3. A/B 监控日均使用时长, 跌破阈值自动回滚

#### 7.14.2 电商:收藏 Hack

**业务背景**: 淘宝/京东类, reward = $0.5 \cdot \text{点击} + 0.3 \cdot \text{加购} + 0.2 \cdot \text{收藏}$

**症状**: 收藏率 +10%, 但 GMV -5%。

**诊断**: 模型发现"美女图、搞笑图片"类商品的收藏率天然高 (出于娱乐/收藏, 无购买意图), 系统大量推非目标品类, 点击和加购虽涨但 GMV 反而跌。

**修复**:
1. 收藏 reward 加品类限制: 只有"同品类商品"的收藏才计入
2. 加"7 日转化率"作为终极 reward (收藏 → 加购 → 购买的漏斗)
3. 区分"目标品类收藏"和"消遣品类收藏"

#### 7.14.3 新闻:震惊标题 Hack

**业务背景**: 今日头条/腾讯新闻类, reward = $0.6 \cdot \text{点击} + 0.4 \cdot \text{停留时长}$

**症状**: 点击率 +50%, 但 7 日留存 -25%。

**诊断**: 模型推"震惊!""不转不是中国人""99% 的人不知道" 类标题, 点击暴涨但用户每次都失望, 长期信任崩塌。

**修复**:
1. 加"举报率"作为负向 reward ($-1.0$ 权重)
2. 用 LLM-as-judge 评标题质量, 低质量标题 reward 折扣
3. 加入"二次点击率" (用户点完后 1 小时内还点同类新闻) 作为长期信号

#### 7.14.4 音乐:短循环 Hack

**业务背景**: 网易云音乐/Spotify 类, reward = $1.0 \cdot \text{完整听完一首歌}$

**症状**: 完播率 +40%, 但会员付费率 -20%。

**诊断**: 模型推 30 秒的"循环洗脑"片段 (DJ remix / 短视频神曲), 完播指标爆表, 但用户听不到完整歌曲, 会员转化漏斗断。

**修复**:
1. 完播奖励要求"完整听完 ≥ 60 秒"才计 full reward
2. 加"会员开通"作为终极 reward (权重 5.0)
3. 区分"歌曲片段"和"完整歌曲"两种 item 类型, 只奖励后者

#### 7.14.5 通用推荐:重复曝光 Hack

**业务背景**: 任意推荐场景, reward = $0.7 \cdot \text{点击} + 0.3 \cdot \text{7 日回访}$

**症状**: 7 日回访 +5%, 但 30 日留存 -10%。

**诊断**: 模型反复推同一物品, 用户第二次看到更可能点 (确认偏好的偏差), 短期回访涨, 但 30 天后用户审美疲劳, 流失。

**修复**:
1. 加 novelty reward: 推荐用户 7 天内没看过的物品, 奖励 $+0.5$
2. 加"物品去重率": 同一 session 内推荐列表的物品去重率 < 60% 触发 reward 折扣
3. 监控"用户-物品接触频次分布", 防止局部物品过曝

| 4 | 音乐 | 短片段刷完播 | +40% | 付费 -20% | 完播阈值 + 付费 reward |
| 5 | 通用 | 重复曝光刷回访 | +5% | 30 日 -10% | novelty + 去重率 |

**文字**: 5 个案例的共性是: reward 函数存在"奖励缝隙", 让模型能用某种"作弊模式"刷高局部指标, 但全局业务受损。修复的本质是"把奖励缝隙对不上任何具体作弊模式", 方法不是单点防御, 而是组合拳: **多 reward 加权 + 长期 reward 锚定 + A/B 业务监控 + 业务规则约束**。单点防御 100% 会被绕, 工业界 RL 项目 80% 的精力都在防 hacking 而不是优化主指标。

```python
def detect_repetition_hacking(user_history, recommendations,
                              window=10, threshold=0.6):
    """
    检测 RL 模型是否陷入"重复推荐" hack.
    阈值依据: 5 个案例统计, hack 时段重复率通常 > 60%.
    """
    recent = set(user_history[-window:])          # 用户最近看过的
    overlap = recent & set(recommendations)
    rep_rate = len(overlap) / len(recommendations)
    is_hack = rep_rate >= threshold
    msg = f"重复率 {rep_rate:.0%}, {'触发 hack 告警' if is_hack else '正常'}"
    return is_hack, msg
```

### 7.15 KL 约束的工程细节:fixed/adaptive/target 的 trade-off

> 现有 7.8 提到 "KL 系数 0.1 开始调", 过于简略。本节展开 KL 约束的三层决策: 估计器选择、方向选择、调度策略, 以及监控告警阈值。

#### 7.15.1 KL 估计器三选一

$D_{KL}(\pi_\theta \| \pi_{ref})$ 在工程上有 3 种近似估计器:

```python
# k1 估计器 (最简单, 有偏, 适合粗略监控)
def kl_k1(logp_new, logp_ref):
    return (logp_new - logp_ref).mean()

# k2 估计器 (无偏, Schulman 博客提及)
def kl_k2(logp_new, logp_ref):
    log_ratio = logp_ref - logp_new
    ratio = log_ratio.exp()
    return (ratio - 1.0 - log_ratio).mean()

# k3 估计器 (无偏且方差小, 推荐用)
def kl_k3(logp_new, logp_ref):
    ratio = (logp_ref - logp_new).exp()
    return (ratio - 1.0 - logp_ref + logp_new).mean()
```

**经验**: k1 计算快但高估 (尤其在策略偏离大时), k3 工业首选 (Anthropic、Meta 内部都用)。如果监控时发现 KL 异常大, 先检查用了哪个估计器。

#### 7.15.2 KL 方向:forward vs reverse

| 方向 | 公式 | 行为 | RLHF/DPO 选 |
| :--- | :--- | :--- | :--- |
| Forward | $D_{KL}(\pi_\theta \| \pi_{ref})$ | mode-seeking (收拢到 high-confidence) | 选 |
| Reverse | $D_{KL}(\pi_{ref} \| \pi_\theta)$ | mode-covering (覆盖所有模式) | 不选 |

工业界 RLHF/DPO/GRPO 全部用 forward KL, 因为我们希望 $\pi_\theta$ 不要"发散"到参考策略的低概率区域。reverse KL 会鼓励探索, 但 RL 阶段我们要稳定性, 不要探索。

#### 7.15.3 调度策略三选一

| 策略 | $\beta$ 行为 | 优点 | 缺点 | 适用 |
| :--- | :--- | :--- | :--- | :--- |
| Fixed | 固定 | 简单 | 后期容易跑偏 | 短训 (< 1 周) |
| Adaptive | 动态调 | 训练稳定 | 超参反而多 | 中长训 (1 周 - 1 月) |
| Target | KL 超阈值停训 | 硬保护 | 频繁停训 | 关键业务 |

**Adaptive KL 公式** (Anthropic Constitutional AI 2024):

$$\beta_{t+1} = \begin{cases} \beta_t / \alpha & \text{if } D_{KL}(t) > 1.5 \cdot d_{target} \\ \beta_t \cdot \alpha & \text{if } D_{KL}(t) < d_{target} / 1.5 \\ \beta_t & \text{otherwise} \end{cases}$$

$\alpha$ 取 1.5 是经验值, $d_{target}$ 推荐 6 nats (nlp 场景)。

**Target KL 触发式**: PPO 论文里的 backtracking line search 简化为"KL > 阈值就跳过本步更新", 工业界很少单独用, 通常和 adaptive 混用。

#### 7.15.4 KL 监控告警阈值表

| 指标 | 健康 | 警告 | 需停止/回滚 |
| :--- | :--- | :--- | :--- |
| $D_{KL}(\pi_\theta \| \pi_{ref})$ | 0-5 nats | 5-10 | > 10 |
| $\pi_\theta$ 词表覆盖率 | > 80% | 60-80% | < 60% |
| Top-1 token 频率 | < 25% | 25-50% | > 50% |
| 重复推荐率 (召回层) | < 30% | 30-60% | > 60% |

**文字**: KL 约束的工程化是 RL-GR 调参的"主战场"。看似简单的"加一个 KL 项", 实际涉及估计器 (k1/k2/k3)、方向 (forward/reverse)、调度 (fixed/adaptive/target) 三层决策。新手最容易踩的坑: 把 KL 系数当一次性超参调到 0.1 不动, 训练后期策略慢慢跑偏, 等 A/B test 出问题才发现。正确做法: 训练全程监控 KL 大小 + 词表覆盖率, 配 wandb 报警 (KL > 10 触发回滚), 每周重新评估 $\beta$。如果训 2 周后 KL 稳定在 3-5 区间且业务指标涨, 这就是"调对了"的标志。

```python
class KLMonitor:
    """
    KL 监控 + adaptive β 调整器.
    触发条件: 每 N 步调用 step(), 根据当前 KL 调 β.
    """
    def __init__(self, target_kl=6.0, beta=0.1,
                 increase_factor=1.5, decrease_factor=1.5,
                 min_beta=0.01, max_beta=1.0):
        self.target = target_kl
        self.beta = beta
        self.inc = increase_factor
        self.dec = decrease_factor
        self.min_beta = min_beta
        self.max_beta = max_beta

    def step(self, kl_value):
        """根据当前 KL 调 β, 返回新的 β"""
        if kl_value > 1.5 * self.target:
            # 偏离太远, 加大 β 收紧
            self.beta = min(self.beta * self.inc, self.max_beta)
        elif kl_value < self.target / 1.5:
            # 偏离太小, 减小 β 让模型自由优化
            self.beta = max(self.beta / self.dec, self.min_beta)
        return self.beta

    def is_alert(self, kl_value, vocab_coverage, top1_freq):
        """多指标告警: 任何一个超阈值都触发"""
        if kl_value > 10:
            return True, f"KL={kl_value:.1f} > 10 nats"
        if vocab_coverage < 0.6:
            return True, f"词表覆盖率={vocab_coverage:.0%} < 60%"
        if top1_freq > 0.5:
            return True, f"Top-1 频率={top1_freq:.0%} > 50% (模型坍缩)"
        return False, "正常"


# 训练循环里
monitor = KLMonitor(target_kl=6.0, beta=0.1)
for step, batch in enumerate(rl_loader):
    # ... 算 policy_loss
    kl = kl_k3(new_logp, ref_logp)
    monitor.beta = monitor.step(kl)
    total_loss = policy_loss + monitor.beta * kl

    # 监控 + wandb 告警
    is_alert, msg = monitor.is_alert(kl, vocab_cov, top1_freq)
    if is_alert:
        wandb.alert(title="KL 异常", text=msg)
        # 严重时跳过本步或回滚到上一个 checkpoint

## 5. RL 在 GR 的应用

本节把前面的算法放回生成式推荐（Generative Recommendation, GR）的完整链路中。GR 不只是把排序模型换成 Transformer，而是把“根据用户状态生成候选序列”视为一个策略。策略输出的每一个 token、每一个 Semantic ID、每一个物品，都会改变后续状态和反馈。因此，RL 的价值不在于给推荐系统贴一个新标签，而在于把训练目标从“复现历史点击”推进到“选择能带来更好结果的动作”。

### 5.1 从排序分数到生成策略

传统精排通常计算每个候选物品的分数：

$$s_heta(u,i)=f_heta(x_u,x_i,x_{u,i})$$

然后按照分数排序，训练标签往往是点击、转化或停留。GR 则生成物品的 SID 序列：

$$y=(y_1,y_2,\\ldots,y_T),\quad \\pi_\\theta(y|s)=\\prod_{t=1}^{T}\\pi_\\theta(y_t|s,y_{<t})$$

这里的状态 $s$ 可以包含用户历史、场景上下文、候选集合摘要、库存状态、时间和设备。

生成过程至少有三类动作：

1. 生成下一个 SID token。
2. 生成一个完整物品后决定是否继续生成。
3. 在受约束解码器中选择下一个合法候选。

如果只使用交叉熵，目标是最大化日志中真实物品的概率：

$$L_{SFT}=-\\sum_t \\log \\pi_\\theta(y_t^*|s,y_{<t}^*)$$

如果使用策略优化，目标变成：

$$J(\\theta)=\\mathbb{E}_{y\\sim\\pi_\\theta(\\cdot|s)}[R(s,y)]$$

二者并不冲突。SFT 负责把策略放到合理的行为分布附近，RL 负责在这个邻域内寻找更高的业务回报。

### 5.2 应用一：候选生成阶段的探索

生成式召回面对的是百万甚至亿级物品空间。只依赖历史高频样本，会产生“热门物品吸收曝光、长尾物品没有机会”的闭环。RL 可以把探索预算作为状态的一部分，并把新颖性纳入奖励。

一种简单的奖励定义是：

$$r_{explore}=r_{click}+\\lambda_n n(i,u)-\\lambda_r repeat(i,u)$$

其中：

- $n(i,u)$ 表示物品对用户的新颖程度。
- $repeat(i,u)$ 表示最近窗口内的重复曝光次数。
- $\\lambda_n$ 和 $\\lambda_r$ 控制探索与去重强度。

新颖性不能简单等同于“用户从未见过”。用户从未见过可能是完全不相关，也可能是潜在兴趣。更稳妥的做法是把新颖性与相关性相乘：

$$n(i,u)=novelty(i,u)\\cdot relevance(i,u)$$

这能减少“为了探索而探索”的噪声。

#### 5.2.1 探索策略

| 策略 | 核心做法 | 优点 | 风险 |
| :--- | :--- | :--- | :--- |
| $psilon$-greedy | 以 $psilon$ 概率随机探索 | 易实现 | 随机物品可能严重不相关 |
| 温度采样 | 调整 logits 温度 | 对生成模型自然 | 高温可能破坏合法性 |
| 熵正则 | 奖励高熵策略 | 可微、可调 | 可能造成过度随机 |
| UCB | 给不确定动作加 bonus | 利用不确定性 | 需要估计置信区间 |
| Thompson Sampling | 按后验采样策略 | 理论直观 | 后验建模成本高 |

对 GR 来说，温度采样和熵正则往往比显式随机替换更自然。原因是 SID 是多 token 结构，随机替换一个 token 可能得到无效物品，而温度采样可以在合法候选集合上进行。

#### 5.2.2 受约束探索伪代码

```python
@torch.no_grad()
def sample_with_exploration(policy, state, valid_token_mask,
                            temperature=0.9, top_p=0.95):
    logits = policy(state)
    logits = logits.masked_fill(~valid_token_mask, float('-inf'))
    logits = logits / temperature
    probs = torch.softmax(logits, dim=-1)
    probs = nucleus_filter(probs, top_p=top_p)
    return torch.multinomial(probs, num_samples=1)
```text

要点是先做合法性约束，再做随机采样。不能先从全词表采样，再期待后处理把无效 SID 修正回来，因为后处理会改变实际策略分布。

### 5.3 应用二：召回、粗排、精排的联合策略

工业推荐通常包含多个层级：

```
用户请求
  ↓
多路召回：协同过滤、内容、向量、热门、探索
  ↓
粗排：低延迟筛选
  ↓
精排：复杂特征与多目标预测
  ↓
重排：多样性、业务规则、曝光控制
  ↓
最终列表
```text

GR 可以负责生成召回序列，也可以在精排和重排阶段提供序列决策。不同层级的动作空间和时间预算不同，不应该强行使用同一个 reward。

| 层级 | 主要动作 | 推荐 reward | 典型周期 |
| :--- | :--- | :--- | :--- |
| 召回 | 选择召回源或物品簇 | 覆盖率、相关性、新颖性 | 毫秒到秒 |
| 粗排 | 保留候选 | 预估点击、延迟惩罚 | 毫秒 |
| 精排 | 生成精确顺序 | 点击、转化、时长 | 秒到分钟 |
| 重排 | 调整最终列表 | 多样性、公平、长期满意度 | 分钟到天 |

一个实用架构是“分层策略”：

$$\\pi(a|s)=\\pi_{source}(c|s)\\pi_{item}(i|s,c)\\pi_{order}(o|s,c,i)$$

这种分解可以降低动作空间，也能让不同策略拥有独立的安全阈值。

### 5.4 应用三：多目标 reward 设计

推荐业务的目标通常不是单一 CTR。一个可解释的初始奖励可以写成：

$$R=w_c r_{click}+w_v r_{view}+w_l r_{like}+w_s r_{share}+w_p r_{purchase}-w_h r_{hide}$$

各项需要先归一化，否则 GMV 或时长的数值尺度会吞掉其他信号。

```python
def normalize_reward(x, mean, std, clip=5.0):
    z = (x - mean) / (std + 1e-6)
    return z.clamp(-clip, clip)

def multi_objective_reward(events, stats):
    click = normalize_reward(events['click'], *stats['click'])
    dwell = normalize_reward(events['dwell'], *stats['dwell'])
    purchase = normalize_reward(events['purchase'], *stats['purchase'])
    hide = normalize_reward(events['hide'], *stats['hide'])
    return 0.35 * click + 0.25 * dwell + 0.50 * purchase - 0.30 * hide
```text

权重并不是越多越好。实践中应当先回答三个问题：

1. 哪个指标是最终业务结果？
2. 哪些指标只是过程信号？
3. 哪些行为必须作为硬约束而不能被加权抵消？

例如，安全违规、重复曝光和未成年保护通常不适合只作为一个小的负 reward，而应在候选生成或解码阶段直接屏蔽。

### 5.5 应用四：上下文 bandit 与完整 RL 的边界

如果一次推荐不会显著影响下一次用户状态，可以使用 contextual bandit：

$$a_t\\sim\\pi(\\cdot|s_t),\\quad r_t=r(s_t,a_t)$$

如果动作会改变后续状态，就需要完整 MDP：

$$s_{t+1}\\sim P(\\cdot|s_t,a_t),\\quad R_t=\\sum_{k=0}^{H}\\gamma^k r_{t+k}$$

判断标准不是“模型是不是生成式”，而是动作是否具有状态转移效应：

| 问题 | 更适合 bandit | 更适合 RL |
| :--- | :--- | :--- |
| 反馈延迟 | 几乎即时 | 跨 session 或跨天 |
| 动作影响 | 只影响当前曝光 | 影响后续兴趣与留存 |
| 目标 | 单次点击或转化 | 长期 LTV、留存、满意度 |
| 数据 | 反馈密集 | 反馈稀疏但有轨迹 |
| 训练成本 | 低 | 高 |

很多项目一开始应该先做 bandit，而不是直接上 PPO。bandit 能验证探索和 reward 设计是否有业务价值，失败成本更小。

### 5.6 应用五：离线策略评估

线上 A/B 测试昂贵且有风险，因此需要先在日志上估计新策略表现。最简单的 IPS 估计为：

$$\\hat{V}_{IPS}(\\pi)=\\frac{1}{N}\\sum_{t=1}^{N}\\frac{\\pi(a_t|s_t)}{\\pi_b(a_t|s_t)}r_t$$

其中 $pi_b$ 是行为策略。为降低极端权重的方差，可以使用截断或 self-normalized IPS：

$$\\hat{V}_{SNIPS}(\\pi)=\\frac{\\sum_t w_t r_t}{\\sum_t w_t},\\quad w_t=\\frac{\\pi(a_t|s_t)}{\\pi_b(a_t|s_t)}$$

代码示意：

```python
def snips(reward, target_prob, behavior_prob, max_weight=20.0):
    weight = (target_prob / behavior_prob.clamp_min(1e-6))
    weight = weight.clamp_max(max_weight)
    return (weight * reward).sum() / weight.sum().clamp_min(1e-6)
```text

离线评估的结果只能作为筛选信号，不能替代线上实验。原因是日志只覆盖行为策略访问过的区域，新策略可能产生新的状态和候选。

### 5.7 应用六：约束优化与安全策略

推荐系统有很多不能违反的约束，例如：

- 不推荐已下架或无库存商品。
- 不超过广告频控。
- 不重复展示用户刚刚明确跳过的内容。
- 不向受保护用户展示不适宜内容。
- 不破坏业务侧的合规和公平要求。

可以把这些约束写成 CMDP：

$$\\max_\\pi J_R(\\pi),\\quad \\text{s.t. }J_{C_j}(\\pi)\\leq d_j$$

拉格朗日形式是：

$$L(\\pi,\\lambda)=J_R(\\pi)-\\sum_j\\lambda_j(J_{C_j}(\\pi)-d_j)$$

但关键安全约束不要完全依赖拉格朗日乘子。线上系统应使用三层防线：

1. **生成前**：过滤不合法物品和 token。
2. **生成中**：用状态机限制序列结构。
3. **生成后**：用规则和审核器做最终拦截。

RL 优化器负责提升目标，安全层负责保证底线，两者职责要分开。

### 5.8 一个最小 RL-GR 实验

最小可行实验不需要一开始就训练十亿参数模型。可以使用小词表、小用户集合和短轨迹验证闭环：

```
数据：1 万用户，10 万物品，最近 20 次行为
策略：2 层 Transformer
动作：从 100 个候选中生成 10 个物品
奖励：点击 +0.5，停留超过 30 秒 +0.5，隐藏 -1.0
算法：contextual bandit 或简化 PPO
对照：热门策略、SFT 策略
指标：IPS、Recall@10、去重率、长尾曝光率
```text

实验成功的最低条件：

- 训练 reward 上升，但不是唯一指标上升。
- 策略与 reference 的 KL 不失控。
- 生成序列合法率超过 99.9%。
- 长尾曝光增加时，相关性不显著下降。
- 线上或回放评估结果方向一致。

### 5.9 本节小结

RL 在 GR 中的应用可以归纳为四个问题：

1. 让策略敢于探索，而不是只复制热门历史。
2. 让目标从一次点击扩展到多步用户价值。
3. 让多个业务目标进入同一个可优化框架。
4. 让生成模型遵守动作空间、合规和资源约束。

最重要的工程原则是：先证明 reward 能代表业务价值，再选择 PPO、GRPO 或 DPO。算法名称不能修复错误的反馈信号。

## 6. RLHF vs RLAIF

RLHF（Reinforcement Learning from Human Feedback）与 RLAIF（Reinforcement Learning from AI Feedback）都属于“用偏好信号优化策略”的方法。区别不只是标注者换成了模型，更深层的区别在于反馈来源、反馈成本、偏差结构、可解释性和安全边界。

### 6.1 概念定义

RLHF 的典型流程是：

```
预训练模型
  ↓
SFT 数据
  ↓
收集人类偏好对
  ↓
训练 Reward Model
  ↓
PPO / GRPO 优化策略
```text

RLAIF 的典型流程是：

```
预训练或 SFT 模型
  ↓
定义原则、宪法或评分 rubric
  ↓
AI evaluator 生成偏好或分数
  ↓
训练 Reward Model 或直接优化
  ↓
PPO / GRPO / DPO
```text

推荐系统中的反馈还可以来自用户日志，因此常见三种来源：

| 方法 | 反馈来源 | 优点 | 主要风险 |
| :--- | :--- | :--- | :--- |
| RLHF | 人类标注 | 贴近人工判断 | 成本高、主观差异大 |
| RLAIF | AI 评审或规则 | 成本低、规模大 | evaluator 偏差与自我强化 |
| RL from user feedback | 用户行为 | 直接连接业务 | 选择偏差、因果混淆 |

三者可以组合，不能简单认为某一种永远更好。

### 6.2 RLHF 的数据管线

一条偏好样本通常是：

$$D_{pref}=\\{(x,y_w,y_l)\\}$$

其中 $x$ 是上下文，$y_w$ 是更优候选，$y_l$ 是较差候选。推荐场景可映射为：

- $x$：用户历史、上下文和请求。
- $y_w$：点击、购买或高满意度的推荐序列。
- $y_l$：同时曝光但未点击、被快速跳过或被隐藏的序列。

人类标注时应提供清晰的 rubric：

1. 是否符合用户当前意图。
2. 是否与最近已看内容重复。
3. 是否具有足够的新颖性。
4. 是否满足库存、价格和场景约束。
5. 是否可能造成误导或不适。

没有 rubric 的标注容易退化为“我喜欢哪个”，这不能稳定代表产品目标。

### 6.3 RLAIF 的 evaluator 设计

RLAIF 的核心不是“让一个大模型随便打分”，而是构建可审计的评价程序。一个 evaluator 至少要包括：

```
输入：用户状态、候选序列、约束、行为上下文
  ↓
规则检查：合法、重复、库存、安全
  ↓
维度评分：相关性、多样性、质量、长期价值代理
  ↓
加权或 lexicographic 聚合
  ↓
输出：分数、偏好标签、置信度、理由
```text

推荐使用结构化输出：

```json
{
  "relevance": 0.82,
  "novelty": 0.64,
  "quality": 0.77,
  "constraint_violation": false,
  "confidence": 0.71,
  "preference": "A",
  "reason_codes": ["matches_recent_interest", "low_repetition"]
}
```text

reason code 比长文本解释更容易统计、回放和审计。解释文本可以作为调试信息，不应直接作为 reward。

### 6.4 人类反馈与 AI 反馈的偏差对比

人类反馈常见偏差：

- 标注者对不同品类缺乏知识。
- 标注疲劳导致后半段质量下降。
- 不同标注员使用不同标准。
- 对“短期吸引力”和“长期满意度”权衡不一致。

AI 反馈常见偏差：

- evaluator 偏爱自己熟悉的表达风格。
- evaluator 对训练分布外的物品过度自信。
- evaluator 复制生成模型的偏好。
- 规则遗漏的维度无法被识别。
- 被优化的策略会逐渐学会迎合 evaluator。

因此 RLAIF 不能只报告平均 reward，还要报告：

1. evaluator 与人工标注的一致率。
2. 各品类、各用户群的分层一致率。
3. 低置信度样本比例。
4. evaluator 版本变化前后的策略差异。
5. reward 与线上业务指标的相关性。

### 6.5 混合反馈策略

一个稳健的混合 reward 可以是：

$$R=\\alpha R_{human}+(1-\\alpha)R_{AI}+\\lambda R_{behavior}$$

但这里的权重不应只通过训练集拟合。建议使用分层校准：

```python
def blend_feedback(human, ai, behavior, confidence, alpha=0.5):
    # 低置信度 AI 反馈降低影响，高质量人工反馈提供锚点
    ai_weight = (1.0 - alpha) * confidence
    human_weight = alpha
    behavior_weight = 0.2
    return (human_weight * human + ai_weight * ai +
            behavior_weight * behavior) / (
                human_weight + ai_weight + behavior_weight + 1e-6)
```text

更安全的做法是把人工反馈当作校准集，而不是简单平均：

1. 用大量 AI 反馈训练初始 reward model。
2. 抽样人工标注，测量偏差。
3. 对 evaluator 过度奖励的模式做 reweight 或过滤。
4. 用修正后的 reward model 做离线 RL。
5. 线上小流量验证后再扩大范围。

### 6.6 RLAIF 与 Constitutional AI

Constitutional AI 的思想是把原则写成可执行的规范，例如：

- 不推荐明显违法或危险内容。
- 不因用户群体身份而降低内容质量。
- 在多样性与相关性之间保持平衡。
- 对商业利益冲突进行透明标记。

在推荐中，原则可以形成一个层级：

```
硬约束：必须满足
  安全、合规、库存、年龄、频控
软约束：尽量优化
  多样性、新颖性、公平性、长期满意度
业务目标：在约束内最大化
  点击、转化、时长、留存、GMV
```text

这个顺序比把所有目标塞进一个线性 reward 更可靠。因为硬约束被少量业务收益抵消，会产生不可接受的行为。

### 6.7 直接偏好优化与 AI 偏好

DPO 不需要显式 reward model，但偏好数据质量仍然决定上限。对 AI evaluator 生成的偏好，必须注意“自蒸馏闭环”：

```
策略 π 生成候选
  ↓
evaluator 根据自己的偏好排序
  ↓
DPO 让 π 更符合 evaluator
  ↓
新策略生成更容易被 evaluator 喜欢的候选
```text

如果 evaluator 没有外部锚点，这个闭环会放大初始偏差。解决方法包括：

1. 固定一套人工校准集。
2. 引入多个异构 evaluator，而不是只用一个模型。
3. 对 evaluator 进行版本冻结，避免训练目标漂移。
4. 记录每个偏好对的置信度和原因码。
5. 监控策略是否只在 evaluator 分数上升、业务指标不升。

### 6.8 成本模型

粗略成本可以拆成：

$$C_{total}=C_{data}+C_{label}+C_{train}+C_{eval}+C_{online}$$

RLHF 通常 $C_{label}$ 高，RLAIF 通常 $C_{eval}$ 高。随着数据规模增加，AI 反馈的边际成本更低，但 evaluator 推理成本可能成为瓶颈。

| 阶段 | RLHF | RLAIF |
| :--- | :--- | :--- |
| 采样 | 人工挑选或标注 | 模型批量判断 |
| 单样本成本 | 高 | 中低 |
| 可扩展性 | 受人力限制 | 受推理吞吐限制 |
| 偏差发现 | 人工审查直观 | 需要校准集 |
| 适合场景 | 复杂价值判断 | 规则明确、规模大 |

### 6.9 推荐系统中的选择建议

可以按以下决策树选择：

```
目标是否涉及安全、伦理或复杂主观判断？
├── 是：先用人工反馈定义标准
│   └── 数据规模扩大后，用 RLAIF 扩展，再人工抽检
└── 否：是否有稳定规则或行为标签？
    ├── 有：规则 + 用户反馈 + RLAIF 混合
    └── 无：先做小规模人工研究，避免盲目自动化
```text

如果候选是商品或视频，AI evaluator 可以辅助判断内容质量和重复度，但购买、留存和真实满意度仍应依赖真实用户反馈。AI 反馈是代理信号，不是业务真相。

### 6.10 评估 RLAIF 是否有效

至少需要四个层面的评估：

| 层面 | 指标 |
| :--- | :--- |
| evaluator | 与人工偏好的一致率、校准误差 |
| reward model | pairwise accuracy、分层 AUC、稳定性 |
| 策略离线 | IPS、SNIPS、反事实风险、覆盖率 |
| 策略线上 | CTR、CVR、留存、负反馈、业务约束 |

一个常见失败模式是 evaluator accuracy 很高，但线上指标下降。原因可能是人工标注任务本身没有覆盖长期价值，也可能是离线偏好对与线上曝光机制不一致。

### 6.11 本节小结

RLHF 更像“用人类价值建立锚点”，RLAIF 更像“用机器反馈扩大规模和覆盖”。推荐系统还需要第三种锚点：真实用户在真实场景中的长期行为。稳健的路线通常是：

```
人工定义原则
  → AI 反馈扩展数据
  → 用户行为校准 reward
  → 小流量在线实验
  → 持续修正 evaluator 和策略
```text

## 7. 长期价值建模

推荐系统最容易优化的是即时点击，最难优化的是用户未来是否还愿意回来。长期价值建模的目标不是把时间窗口无限拉长，而是把当前动作对未来状态和业务结果的影响量化，并控制估计误差。

### 7.1 短期指标为什么会误导

设一次推荐产生点击 $c_t$，用户未来留存为 $l_{t+7}$。如果只优化：

$$J_{short}=\\mathbb{E}[c_t]$$

模型可能偏好标题夸张、内容重复或短期刺激。更完整的目标是：

$$J_{long}=\\mathbb{E}[c_t+\\gamma r_{t+1}+\\gamma^2r_{t+2}+\\ldots]$$

即使点击与留存正相关，也不代表相关系数为 1。原因包括：

1. 点击是低成本行为，留存是高成本结果。
2. 不同用户的点击意图不同。
3. 推荐会改变后续可见内容和用户习惯。
4. 反馈存在延迟和缺失。

### 7.2 用户状态与状态转移

长期价值模型首先要定义状态：

$$s_t=(h_t,c_t,e_t,q_t)$$

其中：

- $h_t$：历史行为序列。
- $c_t$：当前上下文。
- $e_t$：最近曝光和负反馈。
- $q_t$：用户活跃度、疲劳度、兴趣不确定性。

动作 $a_t$ 可以是一个完整推荐列表，而不是单个 item：

$$a_t=[i_{t,1},i_{t,2},\\ldots,i_{t,K}]$$

状态转移由用户行为和环境共同决定：

$$s_{t+1}=F(s_t,a_t,b_t)$$

其中 $b_t$ 是点击、停留、跳过、购买和退出等反馈。

如果状态只保存点击历史，不保存曝光和跳过，模型会把“没有点击”误判成“没有兴趣”。长期价值建模必须同时记录正向与负向接触。

### 7.3 折现因子的选择

折现因子 $gamma$ 体现产品对未来的重视程度：

$$G_t=\\sum_{k=0}^{H-1}\\gamma^k r_{t+k}$$

不同业务可以使用不同的有效视野：

| 业务 | 主要结果 | 建议视野 |
| :--- | :--- | :--- |
| 信息流 | 当前阅读与下一次回访 | 分钟到天 |
| 短视频 | session 深度与次日回访 | session 到 7 天 |
| 电商 | 加购、购买和复购 | 天到 30 天 |
| 音乐 | 连续播放与订阅 | session 到 30 天 |
| 内容社区 | 创作、互动与留存 | 天到数月 |

不要用 $gamma=0.999$ 来“强行表示长期主义”。长期视野越长，回报估计方差通常越高，归因链条也越不可靠。更好的方式是分层建模：短期 reward 负责即时体验，独立的 LTV 头负责较远结果。

### 7.4 多时间尺度价值头

可以让同一个状态编码器输出多个时间尺度的价值：

$$V(s)=[V^{session}(s),V^{day}(s),V^{7d}(s),V^{30d}(s)]$$

```python
class MultiHorizonValue(nn.Module):
    def __init__(self, hidden_dim, horizons=(1, 24, 168, 720)):
        super().__init__()
        self.heads = nn.ModuleList([nn.Linear(hidden_dim, 1)
                                    for _ in horizons])
        self.horizons = horizons

    def forward(self, state_repr):
        return torch.cat([head(state_repr) for head in self.heads], dim=-1)
```text

每个 head 使用对应窗口的标签，例如：

- session head：当前 session 是否继续消费。
- 1d head：次日是否回访。
- 7d head：七日活跃或购买。
- 30d head：长期留存或复购。

联合损失为：

$$L_{value}=\\sum_h w_h L_h(V_h(s),y_h)$$

这里的 $w_h$ 应通过校准和业务价值确定，而不是只看标签数量。

### 7.5 TD 学习与 Monte Carlo 的取舍

Monte Carlo 直接等待轨迹结束：

$$\\hat{V}_{MC}(s_t)=\\sum_{k=0}^{T-t}\\gamma^k r_{t+k}$$

优点是目标无偏，缺点是方差大、反馈延迟高。TD 学习只看一步：

$$y_t^{TD}=r_t+\\gamma V_\\phi(s_{t+1})$$

优点是样本效率高，缺点是目标有偏且会受价值估计误差影响。

n-step return 介于两者之间：

$$G_t^{(n)}=\\sum_{k=0}^{n-1}\\gamma^k r_{t+k}+\\gamma^nV(s_{t+n})$$

| 方法 | 偏差 | 方差 | 反馈速度 | 适合 |
| :--- | :--- | :--- | :--- | :--- |
| MC | 低 | 高 | 慢 | 完整短轨迹 |
| 1-step TD | 高 | 低 | 快 | 高频反馈 |
| n-step | 中 | 中 | 中 | 推荐主流 |
| GAE | 可调 | 可调 | 中 | PPO / actor-critic |

推荐系统中常用 n-step 或 GAE，因为用户轨迹经常被 session 边界截断。

### 7.6 留存作为奖励的归因

“用户七天后回来”不一定完全由某一次推荐造成。若把所有留存奖励都归给最后一次曝光，会引入归因偏差。可使用时间衰减归因：

$$r_t^{retention}=\\sum_{k=1}^{H}\\eta^k I(visit_{t+k})$$

也可把归因分配到整个 session：

$$r_t=\\frac{w_t}{\\sum_jw_j}R_{session},\\quad w_t=attention(s_t,a_t)$$

但注意，attention 权重不天然是因果贡献。它只能作为分配启发式，不能替代随机实验。

### 7.7 因果视角下的长期价值

要回答“如果推荐另一个物品，用户会不会留存”，需要反事实估计。定义动作的潜在结果：

$$Y_t(a)=\\text{用户在时刻 }t\\text{ 采取动作 }a\\text{ 后的长期结果}$$

我们观测到的只有：

$$Y_t=Y_t(A_t)$$

其他动作的结果不可见。IPS、doubly robust 和随机探索都可帮助估计反事实。

Doubly robust 估计器结合 reward model 和 propensity：

$$\\hat{V}_{DR}=\\frac{1}{N}\\sum_t\\left[\\hat{q}(s_t,\\pi)+\\frac{\\pi(a_t|s_t)}{\\pi_b(a_t|s_t)}(r_t-\\hat{q}(s_t,a_t))\\right]$$

它在其中一个模型正确时仍有较好的稳健性，但对日志中的行为概率质量非常敏感。

### 7.8 长期 reward 的稀疏性处理

七日留存标签每天只有一次，直接训练会导致正例稀疏。常见方法：

1. 使用 session 级密集代理信号做预训练。
2. 对长期标签做分层采样，而不是过度复制正例。
3. 使用 survival analysis 预测留存时间。
4. 使用多任务学习共享状态表示。
5. 用 uncertainty head 区分“没有发生”和“尚未观察到”。

生存分析可以输出危险率：

$$h(t|s)=\\lim_{\\Delta t\\to0}\\frac{P(t\\leq T<t+\\Delta t|T\\geq t,s)}{\\Delta t}$$

从而估计生存函数：

$$S(t|s)=\\exp\\left(-\\int_0^t h(\\tau|s)d\\tau\\right)$$

这比把未来某一天简单标成 0/1 更适合处理右删失数据。

### 7.9 用户疲劳与负效用

长期价值下降常常不是因为推荐完全不相关，而是因为频率过高。可以定义疲劳状态：

$$fatigue_t=\\sum_{k=1}^{W}\\rho^k exposure_{t-k}$$

并把疲劳惩罚加入 reward：

$$r_t'=r_t-\\lambda_f\\max(0,fatigue_t-f_0)$$

疲劳特征包括：

- 最近一小时曝光次数。
- 同主题连续曝光长度。
- 用户主动退出次数。
- 快速滑过比例。
- 通知关闭或卸载倾向。

负反馈不是简单的“点击的相反数”。快速滑过、隐藏、举报、关闭通知和卸载，严重程度不同，应分级建模。

### 7.10 长期价值模型的校准

模型预测的长期价值必须做概率校准。常见指标包括：

- Brier score。
- Expected Calibration Error（ECE）。
- 分位桶内实际留存率。
- 各用户群体的校准差异。

```python
def bucket_calibration(pred, label, bins=10):
    edges = torch.linspace(0, 1, bins + 1, device=pred.device)
    rows = []
    for left, right in zip(edges[:-1], edges[1:]):
        mask = (pred >= left) & (pred < right)
        if mask.any():
            rows.append((pred[mask].mean(), label[mask].float().mean(), mask.sum()))
    return rows
```text

未经校准的 LTV 分数不适合直接作为 reward，因为分数的尺度漂移会改变策略更新强度。

### 7.11 长期价值与短期指标的冲突处理

可以采用约束式目标：

$$\\max J_{long}(\\pi),\\quad \\text{s.t. }J_{CTR}(\\pi)\\geq b$$

也可以使用 Pareto 前沿，而不是强行固定一组权重。实际工程中常用分阶段策略：

```
阶段 1：保证 CTR 和合法率不下降
阶段 2：在短期指标约束内提高留存
阶段 3：优化 GMV、LTV 和用户公平性
阶段 4：根据人群差异做个性化权衡
```text

这样可以避免模型为了追求远期指标而破坏基本体验。

### 7.12 长期价值实验设计

实验至少需要覆盖：

| 维度 | 短期观察 | 长期观察 |
| :--- | :--- | :--- |
| 内容质量 | 点击、停留 | 负反馈、次日回访 |
| 电商质量 | 加购、支付 | 退款、复购、GMV |
| 用户体验 | session 深度 | 7/30 日留存 |
| 内容生态 | 曝光分布 | 创作者留存与供给 |

长期实验要避免只在第一天停止。一个实用的序列是：

1. 第一小时监控安全和崩溃。
2. 第一日监控 CTR、负反馈和分布漂移。
3. 第七日监控回访和内容消费质量。
4. 第三十日监控留存、复购和生态指标。

### 7.13 本节小结

长期价值建模不是把一个更远的标签塞进 PPO。它要求：

1. 定义可解释的状态和状态转移。
2. 处理延迟、稀疏和删失反馈。
3. 区分代理指标与最终业务结果。
4. 通过因果和在线实验验证反事实估计。
5. 对短期体验设置底线约束。

## 8. 工业实践

工业级 RL-GR 项目的难点不只在算法，而在数据、服务、训练、评估、上线和回滚之间的闭环。一个能在论文数据集上收敛的策略，未必能在真实流量中安全运行。

### 8.1 端到端系统架构

```
用户请求
  ↓
状态服务：历史、上下文、曝光、约束
  ↓
GR 策略：生成 SID / 物品序列
  ↓
约束解码：合法性、库存、频控、去重
  ↓
召回与重排服务
  ↓
线上反馈埋点
  ↓
日志湖与特征仓
  ↓
离线评估 / Reward Model / RL 训练
  ↓
模型注册、灰度、A/B、监控、回滚
```text

每一个环节都要带上版本信息：

- policy_version。
- reward_version。
- feature_version。
- candidate_version。
- evaluator_version。
- experiment_id。

缺少版本字段时，出现指标变化后很难判断是模型、数据还是策略变更造成的。

### 8.2 日志 schema

推荐日志至少包含：

```
request_id
user_id_hash
session_id
state_snapshot_version
policy_version
candidate_source
item_id / sid
position
propensity
exposure_time
click_time
dwell_time
negative_feedback
conversion
constraint_result
```text

`propensity` 是离线策略评估的重要字段。如果线上只记录最终 item，不记录行为策略的概率，就无法准确计算 IPS 权重。

日志也需要记录未点击曝光。只保存点击事件会丢失负例和曝光分母，最终只能得到点击样本，不能估计 CTR 和偏好。

### 8.3 数据切分与防止泄漏

推荐系统必须按时间切分：

```
训练：第 1-21 天
验证：第 22-24 天
测试：第 25-28 天
线上模拟：第 29-30 天
```text

不能随机打散所有行为，因为同一个用户未来行为会泄漏到训练集。还应注意：

1. 物品元数据的更新时间不能晚于样本时间。
2. 未来的库存和价格不能作为历史特征。
3. 回填的用户标签要带生成时间。
4. reward model 不能看到策略上线后的未来结果。
5. 评估候选必须来自当时真实可见的候选池。

### 8.4 行为策略估计

如果旧系统是确定性 top-k，$pi_b(a|s)$ 可能接近 0 或不可得。解决方案：

- 从线上采样策略保留完整 logits 或 top-k 概率。
- 对旧规则策略拟合 behavior model。
- 使用探索流量获得非零支持。
- 对低支持区域设置保守策略。

行为模型的目标不是预测用户点击，而是预测“旧系统会选择什么”：

$$L_b=-\\sum_t\\log \\pi_b(a_t|s_t)$$

行为模型误差会直接进入 IPS 分母，因此必须报告 propensity calibration。

### 8.5 训练资源规划

RL 训练通常包含以下资源：

| 组件 | 主要资源 | 典型瓶颈 |
| :--- | :--- | :--- |
| 生成采样 | GPU 推理 | token throughput |
| reward model | GPU/CPU | 批量打分 |
| policy 更新 | GPU 显存 | 序列长度与 batch |
| replay/log | 存储与网络 | 读写吞吐 |
| 离线评估 | CPU/GPU | 反事实重放 |
| 线上服务 | CPU/GPU | P99 延迟 |

GRPO 少了 value model，但同一 prompt 需要多次采样。应测量“每个有效训练样本的总 token 成本”，不能只看模型数量。

### 8.6 延迟预算

一个线上请求的延迟可分解为：

$$T_{total}=T_{state}+T_{candidate}+T_{generate}+T_{filter}+T_{rerank}+T_{network}$$

生成式推荐最容易超时的是自回归 decoding。常见优化：

1. 使用有限候选集合上的并行打分。
2. 对 SID 层级做 trie 约束。
3. 缓存用户状态和热门前缀。
4. 对不同用户群使用不同生成长度。
5. 把复杂长期价值模型放到离线或异步链路。

不要把所有 reward model 都放在线上。线上只保留必要的轻量打分和硬约束。

### 8.7 模型发布流程

```
离线训练完成
  ↓
单元测试：token 合法率、shape、数值稳定
  ↓
回放测试：IPS、覆盖率、重复率
  ↓
影子流量：只生成不影响结果
  ↓
1% 灰度：监控安全和 P99
  ↓
5% / 20% / 50% 扩大
  ↓
全量或回滚
```text

每次扩大流量都要有明确的停止条件。不能只写“指标变好就扩大”，还要写“哪些指标变差立即停止”。

### 8.8 监控面板

训练监控：

- policy loss。
- reward mean/std。
- KL divergence。
- entropy。
- clip fraction。
- gradient norm。
- sequence length。
- valid SID ratio。

线上监控：

- CTR、CVR、GMV、时长。
- 7 日和 30 日留存。
- 快速滑过、隐藏、举报。
- 重复曝光率。
- 头部和长尾曝光分布。
- 候选覆盖率。
- P50/P95/P99 latency。
- 超时、空结果、fallback 比例。

监控要按用户、品类、设备、流量来源和新老用户分层。总平均值可能掩盖某个群体的严重退化。

### 8.9 回滚设计

RL 策略必须支持快速回滚：

```python
def choose_policy(request, rollout, fallback):
    if rollout.is_paused():
        return fallback
    if rollout.error_rate() > 0.01:
        rollout.pause()
        return fallback
    if rollout.constraint_violation_rate() > 1e-4:
        rollout.pause()
        return fallback
    return rollout.policy(request)
```text

回滚不应依赖重新部署。推荐把 policy version 放入配置中心，使用原子切换。模型文件、词表、约束图和特征 schema 必须一起版本化。

### 8.10 线上探索的安全边界

探索流量应满足：

- 探索比例有上限。
- 探索候选来自安全过滤后的集合。
- 新物品有最小质量门槛。
- 用户可以快速负反馈。
- 每个实验可单独关闭。

可按用户价值分层设置探索率：

$$\\epsilon(u)=\\epsilon_0+\\lambda\\cdot uncertainty(u)$$

新用户不一定应该拥有最高探索率，因为新用户对错误推荐更敏感。需要综合不确定性、风险和剩余会话长度。

### 8.11 Feature 与 reward 的一致性

线上 reward 使用的事件字段，必须与训练时定义一致。常见错误：

1. 训练用客户端时长，线上用服务端时长。
2. 训练把 30 秒定义为正样本，线上改为 60 秒但未改版本。
3. 训练忽略退款，线上把支付作为终点。
4. 训练按曝光计分，线上按请求计分。
5. 训练按用户聚合，线上按设备聚合。

可以为 reward 定义单独的 contract：

```yaml
reward_version: v3
click:
  event: item_click
  value: 0.5
dwell:
  event: dwell_seconds
  transform: log1p
negative_feedback:
  event: hide_or_report
  value: -1.0
conversion:
  event: paid_order
  delay_window_days: 7
```text

### 8.12 事故演练

至少演练以下故障：

- reward model 输出全部相同。
- policy 生成无效 SID。
- KL 突然爆炸。
- 用户状态服务返回空历史。
- candidate service 延迟超时。
- 日志丢失 propensity。
- 线上流量与训练人群不一致。
- 版本回滚后特征 schema 不兼容。

演练目标不是证明系统不会坏，而是证明坏了能快速发现、止损和恢复。

### 8.13 工业级最小验收标准

```
数据：存在曝光、负反馈和行为概率
模型：合法率、数值稳定、版本可追踪
离线：时间切分，至少一种反事实评估
线上：影子流量和可关闭灰度
安全：硬约束在生成前后都生效
监控：短期、长期、生态、延迟全部分层
回滚：分钟级切回稳定策略
```text

### 8.14 本节小结

工业实践的核心不是“把 PPO 跑起来”，而是让策略在真实反馈、约束和故障条件下可控。对 RL-GR 项目而言，日志字段、策略版本和回滚能力与算法同等重要。

## 9. 性能对比

性能对比不能只给一个 reward 或 Recall@K。生成式推荐的算法会在效果、样本效率、显存、延迟、稳定性和长期业务指标之间做权衡。本节给出可复用的实验框架。

### 9.1 对比对象

建议至少包含以下基线：

1. Popularity：热门物品基线。
2. MF/双塔：传统召回基线。
3. DLRM 或精排模型：监督学习基线。
4. GR-SFT：只用 next-token prediction。
5. Contextual bandit：短期探索基线。
6. DPO：偏好优化基线。
7. PPO：带 value model 的策略优化。
8. GRPO：组内相对奖励的策略优化。

没有简单基线时，很难判断复杂 RL 的增益是否来自模型容量或数据处理。

### 9.2 离线指标

相关性：

$$Recall@K=\\frac{|TopK\\cap GroundTruth|}{|GroundTruth|}$$

$$Precision@K=\\frac{|TopK\\cap GroundTruth|}{K}$$

$$NDCG@K=\\frac{DCG@K}{IDCG@K}$$

多样性：

$$ILD=1-\\frac{2}{K(K-1)}\\sum_{i<j}sim(i,j)$$

新颖性：

$$Novelty@K=-\\frac{1}{K}\\sum_{i\\in TopK}\\log popularity(i)$$

覆盖率：

$$Coverage=\\frac{|\\bigcup_u TopK_u|}{|I|}$$

长期代理：

- 预估次日回访。
- session 延续概率。
- 7 日活跃预测。
- 负反馈概率。

每个指标都应报告均值、标准差和分层结果。

### 9.3 反事实指标

离线策略评估至少报告：

```
IPS value
SNIPS value
Doubly Robust value
Effective Sample Size
weight p50 / p95 / p99
support coverage
```text

有效样本量为：

$$ESS=\\frac{(\\sum_iw_i)^2}{\\sum_iw_i^2}$$

如果 ESS 远小于样本量，说明估计主要由少数高权重样本支撑，结果不稳定。任何离线提升都应附带置信区间或 bootstrap 区间。

### 9.4 训练效率指标

| 指标 | 含义 |
| :--- | :--- |
| tokens/sec | 生成与训练吞吐 |
| samples/sec | 有效样本吞吐 |
| GPU hours | 训练资源消耗 |
| peak memory | 峰值显存 |
| reward gain/GPU hour | 单位资源收益 |
| time-to-target | 达到目标指标耗时 |
| update stability | reward/KL 的震荡程度 |

GRPO 的 value model 成本更低，但 group sampling 会增加 rollout token。公平比较时要记录总生成 token，而不是只记录 optimizer step 数量。

### 9.5 PPO、GRPO、DPO 对比

| 维度 | PPO | GRPO | DPO |
| :--- | :--- | :--- | :--- |
| reward model | 通常需要 | 通常需要 evaluator 或 RM | 不需要显式 RM |
| value model | 需要 | 不需要 | 不需要 |
| 数据 | rollout | 同 prompt 多 rollout | 偏好对 |
| 在线程度 | 偏在线 | 可离线 rollout | 纯离线 |
| 显存 | 高 | 中 | 低 |
| 采样成本 | 中 | 高 | 低 |
| 长期 credit | 较强 | 依赖 group reward | 较弱 |
| 调参复杂度 | 高 | 中高 | 低中 |
| 偏好解释 | reward 可单独分析 | 组内相对 | 对数比隐式 |

不能简单说 GRPO 一定比 PPO 快。若 K 很大，采样成本可能超过 value model 的节省；如果 rollout 已经存在，GRPO 的优势才更明显。

### 9.6 推荐实验矩阵

```
模型：DLRM / GR-SFT / DPO / PPO / GRPO
reward：CTR / 多目标 / 长期代理
数据：短窗口 / 长窗口 / 探索流量
规模：1B / 10B 行为样本
解码：greedy / temperature / constrained
```text

每次只改变一个主要因素。一次同时改模型、reward 和数据，无法判断收益来源。

### 9.7 消融实验

必须做的消融包括：

1. 去掉 KL 约束。
2. 去掉长期 reward。
3. 去掉 novelty reward。
4. 去掉负反馈。
5. 去掉探索熵。
6. 去掉约束解码。
7. 把真实 feedback 换成 evaluator feedback。
8. 把 group size 从 4 改为 8、16。
9. 把 gamma 从 0.9 改为 0.99。
10. 把 reward 权重重新归一化。

如果去掉一个组件后所有指标不变，说明该组件可能是冗余的，也可能没有被正确接入。

### 9.8 统计显著性

在线 CTR 差异不能只看百分比。对于二项指标，可以用 bootstrap 或近似检验获得区间；对于时长和 GMV，通常需要用户级聚合后做 bootstrap。

```python
import numpy as np

def bootstrap_diff(x, y, rounds=2000, seed=0):
    rng = np.random.default_rng(seed)
    diffs = []
    for _ in range(rounds):
        sx = rng.choice(x, size=len(x), replace=True).mean()
        sy = rng.choice(y, size=len(y), replace=True).mean()
        diffs.append(sx - sy)
    return np.quantile(diffs, [0.025, 0.5, 0.975])
```text

统计显著不等于业务显著。还要设置最小可接受提升（MDE）和最小可接受损失。

### 9.9 长期指标的滞后性

短期实验可能在第一天显示提升，但长期指标数周后才显现。应定义早期代理指标：

- 内容质量：二次点击、深度阅读、负反馈。
- 电商质量：退款率、复购意向、收藏到购买漏斗。
- 社区质量：后续发帖、互动质量、创作者回访。

代理指标必须经过历史数据验证。如果代理指标与最终结果相关性不稳定，就不能作为早停条件。

### 9.10 线上吞吐与延迟

生成式策略的性能包括：

$$QPS=\\frac{requests}{second}$$

$$CostPerRequest=\\frac{GPU\\ cost+CPU\\ cost}{requests}$$

延迟应报告：

| 百分位 | 关注点 |
| :--- | :--- |
| P50 | 典型体验 |
| P95 | 大多数长尾请求 |
| P99 | 超时与峰值保护 |
| P99.9 | 极端故障与容量 |

如果 GR 只在 P50 很快而 P99 超时，线上用户体验仍然会恶化。应把空结果、fallback 和超时请求单独统计。

### 9.11 性能-成本前沿

将模型表示为点：

$$point=(quality,latency,cost,risk)$$

若一个方案在质量、延迟、成本和风险上都不差于另一个方案，它才是严格支配方案。更多时候存在 Pareto 前沿：

```
轻量策略：质量略低，延迟低，成本低
PPO：质量高，训练成本高，部署中等
GRPO：训练显存低，rollout 成本高
DPO：训练简单，长期优化能力有限
```text

选择应结合业务约束，而不是追求单一最高分。

### 9.12 常见错误对比

错误一：只比较 Recall@10。生成模型可能通过重复热门物品获得高召回，却损害覆盖和留存。

错误二：PPO 和 GRPO 使用不同 rollout token 数。此时“训练更快”没有可比性。

错误三：把离线 reward 当线上收益。reward model 可能有系统性偏差。

错误四：只报告最好的 checkpoint。应报告训练曲线、最差分层和回滚点。

错误五：忽略过滤器。某模型生成更多无效物品，后处理后看似合法，但真实有效率更低。

### 9.13 推荐报告模板

```
实验名称：
日期与数据窗口：
行为策略版本：
对照模型：
实验模型：
reward 版本：
训练 token：
GPU hours：
P99 latency：

离线：Recall@10 / NDCG@10 / Coverage / ILD / Novelty
反事实：IPS / SNIPS / DR / ESS
线上：CTR / CVR / 时长 / 留存 / GMV
风险：重复率 / 负反馈 / 违规率 / 空结果
分层：新老用户 / 品类 / 设备 / 流量来源
结论：
回滚条件：
```text

### 9.14 本节小结

性能对比的结论应是“在给定成本和风险约束下，哪个方案最适合当前阶段”。通常的工程路径是：

```
SFT 建立强基线
  → DPO 验证偏好数据价值
  → bandit 验证探索价值
  → PPO/GRPO 优化长期与多目标
  → 线上长期指标决定是否全量
```text

## 10. 面试题

本节提供面向推荐、生成式推荐和强化学习岗位的问答框架。回答时先给结论，再给公式或例子，最后说工程 trade-off。不要只背算法缩写。

### 10.1 基础概念题

#### Q1：为什么推荐系统可以看作强化学习问题？

**答**：推荐动作会影响用户接下来看到的内容、行为和状态，反馈也可能跨多个时间步。因此推荐天然具有 state、action、reward、policy 和 transition。若只关心当前点击，可以简化为 contextual bandit；若关心留存、复购或长期满意度，就需要 MDP 或近似 RL。

#### Q2：GR 中 policy 是什么？

**答**：GR 的自回归模型就是 policy。对完整推荐序列 $y$，策略概率为：

$$\\pi_\\theta(y|s)=\\prod_t\\pi_\\theta(y_t|s,y_{<t})$$

如果 SID 是多级 token，单个物品的概率还需要对 token 序列求和或使用特定路径概率。

#### Q3：SFT 和 RL 的目标有什么区别？

**答**：SFT 拟合历史行为，常用 next-token cross-entropy；RL 直接优化采样序列的期望 reward。SFT 依赖已有标签，RL 需要反馈、价值估计和分布控制。SFT 适合建立稳定起点，RL 适合处理长期价值、探索和多目标。

#### Q4：什么时候不应该使用 RL？

**答**：当反馈几乎没有延迟、动作不影响未来状态、数据量不足或 reward 无法可靠定义时，监督学习或 contextual bandit 更简单。上 RL 不是目标，验证业务价值才是目标。

#### Q5：什么是 exposure bias？

**答**：日志只包含被旧策略曝光的物品，用户对未曝光物品的偏好不可见。训练模型会把“没曝光”与“不喜欢”混淆，形成热门物品获得更多曝光的反馈闭环。

#### Q6：IPS 的作用是什么？

**答**：IPS 用目标策略概率与行为策略概率的比值重新加权日志样本：

$$w=\\frac{\\pi(a|s)}{\\pi_b(a|s)}$$

它用于估计新策略的反事实价值，但会在行为概率很小时产生高方差，因此需要截断、归一化、探索支持和置信区间。

#### Q7：on-policy 与 off-policy 有什么区别？

**答**：on-policy 使用当前策略产生的数据，分布匹配但采样成本高；off-policy 使用其他策略或历史日志，样本利用率高但存在分布偏移和重要性采样问题。工业推荐大多是 off-policy，并通过 KL、保守估计或小流量探索降低风险。

#### Q8：Bellman 方程表达什么？

**答**：它把当前价值分解为即时奖励加折现后的下一状态价值：

$$V^\\pi(s)=\\mathbb{E}[r_t+\\gamma V^\\pi(s_{t+1})|s_t=s]$$

它是价值迭代、TD、actor-critic 和 GAE 的基础。

### 10.2 算法对比题

#### Q9：PPO 为什么比 REINFORCE 稳定？

**答**：PPO 使用 advantage 降低方差，并通过 probability ratio clipping 限制策略相对旧策略的更新幅度；通常还加入 reference KL 约束。REINFORCE 直接用完整回报，方差大且容易出现单步更新过大。

#### Q10：PPO 的 clip 机制做了什么？

**答**：定义：

$$r_t(\\theta)=\\frac{\\pi_\\theta(a_t|s_t)}{\\pi_{old}(a_t|s_t)}$$

将 ratio 限制在 $[1-\\epsilon,1+\\epsilon]$，并取未裁剪和裁剪 surrogate 的最小值。它限制过大的策略更新，避免旧数据被快速变成无效数据。

#### Q11：GRPO 与 PPO 的核心差异？

**答**：PPO 通常使用 value model 估计 advantage；GRPO 对同一个 prompt 生成一组样本，使用组内奖励的均值和标准差构造相对 advantage，因此不需要独立 value model。GRPO 节省显存，但增加每个 prompt 的采样成本，并依赖组内奖励差异。

#### Q12：GRPO 的 group size 应如何选择？

**答**：group size 越大，组内相对排序估计通常越稳定，但 rollout 成本线性增加。小规模实验可从 4 或 8 开始，观察 reward 方差、有效 token 成本和最终业务指标，而不是盲目增大 K。

#### Q13：DPO 为什么不需要 reward model？

**答**：KL 正则 RL 目标的最优策略可以写成 reference policy 与 reward 的指数加权形式。反解 reward 后放入 Bradley-Terry 偏好差分，配分函数对同一上下文的两项相互抵消，因此可以直接用 policy/reference 的 log-ratio 优化偏好对。

#### Q14：DPO 相比 PPO 的局限？

**答**：DPO 依赖高质量偏好对，不能直接利用连续 reward 或长轨迹 credit assignment，对在线探索和长期反馈的表达能力较弱。它适合偏好数据已经准备好、需要低成本稳定微调的场景。

#### Q15：value model 的作用是什么？

**答**：value model 估计状态的未来期望回报，用于构造 baseline 和 advantage，降低策略梯度方差。它本身也会产生估计误差和训练不稳定，是 GRPO 尝试移除的主要组件。

#### Q16：GAE 为什么有用？

**答**：GAE 用多步 TD residual 的指数加权估计 advantage：

$$\\hat{A}_t^{GAE(\\gamma,\\lambda)}=\\sum_{l=0}^{\\infty}(\\gamma\\lambda)^l\\delta_{t+l}$$

$\\lambda$ 越大越接近 Monte Carlo，方差更高；越小越接近一步 TD，偏差更高但稳定。

### 10.3 Reward 设计题

#### Q17：如何设计推荐 reward？

**答**：先区分最终目标、过程指标和硬约束。对点击、时长、转化、留存等行为做尺度归一化，再构造可解释的组合；对安全、库存、频控和合规使用硬过滤或约束。最后用离线校准与线上 A/B 验证 reward 是否代表业务结果。

#### Q18：什么是 reward hacking？

**答**：模型找到 reward 函数中的漏洞，提升了被测分数但损害真实目标。例如用短视频刷完播、用标题党刷点击、重复推荐刷回访。解决办法包括多目标 reward、长期指标、KL 约束、规则防线和线上分层监控。

#### Q19：为什么 reward 要归一化？

**答**：点击、停留时长和 GMV 的数值尺度不同。未经归一化时，大尺度信号会支配梯度；归一化还能减少不同时间窗口和人群造成的分布漂移。归一化统计量必须按时间和人群版本化，避免数据泄漏。

#### Q20：点击率高但留存下降，怎么办？

**答**：先检查 reward hacking 和人群分层，再看负反馈、内容质量、重复曝光和用户疲劳。把留存或长期代理加入 reward 只是第一步，还要保留 CTR 底线约束，做足够长的 A/B test，并准备回滚。

#### Q21：如何处理稀疏奖励？

**答**：使用密集代理信号预训练，采用 n-step return、GAE、多任务价值头、分层采样和 survival model。不能简单复制稀疏正例，因为这会改变真实分布并造成过拟合。

#### Q22：正负反馈如何建模？

**答**：将点击、购买、点赞、停留视为不同强度的正反馈，将快速跳过、隐藏、举报、关闭通知和卸载分级建模。负反馈需要与曝光机会绑定，否则“没有点击”可能只是没有看到。

### 10.4 长期价值题

#### Q23：为什么不能只优化 CTR？

**答**：CTR 是即时、低成本反馈，容易被标题党、重复曝光和短期刺激提升。推荐的最终价值往往包含留存、复购、长期满意度和生态质量，因此需要多时间尺度价值和长期实验。

#### Q24：gamma 如何选择？

**答**：根据反馈周期和业务视野选择。短期 session 可用较小 gamma，留存和 LTV 需要更长视野，但 gamma 越大方差和训练难度越高。应通过离线轨迹、稳定性和线上长期指标共同确定，不要只按直觉设置。

#### Q25：长期奖励如何归因到某次推荐？

**答**：可以使用时间衰减、session 分摊、价值模型或反事实估计，但这些方法都是近似。真正的因果归因需要随机探索、实验或可靠的 propensity。attention 权重不能直接当作因果贡献。

#### Q26：长期指标和短期指标冲突怎么办？

**答**：使用约束优化或分阶段优化。先保证安全、合法和即时体验不低于底线，再在约束范围内提高长期价值。不要只把所有指标简单线性加权后上线。

### 10.5 工业实践题

#### Q27：一个 RL-GR 项目最少需要哪些日志字段？

**答**：用户和 session 标识、状态版本、策略版本、曝光物品及位置、行为策略概率、曝光时间、点击、停留、负反馈、转化、候选源和约束结果。尤其是曝光和 propensity，缺少它们很难做可靠的离线反事实评估。

#### Q28：为什么要记录没有点击的曝光？

**答**：未点击曝光是偏好反例和 CTR 分母，也是 DPO 负例构造和 reward model 校准的基础。只记录点击会产生正样本选择偏差。

#### Q29：如何发布 RL 模型？

**答**：先做离线和回放测试，再做影子流量，随后 1% 灰度、逐步扩大。每一步都监控安全、延迟、负反馈、分布和长期代理指标，并支持配置级快速回滚。

#### Q30：线上模型为什么需要 reference policy？

**答**：reference policy 提供稳定行为锚点，KL 惩罚限制 RL 策略偏离 SFT 或旧策略太远，降低 reward hacking、分布外动作和生成坍缩风险。它不是为了让新策略完全不变，而是控制更新半径。

#### Q31：如何定位指标下降是模型问题还是数据问题？

**答**：检查版本和时间线，分别对比输入特征分布、候选分布、reward 分布、策略 KL、解码合法率、线上流量构成和埋点完整性。使用同一 checkpoint 回放不同数据窗口，能帮助隔离模型与数据因素。

#### Q32：P99 延迟超标怎么优化？

**答**：先拆分 state、候选、生成、过滤、重排和网络耗时，再定位长尾。常见手段是缓存状态、限制解码长度、候选集合并行打分、trie 约束、轻量在线模型和异步长期价值计算。不能只优化平均延迟。

### 10.6 设计题

#### Q33：设计一个面向短视频的 RL 推荐系统。

**答题结构**：

```
状态：最近观看序列、停留、跳过、设备、时间、疲劳度
动作：从合法候选中生成下一个视频或列表
即时 reward：有效观看、点赞、关注、分享、负反馈
长期 reward：session 深度、次日回访、7 日留存
约束：年龄、安全、重复、频控、低质内容
训练：SFT → reward model / evaluator → GRPO 或 bandit
评估：CTR、有效观看、留存、负反馈、覆盖、P99
上线：影子 → 1% → 分层灰度 → 快速回滚
```text

关键是说明为什么每个信号进入 reward，以及如何避免短视频长度导致的完播率 hack。

#### Q34：设计一个电商长期价值 reward。

**答题结构**：

1. 点击和加购作为过程信号。
2. 支付作为强正向信号。
3. 退款、取消和低满意度作为延迟负反馈。
4. 复购和长期活跃作为远期信号。
5. 对 GMV 做用户和品类归一化，避免高价商品支配训练。
6. 对库存、价格、合规和频控做硬约束。
7. 用 7 日和 30 日实验验证 reward 是否真正提高业务价值。

#### Q35：设计一个离线 RL 评估方案。

**答题结构**：

```
时间切分日志
  ↓
训练 behavior model / 校准 propensity
  ↓
计算 IPS、SNIPS、DR
  ↓
报告 weight 分布和 ESS
  ↓
按用户、品类、设备分层
  ↓
做 bootstrap 置信区间
  ↓
只挑选稳健候选进入线上影子流量
```text

要主动说明：离线评估不能覆盖行为策略没有支持的动作，最终需要线上小流量实验。

#### Q36：如果 GRPO reward 上升但线上指标下降，你怎么排查？

**答题结构**：

1. 检查 evaluator 或 reward model 是否被策略 hack。
2. 检查离线 reward 与真实用户行为的相关性。
3. 检查 KL、entropy、重复率和词表覆盖率。
4. 检查线上流量与训练人群的分布差异。
5. 检查 reward 版本、日志延迟和标签泄漏。
6. 查看分层指标，定位受损用户群。
7. 回滚模型并构造针对性反例加入训练。

### 10.7 开放题

#### Q37：RL 会不会取代监督学习？

**答**：不会。监督学习提供稳定、低方差的初始化和强基线，RL 处理监督标签难以表达的长期价值、探索和反事实。更现实的范式是 SFT、bandit、RL 和线上实验协同，而不是二选一。

#### Q38：GRPO 是不是 PPO 的全面替代？

**答**：不是。GRPO 去掉 value model，适合组内相对评价稳定、可承受多次 rollout 的场景。若奖励是连续长轨迹、每步 credit 很重要，value model 和 GAE 仍可能更合适。应根据总 token 成本和业务稳定性选择。

#### Q39：RLAIF 是否会让推荐系统失去用户视角？

**答**：如果 AI feedback 没有用户行为校准，就有这种风险。RLAIF 适合扩展规则明确的质量判断，但留存、购买和真实满意度必须用真实用户数据验证。人工校准集、异构 evaluator 和线上实验是必要的锚点。

#### Q40：推荐中的安全应该如何进入 RL？

**答**：安全不能只当一个可被其他 reward 抵消的负项。硬安全条件应在候选过滤、受约束解码和后置审核中保证；RL 只在安全可行域内优化相关性、长期价值和多样性。

#### Q41：如何解释 RL 策略推荐了某个物品？

**答**：提供状态摘要、候选来源、策略概率、reward 各分量、约束结果和 reference 差异。对于生成策略，还要记录 token 或 SID 路径。解释只能说明模型依据，不能把相关性误称为因果。

#### Q42：RL-GR 最大的工程风险是什么？

**答**：不是某个公式写错，而是反馈闭环失控：有偏日志训练策略，策略改变曝光分布，reward model 再把新偏差当成目标，最终指标表面上升但用户和生态受损。版本化日志、反事实评估、灰度和回滚是风险控制的核心。

### 10.8 手撕代码题

#### Q43：实现 discounted return。

```python
def discounted_returns(rewards, gamma):
    out = [0.0] * len(rewards)
    running = 0.0
    for i in range(len(rewards) - 1, -1, -1):
        running = rewards[i] + gamma * running
        out[i] = running
    return out

assert discounted_returns([1.0, 0.0, 1.0], 0.5) == [1.25, 0.5, 1.0]
```text

#### Q44：实现 PPO clipped loss。

```python
def ppo_clipped_loss(new_logp, old_logp, advantage, eps=0.2):
    ratio = (new_logp - old_logp).exp()
    clipped = ratio.clamp(1 - eps, 1 + eps)
    surrogate = torch.minimum(ratio * advantage,
                              clipped * advantage)
    return -surrogate.mean()
```text

需要说明 advantage 应该与 rollout 对齐，并注意 padding token 不应参与 loss。

#### Q45：实现组内相对 advantage。

```python
def group_advantage(rewards, eps=1e-8):
    mean = rewards.mean(dim=-1, keepdim=True)
    std = rewards.std(dim=-1, keepdim=True, unbiased=False)
    return (rewards - mean) / (std + eps)
```text

面试时要补充：如果组内所有 reward 相同，advantage 为 0，训练没有有效方向；需要改进采样、reward 分辨率或组构造。

#### Q46：实现简单的重复曝光惩罚。

```python
def repetition_penalty(history, candidates, window=20):
    recent = set(history[-window:])
    overlap = sum(item in recent for item in candidates)
    return overlap / max(len(candidates), 1)
```text

这个实现是 O(K) 的近似，不能识别语义重复。大规模系统可使用类别、embedding 或主题级去重，但应先验证简单版本是否足够。

### 10.9 快速判断题

#### Q47：$gamma=0$ 时 RL 等价于什么？

**答**：目标只看即时 reward，接近 contextual bandit；并不严格等同于所有 SFT，因为动作采样、探索和 reward 定义仍可能不同。

#### Q48：KL 一直升高说明什么？

**答**：策略正在偏离 reference，可能是 reward 权重过大、KL 系数过小、学习率过高、旧 log probability 错位或 reward hacking。需要结合 entropy、合法率和线上指标判断。

#### Q49：熵下降到接近零说明什么？

**答**：策略趋于确定性，可能已经坍缩到少数热门动作。若探索不足，应检查 entropy coefficient、候选覆盖和 top-1 频率；但低熵也可能是某些确定性业务场景的合理结果。

#### Q50：DPO 的负例能否随便选一个未曝光物品？

**答**：不应随便选。未曝光物品没有真实负反馈，可能只是没被旧策略展示。优先使用同时曝光但未点击或被明确负反馈的物品。

#### Q51：线上 A/B 显著提升 CTR，是否可以直接全量？

**答**：不能。还要检查负反馈、长期留存、覆盖、多样性、生态和延迟。如果任何硬约束恶化，应暂停扩大流量。

### 10.10 面试总结模板

回答 RL-GR 题目可以使用以下五步：

```
第一步：定义状态、动作、即时与长期奖励。
第二步：判断是 bandit 还是完整 RL。
第三步：说明数据是 on-policy 还是 off-policy。
第四步：给出算法选择和稳定性约束。
第五步：给出离线、线上、长期和回滚指标。
```text

最后要主动说明 trade-off：

- 效果 vs 延迟。
- 探索 vs 用户体验。
- 短期指标 vs 长期价值。
- RLAIF 规模 vs evaluator 偏差。
- GRPO 显存 vs rollout 成本。
- 离线效率 vs 反事实可靠性。

### 10.11 全章最终复习

```
GR = 生成式策略 + 受约束动作空间 + 用户反馈闭环
RL = 让策略优化长期回报，而不是只复现历史
RLHF = 人类提供偏好锚点
RLAIF = AI 提供可扩展反馈
PPO = clip + advantage + reference KL
GRPO = group-relative advantage + 无 value model
DPO = 从偏好对直接优化隐式 reward
长期价值 = 多时间尺度 + 延迟反馈 + 因果校准
工业实践 = 日志、版本、监控、灰度、回滚
性能对比 = 效果、成本、延迟、风险的 Pareto 权衡
```text

### 10.12 本节小结

面试中最有价值的回答不是背出“GRPO 省显存”或“PPO 是 on-policy”，而是能解释：数据从哪里来，reward 是否可信，策略如何避免分布偏移，长期指标如何归因，线上出了问题如何止损。只要能把算法、数据和业务闭环连起来，就真正理解了 RL 在 GR 中的角色。
