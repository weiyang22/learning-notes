### 8.1 分布漂移 (Distribution Shift)——为什么 GR 模型会"过期"?

**关键公式**:PSI（Population Stability Index）量化特征分布漂移程度：

$$\text{PSI} = \sum_{i=1}^{K} (P_i^{\text{train}} - P_i^{\text{test}}) \cdot \ln\!\frac{P_i^{\text{train}}}{P_i^{\text{test}}}$$

其中 $P_i^{\text{train}}, P_i^{\text{test}}$ 是特征在第 $i$ 个桶的频率。本质上 PSI = $D_{\text{KL}}(P_{\text{train}} \| P_{\text{test}}) + D_{\text{KL}}(P_{\text{test}} \| P_{\text{train}})$（对称 KL 散度）。

| PSI 值 | 含义 | 建议操作 |
| :--- | :--- | :--- |
| $< 0.1$ | 分布稳定 | 不用干预 |
| $0.1 \sim 0.25$ | 轻微漂移 | 监控，考虑重训 |
| $> 0.25$ | 严重漂移 | 立即重训或告警 |

**文字$\cdot$公式$\cdot$代码 三位一体块**

PSI 成为工业标准,关键在于它一次性解决了三个问题。它本质就是对称 KL 散度,把训练集分布和在线分布两个方向的偏差都计入,所以对称;作为标量,它能跨特征直接比较,运维只要看一个数字;阈值又经过多年实战验证,工程师形成肌肉记忆。小于 0.1 几乎不需干预,模型对线上数据仍有判别力;0.1 到 0.25 之间需要监控并准备重训;大于 0.25 必须立即重训,此时特征的预测能力已经显著退化。实操中通常看 PSI 的 95 分位数,而不是被一两个稳定特征稀释后的均值,因为个别长期不变的特征(比如设备型号)容易把整体均值拉低。

$$\text{PSI} = D_{\text{KL}}(P_{\text{train}} \| P_{\text{test}}) + D_{\text{KL}}(P_{\text{test}} \| P_{\text{train}}), \quad D_{\text{KL}}(P \| Q) = \sum_i P_i \ln\frac{P_i}{Q_i}$$

```python
import numpy as np

def psi(expected, actual, bins=10):
    """PSI = 对称 KL 散度,衡量两分布的偏差"""
    expected = np.array(expected, dtype=float)
    actual = np.array(actual, dtype=float)
    # 用 expected 的分位数划分桶
    breakpoints = np.unique(np.quantile(expected, np.linspace(0, 1, bins + 1)))
    e = np.histogram(expected, breakpoints)[0] + 1e-6
    a = np.histogram(actual, breakpoints)[0] + 1e-6
    return np.sum((a / a.sum() - e / e.sum()) * np.log((a / a.sum()) / (e / e.sum())))

def psi_action(v):
    if v < 0.1:  return "稳定,无需干预"
    if v < 0.25: return "轻微漂移,准备重训"
    return "严重漂移,立即重训"
```

#### 8.1.1 分布漂移的 3 个层次

层次 1:  特征分布漂移 (Feature Drift)
  含义:  $P(X)$ 变了
  例子:  新品类涌现 (e.g.,  AIGC 内容,  元宇宙商品)
        用户设备分布变化 (iPhone 15 占比从 5% → 30%)
        价格分布变化 (促销季)
  影响:  模型对"新特征值"  无从下手
  检测:  PSI (Population Stability Index)
         $\text{PSI} > 0.25$  严重漂移

层次 2:  条件分布漂移 (Concept Drift)
  含义:  $P(Y \mid X)$ 变了
  例子:  用户的"时尚品味"  在 1 年内发生变化
        突发新闻改变了用户的关注点
  影响:  模型学到的"输入→输出" 映射过时
  检测:  监控 $P(Y \mid X)$ 分布
  解法:  滑动窗口训练,  增量学习

层次 3:  标签漂移 (Label Drift)
  含义:  $P(Y)$ 变了
  例子:  整体 CTR 上升 (推荐系统越好,  点击越多)
        季节性 (圣诞季购买率高于平时)
  影响:  校准层 (calibration) 失准
  检测:  监控 label 分布
  解法:  重新校准 (Platt scaling, isotonic regression)

#### 8.1.2 GR 模型的"半衰期"

经验数据 (Meta 2024):
  - HSTU GR 模型部署 1 周后,  $\text{Recall}@10$ 衰减 5-8%
  - 1 个月后,  衰减 15-25%
  - 3 个月后,  衰减 30-50%

衰减原因 (按贡献度排序):
  1.  物品池变化 (新品上架,  长尾物品下架):  40%
  2.  用户兴趣漂移:  30%
  3.  季节性:  15%
  4.  系统环境变化 (UI, 排序规则):  10%
  5.  其他:  5%

应对策略:
  - 每日增量更新 (而不是每月重训)
  - 周期性重训 (每周一次)
  - 在线 A/B test 监控衰减
  - 设定告警阈值 ($\text{Recall}$ 衰减 > 5% 触发重训)

### 8.2 在线学习 (Online Learning)——让模型"持续进化"

#### 8.2.1 在线学习 vs 离线学习

```text
离线学习 (Offline):
  Step 1:  收集数据 (几周到几个月)
  Step 2:  训练模型
  Step 3:  部署
  Step 4:  等待数据再次积累
  Step 5:  重复 1-4

在线学习 (Online):
  Step 1:  部署模型
  Step 2:  实时收集用户反馈
  Step 3:  实时更新模型 (小时级或分钟级)
  Step 4:  持续优化
  Step 5:  持续监控和滚动更新
```

#### 8.2.2 GR 的在线学习挑战

```text
挑战 1:  训练稳定性
  在线数据有噪声, 一次更新可能让模型"学偏"
  例子:  一个小时内用户大多点了一类物品, 模型过度学习
  解法:  小学习率 + 梯度裁剪 + 多步平均

挑战 2:  灾难性遗忘
  在线更新时, 新数据可能"覆盖" 旧知识
  例子:  模型学了"年轻人喜欢 A"  → 学了"中年人喜欢 B"  → 忘记年轻人偏好
  解法:
    - 经验回放 (Experience Replay)
    - 知识蒸馏 (Knowledge Distillation)
    - EWC (Elastic Weight Consolidation)
    - 渐进式学习 (Progressive Learning)

挑战 3:  资源消耗
  GR 模型大 (几 GB 到几十 GB), 实时更新代价高
  例子:  每 10 分钟用新数据 fine-tune 一次, 每次需要 30 分钟
  解法:
    - LoRA 在线微调 (只更新少量参数)
    - 在线蒸馏 (小模型实时更新,  大模型周期重训)
    - 异步训练 (训练和服务解耦)
```

#### 8.2.3 经验回放 (Experience Replay) 详解

在线学习更新公式（带经验回放的混合损失）:

$$\mathcal{L}_{\text{online}} = \lambda_{\text{new}} \cdot \mathcal{L}(\mathcal{D}_{\text{new}}) + \lambda_{\text{replay}} \cdot \mathcal{L}(\mathcal{D}_{\text{buffer}})$$

其中 $\mathcal{D}_{\text{buffer}}$ 是历史数据回放池（通常保留最近 $N$ 条，FIFO 更新）。

```text
思想:  在线学习时, 不只用最新数据, 也用历史数据
  缓解灾难性遗忘, 提升训练稳定性

实现:
  Replay Buffer = 循环队列, 存最近 N 步的数据
  训练 batch = 新数据 (60%) + 回放数据 (40%)

GR 场景:
  Replay Buffer 存 (用户历史, 下一个物品, 反馈)
  大小: 100 万 ~ 1 亿条
  更新策略:  FIFO (先进先出)

代码:
  from collections import deque
  import random

  buffer = deque(maxlen=1_000_000)  # 100 万条

  for user_event in stream:
      buffer.append(user_event)

      if len(buffer) >= batch_size * 10:  # 积累够数据
          # 60% 最新, 40% 随机回放
          new_data = list(buffer)[-int(batch_size * 0.6):]
          old_data = random.sample(list(buffer)[:int(-batch_size * 0.6)],
                                    int(batch_size * 0.4))
          batch = new_data + old_data

          loss = train_step(model, batch)
          update_model(model, loss)
```

**文字$\cdot$公式$\cdot$代码 三位一体块**

经验回放的核心价值,是打破数据时序相关性。在线流的样本高度自相关,连续两个请求几乎来自同一用户,直接喂模型会让梯度震荡,Adam 的二阶矩估计也会失真。把样本塞进 buffer 再随机采样,等于做了隐式的 i.i.d. 修正。配比上,工业经验是新数据 60% 加历史 40%,这个 6:4 来自朴素权衡:新数据多学得快但容易漂,历史多学得稳但响应慢。Priority Replay 看似更优,实则引入幸存者偏差,高分样本反复回放,模型对边界样本的判断力下降,所以大厂很少用。

$$\mathcal{L}_{\text{online}} = 0.6 \cdot \mathcal{L}(\mathcal{D}_{\text{new}}) + 0.4 \cdot \mathcal{L}(\mathcal{D}_{\text{replay}})$$

```python
from collections import deque
import random

class ReplayBuffer:
    def __init__(self, capacity=1_000_000, new_ratio=0.6):
        self.buf = deque(maxlen=capacity)
        self.new_ratio = new_ratio

    def push(self, sample):
        self.buf.append(sample)

    def sample(self, batch_size):
        n_new = int(batch_size * self.new_ratio)
        n_old = batch_size - n_new
        items = list(self.buf)
        # 最新 n_new 条 + 随机 n_old 条
        new_batch = items[-n_new:]
        old_pool = items[:-n_new] if n_new < len(items) else items
        old_batch = random.sample(old_pool, min(n_old, len(old_pool)))
        return new_batch + old_batch
```

### 8.3 持续学习 (Continual Learning)——GR 的"长期记忆"

#### 8.3.1 持续学习 vs 在线学习的区别

```text
在线学习:  关注"实时反馈",  数据分布假设不变
持续学习:  关注"任务变化",  数据分布可能改变

举例:
  在线学习场景:  电商推荐 7×24 持续运行
  持续学习场景:  从"双 11"  到 "双 12"  到 "年货节",  任务/季节在变

GR 中的持续学习:
  - 加入新品类 (e.g.,  直播带货加入推荐)
  - 跨域迁移 (从国内到海外)
  - 新任务 (从 CTR 到 GMV)
```

#### 8.3.2 持续学习的 3 大策略

策略 1:  经验回放 (Replay-based)
  保留历史数据, 和新数据混合训练
  优点:  简单, 有效
  缺点:  显存大, 隐私问题

策略 2:  正则化 (Regularization-based)
  限制重要参数的更新幅度
  代表:  EWC (Elastic Weight Consolidation)
        $L_{\text{new}} = L_{\text{task}} + \lambda \cdot \sum_i F_i \cdot (\theta_i - \theta_i^{\text{old}})^2$
        $F_i$ = Fisher 信息矩阵的第 $i$ 个对角元素
  优点:  无需保留数据
  缺点:  Fisher 矩阵计算昂贵

策略 3:  架构扩展 (Architecture-based)
  为新任务分配新参数
  代表:  ProgressiveNet, MoE (Mixture of Experts)
  优点:  不遗忘
  缺点:  参数量持续增长

#### 8.3.3 GR 的 EWC 实现

**EWC 公式**（Kirkpatrick et al. 2017）：

$$\mathcal{L}_{\text{EWC}} = \mathcal{L}_{\text{new}} + \frac{\lambda}{2} \sum_i F_i \cdot (\theta_i - \theta_i^*)^2$$

其中 $F_i$ 是 Fisher 信息矩阵对角元素，$\theta_i^*$ 是旧任务训练后的参数值。直觉：$F_i$ 大 → 参数对旧任务重要 → 不允许大幅偏移；$F_i$ 小 → 参数不重要 → 自由更新。

Fisher 信息矩阵对角近似：

$$F_i \approx \mathbb{E}_{\mathcal{D}_{\text{old}}}\!\left[\left(\frac{\partial \log p(y|x,\theta)}{\partial \theta_i}\right)^2\right] \approx \frac{1}{N} \sum_{n=1}^N \left(\frac{\partial \mathcal{L}_n}{\partial \theta_i}\right)^2$$

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class EWCLoss:
    """
    Elastic Weight Consolidation:  保护重要参数不被大幅修改
    """
    def __init__(self, model, ewc_lambda=1000):
        self.model = model
        self.ewc_lambda = ewc_lambda
        self.fisher = {}  # Fisher 信息矩阵的对角
        self.old_params = {}  # 旧任务的参数

    def compute_fisher(self, dataloader, num_batches=100):
        """计算 Fisher 信息矩阵 (重要参数的"权重")"""
        self.model.eval()
        fisher = {n: torch.zeros_like(p) for n, p in self.model.named_parameters() if p.requires_grad}

        for i, batch in enumerate(dataloader):
            if i >= num_batches:
                break
            self.model.zero_grad()
            loss = compute_loss(self.model, batch)  # 用户自定义
            loss.backward()
            for n, p in self.model.named_parameters():
                if p.grad is not None:
                    fisher[n] += p.grad.pow(2)

        # 平均
        for n in fisher:
            fisher[n] /= num_batches

        return fisher

    def register_old_task(self, dataloader):
        """注册旧任务, 保存 Fisher 和参数"""
        self.fisher = self.compute_fisher(dataloader)
        self.old_params = {n: p.detach().clone() for n, p in self.model.named_parameters() if p.requires_grad}

    def penalty(self):
        """EWC 惩罚项"""
        loss = 0
        for n, p in self.model.named_parameters():
            if n in self.fisher:
                loss += (self.fisher[n] * (p - self.old_params[n]).pow(2)).sum()
        return self.ewc_lambda * loss
```

**文字$\cdot$公式$\cdot$代码 三位一体块**

EWC 的核心洞察,是参数对旧任务的贡献并不平等。一个训好的 GR 模型有几十亿参数,有些 attention head 对老任务至关重要,有些 output projection 的偏置只是辅助。如果新任务来了之后一视同仁地更新,1% 的关键参数被改 10% 就能让老任务崩盘。EWC 用 Fisher 信息矩阵的对角来量化每个参数的重要性,数值大的绑死,数值小的自由更新。$\lambda$ 要选得偏大(典型 100 到 10000),因为二次惩罚在小偏移下梯度太小,需要放大才能压住更新幅度;$\lambda$ 太小,模型还是会把老知识覆盖掉。

$$F_i = \mathbb{E}_{x \sim \mathcal{D}_{\text{old}}}\!\left[\left(\frac{\partial \log p_\theta(y|x)}{\partial \theta_i}\right)^2\right] \approx \text{一次反向传播} \cdot N$$

```python
def ewc_penalty(model, fisher, old_params, lam=1000):
    """EWC 二次惩罚:F_i 大 → 参数偏移代价大"""
    loss = 0.0
    for n, p in model.named_parameters():
        if n in fisher:
            loss += (fisher[n] * (p - old_params[n]) ** 2).sum()
    return 0.5 * lam * loss
```

### 8.4 长期价值 (Long-term Value, LTV) 建模

#### 8.4.1 为什么 LTV 重要?

```text
短期优化 (只优化点击):
  推荐"标题党"  →  CTR 涨 5%  →  短期指标变好
  用户点开后悔 →  长期留存降 10%  →  长期 LTV 受损

长期优化 (优化 30 天累计价值):
  推荐"高质量"  →  CTR 短期不变  →  短期指标不涨
  用户满意 →  30 天留存涨 15%  →  长期 LTV 大涨

工业界共识:
  长期价值是推荐系统的"北极星指标"
  但短期价值是"可衡量的现实"
  → 需要在两者间平衡
```

#### 8.4.2 LTV 建模的三大挑战

```text
挑战 1:  反馈延迟
  用户点击了 → 30 天后是否再次活跃 → 才能知道 LTV
  但 30 天太长,  模型可能等不到
  解法:
    - 短期代理指标:  次日留存,  7 日留存
    - 早期预测:  用 ML 模型预测"30 日 LTV"  从前 7 日行为
    - 多任务学习:  主任务 = 点击,  辅任务 = 7 日留存

挑战 2:  Credit Assignment
  30 天内有 100 次推荐, 哪次推荐贡献了留存?
  解法:
    - 衰减加权:  越近的推荐贡献越大
    - Shapley value:  公平分配贡献
    - 反事实推理:  Counterfactual

挑战 3:  数据稀疏
  90% 用户在 30 天内不活跃 (流失)
  LTV 标签大量缺失
  解法:
    - 多任务学习 (用 7 日留存代理)
    - 半监督学习
    - 主动学习 (重点标注活跃用户)
```

#### 8.4.3 长期价值的 RL 建模

核心思想：用 RL 优化折现累计奖励（LTV 的形式化定义）:

$$G_t = \sum_{k=0}^{\infty} \gamma^k r_{t+k}, \quad \gamma \in [0.95, 0.99]$$

多目标奖励加权（工业界典型配置）:

$$r_t = w_1 \cdot \mathbf{1}[\text{click}] + w_2 \cdot \mathbf{1}[\text{retain}_{1d}] + w_3 \cdot \mathbf{1}[\text{retain}_{7d}] + w_4 \cdot \mathbf{1}[\text{retain}_{30d}]$$

```text
在 GR 中的实现:
  1.  定义奖励:  r = 0.1·点击 + 0.5·次日留存 + 1.0·7 日留存 + 2.0·30 日留存
  2.  RL 算法:  PPO / GRPO
  3.  训练:  用历史 (用户, 序列, 反馈) 数据, 训练 RL 策略

  # 伪代码
  for trajectory in user_30day_history:
      states = extract_states(trajectory)  # 用户每步的状态
      actions = trajectory['recommendations']  # 每步推荐的物品
      rewards = compute_rewards(trajectory)  # 每步的奖励

      # RL 训练
      loss = ppo_loss(policy, states, actions, rewards, gamma=0.99)

```

**文字$\cdot$公式$\cdot$代码 三位一体块**

LTV 建模的难,难在奖励的极端稀疏和延迟。一次推荐,用户可能在 30 天后才通过复购或留存体现价值,而这 30 天里他已经接受了上千次推荐,究竟是哪一次贡献了留存,这就是 credit assignment 难题。工程上不可能等 30 天再训练,只能用代理奖励:点击(秒级)、次日留存(1 天)、7 日留存(7 天)、30 日留存(30 天)。$\gamma$ 的取值落在 0.95 到 0.99 的甜区,小于 0.9 模型只看眼前变成 CTR 机器,大于 0.99 训练极不稳定(1/(1-$\gamma$) 是有效视野,99 对应 100 步)。工业经验是推荐和信息流取 0.99,短视频取 0.95,因为内容消耗更快。

$$r_t = 0.1 \cdot \mathbb{1}[\text{click}] + 0.5 \cdot \mathbb{1}[\text{retain}_{1d}] + 1.0 \cdot \mathbb{1}[\text{retain}_{7d}] + 2.0 \cdot \mathbb{1}[\text{retain}_{30d}]$$

```python
REWARD_W = {"click": 0.1, "retain_1d": 0.5,
            "retain_7d": 1.0, "retain_30d": 2.0}

def shape_reward(event):
    """多源反馈 → 单一标量 reward"""
    r = 0.0
    if event.get("click"):      r += REWARD_W["click"]
    if event.get("retain_1d"):  r += REWARD_W["retain_1d"]
    if event.get("retain_7d"):  r += REWARD_W["retain_7d"]
    if event.get("retain_30d"): r += REWARD_W["retain_30d"]
    return r
```

### 8.5 在线评估 (Online Evaluation)——Interleaving vs A/B 测试

#### 8.5.1 A/B 测试的局限

```text
A/B 测试:
  用户分两组:
    A 组 (5%):  使用老模型
    B 组 (5%):  使用新模型
  监控:  CTR,  时长,  GMV

问题:
  1.  流量分割,  统计功效低
      5% × 5% = 0.25% 用户看到两个模型
      需要 2-4 周才能达到 95% 统计功效
  2.  浪费 5% 流量给老模型
  3.  难于做"快速迭代"
      每次发版要等 2 周,  1 个月只能发 2 次

大公司痛点:
  - 一个新策略想快速验证
  - A/B 流量紧张
  - 多个团队同时在做实验
```

A/B 测试的统计显著性（双样本 z 检验）:

$$z = \frac{\bar{x}_B - \bar{x}_A}{\sqrt{\frac{s_A^2}{n_A} + \frac{s_B^2}{n_B}}} \quad \text{(需要 } n_A, n_B > 1000 \text{ 才有足够功效)}$$

所需样本量(功效 80%, 显著性 $\alpha=0.05$, 检测效应大小 $\delta$):

$$n \approx \frac{2\sigma^2(z_{1-\alpha/2} + z_{1-\beta})^2}{\delta^2} \approx \frac{16\sigma^2}{\delta^2}$$

$\delta = 0.001$(1 个千分点 CTR 提升)时，通常需要数百万用户天才能检测出来。

#### 8.5.2 Interleaving 的优势

Interleaving 的 win rate 统计量（比 A/B 功效高 10-100 倍的原因）:

$$W = \frac{N_{\text{new wins}}}{N_{\text{new wins}} + N_{\text{old wins}}}, \quad H_0: W = 0.5 \quad \text{(二项检验)}$$

由于每个用户同时接受两个模型，个体内方差被消除，检验功效大幅提升。

```text
Interleaving (交错实验):
  同一组用户, 看到两个模型的混合结果
  例:  用户请求 → 老模型推荐 5 个 + 新模型推荐 5 个 → 合并 10 个
      但物品的顺序随机, 用户看不出哪个来自哪个模型

优势:
  1.  统计功效高 10-100 倍
     因为每个用户都是"实验对象"
  2.  流量利用率 100%
     不需要分流量
  3.  速度快 5-10 倍
     1-2 天就能得到结论
  4.  适合快速迭代

实现:
  user → fetch_old_results() + fetch_new_results() → interleave() → show
  user_clicks → attribution(哪个模型推荐的?)

  attribution 规则:
    - 用户点的是老模型推荐的物品 → 记老模型一次"胜出"
    - 用户点的是新模型推荐的物品 → 记新模型一次"胜出"
    - 用户点的是两者共同的物品 → 平局
```

**文字$\cdot$公式$\cdot$代码 三位一体块**

Interleaving 灵敏度比 A/B 高 10 到 100 倍,关键在用户内方差被消除。A/B 测试把用户切成两组,他们的活跃时段、设备、兴趣都不一样,这些个体差异混在效应估计里,样本要大才能压住。Interleaving 让同一用户同时看到两个模型的结果,这个人就是自己的对照组,个体差异自动抵消。工程上 Interleaving 流量一般只占 1% 到 5%,不需要 5%$\times$ 5% 的双份流量,归因(attribution)是核心,点中的物品属于哪个模型要记录清楚。决策上,Interleaving 适合快速迭代(每两天试一个新点子),A/B 适合最终决策(灰度 5%$\times$ 5%,跑 2 到 4 周看长期指标)。

$$W = \frac{N_{\text{new}}}{N_{\text{new}} + N_{\text{old}}}, \quad \text{Var}(W)_{\text{Interleaving}} \ll \text{Var}(W)_{\text{A/B}}$$

```python
def team_draft(old_list, new_list, k=10):
    """Team Draft 交错:两队轮流选秀,互不重复"""
    result, attr = [], []
    i = j = turn = 0
    while len(result) < k and (i < len(old_list) or j < len(new_list)):
        src = 'old' if turn == 0 else 'new'
        lst, idx = (old_list, i) if src == 'old' else (new_list, j)
        if idx < len(lst) and lst[idx] not in result:
            result.append(lst[idx])
            attr.append(src)
        if src == 'old': i += 1
        else: j += 1
        turn ^= 1
    return result, attr

# 实验方法选择
# 快速迭代 / 中等改动  →  Interleaving (1~2 天, 1% 流量)
# 重大决策 / 长期指标  →  A/B Test   (2~4 周, 5%×5% 流量)
```

```python
import random

def interleaving_recommend(user_id, old_model, new_model, top_k=10):
    """
    Interleaving 推荐:  同一用户同时被老模型和新模型服务
    返回混合后的推荐列表 + 归因信息
    """
    # 1. 两个模型各推荐 top_k * 2 个
    old_results = old_model.recommend(user_id, top_k=top_k * 2)
    new_results = new_model.recommend(user_id, top_k=top_k * 2)

    # 2. 交错合并 (Team Draft 算法)
    interleaved = []
    attribution = []  # 记录每个物品的来源

    # 模拟"两队选秀" 的过程
    i, j = 0, 0
    turn = 0  # 0 表示老模型先选, 1 表示新模型先选
    while len(interleaved) < top_k:
        if turn == 0 and i < len(old_results):
            item = old_results[i]
            if item not in interleaved:
                interleaved.append(item)
                attribution.append('old')
            i += 1
        elif turn == 1 and j < len(new_results):
            item = new_results[j]
            if item not in interleaved:
                interleaved.append(item)
                attribution.append('new')
            j += 1
        turn = 1 - turn  # 切换
```

## 8.9 分布漂移检测进阶——PSI 之外的方法学

### 8.9.1 为什么 PSI 不够用?

PSI 解决的只是"两批样本的边缘分布差多少",但工业线上至少有三类问题它回答不了。

第一,**单变量 PSI 是滞后指标**。阈值 0.1 / 0.25 是经验值,在告警触发时分布往往已经恶化了一到两周,因为 PSI 用的桶是训练集分位数,等线上分位数大幅偏移时累计偏差才会超过阈值。要做"漂移正在发生"的实时捕捉,需要序列式方法。

第二,**PSI 抓不到"形状变化"**。两个分布均值一致、方差不同,PSI 可能很低,但模型判别能力已经改变(比如用户活跃度方差扩大,意味着极端值变多)。Kolmogorov-Smirnov(KS)检验对任意分布形状变化都敏感。

第三,**PSI 难以定位"何时开始漂"**。PSI 是累计量,只能告诉你"今天和训练集差多少",不能告诉你"从哪天开始差"。CUSUM 和 Page-Hinkley 给出的是漂移的起止时间点,直接对接自动重训流水线。

### 8.9.2 四种漂移检测方法对比

| 方法 | 检测对象 | 延迟 | 计算量 | 适合场景 | 工业采用率 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| PSI | 边缘分布 | 1-2 周 | O(N) | 日级离线巡检 | 极高 |
| KS 检验 | 分布形状 | 同 PSI | O(N log N) | 离线诊断 | 中 |
| CUSUM | 均值偏移 | 分钟-小时 | O(1) 增量 | 实时告警 | 高 |
| Page-Hinkley | 同 CUSUM | 分钟-小时 | O(1) 增量 | 在线流式 | 中 |
| ADWIN | 自适应窗口 | 实时 | O(log W) | 概念漂移 | 中 |

#### CUSUM(Cumulative Sum)原理

CUSUM 维护一个累计偏差 $S_t$,目标是在均值发生 $\delta$ 量级偏移时,尽快让 $S_t$ 突破阈值 $h$。

$$S_t = \max(0, S_{t-1} + (x_t - \mu_0 - \delta/2))$$

其中 $\mu_0$ 是参考均值,$\delta$ 是想要检测的最小偏移幅度, $h$ 是告警阈值。当 $S_t > h$ 时,认为漂移发生,把 $S_t$ 归零继续监控。关键参数是 $h$ 和 $\delta$:$h$ 小则灵敏但误报多,$h$ 大则迟钝但稳;$\delta$ 是"工程容忍度",通常设为历史标准差的 0.5 到 1 倍。

#### Page-Hinkley 原理

Page-Hinkley 是 CUSUM 的方差归一化版本,适合监控方差随时间变化的特征。

$$m_T = \sum_{t=1}^{T} (x_t - \mu_0 - \delta), \quad s_T^2 = \sum_{t=1}^{T} (x_t - \mu_0)^2$$

$$\text{PH}_T = m_T - \lambda \cdot s_T$$

当 $\text{PH}_T$ 超过阈值 $h$ 时告警。$\lambda$ 控制对突变的敏感度。

#### KS 检验原理

KS 检验比较两个经验累积分布函数 $F_n(x)$ 和 $G_m(x)$ 的最大垂直距离:

$$D_{n,m} = \sup_x |F_n(x) - G_m(x)|$$

零假设下 $D_{n,m}$ 的临界值约为 $1.36 \sqrt{(n+m)/(nm)}$,超过即拒绝原假设。KS 的好处是分布无关(无参数),代价是必须存全量样本(或用分位数近似)。

#### ADWIN(Adaptive Windowing)原理

ADWIN 维护一个可变长度的窗口 $W$,在每个新样本到达时检测窗口内是否存在"前后两段分布不同"。它自动选择窗口长度,适合"漂移强度随时变化"的场景。复杂度 $O(\log W)$,常数较大,在亿级特征上需要采样。

### 8.9.3 工业级漂移检测 Pipeline

```text
   训练数据 ────→ │   PSI 巡检 │  (每日, 全特征, 离线)
                  └─────┬──────┘
                        │ 触发 PSI > 0.1 的特征
                        ↓
                  ┌────────────┐

                  └─────┬──────┘
                        │ 触发告警
                        ↓
                  ┌────────────┐

                  └─────┬──────┘
```

### 8.9.4 文字·公式·代码 三位一体块

PSI 的滞后在工程上要靠多方法堆叠来弥补。CUSUM 和 Page-Hinkley 是流式方法,只更新一个标量,常数级复杂度,适合挂在线上做秒级告警;PSI 和 KS 是离线方法,要攒一批样本,适合做日级巡检。两者搭配,巡检发现"某特征 PSI 升到 0.15",CUSUM 立刻定位"是过去 3 小时突然变差的",工程师下钻到 KS 看到分布形状改变,几分钟内可以判断是数据源 bug 还是真实漂移。一个常见踩坑是把 CUSUM 的 $\delta$ 设太小,导致正常波动频繁误报,真实生产上 $\delta$ 要用 7 天滚动标准差的中位数来估,而不是直接拍脑袋。

```python
import numpy as np
from scipy.stats import ks_2samp

class CUSUMDetector:
    """单变量 CUSUM 漂移检测器,挂在线上做实时告警"""
    def __init__(self, mu0, delta, h):
        self.mu0 = mu0       # 参考均值(训练集该特征的均值)
        self.delta = delta   # 最小可检测偏移
        self.h = h           # 告警阈值
        self.s = 0.0         # 累计偏差

    def update(self, x):
        self.s = max(0.0, self.s + (x - self.mu0 - self.delta / 2))
        if self.s > self.h:
            self.s = 0.0     # 告警后归零,继续监控
            return True      # 漂移发生
        return False

class PageHinkleyDetector:
    """Page-Hinkley 检测器,适合方差非平稳的特征"""
    def __init__(self, mu0, delta, h, lam=0.1):
        self.mu0, self.delta, self.h, self.lam = mu0, delta, h, lam
        self.m = 0.0  # 偏差累加
        self.s2 = 0.0 # 平方累加
        self.t = 0

    def update(self, x):
        self.t += 1
        self.m += x - self.mu0 - self.delta
        self.s2 += (x - self.mu0) ** 2
        ph = self.m - self.lam * self.s2
        if ph > self.h:
            self.m, self.s2, self.t = 0.0, 0.0, 0
            return True
        return False

def drift_dashboard(train_feat, live_feat, top_k=20):
    """离线日级巡检:KS + PSI 双指标"""
    ks_stat, ks_p = ks_2samp(train_feat, live_feat)
    psi_v = psi(np.histogram(train_feat, 10)[0],
                np.histogram(live_feat, 10)[0])
    return {"ks_stat": ks_stat, "ks_p": ks_p, "psi": psi_v,
            "drift": "Y" if (ks_p < 0.01 and psi_v > 0.1) else "N"}
```

## 8.10 EWC 变体与工程踩坑实录

### 8.10.1 原始 EWC 的 3 大问题

8.3 节给出了 EWC 的标准实现,但在工业 GR 场景直接套用会踩三个坑。

**坑 1:Fisher 矩阵的"任务过拟合"**。Kirkpatrick 原论文的 Fisher 是针对分类任务的交叉熵梯度二阶矩,GR 模型的 next-token prediction 目标不同,直接用 CE 梯度近似 Fisher,经验上会高估 embedding 参数的重要性(因为 embedding 的梯度天然稀疏但幅值大),导致老任务的 token 表征被锁死,新任务学不动。

**坑 2:对角近似的精度不足**。原始 EWC 只保留 Fisher 的对角元素,忽略了参数间的相关性。在 GR 中,token embedding 和 position embedding 之间强相关(同一行/列的 token 共享位置编码),对角近似会"误锁"位置参数,新任务调整位置表征的代价过高。

**坑 3:Fisher 计算代价大**。标准的 Fisher 需要在旧任务上做一次完整前向-反向传播,GR 模型几十亿参数,显存打不下。必须用近似估计算法。

### 8.10.2 主流 EWC 变体对比

| 变体 | 重要性度量 | 优点 | 缺点 | 适合场景 |
| :--- | :--- | :--- | :--- | :--- |
| EWC | Fisher 对角 | 简单,理论清晰 | 任务过拟合,对角近似 | 小模型,任务少 |
| EWC++ | Fisher 完整矩阵 | 精度高 | 显存爆炸 | 不可行(GR 排除) |
| SI (Synaptic Intelligence) | 路径积分 $\Omega_i$ | 在线累积,无需 Fisher | 重要性漂移 | 持续流式学习 |
| MAS (Memory Aware Synapses) | 输出梯度 $\|\partial f/\partial \theta\|^2$ | 不需要标签 | 粒度粗 | 无监督场景 |
| RWalk | Fisher + 路径积分 | 兼顾两者 | 计算量翻倍 | 任务数多 |
| Online EWC | 加权滑动平均 Fisher | 防"新任务 Fisher 覆盖老任务" | 调参复杂 | 长期持续 |

#### SI(Synaptic Intelligence)原理

SI 维护每个参数在训练过程中的"贡献度" $\Omega_i$:

$$\Omega_i = \sum_{t} \frac{\omega_i^{(t)}}{\Delta\theta_i^{(t)} + \epsilon}$$

其中 $\omega_i^{(t)} = -\frac{\partial \mathcal{L}}{\partial \theta_i} \cdot \Delta\theta_i$ 是参数 $\theta_i$ 在第 $t$ 步对损失减少的贡献。$\Delta\theta_i^{(t)}$ 是该步参数变化量。$\epsilon$ 防止除零。SI 的关键优势是**在线累积**:训练过程中持续记录,不需要事后在旧任务上重新算 Fisher。

$$\mathcal{L}_{\text{SI}} = \mathcal{L}_{\text{new}} + \lambda \sum_i \Omega_i (\theta_i - \theta_i^*)^2$$

#### MAS(Memory Aware Synapses)原理

MAS 用模型输出对参数的敏感度代替 Fisher:

$$\Omega_i^{\text{MAS}} = \mathbb{E}_{x}\!\left[\left\|\frac{\partial \|F(x;\theta)\|^2}{\partial \theta_i}\right\|\right]$$

好处是完全无监督,只需要前向传播;坏处是粒度粗,只反映"输出对参数变化的敏感度",不等于"参数对任务性能的重要性"。在 GR 场景下,embedding 参数的 MAS 值会偏低(因为 embedding 维度高、单个参数影响小),导致 embedding 漂移过快。

#### Online EWC 原理

标准 EWC 在多个任务上反复累加 Fisher,容易让"最近任务"的 Fisher 主导惩罚项。Online EWC 用滑动平均衰减:

$$F_i^{(k)} = \alpha F_i^{(k-1)} + (1-\alpha) F_i^{\text{new}}$$

$\alpha \in [0.9, 0.99]$,越小越快遗忘旧 Fisher。

### 8.10.3 GR 场景的工程化方案

```python
import torch
import torch.nn as nn

class SynapticIntelligence:
    """
    SI 实现,适合 GR 持续学习:
    - 训练过程中累积 Ω,无需额外 Fisher 前向
    - 支持多个旧任务,以 dict 形式存储
    """
    def __init__(self, model, lam=1.0, eps=1e-3, damping=0.9):
        self.model = model
        self.lam = lam
        self.eps = eps
        self.damping = damping
        self.omega = {n: torch.zeros_like(p)
                      for n, p in model.named_parameters() if p.requires_grad}
        # 上一轮的参数(用于计算 Δθ)
        self.params_old = {n: p.detach().clone()
                           for n, p in model.named_parameters() if p.requires_grad}
        # 累积的 unnormalized importance
        self.acc = {n: torch.zeros_like(p)
                    for n, p in model.named_parameters() if p.requires_grad}

    def begin_step(self):
        """每个训练 step 开头记录参数"""
        for n, p in self.model.named_parameters():
            if p.requires_grad:
                self.params_old[n] = p.detach().clone()

    def end_step(self):
        """每个训练 step 末尾累积贡献度"""
        for n, p in self.model.named_parameters():
            if p.requires_grad and p.grad is not None:
                delta = p.detach() - self.params_old[n]
                # ω = -∂L/∂θ * Δθ
                omega_step = -p.grad * delta
                self.acc[n] += omega_step

    def register_task(self):
        """训练完一个任务后,把累积的 Ω 归一化并存入"""
        for n, p in self.model.named_parameters():
            if p.requires_grad:
                # Ω = sum / (Δθ_total + ε)
                delta_total = p.detach() - self.params_old[n]
                self.omega[n] += self.acc[n] / (delta_total.abs() + self.eps)
                self.acc[n] = torch.zeros_like(p)
        # 衰减(支持持续学习)
        for n in self.omega:
            self.omega[n] *= self.damping

    def penalty(self):
        loss = 0.0
        for n, p in self.model.named_parameters():
            if n in self.omega:
                loss += (self.omega[n] * (p - self.params_old[n]).pow(2)).sum()
        return self.lam * loss
```

### 8.10.4 文字·公式·代码 三位一体块

GR 持续学习选 SI 还是 EWC,本质是"工程成本 vs 性能上限"的取舍。EWC 理论清晰,但每次新任务来都要在旧任务数据上跑一次完整前向反向,GR 模型几十亿参数,显存放不下,只能采样子集估 Fisher,引入额外噪声。SI 的 $\Omega$ 在训练过程中累积,显存只比正常训练多一倍(存参数快照),代价是新任务刚起步时 $\Omega$ 不准,要训几千步才稳定,前几千步会出现"短时遗忘"。工业经验是 EWC 和 SI 并行跑:SI 作为日常持续学习(小时级),EWC 作为周级 checkpoint 校正(用全量旧任务数据重算 Fisher)。Online EWC 的 $\alpha$ 选 0.95 是常见甜区,既能保留旧任务 Fisher,又让最近任务有足够话语权。

### 8.10.5 灾难性遗忘的评估方法

光有"防遗忘"算法不够,还要能**量化**遗忘程度。三个常用指标:

**(1)Backward Transfer (BWT)**: 在所有旧任务上的性能下降均值。

$$\text{BWT} = \frac{1}{K-1} \sum_{i=1}^{K-1} (R_{K,i} - R_{i,i})$$

$R_{i,j}$ 是训完任务 $i$ 之后,在任务 $j$ 上的性能。BWT 越接近 0 越好,负数表示遗忘。

**(2)Forward Transfer (FWT)**: 旧任务经验对新任务的帮助。

$$\text{FWT} = \frac{1}{K-1} \sum_{i=2}^{K} (R_{i,i} - R_{i,\text{random}})$$

$R_{i,\text{random}}$ 是随机初始化在任务 $i$ 上的性能。FWT 越大表示迁移越好。

**(3)Average Accuracy**: 训完所有任务后,在每个任务上的平均准确率。

$$\text{ACC} = \frac{1}{K} \sum_{i=1}^{K} R_{K,i}$$

GR 场景下的具体计算:在每个"季节/业务"任务上保留 1 万条测试集,训完新任务后回放评估,记录 Recall@10 的差值。

### 8.10.6 持续学习的"工业踩坑" Checklist

```text
□  Fisher 矩阵计算用混合精度(FP16),否则爆显存
□  SI 的 ε 不要小于 1e-4,否则 Δθ 接近 0 时 Ω 爆炸
□  λ 必须随任务数 scale:K 个任务用 λ = λ0 * K
□  持续学习 + 经验回放同时用,效果 > 单独使用
□  每 N 步评估一次 BWT,变化超过 5% 触发告警
□  旧任务数据不能全删,保留 1% 作为"永久回放池"
□  监控"参数偏移总量" = Σ|θ - θ_old|,超过阈值回滚
```

## 8.11 离线-在线 Hybrid 架构与 Contextual Bandit 实战

### 8.11.1 为什么需要 Hybrid 架构

8.2 节讨论的纯在线学习在工业落地中**几乎不可行**。原因有三。

第一,**训练-服务不一致**。GR 模型动辄几十 GB,在线 fine-tune 即使有 LoRA 也需要分钟级,这段时间线上服务要保持稳定,不能"训练时服务中断"。**双链路架构**是工程妥协:在线链路只更新轻量模块(LoRA / 浅层 MLP),离线链路周期重训全量模型(每天到每周)。

第二,**冷启动问题**。新用户 / 新物品 / 新场景没有反馈数据,纯监督学习训不出有效表征,纯在线学习又陷入"无数据 → 不更新 → 无数据"的死循环。Contextual Bandit 给出"探索-利用"框架,显式鼓励尝试未知物品,虽然短期 CTR 降 1-2%,长期 LTV 提升 5-10%。

第三,**反馈延迟**。LTV 建模(8.4 节)提到 30 天反馈延迟,等不了;但完全忽略长期信号又会短视。Hybrid 架构用"短期监督 + 在线 Bandit 探索"双链路,既快又稳。

### 8.11.3 Contextual Bandit 基础

Contextual Bandit 是强化学习的"单步版":每个时刻 $t$,系统观察上下文 $x_t$ (用户特征、场景),选一个动作 $a_t$ (推荐哪个物品),获得奖励 $r_t$ (点击/转化)。目标是最大化累计奖励 $\sum_t r_t$。

$$\pi^* = \arg\max_\pi \mathbb{E}_{x, a \sim \pi(\cdot|x)}\!\big[r(x, a)\big]$$

工业界最常用的两个算法:**LinUCB** 和 **Thompson Sampling**。

#### LinUCB 原理

LinUCB 假设奖励关于特征线性:

$$r(x, a) = x_a^\top \theta_a + \epsilon$$

每个臂 $a$ 维护一个置信上界:

$$\hat{r}(x, a) = x_a^\top \hat{\theta}_a + \alpha \sqrt{x_a^\top A_a^{-1} x_a}$$

其中 $A_a = \sum_t x_{a,t} x_{a,t}^\top + \lambda I$ 是设计矩阵,$\hat{\theta}_a = A_a^{-1} b_a$ 是 ridge 估计。选择臂的规则:

$$a_t = \arg\max_a \hat{r}(x_t, a)$$

第一项是"利用"项(均值估计),第二项是"探索"项(不确定性)。$\alpha$ 控制探索强度,工业典型值 1.0 到 2.0。

#### Thompson Sampling 原理

Thompson Sampling 维护参数的后验分布 $p(\theta | \mathcal{D}_t)$,每次决策从后验中采样 $\tilde{\theta} \sim p(\theta | \mathcal{D}_t)$,选择使期望奖励最大的动作:

$$a_t = \arg\max_a x_a^\top \tilde{\theta}$$

相对 LinUCB,Thompson Sampling 的优势是**天然随机化**,适合"多个 Bandit 并行"场景(每个用户一个 Bandit),不会都集中在同一探索点。

### 8.11.4 FTRL(Follow The Regularized Leader)在线学习

FTRL 是 Google 在广告 CTR 场景的工业级方案,被 TensorFlow 封装为 `tf.train.FtrlOptimizer`。核心思想:每次更新不是直接走梯度下降,而是求解一个"考虑了 L1/L2 正则的全局最优":

$$\theta_{t+1} = \arg\min_\theta \left\{ \sum_{s=1}^{t} g_s \cdot \theta + \frac{1}{2} \sum_{s=1}^{t} h_s (\theta - \theta_s)^2 + \lambda_1 \|\theta\|_1 + \frac{\lambda_2}{2} \|\theta\|_2^2 \right\}$$

$g_s$ 是梯度,$h_s$ 是学习率倒数的一半。FTRL 的关键是**稀疏性**:L1 正则天然让大部分参数归零,在线学习时只有少数特征被更新,工程上只需 push 增量参数,带宽友好。

```python
import numpy as np

class FTRL_Online:
    """
    简化的 FTRL-Proximal 在线学习器,适合线性模型
    工业实现可参考:tf.train.FtrlOptimizer
    """
    def __init__(self, n_features, alpha=0.1, beta=1.0,
                 l1=1.0, l2=1.0):
        self.alpha = alpha
        self.beta = beta
        self.l1, self.l2 = l1, l2
        self.n = n_features
        # 累积梯度
        self.g = np.zeros(n_features)
        # 累积二阶项
        self.h = np.zeros(n_features)
        # 当前权重
        self.w = np.zeros(n_features)
        # z 是 FTRL 内部状态(用于稀疏)
        self.z = np.zeros(n_features)

    def predict(self, x):
        return 1.0 / (1.0 + np.exp(-x.dot(self.w)))

    def update(self, x, y, lr):
        """y ∈ {0, 1}, lr 是学习率(可以衰减)"""
        p = self.predict(x)
        g = (p - y) * x                       # 梯度
        self.g += g
        # 累积二阶项
        self.h += g * g
        # FTRL 更新(简化版,省略 proximal 项)
        for i in range(self.n):
            if abs(self.z[i]) <= self.l1:
                self.w[i] = 0
            else:
                sigma = (np.sqrt(self.h[i] + 1e-8) - np.sqrt(self.h[i] - g[i]**2 + 1e-8)) / self.alpha
                self.w[i] = -(self.z[i] - np.sign(self.z[i]) * self.l1) / (self.l2 + sigma)
        self.z += g - self.alpha * self.w * lr
```

### 8.11.5 OBP(Off-Policy Bandit)与 IPS 估计

Contextual Bandit 收集的数据天然带**选择偏差**——我们只看到被推荐物品的反馈,没看到"如果推荐另一个会怎样"。直接用这些数据训练新模型会有偏差,需要 **IPS(Inverse Propensity Scoring)** 校正:

$$\hat{V}_{\text{IPS}} = \frac{1}{n} \sum_{i=1}^{n} \frac{r_i \cdot \mathbf{1}[\pi_0(a_i|x_i) > 0]}{\pi_0(a_i|x_i)}$$

其中 $\pi_0$ 是日志策略(收集数据时用的策略),$\pi_0(a_i|x_i)$ 是"在上下文 $x_i$ 下选择动作 $a_i$ 的概率"。直觉:被选概率低的动作,样本权重应该放大,补偿它被采样的不足。OpenBanditPipeline(OBP)是日本 Preferred Networks 开源的工业级 Bandit 评估库,内置 IPS、DR(Doubly Robust)、Switch-DR 等多种估计器。

### 8.11.6 文字·公式·代码 三位一体块

Hybrid 架构的核心,是"快慢两条链路 + 显式探索"。离线链路每天重训一次,产出稳态模型,负责 80% 的流量;在线链路小时级更新 LoRA 或浅层参数,负责 20% 的"长尾探索"。Contextual Bandit 不是替代监督学习,而是补足"探索未知"这一环。LinUCB 简单稳定,适合物品池相对固定(几千到几万个候选);Thompson Sampling 天然随机化,适合"多用户并发"且不希望"集体扎堆探索"的场景。FTRL 解决了"在线学习参数膨胀"问题——L1 正则让大部分特征参数归零,工程上 push 增量极小,带宽友好。冷启动的解法是**显式随机化**:对新物品 / 新用户强制随机曝光 100 到 1000 次,即使 CTR 低也要撑过"冷启动期",过了这个窗口才能上 Bandit 决策。

```python
import numpy as np
from scipy.optimize import minimize

class LinUCB:
    """LinUCB 简化实现,适合物品数 < 10K 的推荐场景"""
    def __init__(self, n_arms, context_dim, alpha=1.5):
        self.n_arms = n_arms
        self.d = context_dim
        self.alpha = alpha
        # A_a: (d, d), b_a: (d,)
        self.A = [np.eye(context_dim) for _ in range(n_arms)]
        self.b = [np.zeros(context_dim) for _ in range(n_arms)]

    def select(self, x):
        """x: list of context vectors, one per arm; shape (n_arms, d)"""
        p = np.zeros(self.n_arms)
        for a in range(self.n_arms):
            A_inv = np.linalg.inv(self.A[a])
            theta = A_inv @ self.b[a]
            # 利用项 + 探索项
            p[a] = x[a] @ theta + self.alpha * np.sqrt(x[a] @ A_inv @ x[a])
        return int(np.argmax(p))

    def update(self, arm, x_arm, reward):
        """收到 (上下文, 动作, 奖励) 后更新"""
        self.A[arm] += np.outer(x_arm, x_arm)
        self.b[arm] += reward * x_arm

    @property
    def sparsity(self):
        """返回被更新过的臂数,辅助监控探索度"""
        return sum(1 for a in range(self.n_arms)
                   if not np.allclose(self.b[a], 0))


class HybridServing:
    """
    双链路 + Bandit 的简化服务流程
    实际生产需配合 Kafka + Redis + GPU 服务
    """
    def __init__(self, offline_model, online_lora, bandit):
        self.offline = offline_model
        self.online = online_lora
        self.bandit = bandit

    def recommend(self, user_ctx, candidate_items):
        # 离线打分(80% 流量)
        offline_scores = self.offline.score(user_ctx, candidate_items)
        # 在线打分(20% 流量)
        online_scores = self.online.score(user_ctx, candidate_items)
        # Bandit 探索:从 top-K 中随机挑 1 个
        scores = 0.8 * offline_scores + 0.2 * online_scores
        top_k = np.argsort(-scores)[:20]
        if self.bandit.should_explore(user_ctx):
            chosen = np.random.choice(top_k)
        else:
            chosen = top_k[0]
        return candidate_items[chosen]
```

### 8.11.7 双链路 Hybrid 架构 Checklist

```text
□  离线 / 在线链路解耦,在线故障不影响离线
□  LoRA rank ≤ 16,在线更新单步 < 1s
□  Bandit 探索比例锁定在 5-10%,流量隔离
□  新物品强制随机曝光 ≥ 100 次(冷启动兜底)
□  IPS 估计器与生产策略同源,避免双重偏差
□  FTRL 训练时 L1/L2 用 L-BFGS 调,不能拍脑袋
□  在线链路带版本号,出问题 30 秒内回滚
□  监控"探索-利用比",持续低于 5% 说明 Bandit 失效
□  每月评估一次 IPS 估计的方差,过大时切到 DR
□  离线模型与在线模型 score 分布 KL < 0.1(防止融合后崩坏)
```

## 5. 在线学习

在线学习(Online Learning)是 GR 系统"对抗分布漂移"的第一道防线。它的核心思想是:模型不是训练完一次就完事,而是要在服务过程中持续从用户反馈中学习。本节从理论、算法、工程三个层面展开。

### 5.1 在线学习的本质

#### 5.1.1 离线训练 vs 在线学习的对比

| 维度 | 离线训练 (Offline) | 在线学习 (Online) |
| :--- | :--- | :--- |
| 数据到达方式 | 一次性加载全量数据集 | 流式(sample-by-sample 或 mini-batch) |
| 更新频率 | 每日/每周一次 | 分钟级甚至秒级 |
| 数据量假设 | i.i.d. (独立同分布) | 可能非平稳(non-stationary) |
| 优化目标 | 经验风险最小化 $\frac{1}{N}\sum_{i=1}^N \ell(f_\theta(x_i), y_i)$ | 累积损失最小化 $\sum_{t=1}^T \ell(f_{\theta_t}(x_t), y_t)$ |
| 评估方式 | 静态测试集 | 在线 A/B 或 Interleaving |
| 工程复杂度 | 中等(批处理) | 高(实时数据流 + 模型热更新) |

#### 5.1.2 在线学习的数学刻画

**累积遗憾(Cumulative Regret)**:

$$R(T) = \sum_{t=1}^T \ell(f_{\theta_t}(x_t), y_t) - \min_{\theta^*} \sum_{t=1}^T \ell(f_{\theta^*}(x_t), y_t)$$

**目标**: 找到一个序列 $\theta_1, \theta_2, \ldots, \theta_T$,使得 $R(T) = o(T)$(次线性增长),即平均遗憾 $\frac{R(T)}{T} \to 0$。

**后悔匹配(Regret Matching)** 的核心更新规则:

$$\theta_{t+1} = \theta_t - \eta_t \nabla_\theta \ell(f_{\theta_t}(x_t), y_t)$$

其中 $\eta_t$ 是学习率,在凸优化问题下取 $\eta_t = \frac{1}{\sqrt{t}}$ 可保证 $R(T) = O(\sqrt{T})$。

#### 5.1.3 在线学习 vs 持续学习

这是初学者最容易混淆的两个概念:

| 概念 | 在线学习 | 持续学习 (Continual Learning) |
| :--- | :--- | :--- |
| 主要目标 | 适应数据分布变化 | 适应任务分布变化 |
| 数据假设 | 同任务、新数据 | 新任务、新数据 |
| 灾难性遗忘 | 一般不严重(任务未变) | 核心挑战 |
| 典型方法 | SGD 流式训练 | EWC / Replay / 渐进式网络 |
| GR 中的角色 | 主模型的日常更新 | 拓展到新场景(短视频→直播) |

### 5.2 在线学习的三大算法族

#### 5.2.1 朴素 SGD 流式训练

最简单的方式:每来一个 mini-batch 就更新一次参数。

```python
import torch
from torch.optim import SGD

class OnlineSGD:
    """流式 SGD:每来一个 batch 更新一次"""
    def __init__(self, model, lr=1e-4, momentum=0.9):
        self.model = model
        self.opt = SGD(model.parameters(), lr=lr, momentum=momentum)
        self.step_count = 0

    def update(self, batch):
        # batch: dict with x, y
        self.opt.zero_grad()
        loss = self.model.compute_loss(batch)
        loss.backward()
        self.opt.step()
        self.step_count += 1
        return loss.item()

# 在线数据流
online_stream = KafkaConsumer('gr_clicks').stream()
online_sgd = OnlineSGD(model, lr=1e-4)

for batch in online_stream:
    loss = online_sgd.update(batch)
    if online_sgd.step_count % 1000 == 0:
        logger.info(f"step {online_sgd.step_count}, loss={loss:.4f}")
```

**坑点**:
- 学习率必须远小于离线训练(典型:离线 1e-3,在线 1e-5 或 1e-6)
- 必须做梯度裁剪(clip_grad_norm_),防止被异常样本带偏
- 必须监控"延迟反馈"(用户 30 分钟后才点击),否则模型学到的是错的标签

#### 5.2.2 FTRL(Follow The Regularized Leader)

Google 在广告系统广泛使用的在线学习算法,适合**稀疏、大规模、稀疏特征** 场景。

**核心思想**:在第 $t$ 步,优化的是累积损失 + 累积正则:

$$\theta_{t+1} = \arg\min_\theta \left[ \sum_{s=1}^t \ell(f_\theta(x_s), y_s) + \frac{1}{2\eta} \|\theta - \theta_0\|_2^2 + \lambda_1 \|\theta\|_1 \right]$$

其中:
- $\frac{1}{2\eta}\|\theta - \theta_0\|_2^2$: L2 正则,防止参数漂移太远
- $\lambda_1 \|\theta\|_1$: L1 正则,产生稀疏性(广告/推荐场景特征维度极高)

**为什么 GR 不用 FTRL?** GR 的特征维度虽然高,但主模型是 Transformer/DNN,参数是密集的,L1 正则意义不大。所以 FTRL 主要用于**线性浅层模型**(LR/FM),GR 主模型仍用 SGD 系列。

#### 5.2.3 Bandit 算法(多臂老虎机)

**场景**:GR 模型已经训练好,但需要在多个候选生成策略(召回通道)之间动态分配流量。

| 算法 | 核心思想 | 适用场景 |
| :--- | :--- | :--- |
| $\epsilon$-Greedy | 以 $\epsilon$ 概率随机探索,否则选当前最优 | 基线方法 |
| UCB | 选 $\hat{\mu}_a + c\sqrt{\frac{\ln t}{n_a}}$(均值 + 不确定性) | 探索充分 |
| LinUCB | 上下文相关的 UCB:$\hat{\theta}_a^T x + \alpha\sqrt{x^T A_a^{-1} x}$ | 有用户/物品特征 |
| Thompson Sampling | 从后验分布采样,选采样值最大的臂 | 概率化决策 |
| Contextual Bandit | $r = \mathbb{E}[R \mid x, a]$,通过历史 $(x, a, r)$ 拟合 | 决策式推荐 |

```python
import numpy as np

class LinUCB:
    """LinUCB:上下文老虎机,适合 GR 的多通道流量分配"""
    def __init__(self, n_arms, d, alpha=1.0):
        self.n_arms = n_arms
        self.d = d
        self.alpha = alpha
        # 每个臂维护 A (dxd) 和 b (dx1)
        self.A = [np.eye(d) for _ in range(n_arms)]
        self.b = [np.zeros(d) for _ in range(n_arms)]

    def select(self, x):
        """选择 UCB 最大的臂"""
        ucb_values = []
        for a in range(self.n_arms):
            A_inv = np.linalg.inv(self.A[a])
            theta = A_inv @ self.b[a]
            # 期望奖励 + 不确定性
            mean = theta @ x
            confidence = self.alpha * np.sqrt(x @ A_inv @ x)
            ucb_values.append(mean + confidence)
        return int(np.argmax(ucb_values))

    def update(self, arm, x, reward):
        """用真实反馈更新"""
        self.A[arm] += np.outer(x, x)
        self.b[arm] += reward * x

# 用法:GR 的召回通道动态分配
# 5 个召回通道 → 5 个臂
# 用户 embedding → context
# 点击/转化 → reward
bandit = LinUCB(n_arms=5, d=128)
for user_emb, arm, click in online_log_stream:
    bandit.update(arm, user_emb, click)
```

**LinUCB 在 GR 中的典型应用**:
- 多通道召回(协同过滤 / 内容相似 / 热门 / 探索 / 上下文)动态分配
- 探索 vs 利用(Exploration vs Exploitation)的工业级实现
- 冷启动期间(没有充分历史数据)的过渡方案

### 5.3 在线学习在 GR 中的工程实践

#### 5.3.1 实时数据流水线

```text
[用户行为] → Kafka → Flink(实时特征工程) →
   ↓
[Parquet 流] → 训练 Worker(Spark/Flink ML) →
   ↓
[新模型] → 模型注册中心 → 影子测试 → 在线服务
```

**典型延迟**:
- 行为发生 → Kafka 入库: < 1s
- Flink 特征工程: 5-10s
- 训练(mini-batch 增量): 1-5 min
- 模型发布(热加载): 10-30s
- **端到端延迟**: 5-10 min

#### 5.3.2 模型热更新 vs 冷更新

| 维度 | 热更新(Hot Reload) | 冷更新(Cold Restart) |
| :--- | :--- | :--- |
| 实现 | 加载新权重,继续服务 | 销毁旧 worker,启动新 worker |
| 延迟 | < 1s | 30s - 数 min |
| 中断 | 无中断 | 短暂中断或排队 |
| 一致性 | 可能短暂新旧不一致 | 强一致 |
| 适用 | 在线学习(频繁更新) | 大版本升级 |

**工程注意**:
- 模型参数加载时必须**锁住推理**,避免读到半新半旧的参数
- 推荐用 mmap(内存映射)加载权重,避免 Python pickle 的 GC 抖动
- 用 `torch.compile` 提前编译,加载后跳过 JIT 时间

#### 5.3.3 在线学习的安全护栏

```python
class OnlineLearningGuard:
    """在线学习的安全护栏:防止模型被坏数据带偏"""

    def __init__(self, model, max_param_drift=0.05, grad_clip=1.0):
        self.model = model
        self.max_param_drift = max_param_drift  # 参数漂移上限
        self.grad_clip = grad_clip              # 梯度裁剪
        self.anchor_params = {n: p.detach().clone()
                              for n, p in model.named_parameters()}

    def safe_step(self, loss):
        loss.backward()

        # 1. 梯度裁剪
        torch.nn.utils.clip_grad_norm_(self.model.parameters(),
                                        self.grad_clip)

        # 2. 参数漂移检查
        with torch.no_grad():
            for n, p in self.model.named_parameters():
                if n in self.anchor_params:
                    anchor = self.anchor_params[n]
                    drift = (p - anchor).norm() / (anchor.norm() + 1e-8)
                    if drift > self.max_param_drift:
                        # 回滚并跳过本次更新
                        p.copy_(anchor)
                        logger.warn(f"param {n} drift {drift:.3f}, rolled back")
                        return False
        return True
```

**安全机制清单**:
1. **梯度裁剪**:防止梯度爆炸(异常样本)
2. **参数漂移限制**:防止模型"突变"
3. **异常检测**:监控在线 AUC,若骤降则暂停更新
4. **回滚机制**:保留上一个稳定版本,30 分钟内可一键回滚
5. **A/B 测试**:任何模型变更必须先经过小流量验证

### 5.4 在线学习的局限

- **反馈稀疏**:用户可能 30 分钟甚至几天后才转化,导致 label 延迟
- **因果混淆**:模型推荐 → 用户点击,但点击 ≠ 真实偏好
- **公平性问题**:在线学习会放大已有的偏差(富者愈富)
- **冷启动**:新用户/新物品没有反馈,在线学习也无能为力

这些问题将在本章后续小节继续讨论。

## 6. 长期用户建模

GR 系统的"长期价值"建模是工业级推荐的核心难题。本节从理论到实践,系统讲解如何建模用户的长期兴趣、生命周期价值(LTV)和留存预测。

### 6.1 为什么需要长期建模?

#### 6.1.1 短期指标的陷阱

**反例**:一个新闻推荐系统
- 短期指标:CTR(点击率)
- 长期指标:用户 7 日留存、订阅率、月度活跃天数
- **冲突场景**:标题党文章 CTR 高,但用户读完后不再信任平台 → 7 日留存下降
- **结论**:仅优化 CTR 会"短视",长期反而伤害平台价值

#### 6.1.2 长期 vs 短期指标矩阵

| 短期(< 1 天) | 中期(1-7 天) | 长期(> 7 天) |
| :--- | :--- | :--- |
| CTR / CVR | 7 日留存 | 月活(MAU) |
| 互动次数 | 7 日回访 | 付费用户数(LTV) |
| 跳出率 | 分享数 | 净推荐值(NPS) |
| 平均时长 | 关注数 | 长期 GMV |

#### 6.1.3 长期建模的三大挑战

1. **反馈延迟**:用户今天点击 → 7 天后是否留存?这之间所有"中间反馈"如何利用?
2. **信用分配(Credit Assignment)**:一次会话中 10 次曝光,哪几次真正导致了留存?
3. **状态空间巨大**:用户历史可能长达数年,如何在有限计算下聚合?

### 6.2 长期兴趣建模的核心方法

#### 6.2.1 用户生命周期价值(LTV)建模

**公式定义**:

$$\text{LTV}(u) = \sum_{t=1}^{\infty} \frac{\mathbb{E}[r_t \mid u]}{(1 + d)^t}$$

其中:
- $\mathbb{E}[r_t \mid u]$: 用户 $u$ 在第 $t$ 期的期望收益
- $d$: 折现率(典型 0.95 ~ 0.99/月)
- 实际建模中通常截断到 $T = 24$ 或 $60$ 个月

**LTV 预测模型架构**:

```text
用户历史行为序列 (n 个事件)
   ↓
[行为编码器] (Transformer)
   ↓
用户 embedding (d 维)
   ↓
[LTV 预测头] (MLP)
   ↓
LTV 标量估计
```

```python
import torch
import torch.nn as nn

class LTVPredictor(nn.Module):
    """用户生命周期价值预测器"""
    def __init__(self, n_items, d=128, n_layers=4, max_seq_len=512):
        super().__init__()
        self.item_emb = nn.Embedding(n_items, d)
        self.pos_emb = nn.Embedding(max_seq_len, d)

        encoder_layer = nn.TransformerEncoderLayer(
            d_model=d, nhead=8, dim_feedforward=512,
            dropout=0.1, batch_first=True
        )
        self.encoder = nn.TransformerEncoder(encoder_layer, n_layers)

        # 多个预测头:分别预测 1/3/7/30/90 天的留存/付费
        self.heads = nn.ModuleDict({
            'd1_retention': nn.Linear(d, 1),
            'd7_retention': nn.Linear(d, 1),
            'd30_retention': nn.Linear(d, 1),
            'd1_revenue': nn.Linear(d, 1),
            'd30_revenue': nn.Linear(d, 1),
            'lifetime_value': nn.Linear(d, 1),
        })

    def forward(self, item_seq, lengths):
        # item_seq: (B, L) 物品 ID 序列
        # lengths: (B,) 实际长度
        B, L = item_seq.shape

        x = self.item_emb(item_seq)
        pos = torch.arange(L, device=x.device).unsqueeze(0).expand(B, L)
        x = x + self.pos_emb(pos)

        # mask: padding 位置不参与 attention
        mask = torch.arange(L, device=x.device).unsqueeze(0) >= lengths.unsqueeze(1)
        x = self.encoder(x, src_key_padding_mask=mask)

        # 用最后一个有效位置的输出代表用户
        user_emb = x[torch.arange(B), lengths - 1]

        return {name: head(user_emb).squeeze(-1)
                for name, head in self.heads.items()}
```

#### 6.2.2 多任务学习(Multi-Task Learning, MTL)

**核心思想**:同时预测多个时间窗口的指标,共享底层表示。

$$\mathcal{L}_{\text{total}} = \sum_{k=1}^K w_k \mathcal{L}_k(f_{\theta_{\text{shared}}}(x), y_k)$$

其中 $w_k$ 是任务权重,可用 **GradNorm** 或 **不确定性加权** 自动学习。

```python
class GradNorm:
    """GradNorm:动态调整多任务权重,平衡训练速度"""
    def __init__(self, tasks, alpha=0.16):
        self.tasks = tasks  # ['d1', 'd7', 'd30', 'ltv']
        self.alpha = alpha
        self.weights = {t: 1.0 for t in tasks}
        self.initial_losses = None

    def update_weights(self, losses, shared_params):
        if self.initial_losses is None:
            self.initial_losses = {t: l.item() for t, l in zip(self.tasks, losses)}

        loss_ratios = {t: l.item() / self.initial_losses[t]
                       for t, l in zip(self.tasks, losses)}
        mean_ratio = np.mean(list(loss_ratios.values()))

        for t, l in zip(self.tasks, losses):
            # 训练慢的任务(loss 下降慢)权重升高
            target = mean_ratio ** self.alpha
            grad = torch.autograd.grad(l, shared_params, retain_graph=True)
            grad_norm = sum(g.norm() for g in grad)

            # 简化版:按 loss ratio 调整
            self.weights[t] = loss_ratios[t] / target

        # 归一化,保持总权重为 K
        total = sum(self.weights.values())
        for t in self.weights:
            self.weights[t] *= len(self.tasks) / total
```

#### 6.2.3 长序列建模:从 SASRec 到 HSTU

GR 中用户行为序列可能长达 $10^3$ ~ $10^5$ 个事件。Transformer 的二次复杂度 $O(L^2)$ 难以承受。

**演化路径**:

| 模型 | 序列长度 | 复杂度 | 适用场景 |
| :--- | :--- | :--- | :--- |
| DIN/DIEN | ~100 | $O(L \cdot d)$ | 短序列精排 |
| SASRec | ~500 | $O(L^2 \cdot d)$ | 中等序列召回 |
| BERT4Rec | ~1000 | $O(L^2 \cdot d)$ | 双向建模 |
| TWIN/Longer | ~10000 | $O(L \cdot \log L \cdot d)$ | 长序列 |
| **HSTU (Meta 2024)** | ~10000+ | $O(L \cdot d)$ | 超长序列 |

**HSTU 的核心思想**:把 attention 简化为"加权和 + 缩放",去掉 softmax:

$$\text{HSTU}(Q, K, V) = (Q K^T \odot M) V$$

其中 $M$ 是时间衰减 mask,体现"近期行为更重要"。

```python
class HSTUAttention(nn.Module):
    """Hierarchical Sequential Transduction Unit (Meta 2024)"""
    def __init__(self, d, n_heads=8):
        super().__init__()
        self.d = d
        self.n_heads = n_heads
        self.d_head = d // n_heads

        self.q_proj = nn.Linear(d, d, bias=False)
        self.k_proj = nn.Linear(d, d, bias=False)
        self.v_proj = nn.Linear(d, d, bias=False)
        self.u_proj = nn.Linear(d, d, bias=False)  # 残差投影

    def forward(self, x, timestamps):
        B, L, D = x.shape
        H = self.n_heads

        Q = self.q_proj(x).view(B, L, H, self.d_head).transpose(1, 2)
        K = self.k_proj(x).view(B, L, H, self.d_head).transpose(1, 2)
        V = self.v_proj(x).view(B, L, H, self.d_head).transpose(1, 2)
        U = self.u_proj(x).view(B, L, H, self.d_head).transpose(1, 2)

        # 1. Q @ K^T, 不缩放不 softmax
        attn = Q @ K.transpose(-2, -1)  # (B, H, L, L)

        # 2. 时间衰减 mask(关键!)
        # delta_t: (L, L) 时间差矩阵
        delta_t = timestamps.unsqueeze(-1) - timestamps.unsqueeze(-2)
        time_decay = torch.exp(-self.alpha * delta_t.abs().float())
        attn = attn * time_decay.unsqueeze(0).unsqueeze(0)

        # 3. 直接加权求和
        out = attn @ V  # (B, H, L, d_head)

        # 4. 残差连接(关键的"U"路径)
        out = out + U
        out = out.transpose(1, 2).contiguous().view(B, L, D)
        return out
```

### 6.3 长期价值建模的工程化

#### 6.3.1 标签回填(Label Backfill)

**问题**:训练时只有"今天点击"的标签,没有"用户 7 日后是否留存"的标签。

**解法**:**回填机制**

```text
[第 1 天] 用户登录 → 曝光物品 A → 用户点击
   ↓
[第 2-7 天] 持续观察用户行为,记录:
   - 是否回访?
   - 是否关注/收藏?
   - 是否分享?
   - 是否付费?
   ↓
[第 8 天] 把"7 日留存/付费"标签 回填到第 1 天的样本上
   ↓
[训练时] 用回填后的样本训练 LTV 模型
```

**工程挑战**:
- 标签延迟:必须等 7 天才能拿到标签
- 存储成本:用户 × 物品 × 时间的三维数据
- **实际做法**:用 **滑动窗口回填**(每天补昨天的标签)+ **TTI(Time-To-Interact)** 估计未回填样本的近似标签

#### 6.3.2 反事实推理(Counterfactual Reasoning)

**问题**:模型推荐物品 A 导致用户点击,但如果推荐 B 呢?

**因果图建模**:

```python
class CounterfactualLTV(nn.Module):
    """反事实 LTV 估计:如果推荐不同的物品,长期价值会怎样?"""
    def __init__(self, base_model):
        super().__init__()
        self.base = base_model  # 基础 LTV 预测器
        self.treatment_head = nn.Linear(128, 1)  # 处理效应头

    def forward(self, user_emb, item_emb, factual_action):
        """
        user_emb: 用户状态 (B, d)
        item_emb: 物品表征 (B, d)
        factual_action: 实际推荐物品 (B,)
        """
        # 基础预测:不做任何处理时的 LTV
        base_ltv = self.base(user_emb)

        # 处理效应:推荐物品 i 带来的 LTV 增量
        treatment = self.treatment_head(item_emb).squeeze(-1)

        return base_ltv + treatment
```

#### 6.3.3 长期指标的在线监控

```text
[仪表盘]
   ↓
[核心指标]
   - DAU / MAU / 留存曲线
   - LTV 分位数(P50 / P90 / P99)
   - 用户分层(新 / 老 / 流失风险)
   ↓
[预警机制]
   - 留存曲线连续 3 天下滑 → 告警
   - LTV 突变(> 10%) → 告警
   - 新用户 7 日激活率 < 基线 → 告警
```

### 6.4 长期建模的常见误区

1. **误区 1**:用短期标签训练,用长期指标评估
   - 后果:模型过拟合短期信号,长期效果差
   - 解法:**用长期标签训练**(即使稀疏)

2. **误区 2**:把所有用户一视同仁
   - 后果:活跃用户的偏好被稀释
   - 解法:**分层建模**(高活/中活/低活 各自一套参数)

3. **误区 3**:忽视冷启动用户
   - 后果:新用户被"长期模型"误判
   - 解法:**冷启动分支**(单独的小模型,只用通用特征)

4. **误区 4**:LTV 标签"过时"
   - 后果:用户偏好已变,但训练标签是 30 天前的
   - 解法:**标签滑动窗口**(只用最近 30 天的 LTV 标签训练)

## 7. 冷启动策略

冷启动(Cold Start)是 GR 系统中最棘手的问题之一。本节从用户冷启动、物品冷启动、场景冷启动三个维度展开,给出工业级解决方案。

### 7.1 冷启动的本质

#### 7.1.1 冷启动的三大类型

| 类型 | 含义 | 核心难点 |
| :--- | :--- | :--- |
| 用户冷启动 | 新用户无历史行为 | 无法基于行为做个性化 |
| 物品冷启动 | 新物品无交互数据 | 无法评估物品质量 |
| 系统冷启动 | 新平台无任何数据 | 没有用户也没有物品 |

**数学刻画**:用户冷启动本质是 **稀疏性** 问题。

设用户 $u$ 的特征为 $x_u \in \mathbb{R}^d$,其中 $d_u$ 个维度有值(历史行为稀疏)。当 $d_u \to 0$ 时,模型退化为"基于先验的随机猜测"。

**关键观察**:虽然新用户没有"个性化"信息,但通常有 **属性信息**(年龄/性别/地域/设备) 和 **场景信息**(时间/位置/网络)。这些可以提供 **"群体共性"信号**。

### 7.2 用户冷启动

#### 7.2.1 渐进式个性化

**核心思想**:用先验(群体)→ 短期反馈 → 长期反馈,逐步收敛到个性化。

```text
第 0 分钟(注册完成): 完全群体共性
   ↓  [1 次行为]
第 1 分钟: 基于属性的弱个性化
   ↓  [5-10 次行为]
第 10 分钟: 基于短期反馈的个性化
   ↓  [100+ 次行为]
第 1 天: 完全个性化
```

```python
class ProgressivePersonalization:
    """渐进式个性化:从群体到个体的平滑过渡"""

    def __init__(self, group_model, individual_model, warmup_threshold=10):
        self.group_model = group_model      # 群体共性模型
        self.individual_model = individual_model  # 个性化模型
        self.warmup_threshold = warmup_threshold
        self.user_interactions = {}  # 用户 ID → 交互次数

    def predict(self, user_id, user_features, item_features):
        n_interactions = self.user_interactions.get(user_id, 0)

        # 个性化权重:从 0 渐增到 1
        alpha = min(1.0, n_interactions / self.warmup_threshold)

        group_score = self.group_model(user_features, item_features)
        individual_score = self.individual_model(user_features, item_features)

        # 加权融合
        return (1 - alpha) * group_score + alpha * individual_score

    def update(self, user_id):
        self.user_interactions[user_id] = self.user_interactions.get(user_id, 0) + 1
```

#### 7.2.2 元学习(Meta-Learning)冷启动

**核心思想**:学一个"学得快"的初始参数,使得新用户只需要少量样本就能个性化。

**MAML(Model-Agnostic Meta-Learning)** 框架:

$$\theta^* = \arg\min_\theta \sum_{\mathcal{T}_i \sim p(\mathcal{T})} \mathcal{L}_{\mathcal{T}_i}(f_{\theta - \alpha \nabla_\theta \mathcal{L}_{\mathcal{T}_i}(f_\theta)})$$

其中:
- $p(\mathcal{T})$: 任务分布(每个任务 = 一个用户/物品的冷启动)
- $\theta$: 元参数(适合"快速学习"的初始点)
- 内层:在每个任务上做一次梯度下降
- 外层:在验证集上评估,优化初始 $\theta$

```python
class MAMLRecommender(nn.Module):
    """MAML 风格的元学习冷启动"""
    def __init__(self, base_model, inner_lr=0.01, n_inner_steps=5):
        super().__init__()
        self.base_model = base_model
        self.inner_lr = inner_lr
        self.n_inner_steps = n_inner_steps

    def adapt_to_user(self, support_set):
        """在新用户的少量样本上 adapt"""
        # 克隆参数,避免破坏全局模型
        adapted_model = clone_model(self.base_model)
        opt = torch.optim.SGD(adapted_model.parameters(), lr=self.inner_lr)

        for _ in range(self.n_inner_steps):
            loss = compute_loss(adapted_model, support_set)
            opt.zero_grad()
            loss.backward()
            opt.step()

        return adapted_model

    def meta_train_step(self, batch_of_users):
        """元训练:在多个用户的 support/query 上优化"""
        meta_loss = 0
        for user in batch_of_users:
            support = user.support_set   # 少量有标签样本
            query = user.query_set       # 用于评估的样本

            adapted = self.adapt_to_user(support)
            meta_loss += compute_loss(adapted, query)

        # 反向传播到 base_model 的初始参数
        meta_loss /= len(batch_of_users)
        meta_loss.backward()
        self.meta_opt.step()
```

#### 7.2.3 利用属性特征的冷启动

即使新用户没有行为,**人口统计学特征** 仍能提供有价值的信息:

```text
用户属性 → 群体聚类 → "相似用户" 的偏好 → 推荐

示例:
  用户: {age=25, gender=F, city=北京, device=iPhone}
  相似用户群(基于属性): 10000 人
  相似用户群偏好: 美食(35%)、美妆(28%)、穿搭(22%)、旅游(15%)
  → 给新用户推荐 美食 + 美妆 类内容
```

```python
class AttributeBasedRecommender:
    """基于属性的冷启动推荐"""

    def __init__(self, user_attribute_db, item_db):
        self.user_attr_db = user_attribute_db  # 用户属性向量
        self.item_db = item_db                # 物品向量

    def find_similar_users(self, new_user_attrs, k=10000):
        """找到属性最相似的 k 个用户"""
        # 计算余弦相似度
        similarities = []
        for existing_user, attrs in self.user_attr_db.items():
            sim = cosine_similarity(new_user_attrs, attrs)
            similarities.append((existing_user, sim))
        similarities.sort(key=lambda x: -x[1])
        return similarities[:k]

    def recommend(self, new_user_attrs, n_items=10):
        similar_users = self.find_similar_users(new_user_attrs)

        # 聚合相似用户的历史偏好
        item_scores = defaultdict(float)
        for user_id, sim in similar_users:
            for item_id, interaction in self.user_history[user_id].items():
                item_scores[item_id] += sim * interaction.weight

        # 返回 Top-N
        top_items = sorted(item_scores.items(), key=lambda x: -x[1])[:n_items]
        return top_items
```

### 7.3 物品冷启动

#### 7.3.1 内容特征 + 探索机制

**核心**:新物品没有交互,但有**内容特征**(标题/图片/类目/标签)。可以用内容相似度找"邻居物品",再借邻居的历史数据。

```text
新物品 I
   ↓
[内容编码器] → 内容向量 $z_I$
   ↓
[相似度计算] → 找到 Top-K 邻居物品 $I_1, I_2, \ldots, I_K$
   ↓
[邻居历史聚合] → 利用 $I_i$ 的点击数据估计 $I$ 的质量
```

```python
class ContentBasedColdStart:
    """基于内容相似度的物品冷启动"""

    def __init__(self, content_encoder):
        self.encoder = content_encoder  # ResNet/BERT 等

    def get_initial_quality(self, new_item_content, k=20):
        """用邻居物品估计新物品的初始质量"""
        z_new = self.encoder.encode(new_item_content)

        # 找最近的 k 个物品
        distances, neighbor_ids = self.item_index.search(z_new, k)

        # 邻居的 CTR / CVR 平均作为初始质量估计
        neighbor_ctrs = [self.item_stats[i]['ctr'] for i in neighbor_ids]
        initial_ctr = np.mean(neighbor_ctrs)

        # 加权(更相似的邻居权重更大)
        weights = 1.0 / (distances + 1e-6)
        weighted_ctr = np.average(neighbor_ctrs, weights=weights)

        return weighted_ctr
```

#### 7.3.2 Bandit 探索机制

新物品需要在"探索"(给曝光机会)和"利用"(基于已知 CTR 排序)之间平衡。

**典型方案**:
- **固定曝光配额**:新物品前 1000 次曝光**强制曝光**,无论 CTR
- **置信上界(UCB)**:CTR 估计加上不确定性,鼓励探索
- **Thompson Sampling**:从 Beta 分布采样,新物品采样值高(因为方差大)

```python
class ThompsonSamplingColdStart:
    """Thompson Sampling 解决新物品冷启动"""

    def __init__(self):
        self.alpha = defaultdict(lambda: 1)  # 平滑先验
        self.beta = defaultdict(lambda: 1)

    def get_priority(self, item_id):
        """采样后验,采样值越高优先级越高"""
        # Beta(alpha, beta) 的采样
        sample = np.random.beta(self.alpha[item_id], self.beta[item_id])
        return sample

    def update(self, item_id, clicked, shown):
        """观察反馈后更新"""
        if clicked:
            self.alpha[item_id] += 1
        else:
            self.beta[item_id] += 1
```

```python
# 4. 模型蒸馏:用小模型近似大模型
class Distillation:
    def __init__(self, teacher, student, T=3.0, alpha=0.7):
        self.teacher = teacher  # 大模型(冻结)
        self.student = student  # 小模型(训练)
        self.T = T
        self.alpha = alpha

    def loss(self, x, y):
        soft = F.kl_div(
            F.log_softmax(self.student(x) / self.T, dim=-1),
            F.softmax(self.teacher(x) / self.T, dim=-1),
            reduction='batchmean'
        ) * self.T ** 2
        hard = F.cross_entropy(self.student(x), y)
        return self.alpha * soft + (1 - self.alpha) * hard
```

```python
class RecommendationServer:
    """带限流的推荐服务"""
    def __init__(self, model, max_qps=10000, max_latency_ms=100):
        self.model = model
        self.max_qps = max_qps
        self.max_latency_ms = max_latency_ms
        self.semaphore = asyncio.Semaphore(max_qps)

    async def recommend(self, user_id, context):
        async with self.semaphore:
            start = time.time()

            # 召回(向量检索)
            candidates = await self.retrieve(user_id, context, top_k=500)

            # 精排
            scores = self.model.predict(user_id, candidates, context)
            ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])[:50]

            elapsed_ms = (time.time() - start) * 1000
            if elapsed_ms > self.max_latency_ms:
                # 超时:返回召回阶段的粗排结果
                logger.warn(f"slow inference: {elapsed_ms:.1f}ms")
                return candidates[:50]

            return ranked
```

### 9.3 异常检测

#### 9.3.1 突变检测

**场景**:CTR 突然下跌 30%,如何第一时间发现?

```python
import numpy as np
from scipy import stats

class ChangePointDetector:
    """突变点检测器:基于 CUSUM 算法"""

    def __init__(self, threshold=5.0, drift=0.5):
        self.threshold = threshold
        self.drift = drift
        self.sum_pos = 0
        self.sum_neg = 0
        self.mean = None
        self.std = None

    def update(self, x):
        if self.mean is None:
            self.mean = x
            self.std = 1.0
            return False

        # 更新均值/标准差
        z = (x - self.mean) / (self.std + 1e-8)

        # CUSUM 单边检测
        self.sum_pos = max(0, self.sum_pos + z - self.drift)
        self.sum_neg = max(0, self.sum_neg - z - self.drift)

        is_change = (self.sum_pos > self.threshold or
                     self.sum_neg > self.threshold)

        if is_change:
            # 重置
            self.sum_pos = 0
            self.sum_neg = 0

        return is_change

    def update_stats(self, history):
        self.mean = np.mean(history)
        self.std = np.std(history)


# 用法
detector = ChangePointDetector(threshold=4.0, drift=0.5)
detector.update_stats(historical_ctr)

for ctr in real_time_ctr_stream:
    if detector.update(ctr):
        logger.error(f"CTR 突变检测!当前值={ctr:.4f}")
        trigger_alert("CTR sudden drop")
```

#### 9.3.2 漂移检测

```python
class DriftDetector:
    """分布漂移检测:基于 PSI"""

    def __init__(self, baseline_data, threshold=0.25):
        self.baseline = baseline_data
        self.threshold = threshold
        self.bins = np.linspace(baseline_data.min(), baseline_data.max(), 11)
        self.baseline_hist = np.histogram(baseline_data, self.bins)[0] + 1e-6
        self.baseline_dist = self.baseline_hist / self.baseline_hist.sum()

    def compute_psi(self, current_data):
        current_hist = np.histogram(current_data, self.bins)[0] + 1e-6
        current_dist = current_hist / current_hist.sum()

        psi = np.sum(
            (current_dist - self.baseline_dist) *
            np.log(current_dist / self.baseline_dist)
        )

        return psi, self._action(psi)

    def _action(self, psi):
        if psi < 0.1: return "OK"
        if psi < 0.25: return "WARNING"
        return "CRITICAL"
```

### 10.1 在线学习类

#### Q1:什么是分布漂移?GR 模型部署 1 周后效果为什么会衰减?

**参考答案**:

分布漂移(Distribution Shift)指模型训练时的数据分布与部署后实际服务时的数据分布存在偏差。GR 模型部署后效果衰减主要由以下原因导致:

1. **特征分布漂移**:$P(X)$ 变化。新物品涌现(新品上架)、用户设备升级、价格变化等。
2. **条件分布漂移**:$P(Y \mid X)$ 变化。用户的兴趣随时间演化(如季节性时尚变化)。
3. **标签分布漂移**:$P(Y)$ 变化。整体 CTR 因系统优化而上升,校准层失准。

量化方法:**PSI(Population Stability Index)**:
$$\text{PSI} = \sum_{i} (P_i^{\text{train}} - P_i^{\text{test}}) \ln\frac{P_i^{\text{train}}}{P_i^{\text{test}}}$$

PSI < 0.1 稳定;0.1-0.25 轻微漂移,需监控;> 0.25 严重漂移,必须重训。

**评分要点**:
- 能区分 3 种漂移类型 ✓
- 知道 PSI 公式和阈值 ✓
- 能给出衰减的具体原因(物品池变化 40%、兴趣漂移 30%、季节性 15%、系统变化 10%)✓

#### Q2:在线学习(FTRL)和持续学习(Continual Learning)的区别?

**参考答案**:

| 维度 | 在线学习 | 持续学习 |
| :--- | :--- | :--- |
| 主要目标 | 适应数据分布变化 | 适应任务分布变化 |
| 数据假设 | 同任务、新数据 | 新任务、新数据 |
| 核心挑战 | 反馈稀疏、延迟 | 灾难性遗忘 |
| 典型方法 | FTRL、SGD 流式 | EWC、Replay、ProgressiveNN |

FTRL 的核心公式:
$$\theta_{t+1} = \arg\min_\theta \left[ \sum_{s=1}^t \ell(f_\theta(x_s), y_s) + \frac{1}{2\eta}\|\theta - \theta_0\|_2^2 + \lambda_1\|\theta\|_1 \right]$$

持续学习避免灾难性遗忘的方法:
- **EWC(Elastic Weight Consolidation)**:对重要参数加 L2 正则
- **Replay**:重放旧任务的样本
- **渐进式网络**:为每个任务分配独立的子网络

**评分要点**:
- 区分清楚在线 vs 持续 ✓
- 知道 FTRL 的核心思想 ✓
- 能说出至少一种防灾难性遗忘方法 ✓

#### Q3:LinUCB 算法原理?在 GR 中如何应用?

**参考答案**:

LinUCB 是上下文老虎机算法,核心思想是**乐观面对不确定性(OFU)**。对每个候选动作 $a$,维护:
- $A_a \in \mathbb{R}^{d \times d}$:特征-动作的二阶矩矩阵
- $b_a \in \mathbb{R}^d$:特征-奖励的一阶矩

每个动作的 UCB 值:
$$\text{UCB}_a(x) = \hat{\theta}_a^T x + \alpha \sqrt{x^T A_a^{-1} x}$$

其中 $\hat{\theta}_a = A_a^{-1} b_a$。

第一项是期望奖励估计,第二项是**不确定性**,参数 $\alpha$ 控制探索强度。

**在 GR 中的应用**:
- 多通道召回(协同 / 内容 / 热门 / 探索)动态流量分配
- 冷启动期间,新用户/新物品的探索
- 在线实验的快速验证

```python
class LinUCB:
    def select(self, x):
        # 选 UCB 最大的臂
        for a in range(self.n_arms):
            ucb = theta_a @ x + alpha * sqrt(x @ A_inv @ x)
        return argmax(ucb)
```

**评分要点**:
- 能写出 UCB 公式 ✓
- 理解"乐观面对不确定性"思想 ✓
- 知道在 GR 中的具体应用场景 ✓

### 10.2 长期建模类

#### Q4:为什么不能只优化短期指标(如 CTR)?

**参考答案**:

**核心原因**:短期指标与长期目标存在冲突。

| 反例场景 | 短期最优 | 长期后果 |
| :--- | :--- | :--- |
| 标题党文章 | 高 CTR | 用户失去信任,7 日留存↓ |
| 短期爆款推荐 | 高互动 | 信息茧房,用户审美疲劳 |
| 过度个性化 | 高 CTR | 探索不足,长期兴趣挖掘失败 |

**数学刻画**:
- 短期目标:$\text{CTR} = \mathbb{E}[\mathbb{1}\{\text{click}\}]$
- 长期目标:$\text{LTV}(u) = \sum_t \frac{r_t}{(1+d)^t}$

两者**不满足单调关系**,甚至负相关。

**解法**:
1. 多任务学习(同时预测 CTR / 留存 / LTV)
2. 反事实推理(估计推荐对长期价值的影响)
3. 加权融合:精排分数 = $w_1 \cdot \text{CTR} + w_2 \cdot \text{LTV}_{\text{pred}}$

**评分要点**:
- 能举出具体的"短期好长期差"反例 ✓
- 知道 CTR 和 LTV 不单调相关 ✓
- 知道多任务 / 反事实等解法 ✓

#### Q5:LTV 建模的核心难点是什么?

**参考答案**:

LTV(Lifetime Value)建模的三大难点:

1. **反馈延迟**:用户今天点击 → 7 天后是否留存?中间所有反馈如何利用?
   - 解法:标签回填 + TTI(Time-To-Interact)估计

2. **信用分配**:一次会话 10 次曝光,哪几次真正导致留存?
   - 解法:注意力机制 / Shapley 值

3. **状态空间巨大**:用户历史可能数千个事件
   - 解法:HSTU 等长序列模型

**标签回填机制**:
- 第 1 天:曝光 + 点击 → 暂时标为 "label=未知"
- 第 8 天:回填"7 日留存"标签
- 第 30 天:回填"30 日留存"标签

**工程挑战**:
- 存储成本:用户 × 物品 × 时间 三维数据
- 训练时样本权重:旧样本权重应衰减
- 评估指标:LTV 分位数(P50 / P90 / P99)而非均值

**评分要点**:
- 三大难点至少说对 2 个 ✓
- 知道标签回填机制 ✓
- 知道评估指标不只是均值 ✓

#### Q6:HSTU 为什么能处理超长序列?

**参考答案**:

HSTU(Hierarchical Sequential Transduction Unit)是 Meta 2024 提出的 GR 主干,核心创新:

1. **去掉 Softmax**:把 attention 简化为"加权和",省去归一化
   $$\text{HSTU}(Q, K, V) = (QK^T \odot M)V$$
   其中 $M$ 是时间衰减 mask(类似"近期行为更重要")

2. **时间衰减**:显式建模时间间隔
   $$\text{time\_decay}(t_i, t_j) = \exp(-\alpha |t_i - t_j|)$$

3. **残差路径**:额外的 $U$ 路径,保留原始信息
   $$\text{out} = \text{attn}(Q, K, V) + U$$

**复杂度对比**:
- Transformer: $O(L^2 \cdot d)$
- HSTU: $O(L \cdot d)$(去掉二次项)

支持序列长度从 1000 → 10000+。

**评分要点**:
- 知道去掉 Softmax 的关键改进 ✓
- 知道时间衰减机制 ✓
- 能说出复杂度差异 ✓

### 10.3 冷启动类

### 10.4 性能监控类

#### Q9:PSI 是什么?如何计算?阈值怎么定?

**参考答案**:

PSI(Population Stability Index)衡量两分布的偏差,本质是对称 KL 散度。

**公式**:
$$\text{PSI} = \sum_{i=1}^K (P_i^{\text{train}} - P_i^{\text{test}}) \ln\frac{P_i^{\text{train}}}{P_i^{\text{test}}}$$

**计算步骤**:
1. 把训练集分布按分位数分成 10 桶
2. 统计训练集 / 在线集在各桶的频率
3. 按公式求和

**阈值**:
- < 0.1: 分布稳定,无需干预
- 0.1 ~ 0.25: 轻微漂移,监控 + 准备重训
- > 0.25: 严重漂移,立即重训

**实操注意**:
- 看 95 分位数而非均值(避免被稳定特征稀释)
- 关键特征(用户行为/物品类目)单独监控
- 监控频率:小时级或天级

```python
def psi(expected, actual, bins=10):
    breakpoints = np.unique(np.quantile(expected, np.linspace(0, 1, bins + 1)))
    e = np.histogram(expected, breakpoints)[0] + 1e-6
    a = np.histogram(actual, breakpoints)[0] + 1e-6
    return np.sum((a / a.sum() - e / e.sum()) * np.log((a / a.sum()) / (e / e.sum())))
```

#### Q10:Interleaving 和 A/B 测试的区别?为什么大公司偏爱 Interleaving?

**参考答案**:

**本质区别**:

| 维度 | A/B 测试 | Interleaving |
| :--- | :--- | :--- |
| 实验对象 | 用户分成多组,每组看一种模型 | 同一用户看到多种模型结果的**混合** |
| 流量切分 | 整组互斥 | 可重叠 |
| 灵敏度 | 低(用户级方差大) | 高(在同一用户身上比较) |
| 所需样本量 | 大(通常 2-4 周) | 小(通常 1-3 天) |
| 适用阶段 | 最终决策 | 快速迭代 |

**Interleaving 的实现**:

```python
class Interleaving:
    """Team-Draft Interleaving"""
    def merge(self, ranking_A, ranking_B, k=10):
        # 类似体育比赛的"掷硬币"
        team_a, team_b = [], []
        for i in range(k):
            if hash(f"{i}_{self.user_id}") % 2 == 0:
                team_a.append(ranking_A[i])
                team_b.append(ranking_B[i])
            else:
                team_a.append(ranking_B[i])
                team_b.append(ranking_A[i])
        # 合并:奇数位 A,偶数位 B(类似草稿分配)
        merged = []
        for i in range(k):
            if i % 2 == 0:
                merged.append(team_a[i // 2])
            else:
                merged.append(team_b[i // 2])
        return merged

    def attribute(self, clicks, ranking_A, ranking_B):
        """归因:点击来自哪个模型"""
        # 检查点击物品来自 A 还是 B
        a_clicks = sum(c for c in clicks if c in ranking_A)
        b_clicks = sum(c for c in clicks if c in ranking_B)
        return a_clicks, b_clicks
```

**为什么大公司偏爱 Interleaving**:
- **样本效率高**:方差比 A/B 小 10-100 倍
- **快速迭代**:1-3 天就能得出结论
- **对长尾指标友好**:点击、转化等稀疏指标也能快速验证

**注意事项**:
- 不能完全替代 A/B 测试(最终上线仍需 A/B 验证业务指标)
- 实现复杂度高(归因算法、位置偏差处理)

**评分要点**:
- 区分清楚两者本质 ✓
- 知道 Interleaving 的样本效率优势 ✓
- 知道仍需 A/B 做最终验证 ✓

### 10.6 算法原理类

#### Q13:FTRL 的核心思想?为什么适合大规模稀疏特征?

**参考答案**:

**FTRL(Follow The Regularized Leader)** 的核心思想:

$$\theta_{t+1} = \arg\min_\theta \left[ \sum_{s=1}^t g_s \cdot \theta + \frac{1}{2}\sum_{s=1}^t \sigma_s (\theta - \theta_s)^2 + \lambda_1 \|\theta\|_1 \right]$$

其中 $g_s$ 是梯度,$\sigma_s$ 是学习率倒数。

**三大要素**:
1. **累积梯度**:用所有历史梯度,而不只是当前
2. **L2 正则**:防止参数漂移
3. **L1 正则**:产生稀疏性

**为什么适合大规模稀疏**:
- 特征维度可达亿级,但只有少量非零
- L1 正则将大量权重压到 0,实现**稀疏化**
- 在广告 CTR 预估中,FTRL 是工业标准

**对偶坐标下降推导**(以 L1 + L2 为例):

设 $z_t = \sum_{s=1}^t g_s$, $n_t = \sum_{s=1}^t \sigma_s$

$$\theta_{t+1,i} =
\begin{cases}
0 & \text{if } |z_{t,i}| \le \lambda_1 \\
-\frac{1}{n_t}(z_{t,i} - \lambda_1 \cdot \text{sgn}(z_{t,i})) & \text{otherwise}
\end{cases}$$

**评分要点**:
- 能写出公式 ✓
- 知道 L1 + L2 正则的协同作用 ✓
- 知道稀疏性的来源 ✓

#### Q14:Bandit 算法中 UCB 和 Thompson Sampling 的对比?

**参考答案**:

| 维度 | UCB | Thompson Sampling |
| :--- | :--- | :--- |
| 不确定性处理 | 显式加置信区间 | 从后验采样 |
| 计算复杂度 | 中(需要矩阵求逆) | 低(只需采样) |

**UCB 公式**:

**Thompson Sampling**:

**选择建议**:

- 上下文场景(推荐有用户特征):LinUCB

- 需要概率解释:Thompson Sampling

```python
    """影子测试:新模型和旧模型同时推理,但只有旧模型的结果返回给用户"""
    def __init__(self, prod_model, candidate_model):
        self.prod = prod_model
        self.candidate = candidate_model

    def predict(self, x):
        # 主模型:实际返回
        prod_result = self.prod.predict(x)
        # 影子:仅记录,不返回
        try:
            candidate_result = self.candidate.predict(x)
            self.log_shadow(x, prod_result, candidate_result)
        except Exception as e:
            self.log_shadow_error(e)
        return prod_result

    def log_shadow(self, x, prod, candidate):
        """对比两个模型的预测分布"""
        diff = {
            'mean_diff': (candidate - prod).mean(),
            'rank_diff': kendall_tau(candidate.argsort(), prod.argsort()),
            'top10_overlap': topk_overlap(candidate, prod, k=10),
        }
        self.metrics.update(diff)
```

```python
class DiversityReranker:
    """多样性重排"""
    def rerank(self, candidates, scores, top_k=50):
        # Greedy selection with diversity penalty
        selected = []
        category_count = defaultdict(int)

        for _ in range(top_k):
            best_idx = -1
            best_score = -inf
            for i, (item, score) in enumerate(zip(candidates, scores)):
                if i in [s[0] for s in selected]:
                    continue
                # 多样性惩罚:同类别过多扣分
                penalty = 0.1 * category_count[item.category]
                adjusted = score - penalty
                if adjusted > best_score:
                    best_score = adjusted
                    best_idx = i
            selected.append((best_idx, candidates[best_idx]))
            category_count[candidates[best_idx].category] += 1

        return selected
```

#### Q20:推荐系统的"因果推断"为什么重要?

**参考答案**:

**核心问题**:推荐系统学到的是"相关性",不是"因果性"。

**典型反例**:
- 夏天冰淇淋销量高,游泳溺亡也高
- 相关性:冰淇淋 → 溺亡(错!)
- 因果:夏天 → 两者都高

**在 GR 中的具体反例**:

1. **位置偏差**:用户更倾向点击靠前的物品,不是因为更相关,而是因为位置
2. **曝光偏差**:被推荐的物品 CTR 高,不是因为相关,而是因为被推荐
3. **流行度偏差**:热门物品 CTR 高,不是因为更相关,而是因为更显眼
4. **选择偏差**:用户主动搜索的物品(已知偏好)CTR 高,被动推荐的未必

**因果推断方法**:

1. **倾向性评分加权(IPW)**:
   $$\hat{\text{LTV}}_{\text{IPS}} = \frac{1}{N} \sum_i \frac{y_i}{p(x_i)}$$
   其中 $p(x_i)$ 是物品被推荐给用户 $i$ 的概率。

2. **双稳健估计(Doubly Robust)**:
   $$\hat{\tau} = \frac{1}{N}\sum_i \left[\frac{y_i}{p(x_i)} - \frac{\hat{\mu}(x_i)}{p(x_i)} + \hat{\mu}(x_i)\right]$$

3. **Uplift Modeling**:
   - 训练数据:用户被推荐物品 $A$ 的转化 vs 同一用户被推荐 $B$ 的转化
   - 模型目标:$\text{uplift} = P(Y=1 \mid T=1) - P(Y=1 \mid T=0)$

```python
class IPSEstimator:
    """倾向性评分加权估计器"""
    def __init__(self, propensity_model):
        self.propensity = propensity_model

    def estimate_ctr(self, clicks, exposures):
        # IPS 加权
        prop = self.propensity(exposures)  # 物品被推荐的概率
        weighted_clicks = (clicks / prop).mean()
        return weighted_clicks
```

**评分要点**:
- 区分相关性和因果性 ✓
- 知道位置偏差、流行度偏差等具体反例 ✓
- 知道 IPW / Uplift 等方法 ✓

1. **数据优先**: 数据质量决定上限,模型只是逼近这个上限。把 50% 的时间投入到数据理解和清洗上,这条经验被无数实践证明。数据问题往往比模型问题更关键,但也更容易被忽视。

2. **基线先行**: 先用最简单的方法(如逻辑回归、规则)做基线,确认增益是来自方法还是数据。没有强基线的"创新"往往不靠谱。很多看似 fancy 的方法,在强基线面前提升有限。

3. **迭代式改进**: 不要追求一步到位,而是 baseline → 简单改进 → 高级方法 → 调优。每一步都用验证集确认有提升。每一步的提升幅度通常递减,要预期边际收益下降。

4. **失败案例分析**: 重点看模型做错的样本,往往能发现系统性问题。错误样本里藏着模型没学会的知识。把这些样本按错误类型分类,可以发现模型的薄弱点。

5. **A/B 测试**: 在生产环境做对照实验,用业务指标而非离线指标评估。离线指标只是手段,业务指标才是目的。指标可以被优化,但业务目标很难直接优化。

6. **监控与回滚**: 上线后持续监控关键指标,异常时快速回滚。任何线上系统都必须考虑"最坏情况",并预先设计好应对方案。

**8. 常见误解**

对 "第 8 章:GR 的在线与长期" 常见的误解包括:

1. **"模型越复杂越好"**: 实际上,简单模型 + 好数据往往优于复杂模型 + 烂数据。这条法则在实践中反复被验证。

2. **"训练 loss 越低越好"**: 训练 loss 低不代表泛化好,可能过拟合。要看验证集表现,做误差分析。

3. **"指标好就等于业务好"**: 离线指标与在线业务有 gap,必须做 A/B 测试。指标可以被优化,但业务目标很难直接优化。

4. **"新方法一定比旧方法好"**: 新方法通常针对特定场景,在你的场景未必更好。要谨慎评估,先复现,再改进。

5. **"开源即用"**: 开源代码与你的数据/工程栈往往有 gap,需要适配。盲目复用经常踩坑,要理解代码再做改动。
