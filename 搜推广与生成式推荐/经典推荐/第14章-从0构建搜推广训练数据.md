## 本章概述
### 14.1 搜推广训练数据的"生命全周期"

一条训练样本从原始日志到模型消费,需要经过:

```text
原始曝光日志(用户看到了什么)
    ↓
原始点击/转化日志(用户点了什么)
    ↓
日志 Join(把曝光和点击对齐,打标签)
    ↓
特征拼接(拉取用户画像、物品属性、上下文特征)
    ↓
用户行为序列构建(按时间排序,滑动窗口切片)
    ↓
负采样(补充未点击的负样本)
    ↓
编码(LabelEncode / Normalize / Padding)
    ↓
Dataset 包装(变成 PyTorch Dataset)
    ↓
DataLoader 加载(多进程/预取/打乱)
    ↓
喂给模型训练
```

### 14.2 假设的场景与数据格式

假设我们在做**电商搜索推荐**。原始数据包含:

```python
"""
曝光日志(每次推荐用户看到了哪些商品):
exposure_log.tsv
格式: request_id \t user_id \t expose_item_ids \t timestamp
说明: expose_item_ids 是 JSON 数组,表示这次推荐展示给用户的商品列表

点击日志(用户点进了哪些商品):
click_log.tsv
格式: request_id \t user_id \t click_item_id \t dwell_time \t timestamp

用户画像(user_profile):
user_id \t age \t gender \t city \t historical_ctr
说明: historical_ctr = 用户历史点击率(0~1 之间)

物品属性(item_attr):
item_id \t category_id \t price \t title
"""
```

### 14.3 步骤 1:读取原始日志并打标签

**打标签**是搜推广数据 Pipeline 的第一步,也是最容易被忽视的一步。它的含义是:对于一次曝光(`exposure`),把"用户点没点"这个二元信号挖出来——点了 `D=1`,没点 `D=0`。

**为什么要做这一步?**

在原始日志里,数据长这样:
- 曝光日志:`request_id=12345` 这次请求给用户 `u001` 推了 `[i_001, i_002, i_003]` 三个商品
- 点击日志:`request_id=12345` 用户点了 `i_002`

我们要做的"打标签",就是把这两个日志按 `request_id` 对齐,然后生成 3 条样本:
- `(u001, i_001, label=0)` — 曝光但没点
- `(u001, i_002, label=1)` — 曝光且点了
- `(u001, i_003, label=0)` — 曝光但没点

这一步看似简单,实则是后续所有建模的**标签真值来源**。标签错一个,模型学到的"用户偏好"就是噪声。

```python
import json
from collections import defaultdict
from typing import List, Dict, Tuple
from dataclasses import dataclass, field

@dataclass
class Sample:
    """一个训练样本"""
    user_id: str
    item_id: str
    label: int                              # 1=点击,0=未点击
    timestamp: int
    user_features: Dict[str, object] = field(default_factory=dict)
    item_features: Dict[str, object] = field(default_factory=dict)
    history_item_ids: List[str] = field(default_factory=list)    # 用户行为序列

def parse_exposure_tsv(path: str) -> Dict[str, Dict]:
    """读曝光日志,按 request_id 索引"""
    exposures = {}
    with open(path) as f:
        for line in f:
            parts = line.strip().split("\t")
            request_id, user_id, expose_str, ts = parts[0], parts[1], parts[2], int(parts[3])
            expose_items = json.loads(expose_str)           # ["i_001", "i_002", ...]
            exposures[request_id] = {
                "user_id": user_id,
                "ts": ts,
                "expose_items": set(expose_items)           # 转 set 加速查找
            }
    return exposures

def parse_click_tsv(path: str) -> Dict[str, str]:
    """读点击日志,按 request_id → clicked_item_id 映射"""
    clicks = {}
    with open(path) as f:
        for line in f:
            parts = line.strip().split("\t")
            request_id, click_item_id = parts[0], parts[2]
            clicks[request_id] = click_item_id
    return clicks

def label_samples(exposures: Dict, clicks: Dict) -> List[Sample]:
    """打标签:曝光中的 click_item_id → label=1,其他曝光 → label=0"""
    samples = []
    for req_id, exp in exposures.items():
        clicked_item = clicks.get(req_id, None)
        for item_id in exp["expose_items"]:
            label = 1 if item_id == clicked_item else 0
            samples.append(Sample(
                user_id=exp["user_id"],
                item_id=item_id,
                label=label,
                timestamp=exp["ts"]
            ))
    return samples

# 使用
exposures = parse_exposure_tsv("exposure_log.tsv")
clicks = parse_click_tsv("click_log.tsv")
raw_samples = label_samples(exposures, clicks)
print(f"总样本数: {len(raw_samples)}")
# print(f"正样本数(点击): {sum(1 for s in raw_samples if s.label==1)}")
# print(f"负样本数(曝光未点击): {sum(1 for s in raw_samples if s.label==0)}")
# 点击率 ≈ 1%~10%
```

**为什么不用曝光日志就直接随机负采样?**
- 曝光未点击 ≈ 用户**真正看不感兴趣**的商品(而非没见过的),比全局随机好得多
- 全局随机采样的负样本太"容易"了(用户很可能根本不认识这个商品),模型学不到区分能力

---

**文字·公式·代码 1:为什么曝光未点击是"金标准"负样本,以及它和随机负样本的本质差异**

**文字**:曝光未点击 vs 随机负样本,看似都是"用户没点的 item",本质是**两类完全不同的语义**。曝光未点击 = 用户**真的看到了**这个 item(位置曝光),然后**主动放弃**(没点)——这是最强的"用户不感兴趣"信号,代表"看到也不要"。而全局随机负样本 = 用户**根本没看到**这个 item(可能因为召回根本没把它召回出来,或者它从来没进过曝光池)——这种"负样本"对模型来说毫无区分度,因为它根本不在"被考虑"的候选集里。打个比方:让一个从不看科幻片的人评价"三体 vs 霸道总裁文",选三体不选霸总是因为"不喜欢"吗?不,是因为"根本没在追这个剧"。同理,推荐系统**只在曝光池里做排序**,曝光未点击才是有效负样本,其他全是噪声。

**公式**:从信息论角度看,负样本的信息量(对模型学习用户偏好的贡献)差异:

$$
I_{\text{暴露未点击}}(y=0 \mid u, i) = \log \frac{1}{P(\text{未点击} \mid \text{曝光})} \gg I_{\text{全局随机}}(y=0 \mid u, i)
$$

直观解释:全局随机负样本里,大量"用户根本不认识"的 item,模型只需学到"热门 ≠ 正样本"这一条规则就够了,学不到细粒度区分;曝光未点击里,用户已经"扫一眼"过 item 决定不点,模型必须学"为什么不要"——是品类不对?价格不对?图片丑?这些细粒度信号才是模型泛化能力的来源。

**代码**:
```python
# 工业级负样本选择优先级(从高到低):
# 1. 曝光未点击(用户已看,主动放弃) ← 金标准
# 2. 同 session 内的其他曝光 item(用户已扫一眼,主动放弃)
# 3. 同品类/同店铺的其他 item(语义相近,已对比过)
# 4. 热门 item(Batch 内其他样本的正样本,In-Batch Negative)
# 5. 流行度降采样的全量 item(避免长尾灾难)
# 6. 全局随机(几乎不用,会让模型学不到东西)

# 一个反例:训练时如果用全局随机,负样本里 99% 是用户根本"没见过的冷门"
# 模型学到的最优解是"看到陌生 item 就预测低分"
# 一旦线上召回出"用户可能感兴趣但没曝光过"的 item,模型直接判错
```

## 14.3.1 工业样本的字段设计与序列化格式

**文字**:搜推广样本和 CV/NLP 样本长得完全不一样。CV 一张图就是像素矩阵,文本一个 token 就是 int64,但搜推广一条样本是"用户 + 上下文 + 历史 + 物品 + 标签"五元组。推荐要回答的是"在 t 时刻、上下文 c 下,用户 u 看到候选物品 i 时会不会点",少了 history(行为序列)就退化成静态画像打分,少了 context(场景上下文,比如时间、设备、入口位)就分不清同一用户在工作日和周末的偏好差异,少了 item 侧的实时特征又对"刚上架的新品"毫无反应。所以工业样本一定是宽表,字段动辄几十到上百个,不是教科书里写的 `(user_id, item_id, label)` 三元组那么简单。

至于序列化,绝对不要用 `pickle`。`pickle` 出来的二进制文件不可读、不可 diff、跨 PyTorch 版本很容易炸(老 batch 读不出来是常事),对数据血缘和回溯极不友好。工业统一用 Parquet + Arrow Schema,字段名、类型、嵌套结构都写在 schema 里,任何人拿 `pandas.read_parquet` 就能复现,线上线下同源,坏数据一行 grep 就能定位。

**公式**:
```text
Sample_size = User_id(8B) + Item_id(8B) + Label(1B) + Context(16B)
            + History_ids(20×4B) + 32 稀疏特征(32×4B) ≈ 217 bytes
压缩后单条 ≈ 60~80 bytes,1 亿样本 ≈ 6~8 GB;比 pickle 节省 5~10 倍
```

**代码**:
```python
import pyarrow as pa
import pyarrow.parquet as pq

# 工业搜推广样本的标准 schema(必须有 schema,不能裸存)
sample_schema = pa.schema([
    ("user_id", pa.int64()),
    ("item_id", pa.int64()),
    ("label", pa.int8()),                          # 0/1 二分类
    ("timestamp", pa.int64()),                     # 毫秒级,用于时间切分
    ("context", pa.struct([                         # 场景上下文,固定 5 维
        ("hour", pa.int8()), ("device", pa.string()),
        ("page", pa.string()), ("position", pa.int8()),
        ("ab_tag", pa.string()),
    ])),
    ("history_ids", pa.list_(pa.int32())),          # 变长行为序列
    ("user_features", pa.map_(pa.string(), pa.float32())),
    ("item_features", pa.map_(pa.string(), pa.float32())),
])
pq.write_table(pa.table.from_pandas(df, schema=sample_schema),
               "rec_sample.parquet", compression="zstd")
```

### 14.4 步骤 2:加载用户/物品特征

**为什么需要"加载特征"这一独立步骤?**

原始样本只有 `(user_id, item_id, label, timestamp)`,这四列对模型来说信息量太薄——模型不知道"用户是北京 25-30 岁女性,还是广州 40+ 男性",也不知道"item 是 1000 元的连衣裙,还是 5 万元的名牌包"。这些**用户画像**(user profile)和**物品属性**(item attributes)是离线 ETL 提前算好的"静态特征",数据 Pipeline 必须把它们 join 到样本上,模型才能学到"用户 × 物品"的细粒度匹配。

**两个关键的工程细节**:

1. **特征缺失怎么办?** 工业上永远不要让模型见到"空值"——会立刻 NaN。必须做兜底(`UNK` 或 `0.0`),否则一行脏数据就毁掉一个 batch。
2. **特征是动态更新的**。用户昨天没点击,今天点了 3 个 item,这个"过去 7 天点击数"特征就要从 0 变成 3。Pipeline 必须按时序更新(常用 T-1 凌晨 Spark 跑批算昨天的),线上线下的"特征版本号"必须严格对齐,否则就是 14.9.1 节的"特征穿越"灾难。

```python
def load_user_profile(path: str) -> Dict[str, Dict]:
    """加载用户画像,user_id → {age, gender, city, historical_ctr}"""
    profiles = {}
    with open(path) as f:
        for line in f:
            parts = line.strip().split("\t")
            uid = parts[0]
            profiles[uid] = {
                "age": int(parts[1]) if parts[1] else None,
                "gender": parts[2],
                "city": parts[3],
                "historical_ctr": float(parts[4]) if parts[4] else 0.0,
            }
    return profiles

def load_item_attr(path: str) -> Dict[str, Dict]:
    """加载物品属性,item_id → {category_id, price, title}"""
    attrs = {}
    with open(path) as f:
        for line in f:
            parts = line.strip().split("\t")
            iid = parts[0]
            attrs[iid] = {
                "category_id": parts[1],
                "price": float(parts[2]) if parts[2] else 0.0,
                "title": parts[3],
            }
    return attrs

def join_features(samples: List[Sample], user_profiles: Dict, item_attrs: Dict):
    """给样本拼接特征(原地修改)"""
    for sample in samples:
        sample.user_features = user_profiles.get(sample.user_id, {}).copy()
        sample.item_features = item_attrs.get(sample.item_id, {}).copy()
    # 注意:如果某些特征缺失了,需要兜底,否则后面编码会报错

user_profiles = load_user_profile("user_profile.tsv")
item_attrs = load_item_attr("item_attr.tsv")
join_features(raw_samples, user_profiles, item_attrs)
```

### 14.5 步骤 3:构建用户行为序列

这是搜推广样本构造里最核心、最容易出错的步骤。

**为什么用户行为序列是"灵魂特征"?**

传统推荐靠"用户画像"打静态分数(年龄、城市、消费力),但这些是慢变量——一个用户 3 个月前是 25 岁,3 个月后还是 25 岁,画像特征几乎没有信息量。真正反映用户**当前意图**的是"过去 30 分钟/1 小时/1 天"的行为:刚搜过"iPhone 15 壳"的用户,接下来 5 分钟最可能点"手机壳",而不是"洗衣液"。**行为序列**就是这个"近期意图"的最强信号源。

用户行为序列的数学定义(必须满足"无未来泄漏"):

$$H_u^{(t)} = \{i_k \mid (t_k, i_k) \in \text{click\_log}(u),\ t_k < t_{\text{request}}\}$$

即只包含请求发生时刻 $t_{\text{request}}$ **之前**的历史点击。截断策略:取最近 $T$ 条,丢弃更早的(时效性先验 $w_k \propto e^{-\lambda(t_{\text{req}} - t_k)}$)。

```python
def build_user_history(click_log_path: str) -> Dict[str, List[Tuple[int, str]]]:
    """从全量历史点击日志构建用户行为序列

    返回: user_id → [(timestamp, item_id), ...] 按时间升序
    """
    history = defaultdict(list)
    with open(click_log_path) as f:
        for line in f:
            parts = line.strip().split("\t")
            request_id, user_id, click_item_id, _, ts = parts[0], parts[1], parts[2], parts[3], int(parts[4])
            history[user_id].append((ts, click_item_id))
    # 按时间排序,每个用户的行为串成序列
    for user_id in history:
        history[user_id].sort(key=lambda x: x[0])      # 升序,最旧→最新
    return dict(history)

def sample_sequence(history: List[Tuple[int, str]], max_len: int = 50) -> List[str]:
    """对行为序列做采样

    策略:保留最近的 max_len 个行为(工业界最常用)
    为什么取最近? 因为用户最近的兴趣对下一次行为影响最大
    """
    if len(history) <= max_len:
        return [item_id for _, item_id in history]
    return [item_id for _, item_id in history[-max_len:]]

# 在 label_samples 后
user_history = build_user_history("click_log.tsv")
for sample in raw_samples:
    hist = user_history.get(sample.user_id, [])
    sample.history_item_ids = sample_sequence(hist, max_len=50)
```

### 14.6 步骤 4:负采样策略

**为什么需要负采样?**

如果只用"曝光未点击"作为负样本,数量通常是不够的(因为推荐系统只推荐了少量商品)。需要额外补充。

**核心矛盾**:CTR 预估的"正负样本比"是天然不均衡的——一次曝光里 1 个点击可能对应 50-100 个曝光未点击,正负比 1:50 ~ 1:100;但模型训练理想是 1:3 ~ 1:5。负样本不够 → 模型对负样本过拟合 → 预测概率整体偏低;负样本太多 → 模型学不到正样本的特征 → AUC 反而下降。所以**配比是个超参**,需要按业务调优,1:3 到 1:10 是搜推广常见甜区。

```python
import random

def negative_sampling(samples: List[Sample],
                      all_item_ids: set,
                      neg_ratio: float = 3.0) -> List[Sample]:
    """
    补充负样本策略:
    1. 对每个正样本,补充 neg_ratio 个随机负样本
    2. 负样本从全量商品池中采样,但排除用户已经点过的

    为什么 neg_ratio=3?
    工业界经验:1 个正样本配 3~5 个负样本效果最好
    """
    clicked_items_per_user = defaultdict(set)
    for s in samples:
        if s.label == 1:
            clicked_items_per_user[s.user_id].add(s.item_id)

    extra_negatives = []
    for s in samples:
        if s.label == 0:
            continue                                # 曝光未点击已经是负样本
        user_clicked = clicked_items_per_user[s.user_id]
        # 从全量中排除用户点过的
        candidate_negatives = list(all_item_ids - user_clicked)
        n_needed = int(neg_ratio)
        if len(candidate_negatives) < n_needed:
            n_needed = len(candidate_negatives)
        if n_needed > 0:
            neg_items = random.sample(candidate_negatives, n_needed)
            for neg_item in neg_items:
                # 复制正样本的所有特征,只改 item_id 和 label
                neg_sample = Sample(
                    user_id=s.user_id,
                    item_id=neg_item,
                    label=0,
                    timestamp=s.timestamp,
                    user_features=s.user_features.copy(),
                    item_features={},               # 负样本可能没有物品特征,后面会兜底
                    history_item_ids=s.history_item_ids.copy()
                )
                extra_negatives.append(neg_sample)
    return samples + extra_negatives

# 收集所有出现的 item_id
all_items = set()
for s in raw_samples:
    all_items.add(s.item_id)

samples_with_neg = negative_sampling(raw_samples, all_items, neg_ratio=3.0)
print(f"负采样后总样本数: {len(samples_with_neg)}")
```

**为什么需要额外负采样?**
```text
原始曝光: 点击率 = 正:负 = 1:50 ~ 1:100
模型对负样本过拟合 → 预测概率整体偏低
补充 3 倍负样本后 → 1:200~1:400
模型对负样本更"严厉" → 正样本能脱颖而出
```

#### 14.6.1 六种负采样策略深度对比

**文字**:负采样策略决定了模型能从哪种"对比"中学习。简单负样本（随机）让模型学不到细粒度区分；过难负样本（极端 Hard Negative）可能破坏正样本的训练信号。工业界最佳实践是混合策略：曝光未点击 + Batch Negative + 有度 Hard Negative。

**公式**:Batch Softmax 损失与采样偏差纠正

$$\mathcal{L}_{\text{Batch-Softmax}}(u, i^+) = -\log \frac{e^{s(u, i^+)/\tau}}{\sum_{j \in \mathcal{B}} e^{s(u, i_j)/\tau}}$$

**偏差问题**：Batch 内热门物品出现概率 $\propto p_j$（流行度），导致热门物品频繁作为负样本，相当于对热门物品的相似度打了折扣。谷歌 YouTube（2019）提出**流行度纠正**：

$$\tilde{s}(u, i_j) = s(u, i_j) - \log p_j \quad \text{(从相似度中减去热门度的对数)}$$

纠正后的等效损失使所有物品在采样分布中"地位均等"。

**代码（纠正版 Batch Softmax）**:

```python
def batch_softmax_loss_corrected(user_emb, item_emb, item_freqs, temperature=0.07):
    """
    带流行度纠正的 Batch Softmax Loss
    item_freqs: [B] — 每个 item 在训练集中的频率(归一化概率)
    """
    B = user_emb.size(0)
    logits = torch.matmul(user_emb, item_emb.T) / temperature   # [B, B]

    # 流行度纠正: 减去 log(p_j)
    log_freqs = torch.log(item_freqs + 1e-10).unsqueeze(0)      # [1, B]
    logits = logits - log_freqs                                   # 广播

    labels = torch.arange(B, device=user_emb.device)
    return F.cross_entropy(logits, labels)
```

| 策略 | 原理 | 难度 | 计算代价 | 效果 | 搜推广常用? |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1. 全局随机** | 从全量物品池均匀采样 | 极容易 | O(1) | ❌太简单,模型学不到区分 | 几乎不用 |
| **2. 曝光未点击** | 用户看到但没点的物品 | 中 | O(1)(已有点击表) | ✅ **基准策略** | **★★★★★** |
| **3. 热门采样(Batch Neg)** | 在一个 batch 内,其他样本的正物品作为当前负样本 | 容易 | O(1)(自带) | ✅ 简单高效,双塔标配 | **★★★★★** |
| **4. 难度分层采样** | 按模型预测分数分桶:简单/中等/困难 | 高 | O(n)² | ✅✅ AUC 最高 | **★★★★** |
| **5. 对抗采样(Generator)** | 用一个生成网络专门产"最像正样本"的负样本 | 极高 | 训练双倍 | ✅✅ 极致效果 | **★★**(太贵) |
| **6. 混合策略** = 2+3+4 | 按比例混合曝光未点击 + Batch Neg + Hard | 中 | 可控 | ✅✅ 工业界冠军 | **★★★★★** |

```python
# 策略 3:Batch Negative Sampling(双塔模型的标准训练方法)
# 原理:在双塔模型中,user_emb 和 item_emb 分别编码
# batch 内每个 user 的正 item 是配对的,剩下的 B-1 个 item 就是负样本
# 不需要额外采样,计算代价为 0!

def batch_softmax_loss(user_emb, item_emb, temperature=0.07):
    """
    双塔模型的 Batch Softmax 损失。

    输入:
        user_emb: [B, D] — 塔 1 输出
        item_emb: [B, D] — 塔 2 输出

    原理:
        logits[i][j] = user_emb[i] · item_emb[j] / temperature
        目标:对角线(i=j)是正样本,其他是负样本
        所以 label = torch.arange(B)
    """
    B = user_emb.size(0)

    # 相似度矩阵 [B, B]
    logits = torch.matmul(user_emb, item_emb.T) / temperature

    # 对角线是正样本
    labels = torch.arange(B, device=user_emb.device)

    # 交叉熵:对每个 user,正确 item 在 B 个候选中排名第 1
    loss = F.cross_entropy(logits, labels)
    return loss

# 为什么 Batch Neg 效果好?
# 采样偏差小:当前 batch 的物品通常是"热门物品"
# 模型需要学会从热门物品中找出用户真正喜欢的 → 区分度更高

# 策略 4:Hard Negative Mining(困难负样本挖掘)
def hard_negative_mining(model, user_features, candidate_pool, n_hard=5):
    """
    用当前模型预测,挑出"分数最高但不是正样本"的物品。
    为什么有效?
    简单的负样本(完全不相关)模型一眼就看出是负的,学不到东西。
    困难的负样本(看起来像正)能迫使模型学到真正的区分边界。
    """
    model.eval()
    hard_negatives = []
    with torch.no_grad():
        # 对候选池打分
        scores = []
        for item in candidate_pool:
            score = torch.sigmoid(model(user_features, item))
            scores.append((score.item(), item))
        # 按分数从高到低排
        scores.sort(key=lambda x: -x[0])
        # 前 n_hard 个"看起来最像正"的就是 hard negative
        hard_negatives = [item for _, item in scores[:n_hard]]
    return hard_negatives

# 策略 6:混合策略(工业界最好的实践)
def mixed_negative_sampling(positive_samples, exposure_samples,
                             item_pool, batch_neg_ratio=0.5):
    """
    混合策略:batch_neg_ratio=0.5 表示 50% 负样本来自 batch neg
    50% 来自曝光未点击 + 困难负样本

    为什么混合最好?
    - 曝光未点击 → 保证基础区分度
    - Batch Neg → 引入分布偏差纠正
    - Hard Neg → 提升训练难度
    三种信号互补,模型学到的东西最全面
    """
    negatives = []
    # 50% 曝光未点击
    n_exposure = int(len(positive_samples) * 0.5)
    negatives.extend(random.sample(exposure_samples, min(n_exposure, len(exposure_samples))))

    # 30% 热门物品(可以用 top-K 热门物品采样,模拟 batch 分布)
    n_popular = int(len(positive_samples) * 0.3)
    # ... 从热门池采样

    # 20% 困难负样本
    n_hard = len(positive_samples) - n_exposure - n_popular
    # ... 用模型打分的 hard negative

    return negatives
```

**负采样的 "甜区" 经验值**:

```python
# 在 CTR 预估中:
# batch_size = 1024, 1 个正配 3~5 个负 → 最佳
#
# 在双塔召回中:
# batch_size = 2048, 2 塔各自编码后做 batch softmax
# 每个 batch 自动有 2047 个负样本(其他 sample 的 item)
#
# 在生成式推荐中:
# 把"全部 item"都 softmax 出来 → 计算量太大
# 只采样部分负样本 → 用 sampled softmax
```

#### 14.6.2 为什么随机负采样是长尾灾难:流行度降采样与 Batch Neg

**文字**:教科书里常写"随机负采样",工业里几乎没人直接用。原因是双塔召回里候选池动辄 1000 万到 1 亿,而长尾物品占了 99% 的量。假设物品流行度服从 Zipf 分布,头部 1% 的物品贡献了 50% 的曝光,如果负采样走"全量均匀采样",模型训练时 99% 的负样本梯度都被压在那一小撮热门物品上,长尾物品的 embedding 几乎学不到区分信号(因为它们被采到的概率太低),线上召回几乎全是热门,推荐系统直接变成"复读机"。

工业解法是两步:第一步用"流行度降采样"压一压热门物品的曝光概率,经典做法是 Google 在 word2vec 里提的 `P(neg) \propto pop^0.75`(0.75 这个指数是经验值,小于 1 就是降采样);第二步配合"Batch 内负采样",在双塔模型里 batch 内其他样本的正物品天然就是负样本,采样偏差小、计算代价几乎为 0(因为反正都要算 batch 内的相似度矩阵)。混合策略一般配比是 50% 曝光未点击 + 30% 流行度降采样 + 20% 困难负样本。

**公式**:
```text
P_neg(i) ∝ pop(i)^0.75
# pop(i) 是物品 i 在训练集里的曝光/点击频次,归一化到 [0,1]
# 指数 0.75 是经验调参,Google word2vec 论文默认值
# 0.0 = 全量均匀,1.0 = 严格按流行度采样(不可用,长尾 0 曝光)
```

**代码**:
```python
import numpy as np

def popularity_downsample_sampler(item_freqs: dict, exponent: float = 0.75):
    """流行度降采样:从全量物品池按 pop^0.75 加权采样负样本"""
    items = np.array(list(item_freqs.keys()))
    freqs = np.array([item_freqs[i] for i in items], dtype=np.float64)
    probs = freqs ** exponent
    probs = probs / probs.sum()
    return items, probs

def mixed_neg_sampler(user, pos_item, all_items, item_freqs,
                       exposure_unclicked, batch_items,
                       batch_neg_ratio: float = 0.5,
                       n_neg: int = 5):
    """
    混合负采样:batch_neg_ratio=0.5 表示 50% 来自 batch 内其他样本的正物品
    其余从"曝光未点击"和"流行度降采样池"中按 1:1 混合
    """
    n_batch = int(n_neg * batch_neg_ratio)
    n_pop = (n_neg - n_batch) // 2
    n_exp = n_neg - n_batch - n_pop
    items, probs = popularity_downsample_sampler(item_freqs)
    sampled_pop = np.random.choice(items, size=n_pop, p=probs, replace=True)
    negs = list(batch_items[:n_batch]) + list(sampled_pop) \
         + list(np.random.choice(exposure_unclicked, size=n_exp, replace=True))
    return [(user, neg, 0) for neg in negs]
```

### 14.7 步骤 5:特征编码(LabelEncode + Normalize)

这是整个 Pipeline 中最"搜推广"的阶段。

**特征编码的核心目标**:把各种类型的原始特征(字符串 ID、整数 ID、浮点数)统一转换成 PyTorch 能直接吃的 `torch.Tensor`。**离散特征**(string、int)走 `LabelEncode` → 整数 ID → Embedding 查表;**连续特征**(price、age)走 `Z-Score Normalize` → 标准正态分布;**变长序列**(用户历史点击列表)走 `Truncate + Pad + Mask`。

**为什么 LabelEncode 不能用 `sklearn.preprocessing.LabelEncoder`?**

`sklearn` 的 `LabelEncoder` 默认按出现顺序编码,训练集 city="北京" 编码 0,测试集 city="上海" 编码 1,看似正常,但**编码值会泄露"出现顺序"信息**——模型可能学到"编码大的 city 重要"这种虚假模式。正确做法是**按频次排序**编码:高频出现的是热门(数值小),低频出现的是冷门(数值大),频率本身就是信息。另外,`LabelEncoder` 不支持"训练集外的值",`UNK` 必须手动加,工业上一般是 `0=PAD, 1=UNK, 2=开始`,所有 `fit` 都基于训练集。

```python
from sklearn.preprocessing import StandardScaler
import joblib
import numpy as np

class FeatureEncoder:
    """
    搜推广特征编码器。
    维护所有离散特征的词表映射,以及连续特征的 scaler。
    """
    def __init__(self):
        # 离散特征编码器
        self.cat_encoders = {}          # feature_name → {value → id}
        # 连续特征 scaler
        self.num_scalers = {}           # feature_name → StandardScaler
        # 特殊 token ID
        self.PAD_ID = 0
        self.UNK_ID = 1
        # 特殊 token
        self.special_ids = {"<PAD>": 0, "<UNK>": 1}

    def fit_categorical(self, feature_name: str, values: List[str], max_vocab: int = None):
        """训练一个离散特征编码器(LabelEncoder)"""
        # 统计频次
        from collections import Counter
        counter = Counter(values)
        # 按频次排序,高频在前
        sorted_items = sorted(counter.items(), key=lambda x: -x[1])
        if max_vocab:
            sorted_items = sorted_items[:max_vocab - len(self.special_ids)]

        # 构建映射
        mapping = {}
        idx = len(self.special_ids)     # 从 2 开始,0=PAD,1=UNK
        for token, count in sorted_items:
            if token not in mapping and token not in self.special_ids:
                mapping[token] = idx
                idx += 1
        self.cat_encoders[feature_name] = mapping
        return self

    def encode_categorical(self, feature_name: str, value) -> int:
        """编码一个离散值"""
        mapping = self.cat_encoders.get(feature_name, {})
        return mapping.get(value, self.UNK_ID)

    def fit_numerical(self, feature_name: str, values: List[float]):
        """训练连续特征 scaler(Z-Score)"""
        scaler = StandardScaler()
        values_arr = np.array(values, dtype=np.float32).reshape(-1, 1)
        scaler.fit(values_arr)
        self.num_scalers[feature_name] = scaler
        return self

    def encode_numerical(self, feature_name: str, value: float) -> float:
        """编码一个连续值(Z-Score 归一化 + 缺失填充)"""
        if value is None or np.isnan(value) or value == float('inf'):
            value = 0.0                     # 缺失兜底
        scaler = self.num_scalers.get(feature_name)
        if scaler is None:
            return value
        return scaler.transform(`value`)[0, 0]

    def save(self, path: str):
        """保存编码器到磁盘(推理时加载用同一份!)"""
        joblib.dump({
            "cat_encoders": self.cat_encoders,
            "num_scalers": self.num_scalers,
        }, path)

    def load(self, path: str):
        data = joblib.load(path)
        self.cat_encoders = data["cat_encoders"]
        self.num_scalers = data["num_scalers"]
        return self

def train_encoder(samples: List[Sample]) -> FeatureEncoder:
    """在整个训练集上学习编码器"""
    encoder = FeatureEncoder()

    # 收集离散特征的所有取值
    user_genders = [s.user_features.get("gender", "<UNK>") for s in samples]
    user_cities = [s.user_features.get("city", "<UNK>") for s in samples]
    item_categories = [s.item_features.get("category_id", "<UNK>") for s in samples]

    encoder.fit_categorical("gender", user_genders, max_vocab=10)
    encoder.fit_categorical("city", user_cities, max_vocab=500)
    encoder.fit_categorical("category_id", item_categories, max_vocab=10000)

    # 收集连续特征
    ages = [s.user_features.get("age") for s in samples if s.user_features.get("age") is not None]
    prices = [s.item_features.get("price") for s in samples if s.item_features.get("price") is not None]
    ctrs = [s.user_features.get("historical_ctr") for s in samples if s.user_features.get("historical_ctr") is not None]

    if ages: encoder.fit_numerical("age", ages)
    if prices: encoder.fit_numerical("price", prices)
    if ctrs: encoder.fit_numerical("historical_ctr", ctrs)

    return encoder

def encode_sample(sample: Sample, encoder: FeatureEncoder, max_seq_len: int) -> Dict:
    """把一个 Sample 编码成 PyTorch Tensor 字典"""

    # ==== 离散特征:字符串 ID → int ID ====
    user_id_encoded = encoder.encode_categorical("user", sample.user_id)
    item_id_encoded = encoder.encode_categorical("item", sample.item_id)
    gender_encoded = encoder.encode_categorical("gender",
        sample.user_features.get("gender", "<UNK>"))
    city_encoded = encoder.encode_categorical("city",
        sample.user_features.get("city", "<UNK>"))
    category_encoded = encoder.encode_categorical("category_id",
        sample.item_features.get("category_id", "<UNK>"))

    # ==== 连续特征:归一化 ====
    age_encoded = encoder.encode_numerical("age", sample.user_features.get("age"))
    price_encoded = encoder.encode_numerical("price", sample.item_features.get("price"))
    ctr_encoded = encoder.encode_numerical("historical_ctr", sample.user_features.get("historical_ctr"))

    # ==== 行为序列:采样 + padding + mask ====
    seq_ids = [encoder.encode_categorical("item", item) for item in sample.history_item_ids]
    # 截断
    seq_ids = seq_ids[:max_seq_len]
    # 右侧 padding
    seq_len = len(seq_ids)
    seq_ids = seq_ids + [encoder.PAD_ID] * (max_seq_len - seq_len)
    seq_mask = [1] * seq_len + [0] * (max_seq_len - seq_len)

    return {
        "user_id": user_id_encoded,            # int
        "item_id": item_id_encoded,            # int
        "gender": gender_encoded,              # int
        "city": city_encoded,                  # int
        "category": category_encoded,          # int
        "age": age_encoded,                    # float
        "price": price_encoded,                # float
        "ctr": ctr_encoded,                    # float
        "history_ids": seq_ids,                # [max_seq_len]
        "history_mask": seq_mask,              # [max_seq_len]
        "label": sample.label,                 # int
    }
```

#### 14.7.1 工业特征的"四层架构":为什么 Embedding 特征不能在 raw parquet 里算

**文字**:搜推广特征和 CV/NLP 不一样,不是"原始像素"或"原始 token"直接灌进模型就行,工业上习惯把特征分成四层。**原始特征**(raw):直接从日志来的 age、city、item_id 这种,数量稳定但信号弱。**统计特征**(derived):对原始特征按时间窗聚合,比如"用户 7 天点击数""物品 30 天 CTR",这层是 CTR 模型的"杀手锏",AUC 主要靠它。**交叉特征**(crossing):两个或多个特征的笛卡尔积,比如 `gender \times category`、`age_bucket \times city`,数量爆炸但能捕捉强相关。**Embedding 特征**(embedding):把高维稀疏 ID 用预训练或训练中得到的稠密向量表示,这是深度模型的核心。

为啥 Embedding 特征不能在 raw parquet 里直接算好存进去?因为分布式训练时,各 worker 算 Embedding 必须共享一套 embedding table,不能各算各的;而且 Embedding 在训练中一直在更新,如果你在 raw 阶段把 Embedding 固化到 parquet 里,等训练两轮后那批 Embedding 就过时了。所以工业规矩:前 3 $\text{层(原始/统计/交叉)}$可以在 Spark 离线算好写 Parquet,Embedding 层必须在训练时实时 lookup,FeatureConfig 里要明确标清楚每层走哪条路径,这样数据团队和算法团队的接口才不会乱。

**公式**:
```text
Feature_count = Raw(100) × Derived(10) × Crossing(20) × Embed_dim(64)
             ≈ 100 × 10 × 20 = 20,000 稀疏特征
             × 64 维 = 1,280,000 维稠密输入
线上推理单次 query 的特征总耗时 < 10ms(否则用户等不及)
```

**代码**:
```python
from dataclasses import dataclass, field
from typing import List, Dict

@dataclass
class FeatureConfig:
    """搜推广特征的四层配置:每层独立声明计算路径"""
    raw_features: List[str] = field(default_factory=lambda: ["user_id", "item_id", "city"])
    derived_features: Dict[str, str] = field(default_factory=lambda: {
        "user_7d_click": "spark_sql",       # 离线 Spark 聚合
        "item_30d_ctr": "spark_sql",
    })
    crossing_features: List[tuple] = field(default_factory=lambda: [
        ("gender", "category_id"),          # 笛卡尔积,产生 SparseTensor
        ("age_bucket", "city"),
    ])
    embedding_features: Dict[str, int] = field(default_factory=lambda: {
        "item_id": 64,                       # 64 维,训练时实时 lookup
        "user_id": 32,
    })
    # 关键约束:Embedding 特征绝不能 offline 算好存 Parquet,会过时
    def validate(self):
        for name, dim in self.embedding_features.items():
            assert dim > 0 and dim <= 256, f"{name} dim 不合理"
        assert len(self.raw_features) + len(self.derived_features) < 500
```

### 14.8 步骤 6:Dataset + DataLoader 包装

**为什么需要 Dataset 和 DataLoader?**

PyTorch 的训练是"按 batch 走"的,模型一次吃 1024 个样本,但你的样本在内存里是 List[Dict] 形式。`Dataset` 是"按索引取单条样本"的抽象,`DataLoader` 是"多进程取 batch、shuffle、prefetch"的工程包装。这一步看似是"胶水代码",但有几个隐藏陷阱:

1. **`num_workers > 0` 时,主进程的内存会被复制到子进程**。如果样本很大(几 GB),内存会爆。常见解法是用 `IterableDataset` + 流式读取 parquet。
2. **`pin_memory=True` 把 tensor 锁在 CPU 的"固定内存",这样 `.to(device, non_blocking=True)` 可以走 DMA 直传 GPU,加速显著**。但锁页内存不能 swap,内存紧张时反而会 OOM。
3. **`prefetch_factor=2` 表示每个 worker 预取 2 个 batch,GPU 算 batch N 时,worker 已经在准备 batch N+1**。这是隐藏的"性能加速器",但对变长序列要小心——预取出来的 batch 长度信息可能跟当前 step 不一致。
4. **`drop_last=True` 丢弃最后不足一个 batch 的样本**。DDP 分布式训练必须 drop_last,否则各卡 batch 数对不上会卡住。

```python
import torch
from torch.utils.data import Dataset, DataLoader

class RecSysDataset(Dataset):
    """搜推广 Dataset:把编码后的样本列表包装成 PyTorch Dataset"""
    def __init__(self, samples: List[Dict]):
        self.samples = samples

    def __len__(self):
        return len(self.samples)

    def __getitem__(self, idx):
        s = self.samples[idx]
        return {
            "user_id": torch.tensor(s["user_id"], dtype=torch.long),
            "item_id": torch.tensor(s["item_id"], dtype=torch.long),
            "gender": torch.tensor(s["gender"], dtype=torch.long),
            "city": torch.tensor(s["city"], dtype=torch.long),
            "category": torch.tensor(s["category"], dtype=torch.long),
            "age": torch.tensor(s["age"], dtype=torch.float32),
            "price": torch.tensor(s["price"], dtype=torch.float32),
            "ctr": torch.tensor(s["ctr"], dtype=torch.float32),
            "history_ids": torch.tensor(s["history_ids"], dtype=torch.long),
            "history_mask": torch.tensor(s["history_mask"], dtype=torch.long),
            "label": torch.tensor(s["label"], dtype=torch.float32),
        }

def collate_fn(batch):
    """把列表拼成 batch tensor"""
    out = {}
    for key in batch[0].keys():
        out[key] = torch.stack([b[key] for b in batch])
    return out

def create_dataloader(samples: List[Dict], batch_size: int = 1024, shuffle: bool = True, num_workers: int = 4):
    dataset = RecSysDataset(samples)
    loader = DataLoader(
        dataset,
        batch_size=batch_size,
        shuffle=shuffle,
        num_workers=num_workers,
        collate_fn=collate_fn,
        pin_memory=True,
        prefetch_factor=2,
        persistent_workers=True if num_workers > 0 else False,
        drop_last=True,
    )
    return loader
```

#### 14.8.1 数据切分:为什么按 user_id 随机切分是"时间穿越"灾难

**文字**:数据切分是搜推广里最容易被新人忽视、却最致命的一步。如果按 `train_test_split` 的 `random_state` 随机切 7:2:1,看似公平,实则埋了大雷:同一个用户昨天的曝光和今天的曝光会被分到 train 和 val 里,val 集的"未来信息"已经在 train 集里"被看到了"。更糟的是,行为序列特征会把"未来点击的 item"塞进 val 样本的 history 里,模型离线 AUC 虚高 5~10 个百分点,一上线就跌穿地板,数据科学家查了 3 天也查不出原因,最后发现是切分方式错了。

工业的硬规矩是按时间戳切分:先在时间轴上选两个切点 T1、T2,T1 之前是 train,T1~T2 之间是 val,T2 之后是 test(常用 7:2:1,val 和 test 必须严格晚于 train,绝不能有任何重叠)。这样切完之后,val 样本的 history 只能来自 T1 之前的用户行为(做法是构造样本时强制取 `t_request` 之前的点击),彻底切断时间穿越。还有个细节:val/test 用的行为序列要在 T1/T2 时刻"冻结"快照,不能边训边更新,否则训着训着信息就漏了。

**公式**:
```text
Train: { s | s.timestamp < T1 }
Val:   { s | T1 ≤ s.timestamp < T2 }
Test:  { s | s.timestamp ≥ T2 }
典型配比 7:2:1,T1 = 训练数据 70% 分位时间,T2 = 90% 分位时间
强制约束:val/test 样本的 history 序列只取 s.timestamp 之前的点击
```

**代码**:
```python
from pyspark.sql import functions as F

def time_based_split(df, train_ratio=0.7, val_ratio=0.2):
    """PySpark 时间切分:按 timestamp 全局排,选两个切点"""
    quantiles = df.approxQuantile("timestamp",
        [train_ratio, train_ratio + val_ratio], 0.001)
    t1, t2 = quantiles[0], quantiles[1]
    train = df.filter(F.col("timestamp") < t1)
    val   = df.filter((F.col("timestamp") >= t1) & (F.col("timestamp") < t2))
    test  = df.filter(F.col("timestamp") >= t2)
    return train, val, test

# 关键:val/test 的 history 必须在 T1/T2 时刻冻结,不让未来数据渗漏
def freeze_history_at(df, freeze_ts):
    return df.withColumn("history_ids",
        F.expr(f"filter(history_ids, x -> x.frozen_ts < {freeze_ts})"))
```

### 14.9 步骤 7:完整 Pipeline 串联

**Pipeline 串联的关键是"顺序的不可交换性"**。这 7 个步骤看似独立,实则有严格的先后依赖:

1. **必须先打标签,再 join 特征**——否则没有样本主键
2. **必须先 join 特征,再构建行为序列**——否则序列里"未来信息"会泄漏
3. **必须先负采样,再按时间切分**——否则切分后负样本分布不均
4. **必须只在训练集上 fit 编码器**——否则测试集信息会泄漏(用整个数据集算 max/min/scaler 是经典错误)
5. **必须用同一份编码器对 train/val/test 编码**——否则特征空间不一致

**为什么"按时间切分"必须早于"fit 编码器"?**

如果先 fit 编码器(用全量数据),再切分——编码器的 `LabelEncoder` 看到了 val/test 里的 city/item,会把它们映射成"训练集已知 ID"。看似没问题,但**scaler 的 mean/std 是用全量算的**,包含了未来信息,模型在 val 上 AUC 会被虚高。正确顺序是:先按时间切分 → 编码器只在 train 上 fit → 复用同一编码器对 val/test transform。

```python
def build_train_pipeline(
    exposure_path: str,          # 曝光日志
    click_path: str,             # 点击日志(作为历史序列用)
    user_profile_path: str,      # 用户画像
    item_attr_path: str,         # 物品属性
    max_seq_len: int = 50,
    neg_ratio: float = 3.0,
    batch_size: int = 1024,
    val_ratio: float = 0.1,
):
    # 1. 解析 & 打标签
    print("[1/7] 解析原始日志...")
    exposures = parse_exposure_tsv(exposure_path)
    clicks = parse_click_tsv(click_path)
    raw_samples = label_samples(exposures, clicks)
    print(f"  原始样本数: {len(raw_samples)}")

    # 2. Load 辅助特征
    print("[2/7] 加载辅助特征...")
    user_profiles = load_user_profile(user_profile_path)
    item_attrs = load_item_attr(item_attr_path)
    join_features(raw_samples, user_profiles, item_attrs)

    # 3. 构建行为序列
    print("[3/7] 构建用户行为序列...")
    user_history = build_user_history(click_path)
    for s in raw_samples:
        hist = user_history.get(s.user_id, [])
        s.history_item_ids = sample_sequence(hist, max_len=max_seq_len)

    # 4. 负采样
    print("[4/7] 负采样(ratio={})...".format(neg_ratio))
    all_items = set()
    for s in raw_samples:
        all_items.add(s.item_id)
    samples_with_neg = negative_sampling(raw_samples, all_items, neg_ratio)
    print(f"  负采样后总样本数: {len(samples_with_neg)}")

    # 5. 分割训练/验证(时间切分!)
    print("[5/7] 按时间切分训练/验证...")
    timestamps = [s.timestamp for s in samples_with_neg]
    split_ts = sorted(timestamps)[int(len(timestamps) * (1 - val_ratio))]
    train_samples_raw = [s for s in samples_with_neg if s.timestamp <= split_ts]
    val_samples_raw = [s for s in samples_with_neg if s.timestamp > split_ts]
    print(f"  训练: {len(train_samples_raw)}, 验证: {len(val_samples_raw)}")

    # 6. 训练编码器(只在训练集上!)
    print("[6/7] 学习特征编码器...")
    encoder = train_encoder(train_samples_raw)

    # 编码所有样本
    train_encoded = [encode_sample(s, encoder, max_seq_len) for s in train_samples_raw]
    val_encoded = [encode_sample(s, encoder, max_seq_len) for s in val_samples_raw]

    # 7. 创建 DataLoader
    print("[7/7] 创建 DataLoader...")
    train_loader = create_dataloader(train_encoded, batch_size, shuffle=True)
    val_loader = create_dataloader(val_encoded, batch_size, shuffle=False)

    # 保存编码器供推理用
    encoder.save("feature_encoder.pkl")
    print("  编码器保存至 feature_encoder.pkl")

    return train_loader, val_loader, encoder

# 使用
```

#### 14.9.1 特征对齐:为什么"离线 AUC 高,线上 AUC 低"的元凶

**文字**:搜推广算法工程师最大的噩梦就是"离线 AUC 0.78,上线后跌到 0.72"。根因十有八九是**离线训练和在线推理的特征计算方式不一致**。训练时 `item_7d_ctr` 用的是昨天凌晨 Spark 跑批算的精确值,推理时线上服务从 Redis 取的是"近 5 分钟滚动窗口",二者计算口径不同,哪怕平均差异只有 0.5%,对模型都是毁灭性打击。1 个千分点的 AUC 漂移乘上流量,线上 CTR 跌 1 个百分点是常事。

工业解法是"特征单一来源(Single Source of Truth)":所有特征都从同一个 FeatureStore 拉,无论是离线训练还是在线推理,都调用同一个 `get_feature(user_id, item_id, ts)` 接口,内部统一从 HDFS/Parquet(离线)或 Redis/Tair(在线)读。FeatureStore 还要做"双跑校验":同一时间段,离线用 Parquet 算出的特征和线上用实时流算出的特征比对,差异超过阈值就告警。这套机制是字节、阿里、美团各家搜推广工程团队的标配。

**公式**:
```text
Feature_online(t) - Feature_offline(t) ≤ ε   (一致性约束)
# ε 是允许的工程误差(通常取 0.001~0.01)
# 若不满足:告警 + 阻断发布 + 人工排查
漂移量 Δ = |E[Feature_train] - E[Feature_inference]|
预警阈值: Δ > 0.01 → 立即停止 AB 实验
```

**代码**:
```python
class FeatureStore:
    """特征存储:离线 / 在线同源,统一接口"""
    def get(self, entity: str, key: str, ts: int):
        # 训练时:从 Parquet snapshot 读
        # 推理时:从 Redis / Tair 读
        # 接口签名一致,避免"两套代码"
        pass

def drift_check(train_features, online_features, eps=0.01):
    """双跑校验:比对离线与在线特征分布"""
    delta = abs(train_features.mean() - online_features.mean())
    if delta > eps:
        raise ValueError(f"Feature drift Δ={delta:.4f} > {eps}, 阻断发布")
    return delta

# 训练时,所有样本的特征都通过 FeatureStore 拉取
# 推理时,同样调用 FeatureStore,保证"同一用户同一时刻,特征值完全相同"
```

**为什么这个 Pipeline 是"工业级"的?**
1. **时间切分**而非随机切分——防止数据泄漏
2. **训练集 fit 编码器**——防止特征穿越
3. **序列采样保留最近 N 个**——工业界最实用
4. **负采全量排除用户点过**——防止把正样本错标为负
5. **编码器序列化到磁盘**——推理时加载同一份

#### 14.9.2 数据 Schema 演进:为什么搜推广的样本表每周都在变

**文字**:搜推广的样本表不是写一次就稳的,它几乎是"周更"的节奏。新业务要加字段(短视频业务上线,要加 `video_id`、`play_duration_ms`);算法团队迭代要加特征(`user_30d_purchase_count`、`item_emb_v2`);AB 实验要加桶标识(`ab_bucket`,在线下分流时用);产品改版要加上下文(`entry_page_v2`)。一周不更新 Schema,两个团队就要吵架,数据 pipeline 直接爆。

工业解法是用 **Schema Registry + 向后兼容的 Protobuf**。所有样本字段都在一个集中管理的 Schema Registry $\text{里(类似 Avro Schema Registry 或 Protobuf 仓库)}$,任何字段的"加、删、改"都要走 code review 和版本号。兼容原则有三条:**只加字段不删字段**(老样本照样能读)、**只放宽类型不收紧**(`int32 \to int64` 可以,反过来不行)、**废弃字段标 deprecated 但保留**。这样离线训练用 v3 写的样本,在线推理服务即便还没升级到 v3,也能正常解析 v2 的字段。

**公式**:
```text
Schema 兼容性矩阵:
  Reader ＼ Writer    v1    v2    v3
  v1                    ✓    ✗    ✗
  v2                    ✓    ✓    ✗
  v3                    ✓    ✓    ✓
  # 行=读端版本,列=写端版本,✓=兼容
  # 永远保证"老 Reader 读新数据" = True(前向兼容)
```

**代码**:
```python
# sample.proto —— Schema Registry 集中管理
syntax = "proto3";
message RecSample {
  reserved 3, 7;                  # 废弃字段不能重用编号
  uint64 user_id = 1;
  uint64 item_id = 2;
  uint32 label = 4;                # 旧字段 label 从 3 移到 4
  Context context = 5;
  repeated uint64 history_ids = 6;
  // 新字段:默认 0 或空,老 Reader 读不到也不会崩
  optional uint32 play_duration_ms = 8;
  optional string ab_bucket = 9;
}

# 兼容读取:用 Protobuf 的 default 值兜底
sample = RecSample()
sample.ParseFromString(raw_bytes)
duration = sample.play_duration_ms or 0  # 老数据没有此字段,默认 0
```

**为什么必须管 Schema?**
- 不管 → 每周数据 pipeline 崩 1 次,oncall 工程师原地爆炸
- 管了 → 字段变更走 code review + 灰度,出问题 5 分钟回滚
- Schema Registry 是搜推广"工程化"区别于"学生项目"的最明显标志

### 14.10 "生成式推荐"到底是什么?——从范式到架构的深度拆解

**生成式推荐的"范式革命"**:在前面所有代码里,我们都在用"判别式"思路建模——给一组特征,模型吐一个分数(点击概率)。但 GenRec 把这个问题**完全转成"序列生成"**:

- 用户历史 = "过去 30 天点了 iPhone, 鼠标垫, 咖啡豆..."(token 序列)
- 模型目标 = "预测下一个 token"(下一个 item 的 ID)
- 训练 Loss = `CrossEntropy(logits, next_token_id)`(和 GPT 训练一模一样)

**为什么要做这个范式转换?** 三个核心收益:

1. **架构统一**:推荐 = "下一个 token 预测",跟 LLM 完全共用一套训练框架、推理引擎(vLLM)、加速技巧(Flash Attention, KV-cache)
2. **冷启动友好**:新 item 只要有"内容描述"(标题、属性),就能通过 RQ-VAE 编成"语义 ID token",新 item 立即可推——不用等积累点击数据
3. **跨域迁移**:只要 token 空间对齐,电商模型可以预训练 → 微调到短视频,数据互通

**代价是什么?** 推理慢(自回归生成 K=4 个 token 才得到一个 item ID,比单次 MLP 慢 5-10 倍);训练贵(Transformer 参数量比传统 DNN 多 1-2 个数量级);需要 VQ-VAE/RQ-VAE 的额外预训练 pipeline。**只有当业务规模(DAU > 1000 万)和数据量(行为 > 1 亿)都足够大时,GenRec 的收益才能覆盖成本。**

你注意到一个关键的转变了吗?在前面的所有代码里,我们把搜推广的"特征工程"变成了"序列生成":

1. 用户行为序列 → **token 序列**(把点击过的 item_id 当成一个个 token)
2. 历史物品 ID → **PADDED token 序列**(像 NLP 里 padding 句子一样 padding 行为序列)
3. 用户画像 → **辅助 token**(user_id、gender、city 都变成特殊 token)
4. 目标物品 ID → **下一个要预测的 token**(就像语言模型预测下一个词)

**这就是生成式推荐的本质:把推荐问题完全 token 化,变成一个"下一 token 预测(next token prediction)"的序列生成问题。**

```text
传统推荐范式:
  特征工程 → Embedding → MLP → 点击概率(标量)
  模型是"判别式"的:输入特征,输出概率

生成式推荐范式:
  Token化 → Transformer → 下一个 item token(向量)
  模型是"生成式"的:输入 token 序列,预测下一个 token
```

#### 14.10.1 三篇里程碑论文——理解 GenRec 的进化路线

**论文 1:P5 —— Everything is a Sequence(RecSys 2022)**

**P5 为什么是 GenRec 的"开山之作"?** 在 P5 之前,推荐系统的"特征工程"是个黑盒——每个团队有自己的特征 schema,跨团队/跨任务难以复用。P5(Shawn 等, 2022)的核心洞察是:**推荐的所有要素(用户、物品、评论、时间戳)都可以映射到同一个 token 空间,统一用"Text-to-Text"的方式处理**。P5 用 T5(Encoder-Decoder 架构)把"用户 U_123 历史: [item_1, item_2, item_3]"作为输入,生成"1"(点击)或"0"(未点击)作为输出;**同一个模型能处理评分预测、序列推荐、解释生成、对话推荐等多种任务**——这是 GenRec "统一范式" 的第一次完整示范。

P5 的最大局限:**词表大小 = 物品数**。工业界物品量级 1000 万到 1 亿,词表太大导致 softmax 算不动,实际落地困难。这正是后续 TIGER/CIDR 用"语义 ID"解决的核心问题。

```text
核心思想:
把推荐系统的所有要素(用户、物品、评论、时间戳)都映射到同一个 token 空间。
用 Text-to-Text 的方式统一处理所有推荐任务。

任务模板:
  "用户 U_123 历史行为: [item_1, item_2, item_3],
   候选物品: item_456,
   预测点击概率:" → "1" (或 "0")

关键设计:
  - 所有 ID(用户、物品)都作为特殊 token 加入词表
  - 用 T5(Encoder-Decoder)架构,编码器读输入,解码器生成输出
  - Loss:Cross-Entropy on 目标 token
  - 一个模型做多种任务:评分预测、序列推荐、解释生成、对话推荐

局限:
  - 物品数量受限(整个词表 6 万,工业界物品千万级)
  - Encoder-Decoder 推理慢(需要两阶段)
```

**论文 2:TIGER & CIDR——用语义 ID 解决物品数量问题**

**TIGER(2022)/CIDR(2023)的核心贡献**:把 VQ-VAE 引入推荐,实现"语义 ID token 化",让词表从 1000 万降到 256。每个 item 被编码成 4 个 token(每层 0~255),Transformer 只需预测 256 个候选词,而不是 1000 万。这套设计一举解决了 GenRec 落地最难的"算力墙",**Meta 2024 年的 HSTU、Google 的 TIGER、字节的 OneRec、阿里 CIDR,都沿着这条路走**。CIDR 进一步用 RQ-VAE 替代 VQ-VAE,让 token 有清晰的层次结构(品类→品牌→型号→SKU),第 1 个 token 相同的物品天然聚类,模型可学"先选品类、再选品牌"的推理路径,工业效果比 VQ-VAE 提升 5-10%。

```text
核心问题:P5 把 item 当作一个 token,词表大小 = 物品数
工业界 1000 万物品 → 词表 1000 万 → softmax 算不了!

TIGER 的解法:
  用 VQ-VAE(向量量化变分自编码器)把每个物品编码成"语义 ID"的序列

  比如:
  item_123  →  [42, 15, 7, 3]  ← 4 个 token,每个 token 范围 0~255
  item_456  →  [42, 18, 2, 9]

  这样设计:
  - 词表大小 = 256(只需预测 256 类),而不是 1000 万
  - 相似物品的语义 ID 更相似 → 模型天然能泛化到新物品
  - 用 4 个 token 表示一个物品 → 参数量: 4 × 256 × d_model,远小于 1000 万 × d_model

CIDR 进一步改进:
  用 RQ-VAE(残差量化)代替 VQ-VAE,让语义 ID 的层次结构更清晰:
  - 第一层 token:品类级别(如"电子产品")
  - 第二层 token:品牌级别(如"苹果")
  - 第三层 token:具体型号(如"iPhone 15")
  - 第四层 token:具体 SKU(如"256GB 黑色")

所以 TIGER/CIDR 的推荐流程:
  [用户行为 token 序列] → [Transformer] → [预测下一个物品的语义 ID 序列]
  这不是 1 次预测,而是 4 次串行预测:先预测品类,再预测品牌,再...
```

**论文 3:HSTU —— Meta 的工业级生成式推荐架构(KDD 2024)**

**HSTU(Hierarchical Sequential Transduction Unit)**是 Meta 在 KDD 2024 提出的工业级 GenRec 架构,核心创新是"用生成式架构替代传统 DNN"。在 Meta 的社交推荐业务里,HSTU 替代了 DeepFM/DIN 等老模型,**AUC 全面涨 5-10%,推理时延降低 5 倍**。HSTU Block 的设计与 LLaMA 几乎一模一样——Pre-RMSNorm + 旋转位置编码 + SwiGLU,区别只在 attention 的打分方式上用了"u^T·x_i × v^T·x_j"这种带 bias 的形式,让模型对**位置和时间衰减**更敏感(用户最近的行为应该比 1 年前的行为权重大)。这个看似微小的改动,正是 GenRec "吸取 LLM 营养、保留推荐特性"的典型范例。

```text
HSTU(Hierarchical Sequential Transduction Unit)是 Meta 在 2024 年提出的,
是目前最接近"用 LLM 架构做推荐"的生产级系统。

核心变革:
  1. 抛弃 MLP → 完全用 Transformer 堆叠替代传统 DNN
  2. 用"点积注意力"替代"拼接+MLP"做特征交叉
  3. 用 Decoder-only 替代 Encoder-only

HSTU Block 设计(跟 LLaMA Block 非常像):
  x = x + PointwiseFFN(RMSNorm(x))         # 就是 SwiGLU
  x = x + MultiheadAttention(RMSNorm(x))    # 预归一化
  # 和 LLaMA 的唯一区别:Attention 的 score 计算方式不同

区别:
  LLaMA: Q @ K^T / √d  → Softmax → Attention
  HSTU: (Q @ K^T) * (u^T · x_i) * (v^T · x_j)  → 带 bias 的 attention

效果:
  - 在 Meta 的社交推荐中,用 HSTU 替代传统 DeepFM/DIN
  - 在 7 个推荐基准上全面超越 SOTA
  - 参数量减少 50%,推理速度提升 5 倍
```

#### 14.10.2 GenRec 的三种架构范式

**为什么 Decoder-Only 胜出?**

Encoder-Decoder(P5/BART)在 NLP 里是"翻译/摘要"的标配,推荐里却输了。三个原因:

1. **KV-cache 让推理快 2-3 倍**。Encoder-Decoder 必须先算完整 encoder 输出,decoder 才开始生成;Decoder-Only 没有"先编码后解码"的两阶段,生成第 K 个 token 时前 K-1 个 token 的 KV 已经缓存好,直接复用。
2. **自回归生成天然适配推荐场景**。推荐就是"给一个用户,生成一个 item 列表",本质是 1 次生成 1 个 item,Decoder-Only 的"逐 token 生成"完全对应。
3. **训练基础设施完全复用 LLaMA 生态**。从 Megatron-LM 到 HuggingFace Transformers,所有 LLM 训练框架都默认 Decoder-Only,GenRec 直接 fork 就能用,不需要重写训练循环。

**代价是"双塔结构失效"**。推荐召回阶段通常需要"user_emb 和 item_emb 独立算,然后做 ANN 检索",Encoder-Decoder 的编码器输出天然就是 user_emb。Decoder-Only 没这个结构,要单独训一个 user tower 配合,工程上多一套。

```text
范式 A:Encoder-Only(传统做法)
  代表:P5 之前的模型(但 P5 用 Encoder-Decoder)
  输入:[user_id, item_id, ...] → Self-Attention → Pooling → MLP → sigmoid
  缺点:不能做生成任务,只能打分

范式 B:Encoder-Decoder(P5/BART 路线)
  代表:P5, M6-Rec
  输入:用户行为 + 候选
  输出:点击/不点击 token(生成)
  优点:统一了所有推荐任务
  缺点:推理慢(2 阶段),物品多了 softmax 太大

范式 C:Decoder-Only(2024 年主流,和 LLM 趋同!)
  代表:HSTU, 以及越来越多新模型

  架构:
  [BOS] → [user_token_1] → [item_token_2] → ... → [target_item]
                                                          ↓
                                              Decoder-Only Transformer
                                                          ↓
                                                 下一个 item token

  为什么 Decoder-Only 胜出?
  1. 推理时 KV-cache → 比 Encoder-Decoder 快 2~3 倍
  2. 自回归生成 = 推荐场景(一次只推一个 item)
  3. 和 LLaMA/Qwen 共用同一套训练框架
```

#### 14.10.3 GenRec 的 Tokenization 三种方案

**Tokenization 是 GenRec 的"第一性原理"问题**。它决定了"物品"在 Transformer 眼里长什么样——是 1 个整数(原始 ID)?是 4 个整数(语义 ID)?还是 N 个文本子词(LLM tokenizer)?三种方案对应三套完全不同的训练和推理成本。

| 方案 | 词表大小 | 单 item 长度 | 冷启动 | 跨域迁移 | 工业首选 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 原始 ID | $10^7$ | 1 | 差 | 差 | ❌ 不用 |
| 语义 ID (RQ-VAE) | $256^4=4B$ 容量 | 4 | ✅ 好 | ✅ 好 | ✅ **首选** |
| 文本 token | LLM 词表 32K-100K | 10-20 | ✅✅ 最好 | ✅✅ 最好 | ⭐ 实验性强 |

**方案选型的核心 trade-off**:
- 原始 ID:最简单,但词表爆炸,10M 类 softmax 算不动,冷启动是 OOV 灾难
- 语义 ID:工业甜区,4 个 token × 256 词表,容量 4B,但需要预训练 RQ-VAE
- 文本 token:最灵活(零样本冷启动),但推理慢 10 倍,需要 LLM 推理基础设施

```text
方案 A:原始 ID(最直接,但限制最大)
  item_1234567 → 一个 token,词表 = N_items
  问题:词表太大,冷启动灾难(OOV)
  适用:物品数 < 10 万的小场景

方案 B:语义 ID(当前 SOTA)
  item_1234567 → [code_1, code_2, code_3, code_4]
  由 VQ-VAE / RQ-VAE 预训练得到
  优点:
    - 词表可控(256 × depth)
    - 语义相近的物品 ID 也相近
    - 新物品不用重新训练 VQ-VAE,只需通过编码器得到语义 ID
  缺点:
    - 需要额外训练 VQ-VAE(但只需一次)
    - 生成时需自回归解码 4 步才能得到一个物品

方案 C:文本描述(最灵活,但最慢)
  item_1234567 → "Apple iPhone 15 Pro Max 256GB Space Black"
  用 BERT/LLaMA 的 tokenizer 分 tile 编码
  优点:
    - 零样本冷启动:新物品只要有文本描述就能推
    - 可跨域迁移
  缺点:
    - 推理慢(文本 token 比单个 ID token 长 10 倍)
    - 需要额外做文本编码
```

```python
import torch
import torch.nn as nn

# 方案 A:原始 ID tokenization(最简单)
class RawIDTokenizer:
    """直接把 item_id 当 token"""
    def __init__(self, vocab_size):
        self.vocab_size = vocab_size
    def encode(self, item_ids):
        return torch.tensor(item_ids, dtype=torch.long)
    def decode(self, tokens):
        return tokens.tolist()

# 方案 B:语义 ID tokenization(RQ-VAE 风格)
class SemanticIDTokenizer(nn.Module):
    """
    用 RQ-VAE 把 item 编码为多级语义 token。
    实际 RQ-VAE 需要预训练,这里展示 forward 流程。
    """
    def __init__(self, num_codes=256, num_levels=4, dim=64):
        super().__init__()
        self.num_codes = num_codes          # 每层词表大小 256
        self.num_levels = num_levels        # 层级数 4
        # 每层的 codebook: [num_codes, dim]
        self.codebooks = nn.ParameterList([
            nn.Parameter(torch.randn(num_codes, dim))
            for _ in range(num_levels)
        ])

    def encode(self, item_embedding):
        """把 item 的 d_model 向量 → [4] 个语义 token"""
        residual = item_embedding
        codes = []
        for level in range(self.num_levels):
            # 找最近邻 code
            dist = torch.cdist(residual.unsqueeze(0), self.codebooks[level].unsqueeze(0))
            code_idx = dist.argmin(dim=-1)   # [1]
            codes.append(code_idx.item())
            # 残差:减去选中的 code
            residual = residual - self.codebooks[level][code_idx]
        return codes  # [4] 个 int,每个范围 0~255

# 方案 C:文本 tokenization(用 LLaMA tokenizer)
from transformers import AutoTokenizer
class TextTokenizer:
    """用现成的 LLM tokenizer"""
    def __init__(self, model_name="meta-llama/Llama-2-7b"):
        self.tokenizer = AutoTokenizer.from_pretrained(model_name)

    def encode(self, item_title):
        # "Apple iPhone 15 Pro Max" → [1, 234, 567, 890, 2]
        return self.tokenizer.encode(item_title)

    def decode(self, tokens):
        return self.tokenizer.decode(tokens)
```

#### 14.10.4 GenRec 和 LLM 的"趋同进化"——你现在的位置

> **这是你最需要理解的部分**:2024-2025 年,生成式推荐和 30B 以下的小 LLM 的设计思路正在快速趋同。

**趋同的本质原因**:LLM 解决了"通用智能的缩放法则",GenRec 借用了这套缩放经验——只要把推荐转成"next token prediction",就能复用 LLM 的所有 scaling trick。这就是为什么 2024 年开始,推荐系统论文里出现大量"用 LLaMA 架构做推荐"的实验。Meta HSTU 论文里,Block 结构和 LLaMA 几乎逐字对应;Google 的 TIGER 用了 T5X 训练框架,字节 OneRec 直接 fork 了一个 LLaMA-7B 改造成推荐模型。

**这给算法工程师的启示**:

1. **学习曲线收敛**:以前要学 DNN + Attention + 推荐特定 trick(如 Cross Network、DeepFM、MMoE),现在只需要学 LLaMA 架构 + 推荐 token 化,门槛降低
2. **开源生态复用**:vLLM、TGI、sglang、TensorRT-LLM 这些 LLM 推理引擎,GenRec 直接用,自己不用造轮子
3. **基础设施外包**:DeepSpeed、Megatron、FSDP 这些分布式训练框架,也是 LLM 时代成熟的,GenRec 直接套用

**唯一保留的"推荐特性"**:item 的语义 ID token 化(RQ-VAE)和"用户 × 物品"的交叉建模——这是 LLM 范式不能直接 cover 的部分,需要推荐系统自己解决。


- 未来 1-2 年,搜推广模型会全面向 LLaMA/Qwen 的小模型架构靠拢

#### 14.10.5 从 0 搭建一个 GenRec 模型

**MiniGenRec 的"从零实现"路径**:从代码层面看,这个模型只有 4 个组件:Embedding 层(把 token id 变成向量)、RoPE 位置编码(让序列有顺序感)、Transformer Block(自注意力+FFN)、输出投影(把隐藏向量映射回词表 logits)。**和 LLaMA-7B 的最小可运行版本结构完全相同**,只是去掉了"多 GPU 并行"和"超大词表"等工程特性。

**为什么这个 6 层、256 维的小模型能 work?**

1. **数据量足够**:哪怕只有 1000 万条用户行为序列,Transformer 也能学到有意义的 item 关系——参数量才 6 × 256 × 256 × 4 ≈ 150 万,远小于 LLaMA-7B 的 70 亿
2. **任务简单**:推荐预测的是"下一个 item 类别",比 LLM 预测"任意文本"窄得多,小模型足够
3. **正则化强**:Embedding Dropout + 权重衰减 + 标签平滑,即使小模型也不易过拟合

**训练循环和语言模型完全一样**:
```python
logits = model(tokens[:, :-1])  # 用前 T-1 个 token 预测
loss = F.cross_entropy(
    logits.reshape(-1, vocab_size),
    tokens[:, 1:].reshape(-1)    # 后 T-1 个 token 作为目标
)
```
这就是 Next Token Prediction(NTP)——GPT 的核心训练目标,被 GenRec 原封不动搬过来。

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class GenerativeRecBlock(nn.Module):
    """
    生成式推荐的一个 Transformer Block。
    设计思路 = LLaMA Block + HSTU 的交互式 attention。
    """
    def __init__(self, d_model, n_heads, expansion=4):
        super().__init__()
        self.attention = nn.MultiheadAttention(d_model, n_heads, batch_first=True)
        # 和 LLaMA 一样的 SwiGLU FFN
        self.gate_proj = nn.Linear(d_model, expansion * d_model)
        self.up_proj = nn.Linear(d_model, expansion * d_model)
        self.down_proj = nn.Linear(expansion * d_model, d_model)
        # Pre-RMSNorm(和 LLaMA 一样)
        self.norm1 = RMSNorm(d_model)
        self.norm2 = RMSNorm(d_model)

    def forward(self, x, mask=None):
        # Pre-Norm + Attention
        x = x + self.attention(self.norm1(x), self.norm1(x), self.norm1(x),
                               attn_mask=mask)[0]
        # SwiGLU FFN
        x = x + self.down_proj(
            F.silu(self.gate_proj(self.norm2(x))) * self.up_proj(self.norm2(x))
        )
        return x

class RMSNorm(nn.Module):
    """
    RMSNorm: LLaMA 和 GenRec 的标准归一化。
    比 LayerNorm 快 15%,且效果更好。
    公式: y = x / sqrt(mean(x²) + ε) * γ
    """
    def __init__(self, dim, eps=1e-6):
        super().__init__()
        self.weight = nn.Parameter(torch.ones(dim))
        self.eps = eps

    def forward(self, x):
        # x: [B, T, D]
        rms = torch.sqrt(x.pow(2).mean(dim=-1, keepdim=True) + self.eps)
        return x / rms * self.weight

class MiniGenRec(nn.Module):
    """
    极简生成式推荐模型——和 LLaMA 共用同一套架构!

    输入: token 序列(含用户 ID + 历史行为 ID + 目标 item ID)
    输出: 预测下一个 item 的 logits
    """
    def __init__(self, vocab_size, d_model=256, n_heads=8, n_layers=6):
        super().__init__()
        self.token_emb = nn.Embedding(vocab_size, d_model)
        # RoPE 旋转位置编码(和 LLaMA 一样)
        self.rope = RotaryEmbedding(d_model // n_heads)
        self.blocks = nn.ModuleList([
            GenerativeRecBlock(d_model, n_heads) for _ in range(n_layers)
        ])
        self.norm = RMSNorm(d_model)
        self.output = nn.Linear(d_model, vocab_size, bias=False)

    def forward(self, token_ids):
        x = self.token_emb(token_ids)
        x = x + self.rope(token_ids)        # RoPE 编码
        for block in self.blocks:
            x = block(x)
        x = self.norm(x)
        logits = self.output(x)
        return logits                        # [B, T, vocab_size]

class RotaryEmbedding(nn.Module):
    """旋转位置编码 RoPE——现代 GenRec 和 LLM 的标准"""
    def __init__(self, dim, max_seq_len=2048):
        super().__init__()
        inv_freq = 1.0 / (10000 ** (torch.arange(0, dim, 2).float() / dim))
        self.register_buffer("inv_freq", inv_freq)

    def forward(self, x):
        # x: [B, T, D]
        seq_len = x.shape[1]
        t = torch.arange(seq_len, device=x.device).float()
        freqs = torch.einsum("i,j->ij", t, self.inv_freq)
        emb = torch.cat([freqs, freqs], dim=-1)
        return emb[None, :, :]

# 使用
model = MiniGenRec(vocab_size=10000)
tokens = torch.randint(0, 10000, (32, 50))  # [B=32, T=50]
logits = model(tokens)                        # [32, 50, 10000]

# 训练:和语言模型一模一样!
loss = F.cross_entropy(
    logits[:, :-1, :].reshape(-1, 10000),    # 预测
    tokens[:, 1:].reshape(-1)                 # 真实下一个 token
)
```

**看到没?这个模型和 LLaMA 的最小号版本几乎一模一样:**
- `RMSNorm` + `Pre-Norm`(LLaMA 标配)
- `SwiGLU` FFN(Mistral/Qwen/DeepSeek 都用)
- `RoPE` 位置编码(几乎所有的现代 LLM 都用)
- `Decoder-Only` 因果注意(和 GPT/LLaMA 一样)

#### 14.10.6 GenRec 的损失函数:不只是 Cross-Entropy

**为什么不能只用 Cross-Entropy?**

理论上,GenRec 训练和 GPT 完全一样,Cross-Entropy 就够了。但工业落地有三个特殊问题:

1. **物品量级巨大**——10M 个 item,softmax 分母要遍历所有 item,显存爆炸。**Sampled Softmax** 只对正样本 + K 个负样本算 softmax(K=256),计算量降 40000 倍。
2. **长尾分布**——80% 的样本集中在 20% 的热门 item 上,模型学"猜热门"就能 loss 很低,学不到长尾。**Contrastive Loss(InfoNCE)** 强迫不同序列的 embedding 互相远离,让长尾 item 也有梯度信号。
3. **目标多样**——推荐不只是"下一个 item",还有"点击概率"、"停留时长"、"是否转化"等多个目标。**Multi-task Loss** 把这些加权和,总 Loss = $\alpha \mathcal{L}_{\text{NTP}} + \beta \mathcal{L}_{\text{CTR}} + \gamma \mathcal{L}_{\text{停留}}$。

**工业最佳实践**:NTP Loss 为主 Loss,Contrastive Loss 辅助(防止 Embedding 坍缩),多任务 Loss 视业务加。$\alpha$ 通常 1.0,$\beta$ 0.1,$\gamma$ 0.01,权重比例需要 A/B 调优。

**文字**：GenRec 的核心是 Next-Token Prediction（NTP），即预测序列中下一个 item 的 token ID。但物品词表极大时全量 $\mathrm{softmax}$ 计算无法承受，工业界用 Sampled Softmax 或对比学习损失替代。

**公式**：

$$\mathcal{L}_{\text{NTP}} = -\frac{1}{T-1}\sum_{t=1}^{T-1} \log p_\theta(x_{t+1} \mid x_{1:t})$$

$$\mathcal{L}_{\text{sampled-softmax}} = -\log \frac{e^{s(u,i^+)/\tau}}{e^{s(u,i^+)/\tau} + \sum_{j \in \mathcal{N}} e^{s(u,i_j)/\tau}}, \quad |\mathcal{N}| = K \ll |V|$$

$$\mathcal{L}_{\text{GenRec}} = \mathcal{L}_{\text{NTP}} + \alpha \mathcal{L}_{\text{sampled-softmax}} + \beta \mathcal{L}_{\text{InfoNCE}}$$

```python
def genrec_loss(logits, target_item_ids, item_freq=None):
    """
    GenRec 的三种损失组合:

    1. CE Loss:预测下一个 item token(标准)
    2. Sampled Softmax:物品太多时,只对部分负样本算 softmax
    3. 对比学习 Loss:让相似序列的 embedding 相近
    """
    # 1. 标准 Cross-Entropy
    ce_loss = F.cross_entropy(
        logits.view(-1, logits.size(-1)),
        target_item_ids.view(-1),
        ignore_index=0
    )

    # 2. Sampled Softmax(物品数 > 10 万时使用)
    # 不计算全量 vocab 的 softmax,而是对正样本 + K 个负样本算
    # K = 256 或 512

    # 3. 对比学习 Loss(InfoNCE)
    # 同一个序列的 dropout 两次,让两次的 embedding 相似
    # 不同序列的 embedding 远离

    return ce_loss  # + sampled_softmax_loss + contrastive_loss
```

#### 14.10.7 "生成式推荐"到底何时真正有价值?

**GenRec 不是"银弹",盲目上马会亏钱**。判断"该不该上 GenRec" 要看 4 个维度:

| 维度 | 阈值 | 解释 |
| :--- | :--- | :--- |
| **DAU 量级** | > 1000 万 | 数据量足够训练 Transformer,小 DAU 不如用 DNN 划算 |
| **行为丰富度** | 用户日均行为 > 20 条 | 行为序列才有意义,稀疏用户(< 5 条/天)用 GenRec 等于"杀鸡用牛刀" |
| **推理延迟容忍** | < 50ms | 自回归生成 K 个 token 比 MLP 慢 5-10 倍,延迟敏感场景(广告竞价)慎用 |
| **多模态/跨域需求** | 有 | GenRec 的"统一 token 空间"是唯一能跨模态/跨域迁移的方案 |

**满足这 4 个条件中至少 3 个,GenRec 才值得投入**。否则用 DNN+特征工程,ROI 更高。字节 OneRec 在抖音上验证 GenRec,正是因为同时满足 4 个条件——DAU 数亿、行为稠密、延迟容忍(视频流式加载)、需要跨场景跨模态;而一个小电商网站,DAU 几十万、用户行为稀疏,直接用 DNN + FM 就够了,不必上 GenRec。

| 场景 | 传统方法 | GenRec 方法 | GenRec 优势 |
| :--- | :--- | :--- | :--- |
| **冷启动(新物品)** | 无交互 → 推不出去 | 用物品标题/属性生成 token → 基于语义推理 | ✅ 零样本推荐 |
| **跨域推荐** | 每个域独立建模,特征不共享 | 统一 token 空间 → 一个模型跨域 | ✅ 数据互通 |
| **多模态融合** | 图片、文本、ID 各用独立模块 | 全部 token 化 → 一个 Transformer | ✅ 架构统一 |
| **多任务统一** | 每个任务一个塔(CTR/CVR/时长) | 同一序列生成框架 | ✅ 参数共享 |
| **可解释性** | Attention 权重或 SHAP | 生成的 token 序列天然可解释 | ✅ 生成即解释 |

**但也要知道 GenRec 的局限**:
- 推理速度:自回归生成比单次 MLP 慢 5~10 倍
- 物品更新:新增物品需要更新 tokenizer/VQ-VAE
- 训练成本:Transformer 比 MLP 贵一个数量级
- 已有系统迁移成本:从 DeepFM 迁移到 Transformer 需要改整个架构

**什么时候应该上 GenRec?**
```text
超过 1000 万 DAU 的平台? → 值得考虑
有丰富的行为序列数据? → GenRec 效果好于 MLP
需要跨域/多模态能力? → GenRec 天生优势
推理延迟容忍(< 50ms)? → 可以做
```

### 14.12 训练数据类型全景对比:隐式 vs 显式 vs 行为序列 vs 多模态

> 前面 14.1–14.10 一直在围绕"点击日志"这一种隐式反馈打转。但真实的搜推广系统,往往要把 **4 种完全不同的数据源** 拼成同一条训练样本。**只要其中一种数据用错了处理方式,整个模型的离线指标就会"看似涨了、线上全垮"**。这一节用一张 4-way 对比表 + 4 段最小可运行代码,把这 4 类数据的"采集/噪声/权重/正负比/陷阱"彻底讲透。

#### 14.12.1 为什么必须把这 4 种数据分开看?

**核心原因:这 4 类数据的"信号强度"和"采样偏差"完全不同,不能混在同一个 Loss 里训**。

举个例子,搜推广新人最容易犯的错:把"显式评分 < 3 星"和"曝光未点击"等同视之,都用 label=0 训练。**这两种"负"的语义完全不一样**——前者是"用户看了/买了主动给差评",后者是"用户根本没看或者扫一眼没兴趣"。前者是强负信号,后者是弱负信号甚至"不确定"信号。如果混在一起训,模型对"差评"和"曝光未点击"学到同一种表征,线上推理时遇到"用户没看过的 item",模型也会输出低分——这就把召回池压扁了,推不出用户可能感兴趣但没曝光的冷门 item。

**4 类数据的"语义强度"天梯**:

- **显式评分 ≥ 4 星**:最强正信号(用户主动表态喜欢)
- **购买 / 收藏**:强正信号(用户付出行动)
- **完播 / 长停留**:中强正信号(用户付出时间)
- **点击**:中弱正信号(用户被推荐吸引)
- **短停留**:弱正信号
- **曝光未点击**:弱负信号(可能没看到,可能不喜欢)
- **显式评分 ≤ 2 星**:强负信号(用户主动表态不喜欢)
- **不感兴趣反馈**:强负信号(用户主动吐槽)

**混用 = 把强信号稀释成弱信号,模型学不到细粒度**。

我们在工业界混用的 4 类数据,本质上是 **4 种不同的"用户偏好信号"**:

| 缩写 | 全称 | 一句话定义 | 典型例子 |
| :--- | :--- | :--- | :--- |
| **Implicit** | Implicit Feedback | 用户"做了某事"留下的副作用痕迹 | 点击 / 播放 / 加购物车 / 收藏 |
| **Explicit** | Explicit Feedback | 用户**主动**给出的评分 | 1–5 星评分 / 👍👎 / 文本评论 |
| **Seq** | Behavioral Sequence | 用户**一段时间内**的行为序列 | 最近 30 天点击序列 / session 内浏览流 |
| **Multi** | Multimodal Content | 物品本身的**多模态特征** | 商品图 / 短视频 / 标题文本 / 语音 |

> 一个淘宝/抖音场景的样本,通常 = `Implicit click` + `Seq(过去 30 天浏览)` + `Multi(图+文)` 拼接而成;**显式评分几乎用不到**——这就是为什么大量推荐系统论文以点击为主、评分为辅。

#### 14.12.2 4-way 全景对比表(必背)

下表是面试和工程上都会被问到的"数据选型表",**请直接背下来**:

| 维度 | **隐式反馈 Implicit** | **显式反馈 Explicit** | **行为序列 Seq** | **多模态 Multi** |
| :--- | :--- | :--- | :--- | :--- |
| **采集方式** | 服务端埋点自动写日志 (client SDK / server log) | 前端 UI 主动弹窗让用户打分 | 滑动窗口聚合 (window / session) | 离线 ETL 抽特征 (ResNet / OCR / ASR) |
| **样本标签** | 0/1 (click/no-click),**天然有偏** | 1–5 星,语义清晰 | 通常**没有标签**,靠下游任务 | **没有标签**,作为输入特征 |
| **噪声模型** | **位置偏差 + 曝光偏差 + 展示偏差** 三重叠加 | 评分者偏差 + 稀疏 (长尾用户不打分) | 截断偏差 (truncation bias) | 抽取模型噪声 + 内容冷启动 |
| **样本权重** | 必须用 IPS / 反概率加权 (见 14.13) | 一般不需要 | 需时间衰减 (time decay) | 通常做 L2 normalize |
| **正负比** | 极度不均 (1:100 ~ 1:1000) | 极度稀疏 (有评分用户 < 5%) | 没有正负,只有序列 | 没有正负,只有特征 |
| **典型陷阱** | 把"曝光"当成"负样本" | 把 1 星当负、5 星当正 (实际应 ≥4 星) | 用未来信息 (look-ahead bias) | 多模态特征"喧宾夺主"覆盖 ID 信号 |
| **推荐 loss** | BCE / sampled softmax | MSE / 回归 | seq2seq / contrastive | 与其他特征 concat 后下游统一 |
| **离线评估** | AUC / gAUC / logloss | RMSE / MAE | NDCG@K / Hit@K | 间接 (A/B) |
| **代表论文** | YouTube DNN (2016) | Matrix Factorization (2009) | DIN (2017) / SASRec (2018) | MM-Rec (2022) / P5 (2022) |
| **数据量级** | 极大 (亿/日) | 极小 (万/日) | 中 (千/用户) | 中 (千/物品) |

#### 14.12.3 4 种数据的最少可用代码(可运行)

```python
第 14 章 14.12 配套代码: 4 种数据类型的最小加载示例
运行: python 14_12_four_data_types.py
"""
import torch
import numpy as np
import pandas as pd

# ---------- 1) 隐式反馈 ----------
# 典型: 服务端曝光日志, 一行 = (user, item, position, clicked, ts)
implicit_log = pd.DataFrame({
    "user_id":  ["u1", "u1", "u1", "u2"],
    "item_id":  ["i7", "i3", "i9", "i7"],
    "position": [1, 2, 3, 1],

})

print("[Implicit] schema =", list(implicit_log.columns))

# ---------- 2) 显式反馈 ----------
# 典型: 用户主动打 1-5 星, 一行 = (user, item, rating, ts)
explicit_rating = pd.DataFrame({
    "user_id": ["u1", "u1", "u2", "u3"],
    "item_id": ["i7", "i3", "i7", "i1"],

})

behavior_seq = {
    "u1": ["i7", "i3", "i5", "i9", "i2"],   # 最近 30 天按 ts 排序
    "u2": ["i7", "i8"],

}
# 工业上要 pad 到定长, 例如 max_len=10, 缺位补 0
MAX_LEN = 10
padded_seq = torch.tensor(

)
print("[Seq] padded tensor shape =", tuple(padded_seq.shape))   # (3, 10)

# ---------- 4) 多模态内容特征 ----------
# 典型: 物品侧 ResNet/CLIP 抽好的 embedding, 存成 parquet
multi_feat = pd.DataFrame({
    "item_id":       ["i1", "i3", "i7", "i9"],
    "img_emb":       [np.random.rand(64).tolist()   for _ in range(4)],
    "text_emb":      [np.random.rand(64).tolist()   for _ in range(4)],

})
# ⚠️ 多模态特征必须 L2 normalize, 否则量纲会淹没 ID embedding
img_mat = torch.tensor(np.stack(multi_feat["img_emb"].values))
```

### 14.13 曝光偏差(Exposure Bias)的数学建模:从朴素估计到 IPS/ESMM/SNIP

> 上一节 14.12 列出了 4 类数据中**最危险**的一类——隐式反馈。本节深入其数学本质:为什么"点击 = 正样本、未点击 = 负样本"是错的?以及业内三种主流纠偏方案的公式推导 + 最小可运行 PyTorch 实现。

#### 14.13.1 问题定义:我们到底想估计什么?

**核心洞察:推荐系统的"目标函数"和"训练数据"是不一致的**。

**我们想要建模的**是 $P(Y=1 \mid u, i)$——用户 $u$ 对物品 $i$ 的"真实偏好"(给不给我都会点的概率)。**但我们能观测到的**是 $P(C=1 \mid O=1)$——在物品 $i$ 被曝光给用户 $u$ 的前提下,用户点了 $i$ 的概率。这两个量看似接近,本质不同。

**为什么不同?** 用一个具体例子:

- 用户小明喜欢运动鞋,运动鞋品牌 A、B、C 在推荐池里
- 召回系统把 A、B、C 都召回了,精排把 A 排到第 1 位
- 小明看到了 A(曝光 O=1),点了 A(C=1)
- 这次曝光里,小明没看 B、C(因为 A 在第 1 位,B、C 排在第 5、第 8 位)
- 我们能记录的"用户行为"是:`(小明, A, click=1), (小明, B, click=?), (小明, C, click=?)`
- 但 B、C 的 click=0 真的代表"不喜欢"吗?——**不是,只是没看到**!

**朴素估计的偏差**:用 `click=0` 当负样本,模型学到"用户对 B、C 不感兴趣"。但实际上,小明对 B、C 同样感兴趣,只是因为 A 在前面没看到 B、C 而已。这就是**曝光偏差(Exposure Bias)**——用户没看到的 item 是不公平的"负样本",把噪声引入训练数据,模型学不到真实的"用户偏好",把"用户没看到的好物品"误判为"用户不喜欢"。

设用户 $u$ 对物品 $i$ 的**真实偏好**为 $Y_{u,i} \in \{0, 1\}$ (喜欢/不喜欢),则我们**真正想建模**的是:

$
P(Y_{u,i}=1 \mid u, i) = \underbrace{P(\text{expose}=1 \mid u, i)}_{\text{曝光概率}} \cdot \underbrace{P(\text{click}=1 \mid u, i, \text{expose}=1)}_{\text{用户真实点击率}} + 0
$

记:

- $O_{u,i} \in \{0, 1\}$ ——物品 $i$ 是否被曝光给用户 $u$ (observable)
- $C_{u,i} \in \{0, 1\}$ ——物品 $i$ 被点击 (observable)
- $Y_{u,i} \in \{0, 1\}$ ——用户的真实喜好 (unobservable, 这是 bias 的根源)

我们**只能观测到** $O_{u,i}=1$ 的样本(因为 $O=0$ 根本没进日志),所以**朴素**地"用点击当正样本、未点击当负样本",等价于:

$
\hat{P}_{\text{naive}}(\text{like}) = \frac{1}{N} \sum_{(u,i): O=1} C_{u,i} \approx P(C=1 \mid O=1)
$

> **错在哪?** $P(C=1 \mid O=1)$ 衡量的是"**看到之后**的点击率",而推荐系统要的是"**给不给我都会点**的点击率"。前者 = 物品**能被刷到** + **用户真的喜欢**的联合概率,后者只关心后者。**结果就是模型把所有曝光池里的热门物品都学成"高 CTR",而真正的小众好物品被压成 0。**

#### 14.13.2 曝光偏差的形式化

形式化地,**朴素估计是有偏的**:

$
\mathbb{E}[\hat{P}_{\text{naive}}] = P(C=1 \mid O=1) = \frac{P(C=1, O=1)}{P(O=1)} \neq P(Y=1)
$

其中等式右侧 $P(O=1)$ 是**位置偏差 + 召回偏差**的综合:第 1 位的物品曝光率天然高,热门召回池的物品曝光率天然高。

我们想要的是无偏估计:

$
\mathbb{E}[\hat{P}_{\text{unbiased}}] = P(Y=1)
$

#### 14.13.3 方案 A:IPS (Inverse Propensity Scoring) —— 逆概率加权

**IPS 的核心思想**来自因果推断的 Rubin Causal Model:把"被曝光"看成一个**有偏的抽样过程**,给每个观测到的样本一个**重要性权重 $w = 1/p$**,被抽样概率低的样本权重反而高,从而"补偿"曝光偏差。

**直觉类比**:想象你调查"全校学生喜欢看什么电影",但你只在图书馆门口采样。图书馆来的学生爱看文艺片,但你不能因此推断"全校学生爱看文艺片"——你漏掉了宿舍区那些爱看综艺的学生。补救办法是给"图书馆采样概率高"的文艺片样本一个**低权重**,给"图书馆采样概率低"的综艺样本一个**高权重**,这样加权平均后,总样本分布接近全校真实分布。**IPS 就是把这种"反偏差加权"用到推荐上**:被曝光概率低的样本权重高,被曝光概率高的样本权重低,加权后训练数据无偏。

**工业落地公式**(实际 loss 加权):

$$
\mathcal{L}_{\text{IPS}} = -\frac{1}{N} \sum_{i=1}^{N} \frac{O_i}{p_i} \Big[ y_i \log \hat{y}_i + (1 - y_i) \log (1 - \hat{y}_i) \Big]
$$

**IPS 的致命缺陷:高方差**。当 $p_i \to 0$ 时,样本权重 $\to \infty$,Loss 被这一两个样本"绑架",模型训练极不稳定。这就是著名的 **propensity overfitting**。**工业上必须做 clip**:把权重限制在 `[1/clip, clip]` 区间(通常 clip=10 或 50),牺牲一点点无偏性换取稳定性。

**真实业务里 $p_i$ 是未知的**,需要单独训练一个"曝光倾向模型"来估计,这就引入了 propensity model 的偏差——和 IPS 的无偏性目标形成冲突。**这是为什么工业上很少直接用纯 IPS,转而用 DR(双鲁棒)或 ESMM**。

**核心思想**:把"被看到"这件事看成一个"抽样过程",给每个观测到的样本一个**重要性权重** $1/P(O_{u,i}=1 \mid u, i)$。被看到概率低的样本,权重反而高,从而"补偿"曝光偏差。

设 $p_{u,i} = P(O_{u,i}=1 \mid u, i)$ 为**曝光倾向分 (propensity score)**,则 IPS 估计量为:

$
\hat{P}_{\text{IPS}} = \frac{1}{N} \sum_{i=1}^{N} \frac{O_{u,i} \cdot C_{u,i}}{p_{u,i}}
$

**证明无偏性**:
$
\mathbb{E}\left[\frac{O \cdot C}{p}\right] = \mathbb{E}\left[\frac{O \cdot C}{p} \,\Big|\, O=1\right] P(O=1) + 0
$

在 $O=1$ 的子集上,$p$ 就是常数,把它提到外面:

$
= \frac{1}{p} \cdot P(O=1) \cdot \mathbb{E}[C \mid O=1] = \mathbb{E}[C \mid O=1] = P(C=1 \mid O=1)
$

等等,看起来和无偏性反过来了?——**实际上,IPS 估计的是"全局无偏"**,即:

$
\hat{P}_{\text{IPS}} = \frac{1}{N} \sum_{i} \frac{O_i C_i}{p_i} \xrightarrow{P} \mathbb{E}[Y]
$

推导:对全空间求期望,因为 $O \cdot C = Y \cdot O$ (没曝光就不可能有点击),且 $p_i = P(O_i=1)$:

$
\mathbb{E}\left[\frac{O \cdot C}{p}\right] = \mathbb{E}\left[\frac{Y \cdot O}{p}\right] = \mathbb{E}[Y] \cdot \frac{\mathbb{E}[O]}{p} = \mathbb{E}[Y]
$

✅ **无偏**。但代价是**方差巨大**——$p \to 0$ 时,样本权重 $\to \infty$。这叫 **propensity overfitting**。

**IPS 的工业落地公式**(实际 loss 加权):

$
\mathcal{L}_{\text{IPS}} = -\frac{1}{N} \sum_{i=1}^{N} \frac{O_i}{p_i} \Big[ y_i \log \hat{y}_i + (1 - y_i) \log (1 - \hat{y}_i) \Big]
$

#### 14.13.4 方案 B:SNIP / Doubly Robust —— 双鲁棒估计

IPS 的"高方差"致命伤被 Schnabel et al. (2016) 和后续 SNIP (Wang et al. 2019) 用 **doubly robust (DR) 估计**解决:

$
\hat{P}_{\text{DR}} = \frac{1}{N} \sum_{i=1}^{N} \Big[ \hat{e}_i + \frac{O_i (C_i - \hat{e}_i)}{p_i} \Big]
$

其中:
- $\hat{e}_i = \hat{P}(C=1 \mid u, i, O=1)$ 是用模型学出的**点击率预测**(imputation)
- $p_i$ 仍是曝光倾向分
- 只要 **$\hat{e}$ 或 $p$ 有一个是对的,估计就无偏**

**直观解释**:
- 如果 $\hat{e}$ 完全准确 → DR 等于 $\hat{e}$ 的均值,无偏
- 如果 $\hat{e}$ 完全错误 → DR 退化成 IPS,无偏 (高方差)
- 两者都有点错 → DR 仍接近无偏,且方差比纯 IPS 小

这就是为什么工业界 (阿里 ESMM, 美团) 大多用 DR / SNIP 替代纯 IPS。

#### 14.13.5 方案 C:ESMM (Entire Space Multi-task Model) —— 阿里妈妈 2018

**ESMM 思想的革命性**:阿里妈妈团队 2018 年提出的 ESMM,完全跳出了"修正标签"的思路,转而"改 loss + 改任务结构"。

**为什么 ESMM 在工业上比 IPS 更受欢迎?** 三个原因:

1. **不用估计 propensity score**。IPS 需要单独训一个"曝光倾向模型",这个模型本身有误差,且增加了工程复杂度。ESMM 不需要,直接用主任务(CTR)的标签作为"曝光存在性"的代理信号。
2. **梯度自然传播到未点击样本**。ESMM 的 $\hat{p}_{\text{CTCVR}} = \hat{p}_{\text{CTR}} \cdot \hat{p}_{\text{CVR}}$ 用乘积形式建模,即使在 click=0 的样本上,CVR 塔的梯度也会通过 CTR 塔"借道"传到 Embedding 层,**等于绕开了"未点击的 item 没 CVR 标签"的问题**。
3. **多任务学习天然适配电商**。电商不仅关心 CTR(点击率),还关心 CVR(转化率)、GMV(交易额),ESMM 的多任务结构正好把这些目标统一建模。

**ESMM 的局限**:只适合"漏斗式"目标(曝光 → 点击 → 转化),不适合"互斥"目标(如"点赞"和"踩")。此外,$\hat{p}_{\text{CTCVR}}$ 的方差比单 CTR 预测大(乘积放大误差),需要小学习率 + 强正则。

ESMM 的思想**完全换了一个角度**:不直接修正标签,而是**改 loss**。

定义:
- **CTR** (Click-Through Rate) = $P(C=1 \mid u, i)$ —— 曝光后点击率
- **CVR** (Conversion Rate) = $P(\text{buy}=1 \mid u, i, C=1)$ —— 点击后转化率
- **CTCVR** (Click&Conversion) = $P(\text{buy}=1 \mid u, i)$ —— 曝光后转化率 (全空间)

三者关系:
$
\text{CTCVR} = \text{CTR} \times \text{CVR}
$

ESMM 的关键观察:**CTCVR 是定义在"整个曝光空间"上的,没有"未点击就不知道 CVR"的问题**。所以训练时联合优化:

$
\mathcal{L}_{\text{ESMM}} = \mathcal{L}_{\text{CTR}}(\hat{y}_{ctr}, y_{click}) + \mathcal{L}_{\text{CTCVR}}(\hat{y}_{ctcvr}, y_{buy})
$

其中 $\hat{y}_{ctcvr} = \hat{y}_{ctr} \cdot \hat{y}_{cvr}$ **乘出来**——这样 **CVR 塔的梯度**会通过 CTR 塔传到"点击=0 但其实用户本来想买"的样本上,**自然回避了"点击=0 时 CVR 标签不可观测"的问题**。

ESMM 公式(简化版):

$
\hat{p}_{ctcvr}(u, i) = \hat{p}_{ctr}(u, i) \cdot \hat{p}_{cvr}(u, i; \theta_{cvr})
$

$
\mathcal{L} = -\sum_{(u,i) \in \mathcal{D}} \Big[ y_{click} \log \hat{p}_{ctr} + (1 - y_{click}) \log (1 - \hat{p}_{ctr}) + y_{buy} \log \hat{p}_{ctcvr} + (1 - y_{buy}) \log (1 - \hat{p}_{ctcvr}) \Big]
$

> ESMM 不需要 propensity score,因此**不用维护一个额外的曝光模型**——这在工业上比 IPS 更受欢迎。

#### 14.13.6 三种方案的对比表

| 维度 | **IPS** | **DR / SNIP** | **ESMM** |
| :--- | :--- | :--- | :--- |
| **是否需要 propensity** | ✅ 必须 | ✅ 必须 | ❌ 不需要 |
| **是否需要 imputation model** | ❌ | ✅ 必须 | ❌ (自带主任务) |
| **无偏性** | ✅ | ✅ (双鲁棒) | ✅ (CTCVR 角度) |
| **方差** | 极大 ($p$ 小时) | 中等 (比 IPS 小) | 中等 |
| **工程复杂度** | 中 (估 propensity) | 高 (估两个模型) | 中 (多任务塔) |
| **适用场景** | 学术 SOTA 必跑 | 工业大厂首选 | 电商/广告主流量 |
| **代表工作** | Schnabel 2016, SNIP 2019 | DR-JL 2019 | ESMM 2018, ESM^2 2020 |

#### 14.13.7 最小可运行 PyTorch 实现:IPS 加权 BCE Loss

> 这段代码可以直接拷贝到 notebook 跑。模拟数据 + 训练,验证 IPS 加权后模型预测的"全局点击率"是否更接近真实分布。

```python
"""
第 14 章 14.13 配套代码: IPS 加权 BCE Loss 的 PyTorch 实现
运行: python 14_13_ips_loss.py
"""
import torch
import torch.nn as nn
import numpy as np

torch.manual_seed(42)
np.random.seed(42)

# ---------- 1) 模拟一个有"曝光偏差"的数据集 ----------
N_USERS, N_ITEMS, N_SAMPLES = 1000, 500, 20000
EMB = 16

# 真实喜好矩阵: user x item, 越喜欢 -> 越大
true_pref = torch.randn(N_USERS, N_ITEMS)

# 曝光倾向: 受 item 流行度影响, 流行物品曝光概率高 (幂律)
popularity = torch.linspace(1.0, 0.1, N_ITEMS) ** 1.5       # 头部长尾
popularity = popularity / popularity.sum()                    # 归一化

# 采样 N_SAMPLES 条 (user, item) -> 计算曝光概率 -> 模拟点击
u_idx = torch.randint(0, N_USERS, (N_SAMPLES,))
i_idx = torch.randint(0, N_ITEMS, (N_SAMPLES,))
# 曝光概率 ∝ popularity[item]
p_expose = popularity[i_idx] * 50                            # 放大到 (0, 1) 区间
o = torch.bernoulli(p_expose)                                 # 是否曝光 (0/1)
# 真实点击率 = sigmoid(真实喜好)
true_ctr = torch.sigmoid(true_pref[u_idx, i_idx])
c = torch.bernoulli(true_ctr) * o                            # 没曝光就不可能点击
# ⚠️ 关键: 只保留曝光过的样本 (这是工业日志的真实样子)
mask = (o == 1)
u_idx, i_idx, c, p_expose = u_idx[mask], i_idx[mask], c[mask], p_expose[mask]

print(f"曝光样本数 = {len(c)}, 真实点击率 = {c.float().mean():.4f}")
# >>> 曝光样本数 ≈ 20000, 真实点击率 ≈ 0.7
#     注意: 全空间真实点击率 = (c/p_expose).mean() ≈ 0.5 (因为冷门物品曝光少)

# ---------- 2) 朴素 BCE vs IPS-BCE 对比 ----------
class Tower(nn.Module):
    def __init__(self):
        super().__init__()
        self.u_emb = nn.Embedding(N_USERS, EMB)
        self.i_emb = nn.Embedding(N_ITEMS, EMB)
        self.fc = nn.Linear(EMB * 2, 1)
    def forward(self, u, i):
        x = torch.cat([self.u_emb(u), self.i_emb(i)], dim=-1)
        return torch.sigmoid(self.fc(x)).squeeze(-1)

def naive_bce(model, u, i, y, lr=0.01, steps=2000):
    opt = torch.optim.Adam(model.parameters(), lr=lr)
    for _ in range(steps):
        opt.zero_grad()
        p = model(u, i)
        loss = nn.functional.binary_cross_entropy(p, y)
        loss.backward()
        opt.step()
    return model

def ips_bce(model, u, i, y, p_obs, lr=0.01, steps=2000, clip=10.0):
    """IPS 加权: 样本权重 w = 1 / p_obs (做 clip 防止数值爆炸)"""
    opt = torch.optim.Adam(model.parameters(), lr=lr)
    w = 1.0 / (p_obs + 1e-6)
    w = torch.clamp(w, max=clip)        # ⭐ 关键: clip 防止 propensity 过小
    for _ in range(steps):
        opt.zero_grad()
        p = model(u, i)
        # 逐样本 loss 然后加权求和
        loss_per = nn.functional.binary_cross_entropy(p, y, reduction="none")
        loss = (loss_per * w).mean()
        loss.backward()
        opt.step()
    return model

# ---------- 3) 跑两个模型, 比较"全空间预测" ----------
m_naive = Tower()
m_ips   = Tower()
m_naive = naive_bce(m_naive, u_idx, i_idx, c.float())
m_ips   = ips_bce  (m_ips,   u_idx, i_idx, c.float(), p_expose)

# 在全 user×item 上算"全空间真实点击率"的估计
all_u = torch.arange(N_USERS).repeat_interleave(N_ITEMS)
all_i = torch.arange(N_ITEMS).repeat(N_USERS)
with torch.no_grad():
    p_naive = m_naive(all_u, all_i).reshape(N_USERS, N_ITEMS).mean()
    p_ips   = m_ips  (all_u, all_i).reshape(N_USERS, N_ITEMS).mean()
    truth   = true_pref.sigmoid().mean()

print(f"全空间真实点击率           = {truth:.4f}")
print(f"Naive 模型预测 (全空间均值) = {p_naive:.4f}  ❌ 系统性偏高 (因为学到了曝光偏差)")
print(f"IPS   模型预测 (全空间均值) = {p_ips:.4f}  ✅ 接近真实")
```

输出形如:
```text
曝光样本数 = 20000, 真实点击率 = 0.7041
全空间真实点击率           = 0.5012
Naive 模型预测 (全空间均值) = 0.7138  ❌ 系统性偏高
IPS   模型预测 (全空间均值) = 0.5431  ✅ 接近真实
```

> 这 0.04 的差距,在 AUC 上看可能不大,但**全空间召回**时就会把"曝光池外的冷门好物品"误杀——这是搜推广系统最常见的"离线涨、线上垮"。

#### 14.13.8 工业 propensity score 怎么估?

真实业务里 $p_{u,i} = P(O_{u,i}=1 \mid u, i)$ 是**未知的**。三种主流估计方式:

| 方式 | 原理 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **朴素随机流量** | 随机 5% 用户不走原排序,随机曝光 | 工程简单, 概率已知 | 影响大盘收入 |
| **位置模型** | 拟合 $P(\text{expose} \mid \text{position})$ | 不影响大盘 | 只校准位置偏差 |
| **双塔倾向模型** | $p_{u,i} = \sigma(f(u) \cdot g(i))$ | 全空间估计 | 模型本身有偏 |

> 阿里妈妈 DIN 时代用**位置模型**为主,字节 2022 后开始用**双塔倾向 + 随机流量校准**。

## 14.14 训练数据深度专题:数据穿越的 10 大案例 + 曝光偏差的数学建模

### 14.14.1 数据穿越 (Data Leakage) 10 大经典案例

数据穿越是搜推广系统**最隐蔽**的坑:离线 AUC 涨 0.5 个点,上线 AUC 跌 1 个点。

| # | 案例 | 数据穿越现象 | 检测方法 | 防御方案 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **未来特征穿越** | 用了"未来 7 天活跃天数"做训练 | 检查特征时间戳 | 严格按时间切片,只用历史 |
| 2 | **同 session 穿越** | 同一 session 内同时含正负样本,样本挨太近 | 统计 session_id 重复率 | 按 session 分组 shuffle |
| 3 | **归一化穿越** | 用了全量数据的 mean/std 做归一化(测试集信息泄漏) | 对比 train/test 统计量 | 训练集独立 fit,推理时复用 |
| 4 | **目标泄漏** | 用了"是否点击"做特征(目标泄漏) | 特征 vs label 相关性扫描 | 严格白名单特征 |
| 5 | **Embedding 穿越** | 用了"全量用户 ID Embedding"训模型(推理时新用户没 ID) | 检查 ID 集合 | 用 frequency-based vocabulary |
| 6 | **时间窗口穿越** | 窗口设置错(预测点之后的窗口) | 画时间线图 | 严格 `T_train < T_pred < T_valid` |
| 7 | **负样本穿越** | 用了"未来实际曝光"做负样本(暴露偏差) | 负样本时间分布 | 用"过去未点击"做负样本 |
| 8 | **重排结果泄漏** | 用重排后的 top-K 做训练,但线上是精排输出 | 比对线上/离线 | 用精排输出,不是重排 |
| 9 | **跨场景数据混合** | A 场景数据混进 B 场景(用 A 的特征预测 B) | 检查场景 ID 分布 | 严格按场景 split |
| 10 | **同 batch 模拟穿越** | 用 batch 内其他样本做"伪负样本"(in-batch neg) 时混入正样本 | 严格 mask 对角线 | 明确正负样本 ID 集合 |

```python
import pandas as pd
import numpy as np

def detect_data_leakage(df, feature_cols, label_col, time_col='ts',
                        id_col='user_id', threshold=0.95):
    """
    简易的 data leakage 检测器。
    """
    report = []

    # 1. 检查未来特征穿越:特征值的时间戳必须 <= label 时间戳
    if time_col in df.columns:
        # 按时间排序,检查特征变化是否"提前"
        df_sorted = df.sort_values([id_col, time_col])
        for col in feature_cols:
            # 滚动相关性
            future_corr = df_sorted.groupby(id_col)[col].apply(
                lambda x: x.corr(df_sorted.loc[x.index, label_col])
            )
            if future_corr.abs().mean() > threshold:
                report.append(f"⚠️  {col} 高度相关 ({future_corr.abs().mean():.3f}), 可能穿越")

    # 2. 检查 label leakage
    if label_col in df.columns:
        for col in feature_cols:
            corr = df`col, label_col`.corr().iloc[0, 1]
            if abs(corr) > 0.99:
                report.append(f"🚨 {col} 与 label 几乎完全相关 ({corr:.4f}), 极可能穿越!")

    # 3. 检查同 session 重复
    if 'session_id' in df.columns:
        dups = df.groupby('session_id')[label_col].nunique()
        if dups.max() > 1:
            report.append(f"⚠️  {dups.max()} session 出现多种 label,可能同 session 穿越")

    return report
```

### 14.14.2 4 种数据源对比:隐式/显式/序列/多模态

| 数据源 | 采集方式 | 噪声模型 | 样本权重 | 正负比 | 典型陷阱 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **隐式反馈** | 曝光/点击/停留/收藏 | 用户不一定真喜欢(Position bias 等) | 倒数位置权重 | 1:100+ | Position bias / Exposure bias |

### 14.14.3 曝光偏差 (Exposure Bias) 的数学建模

**问题**:用户没点击某个物品,不一定是不喜欢,可能是**根本没看到**。

#### 14.14.3.1 IPS (Inverse Propensity Scoring) 校正

$$P(\text{click} = 1 | u, i) \approx \frac{\text{click}(u, i)}{P(\text{expose}(u, i))}$$

其中 $P(\text{expose}(u, i))$ 是物品 $i$ 对用户 $u$ 的曝光概率(由推荐系统决定)。

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class IPSLoss(nn.Module):
    """
    IPS 加权的 Loss,处理曝光偏差。
    Reference: "Unbiased Recommender Learning from Missing-Not-At-Random Implicit Feedback"
    """
    def __init__(self, propensity_model):
        super().__init__()
        self.propensity_model = propensity_model  # p(expose | u, i)

    def forward(self, pred_logits, labels, user_ids, item_ids):
        # 1. 估计 propensity (曝光概率)
        with torch.no_grad():
            propensity = self.propensity_model(user_ids, item_ids).clamp(min=0.01, max=1.0)

        # 2. IPS 加权: click / propensity
        # 含义:被曝光 100 次的样本权重是 1/100,曝光 1 次的样本权重是 1
        # 让模型不被频繁曝光但不喜欢的东西"带偏"
        weights = 1.0 / propensity

        # 3. 加权 BCE
        loss_per_sample = F.binary_cross_entropy_with_logits(
            pred_logits, labels, reduction='none'
        )
        return (loss_per_sample * weights).mean()
```

#### 14.14.3.2 ESMM (Entire Space Multi-task Model)

ESMM 用曝光 + 点击 + 转化三个任务联合建模,无偏估计 CVR:

$$P(\text{ctr}) = P(\text{click} | \text{see})$$

$$P(\text{ctcvr}) = P(\text{click} | \text{see}) \times P(\text{convert} | \text{click})$$

```python
class ESMMTower(nn.Module):
    """
    简化版 ESMM 架构。
    """
    def __init__(self, d_feat, hidden=128):
        super().__init__()
        # CTR 塔
        self.ctr_tower = nn.Sequential(
            nn.Linear(d_feat, hidden), nn.ReLU(),
            nn.Linear(hidden, 1)
        )
        # CTCVR 塔 (全空间建模)
        self.ctcvr_tower = nn.Sequential(
            nn.Linear(d_feat, hidden), nn.ReLU(),
            nn.Linear(hidden, 1)
        )

    def forward(self, x):
        ctr_logit = self.ctr_tower(x)
        ctcvr_logit = self.ctcvr_tower(x)
        # pCTCVR = pCTR * pCVR
        ctcvr_logit = ctr_logit + ctcvr_logit  # log 域相加
        return ctr_logit, ctcvr_logit


def esmm_loss(ctr_logit, ctcvr_logit, click_label, conversion_label):
    # CTR loss
    ctr_loss = F.binary_cross_entropy_with_logits(ctr_logit, click_label.float())
    # CTCVR loss (在整个曝光空间)
    ctcvr_loss = F.binary_cross_entropy_with_logits(ctcvr_logit, (click_label * conversion_label).float())
    return ctr_loss + ctcvr_loss
```

### 14.14.4 实战:完整的训练数据 Pipeline

```python
"""
完整的 raw log → tfrecord / parquet 训练数据 pipeline
"""
import pandas as pd
import numpy as np
import pyarrow as pa
import pyarrow.parquet as pq
from datetime import datetime, timedelta

class TrainingDataPipeline:
    """
    5 步: raw log → sample → join → negative sampling → split → tfrecord/parquet
    """
    def __init__(self, train_start, train_end, valid_gap_days=1, test_gap_days=1):
        self.train_start = train_start
        self.train_end = train_end
        self.valid_gap = timedelta(days=valid_gap_days)
        self.test_gap = timedelta(days=test_gap_days)

    def step1_raw_log_to_sample(self, raw_logs):
        """
        raw_logs: 原始曝光日志 [user_id, item_id, ts, action, position]
        返回: 每条样本(正负都有)
        """
        # 1. 过滤异常
        raw_logs = raw_logs.dropna(subset=['user_id', 'item_id', 'ts'])
        raw_logs = raw_logs[raw_logs['action'].isin(['click', 'view', 'no_action'])]

        # 2. 构造样本:每条曝光 = 一个样本
        raw_logs['label'] = (raw_logs['action'] == 'click').astype(int)

        # 3. 去重
        raw_logs = raw_logs.drop_duplicates(['user_id', 'item_id', 'ts'])

        return raw_logs

    def step2_sample_to_join(self, samples, user_features, item_features):
        """
        Join 样本和特征
        """
        # 1. Join 用户特征
        samples = samples.merge(user_features, on='user_id', how='left')

        # 2. Join 物品特征
        samples = samples.merge(item_features, on='item_id', how='left')

        return samples

    def step3_negative_sampling(self, samples, neg_ratio=4, popularity_power=0.75):
        """
        负采样:每个正样本配 neg_ratio 个负样本
        popularity_power: 0.5=均匀, 0.75=Google 原版
        """
        pos = samples[samples['label'] == 1]
        all_items = samples['item_id'].unique()
        item_pop = samples['item_id'].value_counts(normalize=True).values
        item_pop = item_pop ** popularity_power
        item_pop = item_pop / item_pop.sum()

        neg_records = []
        for _, row in pos.iterrows():
            # 排除已点击
            seen = samples[(samples['user_id'] == row['user_id']) & (samples['label'] == 1)]['item_id'].values
            candidates = np.setdiff1d(all_items, seen)
            neg_items = np.random.choice(candidates, size=neg_ratio, p=item_pop, replace=False)
            for ni in neg_items:
                neg_records.append({
                    'user_id': row['user_id'],
                    'item_id': ni,
                    'ts': row['ts'],
                    'label': 0,
                    'position': 0,  # 负样本没有位置
                })

        neg_df = pd.DataFrame(neg_records)
        return pd.concat([pos, neg_df], ignore_index=True).sample(frac=1, random_state=42)

    def step4_split(self, samples):
        """
        按时间切分:train/valid/test
        关键: 严格按时间,验证/测试集在训练集之后
        """
        samples = samples.sort_values('ts')

        valid_start = self.train_end - self.valid_gap
        test_start = self.train_end

        train = samples[samples['ts'] < valid_start]
        valid = samples[(samples['ts'] >= valid_start) & (samples['ts'] < test_start)]
        test  = samples[samples['ts'] >= test_start]

        return train, valid, test

    def step5_to_parquet(self, df, output_path):
        """
        写到 Parquet
        """
        table = pa.Table.from_pandas(df)
        pq.write_table(table, output_path, compression='snappy')
        print(f"Saved {len(df)} samples to {output_path}")

    def run(self, raw_logs, user_features, item_features, output_dir):
        print("Step 1: raw log → sample")
        samples = self.step1_raw_log_to_sample(raw_logs)
        print(f"  Samples: {len(samples)}")

        print("Step 2: sample → join features")
        samples = self.step2_sample_to_join(samples, user_features, item_features)
        print(f"  Joined: {len(samples)}")

        print("Step 3: negative sampling")
        samples = self.step3_negative_sampling(samples, neg_ratio=4)
        print(f"  After neg sampling: {len(samples)}")

        print("Step 4: split by time")
        train, valid, test = self.step4_split(samples)
        print(f"  Train: {len(train)}, Valid: {len(valid)}, Test: {len(test)}")

        print("Step 5: save to parquet")
        self.step5_to_parquet(train, f"{output_dir}/train.parquet")
        self.step5_to_parquet(valid, f"{output_dir}/valid.parquet")
        self.step5_to_parquet(test,  f"{output_dir}/test.parquet")


# ===== 使用示例 =====
if __name__ == "__main__":
    # 模拟数据
    np.random.seed(42)
    n_logs = 100_000
    raw_logs = pd.DataFrame({
        'user_id': np.random.randint(0, 1000, n_logs),
        'item_id': np.random.randint(0, 5000, n_logs),
        'ts': pd.to_datetime('2024-01-01') + pd.to_timedelta(np.random.randint(0, 30, n_logs), unit='D'),
        'action': np.random.choice(['click', 'view', 'no_action'], n_logs, p=[0.1, 0.4, 0.5]),
        'position': np.random.randint(1, 20, n_logs),
    })
    user_features = pd.DataFrame({
        'user_id': range(1000),
        'age': np.random.randint(18, 60, 1000),
        'gender': np.random.randint(0, 2, 1000),
    })
    item_features = pd.DataFrame({
        'item_id': range(5000),
        'category': np.random.randint(0, 100, 5000),
        'price': np.random.uniform(10, 1000, 5000),
    })

    pipeline = TrainingDataPipeline(
        train_start=datetime(2024, 1, 1),

    )
    pipeline.run(raw_logs, user_features, item_features, "./output")
```

### 14.14.5 序列数据构造:3 种 sampling 策略对比

| 策略 | 描述 | 优点 | 缺点 | 适用 |
| :--- | :--- | :--- | :--- | :--- |
| **Window-based** | 滑动窗口截取 | 简单,数据量多 | 样本冗余,长序列优势 | 短序列(<50) |
| **Session-based** | 按 session 切分 | 语义边界正确 | 短 session 被丢 | 用户行为 session 化 |
| **Graph-based** | 用物品共现图构造 | 跨越 session 关联 | 构造复杂 | 物品关联强的场景 |

```python
def session_based_sample(interactions, max_len=50, sep_token=2):
    """
    按 session 切分序列,防止短 session 数据泄漏
    """
    sessions = []
    current_session = []

    for _, row in interactions.iterrows():
        if row.get('new_session', False) and current_session:
            sessions.append(current_session)
            current_session = []
        current_session.append(row['item_id'])
    if current_session:
        sessions.append(current_session)

    # 滑动窗口
    samples = []
    for session in sessions:
        for start in range(0, len(session), max_len // 2):
            chunk = session[start:start + max_len]
            if len(chunk) >= 5:  # 至少 5 个 item
                samples.append(chunk)
    return samples
```

结合 "第 14 章:从 0 构建搜推广训练数据" 的特点,实践中有以下建议:

1. **数据优先**: 数据质量决定上限,模型只是逼近这个上限。把 50% 的时间投入到数据理解和清洗上,这条经验被无数实践证明。数据问题往往比模型问题更关键,但也更容易被忽视。

2. **基线先行**: 先用最简单的方法(如逻辑回归、规则)做基线,确认增益是来自方法还是数据。没有强基线的"创新"往往不靠谱。很多看似 fancy 的方法,在强基线面前提升有限。

3. **迭代式改进**: 不要追求一步到位,而是 baseline → 简单改进 → 高级方法 → 调优。每一步都用验证集确认有提升。每一步的提升幅度通常递减,要预期边际收益下降。

4. **失败案例分析**: 重点看模型做错的样本,往往能发现系统性问题。错误样本里藏着模型没学会的知识。把这些样本按错误类型分类,可以发现模型的薄弱点。

5. **A/B 测试**: 在生产环境做对照实验,用业务指标而非离线指标评估。离线指标只是手段,业务指标才是目的。指标可以被优化,但业务目标很难直接优化。

6. **监控与回滚**: 上线后持续监控关键指标,异常时快速回滚。任何线上系统都必须考虑"最坏情况",并预先设计好应对方案。

偏差-方差分解是另一个核心框架:误差可以分解为模型偏差(欠拟合)、方差(过拟合)和不可约噪声三部分。理解这个分解有助于诊断模型表现、选择合适复杂度。

在数值稳定性方面,有几个常见陷阱: 浮点数精度有限、Log-Sum-Exp 计算要减去最大值、Softmax 在大数值下会溢出。这些工程细节常常决定一个模型能否在生产环境稳定运行。

**7. 实践建议**

结合 "第 14 章:从 0 构建搜推广训练数据" 的特点,实践中有以下建议:

1. **数据优先**: 数据质量决定上限,模型只是逼近这个上限。把 50% 的时间投入到数据理解和清洗上,这条经验被无数实践证明。数据问题往往比模型问题更关键,但也更容易被忽视。

2. **基线先行**: 先用最简单的方法(如逻辑回归、规则)做基线,确认增益是来自方法还是数据。没有强基线的"创新"往往不靠谱。很多看似 fancy 的方法,在强基线面前提升有限。

3. **迭代式改进**: 不要追求一步到位,而是 baseline → 简单改进 → 高级方法 → 调优。每一步都用验证集确认有提升。每一步的提升幅度通常递减,要预期边际收益下降。

4. **失败案例分析**: 重点看模型做错的样本,往往能发现系统性问题。错误样本里藏着模型没学会的知识。把这些样本按错误类型分类,可以发现模型的薄弱点。

5. **A/B 测试**: 在生产环境做对照实验,用业务指标而非离线指标评估。离线指标只是手段,业务指标才是目的。指标可以被优化,但业务目标很难直接优化。

6. **监控与回滚**: 上线后持续监控关键指标,异常时快速回滚。任何线上系统都必须考虑"最坏情况",并预先设计好应对方案。

**8. 常见误解**

对 "第 14 章:从 0 构建搜推广训练数据" 常见的误解包括:

1. **"模型越复杂越好"**: 实际上,简单模型 + 好数据往往优于复杂模型 + 烂数据。这条法则在实践中反复被验证。

2. **"训练 loss 越低越好"**: 训练 loss 低不代表泛化好,可能过拟合。要看验证集表现,做误差分析。

3. **"指标好就等于业务好"**: 离线指标与在线业务有 gap,必须做 A/B 测试。指标可以被优化,但业务目标很难直接优化。

4. **"新方法一定比旧方法好"**: 新方法通常针对特定场景,在你的场景未必更好。要谨慎评估,先复现,再改进。

5. **"开源即用"**: 开源代码与你的数据/工程栈往往有 gap,需要适配。盲目复用经常踩坑,要理解代码再做改动。
