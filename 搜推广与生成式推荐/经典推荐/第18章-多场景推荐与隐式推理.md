## 1. 多场景推荐:挑战与动机

### 1.1 什么是"多场景"?

**多场景的本质:同一个用户在不同页面/入口/时段的偏好差异**。

**为什么多场景比"单场景通用模型"更复杂?**

想象一个 App 首页(瀑布流 + 顶部 banner)和一个详情页(看了又看)。同一个用户在两个场景的"决策模式"完全不同:

- **首页场景**:用户漫无目的刷,被"颜值高"的内容吸引 → 浅点击、点得快
- **详情场景**:用户已经对某个 item 感兴趣,要看"相关推荐" → 决策深、转化高

如果用同一个模型同时服务两个场景,模型会被"漫无目的的首页"主导,详情页效果掉。这就是为什么需要**多场景建模**。

**典型 App 的多场景**:

```text
┌──────────────────────────────────────────┐
│               App 首页                       │
│  ┌──────────┬──────────┬──────────┐       │
│  │ 顶部 Banner │  双列流   │ 底部导航  │     │
│  │  (大图卡) │ (视频卡) │ (图标)    │     │
│  └──────────┴──────────┴──────────┘       │
└──────────────────────────────────────────┘
        │              │              │
       点击           点击           点击
        ↓              ↓              ↓
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 详情页    │  │ 搜索页    │  │ 推送通知  │   ← 多个场景
│ 相关推荐  │  │ 搜索结果  │  │ 推送内容  │
│ "看了又看" │  │          │  │          │
└──────────┘  └──────────┘  └──────────┘
```

每个场景:
- **特征不同**:详情页有"物品详情"特征,搜索页有"搜索 query"特征
- **目标不同**:首页优化"首屏点击",详情页优化"二次点击",搜索页优化"相关性"
- **用户行为分布不同**:首页点击率 ~10%,详情页"看了又看"点击率 ~5%

### 1.2 多场景建模的挑战

**多场景建模面对的 4 个核心挑战,每一个都不是"小问题"**。

**挑战 1:数据分布差异巨大**——首页的曝光分布(头部 item 占据 80% 曝光)vs 详情页的"长尾分布"(相关 item 极分散),统计特征完全不同。一个全局模型会"次优适配每个场景"——既不是最优首页,也不是最优详情页。

**挑战 2:参数效率的天平**——为每个场景训独立模型 → N 倍参数 + N 倍工程成本,长尾场景(推送通知)数据量训不动。完全共享底层 → 牺牲场景特定性,详情页和首页的差异被"磨平"。

**挑战 3:长尾场景的"数据稀疏"**——头部场景(首页)有几亿条样本,长尾场景(推送通知)只有几万条,**训不动深度模型**。怎么"借"头部场景的数据补长尾场景,是多场景建模的核心难题。

**挑战 4:场景间关联**——同一用户跨场景行为**有连贯性**(在首页点了 A,在详情页可能继续看)。场景间不能完全独立,但**共享太多又回到挑战 1**。这是"场景共享 vs 场景独立"的辩证问题。

**多场景建模的目标**:找到一个**统一模型**,既能享受共享参数的高效,又能针对每个场景做适配。

**挑战 1:数据分布差异大**
- 不同场景的用户意图、物品池、特征空间都不同
- 一个全局模型 → "次优适配每个场景"

**挑战 2:参数效率**
- 为每个场景训独立模型 → N 倍参数、N 倍工程
- 共享底层 → 牺牲场景特定性

**挑战 3:数据稀疏**
- 长尾场景(推送通知)数据量少,训不动
- 头部场景(首页)数据量多,但用户口味可能代表整体

**挑战 4:场景间关联**
- 同一用户跨场景行为**有连贯性**(在首页点了 A,在详情页可能继续看)
- 场景间**不能完全独立**

### 1.3 多场景建模的目标

> **找到一个模型,既能享受共享参数的高效,又能针对每个场景做适配**

## 2. 多场景架构:Shared / MMoE / STAR / M2M

### 2.1 共享 + 场景塔(最朴素)

**这是工业界最先尝试的"多场景方案",动机很朴素**。

**为什么"共享底层 + 场景塔"看似合理?**

不同场景(首页/详情/搜索)本质上是同一个用户在不同页面产生的行为。如果完全用 N 个独立模型,既浪费参数(底层特征工程其实可以共用),又丢掉了"用户跨场景偏好稳定"这个先验。共享底层让用户/物品/上下文的通用表征被多个场景复用,场景塔只负责拟合各自的目标分布。**参数效率高、工程简单、效果好于完全独立模型**,这是大多数工业团队的"第一版多场景方案"。

**这种结构的硬伤**:场景塔之间没有信息通道,首页学到的"用户对运动鞋的偏好"无法传递给详情页塔。所有共享只能发生在最底层的稠密向量层,**场景间知识无法深度融合**。对场景间关联强的业务(同一用户在首页和详情页的连续行为),这个结构会浪费"跨场景信号"。

**适用场景**:3 个以内场景、场景间关联弱、工程上想快速上线的 MVP 场景。**3 个以上场景建议升级到 MMoE 或 STAR**。

**文字**: 工业界最先尝试的方案是"共享底层 + 场景塔"。动机很朴素:不同场景(首页/详情/搜索)本质上是同一个用户在不同页面产生的行为,如果完全用 N 个独立模型,既浪费参数(底层特征工程其实可以共用),又丢掉了"用户跨场景偏好稳定"这个先验。共享底层让用户/物品/上下文的通用表征被多个场景复用,场景塔只负责拟合各自的目标分布。但这种结构的硬伤在于场景塔之间没有信息通道,首页学到的"用户对运动鞋的偏好"无法传递给详情页塔,所有共享只能发生在最底层的稠密向量层。

```python
class SharedMultiSceneModel(nn.Module):
    """共享底层 + 每个场景一个塔"""
    def __init__(self, in_dim, scene_list, hidden=128):
        super().__init__()
        # 共享底层
        self.shared = nn.Sequential(
            nn.Linear(in_dim, hidden), nn.ReLU(), nn.LayerNorm(hidden)
        )
        # 每个场景一个塔
        self.towers = nn.ModuleDict({
            scene: nn.Sequential(
                nn.Linear(hidden, hidden), nn.ReLU(), nn.Linear(hidden, 1)
            )
            for scene in scene_list
        })

    def forward(self, x, scene):
        h = self.shared(x)
        return self.towers[scene](h)
```

**缺点**: 场景塔**完全独立**,没有共享场景间信息。

### 2.2 MMoE/MMoE for 多场景(第 4 章介绍过,这里应用于多场景)

**MMoE 的提出是为了解决"共享底层"过于刚性的问题**。

**Shared + 塔的局限**:
所有场景共享同一份底层表达,但场景之间可能存在冲突。首页的曝光分布和详情页的"看了又看"分布差异巨大,共享底层会被"拉平"到平均值,无法照顾每个场景的特征子空间。

**MMoE 的核心创新**:**专家(Expert)+ 门控(Gate)机制**。

- 多个专家各自拟合输入的不同子结构
- 门控根据当前样本动态选择专家组合
- 场景间共享的是"专家集合"而非单一表征

这点很像 Attention,但训练时门控是场景级的,推理时可按场景路由。**美团外卖、淘宝首推等场景里被广泛验证**。

**MMoE 的"专家退化"问题**:
实践中专家容易"站队"——大部分专家被某个场景的强梯度主导,其他场景拿不到有用信号,**专家分布不均**导致效果打折。**升级方案是 PLE**(下一节),用"共享专家 + 私有专家"分离式设计,缓解这个问题。

**MMoE 适用场景**:3-5 个场景,场景间相关性中等,工程团队有 GPU 资源跑多个专家+门控。**10+ 场景建议用 STAR**(参数更高效)。

**文字**: MMoE 的提出是为了解决"共享底层"过于刚性的问题。在 Shared + 塔结构里,所有场景共享同一份底层表达,但场景之间可能存在冲突。首页的曝光分布和详情页的"看了又看"分布差异巨大,共享底层会被"拉平"到平均值,无法照顾每个场景的特征子空间。MMoE 引入了专家(Expert)+门控(Gate)机制:多个专家各自拟合输入的不同子结构,门控根据当前样本动态选择专家组合,场景间共享的是"专家集合"而非单一表征。这点很像 Attention,但训练时门控是场景级的,推理时可按场景路由,在美团外卖、淘宝首推等场景里被广泛验证。

```python
class MMoEMultiScene(nn.Module):
    """每个场景一个 MMoE 门控,共享同一组专家"""
    def __init__(self, in_dim, expert_dim=64, num_experts=4, scenes=['home', 'detail', 'search']):
        super().__init__()
        # 共享专家
        self.experts = nn.ModuleList([
            nn.Sequential(nn.Linear(in_dim, expert_dim), nn.ReLU())
            for _ in range(num_experts)
        ])
        # 每个场景的门控
        self.gates = nn.ModuleDict({
            scene: nn.Linear(in_dim, num_experts) for scene in scenes
        })
        # 每个场景的头
        self.heads = nn.ModuleDict({
            scene: nn.Linear(expert_dim, 1) for scene in scenes
        })

    def forward(self, x, scene):
        expert_outs = torch.stack([e(x) for e in self.experts], dim=1)  # [B, n_experts, D]
        gate = self.gates[scene]
        alpha = F.softmax(gate(x), dim=-1)                                # [B, n_experts]
        h = (alpha.unsqueeze(-1) * expert_outs).sum(dim=1)                 # [B, D]
        return self.heads[scene](h)
```

### 2.3 STAR(Star Topology Adaptive Recommender, Alibaba 2021)

**STAR = Star Topology Adaptive Recommender,Alibaba 2021 在 KDD 发表的工业级多场景架构**。

**STAR 的动机**:
MMoE 解决了"动态路由"问题,但参数量和工程复杂度随之膨胀。每个场景的专家、门控、塔都要单独维护,新加一个场景要重训整个专家池。Alibaba 的 STAR 动机是**"参数要小、训练要稳、冷启动要友好"**。

**STAR 的核心观察**:
**场景之间的差异可以视作对共享参数的一个微小偏置(delta),不需要每个场景都学一整套专家**。STAR 学一个 $W_{\text{shared}}$ + $\alpha \odot W_{\text{scene}}$ 的组合,$\alpha$ 由场景门控生成,本质是用"低秩分解 + 门控缩放"模拟全参数的场景适配。

**数学形式**:
$$
W_{\text{eff}} = W_{\text{shared}} + \alpha_s \odot W_{\text{scene}}
$$
其中 $\alpha_s$ 是场景 $s$ 的门控向量,$\odot$ 是逐元素乘。

**STAR 的工业优势**:
- **参数量小**:场景特定参数 = 共享参数的 1% 量级
- **冷启动友好**:新场景只需学一个 delta,不重训全模型——上个月淘宝购物车页新加"猜你喜欢"场景,只学一行 delta 就能上线
- **训练稳定**:不涉及多专家的门控冲突,loss 曲线更平滑

**STAR 适用场景**:**3 到 10 个场景、相关性中等的场景**。淘宝的首页瀑布流、购物车页、店铺内页都用 STAR。冷启动新场景只学 $W_{\text{scene}}$ 一行参数即可,不用重训全模型。

**文字**: MMoE 解决了"动态路由"问题,但参数量和工程复杂度随之膨胀。每个场景的专家、门控、塔都要单独维护,新加一个场景要重训整个专家池。Alibaba 在 2021 年提出 STAR,动机是"参数要小、训练要稳、冷启动要友好"。核心观察是场景之间的差异可以视作对共享参数的一个微小偏置(delta),不需要每个场景都学一整套专家。STAR 学一个 $W_{shared}$ + $\alpha$⊙$W_{scene}$ 的组合,$\alpha$ 由场景门控生成,本质是用"低秩分解 + 门控缩放"模拟全参数的场景适配。工业上 STAR 适合 3 到 10 个场景、相关性中等的场景(如淘宝的首页瀑布流、购物车页、店铺内页),冷启动新场景只学 $W_{scene}$ 一行参数即可,不用重训全模型。

**核心思想**: 用"星形"结构——**场景特定参数**和**场景共享参数**线性组合。

**架构**:

```text
                 [场景共享参数] W_shared
输入 x → [共享底层] → h ─────────┐
                                 ├─→ 相加 → W_shared + α * W_scene  → 预测
[场景 one-hot] → α = ...        ─┘

[场景特定参数] W_scene ──────────┘
```

**关键创新**: 不是"学一套场景特定参数",而是**学一个 delta**(对共享参数的微调):

$$W_{\text{eff}} = W_{\text{shared}} + \alpha_s \odot W_{\text{scene}}$$

其中 $\alpha_s$ 是**场景 $s$ 的门控向量**,$\odot$ 是逐元素乘。

```python
class STARModel(nn.Module):
    """Star Topology Adaptive Recommender"""
    def __init__(self, in_dim, hidden_dim, num_scenes):
        super().__init__()
        # 共享底层
        self.shared = nn.Linear(in_dim, hidden_dim, bias=False)
        # 场景特定参数(每个场景一份)
        self.scene_params = nn.Parameter(
            torch.randn(num_scenes, hidden_dim, in_dim) * 0.01
        )
        # 场景门控:为每个场景学习一个缩放向量
        self.scene_gates = nn.Linear(num_scenes, hidden_dim)  # [num_scenes] → [hidden_dim]
        # 场景偏置
        self.scene_bias = nn.Parameter(torch.zeros(num_scenes, hidden_dim))

    def forward(self, x, scene_id):
        # x: [B, in_dim]
        # scene_id: [B] (int)
        # 共享路径
        h_shared = self.shared(x)                              # [B, hidden]
        # 场景特定路径
        W_scene = self.scene_params[scene_id]                    # [B, hidden, in_dim]
        gate = self.scene_gates(F.one_hot(scene_id, num_scenes).float())  # [B, hidden]
        h_scene = (W_scene @ x.unsqueeze(-1)).squeeze(-1) * torch.sigmoid(gate)  # [B, hidden]
        bias = self.scene_bias[scene_id]                          # [B, hidden]
        return h_shared + h_scene + bias
```

**优势**:
- 参数量小(场景特定参数 = 共享参数的 1% 量级)
- 场景间共享大部分知识,只在 delta 上分化
- **冷启动友好**:新场景只需学一个 delta,不重训全模型

### 2.4 M2M(Multi-level Multi-task Multi-domain, 字节 2023)

**文字**: STAR 解决了"参数高效"问题,但当场景数继续增长到几十个(字节的抖音/今日头条有首页、关注、直播、商城、搜索、本地生活等多个独立场景),或者一个场景内同时要预测 CTR/CVR/点赞/完播/分享等多个目标时,单一门控已不够用。M2M 的核心是"分层门控":域级别门控做粗粒度的场景路由,场景级别门控做细粒度的任务路由。多层级的好处是参数效率继续提升(细粒度参数不重复),且不同层级可以独立做 A/B 实验。换域门控不影响场景门控,工程上更友好,适合抖音这种"几十个场景 + 多个任务"的产品形态。

**核心思想**: 多场景 + 多任务 + 多域的统一框架。

**架构**:

```text
                [场景编码] (one-hot or learned)
                 ↓
输入 x → [域内共享专家] → M 个专家输出
                 ↓ (门控)
              [场景门控]
                 ↓
            多个任务的塔(CTR, CVR, etc.)
```

**M2M 的关键点**:
- **多层级门控**:域级别 + 场景级别两层门控
- **场景内多任务**:每个场景的 CTR/CVR 联合训练
- **场景间共享专家**:减少参数量

### 2.5 架构选型决策

**架构选型不是"哪个最好",是"哪个最匹配"**。决策的核心是**场景数 × 场景相关性 × 工程资源** 三个维度的权衡:

| 场景数 | 场景相关性 | 推荐架构 | 工业案例 |
| :--- | :--- | :--- | :--- |
| 2-3 | 高(首页+详情) | Shared + 场景塔 | 早期淘宝,简单业务 |
| 2-3 | 中 | MMoE for scenes | 美团外卖推荐 |
| 3-10 | 中-低 | **STAR (推荐)** | 淘宝购物车页/详情页 |
| 5+ | 各种 | M2M / 多级 MoE | 字节抖音(几十个场景) |

**选型的三个判断问题**:

1. **场景数 ≤ 3 且场景间差异小** → Shared + 场景塔,简单实用
2. **场景数 3-10,场景间差异中等,需要冷启动新场景** → STAR,工业甜区
3. **场景数 10+,或一个场景内多任务(CTR/CVR/完播)** → M2M / 多级 MoE,字节/阿里大厂主选

**反向陷阱**:
- **不要为 2 个场景上 MMoE**——杀鸡用牛刀,工程复杂度陡增,AUC 提升 < 0.5%
- **不要为 50 个场景上 STAR**——场景门控本身要训 50 套,参数量爆炸
- **不要一上来就上 M2M**——多级门控 + 多任务的组合,debug 极其困难,先用简单架构跑通,再迭代升级

## 3. 隐式反馈:正样本、负样本、置信度

### 3.1 隐式反馈的种类

**隐式反馈是搜推广的"第一信号源"**——绝大多数业务(电商、短视频、广告)没有用户主动打的 1-5 星,**只有点击、停留、购买这些"行为副作用"**。但这些副作用的"信号强度"差异巨大,直接当 0/1 用会浪费信息。

**正样本的"信号强度天梯"**:

- **点击**:最弱正信号(用户被吸引,但不一定是真喜欢)
- **完播 / 长停留**:中强(短视频 / 直播 / 商品详情页)
- **点赞 / 收藏**:中强(用户主动表态)
- **评论**:中强(用户参与互动)
- **分享 / 转发**:强(社交背书)
- **购买 / 订阅**:最强(用户付出真金白银)

**负样本的"信号强度天梯"**:

- **曝光未点击**:最弱负信号(可能没看到)
- **短停留后跳出**(< 2s):弱负(可能没看清楚)
- **点击后立即返回**:中强负(用户主动"逃走")
- **不感兴趣反馈**:强负(用户主动吐槽,但稀疏)

**业务差异**:同样"完播",抖音的"完播率 > 50%"算正样本,但快手的"完播率 > 30%"就够——不同业务有不同的"长停留"标准。**第 3.3 节专门讲"长停留"的场景化判定**。

**文字**: 隐式反馈的"业务逻辑"和搜索/广告里的转化漏斗是一回事。用户的每个动作都暗含一个偏好强度,只是信号强度差异巨大。短视频里"完播"和"点赞"是不同强度,完播说明内容有意思,点赞说明用户愿意表态;电商里"加购"和"购买"是不同强度,加购可能是比价,购买才是真金白银。下游排序模型要按这种强度做加权,不能把所有正样本都当 label=1 等权看待。隐式反馈的难点不在"信号种类多",而在"信号之间的相对强度需要被精确定义",这块往往要靠业务经验和 A/B 实验反复校准。

**正样本候选**(用户"喜欢"的信号):
- 点击(最弱)
- 完播/长停留(短视频)
- 点赞/收藏
- 评论
- 转发/分享
- 购买/订阅(最强)

**负样本候选**(用户"不喜欢"的信号):
- 曝光未点击(最弱,可能没看到)
- 短停留后跳出(< 2s)
- 点击后立即返回
- 不感兴趣反馈(强负样本,但稀疏)

### 3.2 隐式反馈的"置信度"

**置信度(Confidence)的引入是为了解决"二值标签丢失信息"的问题**。

**核心问题**:
原始 BCE 把所有正样本 label=1,负样本 label=0,但用户点了 A 停留 3 秒和点了 A 停留 30 秒的真实偏好差距很大;曝光未点击可能是"没看到",也可能是"看了不喜欢"。**直接用 0/1 当标签,把"强正"和"弱正"混为一谈,模型学不到细粒度偏好**。

**工业上的解法**:
用 signal_strength $\in$ [0, 3] 这种连续权重,在 BCE 里乘上去:
- "加购" 权重 1.5、"购买" 权重 3.0 是电商常见设置
- "完播" 1.2、"点赞" 1.5、"分享" 2.0 是短视频经验值

**这套权重的真值并不存在**,只能通过线上 A/B 反复调参确定。改一个权重往往要观察一周数据才能看出效果,**工业上要做"权重搜索"而不是拍脑袋**——一维 grid search 把权重在 [0.5, 3.0] 区间内枚举,看哪个 A/B 实验最好。

**置信度权重的"工程实践"**:
- **置信度小于 1.0 的样本可以"弱化"**(如短停留 click 用 0.5,而不是 1.0)
- **置信度为 0 的样本直接丢弃**(短跳出 click 不计入训练)
- **置信度大于 2.0 的样本"强化"**(如购买 × 3.0 等价于"这个正样本 3 倍重要")

**注意置信度不能简单等价于 sample_weight**——BCE loss 里乘以 sample_weight,等价于"过采样重要样本",**改变数据分布**。**正确做法是改 label 软化**(如点击 + 短停留 → label=0.7,而不是 label=1 × weight=0.7),保持数据分布,只是"目标"模糊化。

**文字**: 置信度(Confidence)的引入是为了解决"二值标签丢失信息"的问题。原始 BCE 把所有正样本 label=1,负样本 label=0,但用户点了 A 停留 3 秒和点了 A 停留 30 秒的真实偏好差距很大;曝光未点击可能是"没看到",也可能是"看了不喜欢"。工业界一般用 signal_strength $\in$ [0, 3] 这种连续权重,在 BCE 里乘上去。权重的取值有强业务依赖:电商里"加购"权重 1.5、"购买"权重 3.0 是常见设置;短视频里"完播"1.2、"点赞"1.5、"分享"2.0 也是经验值。这套权重的真值并不存在,只能通过线上 A/B 反复调参确定,改一个权重往往要观察一周数据才能看出效果。

**核心洞察**: 不同的隐式信号**强度不同**。

```python
# 信号强度赋值(工业经验)
signal_weights = {
    'impression_no_click': 0.0,    # 不计入
    'click_bounce': 0.0,           # 点击后跳出,不计入
    'click_short_dwell': 0.3,      # 点击短停留:弱正样本
    'click_long_dwell': 1.0,        # 点击长停留:标准正样本
    'click_full_play': 1.2,         # 完播(短视频):强正样本
    'like': 1.5,                   # 点赞:强信号
    'favorite': 1.8,                # 收藏:长期兴趣
    'comment': 1.5,                 # 评论
    'share': 2.0,                   # 分享:社交背书
    'purchase': 3.0,                # 购买:最强信号
}
```

**应用**: 在损失函数中按权重采样 / 在 BCE 中按置信度加权。

```python
def weighted_bce_loss(logits, labels, signal_strength):
    """
    按隐式信号强度加权的 BCE
    logits: [B] 模型预测
    labels: [B] 0/1
    signal_strength: [B] 0.0 ~ 3.0 的置信度
    """
    bce = F.binary_cross_entropy_with_logits(logits, labels, reduction='none')
    return (bce * signal_strength).mean()

# 生成训练样本
def generate_training_samples(events):
    samples = []
    for event in events:
        if event['type'] == 'click':
            if event['dwell_time'] > 30:
                label, strength = 1, signal_weights['click_long_dwell']
            elif event['dwell_time'] > 5:
                label, strength = 1, signal_weights['click_short_dwell']
            else:
                continue  # 跳出,不计入
        elif event['type'] == 'purchase':
            label, strength = 1, signal_weights['purchase']
        # ...
        samples.append({**event, 'label': label, 'strength': strength})
    return samples
```

### 3.3 隐式正样本的"长停留"判定

**"长停留"是隐式正样本的核心判据**——但"长"在不同场景下含义不同。

**为什么"长停留"需要场景化?**

- **短视频**:用户一次决策 5-30 秒,完播 50% 以上算"真喜欢"
- **电商**:用户一次决策 5-10 分钟(浏览、对比、加购),停留 30 秒+ 或加购算"感兴趣"
- **新闻**:用户一次阅读 1-3 分钟,读完 80% 算"内容有价值"
- **音乐**:听完一整首歌算"喜欢",但快进跳过不算

**统一标准 vs 场景化标准**:

- 统一标准(全公司用同一个阈值,如 30 秒):简单,但短视频/新闻的"30 秒"含义完全不同,会引入大量噪声
- 场景化标准(每个业务自己定阈值):更精确,但工程复杂度高,**必须把阈值作为"超参"管理起来**,不能写死在代码里

**工业经验值**:
- 短视频:**播放完成度 > 50%** 算正样本
- 电商:**停留 > 30 秒 或 加购** 算正样本
- 新闻:**阅读完成度 > 80%** 算正样本
- 音乐:**播放完整首** 算正样本(快进不算)

**调阈值的工业流程**:
1. 先在"看板上"看不同阈值下正样本的**转化漏斗**(点击→加购→购买)差异
2. 选转化率拐点作为阈值(超过拐点,转化率快速提升)
3. 做 A/B 实验验证 AUC 涨/跌,看线上 CTR 是否提升
4. 反复调 2-3 次,锁定阈值

**不能照抄别人的阈值**——抖音的"完播 > 50%"是抖音的数据特点定的,快手可能"完播 > 30%"就够,**每个业务的阈值必须自己调**。

```python
def is_positive(event, scene):
    """
    场景化的"长停留"判定
    不同场景的"长停留"含义不同
    """
    if scene == 'short_video':
        # 短视频:播放完成 50%+ 算长停留
        return event['play_ratio'] > 0.5
    elif scene == 'ecommerce':
        # 电商:点击后停留 > 30s 或 加入购物车
        return event['dwell_time'] > 30 or event['add_to_cart']
    elif scene == 'news':
        # 新闻:阅读完成 80%+ 算长停留
        return event['read_ratio'] > 0.8
    elif scene == 'music':
        # 音乐:播放完整首
        return event['played_full_song']
```

### 3.4 负样本的"曝光未点击"误区

**"曝光未点击"作为负样本的最大陷阱是"采样偏差"**。

**核心问题**:
用户在一个 feed 流里只看到前 10 个 item(屏幕内),后 30 个 item 虽然在 API 响应里,但用户根本没看到。把这种"未点击"当作负样本训练,会让模型学到错误的负相关。

**广告场景的"位置偏差"**:
广告位在第 3 位和第 10 位的曝光位置天然影响点击率,位置靠后的"未点击"不一定是用户不喜欢。把所有未点击都当负样本,模型会把"位置"特征学得过于重要,产生位置偏差(Position Bias)。**用户真的不喜欢第 10 位的广告,还是因为"懒得往下翻"?**模型分不清。

**三个改进方向**:

1. **过滤"不可能被看到"的曝光**:屏幕外物品(item index > 5)、被快速划过的物品(用户停留 < 100ms 跳过的),直接丢弃,不计入训练
2. **引入"可见性估计"**:从用户行为推断"看了没看"——停留时间 > 500ms 算"看到",0-500ms 算"划过去"。可见 = 0/1,可见 = 1 的曝光未点击才算负样本
3. **负样本置信度**:把"未点击"的标签软化为 0.1 而不是硬 0,**让模型知道"我不确定这是不是负样本"**。YouTube 和抖音在 2019 年后都做过类似的去偏实验,线上 CTR 提升 0.5-1%

**工业实践**:
阿里妈妈 DIN 时代用"位置模型"估计 $P(\text{曝光} | \text{位置})$,给位置靠后的负样本一个**低权重**(位置靠后没看到 = 信息少,不应强训)。字节 2022 后开始用"双塔倾向 + 随机流量校准",把 5% 流量随机曝光,直接观察"真实曝光概率"。

**永远不要把所有曝光未点击当硬负样本**。

**文字**: "曝光未点击"作为负样本的最大陷阱是"采样偏差"(Selection Bias)。用户在一个 feed 流里只看到前 10 个 item(屏幕内),后 30 个 item 虽然在 API 响应里,但用户根本没看到。把这种"未点击"当作负样本训练,会让模型学到错误的负相关。广告场景也一样,广告位在第 3 位和第 10 位的曝光位置天然影响点击率,位置靠后的"未点击"不一定是用户不喜欢。把所有未点击都当负样本,模型会把"位置"特征学得过于重要,产生位置偏差(Position Bias)。改进方向是引入"可见性估计"或"位置去偏",更简单的是把"未点击"的标签软化为 0.1 而不是硬 0,YouTube 和抖音在 2019 年后都做过类似的去偏实验。

**朴素**: 曝光未点击 = 负样本。

**问题**:
- 用户**根本没看到**这个物品(在屏幕外 / 被跳过)
- 强行作为负样本 → 学到错误信号

**改进**:
- 过滤"不可能被看到"的曝光(如屏幕外物品)
- 引入**可见性估计**(从用户行为推断"看了没看")
- 用**负样本置信度**而非硬 0/1

## 4. 隐式推理:从行为反推兴趣

### 4.1 什么是"隐式推理"?

**文字**: 隐式推理(Implicit Reasoning)的本质是"从表面行为反推真实意图"。用户的行为序列(点击/滑动/停留)是一组嘈杂的、间接的信号,要从中恢复出"用户当前真正想要什么"。这其实是经典的"逆向推断"问题,和心理学的信号检测论(Signal Detection Theory)同源。在搜推广里,隐式推理的应用远不止"画像生成",还包括:从用户跳过所有视频广告推断"用户疲劳度"、从用户长停留但未购买推断"价格敏感度"、从用户点击同类目 5 件商品推断"主题兴趣漂移"。这些推理结果是召回/排序阶段的强信号,弥补了显式标签(性别/年龄/地域)的稀疏。隐式推理和隐式反馈不是一回事:隐式反馈是"信号采集",隐式推理是"信号解读"。

**显式反馈**: 用户主动说"我喜欢"/"我不喜欢"—— 极稀疏

**隐式推理**: 从用户**行为序列**反推用户的"真实偏好"。

**示例**:
- 用户连续点击 5 个运动鞋 → 推断"对运动鞋感兴趣"
- 用户点了某商品,停留 30s,但没买 → 推断"感兴趣但价格超预算"
- 用户跳过所有视频广告 → 推断"不喜欢广告"

**为什么隐式推理比显式画像更有价值?**

显式画像(年龄、城市、消费力)是慢变量——3 个月前是 25 岁,3 个月后还是 25 岁。隐式推理结果是快变量——**用户最近 1 小时点了什么、看了什么、跳过了什么**,直接反映"当前意图",对实时推荐价值巨大。这就是为什么 GenRec 时代,行为序列建模 + Attention 权重 = 隐式推理,成为推荐系统的核心模块。

### 4.2 隐式推理的方法

**文字**: 隐式推理的范式经历了三次迭代。规则时代(2015 前后)用专家系统,如果"近 20 次点击中运动鞋 $\geq$ 3 次"则推断用户对运动鞋感兴趣。简单可解释,但难泛化,新规则要人工写,维护成本高。神经网络时代(2018 到 2022)用 DIN/DIEN 的 Attention 权重,用户对当前候选的注意力分布本身就是"和历史行为的相关性"。隐式推理和排序目标在同一个模型里联合训练,不需要单独推理,延迟低、易上线。LLM 时代(2024 以后)用大语言模型直接"读"用户行为序列,输出自然语言兴趣画像。好处是可以处理多模态、长序列、做跨域关联;坏处是延迟高(几百 ms),一般用于离线画像生成或精排阶段的辅助特征,不能直接进实时召回。

**三种范式的对比**:

| 范式 | 典型方法 | 延迟 | 效果 | 维护成本 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **规则时代** | 专家系统 / 计数 | 极低(< 1ms) | 中 | 极高(人工规则) | 早期 / MVP 业务 |
| **神经网络** | DIN/DIEN/SASRec | 低(< 10ms) | 高 | 低(端到端训) | 实时召回/精排 |
| **LLM 推理** | GPT-4 / Qwen | 高(几百 ms) | 最高 | 低 | 离线画像 / 辅助特征 |

**工业最佳实践**:
- **实时召回/精排** → 用 DIN/DIEN,Attention 权重就是隐式推理
- **离线用户画像** → 用 LLM 每天/每小时跑一次,生成"兴趣标签 + 自然语言描述",存到特征库
- **不要用 LLM 跑实时召回**——几百 ms 延迟用户等不了,且成本高(每次推理几美分)

**LLM 隐式推理的工程挑战**:
1. **延迟**:Qwen-7B 单次推理 200-500ms,在线场景必须**离线批跑**,每天 1 亿用户的画像用几千张卡并行算
2. **成本**:1 亿用户 × 每天 1 次 = 1 亿次推理,单次 0.01 元 = 每天 1000 万元,长期看不便宜
3. **可控性**:LLM 输出不稳定(同样输入可能输出不同结果),需要 prompt 工程 + 输出 schema 约束

#### 4.2.1 基于规则的推理

```python
def rule_based_inference(user_history):
    """基于规则的隐式推理"""
    inferences = {}
    # 规则 1:最近 N 次点击的主题
    recent_topics = extract_topics(user_history['clicks'][-20:])
    for topic, count in recent_topics.items():
        if count >= 3:
            inferences[f'interest_{topic}'] = count / 20  # 归一化强度
    # 规则 2:完播率 > 50% 的内容
    full_play_items = [e for e in user_history['clicks'] if e.get('play_ratio', 0) > 0.5]
    if full_play_items:
        inferences['interest_quality_content'] = min(1.0, len(full_play_items) / 10)
    # 规则 3:价格区间推断
    if user_history['purchases']:
        prices = [p['price'] for p in user_history['purchases']]
        inferences['price_range_min'] = min(prices)
        inferences['price_range_max'] = max(prices)
    return inferences
```

#### 4.2.3 基于 LLM 的隐式推理(2024+ 趋势)

### 4.3 隐式推理在召回阶段的应用

```python
class ImplicitReasoningRecall(nn.Module):
    """用 LLM 推理的画像做召回"""
    def __init__(self, llm_dim, item_emb_dim, hidden=256):
        super().__init__()
        # LLM 推理的文本特征 → 稠密向量
        self.reasoning_proj = nn.Linear(llm_dim, hidden)
        # 用户行为序列编码
        self.behavior_encoder = nn.Sequential(
            nn.Linear(item_emb_dim, hidden), nn.ReLU(),
            nn.Linear(hidden, hidden)
        )
        # 融合
        self.fusion = nn.Linear(hidden * 2, hidden)
        # 物品侧塔
        self.item_proj = nn.Linear(item_emb_dim, hidden)

    def forward(self, llm_reasoning, user_history, candidate_items):
        # LLM 推理
        z_reason = self.reasoning_proj(llm_reasoning)  # [B, D]
        # 行为
        z_behavior = self.behavior_encoder(user_history).mean(dim=1)  # [B, D]
        # 融合
        z_user = self.fusion(torch.cat([z_reason, z_behavior], dim=-1))  # [B, D]
        # 物品
        z_items = self.item_proj(candidate_items)  # [B, N, D]
        # 相似度
        return (z_user.unsqueeze(1) * z_items).sum(dim=-1)
```

## 5. 工业实践:多场景数据流与隐式信号处理

### 5.1 多场景数据流架构

**工业上多场景数据流的核心工程问题不是"传输",而是"场景分类的稳定性"**。

**"场景漂移"的致命问题**:
同一个用户行为(比如"点击了某商品")可能在首页瀑布流、详情页相关推荐、购物车页猜你喜欢三个场景中发生。如果场景分类服务上线时改了分类规则,**导致历史数据和实时数据的场景标签分布不一致,模型就会发生"场景漂移"**。线上推理的场景 ID 和训练时统计的分布不匹配,AUC 立刻掉几个点。

**工业上的"三不"铁律**:
- 场景分类规则**不能频繁改**——一次改动,模型可能要重训
- Kafka 消息里**必须带"分类器版本"**字段,模型按版本消费
- 落盘到 Hive/Iceberg 后,**每个场景一个分区**,且分区键带"分类器版本",重训时按版本切数据

**这套机制在大厂叫"特征/样本版本化"**,2018 年后基本成为标配。

**多场景数据流的典型架构**:

```text
[客户端 SDK] → 用户行为(点击/曝光/停留)
    ↓ 上报
[Kafka / Pulsar] → 实时事件流
    ↓
[场景识别服务] → 根据 event 字段(场景 ID、页面 ID)分类
    ↓
[Hive / Iceberg] → 场景分类后落盘(分场景分区)
    ↓
[训练任务] → 每个场景独立训练 / 联合训练
```

**关键工程细节**:
- **场景识别服务必须"幂等"**——同一条 event 多次进入,产出的场景分类必须一致
- **Kafka 消费必须"按版本"**——旧版本的 event 走旧训练流程,新版本的 event 走新流程,不能混淆
- **特征/样本版本必须"三处对齐"**——离线训练(用 v1 数据) + 在线推理(用 v1 模型) + A/B 实验(用 v1 流量)

### 5.2 隐式信号处理流水线

**隐式信号处理流水线的工程难点是"窗口对齐"**。

**为什么"窗口对齐"是个难题?**

用户行为分布在不同时间窗口:
- 秒级:停留时长、滑动速度
- 分钟级:点击、加入购物车
- 小时级:访问、浏览
- 天级:购买、订阅

**一个训练样本要聚合多久的行为?**这要按场景调:
- **短视频**:一次滑动 200ms 级别,**窗口 30 秒**合适
- **电商**:一次决策要 5-10 分钟(浏览、比价、加购),**窗口 1 小时**更合理
- **新闻**:一次阅读 1-3 分钟,**窗口 30 分钟**合适

**窗口内的"行为密度"还要做归一化**——1 小时内点 50 次和点 5 次,推断的兴趣强度不能直接用"次数/时间",得考虑"信息熵"(信息熵高的行为更有信号)。

**多端数据(Android/iOS/小程序/网页)的对齐更复杂**:
- 移动端用"前台时间"算停留
- 网页端用"active tab 时间"算停留
- 同一用户在不同端的停留时长定义可能不同
- 归一化时要做**端级修正**,否则会高估 PC 端用户活跃度

**工程上的"信号处理流水线"模式**:
1. 客户端 SDK 上报 raw event(JSON: user_id, item_id, action, ts, duration, ...)
2. Kafka 接收 + 按时间窗口聚合(`windowed aggregation`)
3. Spark/Flink 流处理:按 user_id + window_key 聚合,产出"用户行为窗口画像"
4. 落盘到 Hive/Iceberg,每条画像一个用户 × 一个时间窗口
5. 训练时按用户 × 窗口 join,产出训练样本

**这套流水线的"坑"**:
- 客户端时钟漂移 → 用服务端时间校正
- 重复上报 → 用 request_id 去重
- 漏报 → 用曝光/点击比反推漏报率
- 端到端延迟 → 用 Kafka 分区 + Flink 实时聚合,延迟控制在秒级

### 5.3 多场景的离线评估

**多场景评估的核心原则:"分场景评估 + 综合加权"**。

**为什么不能直接看全局 AUC?**

全局 AUC 把所有场景的样本混在一起算,但不同场景的"用户行为分布"差异巨大:
- 首页样本量大(1000 万/天),但 CTR 高(5-10%),A AUC=0.78
- 详情页样本量小(100 万/天),CTR 低(1-2%),B AUC=0.72

如果只看全局 AUC = 0.77,**会以为模型整体好**;但分场景看,详情页的 AUC 0.72 单独看很差,业务方说"详情页效果掉了",模型团队才发现问题。

**正确做法**:
1. **分场景独立评估**——每个场景有自己的 val_loader,算独立 AUC
2. **综合加权**——按"业务重要性"或"流量占比"加权
3. **看 gAUC 分解**——gAUC 拆到各场景,看"每个场景的用户内排序能力"

**工业上的"加权方式"**:
- **按流量加权**:`overall_auc = Σ(scene_auc × scene_traffic)`
- **按业务重要性加权**:详情页 CTR 涨 0.5% 比首页涨 0.5% 业务价值大(详情页是"看后买"转化高),详情页权重高
- **绝对值 vs 相对值**:场景间 CTR 基线不同,绝对 AUC 不直接可比,**看相对提升**(场景_AUC - 场景基线_AUC)

**评估的"五维检查"**:
- 各场景 AUC
- 各场景 GAUC
- 跨场景一致性(模型在场景 A 上的排序方向是否和场景 B 一致)
- 业务指标(各场景 CTR、CVR、停留)
- A/B 实验(线上真实流量验证)

**永远不要只看"全局 AUC"做决策**——这是多场景建模的入门级错误。

```python
def multi_scene_evaluation(model, val_loaders):
```

## 7. 多场景建模四大范式完整对比:Shared / MMoE / PLE / STAR / Switch

**文字**: 第 2 节覆盖了 Shared + 塔、MMoE、STAR、M2M 四个架构,但工业界真正活跃的"基础范式"其实可以归到四类:硬共享(Shared)、软共享 + 软路由(MMoE/PLE)、低秩场景偏置(STAR)、稀疏专家路由(Switch)。这一节补全 PLE 和 Switch Transformer,把四个范式放进同一张比较表里,讲清楚各自的"参数效率 — 训练稳定性 — 推理延迟 — 冷启动友好度"四维权衡。这套分类不是教科书里的标准答案,而是从 2018 到 2024 年工业界 30+ 篇顶会论文中归纳出来的"实用分类法",做架构选型时直接对着这张表查就行。

### 7.1 PLE(Progressive Layered Extraction, Tencent 2020)

**文字**: PLE 是腾讯微信视频号在 KDD 2020 上提出的,动机是"MMoE 的专家被场景抢了"。MMoE 的所有专家对所有场景开放,理论上专家可以学到场景无关的通用模式,但实践中专家容易"站队"——大部分专家被某个场景的强梯度主导,其他场景拿不到有用信号,这就叫"专家退化"。PLE 的核心是"专家分组 + 渐进分离":每个场景有自己专属的专家(场景私有专家),同时保留一组共享专家。门控不再跨场景抢,而是分场景内做软路由。渐进(Progressive)指的是多层堆叠时,上一层的场景私有输出和共享输出重新融合,再送进下一层。这种"分离式"设计在视频号、快手、抖音都验证过,比 MMoE 离线 AUC 高 0.3~0.8 个百分点。

**核心思想**: 专家分两组:**场景共享专家 + 场景私有专家**。

```text
Layer 1:
  输入 x
    ├─→ [场景共享专家] E_shared  ─┐
    └─→ [场景 s 私有专家] E_s     ─┤
                                   ↓
                              [场景门控 g_s]
                                   ↓
                            融合 h_1
Layer 2: 同样的结构,输入 h_1
```

```python
class PLELayer(nn.Module):
    """PLE 一层:共享专家 + 私有专家 + 门控"""
    def __init__(self, in_dim, expert_dim, num_shared_experts=2,
                 num_scene_experts=2, scenes=('home', 'detail', 'search')):
        super().__init__()
        self.scenes = scenes
        # 共享专家(所有场景共用)
        self.shared_experts = nn.ModuleList([
            nn.Sequential(nn.Linear(in_dim, expert_dim), nn.ReLU())
            for _ in range(num_shared_experts)
        ])
        # 场景私有专家
        self.scene_experts = nn.ModuleDict({
            s: nn.ModuleList([
                nn.Sequential(nn.Linear(in_dim, expert_dim), nn.ReLU())
                for _ in range(num_scene_experts)
            ]) for s in scenes
        })
        # 每个场景一个门控
        self.scene_gates = nn.ModuleDict({
            s: nn.Linear(in_dim, num_shared_experts + num_scene_experts)
            for s in scenes
        })

    def forward(self, x, scene):
        # 共享专家输出
        shared_out = torch.stack([e(x) for e in self.shared_experts], dim=1)  # [B, K_s, D]
        # 场景私有专家输出
        scene_out = torch.stack([e(x) for e in self.scene_experts[scene]], dim=1)  # [B, K_p, D]
        all_out = torch.cat([shared_out, scene_out], dim=1)  # [B, K_s+K_p, D]
        # 门控
        gate = F.softmax(self.scene_gates[scene](x), dim=-1)  # [B, K_s+K_p]
        return (gate.unsqueeze(-1) * all_out).sum(dim=1)       # [B, D]


class PLE(nn.Module):
    """PLE 多层堆叠"""
    def __init__(self, in_dim, expert_dim, n_layers, scenes):
        super().__init__()
        self.layers = nn.ModuleList([
            PLELayer(in_dim if i == 0 else expert_dim, expert_dim, scenes=scenes)
            for i in range(n_layers)
        ])
        # 每个场景一个塔
        self.towers = nn.ModuleDict({
            s: nn.Sequential(nn.Linear(expert_dim, 1)) for s in scenes
        })

    def forward(self, x, scene):
        h = x
        for layer in self.layers:
            h = layer(h, scene)
        return self.towers[scene](h)
```

### 7.2 Switch Transformer(Top-1 Sparse Routing, Google 2021)

**文字**: MMoE 是"软路由"(每个专家都有权重,权重和为 1),Switch Transformer 把路由变成"硬选择"——每个样本只路由到 Top-1 专家(也可以是 Top-K,K=1 时退化为 Switch)。这种稀疏激活的好处是推理时只激活一部分专家,计算量随专家数线性可扩展,适合"几十甚至上百个专家"的大模型场景。在搜推广里,Switch 的应用没那么激进——推荐模型的推理延迟是硬约束(50ms 内必须返回),稀疏路由省下来的算力很快被专家数吃回去。但在 LLM 推荐(如 LLaMA-Rec、GPT4Rec)和"千亿参数推荐模型"场景,Switch 几乎是标配,Google 的 YouTube 在 2023 年披露过基于 Switch 的多场景大模型。

**核心思想**: Top-1 路由,每个样本只激活一个专家。

$$e^*(x) = \arg\max_{i} \text{softmax}(W_g \cdot x)_i$$

```python
class SwitchRouter(nn.Module):
    """Switch Transformer 风格的 Top-1 路由"""
    def __init__(self, in_dim, num_experts, expert_dim, capacity_factor=1.25):
        super().__init__()
        self.num_experts = num_experts
        self.expert_dim = expert_dim
        self.capacity_factor = capacity_factor
        # 门控
        self.gate = nn.Linear(in_dim, num_experts)
        # 专家
        self.experts = nn.ModuleList([
            nn.Sequential(nn.Linear(in_dim, expert_dim), nn.ReLU(),
                          nn.Linear(expert_dim, expert_dim))
            for _ in range(num_experts)
        ])

    def forward(self, x):
        # x: [B, D]
        gate_logits = self.gate(x)               # [B, n_experts]
        gate_softmax = F.softmax(gate_logits, dim=-1)
        # Top-1 选择
        top1_idx = gate_softmax.argmax(dim=-1)    # [B]
        top1_weight = gate_softmax.gather(1, top1_idx.unsqueeze(-1))  # [B, 1]
        # 容量限制(防止一个专家被分配过多样本)
        capacity = int(self.capacity_factor * x.size(0) / self.num_experts)
        # 路由到专家
        out = torch.zeros(x.size(0), self.expert_dim, device=x.device)
        for i, expert in enumerate(self.experts):
            mask = (top1_idx == i)
            n = mask.sum().item()
            if n > capacity:
                # 超容:只取前 capacity 个
                mask_idx = mask.nonzero(as_tuple=True)[0][:capacity]
                expert_in = x[mask_idx]
                expert_out = expert(expert_in)
                out[mask_idx] = expert_out * top1_weight[mask_idx]
            elif n > 0:
                mask_idx = mask.nonzero(as_tuple=True)[0]
                expert_out = expert(x[mask_idx])
                out[mask_idx] = expert_out * top1_weight[mask_idx]
        return out, top1_idx


class SwitchMultiScene(nn.Module):
    """Switch Transformer 风格的多场景推荐"""
    def __init__(self, in_dim, num_experts, expert_dim, scenes):
        super().__init__()
        self.scenes = scenes
        # 共享 Switch 路由器(所有场景共用专家池)
        self.router = SwitchRouter(in_dim, num_experts, expert_dim)
        # 每个场景一个塔
        self.towers = nn.ModuleDict({
            s: nn.Linear(expert_dim, 1) for s in scenes
        })

    def forward(self, x, scene):
        expert_out, _ = self.router(x)
        return self.towers[scene](expert_out)
```

## 8. MMoE 数学原理专题:门控机制与专家负载均衡

**文字**: MMoE 的代码很短(50 行内),但背后的数学并不简单。这一节把门控的梯度、专家的负载分布、容量限制的必要性全部拆开。理解这些数学,工程上才能解释"为什么 PLE 比 MMoE 稳""为什么 Switch 要加 Load Balancing Loss"这些看似工程经验的现象。数学公式看起来吓人,但每一项都对应着一个具体的工程决策,看完应该能直接复现 PLE 和 Switch 的改进点。

### 8.1 MMoE 形式化

**输入**: $x \in \mathbb{R}^d$ (用户/物品/上下文拼接后的稠密向量)

**专家集合**: $E = \{E_1, \dots, E_K\}$,每个 $E_i: \mathbb{R}^d \to \mathbb{R}^D$。

**门控**: $G_k(x) = \text{softmax}(W_g x)_k$,其中 $W_g \in \mathbb{R}^{K \times d}$。

**MMoE 输出**:

$$y_k = \sum_{i=1}^{K} G_i(x) \cdot E_i(x)$$

**多任务输出**: $t_j = H_j(y_{scene(j)})$,其中 $H_j$ 是任务 $j$ 的塔。

### 8.2 门控梯度的"双面性"

**文字**: MMoE 的门控梯度是双面的——同一个门控 $G$ 同时被多个任务的损失回传。这带来两个相反的效果:一方面,门控可以学到"哪个专家对当前任务组合最优",实现自动路由;另一方面,如果两个任务的梯度方向冲突(CTR 优化要扩 A 专家,CVR 优化要扩 B 专家),门控就会在两个目标间震荡,专家被反复"拉过来拉过去",训练不稳定。这是 PLE 出现"专家私有化"分组的直接动机:让每个场景的门控只看到自己的梯度,不和别的场景抢。

**任务 $j$ 对门控 $G_i$ 的梯度**:

$$\frac{\partial \mathcal{L}_j}{\partial G_i(x)} = \frac{\partial \mathcal{L}_j}{\partial y_k} \cdot E_i(x)$$

**多任务叠加**($N$ 个任务):

$$\sum_{j=1}^{N} \frac{\partial \mathcal{L}_j}{\partial G_i(x)} = \sum_{j=1}^{N} \frac{\partial \mathcal{L}_j}{\partial y_k} \cdot E_i(x)$$

**问题**: 任务间梯度冲突 → 门控震荡 → 专家退化。

### 8.3 专家退化的数学刻画

**文字**: "专家退化"是 MMoE 的著名病。直觉上,如果有 4 个专家和 2 个场景,理想情况是 2 个专家服务场景 1、另外 2 个服务场景 2;但实践中,梯度流向总是倾向于"大部分专家被最强任务抢走",导致一个或两个专家被反复使用,其他专家的输出接近 0。用熵来量化:如果门控权重分布 $G(x)$ 的熵 $H(G) = -\sum G_i \log G_i$ 接近 0,说明专家被压扁到一两个。监控这个熵值是 MMoE 调参的常用技巧,熵值掉到 $\log K$ 的 30% 以下就要考虑换 PLE 或加 Load Balancing Loss。

**门控熵**:

$$H(G(x)) = -\sum_{i=1}^{K} G_i(x) \log G_i(x)$$

**健康区间**: $H(G) \in [0.7 \log K, \log K]$。低于 $0.7 \log K$ → 专家退化。

```python
def gate_entropy_loss(gate_probs, eps=1e-8):
    """监控门控熵,熵太低说明专家退化"""
    H = -(gate_probs * torch.log(gate_probs + eps)).sum(dim=-1).mean()
    return H
```

### 8.4 负载均衡损失(Load Balancing Loss)

**文字**: Switch Transformer 的关键工程创新是 Load Balancing Loss。它显式地把"专家使用均匀度"塞进损失函数,避免稀疏路由塌缩到少数专家。公式看起来简单,就是让所有专家的"被路由概率平均"和"被路由样本数比例平均"都趋向 $1/K$。这项损失要乘以一个小系数 $\alpha$(经验值 0.01),不能太大,否则会盖过主任务损失。LLaMA-Rec、Qwen-Rec 等 LLM 推荐模型都复用了这套损失,工程上几乎成了"稀疏 MoE 的标配"。

**Switch Transformer 负载均衡损失**:

$$\mathcal{L}_{\text{balance}} = \alpha \cdot K \cdot \sum_{i=1}^{K} f_i \cdot P_i$$

其中:
- $f_i = \frac{1}{B} \sum_{b=1}^{B} \mathbb{1}[\text{argmax}(G(x_b)) = i]$:专家 $i$ 被路由的样本比例
- $P_i = \frac{1}{B} \sum_{b=1}^{B} G_i(x_b)$:专家 $i$ 的平均门控概率
- $\alpha$:平衡系数(经验值 0.01)

```python
def load_balancing_loss(gate_probs, top1_idx, num_experts, alpha=0.01):
    """
    Switch Transformer 风格的负载均衡损失
    gate_probs: [B, n_experts] softmax 后的门控
    top1_idx:   [B] argmax 后的路由
    """
    B = gate_probs.size(0)
    # P_i: 平均门控概率
    P = gate_probs.mean(dim=0)             # [n_experts]
    # f_i: 被路由的样本比例
    f = torch.zeros(num_experts, device=gate_probs.device)
    for i in range(num_experts):
        f[i] = (top1_idx == i).float().mean()
    # 损失:乘以 K,让最优值是 1 而不是 1/K
    loss = alpha * num_experts * (f * P).sum()
    return loss
```

### 8.5 PLE 的渐进分离:数学视角

**文字**: PLE 的"渐进"二字,数学上对应"逐步去掉场景间共享"。第一层专家分两组(共享 + 私有),门控分场景;第二层把第一层的输出再分两组(共享 + 私有),门控仍然分场景。这种"逐层递减场景间纠缠"的设计,让每一层的专家分组都更精细。可以形式化地证明:PLE 的专家表示空间是 MMoE 的子空间 + 私有化修正,这意味着 PLE 的拟合能力严格不弱于 MMoE,但训练稳定性更优。这是工程上"PLE 几乎总是优于 MMoE"的数学根据。

**PLE 第 $l$ 层输出**:

$$h^{(l)}_s = G^{(l)}_s(x^{(l-1)}) \cdot [E^{(l)}_{\text{shared}}(x^{(l-1)}); E^{(l)}_s(x^{(l-1)})]$$

其中 $G^{(l)}_s$ 是**场景 $s$ 专属门控**——只对当前场景的损失回传梯度。

**理论性质**: $\text{Rep}_{\text{PLE}} \supseteq \text{Rep}_{\text{MMoE}}$,且 $\text{Stab}_{\text{PLE}} \geq \text{Stab}_{\text{MMoE}}$。

## 9. 隐式推理 5 种实现路径:从规则到 World Model

**文字**: 第 4 节把隐式推理分为规则、神经网络、LLM 三种,粒度比较粗。2024 年以后,这个领域被 LLM 重新定义,5 种实现路径清晰可辨:CoT 提示、潜在推理 Token、隐藏状态探针、检索增强、世界模型。这节是第 4 节的深度补全,5 条路径有各自的延迟、推理能力、工程成本,选型时要按业务场景权衡。

### 9.1 路径 1:CoT-style Prompt(显式思维链)

**文字**: 这是 LLM 隐式推理的入门路径。给 LLM 一段 prompt 描述用户行为,然后在 prompt 里插入"让我们一步步思考"(Let's think step by step)的引导词,让 LLM 把推理过程显式输出。优点是开箱即用,不需要训练;缺点是延迟高(几百 ms 到几秒)、输出不稳定(每次跑可能给不同结论)、token 消耗大(推理链占几百 token)。工业上一般离线批量生成用户画像,缓存到特征库,在线只查缓存。

```python
def cot_implicit_reasoning(user_history_text, llm_client):
    """CoT 风格的隐式推理 prompt"""
    prompt = f"""你是推荐系统分析师。基于用户最近 30 天行为,推理其兴趣。

用户行为:
{user_history_text}

让我们一步步思考:
1. 用户最近浏览了哪些类目?频率如何?
2. 用户的消费水平大概是什么档次?
3. 用户在什么时段最活跃?
4. 用户的兴趣是否发生了迁移?
5. 综合以上,用户当前的"主题兴趣"是什么?

最后输出 JSON:
{{
  "interests": [{{"category": "...", "weight": 0.0-1.0}}],
  "price_level": "low/medium/high",
  "active_hours": [0, 1, ..., 23],
  "interest_shift": "stable/drifting/turning"
}}"""
    response = llm_client.generate(prompt, max_tokens=500)
    return parse_json(response)
```

### 9.2 路径 2:Latent Reasoning Token(潜在推理)

**文字**: 显式 CoT 的 token 消耗大,训练上又难以端到端优化。一个更优雅的方案是"潜在推理 token":在输入序列中插入几个可学习的"推理 token"(类似 BERT 的 [CLS]),这些 token 在 Transformer 内部跑 N 步自回归更新,但不映射到词汇表。训练目标直接是下游任务(CTR 预测、兴趣分类),梯度通过推理 token 反传到上游表征。代表工作有 Coconut(Chain of Continuous Thought, 2024)、Quiet-Thought。这条路径的好处是推理完全在连续空间里完成,没有自然语言生成的开销,延迟接近普通 Transformer。坏处是"推理过程"不可解释,只能看最后一层 hidden state。

```python
class LatentReasoningToken(nn.Module):
    """潜在推理 token:在 hidden state 空间里做 N 步迭代"""
    def __init__(self, n_layers, n_reasoning_steps=3, dim=256, num_tokens=4):
        super().__init__()
        self.n_reasoning_steps = n_reasoning_steps
        # 可学习的推理 token
        self.reasoning_tokens = nn.Parameter(torch.randn(num_tokens, dim) * 0.02)
        # 推理层(独立的小 Transformer,只对推理 token 做自回归)
        self.reasoner = nn.TransformerEncoder(
            nn.TransformerEncoderLayer(d_model=dim, nhead=4, dim_feedforward=dim*2,
                                        batch_first=True, dropout=0.1),
            num_layers=n_layers
        )
        # 下游预测头
        self.head = nn.Linear(dim, 1)

    def forward(self, behavior_seq_emb, scene_feat):
        """
        behavior_seq_emb: [B, L, D] 用户行为序列 embedding
        scene_feat:       [B, D]    场景特征
        """
        B = behavior_seq_emb.size(0)
        # 把推理 token 拼到序列前
        rt = self.reasoning_tokens.unsqueeze(0).expand(B, -1, -1)  # [B, n_rt, D]
        x = torch.cat([rt, behavior_seq_emb], dim=1)               # [B, n_rt+L, D]
        # 跑 N 步推理(每步都重新跑 Transformer,但只更新推理 token 位置)
        for _ in range(self.n_reasoning_steps):
            x = self.reasoner(x)
        # 取推理 token 的最终 hidden state
        reasoning_out = x[:, :self.reasoning_tokens.size(0)].mean(dim=1)  # [B, D]
        # 融合场景特征 + 推理
        z = reasoning_out + scene_feat
        return self.head(z)
```

### 9.3 路径 3:Hidden State Probing(隐藏状态探针)

**文字**: 探针(Probing)是一种"模型可解释性"技术,在 LLM 推理过程中,在某几层 hidden state 上接一个轻量分类器,探测"模型在这一层是否已经编码了某类信息"。用在隐式推理里就是:不重新做推理,直接读 LLM 在生成用户画像时各层 hidden state,拿最后一层或倒数第二层训练一个线性/MLP 探针,预测用户的精细兴趣标签。优点是延迟极低(只跑一个 MLP),缺点是依赖 LLM 已经把信息编码到 hidden state——如果 LLM 没有显式"思考"这一步,探针也读不出来。工业上常见的折中是"小 LLM(7B)+ 探针 + 精排模型",延迟和精度的平衡点比较好。

```python
class HiddenStateProber(nn.Module):
    """从 LLM hidden state 探针用户兴趣"""
    def __init__(self, llm_hidden_dim, num_interest_classes, probe_layer=-1):
        super().__init__()
        self.probe_layer = probe_layer  # 选 LLM 哪一层的 hidden state
        # 探针:轻量 MLP
        self.prober = nn.Sequential(
            nn.Linear(llm_hidden_dim, 256),
            nn.ReLU(),
            nn.Dropout(0.1),
            nn.Linear(256, num_interest_classes)
        )

    def forward(self, llm_hidden_states, attention_mask):
        """
        llm_hidden_states: tuple of [B, L, D] 来自 LLM 各层
        attention_mask:    [B, L]
        """
        h = llm_hidden_states[self.probe_layer]  # [B, L, D]
        # 取最后一个有效 token(非 padding)的 hidden state
        last_idx = attention_mask.sum(dim=1) - 1  # [B]
        last_h = h[torch.arange(h.size(0)), last_idx]  # [B, D]
        return self.prober(last_h)  # [B, num_classes]


# 训练时,LLM 冻结,只训练探针
def train_prober(llm, prober, user_history_dataset, lr=1e-3, epochs=3):
    optimizer = torch.optim.Adam(prober.parameters(), lr=lr)
    for epoch in range(epochs):
        for batch in user_history_dataset:
            # LLM 前向(冻结)
            with torch.no_grad():
                outputs = llm(input_ids=batch['input_ids'],
                              attention_mask=batch['attention_mask'],
                              output_hidden_states=True)
                hidden_states = outputs.hidden_states
            # 探针预测
            interest_logits = prober(hidden_states, batch['attention_mask'])
            # 损失:对真实兴趣标签的多分类
            loss = F.cross_entropy(interest_logits, batch['interest_label'])
            optimizer.zero_grad()
            loss.backward()
            optimizer.step()
```

### 9.4 路径 4:Retrieval-Augmented Reasoning(检索增强)

**文字**: 检索增强(RAG)是 2023 年后 LLM 系统的标配。在隐式推理里,先用向量召回找出"和当前用户行为最相似的 K 个历史用户",把这 K 个用户的画像(标签、兴趣、消费水平)作为上下文喂给 LLM,让 LLM 做"基于相似案例的推理"。这条路径的好处是利用了"群体智慧",对长尾用户特别友好(冷启动用户没有足够自身行为,但有相似用户的画像);坏处是引入了一个向量召回系统,工程复杂度+1。字节、腾讯的 LLM 推荐系统都披露过这类架构。

```python
class RetrievalAugmentedReasoning(nn.Module):
    """检索增强的隐式推理"""
    def __init__(self, user_emb_dim, interest_dim, retrieval_dim=128):
        super().__init__()
        # 用户行为编码器
        self.behavior_encoder = nn.Sequential(
            nn.Linear(user_emb_dim, retrieval_dim),
            nn.LayerNorm(retrieval_dim)
        )
        # 相似用户画像聚合
        self.profile_aggregator = nn.MultiheadAttention(
            embed_dim=retrieval_dim, num_heads=4, batch_first=True
        )
        # LLM 输入投影(把检索结果投影到 LLM 输入空间)
        self.llm_input_proj = nn.Linear(retrieval_dim, 4096)
        # 推理后预测
        self.head = nn.Linear(interest_dim, 1)

    def forward(self, user_behavior, similar_users_emb, similar_users_profiles):
        """
        user_behavior:         [B, L, D] 当前用户行为
        similar_users_emb:     [B, K, D] K 个相似用户的 embedding
        similar_users_profiles:[B, K, P] K 个相似用户的画像(标签)
        """
        # 编码当前用户
        z_self = self.behavior_encoder(user_behavior).mean(dim=1)  # [B, retrieval_dim]
        # 用 attention 聚合相似用户画像
        z_ref, _ = self.profile_aggregator(
            query=z_self.unsqueeze(1),
            key=similar_users_emb,
            value=similar_users_profiles
        )  # [B, 1, retrieval_dim]
        # 构造 LLM prompt 中的"参考上下文"
        llm_context = self.llm_input_proj(z_ref.squeeze(1))  # [B, 4096]
        return llm_context, self.head(z_ref.squeeze(1))
```

### 9.5 路径 5:World Model 模拟(世界模型)

**文字**: 世界模型(World Model)是 5 种路径里最"重"的一种,也是和第 20 章直接关联的一条。核心思想是建一个"用户行为模拟器":给定当前用户状态和候选物品,模拟"用户看到这个物品后会做什么"(点击、停留、加购)。隐式推理不再是"读历史推断兴趣",而是"问未来行为倒推兴趣"。好处是推理的精度极高(因为直接模拟了未来),适合做长决策链推理(如"用户是否会在 7 天后复购")。坏处是训练一个高质量世界模型本身就需要亿级行为数据,工程投入巨大;且推理时要做 rollout,延迟难以压到 50ms 以内。代表工作有 DeepMind 的 AgentRec、字节的 SIM User。

```python
class WorldModelReasoner(nn.Module):
    """世界模型驱动的隐式推理"""
    def __init__(self, state_dim, action_dim, hidden=256, n_rollout_steps=5):
        super().__init__()
        self.n_rollout_steps = n_rollout_steps
        # 状态编码器
        self.state_enc = nn.Sequential(
            nn.Linear(state_dim, hidden), nn.LayerNorm(hidden)
        )
        # 动态转移函数:s_t, a_t -> s_{t+1}
        self.transition = nn.Sequential(
            nn.Linear(hidden + action_dim, hidden),
            nn.ReLU(),
            nn.Linear(hidden, hidden)
        )
        # 奖励预测:基于 s_{t+1} 预测隐式偏好
        self.reward_head = nn.Sequential(
            nn.Linear(hidden, 1),
            nn.Sigmoid()
        )
        # 兴趣聚合
        self.interest_head = nn.Linear(hidden, state_dim)

    def rollout(self, initial_state, action_seq):
        """
        模拟:从初始状态出发,执行 action 序列,得到轨迹
        initial_state: [B, D]
        action_seq:    [B, T, action_dim] 候选物品序列
        """
        s = self.state_enc(initial_state)  # [B, hidden]
        rewards = []
        states = [s]
        for t in range(self.n_rollout_steps):
            a = action_seq[:, t, :]
            s = s + self.transition(torch.cat([s, a], dim=-1))  # 残差连接
            r = self.reward_head(s)
            rewards.append(r)
            states.append(s)
        # 堆叠轨迹
        trajectory = torch.stack(states, dim=1)  # [B, T+1, hidden]
        return trajectory, torch.stack(rewards, dim=1)  # rewards: [B, T, 1]

    def infer_interest(self, initial_state, action_seq):
        """通过模拟推导出用户兴趣"""
        traj, rewards = self.rollout(initial_state, action_seq)
        # 兴趣 = 轨迹末态编码
        final_state = traj[:, -1, :]
        interest = self.interest_head(final_state)
        # 隐式偏好强度 = 平均奖励
        implicit_strength = rewards.mean(dim=1)
        return interest, implicit_strength
```

### 9.6 五种路径对比表

| 路径 | 推理延迟 | 训练成本 | 可解释性 | 长尾友好 | 工业落地度 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **CoT Prompt** | 高(秒级) | 零成本(纯推理) | ⭐⭐⭐⭐⭐ 高 | ⭐⭐ 差(冷启动要重新 prompt) | ⭐⭐⭐ 中(离线批量) |
| **Latent Token** | 低(普通 Transformer) | 中(端到端训练) | ⭐ 差(黑盒) | ⭐⭐⭐⭐ 较好 | ⭐⭐ 早期,需验证 |
| **Hidden Probe** | 极低(单 MLP) | 低(只训练探针) | ⭐⭐⭐ 中 | ⭐⭐⭐ 中 | ⭐⭐⭐⭐ 较成熟 |
| **Retrieval-Aug** | 中(召回+LLM) | 中(需向量库) | ⭐⭐⭐⭐ 较高 | ⭐⭐⭐⭐⭐ 极好 | ⭐⭐⭐ 中(工程重) |
| **World Model** | 高(rollout) | 高(亿级数据) | ⭐⭐⭐⭐ 较高 | ⭐⭐⭐ 中 | ⭐⭐ 早期,大厂探索 |

**选型口诀**:
- **冷启动** → Retrieval-Aug
- **可解释** → CoT Prompt
- **实时性** → Hidden Probe
- **精度** → World Model
- **平衡** → Latent Token(2024 后趋势)

## 10. 多场景 vs 多任务 vs 迁移学习 vs 元学习 - 4-way 概念辨析

**文字**: 这四个概念在面试和论文里频繁出现,但边界经常被混淆。它们的"目标函数不同、共享方式不同、应用场景不同",但实际工业项目里经常"四种都用了"。这一节用一张 4-way 对比表 + 决策流程图,把这四类范式的核心差异说清楚。

### 10.1 概念边界

| 概念 | 核心问题 | 共享方式 | 典型代表 |
| :--- | :--- | :--- | :--- |
| **多场景推荐** | 同一模型服务多个**场景** | 场景门控、场景私有参数 | STAR、M2M |
| **多任务学习** | 同一模型预测多个**目标** | 共享底层 + 任务塔 | MMoE、PLE、ESMM |
| **迁移学习** | 把**已有任务**的知识迁移到新任务 | 参数初始化、特征冻结、Adapter | 预训练 + Finetune |
| **元学习** | 学"**如何快速学**"——面对新任务只需少量样本 | MAML 风格的元参数 | MAML、Prototypical Networks |

### 10.2 4-way 对比表

**文字**: 4-way 对比要回答 5 个问题:**输入空间是否一致、输出空间是否一致、是否需要预训练、目标函数、典型痛点**。多场景推荐是"同一输入空间、同一输出空间、不同分布",多任务学习是"同一输入、不同输出空间、共享表征",迁移学习是"不同输入/输出、靠预训练搭桥",元学习是"任务级学习,目标是少样本泛化"。

| 维度 | 多场景 | 多任务 | 迁移学习 | 元学习 |
| :--- | :--- | :--- | :--- | :--- |
| **输入空间** | 相同 | 相同 | 不同 | 任务间不同 |
| **输出空间** | 相同 | 不同(多目标) | 不同 | 任务间不同 |
| **共享单元** | 场景间参数 | 任务间表征 | 源 → 目标参数 | 元参数 + 任务特定参数 |
| **是否预训练** | 否(联合训练) | 否 | 是(源域先训) | 是(元训练) |
| **核心痛点** | 场景漂移 | 任务冲突 | 域差异 | 任务多样性 |
| **代表工作** | STAR / M2M | MMoE / PLE / ESMM | BERT4Rec | MAML / ProtoNet |
| **数据需求** | 中(场景数据) | 中(多任务标注) | 高(源域) | 高(多任务数据) |
| **工业应用度** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐(还在研究) |

### 10.3 选型决策

```text
            ┌─ 多个场景,同一目标 ─────────→ 多场景 (STAR/PLE)
            │
推荐系统 ───┼─ 多个目标,同一场景 ─────────→ 多任务 (MMoE/ESMM)
            │
            ├─ 域差异大,要利用源域数据 ─────→ 迁移学习 (BERT4Rec)
            │
            └─ 冷启动严重,新任务极少样本 ───→ 元学习 (MAML)
```

### 10.4 工业实践:四者混用

**文字**: 真实工业系统往往四种范式叠加:用迁移学习做预训练(BERT4Rec 训物品表征),在预训练基础上加多任务头(MMoE 接 CTR/CVR/完播率),再用多场景范式部署到不同位置(首页/详情/搜索),最后对新场景用元学习做 Few-Shot 适配。这种"四合一"架构在 2023 年后的字节、腾讯、快手都成了默认配置。所以面试时被问"你的推荐系统用了什么",标准答案是"四者都有"——但要能说清楚每一种在哪个模块起了什么作用。

## 11. 综合实战:完整 STAR + 场景特征路由(可运行)

**文字**: 前面 STAR 章节的代码是简化版,只有一个共享 Linear + 场景 delta。这一节给出工业级实现:**场景特征路由 + 多层 STAR + 多任务头 + 多场景评估**。代码完整可运行,约 200 行 PyTorch,跑一遍就能复现 STAR 的核心思想。读者可以基于这份代码做工程化改造(加特征工程、换成 DIN 的 Attention、加 AUC 评估),作为多场景推荐的 baseline。

### 11.1 场景特征工程

```python
import torch
import torch.nn as nn
import torch.nn.functional as F
import numpy as np

# 场景配置
SCENE_CONFIGS = {
    'home':    {'item_feature_dim': 64,  'extra_features': ['user_active_hour', 'feed_position']},
    'detail':  {'item_feature_dim': 128, 'extra_features': ['source_item_id', 'dwell_history']},
    'search':  {'item_feature_dim': 96,  'extra_features': ['query_tokens', 'match_score']},
    'push':    {'item_feature_dim': 64,  'extra_features': ['notify_hour', 'user_recent_active']},
}
SCENES = list(SCENE_CONFIGS.keys())
NUM_SCENES = len(SCENES)


class SceneFeatureRouter(nn.Module):
    """场景特征路由:把不同场景的特征统一到共享空间"""
    def __init__(self, scene_configs, shared_dim=128):
        super().__init__()
        self.scene_configs = scene_configs
        self.shared_dim = shared_dim
        # 每个场景一个特征投影器
        self.scene_projectors = nn.ModuleDict({
            scene: nn.Sequential(
                nn.Linear(cfg['item_feature_dim'], shared_dim),
                nn.LayerNorm(shared_dim),
                nn.ReLU()
            ) for scene, cfg in scene_configs.items()
        })
        # 场景 one-hot embedding
        self.scene_embedding = nn.Embedding(len(scene_configs), shared_dim)

    def forward(self, scene_id, item_feat):
        """
        scene_id: [B] int
        item_feat: dict {scene_name: [B, item_feature_dim]},或统一 [B, max_dim]
        """
        # 投影到共享空间
        shared_feats = []
        for i, scene in enumerate(self.scene_configs.keys()):
            mask = (scene_id == i)
            if mask.any():
                feat_i = item_feat[scene][mask]  # [n_i, item_feature_dim]
                proj = self.scene_projectors[scene](feat_i)  # [n_i, shared_dim]
                shared_feats.append((mask, proj))
        # 重组到原 batch 顺序
        out = torch.zeros(scene_id.size(0), self.shared_dim, device=scene_id.device)
        for mask, proj in shared_feats:
            out[mask] = proj
        # 加场景 embedding(广播)
        scene_emb = self.scene_embedding(scene_id)  # [B, shared_dim]
        return out + scene_emb  # 场景感知的统一特征
```

### 11.2 多层 STAR

```python
class STARLayer(nn.Module):
    """一层 STAR:共享 W_shared + 场景 delta W_scene"""
    def __init__(self, in_dim, out_dim, num_scenes):
        super().__init__()
        self.in_dim = in_dim
        self.out_dim = out_dim
        self.num_scenes = num_scenes
        # 共享参数
        self.W_shared = nn.Linear(in_dim, out_dim, bias=False)
        # 场景特定参数(每个场景一份 delta)
        self.W_scene = nn.Parameter(
            torch.randn(num_scenes, out_dim, in_dim) * 0.01
        )
        # 场景门控(生成缩放向量 alpha)
        self.alpha_net = nn.Sequential(
            nn.Embedding(num_scenes, out_dim),
            nn.Sigmoid()
        )
        # 场景偏置
        self.b_scene = nn.Parameter(torch.zeros(num_scenes, out_dim))
        # 共享偏置
        self.b_shared = nn.Parameter(torch.zeros(out_dim))

    def forward(self, x, scene_id):
        # 共享路径
        h_shared = self.W_shared(x)                       # [B, out_dim]
        # 场景路径
        W_s = self.W_scene[scene_id]                       # [B, out_dim, in_dim]
        h_scene = (W_s @ x.unsqueeze(-1)).squeeze(-1)     # [B, out_dim]
        # 门控缩放
        alpha = self.alpha_net(scene_id)                   # [B, out_dim]
        h_scene = h_scene * alpha
        # 合并
        bias = self.b_shared + self.b_scene[scene_id]      # [B, out_dim]
        return h_shared + h_scene + bias


class MultiLayerSTAR(nn.Module):
    """多层 STAR(渐进式场景适配)"""
    def __init__(self, in_dim, hidden_dim, n_layers, num_scenes, dropout=0.1):
        super().__init__()
        self.layers = nn.ModuleList([
            STARLayer(in_dim if i == 0 else hidden_dim, hidden_dim, num_scenes)
            for i in range(n_layers)
        ])
        self.norms = nn.ModuleList([
            nn.LayerNorm(hidden_dim) for _ in range(n_layers)
        ])
        self.dropouts = nn.ModuleList([
            nn.Dropout(dropout) for _ in range(n_layers)
        ])

    def forward(self, x, scene_id):
        h = x
        for layer, norm, drop in zip(self.layers, self.norms, self.dropouts):
            h = drop(torch.relu(norm(layer(h, scene_id))))
        return h
```

### 11.3 多任务头 + 完整模型

```python
class MultiTaskSTAR(nn.Module):
    """多任务 STAR:多场景 + 多目标"""
    def __init__(self, scene_configs, shared_dim=128, n_star_layers=3, hidden_dim=128):
        super().__init__()
        self.scene_configs = scene_configs
        self.num_scenes = len(scene_configs)
        # 1. 场景特征路由
        self.feature_router = SceneFeatureRouter(scene_configs, shared_dim)
        # 2. 多层 STAR
        self.star = MultiLayerSTAR(
            in_dim=shared_dim,
            hidden_dim=hidden_dim,
            n_layers=n_star_layers,
            num_scenes=self.num_scenes
        )
        # 3. 多任务头(每个场景共享同一组任务头,场景 ID 决定头选择)
        self.task_heads = nn.ModuleDict({
            'ctr':    nn.Linear(hidden_dim, 1),
            'cvr':    nn.Linear(hidden_dim, 1),
            'like':   nn.Linear(hidden_dim, 1),
            'dwell':  nn.Linear(hidden_dim, 1),  # 回归:停留时长
        })
        # 4. 任务门控:不同场景关注不同任务
        self.task_gates = nn.ModuleDict({
            scene: nn.Linear(hidden_dim, len(self.task_heads))
            for scene in scene_configs.keys()
        })

    def forward(self, scene_id, item_feat, user_feat=None):
        """
        scene_id: [B] int
        item_feat: dict of tensors
        user_feat: [B, D_u] 可选
        """
        # 场景特征路由
        z = self.feature_router(scene_id, item_feat)  # [B, shared_dim]
        # 拼用户特征
        if user_feat is not None:
            z = torch.cat([z, user_feat], dim=-1)
            z = nn.Linear(z.size(-1), self.star.layers[0].in_dim).to(z.device)(z)
        # 多层 STAR
        h = self.star(z, scene_id)  # [B, hidden_dim]
        # 多任务输出
        outputs = {}
        for task_name, head in self.task_heads.items():
            outputs[task_name] = head(h)  # [B, 1]
        return outputs
```

### 11.4 训练循环(多场景 + 多任务)

```python
def train_multitask_star(model, dataloader, num_epochs=3, lr=1e-3,
                         task_weights={'ctr': 1.0, 'cvr': 0.5, 'like': 0.3, 'dwell': 0.1}):
    """
    多场景 + 多任务训练
    dataloader 产出:scene_id, item_feat, user_feat, task_labels
    """
    optimizer = torch.optim.Adam(model.parameters(), lr=lr)
    model.train()
    for epoch in range(num_epochs):
        total_loss = 0
        for batch_idx, batch in enumerate(dataloader):
            scene_id  = batch['scene_id']
            item_feat = batch['item_feat']
            user_feat = batch.get('user_feat', None)
            task_labels = {k: v for k, v in batch.items() if k.startswith('label_')}

            # 前向
            outputs = model(scene_id, item_feat, user_feat)

            # 多任务损失
            loss = 0
            for task_name, pred in outputs.items():
                label = task_labels[f'label_{task_name}']
                if task_name == 'dwell':
                    # 回归任务
                    task_loss = F.mse_loss(pred.squeeze(-1), label.float())
                else:
                    # 分类任务
                    task_loss = F.binary_cross_entropy_with_logits(
                        pred.squeeze(-1), label.float()
                    )
                loss = loss + task_weights[task_name] * task_loss

            # 反向
            optimizer.zero_grad()
            loss.backward()
            torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)  # 梯度裁剪
            optimizer.step()
            total_loss += loss.item()

        avg_loss = total_loss / len(dataloader)
        print(f"Epoch {epoch+1}/{num_epochs} | Loss: {avg_loss:.4f}")


# 构造 fake dataloader(示例)
```

### 11.5 多场景独立评估

```python
def evaluate_multiscene(model, val_loaders):
    """多场景独立评估 + 综合"""
    model.eval()
    scene_results = {}
    for scene, loader in val_loaders.items():
        aucs, ctrs = [], []
        with torch.no_grad():
            for batch in loader:
                scene_id = torch.full((batch['label_ctr'].size(0),),
                                      list(SCENE_CONFIGS.keys()).index(scene),
                                      dtype=torch.long)
                outputs = model(scene_id, batch['item_feat'], batch.get('user_feat'))
                ctr_pred = torch.sigmoid(outputs['ctr'].squeeze(-1))
                ctr_label = batch['label_ctr'].float()
                # 简化 AUC(实际用 sklearn.metrics.roc_auc_score)
                from sklearn.metrics import roc_auc_score
                auc = roc_auc_score(ctr_label.cpu(), ctr_pred.cpu())
                ctr = ctr_label.mean().item()
                aucs.append(auc)
                ctrs.append(ctr)
        scene_results[scene] = {
            'auc': np.mean(aucs),
            'ctr': np.mean(ctrs),
        }
    # 加权综合(用 CTR 占比加权)
    total_ctr = sum(r['ctr'] for r in scene_results.values())
    weighted_auc = sum(r['auc'] * r['ctr'] for r in scene_results.values()) / (total_ctr + 1e-8)
    scene_results['overall_weighted_auc'] = weighted_auc
    return scene_results
```

## 18.7 多场景建模四大范式速览

工业推荐系统常需同时服务多个业务场景（首页、猜你喜欢、相似推荐、短视频、电商 feed……），各场景数据分布、用户行为、CTR 量级差异显著。核心问题：**如何用一个模型承载多场景、同时缓解负迁移（negative transfer）**？

| 范式 | 核心结构 | 参数共享方式 | 场景适配粒度 | 典型负迁移处理 | 代表工业实践 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Shared-Bottom** | 单个共享底层 + 多个场景塔 | 100% 底层共享 | 仅塔头独立 | 弱（依赖场景差异本身） | YouTube 2019 早期 |
| **MMoE** (Ma et al., KDD 2018) | K 个共享 Expert + 场景门控 | K 个 Expert 全部共享 | 门控软分配 | 中（Expert 隐式分工） | Google YouTube |
| **PLE** (Tang et al., RecSys 2020) | 共享 Expert + 每场景私有 Expert 分离 | 部分共享 + 部分隔离 | 任务专属 Expert | 强（结构上隔离） | Tencent 微信视频号 |
| **STAR** (Sheng et al., KDD 2021) | 星形拓扑：共享中心 + 场景特定星臂 | 中心节点共享 + 星臂独立 | 星臂整段独立 | 强（参数硬隔离） | Alibaba 猜你喜欢 |

**对比直觉**：Shared-Bottom 是“一家人吃一锅饭”，MMoE 是“自助餐 + 服务员配菜”，PLE 是“共厨房 + 各点各菜”，STAR 是“公共主食 + 各人专属小炒”。负迁移越严重，越倾向 PLE/STAR。

## 18.8 STAR：星形拓扑自适应推荐器

STAR（Star Topology Adaptive Recommender）是阿里 2021 年提出的多场景 CTR 模型，结构上把网络分为两部分：

- **共享参数 $W_c$（中心节点）**：所有场景共用，捕获通用模式
- **场景专属参数 $W_i$（星臂）**：每个场景独立，捕获场景特异模式

对场景 $i$ 的样本，模型输出为：

$$h_i = f_{shared}(x;\ W_c) + f_{specific,i}(x;\ W_i)$$

$$\hat{y}_i = \sigma\!\left(W_{out,i}^{\top} h_i + b_{out,i}\right)$$

关键设计：场景 $i$ 的 $W_i$ **只**用场景 $i$ 的样本梯度更新，天然隔离负迁移；同时 $W_c$ 被所有场景共同优化，吸收跨场景信息。训练时还会对共享中心加一个辅助 loss，避免 $W_c$ 被某一强势场景“独占”。

### 简化版 PyTorch 实现

```python
import torch
import torch.nn as nn

class StarTopologyCTR(nn.Module):
    """简化版 STAR：适用于 K 个场景的二分类 CTR 预估"""
    def __init__(self, num_features, embed_dim, num_scenarios, tower_hidden=64):
        super().__init__()
        # 场景无关特征嵌入
        self.embedding = nn.Embedding(num_features, embed_dim)
        # 共享中心（中心节点）
        self.shared_center = nn.Sequential(
            nn.Linear(embed_dim, tower_hidden),
            nn.ReLU(),
            nn.Linear(tower_hidden, tower_hidden),
        )
        # 每个场景一个星臂
        self.star_arms = nn.ModuleList([
            nn.Sequential(
                nn.Linear(embed_dim, tower_hidden),
                nn.ReLU(),
                nn.Linear(tower_hidden, tower_hidden),
            )
            for _ in range(num_scenarios)
        ])
        # 每个场景独立输出塔
        self.towers = nn.ModuleList([
            nn.Linear(tower_hidden, 1) for _ in range(num_scenarios)
        ])

    def forward(self, feature_ids, scenario_ids):
        """
        feature_ids: (B,) 离散特征 id
        scenario_ids: (B,) 场景 id, 取值 [0, K)
        """
        x = self.embedding(feature_ids)                # (B, D)
        h_shared = self.shared_center(x)                # (B, H)
        logits_list = []
        for i in range(self.star_arms.__len__()):
            h_star = self.star_arms[i](x)               # (B, H)
            h_i = h_shared + h_star                     # 中心 + 星臂
            logits_list.append(self.towers[i](h_i))     # (B, 1)
        stacked = torch.stack(logits_list, dim=1)       # (B, K, 1)
        idx = scenario_ids.view(-1, 1, 1)
        logits = stacked.gather(1, idx.expand(-1, 1, 1)).squeeze(1)  # (B, 1)
        return logits.squeeze(-1)

# ---- 训练伪代码 ----
model = StarTopologyCTR(num_features=1_000_000, embed_dim=32,
                        num_scenarios=4, tower_hidden=64)
opt = torch.optim.Adam(model.parameters(), lr=1e-3)
bce = nn.BCEWithLogitsLoss()

for features, scenarios, labels in dataloader:
    logits = model(features, scenarios)
    loss = bce(logits, labels.float())
    # 可选：辅助 loss 让 shared_center 不被强势场景独占
    aux_loss = sum(
        bce(model.towers[i](model.shared_center(model.embedding(features)))[:, None].mean(0, keepdim=True).expand_as(logits).squeeze(0), labels.float())
        for i in range(model.star_arms.__len__())
    ) * 0.1
    (loss + aux_loss).backward()
    opt.step(); opt.zero_grad()
```

### 关键实现点

1. **参数隔离靠 Python 作用域**：`star_arms[i]` 的梯度只会来自场景 $i$ 的样本，PyTorch 的 autograd 自动完成隔离。
2. **推理时按 `scenario_id` 路由**：线上服务时先查场景，再走对应星臂 + 共享中心，O(1) 开销。
3. **嵌入表通常仍全场景共享**：特征语义在多场景间稳定，仅在 MLP 层做 STAR 拓扑。
4. **扩展**：可在 `shared_center` 与 `star_arms` 之间插入 **注意力融合**（如 APE / APG）以支持场景间细粒度信息流。

### 一句话选型

- 场景数 ≤ 3 且分布相近 → **Shared-Bottom** 即可
- 场景中等差异、有充足数据 → **MMoE**
- 场景差异大、负迁移明显 → **PLE / STAR**
- 场景数 > 10、上线要求稳 → **STAR + 分组星臂**

## 18.9 隐式推理落地建议（衔接下章）

隐式推理的 5 种路径（CoT prompt / latent reasoning token / hidden-state probing / retrieval / world model）在工程上取舍如下：

- **CoT prompt**：仅适用于 LLM 召回/粗排，CTR 精排延迟不可承受
- **Latent reasoning token**：可在小模型蒸馏中用，需 1k+ 条推理轨迹监督
- **Hidden state probing**：零额外成本但只反映“潜在能力”，不可控
- **Retrieval**：冷启动场景最有效，依赖高质量知识库
- **World model**：长期收益最高，短期投入大

推荐起步组合：**STAR 多场景 + Retrieval 增强 + World model 模拟器**——三者配合覆盖短/中/长期信号。

## 18.10 多场景建模 4 大范式深度对比

多场景推荐是搜推广的核心问题:首页信息流、详情页相关推荐、相似商品页、推送通知……**同一个用户在不同场景下偏好不同**。如何用一个统一模型服务多场景?

### 18.10.1 4 大范式架构对比

| 范式 | 共享结构 | 场景信息 | 优点 | 缺点 | 代表论文 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Shared-Bottom** | 1 个共享 MLP | 无(隐式) | 极简 | 场景间相互拖累 | DNN (2016) |
| **MMoE** | K 个 Expert + Gate | 隐式(经 Gate) | 灵活 | 跷跷板现象 | KDD 2018 |
| **PLE** | 共享+场景特定 Expert | 显式分层 | 解决跷跷板 | 参数量大 | RecSys 2020 |
| **STAR** | 星型拓扑 + 场景特定参数 | 显式(全连接权重) | 参数高效 | 场景数受限于权重 | KDD 2021 |

### 18.10.2 数学原理:MMoE 的 Gate 机制

MMoE 用 K 个 Expert 和 N 个 Gate(每任务一个):

$$y_n = h_n\left( \sum_{k=1}^{K} g_n^{(k)}(x) \cdot e_k(x) \right)$$

其中:
- $e_k(x)$:第 k 个 Expert 的输出
- $g_n^{(k)}(x)$:任务 n 对 Expert k 的 softmax 权重
- $h_n$:任务 n 的 Tower MLP

**跷跷板现象的根因**:多个任务的梯度在共享 Expert 上叠加,任务 A 想让 Expert 关注 A 的模式,任务 B 想要 B 的模式,Expert 就会**学到一个"平均值"**,两个任务都达不到最优。

### 18.10.3 PLE 如何解决跷跷板

PLE(Progressive Layered Extraction)把 Expert 分为两类:

$$y_n = h_n\left( \sum_{k=1}^{K_s} g_n^{(s,k)}(x) \cdot e_k^{(s)}(x) + \sum_{k=1}^{K_n} e_k^{(n,n)}(x) \right)$$

- **共享 Expert** $e_k^{(s)}$:服务所有任务
- **场景特定 Expert** $e_k^{(n,n)}$:只服务任务 n

这样每个任务有"专属通道",不会相互拖累。

```python
import torch
import torch.nn as nn

class PLE(nn.Module):
    """
    PLE (Progressive Layered Extraction) 简化实现
    多场景多任务推荐
    """
    def __init__(self, num_tasks=2, num_scenarios=3, num_shared_experts=4,
                 num_specific_experts=2, expert_dim=32, tower_dim=64):
        super().__init__()
        self.num_tasks = num_tasks
        self.num_scenarios = num_scenarios

        # 共享 Expert (所有任务 + 所有场景共享)
        self.shared_experts = nn.ModuleList([
            nn.Sequential(nn.Linear(128, expert_dim), nn.ReLU())
            for _ in range(num_shared_experts)
        ])

        # 每个任务有独立的 Expert (解决跷跷板)
        self.task_experts = nn.ModuleList([
            nn.ModuleList([
                nn.Sequential(nn.Linear(128, expert_dim), nn.ReLU())
                for _ in range(num_specific_experts)
            ])
            for _ in range(num_tasks)
        ])

        # 每个任务一个 Gate
        self.task_gates = nn.ModuleList([
            nn.Sequential(
                nn.Linear(128, num_shared_experts + num_specific_experts),
                nn.Softmax(dim=-1)
            )
            for _ in range(num_tasks)
        ])

        # Tower
        self.towers = nn.ModuleList([
            nn.Sequential(
                nn.Linear(expert_dim, tower_dim),
                nn.ReLU(),
                nn.Linear(tower_dim, 1)
            )
            for _ in range(num_tasks)
        ])

    def forward(self, x, task_ids):
        """
        x: [B, 128] 输入特征
        task_ids: [B]     每个样本的任务/场景 ID
        """
        # 共享 Expert 输出
        shared_outs = torch.stack([e(x) for e in self.shared_experts], dim=1)  # [B, K_s, D]

        outputs = []
        for task_id in range(self.num_tasks):
            # 任务特定 Expert
            task_outs = torch.stack(
                [e(x) for e in self.task_experts[task_id]], dim=1
            )  # [B, K_n, D]

            # 拼接
            all_outs = torch.cat([shared_outs, task_outs], dim=1)  # [B, K_s+K_n, D]

            # Gate 加权
            gate = self.task_gates[task_id](x)  # [B, K_s+K_n]
            mixed = (gate.unsqueeze(-1) * all_outs).sum(dim=1)  # [B, D]

            # Tower
            out = self.towers[task_id](mixed)  # [B, 1]
            outputs.append(out)

        return outputs  # list of [B, 1] for each task


# 测试
if __name__ == "__main__":
    ple = PLE(num_tasks=3, num_specific_experts=2)
    x = torch.randn(32, 128)
    outputs = ple(x, task_ids=None)
    for i, o in enumerate(outputs):
        print(f"Task {i} output: {o.shape}")
```

### 18.10.4 隐式推理的 5 种实现路径

"隐式推理"(Implicit Reasoning)是指模型在隐层完成推理步骤,**不显式生成中间 token**。这是 LLM 推荐的关键设计选择。

| 路径 | 实现方式 | 推理深度 | 训练成本 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **1. CoT-style Prompt** | 让 LLM 显式输出推理步骤 | 强(可解释) | 高(序列长) | 解释性强的场景 |
| **2. Latent Reasoning Token** | 引入特殊 token `[REASON]...[/REASON]` 让 LLM 在隐层推理 | 中 | 中 | 通用生成式推荐 |
| **3. Hidden State Probing** | 直接用最后一层 hidden state 做分类 | 弱 | 低 | 召回/精排打分 |
| **4. Retrieval-Augmented** | 先检索相关物品,再生成 | 强 | 中 | 长尾/冷启动 |
| **5. World Model** | 用世界模型预测用户未来行为 | 强 | 极高 | RL 训练环境 |

### 18.10.5 Latent Reasoning Token 的实战实现

```python
class LatentReasoner(nn.Module):
    """
    在 Transformer 中插入 Latent Reasoning Token 的简化实现
    参考论文: "Chain of Thought Prompting Elicits Reasoning in Large Language Models"
    """
    def __init__(self, vocab_size, d_model=256, n_reason_tokens=8):
        super().__init__()
        # N 个可学习的 reasoning token
        self.reason_tokens = nn.Parameter(torch.randn(n_reason_tokens, d_model) * 0.02)
        self.n_reason = n_reason_tokens

        # 标准的 Transformer Decoder
        decoder_layer = nn.TransformerDecoderLayer(d_model=d_model, nhead=8, dim_feedforward=1024)
        self.decoder = nn.TransformerDecoder(decoder_layer, num_layers=4)

        self.embed = nn.Embedding(vocab_size, d_model)
        self.lm_head = nn.Linear(d_model, vocab_size)

    def forward(self, input_ids):
        """
        input_ids: [B, L] 用户历史 + 候选物品的 S-ID 序列
        """
        B, L = input_ids.shape
        x = self.embed(input_ids)  # [B, L, D]

        # 构造新的序列:[reason_tokens, x]
        # reason_tokens 拼在前面,让模型先做隐式推理
        reason = self.reason_tokens.unsqueeze(0).expand(B, -1, -1)  # [B, N, D]
        x = torch.cat([reason, x], dim=1)  # [B, N+L, D]

        # Causal mask
        L_full = self.n_reason + L
        mask = torch.triu(torch.ones(L_full, L_full) * float('-inf'), diagonal=1)

        # 推理
        out = self.decoder(x, x, tgt_mask=mask)

        # 只取 reasoning token 后的输出做预测
        logits = self.lm_head(out[:, self.n_reason:])
        return logits
```

### 18.10.6 多场景 vs 多任务 vs 迁移学习

| 维度 | 多场景推荐 | 多任务学习 | 迁移学习 | 元学习 |
| :--- | :--- | :--- | :--- | :--- |
| **目标** | 同任务不同分布 | 不同任务同分布 | 跨域 | 快速适应新场景 |
| **样本** | 共享 | 共享 | 不共享 | Few-shot |
| **典型方法** | MMoE, PLE, STAR | MMoE, ESMM, PLE | 预训练+Finetune | MAML, Prototypical Net |
| **工业例子** | 抖音多场景 | CTR+CVR+Like | 跨域推荐 | 新用户冷启动 |
| **评测方式** | 单场景独立指标 | 所有任务指标 | 目标域指标 | Few-shot accuracy |

### 18.10.7 实战:用 MMoE 训练一个 3 场景 3 任务推荐

```python
import torch
import torch.nn as nn

class ScenarioMMoE(nn.Module):
    """
    3 场景 (首页/详情页/推送) × 3 任务 (CTR/CVR/停留时长) 的 MMoE
    """
    def __init__(self, num_scenarios=3, num_tasks=3, num_experts=8, expert_dim=64):
        super().__init__()
        self.num_scenarios = num_scenarios
        self.num_tasks = num_tasks

        # 共享 Expert
        self.experts = nn.ModuleList([
            nn.Sequential(nn.Linear(128, expert_dim), nn.ReLU())
            for _ in range(num_experts)
        ])

        # 每个场景有自己的 Gate
        self.scenario_gates = nn.ModuleList([
            nn.ModuleList([
                nn.Sequential(nn.Linear(128, num_experts), nn.Softmax(dim=-1))
                for _ in range(num_tasks)
            ])
            for _ in range(num_scenarios)
        ])

        # Tower
        self.towers = nn.ModuleList([
            nn.Sequential(nn.Linear(expert_dim, 64), nn.ReLU(), nn.Linear(64, 1))
            for _ in range(num_tasks)
        ])

    def forward(self, x, scenario_ids):
        """
        x:           [B, 128] 拼接后的特征
        scenario_ids:[B]        场景 ID (0/1/2)
        """
        # 所有 Expert 输出
        expert_outs = torch.stack([e(x) for e in self.experts], dim=1)  # [B, K, D]

        # 按场景分组处理
        outputs_per_task = [[] for _ in range(self.num_tasks)]

        for s in range(self.num_scenarios):
            mask = (scenario_ids == s)
            if mask.sum() == 0:
                continue
            x_s = x[mask]  # [n_s, 128]
            exp_s = expert_outs[mask]  # [n_s, K, D]

            for t in range(self.num_tasks):
                gate = self.scenario_gates[s][t](x_s)  # [n_s, K]
                mixed = (gate.unsqueeze(-1) * exp_s).sum(dim=1)  # [n_s, D]
                outputs_per_task[t].append(self.towers[t](mixed))

        # 拼回原始顺序
        final = []
        for t in range(self.num_tasks):
            if outputs_per_task[t]:
                out_t = torch.cat(outputs_per_task[t], dim=0)
                # 还原 batch 顺序(需要按 mask 还原)
                # 简化:这里直接拼接,实际应 scatter
                final.append(out_t)
            else:
                final.append(torch.zeros(x.size(0), 1))

        return final  # [task0_logits, task1_logits, task2_logits]
```

**7. 实践建议**

结合 "第 18 章:多场景推荐与隐式推理" 的特点,实践中有以下建议:

1. **数据优先**: 数据质量决定上限,模型只是逼近这个上限。把 50% 的时间投入到数据理解和清洗上,这条经验被无数实践证明。数据问题往往比模型问题更关键,但也更容易被忽视。

2. **基线先行**: 先用最简单的方法(如逻辑回归、规则)做基线,确认增益是来自方法还是数据。没有强基线的"创新"往往不靠谱。很多看似 fancy 的方法,在强基线面前提升有限。

3. **迭代式改进**: 不要追求一步到位,而是 baseline → 简单改进 → 高级方法 → 调优。每一步都用验证集确认有提升。每一步的提升幅度通常递减,要预期边际收益下降。

4. **失败案例分析**: 重点看模型做错的样本,往往能发现系统性问题。错误样本里藏着模型没学会的知识。把这些样本按错误类型分类,可以发现模型的薄弱点。

5. **A/B 测试**: 在生产环境做对照实验,用业务指标而非离线指标评估。离线指标只是手段,业务指标才是目的。指标可以被优化,但业务目标很难直接优化。

6. **监控与回滚**: 上线后持续监控关键指标,异常时快速回滚。任何线上系统都必须考虑"最坏情况",并预先设计好应对方案。

对 "第 18 章:多场景推荐与隐式推理" 常见的误解包括:

1. **"模型越复杂越好"**: 实际上,简单模型 + 好数据往往优于复杂模型 + 烂数据。这条法则在实践中反复被验证。

2. **"训练 loss 越低越好"**: 训练 loss 低不代表泛化好,可能过拟合。要看验证集表现,做误差分析。

3. **"指标好就等于业务好"**: 离线指标与在线业务有 gap,必须做 A/B 测试。指标可以被优化,但业务目标很难直接优化。

4. **"新方法一定比旧方法好"**: 新方法通常针对特定场景,在你的场景未必更好。要谨慎评估,先复现,再改进。

5. **"开源即用"**: 开源代码与你的数据/工程栈往往有 gap,需要适配。盲目复用经常踩坑,要理解代码再做改动。
