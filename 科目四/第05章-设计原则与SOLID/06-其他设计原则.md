# 其他重要设计原则

SOLID 五原则虽然是面向对象设计的核心,但软件工程的思想远不止这些。本章将介绍五条 **同样重要但风格不同** 的原则:

| 原则 | 英文 | 提出者 | 核心思想 |
|---|---|---|---|
| **KISS** | Keep It Simple, Stupid | Kelly Johnson (1960) | 简单胜于复杂 |
| **YAGNI** | You Aren't Gonna Need It | Ron Jeffries (XP, 1999) | 不需要的不做 |
| **DRY** | Don't Repeat Yourself | Andy Hunt & Dave Thomas (《程序员修炼之道》1999) | 不重复自己 |
| **组合优于继承** | Favor Composition over Inheritance | GoF (1994) | 组合/聚合优先 |
| **迪米特法则** | Law of Demeter (LoD) | Ian Holland (1987, Northeastern Univ.) | 只与直接朋友通信 |

这五条原则和 SOLID 互相补充——SOLID 关注 **类/接口的设计**,这五条关注 **代码演化和系统构建** 的更宏观维度。

---

## 一、KISS 原则(Keep It Simple, Stupid)

### 一句话定义

> **Keep It Simple, Stupid.** —— 大多数系统保持简单比变复杂能工作得更好。

KISS 由洛克希德公司工程师 Kelly Johnson 在 1960 年代提出。当时他设计 SR-71 黑鸟侦察机,要求维修工人在野外条件下用基础工具维修飞机——这迫使设计必须 **极度简单**。后来这个思想被引入软件开发:**"Simple things should be simple, complex things should be possible."**(简单的事应该简单,复杂的事应该可能。)

### 核心思想

**1. 简单是终极的复杂**

Unix 哲学的 "Do one thing and do it well"(做一件事并做好)是 KISS 的极致体现。Linux 内核的 `cat`、`grep`、`awk`、`sed` 各自只做一件事,但通过管道组合可以完成极其复杂的文本处理——这种 "简单组件 + 正交组合" 的设计哲学,是 KISS 在系统设计中的最高境界。

**2. 复杂性是债务,不是资产**

复杂的代码:
- 难以理解,新人 onboarding 慢
- 难以修改,改动牵一发动全身
- 难以测试,边界条件多到爆炸
- 难以调试,bug 隐藏深

每次你写 "聪明" 的代码,你就增加了未来所有人的认知负担。**代码被阅读的次数远多于被编写的次数**——为阅读者优化。

**3. "简单" 不等于 "简陋"**

KISS 不是叫你写简陋的代码。它的意思是:
- **不引入不必要的抽象**(为想象中的扩展而抽象)
- **不引入不必要的灵活性**(为想象中的配置项而引入配置文件)
- **不引入不必要的依赖**(为一个小功能引入 50MB 的库)

**"刚刚够用" 是 KISS 的尺度**。

### Python/Java 正反对比

#### ❌ 反例:过度抽象的简单需求

```java
// 需求:发送一封邮件给管理员
// 一个初级工程师写的"企业级"邮件发送框架

public interface EmailTransport {
    void send(EmailMessage message);
}

public interface EmailMessageBuilder {
    EmailMessageBuilder from(String address);
    EmailMessageBuilder to(String address);
    EmailMessageBuilder subject(String subject);
    EmailMessageBuilder body(String body);
    EmailMessage build();
}

public interface EmailService {
    void sendEmail(EmailMessage message);
    void sendEmailAsync(EmailMessage message);
    void sendBatchEmail(List<EmailMessage> messages);
}

@Component
public class SmtpEmailTransport implements EmailTransport {
    // 100 行 SMTP 配置代码
}

@Component
public class EmailServiceImpl implements EmailService {
    private final EmailTransport transport;
    private final EmailMessageBuilder builder;
    private final ExecutorService executor;
    private final RetryTemplate retryTemplate;
    // ... 一堆依赖
}

@Component
public class AdminNotifier {
    private final EmailService emailService;

    public void notifyAdmin(String message) {
        // 5 行代码发送邮件,但底层调用了 200 行的框架代码
        EmailMessage msg = emailService.builder()  // 等等,这是怎么访问的?
            .from("noreply@company.com")
            .to("admin@company.com")
            .subject("管理员通知")
            .body(message)
            .build();
        emailService.sendEmail(msg);
    }

```

**问题:** 需求只是 "发一封邮件",却引入了一整套邮件框架(接口、构建器、传输、服务、异步、重试……)。代码量膨胀 50 倍,维护成本激增。

#### ✅ 正例:简单直接的实现

```java
@Component
public class AdminNotifier {
    private final JavaMailSender mailSender; // Spring 自带的工具

    public void notifyAdmin(String message) {
        SimpleMailMessage msg = new SimpleMailMessage();
        msg.setFrom("noreply@company.com");
        msg.setTo("admin@company.com");
        msg.setSubject("管理员通知");
        msg.setText(message);
        mailSender.send(msg);
    }
}
```

**对比:** 20 行代码搞定,清晰直接。需要更复杂功能时,再考虑引入抽象。

### 实际应用

**Unix 哲学:** 工具只做一件事,但做到极致
- `cat` 只读文件、`grep` 只搜文本、`sort` 只排序
- 通过管道 `cat file.txt | grep "error" | sort | uniq` 组合出复杂功能

**Spring 框架的 `@Autowired`:** 自动注入依赖,不需要写工厂模式
**Python 的内置数据结构:** `dict`、`list`、`set` 解决 80% 的问题,不需要引入第三方库

### 判断标准

✅ **应用 KISS:**
- 写代码前问自己:能用 5 行代码解决吗?那就不要写 50 行
- 引入依赖前问自己:能用标准库解决吗?那就不要引入第三方
- 设计模式前问自己:能用最简单的写法吗?那就不要套模式

❌ **不要走极端:**
- "简单" 不是 "简陋"——该有的错误处理、参数校验不能省
- "少依赖" 不是 "零依赖"——成熟的三方库比自己写更可靠

## 二、YAGNI 原则(You Aren't Gonna Need It)

### 一句话定义

> **You Aren't Gonna Need It.** —— 不要写你现在不需要的代码。

YAGNI 是极限编程(XP)的核心实践之一,由 Ron Jeffries 在 1999 年明确命名。它的核心论点是:**"未来需要的" 是个糟糕的预测指标,不要为它写代码**。

### 核心思想

**1. 预测未来是反生产力**

当你为 "未来可能需要" 添加功能时,通常会发生三件事:
- 80% 的 "未来需求" 永远不会真正出现
- 真正出现的 20% 中,一半的形态和你想象的完全不一样
- 你为 "想象中的需求" 写的代码,大部分成为 **永远不会被调用却需要维护的死代码**

**2. 简洁设计的核心是 "今天做最好的"**

Kent Beck(TDD 创始人)的 "简单设计" 原则有四条:
1. **跑通所有测试**
2. **没有重复代码**
3. **表达意图清晰**
4. **尽量少的类和方法**

注意顺序——前两条是刚性的,后两条是弹性的。**"尽量少" 放在最后,因为它经常被误解为 "尽量简单到不表达意图"**。

**3. YAGNI 不是反对规划**

YAGNI 反对的是 **"现在就为未来编码"**,不是反对 "为未来做架构预留"。区别在于:
- **YAGNI 反对**:现在写一段不会被调用的死代码,期待未来某天它会被启用
- **支持架构预留**:识别 "未来一定会变" 的变化点(支付方式、序列化格式),在抽象层面预留扩展点

### Python/Java 正反对比

#### ❌ 反例:想象中的扩展点

```java
// 需求:计算订单总价
// 想象中的"灵活性"
public class OrderCalculator {
    // 想象未来可能支持多种折扣
    private DiscountStrategy discountStrategy; // 实际只有一种
    private TaxStrategy taxStrategy; // 实际税率是固定的
    private CurrencyConverter currencyConverter; // 实际只有人民币
    private PricingRuleEngine pricingRuleEngine; // 实际只有一条规则
    private List<PromotionPlugin> plugins; // 列表都为空

    public BigDecimal calculate(Order order) {
        BigDecimal total = BigDecimal.ZERO;
        // 100 行 if-else 判断各种策略组合
        // 但实际只有一种路径会被执行,其他全是死代码
        return total;
    }
}
```

#### ✅ 正例:做今天需要的事

```java
public class OrderCalculator {
    public BigDecimal calculate(Order order) {
        BigDecimal total = order.getItems().stream()
            .map(item -> item.getPrice().multiply(BigDecimal.valueOf(item.getQuantity())))
            .reduce(BigDecimal.ZERO, BigDecimal::add);
        return total.multiply(BigDecimal.valueOf(0.9)); // 当前唯一的 9 折优惠
    }
}

// 当未来真的有第二种折扣时,再做重构——届时抽象的依据是真实数据,不是想象
```

### 实际应用

**Martin Fowler 的 "Rule of Three":** 第一次写直接实现,第二次发现可以复用,第三次就该抽象了。**不要在第一次就抽象**——因为你还没看到 "真实的变化模式"。

**TDD 的 "Red-Green-Refactor":** 先写测试让代码失败,再写实现让测试通过,**最后才重构**。重构的依据是 "测试已经覆盖的真实代码",而不是 "想象中的需求"。

**Spring Boot 的 start:** 只引入你需要的 starter,不要一次性 `spring-boot-starter-*`(全家族)——后者会引入大量你用不到的依赖。

### 判断标准

✅ **应用 YAGNI:**
- 写代码前问:这段代码现在会被调用吗?
- 加配置项前问:真的有第二种配置需求吗?
- 加参数前问:真的有人会传这个参数吗?
- 加抽象层前问:真的有两种实现吗?

❌ **不要走极端:**
- 业务明确会变的部分(支付、优惠、序列化),抽象是合理的——这不算 YAGNI 违反
- 一行注释 "TODO: 未来支持 X" 不算违反,但 "专门写一个空方法" 就违反了

## 三、DRY 原则(Don't Repeat Yourself)

### 一句话定义

> **Every piece of knowledge or logic must have a single, unambiguous, authoritative representation within a system.**
> —— Andy Hunt & Dave Thomas,《程序员修炼之道》(1999)

DRY 直译是 "不要重复自己",但它不只是 "代码不重复"——它的深层含义是 **"知识/逻辑在系统中有且仅有一个权威表示"**。

### 核心思想

**DRY 的三个层次:**

1. **代码级 DRY:** 同样的代码不要写两遍
   - 提取公共方法、抽取公共类、使用工具类
   - 这是最表层的 DRY

2. **逻辑级 DRY:** 同样的业务逻辑不要在多处实现
   - 比如 "VIP 折扣 8 折" 这个规则,不能 A 系统写一遍,B 系统又写一遍
   - 需要把规则抽取到共享的业务模块

3. **知识级 DRY:** 同样的领域知识不要在多处表达
   - 比如 "用户年龄 >= 18 才能注册" 这个业务规则
   - 不能在 UI 校验一次、Service 校验一次、数据库 CHECK 约束又校验一次
   - **真正的知识只在领域模型里表达一次**

**DRY 不是 "所有相似代码都要合并"**:

```java
// ❌ 过度 DRY:把不相似的代码强行合并
public void processUser(User user) {
    validate(user);
    log.info("处理用户");
    notify(user);
}

public void processOrder(Order order) {
    validate(order);
    log.info("处理订单");
    notify(order);
}
// 看起来很对称,但 validate/log/notify 在两个上下文里含义不同,强行抽象反而模糊

// ✅ 适度 DRY:每个方法表达自己的业务意图
public void registerUser(User user) {
    validateUser(user);
    userRepository.save(user);
    log.info("用户注册: {}", user.getUsername());
    notificationService.sendWelcomeEmail(user);
}

public void placeOrder(Order order) {
    validateOrder(order);
    orderRepository.save(order);
    log.info("订单创建: {}", order.getId());
    notificationService.sendOrderConfirmation(order);
}
```

**WET(Write Everything Twice)反模式:** 同样的代码片段散落各处,改一处要改 N 处,极容易遗漏。

### 实际应用

**1. 工具类库(Lombok、Apache Commons、Guava):** 通用功能(字符串处理、集合操作、IO)抽取为标准库,业务代码不重复造轮子。

**2. 共享常量类:**
```java
public final class OrderConstants {
    public static final int MAX_ITEMS_PER_ORDER = 100;
    public static final BigDecimal VIP_DISCOUNT_RATE = new BigDecimal("0.8");
    // 业务常量集中管理,避免"魔数"散落各处
}
```

**3. 配置中心(Nacos、Apollo):** 业务配置集中管理,避免"同一配置在 5 个配置文件里各写一遍"。

**4. 数据库的 CHECK 约束:** 领域规则(如 "年龄 >= 18")在数据库层做一次,业务代码不必重复——但 **业务层校验仍然是必需的**(数据库 CHECK 是最后防线,不是唯一防线)。

### 判断标准

✅ **应用 DRY:**
- 同样的业务逻辑出现 2 次以上 → 抽取
- 同样的配置项出现在多个文件 → 集中管理
- 同样的魔数(`3.14159`、`86400`)散落各处 → 提取常量

❌ **不要走极端:**
- "看起来相似但语义不同" 的代码不要强行合并
- 过度抽象反而增加阅读成本(读者要在多个文件间跳转)
- "我看到重复就忍不住合并" 是另一种形式的过度工程

## 四、组合优于继承(Favor Composition over Inheritance)

### 一句话定义

> **Favor composition over inheritance.** —— GoF《设计模式》(1994)

这是面向对象设计中最 **反直觉但极其重要** 的一条原则。直觉上,"子类继承父类" 是 OO 的核心特征,但 GoF 在《设计模式》开篇就强调:**"优先使用对象组合,而不是类继承"**。

### 核心思想

**1. 继承的三大问题**

- **强耦合**:子类依赖父类的实现细节。父类一旦修改,所有子类可能受影响
- **破坏封装**:子类继承父类的 public/protected 成员,父类的内部细节暴露给子类
- **僵化结构**:继承是 **编译时确定** 的关系,运行时无法改变——而组合是 **运行时灵活组装**

**2. 组合的三大优势**

- **弱耦合**:类只持有其他对象的引用,被组合对象的实现变化不影响组合类
- **保持封装**:被组合对象通过接口暴露能力,内部细节对组合类不可见
- **运行时灵活**:可以在运行时动态替换被组合的对象(策略模式、装饰器模式)

**3. 什么时候用继承?**

继承也有其适用场景:
- **真正的 "is-a" 关系**(行为层面,LSP 满足):如 `Dog extends Animal`、`ArrayList extends AbstractList`
- **少量共享代码**:子类确实需要复用父类的实现(模板方法模式)
- **多态调用**:子类确实需要被当作父类使用

**判断标准:** 如果两个类之间是 "has-a" 关系(如 Car **has-a** Engine),用组合;如果是 "is-a" 关系(如 Dog **is-a** Animal),用继承。

### Python/Java 正反对比

#### ❌ 反例:继承泛滥

```java
// 想给 ArrayList 加个日志功能,新手会这样写
public class LoggingArrayList<E> extends ArrayList<E> {
    @Override
    public boolean add(E e) {
        log.info("添加元素: {}", e);
        return super.add(e);
    }
    @Override
    public E get(int index) {
        log.info("获取元素: {}", index);
        return super.get(index);
    }
    // ... 必须重写所有想加日志的方法
}

// 问题:
// 1. ArrayList 的方法太多了,要重写 N 个方法
// 2. 如果 ArrayList 加了新方法,LoggingArrayList 没有日志
// 3. 如果想同时加日志 + 缓存 + 校验?多重继承?Java 不支持!
```

#### ✅ 正例:组合 + 装饰器

```java
// 通过组合实现"列表 + 日志"功能
public class LoggingList<E> implements List<E> {
    private final List<E> delegate; // 组合:持有真正的 List

    public LoggingList(List<E> delegate) {
        this.delegate = delegate;
    }

    @Override
    public boolean add(E e) {
        log.info("添加元素: {}", e);
        return delegate.add(e);
    }

    // 想加新功能?加新的装饰器类
    public E get(int index) {
        log.info("获取元素: {}", index);
        return delegate.get(index);
    }

    // 其他方法转发给 delegate
    // ...(可以用 IDEA 的 delegate 模板自动生成)
}

// 灵活组合:日志 + 缓存 + 校验
List<String> list = new LoggingList<>(
    new CachingList<>(
        new ValidatingList<>(
            new ArrayList<>()
        )
    )
);
```

**对比收益:**
- 想换底层实现?`new ArrayList<>()` → `new LinkedList<>()` 不动其他代码
- 想叠加新功能?再加一层装饰器,不动原有代码(OCP 完美)
- 单元测试简单——mock `delegate` 即可

#### Python 对比

```python
# ❌ 反例
class LoggingDict(dict):
    def __setitem__(self, key, value):
        print(f"set {key}={value}")
        super().__setitem__(key, value)
    # 但 dict 有几十个方法,无法全部加日志

# ✅ 正例:组合 + 委托
class LoggingDict:
    def __init__(self, delegate: dict | None = None):
        self._data = delegate if delegate is not None else {}

    def __setitem__(self, key, value):
        print(f"set {key}={value}")
        self._data[key] = value

    def __getitem__(self, key):
        return self._data[key]
    # ... 其他方法按需委托
```

### 实际应用

**1. Java I/O 流家族(经典装饰器):**
```java
new BufferedReader(new InputStreamReader(new FileInputStream("file.txt")))
// 组合了"缓冲"+"字符转换"+"文件读取"三个能力,每个都是独立的装饰器
```

**2. Spring 的 `BeanWrapper`、`BeanDecorator`:** 通过组合包装 Bean,而不是继承 Bean 类。

**3. 委托模式(Delegation Pattern):** GoF 23 种设计模式中,很多(策略、装饰器、适配器)都是组合优于继承的应用。

**4. JavaScript 的 mix-in(ES6 之前):** 通过对象组合复用代码,而不是 `Object.create()` 继承。

### 判断标准

✅ **用组合:**
- "has-a" 关系(Car has Engine,Company has Employees)
- 想运行时切换行为(策略模式)
- 想叠加多种能力(装饰器模式)
- 想适配不同接口(适配器模式)

❌ **用继承:**
- "is-a" 关系且 LSP 严格满足(Dog is Animal)
- 框架要求继承(如 Spring 的 `AbstractController`、`JpaRepository`)
- 需要共享实现细节(模板方法模式)

**经验法则:** **继承表达 "我是你的一种",组合表达 "我有一个"**。能用 "has-a" 表达清楚的就用组合,只有必须用 "is-a" 表达时才用继承。

## 五、迪米特法则(Law of Demeter, LoD)

### 一句话定义

> **Each unit should have only limited knowledge about other units: only units "closely" related to the current unit.**
> —— Ian Holland, Northeastern University (1987)

迪米特法则,也叫 "最少知识原则"(Least Knowledge Principle)。通俗讲:**"只与直接朋友通信"**。

### 核心思想

**1. 朋友关系**

一个对象的 "朋友" 包括:
- **this 本身**
- **作为方法参数传入的对象**
- **this 直接创建/实例化的对象**
- **this 直接属性引用的对象**(成员变量)

其他对象都是 "陌生人"。

**2. 不要和陌生人说话**

```java
// ❌ 违反 LoD:链式调用
public double getManagerSalary(Employee emp) {
    return emp.getDepartment().getManager().getSalary(); // 三个点(.)
    // emp → department → manager → salary
    // 当前对象只和 emp 是朋友,不认识 department/manager
}
```

```java
// ✅ 遵循 LoD:只调用直接朋友的方法
public double getManagerSalary(Employee emp) {
    return emp.getManagerSalary(); // 一个点
    // 把"如何获取经理工资"的知识下放到 Employee 内部
}

public class Employee {
    public double getManagerSalary() {
        return department.getManager().getSalary();
    }
}
```

**3. 链式调用的危害**

链式调用(`.getA().getB().getC()`)违反 LoD,因为:
- **暴露结构**:调用方知道了 emp 内部有 department、department 内部有 manager
- **脆弱**:一旦 employee.getDepartment() 改名或返回类型变化,所有调用方都要改
- **难 mock**:测试时要 mock 整个调用链,而不是单个对象

**4. 常见误解:Builder 模式不算违反**

```java
new User.Builder()
    .name("Alice")
    .age(30)
    .email("alice@example.com")
    .build();
```

这种链式是 **Builder 模式** 的标准用法,不算 LoD 违反——因为 Builder 的每个方法都返回 `this`,调用方始终只和 "Builder" 这一个对象交互。

### Python/Java 正反对比

#### ❌ 反例:火车残骸(Train Wreck)

```java
// 反例:典型的"火车残骸"代码
public class OrderProcessor {
    public void processOrder(Order order) {
        // 5 层链式调用,每次都要假设中间对象的结构
        String address = order.getCustomer()
                             .getAddress()
                             .getCity()
                             .getDistrict()
                             .getStreet();
        // 任何一个 get 返回 null 都可能 NPE
        // 任何一个中间方法改名,这段代码都崩溃

        BigDecimal totalPrice = order.getItems().stream()
                                     .map(item -> item.getProduct().getPrice())
                                     .reduce(BigDecimal.ZERO, BigDecimal::add);
        // 同样脆弱
    }
}
```

#### ✅ 正例:封装内部结构

```java
public class Order {
    private Customer customer;
    private List<OrderItem> items;

    // 把"获取配送地址"的知识封装在 Order 内部
    public String getShippingAddress() {
        return customer.getFullAddress(); // Customer 内部封装
    }

    // 把"计算总价"的知识封装在 Order 内部
    public BigDecimal getTotalPrice() {
        return items.stream()
                    .map(OrderItem::getSubtotal) // OrderItem 自己计算小计
                    .reduce(BigDecimal.ZERO, BigDecimal::add);
    }

    public BigDecimal getProductTotal() {
        return items.stream()
                    .map(item -> item.getProduct().getPrice()) // 仍然有链式,但只 2 层
                    .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}

public class Customer {
    private Address address;

    // 封装内部细节
    public String getFullAddress() {
        return address.getFullAddress(); // Address 内部拼接
    }
}

public class OrderItem {
    private Product product;
    private int quantity;

    public BigDecimal getSubtotal() {
        return product.getPrice().multiply(BigDecimal.valueOf(quantity));
    }
}

// 调用方代码极度简洁
public class OrderProcessor {
    public void processOrder(Order order) {
        String address = order.getShippingAddress(); // 1 个点
        BigDecimal total = order.getTotalPrice();    // 1 个点
    }
}
```

### 实际应用

**1. DTO/VO 的设计:** 不要把内部 Entity 直接暴露给前端,封装一个 DTO,只暴露业务需要的数据。

```java
// ❌ 反例:Entity 直接返回,前端能访问到内部结构
@RestController
public class UserController {
    @GetMapping("/users/{id}")
    public User getUser(@PathVariable Long id) {
        return userRepository.findById(id).orElseThrow(); // 返回 Entity
        // 前端可以访问 user.role.permissions[0].resource.url 这种链式
    }
}

// ✅ 正例:返回专门的 DTO
@RestController
public class UserController {
    @GetMapping("/users/{id}")
    public UserDto getUser(@PathVariable Long id) {
        User user = userRepository.findById(id).orElseThrow();
        return UserDto.from(user); // 转换为 DTO
    }
}
```

**2. 领域驱动设计(DDD)的聚合根:** 外部只能通过聚合根访问内部实体,不能直接穿透。

```java
Order order = orderRepository.findById(orderId).orElseThrow();
order.getCustomer().changeAddress(newAddress); // ❌ 外部直接修改 customer
// ✅ 正确做法
order.changeShippingAddress(newAddress); // 通过聚合根操作
```

**3. Facade 模式:** 把子系统的一堆调用封装成一个简单接口,符合 LoD。

```java
public class UserFacade {
    private final UserService userService;
    private final AuthService authService;
    private final ProfileService profileService;

    // 用户注册流程封装成一个方法
    public void registerUser(RegisterDto dto) {
        User user = userService.create(dto);
        authService.setupPassword(user, dto.getPassword());
        profileService.initProfile(user);
        // 调用方不需要知道这三步细节
    }
}
```

### 判断标准

✅ **应用 LoD:**
- 调用方代码中出现 `a.getB().getC().getD()` 形式的链式调用 → 重构
- 类的方法签名中出现了 "内部结构" 类型(如 `getDepartment().getManager()` 返回 `Manager`)→ 封装
- 一旦中间环节变化,大量调用方崩溃 → 加强封装

❌ **不要走极端:**
- 所有 `getter` 都不允许(会导致贫血模型)
- 集合的链式 stream 操作是合理的(`list.stream().filter().map().collect()`)
- Builder 模式、流畅接口(Fluent Interface)允许链式

## 综合对比

| 原则 | 关注点 | 关键问题 | 反模式信号 |
|---|---|---|---|
| **KISS** | 简单性 | "能用 5 行解决吗?" | 引入了不必要的抽象/依赖 |
| **YAGNI** | 节制 | "现在真的需要吗?" | 死代码、占位符、空实现 |
| **DRY** | 复用性 | "这段逻辑出现几次了?" | 复制粘贴的代码块 |
| **组合优于继承** | 灵活性 | "是 is-a 还是 has-a?" | 多层继承、无法运行时切换 |
| **迪米特法则** | 解耦 | "只和直接朋友通信" | 长链式调用、暴露内部结构 |

## 与 SOLID 的关系

这五条原则和 SOLID **互相补充、互不替代**:

- **SOLID 关注类/接口的内部设计**——一个类应该长什么样
- **KISS/YAGNI/DRY/组合/LoD 关注代码演化和系统构建**——一段代码如何随时间演化

比如:
- **SOLID 告诉你怎么设计类**(SRP、OCP、LSP、ISP、DIP)
- **KISS/YAGNI 告诉你不要过度设计**(KISS 不要过度抽象,YAGNI 不要预留扩展)
- **DRY 告诉你知识要在系统中有单一权威表示**(与 SRP 相关)
- **组合优于继承 告诉你怎么表达"复用"**(与 LSP/OCP 相关——继承容易违反 LSP,组合更安全)
- **迪米特法则 告诉你耦合的边界**(与 ISP/DIP 相关——只依赖需要的接口)

## 实战思考

### Q1:这五条原则有没有优先级?

**答:** 没有绝对的优先级,但有 **常见的使用顺序**:
1. 先 YAGNI 决策要不要做
2. 然后 KISS 决定怎么做得简单
3. 再 DRY 抽取公共逻辑
4. 用组合优于继承表达结构关系
5. 用 LoD 控制依赖方向

但这五条经常 **同时起作用**——比如 DRY 抽取时,你会发现用组合比继承更合适(组合优于继承),同时还要保证抽取的接口小而精(LoD 思想)。

### Q2:DRY 和 YAGNI 矛盾吗?

**答:** 表面上看有冲突——DRY 要求 "不要重复",YAGNI 要求 "不要做不需要的"。但二者关注的不同:
- **DRY 关注 "已经存在的重复"**:两段相同的代码已经出现,要合并
- **YAGNI 关注 "想象中的重复"**:为预防未来重复而提前抽象

**"Rule of Three"** 是平衡点:第一次直接写,第二次接受重复,第三次才抽象。**这是 DRY + YAGNI 的最佳实践**。

### Q3:什么时候"继承"还是更好的选择?

**答:** 框架要求继承时(如 Spring 的 `AbstractController`、`JpaRepository`、JUnit 的 `@ExtendWith`),你必须用继承,因为框架 API 决定了继承结构。但你可以:
- 用 **模板方法模式** 减少继承带来的耦合
- 用 **final 类** 防止不当继承(如 `String`、`Integer` 都是 final)
- 在设计自己业务的继承关系时,优先考虑组合

**现代 Java 实践:** 大部分业务代码用 interface + composition,只在框架要求的场景用继承。

## 小结

SOLID 之外的这些原则,共同构成了 **"克制"** 的设计哲学:
- **KISS**:简单胜于复杂
- **YAGNI**:不做不需要的
- **DRY**:不重复自己
- **组合优于继承**:灵活胜过僵化
- **迪米特法则**:解耦胜过耦合

这五条原则和 SOLID 一起,构成了软件设计的完整思想体系。**掌握它们,不是为了在每次编码时机械套用,而是为了在设计决策时有一个理性的思考框架**。

最终目标是:**"让代码读起来比写起来更轻松"**——这是所有设计原则的归宿。
