# 01-创建型模式对比

## 一、概述

**创建型模式** (Creational Patterns) 关注对象的**创建机制**,试图将对象的创建与使用解耦,使系统在不直接暴露创建逻辑的前提下,灵活决定创建什么对象、由谁创建、何时创建。GoF 共归纳出 5 种创建型模式:

| # | 模式 | 一句话定义 | 主要意图 |
|---|---|---|---|
| 1 | **单例模式** (Singleton) | 一个类只有一个实例,提供全局访问点 | 控制实例数量 |
| 2 | **工厂方法模式** (Factory Method) | 定义创建对象的接口,让子类决定实例化哪个类 | 延迟创建到子类 |
| 3 | **抽象工厂模式** (Abstract Factory) | 提供一个接口,用于创建**相关或依赖对象族** | 产品族一致性 |
| 4 | **建造者模式** (Builder) | 将复杂对象的构建与其表示分离,同样的构建过程可创建不同表示 | 分步构建复杂对象 |
| 5 | **原型模式** (Prototype) | 用原型实例指定创建对象的种类,通过拷贝这些原型创建新对象 | 通过克隆创建 |

> **常见疑问**: 为什么 GoF 把创建型模式独立成一类? 因为对象的创建往往涉及"易变"的部分——具体类、依赖关系、装配顺序。把这部分逻辑封装到一层,可以降低系统的耦合度,让"业务代码"只依赖抽象而非具体实现。

## 二、对比表格

### 2.1 核心维度对比

| 维度 | 单例 (Singleton) | 工厂方法 (Factory Method) | 抽象工厂 (Abstract Factory) | 建造者 (Builder) | 原型 (Prototype) |
|---|---|---|---|---|---|
| **核心意图** | 控制实例数量=1 | 子类决定具体类 | 创建一整个产品族 | 分步构建复杂对象 | 通过克隆创建新对象 |
| **典型产出数量** | 1 个全局实例 | 多个 (按调用) | 多个 (按产品族) | 1 个 (但参数可调) | 多个 (克隆源对象) |
| **抽象层级** | 类自身 | 工厂方法 | 工厂接口 + 产品族接口 | Director + Builder | Prototype 接口 |
| **复杂度** | 低 | 中 | 高 | 中 | 中 |
| **扩展性** | 差 (要改原类) | 好 (新增工厂) | 好 (新增工厂) | 优秀 (新增 Builder) | 优秀 (新增原型) |
| **封装什么** | 实例化的次数 | 实例化的**类型** | 实例化的**一组类型** | 实例化的**过程** | 实例化的**来源** |
| **是否符合开闭原则** | ❌ | ✅ | ✅ | ✅ | ✅ |
| **是否依赖继承** | 否 | 是 | 是 | 否 | 否 |
| **典型适用场景** | 配置、连接池、日志 | 框架扩展点 (Logger、Cache) | 跨平台 UI、跨数据库 | HttpClient、SQL Builder | 高成本对象 (DB Connection) |
| **线程安全挑战** | 必须解决 | 通常由工厂方法保证 | 通常由工厂方法保证 | 不涉及 | 深拷贝 / 浅拷贝 |
| **代表实现** | `Runtime.getRuntime()` | `LoggerFactory.getLogger()` | `DocumentBuilderFactory` | `StringBuilder` | `Object.clone()` |

### 2.2 性能与使用频率对比

| 维度 | 单例 | 工厂方法 | 抽象工厂 | 建造者 | 原型 |
|---|---|---|---|---|---|
| **对象创建开销** | 极低 (1 次) | 中等 | 中等 | 高 (多步) | 低 (克隆) |
| **运行时内存占用** | 最小 | 一般 | 较大 (多个工厂类) | 一般 | 较小 |
| **代码量** | 最少 | 中等 | 多 | 中等 | 少 |
| **易测试性** | 难 (全局状态) | 容易 | 容易 | 容易 | 容易 |
| **学习曲线** | 低 | 中 | 高 | 中 | 中 |

### 2.3 与 SOLID 原则的关系

| 原则 | 单例 | 工厂方法 | 抽象工厂 | 建造者 | 原型 |
|---|---|---|---|---|---|
| **S (单一职责)** | ✅ 兼顾实例控制 | ✅ 兼顾创建 | ✅ 兼顾产品族 | ✅ 构建与表示分离 | ✅ 创建与表示分离 |
| **O (开闭原则)** | ❌ 改类违反 | ✅ 扩展子类 | ✅ 扩展工厂 | ✅ 扩展 Builder | ✅ 扩展原型 |
| **L (里氏替换)** | N/A | ✅ | ✅ | ✅ | ✅ |
| **I (接口隔离)** | ✅ 类小 | ✅ | ⚠️ 接口可能臃肿 | ✅ | ✅ |
| **D (依赖倒置)** | ❌ 常违反 | ✅ 依赖抽象 | ✅ 依赖抽象 | ✅ 依赖抽象 | ✅ 依赖抽象 |

## 四、实战代码示例

### 4.1 单例模式 (Python + Java)

**Python 实现** (`metaclass` + `__new__`):

```python
import threading


class SingletonMeta(type):
    """线程安全的单例元类"""
    _instances = {}
    _lock = threading.Lock()

    def __call__(cls, *args, **kwargs):
        if cls not in cls._instances:
            with cls._lock:
                if cls not in cls._instances:
                    cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]


class ConfigManager(metaclass=SingletonMeta):
    def __init__(self):
        if hasattr(self, "_initialized"):
            return
        self.props = {}
        self._initialized = True

    def get(self, key):
        return self.props.get(key)

    def set(self, key, value):
        self.props[key] = value


# 测试: 两个实例必须相同
c1 = ConfigManager()
c2 = ConfigManager()
assert c1 is c2  # ✅ True
```

**Java 实现** (Double-Checked Locking + volatile):

```java
public class Singleton {
    private static volatile Singleton instance;

    private Singleton() {
        if (instance != null) {
            throw new RuntimeException("Use getInstance()");
        }
    }

    public static Singleton getInstance() {
        if (instance == null) {                       // 1) 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {               // 2) 第二次检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**Java 最佳实现 (枚举 - Joshua Bloch 推荐)**:

```java
public enum Singleton {
    INSTANCE;
    private final Map<String, String> config = new ConcurrentHashMap<>();

    public void set(String k, String v) { config.put(k, v); }
    public String get(String k) { return config.get(k); }
}
```

### 4.2 工厂方法模式 (Python + Java)

**Python 实现**:

```python
from abc import ABC, abstractmethod


class Product(ABC):
    @abstractmethod
    def use(self): ...


class ConcreteProductA(Product):
    def use(self):
        return "Using Product A"


class ConcreteProductB(Product):
    def use(self):
        return "Using Product B"


class Factory(ABC):
    @abstractmethod
    def create_product(self) -> Product: ...


class FactoryA(Factory):
    def create_product(self):
        return ConcreteProductA()


class FactoryB(Factory):
    def create_product(self):
        return ConcreteProductB()


def client_code(factory: Factory):
    product = factory.create_product()
    return product.use()


print(client_code(FactoryA()))  # Using Product A
print(client_code(FactoryB()))  # Using Product B
```

**Java 实现**:

```java
public interface Product { void use(); }

public class ProductA implements Product {
    public void use() { System.out.println("A"); }
}

public abstract class Factory {
    public Product create() {
        Product p = factoryMethod();
        p.use();
        return p;
    }
    protected abstract Product factoryMethod();
}

public class FactoryA extends Factory {
    @Override
    protected Product factoryMethod() { return new ProductA(); }
}
```

### 4.3 抽象工厂模式

**Java 实现**: 跨平台 UI 控件族。

```java
// 抽象产品
public interface Button { void paint(); }
public interface Checkbox { void paint(); }

// 抽象工厂
public interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

// 具体工厂: Windows
public class WinFactory implements GUIFactory {
    public Button createButton() { return new WinButton(); }
    public Checkbox createCheckbox() { return new WinCheckbox(); }
}

// 具体工厂: Mac
public class MacFactory implements GUIFactory {
    public Button createButton() { return new MacButton(); }
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}

// 客户端
public class Application {
    private final Button button;
    private final Checkbox checkbox;
    public Application(GUIFactory factory) {
        button = factory.createButton();
        checkbox = factory.createCheckbox();
    }
    public void paint() { button.paint(); checkbox.paint(); }
}
```

### 4.4 建造者模式

**Java 实现** (Lombok 风格):

```java
public class HttpRequest {
    private final String url;
    private final String method;
    private final Map<String, String> headers;
    private final String body;
    private final int timeoutMs;

    private HttpRequest(Builder b) {
        this.url = b.url;
        this.method = b.method;
        this.headers = b.headers;
        this.body = b.body;
        this.timeoutMs = b.timeoutMs;
    }

    public static class Builder {
        private final String url;          // 必填
        private String method = "GET";
        private Map<String, String> headers = new HashMap<>();
        private String body = "";
        private int timeoutMs = 5000;

        public Builder(String url) { this.url = url; }
        public Builder method(String m) { this.method = m; return this; }
        public Builder header(String k, String v) { this.headers.put(k, v); return this; }
        public Builder body(String b) { this.body = b; return this; }
        public Builder timeout(int ms) { this.timeoutMs = ms; return this; }
        public HttpRequest build() { return new HttpRequest(this); }
    }
}

// 使用
HttpRequest req = new HttpRequest.Builder("https://api.x.com/users")
        .method("POST")
        .header("Content-Type", "application/json")
        .body("{\"name\":\"Alice\"}")
        .timeout(3000)
        .build();
```

**Python 等价实现** (使用 `dataclasses`):

```python
from dataclasses import dataclass, field
from typing import Dict


@dataclass
class HttpRequest:
    url: str
    method: str = "GET"
    headers: Dict[str, str] = field(default_factory=dict)
    body: str = ""
    timeout_ms: int = 5000


req = HttpRequest(url="https://api.x.com/users",
                  method="POST",
                  headers={"Content-Type": "application/json"},
                  body='{"name":"Alice"}',
                  timeout_ms=3000)
```

### 4.5 原型模式

**Java 实现** (深拷贝示例):

```java
public class Sheep implements Cloneable {
    private String name;
    private int age;
    private Address address;   // 引用类型

    public Sheep(String name, int age, Address address) {
        this.name = name;
        this.age = age;
        this.address = address;
    }

    /** 深拷贝 */
    @Override
    public Sheep clone() {
        try {
            Sheep copy = (Sheep) super.clone();
            copy.address = this.address.clone();  // 递归克隆
            return copy;
        } catch (CloneNotSupportedException e) {
            throw new AssertionError();
        }
    }
}

public class Address implements Cloneable {
    public String city;
    public Address(String city) { this.city = city; }
    @Override
    public Address clone() throws CloneNotSupportedException {
        return (Address) super.clone();
    }
}
```

**Python 实现** (使用 `copy` 模块):

```python
import copy

class Sheep:
    def __init__(self, name, age, address):
        self.name = name
        self.age = age
        self.address = address  # {'city': ...}


addr = {'city': 'Beijing'}
s1 = Sheep('Dolly', 3, addr)
s2 = copy.deepcopy(s1)

s2.address['city'] = 'Shanghai'
print(s1.address['city'])  # Beijing ✅ 深拷贝成功
```

## 五、真实项目案例

### 5.1 单例 - Java `Runtime`

```java
public class Runtime {
    private static final Runtime currentRuntime = new Runtime();
    public static Runtime getRuntime() { return currentRuntime; }
    private Runtime() {}
    // ... exec(), availableProcessors() ...
}
```
应用场景: 进程信息、全局环境访问,整个 JVM 共享一个 Runtime。

### 5.2 工厂方法 - SLF4J 的 `LoggerFactory`

```java
public class LoggerFactory {
    public static Logger getLogger(Class<?> clazz) {
        // 根据 classpath 上的实现类 (logback / log4j) 反射创建
        return StaticLoggerBinder.getSingleton().getLoggerFactory().getLogger(clazz.getName());
    }
}
```
应用场景: 用户调用统一接口,具体 Logger 由日志框架实现,解耦。

### 5.3 抽象工厂 - JDBC `Connection` 体系

JDBC 中 `Connection`、`Statement`、`ResultSet` 是一族产品。`DriverManager.getConnection()` 返回 MySQL、Oracle、PostgreSQL 各自的实现,但方法签名一致——这就是抽象工厂的应用。

### 5.4 建造者 - OkHttp 的 `Request.Builder`

```java
Request request = new Request.Builder()
        .url("https://api.x.com")
        .addHeader("Authorization", "Bearer xxx")
        .post(RequestBody.create(MediaType.parse("application/json"), "{}"))
        .build();
```
OkHttp 的设计把 Http 请求参数化做得非常彻底,建造者模式让链式调用天然支持。

### 5.5 原型 - Spring Bean 的 `@Scope("prototype")`

Spring 容器默认 singleton,但通过 `@Scope("prototype")` 注解可以让 Bean 的创建行为符合原型模式: 每次 `getBean()` 都返回新实例(类似 new)。

## 六、选择建议

### 6.1 何时用哪个?

| 场景 | 推荐模式 | 原因 |
|---|---|---|
| 全局唯一资源 (配置、日志) | 单例 | 节省内存,提供统一访问点 |
| 框架提供扩展点 (Logger、Cache) | 工厂方法 | 让用户在不改源码的前提下替换实现 |
| 跨平台/跨厂商的产品族 | 抽象工厂 | 保证产品族内部一致性 |
| 对象参数多、构造过程复杂 | 建造者 | 让构建过程清晰、可读、可选参数 |
| 对象创建成本高 (DB连接、线程) | 原型 | 克隆比 new 高效 |
| 业务对象 (POJO) | 直接 new | 不要为了用模式而用 |

### 6.2 组合使用建议

| 组合 | 示例 |
|---|---|
| 单例 + 工厂方法 | 单例工厂 (Spring BeanFactory 默认就是单例 + 工厂方法) |
| 建造者 + 原型 | Builder 创建一个原型对象,然后基于它克隆 |
| 抽象工厂 + 工厂方法 | 抽象工厂内部通常用工厂方法实现每个产品 |
| 单例 + 建造者 | 单例内部维护一个 Builder 作为参数构造器 |

### 6.3 替代方案考量

- **单例** → 考虑依赖注入 (Spring `@Component`) 而非手写单例
- **工厂方法** → 考虑函数式接口 `Supplier<T>`
- **抽象工厂** → 考虑 DI 容器自动注入 (Spring profile)
- **建造者** → 考虑 Kotlin data class / Java record
- **原型** → 考虑 `MapStruct`、`BeanUtils.copyProperties()`

## 七、常见误区

### 7.1 单例的误区

| 误区 | 后果 | 正确做法 |
|---|---|---|
| ❌ 用 `synchronized` 修饰整个方法 | 性能差 | 用 DCL + `volatile` |
| ❌ 不用 `volatile` | 指令重排导致拿到半初始化的对象 | 必须 `volatile` |
| ❌ 用 `static` 静态变量模拟单例 | 失去延迟加载能力 | 用静态内部类或枚举 |
| ❌ 单例持有可变状态 | 多线程数据竞争 | 状态尽量无副作用或加锁 |
| ❌ 单例依赖其他单例 | 测试难 | 改为构造注入 |

### 7.2 工厂方法的误区

- ❌ 工厂类只创建一种产品 → 直接 `new` 即可
- ❌ 工厂方法返回 `null` → 抛异常或返回默认值
- ❌ 工厂类全是静态方法 → 无法继承扩展,失去工厂方法的意义

### 7.3 抽象工厂的误区

- ❌ 产品族只有 1 个产品 → 工厂方法足够
- ❌ 抽象工厂接口过于臃肿 → 拆分多个小接口
- ❌ 工厂内部 `new` 死 → 工厂方法 + 反射注入

### 7.4 建造者的误区

- ❌ 必填字段放在 `build()` 才校验 → 构造时立即校验
- ❌ Builder 状态可变 → 导致 build 顺序影响结果
- ❌ 字段超过 8 个仍用 Builder → 考虑是否参数设计本身有问题

### 7.5 原型的误区

- ❌ 默认实现浅拷贝 → 引用类型共享导致 bug
- ❌ 忘记 `Cloneable` 接口 → 抛 `CloneNotSupportedException`
- ❌ 循环引用的对象克隆 → 栈溢出

## 八、小结

| 模式 | 一句话 | 关键字 | 关键类 |
|---|---|---|---|
| **单例** | 全局唯一实例 | `volatile` `DCL` `enum` | `Runtime` |
| **工厂方法** | 子类决定创建哪个 | `Factory` `create()` | `LoggerFactory` |
| **抽象工厂** | 一族相关对象 | `Factory` `Product族` | `DocumentBuilderFactory` |
| **建造者** | 分步构建复杂对象 | `Builder` `Director` `链式调用` | `StringBuilder` |
| **原型** | 克隆生成新对象 | `clone()` `Prototype` | Spring `@Scope("prototype")` |

**核心选型原则**:
1. **优先简单**: 能 `new` 就 `new`,能用 `Supplier<T>` 就不用工厂。
2. **依赖抽象**: 不依赖具体类,面向接口编程。
3. **避免过度设计**: 只有在有"变化点"的地方才引入创建型模式。
4. **考虑现代替代**: Lombok、Spring、Record、DataClass 已经把很多模式内置化了。

> 设计模式不是银弹,而是"行业前辈的命名经验"。理解它们的**意图 (intent)** 比死记结构更重要。
