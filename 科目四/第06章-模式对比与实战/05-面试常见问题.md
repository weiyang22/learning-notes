# 05. 设计模式面试常见问题

> 精选 20 道高频面试题, 含答案 + 追问方向 + 实战建议.

---

## 1. 单例模式的 5 种实现方式

**答案**:

| 方式 | 关键点 |
| :--- | :--- |
| 饿汉 (static final) | 类加载即创建, 线程安全, 无锁 |
| 懒汉 (synchronized) | 第一次调用才创建, 但每次都加锁, 性能差 |
| 双重检查锁定 (DCL) | volatile + 两次 if, 兼顾懒加载和性能 |
| 静态内部类 | 利用类加载机制, 天然线程安全 + 懒加载 |
| 枚举 | JVM 保证, 防反射/反序列化破坏, 最佳实践 |

**追问方向**:
- 为什么双重检查需要 `volatile`? (防止指令重排序, 确保多线程可见性)
- 反射 / 反序列化如何破坏单例? (构造器私有但反射可访问)
- 为什么枚举能防止破坏? (JVM 在初始化 enum 时保证单例)

**实战建议**: 优先用枚举或静态内部类, 简单可靠.

## 2. 双重检查锁定为什么需要 volatile?

**答案**: 防止**指令重排序**.

```java
// 错误: 没有 volatile 可能返回未初始化的对象
instance = new Singleton();
// 实际指令:
// 1. 分配内存 (memory = allocate())
// 2. 初始化对象 (ctorInstance = mem)
// 3. 引用赋值 (instance = mem)  ← 可能重排序到 2 之前!
// 另一个线程 if (instance == null) → false, 直接返回未初始化的 instance
```

**volatile 的作用**: 防止重排序 + 保证可见性.

**追问**:
- volatile 的实现原理? (内存屏障)
- 还有哪些场景需要 volatile? (DCL, 状态标志, 独立观察)

## 3. 工厂方法和抽象工厂的区别

**答案**:

| 维度 | 工厂方法 | 抽象工厂 |
| :--- | :--- | :--- |
| 粒度 | **一个**产品 | **一族**产品 |
| 方法数 | 1 个 | 多个 |
| 复杂度 | 简单 | 复杂 |
| 扩展 | 加子类 (容易) | 加新族 (容易) / 加新产品 (难) |

**代码示例**:
```java
// 工厂方法: 1 个工厂方法
public abstract class Logistics {
    public void plan() {
        Vehicle v = createVehicle();  // 1 个方法
        v.deliver();
    }
    abstract Vehicle createVehicle();
}

// 抽象工厂: 多个工厂方法
public abstract class GUIFactory {
    abstract Button createButton();       // 多个方法
    abstract TextField createTextField();
    abstract Checkbox createCheckbox();
}
```

**追问**: 抽象工厂的缺点? (类数量多, 加新产品要改所有工厂)

## 4. 建造者模式和工厂模式的区别

**答案**:

| 维度 | 建造者 | 工厂 |
| :--- | :--- | :--- |
| 关注 | **构建过程** (怎么造) | **创建结果** (造什么) |
| 步骤 | 多步链式 | 一次性 |
| 复杂度 | 复杂对象 | 任意对象 |
| 链式调用 | ✅ | ❌ |

**代码对比**:
```java
// 工厂
User user = UserFactory.create("Alice", 25, "alice@x.com");

// 建造者
User user = new UserBuilder()
    .name("Alice")
    .age(25)
    .email("alice@x.com")
    .build();
```

## 5. 装饰器模式和代理模式的区别

**答案**:

| 维度 | 装饰器 | 代理 |
| :--- | :--- | :--- |
| 目的 | **添加职责** | **控制访问** |
| 接口 | 保持原接口 | 保持原接口 |
| 关系 | 装饰器知道被装饰者 | 代理可能不知道 (远程代理) |
| 调用 | 显式包装 | 隐式 (客户端无感) |

**代码示例**:
```java
// 装饰器: 同接口, 包装增强
InputStream in = new BufferedInputStream(new FileInputStream("a.txt"));
// 客户端知道自己在用 BufferedInputStream

// 代理: 客户端拿到接口, 不知道具体是哪个实现
UserService userService = (UserService) Proxy.newProxyInstance(
    loader, interfaces, invocationHandler);
// 客户端不知道是 UserServiceImpl 还是代理
```

## 6. 适配器模式和装饰器模式的区别

**答案**:

| 维度 | 适配器 | 装饰器 |
| :--- | :--- | :--- |
| 目的 | **转换接口** | **添加职责** |
| 接口 | 转换为**不同**接口 | 保持**相同**接口 |
| 关系 | 把 A 适配成 B | 给 A 加功能 |
| 嵌套 | 通常 1 层 | 可多层 |

**代码对比**:
```java
// 适配器: 把 InputStream 适配成 Reader
Reader reader = new InputStreamReader(inputStream, "UTF-8");

// 装饰器: 给 InputStream 加缓冲功能
InputStream in = new BufferedInputStream(inputStream);
```

## 7. 观察者模式和发布订阅的区别

**答案**:

| 维度 | 观察者 | 发布订阅 |
| :--- | :--- | :--- |
| 耦合 | Subject 知道 Observer | 通过 Broker 解耦 |
| 调用 | 同步 | 异步 |
| 范围 | 单进程 | 跨进程 |
| 中间层 | 无 | Broker/EventBus |

**演进**: 观察者 + 中介者 = 发布订阅.

## 8. 策略模式和状态模式的区别

**答案**:

| 维度 | 策略 | 状态 |
| :--- | :--- | :--- |
| 关注 | **算法替换** | **行为随状态变** |
| 状态转换 | 不知道其他策略 | 状态之间可转换 |
| Context | 主动选 | 内部转换 |

**代码对比**:
```java
// 策略: 排序算法可替换
sortContext.setStrategy(new QuickSort());

// 状态: 订单状态自动转换
order.process();  // CreatedState -> PaidState -> ShippedState
```

## 9. 模板方法模式和策略模式的区别

**答案**:

| 维度 | 模板方法 | 策略 |
| :--- | :--- | :--- |
| 关系 | **继承** | **组合** |
| 算法骨架 | 父类定 | 无骨架 |
| 变化点 | 子类重写钩子 | Context 持有 Strategy |

**代码对比**:
```java
// 模板方法: 继承
abstract class DataProcessor {
    public final void process() {
        read();
        parse();
        save();
    }
    abstract void read();
}

// 策略: 组合
class SortContext {
    SortStrategy strategy;
    void sort() { strategy.sort(); }
}
```

**注意**: 模板方法违反 "组合优于继承", 但适合固定流程场景.

## 11. 享元模式的本质

**答案**: 用**共享**技术减少大量**细粒度对象**的创建.

```java
// 围棋棋子: 只有黑/白, 共享
class ChessPiece {
    private static final ChessPiece BLACK = new ChessPiece("黑");
    private static final ChessPiece WHITE = new ChessPiece("白");
    
    public static ChessPiece get(String color) {
        return "黑".equals(color) ? BLACK : WHITE;
    }
}
```

**应用**: 字符池, 数据库连接池, 线程池, Java Integer (-128 到 127 缓存)

## 12. 组合模式如何处理树形结构

**答案**: 让**单个对象**和**组合对象**实现**同一个接口**, 客户端统一对待.

```java
public interface FileSystemNode {
    void display();
    long size();
}

public class File implements FileSystemNode {
    private String name;
    private long size;
    
    public void display() { System.out.println(name); }
    public long size() { return size; }
}

public class Directory implements FileSystemNode {
    private List<FileSystemNode> children = new ArrayList<>();
    
    public void display() {
        for (FileSystemNode child : children) {
            child.display();  // 多态调用
        }
    }
    
    public long size() {
        return children.stream().mapToLong(FileSystemNode::size).sum();
    }
}
```

**关键**: `Directory` 持有 `List<FileSystemNode>`, 不区分是 File 还是 Directory.

## 13. 命令模式的优缺点

**优点**:
- 解耦调用者和接收者
- 容易实现撤销/重做 (栈)
- 容易实现宏命令 (组合)

**缺点**:

## 14. 中介者模式可能成为上帝对象吗?

**答案**: **是**, 这是中介者模式的最大缺点.

```java
// 警告: 风险
class ChatRoom implements Mediator {
    // 所有交互都在这里
    public void notify(...) { ... }
    public void whenUserJoins() { ... }
    public void whenUserLeaves() { ... }
    public void whenMessageSent() { ... }
    // ...
}
```

**如何避免**:
- 不要强制使用中介者, 简单情况直接调用
- 拆分为多个中介者 (按业务领域)
- 中介者只负责**协调**, 不做具体业务

## 15. SOLID 5 原则如何记忆

**答案**: 用一句话记忆每个原则:

| 字母 | 原则 | 一句话 |
| :--- | :--- | :--- |
| **S** | 单一职责 | **一个类只做一件事** |
| **O** | 开闭 | **对扩展开放, 对修改关闭** |
| **L** | 里氏替换 | **子类能替换父类** |
| **I** | 接口隔离 | **不要依赖不需要的接口** |
| **D** | 依赖倒置 | **依赖抽象不依赖具体** |

**记忆口诀**: "S**单**O**开**L**替**I**隔**D**倒**" → 单元开路替代隔离倒置.

## 16. 单一职责原则的"职责"如何划分

**答案**: "职责" = **引起变化的原因** (罗伯特·马丁).

```java
// 反例: 一个类有多个变化原因
class Employee {
    void calculatePay() { ... }    // 变化原因 1: 薪资算法变
    void saveToDB() { ... }        // 变化原因 2: 数据库变
    void generateReport() { ... }  // 变化原因 3: 报表格式变
}

// 正例: 拆分
class Employee { String name; ... }        // 数据
class PayCalculator { void calc(Employee); }  // 薪资
class EmployeeRepository { void save(Employee); }  // 持久化
class ReportGenerator { void gen(Employee); }  // 报表
```

**判断标准**: 这个类有几个理由让你修改? 多于 1 个就该拆.

## 17. 开闭原则的应用场景

**答案**: 框架的扩展点设计.

```java
// JDK: InputStream 抽象 - 加新流不影响现有代码
public abstract class InputStream {
    public abstract int read();
}
// BufferedInputStream, GZIPInputStream, ObjectInputStream 都是子类
// 加 CipherInputStream 也不动旧代码

// Spring: BeanPostProcessor - 框架扩展点
public interface BeanPostProcessor {
    Object postProcessBeforeInitialization(Object bean, String name);
}
```

**关键**: 用**抽象 + 多态**, 让变化通过**新子类**而非**修改现有代码**实现.

## 18. 里氏替换原则的违反情况

**答案**: 子类改变父类行为 (行为变异).

```java
// 反例: Square extends Rectangle
class Rectangle {
    protected int width, height;
    public void setWidth(int w) { this.width = w; }
    public void setHeight(int h) { this.height = h; }
    public int area() { return width * height; }
}

class Square extends Rectangle {
    @Override
    public void setWidth(int w) {
        this.width = w;
        this.height = w;  // ❌ 改变了父类行为: setWidth 也改变了 height
    }
}

// 客户端代码: 
Rectangle r = new Square();
r.setWidth(5);
r.setHeight(3);
assert r.area() == 15;  // ❌ Square.area() == 25, 不是 15
```

**违反 LSP 的表现**: 父类能用的地方, 子类不一定能用.

## 19. 设计模式过度使用的危害

**答案**: 5 大危害

1. **增加复杂度**: 小问题用大模式, 难以理解
2. **降低性能**: 多层包装 / 间接调用
3. **代码膨胀**: 类数量爆炸 (5 个模式可能产生 20+ 类)
4. **过度抽象**: 简单的 if-else 变成模板方法 + 工厂 + 策略
5. **阻碍迭代**: 加新行为要理解整个模式体系

**反例**:
```java
// ❌ 一个简单加法用 5 个模式
ValueProviderFactory
  .createProvider(...)
  .getStrategy(...)
  .execute(new Context(...))
  .process(new Operation(...));
// 不如直接写: int sum = a + b;
```

**判断标准**: **没有 3+ 个类似对象**就不需要模式.

## 20. 面试中如何回答"请举例说明你在项目中用到的设计模式"

**答案模板**:

```text
我在 [项目名] 中, 用了 [模式名] 解决了 [具体问题].

具体场景: [业务场景, 比如 "日志系统需要支持多输出源"]
解决方案: [用模式实现, 比如 "用抽象工厂 + 策略模式"]
效果: [带来的好处, 比如 "新增 ES 输出只需加个类, 不改核心代码"]
```

**实战建议**:
- ✅ 准备 2-3 个**真实项目**案例
- ✅ 每个案例讲清楚 **为什么用** + **怎么用** + **效果**
- ✅ 提到 **权衡**: "考虑过简单方案, 但 [原因] 选择了模式"
- ❌ 不要为了用模式而用, 简单问题用 if-else

**示例答案**:
> "在 [支付系统] 中, 我们用**策略模式**处理多种支付方式 (支付宝/微信/银联). 最初用 if-else, 加新支付方式要改核心代码. 重构后, 每种支付方式是独立 Strategy 类, 加新支付方式只需加类, 业务代码不动. 同时用**工厂方法**选择具体策略, 客户端只面向接口编程."

## 21. (加分题) 设计模式如何分类记忆?

**答案**: 按 "创建 / 结构 / 行为" 三大类

| 类别 | 关注点 | 模式数 | 记忆关键词 |
| :---: | :--- | :---: | :--- |
| 创建型 | **谁** 出生 | 5 | 工厂系列 + 单例 + 建造者 + 原型 |
| 结构型 | **怎么组合** | 7 | 适配/桥接/组合/装饰/外观/享元/代理 |
| 行为型 | **怎么互动** | 11 | 观察者/策略/命令/责任链/... |

**口诀**: "**生**(创建) → **长**(结构) → **动**(行为)"

## 22. (加分题) 反模式 (Anti-pattern) 有哪些?

**答案**: 常见反模式

| 反模式 | 描述 | 替代方案 |
| :--- | :--- | :--- |
| **God Object** | 一个类做所有事 | 单一职责 |
| **Spaghetti Code** | 嵌套 if-else | 状态模式/策略 |
| **Lava Flow** | 死代码不敢删 | 持续重构 |
| **Golden Hammer** | 一个模式解决所有问题 | 灵活运用 |
| **Big Ball of Mud** | 系统结构混乱 | 架构分层 |
| **Poltergeist** | 类只用来传参 | 用 Record/数据类 |
| **Copy-Paste Programming** | 重复代码 | DRY + 抽象 |
| **Inner Platform Effect** | 系统再造一个系统 | 简化设计 |

**关键**: 反模式是"看起来在工作但实际上有问题"的设计.
