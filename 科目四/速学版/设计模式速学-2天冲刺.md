# 📘 创建型模式 (5 种)

## 1. 单例 (Singleton) ⭐⭐⭐ 高频

**一句话**: 保证一个类**只有一个实例**, 并提供一个访问它的全局访问点.

**datawhale 模式引入** (《大话设计模式》案例):

去公司上班, 公司只有一个 CEO. 不管 CEO 在不在办公室, 所有人都能找他签字. CEO 必须保证唯一性 (否则签字乱套). 单例模式就是让一个类有且只有一个实例, 并提供全局访问.

**类比现实**:
- CEO: 一个公司只有一个
- 打印机: 一台电脑只连一个打印机
- 配置文件: 一个应用只加载一次
- 数据库连接池: 一个池只创建一份

**5 种实现对比**:

| 方式 | 懒加载 | 线程安全 | 性能 | 推荐 |
| :--- | :---: | :---: | :---: | :--- |
| 饿汉 (static final) | ❌ | ✅ | 高 | 单例占用少时 |
| 懒汉 (synchronized) | ✅ | ✅ | 低 | 简单场景 |
| 双重检查 (DCL) | ✅ | ✅ | 高 | **生产首选** |
| 静态内部类 | ✅ | ✅ | 高 | 优雅写法 |
| 枚举 | ❌ | ✅ | 高 | **Joshua Bloch 推荐** |

**最佳实践: 枚举 (Joshua Bloch 推荐)**:

```java
public enum Singleton {
    INSTANCE;
    public void doWork() { System.out.println("Singleton work"); }
}

// 使用
Singleton.INSTANCE.doWork();
```

**双重检查 (DCL) 生产环境写法**:

```java
public class Singleton {
    private volatile static Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**关键点**: 双重检查需 `volatile` 防指令重排序 + 保证内存可见性.

**追问**: 反射 / 反序列化如何破坏单例? 答: 反射访问私有构造器创建新实例; 枚举天然防御这些攻击.

## 2. 工厂方法 (Factory Method) ⭐⭐⭐ 高频

**一句话**: 定义一个用于创建对象的接口, 但让**子类决定实例化哪个类**.

**datawhale 模式引入** (《大话设计模式》案例):

去餐厅吃饭, 服务员根据你的选择给你做不同菜 (中餐/西餐/日餐). 服务员不需要知道每种菜怎么做, 只负责"创建". 厨师决定具体做什么菜. 服务员是 Client, 厨师是 Factory.

**类比现实**:
- 餐厅服务员: 根据客人选择派给不同厨师
- 日志记录器: 文件日志 vs 数据库日志
- 数据库连接: MySQL 连接 vs PostgreSQL 连接

**4 个角色**:

| 角色 | 职责 |
| :--- | :--- |
| Product | 抽象产品 (接口/抽象类) |
| ConcreteProduct | 具体产品 (实现 Product) |
| Creator | 抽象工厂 (声明 factoryMethod) |
| ConcreteCreator | 具体工厂 (实现 factoryMethod, 返回具体产品) |

**Java 实现 (物流)**:

```java
// 抽象产品
public interface Vehicle {
    void deliver();
}

// 具体产品
public class Truck implements Vehicle {
    public void deliver() { System.out.println("卡车陆运"); }
}

public class Ship implements Vehicle {
    public void deliver() { System.out.println("轮船海运"); }
}

// 抽象创建者
public abstract class Logistics {
    public void plan() {  // 模板方法 (用工厂方法)
        Vehicle v = createVehicle();
        v.deliver();
    }

    protected abstract Vehicle createVehicle();  // 工厂方法
}

// 具体创建者
public class RoadLogistics extends Logistics {
    protected Vehicle createVehicle() { return new Truck(); }
}

public class SeaLogistics extends Logistics {
    protected Vehicle createVehicle() { return new Ship(); }
}

// 使用
Logistics logistics = new RoadLogistics();
logistics.plan();  // 自动用卡车发货
```

**应用**: JDBC `Connection.createStatement()`, Spring `FactoryBean`, Log4j Appender.

**vs 简单工厂**: 简单工厂一个 if-else (违反开闭); 工厂方法用多态扩展.

**追问**: 工厂方法 + 模板方法 是什么关系? 答: 工厂方法常嵌在模板方法中使用, 如上例.

## 3. 抽象工厂 (Abstract Factory) ⭐⭐ 中频

**一句话**: 提供一个创建一系列相关或相互依赖对象的接口, 而无需指定它们的具体类.

**datawhale 模式引入** (《大话设计模式》案例):

跨平台 UI 库 (Windows / Mac / Linux), 每种平台都有 Button 和 TextBox. 如果直接用工厂方法, 要分别创建 WinButton + MacButton + WinTextBox + MacTextBox, 容易混搭 (Windows 的 Button + Mac 的 TextBox 风格不一致). 抽象工厂保证**同族产品**必须配套.

**类比现实**:
- 跨平台 UI: Windows / Mac / Linux 风格统一
- 跨数据库访问: MySQL/Oracle 各自一套组件
- 跨主题皮肤: 浅色主题 / 深色主题 风格统一

**4 个角色**:

| 角色 | 职责 |
| :--- | :--- |
| AbstractFactory | 抽象工厂 (声明一族产品的创建方法) |
| ConcreteFactory | 具体工厂 (实现一族产品) |
| AbstractProduct | 抽象产品 (多个, 如 Button / TextBox) |
| ConcreteProduct | 具体产品 (按工厂家族分类) |

**Python 实现 (跨平台 UI)**:

```python
from abc import ABC, abstractmethod

class Button(ABC):
    @abstractmethod
    def render(self): pass

class TextBox(ABC):
    @abstractmethod
    def render(self): pass

class WinButton(Button):
    def render(self): print("[Win 风格] Button")

class WinTextBox(TextBox):
    def render(self): print("[Win 风格] TextBox")

class MacButton(Button):
    def render(self): print("[Mac 风格] Button")

class MacTextBox(TextBox):
    def render(self): print("[Mac 风格] TextBox")

class GUIFactory(ABC):
    @abstractmethod
    def create_button(self) -> Button: pass
    @abstractmethod
    def create_textbox(self) -> TextBox: pass

class WinFactory(GUIFactory):
    def create_button(self): return WinButton()
    def create_textbox(self): return WinTextBox()

class MacFactory(GUIFactory):
    def create_button(self): return MacButton()
    def create_textbox(self): return MacTextBox()

# 使用
factory = WinFactory()
button = factory.create_button()
textbox = factory.create_textbox()
button.render()    # [Win 风格] Button
textbox.render()   # [Win 风格] TextBox
```

**应用**: JDK 跨平台 UI, Spring ApplicationContext, 数据库连接池.

**追问**: 加新产品 (如 Tooltip) 怎么办? 答: 修改抽象工厂接口 (破坏 OCP), 这就是抽象工厂的缺点.

**vs 工厂方法**: 一个工厂生产**一种** vs **一族**.

## 4. 建造者 (Builder) ⭐⭐⭐ 高频

**一句话**: 将一个复杂对象的构建与它的表示分离, 使得同样的构建过程可以创建不同的表示.

**datawhale 模式引入** (《大话设计模式》案例):

去 KFC 买套餐, 服务员一步步给你加汉堡 + 薯条 + 可乐. 套餐是产品, 加每一步是建造步骤. 同样的步骤可以组合出不同套餐 (A 套餐 / B 套餐). 这就是建造者模式.

**类比现实**:
- 套餐: 汉堡 + 薯条 + 可乐 = 套餐 A / B / C
- HTTP 请求: 协议 + URL + Header + Body = 不同请求
- 电脑配置: CPU + 内存 + 硬盘 + 显卡 = 多种配置
- Java StringBuilder: append 链式

**3 个角色**:

| 角色 | 职责 |
| :--- | :--- |
| Builder | 抽象建造者 (step1/step2/...) |
| ConcreteBuilder | 具体建造者 (实现步骤 + getResult) |
| Director | 指挥者 (使用 Builder 顺序构建) |
| Product | 复杂产品 (多个部分组成) |

**Java 标准写法 (HttpClient)**:

```java
HttpRequest req = HttpRequest.newBuilder()
    .uri(URI.create("https://api.x.com"))
    .header("Content-Type", "application/json")
    .timeout(Duration.ofSeconds(30))
    .build();
```

**Python 自定义实现 (套餐)**:

```python
class Meal:
    def __init__(self):
        self.items = []
    def add(self, item): self.items.append(item)
    def show(self):
        print("套餐包含:", ", ".join(self.items))

class MealBuilder:
    def __init__(self):
        self.meal = Meal()

    def add_burger(self): self.meal.add("汉堡"); return self
    def add_fries(self): self.meal.add("薯条"); return self
    def add_drink(self): self.meal.add("可乐"); return self
    def build(self): return self.meal

# 使用 - 链式调用
meal = (MealBuilder()
        .add_burger()
        .add_fries()
        .add_drink()
        .build())
meal.show()  # 套餐包含: 汉堡, 薯条, 可乐
```

**Lombok 简化**: `@Builder` 注解一键生成.

```java
@Builder
public class User {
    private String name;
    private int age;
    private String email;
}
// 自动生成 User.builder().name(...).age(...).build()
```

**应用**: HttpRequest, StringBuilder, Lombok @Builder, JPA 查询构造, MyBatis SqlBuilder.

## 5. 原型 (Prototype) ⭐ 低频

**一句话**: 用原型实例指定创建对象的种类, 并通过拷贝这些原型创建新的对象.

**datawhale 模式引入** (《大话设计模式》案例):

去打印店复印简历, 老板不重新写一遍, 而是复印一份. 复印就是克隆, 原件就是原型. 简历模板就是这个原型模式.

**类比现实**:
- 细胞分裂: 一个细胞分裂成两个完全一样的
- Word 文档复制: Ctrl+C, Ctrl+V
- Java Object.clone(): 浅拷贝
- 深拷贝工具: 序列化再反序列化

**Python 实现 (简历克隆)**:

```python
import copy

class Resume:
    def __init__(self, name):
        self.name = name
        self.skills = []

    def add_skill(self, skill): self.skills.append(skill)

    def clone(self):
        return copy.deepcopy(self)  # 深拷贝

    def show(self):
        print(f"简历: {self.name}, 技能: {self.skills}")

# 创建原型
prototype = Resume("张三")
prototype.add_skill("Python")
prototype.add_skill("机器学习")

# 克隆
clone1 = prototype.clone()
clone1.name = "李四"  # 修改克隆不影响原型
clone1.add_skill("Java")  # 深拷贝, 独立修改

prototype.show()  # 张三, [Python, 机器学习]
clone1.show()      # 李四, [Python, 机器学习, Java]
```

**关键**: 区分浅拷贝 vs 深拷贝, 默认 clone 是浅.

- 浅拷贝: 复制对象本身, 但嵌套对象共享引用 (危险)
- 深拷贝: 递归复制所有嵌套对象 (安全但慢)

**应用**: Java Object.clone(), Prototype 模式常用于**创建成本高**的对象 (如数据库查询结果).

# 🏗 结构型模式 (7 种)

## 6. 适配器 (Adapter) ⭐⭐⭐ 高频

**一句话**: 将一个类的接口转换成客户希望的另一个接口, 使原本由于接口不兼容而不能一起工作的那些类可以一起工作.

**datawhale 模式引入** (《大话设计模式》案例):

买港行电器, 插头是英标三脚 (220V), 但国内插座是两脚 (220V), 插不进去. 买个"转换插头" (适配器), 英标就变成国标了, 电器能用了.

**类比现实**:
- 电源转换插头: 英标 ↔ 国标
- 读卡器: SD 卡 ↔ USB
- Java I/O: 字节流 ↔ 字符流
- 第三方 SDK 适配: 旧 API ↔ 新 API

**3 种角色**:

| 角色 | 职责 |
| :--- | :--- |
| Target | 目标接口 (客户端期望的接口) |
| Adaptee | 被适配者 (已有接口, 但不兼容) |
| Adapter | 适配器 (实现 Target, 包装 Adaptee) |

**对象适配 (组合, 推荐)**:

```java
public class InputStreamReader extends Reader {
    private InputStream in;  // 持有被适配者

    public InputStreamReader(InputStream in, String charset) {
        this.in = in;
    }

    public int read() {  // 委托给被适配者
        return in.read();
    }
}

// 使用
InputStream is = new FileInputStream("a.txt");
Reader r = new InputStreamReader(is, "UTF-8");  // 字节流 → 字符流
```

**类适配 vs 对象适配**:
- **类适配**: Java 多继承, 实现 Target 接口 + 继承 Adaptee (不灵活)
- **对象适配** (推荐): 实现 Target 接口 + 持有 Adaptee 引用 (组合, 更灵活)

**类适配 vs 对象适配**: Java 单继承推荐**对象适配** (组合).

## 7. 桥接 (Bridge) ⭐⭐ 中频

**一句话**: 将抽象部分与它的实现部分分离, 使它们都可以独立地变化.

**datawhale 模式引入** (《大话设计模式》案例):

画图, 图形 (圆/方/三角) 有颜色 (红/黄/蓝). 不用桥接的话, 3 种形状 × 3 种颜色 = 9 个类 (红圆, 黄圆, 蓝圆, 红方, ...). 用桥接, 形状和颜色解耦: 形状持有颜色引用, 加新颜色不用改形状.

**类比现实**:
- 电视: 品牌 (Sony / TCL / 小米) + 内容源 (HDMI / AV / 网络)
- 手机: 操作系统 (Android / iOS) + 应用
- JDBC Driver: Connection (抽象) + Driver (实现)
- Logger: 输出格式 (文字/JSON) + 输出位置 (文件/网络)

**结构组成**:

```text
      ┌─────────────────────┐
      │   <<Abstraction>>   │
      │    (抽象层)         │
      ├─────────────────────┤
      │ -implementor        │ ─────── 桥接 ───────┐
      ├─────────────────────┤                     │
      │ +operation()        │                     ▼
      └──────────△──────────┘         ┌──────────────────┐
                 ▲                   │ <<Implementor>>  │
      ┌──────────┴──────────┐         │   (实现层)       │
      │ RefinedAbstraction  │         ├──────────────────┤
      │ (具体抽象)          │         │ +operationImpl() │
      └─────────────────────┘         └──────────△───────┘
                                                 │
                                ┌────────────────┴─────┐
                                │ ConcreteImplementorA  │
                                │ ConcreteImplementorB  │
                                └───────────────────────┘
```

**应用**: JDBC 驱动, AWT 跨平台, 日志框架 (SLF4J + Logback).

**追问**: 桥接 vs 装饰器区别? 答: 桥接是**类结构层面**的解耦 (设计期就分开); 装饰器是**对象层面**的增强 (运行时包装).

**核心**: 用**组合**替代多层继承, 解决 N×M 类爆炸.

## 8. 组合 (Composite) ⭐⭐ 中频

**一句话**: 将对象组合成树形结构以表示"部分-整体"的层次结构, 使客户端对单个对象和组合对象的使用具有一致性.

**datawhale 模式引入** (《大话设计模式》案例):

公司组织结构: CEO 下有 VP, VP 下有总监, 总监下有经理, 经理下有员工. 整棵树, 每个节点都能显示自己的下属 (不论是员工还是 VP). CEO 和员工用同一个方法 (show) 展示自己的信息.

**类比现实**:
- 文件系统: 文件 + 文件夹 (文件夹包含文件或子文件夹)
- 公司组织架构: 员工 + 部门 (部门包含员工或子部门)
- GUI 组件: 按钮 + 面板 (面板包含按钮或子面板)
- HTML DOM: 元素 + 嵌套元素

**3 个角色**:

| 角色 | 职责 |
| :--- | :--- |
| Component | 抽象组件 (声明接口) |
| Leaf | 叶子节点 (无子节点) |
| Composite | 容器节点 (有子组件列表) |

**Python 实现 (文件系统)**:

```python
from abc import ABC, abstractmethod
from typing import List

class FileSystemNode(ABC):
    @abstractmethod
    def display(self, indent=0): pass

class File(FileSystemNode):
    def __init__(self, name):
        self.name = name
    def display(self, indent=0):
        print(" " * indent + f"📄 {self.name}")

class Directory(FileSystemNode):
    def __init__(self, name):
        self.name = name
        self.children: List[FileSystemNode] = []
    def add(self, child):
        self.children.append(child)
    def display(self, indent=0):
        print(" " * indent + f"📁 {self.name}")
        for child in self.children:
            child.display(indent + 2)

# 使用
root = Directory("根目录")
docs = Directory("文档")
docs.add(File("简历.md"))
src = Directory("源码")
src.add(File("main.py"))
root.add(docs)
root.add(src)
root.display()  # 树形打印
```

**应用**: 文件系统, 公司组织架构, GUI 组件树, HTML DOM, 菜单树, 算术表达式.

**追问**: 组合模式 vs 装饰器模式? 答: 组合是树形结构 (一对多), 装饰器是链式结构 (一对一).

**经典**: 文件系统 (File + Directory), UI 组件树.

## 9. 装饰器 (Decorator) ⭐⭐⭐ 高频

**一句话**: 动态给对象**添加职责**, 不改原类.

```java
InputStream in = new BufferedInputStream(new FileInputStream("a.txt"));
// 文件流 → 加缓冲 → 提高性能
```

**vs 适配器**: 装饰器保持**同接口**加功能; 适配器**改接口**.

**vs 代理**: 装饰器客户端**知道**自己在包装; 代理客户端**不知道**.

## 10. 外观 (Facade) ⭐⭐ 中频

## 11. 享元 (Flyweight) ⭐ 低频

**一句话**: 运用共享技术有效地支持大量细粒度的对象.

**datawhale 模式引入** (《大话设计模式》案例):

围棋有 361 个交叉点, 每个点上有黑子/白子/无子 3 种状态. 不用享元模式, 需要 361 个对象. 用享元模式, 只需要 2 个对象 (黑子 + 白子), 位置信息存在外部.

**类比现实**:
- 围棋棋子: 几百个位置但只有 2 种颜色共享
- Java Integer 缓存 (-128 到 127 共享)
- 字符池: 文章中重复的字符共享
- 数据库连接池: 多个查询共享几个连接

**结构组成**:

```text
        ┌──────────────────┐
        │   <<Flyweight>>  │
        │     (享元)        │
        ├──────────────────┤
        │ -intrinsicState  │  ← 内部状态 (共享)
        │ -extrinsicState  │  ← 外部状态 (由 client 传入)
        │ +operation()     │
        └──────────△───────┘
                   │
        ┌──────────┴────────┐
        │ ConcreteFlyweight │
        ├──────────────────┤
        │ +operation()     │
        └──────────────────┘

        ┌──────────────────┐
        │ FlyweightFactory │  ← 管理共享池
        ├──────────────────┤
        │ +get(key)        │
        └──────────────────┘
```

**Python 实现 (围棋棋子)**:

```python
import threading

class ChessPiece:
    _pool = {}  # 享元池

    def __new__(cls, color):
        # 已存在则返回共享对象
        if color in cls._pool:
            return cls._pool[color]
        # 否则创建新对象
        instance = super().__new__(cls)
        instance.color = color
        cls._pool[color] = instance
        return instance

# 使用
black = ChessPiece("黑")  # 创建
white1 = ChessPiece("白")  # 创建
white2 = ChessPiece("白")  # 共享 (与 white1 同一对象)

print(black is white1)   # False
print(white1 is white2)  # True (享元!)
```

**应用**: 围棋棋子, Java Integer, String 常量池, 数据库连接池, 线程池.

## 13. 观察者 (Observer) ⭐⭐⭐ 高频

**一句话**: 定义对象间一种**一对多**的依赖关系, 当一个对象状态发生改变时, 所有依赖它的对象都得到通知并自动更新.

**datawhale 模式引入** (《大话设计模式》案例):

小公司老板回来, 秘书通知前台 (准备茶) + 财务 (准备报销) + 助理 (准备文件). 秘书就是 Subject, 前台/财务/助理是 Observer. 秘书不知道具体要做什么 (不关心细节), 但老板回来时所有人都要被通知 (状态变化自动联动).

**类比现实**:
- 报社订阅: 报社是 Subject, 订户是 Observer
- 微信公众号: 公众号是 Subject, 关注者是 Observer
- 浏览器事件: DOM 是 Subject, listener 是 Observer

**4 个角色**:

| 角色 | 职责 |
| :--- | :--- |
| Subject | 抽象主题 (管理 Observer, 状态变化时通知) |
| Observer | 抽象观察者 (update 方法) |
| ConcreteSubject | 具体主题 (维护状态) |
| ConcreteObserver | 具体观察者 (收到通知后做反应) |

**Python 实现 (股价通知)**:

```python
from abc import ABC, abstractmethod
from typing import List

# 抽象观察者
class Observer(ABC):
    @abstractmethod
    def update(self, subject): pass

# 抽象主题
class Subject(ABC):
    def __init__(self):
        self._observers: List[Observer] = []

    def attach(self, observer):
        self._observers.append(observer)

    def detach(self, observer):
        self._observers.remove(observer)

    def notify(self):
        for obs in self._observers:
            obs.update(self)

# 具体主题: 股票
class Stock(Subject):
    def __init__(self, symbol, price):
        super().__init__()
        self._symbol = symbol
        self._price = price

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, value):
        if value != self._price:
            self._price = value
            self.notify()  # 状态变化自动通知

# 具体观察者: 投资者
class Investor(Observer):
    def __init__(self, name):
        self.name = name

    def update(self, subject):
        print(f"  → {self.name} 收到: {subject._symbol} = {subject._price}")

# 使用
apple = Stock("AAPL", 150)
alice = Investor("Alice")
bob = Investor("Bob")
apple.attach(alice)
apple.attach(bob)
apple.price = 155
# 输出:
#   → Alice 收到: AAPL = 155
#   → Bob 收到: AAPL = 155
```

**应用**: DOM 事件, Spring ApplicationEvent, Kafka, Vue 响应式, React Context.

**vs 发布订阅**: 观察者 Subject 知道 Observer; 发布订阅有 **Broker** 解耦.

## 14. 策略 (Strategy) ⭐⭐⭐ 高频

**一句话**: 定义一系列算法, 把它们一个个封装起来, 并且使它们可以**相互替换**.

**datawhale 模式引入** (《大话设计模式》案例):

去商场买东西, 不同等级会员折扣不同 (普通 9 折, 银卡 8 折, 金卡 7 折). 收银系统根据会员等级选择不同的折扣算法. 这里"折扣"就是策略, 不同等级是不同实现.

**类比现实**:
- 出行方式: 飞机/火车/汽车, 不同策略
- 排序算法: 快速排序/归并排序/堆排序
- 支付方式: 支付宝/微信/银联

**类比现实**:
- 出行方式: 飞机/火车/汽车 (Strategy 不同实现)
- 排序算法: 快速/归并/堆排序 (可切换)
- 支付方式: 支付宝/微信/银联 (互不影响)

**3 个角色**:

| 角色 | 职责 |
| :--- | :--- |
| Strategy | 抽象算法接口 |
| ConcreteStrategy | 具体算法 (QuickSort / MergeSort) |
| Context | 上下文, 持有 Strategy 引用, 委托调用 |

**Python 实现 (排序)**:

```python
from abc import ABC, abstractmethod
from typing import List

# 抽象策略
class SortStrategy(ABC):
    @abstractmethod
    def sort(self, data: List[int]) -> List[int]: pass

class QuickSort(SortStrategy):
    def sort(self, data):
        return sorted(data)

class BubbleSort(SortStrategy):
    def sort(self, data):
        result = data.copy()
        for i in range(len(result)):
            for j in range(len(result) - i - 1):
                if result[j] > result[j + 1]:
                    result[j], result[j+1] = result[j+1], result[j]
        return result

# 上下文
class SortContext:
    def __init__(self, strategy: SortStrategy):
        self.strategy = strategy

    def set_strategy(self, strategy):  # 运行时切换
        self.strategy = strategy

    def sort(self, data):
        return self.strategy.sort(data)

# 使用
ctx = SortContext(QuickSort())
ctx.sort([3, 1, 4, 1, 5])  # 快速排序
ctx.set_strategy(BubbleSort())  # 切换算法
ctx.sort([3, 1, 4, 1, 5])     # 冒泡排序
```

**应用**: Comparator, ThreadPoolExecutor.RejectedExecutionHandler, Java 加密算法切换.

**vs 状态**: 策略关注**怎么做事**; 状态关注**怎么转换**.

## 15. 命令 (Command) ⭐⭐⭐ 高频

**一句话**: 将请求**封装为对象**, 从而使你可以用不同的请求对客户进行参数化, 对请求排队或记录日志, 以及支持可撤销的操作.

**datawhale 模式引入** (《大话设计模式》案例):

我们去烧烤摊吃烧烤, 客人点单后, 服务员记录订单交给厨师. 这里"订单"就是一个命令对象, 包含客人点的菜品. 服务员不用关心具体是哪个厨师, 厨师也不用关心是哪个服务员. 订单就是服务员和厨师的解耦层.

**类比现实**:
- 餐厅订单: 包含菜品信息, 服务员交给厨房
- 遥控器按键: 每个按键对应一个命令
- 数据库事务: 每个 SQL 是一个命令

**4 个角色**:

| 角色 | 职责 |
| :--- | :--- |
| Command | 抽象命令接口 (execute + undo) |
| ConcreteCommand | 具体命令 (绑定 Receiver) |
| Invoker | 调用者 (持有命令历史栈) |
| Receiver | 接收者 (真正干活) |

**Java 完整实现 (文本编辑器撤销)**:

```java
// 1. 抽象命令
interface Command {
    void execute();
    void undo();
}

// 2. 具体命令: 插入字符
class InsertCommand implements Command {
    private TextDocument doc;
    private int position;
    private char character;

    public InsertCommand(TextDocument doc, int pos, char ch) {
        this.doc = doc;
        this.position = pos;
        this.character = ch;
    }

    public void execute() {
        doc.insert(position, character);
    }

    public void undo() {
        doc.delete(position);
    }
}

// 3. 接收者
class TextDocument {
    private StringBuilder text = new StringBuilder();

    public void insert(int pos, char c) {
        text.insert(pos, c);
    }

    public void delete(int pos) {
        text.deleteCharAt(pos);
    }
}

// 4. 调用者 (持有历史栈)
class Editor {
    private Stack<Command> history = new Stack<>();
    private TextDocument doc = new TextDocument();

    public void execute(Command cmd) {
        cmd.execute();
        history.push(cmd);  // 入栈
    }

    public void undo() {
        if (!history.isEmpty()) {
            history.pop().undo();  // 弹栈并撤销
        }
    }
}
```

**应用**:
- **撤销/重做**: 文本编辑器, Photoshop, IDE
- **任务队列**: Celery, Sidekiq, Kafka
- **数据库事务**: JDBC `Statement.execute()`, Spring `@Transactional`
- **GUI 按钮**: Swing 的 `Action`, Android 的 `Runnable`

**datawhale 重点强调**: 命令模式是**撤销/重做**的经典方案, 关键在于 Invoker 持有**历史栈**.

**追问方向**: 如何实现宏命令 (多条命令组合) ? 答: 用 Composite 模式组合命令.

## 17. 迭代器 (Iterator) ⭐⭐ 中频

**一句话**: 提供一种方法顺序访问一个聚合对象中各个元素, 而又无须暴露该对象的内部表示.

**datawhale 模式引入**: 去食堂打饭, 阿姨面前有不同菜, 你一个一个选, 但你不关心菜怎么放的. 阿姨就是迭代器, 给你统一遍历接口.

**4 个角色**:
- Iterator: 抽象迭代器 (hasNext, next)
- ConcreteIterator: 具体迭代器
- Aggregate: 抽象聚合 (createIterator)
- ConcreteAggregate: 具体聚合 (返回迭代器)

**Pythonic 实现**:

```python
# 方式 1: 实现迭代器协议
class CountDown:
    def __init__(self, start):
        self.current = start
    def __iter__(self):
        return self
    def __next__(self):
        if self.current <= 0:
            raise StopIteration
        self.current -= 1
        return self.current + 1

# 方式 2: 生成器 (更简洁)
def count_down(start):
    while start > 0:
        yield start
        start -= 1
```

**Java 实现 (JDK 风格)**:

```java
public interface Iterator<T> {
    boolean hasNext();
    T next();
}

public class ArrayIterator<T> implements Iterator<T> {
    private T[] array;
    private int index = 0;
    public ArrayIterator(T[] array) { this.array = array; }
    public boolean hasNext() { return index < array.length; }
    public T next() { return array[index++]; }
}

String[] arr = {"a", "b", "c"};
Iterator<String> it = new ArrayIterator<>(arr);
while (it.hasNext()) System.out.println(it.next());
```

**应用**: 集合遍历, 数据库游标 (JDBC ResultSet), 文件系统目录扫描, React 组件列表渲染.

**追问**: 迭代器模式的优缺点? 答: 优点 (统一遍历接口), 缺点 (增加类数量).

## 18. 中介者 (Mediator) ⭐ 低频

**一句话**: 用**中介对象**封装同事间**双向**复杂通信, 让各同事不需要显式相互引用.

**datawhale 模式引入** (《大话设计模式》案例):

公司里每个同事都要与多个部门沟通, 如果每个部门都知道所有其他部门, 关系会非常混乱. 引入"总经理"作为中介者, 任何沟通都通过总经理转发, 部门之间不需要相互知道, 关系就清晰了.

**类比现实**:
- 公司: 部门之间沟通通过总经理 (中介者)
- 机场: 飞机之间不直接通信, 都通过塔台 (中介者)
- GUI: 对话框的组件之间不互相调用, 都通过 Dialog (中介者)

**结构组成**:

```text
            ┌──────────────────┐
            │   <<Mediator>>    │
            │      Mediator     │
            ├──────────────────┤
            │ +notify(c, ev)    │
            └──────────△─────────┘
                       │ (实现)
        ┌──────────────┴──────────────┐
        │                             │
┌──────────────┐          ┌──────────────┐
│ColleagueA    │          │ColleagueB    │
├──────────────┤          ├──────────────┤
│-mediator     │          │-mediator     │
│+send(msg)    │          │+send(msg)    │
│+receive(msg) │          │+receive(msg) │
└──────────────┘          └──────────────┘
        △                             △
        └──────────────┬──────────────┘
                       │ (都持有 Mediator 引用)
```

**Python 实现 (聊天室)**:

```python
from abc import ABC, abstractmethod
from typing import List

# 抽象中介者
class Mediator(ABC):
    @abstractmethod
    def notify(self, sender, event: str): pass

# 抽象同事
class Colleague(ABC):
    def __init__(self, mediator: Mediator):
        self.mediator = mediator

# 具体同事: 用户
class User(Colleague):
    def __init__(self, name: str, mediator: Mediator):
        super().__init__(mediator)
        self.name = name

    def send(self, msg: str):
        print(f"{self.name} 发送: {msg}")
        self.mediator.notify(self, msg)  # 通过中介者

    def receive(self, sender, msg: str):
        print(f"  → {self.name} 收到 {sender.name} 的消息")

# 具体中介者: 聊天室
class ChatRoom(Mediator):
    def __init__(self):
        self.users: List[User] = []

    def register(self, user: User):
        if user not in self.users:
            self.users.append(user)

    def notify(self, sender, event: str):
        for user in self.users:
            if user != sender:  # 转发给其他用户
                user.receive(sender, event)

# 使用
room = ChatRoom()
alice = User("Alice", room)
bob = User("Bob", room)
charlie = User("Charlie", room)

room.register(alice)
room.register(bob)
room.register(charlie)

alice.send("大家好!")
# 输出:
# Alice 发送: 大家好!
#   → Bob 收到 Alice 的消息
#   → Charlie 收到 Alice 的消息
```

**风险**: 容易变成"上帝对象", 所有交互都在中介者里.

**datawhale 的建议**: 当中介者方法数 > 15 个时考虑拆分; 或者改用观察者模式 (用事件替代中介者).

**vs 观察者**: 中介者**双向**通信; 观察者**单向**通知.

## 19. 备忘录 (Memento) ⭐⭐ 中频

**一句话**: 在不破坏封装性的前提下, 捕获一个对象的内部状态, 并在该对象之外保存这个状态, 这样以后就可将该对象恢复到原先保存的状态.

**datawhale 模式引入** (《大话设计模式》案例):

打游戏有"存档"功能. 玩家在关键节点 (Boss 前) 存档, 死亡后可以读档回到存档点. 存档就是备忘录 (Memento), 存储玩家所有状态.

**类比现实**:
- 游戏存档: 记录所有游戏状态
- 数据库事务: 保存回滚点
- Git commit: 记录代码快照
- 浏览器后退: 保存历史 URL

**3 个角色**:

| 角色 | 职责 |
| :--- | :--- |
| Originator | 原发器 (创建/恢复备忘录) |
| Memento | 备忘录 (存储状态, 防止 Originator 以外的对象访问) |
| Caretaker | 管理者 (维护备忘录历史, 不能修改备忘录内容) |

**Python 实现 (编辑器撤销)**:

```python
from dataclasses import dataclass

# 备忘录
@dataclass
class EditorMemento:
    text: str
    cursor: int

# 原发器
class Editor:
    def __init__(self):
        self.text = ""
        self.cursor = 0

    def save(self) -> EditorMemento:
        # 创建快照
        return EditorMemento(text=self.text, cursor=self.cursor)

    def restore(self, m: EditorMemento):
        self.text = m.text
        self.cursor = m.cursor

# 管理者 (历史栈)
class History:
    def __init__(self):
        self._stack = []

    def push(self, m):
        self._stack.append(m)

    def pop(self):
        if self._stack:
            return self._stack.pop()
        return None

# 使用
editor = Editor()
history = History()

editor.text = "Hello"
history.push(editor.save())  # 存档

editor.text = "Hello World"  # 改动
editor.restore(history.pop())  # 撤销到 "Hello"
print(editor.text)  # "Hello"
```

**应用**: 编辑器 Ctrl+Z, 数据库事务回滚, Git commit, 游戏存档.

**关键设计**: Memento 应该是**不可变**的 (创建后不能修改), 否则 Originator 恢复时可能拿到不一致的状态.

**追问方向**: 备忘录占用内存大怎么办? 答: 用差异存储 (Command 模式), 只保存增量.

## 20. 状态 (State) ⭐⭐ 中频

**一句话**: 允许对象在内部状态发生改变时改变它的行为, 对象看起来好像修改了它的类.

**datawhale 模式引入** (《大话设计模式》案例):

一天 24 小时, 人在不同时间状态不同 (早上精神 → 中午吃饭 → 下午工作 → 晚上睡觉). 每个状态对应不同行为. 用程序模拟时, 不用一堆 if-else, 而是每个状态一个类.

**类比现实**:
- 红绿灯: 红灯停 / 绿灯行 / 黄灯等 (状态决定行为)
- 电梯: 待机 / 上行 / 下行 / 故障 (不同状态不同操作)
- TCP 连接: LISTEN / ESTABLISHED / FIN_WAIT (协议状态机)
- 工作流: 草稿 → 审核 → 发布 (状态驱动)

**3 个角色**:

| 角色 | 职责 |
| :--- | :--- |
| State | 抽象状态接口 (handle 方法) |
| ConcreteState | 具体状态 (处理 + 转换到下一个状态) |
| Context | 上下文, 持有当前状态引用 |

**Python 实现 (订单)**:

```python
from abc import ABC, abstractmethod

# 抽象状态
class OrderState(ABC):
    def __init__(self, order):
        self.order = order
    @abstractmethod
    def handle(self): pass

# 具体状态
class CreatedState(OrderState):
    def handle(self):
        print("验证订单...")
        self.order.set_state(PaidState(self.order))

class PaidState(OrderState):
    def handle(self):
        print("发货中...")
        self.order.set_state(ShippedState(self.order))

class ShippedState(OrderState):
    def handle(self):
        print("已送达")
        self.order.set_state(CompletedState(self.order))

class CompletedState(OrderState):
    def handle(self):
        print("订单已完成")

# 上下文
class Order:
    def __init__(self):
        self.state = CreatedState(self)

    def set_state(self, state):
        self.state = state

    def process(self):
        self.state.handle()  # 委托给当前状态

# 使用
order = Order()
order.process()  # CreatedState → PaidState (验证后)
order.process()  # PaidState → ShippedState (发货后)
order.process()  # ShippedState → CompletedState (送达后)
```

**应用**: TCP 连接状态机, 订单状态, 工作流, 电梯控制, 游戏角色状态.

**vs 策略**: 状态之间**可自动转换**; 策略**独立**.

**追问方向**: 状态类会有很多 if/else 吗? 答: 状态转换可以封装在状态内部, Context 无需知道转换细节.

## 21. 模板方法 (Template Method) ⭐⭐⭐ 高频

**一句话**: 定义一个操作中的算法的骨架, 而将一些步骤延迟到子类中, 使得子类可以不改变一个算法的结构即可重定义该算法的某些特定步骤.

**datawhale 模式引入** (《大话设计模式》案例):

去银行办业务, 流程是固定的: 取号 → 排队 → 办理 → 评价. 但"办理"的具体内容不同 (存款 / 取款 / 转账). 流程骨架不变 (模板), 具体步骤不同 (子类实现).

**类比现实**:
- 银行办理业务: 取号 → 等候 → 办理 → 评价 (骨架固定, 办理多样)
- Servlet: init → service → destroy (骨架固定, service 多样)
- Spring Bean 生命周期: 实例化 → 注入 → 初始化 → 销毁
- TestCase: setUp → runTest → tearDown

**类比现实**:
- 银行办理业务: 取号 → 等候 → 办理 → 评价 (骨架固定, 办理多样)
- Servlet: init → service → destroy (骨架固定, service 多样)
- Spring Bean 生命周期: 实例化 → 注入 → 初始化 → 销毁
- JUnit TestCase: setUp → runTest → tearDown

**Python 实现 (数据处理)**:

```python
from abc import ABC, abstractmethod

class DataProcessor(ABC):
    # 模板方法 - 算法骨架
    def process(self):
        self.read()
        self.parse()
        self.save()

    @abstractmethod
    def read(self): pass

    @abstractmethod
    def parse(self): pass

    @abstractmethod
    def save(self): pass

# 具体子类: CSV 处理
class CSVProcessor(DataProcessor):
    def read(self):
        print("读 CSV")

    def parse(self):
        print("解析 CSV")

    def save(self):
        print("保存 CSV 到数据库")

# 具体子类: JSON 处理
class JSONProcessor(DataProcessor):
    def read(self):
        print("读 JSON")

    def parse(self):
        print("解析 JSON")

    def save(self):
        print("保存 JSON 到 MongoDB")

# 使用
processor = CSVProcessor()
processor.process()  # 调用模板, 自动按顺序执行
# 输出:
# 读 CSV
# 解析 CSV
# 保存 CSV 到数据库
```

**应用**: Spring JdbcTemplate, Servlet init/service/destroy, JUnit Template, Spring 各种 Template 类.

**与策略模式的区别**:
- 模板方法: **继承**, 父类定骨架
- 策略模式: **组合**, Context 持有算法

**追问方向**: 模板方法违反 OCP 吗? 答: 不违反 (加新算法加新子类, 不改父类). 但违反"组合优于继承".

# 🔥 高频面试题 (10 道)

## Q1: 单例的 5 种实现, 哪种最好?

**答**: 枚举最好. 双重检查 (DCL) 第二, 需 `volatile` 防重排序.
饿汉简单但不能懒加载, 懒汉 synchronized 性能差.

**5 种实现对比**:

| 方式 | 懒加载 | 线程安全 | 性能 | 推荐场景 |
| :--- | :---: | :---: | :---: | :--- |
| 饿汉 (static final) | ❌ | ✅ | 高 | 单例占用少, 启动可加载 |
| 懒汉 (synchronized) | ✅ | ✅ | 低 | 简单场景 (方法同步性能够) |
| 双重检查锁定 (DCL) | ✅ | ✅ | 高 | **生产环境首选** |
| 静态内部类 | ✅ | ✅ | 高 | 优雅写法 |
| 枚举 | ❌ | ✅ | 高 | **Joshua Bloch 推荐**, 防反射/反序列化 |

**datawhale 推荐写法 (DCL)**:

```java
public class Singleton {
    private volatile static Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) instance = new Singleton();
            }
        }
        return instance;
    }
}
```

**关键点**:
- `volatile` 防指令重排序, 保证可见性
- 双重检查避免每次加锁
- 枚举天然防反射破坏

**追问方向**: 反射/反序列化如何破坏单例? 枚举如何防御?

## Q2: 双重检查为什么需要 `volatile`?

**答**: 防**指令重排序** + 保证**内存可见性**.

`new Singleton()` 实际分 3 步:
1. 分配内存 (memory = allocate())
2. 初始化对象 (ctorInstance = mem)
3. 引用赋值 (instance = mem) ← 可能重排序到 2 之前

**没有 volatile 的风险**:

```java
// 线程 A
if (instance == null) {
    synchronized (this) {
        if (instance == null) {
            instance = new Singleton();  // 重排序!
        }
    }
}

// 线程 B
if (instance != null) {       // ← true (instance 已赋值)
    return instance.member;     // ← 但 instance 还没初始化, NPE!
}
```

`volatile` 的双重作用:
- **防止重排序**: 通过内存屏障, 保证 3 步按顺序执行
- **保证可见性**: 写完后立刻对其他线程可见

**追问方向**: volatile 的实现原理 (Lock + 总线嗅探 / MESI 协议)?

## Q3: 工厂方法 vs 抽象工厂?

**答**: 工厂方法生产**一种**产品, 抽象工厂生产**一族**相关产品.

**对比表**:

| 维度 | 工厂方法 | 抽象工厂 |
| :--- | :--- | :--- |
| 粒度 | 单个产品 | 一族产品 |
| 方法数 | 1 个工厂方法 | 多个工厂方法 |
| 复杂度 | 较低 | 较高 |
| 扩展产品 | 加子类 (容易) | 加新族 (容易) |
| 扩展产品族 | 难 | 难 |
| 类数量 | 较少 | 较多 |

**应用对比**:
- **工厂方法**: JDBC `Connection.createStatement()`, Spring `FactoryBean`
- **抽象工厂**: JDK 跨平台 UI 工具包, Spring `ApplicationContext`

**核心区别**: 抽象工厂 = 多个工厂方法的组合, 保证产品族**配套**(Windows 按钮 + Mac 文本框混搭会出问题).

**追问方向**: 抽象工厂的扩展困难如何解决? (回答: 通过接口隔离)

## Q4: 装饰器 vs 代理?

**答**: 

| 维度 | 装饰器 | 代理 |
| :--- | :--- | :--- |
| 目的 | 添加职责 | 控制访问 |
| 接口 | 保持原接口 | 保持原接口 |
| 客户端感知 | **知道**自己在包装 | **不知道**真实对象 |
| 关注 | 增强功能 | 访问保护 |

**代码对比**:

```java
// 装饰器: 客户端知道自己用的是 BufferedInputStream
InputStream in = new BufferedInputStream(
    new FileInputStream("a.txt")
);
// 直接用 in 读, 知道有缓冲

// 代理: 客户端拿到的是接口, 不知道是真实对象还是代理
UserService userService = (UserService) Proxy.newProxyInstance(
    classLoader, interfaces, invocationHandler
);
// 不知道 userService 是不是代理对象
```

**datawhale 解读**: 装饰器是"包装增强", 代理是"中介控制".

**JDK 应用**:
- 装饰器: `BufferedInputStream`, `GZIPInputStream`, `CipherInputStream`
- 代理: JDK 动态代理 (`Proxy.newProxyInstance`), Spring AOP (`JdkDynamicAopProxy`)

**追问方向**: 装饰器可以多层嵌套, 代理可以吗?

## Q5: 适配器 vs 装饰器?

**答**:
- 适配器: **转换接口**, 把 A 适配成 B 接口
- 装饰器: **保持同接口**, 给 A 加功能

| 维度 | 适配器 | 装饰器 |
| :--- | :--- | :--- |
| 接口 | 改变 (A → B) | 不变 (保持 A) |
| 目的 | 兼容性 | 增强功能 |
| 嵌套 | 通常 1 层 | 可多层 |
| 时机 | 解决已有不兼容 | 设计时就扩展 |

**代码对比**:

```java
// 适配器: 把 InputStream 适配成 Reader (接口变了)
Reader r = new InputStreamReader(is, "UTF-8");

// 装饰器: 给 InputStream 加缓冲 (接口不变)
InputStream in = new BufferedInputStream(new FileInputStream("a.txt"));
```

**判断口诀**:
- 适配器: 翻译 (把方言转普通话)
- 装饰器: 包装 (给普通酒加礼盒)

## Q6: 策略 vs 状态?

**答**:

| 维度 | 策略 | 状态 |
| :--- | :--- | :--- |
| 关注 | 怎么做事 (算法) | 处于什么状态 |
| 切换 | 客户端主动换 | 自动转换 |
| 关系 | 互相独立 | 有关联 (状态之间) |
| 例子 | 排序算法 | 订单状态 |

**代码对比**:

```java
// 策略: 主动选排序算法
sortContext.setStrategy(new QuickSort());
sortContext.sort(data);
// 切换到另一个
sortContext.setStrategy(new MergeSort());
sortContext.sort(data);

// 状态: 订单状态自动转换
order.process();  // CreatedState → PaidState → ShippedState → CompletedState
// 不需要手动 setState
```

**记忆口诀**: 策略关注**算法**, 状态关注**行为变化**.

**追问方向**: 订单处理用策略还是状态? 答: 状态, 因为订单流程是状态驱动的.

## Q7: 观察者 vs 发布订阅?

**答**:

| 维度 | 观察者 | 发布订阅 |
| :--- | :--- | :--- |
| 耦合 | Subject 知道 Observer | 通过 Broker 解耦 |
| 调用 | 同步 (直接) | 异步 (通过 Broker) |
| 范围 | 单进程 | 跨进程 |
| 性能 | 高 (直接调用) | 中 (网络/序列化开销) |
| 例子 | DOM 事件 | Kafka, RabbitMQ |

**演进关系**:

```text
观察者模式
   ↓ 加 Broker
发布订阅模式
```

观察者模式加一个中间层 (Broker) 就变成发布订阅. Broker 负责:
- 接收发布者的消息
- 根据订阅规则路由给订阅者
- 订阅者和发布者互不知道对方

**真实例子**:
- **观察者**: JDK `addActionListener`, Spring `ApplicationEvent`
- **发布订阅**: Kafka `Producer/Consumer + Topic`, Redis Pub/Sub

**追问方向**: 观察者模式的同步阻塞问题? (答: 用异步或消息队列)

## Q8: 中介者模式会变成上帝对象吗?

**答**: **会**, 这是中介者模式最大缺点.

**datawhale 观点**: 中介者集中所有交互逻辑, 容易膨胀成"上帝类", 这是它的主要批评.

**上帝对象的风险**:
- 单个类承担过多职责 (违反 SRP)
- 修改影响面广 (一处改全部影响)
- 测试困难 (依赖太多)
- 复用困难 (必须带所有交互逻辑)

**缓解策略**:

| 策略 | 做法 |
| :--- | :--- |
| 不强制使用 | 2 个对象间简单调用不用中介者 |
| 拆分中介者 | 按业务领域拆分为多个 (ChatRoom → ChatMediator + AdminMediator) |
| 限制职责 | 中介者只负责**路由**, 不做具体业务 |
| 用事件替代 | 改用观察者, 中介者变事件总线 |

**判断标准**: 中介者方法数 > 15 个 = 危险信号, 考虑拆分.

## Q9: SOLID 中最易违反哪个?

**答**: **SRP** (单一职责) 是最容易违反的, 因为它的定义最模糊.

**各原则违反频率 (经验)**:

| 原则 | 违反频率 | 危害 | 检测难度 |
| :--- | :---: | :--- | :---: |
| SRP 单一职责 | ⭐⭐⭐⭐⭐ | 中 | 高 (职责边界模糊) |
| OCP 开闭 | ⭐⭐⭐ | 中 | 中 |
| LSP 里氏替换 | ⭐⭐ | 高 | 低 (测试可见) |
| ISP 接口隔离 | ⭐⭐⭐ | 低 | 中 |
| DIP 依赖倒置 | ⭐⭐⭐⭐ | 高 | 低 |

**SRP 难判定的原因**: "职责"没有明确边界. 一个 `User` 类是否同时管业务 + 持久化, 算不算违反 SRP?

**判断口诀**: 这个类有几个**不同的理由**让你修改?
- 1 个理由 → 单职责 ✓
- 多个理由 → 违反 SRP ✗

**实战例子**:

```java
// ❌ 违反 SRP
class User {
    void save() { db.save(this); }     // 理由 1: 存储方式变
    String report() { return ...; }      // 理由 2: 报表格式变
    boolean auth() { return ...; }       // 理由 3: 认证逻辑变
}

// ✅ 符合 SRP
class User { String name; }                       // 数据
class UserRepository { void save(User); }        // 持久化
class UserReporter { String gen(User); }         // 报表
class UserAuth { boolean check(User); }          // 认证
```

## Q10: 什么时候不用模式?

**答**: 模式是经验沉淀, 不是银弹. 以下场景**不应该**用模式:

**不要用模式的 7 种场景**:

| 场景 | 原因 | 替代方案 |
| :--- | :--- | :--- |
| 问题简单 | 模式增加复杂度 | 直接写, 不要过早抽象 |
| 状态 ≤ 2 | 状态模式反而复杂 | if-else |
| 算法只有 1 种 | 策略模式无意义 | 直接调用 |
| 项目初期 | 需求变化快, 模式易过时 | YAGNI 原则 |
| 团队不熟悉 | 维护成本高 | 先培训再引入 |
| 一次性代码 | 不需要复用 | 直接写 |
| 性能关键 | 模式增加间接调用 | 直接优化 |

**判断流程**:

```text
需要用模式吗?
├─ 问题复杂? ──── 否 ──→ 直接写
└─ 是
   ├─ 有 ≥3 个类似情况? ── 否 ──→ 直接写
   └─ 是
      ├─ 将来会扩展? ── 否 ──→ if-else 足够
      └─ 是
         ├─ 团队熟悉? ── 否 ──→ 先培训
         └─ 是 ──→ 使用模式
```

**3 个反问**:
1. 这个模式解决了什么问题?
2. 没有模式会怎么样?
3. 用模式后, 团队能维护吗?

如果答不出 → **不要用模式**.

> 在支付系统中, 我用**策略模式**处理多种支付方式 (支付宝/微信/银联). 最初用 if-else, 加新支付方式要改核心代码. 重构后每种支付是独立 Strategy 类, 加新支付只需加类, 业务代码不动. 同时用工厂方法选择具体策略, 客户端只面向接口编程.

# ⚠️ 常见误区

1. **过度设计**: 3 个对象以下别用模式, 直接 if-else 更清晰
2. **生搬硬套**: 看到 if-else 就想用策略, 但要先看是否真的有多算法切换需求
3. **忘记删代码**: 模式代码占空间, 不需要时及时移除
4. **过度抽象**: 不要为"将来可能扩展"预留太多模式
5. **忽略性能**: 多层装饰器 / 多次反射 / 深拷贝都可能成为性能瓶颈

## 🧠 深入理解: 设计模式的"为什么"

### 为什么需要设计模式?

设计模式不是凭空发明的, 是无数开发者**反复遇到同一类问题**后沉淀出的最佳实践. 理解"为什么", 比死记硬背"是什么"重要 10 倍.

**核心动机 (4 大类)**:

#### 1. 解耦 (Decoupling)

没有模式时, 类之间直接相互引用, 形成紧耦合. 一个类的修改会影响所有依赖它的类. 紧耦合会导致:

第一, 修改代价高: 改一处, 处处改动, 牵一发动全身.
第二, 测试困难: 必须真实创建所有依赖, 无法单独测一个类.
第三, 复用困难: 类绑死在具体实现上, 难以在不同场景复用.

使用模式后, 类依赖抽象接口而非具体实现. 抽象定义"做什么", 具体实现定义"怎么做". 这样换实现不动调用方, 测试容易 mock, 复用灵活.

#### 2. 应对变化 (Change)

软件唯一不变的就是**变化本身**. 设计模式让变化**局部化**, 不影响其他代码. 业务变化时, 只需修改模式的具体实现, 不动使用模式的地方.

比如, 排序算法可能从 QuickSort 换成 MergeSort. 没用模式: 满代码搜索替换. 用策略模式: 只换 Strategy 实现. 加 HeapSort 也只需加类, 不改 Context.

#### 3. 复用经验 (Reuse)

不用模式, 每个项目都重新发明轮子. 有模式, 直接用 JDK / Spring 已实现的标准方案. 模式让经验**跨项目复用**.

#### 4. 沟通语言 (Communication)

设计模式是**开发者之间的共同词汇**. 当你说"这里用策略模式", 团队立刻懂你的设计意图, 不用再解释什么是策略模式. 这种共同语言**极大提升沟通效率**.

### 模式背后的设计原则

每个模式都体现**多个设计原则**. 记住原则比模式本身更重要. SOLID 是面向对象设计的 5 大核心原则.

#### 单一职责原则 (Single Responsibility Principle, SRP)

**核心**: 一个类**只有一个**让它变化的原因. 这个原因就是"职责".

**判断标准**: 这个类有几个"理由"让你修改? 多于 1 个就该拆. 常见违反: 一个 User 类既做持久化, 又生成报表, 又做认证, 又发邮件. 这种"上帝类"难以维护, 因为任何一个职责变化都要改这个类.

**示例**: 把 User 类拆为 User (纯数据) + UserRepository (持久化) + UserReportGenerator (报表) + UserAuthenticator (认证). 每个类单一职责, 修改互不影响.

#### 开闭原则 (Open/Closed Principle, OCP) - 重点

**核心**: 对**扩展**开放, 对**修改**关闭.

**含义**: 加新功能时, 通过**增加新代码**实现, 而不是**修改老代码**. 通过抽象 + 多态实现 OCP.

**违反 OCP 的迹象**: 加新功能要改老代码 (if-else 增加分支). 修正: 用多态代替 if-else, 新功能加新子类.

**意义**: OCP 是面向对象设计的核心目标. 其他原则大多为 OCP 服务.

#### 里氏替换原则 (Liskov Substitution Principle, LSP)

**核心**: 子类必须能**替换**父类, 且不改变程序正确性.

**判断**: 子类是否改变了父类的方法行为 (前置/后置条件, 不变量)?

**违反例子**: Rectangle 有 setWidth / setHeight 方法, Square 继承 Rectangle 但 setWidth 也改变了 height. 这是经典违反. 调用 Rectangle 的代码换成 Square 会出错.

**违反后果**: 子类无法透明替换父类, 多态失效, 必须用 instanceof 检查, 违反 OCP.

#### 接口隔离原则 (Interface Segregation Principle, ISP)

**核心**: 客户端**不依赖**它不需要的方法. 接口要小而专.

**违反例子**: Worker 接口有 work / eat / sleep 方法. Robot 实现 Worker 但不需要 eat. 应该拆分为 Workable + Eatable + Sleepable, Robot 只实现 Workable.

**违反后果**: 接口臃肿, 实现类被迫实现不需要的方法, 客户端依赖过多.

#### 依赖倒置原则 (Dependency Inversion Principle, DIP) - 重点

**核心**: 高层模块**不依赖**低层模块, 二者都依赖**抽象**. 抽象不依赖细节, 细节依赖抽象.

**实现**: 通过抽象接口 + 依赖注入 (DI). Spring IoC 容器就是 DIP 的最佳实践.

**违反后果**: 高层直接 new 低层, 换实现要改高层.

### 模式的"组合使用"

真实项目**很少单独**使用一个模式, 经常是**多个模式组合**.

#### 经典组合 1: MVC 架构

Model View Controller 体现了多种模式组合: Model 是单例 (全局数据) 或工厂方法 (创建数据对象); View 是观察者 (监听 Model 变化自动刷新); Controller 是策略 (不同业务用不同 Controller) + 命令 (处理用户请求封装为对象).

#### 经典组合 2: 跨平台 GUI

抽象工厂创建不同平台的 UI 组件族 (Windows / Mac); 桥接分离抽象 (Component) 与实现 (Peer); 策略选择布局算法 (Flow / Border / Grid); 装饰器添加滚动条 / 边框.

#### 经典组合 3: 数据库访问

工厂创建 Connection; 模板方法定义 JdbcTemplate 查询流程; 策略选择不同数据库驱动 (MySQL / Oracle); 装饰器用连接池包装真实 Connection.

#### 经典组合 4: 游戏框架

状态管理角色状态机 (站立 / 行走 / 跳跃); 观察者让 UI 监听角色状态; 策略实现不同 AI 行为; 命令封装玩家操作支持撤销重做; 备忘录保存游戏进度; 单例管理游戏主循环.

### 模式选择的决策框架

#### 第一步: 这是什么问题类型?

需要创建对象, 选创建型模式. 需要组合类与对象, 选结构型模式. 需要管理对象间的交互与通信, 选行为型模式.

#### 第二步: 更具体的问题?

唯一性需求, 选单例. 创建一族产品, 选抽象工厂. 多参数对象构建, 选建造者. 接口不兼容, 选适配器. 动态给对象添加职责, 选装饰器. 状态变化自动通知, 选观察者. 算法可运行时替换, 选策略. 行为随内部状态改变, 选状态. 多步处理请求, 选责任链. 需要撤销重做, 选命令加备忘录.

#### 第三步: 检查是否真的需要

**反问 3 个问题**判断是否过度设计. 是否有 ≥3 个类似情况? 少于 3 个, 直接写更简单. 将来会扩展吗? 不扩展就用最简单的方案. 团队熟悉这个模式吗? 不熟悉维护成本高.

#### 第四步: 简单方案优先

1 个 if-else 直接写. 3 个 if-else, 可能扩展, 用策略模式. 5+ 个 if-else, 复杂逻辑, 用状态模式. 不要为了模式而模式.

### 💡 实战经验

#### 经验 1: 不要为了用模式而用模式

1 个排序算法, 用策略模式是过度设计, 直接写 sort() 方法就行. 3+ 排序算法, 可运行时切换, 才适合策略模式. **判断标准: 这个模式是否解决了实际问题?**

#### 经验 2: 模式可以渐进引入

V1 直接写 if-else. V2 用多态替换 (简单工厂). V3 用策略模式 (运行时切换). **不要一开始就追求完美设计**.

#### 经验 3: 注意模式的代价

每个模式都有代价. 单例: 全局状态难测试. 工厂方法: 类数量增加. 装饰器: 多层包装调试困难. 代理: 反射性能开销. 观察者: 循环依赖风险. 中介者: 上帝对象风险.

#### 经验 4: 模式代码的可读性

写完模式代码, 问自己 3 个问题: 新人能 5 分钟看懂吗? 加新功能要改哪些文件? 单测容易写吗? 如果都不是, 考虑重构.

### 🛠️ 真实项目模式使用案例

#### 案例 1: Spring Framework (几乎用了所有模式)

Spring 是设计模式的集大成者. 单例: Bean 默认 scope. 工厂方法: BeanFactory.getBean(). 抽象工厂: ApplicationContext. 建造者: BeanDefinitionBuilder. 适配器: HandlerAdapter. 桥接: ResourceLoader. 装饰器: HttpRequestDecorator. 代理: AOP 动态代理. 观察者: ApplicationEvent. 策略: PlatformTransactionManager. 模板方法: JdbcTemplate. 责任链: SecurityFilterChain.

#### 案例 2: JDK 集合框架

Iterator 模式是 JDK 的精髓. ArrayList 和 LinkedList 用同一套遍历代码, 因为它们都实现 Iterable 接口. 把遍历逻辑从集合中分离, 让集合专注于存储, 遍历专注于访问. 这是单一职责原则的体现.

#### 案例 3: React 组件模式 (前端)

高阶组件 (HOC) 是装饰器模式: withAuth(Component) 包装原组件加权限检查. Context API 是中介者模式: useContext 让深层组件获取共享状态, 无需层层传 props.

#### 案例 4: Kafka 生产者-消费者

Kafka = 观察者 + 发布订阅 + 中介者. 生产者是 Subject (发布), 消费者是 Observer (订阅), Kafka 集群是中介者 (Broker). 但 Kafka 把推模式改为拉模式, 让消费者主动控制消费速度.

#### 案例 5: Docker 容器编排

调度器用策略模式 (不同调度策略: FIFO, Round Robin, Resource-aware). 健康检查用职责链 (HTTP / TCP / Exec 检查依次尝试). 日志收集用观察者 (各个组件订阅 LogEvent). 网络配置用桥接 (CNI 插件解耦容器和网络).

### 🎯 常见陷阱

#### 陷阱 1: 单例的"全局状态"

单例持可变状态, 测试困难. 测试 1 的数据被测试 2 看到, 互相影响. 建议: 单例对象应该是无状态的 (只提供方法, 不存数据).

#### 陷阱 2: 装饰器链的内存开销

5 层装饰器: 每次调用方法都要走 5 层. 建议: 控制装饰层数 (一般 ≤ 4 层).

#### 陷阱 3: 观察者的内存泄漏

Subject 持有 Observer 列表. 如果 Observer 没在生命周期结束时反注册, 永远不会被 GC. 解决: 在 dispose / unbind 时反注册.

#### 陷阱 4: 责任链的循环引用

A → B → A (循环), 无限循环. 建议: 仔细设计链, 或加最大跳数限制.

#### 陷阱 5: 模板方法违反 DIP

父类直接依赖子类. 父类应该通过抽象方法, 不直接 new 子类.

### 🧭 模式与架构

设计模式 vs 架构模式 vs 设计原则:

设计模式 范围类/对象级, 例子单例/工厂, 目的解决具体问题, 数量 23 种 (GoF).

架构模式 范围系统级, 例子微服务/事件驱动, 目的整体结构, 数量数十种.

设计原则 范围任何层级, 例子 SOLID/DRY, 目的指导决策, 数量 5-10 个.

设计原则是抽象的指导思想, 架构模式是系统级的应用, 设计模式是代码级的具体实现. 它们层层递进, 指导我们写出更好的代码.
