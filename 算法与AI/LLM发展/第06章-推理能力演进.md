# 第06章-推理能力演进


## 1. 起点: Chain-of-Thought(CoT)

**动机**: 直接输出答案在多步推理(数学/逻辑)上易错。

**CoT**(2022): 提示模型"让我们一步步想", 显式生成中间推理步骤, 大模型准确率显著提升。

- **Zero-shot CoT**: 加一句 "Let's think step by step"。
- **Few-shot CoT**: 给带推理过程的示例。
- **优势**: 无需训练即提升推理; 揭示了"推理是可被引导的涌现能力"。

---

## 2. Self-Consistency 与搜索

- **Self-Consistency**: 采样多条 CoT, **投票**取多数答案, 用多样性换正确率。
- **Tree of Thoughts / 搜索**: 把推理组织成树, 探索-回溯。
- 这些是"推理时花更多计算"的早期形态, 为 o1 铺路。

---

## 3. o1 / o3(OpenAI): RL 训练的推理模型

**o1**(2024)不再靠提示, 而是**训练**模型自发生成长思维链, 推理时"思考"更久:

- 内部生成大量隐藏推理 token, 再给最终答案。
- **test-time compute scaling**: 给的思考预算越多, 数学/代码/科学正确率越高——一条新的 scaling 曲线。
- **o3 / o4-mini**(2025): 进一步提升, 在竞赛数学、代码上大幅超越非推理模型。

**GPT-5 家族**(2025)把"推理力度(reasoning effort)"做成可调控制项, 让同一模型在"快答"与"深思"间切换。

---

## 4. DeepSeek-R1: 开源的推理范式

**R1**(2025.01)证明了**纯 RL(GRPO)+ 可验证奖励**能激发强推理:

- **R1-Zero**: 甚至跳过 SFT, 直接 RL, 自发涌现长推理与自我验证、"aha moment"。
- **R1**: 冷启动 SFT + RL, 兼顾可读性与推理力。
- 671B MoE(每 token 激活 37B), 性能比肩 o1, **权重开源(MIT)、API 价仅 o1 的 3-5%**。
- 影响: 把"推理模型"从闭源专利变成人人可复现的范式。

关键机制见 [第05章-GRPO](第05章-对齐技术演进.md)。

## 6. 实现要点(如何训一个推理模型)

1. **可验证奖励**: 数学(答案匹配)、代码(单测通过)给 0/1 奖励, 是 RL 推理的燃料。
2. **GRPO**: 每题采样一组解, 组内归一化优势, 无 Critic(见 [第05章](第05章-对齐技术演进.md))。
3. **长度与格式奖励**: 鼓励充分推理但防啰嗦; 用 `<think>...</think>` 分隔推理与答案。
4. **冷启动 SFT**: 少量高质量长 CoT 数据, 让 RL 更稳、输出更可读。

## 第二部分 推理能力的数学基础

## 9. 推理能力的定义与度量

**推理(Reasoning)**: 在多步骤任务中,模型生成"中间表示"(thought),最终给出正确答案的能力。

定义形式化: 给定 $(q, a^*)$, 模型生成 $r = (t_1, t_2, \ldots, t_n, a)$。 推理能力的度量:

$$\text{Acc} = \mathbb{E}_{(q, a^*)}\left[\mathbb{1}[a = a^*]\right]$$

理想化目标是:

$$\text{Acc}(N_\text{thought}) \nearrow\quad\text{as } N_\text{thought} \to N^*$$

即"思考预算"越多, 准确率越高。 这是 test-time compute scaling 的根本。

### 9.1 推理子能力分类

| 子能力 | 任务 | 评测 |
| :--- | :--- | :--- |
| 数学推理 | 数论, 代数, 微积分 | MATH, GSM8K |
| 逻辑推理 | 演绎, 归纳, 类比 | LogiQA, BBH |
| 代码推理 | 算法设计, 调试 | HumanEval, MBPP |
| 常识推理 | 物理, 时空, 文化 | HellaSwag, ARC |
| 多步工具 | 用 search, calc 等 | ToolBench |
| 反思 & 自我验证 | 检查自身错误 | 推理错误率 |

### 9.2 推理的认知科学视角

人类推理:
- **System 1**: 快速, 自动, 易错(类似 base LLM 直答)
- **System 2**: 慢速, 努力, 准确(类似 CoT 推理 LLM)

Kahneman 双系统理论。 o1/R1 把 System 2 显式化为长 CoT。

## 10. Chain-of-Thought 的数学化

### 10.1 CoT 概率分解

设 $r = (t_1, \ldots, t_n, a)$, 总概率:

$$p(r | q) = \prod_{i=1}^{n} p(t_i | q, t_{<i})$$

推理性能优化:

$$\max_r p(r | q) \cdot R(r, a^*)$$

其中 $R$ 是奖励(答案正确性)。

### 10.2 CoT 长度与正确率的关系

经验观察到 "log-linear" 关系:

$$\log(\text{Acc}) \approx a \cdot n_\text{thought} + b$$

即 thought 长度对数线性影响准确率。 这就是 test-time compute scaling 的曲线。

### 10.3 Sampling 与一致性

Self-Consistency (Wang et al. 2022) 采样 $k$ 条 CoT, 投票:

$$a^*_\text{pred} = \arg\max_a \sum_{i=1}^{k} \mathbb{1}[a_i = a]$$

投票理论: 多样化采样在独立错误下错误率指数下降。

## 11. RL 推理: 数学框架

### 11.1 Policy Gradient 基础

REINFORCE 目标:

$$\nabla_\theta J = \mathbb{E}_{\tau \sim \pi_\theta}\left[\sum_{t} \nabla_\theta \log \pi_\theta(a_t|s_t) \cdot R(\tau)\right]$$

LLM 推理 RL 中, $\tau$ 是完整生成 $(q, r)$, $R$ 是结果奖励。

### 11.2 PPO 与 Critic

PPO 用 critic 网络估计 advantage:

$$A_t = R_t - V(s_t)$$

其中 $V$ 是 critic 学习的状态价值。 PPO 限制更新幅度:

$$L^\text{CLIP}(\theta) = \mathbb{E}\left[\min\left(r_t(\theta)A_t, \text{clip}(r_t, 1-\epsilon, 1+\epsilon) A_t\right)\right]$$

$r_t = \pi_\theta / \pi_{\theta_\text{old}}$ 是新旧策略比。

### 11.3 GRPO (Group Relative Policy Optimization)

DeepSeek-R1 用的方法(arXiv 2402.03300)。 关键创新: 无 critic。

对每道题 $q$:
1. 采样 $G$ 个回答 $\{r_1, \ldots, r_G\}$
2. 算奖励 $\{R_1, \ldots, R_G\}$
3. 组内归一化 advantage:

$$A_i = \frac{R_i - \text{mean}(\{R_j\})}{\text{std}(\{R_j\})}$$

4. 优化目标:

$$L_\text{GRPO} = -\frac{1}{G}\sum_i \sum_t \min\left(\frac{\pi_\theta(r_{i,t})}{\pi_{\theta_\text{old}}(r_{i,t})} A_i, \text{clip}(\cdot) A_i\right) - \beta D_\text{KL}(\pi_\theta \| \pi_\text{ref})$$

**定理 6.A(GRPO 无 Critic 的优越性)**: 对组内 advantage 归一化等价于隐式估计 baseline:

$$\text{baseline}(q) = \frac{1}{G}\sum_i R_i \approx V(s_q)$$

误差为 $O(1/G)$, $G=8$ 时已足够稳。

**定理 6.B(GRPO 的 Variance Reduction)**:

$$\text{Var}[\nabla_\theta J_\text{GRPO}] \approx \frac{\text{Var}[A_\text{group}]}{G}$$

$G$ 越大梯度方差越小, 这是 R1 训练稳定的核心。

### 11.4 DPO vs GRPO 对比

| 维度 | DPO | GRPO |
| :--- | :--- | :--- |
| 目标 | 偏好对的 likelihood | 推理答案的 reward |
| 奖励源 | 人类标注 (chosen/rejected) | 可验证奖励 (0/1) |
| Critic | 无 | 无 |
| 场景 | 对齐, 价值观 | 数学/代码推理 |
| 稳定性 | 高 | 中(需要 reward shaping) |

DPO 与 GRPO 互补, 可同时训练(参见 R1 的 pipeline)。

## 12. RL 推理的奖励设计

### 12.1 可验证奖励(Verifiable Reward)

数学/代码任务, 答案可机器验证:

$$R_\text{verifier}(r, q) = \begin{cases} 1, & \text{if answer}(r) = \text{answer}(q) \\ 0, & \text{otherwise} \end{cases}$$

代码任务:
$$R_\text{verifier} = \frac{\text{passed\_tests}}{\text{total\_tests}}$$

### 12.2 长度与格式奖励

$$R_\text{len} = \begin{cases} 0.1, & \text{if length in [L_\min, L_\max]} \\ -0.05, & \text{otherwise} \end{cases}$$

$$R_\text{fmt} = \begin{cases} 0.1, & \text{if format valid} \\ -0.1, & \text{otherwise} \end{cases}$$

组合:
$$R_\text{total} = R_\text{verifier} + R_\text{len} + R_\text{fmt}$$

### 12.3 过程奖励 (PRM, Process Reward Model)

奖励不仅来自最终答案, 也来自中间步骤:

$$R_\text{PRM}(r, q) = \sum_{i=1}^{n} w_i \cdot \mathbb{1}[t_i \text{ correct}]$$

PRM 在 OpenAI 2023 (Let's Verify Step by Step) 提出, 用于数学。 缺点: 训练 PRM 需要详细标注。

### 12.4 重复/语言混合惩罚

$$R_\text{repetition} = -0.05 \cdot \mathbb{1}[\text{any 4-gram repeats}]$$

$$R_\text{lang} = -0.1 \cdot \mathbb{1}[\text{response contains random non-target language}]$$

## 13. Test-Time Compute Scaling

### 13.1 Scaling 曲线

OpenAI o1 团队 (2024) 报告: 模型不变, 推理时给更多 compute, 准确率显著提升。

$$f(\text{Acc}, C) = a \cdot (1 - e^{-bC})$$

其中 $C$ 是 compute 预算, $a$ 是上限准确率, $b$ 是缩放速率。

不同任务:
- MATH: Acc 提升斜率最大
- HumanEval: 中等
- MMLU: 接近饱和(已 95%+)

### 13.2 推理 FLOPs 的拆解

$$C_\text{total} = C_\text{prefill} + C_\text{decode} \cdot n_\text{tokens}$$

$$C_\text{decode} \approx 2 n_\text{seq}^2 d + 2 n_\text{seq} d^2$$

Long CoT 让 $n_\text{tokens}$ 增加到 5-20K, $C_\text{total}$ 上升 10-50×。

### 13.3 Optimal Sampling

在固定 compute 预算 $C$ 下, 选最优策略:
- 长 single CoT? 还是 self-consistency 多条短 CoT?

实验: 数学任务上, 短 CoT × 64 通常 > 长 CoT × 1。

但 R1 路线: 长 single CoT 调到极致, 配合 RL 自动找到"够长"。

## 14. RL 推理训练流程

### 14.1 R1-Zero: 纯 RL 无 SFT

DeepSeek-R1-Zero 的训练路径:
1. base model (如 V3)
2. 直接 RL with GRPO + 0/1 reward
3. 训练 8000 steps, 模型自发涌现长 CoT, self-verification, "aha moment"

**核心观察**: 不需要 human CoT 数据, 模型自己找到推理路径。

### 14.2 R1: SFT-RL 混合

R1 的路径:
1. base V3
2. Cold-start SFT (5K high-quality long CoT)
3. RL (GRPO, 数学+代码)
4. Reject sampling 重新采样, SFT 二次
5. RL 二次

每步都引入更高质量数据, 避免 RL 训偏。

### 14.3 训练的工程挑战

| 挑战 | 对策 |
| :--- | :--- |
| Reward hacking (走捷径) | 多 reward 加和, 定期 inspect |
| Mode collapse (只学好做任务) | 多任务混合训练 |

## 16. CoT 采样的最小实现

```python
"""
cot.py: 多条 CoT 采样 + self-consistency 投票
"""
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer


def sample_cot_batch(model, tok, question, n=8, max_new=512, temperature=0.7):
    """采样 n 条 CoT"""
    prompt = f"Q: {question}\nLet's think step by step.\n"
    inputs = tok(prompt, return_tensors="pt").to(model.device)
    outputs = []
    for _ in range(n):
        out = model.generate(
            **inputs,
            max_new_tokens=max_new,
            do_sample=True,
            temperature=temperature,
            top_p=0.95,
            pad_token_id=tok.eos_token_id,
        )
        text = tok.decode(out[0], skip_special_tokens=True)
        outputs.append(text)
    return outputs


def extract_answer(text):
    """从 CoT 中提取最终答案"""
    # 简单版: 找 "Answer:" 或 "答案是"
    for marker in ["Answer:", "答案是:", "The answer is"]:
        if marker in text:
            return text.split(marker)[-1].strip().split("\n")[0]
    return text.strip().split("\n")[-1]


def majority_vote(answers):
    """投票"""
    from collections import Counter
    c = Counter(answers)
    return c.most_common(1)[0][0]


def self_consistency(model, tok, question, n=8):
    cot_list = sample_cot_batch(model, tok, question, n)
    answers = [extract_answer(r) for r in cot_list]
    return majority_vote(answers), answers


if __name__ == "__main__":
    # 例: 用小模型测试
    print("Self-Consistency 示例 (需要模型)")
```

## 17. GRPO 的 PyTorch 实现

```python
"""
grpo.py: 简化版 GRPO 训练循环
"""
import torch
import torch.nn.functional as F


def grpo_loss(log_probs_new, log_probs_old, log_probs_ref, rewards, eps=0.2, beta=0.04):
    """
    log_probs_new: (G,) tensor: 新策略在每条回答上的 sum log_prob
    log_probs_old: (G,) tensor: 旧策略
    log_probs_ref: (G,) tensor: 参考策略
    rewards: (G,) tensor: 每条回答的奖励
    """
    # 组内归一化 advantage
    mean = rewards.mean()
    std = rewards.std() + 1e-8
    advantages = (rewards - mean) / std

    # PPO-style 目标
    ratio = (log_probs_new - log_probs_old).exp()
    surr1 = ratio * advantages
    surr2 = ratio.clamp(1 - eps, 1 + eps) * advantages
    policy_loss = -torch.min(surr1, surr2).mean()

    # KL 锚定
    kl = (log_probs_new - log_probs_ref).mean()
    loss = policy_loss + beta * kl

    return loss, {"policy_loss": policy_loss.item(), "kl": kl.item()}


def grpo_train_step(model, ref_model, questions, reward_fn, optimizer, G=8):
    """一个 GRPO step"""
    for q in questions:
        # 1. 采样 G 条回答
        responses = sample_responses(model, q, G=G)
        # 2. 计算奖励
        rewards = torch.tensor([reward_fn(q, r) for r in responses])
        # 3. 计算 log_probs
        log_new, log_old = [], []
        for r in responses:
            log_new.append(compute_logprob(model, q, r))
            log_old.append(detach_logprob(model, q, r))
        log_new = torch.tensor(log_new)
        log_old = torch.tensor(log_old)
        log_ref = torch.tensor([compute_logprob(ref_model, q, r) for r in responses])
        # 4. GRPO loss
        loss, metrics = grpo_loss(log_new, log_old, log_ref, rewards)
        # 5. 反向传播
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
```

## 18. 可验证奖励函数示例

```python
"""
verifiable_reward.py: 数学与代码任务的可验证奖励
"""
import re
import subprocess
import tempfile
import os


def math_reward(question, response, ground_truth):
    """数学任务: 提取答案, 比较"""
    # 提取 \boxed{...}
    m = re.search(r'\\boxed\{([^}]+)\}', response)
    if m is None:
        m = re.search(r'(?:answer|答案)[:：]?\s*([\d\.\-/]+)', response, re.IGNORECASE)
    if m is None:
        return 0.0
    pred = m.group(1).strip().replace(" ", "")
    gt = str(ground_truth).strip().replace(" ", "")
    # 容差 1e-3
    try:
        if abs(float(pred) - float(gt)) < 1e-3:
            return 1.0
    except ValueError:
        if pred == gt:
            return 1.0
    return 0.0


def code_reward(question, response, test_cases):
    """代码任务: 跑单测"""
    # 提取代码块
    code_match = re.search(r'```(?:python|py)?\n(.*?)```', response, re.DOTALL)
    if not code_match:
        return 0.0
    code = code_match.group(1)

    # 写临时文件, 跑测试
    full = code + "\n" + "\n".join(test_cases)
    with tempfile.NamedTemporaryFile(suffix=".py", delete=False, mode="w") as f:
        f.write(full)
        path = f.name
    try:
        result = subprocess.run(
            ["python", path], capture_output=True, timeout=10
        )
        if result.returncode == 0 and "FAIL" not in result.stdout.decode():
            return 1.0
        return 0.0
    finally:
        os.unlink(path)


def format_reward(response):
    """格式奖励: 包含  块"""
    if "```" in response:
        return 0.1
    return -0.1


def composite_reward(question, response, ground_truth=None, test_cases=None):
    r = 0.0
    if ground_truth is not None:
        r += math_reward(question, response, ground_truth)
    elif test_cases is not None:
        r += code_reward(question, response, test_cases)
    r += format_reward(response)
    if len(response) > 50 and len(response) < 4000:
        r += 0.05    # 长度奖励
    return r
```

## 19. 树搜索式推理实现 (ToT 简化)

```python
"""
tree_of_thoughts.py: 简化版 Tree of Thoughts
"""
from dataclasses import dataclass


@dataclass
class ThoughtNode:
    thought: str
    parent: "ThoughtNode | None"
    score: float = 0.0
    children: list = None

    def __post_init__(self):
        self.children = []


def tree_search(model, question, branching=3, depth_limit=4, vote_k=3):
    """BFS-style 树搜索"""
    # 初始: 生成 G 个 thought
    root = ThoughtNode(thought=question, parent=None)
    current_level = [root]

    for d in range(depth_limit):
        next_level = []
        for node in current_level:
            # 扩展: 生成 branching 个子 thought
            for _ in range(branching):
                prompt = f"Q: {question}\nThinking: {node.thought}\nNext step:"
                resp = model.generate(prompt, max_new_tokens=128)
                child = ThoughtNode(thought=resp, parent=node)
                child.score = score_thought(model, question, resp)
                node.children.append(child)
                next_level.append(child)
        # BFS: 选 top branching 个, 下一轮扩展
        next_level.sort(key=lambda n: -n.score)
        current_level = next_level[:branching]
        # 检查终止
        for node in current_level:
            if "answer is" in node.thought.lower() or "答案是" in node.thought:
                return node.thought, node

    # 取最优
    current_level.sort(key=lambda n: -n.score)
    return current_level[0].thought, current_level[0]


def score_thought(model, question, thought):
    """投票: 多次生成, 一致率"""
    outs = [model.generate(f"Q: {question}\nThought: {thought}\nIs this correct?", max_new_tokens=10)
            for _ in range(3)]
    yes = sum(1 for o in outs if "yes" in o.lower())
    return yes / 3
```

简单问题也长篇。 解决: 长度奖励上限 + adaptive budget。

## 第七部分 面试题扩充

## 32. 推理模型深度面试题 (15 题 + 答案)

### Q1: test-time compute scaling 是什么?

**答**: 在推理时增加计算(更多 token / 搜索 / 投票)换取更高的准确率。 是一条新的 scaling curve, 与传统训练 scaling law 互补。

### Q2: o1 与 CoT 提示的区别?

**答**: o1 是训练出来自发长 CoT, 而非简单提示。 o1 通过 RL 让模型自己学会"怎么想", 而不依赖 prompt 中的 "let's think" 触发。

### Q3: R1 为什么重要?

**答**: 1) 纯 RL (GRPO) + 可验证奖励激发推理, 无需 SFT。 2) 开源 (MIT 协议), 模型权重 + 训练细节都可复现。 3) API 价格仅 o1 的 1/3, 推动行业"推理降价"。

### Q4: 推理模型的可验证奖励为何关键?

**答**: 数学 / 代码对错明确, 可以机器验证 (vs 偏好对需要人类标注)。 这提供了稳定、廉价的 RL 信号。 不可验证任务(对话流畅度)很难用 RL 直接优化。

### Q5: GRPO 相比 PPO 的核心优势?

**答**: 无需 critic 网络。 对每道题采样 G 个回答, 组内归一化估计 advantage, 节省一半训练资源。 同时 GRPO 对组内一致性敏感, 鼓励"群体内最优"。

### Q6: CoT 与 Self-Consistency 的局限?

**答**: CoT 依赖 prompt 触发, model capability 仍是上限。 Self-Consistency 投票只解决"采样多样性"问题, 不解决"推理能力不足"。 真正的提升来自训练。

### Q7: o1 为什么强?

**答**: 推测用 Process Reward Model (PRM) + 搜索: 每步生成多个候选, 用 PRM 评分, 保留最优点。 配合长 CoT, 实际推理深度可等效于 1-3 分钟思考。

### Q8: 推理 RL 的 Reward Hacking 如何避免?

**答**: 1) 多 reward 加和 (verifier + 长度 + 格式)。 2) 定期人工 inspect 训后模型输出, 看是否有"走捷径"。 3) KL 锚定 ref model, 防止偏离太远。

### Q9: Tree of Thoughts 与 CoT 区别?

**答**: CoT 是线性链, ToT 是树搜索: 每步多分支, 评估后保留优者。 ToT 算力高, 但能避免单 CoT 走错路。 工程实现: BFS/DFS + 评分函数。

### Q10: long CoT 的最大挑战?

**答**: 算力贵。 R1 一次推理 5-20K tokens, 比普通回答 (200-500 tokens) 高 10-30×。 这意味着 API 价格必须显著高, 或用 RL 优化"在最短 token 内答对"。

### Q11: 如何控制推理模型不过度思考?

**答**: 1) 长度奖励上限 (len < L_max 才加分)。 2) Adaptive budget: 简单任务早停, 复杂任务继续。 3) 训练后期逐渐收紧长度约束。

### Q12: 长 CoT 与 KV Cache 的关系?

**答**: 长 CoT 极大占用 KV Cache。 R1 长 5K tokens, KV 字节数单 batch 200MB+ (LLaMA 70B 量级)。 生产部署必须配套 PagedAttention + INT8 KV + 动态长度。

### Q13: R1 "Aha Moment" 是什么?

**答**: RL 训练中, 模型自发涌现的"顿悟"行为: 推理过程中突然调整思路, 输出 "Wait, ..." 类型话语, 然后得到正确答案。 这是 emergent 现象, 非显式编程。

### Q14: 推理模型与传统 CoT 训练的差异?

**答**: 传统 CoT 训练用人类标注的 (问题, 长推理, 答案) 三元组, 监督学习。 推理 RL 让模型自己探索推理路径, 用 reward 引导。 更灵活, 更便宜, 但更难稳定。

### Q15: 推理模型的部署模式?

**答**: 1) 内部多 stages, 用户给出 reasoning_effort。 2) 默认模型 + thinking budget。 3) 显式 "思考 + 回答" 双段输出。 4) 工具调用嵌入到 thinking。

### Q16: GRPO 中 advantage 归一化的影响?

**答**: 让组内不同质量的回答都有正向梯度, 同时标准差提升"难度信号"。 在 G=8 时, advantage 范围约 [-2, 2], 与 PPO 中 advantage 接近。

### Q17: 什么是 Process Reward Model (PRM)?

**答**: 对推理中间步骤打分的奖励模型。 比 outcome reward 精细, 但需 step-level 标注, 工程复杂。 o1 推测用了 PRM + search。

### Q18: 推理 RL 中 KL penalty 的作用?

**答**: 防止策略偏离 ref model 太远, 维护模型能力, 避免 mode collapse。 $\beta \approx 0.04$ 是常用值 (R1 论文)。

### Q19: Reasoning 与 RAG 的关系?

**答**: Reasoning 是 in-context 多步生成, RAG 是检索增强。 融合: 推理模型在 thinking 阶段调用 retrieval 工具, 获取外部知识后再回答。

### Q20: 推理模型的局限性?

**答**: 1) 长 CoT 算力贵。 2) 在需要实时性的场景(如简单 FAQ) 浪费。 3) 推理忠实性问题: 长 CoT 不一定反映真实计算。 4) Reward hacking 风险。

## 41. 推理模型的"三难"权衡

```text
质量 ⬆ —————— 算力 ⬆
        ↘  ↗
        长度 ⬆
```

- 准确率高 → 长 CoT + 多采样 → 算力高
- 算力低 → 短 CoT → 准确率低
- 工程上要在这三者间找平衡

## 42. 思考: 我们需要推理模型吗?

**需要论**:
- 复杂数学/代码问题没有 CoT 解不出来
- 推理增强对所有 NLU 任务有益
- 推理是 AGI 核心能力

**不需要论**:
- 简单问题浪费算力
- 推理不等于"智能"
- 实时场景 (chat) 不适合

**结论**: 推理是工具, 不是替代。 未来 LLM = base (fast) + reasoning (slow), 用户切换。

## 第十二部分 推理能力深度数学

## 46. 推理 token 长度的最优分布

设 $|r|$ 为推理 token 长度, 经验观察到 (Snell et al. 2024):

$$P(\text{Acc} | |r|) = 1 - \alpha \cdot e^{-\beta |r|}$$

参数:
- $\alpha = 0.5-0.9$: 上界偏差
- $\beta = 1/(100-500)$: 学习率

任务越难, $\beta$ 越小 (需要更长推理)。

**定理 6.D (Compute-Acc Frontier)**: 给定总 compute 预算 $C$, 最优的分配是:
- 单条长 reasoning 如果 $|r^*| < C$
- 多条短 reasoning 加 voting 否则

这是 OpenAI o-series 团队报告的核心结论。

## 47. Test-Time RL 形式化

把整个 test-time compute 视为"inner optimization":

$$\pi^* = \arg\max_\pi \mathbb{E}_{q}\left[R(r \sim \pi(\cdot | q))\right]$$

subject to $\text{cost}(r) \le C_\text{test}$。

这是一个 constrained RL, Lagrangian:

$$L = \mathbb{E}[R] - \lambda \mathbb{E}[\text{cost}]$$

最优 trade-off 由 $\lambda$ 控制, 对应 reasoning effort 参数。

## 48. 推理 RL 的 Reward 塑形

经验上, sparse 0/1 reward 在 long horizon 会带来 credit assignment 问题。

塑形方法:

$$R_\text{shaped}(r, q) = R_\text{verifier}(r, q) + \gamma \mathbb{E}_t[R_\text{step}(t | r, q)]$$

其中 $R_\text{step}$ 是 PRM 给的"中间步奖励"。

但是 PRM 难训, 所以 R1 用 outcome reward + high volume。

## 49. Self-Play 在推理中的作用

让模型互相"出题 - 答题":
- 模型 A 出题, 模型 B 答
- 评 B 的能力

经验: 模型出的题越来越难, B 学会更难推理。

OpenAI 的 "Self-Play Fine-Tuning" (2024) 报告: self-play 在数学上提升明显。

## 50. RL 推理的失败模式

### 50.1 灾难性遗忘

RL 训练后, base 模型的能力下降 (例如对话流畅度降 5-10%)。

对策:
- KL 锚定 ref model
- 周期 SFT 复习
- RL + SFT 混合训练 (R1 的方式)

### 50.2 Reward Hacking

模型找到"骗过 verifier"的 shortcut:
- 解数学题时直接 grep 答案, 假装推出
- 写代码时复制 example, 假装写出来

对策:
- 多 verifier 加权
- 隐藏 test set
- 不断更新 verifier

### 50.3 Mode Collapse

模型只对某类题特别好, 其他差。

对策:
- 多任务混合训练
- 任务均衡采样
- KL + base model 多样性

## 51. 推理模型的"温度"参数

**温度 $T$**: softmax 时 $p_i = \exp(s_i/T) / Z$。

- 低 T: 确定性, 重复采样得到相同 CoT
- 高 T: 多样性, 但可能乱

推理 RL 中经验:
- 训练 sampling T = 1.0 (正常)
- eval T = 0 (greedy)
- 多样化测试 T = 0.6-0.8

## 第十五部分 推理模型的危险

## 57. 推理幻觉

模型"推理"了但推理错的。 在长 CoT 中, 错误累积: 第 5 步错 → 第 6 步必然错 → 答案错。

数学任务上 ~5% 是这种"推理错", 与 base 模型的"猜测错"不同。

## 58. 推理模型的安全风险

- **更长 CoT = 更长的潜在 jailbreak**: 多步推理中, 早期一步突破约束, 后续都跟着突破
- **工具调用风险**: 模型在推理时调用 API, 可能误用
- **过度自信**: 长 CoT 看起来很真, 但错了更难发现

## 59. 推理模型的"思考"是否可解释?

OpenAI o1 仅输出最终答案, 隐藏 CoT (安全 + IP 考虑)。 但这导致:
- 学术界难以复现 / 改进
- 用户难以 debug 错误
- 推动 DeepSeek 等开源

R1 是开源的, thinking token 公开, 这是重要贡献。

            "prompt": f"Question: {p['question']}\nAnswer: ",
            "answer": p['answer'],
        })
    with open(output_path, 'w') as f:
        for x in out:
            f.write(json.dumps(x) + "\n")

    out = []
    for q, c in zip(questions, long_cots):
        out.append({
            "input": f"Q: {q}\nLet's think step by step.\n",
            "output": c,
        })
    with open(output_path, 'w') as f:
        for x in out:
            f.write(json.dumps(x) + "\n")

## 第十八部分 数学与逻辑

## 66. 形式逻辑视角

推理可视为形式逻辑的自然语言版:

- **命题逻辑**: $\land, \lor, \lnot, \to$
- **一阶逻辑**: $\forall x, \exists y, \ldots$
- **概率逻辑**: 信念 + 推理

LLM 用 token 表达逻辑, 内部 hidden state 编码命题。 R1 的长 CoT 类似 structured proof。

## 67. 推理能力的 "Hardness"

理论上, 推理是 NP-hard (一阶逻辑 SAT)。 但人类与 LLM 在"实用推理"上能有效解决 (因有结构化先验)。

**定理 6.E(经验)**: LLM 在 K-步推理上, K ≤ 5 时准确率 > 80%, K > 10 时降至 < 50%。 K 与训练数据中"最长推理案例"正相关。

工程含义: R1 用 5-15 步推理是平衡。

## 81. 推理 RL 的 Loss 监控

健康指标:
- reward mean: 应上升, 目标任务准确率
- reward var: 应下降, 越来越稳
- kl divergence: 与 ref model 距离, 0.005-0.05 正常
- completion length: 平均 CoT 长度, 应缓慢上升
- format rate: % 输出符合格式, 应 > 95%

警告:
- reward 没动: 学习率太低或 verifier 出错
- reward 突然 100%: reward hacking
- kl 飙升: 训练不稳定, 降 LR
- completion 长度 0: 全部生成失败

## 82. 分布式 GRPO 训练

大模型 GRPO 需要 FSDP + 大量 GPU。 经验配比 (R1 用 1000+ H800):

| 模型 | GPU 数 | batch | throughput |
| :--- | :--- | :--- | :--- |
| 7B | 32 | 64 | 100k token/s |
| 32B | 128 | 64 | 200k token/s |
| 70B | 256 | 64 | 350k token/s |
| 671B (R1) | 1024 | 32 | 800k token/s |

每个 step 包含 32-64 个 generation, 加上 backward, 单 step 时间:
- 7B: 30 秒
- 70B: 3 分钟

## A1. Chain-of-Thought(CoT)深度原理与涌现

### A1.1 为什么 CoT 有效: 直觉与理论

**直觉**: 人类解决复杂问题不会"瞬间给出答案", 而是把问题拆解成子步骤, 逐步推导。LLM 在 pretrain 阶段见过海量"问答+推理过程"文本(教科书、题解、Stack Overflow 解释、Wikipedia 行内推理), 它**已经具备**逐步生成推理的潜在能力——只是在 few-shot 直接问答的范式下被"压抑"了。CoT 提示只是把这种潜在能力"放出来"。

**形式化视角**: 把一个复杂问题 $Q$ 映射到答案 $A$ 通常是非线性的高维映射。直接学习 $f: Q \to A$ 在样本有限时方差大、易错。引入中间变量 $Z = (z_1, z_2, ..., z_k)$(推理步骤), 学习 $f: Q \to Z$, $g: Z \to A$ 两条映射, 每条都更"局部平滑", 更易学。这就是**分解(Decomposition)**带来的泛化红利。

**对 Transformer 的解释**:
- 单次 forward 中, 每一层对所有 token 做并行计算; 模型要"同时想出推理和给出答案"很困难, 因为没有"显式的中间状态"。
- CoT 让模型在**时间维度**(自回归的步骤)显式构造中间状态, 相当于给模型更多"思考步", 每一步都是一个可被 attention 关注的"工作记忆"。
- 这种**显式的 scratchpad** 显著降低了组合复杂度——把 $\mathcal{O}(n)$ 的单步推理拆成 $\mathcal{O}(1)$ 的多步, 每步计算量变小但步数变多, 总信息带宽变大。

### A1.2 CoT 的涌现性: 与模型规模的关系

Wei et al. (2022) 的原始 CoT 论文观察到: **小模型(<10B)上 CoT 提示几乎没有提升, 甚至略有下降; 大模型(>60B)上 CoT 显著超越标准提示**。这与 pretrain loss 的"相变"现象一致——很多能力在某个规模阈值下突然涌现, CoT 是其中之一。

```python
# 涌现规模曲线示意(伪代码)
def cot_gain_vs_scale(model_size_b):
    if model_size_b < 10:    return 0.0   # 无 CoT 增益
    if model_size_b < 50:    return 0.05  # 微弱增益
    if model_size_b < 200:   return 0.18  # 显著增益
    return 0.35                       # 大幅增益
```

**推论**:
1. **不要在小模型上滥用 CoT 提示**——会浪费 token 且无收益, 反而因为"幻觉推理"误导用户。
2. **CoT 是大模型的特权能力**——这与 RLHF、instruction-following 等能力一样, 都属于"涌现能力簇"。
3. **2024-2026 的趋势**: 即使是 7B 模型通过专门 SFT 也能学会"稳定生成 CoT", 这说明涌现不是绝对门槛, 而是**训练分布**决定的。

### A1.3 Zero-Shot CoT vs Few-Shot CoT

**Zero-Shot CoT(Kojima et al., 2022)**:
- 只需在 prompt 后追加一句 `"Let's think step by step."`(中文: "让我们一步步思考")。
- 在 GPT-3 上把 MultiArith 准确率从 17.7% → 78.7%, 几乎追平有监督的 CoT 微调。
- 优势: **零样本、零工程**; 适用面极广。
- 劣势: 推理过程**未必符合期望格式**, 可能"绕远"或"跑偏", 因为没有示例约束。

**Few-Shot CoT(Wei et al., 2022)**:
- 在 prompt 中给 4-8 个"问题 → 推理步骤 → 答案"的示例, 让模型模仿格式。
- 优势: 输出格式可控、风格统一, 推理质量更稳定。
- 劣势: 需要精心构造示例, **示例的选择对结果影响极大**(Anthropic 2023 的研究表明: 示例的"难度顺序"、"答案分布"对结果影响 > 10 个百分点)。
- 工程经验: 示例最好**按难度递增**排列, 且**答案分布均匀**(不要 8 个示例全是同一个答案)。

```python
# Few-shot CoT prompt 模板
FEW_SHOT_COT_TEMPLATE = """
Q: {example_q1}
A: {example_a1_with_reasoning}

Q: {example_q2}
A: {example_a2_with_reasoning}

Q: {example_q3}
A: {example_a3_with_reasoning}

Q: {real_question}
A:
"""
# 注意: 模型输出后, 通常还需要解析最后的 "答案是 X" 行
```

### A1.4 CoT 的变体

**Self-Ask(Press et al., 2022)**:
- 让模型**显式生成子问题**, 然后逐个回答子问题, 最后综合。
- 与 ToT 类似, 但没有显式的搜索树, 而是线性的"主问题 → 子问题链"。
- 在 multi-hop QA(需要跨文档推理)上比标准 CoT 提升 10-20 个百分点。

**Chain-of-Symbol(CoS)**:
- 把场景建模为符号世界(物体、关系用符号表示), 让模型在符号空间做推理, 再翻译回自然语言。
- 适用于空间推理、几何题。

**Program-of-Thought(PoT, Chen et al., 2022)**:
- 让模型生成**代码**(通常是 Python), 用代码解释器执行得到答案。
- 把推理"外包"给确定性计算, 模型只负责"把问题翻译成代码"。
- **优势**: 计算准确(无浮点幻觉)、可验证、复用现成库; **劣势**: 需要 code interpreter、并非所有问题都能表达成代码。

```python
# PoT 示例: 模型生成的"代码"
def solve():
    total_apples = 5
    eaten = 2
    remaining = total_apples - eaten
    given_to_friend = 1
    final = remaining - given_to_friend
    return final  # = 2
# → 用户得到答案 2, 而无需信任模型的逐步自然语言推理
```

**Chain-of-Table**:
- 把表格作为"可推理对象", 让模型生成 SQL-like 操作, 逐步变换表格内容, 最终从变换后的表格读出答案。
- 在 TableQA 上显著优于纯文本 CoT。

**Thread-of-Thought(ToT 的轻量版)**:
- 不断追问"等等, 还有吗? 还有吗?", 让模型把思考过程"展开"得更彻底。
- 在长上下文、多约束问题上比 CoT 更稳。

### A1.5 CoT 的失败模式与缓解

**失败模式 1: 幻觉推理(Hallucinated Reasoning)**
- 模型生成了看似合理的推理步骤, 但某一步是错的, 后续被错带。
- **缓解**: 加 Self-Verification(让模型回头检查每一步); 或用外部工具验证(如 Python 执行、数据库查询)。

**失败模式 2: 不一致的推理过程**
- 同一问题不同 temperature 下输出差异巨大。
- **缓解**: Self-Consistency(采样多条投票)、降低 temperature(如 0)。

**失败模式 3: 推理过程与最终答案矛盾**
- 模型说"答案是 5", 但推理过程最后一步是 7。
- **缓解**: 用"答案提取器"从推理最后一句强制抽取; 用 PRM(过程奖励模型)对中间步骤打分。

**失败模式 4: 长 CoT 退化**
- 问题变难, 模型开始"绕圈子"、重复、改写, 但推进不动。
- **缓解**: 限制最大步数; 加 reflection token("让我再想想")引导模型做局部重写而非整体重写。

### A1.6 CoT 的代价

**Token 成本**: CoT 通常让输出长度增加 5-50 倍。原本 50 token 的答案, CoT 后可能 500-2500 token。

| 任务 | 直接回答 token | CoT 后 token | 倍数 |
| :--- | :---: | :---: | :---: |
| 简单算术 | ~20 | ~150 | 7x |
| GSM8K 应用题 | ~50 | ~500 | 10x |
| MATH 竞赛 | ~200 | ~2000 | 10x |
| 代码生成 | ~300 | ~1500 | 5x |

**延迟成本**: 自回归生成, 长度翻倍 ≈ 延迟翻倍。CoT 的延迟敏感场景(实时对话、低延迟 API)需要谨慎使用。

**成本/收益权衡**:
- 对**简单问题**: CoT 浪费 token、无收益 → 不要用。
- 对**中等问题**: CoT 提升 10-30 个百分点, 成本 5-10x → 视 SLA 决定。
- 对**困难问题**: CoT 提升 30+ 个百分点, 不 CoT 基本做不对 → 必须用。

**优化方向**:
- **CoT 压缩(Concise CoT)**: 训练模型用更少 token 完成等价推理。
- **动态 CoT**: 根据问题难度决定要不要 CoT(简单题直接答, 难题才展开)。
- **Skip-CoT**: 让模型自己判断"是否需要 CoT"(一个 0/1 决策)。

### A1.7 CoT 与 RLHF/Instruction-Tuning 的关系

**预训练阶段**: 模型"见过"推理过程, 但没专门学"如何按用户要求输出推理"。
**SFT 阶段**: 用"问题 + 高质量 CoT + 答案"的数据 fine-tune, 模型学会"按格式输出推理"。
**RLHF/RLAIF 阶段**: 偏好数据里"推理正确、答案正确"的样本被强化, 模型学会"推理过程也要高质量"。

→ **CoT 是"能力", Instruction-Tuning 是"使用说明书"**。两者缺一不可。

## A2. Tree of Thoughts(ToT)与 Graph of Thoughts(GoT)

### A2.1 ToT 的核心思想: 把推理组织成可搜索的树

CoT 是**线性**推理(每一步只有一个下一步), 但现实中很多问题有"岔路"——需要先尝试一条路径, 发现走不通再回溯试另一条。Tree of Thoughts(Yao et al., 2023)把推理建模成**显式的树搜索**:

- **节点(node)**: 一个"中间状态"(一段推理 + 部分答案)。
- **边(edge)**: 从一个状态到下一个状态的"思考"。
- **搜索**: 用 BFS/DFS/Beam Search 在树上找最优解。

ToT 的 4 个关键组件:
1. **Thought Decomposition**: 把问题拆成"思考步骤"(每步几个 sentence, 而不是一句)。
2. **Thought Generator**: 给定当前状态, 生成 k 个候选下一步(用模型 with CoT prompt, 采样 temperature > 0)。
3. **State Evaluator**: 给每个候选状态打分(用 LM 自身打分, 或专门训练的 value model)。
4. **Search Algorithm**: BFS、DFS、Beam Search 中选一种。

### A2.2 ToT 的算法骨架

```python
# ToT 的 BFS 伪代码
def tot_bfs(initial_state, evaluator, generator, beam_width=3, max_depth=4):
    frontier = [(initial_state, [])]   # (state, path_so_far)
    for depth in range(max_depth):
        candidates = []
        for state, path in frontier:
            thoughts = generator(state, k=beam_width)  # 生成 k 个下一步
            for t in thoughts:
                new_state = state + t
                score = evaluator(new_state)
                candidates.append((score, new_state, path + [t]))
        # 保留 top-beam_width 个候选
        candidates.sort(reverse=True)
        frontier = [(s, p) for s, _, p in candidates[:beam_width]]
    # 取 frontier 中分数最高的
    best_state, best_path = max(frontier, key=lambda x: evaluator(x[0]))
    return best_path
```

**关键参数**:
- `beam_width` (b): 每层保留多少候选。b=3 是常用起点, 太大浪费 token。
- `max_depth` (T): 最大深度。超过 T 强制停止, 避免无限搜索。
- 总计算量 ≈ $b^T$ 次 thought generation。b=3, T=4 → 81 次 LM 调用, 适合 GPT-4 级别 API。

### A2.3 ToT 的适用场景与效果

**Game of 24**(用 4 个数字通过四则运算得到 24):
- 标准 CoT: GPT-4 成功率 ~4%。
- ToT(b=5): 成功率 ~74%。
- 提升近 20 倍, 是 ToT 最著名的 demo。

**Creative Writing(写连贯的 4 段故事)**:
- CoT 容易前后矛盾。
- ToT 让模型先生成多个候选段落, 用 LM 评估"连贯性", 选最佳——任务连贯性从 ~60% 提升到 ~84%。

**Mini Crosswords(填字游戏)**:
- CoT 经常卡在"某个词填不上 → 后面全错"。
- ToT 让模型回溯试其他词, 准确率从 ~16% 提升到 ~60%。

### A2.4 ToT 的局限

1. **大量 LM 调用**: $b^T$ 次生成, 每次还要 evaluator 一次, 总成本是 CoT 的几十到几百倍。
2. **依赖好的 evaluator**: evaluator 本身就是 LM, LM 评估 LM 的可靠性堪忧——尤其是"长链推理"中, 中间状态的质量评估很 noisy。
3. **状态空间设计**: thought 的"颗粒度"很难选。太粗(整段)→ 搜索空间不够; 太细(每句)→ 状态爆炸。
4. **不适合所有问题**: 线性推理(单步问题)、连续推导(数值计算)用 ToT 是浪费。

→ ToT 是"在某些困难问题上值得用"的工具, 不是通用默认。

### A2.5 Graph of Thoughts(GoT): 树到图的推广

Besta et al. 2023 的 GoT 把 ToT 推广到**有向无环图(DAG)**:
- **节点**: 仍然是 thought。
- **边**: 不仅"下一步", 还可以"合并"——把多个 thought 的内容合成一个新的 thought。
- 这模拟了人类的"汇总多条信息"的过程。

```python
# GoT 中的 "聚合" 操作
def aggregate_thoughts(thoughts: list[str]) -> str:
    prompt = f"""
    以下是关于同一问题的多个角度分析:
    {chr(10).join(f'- {t}' for t in thoughts)}
    请综合它们, 给出一个更全面的总结:
    """
    return llm(prompt)
```

**适用场景**:
- **排序任务**(Sort): 把 8 个数字排序, 树搜索可以用"归并"操作把两两有序子序列合并, 而非纯线性比对。
- **集合运算**(Set): 关键词提取 + 去重 + 归并, GoT 比 ToT 更自然。
- **多源综合**(Synthesis): 多篇文档摘要, 用"汇总"边把多个摘要因子合并。

**实验**: 在 Sort 和 Set 操作上, GoT 比 ToT 节省 2-10x 的 token, 同时准确率更高(因为聚合信息更稳定)。

### A2.6 Reasoning via Planning(RAP): ToT 的强化学习版

RAP(Hao et al., 2023)把 ToT 改成**世界模型 + 规划**的 RL 形式:
- **世界模型**: 给定当前状态和 action, 预测下一个状态(用一个 LM 模拟)。
- **策略**: 用 MCTS 在世界模型上搜索。
- 训练: 用 PPO 等 RL 算法优化策略。

优势: 比纯 ToT 更系统化, 可学习; 劣势: 训练成本高、需要专门的世界模型。

### A2.7 Tree Search 与 LLM 的未来结合

- **AlphaGo 式 MCTS + LLM**: 类似 AlphaZero, 用 LLM 当 policy + value 网络, MCTS 做搜索。这正是 o1 / R1 在做的事情——只不过它们的搜索是"隐式的"(模型内化为长 CoT), 而非"显式调用 LLM"。
- **LLM-as-a-Judge**: 用另一个 LM 当 evaluator。在 ToT 中这个 judge 必须与"生成模型"能力相当, 否则 judge 偏弱导致搜索走偏。
- **Test-time Tree Search**: 2025 年后出现的"在生成时实时做 tree search"的范式——模型每生成一步, 都评估多个候选, 选最佳。对短答案(分类、抽取)特别有效。

### A2.8 与 ReAct 的区别

| 维度 | ToT | ReAct |
| :--- | :--- | :--- |
| 结构 | 树(图) | 序列(Thought + Action + Observation 循环) |
| 节点数 | 显式展开 $b^T$ | 单一路径, 但可调用工具回退 |
| 适用 | 搜索/规划类(数学、游戏、谜题) | 工具调用、Agent 决策 |
| 失败处理 | 回溯换分支 | 通过工具 observation 调整下一步 |

→ 两者**互补**: ToT 适合"内部推理有多种走法"的题目; ReAct 适合"需要外部信息/操作"的任务。复杂 Agent 系统往往两者结合(高层用 ToT 规划, 每步用 ReAct 执行)。

### A2.9 工业实践建议

**何时用 ToT**:
- 任务本质是"组合搜索"(数学证明、密码破译、调度规划)。
- 单一 CoT 准确率 < 50%, 需要"试错 + 回溯"。
- 延迟/成本可接受(每个问题 100-1000 次 LM 调用)。

**何时不用 ToT**:
- 任务是"信息抽取""翻译""简短问答"——直接用 single-pass。
- 实时性要求高(< 1 秒)——ToT 至少 10-30 秒。
- 已经有强 verifier(如 code interpreter 可以跑测试)→ 用"ReAct + verify", 不需要 tree。

## A3. Self-Consistency 与采样策略

### A3.1 Self-Consistency 原理

**核心思想**(Wang et al., 2022): 单次 CoT 可能因为某一步骤出错而错到底。如果**采样多条独立 CoT**, 多数会"碰巧正确", 然后通过**投票**选多数答案——Diversity + Aggregation > Single Best。

直觉来源: 人类的"头脑风暴"——如果让 5 个人独立解题, 多数人给出同一个答案, 通常是正确答案。LLM 的"采样多样性"模拟了这种"独立思考者"群体。

```python
# Self-Consistency 简化实现
def self_consistency(problem, llm, n_samples=20, temperature=0.7):
    answers = []
    for _ in range(n_samples):
        cot = llm(problem + " Let's think step by step.",
                  temperature=temperature)
        ans = extract_final_answer(cot)
        answers.append(ans)

    # 投票
    from collections import Counter
    counter = Counter(answers)
    majority_answer = counter.most_common(1)[0][0]
    return majority_answer, counter
```

**对 GSM8K 的效果**: 单次 CoT 准确率 ~57% → Self-Consistency (n=40) 准确率 ~74%。提升 ~17 个百分点。

### A3.2 采样温度与多样性的权衡

**温度 (Temperature)**:
- T = 0: greedy, 每次采样都一样(SC 无效)。
- T = 0.3-0.7: 适度多样, SC 收益最大。
- T = 1.0+: 多样性高, 但质量也下降, 单次准确率掉。

**Top-p (Nucleus Sampling)**:
- p = 0.9: 从累计概率前 90% 的 token 中采样。
- 比 temperature 更可控, 通常 p=0.9-0.95 配合 T=0.7 是常用组合。

**Top-k**:
- k = 40: 只从前 40 个 token 中采样。
- 与 top-p 组合: "top-k=40 + top-p=0.9" 是 OpenAI API 的常见默认。

**Frequency Penalty / Presence Penalty**:
- 频率惩罚: 已出现过的 token 降低概率, 鼓励新 token。
- 用于减少 SC 样本之间的"重复模式", 提升多样性。

### A3.3 投票策略的进阶

**朴素多数投票(Majority Voting)**:
- 取出现次数最多的答案。
- 假设: 每个答案独立同分布, 多对一准。
- 问题: 当正确答案本身是"少数派"时, 多数派反而是错的(尤其在难题上)。

**加权投票(Weighted Voting)**:
- 每个答案的权重 = 该答案的所有 CoT 路径的"平均置信度"。
- 模型对每个答案给一个 logprob 或 LM 评估分数, 高置信的答案权重更高。
- 经验: 比朴素投票提升 2-5 个百分点。

**置信度加权**:
```python
def weighted_majority(answers_with_logprob):
    weighted = {}
    for ans, lp in answers_with_logprob:
        weighted[ans] = weighted.get(ans, 0) + math.exp(lp)
    return max(weighted, key=weighted.get)
```

**基于一致性的过滤**:
- 只保留"中间步骤大致一致"的样本投票(用 BLEU、embedding 相似度衡量过程相似性)。
- 过滤掉"过程完全跑偏"的样本, 提升投票质量。

**Self-Consistency 的扩展**:
- **Complex SC**: 让模型先生成"几个候选解法", 再让模型自己评估哪个解法最可信, 综合得出答案。
- **DiVeRSe**: 用专门训练的 verifier 对每条 CoT 打分, 加权投票。
- **Universal SC**: 不止投票答案, 投票推理过程, 把"过程相似、答案一致"的样本聚类, 取最大类的答案。

### A3.4 采样数量 n 的选择

**成本-收益曲线**:
- n = 5: 提升 ~5 个百分点, 成本 5x, 性价比最高。
- n = 20: 提升 ~10-15 个百分点, 成本 20x。
- n = 40: 提升 ~17 个百分点, 边际收益递减。
- n > 100: 提升 < 2 个百分点, 几乎无收益。

**工业推荐**:
- 普通问题: n = 5-10。
- 关键决策(医疗/法律): n = 20-50。
- 难题(奥赛/数学竞赛): n = 100+ 通常不值得, 应换更强模型。

### A3.5 Self-Consistency 的局限

1. **对开放式问题无效**: 没有"唯一答案"可投票(写作、对话)。
2. **不解决"系统性错误"**: 如果所有 CoT 都因为同一个误解走偏, 投票也救不回来。
3. **成本**: n 倍 LM 调用, 对延迟敏感的 API 不友好。
4. **答案分布偏斜**: 如果正确答案占比天然低(难题中只有 5% 的 CoT 能做对), SC 反而选错答案。

**改进**:
- 用 PRM(过程奖励模型)对每条 CoT 打分, 选"过程最可信"的, 而非"答案最多数"。
- 用 LLM-as-Judge 让模型自己评估答案合理性, 取"最合理"答案。

### A3.6 推理温度的特殊设置

**直觉**: 推理任务 vs 生成任务对 temperature 的需求不同。
- 生成任务(写作、对话): 高 temperature 带来多样性, 收益高。
- 推理任务(数学、代码): 高 temperature 引入"错误"多样性, 通常应低 temperature。

**经验设置**:
- 单次 CoT: T = 0(greedy) 通常最优。
- Self-Consistency: T = 0.5-0.7, 在"多样性"和"质量"间权衡。
- 创造性推理: T = 0.9-1.0(允许模型跳出思维定势)。

### A3.7 与其他技术的组合

**Self-Consistency + CoT**:
- 经典组合, 几乎所有推理 benchmark 的 SOTA 都用。

**Self-Consistency + PoT(Program of Thoughts)**:
- 模型生成代码, 代码可被解释器执行; 多次采样, 取"执行成功且答案一致"的代码。
- 比纯 CoT + SC 更可靠, 因为代码执行是 deterministic。

**Self-Consistency + Tree Search**:
- ToT 的每条分支可以再 SC; 反过来 SC 的每条路径可以用 ToT 搜索。
- 形成"tree of self-consistency", 进一步提升复杂问题的准确率, 但成本极高。

**Self-Consistency + Tool Use**:
- 模型可以多次尝试不同工具调用路径, 用 SC 投票最终答案。

### A3.8 推理采样中的"陷阱"

**Repetition Penalty 误用**:
- 高 repetition_penalty 会让模型避免重复, 但在推理中可能让模型"强行换说法"而失去准确性。
- 推理任务通常设 repetition_penalty = 1.0(不惩罚)。

**Seed 不固定**:
- 不固定 seed 时, 不同调用之间结果完全不可复现——对 SC 调试不友好。
- 调试时固定 seed; 生产中可以放宽。

**Logprob 不可用**:
- 一些 API 不返回 logprob(只返回生成的 token)。此时无法做加权投票, 只能用朴素投票。
- 解决: 让模型额外生成"我对这个答案的置信度是 X%"。

### A3.9 与 o1 / R1 时代的关系

在 o1 / R1 出现之前, Self-Consistency 是工业界"提准确率"的标配手段; 之后, 它依然是**推理模型的外部增强**——你可以对 o1 的多个回答做 SC(尽管 o1 自身已经在内部做了大量采样)。

**新趋势**:
- **Pass@K vs Majority@K**: 不投票, 而是从 K 次采样中选"通过率最高"的答案(用于生成代码)。
- **Reward Model 引导的采样**: 不是均匀采样, 而是用 RM 选"高 reward"的路径(类似 best-of-N)。

## A4. ReAct: Reasoning + Acting 的范式

### A4.1 ReAct 的核心思想

Yao et al. 2022 的 ReAct 把推理和**工具调用**结合成一个 interleaved 序列:

```text
Thought 1 → Action 1 → Observation 1 → Thought 2 → Action 2 → Observation 2 → ... → Final Answer
```

- **Thought**: 模型的内部推理(决定下一步做什么)。
- **Action**: 调用工具(如 Search["..."], Calculator["2+3"], Python["print(2**10)"])。
- **Observation**: 工具返回的结果(注入回 prompt)。
- **循环**: 直到模型判断"有足够信息给出最终答案"。

```python
# ReAct prompt 模板
REACT_PROMPT = """
Question: {question}
Thought 1: {thought_1}
Action 1: {action_1}
Observation 1: {obs_1}
Thought 2: {thought_2}
Action 2: {action_2}
Observation 2: {obs_2}
...
Thought N: 现在我有足够信息给出最终答案
Final Answer: {final_answer}
"""
```

### A4.2 ReAct 与 CoT 的对比

| 维度 | CoT | ReAct |
| :--- | :--- | :--- |
| 信息来源 | 模型内部知识 | 模型 + 外部工具 |
| 幻觉 | 多 | 少(工具是 verifiable) |
| 适用 | 知识型推理 | 知识型 + 操作型任务 |
| 实时性 | 受训练数据 cutoff 限制 | 可访问实时信息 |
| 多步交互 | 不支持 | 原生支持(observation 反馈) |

**经典示例(用 ReAct 答"Who directed the movie that won Best Picture in 2024?")**:
```text
Thought 1: 我需要先查 2024 年奥斯卡最佳影片。
Action 1: Search["2024 Oscar Best Picture winner"]
Observation 1: "Oppenheimer" won Best Picture at the 96th Academy Awards (2024).
Thought 2: 现在查 Oppenheimer 的导演。
Action 2: Search["Oppenheimer director"]
Observation 2: Christopher Nolan directed Oppenheimer.
Thought 3: 有了最终答案。
Final Answer: Christopher Nolan.
```

### A4.3 ReAct 的失败模式与缓解

**失败 1: 错误的工具选择**
- 模型选了不合适的工具(如该用 Search 却用了 Calculator)。
- **缓解**: 工具描述要清晰, 给出"何时用哪个工具"的示例。

**失败 2: 错误的参数**
- Action: Search"2024 Best Pictur", Observation 返回无关内容。
- **缓解**: 让模型在 Thought 中"复述要查的关键字"; 用模糊匹配 fallback。

**失败 3: 循环调用**
- 模型反复调同一个工具, 得不到新信息。
- **缓解**: 限制最大步数; 检测重复 action 直接 break。

**失败 4: Observation 过长撑爆 context**
- 一次搜索返回 5000 token, prompt 迅速增长。
- **缓解**: 截断 / 摘要 / 选择性注入; 用 RAG 而非全量 Search。

**失败 5: 模型不信任 Observation**
- 模型已经有先验"我认为答案是 X", 但 Observation 显示是 Y, 模型忽略 Y。
- **缓解**: 在 prompt 中显式强调"以 Observation 为准"; 加 system message 提醒。

### A4.4 ReAct 的工程实现要点

```python
class ReActAgent:
    def __init__(self, llm, tools, max_steps=10):
        self.llm = llm
        self.tools = tools   # {"Search": search_fn, "Calculator": calc_fn, ...}
        self.max_steps = max_steps

    def run(self, question):
        history = [f"Question: {question}"]
        for step in range(self.max_steps):
            # 生成下一步
            prompt = self.format_prompt(history)
            output = self.llm(prompt, stop=["Observation:"])

            # 解析 Thought / Action
            thought, action = self.parse(output)
            history.append(f"Thought {step+1}: {thought}")

            # 检测 Final Answer
            if "Final Answer:" in action:
                history.append(f"Final Answer: {self.extract_answer(action)}")
                return self.extract_answer(action)

            # 执行 Action
            tool_name, tool_input = self.parse_action(action)
            obs = self.tools[tool_name](tool_input)
            history.append(f"Action {step+1}: {action}")
            history.append(f"Observation {step+1}: {obs}")

        # 达到最大步数, 强制总结
        return self.llm(self.format_prompt(history) + "Final Answer:")
```

**工程细节**:
- **解析鲁棒性**: 用正则或 grammar 解析 Thought/Action/Observation; 不要用纯字符串匹配。
- **错误处理**: 工具调用失败时, Observation 写入错误信息, 让模型决定下一步(重试/换工具)。
- **超时**: 单次工具调用设超时, 防止整个 ReAct 卡住。
- **日志**: 记录每一步, 便于调试。

### A4.5 ReAct 之后的演进

**Reflexion(Shinn et al., 2023)**:
- ReAct + 反思: 每轮结束后, 模型对自己的轨迹打分/反思, 把反思写入 memory。
- 下次尝试时参考上次的反思, 避免重复错误。
- 显著提升多步任务(HotPotQA, AlfWorld)的成功率。

**Toolformer(Schick et al., 2023)**:
- 不是 prompt 工具调用, 而是把工具调用"学进"模型参数。
- 模型在生成时会"决定"插入 `[Search("query")]`, 用 API 返回替换。
- 优势: 推理速度更快(无 ReAct 多轮); 劣势: 训练成本高、灵活性差。

**Gorilla / Function Calling(GPT-4 时代的范式)**:
- 用 JSON Schema 描述工具, 模型输出严格的 JSON 调用。
- 主流 Agent 框架(LangChain, LlamaIndex)都用 function calling 而非 ReAct 的字符串模板。

**AutoGPT / BabyAGI(2023)**:
- ReAct 范式 + 长期目标 + 子任务分解, 形成"自主 Agent"。
- 实践中经常陷入循环或做出无意义动作; 后续框架(AgentVerse, MetaGPT)做了大量工程改进。

### A4.6 现代 Agent 系统中的 ReAct

**Multi-Agent 协作**:
- 一个 Agent 做 planner(高层决策), 多个 Agent 做 executor(调用工具执行)。
- Planner 用 CoT/ToT, Executor 用 ReAct。
- 这是 MetaGPT / AutoGen 的核心架构。

**RAG + ReAct**:
- Retrieval 不是"一次性 top-k", 而是 ReAct 的一个 Action: 模型主动决定"要不要检索、检索什么"。
- Self-RAG, FLARE, IRCoT 都是这种思路。

**Tool-use 大模型训练(2024-2026)**:
- 专门 SFT 在"工具调用轨迹"上, 模型学会"何时该调哪个工具"。
- 代表: ToolACE, xLAM, Hermes Function Calling, Qwen-Agent。
- 训练数据: 大规模合成(给定 schema, 用强模型生成调用轨迹)+ 人工精修。

### A4.7 ReAct 的成本

每次 ReAct 调用包含 N 轮, 每轮 1 次 LLM 调用 + 1 次工具调用。
- 简单问题: N = 2-3, 成本 ≈ 3-4x 普通调用。
- 中等问题: N = 5-8, 成本 ≈ 6-9x。
- 复杂任务: N = 20+, 成本极高(可能 100x)。

**优化**:
- **并行工具调用**: 一步调多个工具(如同时 Search 5 个相关实体)。
- **早期终止**: 模型在 prompt 中说"我有足够信息了", 立即跳出循环。
- **小模型做 ReAct, 大模型做 judge**: 减少推理成本。

### A4.8 工业实践清单

**ReAct 适合的任务**:
- 知识检索 + 推理(如客服问答、研究助手)。
- 多步操作(如浏览器自动化、SQL 生成 + 执行)。
- 需要外部反馈的任务(代码调试、API 调用 + 错误处理)。

**ReAct 不适合的任务**:
- 纯生成(写作、翻译)——直接单次生成。
- 一次性问答——单次 CoT 足够。
- 强实时性(对话延迟 < 500ms)——ReAct 太慢。

## A5. OpenAI o1 / o3: 推理模型的设计哲学

### A5.1 o1 的核心洞察: 把 CoT 内化为训练目标

2024 年 9 月, OpenAI 发布 o1, 核心不是"另一个 GPT", 而是:

> "模型在回答前, 先自己生成大量 hidden reasoning tokens; 这些 tokens 越高质量、越长, 最终答案越好。"

这相当于把"CoT 提示"从**inference time** 的事情, 变成**training time** 的事情:
- 用 RL 训练模型"自发生成高质量 CoT"。
- 推理时, 模型自己知道"该想多久", 而不是被 prompt 强行要求"先想再答"。

### A5.2 o1 的训练流程(公开推测)

OpenAI 没有公开所有细节, 但根据公开演讲、论文和社区推测:

**阶段 1: SFT on high-quality CoT**
- 用 GPT-4 生成"问题 + 详细 CoT + 答案"的数据。
- 数据量不大(几十万到几百万条), 但质量极高。
- SFT 让模型学会"按某种格式生成推理"。

**阶段 2: RL with verifiable rewards(GRPO/PPO)**
- 在数学、代码、科学等"答案可验证"的领域, 让模型采样多条 CoT。
- 正确答案 → 正奖励; 错误答案 → 负奖励(可能加 length penalty、format penalty)。
- OpenAI 称之为 "Learning to Think with Chain of Thought"。

**阶段 3: 推理时 scaling**
- 训练时强制模型"思考够长", 推理时模型也会自动"思考到收敛"。
- 给更多推理预算(time/compute), 模型倾向于"继续验证、继续思考", 准确率上升。

### A5.3 test-time compute scaling 的实证

OpenAI 在 o1 发布会上展示了一张标志性图:

### A5.4 o3 与 o4-mini(2025)

**o3**:
- 比 o1 更强, 在 AIME、GPQA、Codeforces 上接近或超越人类专家。
- 训练时用了更多 RL 算力, 也可能用了更新的 base model。
- o3 在 ARC-AGI 上达到 87.5%(在 high compute 配置下), 这是相当惊人的——ARC-AGI 是以"对人类小孩简单、对 AI 极难"著称的 benchmark。

**o4-mini**:
- 更小、更快, 推理能力仍然很强。
- 适合成本敏感场景(API 价格仅 o3 的 ~10%)。

### A5.5 GPT-5 与 "reasoning effort" 参数(2025-2026)

GPT-5 引入了一个新维度: **reasoning effort**。
- 用户/应用可以指定 `reasoning_effort = low / medium / high`。
- `low`: 几乎不额外思考, 接近普通 GPT-4o 速度。
- `medium`: 中等思考, 准确率显著提升。
- `high`: 长思考, 接近 o3 准确率。

**意义**:
- 单一模型, 不同成本/准确率 trade-off, 用户按需选择。
- 应用侧可以做"路由"(简单问题用 low, 难题用 high)。
- 标志: 推理成为模型的第一公民能力, 可被显式控制。

### A5.6 o-series 与 GPT-series 的融合趋势

2026 年的趋势: "推理"和"非推理"模型不再分家, 而是同一个模型的两个模式:
- 同一组权重, 关闭 reasoning_effort 就是快答, 开启就是深思。
- 类似"思考 vs 直觉"的双模式(类似 System 1 / System 2 思维)。
- 实际部署中, 用户感知不到切换, 但模型内部按需调整。

### A5.7 o1 范式的"代价"

**延迟**: o1 的响应比 GPT-4o 慢 5-50x(平均 ~10x)。
- 一个"普通问题"可能要等 30 秒(其中 28 秒是思考)。
- 用户体验: 必须有"模型正在思考"的 UI 提示, 否则用户以为卡死。

**Token 成本**:
- 推理 tokens 计费(虽然比 GPT-4o 单价便宜, 但量太大)。
- 一次 o1 调用可能花 0.10-1.00 USD。

**可解释性下降**:
- 隐藏的 reasoning tokens 不暴露给用户, 用户看到的只是最终答案。
- 一些场景(教育、研究)需要"看到模型怎么想的", o1 不满足。

**忠实性问题**:
- 公开的 CoT 是"事后合理化", 不一定是真实计算过程。
- 研究(Anthropic 2025)表明: 模型解释 ≠ 模型真实推理过程, 尤其在 o1-style 训练后。
- 解决方案: 训练"faithful reasoning"(强制模型解释与计算一致)。

### A5.8 o1 范式对行业的冲击

**API 定价重构**:
- 旧模式: 按 token 计费, 模型越大越贵。
- 新模式: 按 "answer token + reasoning token" 分别计费, 或按 "reasoning effort" 计费。
- Anthropic Claude 4.x extended thinking、DeepSeek R1 都采用这种定价。

**应用架构变化**:
- 旧架构: LLM 微服务, 一次调用得答案。
- 新架构: 推理 + 工具 + 反思, 可能多次内部循环。
- LangChain / LlamaIndex / DSPy 等框架都加了"reasoning effort" 控制。

**评估体系变化**:
- 旧 benchmark: 单次问答准确率。
- 新 benchmark: 多步推理、长链推理、可验证任务的成功率(AIME / ARC-AGI / CodeForces)。

### A5.9 o1 的不可知部分与社区推测

OpenAI 没公开:
- 推理时 hidden tokens 的最大长度(有人推测是 30K-100K)。

- base model 的规模(从推理成本推测可能是 100B-300B 量级)。

社区推测: o1 的 hidden reasoning 可能包括"自我辩论、验证、反例搜索", 类似 AlphaGo 的 MCTS 隐式搜索。这与 DeepSeek-R1 公开的"内部涌现自我验证"非常一致。

## A6. DeepSeek-R1: 开源推理模型的范式

### A6.1 为什么 R1 重要

DeepSeek 在 2025 年 1 月发布 R1, 意义不在于"又一个推理模型", 而在于:

1. **完全开源**: 模型权重(MIT)、训练数据(部分)、训练 pipeline 都公开。
2. **可复现**: 任何人都能用公开的 recipe 训出等效模型。
3. **极致性价比**: 671B MoE, 每 token 激活 37B, 推理 API 价格仅 o1 的 3-5%。
4. **纯 RL 范式**: 证明不需要"人类推理标注"也能训出强推理。

→ R1 把"推理模型"从"OpenAI 专利"变成"公开科学"。

### A6.2 R1-Zero: 跳过 SFT, 纯 RL 涌现推理

**实验思路**(大胆):
- 不做 SFT, 不给任何"高质量 CoT 数据"。
- 直接用一个 base LLM + RL with verifiable rewards。
- 让模型自己"摸索"如何推理。

**结果**(震撼):
- 模型自发学会了"长推理"——从最初几十 token 的回答, 逐渐变成几千 token 的"思考过程"。
- **"aha moment"**: 在某个训练 step, 模型突然开始"反思自己刚才的推理, 主动验证, 重新尝试"——这是**没有任何人类提示**的情况下涌现的!
- 最终 R1-Zero 在 AIME 2024 上达到 71% 准确率(与 o1 持平)。

**涌现的行为**:
- "Wait, let me reconsider..."(等一下, 让我重新考虑)
- "Let me try another approach..."(让我换一种方法)
- "Double-check: ..."(再检查一遍)

→ 这些行为**没有被显式训练**, 是 RL 优化"正确答案"奖励时的副产品。

### A6.3 R1: 冷启动 SFT + RL 的工程化版本

R1-Zero 很强但有两个问题:
1. **可读性差**: 推理过程混乱, 夹杂多种语言, 不易读。
2. **语言混乱**: 模型可能在中英混杂, 不适合消费级应用。

**R1 的解决方案**:
1. **冷启动 SFT(Cold Start SFT)**:
   - 收集几千条"高质量、可读"的 CoT 数据(可以由 R1-Zero 生成, 人工筛选)。
   - 用这些数据 SFT base model, 让模型学会"以可读格式思考"。
2. **RL 阶段 1(Reasoning RL)**:
   - 在数学、代码、科学任务上 RL, 用 GRPO + 可验证奖励。
   - 让模型"可读地思考 + 答对"。
3. **拒绝采样 + SFT(Rejection Sampling SFT)**:
   - 用 R1 生成大量样本, 只保留"答对且可读"的。
   - 用这些样本继续 SFT, 提升通用能力。
4. **RL 阶段 2(General RL, 全场景 RL)**:
   - 在写作、对话、推理等所有任务上 RL, 平衡多种能力。
   - 奖励函数: 准确性 + 格式 + 有用性 + 无害性。

**结果**: R1 在 MATH-500 上 97.3%(超 o1), 在 AIME 2024 上 79.8%(接近 o3)。

### A6.4 GRPO 算法详解

GRPO(Group Relative Policy Optimization)是 R1 训练的核心算法,DeepSeek 在 2024 年提出:

```python
# GRPO 核心思想
def grpo_loss(prompt, group_rollouts):
    """
    group_rollouts: 对同一 prompt 采样的一组回答 (o_1, o_2, ..., o_G)
    每个 o_i 有 reward r_i
    """
    # 1. 组内归一化优势(advantage)
    advantages = [(r - mean(r)) / (std(r) + 1e-8) for r in rewards]

    # 2. PPO-style clipped objective(per-sample)
    loss = 0
    for o, adv in zip(group_rollouts, advantages):
        ratio = exp(log_prob_new(o) - log_prob_old(o))
        clipped = clip(ratio, 1-eps, 1+eps)
        loss += -min(ratio * adv, clipped * adv)

    # 3. KL 散度惩罚(防止偏离 reference policy 太远)
    loss += beta * KL(new_policy || old_policy)

    return loss.mean()
```

**与 PPO 的关键区别**:
- **没有 Critic(Value Model)**: PPO 需要训练一个 value network 估计 V(s), GRPO 用"组内采样奖励的均值和方差"作为 baseline。
- **组内归一化**: 每次更新基于一组样本的相对优劣, 而非全局 value。
- **更稳定**: 不依赖 Critic 的准确性, 在数学/代码等"奖励稀疏"任务上特别稳定。
- **更省显存**: 没有 Critic = 节省约 50% 的显存。

### A6.5 R1 的奖励函数设计

**核心奖励**(可验证):
```python
def accuracy_reward(problem, response):
    """答案匹配奖励: 数学题答案正确则 +1"""
    pred = extract_boxed_answer(response)  # 解析 \boxed{...}
    gold = get_ground_truth(problem)
    return 1.0 if math_equal(pred, gold) else 0.0

def code_reward(problem, response):
    """代码奖励: 通过所有单测则 +1"""
    code = extract_code(response)
    if not code: return 0.0
    try:
        run_tests(code, problem.test_cases)
        return 1.0
    except:
        return 0.0
```

**格式奖励**:
```python
def format_reward(response):
    """格式奖励: 使用 <think>...</think> 包围推理过程"""
    has_think = "<think>" in response and "</think>" in response
    has_answer = "<answer>" in response or "\\boxed{" in response
    return 0.5 if (has_think and has_answer) else -0.5
```

**长度奖励**(可选, 慎用):
```python
def length_reward(response, target_tokens=2048):
    """长度奖励: 鼓励充分但不啰嗦的推理"""
    n = len(tokenize(response))
    if n < 200: return -0.5     # 太短, 没认真想
    if n > target_tokens * 1.5: return -0.2  # 太长, 啰嗦
    return 0.1                   # 适中
```

**关键原则**:
- 奖励函数要**稀疏 + 清晰**: 0/1 的答案奖励是主信号, 格式/长度奖励是辅助(权重小)。
- 长度奖励要小心, 否则模型会"灌水"凑长度(产生大量重复低质内容)。

### A6.6 R1 的工程经验总结

1. **冷启动数据要精不要多**: 几千条高质量 CoT 比百万条噪声数据更有效。
2. **可验证奖励是核心**: 没有可验证奖励的领域(如写作、对话)RL 难做。
3. **拒绝采样是 SFT 的金标准**: 让模型自己生成 → 过滤 → 再训练, 循环迭代。
4. **多阶段 RL**: 先在专门任务(数学/代码)训, 再在通用任务训, 避免"灾难性遗忘"。
5. **Group Size 影响**: GRPO 的 group size 越大, 优势估计越准, 但训练越慢。一般 8-16 是甜蜜点。
6. **KL 系数选择**: 太小 → 模型跑偏; 太大 → 学不动。一般 0.001-0.01。

### A6.7 R1 的蒸馏小模型

DeepSeek 还发布了**蒸馏版** R1(基于 Qwen / Llama 系列):

- Qwen2.5-7B + R1 蒸馏: GSM8K 准确率 ~85%(接近 GPT-4o)。
- Llama-3.1-8B + R1 蒸馏: GSM8K 准确率 ~88%。

**意义**: 即使是 1.5B 模型, 也能学会"长推理模式"——这意味着推理能力可以被"传授", 而非涌现门槛。

**蒸馏方法**:
```python
# 用 R1 生成训练数据
def distill_data(base_model, r1_model, problems, n_samples=10):
    data = []
    for prob in problems:
        responses = []
        for _ in range(n_samples):
            resp = r1_model.generate(prob, temperature=0.6)
            if accuracy_reward(prob, resp) == 1.0:  # 只用正确的样本
                responses.append(resp)
        # 选最佳(或随机) 作为 SFT 数据
        if responses:
            best = max(responses, key=lambda r: quality_score(r))
            data.append({"problem": prob, "response": best})
    return data

# 用 SFT 训练 base model
for sample in distill_data:
    sft_loss = cross_entropy(base_model(sample.problem), sample.response)
    sft_loss.backward()
```

## A7. Process Reward Model(PRM)vs Outcome Reward Model(ORM)

### A7.1 奖励模型的两种范式

**Outcome Reward Model(ORM)**:
- 给定 (问题, 答案), 给出一个"答案正确性"分数。
- 只看最终结果, 不管过程。
- 代表: 经典的 RLHF reward model(基于"人类偏好对")。

**Process Reward Model(PRM)**:
- 给定 (问题, 中间步骤, 当前状态), 给每个中间步骤一个"这一步是否正确"的分数。
- 看每一步, 不只是最终答案。
- 代表: OpenAI "Let's Verify Step by Step"(2023), Math-Shepherd。

```python
# ORM vs PRM 的接口差异
def orm_score(problem, full_response):
    """ORM: 给完整回答打分"""
    final_answer = extract_answer(full_response)
    return 1.0 if matches_ground_truth(final_answer) else 0.0

def prm_score(problem, steps):
    """
    PRM: 给每个步骤打分
    steps: ["step 1 reasoning...", "step 2 reasoning...", ...]
    returns: [score_step1, score_step2, ...]
    """
    return [prm_model(problem, step_i) for step_i in range(len(steps))]
```

### A7.2 为什么 PRM 更适合推理任务

**稀疏奖励问题**:
- ORM 只在最终答案给奖励, 中间步骤都是 0。
- 这导致 credit assignment 极其困难——模型不知道"哪一步是关键"。
- RL 训练时, 模型倾向于把所有步骤的概率都调高, 而不是强化"关键步骤"。

**PRM 的优势**:
1. **Dense Reward**: 每一步都有反馈, 模型能区分"哪一步贡献大"。
2. **Best-of-N 引导**: 推理时, 用 PRM 对多条候选推理打分, 选 best(类似 inference-time 搜索)。
3. **错误定位**: 哪一步错了一目了然, 便于 debugging。

**OpenAI 的"Let's Verify Step by Step"**:
- 训练一个 PRM 在数学任务上。
- 每个 step 由人类标注"对/错"。
- 推理时: 生成多条解, 用 PRM 选 best。
- 在 MATH benchmark 上, ORM + best-of-100 准确率 72%, PRM + best-of-100 准确率 78%——PRM 在 dense ranking 上显著优于 ORM。

### A7.3 PRM 的训练数据构造

**人工标注**(OpenAI 方式):
- 让模型生成多条解, 人类对每一步打 "✓ / ✗"。
- 成本高: 一道数学题可能有 10-20 步, 标注 100 题 = 1000-2000 个标注。
- 准确率高: 标注者通常能识别"哪步开始错"。

**自动标注(Math-Shepherd, 2024)**:
- 不靠人工, 用"自动验证"推断每步是否正确:
  - **方法 A**: 把"该步之前的中间状态"喂给一个强 LLM, 问"基于当前信息, 后续能否正确解题"——能 → 该步正确, 不能 → 该步错误。
  - **方法 B**: 用 ORM 反推, "如果这一步错了, 最终答案错的概率增加多少"。

```python
# Math-Shepherd 的自动标注伪代码
def auto_label_steps(problem, steps, final_answer_correct, strong_llm):
    labels = []
    for i in range(len(steps)):
        # 把"前 i 步 + 真实答案"给强 LLM, 让它预测"基于前 i 步, 后续能不能推出正确答案"
        prefix = "\n".join(steps[:i+1])
        prompt = f"基于以下推理步骤: \n{prefix}\n问: 最终答案 = {extract_ans(problem)} 是否合理?"
        pred = strong_llm(prompt)  # yes / no
        labels.append(1 if "yes" in pred.lower() else 0)
    return labels
```

**优点**: 成本低(全自动), 可大规模生成(几百万 step)。**缺点**: 标注质量依赖强 LLM, 可能引入"教师模型"的偏差。

### A7.4 PRM 在 RL 训练中的作用

```python
# PRM-guided RL 的奖励函数
def prm_guided_reward(problem, response, prm_model):
    steps = split_into_steps(response)  # 按"step N:"或"\n\n"拆分
    step_scores = prm_model(problem, steps)  # PRM 给每步打分

    # 总奖励 = 最终答案奖励 + PRM 加权
    final_ans = extract_answer(response)
    ans_reward = 1.0 if matches_gt(problem, final_ans) else 0.0

    # PRM 提供的 dense 信号: 平均分 + 关键步骤分
    prm_bonus = 0.1 * sum(step_scores) / len(step_scores)

    # 关键: 不让模型"绕远"——惩罚不一致的低分步骤
    consistency_penalty = -0.05 * count([s for s in step_scores if s < 0.3])

    return ans_reward + prm_bonus + consistency_penalty
```

**好处**:
- 模型能学到"这一步是关键, 要做对"——而 ORM 只能给"全对或全错"的稀疏信号。
- 训练更稳定, 收敛更快。

### A7.5 PRM 在推理时(Inference Time)的作用

**Best-of-N Sampling**:
```python
def best_of_n_with_prm(problem, n_samples, generator, prm):
    candidates = [generator(problem) for _ in range(n_samples)]
    scores = [prm.total_score(problem, split_steps(c)) for c in candidates]
    return candidates[argmax(scores)]
```

**Beam Search with PRM**:
- 在 ToT 搜索中, 用 PRM 当 evaluator, 比"LM 自评"稳定得多。
- 每生成一个候选, 立即用 PRM 打分; 剪枝低分候选。

**Step-level Rejection**:
- 生成时, 每步都用 PRM 实时打分; 低分步骤回滚, 重新生成该步。
- 相当于"边生成边验证", 比"生成完整答案再验证"更高效。

### A7.6 PRM 的失败模式

**PRM 不准确**:
- PRM 自身是模型, 也会错; 在训练分布外(OOD)的题目上 PRM 可能给出错误的"步骤对错"。
- 缓解: 用多个 PRM ensemble, 取多数。

**Reward Hacking**:
- 模型可能学到"PRM 喜欢某种风格", 写出"看似正确但实际错"的步骤。
- 缓解: 定期人工 spot-check; 用对抗样本训练 PRM。

**过度依赖 PRM**:
- 模型在 PRM 评分高的区域"过度自信", 实际可能错。
- 缓解: PRM 分数仅作为辅助, 最终答案仍需 ORM 验证。

**维度爆炸**:
- PRM 需要为每个 step 标注, 标注成本随 step 线性增长。
- 缓解: 自动标注(Math-Shepherd)、稀疏标注(只标关键步骤)。

### A7.7 PRM 在 2024-2026 的进展

**Math-Shepherd(2024)**:
- 用 LLM-as-judge 自动标注 step label。
- 训练 PRM 仅用自动数据, 达到接近人工标注 PRM 的效果。

**OmegaPRM(2025)**:
- 用 MCTS 自动搜索"哪些步骤是关键的", 自动标注。
- 比 Math-Shepherd 更精细。

**Process Reward Models for Tree Search(2025)**:
- 把 PRM 用于 Beam Search + Tree Search 的 evaluator。
- 在竞赛数学上比纯 ORM-based 搜索提升 5-10 个百分点。

**Implicit PRM(2025-2026)**:
- 一些工作发现: 经过 o1-style RL 训练的模型, 内部已经隐式学会了"评估自己推理步骤的能力"。
- 不需要显式 PRM, 模型自己决定何时回溯、何时继续。
- 这是 R1 / o1 的核心洞察之一。

### A7.8 PRM vs ORM 的实际选择

| 场景 | 推荐 |
| :--- | :--- |
| 任务结果可验证(数学、代码) | PRM + ORM 联合 |
| 任务结果难验证(对话、写作) | ORM 为主, PRM 难训 |
| RL 训练阶段 | PRM 更稳定, 收敛更快 |
| 推理时 best-of-N | PRM 显著优于 ORM |
| 训练成本敏感 | ORM 更便宜(标注成本低) |
| 推理成本敏感 | PRM + 少采样可能更好 |

### A7.9 PRM 的未来方向

1. **Generative PRM**: PRM 不再打分, 而是用自然语言解释"为什么这一步对/错"。人类可读、可解释。
2. **Multimodal PRM**: 推理步骤涉及图像(几何、电路图), PRM 需要理解视觉。
3. **Long-Horizon PRM**: 推理步数从 10 步扩展到 100+ 步(科研任务), PRM 需保持长时间跨度的一致性评估。
4. **PRM Distillation**: 用大 PRM 的判断训小 PRM, 部署成本降低。

## A8. Search、Planning 与 MCTS 在推理中的作用

### A8.1 为什么需要显式搜索

LLM 推理本质是"在 token 空间的自回归采样", 这本身是一种**贪心/采样搜索**——但缺乏"后退"和"前瞻"。

**显式搜索的价值**:
1. **前瞻(Lookahead)**: 在某个步骤, 不只考虑"下一步最可能是什么", 而是"未来 K 步可能怎么走, 哪条最好"。
2. **回溯(Backtracking)**: 走到死胡同时, 能回到之前的分叉点换条路。
3. **剪枝(Pruning)**: 提前排除明显无望的分支, 节省算力。

→ 这正是 AlphaGo / AlphaZero 战胜人类的核心——MCTS 让"搜索 + 学习"成为可能。

### A8.2 MCTS 在 LLM 推理中的应用

**经典 MCTS 4 步**:
1. **Selection**: 从根节点开始, 用 UCB(Upper Confidence Bound)选择子节点, 一直走到叶子。
2. **Expansion**: 在叶子节点扩展一个新子节点(让 LLM 生成一个新的 thought)。
3. **Simulation(Rollout)**: 从新节点往下随机/启发式走, 直到终止。
4. **Backpropagation**: 把 rollout 结果(win/lose)沿路径回传, 更新所有访问过的节点的 value。

```python
# LLM-MCTS 简化实现
class LLM_MCTS:
    def __init__(self, llm, value_model, c_puct=1.4):
        self.llm = llm
        self.value_model = value_model
        self.c_puct = c_puct
        self.tree = {}  # state -> {children: [...], visits: N, value: W}

    def search(self, root_state, n_simulations=100):
        for _ in range(n_simulations):
            path = []
            state = root_state

            # 1. Selection
            while self.is_expanded(state):
                children = self.tree[state]['children']
                scores = [
                    (child.value / child.visits) +
                    self.c_puct * sqrt(log(self.tree[state]['visits']) / child.visits)
                    for child in children
                ]
                state = children[argmax(scores)]
                path.append(state)

            # 2. Expansion
            new_thoughts = self.llm.sample(state, n=3)  # 采样 3 个下一步
            for thought in new_thoughts:
                new_state = state + thought
                self.tree[new_state] = {'children': [], 'visits': 0, 'value': 0}
                self.tree[state]['children'].append(new_state)

            # 3. Simulation (Rollout)
            rollout_state = state
            for _ in range(5):  # rollout 5 步
                rollout_state += self.llm.sample(rollout_state, n=1)[0]
            rollout_value = self.value_model(rollout_state)

            # 4. Backprop
            for s in path + [state]:
                self.tree[s]['visits'] += 1
                self.tree[s]['value'] += rollout_value

        return argmax([c.value / c.visits for c in self.tree[root_state]['children']])
```

### A8.3 MCTS 与 LLM 推理的结合范式

**范式 1: LLM as Policy Network, MCTS as Search**
- LLM 生成候选 thought(类似 AlphaGo 的 policy network)。
- 用 value model(可以是另一个 LM 或 PRM)评估每个 thought。
- MCTS 做树搜索, 找到最优路径。
- 代表: RAP(Hao et al., 2023), LATS(Zhou et al., 2023)。

**范式 2: LLM as Everything(纯 LM-MCTS)**
- 用同一个 LLM 当 policy + value + rollout。
- 简化实现, 但效率低(每次 search 数百次 LM 调用)。

**范式 3: 隐式 MCTS(Internalized MCTS)**
- 模型在长 CoT 内部隐式做"搜索-验证-回溯", 而非显式调用 MCTS。
- 这是 o1 / R1 的范式。
- 模型学会"反思刚才的推理, 重新尝试, 验证答案"——这正是 MCTS 的所有要素, 只是用"自然语言思维"实现。

### A8.4 Search 的工程权衡

| 维度 | Greedy | Beam | MCTS | ToT |
| :--- | :--- | :--- | :--- | :--- |
| 候选数 | 1 | k | ~100 | $b^T$ |
| 延迟 | 最低 | 低 | 高 | 极高 |
| 准确率(难题) | 低 | 中 | 高 | 最高 |
| 实现复杂度 | 低 | 中 | 高 | 中 |
| 适用 | 简单题 | 中等题 | 难题 | 极难题 |

**经验法则**:
- 简单题(GSM8K easy): Greedy 足够。
- 中等题(MATH 中档): Beam Search (k=4)。
- 困难题(AIME, 奥赛): MCTS。
- 极难题(数学竞赛决赛): ToT 或 AlphaGo 级别的搜索。

### A8.5 Planning 与推理

Planning 是"高层决策": 先想清楚"整个解题路径", 再一步步执行。LLM 中的 Planning 范式:

**Plan-and-Solve(Wang et al., 2023)**:
```python
# Plan-and-Solve 的 prompt
PROMPT = """
请分两步解决问题:
Step 1: 制定计划(列出解决本题需要的步骤)。
Step 2: 按计划执行(逐步求解)。

问题: {problem}

计划:
1. [第一步: 提取已知条件]
2. [第二步: 列出方程]
3. [第三步: 求解方程]
4. [第四步: 验证答案]

执行:
1. 已知条件: ...
2. 方程: ...
3. 解: ...
4. 验证: ...
"""
```

**Least-to-Most(Zhou et al., 2022)**:
- 把复杂问题拆成"最简单子问题"。
- 先解最简单的, 再用其结果解下一个。
- 适合"递进式"问题(数学归纳、递推、复杂多步)。

**LLM+P(Liu et al., 2023)**:
- 用 PDDL(Planning Domain Definition Language)形式化任务。
- LLM 把自然语言转成 PDDL, 用经典 planner(Fast Downward)解, 再转回自然语言。
- 适合有"严格规则"的任务(物流、调度)。

### A8.6 蒙特卡洛推理与 Self-Refine

**Self-Refine(Madaan et al., 2023)**:
- 模型生成初始答案 → 模型自己给出反馈 → 模型根据反馈改进。
- 循环迭代, 每次都"上次的基础上修改"。
- 不需要外部 verifier, 只需要模型有"自我评估"能力。

```python
def self_refine(problem, llm, max_iters=3):
    response = llm(problem)
    for i in range(max_iters):
        feedback = llm(f"问题: {problem}\n当前回答: {response}\n请批评并给出改进建议:")
        if "已经完美" in feedback: break
        response = llm(f"问题: {problem}\n上次回答: {response}\n反馈: {feedback}\n请改进:")
    return response
```

**效果**: 在代码生成、数学推理、对话生成上, 3 轮 self-refine 通常提升 5-10 个百分点。

### A8.7 AlphaGo 类比与 R1

DeepSeek-R1 的训练过程, 可以类比为 AlphaZero:

| AlphaZero | DeepSeek-R1 |
| :--- | :--- |
| Self-play 生成数据 | 模型自采样生成 CoT |
| Value network 评估 | PRM(隐式)评估每步 |
| Policy network 选择 action | LM 选择下一步 token |
| MCTS 搜索最优路径 | 推理时隐式 search |
| RL 不断改进 policy/value | GRPO 改进 policy |

**关键**: AlphaZero 的核心不是 MCTS, 而是"RL + 搜索"形成自我增强的飞轮。R1 的"纯 RL"也遵循同样模式——只不过用"自然语言推理"代替"棋盘位置"。

### A9.7 评测的注意事项

**数据污染(Data Contamination)**:
- 模型可能在 pretrain 阶段"见过" benchmark 题。
- 表现虚高。
- 缓解: 用 held-out benchmark(LiveCodeBench, FrontierMath), 用 n-gram 检测污染。

**Held-out 评估的重要性**:
- 真实场景的题目 ≠ benchmark。
- 应在自家数据集上做"私有评估"。

**Multiple Choice vs Free Response**:
- 选择题易评估但可能"猜对"。
- 开放回答更真实但评估难(需 LM-as-judge)。

**多次采样与一致性**:
- 同一 benchmark 跑 5 次取平均, 减少方差。
- 报告 mean ± std。

**推理时间的计入**:
- 推理模型在"高 effort"下准确率更高——评估应固定推理预算。
- 否则不同模型的"thinking budget" 不同, 不可比。

### A9.8 推理评测的新趋势

**Test-time Scaling Laws**:
- 评估"推理算力 vs 准确率"曲线。
- 不只看"准确率", 还看"在 1000 tokens 推理下准确率多少"。

**Composite Reasoning Benchmarks**:
- 综合多个子任务(数学 + 代码 + 逻辑), 综合得分。
- 代表: MMLU-Pro, GPQA, FrontierMath。

**Robustness to Adversarial**:
- 在原 benchmark 上加扰动(改数字、改选项顺序), 看准确率掉多少。
- 评估"真实推理"vs"模式匹配"。

**Cost-Adjusted Benchmarks**:
- 报告"每美元准确率"或"每分钟准确率"。
- 评估性价比。

**Calibration / Faithfulness**:
- 模型对错的置信度是否准确?
- 模型解释与真实推理是否一致?

## A10. 推理成本与延迟权衡

### A10.1 推理成本的三维度

**算力成本(Compute Cost)**:
- 每次推理消耗的 FLOPs。
- 推理模型: $O(n^2 \cdot L)$ per token($n$ 是序列长度, $L$ 是层数)。
- 长 CoT 让 $n$ 从 100 变成 10000, 单 token 成本增加 100x, 总成本增加 100x。

**时间成本(Latency)**:
- 用户从发出请求到收到完整响应的时间。
- 受限于自回归生成的串行性——生成 N tokens 至少需要 N 个 forward pass。
- 推理模型平均延迟: 30-60 秒(普通模型 3-5 秒)。

**金钱成本(Dollar Cost)**:
- API 价格 = token 数 × 单价。
- 推理模型常见定价:
  - 隐藏推理 tokens: $3-15 / 1M tokens。
  - 输出 tokens: $15-60 / 1M tokens。
- 一次复杂任务可能花费 $0.10-1.00。

### A10.2 cost-accuracy 曲线

经典曲线(以 GSM8K 为例):
```text
Accuracy
100% |                                              .------o1
 95% |                                         .----.
 90% |                                    .----.
 85% |                              .----.        GPT-4o + SC(n=40)
 80% |                        .----.
 75% |                  .----.
 70% |            .----.                       GPT-4o + CoT
 65% |      .----.
 60% |  .--.                                   GPT-4o
 50% +------------------------------------------------- 算力(log)
     1x    10x    100x    1000x   10000x
```

**关键洞察**:
- 同样 1x 算力下, o1 ~95% vs GPT-4o ~70%。
- 但 o1 的"1x 算力"等价于 GPT-4o 的"100x 算力"——是范式差距。
- o1 在 1000x 算力下几乎 100%, 但边际收益递减。

### A10.3 推理时压缩与加速

**Speculative Decoding**:
- 用小模型(drafter)快速生成候选, 大模型(target)并行验证。
- 对推理任务收益大, 因为"猜测成功率"高(CoT 的下一步通常较确定)。
- 加速比: 2-4x。

**Early Exit / Adaptive Compute**:
- 模型在不同 token 位置可以选择"提前停止"(在简单题上)。
- 训练"中途退出"头: 在第 K 层时, 决定是否已经得到答案。
- 适合"简单问题占比高"的场景。

**CoT 压缩**:
- 训练模型用更少 token 完成等价推理(Concise CoT)。
- 蒸馏: 用"短 CoT"模型模仿"长 CoT"模型的答案。
- 经验: 可压缩到 30-50% 长度, 准确率损失 < 3%。

**KV Cache 优化**:
- 长 CoT 的 KV cache 占大量显存。
- 优化: PagedAttention(vLLM), FlashAttention, KV cache compression。
- 让推理服务支持更长 context + 更高并发。

**模型量化**:
- FP16 → INT8 → INT4, 显存和算力都减少。
- 推理模型 INT4 量化通常损失 < 2% 准确率。

### A10.4 延迟优化技术

**Batching**:
- 同一时间处理多个请求(continuous batching)。
- 把多个请求的 forward 合并, 提升 GPU 利用率。
- 推理服务的核心优化。

**Pipeline Parallelism**:
- 长 CoT 可以分多段, 不同 GPU 算不同段。
- 减少单请求延迟(对超大模型)。

**Speculative Decoding(再次)**:
- 同时加速延迟和算力。

**并行采样**:
- Self-Consistency 需要 N 次采样——这 N 次可以并行。
- 总延迟 = 1 次采样时间(如果 GPU 够多)。

**请求路由**:
- 简单题路由到 fast model(GPT-4o mini), 难题路由到 reasoning model(o1)。
- 整体平均延迟显著降低, 成本也降低。

### A10.5 推理服务的架构

**Token Streaming**:
- 用户看到"模型正在打字", 实际是流式返回 token。
- UX 上感觉延迟低, 实际上后端可能要等全部生成完才结算。
- 流式输出可降低"感知延迟"(perceived latency)。

**Server-Sent Events (SSE)**:
- 后端用 SSE 协议 push token 给前端。
- 推理模型特别需要——30 秒的"完整生成"会让人焦虑, 流式 + "正在思考" 提示更好。

**Interrupt / Cancel**:
- 用户可以在生成中途取消。
- 推理模型可以"在合适的位置停止"(不要在生成一半中途停, 可能给出半成品答案)。
- Anthropic Claude 实现了"stop_reason"机制。

**Reasoning Effort Routing**:
- 用户/应用指定 reasoning_effort(low/medium/high)。
- 后端用对应模型/参数:
  - low: GPT-4o mini 或 distilled R1。
  - medium: GPT-4o + SC(n=5)。
  - high: o1 / R1 full。

### A10.6 成本优化的工程经验

**经验 1: 80/20 法则**
- 80% 的请求是简单问题, 用轻量模型即可。
- 20% 的复杂请求才需要推理模型。
- 路由策略: 简单分类器先判断, 再分发。
- 整体成本下降 5-10x, 平均准确率几乎不降。

**经验 2: 推理预算控制**
- 给每个请求 max_thinking_tokens(如 4000)。
- 简单题用不到 1000 tokens, 难题可能撞上限。
- 设上限防止异常推理(如陷入循环)。

**经验 3: 答案提取后处理**
- 推理模型输出 `<think>...</think><answer>...</answer>`。
- 提取 `<answer>` 部分作为"最终答案"。
- 给用户的 UI 只显示答案, 不显示 <think>。
- 节省用户注意力 + 减少误解。

**经验 4: 缓存**
- 相同问题缓存答案(语义 hash)。
- 推理模型响应慢, 缓存对重复问题收益大。
- 但要小心"答案过时"——推理正确性可能随时间变化(如代码生成)。

**经验 5: 多阶段推理**
- 把难题分成"理解阶段"(快模型) + "推理阶段"(慢模型)。
- 让快模型先"重写问题"为更清晰的形式, 再给慢模型。
- 比直接给慢模型原题略好, 整体成本降低。

### A10.7 推理模型的隐性成本

**Hidden Token 计费**:
- o1 等模型的隐藏推理 token 也计费。
- 一次 "普通" 任务可能消耗 5000 reasoning tokens。
- 用户感知不到这部分 token, 但账单上要算。

**认知成本(Cognitive Cost)**:
- 用户的"等待成本"—— 30 秒等待 + 不能中断 = 用户体验差。
- 一些应用甚至故意隐藏"等待时间", 用 loading 动画掩盖。

**忠实性成本**:
- 推理模型给出"看似合理"的解释, 但解释 ≠ 真实计算。
- 误导用户对"模型怎么工作的"形成错误直觉。
- 在教育、医疗等高 stakes 场景, 这是大问题。

**环境成本**:
- 一次推理消耗的电能 ≈ 一次 Google 搜索的 10-100x。
- 推理模型可能再高 10-50x。
- 长期大规模部署对碳排放有显著影响。

### A10.8 何时用/不用推理模型

**用推理模型**:
- 任务难度高(数学竞赛、SWE 难题)。
- 准确率要求 > 90%。
- 单次调用, 不在意延迟。

**不用推理模型**:
- 简单任务(摘要、翻译、抽取)。
- 实时对话(< 2 秒延迟要求)。
- 成本敏感(高并发低单价)。
- 创意生成(CoT 反而限制多样性)。

**混合策略**:
- 简单模型 + 复杂模型混合, 用路由决定。
- 典型 SaaS 模式: 默认 fast model, 用户可手动切到 "thinking mode"。

### A10.9 推理模型的未来成本曲线

**单位推理成本下降**:
- 模型蒸馏: 用 R1 训小模型, 7B 接近 32B。
- 量化: INT4 推理模型显存少 4x。
- 硬件升级: H100 → B100 → H200, 每瓦性能提升 2-3x/年。

**预期**:
- 2025: 推理 API 价格 $5/M tokens。
- 2026: $1/M tokens(蒸馏 + 量化 + 硬件升级共同作用)。
- 2027: $0.20/M tokens(推理能力下放到 7B 模型)。

→ 推理能力将"民主化", 像今天的 GPT-3.5 一样成为标配。

### A11.9 工业部署经验(2026)

**经验 1: 多模型路由**
- 不依赖单一模型, 而是按需路由。
- 简单任务 → fast model(GPT-4o mini, R1-Distill-Qwen-7B)。
- 困难任务 → reasoning model(o1-mini, R1)。
- 关键任务 → 最强模型(o3, R1 full)。
- 平均成本降低 5-10x。

**经验 2: 推理 + 检索 + 工具的三件套**
- RAG 提供事实, Reasoning 提供逻辑, Tools 提供执行。
- 单独用任何一项都不够, 组合起来是 2026 工业标准。

**经验 3: 评估与监控**
- 持续评估(held-out test set + 用户反馈)。
- 监控"模型漂移"——同 benchmark 准确率突然下降。
- A/B 测试新模型版本, 不能盲切换。

**经验 4: 成本透明**
- 给用户展示"这个回答用了多少 token, 多少 reasoning"。
- 让用户控制 reasoning effort(选项滑块)。
- 类似 Cloudflare 展示带宽使用。

**经验 5: 缓存与去重**
- 相同问题直接返回缓存答案。
- 语义缓存: 用 embedding 找相似问题。
- 对推理模型节省巨大。

## A12. 推理能力面试题集(15 题)

### A12.1 基础概念(1-5 题)

**Q1: 什么是 Chain-of-Thought(CoT)?为什么有效?**

A: CoT 是让 LLM 在给出最终答案前显式生成中间推理步骤的提示/训练技术。有效的原因:
1. **分解复杂问题**: 把 $\mathcal{O}(n)$ 单步推理拆成 $\mathcal{O}(1)$ 多步, 每步更易学。
2. **利用 LLM 的潜在能力**: pretrain 阶段见过大量"问题+推理+答案"数据, 模型已具备推理能力, CoT 把它"放出来"。
3. **涌现能力**: 在大模型(>60B)上特别有效, 小模型收益有限。
4. **可解释性**: 用户能看到推理过程, 便于验证。

**Q2: Self-Consistency 的核心思想是什么?什么时候效果最好?**

A: 核心: 对同一问题采样多条独立 CoT, 用投票选多数答案。效果最好时:
- 答案空间小(是/否、A/B/C/D、数字)。
- 单次 CoT 准确率 30-80%(太低投票无效,太高没必要)。
- 模型的多样性足够(temperature 0.5-0.7)。
- 任务成本可接受(N 倍 LM 调用)。

**Q3: o1 与 CoT 提示的本质区别是什么?**

A:
- **CoT 提示**: 用户在 prompt 里写"先想再答", 模型按要求生成 CoT; 推理能力依赖 pretrain, 模型本身不一定擅长长推理。
- **o1**: 模型经过专门 RL 训练, 把"长 CoT"作为**训练目标**, 模型自发生成高质量推理; 推理时不需要特殊提示, 模型自己知道"该想多久"。
- 比喻: CoT 是"教鹦鹉说话", o1 是"鹦鹉学会了思考"。

**Q4: 什么是 test-time compute scaling?与训练时 scaling 的区别?**

A:
- **训练时 scaling**: 增大模型参数量、训练数据量、训练算力, 模型本身变强。代价是一次性大, 推理时免费。
- **推理时 scaling**: 同一模型在推理时花更多算力(更长 CoT、更多采样、更多搜索), 让单次推理更准确。代价是每次推理都更慢、更贵。
- **o1 的意义**: 证明 test-time scaling 是独立于 training scaling 的新维度, 两者可叠加。

**Q5: 推理模型的"隐藏 token"是什么?**

A: o1 等推理模型在给出最终答案前, 生成大量"思考 token", 这些 token 不暴露给用户, 但被计入费用。隐藏 token 的作用:
- 内部推理空间(让模型"想"得更彻底)。
- 防止用户依赖模型解释(避免误解)。
- 商业秘密(竞争对手无法看到推理细节)。

### A12.2 算法理解(6-10 题)

**Q6: GRPO 与 PPO 的核心区别是什么?**

A:
- **PPO**: 需要训练 Critic(value network) 估计 V(s), 用 GAE(Generalized Advantage Estimation) 计算 advantage。
- **GRPO**: 没有 Critic, 用"同一 prompt 采样的一组回答的奖励"做组内归一化作为 advantage。
- 优势: GRPO 更稳定(不依赖 Critic 准确性)、更省显存(无 Critic = 节省 ~50%)、在稀疏奖励任务(数学/代码)上效果更好。
- 劣势: GRPO 需要更大的 group size(8-16), 单次更新的样本更多。

**Q7: PRM 和 ORM 各自的优劣?**

A:
- **ORM(Outcome Reward Model)**: 只看最终答案对错。优势: 简单、可验证、易训练。劣势: 稀疏奖励、credit assignment 困难。
- **PRM(Process Reward Model)**: 看每一步是否正确。优势: dense reward、可定位错误、推理时可引导搜索。劣势: 标注成本高、PRM 自身可能不准确、reward hacking 风险。
- **经验**: 推理任务优选 PRM(尤其数学), 通用任务优选 ORM。

**Q8: ReAct 与 ToT 的区别?何时用哪个?**

A:
- **ReAct**: 序列结构(Thought → Action → Observation 循环), 适合"需要外部信息"的任务(工具调用、Agent)。
- **ToT**: 树结构(显式多分支 + 回溯), 适合"内部推理有多种走法"的任务(数学证明、博弈、谜题)。
- **选择**: 任务是否需要"外部信息/操作"?是 → ReAct。是否需要"尝试多条路径"且能验证?是 → ToT。复杂系统往往两者结合(ToT 高层规划, ReAct 低层执行)。

**Q9: MCTS 在 LLM 推理中如何应用?**

A: 4 步:
1. **Selection**: 用 UCB 选择最有潜力的子节点。
2. **Expansion**: 用 LLM 在叶子节点生成新候选 thought。
3. **Simulation**: 用 LLM(或 value model)模拟 rollout 到终止。
4. **Backprop**: 把 rollout 结果回传, 更新路径上所有节点的 value。
代表工作: RAP(Hao 2023), LATS(Zhou 2023)。2025 后, 隐式 MCTS(让模型在长 CoT 中自己做 search)成为主流(o1 / R1)。

**Q10: 冷启动 SFT 在 R1 训练中起什么作用?**

A: R1-Zero(纯 RL)虽然推理能力强, 但可读性差、语言混乱。冷启动 SFT 用几千条"高质量、可读"的 CoT 数据做 SFT, 让模型学会:
1. **格式**: 用 `<think>...</think>` 分隔推理与答案。
2. **语言一致性**: 全程中文/英文, 不混杂。
3. **推理结构**: 按"分析问题→列条件→逐步推导→验证答案"组织。
冷启动后, RL 训练更稳定, 输出更易被用户接受。

### A12.3 工程实践(11-13 题)

**Q11: 推理模型部署时如何控制成本?**

A:
1. **路由**: 简单任务用 fast model, 复杂任务用 reasoning model。
2. **推理预算**: 限制 max_thinking_tokens, 防止异常推理。
3. **蒸馏**: 用 R1 训小模型, 7B 接近 32B 准确率。
4. **量化**: INT4 推理, 显存/算力 4x 下降。
5. **缓存**: 相同问题直接返回答案。
6. **Speculative Decoding**: 加速生成, 2-4x。
7. **Self-Consistency 优化**: 并行采样, 总延迟 = 单次延迟。

**Q12: 推理模型的"忠实性"问题是什么?**

A: 模型的 CoT 解释与"真实计算过程"可能不一致。例如, 模型可能说"我先计算了 2+3=5", 但实际推理中它用了错误的步骤偶然得到 5。
- **影响**: 用户被误导, 高 stakes 场景(医疗/法律)危险。
- **原因**: RL 训练时奖励"正确答案", 模型学到"无论推理真假, 只要答案对"。
- **解决**: 训练"faithful reasoning"(强制推理与计算一致); 用 PRM 监督中间步骤; 限制"事后合理化"。

**Q13: 如何评估推理模型的真实能力?**

A:
1. **多 benchmark 组合**: 不要只看一个, 综合 MATH / AIME / GPQA / LiveCodeBench。
2. **held-out 评估**: 用未污染的私有测试集。
3. **Test-time scaling 曲线**: 报告不同推理预算下的准确率。
4. **cost-adjusted 指标**: 报告"每美元准确率"。
5. **Robustness**: 加扰动(改数字、改选项顺序)看准确率掉多少。
6. **Calibration**: 模型对错的置信度是否准确。
7. **可解释性**: CoT 是否反映真实推理过程。

### A13.1 Self-Consistency 完整实现

```python
import re
import math
from collections import Counter
from typing import List, Optional, Callable

class SelfConsistencyReasoner:
    """Self-Consistency 完整实现,支持加权投票和置信度评估"""

    def __init__(self, llm_call: Callable, n_samples: int = 20,
                 temperature: float = 0.7, top_p: float = 0.9,
                 max_tokens: int = 1024):
        self.llm_call = llm_call
        self.n_samples = n_samples
        self.temperature = temperature
        self.top_p = top_p
        self.max_tokens = max_tokens

    def extract_answer(self, response: str) -> Optional[str]:
        """从 LLM 输出中提取最终答案"""
        # 优先匹配 \boxed{...}
        boxed = re.search(r'\\boxed\{([^}]+)\}', response)
        if boxed:
            return boxed.group(1).strip()
        # 其次匹配 "答案是 X"
        m = re.search(r'答案是[:：]?\s*([^\n]+)', response)
        if m:
            return m.group(1).strip()
        # 最后匹配最后一行数字/选项
        lines = [l.strip() for l in response.strip().split('\n') if l.strip()]
        return lines[-1] if lines else None

    def sample_one(self, prompt: str, seed: int) -> tuple:
        """采样一条推理"""
        response, logprob = self.llm_call(
            prompt, temperature=self.temperature, top_p=self.top_p,
            max_tokens=self.max_tokens, seed=seed,
            return_logprob=True
        )
        answer = self.extract_answer(response)
        return response, answer, logprob

    def reason(self, problem: str) -> dict:
        """完整 Self-Consistency 流程"""
        cot_prompt = f"{problem}\nLet's think step by step."

        # 1. 采样 N 次
        samples = []
        for i in range(self.n_samples):
            response, answer, logprob = self.sample_one(cot_prompt, seed=i)
            if answer is not None:
                samples.append({"response": response, "answer": answer, "logprob": logprob})

        if not samples:
            return {"answer": None, "confidence": 0.0, "samples": []}

        # 2. 多数投票
        answer_counts = Counter(s["answer"] for s in samples)
        majority_answer, majority_count = answer_counts.most_common(1)[0]

        # 3. 加权投票(按 logprob 加权)
        weighted = {}
        for s in samples:
            ans = s["answer"]
            weighted[ans] = weighted.get(ans, 0) + math.exp(s["logprob"] / 100)  # 归一化
        weighted_answer = max(weighted, key=weighted.get)

        # 4. 置信度 = 多数派占比
        confidence = majority_count / len(samples)

        return {
            "answer": majority_answer,
            "weighted_answer": weighted_answer,
            "confidence": confidence,
            "n_samples": len(samples),
            "majority_count": majority_count,
            "all_answers": dict(answer_counts),
            "samples": samples[:3]   # 保留前3个样本供调试
        }
```

### A13.2 GRPO 训练循环(简化版)

```python
import torch
import torch.nn.functional as F
from torch.optim import AdamW

class GRPOTrainer:
    """简化版 GRPO 训练器"""

    def __init__(self, model, ref_model, lr=1e-6, kl_coef=0.01,
                 clip_eps=0.2, group_size=8):
        self.model = model
        self.ref_model = ref_model    # 参考模型(冻结)
        self.optimizer = AdamW(model.parameters(), lr=lr)
        self.kl_coef = kl_coef
        self.clip_eps = clip_eps
        self.group_size = group_size

    def compute_logprobs(self, model, input_ids, response_ids):
        """计算 response 部分每个 token 的 log prob"""
        full = torch.cat([input_ids, response_ids], dim=-1)
        outputs = model(full)
        logits = outputs.logits[:, :-1, :]   # 预测下一 token
        target = full[:, 1:]

        # 只取 response 部分
        resp_start = input_ids.shape[1] - 1
        resp_logits = logits[:, resp_start:, :]
        resp_targets = target[:, resp_start:]

        log_probs = F.log_softmax(resp_logits, dim=-1)
        token_logprobs = log_probs.gather(2, resp_targets.unsqueeze(-1)).squeeze(-1)
        return token_logprobs.sum(dim=-1)   # [batch_size]

    def grpo_loss(self, prompts, responses, rewards):
        """
        prompts: list of prompt strings (length B)
        responses: list of response lists, each length G(每 prompt 采 G 个回答)
        rewards: list of reward lists, each length G
        """
        # 1. 计算优势(组内归一化)
        advantages = []
        for r_group in rewards:
            mean_r = sum(r_group) / len(r_group)
            std_r = (sum((x - mean_r) ** 2 for x in r_group) / len(r_group)) ** 0.5
            advantages.append([(r - mean_r) / (std_r + 1e-8) for r in r_group])

        # 2. 拼接所有 (prompt, response) 对
        all_prompts, all_responses, all_advantages = [], [], []
        for p, resp_list, adv_list in zip(prompts, responses, advantages):
            for r, a in zip(resp_list, adv_list):
                all_prompts.append(p)
                all_responses.append(r)
                all_advantages.append(a)

        # 3. 准备 batch
        input_ids = self.tokenize(all_prompts)
        response_ids = self.tokenize(all_responses)
        advantages = torch.tensor(all_advantages, dtype=torch.float32)

        # 4. 计算新旧策略的 log probs
        new_logprobs = self.compute_logprobs(self.model, input_ids, response_ids)
        with torch.no_grad():
            old_logprobs = self.compute_logprobs(self.model, input_ids, response_ids)
            ref_logprobs = self.compute_logprobs(self.ref_model, input_ids, response_ids)

        # 5. PPO-clipped objective
        ratio = torch.exp(new_logprobs - old_logprobs)
        clipped = torch.clamp(ratio, 1 - self.clip_eps, 1 + self.clip_eps)
        policy_loss = -torch.min(ratio * advantages, clipped * advantages).mean()

        # 6. KL 惩罚
        kl = (new_logprobs - ref_logprobs).mean()
        loss = policy_loss + self.kl_coef * kl

        # 7. 反向传播
        self.optimizer.zero_grad()
        loss.backward()
        self.optimizer.step()

        return {"loss": loss.item(), "policy_loss": policy_loss.item(),
                "kl": kl.item(), "mean_reward": sum(sum(r) for r in rewards) / sum(len(r) for r in rewards)}

    def tokenize(self, texts):
        """占位: 实际用 tokenizer"""
        return torch.randint(0, 1000, (len(texts), 512))
```

### A13.3 推理服务路由(Router)

```python
class ReasoningRouter:
    """根据问题难度路由到不同模型"""

    def __init__(self, fast_model, reasoning_model, classifier=None):
        self.fast_model = fast_model
        self.reasoning_model = reasoning_model
        self.classifier = classifier or self._default_classifier

    def _default_classifier(self, problem: str) -> tuple:
        """
        默认难度分类器:
        返回 (difficulty: 'easy'|'medium'|'hard', confidence: float)
        """
        # 启发式: 长问题、有数字、含代码 → 更难
        score = 0
        if len(problem) > 500: score += 1
        if any(c.isdigit() for c in problem): score += 1
        if "```" in problem: score += 1
        if any(kw in problem for kw in ["证明", "推导", "证明", "竞赛", "optimize"]):
            score += 1

        if score <= 1: return ("easy", 0.9)
        if score <= 3: return ("medium", 0.7)
        return ("hard", 0.8)

    def route(self, problem: str, **kwargs) -> dict:
        difficulty, conf = self.classifier(problem)

        if difficulty == "easy":
            answer = self.fast_model(problem, **kwargs)
            return {"answer": answer, "model": "fast", "difficulty": difficulty}
        elif difficulty == "medium":
            # 中等: fast + 单次 CoT
            answer = self.fast_model(problem + " Let's think step by step.", **kwargs)
            return {"answer": answer, "model": "fast+cot", "difficulty": difficulty}
        else:
            # 困难: reasoning model + self-consistency
            answer = self.reasoning_model(
                problem,
                reasoning_effort="high",
                n_samples=5
            )
            return {"answer": answer, "model": "reasoning", "difficulty": difficulty}
```

import re

class ReActAgent:

        self.llm = llm
        self.tools = tools
        self.max_steps = max_steps
        self.max_thoughts_history = max_thoughts_history

    def parse_step(self, output: str) -> Dict[str, str]:
        """解析 Thought / Action / Action Input"""
        thought_match = re.search(r'Thought\s*\d*[:：]\s*(.+?)(?=Action|$)', output, re.DOTALL)
        action_match = re.search(r'Action\s*\d*[:：]\s*(\w+)', output)
        input_match = re.search(r'Action\s*\d*\s*Input[:：]\s*(.+?)(?=Observation|$)', output, re.DOTALL)

        return {
            "thought": thought_match.group(1).strip() if thought_match else "",
            "action": action_match.group(1).strip() if action_match else "",
            "action_input": input_match.group(1).strip() if input_match else ""
        }

    def format_history(self, history: List[str]) -> str:
        """格式化 history,控制长度避免 context 爆炸"""
        if len(history) > self.max_thoughts_history * 3:
            # 只保留最近 N 步
            history = history[-(self.max_thoughts_history * 3):]
            history.insert(0, "...(省略早期步骤)...")
        return "\n".join(history)

    def execute_action(self, action: str, action_input: str) -> str:
        """执行 Action,带错误处理"""
        if action not in self.tools:
            return f"Error: 工具 '{action}' 不存在。可用工具: {list(self.tools.keys())}"
        try:
            result = self.tools[action](action_input)
            # 截断过长结果
            result_str = str(result)
            if len(result_str) > 2000:
                result_str = result_str[:2000] + "...(截断)"
            return result_str
        except Exception as e:
            return f"Error: 工具执行失败 - {type(e).__name__}: {str(e)}"

    def run(self, question: str, system_prompt: str = None) -> str:
        """运行 ReAct 循环"""
        tool_descriptions = "\n".join(f"- {name}: {fn.__doc__}" for name, fn in self.tools.items())

        default_system = f"""你是一个 ReAct Agent,可以使用以下工具:
{tool_descriptions}

按以下格式响应:
Thought 1: <你的思考>
Action 1: <工具名>
Action 1 Input: <工具输入>
Observation 1: <(由系统填充)>
...
Thought N: 我现在可以给出最终答案了
Final Answer: <你的最终答案>
"""

        system = system_prompt or default_system
        history = [f"Question: {question}"]

        for step in range(self.max_steps):
            # 1. 让模型生成下一步
            prompt = f"{system}\n\n{self.format_history(history)}"
            output = self.llm(prompt, stop=["Observation"])

            # 2. 解析
            parsed = self.parse_step(output)

            # 3. 检测 Final Answer
            if "Final Answer:" in output:
                final = re.search(r'Final Answer:\s*(.+?)$', output, re.DOTALL)
                if final:
                    history.append(f"Final Answer: {final.group(1).strip()}")
                    return final.group(1).strip()

            # 4. 执行 Action
            history.append(f"Thought {step+1}: {parsed['thought']}")

            if not parsed['action']:
                # 模型没给出 action,可能想直接给答案
                history.append("Action: (无)")
                history.append("Observation: 请给出 Action 或 Final Answer")
                continue

            history.append(f"Action {step+1}: {parsed['action']}")
            history.append(f"Action {step+1} Input: {parsed['action_input']}")

            obs = self.execute_action(parsed['action'], parsed['action_input'])
            history.append(f"Observation {step+1}: {obs}")

            # 5. 检测循环(防止重复 action)
            recent_actions = [h for h in history[-6:] if h.startswith("Action")]
            if len(recent_actions) >= 4 and len(set(recent_actions)) == 1:
                # 重复同一个 action,给模型强制提示
                history.append("Observation: 你在重复同一个 Action,可能走错了。请换个思路。")

        # 达到最大步数,强制让模型给答案
        prompt = f"{system}\n\n{self.format_history(history)}\n\nThought: 我已经尝试了足够多次,现在给出 Final Answer。"
        output = self.llm(prompt)
        final = re.search(r'Final Answer:\s*(.+?)$', output, re.DOTALL)
        return final.group(1).strip() if final else "未能在规定步数内完成"

### A13.6 评估 pipeline

```python
import json
from typing import Dict, List, Callable
from dataclasses import dataclass, field

@dataclass
class EvalResult:
    problem_id: str
    problem: str
    expected: str
    predicted: str
    correct: bool
    latency_ms: float
    tokens_used: int
    cost_usd: float
    reasoning_tokens: int = 0
    metadata: Dict = field(default_factory=dict)

class ReasoningEvaluator:
    """推理模型评估 pipeline"""

    def __init__(self, model_fn: Callable, judge_fn: Callable = None):
        self.model_fn = model_fn
        self.judge_fn = judge_fn or self._default_judge

    def _default_judge(self, pred: str, expected: str) -> bool:
        """默认 judge: 简单字符串匹配"""
        pred_clean = pred.strip().lower()
        expected_clean = expected.strip().lower()
        return pred_clean == expected_clean or expected_clean in pred_clean

    def evaluate_dataset(self, dataset: List[Dict],
                         n_samples: int = 1,
                         reasoning_effort: str = "medium") -> List[EvalResult]:
        """
        dataset: [{"id": ..., "problem": ..., "expected": ...}, ...]
        """
        results = []
        for item in dataset:
            problem = item["problem"]
            expected = item["expected"]

            for sample_idx in range(n_samples):
                result = self.model_fn(
                    problem,
                    reasoning_effort=reasoning_effort,
                    sample_idx=sample_idx
                )

                eval_result = EvalResult(
                    problem_id=item["id"],
                    problem=problem,
                    expected=expected,
                    predicted=result["answer"],
                    correct=self.judge_fn(result["answer"], expected),
                    latency_ms=result["latency_ms"],
                    tokens_used=result["tokens_used"],
                    cost_usd=result["cost_usd"],
                    reasoning_tokens=result.get("reasoning_tokens", 0),
                    metadata={"sample_idx": sample_idx, **result.get("metadata", {})}
                )
                results.append(eval_result)

        return results

    def summarize(self, results: List[EvalResult]) -> Dict:
        """汇总统计"""
        if not results:
            return {}

        n = len(results)
        correct = sum(1 for r in results if r.correct)
        total_tokens = sum(r.tokens_used for r in results)
        total_reasoning = sum(r.reasoning_tokens for r in results)
        total_cost = sum(r.cost_usd for r in results)
        avg_latency = sum(r.latency_ms for r in results) / n

        return {
            "accuracy": correct / n,
            "n_samples": n,
            "n_correct": correct,
            "total_tokens": total_tokens,
            "total_reasoning_tokens": total_reasoning,
            "total_cost_usd": total_cost,
            "avg_latency_ms": avg_latency,
            "cost_per_correct_usd": total_cost / max(correct, 1),
            "tokens_per_correct": total_tokens / max(correct, 1)
        }

    def by_difficulty(self, results: List[EvalResult]) -> Dict:
        """按难度分桶"""
        buckets = {"easy": [], "medium": [], "hard": []}
        for r in results:
            diff = r.metadata.get("difficulty", "medium")
            buckets.setdefault(diff, []).append(r)

        return {
            diff: self.summarize(rs)
            for diff, rs in buckets.items() if rs
        }
```

### A13.7 推理预算控制器

```python
class ReasoningBudgetController:
    """推理预算控制: 防止异常长的推理"""

    def __init__(self, max_tokens: int = 8000, warn_tokens: int = 5000):
        self.max_tokens = max_tokens
        self.warn_tokens = warn_tokens

    def check_and_truncate(self, response: str) -> Dict:
        """检查推理长度,必要时截断"""
        # 假设有方法获取 token 数
        n_tokens = self.count_tokens(response)

        result = {
            "response": response,
            "truncated": False,
            "warning": False,
            "n_tokens": n_tokens
        }

        if n_tokens > self.max_tokens:
            # 截断到 max_tokens,保留到最近的"答案标记"
            truncated = self.truncate_at_answer(response, self.max_tokens)
            result["response"] = truncated
            result["truncated"] = True
            result["warning"] = True
        elif n_tokens > self.warn_tokens:
            result["warning"] = True

        return result

    def truncate_at_answer(self, text: str, max_tokens: int) -> str:
        """截断到最近的答案标记"""
        # 找到最后一个 \boxed{ 或 Final Answer 位置
        markers = ["\\boxed{", "Final Answer:", "<answer>", "答案是"]
        best_pos = -1
        for marker in markers:
            pos = text.rfind(marker)
            if pos > best_pos:
                best_pos = pos

        if best_pos > 0:
            return text[:best_pos] + "\n\n[推理被截断,以下是最终答案]\n" + text[best_pos:]
        else:
            # 没有答案标记,直接截断
            return text[:int(len(text) * self.max_tokens / self.count_tokens(text))]

    def count_tokens(self, text: str) -> int:
        """占位: 实际用 tokenizer"""
        # 粗略估算: 1 token ≈ 4 chars(英文) 或 1.5 chars(中文)
        return len(text) // 3
