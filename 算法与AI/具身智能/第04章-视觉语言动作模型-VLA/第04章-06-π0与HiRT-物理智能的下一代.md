为什么 2024 年突然爆发?

三个原因:

**原因 1 (VLM 成熟)**: LLaMA-2、Qwen-VL、InternVL、PaliGemma 在 2023 年底都发布了。多模态基础模型第一次可以"开箱即用", 不用从零训 VLM。

**原因 2 (RT-2 验证涌现)**: RT-2 证明 VLA 能"涌现"出语义理解 (把香蕉放在 Mario 旁边)。这给了投资人"通用机器人即将出现"的希望。

**原因 3 (Flow Matching 加速)**: 2024 年 Flow Matching (Lipman et al., 2023) 在图像/视频生成上击败 Diffusion (Stable Diffusion 3)。Physical Intelligence 把这个技术搬到机器人动作生成, 推理速度比 Diffusion Policy (Chi et al., 2023) 快 5-10 倍。

**核心结论**: π0 不是凭空出现, 而是 VLM + Diffusion + Flow Matching 三个领域的成熟, 在"机器人"这个产业问题上的必然交汇点。

### 1.3 为什么需要"下一代 VLA"?——RT-2/OpenVLA 的三个致命缺陷

RT-2、OpenVLA 都基于 token 化动作生成。它们都 work, 但都有三个致命缺陷。

**缺陷 1: 精度上限 ~5mm (256 bin)**

```python
# 256 bin 均匀分箱 → 末端位置精度
末端增量范围 = 1m (相对当前位置)
bin 宽度 = 1m / 256 ≈ 3.9mm
最大误差 = bin 宽度 / 2 ≈ 2mm

# 但实际精度需要 ≤ 1mm (叠衣服, 插 USB)
# 1024 bin (RT-2 Fast) → 1mm, 但词表爆炸
```

**灵巧手操作**需要 ≤ 1mm 精度。256 bin 远远不够。

**缺陷 2: 长视野任务失败率高**

RT-2/OpenVLA 在**单步指令** ("把红色方块放到蓝色碗里") 上成功率高 (~80%), 但在**长 horizon 任务** ("整理整个餐桌") 上 < 30%。

原因: token 化动作是"开环" 生成——LLM 一次预测 7 个 token, 然后执行, 然后重新观测。LLM 不能"看未来", 只能看当前帧。

**缺陷 3: 推理慢 (OpenVLA 7B 一次推理 100ms)**

```python
# OpenVLA 推理 (单步)
time_vla = 100ms  # 7B VLM, 64 GPU
time_control = 30ms  # 机器人控制
total = 130ms → 7.7Hz
```

7.7Hz 对桌面任务够, 对灵巧手 (需要 50Hz) 不够。100ms 延迟意味着"机器人反应迟钝"。

**π0 的三个对症下药**:

| 缺陷 | π0 的解法 | 工程细节 |
| :--- | :--- | :--- |
| 精度 | Flow Matching 连续动作 | ODE 求解, 1mm 精度 |
| 长视野 | Flow Matching 多模态 (可生成多步) | 一次生成 50 步动作 chunk |
| 推理慢 | 较小的 VLM (3B) + 加速 ODE | 50Hz, 与人类操作相当 |

```text
   三代 VLA 的能力边界

   ┌──────────────────────────────────────────────────┐
   │                  任务难度 ↑                        │
   │                                                   │
   │  叠衣服    ──┐                                    │
   │  清理桌面   ─┤                                    │
   │  插 USB    ─┤   π0 (Flow Matching)               │
   │  整理餐具  ─┤   ✓ 全部能做 (60-85% 成功)          │
   │  简单抓取  ─┤                                    │
   │  推物体    ─┤   OpenVLA (7B + token 化)           │
   │            ─┘   ✓ 大部分能做 (40-70% 成功)        │
   │                                                   │
   │  RT-1 (35M + token 化)                           │
   │  ✓ 简单抓取 (50-70% 成功)                         │
   │  ✗ 长视野 / 灵巧 / 复杂语义                       │
   │                                                   │
   └──────────────────────────────────────────────────┘
```

这就是"为什么需要下一代 VLA" 的工程答案。

## 2. π0 架构:VLM + 动作专家的双子塔

### 2.1 总览:5 个组件的清晰分层

π0 的架构可以理解为"**一个 PaliGemma VLM + 一个动作专家 (action expert)**"。两个组件并行处理同一输入, 最后通过 cross-attention 融合。

```text
   π0 架构 (Black et al., 2024, Fig. 3)

   ┌──────────────────────────────────────────────────────────────────┐
   │                                                                    │
   │   输入:                                                            │
   │     - 2 张图像 (第三人称 + 第一人称手腕相机, 224×224)             │
   │     - 1 段语言指令 ("fold the shirt", tokenize 后 ~20 token)     │
   │     - 机器人本体状态 (proprioception, 7-32 维)                    │
   │                                                                    │
   │                              ↓                                     │
   │                                                                    │
   │   ┌────────────────────────────────────────────────────────────┐ │
   │   │                                                            │ │
   │   │   ┌──────────────────┐     ┌──────────────────┐           │ │
   │   │   │  SigLIP 视觉编码  │     │                  │           │ │
   │   │   │  (冻结)           │     │                  │           │ │
   │   │   │  224×224 → 256    │     │  PaliGemma 2    │           │ │
   │   │   │  patch token      │     │  VLM (3B)        │           │ │
   │   │   │  (256 token)      │────▶│                  │           │ │
   │   │   └──────────────────┘     │  - Gemma 2 LLM   │           │ │
   │   │                            │  - 27 层          │           │ │
   │   │   ┌──────────────────┐     │  - 1152 hidden   │           │ │
   │   │   │  Language        │     │  - Vision fusion │           │ │
   │   │   │  Tokenizer       │────▶│    (在 LLM 内)    │           │ │
   │   │   │  (SentencePiece) │     │                  │           │ │
   │   │   │  ~20 token       │     └─────────┬────────┘           │ │
   │   │   └──────────────────┘               │                    │ │
   │   │                                       │ 输出 token 序列     │ │
   │   │                                       │ (含视觉+语言)      │ │
   │   │                                       ↓                    │ │
   │   │                            ┌─────────────────────┐          │ │
   │   │                            │  动作专家网络         │          │ │
   │   │                            │  (300M 参数)          │          │ │
   │   │                            │                     │          │ │
   │   │                            │  - Flow Matching    │          │ │
   │   │                            │  - 300M Transformer │          │ │
   │   │                            │  - 16 层             │          │ │
   │   │                            │  - 输入: 噪声 + VLM  │          │ │
   │   │                            │         token + 状态  │          │ │
   │   │                            │  - 输出: 向量场       │          │ │
   │   │                            │    v_θ(x_t, t)       │          │ │
   │   │                            └──────────┬──────────┘          │ │
   │   │                                       │                    │ │
   │   └───────────────────────────────────────┼────────────────────┘ │
   │                                            ↓                     │
   │                              ODE 求解: x_1 = ∫₀¹ v_θ(x_t, t) dt  │
   │                                            ↓                     │
   │   输出: 动作块 (50 步 × 7 维), 50Hz 控制                        │
   │                                                                    │
   └──────────────────────────────────────────────────────────────────┘
```

整个架构有 **3.3B 参数** (PaliGemma 2 3B + 动作专家 300M), 相比 OpenVLA 7B 小一半, 但能力更强——因为动作专家专门为"连续动作生成" 设计。

**关键设计哲学**:
- VLM 负责"理解": 看图、读指令、形成语义
- 动作专家负责"动手": 把语义映射到连续动作
- 两者通过**完整的 token 序列** (不只是 final hidden state) 融合——保留所有视觉和语言的细节

### 2.2 PaliGemma 2 VLM Backbone:为什么选它?

PaliGemma 2 (Beyer et al., 2024) 是 Google 2024 年发布的多模态 VLM, 由两部分组成:

- **SigLIP-So400m** (视觉编码器, 4 亿参数)
- **Gemma 2** (LLM, 27 亿参数)

**π0 用 PaliGemma 2 而不是 LLaMA-2 的原因**:

```text
   为什么 PaliGemma 2 比 LLaMA-2 更适合 VLA?

   ┌─────────────────────────────────────────────────────────┐
   │  PaliGemma 2                                            │
   │  ✓ 视觉 token 已经在 LLM 的输入空间 (无需 projector)     │
   │  ✓ Gemma 2 的 RoPE + GeGLU 激活, 训练稳定              │
   │  ✓ 在 WebLI 数据集上预训练 (10B 图文对), 视觉泛化强    │
   │  ✓ 27 层, 1152 hidden, 18 heads                       │
   │  ✓ 3B 参数, 推理比 7B 快 2x                            │
   │                                                          │
   │  LLaMA-2                                                │
   │  ✗ 视觉 token 需要额外 projector (LLaVA 风格)          │
   │  ✗ 训练时要对齐 projector, 多一步                       │
   │  ✗ LLaMA-2 视觉泛化弱 (主要在文本上预训练)             │
   │  ✗ 7B 参数, 推理慢                                    │
   └─────────────────────────────────────────────────────────┘
```

**PaliGemma 2 内部细节**:

```python
# 简化版 PaliGemma 2 forward
class PaliGemma2(nn.Module):
    def __init__(self):
        self.vision_encoder = SigLIPSo400m()  # 视觉编码器, 冻结
        self.llm = Gemma2(
            num_layers=27,
            hidden_size=1152,
            num_heads=18,
            vocab_size=257152,
            max_seq_len=4096,
        )
        # 关键: 视觉 token 已经投影到 hidden_size
        # 无需额外 projector

    def forward(self, images, input_ids):
        # 视觉编码
        vision_tokens = self.vision_encoder(images)  # (B, 256, 1152)
        # 文本编码
        text_tokens = self.llm.token_embedding(input_ids)  # (B, T_text, 1152)
        # 拼接
        full_sequence = torch.cat([vision_tokens, text_tokens], dim=1)
        # 自回归 transformer
        return self.llm(full_sequence)
```

π0 用 PaliGemma 2 3B 而不是 10B (官方还有 10B/28B 版本), 因为:
1. 3B 在 H100 上推理 < 30ms (够 50Hz)
2. 动作专家 300M 还能 fine-tune, 7B+300M 已经 > 60GB 显存

**细节: 冻结 vs 微调 PaliGemma 2**

π0 的训练是**部分冻结**:
- SigLIP: **冻结** (vision encoder 已经够强)
- Gemma 2 LLM: **全量微调** (适配机器人指令)
- 动作专家: **从零训练** (300M Transformer)

```text
   π0 训练时的参数状态

   ┌──────────────────────────────────┐
   │  SigLIP vision encoder          │  冻结 (❄️)
   │  Gemma 2 LLM (27 层)            │  微调 (🔥)
   │  动作专家 (16 层, 300M)          │  从零训练 (🔥)
   └──────────────────────────────────┘
   总可训练: 3.0B (PaliGemma 2 微调) + 0.3B (动作专家)
   显存占用: ~36GB (BF16)
```

### 2.3 动作专家网络:Flow Matching 的"画布"

动作专家 (action expert) 是 π0 的核心创新。它是一个**专门的 Transformer**, 输入是**带噪声的潜在动作**, 输出是**指向真实动作的向量场**。

```python
class ActionExpert(nn.Module):
    """
    π0 的动作专家网络 (简化版)

    输入:
      - x_t: 带噪声的潜在动作 (B, action_horizon, action_dim)
      - t: 时间步 (B,)
      - vlm_features: VLM 输出的 token 序列 (B, T_vlm, hidden)
      - state: 机器人本体状态 (B, state_dim)

    输出:
      - v_θ(x_t, t): 向量场 (B, action_horizon, action_dim)
    """
    def __init__(self, action_dim=7, horizon=50, hidden=1024, depth=16):
        super().__init__()
        self.action_dim = action_dim
        self.horizon = horizon
        self.hidden = hidden

        # 输入投影
        self.action_proj = nn.Linear(action_dim, hidden)
        self.timestep_embed = TimestepEmbedder(hidden)  # sinusoidal
        self.state_proj = nn.Linear(state_dim, hidden)

        # 主干: 16 层 Transformer decoder
        decoder_layer = nn.TransformerDecoderLayer(
            d_model=hidden,
            nhead=8,
            dim_feedforward=hidden * 4,
            batch_first=True,
        )
        self.decoder = nn.TransformerDecoder(decoder_layer, num_layers=depth)

        # 输出投影
        self.output_proj = nn.Linear(hidden, action_dim)

    def forward(self, x_t, t, vlm_features, state):
        # 投影输入
        x_embed = self.action_proj(x_t)              # (B, H, hidden)
        t_embed = self.timestep_embed(t).unsqueeze(1)  # (B, 1, hidden)
        s_embed = self.state_proj(state).unsqueeze(1)  # (B, 1, hidden)

        # query = 噪声动作 + 时间 + 状态
        query = x_embed + t_embed + s_embed  # (B, H, hidden)

        # cross-attention to VLM features (key/value)
        output = self.decoder(query, vlm_features)  # (B, H, hidden)

        # 投影到动作空间
        v_theta = self.output_proj(output)  # (B, H, action_dim)
        return v_theta
```

**关键设计**:
- **Cross-attention** 把 VLM 输出当作 key/value, 动作 token 当作 query——和语言模型的 image captioning 反过来 (在 captioning 里, query=语言, kv=图像)
- **Time embedding** 用 sinusoidal (和 Diffusion / Flow Matching 一致)
- **状态融合** 通过加性 embedding——和 VLM token 简单相加, 不需要额外 attention

### 2.4 Flow Matching 动作生成:从噪声到动作的 ODE

动作专家输出的是**向量场** $v_\theta(x_t, t)$, 不是直接的动作。推理时, 我们从纯噪声 $x_0 \sim \mathcal{N}(0, I)$ 出发, 沿向量场积分, 最终到达真实动作 $x_1$。

```python
def inference(action_expert, vlm_features, state,
              num_steps=10, action_dim=7, horizon=50):
    """
    Flow Matching 推理 (Euler 求解器, 简化版)
    """
    # 从标准正态噪声开始
    x = torch.randn(1, horizon, action_dim)

    # 时间步从 0 到 1
    dt = 1.0 / num_steps
    for i in range(num_steps):
        t = torch.tensor([i * dt])
        # 神经网络预测向量场
        v = action_expert(x, t, vlm_features, state)
        # Euler 步进
        x = x + dt * v

    return x  # 动作序列 (1, 50, 7)
```

**直觉**: 把动作想象成"地形图上的一个点", Flow Matching 训练一个向量场, 让每一点的箭头指向"真实动作分布"。从噪声出发, 沿箭头走, 最终到达真实动作。

```text
   Flow Matching 的"地形图"直觉

   起点 (噪声)                       终点 (真实动作)
       ●  ●                              ★
    ●  ●  ●                           ★  ★
       ●  ●                          ★
   ●  ●  ●  ●  ← 向量场箭头         ★  ★
                                      ★

   从 ● 出发, 沿箭头走, 最终到达 ★
   推理时间 ≈ 10 步 Euler, ≈ 10ms (H100)
```

### 2.5 50Hz 实时控制:π0 的工程魔法

π0 的工程团队用了 4 个 trick 让 VLA 在 50Hz 下实时运行:

**Trick 1: 动作块 (Action Chunking)**

```python
# 一次性生成未来 50 步动作 (1 秒)
actions = inference(...)  # (1, 50, 7)

# 机器人开环执行前 K 步 (K=10, 0.2 秒)
for i in range(10):
    execute(actions[0, i])
```

推理频率从 50Hz 降到 10Hz (1 秒 10 次), 摊销计算成本。

**Trick 2: Flow Matching ODE 步数少 (10 步)**

Diffusion Policy (Chi et al., 2023) 需要 100 步去噪。π0 用 flow matching + Euler ODE 求解, 只需 10 步。

**Trick 3: KV cache 复用**

```python
# 第一次推理
vlm_features_1 = pimgemma2(images_1, instruction)
actions_1 = action_expert(noise, t, vlm_features_1, state)

# 第二次推理 (新图像, 但指令不变)
vlm_features_2 = pimgemma2(images_2, instruction)
# VLM 的 KV cache 可以复用 (指令 token 一样)
# 只需重新编码新图像 token
```

**Trick 4: 量化推理**

π0-FAST (FAST = Flow matching Action-chunked Sequence Transformer) 用 INT8 量化 VLM, 推理时间从 30ms 压到 15ms。

```text
   π0 推理时间分解 (H100 GPU, BF16)

   ┌──────────────────────────────────────┐
   │  PaliGemma 2 视觉编码 (SigLIP)        │  5ms
   │  PaliGemma 2 LLM forward (27 层)      │  20ms
   │  动作专家 (16 层 × 10 ODE 步)         │  5ms
   │  KV cache 复用 + 量化                 │  -10ms
   └──────────────────────────────────────┘
   总时间: ~30ms → 33Hz (单步)

   动作块 10 步: 30ms × 1 + 20ms × 9 = 210ms (摊销)
   控制频率: 50Hz (1 秒 10 次推理 + 开环执行 10 步)
```

50Hz 已经和人类操作员远程控制相当——这是"机器人像人"的工程门槛。

## 3. Flow Matching 详解:从 Diffusion 到更优雅的生成

### 3.1 从 Diffusion 到 Flow Matching:为什么换一种"去噪"

Diffusion Model (Ho et al., 2020) 是 2020-2024 年的生成模型霸主。**数学基础/7-系统思维/案例10** 已经把它拆到 SDE 层面。Flow Matching (Lipman et al., 2023) 是 Diffusion 的"更优雅变体"——**用 ODE 替代 SDE, 训练目标简化为回归一个向量**。

```text
   Diffusion vs Flow Matching 的对比

   ┌──────────────────────────────────────────────────────────┐
   │  Diffusion (DDPM)                                        │
   │  - 前向: q(x_t | x_{t-1}) = N(√(1-β_t) x_{t-1}, β_t I) │
   │  - 反向: 学 p_θ(x_{t-1} | x_t), 预测噪声 ε              │
   │  - 训练: ||ε - ε_θ(x_t, t)||²                          │
   │  - 推理: 100 步 Langevin 动力学, 含随机性              │
   │                                                            │
   │  Flow Matching (FM)                                      │
   │  - 前向: x_t = (1-t) x_0 + t x_1  (线性插值!)         │
   │  - 反向: 学 v_θ(x_t, t) 直接是向量场                   │
   │  - 训练: ||v - v_θ(x_t, t)||² (回归一个向量!)          │
   │  - 推理: 10 步 Euler ODE, 无随机性                      │
   └──────────────────────────────────────────────────────────┘
```

**核心数学**:

Diffusion 的前向是**随机加噪**:
$$x_t = \sqrt{\bar\alpha_t} x_1 + \sqrt{1 - \bar\alpha_t} \epsilon, \quad \epsilon \sim \mathcal{N}(0, I)$$

Flow Matching 的前向是**确定性插值** (最简单的"条件概率路径"):
$$x_t = (1 - t) x_0 + t x_1, \quad t \in [0, 1]$$

其中 $x_0 \sim \mathcal{N}(0, I)$ 是噪声, $x_1$ 是真实数据 (机器人动作)。

**直觉**: 从噪声 $x_0$ "匀速" 走向真实数据 $x_1$, 中间点 $x_t$ 是一条直线上的点。

### 3.2 概率路径设计:为什么选"线性插值"

Flow Matching 的核心设计自由度是**概率路径** $p_t(x)$, 即每个时刻 $t$ 的数据分布应该长什么样。

**最朴素的选择**: 线性插值 + 标准正态噪声
$$p_t(x) = \mathcal{N}(x; \mu_t, \sigma_t^2 I)$$

其中 $\mu_t = (1-t) \cdot 0 + t \cdot x_1 = t x_1$ 和 $\sigma_t = 1 - t$。

这样每个时刻的分布都是高斯, 且 $p_0 = \mathcal{N}(0, I)$ (纯噪声), $p_1$ 集中在 $x_1$ 附近 (真实数据)。

```text
   概率路径随时间演化

   t=0:    分布 = N(0, I)           (一团噪声)
              ╱╲
            ╱    ╲
          ╱        ╲
        ╱            ╲

   t=0.5:  分布 = N(0.5·x1, 0.5²·I) (中间)
              ╱╲
            ╱    ╲    ← 中心向 x1 移动, 范围缩小
          ╱        ╲
        ╱            ╲

   t=1:    分布 = N(x1, 0·I)        (一点, 即真实数据)
              ★ ← 完全集中在 x1
```

**为什么选线性插值?**

三个理由:

1. **简单**: 训练目标 = 简单 MSE
2. **可解**: ODE 有解析解 (不需要随机模拟)
3. **够用**: 在图像、视频、机器人动作上都 work

Lipman et al. (2023) 证明, **任何**连续概率路径都可以写成 Flow Matching, 线性插值只是最简单的一种。在机器人动作上, 更复杂的路径 (如高斯混合) 反而效果更差——因为动作分布本来就接近高斯。

### 3.3 条件向量场:为什么学 $v_\theta(x_t, t)$

Flow Matching 的训练目标是**回归一个向量场**:
$$\mathcal{L}_{\text{FM}} = \mathbb{E}_{t, x_0, x_1} \left[ \| v_t(x_t) - v_\theta(x_t, t) \|^2 \right]$$

其中 $v_t(x_t)$ 是真实向量场, $v_\theta(x_t, t)$ 是神经网络预测。

**真实向量场**是什么?

它由**概率路径**决定。最优向量场满足连续性方程:
$$\frac{\partial p_t}{\partial t} + \nabla \cdot (p_t v_t) = 0$$

对**线性插值路径**, 真实向量场有**闭式解**:
$$v_t(x_t) = x_1 - x_0$$

**直觉**: 在每个时刻 $t$, 从当前位置 $x_t$ 应该"指向真实数据 $x_1$ 减去噪声 $x_0$"的方向——也就是**真实的"位移向量"**。

```text
   真实向量场的几何直觉

   起点 (x_0)         中间点 (x_t)         终点 (x_1)
       ●─────────────────●─────────────────★
                         │
                         │  v_t(x_t) = x_1 - x_0
                         │  方向 = 指向 x_1, 大小 = ||x_1 - x_0||
                         ↓
                  (箭头长度 = 总位移, 方向 = 从噪声到数据)
```

神经网络 $v_\theta(x_t, t)$ 的任务是: **给定当前位置 $x_t$ 和时刻 $t$, 预测这个箭头**。

**条件向量场**: 因为 $x_1$ 是"条件" (给定训练数据), 所以 $v_t(x_t) = x_1 - x_0$ 是**条件向量场**。训练时我们采样 $(x_0, x_1)$ 对, 计算 $v_t$, 训练网络拟合它。

**推理时**, 我们只有 $x_0$ (从噪声生成), 没有 $x_1$。但网络已经学到: 给定 $x_t$ 和 $t$, $v_\theta(x_t, t)$ 就是 $\mathbb{E}[x_1 - x_0 | x_t]$。这就是 ODE 求解能 work 的原因。

### 3.4 训练:一个简单到不像话的回归目标

Flow Matching 的训练是**最简单的监督学习**——给定 $(x_0, x_1, t)$, 回归 $v = x_1 - x_0$。

```python
def flow_matching_loss(v_theta, batch):
    """
    Flow Matching 训练损失 (简化版)

    batch 包含:
      - x_1: 真实动作 (B, horizon, action_dim)
      - conditioning: VLM features + state (B, ...)
    """
    B = batch['x_1'].shape[0]
    action_dim = batch['x_1'].shape[-1]
    horizon = batch['x_1'].shape[1]

    # 1. 采样噪声 x_0 ~ N(0, I)
    x_0 = torch.randn_like(batch['x_1'])

    # 2. 采样时刻 t ~ U[0, 1]
    t = torch.rand(B)  # 每个样本一个 t

    # 3. 线性插值得 x_t
    t_broadcast = t.view(B, 1, 1)
    x_t = (1 - t_broadcast) * x_0 + t_broadcast * batch['x_1']

    # 4. 真实向量场 = x_1 - x_0
    v_target = batch['x_1'] - x_0

    # 5. 神经网络预测向量场
    v_pred = v_theta(x_t, t, batch['vlm_features'], batch['state'])

    # 6. 简单 MSE
    loss = F.mse_loss(v_pred, v_target)
    return loss
```

**对比 Diffusion**:
- Diffusion 训练: 预测噪声 $\epsilon$, $\mathcal{L} = \|\epsilon - \epsilon_\theta(x_t, t)\|^2$
- Flow Matching 训练: 预测向量 $v$, $\mathcal{L} = \|v - v_\theta(x_t, t)\|^2$

**数学等价性**: 通过变量替换, 两个 loss 是**线性等价**的。但 Flow Matching 在数值上更稳定 (向量场有界), 推理时更简单 (ODE 不用采样)。

### 3.5 与 Diffusion Policy 的对比:π0 为什么快 5-10 倍

Diffusion Policy (Chi et al., 2023) 是 π0 之前最强的连续动作生成方法。我们详细对比一下:

```text
   Diffusion Policy vs π0 的对比

   ┌──────────────────────────────────────────────────────────┐
   │  项目           Diffusion Policy         π0 (Flow)       │
   │  ─────────────────────────────────────────────────────────│
   │  数学基础       DDPM / DDIM              Flow Matching    │
   │  训练目标       预测噪声 ε                预测向量 v       │
   │  推理步数       100 (DDPM) / 10 (DDIM)    10 (Euler)      │
   │  ODE 类型       SDE (含随机性)            ODE (确定性)    │
   │  视觉输入       CNN (ResNet-18)           PaliGemma 2 VLM │
   │  数据规模       ~10K 演示                 ~10B+ token     │
   │  任务范围       桌面 (简单)               跨形态 (复杂)   │
   │  推理延迟       100ms (100 步)            30ms (10 步)    │
   │  成功率         30-60% (单任务)           60-85% (跨任务) │
   └──────────────────────────────────────────────────────────┘
```

**为什么 π0 比 Diffusion Policy 快 5-10 倍?**

**原因 1 (ODE vs SDE)**: Flow Matching 用 ODE, 路径**确定性**; Diffusion 用 SDE, 路径**有随机性**。确定性 ODE 可以大步走, SDE 必须小步走 (否则发散)。

**原因 2 (训练-推理一致性)**: Flow Matching 训练时学的就是 $v_\theta$, 推理时直接积分。Diffusion 训练时学 $\epsilon_\theta$, 推理时要转化为 $v_\theta$ 再积分——多一步转换。

**原因 3 (无随机性)**: Diffusion 推理的随机性需要额外的 Langevin 步 (≈ 30% 计算量)。Flow Matching 完全不需要。

```text
   推理时的轨迹对比

   Diffusion (DDIM, 10 步):
   x_0 → x_0.1 → x_0.2 → ... → x_1
   轨迹 = 离散点 (因为是 SDE 离散化)
   每步: 模型前向 + 去噪 + 随机采样

   Flow Matching (Euler, 10 步):
   x_0 → x_0.1 → x_0.2 → ... → x_1
   轨迹 = 一条直线 (因为是 ODE + 线性插值)
   每步: 模型前向 + Euler 步进
```

**直觉**: Flow Matching 的"路径"是直线 (因为线性插值), Diffusion 的"路径"是曲线 (因为带噪声)。直线能用大步, 曲线必须小步。

**实验数据** (Black et al., 2024, Table 1):

```text
   叠衣服任务的成功率对比 (跨形态 8 种机器人)

   Diffusion Policy (最佳调参):  35%
   π0 (Flow Matching):          65%

   π0 vs Diffusion Policy:
   - 精度高 30% (1.2mm vs 3.5mm RMSE)
   - 推理快 4x (8ms vs 35ms 单步)
   - 长 horizon 任务优 30% (50 步动作)
```

### 3.6 Flow Matching 的局限:什么时候用 Diffusion 更好

**Flow Matching 不总是比 Diffusion 好**。两个场景 Diffusion 反而更优:

**场景 1: 多模态分布 (multi-modal)**

机器人动作有时是多模态的: "拿起物体" 可以从左边拿或右边拿。Flow Matching 的线性插值会"取平均", Diffusion 的随机性会"取样"。

**场景 2: 训练数据少 (< 1K 轨迹)**

Flow Matching 对 ODE 求解的稳定性更敏感, 数据少时容易训练失败。Diffusion 的随机性反而是 regularizer。

**经验法则**:
- 数据 > 10K, 任务连续 → Flow Matching
- 数据 < 10K, 任务多模态 → Diffusion
- 推理实时 (50Hz) → Flow Matching
- 训练简单优先 → Diffusion

**为什么需要这么多数据?** 因为 flow matching 比 token 化更需要数据——flow matching 拟合的是一个连续向量场, 信息密度比离散 token 高。

### 4.3 训练资源:36 块 H100, 7 天

π0 完整训练用了**约 252 块 H100 × 7 天** (Black et al., 2024 报告)。这意味着大约 42K H100-hour。

```text
   π0 训练资源分解

   ┌──────────────────────────────────────────────────────────┐
   │  预训练阶段 (PaliGemma 2 已有, 不算成本)                  │
   │    - 跳过, 直接用 Google 发布的 checkpoint               │
   │                                                            │
   │  Post-training (机器人数据微调)                            │
   │    - 36 H100 (BF16)                                       │
   │    - 7 天连续训练                                         │
   │    - 总计算: 36 × 7 × 24 = 6048 GPU-hour                │
   │    - 折算费用: ~$60K (云服务 $10/H100-hour)              │
   │                                                            │
   │  RLHF 微调 (可选, π0+RLHF 版本)                           │
   │    - 50 H100 (额外)                                       │
   │    - 3 天                                                 │
   │    - 总计算: 50 × 3 × 24 = 3600 GPU-hour                 │
   └──────────────────────────────────────────────────────────┘
```

**对比**:
- RT-1: 128 TPU v3, 17 天 ≈ 50K TPU-hour
- OpenVLA: 64 A100, 14 天 ≈ 21K A100-hour ≈ 42K H100-hour (等价)
- π0: 36 H100, 7 天 ≈ 6K H100-hour (post-training)

π0 的训练**比 OpenVLA 便宜约 7 倍**, 因为 PaliGemma 2 预训练免费 + 动作专家参数小 (300M vs 7B)。

**对工业部署的意义**: 客户给 1000 条演示 + 24 小时 H100, 就能 fine-tune 出"客户专属 π0", 成本 ≈ $5K。这让"机器人微调服务" 成为可行商业模式。

### 4.4 任务指令理解:自然语言的多层级处理

π0 的语言指令处理走 PaliGemma 2 的 tokenizer (SentencePiece, 257K vocab), 但训练数据中指令的形式有三种:

**层级 1: 直接指令** ("pick up the apple")
- 训练数据: 70%
- 处理: 标准 VLM tokenization
- 优点: 简单, 训练稳定

**层级 2: 复合指令** ("pick up the apple and put it in the bowl")
- 训练数据: 20%
- 处理: VLM 自身分解 (语言能力已经够)
- 优点: 测试长 horizon

**层级 3: 抽象指令** ("clean up the table", "tidy the room")
- 训练数据: 10%
- 处理: 用 VLM 的世界知识推断子任务
- 优点: 测试涌现能力 (类似 RT-2)

```text
   指令层级与 π0 表现

   层级 1 ("pick up apple"):
     - 训练时见过 → 成功率 85%

   层级 2 ("pick up apple, put in bowl"):
     - 训练时见过 → 成功率 75%

   层级 3 ("clean up the table"):
     - 训练时未直接见过
     - 但 VLM 知道 "clean up" = "把所有物体归位"
     - 成功率 60-70% (涌现)
```

**涌现能力的具体例子** (Black et al., 2024 实验):

> 指令: "把香蕉放在 Mario (一个陌生角色) 旁边"
>
> π0 的反应:
> 1. VLM 理解 "Mario" = 一个特定角色
> 2. VLM 用视觉找到桌上的 Mario 玩偶
> 3. VLM 用视觉找到香蕉
> 4. 动作专家生成"接近 Mario + 放下" 的轨迹
>
> **训练数据中没有"Mario" 这个概念**, 但 PaliGemma 2 在 WebLI 上见过 Mario 的图像。这种"组合性"是 VLM 涌现能力的体现。

```text
   5 类复杂任务的成功率对比

   ┌─────────────────────────────────────────────────────────────┐

   │  叠衣服 (T-shirt)  < 10%    < 30%      65%       78%        │
   │  清理桌面          20%      35%        70%       85%        │
   │  整理餐具          15%      30%        60%       72%        │

   └─────────────────────────────────────────────────────────────┘
```

**注意**: 这些任务在**真实机器人**上评估, 不是仿真。成功率 = 10 次试验中完成任务的次数 (任务定义严格)。

**为什么 π0 大幅领先?**

三个原因:

1. **连续动作精度**: 叠衣服需要 1-2mm 精度对齐, 256 bin 远远不够
2. **长视野 (50 步 chunk)**: 叠衣服需要 60+ 步, π0 一次生成 50 步, RT-2 一次生成 7 步

### 5.2 零样本泛化:在未见过的物体上 work

π0 在**完全没见过的物体** 上的成功率:

```text
   零样本泛化测试 (训练时未见过这些物体)

   ┌──────────────────────────────────────────────────┐
   │  物体类型              RT-2     OpenVLA   π0       │
   │  ────────────────────────────────────────────────│

   └──────────────────────────────────────────────────┘
```

π0 在"新类别"和"抽象概念"上的优势, 来自 PaliGemma 2 在 WebLI 上的**视觉-语言预训练**。当指令说"Mario 玩偶", VLM 能用图像识别能力找到它, 即使机器人数据中没有 Mario 这个标签。

**直觉**: PaliGemma 2 看过 10B 张网络图片 (包括 Mario、海绵宝宝、Hello Kitty 等), 这些"概念" 在 LLM 内部已经有了。π0 用 VLM 作为 backbone, 自动继承这些知识。

### 5.3 长视野操作:50 步动作块

π0 一次生成 50 步动作 (1 秒 @ 50Hz), 开环执行, 然后重新观测。

```text
   长视野任务的"分块执行"

   ┌─────────────────────────────────────────────────────┐
   │  任务: "叠一件 T-shirt"                                │
   │  总步数: ~120 步 (2.4 秒)                            │
   │                                                      │
   │  Chunk 1 (步 1-50):   "接近 T-shirt"                 │
   │  Chunk 2 (步 51-100): "抓住 + 提起"                  │
   │  Chunk 3 (步 101-150):"对折 + 放下"                  │
   │                                                      │
   │  推理 3 次, 每次 30ms, 总推理时间 90ms              │
   │  执行 120 步, 总执行时间 2.4s                        │
   │  端到端: 2.4s + 0.09s ≈ 2.5 秒                       │
   └─────────────────────────────────────────────────────┘
```

**为什么 50 步 (不是 100 步)?**

权衡:
- 太大 (> 100 步): 开环累积误差, 失败率上升
- 太小 (< 20 步): 推理频率太高 (100Hz), 计算成本爆炸

π0 选 50 步, 因为**OOD 误差 (out-of-distribution)** 在 50 步内累积 < 5mm, 对大多数任务够用。

π0 训练用了 8 种机器人数据。**同种机器人 fine-tune 100 条演示**, 就能在**新形态机器人**上达到 70% 成功率 (vs 从零训练 30%)。

### 5.5 π0 的局限:三个仍未解决的问题

**局限 1: 仍需要 100+ 演示 fine-tune**

零样本 (无 fine-tune) 成功率 < 30%, 远低于"涌现" 预期。要达到 70%, 仍需要 100-1000 条客户演示。

**局限 2: 物理推理失败**

指令: "把鸡蛋放进杯子, 不要打碎"
- π0 的反应: 抓起鸡蛋 → 放下杯子
- 失败原因: 不理解"鸡蛋易碎" 这个物理属性

PaliGemma 2 在 WebLI 见过鸡蛋, 但物理交互的"软硬" "易碎" 不是 VLM 能学到的——这需要**触觉反馈** 和**力矩感知**, π0 目前不支持。

**局限 3: 多机器人协作**

π0 是**单机器人** 训练。多机器人协作 (如双臂递物) 仍是开放问题。

```text
   π0 能做 / 不能做 的任务边界

   能做 (70%+ 成功率):
     - 单臂抓取 (训练过的物体类别)
     - 双臂简单协作 (递物, 共同举起)
     - 长视野 (2-3 秒, 50 步)
     - 自然语言指令 (训练过的指令形式)

   不能做 / 困难:
     - 触觉推理 (鸡蛋易碎)
     - 多机器人协调 (>2 个)
     - 人类交互 (扶老人, 喂饭)
     - 工具使用 (用锤子, 用扳手)
     - 移动操作 (UR5 在固定桌面)
```

## 6. HiRT:层级 RT 的双层架构

### 6.1 为什么需要"层级":π0 的长 horizon 局限

π0 一次生成 50 步 (1 秒)。但**真实的家务任务**需要 30-60 秒, 即 1500-3000 步。

如果让 π0 直接生成 1500 步:
1. **计算成本爆炸**: 1500 步 token × 7 维 = 10K 输出, 推理 600ms
2. **OOD 累积误差**: 开环 1500 步, 误差累积到 5cm, 任务失败
3. **语义丢失**: LLM 不能"看未来 1500 步", 只能基于当前图像

**HiRT (Hierarchical RT)** 是 Belkhale et al. (2024) 提出的解法: **双层架构, 高层规划 + 低层控制**。

```text
   HiRT 的双层架构

   ┌─────────────────────────────────────────────────────────────┐
   │  高层 (High-Level Policy, 1Hz)                               │
   │                                                              │
   │  输入: 当前图像 + 指令                                       │
   │  模型: VLM (RT-2 风格, 离散 token)                           │
   │  输出: 子目标 (subgoal), 50 步 / 1 秒                        │
   │  例子: "移动到杯子前 10cm" / "抓住杯子" / "提起"            │
   │                                                              │
   │  ──────────────────────────────────────────────────────── │
   │                                                              │
   │  低层 (Low-Level Policy, 50Hz)                               │
   │                                                              │
   │  输入: 当前图像 + 子目标 + 本体状态                          │
   │  模型: 小型 Transformer (Flow Matching 或 token)             │
   │  输出: 7 维动作 (单步), 50Hz                                 │
   │                                                              │
   └─────────────────────────────────────────────────────────────┘
```

**类比**: 高层是"项目经理", 决定"下一步做什么"; 低层是"工程师", 决定"具体怎么做"。

### 6.2 高层 VLM:输出子目标 (subgoal)

HiRT 的高层用的是 **RT-2 风格的 VLM**, 输出**子目标** (subgoal), 不是原始动作。

子目标的定义 (Belkhale et al., 2024):

```text
   子目标的 4 种形式

   形式 1: 末端位姿目标
     - "末端到 (x=0.5, y=0.2, z=0.3), 姿态 (roll=0, pitch=π/2, yaw=0)"
     - 输出: 6 维 (位置 + 姿态), 整数化到 256 bin

   形式 2: 物体级目标
     - "抓住物体 A" / "把物体 B 放到 C 上"
     - 输出: 物体 ID + 关系 (抓/放/推)

   形式 3: 图像目标 (visual goal)
     - "让当前图像接近这张目标图像"
     - 输出: 目标图像的 latent embedding (用 VAE 编码)

   形式 4: 自然语言目标
     - "进入抓取预备姿态"
     - 输出: 语言 token (类似 RT-2)
```

**HiRT 选了形式 1 + 形式 4**: 末端位姿目标为主, 语言目标为辅 (用来指定高级动作如"释放")。

**为什么不用 Flow Matching 在高层?**

高层 VLM 的输出是**离散 token** (末端位姿的 256 bin), 适合 VLM 的 token 化生成。低层 Flow Matching 输出连续动作, 适合精细控制。**双层用不同范式, 各自最优**。

### 6.3 低层策略:Flow Matching 的 50Hz

低层策略是**专门的 Flow Matching Transformer**, 输入比高层更密集:

```python
class LowLevelPolicy(nn.Module):
    """
    HiRT 低层策略 (简化版)

    输入:
      - current_image: 当前图像 (B, 3, 224, 224)
      - subgoal: 高层输出的子目标 (B, subgoal_dim)
      - state: 本体状态 (B, state_dim)

    输出:
      - action: 7 维连续动作 (B, action_dim)
    """
    def __init__(self, action_dim=7, subgoal_dim=6, hidden=512, depth=8):
        super().__init__()
        self.vision_encoder = SigLIPSo400m()  # 共享高层
        self.subgoal_proj = nn.Linear(subgoal_dim, hidden)
        self.state_proj = nn.Linear(state_dim, hidden)

        # 小型 transformer
        self.transformer = TransformerEncoder(
            num_layers=depth,
            d_model=hidden,
            nhead=8,
        )

        # Flow Matching 头
        self.flow_head = FlowMatchingHead(hidden, action_dim)

    def forward(self, current_image, subgoal, state):
        # 视觉编码
        vision_tokens = self.vision_encoder(current_image)  # (B, 256, 1152)
        # 投影到统一 hidden
        vision_tokens = vision_tokens[:, :, :hidden]
        # 拼接子目标和状态
        sg_embed = self.subgoal_proj(subgoal).unsqueeze(1)
        s_embed = self.state_proj(state).unsqueeze(1)
        full_seq = torch.cat([vision_tokens, sg_embed, s_embed], dim=1)
        # Transformer
        features = self.transformer(full_seq)  # (B, T, hidden)
        # Flow Matching 预测向量场
        v = self.flow_head(features[:, -1])  # 用最后一帧
        return v
```

**为什么低层用 Flow Matching (而不是 token 化)?**

低层需要**毫秒级**推理 + **毫米级**精度。Flow Matching 10 步 ODE ≈ 5ms, 比 token 化的 7 token 自回归 (≈ 30ms) 快 6 倍。

**训练数据**: 低层用**专家演示** (human teleop), 高层用**子目标标注** (人工标 "现在该抓了", "现在该放了")。

### 6.4 在多步任务的应用:HiRT vs π0

HiRT 在 3 类长视野任务上的对比:

```text
   长视野任务对比 (跨 3 种机器人)

   ┌──────────────────────────────────────────────────────────┐
   │  任务              π0 (50 步)     HiRT (1Hz+50Hz)        │
   │  ────────────────────────────────────────────────────────│
   │  整理整个桌面       45%           70%                    │
   │  做饭 (简单食谱)    20%           55%                    │
   │  叠 5 件衣服        30%           60%                    │
   │  擦窗户             40%           65%                    │
   │  ────────────────────────────────────────────────────────│
   │  推理频率           10Hz          高层 1Hz + 低层 50Hz    │
   │  单步延迟           30ms          高层 100ms + 低层 5ms  │
   │  总推理 (60s 任务)  600ms         6000ms (高层) + 3000ms │
   └──────────────────────────────────────────────────────────┘
```

**HiRT 的优势**:
1. **长 horizon**: 高层 1Hz, 一小时任务也能规划
2. **错误恢复**: 高层每 1 秒重新规划, 子目标错了可以纠错
3. **语义清晰**: 高层输出人类可读的子目标 (debug 友好)

**HiRT 的劣势**:
1. **复杂**: 需要两层训练数据 (高层子目标 + 低层演示)
2. **误差传播**: 低层不能达到子目标 → 高层规划错位

### 6.5 HiRT 的工程细节:子目标的设计空间

子目标的形式对 HiRT 性能影响巨大。Belkhale et al. (2024) 做了 ablation:

```text
   子目标形式的对比实验

   ┌──────────────────────────────────────────────────────┐
   │  子目标形式              任务成功率    训练数据量      │
   │  ──────────────────────────────────────────────────│
   │  末端位姿 (xyz + rpy)    70%           100 条/任务    │
   │  物体级 (抓 A / 放 B)    60%           50 条/任务     │
   │  图像目标 (VAE latent)   65%           200 条/任务    │
   │  自然语言                50%           500 条/任务    │
   │  ──────────────────────────────────────────────────│
   │  最优: 末端位姿 (简洁, 数据少, 精度高)             │
   └──────────────────────────────────────────────────────┘
```

**为什么末端位姿最好?**

三个原因:
1. **精度足够**: 末端位姿的 6 个数能覆盖所有家务任务
2. **训练数据少**: 末端位姿可从演示轨迹自动提取, 无需人工标注
3. **低层可执行**: Flow Matching 天然接受 6 维目标, 转 7 维动作 (加 gripper)

**工业选择**: 90% 的工业 HiRT 系统用末端位姿子目标。

## 7. PyTorch 实验:从零实现 Flow Matching VLA

### 7.1 Flow Matching 简化版:30 行核心代码

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class SimpleFlowMatching(nn.Module):
    """
    最简 Flow Matching 网络 (CPU 可跑, 30 行)
    输入: x_t (噪声动作), t (时间), cond (条件向量)
    输出: v (向量场)
    """
    def __init__(self, action_dim=4, cond_dim=8, hidden=64):
        super().__init__()
        self.t_embed = nn.Sequential(
            nn.Linear(1, hidden), nn.SiLU(),
            nn.Linear(hidden, hidden),
        )
        self.net = nn.Sequential(
            nn.Linear(action_dim + cond_dim + hidden, hidden),
            nn.SiLU(),
            nn.Linear(hidden, hidden),
            nn.SiLU(),
            nn.Linear(hidden, action_dim),
        )

    def forward(self, x_t, t, cond):
        # t: (B,)
        t_emb = self.t_embed(t.unsqueeze(-1))  # (B, hidden)
        # 拼接 x_t, cond, t_emb
        h = torch.cat([x_t, cond, t_emb], dim=-1)
        return self.net(h)


def train_flow_matching(model, dataset, n_epochs=1000, lr=1e-3):
    """Flow Matching 训练循环"""
    optim = torch.optim.Adam(model.parameters(), lr=lr)
    for epoch in range(n_epochs):
        x_1, cond = dataset.sample(batch_size=64)  # 真实动作 + 条件
        x_0 = torch.randn_like(x_1)                # 噪声
        t = torch.rand(len(x_1))                   # 时间

        # 线性插值
        x_t = (1 - t.view(-1, 1)) * x_0 + t.view(-1, 1) * x_1
        # 真实向量场
        v_target = x_1 - x_0
        # 预测
        v_pred = model(x_t, t, cond)
        # 简单 MSE
        loss = F.mse_loss(v_pred, v_target)

        optim.zero_grad()
        loss.backward()
        optim.step()

        if epoch % 200 == 0:
            print(f"Epoch {epoch}, loss: {loss.item():.4f}")


@torch.no_grad()
def inference(model, cond, n_steps=10, action_dim=4):

    x = torch.randn(1, action_dim)  # 从噪声出发
    dt = 1.0 / n_steps
    for i in range(n_steps):
        t = torch.tensor([i * dt])
        v = model(x, t, cond)
        x = x + dt * v
    return x
```

### 7.2 π0 推理代码 (Toy):完整闭环

```python
class ToyPaliGemma(nn.Module):
    """PaliGemma 2 的玩具替代: 把图像 + 指令编码成 hidden 序列"""
    def __init__(self, hidden=128):
        super().__init__()
        self.vision_proj = nn.Linear(3 * 16 * 16, hidden)  # 16x16 玩具图
        self.text_proj = nn.Linear(8, hidden)              # 8 维玩具指令
        self.fusion = nn.TransformerEncoder(
            nn.TransformerEncoderLayer(hidden, nhead=4, dim_feedforward=hidden*4, batch_first=True),
            num_layers=2,
        )

    def forward(self, image, instruction):
        # image: (B, 3, 16, 16), instruction: (B, 8)
        B = image.shape[0]
        img_flat = image.view(B, -1)
        img_embed = self.vision_proj(img_flat).unsqueeze(1)  # (B, 1, hidden)
        text_embed = self.text_proj(instruction).unsqueeze(1)  # (B, 1, hidden)
        seq = torch.cat([img_embed, text_embed], dim=1)
        return self.fusion(seq)  # (B, 2, hidden)


class ToyPi0(nn.Module):
    """π0 的玩具实现"""
    def __init__(self, action_dim=4, state_dim=4, horizon=8):
        super().__init__()
        self.vlm = ToyPaliGemma(hidden=128)
        self.action_expert = SimpleFlowMatching(action_dim, cond_dim=128+state_dim, hidden=64)
        self.state_proj = nn.Linear(state_dim, 128)
        self.horizon = horizon

    def forward(self, image, instruction, state, x_t, t):
        vlm_features = self.vlm(image, instruction)  # (B, 2, 128)
        vlm_pooled = vlm_features.mean(dim=1)        # (B, 128)
        state_emb = self.state_proj(state)            # (B, 128)
        cond = torch.cat([vlm_pooled, state_emb], dim=-1)  # (B, 256)
        # x_t: (B, horizon, action_dim) → 展平到 (B, horizon * action_dim)
        B = x_t.shape[0]
        x_flat = x_t.view(B, -1)
        # 每个时间步独立预测向量
        v_flat = self.action_expert(x_flat, t, cond)
        return v_flat.view(B, self.horizon, -1)


@torch.no_grad()
def pi0_inference(model, image, instruction, state, n_steps=10):
    """π0 推理: VLM 编码 + Flow Matching 求解"""
    # 1. VLM 编码 (一次性)
    vlm_features = model.vlm(image, instruction)
    vlm_pooled = vlm_features.mean(dim=1)
    state_emb = model.state_proj(state)
    cond = torch.cat([vlm_pooled, state_emb], dim=-1)

    # 2. Flow Matching 求解
    action_dim = 4
    horizon = 8
    x = torch.randn(1, horizon * action_dim)
    dt = 1.0 / n_steps
    for i in range(n_steps):
        t = torch.tensor([i * dt])
        v = model.action_expert(x, t, cond)
        x = x + dt * v

    return x.view(1, horizon, action_dim)

        # 指令: 8 维 one-hot-ish
        instruction = torch.zeros(batch_size, 8)
        instruction[:, 0] = 1.0  # "push"
        # 状态: 4 维随机
        state = torch.randn(batch_size, 4)

        action = torch.zeros(batch_size, 8, 4)
```

### 7.3 HiRT 两阶段 Demo

```python
class HiRTHighLevel(nn.Module):
    """HiRT 高层: 输出子目标 (末端位姿)"""
    def __init__(self, subgoal_dim=6, hidden=128):
        super().__init__()
        self.vlm = ToyPaliGemma(hidden=hidden)
        self.subgoal_head = nn.Linear(hidden, subgoal_dim)

    def forward(self, image, instruction):
        features = self.vlm(image, instruction)
        subgoal = self.subgoal_head(features.mean(dim=1))
        return subgoal  # (B, 6): [x, y, z, roll, pitch, yaw]


class HiRTLowLevel(nn.Module):
    """HiRT 低层: 输出 50Hz 动作"""
    def __init__(self, action_dim=7, subgoal_dim=6, state_dim=7, hidden=64):
        super().__init__()
        self.action_expert = SimpleFlowMatching(
            action_dim=action_dim,
            cond_dim=hidden + subgoal_dim + state_dim,
            hidden=hidden,
        )
        self.vision_proj = nn.Linear(3 * 16 * 16, hidden)
        self.subgoal_proj = nn.Linear(subgoal_dim, hidden)
        self.state_proj = nn.Linear(state_dim, hidden)

    def forward(self, image, subgoal, state, x_t, t):
        vision_feat = self.vision_proj(image.view(image.shape[0], -1))
        sg_feat = self.subgoal_proj(subgoal)
        s_feat = self.state_proj(state)
        cond = torch.cat([vision_feat, sg_feat, s_feat], dim=-1)
        return self.action_expert(x_t, t, cond)


def hirt_inference(high_level, low_level, image, instruction, state, n_steps=10):
    """HiRT 完整推理: 高层 → 子目标 → 低层 → 动作"""
    # 1. 高层: VLM 编码 + 输出子目标
    subgoal = high_level(image, instruction)  # (1, 6)

    # 2. 低层: Flow Matching 求解动作
    action_dim = 7
    x = torch.randn(1, action_dim)
    dt = 1.0 / n_steps
    for i in range(n_steps):
        t = torch.tensor([i * dt])
        v = low_level(image, subgoal, state, x, t)
        x = x + dt * v

    return x, subgoal
```

**自检**: 推理应返回 (action, subgoal), action ≈ 由 subgoal 决定的"接近子目标"的动作。

## 9. 与数学基础的关系:三处高复用

### 9.1 数学基础/7-系统思维/案例10-Diffusion ← Flow Matching

**Diffusion 是 Flow Matching 的前身**。本章的 §3 直接对应数学基础/7-系统思维/案例10 的扩散模型部分。

**关键复用点**:
- **前向过程**: Diffusion 用随机加噪, Flow Matching 用确定性插值——两者极限一致 ($p_0$ = 噪声, $p_1$ = 数据)
- **反向过程**: Diffusion 学 $\epsilon_\theta(x_t, t)$, Flow Matching 学 $v_\theta(x_t, t)$——变量替换线性等价
- **SDE vs ODE**: Diffusion 用反向 SDE, Flow Matching 用 ODE——后者更简单

```text
   数学基础/7-系统思维/案例10-Diffusion ←→ 本章 §3 Flow Matching

   ┌──────────────────────────┐    ┌──────────────────────────┐
   │  案例10                   │    │  本章 §3                  │
   │  - 前向加噪 (随机)        │    │  - 前向插值 (确定性)      │
   │  - 反向去噪 (SDE)         │    │  - 反向 ODE (更简单)      │
   │  - 训练: 预测噪声 ε      │    │  - 训练: 预测向量 v      │
   │  - 推理: 100 步           │    │  - 推理: 10 步            │
   │  - 应用: 图像/视频生成    │    │  - 应用: 机器人动作生成   │
   └──────────────────────────┘    └──────────────────────────┘
              ↓                                ↓
   数学工具一致: 高斯分布, 随机过程, ODE 求解, 率失真理论
```

**核心洞察**: Flow Matching 把 Diffusion 的"加噪-去噪"重新表述为"插值-求向量场", 数学更优雅, 工程更快。

π0 的 VLM backbone 是 PaliGemma 2, 内部是 Transformer。本章 §2.2 直接对应数学基础/7-系统思维/案例14。

## 10. 常见误区:π0 的 8 个"听起来对但实际错"

### 10.1 "π0 = RT-2 + Flow Matching"

**错**。π0 不只是"RT-2 加一个 Flow Matching 头"。

真实差异:
1. **Backbone 不同**: RT-2 用 PaLI-X (12B), π0 用 PaliGemma 2 (3B)
2. **训练数据不同**: RT-2 用 13 万 Google Robot 演示, π0 用 10B+ token 跨形态数据
3. **动作专家**: π0 的动作专家是专门架构 (cross-attention + time embedding), 不是简单头
4. **PaliGemma 2 的视觉泛化**: π0 继承了 WebLI 上的 10B 图文对, 这是 RT-2 (PaLI-X) 也有的能力, 但 π0 更彻底

**关键**: π0 是一个**重新设计的端到端 VLA**, 不是 RT-2 的小修小补。

### 10.2 "Flow Matching 总是比 Diffusion 好"

**错**。Flow Matching 在**连续动作 + 充足数据 + 实时推理** 场景下更好, 但其他场景不一定。

经验法则:
| 场景 | 推荐 | 理由 |
| :--- | :--- | :--- |
| 桌面 7 DoF, 数据 > 10K | Flow Matching | 精度高, 推理快 |
| 桌面 7 DoF, 数据 < 1K | Diffusion | 训练更稳定 |
| 灵巧手 14+ DoF | Flow Matching | 必须高精度 |
| 多模态动作分布 | Diffusion | 随机性避免平均 |
| 视频/音频生成 | Diffusion | 仍占主流 |

### 10.3 "π0 是端到端的"

**部分错**。π0 的"端到端"指的是**从图像 + 指令到动作**直接输出, 但训练数据是**分阶段**的:
1. PaliGemma 2 在 WebLI 上预训练 (Google 的工作)
2. 跨形态机器人数据微调
3. 客户演示 fine-tune
4. (可选) RLHF 微调

所以严格说, π0 不是"一个网络从零训到底", 而是"基础模型 + 微调" 的工程系统。

### 10.4 "π0 解决了所有机器人问题"

**错**。π0 在 §5.5 列出的局限仍未解决:
- 触觉推理 (鸡蛋易碎)
- 工具使用 (锤子、扳手)
- 多机器人协调
- 人类交互

**目前最强 VLA 仍需要 fine-tune, 仍做不到完全 zero-shot**。

### 10.5 "HiRT 是 π0 的升级版"

**错**。HiRT 和 π0 是**正交**的两个项目:
- π0 是 Physical Intelligence 的模型
- HiRT 是 Google DeepMind 的架构 (Belkhale et al., 2024)
- π0 可以用 HiRT 风格分层 (高层输出子目标, 低层 Flow Matching)
- π0 也可以不用 HiRT 风格 (端到端 50 步动作)

它们是"配合"而不是"升级"关系。

### 10.6 "π0 是开源的"

**错**。π0 论文 (Black et al., 2024) 公开了, 但**模型权重未开源** (截至 2026 年)。Physical Intelligence 的商业模式是"卖 fine-tuning 服务", 不是"卖模型"。

开源 VLA 的选择:
- OpenVLA (Stanford/Berkeley, 7B)
- Octo (Berkeley, 27M)
- RT-1 / RT-2 (Google 部分开源)

如果想自己跑 π0 类似的实验, 用 OpenVLA 7B + Flow Matching 头改造, 是最佳开源选择。

### 10.7 "π0 离 AGI 已经很近"

**错**。π0 在**结构化家务任务**上达到 65-85%, 但离 AGI 还有几个数量级:

## 11. L7/L8 面试 Q&A

### Q1: π0 vs OpenVLA 的核心差异是什么?

**A**: 三个核心差异:

1. **动作生成**: π0 用 Flow Matching (连续), OpenVLA 用 token 化 (离散)
   - π0 精度 1mm, OpenVLA 精度 4mm
2. **Backbone**: π0 用 PaliGemma 2 (3B), OpenVLA 用 LLaMA-2 (7B)
   - π0 推理 30ms, OpenVLA 推理 100ms
3. **训练数据**: π0 用 10B+ token 跨形态, OpenVLA 用 970K 轨迹 Open X-Embodiment
   - π0 跨 8 种机器人, OpenVLA 主要在单一类

追问: "为什么 π0 选 PaliGemma 2 而不是 LLaMA-2?"
→ PaliGemma 2 原生多模态, 视觉 token 已经在 LLM 输入空间, 无需额外 projector; Gemma 2 比 LLaMA-2 训练更稳定 (RMSNorm + GeGLU); 3B 比 7B 推理快 2x, 适合实时控制。

### Q2: Flow Matching 的数学是什么? 训练目标?

**A**: 数学核心是**学一个 ODE 向量场**:

1. **前向 (训练时模拟)**: 从噪声 $x_0 \sim \mathcal{N}(0, I)$ 线性插值到真实数据 $x_1$:
   $$x_t = (1 - t) x_0 + t x_1, \quad t \in [0, 1]$$

2. **真实向量场**: $v_t(x_t) = x_1 - x_0$ (闭式解)

3. **训练目标**: 神经网络 $v_\theta(x_t, t)$ 拟合真实向量场:
   $$\mathcal{L}_{\text{FM}} = \mathbb{E}_{t, x_0, x_1} \left[ \| v_t(x_t) - v_\theta(x_t, t) \|^2 \right]$$

4. **推理 (Euler ODE)**: 从噪声出发, 沿向量场积分:
   $$x_{t + \Delta t} = x_t + \Delta t \cdot v_\theta(x_t, t)$$

追问: "和 Diffusion 的关系?"
→ 数学等价 (通过变量替换), 但 Flow Matching 用 ODE 替代 SDE, 推理路径更直, 步数从 100 降到 10。

### Q3: HiRT 的双层架构是什么? 为什么需要它?

**A**: 双层架构:
- **高层 (1Hz)**: VLM (RT-2 风格), 输入图像+指令, 输出子目标 (末端位姿, 6 维)
- **低层 (50Hz)**: Flow Matching Transformer, 输入图像+子目标+状态, 输出 7 维动作

**为什么需要**:
1. **长 horizon**: 高层 1Hz 规划 30-60 秒任务, 低层 50Hz 执行
2. **错误恢复**: 高层每 1 秒重新规划, 子目标错了可以纠错
3. **语义清晰**: 高层输出人类可读的子目标, debug 友好

追问: "π0 不用 HiRT 是怎么做的?"
→ π0 用"动作块" (50 步), 端到端生成, 开环执行 50 步后重新观测。简单但 horizon 受限 (~2 秒)。HiRT 把 horizon 扩展到 60 秒, 但需要标注子目标训练数据。

### Q4: π0 的训练数据是什么?

**A**: π0 训练用三类数据:
1. **跨形态演示**: 8 种机器人 (UR5, Franka, Aloha, Aloha 2, Google Robot, Toyota HSR, Figure 02), 累计 ~10B token 等效
2. **Open X-Embodiment**: 学术界 60+ 数据集, 1M+ 轨迹
3. **PaliGemma 2 预训练**: WebLI 10B 图文对 (Google 提供)

训练资源: 36 H100 × 7 天 ≈ 6K H100-hour。

追问: "客户 fine-tune 需要多少数据?"
→ 100-1000 条演示 + 24 小时 H100, 即可达到 70% 成功率。这是"卖 fine-tuning 服务" 的工程基础。

### Q5: π0 离 AGI 还有多远?

**A**: π0 在**结构化家务任务**上达到 65-85%, 但离"机器人 AGI"还有几个数量级:

| 能力维度 | 当前 π0 | "AGI" 所需 | 差距 |
| :--- | :--- | :--- | :--- |
| 数据规模 | 10B token | 1T+ token | 100x |
| 任务成功率 | 70% (结构化家务) | 95%+ (任意任务) | 大 |
| 触觉推理 | 无 | 必需 | 缺 |
| 工具使用 | 无 | 必需 | 缺 |
| 元学习 | 无 (100 条 fine-tune) | 5 条学会 | 20x 差距 |
| 多机器人协调 | 弱 | 必需 | 缺 |
| 持续学习 | 无 | 必需 | 缺 |

**工程路径已清晰, 但每个差距都是 1-3 年研究投入**。π0 是"开始", 不是"结束"。

追问: "为什么不用更大的模型?"
→ 实时推理要求 50Hz (20ms), 3B VLM + 300M 动作专家已经接近上限。更大的模型需要模型压缩 (量化 + 蒸馏), 这是 2025-2027 的工作。

### Q6: π0 怎么做到 50Hz 实时控制?

**A**: 四个 trick 配合:
1. **动作块 (Action Chunking)**: 一次生成 50 步, 开环执行, 摊销推理时间
2. **Flow Matching 步数少**: 10 步 Euler ODE, 比 Diffusion 100 步快 10x
3. **KV cache 复用**: VLM 编码新图像时, 语言 token 的 KV cache 复用
4. **量化推理 (π0-FAST)**: VLM 用 INT8 量化, 推理时间从 30ms 压到 15ms

最终: 单步推理 30ms, 开环执行 50 步, 控制频率 50Hz (1 秒 10 次推理 × 5 开环步)。

### Q7: π0 的动作专家为什么是 cross-attention 而不是 MLP?

**A**: 三个原因:
1. **VLM 输出是序列**: VLM 输出 ~256+ 个 token (256 vision + 20 language), 需要保留每个 token 的语义
2. **动作 token 需要"查询" VLM**: 不同动作维度对应 VLM 不同部分 (末端位置对应视觉 token, 抓取对应语言 token), cross-attention 自然分配
3. **可扩展**: 增加 VLM 层数不影响动作专家, 反之亦然

MLP (把 VLM 输出平均成一个向量) 会丢失细节, 性能差 20%。

### Q8: π0 用了多少算力训练?

**A**: 完整 post-training 用 36 H100 × 7 天 ≈ 6K H100-hour, 折算费用 ≈ $60K (云服务 $10/H100-hour)。RLHF 微调额外 50 H100 × 3 天 ≈ 4K H100-hour。

对比:
- OpenVLA: 64 A100 × 14 天 ≈ 21K A100-hour ≈ 42K H100-hour (等价)
- π0: 6K H100-hour (便宜 7x, 因为 PaliGemma 2 预训练免费 + 动作专家小)

**对工业部署的意义**: 客户给 1000 条演示 + 24 小时 H100, fine-tune 出"客户专属 π0", 成本 ≈ $5K。

## 14. π0 Flow Matching 深度拆解

前面 1-13 节把 π0 当"黑盒"讲了。这一节我们把它拆开,看 Flow Matching 这把"手术刀"到底怎么切动作空间。

### 14.1 Flow Matching 的概率路径

先回忆 Diffusion Policy (Chi et al. 2023) 干了什么:加噪 $\to$ 去噪。Flow Matching (Lipman et al. 2023) 换了条路:学一个 ODE 的向量场。

**Diffusion 的概率路径**:
$$x_t = \alpha_t x_1 + \sigma_t \epsilon, \quad \epsilon \sim \mathcal{N}(0, I)$$
其中 $\alpha_t^2 + \sigma_t^2 = 1$, $t \in [0, 1]$, $x_1$ 是真实动作, $x_0 \sim \mathcal{N}(0, I)$ 是噪声。

**Flow Matching 的概率路径** (Linear Optimal Transport):
$$x_t = (1 - t) x_0 + t x_1, \quad x_0 \sim \mathcal{N}(0, I)$$
简单到极致:从噪声到动作是一条直线 (linear interpolation)。

**目标向量场**:
$$u_t(x_t) = x_1 - x_0$$
也就是从噪声指向真实动作的"速度向量"。

**网络学什么**:
$$v_\theta(x_t, t) \approx u_t(x_t)$$
推理时,沿 ODE 积分:
$$x_{t+dt} = x_t + v_\theta(x_t, t) \cdot dt$$

**关键差异**:Diffusion 学的是"去噪残差" $\epsilon_\theta(x_t, t)$,Flow Matching 学的是"瞬时速度" $v_\theta(x_t, t)$。两者数学等价 (因为 $\epsilon$ 和 $v$ 可互相换算),但 Flow Matching 的训练目标更"自然",对应着一条直线路径,所以积分步数可以少 5-10 倍。

```text
   Diffusion Policy: 50 步 DDIM
   ┌────┐  ┌────┐  ┌────┐  ┌────┐  ...   50 步
   │ x_t├─>│x_t'├─>│x_t├─>│x_t'├─>
   └────┘  └────┘  └────┘  └────┘

   π0 Flow Matching: 10 步 Euler
   ┌────┐  ┌────┐  ┌────┐
   │ x_t├──>│x_t'├──>│x_t'├──> ...   10 步 (等距大步长)
   └────┘  └────┘  └────┘

   每步走的"距离"长, 步数少 5x
   → 推理频率从 3Hz 提到 10Hz (π0) / 50Hz (π0-FAST)
```

### 14.3 PyTorch 实现:Flow Matching Action Head (完整可跑)

这段代码是 π0 动作头的最小实现。CPU 可跑, 30 行内。

```python
import torch
import torch.nn as nn
import math

class SinusoidalTimeEmbedding(nn.Module):
    """把时间 t ∈ [0, 1] 编码成高频向量"""
    def __init__(self, dim: int):
        super().__init__()
        self.dim = dim

    def forward(self, t: torch.Tensor) -> torch.Tensor:
        half = self.dim // 2
        freqs = torch.exp(-math.log(10000) * torch.arange(half) / half).to(t.device)
        args = t[:, None].float() * freqs[None]
        return torch.cat([torch.sin(args), torch.cos(args)], dim=-1)


class FlowMatchingActionHead(nn.Module):
    """
    π0 风格的 Flow Matching 动作头。
    输入: 噪声 x_0 + 时间 t + VLM context (条件)
    输出: 向量场 v_θ(x_t, t) ∈ R^{action_dim}
    """
    def __init__(self, action_dim: int = 16, cond_dim: int = 1024, hidden: int = 512):
        super().__init__()
        self.time_embed = SinusoidalTimeEmbedding(hidden)
        self.cond_proj = nn.Linear(cond_dim, hidden)
        self.net = nn.Sequential(
            nn.Linear(action_dim + 2 * hidden, hidden), nn.SiLU(),
            nn.Linear(hidden, hidden), nn.SiLU(),
            nn.Linear(hidden, hidden), nn.SiLU(),
            nn.Linear(hidden, action_dim),
        )

    def forward(self, x_t: torch.Tensor, t: torch.Tensor, cond: torch.Tensor) -> torch.Tensor:
        """v_θ(x_t, t, cond)"""
        t_emb = self.time_embed(t)              # (B, hidden)
        c_emb = self.cond_proj(cond)            # (B, hidden)
        h = torch.cat([x_t, t_emb, c_emb], -1)  # (B, action_dim + 2*hidden)
        return self.net(h)


def flow_matching_loss(model, x_1, cond):
    """
    训练损失: 随机采 t ∈ [0,1], 学目标向量场 u_t = x_1 - x_0。
    """
    B = x_1.shape[0]
    x_0 = torch.randn_like(x_1)                   # 噪声
    t = torch.rand(B, device=x_1.device)          # 随机时间步
    t_b = t[:, None]                              # 广播
    x_t = (1 - t_b) * x_0 + t_b * x_1             # 线性插值
    target_v = x_1 - x_0                          # 真实向量场
    pred_v = model(x_t, t, cond)                  # 预测向量场
    return ((pred_v - target_v) ** 2).mean()


@torch.no_grad()
def euler_sample(model, cond, action_dim: int = 16, n_steps: int = 10):
    """
    Euler ODE 求解器, 从噪声积分到动作。
    推理时调用, 输出 action_chunk。
    """
    x = torch.randn(1, action_dim, device=cond.device)
    dt = 1.0 / n_steps
    for i in range(n_steps):
        t = torch.full((1,), i * dt, device=cond.device)
        v = model(x, t, cond)
        x = x + v * dt
    return x  # 动作序列 (此处单步, 实际可扩展到 chunk)


# ponytail: 这是简化版, 真实 π0 用 Transformer + cross-attention 接 VLM tokens
if __name__ == "__main__":
    model = FlowMatchingActionHead(action_dim=16, cond_dim=1024)
    x_1 = torch.randn(8, 16)         # 真实动作 batch
    cond = torch.randn(8, 1024)      # VLM 输出
    loss = flow_matching_loss(model, x_1, cond)
    print(f"loss={loss.item():.4f}")  # 应在 ~1.0 附近 (随机初始化)
    action = euler_sample(model, cond)
    print(f"action shape={action.shape}")  # (1, 16)
```

**关键设计选择**:
1. **线性插值** $x_t = (1-t)x_0 + tx_1$ 而非线性 (cosine, VP): π0 选了最简单的"直线",因为线性对应最优传输 (optimal transport),积分误差最小。
2. **10 步 Euler** 而不是 50 步 DDIM:π0 论文 (Black et al. 2024) 报告 10 步的 FID 指标已逼近 50 步 (差距 < 2%),速度优势压倒精度损失。
3. **Action Expert 独立于 VLM**: 300M 参数的小 Transformer,不污染 VLM 的语言能力 (类似 MoE 设计)。

### 14.4 训练目标的数学细节

Flow Matching 的损失函数有两种等价写法 (Lipman et al. 2023):

**Conditional Flow Matching (CFM, π0 用这个)**:
$$\mathcal{L}_{CFM} = \mathbb{E}_{t, x_0, x_1} \|v_\theta(x_t, t) - (x_1 - x_0)\|^2$$

**Flow Matching (FM, 理论)**:
$$\mathcal{L}_{FM} = \mathbb{E}_{t, x_t} \|v_\theta(x_t, t) - u_t(x_t)\|^2$$
其中 $u_t(x_t)$ 是 marginal 向量场,需要在整个数据分布上积分,不可计算。

Lipman 等人证明:$\nabla \mathcal{L}_{CFM} = \nabla \mathcal{L}_{FM}$,所以 CFM 是 FM 的无偏估计,直接用就行。

**Simulator-based 视角** (另一套等价说法):
$$\mathcal{L}_{SM} = \mathbb{E}_{t, x_0, x_1} \|v_\theta(x_t, t) - \dot{x}_t\|^2$$
其中 $\dot{x}_t = \frac{d x_t}{dt} = x_1 - x_0$ (线性插值下)。

三种说法,一个梯度,选最简单的 CFM。

## 15. HiRT 层级策略完整实现

### 15.1 HiRT 的两层架构

HiRT (Hierarchical Robot Transformer, Belkhale et al. 2024) 是 Stanford 的 Sergey Levine 团队的工作,核心思想:高层规划"做什么",低层执行"怎么做"。

```text
   HiRT 时间尺度
   ┌────────────────────────────────────────────┐
   │ High-Level VLM (1 Hz)                      │
   │ 输入: 图像 + 语言指令                       │
   │ 输出: subgoal embedding (subgoal_id + 描述) │
   │ 网络: Frozen PaliGemma 2B                  │
   │                                                │
   │      ↓ 每 1 秒更新一次 subgoal                │
   │                                                │
   │ Low-Level Policy (50 Hz)                     │
   │ 输入: 当前状态 + subgoal + 历史动作           │
   │ 输出: 7-DoF 动作 + 夹爪                       │
   │ 网络: 50M Transformer (从头训练)              │
   │                                                │
   │      ↓ 每 20ms 控制一次                       │
   │                                                │
   │ Robot Actuator                                │
   └────────────────────────────────────────────┘
```

**为什么分层?**
- **问题**:单层 VLA 处理"叠 T 恤"需要 30 步规划,但 30 步推理就要 3 秒 (3Hz),反应太慢。
- **解法**:高层只规划"宏观子目标" (例如"抓起左袖"),低层快速执行 (50Hz)。
- **频率对比**:单层 π0 10Hz (叠衣服成功 65%), HiRT 50Hz (叠衣服成功 80%)。

### 15.2 PyTorch 实现:HiRT 双层策略

```python
import torch
import torch.nn as nn
from typing import Optional


class HighLevelSubgoalHead(nn.Module):
    """
    高层 VLM 头: 输出 subgoal token。
    实际中复用 PaliGemma 2B 的最后一层, 这里做最小示意。
    """
    def __init__(self, n_subgoals: int = 256, hidden: int = 1024):
        super().__init__()
        self.proj = nn.Linear(hidden, n_subgoals)

    def forward(self, vision_tokens: torch.Tensor, lang_tokens: torch.Tensor) -> torch.Tensor:
        """v_tokens: (B, N_v, D), l_tokens: (B, N_l, D) → subgoal logits"""
        pooled = (vision_tokens.mean(1) + lang_tokens.mean(1)) / 2
        return self.proj(pooled)  # (B, n_subgoals)


class LowLevelTransformer(nn.Module):
    """
    低层策略: 50Hz, 50M 参数。
    输入: 状态 + subgoal + 历史, 输出: 动作。
    """
    def __init__(self, state_dim: int = 14, subgoal_dim: int = 256,
                 action_dim: int = 14, hidden: int = 256, n_heads: int = 4):
        super().__init__()
        self.state_proj = nn.Linear(state_dim, hidden)
        self.subgoal_proj = nn.Linear(subgoal_dim, hidden)
        self.hist_proj = nn.Linear(action_dim, hidden)
        self.pos_emb = nn.Parameter(torch.randn(1, 32, hidden) * 0.02)
        layer = nn.TransformerEncoderLayer(hidden, n_heads, hidden * 4,
                                           batch_first=True, activation="gelu")
        self.transformer = nn.TransformerEncoder(layer, num_layers=4)
        self.action_head = nn.Linear(hidden, action_dim)

    def forward(self, state: torch.Tensor, subgoal: torch.Tensor,
                hist_actions: torch.Tensor) -> torch.Tensor:
        """
        state:        (B, state_dim)
        subgoal:      (B, subgoal_dim)
        hist_actions: (B, T_hist, action_dim) — 最近 32 步历史
        """
        s = self.state_proj(state).unsqueeze(1)        # (B, 1, H)
        g = self.subgoal_proj(subgoal).unsqueeze(1)    # (B, 1, H)
        h = self.hist_proj(hist_actions)                # (B, T_hist, H)
        seq = torch.cat([s, g, h], dim=1) + self.pos_emb[:, :s.size(1)+h.size(1)]
        out = self.transformer(seq)
        return self.action_head(out[:, 0])              # 用 state+subgoal token 输出


class HiRT(nn.Module):
    """HiRT 完整两层"""
    def __init__(self, n_subgoals: int = 256, vlm_dim: int = 1024):
        super().__init__()
        self.high = HighLevelSubgoalHead(n_subgoals, vlm_dim)
        self.low = LowLevelTransformer(subgoal_dim=n_subgoals)

    @torch.no_grad()
    def step(self, vision_tokens, lang_tokens, state, hist_actions, n_low_steps: int = 50):
        """
        一步高层推理 + n_low_steps 步低层推理。
        高层 1Hz, 低层 50Hz。
        """
        subgoal_logits = self.high(vision_tokens, lang_tokens)
        subgoal_emb = torch.softmax(subgoal_logits, dim=-1)
        actions = []
        for _ in range(n_low_steps):
            a = self.low(state, subgoal_emb, hist_actions)
            actions.append(a)
            hist_actions = torch.cat([hist_actions[:, 1:], a.unsqueeze(1)], dim=1)
        return torch.stack(actions, dim=1)  # (B, n_low_steps, action_dim)


# ponytail: 高层 VLM 在真实 HiRT 中是 frozen PaliGemma 2B, 这里用 placeholder
if __name__ == "__main__":
    model = HiRT()
    v = torch.randn(1, 256, 1024)
    l = torch.randn(1, 32, 1024)
    s = torch.randn(1, 14)
    h = torch.randn(1, 32, 14)
    chunk = model.step(v, l, s, h, n_low_steps=10)
    print(f"action chunk: {chunk.shape}")  # (1, 10, 14)
```

**关键设计**:
- **高层只输出 subgoal embedding**,不直接输出动作,避免 1Hz 推理的速度瓶颈。
- **低层 50M 参数**(对比高层 2B),部署时低层可跑在机器人上的小 NPU (如 Jetson Orin)。
- **共享 subgoal 接口**:高层和低层通过固定维度的 embedding 通信,可以独立升级。

### 15.3 HiRT vs π0 的取舍

| 维度 | π0 (单层) | HiRT (分层) |
| :--- | :--- | :--- |
| 推理频率 | 10Hz | 50Hz |
| 长视野任务 | 一般 | 强 |
| 工程复杂度 | 低 | 中 |
| 部署硬件 | A100 GPU | 高层 GPU + 低层 NPU |
| 适用场景 | 短视野 (1-3 步) | 长视野 (10+ 步) |
| 训练数据 | 单段轨迹 | 段级标注 (subgoal) |

经验法则:**任务步骤 ≤ 5 步用 π0,> 5 步用 HiRT**。

## 16. π0 双手机械臂工业案例

Physical Intelligence 第一个商业落地方向是**家庭服务机器人**,核心难点是双臂协同 (bimanual manipulation)。这一节拆 π0 在 DROID 数据集上的工程实践。

### 16.1 任务定义

```text
   π0 双臂任务示例: 清理餐桌
   ┌──────────────────────────────────┐
   │  任务: 把桌面 6 个杯子移到洗碗机   │
   │  时长: ~90 秒                     │
   │  步骤: ~25 步                      │
   │  成功率: π0 单层 50%, π0 + 分层 78% │
   └──────────────────────────────────┘

   关键子任务:
   1. 左臂抓杯子 (5s)
   2. 右臂开门洗碗机 (3s)
   3. 左臂把杯子递给右臂 (4s, 双臂协同!)
   4. 右臂放入洗碗机 (3s)
   5. 重复 6 次
```

### 16.2 状态空间设计

π0 的动作空间是 **16 维连续向量**:
- 左臂: 6 维关节角增量 + 1 维夹爪 = 7 维
- 右臂: 6 维关节角增量 + 1 维夹爪 = 7 维
- 移动底盘: 2 维 (x, y 速度)

加上语言指令和当前帧图像,组成 π0 的输入。

**关键工程决策**:
1. **用 delta 不用 absolute**:关节角的"增量"比"绝对值"对数据分布更友好,Flow Matching 学起来更稳。
2. **action_chunk = 50 步**:一次推理输出未来 50 步动作,执行 5 秒,然后重新推理。chunk 长度是 π0 最敏感的超参数。
3. **频率不匹配**:VLM 推理 10Hz,但执行 50Hz,所以 chunk 之间用线性插值平滑过渡。

### 16.3 双臂协同的难点

```text
   双臂协同场景
   ┌─────────────────────────────────────────┐
   │                                          │
   │   左臂抓杯子 ──┐                          │
   │                ├──> 同时刻双方位置关系    │
   │   右臂等待  ───┘    必须精确 (< 2cm)      │
   │                                          │
   │   左臂递杯子 ──┐                          │
   │                ├──> 物体交接, 接触约束    │
   │   右臂接住  ───┘                          │
   │                                          │
   └─────────────────────────────────────────┘
```

物理上,双臂协同需要:
- **时序对齐**:两个臂必须在同一时间达到交接点 (误差 < 100ms)
- **力协调**:交接瞬间双方力不能冲突 (碰撞或脱手)
- **视觉遮挡**:交接时一个臂挡住另一个臂的视野

π0 通过两个手段解决:
1. **集中式策略**:16 维输出同时控制两臂,模型自动学协同 (而非两臂独立策略)
2. **chunk-level 规划**:一次输出 50 步,自然覆盖交接前后的过渡

### 16.4 失败模式分析

π0 在双臂任务上的常见失败:

| 失败模式 | 占比 | 原因 | 解法 |
| :--- | :--- | :--- | :--- |
| 抓空 (grasp miss) | 35% | 视觉定位误差 | 加深度图 (3D-VLA) |
| 物体滑落 (slip) | 20% | 接触力估计不准 | 加触觉传感器 |
| 协同失败 | 25% | 双臂时序不对齐 | 增大 chunk 长度 |
| 路径碰撞 | 15% | 缺乏 3D 推理 | 3D-VLA, SpatialVLA |
| 其他 | 5% | 长尾问题 | 更大模型 + 更多数据 |

**工程教训**:**视觉定位是瓶颈**。π0 用单目 + SigLIP,精度有限。后续的 3D-VLA、SpatialVLA 加深度图,把这部分失败率砍掉一半。

## 17. Flow Matching vs Diffusion Policy 工业基准

这一节用具体数字对比 π0 (Flow Matching) 和 Diffusion Policy (Chi et al. 2023) 在真实机器人任务上的差异。

### 17.1 推理速度对比

| 模型 | 推理频率 | 单步延迟 | 10 秒任务延迟 |
| :--- | :--- | :--- | :--- |
| Diffusion Policy (50 步 DDIM) | 3 Hz | 333ms | 30s (其中 10s 推理 + 20s 执行) |
| Diffusion Policy (10 步 DDIM) | 7 Hz | 143ms | 14s |
| **π0 Flow Matching (10 步)** | **10 Hz** | **100ms** | **10s** |
| **π0-FAST (5 步)** | **50 Hz** | **20ms** | **5s** |
| Diffusion Forcing (2024) | 60 Hz | 17ms | 4s |

**关键观察**:Flow Matching 不是"又快又准",而是"用更少步数达到相同精度"。Diffusion Forcing 用"自回归扩散"也能到 60Hz,但实现复杂 5 倍,工程不友好。

### 17.2 任务成功率对比 (DROID 数据集)

DROID 是 Stanford 2024 发布的最大开源机器人数据集 (76k 演示, 564 个任务)。在 DROID 上:

| 任务类别 | Diffusion Policy | π0 | π0-FAST | HiRT |
| :--- | :--- | :--- | :--- | :--- |
| 简单抓取 (pick-and-place) | 82% | 88% | 90% | 92% |
| 推物体 (push) | 75% | 85% | 87% | 88% |
| 双臂协同 | 35% | 65% | 68% | 78% |
| 长视野 (10+ 步) | 28% | 50% | 55% | 75% |
| **平均** | **55%** | **72%** | **75%** | **83%** |

**结论**:
1. **Flow Matching 在所有任务上赢 Diffusion Policy**,差距 15-20 个百分点
2. **分层 (HiRT) 在长视野任务上赢单层 (π0)**,差距 25 个百分点
3. **Diffusion Policy 已经过时**,2024 后新工作基本不引用

### 17.3 训练成本对比

| 模型 | 参数量 | 训练数据 | 训练时长 (8x A100) | 推理显存 |
| :--- | :--- | :--- | :--- | :--- |
| Diffusion Policy | 50M | 100k 轨迹 | 12 小时 | 2GB |
| π0 Flow Matching | 3B | 10M 轨迹 | 5 天 | 16GB |
| π0-FAST | 3B | 10M 轨迹 | 7 天 | 24GB (Tokenizer 额外) |
| HiRT (低层) | 50M | 100k 轨迹 | 18 小时 | 2GB |
| HiRT (整体) | 3.05B | 10M + 100k | 6 天 | 18GB |

**关键观察**:π0 比 Diffusion Policy 大 60 倍,但任务性能好 17 个百分点。**这是规模换性能,不是架构换性能**。

### 17.4 何时选哪个?

- **学术研究 / 小数据 (1k 轨迹)**: Diffusion Policy (够用, 训练快)
- **工业落地 / 中等数据 (10k-100k)**: π0 Flow Matching (性能 + 速度平衡)
- **家庭服务 / 长视野**: HiRT (必选分层)
- **极致实时 (50Hz+)**: π0-FAST + Diffusion Forcing

### 18.2 数据处理的工程坑

**坑 1:异构机器人形态**。Open X-Embodiment 里有 22 种机器人 (Franka、ALOHA、Hello Robot、Mobile ALOHA...),它们的关节数 (6-16)、相机数 (1-3)、控制频率 (10-50Hz) 全不同。

**解法**:**形态无关的 token 化**。把每个关节角归一化到 [-1, 1],每种机器人的动作向量补齐到 16 维 (不够补零, 多余截断)。Flow Matching head 输出 16 维,具体哪个关节有效由"形态 mask"决定。

**坑 2:数据质量差异巨大**。Open X-Embodiment 里有 200k 轨迹是业余采集的,成功率 30%。

**解法**:**数据过滤 + 加权**。π0 论文 (Black et al. 2024 附录 C) 报告:用视觉语言模型给每条轨迹打"质量分",然后按分数加权采样。低质量数据不是直接删,而是降权 0.1 倍。

**坑 3:语言标注不一致**。"pick up the cup" 在不同数据集里写"grab cup"、"take the cup"、"grasp the mug"。

**解法**:**用 LLM 重写**。用 GPT-4 把所有指令重写成统一风格 ("verb + object + destination"),语言一致性从 40% 提到 95%。

### 18.3 预训练 vs 微调

π0 的训练分两阶段:

**预训练 (Pre-training, 5 天, 8x A100)**:
- 数据:全量 10M 轨迹
- 任务:Next Action Prediction (Flow Matching loss)
- 学习率:1e-4 线性 warmup + cosine decay
- Batch size:2048

**微调 (Fine-tuning, 6 小时, 1x A100)**:
- 数据:特定任务的 1k-10k 演示
- 任务:同预训练, 但损失加 RLHF 项
- 学习率:1e-5
- Batch size:128

**RLHF 微调** (π0 的差异化):
- **偏好数据**:让 π0 执行任务,人类对 (成功, 失败) 对标注偏好
- **DPO 损失**:$\mathcal{L}_{DPO} = -\log \sigma(\beta (r_\theta(\text{success}) - r_\theta(\text{fail})))$
- **效果**:在长视野任务上 +5 个百分点

## 19. L7/L8 工程师 Q&A

### Q1: Flow Matching 的"流"到底指什么?

**A**: 不是流体力学, 是 Normalizing Flows (Rezende & Mohamed 2015) 的"流"。指一个可逆映射 $f: \mathbb{R}^d \to \mathbb{R}^d$, 把简单分布 (高斯) 推到复杂分布 (动作)。Flow Matching 学的是这个映射的"速度场" $v_\theta(x_t, t)$。

数学上: $\frac{dx_t}{dt} = v_\theta(x_t, t)$, 推理时从 $t=0$ 积分到 $t=1$。"流"是 ODE 的几何直观——粒子沿速度场流动。

### Q2: 为什么 π0 不直接用 PPO / SAC 做 RL?

**A**: 试过, 失败了。三个原因:
1. **样本效率差**:RL 需要 10M+ 真实环境交互, Physical Intelligence 只有 100k 远程操作轨迹, 差 100x
2. **稀疏奖励**:叠衣服任务成功才给 +1, 中间 30 步全 0 奖励, PPO 几乎学不到东西
3. **安全约束**:真实机器人不能随便试错, 一次碰撞可能损坏 10 万元的硬件

所以 π0 用**行为克隆 (BC) + Flow Matching + RLHF 微调**的组合, BC 解决冷启动, Flow Matching 解决精度, RLHF 解决偏好对齐。

### Q3: HiRT 高层 VLM 能不能和 π0 共用?

**A**: 能, 而且这是 2025 年的趋势。具体做法:
- 高层用 π0 的 PaliGemma + Flow Matching head, 但 Flow Matching 输出改成 "subgoal embedding" 而非动作
- 低层用独立的 50M Transformer
- 端到端微调

实际工程中, 高层 VLM 冻结 (节省显存), 只训低层。

### Q4: π0 在 sim-to-real 上的表现如何?

**A**: π0 没用 sim-to-real。三个原因:
1. **sim 物理不准**:接触、摩擦、布料在 MuJoCo / Isaac Sim 里和真实差 20%
2. **sim 视觉不像**:渲染的纹理、光照和真实相机差太大
3. **数据成本反转**:sim 便宜但要 sim-to-real 工程 (几十人月), 真实远程操作贵但直接可用

**Physical Intelligence 的赌注**:真实数据成本下降 (远程操作员 50$/小时 → 5$/小时用 VR), 比 sim-to-real 工程便宜。

### Q5: π0 推理 10Hz 在工业落地够用吗?

**A**: 看场景。
- **搬运 / 物流**: 5Hz 够, π0 过剩
- **装配 / 插接**: 10Hz 边界, π0 勉强
- **触觉敏感任务 (拧螺丝、贴胶带)**: 20Hz+ 必须, π0-FAST 或加触觉闭环
- **协作机器人 (与人共处)**: 50Hz+ 强制, HiRT 或 Diffusion Forcing

工业落地不要迷信一个数字。看任务。

### Q6: PaliGemma 为什么比 LLaMA 更适合 VLA?

**A**: 三个差异:
1. **原生多模态**:PaliGemma 训练时 SigLIP 视觉编码器和 Gemma LLM 联合优化, 视觉 token 已经在 LLM 输入空间里, 无需额外 projector (省 10% 参数量)
2. **分辨率**:PaliGemma 默认 224x224 视觉 token, 工业相机原生分辨率, 不用 resize
3. **训练数据**:PaliGemma 训过 WebLI (10B 图文对), 视觉理解比纯 LLM 好

代价是 PaliGemma 2B 的语言能力弱于 LLaMA-2-7B (常识、推理)。π0 通过加 Action Expert (300M) 补足。

### Q7: 训练 π0 需要多少 A100 小时?

**A**: 预训练 5 天 × 8 GPU = 960 A100 小时。折算成本:
- AWS p4d.24xlarge: $32/小时, 单卡 $4/小时, 总 $3840
- Lambda Labs 1.5$/小时, 总 $1440
- 自建:电费 + 折旧, 约 $800

**微调** 6 小时 × 1 GPU = 6 小时, $24。

**对比**:训练 GPT-3 是 355 GPU 年 (3.14M A100 小时), π0 是 GPT-3 的 1/3000。机器人数据比语言数据贵但规模小。

### Q8: 普通人怎么用上 π0?

**A**: 三条路:
1. **Hugging Face**: 2025 年 5 月 π0.5 开源了, `from_pretrained("physical-intelligence/pi05")` 直接加载, 权重 Apache 2.0
2. **租用 GPU**: 不想买 GPU 的话, Lambda Labs / RunPod 租 A100, 跑 inference 50ms/步
3. **接机器人**: π0 输出 ROS 话题, 任何支持 ROS 的机械臂 (Franka、UR、ALOHA) 都能直接控制

**注意**: π0 训过的机器人有限 (Franka + ALOHA + Hello Robot), 用在自家机械臂上需要微调 1-3 小时。

## 20. 跨章交叉引用

π0 不是孤岛, 它和教程其他章节有大量交叉点。这一节列出关键引用, 帮你建立知识网络。

### 20.1 与第 2 章 (动作 token 化) 的对比

第 2 章讲的 RT-2 把动作离散化成 256 个 token, 用语言模型的方式生成。π0 是"对立路线":动作保持连续, 用 Flow Matching 生成。

**对比矩阵**:

| 维度 | RT-2 (token) | π0 (flow) |
| :--- | :--- | :--- |
| 动作精度 | 1/256 = 0.4% | 理论无限 |
| 推理速度 | 3 Hz | 10 Hz |
| 训练稳定性 | 高 | 中 (Flow Matching 需要调 t) |
| 长视野 | 弱 (token 自回归慢) | 强 (一次输出 chunk) |
| 工程复杂度 | 低 | 中 |

**结论**: token 化适合低维控制 (3-DoF 夹爪), Flow Matching 适合高维连续控制 (7+ DoF 机械臂)。

### 20.2 与第 5 章 (OpenVLA) 的对比

OpenVLA 是 2024 年 Berkeley 的 7B VLA, 和 π0 同代。两者都基于开源 VLM (LLaMA-2 / PaliGemma), 但:

- **OpenVLA**: 7B, token 化, 单目视觉, 开源权重
- **π0**: 3B, Flow Matching, 多目视觉, 半开源

**经验法则**:
- 学术研究 → OpenVLA (易复现)
- 工业落地 → π0 (精度 + 速度)
- 教学示例 → OpenVLA (代码简单)

### 20.3 与第 7 章 (Diffusion Policy) 的数学等价

第 7 章会讲 Diffusion Policy (Chi et al. 2023), 它和 π0 的 Flow Matching 数学上等价 (Lipman et al. 2023 证明)。

**关键等价**:
- Diffusion 的 $\epsilon_\theta(x_t, t)$ ↔ Flow Matching 的 $v_\theta(x_t, t)$
- 转换公式: $v = (x_1 - \epsilon \sigma_t) / \alpha_t$
- 训练目标: $\mathcal{L}_{DDPM} \propto \mathcal{L}_{CFM}$ (差一个 $t$ 的权重)

**为什么 Flow Matching 更优**:
1. 训练目标更"自然" (学速度场, 不是噪声残差)
2. 路径更"直" (线性 vs cosine), 积分误差小
3. 推理步数少 (10 vs 50), 速度快 5x

### 20.4 与第 8 章 (RLHF) 的关联

π0 的微调用 DPO (Direct Preference Optimization), 这是 RLHF 的简化版。第 8 章会讲 PPO / DPO / GRPO 的区别。

**π0 用 DPO 的原因**:
- PPO 需要训练 reward model + 策略网络, 工程复杂
- DPO 直接用偏好对 (成功 vs 失败) 训练, 单阶段, 易实现
- 性能差距 < 2%, 工程友好胜出

### 20.5 与第 9 章 (工业实践) 的展望

第 9 章会讲 VLA 落地的商业逻辑。π0 是当前天花板:

- **卖模型**: Physical Intelligence 估值 24 亿, 卖 π0 API 给物流公司 ($0.01/步)
- **卖机器人**: π0 + 自家硬件 (ALOHA 2), 整机 $50k
- **卖方案**: 集成商买 π0 + 机器人, 给终端用户做定制 (工厂、医院)

**预测** (2025-2027):
- 2025: π0 进入 10 家工厂, 50 家研究机构
- 2026: π0 衍生出 50 个垂直模型 (π0-pick, π0-fold, π0-cook)
- 2027: 家庭机器人出货 100 万台, π0 是基础模型

## 21. 总结:π0 的"五个为什么"

### 21.1 为什么是 Flow Matching 而不是 Diffusion?

Diffusion 50 步太慢, Flow Matching 10 步够用, 速度快 5x。数学等价, 工程不等价。

### 21.2 为什么是 PaliGemma 而不是 LLaMA?

PaliGemma 原生多模态, 视觉 token 已在 LLM 空间, 不用 projector。省参数、省训练、省工程。

### 21.3 为什么是连续动作而不是离散 token?

机器人动作精度要 1mm, 256 个 token 量化到 16 维空间平均每维 16 个值, 精度 1/16 = 6.25%, 不够。连续动作理论无限精度, Flow Matching 学起来比 token 自回归简单。

### 21.4 为什么是 3B 而不是 7B?

PaliGemma 2B + Action Expert 300M = 总 2.3B, 比 OpenVLA 7B 小 3 倍, 推理显存 16GB (vs 24GB), 工业部署友好 (单 A100 跑得动)。

### 21.5 为什么是 action_chunk (50 步) 而不是单步?

单步推理 100ms, 机器人控制周期 20ms, 跟不上。chunk 一次输出 50 步, 执行 5 秒, 然后重推理。牺牲反应速度换一致性。

## 24. π0 Action Chunking 的物理直觉

### 24.1 为什么要"一次输出 50 步"?

单步控制的问题是**反应速度 vs 一致性的矛盾**:
- 单步推理 100ms, 频率 10Hz
- 机器人动力学需要 50Hz 控制才平滑
- 如果每步重推理, 50ms 周期内 5ms 推理 + 45ms 执行, 没问题

但实际工程中, **传感器噪声** 和 **执行器延迟** 让单步控制产生抖动:
- 相机 30fps, 推理间隔内看到的图像过时 33ms
- 电机响应延迟 5-10ms
- 累积误差导致动作抖动

**Action chunking 解决**:一次推理输出 50 步轨迹, 一次性执行 5 秒, 期间不再重推理。
- **优势**: 轨迹平滑, 内部一致 (前后连贯)
- **代价**: 对突发干扰反应慢 (5 秒反应延迟)
- **折中**: chunk 长度 = 50, 每 5 秒重规划一次

### 24.2 chunk 长度的工程权衡

```text
   chunk 长度 vs 性能 (DROID 抓取任务)

   chunk=1   频率=10Hz  抖动大  成功=72%   反应最快
   chunk=10  频率=5Hz   较平滑 成功=82%    反应 200ms
   chunk=50  频率=2Hz   平滑   成功=88%    反应 1s   ← π0 默认
   chunk=100 频率=1Hz   很平滑 成功=83%    反应 2s   ← 倒退, 反应太慢
```

**最优在 50 步** (π0 论文实验结果)。再长会"过度预测", 反而准确率下降。

### 24.3 时间一致性损失 (Temporal Consistency Loss)

π0 训练时加了一个隐式的 TC 损失:
$$\mathcal{L}_{TC} = \mathbb{E}_{t, s} \|v_\theta(x_t, t) - v_\theta(x_t', t')\|^2 \cdot \mathbb{1}[|t-t'| < \epsilon]$$

直觉: 相邻时间步的向量场应该相似, 不要"突变"。实现细节在 π0 论文附录 B。

## 25. VLA 训练数据的"长尾"问题

### 25.1 数据长尾分布

π0 用的 10M 轨迹里, 任务频率严重不均:

```text
   任务频率分布 (近似)
   ┌────────────────────────────────────────┐
   │ pick up           25%  (250万轨迹)     │  ← 长头
   │ put down          20%                  │
   │ open drawer       15%                  │
   │ close drawer      12%                  │
   │ push              10%                  │
   │ ...                                    │
   │ fold shirt        0.5% (5万)           │  ← 长尾
   │ cook egg          0.1% (1万)           │
   │ tie knot          0.05% (5千)          │
   │ catch ball        0.01% (1千)          │
   └────────────────────────────────────────┘
```

**问题**: 模型在长尾任务上欠拟合, 成功率 < 30%, 而长头任务 > 90%。

### 25.2 解法 1: 数据上采样

对长尾任务过采样, 让 batch 里出现频率均衡:
- 短头任务下采样 0.1x
- 长尾任务上采样 10x
- 训练 1 个 epoch = 实际看到 3-5 个 epoch 的长尾数据

**代价**: 总训练时间变长, 长头任务可能欠拟合。

### 25.3 解法 2: 加权损失

每条轨迹带一个权重 $w_i$:
$$\mathcal{L} = \sum_i w_i \mathcal{L}_i$$

权重反比于任务频率: 罕见任务 $w = 10$, 常见任务 $w = 0.1$。

### 25.4 解法 3: 元学习 (MAML)

MAML (Finn et al. 2017) 让模型"快速适应新任务":
- 训练: 模拟"少样本场景", 强制模型只用 10-100 条数据就学会
- 推理: 面对长尾任务, 也能从少量演示中快速学习

π0 没直接用 MAML, 但 π0-FAST 加了 MAML-style 的微调 (5-shot adaptation)。

### 25.5 工业经验: 数据多样性 > 数据量

经验法则:
- 100 种任务 × 100 条演示 = 10k 轨迹 (多样)
- 1 种任务 × 10000 条演示 = 10k 轨迹 (单一)

前者的泛化性能 > 后者。Physical Intelligence 内部数据 (1M 轨迹, 25 任务) 比 Open X-Embodiment (6M 轨迹, 500 任务) 训练效果好, 因为**任务多样性**。

## 29. 数学专题: Flow Matching 的收敛性证明

这一节给理论派工程师看的形式化证明 (Lipman et al. 2023)。

### 29.1 前提条件

设数据分布 $p_1(x)$, 简单分布 $p_0(x) = \mathcal{N}(0, I)$。

定义概率路径 $p_t(x)$ 为 $p_0$ 和 $p_1$ 的线性插值:
$$p_t(x) = \int p_t(x | x_1) p_1(x_1) dx_1$$
其中 $p_t(x | x_1) = \mathcal{N}(x; tx_1, (1-t)^2 I)$。

### 29.2 边际向量场

边际向量场 $u_t(x)$ 定义为:
$$u_t(x) = \int u_t(x | x_1) \frac{p_t(x | x_1) p_1(x_1)}{p_t(x)} dx_1$$
其中条件向量场 $u_t(x | x_1) = \frac{x_1 - x}{1-t}$ (线性插值的导数)。

### 29.3 核心定理

**定理** (Lipman et al. 2023 Theorem 1):
$$\nabla_\theta \mathcal{L}_{FM}(\theta) = \nabla_\theta \mathcal{L}_{CFM}(\theta)$$

其中:
$$\mathcal{L}_{FM} = \mathbb{E}_{t, x \sim p_t} \|v_\theta(x, t) - u_t(x)\|^2$$
$$\mathcal{L}_{CFM} = \mathbb{E}_{t, x_1 \sim p_1, x_0 \sim p_0} \|v_\theta(x_t, t) - (x_1 - x_0)\|^2$$

**证明要点**: 利用 Jensen 不等式和条件期望的线性, 两个损失的梯度形式相同。

### 29.4 工程意义

- 可以直接用 CFM 训练, 无偏估计 FM
- CFM 不需要知道边际向量场 (那是 intractable 的)
- 实践中: 随机采 $t$, 采 $x_0$, 采 $x_1$, 计算 $x_t = (1-t)x_0 + tx_1$, 训练 MSE

### 29.5 收敛速度

对于 $L$-Lipschitz 目标, $\mathcal{L}_{CFM}$ 在 $n$ 步后以 $\mathcal{O}(L/n^{1/2})$ 收敛。

实际: 10k 步达到 95% 性能, 100k 步收敛。

## 31. L7/L8 工程师补充 Q&A (进阶)

### Q9: π0 的"涌现"行为有哪些?

**A**: 涌现 (emergence) 指模型在没有专门训练过的任务上表现。π0 报告的几个:

1. **新物体泛化**: 训练时只有"红杯子", 测试时给"蓝色塑料瓶", 成功率 70%
2. **新指令组合**: "把香蕉放到 Mario 旁边" (RT-2 已验证), π0 也涌现
3. **长视野任务分解**: 没训过"做三明治", 但能拆成"拿面包 → 涂酱 → 放火腿"
4. **错误恢复**: 物体掉了能自己捡起来 (没专门训练)

涌现的根本原因: 预训练数据规模足够大 (10M 轨迹), 模型在数据中"自学"了组合泛化。

### Q10: π0 怎么避免"灾难性遗忘"?

**A**: 灾难性遗忘指学新任务忘旧任务。π0 用两个手段:

1. **数据回放 (Replay Buffer)**: 训练时 80% 新数据 + 20% 旧数据混合
2. **正则化 (EWC)**: Fisher 信息矩阵约束关键参数不剧烈变化

实际效果: π0 微调 100 个不同任务后, 原始任务的性能保持 95%。

### Q11: π0 的"语义理解"到底是真理解还是模式匹配?

**A**: 哲学问题, 工程上不关心。但有几个客观证据:

- **零样本指令**: "把红色方块放在绿色圆圈左边", 训练时没见过这个组合, 70% 成功 (vs 随机 30%)
- **否定理解**: "不要碰杯子", π0 能避开杯子 (在有限测试集上 60%)
- **属性绑定**: "小的红色东西", 能区分小红色 vs 大红色

**结论**: 不是纯模式匹配, 也不是真正"理解"。介于两者之间的"功能理解" (functional understanding), 足以完成工业任务。

### Q12: π0 在 Jetson Orin Nano 上能跑吗?

**A**: 勉强能, 但要量化:
- 原始 FP16: 显存 8GB, 推理 800ms (Orin Nano 算力 40 TOPS)
- INT8 量化: 显存 4GB, 推理 400ms
- 模型剪枝 (1.5B): 推理 200ms

**结论**: Orin Nano 跑 π0-Lite (1.5B) + INT8 = 200ms / 10Hz, 勉强可用。
Orin AGX (275 TOPS) 跑 π0 全量 = 100ms / 10Hz, 工业可用。

### Q13: 如何 debug π0 输出"抖动"?

**A**: 三步定位:

1. **看 joint 速度曲线**: 正常应该平滑, 抖动 = 锯齿状尖峰
2. **看 action_chunk 内部一致性**: 相邻动作差异 > 0.1 = 抖动
3. **看传感器时间戳**: 相机延迟 vs 推理时间错位 = 抖动

修复:
- 加 Savitzky-Golay 平滑 (5 点窗)
- 增加 action chunk 长度 (50 → 100)
- 检查相机帧率 (必须 ≥ 30fps)

### Q14: π0 能不能迁移到四足机器人?

**A**: 理论上能, 工程上要改:

- 自由度: 12 (四腿 × 3) vs 6-7 (单臂)
- 任务: 移动 + 平衡 vs 抓取 + 操作
- 频率: 200Hz (平衡) vs 50Hz (操作)

**实际**: π0 输出改成 12 维, 加平衡约束 (ZMP), 重新训练。
**社区已有**: π0-Quad (MIT 2025), 四足 + 机械臂组合, 移动抓取。
