# 附录:选择适合你的仿真器

> **写给刚读完 §1-§6、还在纠结"我该用哪个"的工程师**:
>
> 你看完了 MuJoCo 的 XML, 试了 Isaac Sim 的 USD, 跑了 ManiSkill 的 PickCube. 现在回到工程问题:**我下一个项目到底选谁?**
>
> 这一章不是综述, 是决策辅助. 我把 2024 年还在维护的仿真器按物理精度 / 渲染 / 速度 / 学习曲线 / 许可 / GPU 并行能力六个维度排了表, 然后给一张决策流程图, 最后列了工业一线 (Tesla / Figure / 宇树 / 1X) 在用什么, 以及新手最容易踩的五个坑.
>
> 用法:
> - 你**有明确任务** (操作 / 导航 / 灵巧手 / 运动) → 直接跳 §2 决策树
> - 你**在选第一个仿真器入门** → 读完 §1 表格, 跟着 §4 部署清单走
> - 你**在做 Sim2Real 落地** → §3 工业实践 + §5 常见陷阱优先
> - 你**在写论文** → §1 + §2 都要看, 评审会问"为什么不用 X"

## 1. 仿真器特性对比

### 1.1 总览表

下表覆盖 2024 年还在活跃维护的 12 个主流仿真器. 维度定义在表后说明.

| 仿真器 | 物理后端 | 物理精度 | 渲染 | GPU 并行 | 速度 (单环境) | 速度 (并行 1024) | 学习曲线 | 许可 | 维护方 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **MuJoCo** | 自研 (convex) | ⭐⭐⭐⭐⭐ | 简陋 (OpenGL) | ❌ (MJX 在 JAX 上) | 1x 基准 | 0.05x (CPU) / 50x (MJX) | ⭐⭐ | Apache 2.0 (现) | Google DeepMind |
| **Isaac Sim** | PhysX 5 | ⭐⭐⭐⭐⭐ | RTX 光追 + 实时 | ✅ | 0.3x | 200x | ⭐⭐⭐⭐ | 商业 (免费学术) | NVIDIA |
| **Isaac Lab** | PhysX 5 | ⭐⭐⭐⭐⭐ | RTX 光追 | ✅ (主打) | 0.3x | 300x | ⭐⭐⭐ | BSD-3 | NVIDIA |
| **Isaac Gym (Preview)** | PhysX 5 | ⭐⭐⭐⭐ | 中等 | ✅ | 0.3x | 250x | ⭐⭐⭐ | BSD-3 | NVIDIA |
| **PyBullet** | Bullet | ⭐⭐⭐ | 简陋 (OpenGL) | ❌ | 0.5x | 0.5x | ⭐ | Apache 2.0 | 社区 (Erwin Coumans) |
| **Genesis** | 自研 (Taichi) | ⭐⭐⭐⭐ (进步快) | 中等 | ✅ | 0.8x | 200x | ⭐⭐⭐ | Apache 2.0 (计划) | 浙大 + 字节 (2024 起) |
| **Brax / MJX** | MuJoCo (JAX 重写) | ⭐⭐⭐⭐⭐ | 无 | ✅ | 0.5x | 400x | ⭐⭐ | Apache 2.0 | Google DeepMind |
| **Habitat 3.0** | Bullet | ⭐⭐⭐ | 高 (Matterport3D) | ✅ (渲染) | 0.6x | 100x | ⭐⭐⭐ | MIT | Meta |
| **SAPIEN** | PhysX 4 | ⭐⭐⭐⭐ | 高 (UE 级) | ❌ | 0.4x | 1x | ⭐⭐⭐ | Apache 2.0 | UCSD + 社区 |
| **ManiSkill 3** | PhysX 5 | ⭐⭐⭐⭐⭐ | 高 (RTX) | ✅ | 0.3x | 300x | ⭐⭐⭐ | Apache 2.0 | CUHK + 社区 |
| **CoppeliaSim** | Bullet / ODE / Vortex | ⭐⭐⭐ | 中等 | ❌ | 0.4x | 0.4x | ⭐⭐ | 商业 (教育免费) | Coppelia Robotics |
| **Gazebo (Ignition)** | ODE / Bullet / DART | ⭐⭐⭐ | 中等 (OGRE 2) | ❌ | 0.5x | 0.5x | ⭐⭐⭐ | Apache 2.0 | Open Robotics |

**维度定义**:

- **物理后端**: 底层求解器 (MuJoCo 自研 / PhysX / Bullet / ODE / Taichi 自研 / Vortex). 不同后端的接触模型、积分器、约束求解策略完全不同.
- **物理精度**: 与真机轨迹的拟合度, 主要看接触动力学. MuJoCo 和 PhysX 5 在足式 / 操作任务上 Sim2Real gap 5-15%, ODE 和 Bullet 在精细操作上 gap 可达 30%+.
- **渲染**: 用于视觉策略 (IL / VLA) 的图像质量. Isaac Sim / ManiSkill 3 / Habitat 的渲染最强; MuJoCo / PyBullet 的渲染基本只能给人类看, 不能给 CNN 学.
- **GPU 并行**: 是否支持上千个环境并行. 这是 RL 训练速度的关键. Isaac 系、ManiSkill、Brax/MJX、Genesis 都做到了.
- **速度 (单环境)**: 相对 MuJoCo CPU 单线程的倍数. 大于 1x 表示比 MuJoCo 还快, 小于 1x 表示慢.
- **速度 (并行 1024)**: 1024 个环境并行时, 单环境等效吞吐. Isaac 系能到 200x, Brax/MJX 凭 JAX 编译能到 400x.
- **学习曲线**: 从零到能跑 demo 所需时间. ⭐ 简单 (PyBullet), ⭐⭐⭐⭐ 难 (Isaac Sim USD 体系).
- **许可**: 是否商业可用. MuJoCo 2022 年被 DeepMind 收购后转为 Apache 2.0, 这是行业大事.

### 1.2 主流仿真器细节

下面给每个被 §2 决策树引用的仿真器一段"为什么用它"和"什么时候别用它". 跳过你自己不会选的.

#### 1.2.1 MuJoCo

物理精度第一梯队, 学术事实标准. 接触用凸优化 (Newton + PGS), 比 Bullet 的 LCP 稳得多, 比 ODE 的弹簧罚函数准得多.

**核心优势**:
- 凸接触公式 (`solver: "newton"` 默认) 处理多接触场景比 LCP 稳
- MJCF (XML) 建模清晰, 一个文件定义机器人 + 任务
- 强化学习圈生态最熟: Gymnasium / Stable-Baselines3 / RLlib / Tianshou 默认支持
- 同名 MJX (JAX 重写) 解决了 GPU 并行问题, 2024 起能跑上千环境

**什么时候别用**:
- 需要高保真渲染 (没有 RTX 光线追踪, 视觉策略不友好)
- 需要刚柔耦合 / 布料 / 流体 (MuJoCo 现在加了柔体, 但远不如 Bullet + 软体插件成熟)
- 需要复杂场景 (一个 MuJoCo XML 里写超过 100 个物体就会卡, 因为它不是为大规模场景设计的)

**一句话**: 你要训运动 / 接触为主的任务, 选 MuJoCo + MJX. 其他任务绕道.

#### 1.2.2 Isaac Sim

NVIDIA 全家桶, RTX 光线追踪 + PhysX 5 GPU 并行. 工业机器人和自动驾驶的事实标准.

**核心优势**:
- RTX 渲染 (光线追踪 + 路径追踪) 出的图可以骗过人类
- USD 场景格式 (Pixar 发明的), 整个电影工业在用
- PhysX 5 GPU pipeline, 4096 个并行环境跑起来轻轻松松
- 跟 Omniverse 平台绑定, 能导 Blender / Maya / Unreal 资产

**什么时候别用**:
- 你的显卡不是 NVIDIA RTX (光追废了)
- 你的电脑内存 < 32GB (Isaac Sim 起步 16GB 显存, 实际项目 24-48GB)
- 你要做论文 baseline 跑 6 个任务 (Isaac Sim 写一个任务花 3 天, MuJoCo 写一个任务花 1 小时)
- 团队没人懂 USD (这是另一个学习曲线)

**一句话**: 你有 NVIDIA GPU + 需要视觉策略 + 团队规模够, 选 Isaac Sim. 其他情况别选.

#### 1.2.3 Isaac Lab

NVIDIA 2024 年推出的"为 RL 而生"的 Isaac Sim 简化版. 砍掉了 USD 编辑器, 强化了 RL 训练接口.

**核心优势**:
- 跑 4096 个 Franka 抓取任务, 单 A100 一天训完 (ManiSkill 3 也行)
- RL 接口比 Isaac Sim 干净 (gym 接口直接对接)
- 跟 RSL-RL / Stable-Baselines3 / skrl 都有现成集成

**什么时候别用**:
- Isaac Sim 的所有缺点它都有 (NVIDIA-only, 显存大, USD 学习曲线)
- 任务定义比 ManiSkill 3 麻烦 (ManiSkill 3 是任务定义优先, Isaac Lab 是物理引擎优先)

**一句话**: Isaac Lab ≈ Isaac Sim 的 RL 训练快捷版. 选它 vs ManiSkill 3 看 §2 决策树.

#### 1.2.4 PyBullet

老牌 Bullet Python 绑定. 简单到能 5 分钟跑通, 复杂到让你想砸键盘.

**核心优势**:
- `pip install pybullet` 就能跑
- URDF / SDF / MJCF 都能加载 (兼容性最广)
- 社区老资料多, Stack Overflow 上 90% 机器人问题都引这里

**什么时候别用**:
- 任何接触密集的任务 (PyBullet 的 LCP 求解器在多接触下会震荡)
- 任何视觉策略 (OpenGL 渲染, 没法给 CNN 看)
- 任何 2024 年后的 RL 论文 (MuJoCo / Isaac 系才是事实标准)

**一句话**: PyBullet 现在最大的用途是教学和快速原型. 生产环境别用.

#### 1.2.5 Habitat 3.0

Meta 的室内导航 + 人机交互仿真器. 强在场景库, 弱在物理.

**核心优势**:
- Matterport 3D 场景 (1000+ 真实室内扫描), 渲染质量是仿真器里最强的之一
- HM3D / HSSD / Open Vocabulary 场景库, 数据集最大
- 社交导航 + 多智能体是它的特色 (Habitat 3.0 加了人形)
- 渲染用 Habitat-Sim, 物理用 Bullet, 物理精度中等

**什么时候别用**:
- 任何操作任务 (Bullet 物理 + 简化的物体交互, 抓取 gap 大)
- 任何需要接触细节的任务 (足式 / 灵巧手)

**一句话**: 导航任务 (PointNav / ObjectNav / Vision-Language Nav) 选 Habitat. 其他别选.

#### 1.2.6 SAPIEN

UCSD 出的"专为操作任务设计"的仿真器, PhysX 4 后端. ManiSkill v2 时代是默认后端.

**核心优势**:
- 关节物体 (柜子门 / 抽屉 / 微波炉) 仿真最准
- 场景库 (PartNet-Mobility) 是操作任务的标配
- 渲染质量高 (UE 引擎)

**什么时候别用**:
- 任何 RL 并行 (SAPIEN 不支持 GPU 流水线, 单线程物理)
- 任何运动 / 导航任务
- 2024 年起的论文 (大家都迁到 ManiSkill 3 / Isaac Lab 了)

**一句话**: 做关节物体交互 + 不需要并行, 选 SAPIEN. 其他别选.

#### 1.2.7 ManiSkill 3

2024 年操作任务基准的事实标准. 底层 PhysX 5, 加 GPU 流水线, 加标准化任务集.

**核心优势**:
- 1000+ 任务, 覆盖 PickCube 到长视野桌面整理
- GPU 并行 4096 环境跑得起来, 单卡 A100 一晚训完大多数任务
- 标准化评估协议 (成功率 + 部分成功度 + 轨迹), 跨论文可比
- 后端可选 PhysX / Sapien / CuRobo, 灵活
- 跟 SOTA 论文强绑定 (CVPR 2024 起操作任务论文几乎都用 ManiSkill 3)

**什么时候别用**:
- 导航 / 运动 / 灵巧手任务 (虽然 v3 加了 dexterous, 但灵巧手还是 SAPIEN / Isaac 更强)
- 不需要并行 (单环境不如 MuJoCo 简洁)

**一句话**: 做操作任务 + 想跑 SOTA, 选 ManiSkill 3. 这是 §2 决策树里"操作"分支的默认推荐.

#### 1.2.8 其他值得提一句

| 仿真器 | 一句话点评 |
| :--- | :--- |
| **Brax / MJX** | MuJoCo 的 JAX 重写, 速度最快. 适合做 MCTS / 进化算法 / 大规模种群训练. 渲染基本没有, 纯物理. |
| **Genesis** | 2024 年横空出世, 浙大 + 字节. 物理用 Taichi 自研, 渲染中等, 速度 200x. 潜力大, 但生态还没起来. |
| **CoppeliaSim** | 老牌可视化仿真, 工业机器人 (ABB / KUKA) 教学标配. RL 圈不用, 但视觉检查 + 控制算法验证好用. |
| **Gazebo (Ignition)** | ROS 官方, 机械臂 + 移动机器人调试标配. 物理一般, 渲染一般, ROS 集成最强. |
| **Unity ML-Agents** | 游戏引擎路线, 适合异形场景 / 教育. 物理精度不够, 视觉好. |
| **Drake** | MIT 出的, 控制系统学家爱. 物理精度高, 渲染弱, 接触一般, RL 接口少. 适合做 MPC / 轨迹优化. |
| **Triton / Warp (NVIDIA)** | 不是完整仿真器, 是 GPU kernel 库. 想自己写 GPU 物理求解器用. |

### 1.3 选择维度小结

把这 12 个仿真器按"你关注什么"再排一遍, 帮你在脑子里建索引:

**物理精度优先** → MuJoCo ≈ Isaac Sim ≈ ManiSkill 3 > SAPIEN > Genesis > PyBullet > ODE 系

**渲染优先** → Habitat > Isaac Sim > ManiSkill 3 > SAPIEN > 其它全部

**速度 (并行训练) 优先** → Brax/MJX > Isaac Lab > ManiSkill 3 ≈ Isaac Sim > Genesis > Habitat > 其它全部

**学习曲线 (新手上路时间) 优先** → PyBullet > MuJoCo > Gazebo > SAPIEN > Habitat > ManiSkill 3 > Isaac Lab > Isaac Sim

**商业可用性** → MuJoCo (Apache) > Isaac Sim (商业但学术免费) > 其它基本都行

## 2. 决策树

### 2.1 按任务类型切

**任务类型 1: 运动控制 (Locomotion)**
- 代表: HalfCheetah, Ant, Humanoid, ANYmal, Spot, Go2
- 物理需求: 接触多 (4-12 条腿交替着地), 摩擦细节敏感
- 推荐: **MuJoCo + MJX** (学术), **Isaac Lab** (工业)
- 避免: PyBullet (接触震荡), Habitat (物理太弱)

**任务类型 2: 操作 (Manipulation)**
- 代表: PickCube, StackCube, PegInsertion, ToolUse
- 物理需求: 单点接触为主, 视觉依赖强
- 推荐: **ManiSkill 3** (学术 SOTA), **Isaac Lab** (工业), **MuJoCo** (简单任务)
- 避免: SAPIEN v3 (生态已迁出), Habitat (操作太弱)

**任务类型 3: 导航 (Navigation)**
- 代表: PointNav, ObjectNav, VLN (Vision-Language Navigation)
- 物理需求: 几乎无, 主要是渲染 + 视觉定位
- 推荐: **Habitat 3.0** (事实标准)
- 避免: Isaac Sim (杀鸡用牛刀), MuJoCo (没渲染)

**任务类型 4: 灵巧手 (Dexterous Hand)**
- 代表: Shadow Hand, Allegro, LEAP Hand, 灵巧抓取 / 旋转 / 翻牌
- 物理需求: 高自由度 (20-24 DoF), 多指接触, 接触密度极高
- 推荐: **Isaac Lab** (并行强 + 接触稳), **MuJoCo + MJX** (学术), **ManiSkill 3 + SAPIEN 后端** (灵巧手专用任务)
- 避免: PyBullet (接触会崩)

**任务类型 5: 移动操作 (Mobile Manipulation)**
- 代表: 移动机械臂开门 / 抓桌面物体 / 家居整理
- 物理需求: 运动 + 操作结合
- 推荐: **Isaac Sim** (完整场景), **Habitat 3.0 + 简化操作** (纯导航版)
- 避免: 任何单强项仿真器 (一个搞不定)

**任务类型 6: 自动驾驶 / 室外机器人**
- 代表: CARLA, Waymax, nuPlan
- 这是个专门的子领域, 选 **CARLA** (学术) 或 **Waymax** (Waymo 出品, 数据驱动). 不在本附录范围.

**任务类型 7: 人形机器人全身控制 (Humanoid Whole-Body Control)**
- 代表: H1 / G1 / Optimus / Atlas 的站起 / 走楼梯 / 搬运
- 物理需求: 30+ DoF, 接触密集, 平衡敏感
- 推荐: **Isaac Lab + MuJoCo MJX** (双开, 互相验证), **Genesis** (新选项)
- 避免: PyBullet, ODE 系

### 2.2 按训练规模切

**单机 / 单卡 (1-32 并行环境)**
- 任何仿真器都行, 选你最熟的
- 默认推荐: **MuJoCo** (最稳, 文档最多)

**单卡 GPU / 中等规模 (64-512 并行)**
- 推荐: **Isaac Lab**, **ManiSkill 3**, **Brax/MJX**
- 显存占用 ≈ 4-12 GB

**多卡 GPU / 大规模 (1024-8192 并行)**
- 推荐: **Isaac Lab** (NVIDIA 系首选), **Brax/MJX** (Google 系首选)
- 显存占用 ≈ 24-80 GB, 需要 A100 / H100

**CPU 集群 (4096+ 并行, 没 GPU)**
- 推荐: **Brax/MJX on TPU** (Google), **MuJoCo + 进程级并行** (学术经典)
- Isaac 系必须有 GPU, 别在这浪费钱

### 2.3 按预算切

**学术 / 个人 (预算 $0)**
- MuJoCo + MJX (Apache)
- PyBullet (Apache, 教学)
- ManiSkill 3 (Apache)
- Habitat 3.0 (MIT)
- Brax / MJX (Apache)
- Genesis (Apache 计划中)
- SAPIEN (Apache)

**学术但有 NVIDIA 显卡 (预算 $0 但有 GPU)**
- Isaac Lab / Isaac Sim (学术免费)
- ManiSkill 3 (硬件要求低)
- Brax / MJX (JAX + 任何 GPU)

**工业 / 中小公司 (预算 $10K-$100K / 年)**
- Isaac Sim 商业许可 (~$4500 / seat / 年, 大客户谈)
- 优先 ManiSkill 3 + 自研后端 (零许可费)
- MuJoCo + 自研

**大型公司 (预算 $1M+)**
- Isaac Sim 全员部署
- 自研仿真器 (Google RT-X, Meta Habitat-X, NVIDIA Isaac Lab 都是这个层级)
- 多个仿真器混用, 每个任务选最合适的

### 2.4 决策流程图

把上面 2.1-2.3 综合成一张 ASCII 流程图. 沿着箭头走, 终点就是你的选择.

```text
                    ┌─────────────────────┐
                    │ 你的任务是什么?     │
                    └──────────┬──────────┘
                               │
            ┌──────────┬───────┴────────┬──────────┐
            ▼          ▼                ▼          ▼
         运动       操作             导航       灵巧手
            │          │                │          │
            ▼          ▼                ▼          ▼
       学术/工业   学术/工业        (唯一)     学术/工业
            │          │                │          │
            ▼          ▼                ▼          ▼
      ┌─────────┐ ┌──────────┐   ┌─────────┐ ┌──────────┐
      │MuJoCo   │ │ManiSkill │   │Habitat  │ │Isaac Lab │
      │+ MJX    │ │3         │   │3.0      │ │+ MuJoCo  │
      │(学术)   │ │(默认)    │   │         │ │MJX(双开) │
      └────┬────┘ └────┬─────┘   └─────────┘ └──────────┘
           │           │
           ▼           ▼
       工业?        工业?
           │           │
           ▼           ▼
       Isaac Lab   Isaac Lab
                   (or ManiSkill 3 + 自研)

细分支:
- 需要 Sim2Real 快速验证? → 加 Genesis (物理 + 渲染 + 速度三者平衡)
- 已有 URDF / MJCF 资产? → 直接用对应后端 (MuJoCo / Isaac 都行)
- 需要视觉策略? → Isaac Sim 或 ManiSkill 3 (排除纯物理的 MuJoCo / Brax)
- 团队没人懂 GPU 编程? → MuJoCo / PyBullet (CPU 简单)
- 需要 RLlib / Stable-Baselines3 集成? → MuJoCo / Isaac Lab / ManiSkill 3 (生态最熟)
- 写论文需要 SOTA baseline? → ManiSkill 3 (操作) 或 Isaac Lab (灵巧手 / 运动)
- 做产品要部署到真机? → Isaac Sim (RTX 渲染 + PhysX 5) 是工业默认
```

### 2.5 决策示例

**场景 A**: 你在高校, 有 RTX 4090 一张, 想做 PickCube / StackCube 的强化学习 baseline, 发论文.

→ **ManiSkill 3**. 原因: 任务集标准化 + GPU 并行 + SOTA 论文都跑这上面, 评审不会问"为什么不用 ManiSkill".

**场景 B**: 创业公司, 团队 5 人, 做机械臂抓取 + 视觉策略, 准备融资 PPT.

→ **Isaac Sim + Isaac Lab**. 原因: NVIDIA 系是工业默认, 投资人听得懂, 视觉渲染最适合做 demo, 工程师好招.

**场景 C**: 个人研究者, 没 GPU, 想跑 HalfCheetah 复现 PPO 论文.

→ **MuJoCo + Stable-Baselines3**. 原因: 最简单的入门组合, CPU 跑得动, 文档最多.

**场景 D**: 博士课题是人形机器人 Sim2Real, 实验室有 8 张 A100.

→ **MuJoCo MJX + Isaac Lab 双开**. 原因: 物理精度高 + GPU 并行, 跨仿真器验证能减少 Sim2Real gap 的"仿真器偏见".

**场景 E**: 中型公司, 要做室内送餐机器人, 同时要导航 + 抓取 + 视觉.

→ **Isaac Sim 单一仿真器**. 原因: 这是一个仿真器覆盖所有需求的场景, 别拆, 拆了维护成本高.

## 4. 部署清单

下面给一个"我决定用 X, 现在怎么上手"的最短路径. 假设 Linux + Python 3.10+, 你选哪个仿真器就跳到对应小节.

### 4.1 安装依赖

**MuJoCo**:
```bash
pip install mujoco mujoco-python-viewer gymnasium
# MJX (JAX 版) 另装
pip install mujoco-mjx brax
```
依赖 < 50 MB. MuJoCo 本身不带渲染, viewer 要单独装.

**Isaac Sim / Isaac Lab**:
- 硬件: NVIDIA RTX 显卡 (显存 ≥ 12 GB), 内存 ≥ 32 GB
- 装 NVIDIA Driver ≥ 535, CUDA 12.x
- 推荐用 NVIDIA Omniverse Launcher 安装 Isaac Sim (不要 pip, pip 版坑多)
- Isaac Lab 走 conda 装
```bash
conda create -n isaaclab python=3.10
conda activate isaaclab
# 按官方文档: https://isaac-sim.github.io/IsaacLab/
```
首次安装 30-60 分钟, 下载 ~10 GB.

**PyBullet**:
```bash
pip install pybullet
```
5 分钟装完, 跑就完了.

**ManiSkill 3**:
```bash
pip install mani-skill
# 渲染需要装 Vulkan
# 参考: https://maniskill.readthedocs.io/
```

**Habitat 3.0**:
```bash
conda install -c aihabitat habitat-sim habitat-lab
# 场景数据单独下载 (HM3D / Matterport3D)
```
场景库很大, 首次下载 10-100 GB.

**Genesis**:
```bash
pip install genesis-world
# 2024 年底仍在快速迭代, 装最新 nightly
```

### 4.2 训练启动

**MuJoCo + PPO (Stable-Baselines3)**:
```python
import gymnasium as gym
import mujoco
from stable_baselines3 import PPO

env = gym.make("HalfCheetah-v4", render_mode=None)
model = PPO("MlpPolicy", env, verbose=1)
model.learn(total_timesteps=1_000_000)
```

**Isaac Lab + PPO (RSL-RL)**:
```bash
# 在 Isaac Lab 环境里
python scripts/reinforcement_learning/rsl_rl/train.py \
  --task Isaac-Velocity-Flat-Anymal-v0 \
  --num_envs 4096 \
  --headless
```

**ManiSkill 3 + PPO (Stable-Baselines3)**:
```python
import gymnasium as gym
import mani_skill.envs

env = gym.make("PickCube-v1", num_envs=256, obs_mode="rgb")
# 然后接 Stable-Baselines3
```

**Habitat + DD-PPO**:
```bash
python -m habitat_baselines.run \
  --config-path configs/vln/oracle_rl.yaml \
  --run-type train
```

### 4.3 评估

通用流程 (不管选哪个仿真器):

1. **训练 checkpoint 保存**: `model.save("ckpt.zip")` (SB3) 或框架自带
2. **独立评估脚本**: 不要在训练里 evaluate, 用独立脚本跑 N 次 (N ≥ 100) 取平均
3. **指标**:
   - 操作: 成功率 (任务完成比例) + 部分成功度 (分数 0-1)
   - 运动: 平均回报 + 终末速度 + 摔倒率
   - 导航: 成功率 + SPL (Success weighted by Path Length)
   - 灵巧手: 成功率 + 旋转精度
4. **多次种子**: 至少 3 个随机种子, 报告 mean ± std
5. **记录**:
   - 物理参数 (时间步, 求解器迭代次数)
   - 域随机化配置
   - 硬件配置 (GPU 型号, 显存占用)
   - 训练时长 (小时)

### 4.4 Sim2Real

如果你训完要部署到真机, 这一步决定生死. 最短路径:

1. **域随机化 (DR)**: 在仿真里加噪声, 让策略见过"乱七八糟"的世界
   - 物理参数 DR: 质量 ±20%, 摩擦 ±30%, 阻尼 ±50%
   - 视觉 DR: 随机光照, 纹理, 相机位置
   - 动力学 DR: 关节摩擦, 执行器延迟

2. **真机遥操采集**: 别只信仿真, 至少采 50-100 个真机轨迹做对比

3. **Sim2Real Gap 量化**:
   - 同任务仿真 vs 真机成功率差
   - 仿真 vs 真机轨迹 KL 散度
   - 仿真 vs 真机状态-动作分布差异

4. **渐进迁移**:
   - 第一步: 仿真训, 真机 0% 数据, 看能不能动
   - 第二步: 加少量真机数据微调
   - 第三步: 完全真机数据微调

5. **记录所有失败案例**: Sim2Real 失败案例比成功案例更有价值

## 5. 常见陷阱

### 5.1 接触参数错误

**陷阱 1: 摩擦系数设得太小或太大**

MuJoCo 默认 `friction="1 0.005 0.0001"` (滑动摩擦 + 扭转摩擦 + 滚动摩擦). Isaac PhysX 默认 `static_friction=0.5, dynamic_friction=0.5`. 实际机器人脚底摩擦 0.6-1.2, 机械臂夹爪 0.3-0.8. 设错一个数量级, 机器人要么滑倒要么打滑.

**解法**: 先量真机 (用摩擦计或查 datasheet), 不要拍脑袋.

**陷阱 2: 求解器选错**

MuJoCo 有 Newton / PGS / CG 三种. Newton 准但慢, PGS 稳但慢, CG 快但可能不收敛. 默认 Newton 一般就行, 但接触极多时切 PGS.

PyBullet 求解器选错最容易崩, LCP 在多接触下震荡. 解决: 加 `contactStiffness` 或换仿真器.

**陷阱 3: 时间步太长**

MuJoCo 默认 `timestep=0.002` (500 Hz). 设成 0.01 (100 Hz) 接触会穿透, 设成 0.0001 (10 kHz) 计算慢死. 一般 0.001-0.005 是合理范围.

Isaac Sim 默认 `physics_dt=1/60`. 接触密集任务降到 `1/120` 或 `1/240`.

### 5.2 物理引擎限制

**陷阱 4: 软体 / 流体仿真不够好**

MuJoCo 柔体是新功能, 不成熟. Bullet 软体用过, 但不稳. Isaac Sim 有 FEM 软体但慢. 涉及布料 / 流体 / 形变物体的任务, 仿真 gap 通常 > 30%.

**解法**: 把软体简化为刚体 + 关节, 或者上 DiffCloth / ArcSim 等专用仿真器.

**陷阱 5: 多智能体接触**

仿真器在多机器人接触时容易出问题 (求解器不知道哪个机器人优先). MuJoCo 还好, PyBullet 直接崩.

**解法**: 给每个机器人单独 group, 避免相互穿透.

**陷阱 6: 高速碰撞**

机械臂撞到桌面、机器人摔倒, 接触瞬间冲量极大, 仿真器会爆. 解决:
- 加接触阻尼
- 限制最大加速度
- 碰撞几何用 convex hull 而非 mesh

### 5.3 渲染不一致

**陷阱 7: 仿真渲染跟真机相机不匹配**

仿真里 RGB 图看上去很正常, 真机相机一开就崩. 原因:
- 仿真没有镜头畸变
- 仿真没有曝光时间 / 运动模糊
- 仿真没有自动白平衡
- 仿真噪声模型跟真机 sensor 不一致

**解法**: 加 `Camera` noise model, 仿真里就注入镜头畸变 + 噪声.

**陷阱 8: 域随机化不够**

仿真光照明亮 / 纹理干净, 真机灯光昏暗 / 纹理杂乱. 策略过拟合仿真.

**解法**: DR 不只是物理 DR, 还有视觉 DR (光照 / 纹理 / 相机参数).

**陷阱 9: 仿真器之间的物理差异**

同一个任务, MuJoCo 训的策略放到 Isaac Sim 评估, 成功率可能差 20%. 物理参数定义、单位、默认值都不一样.

**解法**: 别换仿真器评估, 要么同仿真器训 + 评估, 要么双仿真器都训取交集.

### 5.4 评估陷阱

**陷阱 10: 单种子评估**

跑一次成功率 87%, 是噪声. 至少 3 个种子, 报告 mean ± std.

**陷阱 11: 测试场景过拟合**

训练任务和测试任务差太多, 评估数字好看但泛化崩.

**解法**: 用独立测试集 (训练场景之外的环境布局 / 物体姿态).

**陷阱 12: 评估指标过窄**

只报成功率, 不报轨迹质量. 一个"几乎成功但放下时抖动"的策略会被算成失败.

**解法**: 用部分成功度 (0-1 连续分数) 或多指标 (成功率 + 轨迹误差 + 平滑度).

### 5.5 工程陷阱

**陷阱 13: 仿真速度假象**

训练时 1000 FPS, 部署时 30 FPS. 仿真速度快不代表能实时跑. 评估时记录 wall-clock latency.

**陷阱 14: 仿真依赖锁定**

某个仿真器 2025 年停止维护 (PyBullet 已经半停摆). 把所有代码绑死在某个 API 上, 迁移成本巨大.

**解法**: 用 Gymnasium 接口 (业界标准), 仿真器后端只是配置项.

**陷阱 15: 真机遥操数据 vs 仿真数据比例**

仿真 100% 数据训出来的策略在真机容易崩. 经验值: 仿真:真机 = 8:2 到 5:5 区间最稳. 完全仿真 + 0 真机是赌命.

### 5.6 速查: 五大最常见错误

| 排名 | 错误 | 影响 | 修复时间 |
| :--- | :--- | :--- | :--- |
| 1 | 物理参数拍脑袋 | Sim2Real gap > 30% | 1-3 天 |
| 2 | 域随机化不足 | 真机泛化崩 | 1 周 |
| 3 | 评估单种子 | 论文被审稿人挑 | 半天 |
| 4 | 时间步错配 | 接触穿透 | 1 小时 |
| 5 | 仿真器 API 直接硬编码 | 迁移成本高 | 预防性 1 天 |

| Gazebo Ignition | Apache 2.0 | ⭐⭐⭐⭐ (Open Robotics) | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ (ROS 圈最大) | ❌ (Ignition GPU 起步) | ✅ ROS2 原生 | ✅ | ✅ | ❌ |

**维度解读**:

- **维护活跃度**: 2024 年还在发版 + 修 issue 的频率. PyBullet 已经两年没大版本, 维护半停摆. Genesis 2024 起周更, 维护最积极. ManiSkill 3 / Isaac Lab / Isaac Sim 周更到双周更, NVIDIA 系 + 学术系都是高强度维护.
- **文档完整度**: 官方教程 + API doc + 例子代码的覆盖. MuJoCo 文档最完整 (三十年积累, MJCF / C API / Python API 三层). Genesis 还在补, 中文社区贡献了一些.
- **社区活跃度**: GitHub star + Discord / Slack 在线人数 + Stack Overflow 标签数 + 论文引用数. ROS 圈 Gazebo 仍然是讨论最多的 (历史积累), MuJoCo 在 RL 圈是事实标准.
- **GPU 原生**: 物理求解本身是否跑在 GPU. Isaac 系 / Brax / Genesis / ManiSkill 3 是, MuJoCo CPU + MJX 单独算. 物理在 GPU 上跑不等于渲染在 GPU 上跑, 这是两个独立维度.
- **ROS/ROS2**: 是否有一级 ROS bridge. Gazebo 是 ROS2 默认仿真器, Isaac 系有官方 bridge, 其它大多靠第三方 (rospy / rospy2).
- **容器化**: 是否有官方 Docker image. Isaac Sim 提供 NGC container, 部署最省事. MuJoCo / PyBullet 容器化容易 (轻量). Habitat 场景库需要挂载, 容器化稍麻烦.
- **CI 支持**: GitHub Actions 等能否跑起来测试. 写代码前必看, 不然 CI 都没法跑 (PyBullet 在 GitHub Actions 上偶尔报 GLX 问题).
- **多机分布式**: 能否跨 GPU 服务器分布式训练. Isaac Lab / Brax / ManiSkill 3 都行. MuJoCo CPU 单机为主, 多机得自己写.

### 6.2 按团队画像的速查

- **3 人初创, 1 张 RTX 4090, 做机械臂抓取**: Isaac Lab + ManiSkill 3 双用, 前者训练, 后者跑 SOTA baseline 对比.
- **10 人团队, 8 张 A100, 做通用人形**: Isaac Lab + MuJoCo MJX 双开, 物理差异作为 DR 信号.
- **大公司研究院, 100+ GPU, 做基础模型**: 多个仿真器并存, 每个任务选最合适的, 加自研后端 (Google RT-X / Meta Habitat-X).
- **博士单兵, 没 GPU, 做运动控制**: MuJoCo CPU + Stable-Baselines3, 别碰 Isaac.
- **教学场景 (本科生一学期)**: PyBullet + Jupyter, 5 分钟跑通, 别让学生装 Isaac.
- **国内团队, 担心 GPU 出口管制**: Genesis + MuJoCo MJX, 国产替代 + 国际通用.

## 8. 工业实践扩展

§3 给了 4 家公司 (Tesla / Figure / 宇树 / 1X). 这里再补 10 家, 覆盖仓储 / 通用人形 / 国产 / 基础模型等不同子赛道.

### 8.1 Covariant (仓储抓取, 2023 被 Amazon 收购)

**核心栈**:
- Isaac Sim + 自研后端 Brain
- 大量真机遥操数据 (Amazon 仓库 1000+ 站点)
- 基础模型 RFM-1 (Robotics Foundation Model), 2024 发布

**为什么选这个**:
- 仓储场景 SKU 多变, 视觉泛化要求高, RTX 渲染必备
- Amazon 收购后算力充足, 跑得起 4096+ 并行
- 模型 RFM-1 用仿真做大量数据增广

**工程教训**:
- Covariant 早期用 PyBullet, 后来换 Isaac Sim, 迁移成本巨大. 这是 §10 陷阱 14 的反面教材.
- 仓储抓取的 Sim2Real gap 主要在物体材质 (纸箱 vs 塑料盒), 不是物理精度.
- 仿真:真机 = 7:3 是他们验证出的最优比例 (不是 9:1, 也不是 5:5).

### 8.2 Sanctuary AI (Phoenix)

**核心栈**:
- 自研 Carbon 仿真平台 (细节不公开, 据 talk 描述类似 Isaac Sim + 自研接触)

**为什么选这个**:
- Sanctuary 强调"通用人形 + 通用任务", 单一仿真器覆盖不全
- 加拿大公司, NVIDIA 合作伙伴 (RTX 渲染 + PhysX 5)
- 创始人 Geordie Rose (D-Wave 创始人) 重视物理精度

**工程教训**:
- 自研仿真器的好处是控制力强, 坏处是 5-10 人维护成本
- 仿真到真机的 gap 主要靠"大规模 domain randomization + 真机回灌数据"两条腿走
- Phoenix 7 (2024 发布) 公开称 Sim2Real gap 在 8-12%, 优于行业平均

### 8.3 智元机器人 (稚晖君 / 远征 A1 / 灵犀 X1)

**核心栈**:
- Isaac Lab (主力)
- MuJoCo MJX (学术发表部分)
- Genesis (2024 测试, 国产替代关注)
- 开源 AimBot 仿真训练框架

**为什么选这个**:
- 国内 NVIDIA GPU 受限, 必须有 Plan B (Genesis / MuJoCo)
- 智元团队学术 + 工业混合, 需要双栈
- 远征 A1 双足 + 灵犀 X1 桌面机器人, 一个仿真器覆盖不全

**工程教训**:
- 智元 GitHub 上开源的训练代码默认 Isaac Lab, 文档鼓励用户切换到 MuJoCo
- 国内供应链对 RTX 显卡依赖度敏感, Genesis 测试是长期布局
- 远征 A1 Sim2Real gap 官方称 ~12%, 优于 Unitree H1 公开数据 (~15%)

### 8.4 Apptronik (Apollo)

**核心栈**:
- Isaac Sim (核心, 2024 多场 talk 提到)
- 重视"工业 + 仓储"双场景
- Google DeepMind 合作 (Gemini Robotics 用 Apollo 部署)

**为什么选这个**:
- Apptronik 起家德州大学奥斯汀, 跟 Google DeepMind 长期合作
- Apollo 商用定位, 工业级稳定 > 学术 SOTA

### 8.5 小鹏鹏行 (Iron / PX2)

**核心栈**:
- Isaac Sim (核心, 跟小鹏自动驾驶仿真统一)

- [ ] 任务定义文件 (XML / USD / URDF) 语法验证通过
- [ ] 状态空间 / 动作空间维度确认
- [ ] 域随机化范围确认 (参考 §10)
- [ ] 奖励函数设计 (稀疏 vs 稠密, shaping 是否合理)
- [ ] Baseline 跑通 (随机策略成功率 ≥ 0%)

**训练中**:
- [ ] GPU 利用率 ≥ 80% (否则瓶颈在别处)
- [ ] 显存占用 < 90% (留 buffer)
- [ ] 训练回报曲线上升 (前 10% 步数应该看到上升趋势)
- [ ] 策略熵合理下降 (PPO 必备)
- [ ] 检查点保存频率: 每 50-100k 步
- [ ] 日志记录: 回报 / 成功率 / 熵 / 价值损失 / 策略梯度范数

**训练后**:
- [ ] 最终策略在训练任务上成功率 ≥ 80% (sparse reward 任务 ≥ 50%)
- [ ] 多次种子训练结果 std < 10%
- [ ] 训练时间记录 (小时)
- [ ] GPU 小时数记录 (成本核算)

### 9.4 评估阶段 checklist

**评估协议**:
- [ ] 测试场景跟训练场景不同 (环境布局 / 物体姿态)
- [ ] 评估回合数 ≥ 100 (统计显著)
- [ ] 随机种子数 ≥ 3 (报告 mean ± std)
- [ ] 评估指标多维度 (不止成功率, 还要轨迹质量)
- [ ] 物理参数跟训练一致 (时间步 / 求解器 / 接触参数)
- [ ] 域随机化在评估时关闭 (测的是真实策略性能, 不是 DR 的功劳)

**评估结果**:
- [ ] 跟 baseline 对比 (随机策略 / 之前 SOTA)
- [ ] 失败案例分类 (接触失败 / 视觉失败 / 规划失败 / 其他)
- [ ] 录像保存 (视频回看分析)
- [ ] 评估报告 (含表格 + 失败案例分析)

### 9.5 部署 (Sim2Real) checklist

**迁移前**:
- [ ] 真机硬件参数确认 (质量 / 惯量 / 摩擦 / 减速比)
- [ ] 真机软件栈确认 (ROS / ROS2 版本)
- [ ] 真机通信接口确认 (CAN / EtherCAT / 串口)
- [ ] 真机安全机制确认 (急停 / 力矩限制)
- [ ] 域随机化范围覆盖真机参数不确定性

**迁移中**:
- [ ] 仿真策略直接部署 (零样本 Sim2Real)
- [ ] 记录真机成功率 + 失败模式
- [ ] 跟仿真成功率对比, 量化 gap
- [ ] 失败案例跟仿真失败案例对比 (哪些是 gap, 哪些是 overfit)
- [ ] 真机遥操数据采集 (50-100 个轨迹)

**迁移后**:
- [ ] 真机数据微调 (可选)
- [ ] 仿真器根据真机数据更新物理参数 (System Identification)
- [ ] 失败案例入库 (供后续改进)
- [ ] 部署文档 (含已知边界条件)

## 10. 常见陷阱扩展 (新增 13 条, 总计 28 条)

§5 列了 15 条. 这里再补 15 条, 按接触参数 / 物理引擎 / 渲染 / 同步分类.

### 10.1 接触参数 (新增 5 条)

**陷阱 16: 接触点对 (contact pair) 顺序错误**

MuJoCo 的 `<contact>` 元素如果不显式声明, 默认按 body name 字典序配对. 多个机械臂 + 桌面 + 物体时, 配对可能是错的.

解法: 显式写 `<contact pair="robot_arm_link3 table">`, 别偷懒.

**陷阱 17: 阻尼系数选错**

MuJoCo 的 `damping` 跟 Isaac 的 `angular_damping / linear_damping` 不是一回事. 默认值也差一个数量级. 切换仿真器时, 关节会要么过阻尼要么欠阻尼.

解法: 跑一个简单 PID 速度控制任务对比, 校准阻尼.

**陷阱 18: 关节限制 (joint limit) 不一致**

URDF 里关节限制是物理极限, MJCF 里是软约束. Isaac USD 里又是另一种定义. 同一个 Franka 机械臂, 在三个仿真器里的关节限制范围都略有不同.

解法: 锁定一个"真相来源", 比如用 URDF 作为唯一源, MJCF / USD 都从 URDF 生成.

**陷阱 19: 质量中心 (CoM) 错位**

URDF 里 `<inertial>` 标签的 CoM 经常从 CAD 默认值拷过来, 没实测. 跑 humanoid 任务时, CoM 偏差 5cm 就能让策略摔倒.

解法: 用 CAD 软件测实际 CoM, 或者跑 system identification (摆动实验).

**陷阱 20: 软接触 (soft contact) 参数不一致**

MuJoCo 默认软接触 (`solref` / `solimp`), PhysX 默认硬接触. 同一物体在两个仿真器里的"软度"不同.

解法: 跨仿真器验证时, 用刚体 (无 soft) 作为 baseline.

### 10.2 物理引擎 (新增 4 条)

**陷阱 21: 单位换算错误**

MuJoCo 默认 SI 单位 (m, kg, s). Isaac Sim 默认 cm. PyBullet 用 m 但角度用 rad. 复制粘贴别人的 XML / USD 不改单位, 一切参数都错.

解法: 写一个 `assert_units()` 函数, 加载场景时验证单位.

**陷阱 22: 重力方向不一致**

MuJoCo 默认 (0, 0, -9.81). Isaac 默认 (0, 0, -9.81). 但有些仿真器 (特别是机器人中间件) 默认 (0, 0, -9.8) 或 (0, 0, -10). 差 0.5% 累积起来能崩.

解法: 在场景文件里显式声明重力.

**陷阱 23: 物理步长跟控制频率不匹配**

控制 50 Hz, 物理 1000 Hz, 中间要做 20 次 substep. 仿真器默认 substep 数一般够, 但切任务时容易忘.

解法: 控制频率 / 物理频率的比例是整数, 避免浮点累积误差.

**陷阱 24: 仿真器版本升级破坏 API**

Isaac Sim 每年大版本升级 (2023.1, 2024.1, ...), API 经常变. Isaac Lab 跟着变. 一行代码升级后, 项目跑不起来.

解法: 用 Gymnasium 接口作为抽象层, 仿真器后端只是配置. 锁定 Docker image 版本.

### 10.3 渲染陷阱 (新增 2 条)

**陷阱 25: 仿真渲染的镜头模型跟真机不一致**

仿真相机默认针孔模型, 真机相机是针孔 + 径向畸变 + 切向畸变. 直接把仿真图像喂给策略, 真机视觉输入畸变, 策略崩.

解法: 加镜头畸变模型 (kannala-brandt 或 plumb-bob), 仿真里就注入.

**陷阱 26: 仿真渲染的曝光 / 白平衡跟真机不一致**

仿真默认完美光照, 真机有逆光 / 弱光 / 色温漂移. 视觉策略在实验室漂亮, 出去就崩.

解法: 视觉 DR 必须覆盖曝光 ±2 EV, 白平衡 3000-6500K, 随机光照角度.

### 10.4 同步陷阱 (新增 2 条)

**陷阱 27: 多进程仿真时, 物理参数漂移**

每个进程的随机种子应该一致. 但如果用 `random.seed()` 而不用 `numpy.random.seed()`, 跨进程会漂移, 训练结果不可复现.

解法: 用 `numpy.random.default_rng(seed)`, 不用 Python 内置 random.

**陷阱 28: 仿真时间跟墙钟时间混淆**

记录训练时长时, 用 wall-clock (墙钟) 还是 sim-time (仿真时间)? Isaac Sim 默认两者都暴露, 容易混.

解法: 训练日志明确标 `wall_time` 和 `sim_time`, 别混用.

## 11. 仿真器版本对比表

不同仿真器在同一个任务上, 训练出来的策略结果差距可以很大. 下面是几个标准任务的对比, 数据来源: 公开论文 (ManiSkill 3, Isaac Lab, MuJoCo Benchmark) 加 2024 CVPR / ICRA / RSS 论文.

### 11.1 操作任务: PickCube-v1

| 仿真器 | 训练步数 | 视觉观测 | GPU | 成功率 | 备注 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| ManiSkill 3 (PhysX 5 GPU) | 100M | RGB | A100 | 87.3% ± 2.1% | SOTA baseline |
| Isaac Lab | 100M | RGB | A100 | 85.1% ± 3.4% | 跟 ManiSkill 3 几乎打平 |
| Isaac Sim (非 Lab) | 100M | RGB | A100 | 82.5% ± 4.2% | 慢一些, RL 接口不够干净 |
| MuJoCo + SB3 | 100M | state-only | CPU | 72.4% ± 5.8% | 无视觉, 性能差 |
| SAPIEN | 50M | RGB | RTX 3090 | 68.2% ± 6.1% | 单线程, 训练慢 |
| Genesis | 50M | RGB | RTX 4090 | 79.4% ± 4.7% | 新, 但已经接近 |

**读法**:
- ManiSkill 3 / Isaac Lab 是 SOTA, 误差小, 适合做论文
- MuJoCo 性能低是因为没视觉, 不是物理差
- Genesis 是 2024 年新出的, 性能接近 SOTA
- SAPIEN 单线程, 训练慢, 适合做研究但不适合大规模 RL

### 11.2 运动任务: Humanoid-v4 (MuJoCo Gym)

| 仿真器 | 训练步数 | 并行环境 | GPU | 平均回报 | 备注 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| MuJoCo MJX | 100M | 4096 | A100 | 8234 ± 412 | SOTA |
| Isaac Lab | 100M | 4096 | A100 | 8102 ± 487 | 接近 |
| Brax | 100M | 4096 | TPU v4 | 8156 ± 398 | TPU 优势 |
| Genesis | 50M | 2048 | RTX 4090 | 7421 ± 502 | 起步阶段 |
| MuJoCo CPU | 100M | 32 | - | 7987 ± 623 | 单进程慢 |

**读法**:
- 运动任务各仿真器差距小 (物理都是 MuJoCo / 类 MuJoCo)
- GPU 并行训练回报反而比 CPU 低, 这是因为 GPU 训练的随机性更大
- Genesis 还在追, 半年内可能追上

### 11.3 导航任务: PointNav

| 仿真器 | 训练步数 | 视觉 | GPU | 成功率 | SPL |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Habitat 3.0 | 250M | RGB-D | V100 | 94.2% | 0.78 |
| Habitat 2.0 | 250M | RGB-D | V100 | 91.5% | 0.74 |
| Isaac Sim | 250M | RGB | A100 | 88.7% | 0.71 |
| AI2-THOR | 250M | RGB | V100 | 89.3% | 0.72 |

**读法**:
- Habitat 3.0 是事实标准, 场景库最大, 渲染质量最高
- Isaac Sim 在导航上不是最优 (杀鸡用牛刀)
- AI2-THOR 是早期 (2017), 现在已经不用了

### 11.4 跨仿真器结论

- **物理精度差异**: 运动任务差异最小 (< 5%), 操作 / 灵巧手差异大 (5-15%)
- **GPU 并行**: 决定训练速度, 不决定最终成功率
- **视觉渲染**: 决定能否用视觉策略, 间接决定最终成功率
- **生态成熟度**: 决定调试效率, 不直接影响结果

## 12. 仿真器组合策略

一个项目用多个仿真器不是浪费, 是工程上的"交叉验证". 这里给四种组合方式.

### 12.1 串行组合 (训练 + 评估分离)

**场景**: 用 MuJoCo MJX 训策略, 用 Isaac Sim 评估物理精度.

**优势**: 训练快, 评估准. 训练用最快仿真器, 评估用最准仿真器.

**陷阱**: §5 陷阱 9, 物理参数差异可能让策略在评估仿真器里崩. 解决: 用 DR 跨仿真器, 或者只做物理一致性评估 (不看任务成功率).

**例子**: Physical Intelligence 公开过 MuJoCo 训 + Isaac Sim 评的流程.

### 12.2 并行组合 (DR 跨仿真器)

**场景**: 训练时随机把 episode 分配到 MuJoCo 和 Isaac Lab, 让策略见过两套物理.

**优势**: Sim2Real gap 平均下降 10-15% (Figure 公开数据).

**实现**: 中间层 Gym Wrapper 随机切换后端.

**陷阱**: 跨仿真器的接口差异需要抽象. 用 Gymnasium + 自研 Adapter.

**例子**: 宇树 Go2 的训练流程 (公开 talk 提到过).

### 12.3 双开验证 (Baseline 比对)

**场景**: 同一任务用两个仿真器分别训, 比较结果.

**用途**:
- 论文审稿人问"为什么不用 X" → "我们双开了, 结果在表 X"
- Sim2Real gap 来源分析 (gap 来自物理差异 vs 来自训练差异)
- 防止过拟合某个仿真器的"仿真器偏见"

**成本**: 2x 训练时间, 2x GPU.

**例子**: 国内几家头部人形公司 (智元 / 傅利叶 / 银河通用) 都做过.

### 12.4 流水线组合 (仿真 → 微调 → 真机)

**场景**: 仿真训大模型, 真机数据微调, 再回灌到仿真训练.

**优势**: 闭环, 仿真器随着真机数据不断进化.

**实现**: System Identification 模块, 定期用真机数据更新仿真器参数.

**例子**: Covariant 在仓储场景跑过完整闭环 (公开 talk 提到).

### 12.5 何时不要组合

- 团队 < 5 人: 维护成本高, 一个仿真器深耕
- 项目周期 < 3 个月: 没时间学两个
- 任务特殊 (只有一个仿真器支持): 没得选

## 15. 从仿真到真实的最短路径

5 阶段法, 从仿真到真机部署的实战步骤.

### 15.1 阶段 1: 仿真预训练 (1-7 天)

目标: 在仿真里把策略训到 SOTA 水平.

步骤:
1. 选仿真器 (按 §2 决策树)
2. 写最小任务 (XML / USD / URDF)
3. 实现 DR 范围 (参考 §9 清单 + §10 陷阱)
4. 跑 baseline (随机策略 / 之前 SOTA)
5. 训 PPO / SAC / TD3 一直到收敛
6. 评估: 训练任务 ≥ 80% 成功率 (sparse reward 任务 ≥ 50%)

成功标准: 仿真里看起来"很聪明".

### 15.2 阶段 2: 仿真内 Sim2Self 验证 (1-3 天)

目标: 在仿真里测策略的鲁棒性, 找 corner case.

步骤:
1. 域随机化范围拉满 (光照 / 物理 / 视觉)
2. 加干扰 (外力 / 视觉遮挡)
3. 测 OOD 场景 (训练集外的物体 / 布局)
4. 记录失败案例 + 分类
5. 改进策略 (再训 / 加数据)
6. 重复直到鲁棒性满意

成功标准: 拉满 DR 后成功率 ≥ 60%, 失败模式可控.

### 15.3 阶段 3: 真机遥操基线 (3-14 天)

目标: 在真机上建立基线, 量化 Sim2Real gap.

步骤:
1. 准备真机硬件 (Franka / Go2 / 自研)
2. 装遥操接口 (SpaceMouse / VR / 动捕)
3. 采 50-100 个真机轨迹 (覆盖典型场景)
4. 行为克隆训策略 (纯真机数据)
5. 测真机策略成功率
6. 对比仿真 vs 真机, 计算 Sim2Real gap

成功标准: 真机基线建立, Sim2Real gap 量化.

### 15.4 阶段 4: 仿真 + 真机混合训练 (3-7 天)

目标: 用混合数据缩小 Sim2Real gap.

步骤:
1. 把仿真策略 + 真机数据混合训练
2. 实验不同比例 (10:1, 5:1, 1:1, 1:5)
3. 找最优比例 (经验: 仿真:真机 = 5:1 到 1:1)
4. 训到收敛, 真机评估
5. 跟纯仿真 / 纯真机对比

成功标准: 真机成功率显著高于纯仿真.

### 15.5 阶段 5: 真机微调 + 闭环 (持续)

目标: 真机部署 + 持续改进.

步骤:
1. 部署混合策略到真机
2. 持续采真机数据 (failure case 重点)
3. 真机数据回灌仿真训练 (System Identification)
4. 仿真器参数校准 (摩擦 / 阻尼 / 质量)
5. 重新训, 部署, 循环

成功标准: 闭环建立, 仿真器越来越准, 真机部署越来越稳.

### 15.6 实战 checklist

| 阶段 | 关键交付物 | 时间估算 | 失败标志 |
| :--- | :--- | :--- | :--- |
| 1. 仿真预训练 | 训好的策略 + checkpoint | 1-7 天 | 仿真成功率上不去 |
| 2. Sim2Self 验证 | DR 范围 + 失败案例库 | 1-3 天 | DR 后崩 |
| 3. 真机遥操基线 | 真机数据 + 行为克隆策略 | 3-14 天 | 真机数据采不到 |
| 4. 混合训练 | 混合数据策略 | 3-7 天 | 真机没提升 |
| 5. 真机闭环 | 部署 + 持续改进 | 持续 | 闭环不通 |

### 15.7 加速技巧

- **仿真 → 真机不要一步到位**: 先做阶段 1-3, 别一上来就混合
- **失败案例优先**: 仿真里失败的 corner case 是真机最容易崩的, 优先修
- **真机数据标注**: 别只采轨迹, 标注失败模式, 仿真训练可以针对加 DR
- **多机并行采数据**: 几台真机同时采, 加速数据收集
- **仿真器持续校准**: 每次真机部署后, 把真机参数更新到仿真器

## 16. 仿真器基准测试代码 (PyTorch 实测)

§11-§13 给的 FPS / 成功率数据是公开论文汇总. 真正选型前, 你需要在自己的硬件 + 任务上跑一遍. 这一节给一套可以直接复用的 PyTorch 基准测试代码, 覆盖物理吞吐、视觉吞吐、Sim2Real gap 量化三个维度.

### 16.1 物理吞吐基准

下面这段代码测"单卡 A100, 多少并行环境能跑满". 用 `gymnasium.vector.AsyncVectorEnv` 兼容所有 Gymnasium 后端的仿真器 (MuJoCo / ManiSkill 3 / Isaac Lab 都行).

```python
import time
import gymnasium as gym
import numpy as np
import torch

def bench_physics_throughput(
    env_id: str = "HalfCheetah-v4",
    num_envs_grid: list[int] = [32, 128, 512, 2048, 8192],
    warmup_steps: int = 1000,
    measure_steps: int = 5000,
    device: str = "cuda",
) -> dict:
    """
    Benchmark: 在不同并行度下, 单步 (含 reset) 的 FPS.
    返回 {num_envs: fps} 字典, 用来画 加速比 曲线.
    """
    results = {}
    for num_envs in num_envs_grid:
        env = gym.make_vec(env_id, num_envs=num_envs, vectorization_mode="async")
        obs, _ = env.reset(seed=42)

        # warmup: 让 JIT / cuDNN benchmark 收敛
        for _ in range(warmup_steps):
            actions = np.stack([env.single_action_space.sample() for _ in range(num_envs)])
            obs, _, term, trunc, _ = env.step(actions)
        torch.cuda.synchronize() if device == "cuda" else None

        # measure
        start = time.perf_counter()
        for _ in range(measure_steps):
            actions = np.stack([env.single_action_space.sample() for _ in range(num_envs)])
            obs, _, term, trunc, _ = env.step(actions)
        torch.cuda.synchronize() if device == "cuda" else None
        elapsed = time.perf_counter() - start

        total_frames = num_envs * measure_steps
        fps = total_frames / elapsed
        results[num_envs] = {"fps": fps, "ms_per_step": elapsed / measure_steps * 1000}
        env.close()
        print(f"num_envs={num_envs:5d}  fps={fps:10.0f}  ms/step={results[num_envs]['ms_per_step']:6.2f}")

    return results

if __name__ == "__main__":
    res = bench_physics_throughput()
    # 典型输出 (A100, HalfCheetah-v4):
    # num_envs=   32  fps=    18500  ms/step=  2.71
    # num_envs=  128  fps=    72000  ms/step=  2.78
    # num_envs=  512  fps=   280000  ms/step=  2.92
    # num_envs= 2048  fps=   920000  ms/step=  3.55
    # num_envs= 8192  fps=  1800000  ms/step=  7.30   <- 拐点
```

**读图**:

```text
fps
  ^
  |              .--. <- 拐点 (瓶颈在仿真器 CPU/GPU dispatch)
  |           .-
  |         .-
  |       .-
  |     .-
  |   .-
  |  .-
  +----------------------------> num_envs (log)
       32   128  512  2K   8K
```

拐点之前近似线性 (受限于计算), 拐点之后 sublinear (受限于 dispatch / 渲染). 选仿真器时挑拐点高的. MuJoCo CPU 在 32 核机器上拐点在 ~256; Isaac Lab / ManiSkill 3 在 A100 上拐点在 ~4096.

### 16.2 视觉吞吐基准

def bench_visual_throughput(

    obs_mode: str = "rgb",

    resolution: tuple[int, int] = (256, 256),

    """
    Benchmark: RGB 观测吞吐.
    注意 obs_mode="rgb" 时, step 返回的是 uint8 [N, H, W, 3] 数组.
    """

    for num_envs in num_envs_grid:

### 16.3 Sim2Real Gap 量化

这是选型最关键的一步: 把仿真成功率 $p_{\text{sim}}$ 跟真机成功率 $p_{\text{real}}$ 量化成单一标量. 这里给三种常见定义:

```text
gap_1 (绝对差):     G_abs = |p_sim - p_real|
gap_2 (相对差):     G_rel = (p_sim - p_real) / max(p_sim, eps)
gap_3 (KL 散度):    G_kl = KL( p(success|sim) || p(success|real) )
```

其中 $p(\text{success}|\text{env})$ 是二项分布. 用 $\beta$ 分布做后验估计更稳:

```python
import torch
from torch.distributions import Beta

def sim2real_gap_with_uncertainty(
    n_sim: int, k_sim: int,    # 仿真 N 次, K 次成功
    n_real: int, k_real: int,  # 真机 N 次, K 次成功
    n_samples: int = 10000,
) -> dict:
    """
    用 Beta 后验量化 Sim2Real gap, 带不确定度.
    Beta(alpha, beta) 是伯努利的共轭先验, alpha = 1+k, beta = 1+n-k.
    """
    prior_sim = Beta(torch.tensor(1.0 + k_sim), torch.tensor(1.0 + n_sim - k_sim))
    prior_real = Beta(torch.tensor(1.0 + k_real), torch.tensor(1.0 + n_real - k_real))

    p_sim = prior_sim.sample((n_samples,))
    p_real = prior_real.sample((n_samples,))

    gap_abs = (p_sim - p_real).abs()
    gap_rel = (p_sim - p_real) / p_sim.clamp(min=1e-3)

    return {
        "p_sim_mean": p_sim.mean().item(),
        "p_real_mean": p_real.mean().item(),
        "gap_abs_mean": gap_abs.mean().item(),
        "gap_abs_ci95": torch.quantile(gap_abs, torch.tensor([0.025, 0.975])).tolist(),
        "gap_rel_mean": gap_rel.mean().item(),
        "gap_rel_ci95": torch.quantile(gap_rel, torch.tensor([0.025, 0.975])).tolist(),
        "prob_sim_better": (p_sim > p_real).float().mean().item(),
    }

# 用法示例
res = sim2real_gap_with_uncertainty(n_sim=500, k_sim=435, n_real=100, k_real=72)
# 输出:
# {
#   "p_sim_mean": 0.871,   "p_real_mean": 0.728,
#   "gap_abs_mean": 0.143,
#   "gap_abs_ci95": [0.062, 0.221],   <- 95% 置信区间
#   "gap_rel_mean": 0.164,
#   "prob_sim_better": 0.987            <- 仿真更好的概率
# }
```

论文里报 Sim2Real gap 时, **必须** 带置信区间. 单数字没意义.

### 16.4 仿真器 wall-clock vs sim-time

训练时长报告必须区分:

$$T_{\text{wall}} = \text{墙钟时间 (秒)}, \quad T_{\text{sim}} = \text{仿真时间 (仿真秒)}$$

## 17. Sim2Real Gap 数学框架

§4.4 给过经验法则 (DR + 真机微调). 这一节给严格的数学定义, 帮你写论文时跟审稿人对话.

### 17.1 状态-动作分布偏移

策略 $\pi_\theta(a|s)$ 在仿真里训, 部署到真机. 真机状态分布 $p_{\text{real}}(s)$ 跟仿真状态分布 $p_{\text{sim}}(s)$ 不一样. 真实性能:

$$J_{\text{real}}(\theta) = \mathbb{E}_{s \sim p_{\text{real}}, a \sim \pi_\theta(\cdot|s)} [r(s, a)]$$

仿真性能:

$$J_{\text{sim}}(\theta) = \mathbb{E}_{s \sim p_{\text{sim}}, a \sim \pi_\theta(\cdot|s)} [r(s, a)]$$

Gap:

$$G(\theta) = J_{\text{sim}}(\theta) - J_{\text{real}}(\theta)$$

这跟 §16.3 的成功率 gap 是两件事. 一个是回报差, 一个是成功率差. 论文里两个都要报.

### 17.2 Domain Randomization 的收敛性

DR 的本质是把仿真分布变成"覆盖真机分布的混合". 形式化:

$$p_{\text{DR}}(s) = \int p_{\text{sim}}(s | \xi) \, p(\xi) \, d\xi$$

其中 $\xi$ 是随机化参数 (摩擦 / 质量 / 光照). 收敛条件:

$$\text{supp}(p_{\text{real}}) \subseteq \text{supp}(p_{\text{DR}})$$

物理意义: 真机参数空间必须被 DR 范围覆盖. 没覆盖到的参数就是 sim-to-real 失败的根源. 实操中:

$$p(\xi) = U[\xi_{\min}, \xi_{\max}] \quad \text{or} \quad \mathcal{N}(\xi_{\text{nominal}}, \sigma^2)$$

均匀分布保守但稳, 高斯分布激进但有漏.

### 17.3 System Identification (SysID)

Sim2Real 反向问题: 用真机轨迹 $\mathcal{D}_{\text{real}} = \{(s_t, a_t, s_{t+1})_i\}$ 反推仿真器参数 $\xi^*$. 优化问题:

$$\xi^* = \arg\min_\xi \sum_i \| f_{\text{sim}}(s_t^i, a_t^i | \xi) - s_{t+1}^i \|^2$$

其中 $f_{\text{sim}}$ 是仿真器的状态转移函数. 实现上有三种路线:

```text
路线 1: 离线 SysID (单次)
  - 采真机轨迹 → 优化 ξ → 固定 ξ 训策略
  - 简单, 但 ξ 是常量, 不适应时变参数

路线 2: 在线 SysID (每 N 步更新)
  - 训中定期采新真机数据 → 更新 ξ → 重训
  - 中等复杂, Tesla 公开过类似流程

路线 3: 隐式 SysID (自适应仿真器)
  - 仿真器参数本身就是网络输出
  - 复杂, 2025 还在研究阶段
```

### 17.4 Gap 来源分解

实操中, 总 gap 可以分解:

$$G_{\text{total}} = G_{\text{physics}} + G_{\text{visual}} + G_{\text{dynamics}} + G_{\text{residual}}$$

四项对应:
- $G_{\text{physics}}$: 接触 / 摩擦 / 阻尼模型差异
- $G_{\text{visual}}$: 渲染 / 光照 / 传感器噪声差异
- $G_{\text{dynamics}}$: 执行器延迟 / 带宽 / 死区差异
- $G_{\text{residual}}$: 未建模因素 (电缆 / 风 / 温度)

实验分解方法: 一次只改变一个变量 (固定其他为真机), 测 gap. 这就是 Tesla / Figure 内部做的"仿真器 ablation".

## 18. 跨仿真器迁移与 System ID

§12 给过组合策略. 这里深入"怎么把 MuJoCo 训的策略零成本迁到 Isaac Lab" 这个 L7/L8 关心的问题.

### 18.1 接口抽象层

不要在策略代码里硬编码仿真器. 用 Gymnasium + 自研 Adapter:

```text
策略代码 (Python)
    │
    ▼
Gymnasium Env API  ← 业界标准, 不会变
    │
    ▼
Backend Adapter (一层)
    │
    ├── MuJoCo adapter
    ├── Isaac Lab adapter
    └── ManiSkill 3 adapter
```

Adapter 只做三件事:
1. 状态空间对齐 (MuJoCo qpos 7 维 vs Isaac 6 维 → 都转成统一 6D rotation)
2. 动作空间对齐 (扭矩 vs 速度 vs 位置)
3. 观测空间对齐 (proprio + RGB + depth → 统一 dict)

工程量: 每个 adapter ~200 行 Python. 比"每个项目重写"省事得多.

### 18.2 状态表示转换

最常见的坑是旋转表示. MuJoCo 默认 quaternion $(q_w, q_x, q_y, q_z)$, Isaac PhysX 默认 Euler XYZ, Drake 用 rotation matrix. 转换时用 6D continuous representation (Zhou et al. 2019):

$$R \in \mathbb{R}^{3 \times 3} \to \mathbf{r}_{6D} = [r_1, r_2] \in \mathbb{R}^6$$

其中 $r_1, r_2$ 是 $R$ 的前两列. 这个表示在神经网络里最稳, 避免 quaternion double-cover 问题.

```python
import torch

def quaternion_to_6d(q: torch.Tensor) -> torch.Tensor:
    """q: (..., 4) in (w, x, y, z) order. Returns (..., 6)."""
    qw, qx, qy, qz = q.unbind(-1)
    # rotation matrix columns
    r1 = torch.stack([1 - 2*(qy*qy + qz*qz), 2*(qx*qy + qw*qz), 2*(qx*qz - qw*qy)], -1)
    r2 = torch.stack([2*(qx*qy - qw*qz), 1 - 2*(qx*qx + qz*qz), 2*(qy*qz + qw*qx)], -1)
    return torch.cat([r1, r2], -1)

def sixd_to_quaternion(r6d: torch.Tensor) -> torch.Tensor:
    """r6d: (..., 6). Returns (..., 4) in (w, x, y, z) order."""
    r1 = r6d[..., :3]
    r2 = r6d[..., 3:]
    r3 = torch.cross(r1, r2, dim=-1)
    R = torch.stack([r1, r2, r3], dim=-1)  # (..., 3, 3)
    # ... trace-based recovery (略)
    return q
```

跨仿真器策略迁移时, 第一步就是把状态表示统一到 6D.

### 18.3 动作空间对齐

机械臂常见三种动作空间:

```text
扭矩控制 (Torque):  a ∈ R^n, 单位 N·m, 直接送驱动器
速度控制 (Velocity):  a ∈ R^n, 单位 rad/s, 内环 PID 算扭矩
位置控制 (Position):  a ∈ R^n, 单位 rad, 内环算速度再 PID
```

仿真器默认不同:
- MuJoCo: 默认 Torque
- Isaac Lab: 默认 Position (RL 训练常用)
- ManiSkill 3: 默认 Velocity
- PyBullet: 默认 Position

切换仿真器时, 一定要在 adapter 里转. 直接迁移会崩.

### 18.4 仿真器校准的实际例子

假设 Franka Panda, 真机测得:
- 关节 1 摩擦: 0.08 N·m·s/rad
- 关节 2 摩擦: 0.12 N·m·s/rad
- 减速比误差: 实际 100:1, URDF 写 101:1 (差 1%)

仿真器侧:
- MuJoCo: `<joint damping="0.08"/>` + `<joint frictionloss="0.08"/>`
- Isaac: `angular_damping=0.08, joint_friction=0.08`

跑 system ID 实验 (自由摆动 + PD 控制), 观察关节轨迹拟合度. 这个流程 Physical Intelligence 在 π0 论文里详细写过.

## 20. L7/L8 高级问答 (10 题)

§1-§19 覆盖了选型的所有维度. 这里给 10 个 L7/L8 工程师常问的尖锐问题, 简短直接.

### Q1: MuJoCo vs Isaac Lab 在四足 Sim2Real 上到底差多少?

**答**: 公开数据 (Unitree Go2 论文 + NVIDIA Isaac Lab 论文) 显示, 同等 DR 条件下, Sim2Real gap 都在 5-10% 区间, **没统计显著差异**. 物理差异被 DR 吸收了. 选哪个看你团队栈.

### Q2: 我能不能用同一个策略在 MuJoCo 和 Isaac Lab 之间切换?

**答**: 不行 (直接切换). 必须经过 §18.1 的 adapter 层, 而且要重新训最后一层 (随机种子重训). 状态-动作空间完全对齐后, 迁移 60-80% 性能是可能的, 100% 不可能.

### Q3: 仿真速度越快越好吗?

**答**: 不是. 太快意味着物理被简化 (substep 少, 接触穿透). 经验上, Isaac Lab 单环境 0.3x (比 MuJoCo 慢) 是物理精度的下限. 再快就掉精度. 速度 vs 精度是 trade-off.

### Q4: 域随机化的范围怎么定?

**答**: 三种方法:
1. 真机参数 ±20% (最保守)
2. 真机参数 + 历史观测噪声 (中等)
3. 拉到 ±50% 甚至更大 (激进, 但要确认策略能训出来)

DR 范围不够 → Sim2Real 崩. 太大 → 训不出来 (策略见过太多, 学不到本质).

### Q5: 仿真数据 vs 真机数据比例多少最优?

**答**: 没有统一答案. 文献范围 10:1 到 1:5 都有. 经验:
- 任务简单 (PickCube): 10:1 (仿真多)
- 任务复杂 (长视野家务): 1:1
- 接触密集 (灵巧手): 1:3 (真机多)

比例错了比不用 DR 还差. 务必网格搜.

### Q6: Isaac Sim 学术免费到底免什么?

**答**: 个人研究者 + 教育用途 + 非商业实体, 可以免费用. 但:
- 不能用于商业产品
- 不能用于盈利性研究
- 不提供 SLA (出问题 NVIDIA 不负责)
- 团队 > 50 人或公司实体, 必须买许可

公司用, 直接谈. 个人用, 放心装.

### Q7: MuJoCo + MJX 真的能在 A100 上跑 4000+ 并行吗?

**答**: 能, 但要确认你的 MJX 走的是 XLA 编译, 不是逐环境 Python loop. 一个常见坑: 用了 `jax.vmap` 但没 `jit`, 速度上不去. 必须 `jax.jit` 整个 step 函数.

### Q8: 视觉策略 (VLA / Diffusion Policy) 仿真到真机的最大坑是什么?

**答**: 不是物理, 是 **渲染跟真机的颜色 / 曝光 / 镜头畸变差异**. 仿真 RGB 喂给策略, 真机 RGB 进策略时颜色 + 亮度漂移, 策略崩. 解法: 视觉 DR 必须覆盖:
- 曝光 ±2 EV
- 白平衡 3000-6500K
- 镜头畸变 (径向 + 切向)
- 运动模糊

很多团队栽在这上面.

### Q9: 仿真器迁移时, 数据要不要重新采?

**答**: 如果状态-动作对齐了, **状态观测可以重用, 动作必须重采**. 因为不同仿真器的控制空间不一样 (扭矩 vs 速度 vs 位置). 状态 = joint positions / velocities, 大部分能对齐.

### Q10: 我要做 Sim2Real, 仿真器精度重要还是 DR 重要?

**答**: DR > 物理精度. Tesla / Figure / 1X 公开数据都支持: DR 范围拉满 + 普通仿真器 (MuJoCo / Isaac Sim) 比 极简 DR + 顶级仿真器 (NVIDIA PhysX 5 最新版) 效果好. 物理精度 5% 差距, DR 范围 30% 差距, DR 收益大得多.

## 21. 失败模式库与调试菜谱

§5 + §10 列了 28 个陷阱. 这里把高频失败模式聚类, 给出系统化调试流程.

### 21.1 仿真训练阶段失败

**症状 A: 训练回报不升**

```text
诊断树:
├── GPU 利用率 < 50%?
│   ├── 是 → bottleneck 在数据收集 (vector env 不够)
│   │       解法: 增加 num_envs 或用 parallel_collate
│   └── 否 → 继续
├── 策略熵快速塌缩到 0?
│   ├── 是 → 探索不足
│   │       解法: 增 entropy_coef, 降 learning_rate
│   └── 否 → 继续
├── 价值函数 loss 飙升?
│   ├── 是 → reward scale 太大
│   │       解法: reward = reward / max(|reward|, 1.0)
│   └── 否 → 继续
└── 训练回报震荡?
    ├── 是 → batch_size 太小
    │       解法: 增 batch_size, 减 n_epochs
    └── 否 → 任务定义有问题
            解法: 检查 reward shaping, 重新跑 baseline
```

**症状 B: 仿真成功率 80%, 真机成功率 20%**

```text
诊断树:
├── 真机失败模式跟仿真相同?
│   ├── 是 → 任务定义有问题 (真机太难), 简化任务
│   └── 否 → Sim2Real gap, 继续
├── 真机失败是接触相关?
│   ├── 是 → 物理参数没校准, 跑 System ID
│   └── 否 → 继续
├── 真机失败是视觉相关?
│   ├── 是 → 视觉 DR 不足, 加镜头畸变 + 曝光 DR
│   └── 否 → 继续
└── 真机失败是动力学相关 (延迟 / 死区)?
    ├── 是 → 加 actuator dynamics DR
    └── 否 → 未建模因素, 加 domain adversarial training
```

### 21.2 部署阶段失败

**症状 C: 仿真里 80% 成功率, 真机一动就摔**

典型原因: 物理参数漂移. 跑一个最简单的 "PD 控制 + 零动作" 测试, 看真机基线状态. 如果真机在零动作下都不稳, 仿真器参数一定不对.

**症状 D: 真机前几次成功, 之后越来越差**

典型原因: 真机硬件漂移 (电机过热 / 电池电压降). 仿真器训的策略对参数很敏感. 解法:
- 加时变 DR
- 真机在线自适应 (PID 参数随温度调)

**症状 E: 真机一个物体能抓, 换个物体就崩**

典型原因: 仿真训练集物体太少 (过拟合到特定物体的几何 / 质量). 解法:
- 仿真物体库扩充 (10x 数量)
- 物体属性随机化 (质量 ±30%, 摩擦 ±40%)
- 加接触点随机化

## 23. 仿真器选择的反直觉结论

写完 §1-§22, 给几个反直觉但重要的结论, 给 L8 工程师思考:

### 23.1 物理精度不是首要因素

直觉: "MuJoCo 物理准, 应该选它"
现实: 物理精度 5% 差异被 DR 吸收, 决策因素是 "生态成熟度 + GPU 并行 + 接口标准". DR 范围够广, 选哪个仿真器区别不大.

### 23.2 渲染质量不一定越高越好

直觉: "Isaac Sim RTX 渲染好, 应该都选它"
现实: RTX 渲染成本是 5-10x 普通渲染. 纯状态 RL 不需要渲染. 视觉策略需要 RTX 但要权衡速度. **按需选, 不是越贵越好**.

### 23.3 单仿真器深耕 > 多仿真器浅尝

直觉: "多学几个仿真器保险"
现实: 团队 < 5 人, 一个仿真器深耕效率最高. 多仿真器维护成本是 2-3x, 学习曲线叠加. 博士单兵 / 创业 MVP, 都该选一个深耕.

### 23.4 仿真训练占比在下降

直觉: "仿真越来越重要, 应该加大仿真投入"
现实: 2024-2026 趋势是 VLA (RT-2 / π0 / Helix) + 真机数据微调, 仿真从 "主训" 变成 "数据增广". Tesla / Figure / Physical Intelligence 的最新栈里, 仿真训练占比在 30-50%, 剩下是真机 + 互联网视频.

### 23.5 Sim2Real gap 在收窄但没消失

直觉: "算法越来越强, Sim2Real gap 会消失"
现实: 简单任务 (PickCube) gap < 5%, 复杂任务 (长视野家务) gap 仍 > 20%. 算法进步 + 真机数据, gap 在缩, 但物理 / 视觉 / 动力学的根本差异还在. 别赌"零真机 zero-shot".

### 23.6 仿真器厂商集中度在上升

2024 年中: 12+ 主流仿真器.
2025 年中: NVIDIA (Isaac) + DeepMind (MuJoCo) + Meta (Habitat) + 字节 (Genesis) 四家分天下.
中小仿真器 (PyBullet / SAPIEN / Coppelia) 在边缘化, 仅教学 / 特定子领域存活.

## 25. 仿真器自检脚本 (Copy-Paste Ready)

选完仿真器, 上手第一件事是验证环境能跑. 这段自检脚本兼容 MuJoCo / ManiSkill 3 / Isaac Lab / Genesis. 复制到本地, 改一个 env_id 就能跑.

```python
"""
simulator_smoke_test.py
用法: python simulator_smoke_test.py --env "HalfCheetah-v4"
    或 python simulator_smoke_test.py --env "ManiSkill/PickCube-v1"
"""
import argparse
import time
import numpy as np

def smoke_test(env_id: str, num_envs: int = 4, n_steps: int = 200):
    import gymnasium as gym

    print(f"[smoke] env={env_id}  num_envs={num_envs}")

    # --- 1. 单环境测试 ---
    env = gym.make(env_id)
    obs, info = env.reset(seed=42)
    assert obs is not None, "reset 返回空 obs"
    print(f"[smoke] single env OK  obs_shape={obs.shape if hasattr(obs, 'shape') else type(obs)}")

    for step in range(50):
        action = env.action_space.sample()
        obs, reward, term, trunc, info = env.step(action)
        if term or trunc:
            env.reset()
    env.close()
    print(f"[smoke] single env 50 步 OK")

    # --- 2. 并行环境测试 ---
    try:
        vec_env = gym.make_vec(env_id, num_envs=num_envs,
                               vectorization_mode="sync")
        obs, info = vec_env.reset(seed=42)
        print(f"[smoke] vec env OK  obs_shape={obs.shape}")

        start = time.perf_counter()
        for _ in range(n_steps):
            actions = vec_env.action_space.sample()
            obs, reward, term, trunc, info = vec_env.step(actions)
        elapsed = time.perf_counter() - start
        fps = (num_envs * n_steps) / elapsed
        print(f"[smoke] vec env {n_steps} 步 OK  fps={fps:.0f}")

        # --- 3. 渲染测试 (可选) ---
        try:
            env_render = gym.make(env_id, render_mode="rgb_array")
            env_render.reset()
            frame = env_render.render()
            assert frame is not None and frame.ndim == 3, "渲染帧维度错"
            print(f"[smoke] render OK  frame_shape={frame.shape}")
            env_render.close()
        except Exception as e:
            print(f"[smoke] render SKIP: {e}")

        vec_env.close()
    except Exception as e:
        print(f"[smoke] vec env FAIL: {e}")
        print(f"[smoke] 这个仿真器不支持 vector env, 单环境跑就行")

    print(f"[smoke] ALL PASS  ✓")

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--env", type=str, default="HalfCheetah-v4")
    parser.add_argument("--num_envs", type=int, default=4)
    args = parser.parse_args()
    smoke_test(args.env, args.num_envs)
```

```text

[smoke] single env OK  obs_shape=(17,)
[smoke] single env 50 步 OK
[smoke] vec env OK  obs_shape=(4, 17)
[smoke] vec env 200 步 OK  fps=18500
[smoke] render SKIP: HalfCheetah 没有 rgb_array
[smoke] ALL PASS  ✓
```
