# 6.7 Mixture of Depths (MoD)

---

## 1. 内容介绍

**Mixture of Depths (MoD)** 是 NVIDIA 2024 年提出的**动态深度分配**架构, 让模型**动态跳过不需要的层**, 节省 50%+ 计算.

**核心思想**: 不是所有 token 都需要经过所有层, 简单的 token 早 exit, 复杂的 token 多算.

---

## 2. 为什么这么做

**问题 (Transformer 的固定深度)**:
- 所有 token 都要经过 $N$ 层 (e.g. 32 层)
- 简单 token (如 "the", "a") 浪费算力
- 复杂 token (数学题, 推理) 算力不够

**解决思路**:
- 每个 token 在每层前, 路由器决定"跳过"或"经过"
- 跳过的 token 直接到下一层 (identity / residual)
- 不同 token 走不同路径

**vs MoE (稀疏专家)**:
- MoE: 同一层内选不同专家
- MoD: 不同 token 走不同层数
- MoD 更通用, 节省更多

---

## 3. 这么做的原因 (MoD vs MoE)

| 维度 | MoE | MoD |
|---|---|---|
| 稀疏维度 | 专家 | 深度 (层数) |
| 节省 | 激活参数 (计算相似) | 跳过层 (真正省) |
| 实现 | 路由 + 多专家 | 路由 + 跳过 |
| 训练 | 复杂 (负载均衡) | 简单 (top-k=容量) |
| 加速 | 推理慢 (路由开销) | 推理真快 |
| 质量 | ★★★★★ | ★★★★ |

**MoD 的关键设计**:
- **容量 (Capacity)**: 每层最多处理 $C$ 个 token, 其余跳过
- **路由器**: 简单 MLP 输出 0/1 (是否处理)
- **跳过机制**: 没选中的 token 直接到下一层 (residual)

---

## 4. 解决了什么问题

- **推理加速**: 简单 token 早 exit, 总体计算减 50%+
- **模型灵活性**: 不同 token 走不同路径
- **可解释**: 路由器决定哪些 token 重要

---

## 5. 意义

- 2024+ 动态架构的新方向
- NVIDIA 在 Mamba / MoD 等都有投入

---

## 6. 公式表达

```text
MoD Block:
  # 路由器: 决定每个 token 是否进这一层
  router_logits = W_router(x)  # (B, n, 1)
  keep = top-k(router_logits, k=C)  # 选 C 个, 其余跳过

  # 选中的 token 走 block
  x_kept = x[keep]  # (B, C, d)
  y_kept = x_kept + Block(x_kept)

  # 跳过的 token 走 identity
  y_skipped = x[~keep]  # (B, n-C, d)

  # 合并 (按原顺序)
  y = combine(y_kept, y_skipped, keep)  # (B, n, d)

  # 残差
  return x + y

Capacity: 每层最多处理 n × C_fraction 个 token
典型: C_fraction = 0.5 (50% token 经过这一层)
```

## 9. 答案

### 答案 1: MoD vs MoE

```text
MoE (Mixture of Experts):
  - 同一层, 选不同专家
  - 总参数量大, 激活量小
  - 路由 + 专家计算, 路由开销大
  - 适合: 大容量 LLM (Mixtral, DeepSeek-V3)

MoD (Mixture of Depths):
  - 同一模型, 选跳过层
  - 总计算量小, 激活量小
  - 路由器简单, 跳过即 identity
  - 适合: 推理加速, 节能
```

### 答案 2: MoD Block

```python
import numpy as np

class MoDBlock:
    def __init__(self, d_model, capacity=0.5):
        self.d_model = d_model
        self.capacity = capacity
        # 路由器: 简单线性
        self.W_router = np.random.randn(d_model, 1) * 0.02
        # 标准 transformer block (简化)
        self.W1 = np.random.randn(d_model, 4 * d_model) * 0.02
        self.W2 = np.random.randn(4 * d_model, d_model) * 0.02

    def forward(self, x):
        """
        x: (B, n, d_model)
        每层最多处理 capacity * n 个 token
        """
        B, n, d = x.shape
        # 1. 路由器得分
        router_logits = x @ self.W_router  # (B, n, 1)
        router_logits = router_logits.squeeze(-1)  # (B, n)

        # 2. 选 top-C 个 token
        n_keep = int(n * self.capacity)
        top_idx = np.argsort(-router_logits, axis=-1)[:, :n_keep]  # (B, n_keep)

        # 3. 处理选中的 token
        # 简化: 用 fancy indexing
        keep_mask = np.zeros((B, n), dtype=bool)
        for b in range(B):
            keep_mask[b, top_idx[b]] = True

        y = x.copy()
        for b in range(B):
            kept = x[b, keep_mask[b]]  # (n_keep, d)
            # 走 transformer block
            block_out = np.maximum(0, kept @ self.W1) @ self.W2
            y[b, keep_mask[b]] = kept + block_out
            # 跳过的: identity (不修改)

        return y
```

**关键**: 跳过的 token 不算 block, 直接 residual → identity.

### 答案 3: 理论加速

```text
模型 32 层
capacity = 0.5 (每层处理 50% token)
```

**平均路径长度**:
- 每个 token 平均 32 × 0.5 = 16 层经过
- 等效于 16 层 Transformer

**加速**: 32 / 16 = **2x**

**但实际**:
- 路由器有开销 (每层都计算 router_logits)
- 跳过 token 仍要算 attention (除非 router 前算)
- 实际加速约 1.5-1.8x

## 10. MoD 的局限

```text
1. 路由器训练难:
   - 二元决策, 不可微 (用 straight-through estimator)
   - 容量限制要严格 (否则所有 token 都选)

2. 加速有限:
   - 路由器开销大
   - 不并行时跳过没省
   - 实际加速 1.5-1.8x (理论 2x)

3. 工程复杂:
   - 动态图 (不规则 batch)
   - 不易优化
```

## 11. 深入: 为什么用"容量固定 top-k"而非"阈值门控"

直觉上应该"路由分数 > 阈值就处理"。但那样每个 batch 处理的 token 数**不确定** → 计算图动态、显存不可预测、难并行。MoD 改用**固定容量 top-k**:每层恰好处理 $C\cdot n$ 个 token,保证:
- **静态计算图**:每层算量固定,可预测、可编译优化。
- **可批处理**:选中的 token 打包成规则张量。

代价:引入了"未来信息"——top-k 需要看到整段序列的分数(训练时用 causal 友好的变体或辅助预测器规避)。

---

## 12. 深入: 路由不可微问题与训练技巧

"处理 or 跳过"是二元决策,不可微。解法:
- **让路由权重参与残差**:被选中的 token 输出乘以路由分数(sigmoid),使梯度能流回路由器(类比 MoE 的门控权重)。
- **辅助预测器**:训练一个小网络预测"该 token 是否会被 top-k 选中",推理时用它做 causal 决策(不依赖未来)。

这与 MoE 路由的可微化思路一脉相承(见 [5.6 MoE](../第05章-Transformer架构/第05章-06-MOE.md))。

---

## 13. 深入: 动态计算的谱系(MoD 在其中的位置)

"让不同输入用不同计算量"是一大趋势,MoD 是其中一支:

| 技术 | 动态维度 | 机制 |
| :--- | :--- | :--- |
| **早退出(Early Exit)** | 深度 | 置信度够就提前出层 |
| **MoD** | 深度(逐层) | 每层选部分 token 处理 |
| **MoE** | 宽度 | 选部分专家 |
| **投机解码** | 序列 | 小模型草稿+大模型验证 |
| **推理模型(o1)** | 序列长度 | 难题生成更长推理链 |

**共同哲学**:计算量应随"输入难度"自适应,而非一刀切。这与推理模型的 test-time compute(见 [LLM发展第06章](../../LLM发展/第06章-推理能力演进.md))是同一思想在不同层面的体现。

## 15. MoD 论文背景与历史脉络

### 15.1 论文出处

**标题**: "Mixture-of-Depths: Dynamically allocating compute in transformer-based language models"

**作者**: Raposo et al. (NVIDIA)

**年份**: 2024

**链接**: arXiv 2404.02258

**核心贡献**: 首次系统性地展示**如何**在 Transformer 中实现**逐 token 动态深度**, 并验证其在大规模 (e.g. 1B-3B) Transformer LM 上的可行性。

### 15.2 位置: 在 LLM 架构演进树中的位置

```text
2017: Transformer (固定深度)
        │
2018-2020: BERT/GPT-1/2 (固定深度)
        │
2020-2022: GPT-3, T5 (固定深度)
        │
```

## 16. 形式化: MoD 的精确定义

### 16.1 标准 Transformer 层 (回顾)

**前置 Norm + Transformer Block (简化)**:
```text
h_l = h_{l-1} + Attention(RMSNorm(h_{l-1}))
h_l = h_l   + FFN(RMSNorm(h_l))
```

**所有 token 都走完这 N 层。**

### 16.2 MoD 改造

在每层前加一个**路由器**:

$$
\text{router}_\ell(h_{l-1}) = \sigma(W_\ell \cdot h_{l-1}) \in [0,1]
$$

然后**选 top-C 个** (固定容量):
$$
\text{mask}_\ell = \text{top-}k(\text{router}_\ell(h_{l-1}), k=C\cdot n)
$$

实际层:
$$
h_l = \begin{cases}
h_{l-1} + F_\ell(h_{l-1}) & \text{if token 被选} \\
h_{l-1} & \text{otherwise (residual)}
\end{cases}
$$

其中 $F_\ell$ 是该层的 Transformer Block (attention + FFN)。

### 16.3 Capacity Fraction

每层最多处理的 token 比例:
$$
c = \frac{C}{n}, \quad c \in (0, 1]
$$

典型设置:
| 模型 | C 值 | 比例 | 备注 |
| :--- | :--- | :--- | :--- |
| **Nano MoD** | 0.5n | 50% | 论文 default |
| **Decoder Only 大模型** | 0.5n | 50% | 推理加速主要 |

**不是所有层都是同一 C**: 论文展示了 C 随深度变化有时更好 (e.g. 中间层低, 顶层高)。

### 16.4 路由器的"决策空间"

路由器实际是个**二进制决策**: 处理 or 跳过。

二种实现:
1. **Soft routing (加权)**:
   $$h_l = h_{l-1} + w \cdot F(h_{l-1}), \quad w = \sigma(router)$$
   > 缺点: 算 $F$ 总是要算, 没省算力。

2. **Hard routing (top-k)**:
   $$h_l = h_{l-1} + F(h_{l-1}) \cdot \mathbb{1}[\text{selected}]$$
   > 优点: 真的省算力。**MoD 用这个**。

### 16.5 完整数学表达

**输入**: token 序列 $x \in \mathbb{R}^{n \times d}$, 当前层 $h_{l-1}$.

**Step 1**: 计算路由分数
$$
r = W_\ell h_{l-1} \in \mathbb{R}^{n \times 1}, \quad r_i = W_\ell^\top h_{l-1,i}
$$

**Step 2**: 选择 top-C
$$
\text{idx}_{\text{keep}} = \text{argtop-}k(r, k = \lfloor c \cdot n \rfloor) \in \mathbb{R}^{C}
$$

**Step 3**: 选中的 token 走 block
$$
h_{l-1}^{\text{keep}} = h_{l-1}[\text{idx}_{\text{keep}}] \in \mathbb{R}^{C \times d}
$$
$$
h_{\text{processed}} = F(h_{l-1}^{\text{keep}}) \in \mathbb{R}^{C \times d}
$$

**Step 4**: 合并 (恢复原顺序)
$$
h_l = \text{scatter}(h_{\text{processed}}, h_{l-1}, \text{idx}_{\text{keep}})
$$

其中 $\text{scatter}$ 把处理过的 token 放回原位置, 未处理的 token 保持 residual。

### 16.6 容量限制的必要性

**直觉**: 路由器训练时会被"诱惑"——把所有 token 都打高分, 这样所有 token 都进 block → 退化为标准 Transformer。

**容量的"力"**:
- 强制每层**最多**处理 $C$ 个 token
- 路由器必须"挑选"哪些最该处理
- 自然让路由器学到"判断 token 难度"

**对比 MoE 的辅助 loss**:
- MoE 用 load balancing loss 鼓励均匀分布 (否则专家偏载)
- MoD 的固定 capacity 天然达到此目的 (无需额外 loss)

## 17. PyTorch 完整实现

下面是**生产级** 的 MoD 实现:

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class MoDRouter(nn.Module):
    """MoD 路由器: 每层独立"""
    def __init__(self, d_model, hidden=64):
        super().__init__()
        # 简单 MLP 输出 scalar
        self.net = nn.Sequential(
            nn.Linear(d_model, hidden),
            nn.SiLU(),
            nn.Linear(hidden, 1, bias=False)
        )
        # 初始化: 让一开始多数 token 都不被选中
        nn.init.constant_(self.net[-1].weight, -0.1)

    def forward(self, x):
        # x: (B, n, d_model)
        # 返回: (B, n) 路由分数 (scalar per token)
        return self.net(x).squeeze(-1)


class MoDBlock(nn.Module):
    """单个 MoD 块 = 路由器 + 标准 Transformer Block"""
    def __init__(self, d_model, n_heads, capacity_fraction=0.5,
                 ffn_mult=4, use_rmsnorm=True):
        super().__init__()
        self.d_model = d_model
        self.capacity = capacity_fraction
        self.n_heads = n_heads
        assert 0 < capacity_fraction <= 1.0

        # 路由器
        self.router = MoDRouter(d_model)

        # 标准 Transformer Block (处理的 token 走这里)
        self.use_rmsnorm = use_rmsnorm
        if use_rmsnorm:
            self.norm1 = nn.RMSNorm(d_model)
            self.norm2 = nn.RMSNorm(d_model)
        else:
            self.norm1 = nn.LayerNorm(d_model)
            self.norm2 = nn.LayerNorm(d_model)

        self.attn = nn.MultiheadAttention(d_model, n_heads, batch_first=True)
        self.ffn = nn.Sequential(
            nn.Linear(d_model, d_model * ffn_mult, bias=False),
            nn.GELU(),
            nn.Linear(d_model * ffn_mult, d_model, bias=False),
        )

    def forward(self, x):
        """
        x: (B, n, d_model)
        返回: y (B, n, d_model)
        """
        B, n, d = x.shape
        C = max(1, int(self.capacity * n))  # 本层最大处理 token 数

        # 1. 路由
        router_logits = self.router(x)  # (B, n)

        # 2. 选 top-C (forward 时)
        if not self.training:
            # 推理: 真正选 top-C, 跳过其余
            topk_logits, topk_idx = torch.topk(router_logits, k=C, dim=-1)  # (B, C)

            # 3. 收集被处理的 token
            # gather: (B, n, d) → (B, C, d)
            idx_expanded = topk_idx.unsqueeze(-1).expand(-1, -1, d)
            x_kept = torch.gather(x, dim=1, index=idx_expanded)

            # 4. 跑块
            h = self.norm1(x_kept)
            h, _ = self.attn(h, h, h, need_weights=False)
            h_kept = x_kept + h
            h_kept = h_kept + self.ffn(self.norm2(h_kept))

            # 5. 散布回去 (scatter)
            y = x.clone()
            y.scatter_(dim=1, index=idx_expanded, src=h_kept)

            return y
        else:
            # 训练: 用 straight-through estimator 或者用 soft routing
            # 简化: 训练时所有 token 都走, 但算 loss 时强制 top-k
            h = self.norm1(x)
            h, _ = self.attn(h, h, h, need_weights=False)
            h = x + h
            h = h + self.ffn(self.norm2(h))
            return h
```

### 17.1 训练时的" 关键"

训练时的难点是**梯度反传**——"跳过的 token" 不算 block, 路由决策是离散的。

**NVIDIA 论文的解法**:
1. 用 `torch.where` 或 `torch.scatter` 区分
2. 路由器输出 sigmoid score, 乘到 block 输出上 (类似 MoE 的 gate)
3. capacity 强制保证选 C 个 (用 topk)

**简化训练形式** (论文中的 loss):

$$
\mathcal{L} = \mathcal{L}_{\text{LM}} + \alpha \cdot \mathcal{L}_{\text{balance}}
$$

其中 $\mathcal{L}_{\text{balance}}$ 鼓励路由均衡 (用 topk 隐式保证)。

### 17.2 端到端 MoD 模型

```python
class MoDTransformer(nn.Module):
    """带 MoD 的标准 Transformer Decoder"""

    def __init__(self, n_layers=12, d_model=512, n_heads=8,
                 vocab_size=50000, capacity_fraction=0.5, max_seq_len=2048):
        super().__init__()
        self.embed = nn.Embedding(vocab_size, d_model)
        self.pos_embed = nn.Embedding(max_seq_len, d_model)

        # N 个 MoD Block
        self.blocks = nn.ModuleList([
            MoDBlock(d_model, n_heads, capacity_fraction=capacity_fraction)
            for _ in range(n_layers)
        ])

        self.lm_head = nn.Linear(d_model, vocab_size, bias=False)
        # weight tying
        self.lm_head.weight = self.embed.weight

    def forward(self, input_ids):
        B, n = input_ids.shape
        pos = torch.arange(n, device=input_ids.device).unsqueeze(0).expand(B, n)

        x = self.embed(input_ids) + self.pos_embed(pos)

        for block in self.blocks:
            x = block(x)

        logits = self.lm_head(x)
        return logits


# 训练循环 (简化)
def train_step(model, batch, optimizer, scheduler=None):
    input_ids, labels = batch

    optimizer.zero_grad()
    logits = model(input_ids)
    loss = F.cross_entropy(
        logits.view(-1, logits.shape[-1]),
        labels.view(-1),
        ignore_index=-100
    )
    loss.backward()
    optimizer.step()
    if scheduler: scheduler.step()
    return loss.item()
```

### 17.3 推理加速计算

```python
def estimate_mod_speedup(n_layers=32, capacity=0.5):
    """
    估计 MoD 理论加速比
    """
    # 假设平均每个 token 实际经过的层数
    avg_layers_per_token = n_layers * capacity

    # 等效深度
    effective_depth = avg_layers_per_token

    # 加速比 (vs 全部 token 走全部层)
    speedup = n_layers / effective_depth

    # 实际加速 (考虑路由器开销, 不完美路由)
    real_speedup = speedup * 0.85  # 经验值: 实际约 85% 的理论

    return {
        'avg_layers_per_token': avg_layers_per_token,
        'effective_depth': effective_depth,
        'theoretical_speedup': speedup,
        'realistic_speedup': real_speedup,
    }


# 例
print(estimate_mod_speedup(n_layers=32, capacity=0.5))
# {'avg_layers_per_token': 16.0, 'effective_depth': 16.0,
#  'theoretical_speedup': 2.0, 'realistic_speedup': 1.7}
```

## 18. MoD 训练策略深度解析

### 18.1 路由器"初始化" 的重要性

**问题**: 一开始路由器随机, 所有 token 都想进 block。Capacity 强制 top-k, 但可能不均衡。

**NVIDIA 解决方案**: 用"先训个 warmup"
1. 前 N 步: capacity = 1.0 (即不跳过, 标准 Transformer)
2. 然后逐渐降到目标 C
3. 让路由器先"看"一些数据, 再决定跳过哪些

代码示意:
```python
def get_capacity(step, warmup_steps=10000, target=0.5):
    if step < warmup_steps:
        # 线性下降
        return 1.0 - (1.0 - target) * (step / warmup_steps)
    return target

# 训练循环
for step, batch in enumerate(dataloader):
    cap = get_capacity(step)
    model.blocks[0].capacity = cap
    # ...
```

### 18.2 负载均衡 (Load Balance)

**问题**: 路由器可能总是选同一批 token (e.g. 训练后专挑"a, the, of" 等简单 token), 导致:
- 大部分 token 走 short path (浪费层)
- 少数 token 走 full path (但层也不够)
- 质量下降

**解法**:
- Capacity 强制保证 top-k
- 辅助 loss: 鼓励 router 分数均衡 (类似 MoE 的 aux loss)

```python
def router_balance_loss(router_logits, k):
    """
    路由器均衡损失: 让 router 输出分布合理

    router_logits: (B, n)
    k: top-k 大小
    """
    # Fraction of tokens that should be kept
    expected_keep = k / router_logits.shape[-1]

    # 实际选择的 token (top-k 视为 1, 其余 0)
    topk_idx = torch.topk(router_logits, k=k, dim=-1).indices
    mask = torch.zeros_like(router_logits)
    mask.scatter_(-1, topk_idx, 1.0)

    # 实际保留比例
    actual_keep = mask.mean()

    # 偏差
    imbalance = (actual_keep - expected_keep) ** 2

    return imbalance
```

### 18.3 Straight-Through Estimator

**问题**: top-k 是离散操作, 不可微。

**NVIDIA 论文用了**: Sigmoid + multiply, 让梯度流过路由器:
```python
# 路由得分
score = torch.sigmoid(router_logits)  # [0, 1]

# top-k 选定的 mask (硬决策)
topk_idx = torch.topk(router_logits, k=C).indices
mask = torch.zeros_like(router_logits)
mask.scatter_(-1, topk_idx, 1.0)

# 关键 trick: 让 mask 有梯度 (把 sigmoid score 作为梯度传递)
# 即 mask 乘以 sigmoid score 但 mask 仍控制 0/1
soft_mask = mask + (score - mask).detach()  # forward 用 mask, backward 走 score

# 用 soft_mask 加权
out = block(x) * soft_mask.unsqueeze(-1)
```

这是 Straight-Through Estimator (STE) 的标准应用。

## 20. MoD 与其他动态架构的关系

### 20.1 MoD vs MoE (核心对比)

| 维度 | MoE | MoD |
| :--- | :--- | :--- |
| **稀疏维度** | 宽度 (专家) | 深度 (层) |
| **路由对象** | token → 选哪些专家 | token → 选/不选该层 |
| **节省方式** | 每 token 只激活部分专家 | 每层只算部分 token |
| **路由开销** | 大 (路由矩阵 + 专家选) | 小 (top-k 简单 + identity) |
| **额外显存** | 高 (所有专家权重在显存) | 零 (跳过就是 identity) |
| **训练 trick** | 复杂 (LB loss) | 简单 (capacity 强制) |
| **推理加速** | 中 (路由开销 + 显存爆) | 高 (层跳过真省) |
| **适用场景** | 想要大总参数, 计算预算紧 | 想要小总参数, 推理加速 |
| **代表模型** | Mixtral, DeepSeek-V3 | NVIDIA MoD, 自家小模型 |
| **可叠加** | ✓ + MLA, + FP8 | ✓ + MoE (混合) |

### 20.2 MoD vs Early Exit

| 维度 | Early Exit | MoD |
| :--- | :--- | :--- |
| **退出方式** | 一旦够好, 整体退出 | 逐 token 退出 |
| **决策** | 整个序列一起 (per batch) | 逐 token 独立 |
| **节省** | 短问题加速大 | 每层都省 |

### 20.3 MoD vs Mamba (Linear Attention)

| 维度 | Mamba | MoD |
| :--- | :--- | :--- |
| **核心思想** | 用 SSM 取代 attention (序列方向) | 跳过 Transformer 层 (深度方向) |
| **复杂度** | $O(n)$ 序列 | $O(n)$ 也, 但算力按 token 减 |
| **记忆** | 固定大小 state | 完整 attention |
| **长上下文** | 优势明显 | 不变 |

### 20.4 MoD vs Branchy/Multi-Exit

Multi-exit 是另一种 early-exit 变体。区别:

- Multi-exit: 每个 block 后可 exit (整序列整体决定)
- MoD: 每层独立决定每个 token

MoD 更细粒度, 加速更显著。

## 21. MoD 的局限与改进方向

### 21.1 主要局限

**1. 兼容性差**
- MoD 需要定制训练 + 推理 pipeline
- 现有推理框架 (vLLM, TGI) 默认不支持
- 需要专门的 kernel (类似 FlashAttention 的 fused MoD kernel)

**2. 训练不稳定**
- 路由器在学, 但下游 LM 也在学
- 容易震荡 (有时所有 token 都进, 有时都不进)
- 需要仔细的容量 schedule

**3. 实际加速比理论低**
- 路由器开销 + 不规则 batch + scatter/gather 操作
- 实测加速 1.5-1.8x (理论 2x)

**4. 工程复杂**
- PyTorch 默认实现下, MoD 反而更慢 (因为 scatter/gather overhead)
- 必须用 DeepSpeed、FlashInfer 之类的定制实现

**5. 与 KV Cache 配合复杂**
- 跳过的 token 算 attention 时怎么办?
  - 选项 A: 不算 (但需不规则 attention mask)
  - 选项 B: 算, 但用 skip token 的 h_{l-1} 作为 input

**6. Multi-batch 复杂**
- 不同句子的 token 数不同, capacity fraction ≠ 实际 token 数
- 需要做 token padding 或类似 MoE 的 batch padding

### 21.2 改进方向

**1. 与 MoE 混合 (MoE + MoD)**
- 同时做动态宽度 + 动态深度
- 2024+ 的研究前沿

**2. 自适应 Capacity**
- 不用固定 C, 而是 learned per layer per batch
- 见 NVIDIA 论文的 "expert choice routing" 思想

**3. 与 FlashAttention 集成**
- 跳过 token 的 attention 跳过计算
- fused kernel

**4. 替代品: Mamba / Linear Attention**
- 完全换掉 attention, 直接 $O(n)$ 序列
- 与 MoD 思路不同但目标一致

## 23. MoD 的训练 Loss 完整推导

### 23.1 标准 LM Loss

$$
\mathcal{L}_{\text{LM}} = -\sum_i \log p_\theta(x_i | x_{<i})
$$

直接 forward 训练, 与 MoD 无差。

### 23.2 Router 单独的 Loss

**Option A**: 让路由器隐式通过 LM Loss 学习 (无辅助 loss)
- 论文中 capacity 强制 + LM loss 已经够

**Option B**: 加辅助 Load Balance Loss

$$
\mathcal{L}_{\text{balance}} = \alpha \cdot \sum_\ell \text{Var}(\text{fraction of kept tokens in layer } \ell)
$$

类似 MoE 的 LB loss, 但应用在"每层保留率" 上。

### 23.3 总 Loss

$$
\mathcal{L} = \mathcal{L}_{\text{LM}} + \beta \mathcal{L}_{\text{balance}}
$$

论文设置: $\beta \approx 0.01$ (轻量)。

## 24. 前沿拓展: 混合稀疏 (MoE + MoD)

### 24.1 思想

```text
          ┌─────┴─────┐
        MoD           MoE
   (跳过层)        (选专家)
          │           │
          └─────┬─────┘
                │
        同时动态深度 + 动态宽度
```

**Combined architecture**:

```python
class MoE_MoD_Block(nn.Module):
    """
    每个层: 同时决定 token 是否跳过, 跳过的 token 是否进入哪个专家
    """
    def __init__(self, d_model, n_experts=8, capacity=0.5):
        super().__init__()
        self.d_model = d_model
        self.capacity = capacity

        # MoD 路由器
        self.depth_router = MoDRouter(d_model)

        # MoE 路由器
        self.width_router = nn.Linear(d_model, n_experts)

        # 多个 FFN 专家 (替代标准 FFN)
        self.experts = nn.ModuleList([
            nn.Sequential(
                nn.Linear(d_model, 4 * d_model),
                nn.GELU(),
                nn.Linear(4 * d_model, d_model)
            ) for _ in range(n_experts)
        ])

    def forward(self, x):
        B, n, d = x.shape
        C = int(self.capacity * n)

        # 1. MoD: 选 top-C 个 token
        depth_logits = self.depth_router(x)
        topk_idx = torch.topk(depth_logits, k=C).indices
        x_kept = torch.gather(x, 1, topk_idx.unsqueeze(-1).expand(-1,-1,d))

        # 2. MoE: 给选中的 token 选 top-1 专家
        width_logits = self.width_router(x_kept)
        weights = F.softmax(width_logits, dim=-1)
        expert_id = width_logits.argmax(dim=-1)  # (B, C)

        # 3. 每个 token 走对应专家
        out_kept = torch.zeros_like(x_kept)
        for e_id, expert in enumerate(self.experts):
            mask = (expert_id == e_id)
            if mask.any():
                out_kept[mask] = expert(x_kept[mask])

        # 4. 散布
        y = x.clone()
        y.scatter_(1, topk_idx.unsqueeze(-1).expand(-1,-1,d), out_kept + x_kept)
        return y
```

**期望**: 进一步降低 FLOPs 同时保持高参数总量。

**挑战**: 双重路由不稳定性大幅增加。

## 25. 章末思考题 (面试向)

### 思考题 1: MoD 的"容量限制" 为什么必须有?

**参考答案**:
- 没有容量限制, 路由器倾向于全选 (因为可以减少 LM loss)
- 容量限制强制路由器"挑选"哪些值得算
- 同时保证每层算力固定 (即静态计算图)

### 思考题 2: 路由器训练不可微, 怎么破?

**参考答案**:
- Straight-Through Estimator (STE): top-k 决策 + sigmoid score 梯度
- 路由器输出乘到 block 输出 (类 MoE 的 gate)
- 辅助预测器 (训练一个独立网络预测路由器决策)

### 思考题 3: MoD 加速 1.5x, 量化加速 1.5x, 两者叠加会变成 >2x 吗?

**参考答案**:
- 是的! 它们在算力的不同维度上节省:
  - MoD 节省**算的 token 数** × 每 token 算的层数
  - 量化节省**每 token 算 FLOPs** (降低精度操作更快) + 减少**读取带宽**
- 二者正交, 叠加接近 1.5 × 1.5 = 2.25x 实测 (考虑访存瓶颈接近)
- 实战组合: MoD INT4 + Spec Decoding + Prefix Cache, 总加速 5-10x

### 思考题 4: 如果把 capacity 设为 0.1, 模型完全跳过 90% token, 会怎样?

**参考答案**:
- 极端情况, 但**会过拟合**到极少被处理的 token
- 论文中 capacity ≈ 0.5 是甜点
- 太低 → 重要 token 算力不够
- 太高 → 几乎没省算力

### 思考题 5: MoD 与 KV Cache 兼容性如何?

**参考答案**:
- 跳过的 token 不算 block attention → 需要在 attention 里排除 skip token
- 但 KV Cache 仍要存 (因为后续可能用到)
- "Forward-only 节省" + "KV 显存不省" → 推理 FLOPs 省但 KV 不省
- 实测: token 跳过率 50% → FLOPs 减半, 但 KV Cache 不减
- 在 decode 阶段, FLOPs 是 memory-bound 的, **真正加速看 KV + FLOPs 二者**

## 32. 完整生产级 MoD 推理内核 (代码)

```python
"""
生产级 MoD 推理引擎 (伪代码, 示意)
实际需要 CUDA / Triton kernel 才能跑赢原版 Transformer
"""

import torch
import torch.nn as nn

class MoDInferenceEngine:
    """MoD 推理专用引擎"""

    def __init__(self, model, tokenizer):
        self.model = model
        self.tokenizer = tokenizer
        self.kv_cache = None
        self.stats = {
            'kept_per_layer': [],
            'skipped_per_layer': [],
        }

    @torch.no_grad()
    def generate(self, prompt_ids, max_new=200):
        # Prefill (一次算全部 token, 不跳过)
        out = self.model(
            prompt_ids,
            past_key_values=None,
            use_cache=True,
            output_router_logits=True  # 让 router 顺手存
        )
        self.kv_cache = out.past_key_values
        router_stats = out.router_logits  # (B, n, n_layers) 各层路由分数

        generated = prompt_ids[0].tolist()

        # Decode 循环
        while len(generated) < len(prompt_ids[0]) + max_new:
            # 一次 forward: 当前 token + 之前 KV
            last_token = torch.tensor(`generated[-1]`], device=self.kv_cache[0][0].device)
            out = self.model(
                last_token,
                past_key_values=self.kv_cache,
                use_cache=True,
                output_router_logits=True
            )
            self.kv_cache = out.past_key_values
            logits = out.logits[0, -1]

            # Greedy 采样 (简化)
            next_token = logits.argmax().item()
            generated.append(next_token)

            if next_token == self.tokenizer.eos_token_id:
                break

        return generated

    def report(self):
        """报告每层实际处理率 (用于分析)"""
        for l, (kept, skipped) in enumerate(zip(
            self.stats['kept_per_layer'],
            self.stats['skipped_per_layer']
        )):
            total = kept + skipped
            rate = kept / max(1, total)
            print(f"Layer {l}: kept={kept}, skipped={skipped}, kept_rate={rate:.2%}")
```

## 33. 与 量化 / 推测解码的协同

### 33.1 MoD + 量化 (INT8)

```text
MoD 节省: 跳过的 token 不算 block (FLOPs ↓)
量化节省: 算的 token 也更快 (bandwidth ↓)

协同效果: 双重叠加, 总加速 ≈ 1.5 × 1.5 ≈ 2.25x 实测

实现: MoD 路由器判断后, 选中的 token 走 INT8 的块;
      未选中的 token 不走 block (无论量化与否)
```

### 33.2 MoD + 推测解码

```text
Spec Decoding 节省: K 个 token 一起验证 (权重读取摊薄)
MoD 节省: 跳过的 token 不算 FLOPs

协同效果: 加速叠加, 可达 2-4x

实现: Draft 模型也用 MoD, 验证模型也用 MoD;
      batch 调度需要小心 (维度增加)
```

### 33.3 MoD + Prefix Cache

```text
Prefix Cache 节省: 已计算的 KV 复用
MoD 节省: 跳过 token 的 block 算力

协同: 不冲突, 但有取舍:
  - Cache 命中时: 跳过的 token 节省更显著 (block 跳过, KV 也被复用)
  - Cache miss 时: 正常 MoD

实际: 大多场景下, cache 命中率高时 MoD 的边际收益减小
      (因为 KV 占大头, 算力占比小)
```

## 35. 高级: 路由器的可解释性

路由器的决策可以被" 提取" 出来作为可解释性分析:

```python
@torch.no_grad()
def extract_router_decisions(model, input_text):
    """提取路由决策, 用于分析"""
    tokenizer = ...
    ids = tokenizer(input_text, return_tensors='pt').input_ids.cuda()

    # 注册 hook 抓 router 输出
    router_decisions = []
    def hook(module, input, output):
        # router_logits: (B, n, 1)
        scores = torch.sigmoid(output.detach())
        # 假设 top-k 选择的决定已经做了
        # 这里简化为只记录 score
        router_decisions.append(scores.cpu())

    hooks = []
    for name, mod in model.named_modules():
        if 'router' in name:
            hooks.append(mod.register_forward_hook(hook))

    model(ids)

    for h in hooks:
        h.remove()

    # 分析
    for layer_id, scores in enumerate(router_decisions):
        # scores: (1, n, 1)  每个 token 的路由分数
        scores = scores.squeeze()
        tokens = tokenizer.convert_ids_to_tokens(ids[0])

        print(f"Layer {layer_id}:")
        for tok, score in zip(tokens, scores):
            print(f"  {tok}: {score.item():.3f} {'✗' if score < 0.5 else '✓'}")
```

```text
  a:    0.07 ✗
  galaxy: 0.94 ✓
```

## 37. 思考: MoD 的"哲学"

动态计算的核心哲学是:
> **"简单的输入不需要算那么多, 复杂的输入需要多算一点"**

这是 Transformer 以来最重要的架构反思之一。

```text
Transformer 假设: 所有 token 一视同仁 (固定 N 层)
MoE (2022):       同 token 在不同层走不同专家 (固定 N 层)
MoD (2024):       不同 token 走不同层数 (动态 N 层)
Linear Attention (Mamba): 不同 token 算 O(1) 状态 (替代 attention)
```

未来一定是**更多维度可调** 的混合架构。

## 39. 训练 MoD 模型的完整流程

### 39.1 完整 PyTorch 训练循环

下面是端到端的训练代码, 包含 capacity schedule, 路由器 STE, 平衡 loss:

```python
import torch
import torch.nn as nn
import torch.nn.functional as F
import torch.optim as optim
from torch.utils.data import DataLoader, Dataset
import math

class MoDConfig:
    def __init__(self):
        self.n_layers = 12
        self.d_model = 512
        self.n_heads = 8
        self.vocab_size = 32000
        self.capacity_target = 0.5
        self.capacity_warmup_steps = 5000
        self.router_balance_loss_coeff = 0.01
        self.learning_rate = 3e-4
        self.weight_decay = 0.1
        self.batch_size = 32
        self.max_seq_len = 1024


def get_capacity_at_step(step, config: MoDConfig):
    """线性的 capacity schedule"""
    if step < config.capacity_warmup_steps:
        # 从 1.0 线性下降到目标
        progress = step / config.capacity_warmup_steps
        return 1.0 - (1.0 - config.capacity_target) * progress
    return config.capacity_target


def mod_loss_with_balance(model_outputs, labels, capacity_actual,
                          config: MoDConfig):
    """
    MoD 训练 Loss = LM Loss + Balance Loss
    """
    # 1. 标准 LM Loss
    logits = model_outputs['logits']
    lm_loss = F.cross_entropy(
        logits.view(-1, logits.shape[-1]),
        labels.view(-1),
        ignore_index=-100
    )

    # 2. Router Balance Loss (辅助, 鼓励均衡)
    # capacity_actual: 各层实际保留率
    # 目标: capacity_target
    balance_loss = 0.0
    for l, actual in enumerate(capacity_actual):
        target = config.capacity_target
        # 偏差平方
        balance_loss += (actual - target) ** 2
    balance_loss = config.router_balance_loss_coeff * balance_loss / len(capacity_actual)

    return lm_loss + balance_loss


class Trainer:
    def __init__(self, model, config: MoDConfig, dataset):
        self.model = model
        self.config = config
        self.dataset = dataset

        self.optimizer = optim.AdamW(
            model.parameters(),
            lr=config.learning_rate,
            weight_decay=config.weight_decay,
            betas=(0.9, 0.95)
        )
        self.scheduler = optim.lr_scheduler.CosineAnnealingLR(
            self.optimizer, T_max=100000
        )
        self.step = 0

    def train_one_step(self, batch):
        self.step += 1
        capacity = get_capacity_at_step(self.step, self.config)

        # 更新所有 MoD 块的 capacity
        for block in self.model.blocks:
            block.capacity = capacity

        # Forward
        input_ids = batch['input_ids'].cuda()
        labels = batch['labels'].cuda()

        outputs = self.model(input_ids, output_router_stats=True)
        logits = outputs['logits']
        router_stats = outputs['router_stats']  # 各层实际保留率 (list of float)

        # Loss
        loss = mod_loss_with_balance({'logits': logits}, labels, router_stats, self.config)

        # Backward
        self.optimizer.zero_grad()
        loss.backward()
        torch.nn.utils.clip_grad_norm_(self.model.parameters(), 1.0)
        self.optimizer.step()
        self.scheduler.step()

        return {
            'loss': loss.item(),
            'lm_loss': outputs.get('lm_loss', loss.item()),
            'capacity': capacity,
            'lr': self.scheduler.get_last_lr()[0],
        }

    def train(self, n_steps=100000, log_every=100):
        loader = DataLoader(self.dataset, batch_size=self.config.batch_size,
                           shuffle=True, num_workers=4)
        iterator = iter(loader)

        for step in range(n_steps):
            try:
                batch = next(iterator)
            except StopIteration:
                iterator = iter(loader)
                batch = next(iterator)

            stats = self.train_one_step(batch)
            if step % log_every == 0:
                print(f"Step {step}: loss={stats['loss']:.4f}, "
                      f"capacity={stats['capacity']:.3f}, "
                      f"lr={stats['lr']:.2e}")
```

```python
    c = tl.program_id(1)

    idx = tl.load(kept_idx_ptr + b * C + c)
    x = tl.load(x_ptr + b * n * d + idx * d + tl.arange(0, d))

    # Attention (这里简化)
```

## 45. MoD 数学推导 (完整版)

### 45.1 等效深度期望

**定义**: 模型有 L 层, 容量 $c$。

**单个 token 走过 $l$ 层的概率**: 假设各层独立 (实际不独立, 简化):

$$
P(\text{token 经过 layer } l) = c^l + (1-c^l) P(\text{先选又被拒})
$$

近似 (简化): $P(\text{token 经过 layer } l) \approx c$ (各层同分布)。

**期望深度**:
$$
E[\text{depth}] = \sum_{l=1}^{L} P(\text{passes layer } l) \approx L \cdot c
$$

### 45.2 加速比推导

**FLOPs 对比**:

$$
\frac{\text{FLOPs}_{\text{MoD}}}{\text{FLOPs}_{\text{std}}} = \frac{L \cdot c \cdot \text{FLOPs}_{\text{block}}}{L \cdot \text{FLOPs}_{\text{block}}} = c
$$

**实测加速比** (考虑路由器开销、scatter/gather、内存访问限制):
$$
S = \frac{1}{c + c_{\text{router}} + \epsilon_{\text{overhead}}}
$$

其中 $c_{\text{router}}$ 是路由器开销比例 (~5%), $\epsilon_{\text{overhead}}$ ~ 5-10%。

**当 $c = 0.5$**:
$$
S \approx \frac{1}{0.5 + 0.05 + 0.07} \approx 1.61 \text{x}
$$

实测 1.5-1.8x, 一致。

### 45.3 单 token 输出延迟分析

**延迟 = Prefill + Decode × N**

```text
Standard:
  Prefill: t_p (一次算全部)
  Decode: N × t_d (每 1 token 1 次 forward)
  Total: t_p + N × t_d

MoD:
  Prefill: t_p + (N × c_r)  # 路由器算 N × L 次
  Decode: N × c × t_d  # 平均算 50% 层
  Total: t_p + N × (c_r + c × t_d)
```

**加速比** (decode 主导时):
$$
S = \frac{N \times t_d}{N \times (c_r + c \times t_d)} = \frac{t_d}{c_r + c \times t_d}
$$

当 $c_r \ll c \times t_d$:
$$
S \to \frac{1}{c} = \frac{1}{0.5} = 2 \text{x}
$$

## 48. MoD 中的边际效益分析

**关键问题**: 多一层 (或 capacity 加 0.1) 能带来多少质量提升?

```text
假设: L=32, c=0.5, 模型总参数量 7B

边际 quality: dQ/dl ≈ ?
边际 cost:    dC/dc ≈ L × t_d ≈ constant (per token)

Sweet spot:
  - c 太低 (e.g. 0.1) → 质量崩
  - c 太高 (e.g. 0.9) → 几乎没省
  - c = 0.4-0.6 → 最佳 trade-off
```

**理论分析**: 在 isoFLOPs (固定总 FLOP) 下, c 应该选**与训练量匹配**的:
- 训练少 → c 高 (每个 token 都重要)
- 训练多 → c 可以低 (冗余度)

NVIDIA 实验: 训练越久, MoD 的 c 可以越低 (且质量反而更好)。

## 49. 互动 Q&A

### Q: MoD 可以叠加 MoE 吗?

A: 可以 (见前文 §24)。但**双重路由不稳定**, 训练困难。**未广泛验证**。

### Q: MoD 训练时 train loss 不降?

A: 常见原因:
- Capacity schedule 太激进 (从 1.0 一步降到 0.1)
- 路由器初始化方差太大
- Balance loss 太大

解: 调整 capacity schedule, 调小 balance loss。

### Q: MoD 模型已经训好, 能不能量化?

A: 可以。MoD 模型架构与标准 Transformer 兼容, GPTQ / AWQ 都可以直接量化选中的 token。

### Q: MoD 在 batch 大时加速明显吗?

A: **奇怪地, batch 大时 MoD 加速下降**:
- 因为 batch 大时, scatter/gather 总开销相对小
- **但 router 决策依赖于 batch 内的 token 分布**, 大 batch 更稳定
- 实测: batch=32 加速比 1.5x, batch=4 加速比 1.8x

### Q: MoD 是 parameter-efficient 吗?

A: **是**。MoD 模型总参数与标准 Transformer 相同, 但相同算力下表现更好 (或相同表现下算力更少)。

## 50. 易错点 / 面试坑

```text
坑 1: 误以为 MoD 不需要改原有模型
   答: 不对, MoD 需要**训练时**改造 (加 router 训练)
       推理时改的"压缩" 路径不算 MoD, 算 early exit / 剪枝

坑 2: MoD 等同于"early exit"
   答: 不对。Early exit 是**整序列**提前出; MoD 是**逐 token** 决定。

坑 3: MoD 的加速比是固定的 (1.5x)
   答: 不对。加速比取决于 capacity:
       c=0.5 → 2x 理论, 1.5-1.8x 实测
       c=0.2 → 5x 理论, 3x 实测

坑 4: MoD 模型在 KV 内存上省
   答: 不对。跳过的 token 仍要存 KV, 主要省的是**计算量** (不是显存)。

坑 5: 路由器随机即可
   答: 不对。路由器需要 warmup + 容量 schedule, 否则训练失败。

坑 6: MoD 是 MoE 的简单变种
   答: 不对。MoD 跳过层, MoE 选专家。维度不同。

坑 7: MoD 越大越好
   答: 不对。MoD 在中小模型 (1-3B) 上效果最好, 大模型反而难训。

坑 8: MoD 总是节省 50% 算力
   答: 不对。Router 开销 + scatter + batch 影响, 实际省 25-40%
```

**7. 实践建议**

结合 "Mixture of Depths (MoD) 动态深度分配" 的特点,实践中有以下建议:

1. **数据优先**: 数据质量决定上限,模型只是逼近这个上限。把 50% 的时间投入到数据理解和清洗上,这条经验被无数实践证明。数据问题往往比模型问题更关键,但也更容易被忽视。

2. **基线先行**: 先用最简单的方法(如逻辑回归、规则)做基线,确认增益是来自方法还是数据。没有强基线的"创新"往往不靠谱。很多看似 fancy 的方法,在强基线面前提升有限。

3. **迭代式改进**: 不要追求一步到位,而是 baseline → 简单改进 → 高级方法 → 调优。每一步都用验证集确认有提升。每一步的提升幅度通常递减,要预期边际收益下降。

4. **失败案例分析**: 重点看模型做错的样本,往往能发现系统性问题。错误样本里藏着模型没学会的知识。把这些样本按错误类型分类,可以发现模型的薄弱点。

5. **A/B 测试**: 在生产环境做对照实验,用业务指标而非离线指标评估。离线指标只是手段,业务指标才是目的。指标可以被优化,但业务目标很难直接优化。

6. **监控与回滚**: 上线后持续监控关键指标,异常时快速回滚。任何线上系统都必须考虑"最坏情况",并预先设计好应对方案。

**8. 常见误解**

对 "Mixture of Depths (MoD) 动态深度分配" 常见的误解包括:

**7. 实践建议**

结合 "Mixture of Depths (MoD) 动态深度分配" 的特点,实践中有以下建议:

1. **数据优先**: 数据质量决定上限,模型只是逼近这个上限。把 50% 的时间投入到数据理解和清洗上,这条经验被无数实践证明。数据问题往往比模型问题更关键,但也更容易被忽视。

2. **基线先行**: 先用最简单的方法(如逻辑回归、规则)做基线,确认增益是来自方法还是数据。没有强基线的"创新"往往不靠谱。很多看似 fancy 的方法,在强基线面前提升有限。

3. **迭代式改进**: 不要追求一步到位,而是 baseline → 简单改进 → 高级方法 → 调优。每一步都用验证集确认有提升。每一步的提升幅度通常递减,要预期边际收益下降。

4. **失败案例分析**: 重点看模型做错的样本,往往能发现系统性问题。错误样本里藏着模型没学会的知识。把这些样本按错误类型分类,可以发现模型的薄弱点。

5. **A/B 测试**: 在生产环境做对照实验,用业务指标而非离线指标评估。离线指标只是手段,业务指标才是目的。指标可以被优化,但业务目标很难直接优化。

6. **监控与回滚**: 上线后持续监控关键指标,异常时快速回滚。任何线上系统都必须考虑"最坏情况",并预先设计好应对方案。

**8. 常见误解**

对 "Mixture of Depths (MoD) 动态深度分配" 常见的误解包括:

1. **"模型越复杂越好"**: 实际上,简单模型 + 好数据往往优于复杂模型 + 烂数据。这条法则在实践中反复被验证。

2. **"训练 loss 越低越好"**: 训练 loss 低不代表泛化好,可能过拟合。要看验证集表现,做误差分析。

3. **"指标好就等于业务好"**: 离线指标与在线业务有 gap,必须做 A/B 测试。指标可以被优化,但业务目标很难直接优化。

4. **"新方法一定比旧方法好"**: 新方法通常针对特定场景,在你的场景未必更好。要谨慎评估,先复现,再改进。

5. **"开源即用"**: 开源代码与你的数据/工程栈往往有 gap,需要适配。盲目复用经常踩坑,要理解代码再做改动。
