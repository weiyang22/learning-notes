# 7.2 分布式训练 (DDP / FSDP / DeepSpeed)

---

## 1. 内容介绍

**分布式训练**用多卡/多机训练大模型, 解决单卡显存不够、速度慢的问题. 3 大策略:
- **DDP** (Data Parallel, 2017): 数据并行
- **FSDP** (Fully Sharded Data Parallel, 2022): 全分片
- **DeepSpeed ZeRO** (Zero Redundancy Optimizer): 优化器状态分片

---

## 2. 为什么这么做

**问题 (单卡训练 7B 模型)**:
- 模型: 7B × 2 bytes (FP16) = 14 GB
- 优化器状态 (AdamW): 7B × 8 bytes (FP32 master + 2 momentum) = 56 GB
- 梯度: 7B × 2 bytes = 14 GB
- 激活: 几 GB
- **总计 90+ GB**, 单卡 (A100 80GB) 勉强

**解决思路**:
- 多卡: 用 8 张 A100 = 640 GB
- 但数据并行 (DP) 复制完整模型到每卡, 显存没省
- 模型并行: 切分模型, 通信复杂
- **优化器状态分片 (ZeRO)**: 每卡只存一部分优化器状态, 显存省 4-8 倍

---

## 3. 这么做的原因 (3 大方案对比)

| 方案 | 模型存储 | 优化器状态 | 梯度 | 通信 |
|---|---|---|---|---|
| DP (DataParallel) | 复制到每卡 | 复制 | 复制 | 同步梯度 |
| **DDP** (DistributedDataParallel) | 复制 | 复制 | 复制 | Ring AllReduce |
| **ZeRO-1** | 复制 | 分片 | 复制 | 减少优化器同步 |
| **ZeRO-2** | 复制 | 分片 | 分片 | 减少梯度同步 |
| **ZeRO-3** (FSDP) | 分片 | 分片 | 分片 | 最小显存 |
| **TP** (张量并行) | 切分 | 复制 | 复制 | 切分矩阵乘 |
| **PP** (流水线并行) | 切分 | 复制 | 复制 | 切分阶段 |

**为什么 LLM 训练几乎都用 ZeRO-3 / FSDP?**
- 模型很大 (7B+), 单纯数据并行显存不够
- ZeRO-3 把模型 + 优化器 + 梯度都分片, 显存省 8 倍
- 配合 TP / PP 可以训 100B+ 模型

---

## 4. 解决了什么问题

- **显存**: 单卡 90GB → 多卡 12GB / 卡 (8 卡 ZeRO-3)
- **速度**: 线性扩展 (理想情况下)
- **大模型**: 100B+ 模型成为可训练

---

## 5. 意义

- 2023+ 大模型训练的标配
- DeepSpeed / FSDP / Megatron 是三大主流框架

---

## 6. 公式表达

```text
DDP 训练:
  for batch in dataloader:
    loss = model(batch)  # 每卡独立算
    loss.backward()        # 每卡独立算梯度
    all_reduce(gradients)  # 同步所有卡的梯度
    optimizer.step()       # 每卡独立更新 (因为梯度已同步)

ZeRO-1 (优化器状态分片):
  8 卡, 每卡存 1/8 优化器状态
  通信: all_gather 完整状态 (用时), 切片存储

ZeRO-3 (全分片, = FSDP):
  模型参数 + 优化器 + 梯度都分片
  前向时 all_gather 需要的参数
  反向时同样
  显存: 1/8 (8 卡时)
```

## 9. 答案

### 答案 1: 3 大方案区别

```text
DDP (Data Parallel, 简单):
  - 每张卡存完整模型 + 优化器 + 梯度
  - 前向/反向各卡独立
  - 反向后 AllReduce 同步梯度
  - 显存: 单卡 × N
  - 通信: 2 × model_size
  - 适合: 单机能装下的模型 (< 1.5B)

ZeRO-1 (优化器状态分片):
  - 每张卡存 1/N 优化器状态
  - 模型 + 梯度仍复制
  - 通信: 多一些 (gather 优化器状态)
  - 显存: 单卡 × (1 + 2/N) ≈ 单卡
  - 适合: 中等模型 (1.5B - 7B)

ZeRO-3 (FSDP, 全分片):
  - 模型 + 优化器 + 梯度都分片
  - 前向时 all_gather 模型参数
  - 反向时 all_gather 模型参数
  - 显存: 单卡 × (1/N + 1/N + 1/N) ≈ 单卡 / N
  - 通信: 3 × model_size (更多)
  - 适合: 大模型 (7B - 100B+)
```

### 答案 2: 通信开销

```python
def estimate_communication(n_gpus, model_size_gb, strategy="ddp"):
    if strategy == "ddp":
        # AllReduce: 2 × model_size (前向 + 反向)
        comm = 2 * model_size_gb
    elif strategy == "zero3":
        # AllGather: 3 × model_size (前向/反向/优化器)
        comm = 3 * model_size_gb
    elif strategy == "tp":
        # 张量并行: 通信量取决于切分方式
        comm = 2 * model_size_gb / n_gpus  # 近似
    return comm

# LLaMA-7B (7 GB)
n_gpus = 8
size = 7
print(f"DDP: {estimate_communication(n_gpus, size, 'ddp'):.1f} GB")
print(f"ZeRO-3: {estimate_communication(n_gpus, size, 'zero3'):.1f} GB")
```

### 答案 3: Ring AllReduce

```text
8 个 GPU 排成环
Step 1: 每个 GPU 把 chunk 发给下一个 GPU, 接收上一个 GPU 的 chunk
       (8 步后, 每个 GPU 都有 1/8 数据)
Step 2: 同样的方式, 但每个 GPU 把自己独有的部分传出去
       (8 步后, 每个 GPU 都有完整数据)

总: 16 步, 但每步只传 1/8 数据
相比 naive all-reduce: 通信量减为 1/8
```

**复杂度**: $O(N)$ 步, 每步传 $1/N$ 数据 → 总 $O(1)$ 步 vs 1 步 (但数据量相同).

## 深入: 四种并行的正交组合(3D/4D 并行)

大模型训练不是选一种并行,而是**多种正交叠加**:

| 并行 | 切什么 | 通信 | 适合 |
| :--- | :--- | :--- | :--- |
| **数据并行(DP)** | 切 batch,复制模型 | 梯度 AllReduce | 模型能装下单卡 |
| **张量并行(TP)** | 切单层矩阵(行/列) | 每层 All-Reduce(高频) | 单层太大,机内 NVLink |
| **流水线并行(PP)** | 切层(不同卡不同层) | 层间点对点 | 层数多,跨机 |
| **专家并行(EP)** | 切 MoE 专家 | all-to-all | MoE 模型 |
| **序列/上下文并行** | 切序列长度 | 见 Ring Attention | 超长上下文 |

> 典型配置(千卡训 100B+):TP=8(机内)× PP=数机 × DP=剩余,再叠 ZeRO 分片优化器。这就是 "3D 并行"。**TP 通信最密集必须放机内(NVLink),DP/PP 可跨机**。

---

## 深入: ZeRO 三个 stage 的取舍

ZeRO 沿"参数/梯度/优化器状态"三样逐步分片(见 [工程能力第03章 16N](../../../基础/工程基础/工程能力/第03章-参数量与显存预估.md)):

```text
ZeRO-1: 只分片优化器状态(12N→12N/K)  通信≈DP  省显存中
ZeRO-2: +分片梯度(2N→2N/K)          通信≈DP  省显存多
ZeRO-3: +分片参数(2N→2N/K)          通信×1.5 省显存最多(≈单卡/K)
```

**权衡**:stage 越高越省显存,但 ZeRO-3 前向/反向都要 all-gather 参数 → 通信增加。带宽好(NVLink/IB)选 ZeRO-3,带宽差则 ZeRO-2 + 梯度累积。FSDP 是 PyTorch 原生的 ZeRO-3。

---

## 深入: 通信-计算重叠是性能关键

分布式训练的隐藏杀手是**通信暴露**(GPU 等通信)。优化都围绕"让通信藏在计算背后":
- **梯度分桶(bucketing)**:反向边算边发,不等全部梯度(DDP 默认)。
- **计算通信重叠**:ZeRO-3 预取下一层参数,当前层计算时后台 all-gather。
- **梯度累积**:多个 micro-batch 累积再同步,摊薄 AllReduce 频率。
- 详见 [工程能力第07章 性能剖析](../../../基础/工程基础/工程能力/第07章-性能剖析与优化.md)。

---

## 深入: Ring AllReduce 为什么带宽最优

Naive AllReduce(所有卡发给一个主卡)让主卡带宽成瓶颈。**Ring AllReduce** 把梯度切成 $N$ 块,环形传递:reduce-scatter($N-1$ 步)+ all-gather($N-1$ 步),每步每卡只收发 $1/N$ 数据。**总通信量与卡数无关**(每卡收发约 $2\times$ 模型大小),这是它成为标准的原因(NCCL 实现)。

## A.1 ZeRO-1 / ZeRO-2 / ZeRO-3 全方位详解

### A.1.1 三阶段划分的本质: 把哪些张量分片

ZeRO (Zero Redundancy Optimizer, Microsoft 2019) 的核心洞察是: **数据并行时, 每张卡都冗余地存了同一份模型 + 优化器 + 梯度**, 而这些东西可以按 rank 切成 $K$ 份 (假设 $K$ 张卡), 每卡只存自己那一片, 用到时再临时 all-gather.

模型训练一个 step 涉及 3 类张量:

| 张量类型 | 形状 | 单卡大小 (FP32, $\Psi$=参数量) |
| :--- | :--- | :--- |
| 参数 $P$ | $\Psi$ | $4\Psi$ bytes (FP32 master weights) |
| 梯度 $G$ | $\Psi$ | $4\Psi$ bytes (FP32 master grads) 或 $2\Psi$ (FP16 grads) |
| 优化器状态 $O$ (AdamW) | $2\Psi$ (一阶矩 $m$ + 二阶矩 $v$) | $8\Psi$ bytes (FP32) |
| **总计** | — | $\mathbf{16\Psi}$ bytes |

按 stage 划分:

```text
ZeRO-1: P 复制, G 复制, O 分片 → 每卡显存 = 4Ψ + 4Ψ + 8Ψ/K = 8Ψ + 8Ψ/K
ZeRO-2: P 复制, G 分片, O 分片 → 每卡显存 = 4Ψ + 4Ψ/K + 8Ψ/K = 4Ψ + 12Ψ/K
ZeRO-3: P 分片, G 分片, O 分片 → 每卡显存 = 4Ψ/K + 4Ψ/K + 8Ψ/K = 16Ψ/K
```

> 关键: ZeRO-1 省 $\frac{K-1}{K}\times 8\Psi$, ZeRO-3 比 DP 省 $\frac{K-1}{K}\times 16\Psi$. **理论上 ZeRO-3 显存降为 DP 的 $1/K$**.

### A.1.2 ZeRO-1: 优化器状态分片

**动机**: AdamW 的 $m, v$ 占 $8\Psi$ bytes, 是大头, 但更新参数时 $m_i, v_i$ 只需要用一次. 完全可以分片:

```python
# 伪代码 (DeepSpeed 实现)
class ZeRO1Optimizer:
    def __init__(self, params, lr, world_size, rank):
        self.params = params                      # 每卡都有完整参数
        self.lr = lr
        self.rank = rank
        self.world_size = world_size

        # 把参数切成 K 片, 第 rank 片存在本卡
        shard_id = rank
        self.optimizer_states = {}                # 只存本卡那一片的 m, v

        for p in self.params:
            if p.shard_id == rank:
                self.optimizer_states[p] = (torch.zeros_like(p), torch.zeros_like(p))

    def step(self):
        # Step 1: 本卡上, 用本卡的 m, v 更新本片参数
        for p in self.params:
            if p.shard_id == self.rank:
                m, v = self.optimizer_states[p]
                # AdamW update
                p.data -= self.lr * m / (v.sqrt() + eps)

        # Step 2: 把更新后的完整参数广播给所有卡
        # (这一步可以用 all_gather 一次完成)
        for p in self.params:
            dist.broadcast(p.data, src=p.shard_id)
```

**显存定量 (LLaMA-7B, K=8, FP32)**:
- DP: $16 \times 7 = 112$ GB
- ZeRO-1: $8 \times 7 + 8 \times 7 / 8 = 56 + 7 = 63$ GB (省 ~44%)
- 单卡 A100 80GB 还能装下

**通信**: 与 DP 几乎一样 (多了 all_gather 更新后的参数), 实际通信量增加 < 5%.

**使用场景**: 1.5B-7B 模型, 显存瓶颈在优化器状态, 但模型 + 梯度能装下.

### A.1.3 ZeRO-2: + 梯度分片

**动机**: 反向计算完梯度后, 立刻 reduce-scatter 到对应 rank, 不需要每卡都存完整梯度. 等 step 时再 all-gather 需要的部分.

```python
class ZeRO2Optimizer:
    def __init__(self, params, lr, world_size, rank):
        self.params = params
        self.lr = lr
        self.rank = rank
        self.world_size = world_size

        # 初始化优化器状态 (分片)
        self.optimizer_states = {}
        for p in self.params:
            if p.shard_id == rank:
                self.optimizer_states[p] = (torch.zeros_like(p), torch.zeros_like(p))

    def backward_hook(self, p, grad):
        """反向传播时, 梯度按 rank 分片"""
        # reduce-scatter: 把 p.grad 切片发给对应的 rank
        # rank-r 只收到 p.grad 的第 r 片
        # 其他 rank 不存这份梯度
        shard = grad.chunk(self.world_size, dim=0)[self.rank]
        dist.reduce_scatter(shard, grad, op=dist.ReduceOp.SUM)
        # 本卡的 p.grad 只保留 1/K, 其他部分不发回来
        p.grad = shard

    def step(self):
        # Step 1: all_gather 优化器状态需要的部分 (按需)
        for p in self.params:
            if p.shard_id != self.rank:
                # 从对应 rank 拿到本片参数对应的优化器状态
                shard_m, shard_v = self._fetch_optimizer_state(p)
                # 计算这一片参数的更新
                p.shard_data -= self.lr * shard_m / (shard_v.sqrt() + eps)
            else:
                m, v = self.optimizer_states[p]
                p.shard_data -= self.lr * m / (v.sqrt() + eps)

        # Step 2: all_gather 更新后的参数, 让所有卡都有完整参数
        for p in self.params:
            dist.all_gather(p.data, p.shard_data)
```

**显存定量 (LLaMA-7B, K=8, FP32)**:
- DP: $16 \times 7 = 112$ GB
- ZeRO-1: $63$ GB
- ZeRO-2: $4 \times 7 + 12 \times 7/8 = 28 + 10.5 = 38.5$ GB (省 ~66%)
- A100 80GB 甚至能跑 LLaMA-13B

**通信**: 与 DP 几乎一样 (多了 reduce-scatter 替代 all-reduce), 略增.

**使用场景**: 7B-13B 模型, 显存瓶颈开始出现, 但还在可承受范围.

### A.1.4 ZeRO-3: + 参数分片 (等价于 FSDP)

**动机**: 模型参数本身也可以分片. 前向/反向时按需 all_gather, 用完即弃.

**这是 PyTorch FSDP 的等价实现**:

```python
import torch
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

# 启动 FSDP 训练
model = TransformerLM(vocab_size=50000, n_layers=32, d_model=4096)
model = FSDP(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,  # = ZeRO-3
    mixed_precision=MixedPrecision(
        param_dtype=torch.float16,
        reduce_dtype=torch.float16,
        buffer_dtype=torch.float16,
    ),
    backward_prefetch=BackwardPrefetch.BACKWARD_PRE,
    forward_prefetch=True,
)

# 训练循环
for batch in dataloader:
    loss = model(batch)
    loss.backward()
    optimizer.step()
```

**前向传播时 FSDP 的细节**:

```python
def fsdp_forward(self, x):
    # Step 1: all_gather 本层需要的参数
    # 每层参数都分片, 用到时 gather, 用完即弃
    self._all_gather_params()

    # Step 2: 正常前向计算
    out = self._compute(x)

    # Step 3: 释放临时 gather 出的完整参数 (节省显存)
    self._free_temp_params()

    return out
```

**显存定量 (LLaMA-7B, K=8, FP32)**:
- DP: $112$ GB
- ZeRO-1: $63$ GB
- ZeRO-2: $38.5$ GB
- ZeRO-3 = FSDP: $16 \times 7/8 = 14$ GB (省 ~87.5%)
- 一张 A100 40GB 就能跑 LLaMA-7B

**通信增加**: ZeRO-3 前向 + 反向各一次 all_gather (模型参数), 加上梯度 reduce-scatter. 相比 DDP 通信量增 ~50% (但被 NVLink/IB 摊薄).

**使用场景**: 7B-100B+ 模型, 单卡装不下, 必须分片.

### A.1.5 三大 stage 的对比汇总

| 指标 | DP | ZeRO-1 | ZeRO-2 | ZeRO-3 (FSDP) |
| :--- | :--- | :--- | :--- | :--- |
| **单卡显存** | $16\Psi$ | $8\Psi + \frac{8\Psi}{K}$ | $4\Psi + \frac{12\Psi}{K}$ | $\frac{16\Psi}{K}$ |
| **LLaMA-7B 单卡显存 (K=8)** | 112 GB | 63 GB | 38.5 GB | 14 GB |
| **通信开销** | $2\Psi$ (AllReduce) | $2\Psi$ (略增) | $2\Psi$ (略增) | $3\Psi$ (前/反 AllGather + 梯度 reduce-scatter) |
| **支持最大模型** | ~1.5B (A100) | ~7B | ~13B | 100B+ |
| **NCCL 通信原语** | AllReduce | AllReduce + AllGather | ReduceScatter + AllGather | AllGather + ReduceScatter (双倍) |

**重要公式**: ZeRO-3 显存降为 $1/K$, 通信增为 $1.5\times$, 通信-计算比上升. 但实际训练大模型时, **算力是瓶颈, 不是通信** (H100 NVLink 900 GB/s 远快于单卡算力), 所以 ZeRO-3 仍是首选.

### A.1.6 ZeRO-Infinity: 进一步扩展到 NVMe

ZeRO-Infinity (DeepSpeed 2021) 把分片扩展到 CPU 内存 + NVMe SSD:
- 模型分片可以卸载到 CPU RAM (几百 GB)
- 优化器状态可以卸载到 NVMe (几 TB)
- 通信: GPU ↔ CPU ↔ NVMe (带宽下降, 但容量暴涨)

**单卡可训练 32T 参数模型** (理论). 实际用于 GPT-NeoX 等超大模型预训练.

### A.1.7 显存 vs 带宽的权衡曲线

理论模型: **训练效率 = $\frac{\text{计算量}}{\text{计算时间 + 通信时间}}$**.

GPU FLOPS $F$, GPU 显存带宽 $B$, 节点间互联 $I$, 节点数 $K$:

```text
计算时间: T_compute = 6Ψ / F              (每个参数 6 FLOPs: 前向 2Ψ + 反向 4Ψ)
通信时间 (DDP): T_comm_ddp = 2Ψ / (K·I)    (AllReduce 后, 摊到每卡)
通信时间 (ZeRO-3): T_comm_z3 = 3Ψ / I      (AllGather + reduce-scatter)
```

> $K$ 越大, DDP 通信摊得越薄; ZeRO-3 通信摊不开. 所以 **当 $K$ 极大 (≥64) 时, DDP 反而比 ZeRO-3 通信高效**, 但显存吃不下. 实际工程用 ZeRO-3 + Gradient Checkpointing + Activation Offload 三件套.

## A.2 FSDP vs DDP 深度对比

### A.2.1 核心区别一句话

> **DDP**: 每张卡存完整模型, 切 batch.
> **FSDP**: 每张卡存模型切片, 用到时临时 gather.

### A.2.2 DDP 详细工作流

```python
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

# 初始化进程组
dist.init_process_group(backend="nccl")
rank = dist.get_rank()
world_size = dist.get_world_size()

# 每张卡加载完整模型
model = TransformerLM(...).to(rank)

# DDP 包装
model = DDP(model, device_ids=[rank])

# 数据并行: 每个 rank 拿到不同 batch
sampler = torch.utils.data.distributed.DistributedSampler(dataset)
loader = DataLoader(dataset, sampler=sampler, batch_size=batch_size_per_rank)

# 训练循环
for batch in loader:
    loss = model(batch.to(rank))             # 每卡独立前向
    loss.backward()                            # 每卡独立反向, 梯度留在本地

    # DDP 内部: 反向时自动 bucket 梯度 + AllReduce
    # 这一步对用户透明, 触发在 loss.backward() 里

    optimizer.step()                           # 梯度已同步, 每卡独立更新
```

**DDP 的关键优化: 梯度分桶 (Bucketing)**

```python
# PyTorch DDP 源码中, 默认 bucket_size = 25MB
# 反向时, 梯度按反方向累积到桶里, 桶满了就立刻 AllReduce
# 不等所有梯度都算完才开始同步
# 这样能把通信藏在反向计算背后
```

**DDP 通信分析**:
- AllReduce 通信量 = $2\Psi$ (前后向各一次梯度累加)
- 实际耗时 = $2\Psi / (\text{Interconnect Bandwidth})$
- NVLink 内部: ~900 GB/s, 8 卡 DDP 通信几乎可忽略
- IB 跨机: ~200 GB/s, 8 机 DDP 通信为 NVLink 的 1/4, 还能接受

**DDP 适用边界**:
- 模型 ≤ 1.5B (FP32 master weights) → 单卡 24GB 显存够用
- 模型 ≤ 3B (BF16) → 单卡 24GB 显存够用 (A100 40GB 也行)
- 节点数 ≤ 256 → 通信开销可控

### A.2.3 FSDP 详细工作流

```python
import torch
from torch.distributed.fsdp import (
    FullyShardedDataParallel as FSDP,
    MixedPrecision,
    BackwardPrefetch,
    ShardingStrategy,
)
from torch.distributed.fsdp.wrap import transformer_auto_wrap_policy

# 自动 wrap 每个 Transformer block 为 FSDP 子模块
# 这是关键: FSDP 按模块分片, 不是按参数分片
auto_wrap_policy = transformer_auto_wrap_policy(
    transformer_layer_cls={TransformerBlock},
)

model = TransformerLM(...)
model = FSDP(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,  # = ZeRO-3
    auto_wrap_policy=auto_wrap_policy,              # 关键: 按 block 分片
    mixed_precision=MixedPrecision(
        param_dtype=torch.bfloat16,
        reduce_dtype=torch.bfloat16,
        buffer_dtype=torch.bfloat16,
    ),
    backward_prefetch=BackwardPrefetch.BACKWARD_PRE,  # 预取下一层
    forward_prefetch=True,
    cpu_offload=None,  # 可选: CPU offload
    device_id=torch.cuda.current_device(),
)

# 训练循环: 与 DDP 完全一样!
for batch in loader:
    loss = model(batch)
    loss.backward()
    optimizer.step()
```

**FSDP 的关键参数: auto_wrap_policy**

> FSDP 默认会把整个 model 作为一个 FSDP unit, 但这样所有参数一次性 all_gather, 显存峰值很高. 最佳实践是**按 TransformerBlock 分片**, 这样只 gather 当前计算需要的 block, 显存峰值降为模型大小的 $1/N_{\text{block}}$.

```python
# 错误: 整个 model 作为 1 个 FSDP unit
model = FSDP(model, ...)  # 不好: gather 整个 7B 模型

# 正确: 每个 TransformerBlock 作为 1 个 FSDP unit
from torch.distributed.fsdp.wrap import transformer_auto_wrap_policy
auto_wrap_policy = transformer_auto_wrap_policy(
    transformer_layer_cls={TransformerBlock},  # 自动识别 Block
)
model = FSDP(model, auto_wrap_policy=auto_wrap_policy, ...)  # 好
```

### A.2.4 DDP vs FSDP 对比表

| 维度 | DDP | FSDP |
| :--- | :--- | :--- |
| **单卡显存 (LLaMA-7B)** | 112 GB (装不下) | 14 GB (轻松装) |
| **最大模型 (A100 80GB, K=8)** | ~3B | 70B+ |
| **通信开销** | $2\Psi$ (AllReduce) | $3\Psi$ (AllGather + RS, ~1.5x) |
| **延迟 (LLaMA-7B 单 step)** | 基准 1.0x | ~1.3-1.5x |
| **实现复杂度** | 简单 (1 行包装) | 中等 (auto_wrap_policy 等) |
| **checkpoint 兼容** | 原生 DDP state_dict | 需要 _fsdp_wrap, 重组较复杂 |
| **检查点加载** | 直接加载 | 需要 ShardingStateDictConfig |
| **activation checkpointing** | 自己加 | 与 FSDP 协同更好 (FSDP 可以 unshard 后再 checkpoint) |

### A.2.7 常见 FSDP 调参技巧


## A.3 Megatron-LM 3D Parallel 详解

### A.3.1 为什么需要 3D 并行

单一并行策略的天花板:

| 策略 | 切分对象 | 通信密度 | 单机上限 | 多机上限 |
| :--- | :--- | :--- | :--- | :--- |
| DP | batch | 低 (AllReduce 一次) | 单卡能装模型 | 8-16 机 (通信成瓶颈) |
| TP | 单层矩阵 | 高 (每层 AllReduce) | NVLink (8 卡) | 不能跨机 (带宽不够) |
| PP | 层 | 中 (点对点) | 无限制 | 多机 (但空泡率高) |
| ZeRO-3 | 参数/梯度/优化器 | 中 (AllGather) | 多机多卡 | 128+ 机 (NVMe 卸载可达千卡) |

**3D 并行 = DP + TP + PP**, 把三种切分正交叠加, 训千亿参数模型 (GPT-3 175B, BLOOM 176B).

> Megatron-LM (NVIDIA 2019) 是 3D 并行的标杆实现, 后被 Megatron-DeepSpeed (DeepSpeed 2021) 和 Megatron-Core (NVIDIA 2023) 持续优化.

### A.3.2 张量并行 (TP) 详解

**核心: 把单个矩阵乘切到多卡上并行算.**

考虑 Transformer 中的 FFN:
$$
\text{FFN}(x) = \text{GeLU}(x W_1) W_2
$$
其中 $W_1 \in \mathbb{R}^{d \times d_{ff}}$, $W_2 \in \mathbb{R}^{d_{ff} \times d}$, $d_{ff} = 4d$.

**列切分 (Column Parallel)**:
$$
\text{FFN}(x) = [\text{GeLU}(x W_{1}^{(1)}) \| \text{GeLU}(x W_{1}^{(2)})] [W_2^{(1)}; W_2^{(2)}]
$$

具体:
- 把 $W_1$ 按列切成 $K$ 份: $W_1 = [W_1^{(1)}, W_1^{(2)}, \ldots, W_1^{(K)}]$, 每张卡持有 $W_1^{(k)}$
- 输入 $x$ 每卡都复制一份, 各自算 $\text{GeLU}(x W_1^{(k)}) \in \mathbb{R}^{d_{ff}/K}$
- 所有卡的输出拼接成 $\mathbb{R}^{d_{ff}}$

**行切分 (Row Parallel)**:
$$
\text{FFN}(x) = x W_1 W_2 = [x^{(1)}, x^{(2)}, \ldots, x^{(K)}] [W_2^{(1)}; W_2^{(2)}; \ldots; W_2^{(K)}]
$$

- $W_2$ 按行切成 $K$ 份: $W_2 = [W_2^{(1)}; W_2^{(2)}; \ldots; W_2^{(K)}]$, 每卡持有 $W_2^{(k)}$
- 输入 $x$ 也按列切成 $K$ 份, 每卡持有 $x^{(k)}$
- 每卡算 $x^{(k)} W_1^{(k)} W_2^{(k)} \in \mathbb{R}^{d}$
- 所有卡的输出相加 (AllReduce)

**Transformer Block 中的 TP 切分 (Megatron 风格)**:

```python
class TransformerBlockTP(nn.Module):
    def __init__(self, d_model, n_heads, d_ff, tp_world_size):
        super().__init__()
        self.tp_size = tp_world_size

        # Self-Attention: QKV 投影按列切分 (每个 head 独立一个 rank)
        self.qkv_proj = ColumnParallelLinear(d_model, 3 * d_model, tp_world_size)

        # Output 投影按行切分
        self.out_proj = RowParallelLinear(d_model, d_model, tp_world_size)

        # FFN 第一层按列切分
        self.ffn_w1 = ColumnParallelLinear(d_model, d_ff, tp_world_size)

        # FFN 第二层按行切分
        self.ffn_w2 = RowParallelLinear(d_ff, d_model, tp_world_size)

    def forward(self, x):
        # x: (B, S, d_model), 每张 TP 卡都有完整副本

        # 1. QKV 投影 (列切分, 每卡算自己的 QKV)
        qkv = self.qkv_proj(x)  # (B, S, 3*d_model/tp_size), 本卡结果
        q, k, v = qkv.chunk(3, dim=-1)

        # 2. Attention 计算 (本卡, head 之间独立)
        attn = self._attention(q, k, v)  # (B, S, d_model/tp_size)

        # 3. Output 投影 (行切分, 最后需要 AllReduce)
        out = self.out_proj(attn)  # (B, S, d_model), 但每卡是部分结果
        # 注意: RowParallelLinear 内部自动 AllReduce
        # 因此 out 在每张卡上都是完整的 d_model 维度

        # 4. FFN
        h = self.ffn_w1(out)  # (B, S, d_ff/tp_size)
        h = F.gelu(h)
        out = self.ffn_w2(h)  # (B, S, d_model), 自动 AllReduce

        return out
```

**通信量分析**:
- 每个 Block 2 次 AllReduce (out_proj + ffn_w2)
- 通信量 = $B \times S \times d_{\text{model}} \times 4$ bytes (FP32) × 2 次 = $8BSd$ bytes per block
- LLaMA-7B (32 层, d=4096, S=2048, B=4): 单 step 总通信 ≈ $8 \times 32 \times 4 \times 2048 \times 4096 = 8.6$ GB per rank
- NVLink 900 GB/s → 单步通信 ~10ms, 可接受

**TP 的硬约束**: 通信是高频 (每层 2 次 AllReduce), 必须用 NVLink, **不能跨机**. 实际 TP=8 (单机 8 卡), 跨机用 DP 或 PP.

### A.3.3 流水线并行 (PP) 详解

**核心: 把模型按层切成 $P$ 段, 每张卡负责一段.**

```text
GPU 0: Layer 0 - Layer 7    (8 层)
GPU 1: Layer 8 - Layer 15   (8 层)
GPU 2: Layer 16 - Layer 23  (8 层)
GPU 3: Layer 24 - Layer 31  (8 层)
```

**朴素 PP 问题: 空泡 (Bubble)**

```text
时间 →
GPU 0: [F0][F0][F0][F0][B0][B0][B0][B0]
GPU 1:    .   [F1][F1][F1][B1][B1][B1][B1]
GPU 2:    .       [F2][F2][B2][B2][B2][B2]
GPU 3:    .           [F3][B3][B3][B3][B3]

上图中"空泡"是 GPU 等待上游数据的时间, P=4 时空泡率 ~25%.
```

**GPipe (Google 2019)**: 把 micro-batch 切成更多份, 让流水线饱满:

```python
# GPipe: 把 batch 切成 4 个 micro-batch, 错开时间
# 时间 →
# GPU 0: F0a F0b F0c F0d | B0d B0c B0b B0a
# GPU 1:    F1a F1b F1c F1d | B1d B1c B1b B1a
# GPU 2:       F2a F2b F2c F2d | B2d B2c B2b B2a
# GPU 3:          F3a F3b F3c F3d | B3d B3c B3b B3a

# M 个 micro-batch 完美填满流水线, 空泡 = (P-1) / M
# M=4, P=4 → 空泡率 25%
# M=16, P=4 → 空泡率 ~6% (但要存 M 个 micro-batch 的激活, 显存增 M 倍)
```

**PipeDream (Microsoft 2019)**: 1F1B (One Forward, One Backward) 调度, 减少激活存储:

```python
# 时间 →
# GPU 0: F0a F0b F0c F0d B0a F0e B0b ...
# GPU 1:    F1a F1b F1c F1d B1a F1e ...
# ...
# 稳态后, 每张卡 1F + 1B 交替, 激活只需存 1 个 micro-batch
# 空泡 = (P-1), 但激活显存省 M 倍
```

**通信**: 仅在 stage 边界点对点 (send/recv), 通信量 = $B \times S \times d_{\text{model}}$ per micro-batch. 远小于 TP 的 AllReduce, **可以跨机**.

### A.3.4 数据并行 (DP) 在 3D 中的角色

3D 并行中, DP 是 "外层" 并行:

```text
总 GPU = TP × PP × DP
例如: 64 GPU = 8 (TP) × 4 (PP) × 2 (DP)
```

每组 (TP × PP) 构成一个 "模型副本", 复制 $DP$ 份, 切 batch.

```text
GPU 0-7:   模型副本 0 (TP=8 + PP=1, 切 Layer 0-7)
GPU 8-15:  模型副本 0 (TP=8 + PP=1, 切 Layer 8-15)
GPU 16-23: 模型副本 0 (TP=8 + PP=1, 切 Layer 16-23)
GPU 24-31: 模型副本 0 (TP=8 + PP=1, 切 Layer 24-31)
GPU 32-39: 模型副本 1 (同上, 不同 batch)
...
```

DP 之间 AllReduce 梯度, 通信量 = $2\Psi$, 但每卡只算 $\Psi / (\text{TP} \times \text{PP})$ 的梯度.

| 维度 | Megatron 3D | FSDP + DP |

### A.3.8 3D 并行的 GPU 拓扑约束

```text
硬件拓扑假设 (典型 8 卡 A100 节点):
  - 8 卡 NVLink 全互联 (~900 GB/s 双向)
  - 节点间 IB (~200 GB/s)

并行配置推荐:
  TP=8 (机内, NVLink 必须)
  PP=2-4 (跨机, IB 可接受)
  DP=剩余 (跨机, IB 可接受)

如果节点数 N=64:
  TP=8, PP=4, DP=2 → 总 64 GPU
  含义: 4 节点构成一组 3D 模型副本, 复制 2 份
```

**关键约束**:
1. **TP 必须机内 (NVLink)**: TP 通信是每层 2 次 AllReduce, 跨机带宽不够
2. **PP 可跨机**: PP 通信是 stage 边界点对点, 跨机可接受
3. **DP 可跨机**: DP 通信是 AllReduce 一次/step, 跨机可接受

```yaml
# 通信: all-to-all (token dispatch + combine)
```

**EP 通信模式**:
- Token dispatch: 把 token 按路由分配到对应 expert 所在卡 (all-to-all)
- Expert compute: 每卡并行算自己的 expert
- Token combine: 把 expert 输出回收 (all-to-all)

通信量: $2 \times B \times S \times d_{\text{model}}$ (一次 dispatch + 一次 combine).

### A.4.5 显存优化的"三件套"

> 大模型训练的标配: **ZeRO-3 + Activation Checkpointing + CPU Offload**.

```python
# 三件套一起用
from torch.distributed.fsdp import (
    FullyShardedDataParallel as FSDP,
    MixedPrecision,
    BackwardPrefetch,
)
from torch.distributed.fsdp.api import CPUOffload
from torch.utils.checkpoint import checkpoint

model = FSDP(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,  # 三件套之一
    mixed_precision=MixedPrecision(param_dtype=torch.bfloat16, ...),
    cpu_offload=CPUOffload(offload_params=True),    # 三件套之二
    backward_prefetch=BackwardPrefetch.BACKWARD_PRE,
)

# 三件套之三: Activation Checkpointing
# 每个 TransformerBlock 用 checkpoint 包装
for block in model.blocks:
    block.forward = checkpoint(block._forward, use_reentrant=False)
```

**LLaMA-70B 单卡 (A100 80GB) 实际显存分布**:
- 原始 (无优化): 70B × 16 bytes = 1120 GB → 装不下
- + ZeRO-3 单机 8 卡: 1120 / 8 = 140 GB / 卡 → 装不下
- + + CPU offload: 优化器状态 + 部分参数卸载, ~40 GB / 卡
- + + + Activation Checkpointing: 激活从 60 GB 降到 ~10 GB
- + + + + BF16: 参数和优化器再省 ~30%

最终: ~30 GB / 卡 → **8 卡 A100 80GB 能跑 LLaMA-70B**.

### A.4.7 Checkpoint 工程实践

**3D 并行的 Checkpoint 切片保存**:

```python
# Megatron-LM 风格: 每张卡保存自己负责的那一片参数
def save_checkpoint(model, optimizer, iteration, save_dir):
    rank = dist.get_rank()
    world_size = dist.get_world_size()

    # 收集所有 rank 的参数
    state_dict = {}
    for name, param in model.named_parameters():
        # 假设每个参数按 TP/PP 切分, 只 rank 0 保存完整状态
        if rank == 0:
            gathered = torch.zeros(param.shape, dtype=param.dtype, device='cpu')
            dist.gather(param.data, gathered, dst=0)
            if rank == 0:
                state_dict[name] = gathered

    if rank == 0:
        torch.save({
            'iteration': iteration,
            'model_state_dict': state_dict,
            'optimizer_state_dict': optimizer.state_dict(),
        }, f"{save_dir}/checkpoint_{iteration}.pt")
```

**ZeRO-3 的 Checkpoint 处理**:

```python
# ZeRO-3 下, 每个 rank 只持有 1/N 的分片, 不能直接保存完整模型
# 方法 1: 用 stage3_gather_16bit_weights_on_model_save=True
ds_config = {
    "zero_optimization": {
        "stage": 3,
        "stage3_gather_16bit_weights_on_model_save": True,  # 保存时 gather
    }
}

# 方法 2: 手动 gather 后保存
from deepspeed import zero
with zero.Init():
    # 在 zero context 下, 调用会触发 gather
    state_dict = model.state_dict()
if dist.get_rank() == 0:
    torch.save(state_dict, "checkpoint.pt")
```

### A.4.10 训练效率监控

**关键指标**:

| 指标 | 含义 | 健康范围 |
| :--- | :--- | :--- |
| **Tokens/sec/GPU** | 单卡吞吐 | LLaMA-7B FP16: 8K-15K, 70B BF16: 2K-5K |
| **GPU 利用率** | SM 活跃比例 | > 80% |
| **显存利用率** | HBM 占用 | 70-90% (留 buffer) |
| **通信占比** | nccl kernel 时间占比 | < 30% |
| **TFLOPS** | 实际算力 | LLaMA-7B FP16: 100-180 TFLOPS (A100 峰值 312) |
| **MFU (Model FLOPS Utilization)** | 实际 / 理论 FLOPS | > 50% (优秀), > 30% (合格) |

**MFU 计算公式**:

$$
\text{MFU} = \frac{6 \Psi B S}{\text{step\_time} \times \text{peak FLOPS}}
$$

其中:
- $\Psi$: 参数量
- $B$: global batch size
- $S$: sequence length
- step_time: 单步耗时 (秒)
- peak FLOPS: 硬件理论峰值 (A100 312 TFLOPS BF16)

例: LLaMA-7B, B=32, S=2048, step_time=2s, $\Psi$=7e9

$$
\text{MFU} = \frac{6 \times 7 \times 10^9 \times 32 \times 2048}{2 \times 312 \times 10^{12}} = \frac{2.75 \times 10^{15}}{6.24 \times 10^{14}} \approx 4.4
$$

等等, 这 > 1 不对. 实际应该是 MFU = 实际 / 理论 = $2.75 \times 10^{15} / (2 \times 312 \times 10^{12}) = 4.4$.

> 检查: $6 \times 7e9 = 4.2e10$ FLOPs per token, B*S = 32*2048 = 65536 tokens, 总 = $4.2e10 \times 65536 = 2.75e15$ FLOPs/step, step_time=2s, throughput = $1.38e15$ FLOPS = 1.38 PFLOPS. A100 理论 312 TFLOPS, 实际 1.38 PFLOPS = 1380 TFLOPS, **超了**!

**实际 MFU 计算**: 应该用 batch step, 不是 global. LLaMA-7B MFU 实际约 50-60% (Meta 论文).

## A.5 面试题精选 (25 道)

> 题目按难度分级: ★ 简单 / ★★ 中等 / ★★★ 困难. 涵盖原理、计算、工程、调优.

### Q1 (★): DDP 和 DP (DataParallel) 的区别?

**答**:
- **DP (DataParallel, 单进程多线程)**: 单进程控多卡, GIL 限制, 通信走 PCIe. 主卡 (rank 0) 做梯度累加 + 参数广播, 主卡瓶颈明显.
- **DDP (DistributedDataParallel, 多进程)**: 每卡一个进程, 走 NCCL, Ring AllReduce. 速度是 DP 的 5-10x, **工业标准**.

```python
# DP
model = nn.DataParallel(model, device_ids=[0, 1, 2, 3])

# DDP
model = nn.parallel.DistributedDataParallel(model, device_ids=[local_rank])
```

### Q2 (★): ZeRO-3 与 FSDP 是什么关系?

**答**: **FSDP (Fully Sharded Data Parallel) 是 PyTorch 1.11+ 原生的 ZeRO-3 实现**. 二者在原理上等价:
- 都把模型参数、梯度、优化器状态按 rank 分片
- 前向/反向时按需 all_gather 参数
- 通信原语相同 (AllGather + ReduceScatter)

DeepSpeed ZeRO-3 早于 FSDP 推出 (2019), FSDP 是 PyTorch 官方跟进 (2022).

### Q3 (★★): 训练 7B 模型, 8 卡 A100, 用什么策略?

**答**:
- 单机 8 卡, 模型 7B FP16 = 14 GB
- 推荐 **DDP + BF16 + Gradient Checkpointing**, 不用 ZeRO
- 单卡显存: 14 GB (模型) + 14 GB (梯度) + 56 GB (AdamW FP32) = 84 GB → A100 80GB 装不下!
- **实际用**: ZeRO-2 + BF16 (单卡 14 + 14 + 56/8 = 35 GB) + Activation Checkpointing
- 或者: ZeRO-3 + CPU Offload + Activation Checkpointing

### Q4 (★★★): 计算 DDP 单 step 通信量

LLaMA-7B (7e9 参数), 8 卡 DDP, NVLink 900 GB/s, 求单 step 通信耗时.

**答**:
- 通信量: $2 \times 7$ GB = 14 GB (前向 + 反向梯度 AllReduce)
- 实际: AllReduce 通信量 = $2(N-1)/N \times \Psi$, N=8 时 ≈ 12.25 GB
- 耗时: 12.25 / 900 = 13.6 ms (理想情况, 不计延迟)
- 实测: 加上启动开销, 约 30-50 ms

### Q5 (★★): ZeRO-3 比 ZeRO-2 显存省多少?

LLaMA-7B, 8 卡, FP32 master weights.

**答**:
- ZeRO-2: 单卡 = $4\Psi + 12\Psi/K = 28 + 10.5 = 38.5$ GB
- ZeRO-3: 单卡 = $16\Psi/K = 14$ GB
- 省: $38.5 - 14 = 24.5$ GB / 卡, 折算 $24.5/38.5 \approx 64\%$
- 等价: 同样模型, ZeRO-3 比 ZeRO-2 多支撑近 3 倍大

### Q6 (★★★): Megatron 3D 并行中, TP=8, PP=4, DP=2, 总 64 卡, 训 175B 模型, 每卡显存多少?

**答**:
- 每卡参数: $175 / (8 \times 4) = 5.47$ B
- FP16: 10.94 GB
- FP32 master: 21.88 GB
- 梯度: 21.88 GB
- 优化器 (AdamW FP32): 43.76 GB
- 激活 (含 checkpoint): 15 GB
- 总: ~113 GB → **A100 80GB 装不下**, 需要 H100 80GB (BF16 优化器省一半)

### Q7 (★★): Ring AllReduce 为什么优于朴素 AllReduce?

**答**: 朴素 AllReduce 主卡带宽成瓶颈 ($O(N)$ 延迟), Ring 把数据切成 $N$ 块环形传, 每步只传 $1/N$, 总 $O(1)$ 通信量 (与卡数无关). NCCL / MPI 都用 Ring 实现.

### Q8 (★★★): 训练时 GPU 利用率只有 30%, 怎么诊断?

**答**: 按顺序检查:
1. **数据加载瓶颈**: 用 `torch.profiler` 看 `DataLoader` 时间, 异步 prefetch 不够 → 增大 `num_workers`
2. **通信瓶颈**: 看 NCCL kernel 时间占比, > 30% → 降 ZeRO stage 或加 micro batch
3. **CPU 瓶颈**: 看 DataLoader 时间 > GPU 时间 → 优化数据预处理 (cache / 预计算)
4. **kernel 太小**: 模型层数少 / batch 太小 → 加 batch 或减少 GPU
5. **同步开销**: 检查不必要的 `torch.cuda.synchronize()` / `.item()` / `.cpu()`

### Q9 (★★★): 如果训练 loss 突然 spike, 可能的原因?

**答**:
- **学习率太大**: 看 LR 是否在 spike 时正好调到峰值
- **数据问题**: 检查 data pipeline, 是否有 OOV token / 异常长序列
- **优化器状态损坏**: 加载 checkpoint 时 dtype 不匹配, 浮点溢出
- **AllReduce 通信错误**: NCCL 超时, 集群某个节点故障
- **梯度爆炸**: grad clip 未生效 / 设置过大

```python
# 诊断代码
if loss > 3 * running_avg_loss:
    print("⚠️  Loss spike detected")
    # 1. 检查 NaN
    if torch.isnan(loss):
        print("NaN loss! Skipping batch, reducing LR")
        optimizer.zero_grad()
        return
    # 2. 跳过这一 batch
    # 3. 检查 checkpoint
    # 4. 缩小 LR
```

### Q10 (★★): FSDP 和 DeepSpeed ZeRO-3 的代码差异?

**答**: 用户视角几乎一致:
```python
# FSDP
model = FSDP(model, sharding_strategy=ShardingStrategy.FULL_SHARD, ...)
loss = model(batch); loss.backward(); optimizer.step()

# DeepSpeed ZeRO-3
model_engine, optimizer, _, _ = deepspeed.initialize(model=model, config=ds_config)
loss = model_engine(batch); model_engine.backward(loss); model_engine.step()
```

差异:
- DeepSpeed 配置更丰富 (offload, overlap_comm 等)
- FSDP 与 PyTorch 生态更紧 (TorchDynamo, compile 兼容)
- DeepSpeed 有 ZeRO-Infinity (NVMe 卸载), FSDP 没有等价物

### Q11 (★): 什么是 Gradient Checkpointing?

**答**: 反向传播时, 不存所有中间激活, 只存 checkpoint. 反向到某层时, 从最近的 checkpoint 重新前向算激活.
- 显存: 激活从 $O(L \times B \times S \times d)$ 降到 $O(\sqrt{L} \times B \times S \times d)$
- 计算: 多 ~30% (重新前向)
- 适合: 大模型 + 显存不够

### Q12 (★★): 混合精度训练中, FP16 / BF16 / FP32 各自的角色?

**答**:
- **FP32 master weights**: 优化器更新参数用的"权威"副本, 防止 FP16 精度不足
- **FP16 / BF16 weights**: 前向/反向用的"工作"副本
- **FP16 / BF16 gradients**: 反向算出的梯度
- **FP32 optimizer states**: AdamW 的 $m, v$, 用 FP32 防精度损失

BF16 vs FP16:
- FP16: 8 bit 指数, 10 bit 尾数, 范围窄, 易 overflow
- BF16: 8 bit 指数 (同 FP32), 7 bit 尾数, 范围大, 不易 overflow, 但精度略差
- 现代硬件 (A100, H100) BF16 速度与 FP16 一样, **BF16 是新标准**

### Q13 (★★★): 解释 Gradient Accumulation 的作用

**答**: 把大 batch 切成多个 micro batch, 累积梯度后统一更新. 作用:
1. **突破单卡显存限制**: 大 batch 装不下, 用 micro batch 模拟
2. **减少通信频率**: 多个 micro batch 累积一次 AllReduce, 通信摊薄
3. **稳定训练**: 等效大 batch, 减少梯度噪声

```python
accumulation_steps = 8
optimizer.zero_grad()
for i, batch in enumerate(loader):
    loss = model(batch) / accumulation_steps
    loss.backward()  # 梯度累积

    if (i + 1) % accumulation_steps == 0:
        optimizer.step()       # 每 8 个 micro batch 更新一次
        optimizer.zero_grad()
```

### Q14 (★★): 3D 并行中, TP 为什么不能跨机?

**答**: TP 通信是每层 2 次 AllReduce (高频小包), 跨机带宽 IB (~200 GB/s) 比 NVLink (~900 GB/s) 慢 4-5x, 通信暴露会成为瓶颈. NVLink 是 GPU 直连, IB 走网卡 + 交换机 + CPU, 延迟也高. **TP 必须放机内 (NVLink)**.

### Q15 (★★★): 计算 LLaMA-70B 单卡训练显存的"最小可能"

LLaMA-70B 用 BF16 训练, 单卡 A100 80GB. 假设 ZeRO-3 + CPU Offload + Activation Checkpointing.

**答**:
- BF16 参数: 70e9 × 2 / K
- BF16 梯度: 70e9 × 2 / K
- FP32 master weights: 70e9 × 4 / K
- FP32 优化器状态: 70e9 × 8 / K
- 激活 (checkpoint): ~5 GB / 卡 (固定, 不分片)

如果 K=8, 完全 in-GPU:
- 参数 + 梯度 + master + 优化器 = 16 × 70 / 8 = 140 GB / 卡 → 装不下
- 加 CPU offload (优化器 + FP32 master 到 CPU): 4 × 70 / 8 = 35 GB → 80 GB 装得下
- 实际配置: ZeRO-3 + CPU offload + Activation Checkpointing, K=8, 单卡约 50 GB

### Q16 (★★): AllReduce 和 AllGather 的区别?

**答**:
- **AllReduce**: 每张卡都有完整数据 (求和后广播)
- **AllGather**: 每张卡提供 1/N 数据, 收完后每张卡都有完整数据 (无求和)

```python
# AllReduce (sum)
dist.all_reduce(tensor, op=dist.ReduceOp.SUM)  # 每卡都收到求和结果

# AllGather (gather, no sum)
output = [torch.zeros_like(tensor) for _ in range(world_size)]
dist.all_gather(output, tensor)  # 每卡收到完整列表
```

ZeRO-3 用 AllGather (无求和), DDP 用 AllReduce (求和).

### Q17 (★★★): 设计一个训练 GPT-2 1.5B 的方案

**约束**: 8 卡 A100 80GB, 数据 100B tokens, 预算 7 天.

**答**:

```yaml
精度: BF16
batch: global=512, micro=8, accum=8
```

### Q18 (★★): 解释 `set_grad_enabled(False)` 在分布式训练中的作用

**答**: 在推理 / 评估时关闭梯度计算, 节省显存 + 加速.

```python
model.eval()
with torch.no_grad():  # 等价 set_grad_enabled(False) + set_grad_enabled(True)
    for batch in val_loader:
        loss = model(batch)
```

分布式中: 每张卡独立评估自己分到的 batch, 用 `model.module` 访问原始模型 (去掉 DDP 包装).

### Q19 (★★★): 训练时, 显存爆了, 但 GPU 利用率不到 50%, 为什么?

**答**: **计算-通信重叠失败**. 显存爆意味着要么模型太大, 要么激活太多. 但 GPU 利用率低说明大部分时间 GPU 在等 (通信 / 数据加载).
- 可能 1: CPU Offload 频繁 swap, 数据搬运占满 PCIe
- 可能 2: AllGather / ReduceScatter 没藏好, GPU 干等
- 可能 3: 通信 + 计算序列化, 没 overlap

解决:
1. 关闭 CPU Offload, 改用纯 GPU ZeRO-3 (通信-计算重叠更好)
2. 增大 micro batch, 减少通信频率
3. 调整 FSDP 的 `backward_prefetch` 和 `forward_prefetch`

### Q20 (★★★): DeepSpeed 的 ZeRO-Infinity 和 ZeRO-3 区别?

**答**:
- **ZeRO-3**: 把模型参数 / 梯度 / 优化器状态分片到 GPU 显存
- **ZeRO-Infinity**: 把 ZeRO-3 的分片进一步扩展到 CPU RAM + NVMe SSD, 容量天花板从 GPU 显存 (几十 GB/卡) 提到 NVMe (几 TB/卡)

```yaml
# ZeRO-Infinity config
zero_optimization:
  stage: 3
  offload_optimizer:
    device: nvme
    nvme_path: /mnt/nvme
    pin_memory: true
  offload_param:
    device: nvme
    nvme_path: /mnt/nvme
    pin_memory: true
  # 通信开销高, 但可训 32T 参数模型
```

代价: PCIe 带宽 (~32 GB/s) vs NVLink (~900 GB/s), 慢 30 倍, 所以 ZeRO-Infinity 主要用于**训练超大模型但算力不敏感**的场景.

### Q21 (★): 什么是 gradient bucketing?

**答**: DDP / ZeRO 反向传播时, 不等所有梯度都算完才开始同步, 而是按参数分组到 bucket (默认 25 MB / bucket), bucket 满了立刻 AllReduce. 好处: 把通信藏在反向计算背后.

### Q22 (★★): 解释 DP 中, 为什么主卡会成为瓶颈?

**答**: DP 流程:
1. 主卡把 batch 切 $N$ 份, 分发给 $N$ 张卡
2. 每张卡独立前向/反向
3. 每张卡把梯度 gather 到主卡
4. **主卡**做梯度累加 + 更新参数
5. 主卡把更新后的参数 broadcast 给所有卡

主卡单卡要做 (N-1) 倍的梯度累加 + 1 次 broadcast, **N 越大, 主卡越慢**. DDP 用 Ring AllReduce 解决了这个问题.

### Q23 (★★★): 设计 3D 并行训练 LLaMA-70B 的集群拓扑

**答**:
- 总 GPU: 128 (16 机 × 8 卡 A100 80GB)
- 并行配置: TP=8 (机内), PP=2 (跨机), DP=8 (剩余)
- 模型切片: PP=2 → 每段 40 层, TP=8 → 每张卡分 1/8 矩阵
- 单卡参数: $70 / (8 \times 2) = 4.375$ B
- 单卡显存 (BF16): $4.375 \times 16 = 70$ GB / 卡 (含 FP32 master + 优化器)

### Q24 (★★): 为什么用 BF16 而非 FP16 训练?

**答**:
- **FP16**: 指数 5 bit, 范围 $[6 \times 10^{-5}, 65504]$, 易 overflow (loss spike)
- **BF16**: 指数 8 bit (同 FP32), 范围 $[10^{-38}, 10^{38}]$, 不易 overflow
- **BF16 精度**: 尾数 7 bit, 比 FP16 略差, 但训练 LLM 够用

实际:
- BF16 + FP32 master weights 是 2023+ 标准
- H100 的 BF16 算力与 FP16 一样 (但有 FP8 比 BF16 快 2x, 是新趋势)

### Q25 (★★★): 描述 vLLM PagedAttention 和分布式训练的关系

**答**: **二者正交, 不冲突**.
- 分布式训练: 解决"如何训大模型"
- vLLM 推理: 解决"如何高效推理大模型"
- 训练完的 checkpoint 可以直接加载到 vLLM

```python
# 训练
model_engine.save_checkpoint("checkpoint_dir")

# 推理 (用 vLLM)
from vllm import LLM
llm = LLM(model="checkpoint_dir")
outputs = llm.generate(["Hello, my name is"])
```

推理时, vLLM 用 PagedAttention (KV cache 分页) + Continuous Batching, 把吞吐量提升 24x. **训练时不需要这些, 因为 KV cache 每次 step 后释放**.

### A.6.3 常见踩坑清单

1. **ZeRO-3 + CPU Offload 时, 不要用 `torch.compile`**: CPU ↔ GPU 数据搬运会破坏编译优化
2. **FSDP checkpoint 加载**: 必须用 `ShardingStateDictConfig` 或 `FullStateDictConfig` 上下文
3. **MoE 模型**: 常规 ZeRO-3 不支持 expert 分片, 必须用 DeepSpeed MoE config 或 Megatron EP
4. **Gradient Checkpointing 失效**: 如果用了 `torch.utils.checkpoint`, 但外层又用了 FSDP auto_wrap, 可能不生效. 正确做法是在 FSDP wrap 之前 wrap checkpoint
5. **混合精度 loss scale**: FP16 训练必须用动态 loss scale, BF16 不需要
6. **NCCL timeout**: 长 step 训练 (大模型, 长序列), 默认 30 分钟 NCCL 超时不够, 用 `export NCCL_TIMEOUT=7200`
7. **CPU Offload 启动慢**: 第一次迭代要把 optimizer state 搬到 CPU, 可能 5-10 分钟, 不要误以为 hang

## A.8 实战代码库: 6 个可直接复用的模板

> **本节定位**: 给工业实战中最常用的 6 个分布式训练场景, 提供可直接跑通的 PyTorch 代码模板. 复制粘贴 + 改模型/数据即可用.

### A.8.1 模板 1: DDP 单机多卡训练 (CIFAR-10 完整示例)

```python
# train_ddp.py
import os
import argparse
import torch
import torch.nn as nn
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader
from torch.utils.data.distributed import DistributedSampler
import torchvision
import torchvision.transforms as T

def setup():
    """初始化进程组"""
    dist.init_process_group(backend="nccl")
    torch.cuda.set_device(int(os.environ["LOCAL_RANK"]))

def cleanup():
    dist.destroy_process_group()

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--epochs", type=int, default=10)
    parser.add_argument("--batch_size", type=int, default=128)
    parser.add_argument("--lr", type=float, default=1e-3)
    args = parser.parse_args()

    setup()
    rank = dist.get_rank()
    world_size = dist.get_world_size()
    local_rank = int(os.environ["LOCAL_RANK"])
    device = torch.device(f"cuda:{local_rank}")

    # 仅 rank 0 打印
    if rank == 0:
        print(f"World size: {world_size}")

    # 数据: 用 DistributedSampler 切分数据
    transform = T.Compose([T.ToTensor(), T.Normalize((0.5,), (0.5,))])
    dataset = torchvision.datasets.CIFAR10(
        root="./data", train=True, download=True, transform=transform
    )
    sampler = DistributedSampler(dataset, num_replicas=world_size, rank=rank, shuffle=True)
    loader = DataLoader(
        dataset, batch_size=args.batch_size, sampler=sampler,
        num_workers=4, pin_memory=True
    )

    # 模型
    model = torchvision.models.resnet50(num_classes=10).to(device)
    model = DDP(model, device_ids=[local_rank])

    # 优化器
    optimizer = torch.optim.AdamW(model.parameters(), lr=args.lr)
    criterion = nn.CrossEntropyLoss()

    # 训练循环
    for epoch in range(args.epochs):
        sampler.set_epoch(epoch)  # 关键: 每个 epoch 重新打散数据
        model.train()

        for batch_idx, (data, target) in enumerate(loader):
            data, target = data.to(device), target.to(device)

            optimizer.zero_grad()
            output = model(data)
            loss = criterion(output, target)
            loss.backward()  # DDP 内部触发 AllReduce
            optimizer.step()

            if rank == 0 and batch_idx % 10 == 0:
                print(f"Epoch {epoch} | Batch {batch_idx}/{len(loader)} | Loss {loss.item():.4f}")

    # 仅 rank 0 保存模型
    if rank == 0:
        torch.save(model.module.state_dict(), "resnet50_ddp.pt")

    cleanup()

if __name__ == "__main__":
    main()

# 运行: torchrun --nproc_per_node=8 train_ddp.py
```

### A.8.2 模板 2: FSDP 训练 Transformer (LLaMA 风格)

```python
# train_fsdp.py
import os
import torch
import torch.nn as nn
import torch.distributed as dist
from torch.distributed.fsdp import (
    FullyShardedDataParallel as FSDP,
    MixedPrecision,
    BackwardPrefetch,
    ShardingStrategy,
)
from torch.distributed.fsdp.wrap import transformer_auto_wrap_policy
from torch.utils.checkpoint import checkpoint

# 简化的 Transformer Block
class TransformerBlock(nn.Module):
    def __init__(self, d_model, n_heads, d_ff):
        super().__init__()
        self.ln1 = nn.LayerNorm(d_model)
        self.attn = nn.MultiheadAttention(d_model, n_heads, batch_first=True)
        self.ln2 = nn.LayerNorm(d_model)
        self.ffn = nn.Sequential(
            nn.Linear(d_model, d_ff), nn.GELU(), nn.Linear(d_ff, d_model)
        )

    def forward(self, x):
        h = self.ln1(x)
        h, _ = self.attn(h, h, h, need_weights=False)
        x = x + h
        h = self.ffn(self.ln2(x))
        return x + h

class TransformerLM(nn.Module):
    def __init__(self, vocab_size, n_layers, d_model, n_heads, d_ff):
        super().__init__()
        self.embed = nn.Embedding(vocab_size, d_model)
        self.blocks = nn.ModuleList([
            TransformerBlock(d_model, n_heads, d_ff) for _ in range(n_layers)
        ])
        self.ln_f = nn.LayerNorm(d_model)
        self.head = nn.Linear(d_model, vocab_size, bias=False)

    def forward(self, ids):
        x = self.embed(ids)
        for block in self.blocks:
            x = checkpoint(block, x, use_reentrant=False)  # Activation Checkpointing
        return self.head(self.ln_f(x))

def main():
    # 初始化
    dist.init_process_group(backend="nccl")
    rank = dist.get_rank()
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)

    # 模型 (LLaMA-7B 量级)
    model = TransformerLM(
        vocab_size=50000, n_layers=32, d_model=4096,
        n_heads=32, d_ff=11008
    )

    # FSDP 包装: 按 TransformerBlock 分片
    auto_wrap_policy = transformer_auto_wrap_policy(
        transformer_layer_cls={TransformerBlock},
    )
    model = FSDP(
        model,
        sharding_strategy=ShardingStrategy.FULL_SHARD,  # ZeRO-3
        auto_wrap_policy=auto_wrap_policy,
        mixed_precision=MixedPrecision(
            param_dtype=torch.bfloat16,
            reduce_dtype=torch.bfloat16,
            buffer_dtype=torch.bfloat16,
        ),
        backward_prefetch=BackwardPrefetch.BACKWARD_PRE,
        forward_prefetch=True,
        limit_all_gathers=True,
        device_id=torch.cuda.current_device(),
    )

    # 优化器 (必须在 FSDP 包装后创建)
    optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)

    # 训练循环
    for step in range(10000):
        ids = torch.randint(0, 50000, (4, 2048), device=f"cuda:{local_rank}")
        logits = model(ids)
        loss = nn.functional.cross_entropy(
            logits.view(-1, 50000), ids.view(-1)
        )
        loss.backward()
        optimizer.step()
        optimizer.zero_grad()

        if rank == 0 and step % 10 == 0:
            print(f"Step {step} | Loss {loss.item():.4f}")

if __name__ == "__main__":
    main()

# 运行: torchrun --nproc_per_node=8 train_fsdp.py
```

### A.8.3 模板 3: DeepSpeed ZeRO-3 + CPU Offload

```python
# train_deepspeed.py
import deepspeed
import torch
import torch.nn as nn

# 模型定义 (同上)
class TransformerBlock(nn.Module):
    def __init__(self, d_model, n_heads, d_ff):
        super().__init__()

        self.ln2 = nn.LayerNorm(d_model)
        self.ffn = nn.Sequential(
            nn.Linear(d_model, d_ff), nn.GELU(), nn.Linear(d_ff, d_model)

        x = x + h
        return x + self.ffn(self.ln2(x))

class TransformerLM(nn.Module):
    def __init__(self, vocab_size, n_layers, d_model, n_heads, d_ff):
        super().__init__()
        self.embed = nn.Embedding(vocab_size, d_model)
        self.blocks = nn.ModuleList([
            TransformerBlock(d_model, n_heads, d_ff) for _ in range(n_layers)
        ])
        self.head = nn.Linear(d_model, vocab_size)

    def forward(self, ids):
        x = self.embed(ids)
        for block in self.blocks:
            x = block(x)
        return self.head(x)

def main():
    # DeepSpeed 配置
    ds_config = {
        "train_batch_size": 32,
        "gradient_accumulation_steps": 4,
        "gradient_clipping": 1.0,
        "fp16": {"enabled": True, "loss_scale": 0, "initial_scale_power": 16},
        "zero_optimization": {
            "stage": 3,
            "offload_optimizer": {"device": "cpu", "pin_memory": True},
            "offload_param": {"device": "cpu", "pin_memory": True},
            "overlap_comm": True,
            "contiguous_gradients": True,
            "sub_group_size": 1e9,
            "reduce_bucket_size": "auto",
            "stage3_prefetch_bucket_size": "auto",
            "stage3_param_persistence_threshold": "auto",
            "stage3_max_live_parameters": "auto",
            "stage3_max_reuse_distance": "auto",
            "stage3_gather_16bit_weights_on_model_save": True,
        },
        "optimizer": {"type": "AdamW", "params": {"lr": 3e-4, "betas": [0.9, 0.95]}},
        "scheduler": {"type": "WarmupDecayLR", "params": {"warmup_num_steps": 1000}},
        "activation_checkpointing": {
            "partition_activations": False,
            "cpu_checkpointing": False,
            "contiguous_memory_optimization": True,
            "number_checkpoints": None,
        },
    }

    model = TransformerLM(50000, 32, 4096, 32, 11008)

    # DeepSpeed 初始化
    model_engine, optimizer, _, scheduler = deepspeed.initialize(
        args=None, model=model, config=ds_config
    )

    # 训练循环
    for step in range(10000):
        ids = torch.randint(0, 50000, (4, 2048), device=model_engine.device)
        logits = model_engine(ids)
        loss = nn.functional.cross_entropy(logits.view(-1, 50000), ids.view(-1))
        model_engine.backward(loss)
        model_engine.step()

        if model_engine.global_rank == 0 and step % 10 == 0:
            print(f"Step {step} | Loss {loss.item():.4f}")

    # 保存 (仅 rank 0)
    if model_engine.global_rank == 0:
        model_engine.save_checkpoint("checkpoint_dir")

if __name__ == "__main__":
    main()

# 运行: deepspeed --num_gpus=8 train_deepspeed.py
```

### A.9.4 常见的"性能不达预期"原因与修复

| 现象 | 原因 | 修复 |
| :--- | :--- | :--- |
| GPU 利用率 < 50% | 数据加载瓶颈 | `num_workers` 加大 + 预计算到内存 |
| GPU 利用率波动 | CPU 调度抖动 | `torch.cuda.set_per_process_memory_fraction` 限制 |
| 通信占比 > 30% | ZeRO stage 过高 / micro batch 太小 | 降 ZeRO stage 或加大 micro batch |
| loss 不下降 | LR 太大 / 数据问题 / 模型 bug | 缩小 LR, 检查数据 |
| loss spike | FP16 溢出 / 异常数据 | 改 BF16 + 检查数据 |
| 显存爆 | 模型太大 / 激活太多 | ZeRO-3 + Activation Checkpointing |
| step 时间不一致 | 数据加载抖动 / 通信抖动 | 加大 num_workers + NCCL 优化 |

### 110. 分布式训练 (DDP / FSDP / DeepSpeed ZeRO) - 优化视角 视角

**核心议题**: 本节从优化视角视角切入,系统展开 "分布式训练 (DDP / FSDP / DeepSpeed ZeRO)" 的相关讨论。

**1. 背景与动机**

任何技术或方法的出现都不是孤立的,而是回应特定历史条件下的具体问题。"分布式训练 (DDP / FSDP / DeepSpeed ZeRO)" 的发展也不例外。要理解它,必须回到它出现的那个时间点,看清它要解决的真实问题是什么。当时的主流方案有哪些不足? 它的提出填补了哪些空白? 这些问题的回答,决定了我们今天该如何使用它。

从知识论角度看,**技术演进是问题驱动的**——不是先有方案再找问题,而是先有问题再有方案。这个观察可以帮助我们避免"拿着锤子找钉子"的陷阱,真正把方法用对地方。

历史维度上,我们看到三个规律:

1. **从特殊到一般**: 早期方法往往针对特定场景,后期抽象出通用框架。学习的认知规律也是先掌握具体案例,再抽象出一般模式。这种"自下而上"的学习方式,在机器学习模型的设计里反复出现。

2. **从手工到自动**: 经验规则逐步被数据驱动的方法取代。在早期,很多 AI 系统依赖人工编写的规则。统计学习方法的崛起让"从数据中学习"成为可能。深度学习进一步把特征工程也自动化了。今天的大模型时代,我们看到端到端学习从感知扩展到了推理与生成。

3. **从局部到全局**: 关注单个组件,演进到关注整个系统。早期模型评估只关注单点指标,现在更关注全链路的协同效应。这种"系统视角"的转变,与软件工程从单体架构到微服务架构的演进高度相似。

**2. 优化视角视角的展开**

从优化视角视角出发,我们可以把 "分布式训练 (DDP / FSDP / DeepSpeed ZeRO)" 拆解为以下几个层次:

**第一层: 概念层** —— 这是最抽象的层次,定义了我们要研究的对象是什么。例如,"推荐系统"在概念层是一个"为用户从物品集合中筛选合适物品"的问题。这个层次的特点是清晰、稳定、不易变化。一个好的概念定义应该具备几个特征:可操作性、可测量性、可扩展性。

**第二层: 模型层** —— 把概念实例化为数学模型。同一概念可以有不同的模型化方式,例如"推荐系统"可以是协同过滤、矩阵分解、深度学习等。模型的选择决定了后续算法的空间,也决定了能利用的归纳偏置(比如序列模型擅长捕捉时序依赖,图模型擅长建模关系结构)。模型选型是工程实践中最重要的决策之一。
