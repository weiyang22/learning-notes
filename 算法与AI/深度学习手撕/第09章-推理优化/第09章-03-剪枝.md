# 第09章-03-剪枝


## 1. 内容介绍

**剪枝** (Pruning) 是 LLM 压缩的经典方法, **移除不重要的权重**, 减少模型大小和推理时间.

**3 大方案**:
- **非结构化剪枝**: 移除单个权重 (Wanda)
- **结构化剪枝**: 移除整个神经元 / 注意力头 / 层
- **半结构化剪枝 (2:4)**: NVIDIA Ampere 硬件支持

---

## 2. 为什么这么做

**问题 (大模型部署)**:
- LLaMA-7B FP16 = 14 GB, 消费级 GPU 装不下
- 量化 (INT4) 可以省 4 倍, 但质量可能下降
- 剪枝 + 量化结合, 既省显存, 又保质量

**解决思路**:
- LLM 大量权重"不重要" (接近 0)
- 移除这些, 模型大小减少, 推理加速
- 关键: 用合理标准判断"哪些权重重要"

---

## 3. 这么做的原因 (3 大方案对比)

| 方案 | 描述 | 压缩比 | 加速比 | 难度 |
|---|---|---|---|---|
| **Wanda** (非结构化) | 按 \|权重 × \|激活\| 排序剪枝 | 50% | ❌ (稀疏) | 中 |
| **SparseGPT** | 一次性 GPT 大剪枝 (类似 GPTQ) | 50-60% | ❌ | 中 |
| **结构化剪枝** | 整层/整头/整神经元剪 | 20-30% | ✅ (硬件友好) | 易 |
| **2:4 稀疏** | 4 个权重中保留 2 个 | 50% | ✅ (A100 加速) | 易 |
| **LLM-Pruner** | 重要性评分 + 全局剪枝 | 20% | 中 | 中 |

**为什么 Wanda 流行?**
- 不需要训练 (剪枝前模型)
- 评估标准简单: 重要性 = |权重| × |激活|
- 一次性剪枝, 几小时完成
- 50% 剪枝率下, 质量几乎不掉

**为什么 LLM 很少用结构化剪枝?**
- LLM 每层都有用, 删一层会大幅掉点
- 删神经元 / 头也类似
- 不结构化剪枝能保留每层, 效果更好

---

## 4. 解决了什么问题

- **显存**: 50% 剪枝 + 4bit 量化 = 12 倍减少 (7B → ~1.5GB)
- **推理**: 稀疏计算 (理论上) 加速
- **保留质量**: 合理剪枝 < 1% 性能损失

---

## 5. 意义

- 2023+ LLM 部署的"标配"之一
- 与量化结合, 极致压缩

---

## 6. 公式表达

```text
Wanda (按重要性剪枝):
  score_ij = |W_ij| · ||X_j||_2   # 第 i 行第 j 列的权重 × 该列输入的 L2 范数
  按 score 排序, 保留 top K, 置 0 其余

  其中 X 是输入激活的统计 (校准数据集)

结构化剪枝 (剪整个注意力头):
  score_head = ||W_head||_F  # 头的 Frobenius 范数
  按 head score 排序, 移除 score 最低的几个头

SparseGPT (类似 GPTQ):
  1. 逐列处理
  2. 用 Hessian 决定哪些权重重要
  3. 一次性剪枝 + 量化
```

```python
def wanda_importance(W, X_calib):
```

## 9. 答案

### 答案 1: 3 大方案对比

| 方案 | Wanda | SparseGPT | 结构化 |
|---|---|---|---|
| 粒度 | 单个权重 | 单个权重 | 整头/层 |
| 评估标准 | $\vert W \vert \cdot \vert X \vert$ | Hessian | 头范数 |
| 压缩比 | 50% | 50-60% | 20-30% |
| 推理加速 | ❌ (稀疏难加速) | ❌ | ✅ (硬件友好) |
| 实施难度 | 易 | 中 | 易 |
| 适用 | LLM 通用 | LLM 通用 | 端侧部署 |

### 答案 2: Wanda 重要性

```python
def wanda_importance(W, X_calib):
    """
    Wanda 重要性: score_ij = |W_ij| · ||X_j||_2

    W: (out_dim, in_dim)
    X_calib: (n_calib, in_dim)
    """
    col_norms = np.linalg.norm(X_calib, axis=0)  # (in_dim,)
    return np.abs(W) * col_norms
```

**核心思想**:
- |W|: 权重本身大, 重要
- |X|: 激活值大, 这个权重经常被"激活", 重要
- 乘积: 两者都大才重要

### 答案 3: Wanda 剪枝

```python
def wanda_prune(W, X_calib, sparsity=0.5):
    """
    Wanda 剪枝: 保留 top (1 - sparsity) 的权重

    W: (out, in) 权重
    X_calib: (n_calib, in) 校准数据
    sparsity: 剪枝率 (0.5 = 剪掉 50%)
    """
    importance = wanda_importance(W, X_calib)  # (out, in)

    # 每个输出通道 (行) 单独剪枝, 保证每行有相同保留数
    n_keep = int(W.shape[1] * (1 - sparsity))

    # 按行排序
    threshold = np.sort(importance, axis=1)[:, n_keep-1:n_keep]  # 每行阈值
    mask = importance >= threshold  # (out, in)  True = 保留

    return W * mask  # 剪掉的权重置 0
```

### 答案 4: 剪枝后显存

```text

50% Wanda 剪枝:
  - 50% 权重为 0, 但仍用 FP16 存
  - 理论 7 GB, 实际用 sparse storage 更省
+ INT4 量化 (Q4_0 格式):
  - 4 bit/参数 + group scale
  - 7B × 4 bit = 3.5 GB (理论)
  - 实际 ≈ 4 GB
+ 结构化剪枝 (整头 25%):
  - 模型大小进一步减少
  - 推理速度提升 (头数减少)

最终: 7B LLM → 约 4 GB, 可装入 RTX 4090 (24GB) 跑 7B 模型
```

## 深入: 非结构化 vs 结构化剪枝(能不能真加速)

| 类型 | 剪什么 | 稀疏度 | 实际加速? |
| :--- | :--- | :--- | :--- |
| **非结构化** | 单个权重置 0 | 高(50%+) | ❌ 普通硬件难加速(不规则) |
| **半结构化(2:4)** | 每4个留2个 | 50% | ✅ Ampere+ 稀疏 Tensor Core 加速 |
| **结构化** | 整通道/整头/整层 | 低 | ✅ 直接变小、真加速 |

> 关键陷阱:**非结构化剪枝省的是"理论 FLOPs"**,但不规则稀疏在 GPU 上难加速(需专用稀疏核)。要真加速,用 **2:4 半结构化**(NVIDIA 稀疏张量核支持)或**结构化**(直接删头/删层,模型真变小)。

---

## 深入: 剪枝为什么有效 —— 彩票假设

**彩票假设(Lottery Ticket Hypothesis)**:一个随机初始化的大网络中,存在一个稀疏子网络("中奖彩票"),单独训练也能达到原网络性能。这为剪枝提供了理论直觉——大模型存在大量冗余,存在高质量的稀疏子结构。

- 传统:训练→剪枝→**微调恢复**(迭代)。
- LLM 时代:重训太贵,转向 **one-shot 无需微调**的 Wanda/SparseGPT(用校准数据一次剪好)。

---

## 深入: Wanda vs SparseGPT vs 幅度剪枝

| 方法 | 重要性准则 | 是否需更新权重 |
| :--- | :--- | :--- |
| 幅度剪枝 | $\|W\|$ | 否 |
| **Wanda** | $\|W\|\cdot\|X\|$(权重×激活范数) | 否(极简) |
| **SparseGPT** | Hessian 加权 + 误差补偿 | 是(逐列更新剩余) |

Wanda 的洞察:**权重重要性要结合激活**——一个小权重若总被大激活乘,影响也大。这与量化里 AWQ/SmoothQuant"看激活"的思路一致(见 [9.1 量化](第09章-01-量化.md))。

---

## 深入: 压缩技术的组合与取舍

剪枝、量化、蒸馏可叠加:`结构化剪枝(减层/头)+ INT4量化 + 蒸馏恢复`。但都有代价:
- 剪枝/量化越激进 → 质量掉越多,需微调或蒸馏补偿。
- **优先级**:通常先量化(性价比最高、质量损失小),剪枝作为补充,蒸馏用于恢复。

## 5. 结构化剪枝算法

### 5.1 为什么需要"真"结构化

非结构化剪枝 (Wanda / SparseGPT) 把单个权重置 0,理论 FLOPs 下降,但**模型 shape 不变**,显存不变,普通 GPU (cuBLAS / cuDNN) 也跑不出加速。要真正得到一个**更小、更快**的稠密模型,必须做**结构化剪枝**:整层 / 整头 / 整神经元 / 整通道地删。

结构化剪枝的 4 类粒度,从粗到细:

| 粒度 | 删什么 | LLM 典型压缩比 | 推理加速 | 适用场景 |
|---|---|---|---|---|
| **层剪枝 (Layer pruning)** | 整个 Transformer block | 10-25% (删 2-6/32 层) | ✅ 直接 | 端侧 / 嵌入式 |
| **注意力头剪枝 (Head pruning)** | Multi-Head Attn 中的某个 head | 10-25% | ✅ 直接 | 推理加速 |
| **FFN 神经元剪枝 (Neuron pruning)** | FFN 中间维度的某个神经元 | 20-40% | ✅ 直接 | 模型瘦身 |
| **隐藏维度剪枝 (Hidden dim pruning)** | 整个 hidden_dim 维度 | 10-30% | ✅ 直接 | 统一缩 |
| **通道剪枝 (Channel pruning)** | 输入/输出通道 | Conv 常见 | ✅ 直接 | 视觉模型 |

LLM 因为**每层都很重要**(任一层删除都会掉点 5-15%),实际工程里**层剪枝压缩比极低**;主流做法是**头剪枝 + 神经元剪枝组合**,把 7B 砍到 6B 左右,再叠加量化。

### 5.2 层剪枝 (Layer Pruning)

**核心思路**:Transformer 的某些层是"冗余"的,删除后影响小。

**重要性评分**:
```text
score_l = ||X_l - X_{l+1}||_2 / ||X_l||_2   # 第 l 层输出变化幅度
# 变化越小 → 该层越冗余 → 可删
```

或 **Block Importance (BI)** (Lagunas et al. 2021):
```text
BI_l = E[||h_{l+1} - h_l||^2]    # h 是 token 表示
```

**实现**:
```python
import torch
import numpy as np

def layer_importance(model, calib_loader, device='cuda'):
    """
    计算每层 BI (Block Importance)
    返回: (n_layers,) 的重要性分数,越大越重要
    """
    n_layers = len(model.layers)  # 假设 model 是 Decoder-only
    importance = torch.zeros(n_layers, device=device)
    handles = []

    # 在每层输出后插入 hook
    layer_outputs = {}
    def make_hook(idx):
        def hook(module, inp, out):
            layer_outputs[idx] = out.detach()
        return hook

    for idx, layer in enumerate(model.layers):
        h = layer.register_forward_hook(make_hook(idx))
        handles.append(h)

    n_samples = 0
    with torch.no_grad():
        for batch in calib_loader:
            input_ids = batch['input_ids'].to(device)
            _ = model(input_ids)

            # 相邻层输出差的 L2 范数
            for i in range(n_layers - 1):
                diff = layer_outputs[i+1].float() - layer_outputs[i].float()
                importance[i] += diff.norm(dim=-1).mean()

            n_samples += input_ids.size(0)
            layer_outputs.clear()

    for h in handles:
        h.remove()

    return (importance / n_samples).cpu().numpy()


def prune_layers(model, importance, target_prune_ratio=0.2):
    """
    按 BI 排序,删掉最不重要的层
    target_prune_ratio: 剪掉 20% 的层 (7B 32 层 → 剪 6 层)
    """
    n_layers = len(model.layers)
    n_prune = int(n_layers * target_prune_ratio)
    # 排序后剪掉最后 n_prune 个 (BI 最小)
    sorted_idx = np.argsort(importance)
    prune_idx = set(sorted_idx[:n_prune].tolist())
    print(f'[Layer Prune] 剪掉层: {sorted(prune_idx)}')

    # 方法 1: 物理删除 (难,改 forward)
    # 方法 2: 用 mask 跳过 (推荐)
    model._prune_layer_mask = torch.ones(n_layers)
    for i in prune_idx:
        model._prune_layer_mask[i] = 0
    return model
```

**陷阱**:
- LLaMA-7B 32 层,**最多剪 4-6 层** (12-19%),再多就崩。
- 剪掉的层要**均匀分布** (前/中/后都剪),不能全剪后面。
- 剪完**必须做轻量微调** (几百步 LoRA),否则困惑度飙升。

### 5.3 注意力头剪枝 (Head Pruning)

**核心思路**:Multi-Head Attention 有 32-64 个 head,某些 head 实际贡献很小,可以整 head 删。

**重要性评分**:
```text
score_h = ||A_h||_1        # 第 h 个 head 的注意力输出 L1 范数
# 范数小 → head 输出弱 → 可删
```

或 **Head Importance (Michel et al. 2019)**:
```text
IH_h = E_x [||attn_h(x)||_1] / E_x [||attn(x)||_1]
```

**实现**:
```python
def head_importance(model, calib_loader, device='cuda'):
    """
    累计每个 head 的平均 attention 输出范数
    """
    n_layers = len(model.layers)
    n_heads = model.config.num_attention_heads
    head_imp = torch.zeros(n_layers, n_heads, device=device)
    n_tokens = 0

    handles = []
    head_outputs = {}

    def make_hook(layer_idx, head_idx):
        def hook(module, inp, out):
            # out: (B, T, hidden), split per head
            B, T, H = out.shape
            head_dim = H // n_heads
            out_h = out.view(B, T, n_heads, head_dim)
            head_outputs[(layer_idx, head_idx)] = out_h[:, :, head_idx].norm(dim=-1).sum()
        return hook

    # 注册 hook
    for li, layer in enumerate(model.layers):
        for hi in range(n_heads):
            h = layer.self_attn.o_proj.register_forward_hook(
                make_hook(li, hi)
            )
            handles.append(h)

    with torch.no_grad():
        for batch in calib_loader:
            input_ids = batch['input_ids'].to(device)
            _ = model(input_ids)
            for (li, hi), v in head_outputs.items():
                head_imp[li, hi] += v
            n_tokens += batch['input_ids'].numel()
            head_outputs.clear()

    for h in handles:
        h.remove()

    return (head_imp / n_tokens).cpu().numpy()


def prune_heads(model, importance, target_prune_heads=64):
    """
    在 32 层 × 32 head 里剪 64 个
    """
    flat = importance.flatten()
    sorted_idx = np.argsort(flat)
    prune_idx = sorted_idx[:target_prune_heads]
    n_heads = model.config.num_attention_heads

    prune_mask = {}
    for idx in prune_idx:
        layer_idx = idx // n_heads
        head_idx = idx % n_heads
        prune_mask.setdefault(layer_idx, []).append(head_idx)
    return prune_mask  # {layer_idx: [head_idx, ...]}
```

**陷阱**:
- LLaMA-7B 32 层 × 32 head = 1024 个,**最多剪 64-128 个** (~10%)。
- 剪 head 后 hidden_dim 必须调整,或**重新分配 head_dim** (不推荐)。
- 头剪枝后,如果只剪 head 不调 head_dim,实际**模型 size 几乎不变**——只是 attention 计算少了一点。要真省显存,需配合隐藏维度剪枝。

### 5.4 FFN 神经元剪枝 (Neuron Pruning)

FFN 中间维度 (intermediate_size) 通常是 hidden 的 4 倍 (LLaMA-7B: 11008 vs 4096),是**模型体积的最大头**。剪 FFN 神经元最划算。

**重要性评分**:
```text
# 看 FFN 中间维度每个神经元被激活的频率
score_n = E_x [|act_n(x)|] / E_x [||act(x)||]
# 激活小 → 神经元对输出贡献小 → 可删
```

或直接利用 **activation frequency**:
```text
# 统计每个神经元的 ReLU/SiLU 后激活值,接近 0 的死神经元直接删
```

**实现**:
```python
def ffn_neuron_importance(model, calib_loader, device='cuda'):
    """
    收集每个 FFN gate_proj 输出维度的重要性
    LLaMA 使用 SwiGLU: out = down(silu(gate(x)) * up(x))
    看 gate_proj 输出后激活值的大小
    """
    n_layers = len(model.layers)
    inter_size = model.config.intermediate_size
    neuron_imp = torch.zeros(n_layers, inter_size, device=device)
    n_tokens = 0

    handles = []
    def make_hook(li):
        def hook(module, inp, out):
            # out: (B, T, inter_size), 每个维度 = 一个神经元
            neuron_imp[li] += out.abs().sum(dim=(0, 1))
        return hook

    for li, layer in enumerate(model.layers):
        h = layer.mlp.gate_proj.register_forward_hook(make_hook(li))
        handles.append(h)

    with torch.no_grad():
        for batch in calib_loader:
            _ = model(batch['input_ids'].to(device))
            n_tokens += batch['input_ids'].numel()

    for h in handles: h.remove()
    return (neuron_imp / n_tokens).cpu().numpy()


def prune_ffn_neurons(model, importance, target_ratio=0.3):
    """
    剪 30% FFN 神经元 (11008 → 7705)
    实现: 把每个 layer.mlp 替换成新维度
    """
    n_layers, inter_size = importance.shape
    n_keep = int(inter_size * (1 - target_ratio))

    for li in range(n_layers):
        imp = importance[li]
        sorted_idx = np.argsort(imp)
        keep_idx = sorted_idx[-n_keep:]  # 保留 top-n_keep

        # 实际修改模型: 重新索引 weight
        layer = model.layers[li].mlp
        old_inter = inter_size
        new_inter = n_keep

        layer.gate_proj.weight = nn.Parameter(
            layer.gate_proj.weight[keep_idx].clone()
        )
        layer.up_proj.weight = nn.Parameter(
            layer.up_proj.weight[keep_idx].clone()
        )
        layer.down_proj.weight = nn.Parameter(
            layer.down_proj.weight[:, keep_idx].clone()
        )

        # bias if exists
        if layer.gate_proj.bias is not None:
            layer.gate_proj.bias = nn.Parameter(
                layer.gate_proj.bias[keep_idx].clone()
            )
```

**为什么 FFN 剪枝最划算**:
- 中间维度通常 = 4 × hidden,占模型参数大头。
- LLaMA-7B: hidden=4096, inter=11008, FFN 占 60%+。
- 剪 30% FFN ≈ 模型大小 -18%。
- 配合 hidden_dim 统一缩,可以直接用 8-bit / 4-bit 量化。

### 5.5 隐藏维度剪枝 (Hidden Dim Pruning)

**核心思路**:同时缩 hidden 和 FFN 中间维度。

```text
原始: hidden=4096, inter=11008
剪后: hidden=3072 (75%), inter=8192 (75%)
```

**LLM-Pruner (Ma et al. 2023)** 的做法:
1. 计算每层的 importance (类似 BI)
2. 按 importance 排序,选最重要的维度保留
3. 全局重映射 + LoRA 微调恢复

**实现概览** (集成 LLM-Pruner):
```python
# LLM-Pruner 官方代码
# https://github.com/horse-x/LLM-Pruner

import llm_pruner as lp

pruned_model = lp.prune(
    model,
    importance_cache=importance_dict,
    pruning_ratio=0.2,  # 剪 20%
    recover_files='./recover_data',
)
```

### 5.6 通道剪枝 (Channel Pruning, 视觉模型常用)

CV 模型 (ResNet / ViT) 里常用,**沿输入/输出通道整维剪**:

```text
重要性: ||W_c||_F    # 第 c 个输出通道的 Frobenius 范数
```

**实现** (Torch 内置):
```python
import torch.nn.utils.prune as prune

# L1 unstructured → 转 structured
module = model.layer[0].conv1
prune.ln_structured(module, name='weight', amount=0.3, dim=0, n=1)
# dim=0 表示剪 output channel, n=1 表示 L1-norm
```

**陷阱**:
- ViT 通道剪枝要**全局等比例剪** (每层剪 20%),否则某层剪太多会崩。
- 剪完要 finetune 数小时才能恢复精度。

### 5.7 结构化剪枝统一流程

**标准 5 步**:
1. **重要性评估**: 用校准数据 (1k 条文本) 跑一遍,收集每层/头/神经元的 importance。
2. **全局排序**: 把所有可剪单元 importance 排序。
3. **剪枝决策**: 按目标压缩比,选保留的单元。
4. **物理修改**: 重新索引 weight, 修改 layer shape。
5. **轻量微调**: LoRA / 全量 finetune (几百步到几千步),恢复质量。

**代价**:
- LLM 7B 剪 20% (LLM-Pruner): 重要 30 min (评估) + 1h 微调 (8×A100)
- LLM 7B 剪 50% (激进): 必崩 + 需大量数据恢复

### 5.8 小结: 结构化 vs 非结构化

| 维度 | 结构化 | 非结构化 (Wanda) |
|---|---|---|
| 推理加速 | ✅ 硬件友好 | ❌ 需稀疏库 |
| 显存省 | ✅ 模型真变小 | ❌ shape 不变 (除非用 sparse storage) |
| 压缩比 | 10-30% | 50% |
| 质量损失 | 中 (需微调) | 小 (无需微调) |
| 实施难度 | 中 (需微调) | 易 (一次性) |
| 适用 | 端侧部署 + 极致压缩 | LLM 通用 + 配合量化 |

**实战组合**: Wanda 50% 剪枝 (省 50% weight) **不一定真省显存**;LLM-Pruner 20% 结构化剪枝 **模型真小 20%**。两者结合可以做到**真省 + 加速**。

## 6. Wanda / SparseGPT 详解

### 6.1 Wanda 原理再深入

**论文**: *Pruning by Weights and activations* (Sun et al., ICML 2023)

**问题**: 传统幅度剪枝只看 |W| 不看激活,导致:
- 大权重但激活小 → 实际贡献小,被错误保留
- 小权重但激活大 → 实际贡献大,被错误剪掉

**洞察**: 权重重要性应该结合**激活幅度**:
```text
S_ij = |W_ij| · ||X_j||_2
# X_j: 第 j 个输入特征在所有校准样本上的 L2 范数
```

**为什么是 L2 范数**:
- L2 是输入分布的二阶矩,稳定
- L1 易被 outlier 主导
- L∞ 退化成"看最大值",信息少

**校准过程**:
1. 收集 32-256 条校准文本 (C4 / WikiText 即可)
2. 每层前向,记录输入 X ∈ ℝ^{N × d_in}
3. 计算 ||X_j||_2 = √(Σ x_ij²),得到 d_in 维向量
4. **逐行 (output channel) 剪枝**: 对每个输出通道 i,按 S_ij 排序,保留 top-k

**为什么逐行不逐列**:
- 保持每行有相同保留数 → 输出分布不偏
- 比整层排序更稳定
- 实验证明 perplexity 更优

**实现** (完整版):
```python
import torch
import numpy as np

@torch.no_grad()
def wanda_prune_full(model, calib_data, sparsity=0.5, device='cuda'):
    """
    完整 Wanda 流程
    model: nn.Module, Linear 层会被剪
    calib_data: List[Tensor], 每条 (1, seq_len)
    sparsity: 0.5 表示剪掉 50%
    """
    model.eval()
    use_cache = False

    # ============= 1. 注册 hook 收集每一层的输入 =============
    linear_inputs = {}
    hooks = []

    def make_hook(name):
        def hook(module, inp, out):
            # inp: tuple, inp[0]: (B, T, d_in)
            x = inp[0].detach()
            x = x.reshape(-1, x.shape[-1])  # (B*T, d_in)
            if name not in linear_inputs:
                linear_inputs[name] = []
            linear_inputs[name].append(x.cpu())
        return hook

    for name, module in model.named_modules():
        if isinstance(module, torch.nn.Linear):
            hooks.append(module.register_forward_hook(make_hook(name)))

    # ============= 2. 前向校准 =============
    for batch in calib_data:
        batch = batch.to(device)
        try:
            model(batch, use_cache=False)
        except TypeError:
            model(batch)

    for h in hooks: h.remove()

    # ============= 3. 合并输入 → 计算 col_norms → 剪枝 =============
    for name, module in model.named_modules():
        if not isinstance(module, torch.nn.Linear): continue
        if name not in linear_inputs: continue

        # 拼所有校准激活
        X = torch.cat(linear_inputs[name], dim=0)  # (ΣB*T, d_in)
        col_norms = X.norm(p=2, dim=0)  # (d_in,)

        # 权重
        W = module.weight.data  # (d_out, d_in)

        # 重要性 = |W| × col_norms
        importance = (W.abs() * col_norms.to(device))

        # 逐行剪枝: 每行保留 top-k
        d_out, d_in = W.shape
        n_keep = int(d_in * (1 - sparsity))

        # 排序 (沿 d_in 维度)
        threshold = importance.kthvalue(d_in - n_keep + 1, dim=1).values  # 每行阈值
        mask = importance >= threshold.unsqueeze(1)  # (d_out, d_in)

        # 应用 mask
        module.weight.data *= mask.to(device)

    return model
```

**关键细节**:
- `kthvalue`: 取每行第 k 大的值,做阈值。`>= threshold` 保留。
- col_norms 必须算在 CPU 内存上 (校准数据大,容易爆显存)。
- bias 不剪 (剪 bias 会改变输出分布)。

**超参**:
- **sparsity 0.5** 是个稳的点,**Wanda 论文**显示 50% 几乎不掉点 (LLaMA-7B perplexity 5.68 → 6.66)。
- **校准数据量**: 32-256 条文本,**太长反而过拟合**校准分布。
- **校准数据选择**: C4 / Wikipedia / 领域数据;多样性优先。

**陷阱**:
- **不做任何微调**就能用,但某些下游任务 (MMLU/HumanEval) 掉点 ~5%。
- **embedding 层和 lm_head 不剪** (剪了就崩)。
- **LayerNorm 不剪** (虽然不是 Linear)。

### 6.2 SparseGPT 原理

**论文**: *SparseGPT: Massive Language Models Can be Accurately Pruned in One-Shot* (Frantar & Alistarh, ICML 2023)

**和 Wanda 关键差异**:
| | Wanda | SparseGPT |
|---|---|---|
| 重要性准则 | \|W\| × \|X\| | **Hessian 加权** |
| 是否更新剩余权重 | ❌ | ✅ 逐列更新,补偿剪枝误差 |
| 适用矩阵 | Linear | **整个 Linear 权重矩阵** |
| 时间复杂度 | O(d² × n_calib) | O(d³) 但**常数小** |
| 质量 | 中 | **优** |

**核心: 贪心列剪枝 + 误差补偿**

数学推导 (简版):
```text
目标: 在 W 上做 50% 剪枝,最小化 ||WX - ŴX||² (输出变化最小)
     等价于 ||(W - Ŵ)X||² 最小

令 H = XX^T (Hessian, d×d, 计算量来自校准激活)
问题化为:
   min_{Ŵ 稀疏} ||(W - Ŵ)X||²
   = min_{Ŵ} ||Ŵ - W||²_Σ
   其中 ||A||²_Σ = trace(A · H · A^T)  (Σ-weighted norm)
```

**算法**:Adaptive Mask Selection + Cholesky 分解。
1. 计算 Hessian H = 2·X_calib · X_calib^T (d × d),Cholesky 分解得 L (下三角)。
2. 逐列处理 (j = d-1, d-2, ..., 0):
   - 计算 w_j 列的重要性 = |w_j| / [L^{-1}]_{jj}
   - 如果不保留 (剪),把 w_j 设为 0
   - 更新剩余列补偿误差:**w_{:, :j} -= w_j · L^{-1}[:, j] / L^{-1}[j, j]** (关键:Cholesky 更新)
3. 输出压缩后的权重 W_new。

**伪代码**:
```text
input: W (m × d), H = 2·X^T·X (d × d), sparsity s
output: W_new (剪枝+误差补偿)

L = Cholesky(H)                    # d × d,下三角
for j in reversed(range(d)):
    if j ∉ columns_to_keep:        # mask: 第 j 列是否保留
        w_j = 0
    else:
        # 计算重要性
        importance_j = |w_j| / diag(L^{-1})[j]

        # 更新剩余列 (用 Cholesky L,避免 O(d^3) 求逆)
        u = L^{-1}[:, j] / L^{-1}[j, j]   # d 维
        w_remaining = w_remaining - w_j · u[剩]

# 简化版实现
```

**完整 PyTorch 实现** (~120 行):
```python
import torch
import math

def sparsegpt_prune(model, calib_data, sparsity=0.5, device='cuda'):
    """
    SparseGPT 单层剪枝 (扩展到多层循环)
    """
    for name, layer in model.named_modules():
        if not isinstance(layer, torch.nn.Linear):
            continue

        W = layer.weight.data.float()  # (out, in)
        d_out, d_in = W.shape

        # 1. 收集校准输入 → 计算 Hessian
        inputs = collect_layer_inputs(model, layer, calib_data)  # (N, d_in)
        H = 2 * inputs.t().float() @ inputs.float()  # (d_in, d_in)
        H.diagonal().add_(1e-6)  # 防数值奇异

        # 2. Cholesky 分解
        try:
            L = torch.linalg.cholesky(H)
        except:
            # 失败时退到对角近似
            L = torch.diag(H.diagonal().sqrt())

        # 3. 逐列剪枝
        L_inv = torch.linalg.solve_triangular(
            L, torch.eye(d_in, device=device), upper=False
        )  # 即 L^{-1}

        W_new = W.clone()
        cols_to_prune = int(d_in * sparsity)

        # 简单版本: 按重要性剪 (不严格符合 SparseGPT 的 mask 自适应)
        importance = W.abs() / L_inv.diagonal().unsqueeze(0)  # (out, in)
        threshold = importance.kthvalue(d_in - (d_in - cols_to_prune) + 1, dim=1).values

        mask = importance >= threshold.unsqueeze(1)
        W_new *= mask.float()

        # 误差补偿: 用 mask 后的 W 更新 W
        # 实际实现需要逐列迭代,这里是简化版
        Err = (W - W_new) @ inputs.t() @ torch.linalg.solve(
            H, torch.eye(d_in, device=device)
        )
        W_new = W_new + W @ Err

        layer.weight.data = W_new.to(layer.weight.dtype)

    return model
```

**优缺点**:
- ✅ 一次性剪枝 + 误差补偿,**质量比 Wanda 好 5-15%**
- ❌ **慢**: LLaMA-7B 全模型剪一遍要 1-3 小时 (单 A100)
- ❌ Cholesky 在 d 大时显存吃紧 (4096 → 4096×4096 = 64MB 一层)

**工程技巧**:
- **Hessian 计算分块**: 不要一次性算所有校准数据,分批累加,防爆显存。
- **bias 修正**: SparseGPT 处理 weight,bias 要单独处理 (一般不动)。
- **AMP**: 用 FP16/BF16 跑前向,FP32 算 Hessian (精度优先)。

### 6.3 Wanda vs SparseGPT 实战对比

**实验 (LLaMA-7B, WikiText perplexity)**:
| 方法 | sparsity | Perplexity | 耗时 (1×A100) |
|---|---|---|---|
| 原始 | 0% | 5.68 | - |
| Magnitude (幅度) | 50% | 20.5 | 5 min |
| Wanda | 50% | 6.66 | 15 min |
| SparseGPT | 50% | **6.21** | 2.5 h |
| SparseGPT + recovery LoRA | 50% | 5.92 | 3 h |

**结论**:
- Wanda 是**性价比之王**: 15 分钟,质量可接受。
- SparseGPT 是**精度之王**: 但慢 10×。
- 工业部署多选 **Wanda + 轻量 LoRA** (半小时搞定)。

### 6.4 RIA / OWL 等进阶方法

**RIA (Reweighted Importance and Activation)**:
- 在 Wanda 基础上,对重要性分数做**再加权**,适应非均匀分布。
- 比 Wanda 略好,但慢 2×。

**OWL (Outlier Weighed Layerwise)**:
- 识别 LLM 里的 outlier 维度 (某些激活维度特别大)。
- 剪枝时**保护 outlier 维度**,只剪正常维度。
- 适合有强 outlier 的模型 (如 LLaMA-2 / Mistral)。

## 7. 动静结合剪枝

### 7.1 静态剪枝 (Static Pruning)

**定义**: 训练 / 剪完之后,被剪掉的权重**永久 0**,推理时不动。

```text
训练 / 剪枝:  W → W_pruned (50% 是 0)
推理:        f(x; W_pruned)  永远是稀疏的
```

**Wanda / SparseGPT / LLM-Pruner 全是静态剪枝。**

### 7.2 动态剪枝 (Dynamic Pruning)

**定义**: 推理时**根据输入动态决定**哪些权重参与计算。

```text
input x → 决定 mask m(x) → 计算 y = f(x; W ⊙ m(x))
```

**典型场景**:
- **Token-level 剪枝**: 不同 token 重要性不同,只算 top-k 重要 token 的 attention。
- **Expert-level 剪枝** (MoE): 每个 token 选 top-k expert,其他 expert 不算。
- **Layer-skip 动态**: 简单样本跳过某些层 (LayerSkip / CALM)。

### 7.3 静态 + 动态混合

**LayerSkip** (Elhoushi et al. 2024):
- **训练时**: 训练模型**主动跳过**部分层 (类似 dropout,但跳层)。
- **推理时**: 简单样本 early-exit,跳 5-10 层;复杂样本跑全 32 层。

```python
# LayerSkip 推理示意
def layered_inference(x, model, exit_threshold=0.95):
    hidden = model.embed(x)
    for i, layer in enumerate(model.layers):
        hidden = layer(hidden)
        if i < model.config.num_layers - 2:  # 最后 2 层不跳
            # 简单置信度判断
            logits = model.lm_head(model.norm(hidden[:, -1]))
            conf = logits.softmax(-1).max().item()
            if conf > exit_threshold:
                return logits
    return model.lm_head(model.norm(hidden[:, -1]))
```

**CALM** (早退):
- 每层后接一个 classifier,置信度高就 early-exit。
- 平均加速 1.5-3×。

### 7.4 Token-level 动态剪枝 (Sparse Attention)

**SparseAttention / Scissorhands**:
- 不用 dense attention,**只算 top-k 重要 token 的 attention**。
- 实现: 用预算路由选 top-k 个 KV cache 位置。

```python
def sparse_attention(Q, K, V, budget=128):
    """
    只算 budget 个最重要的 KV
    """
    # 估算每个 KV 的重要性 (用 QK 乘积近似)
    importance = Q @ K.t()  # (T_q, T_k)
    topk = importance.topk(budget, dim=-1).indices  # (T_q, budget)

    # 只算 topk 的 attention
    out = torch.zeros_like(Q)
    for q_idx in range(Q.size(0)):
        k_idx = topk[q_idx]
        out[q_idx] = F.scaled_dot_product_attention(
            Q[q_idx:q_idx+1], K[k_idx], V[k_idx]
        )
    return out
```

**挑战**:
- **不规则访存**: GPU 难加速。
- **预训练**: 模型没"见过"稀疏 attention,要做**继续训练**(几百步)让模型适应。
- **StreamingLLM**: 选 KV cache 子集,适合超长上下文。

### 7.5 MoE + 动态剪枝

**Mixture of Experts** 天然动态:
- 每层有 8-64 个 FFN (expert)。
- 路由选 top-2 expert,**其他 expert 不算**。
- **总 FLOPs**: 假设 dense 1×,MoE 是 0.5-1×,但**总参数大** (8 expert × 1)。

**Mixtral 8×7B**:
- 总参 47B,激活 ~13B (per token)。
- 推理速度 = 13B dense 模型。
- 显存 = 47B (全加载)。

### 7.6 动态剪枝的统一视角

**核心 trade-off**:
```text
静态: 省不规则访存开销,但被剪的权重"彻底浪费"
动态: 充分利用权重,但每步要算 mask,有开销
```

**LLM 上动态剪枝的困境**:
- LLM 推理主流是**批量 + 流式**,每 token 计算量小,动态开销占比大。
- 工程上**静态 + 量化** 仍然是最优解。
- 动态剪枝主要在**边缘 / 移动端 + 长上下文**有戏。

### 7.7 混合方案的工业落地

**典型组合**:
```text
Wanda 50% 静态剪枝  +  量化 (INT4)  +  Dynamic early-exit (CALM)
=  显存省 4× + 推理加速 1.5-2×
```

**示例**: Llama-2-7B 部署:
| 步骤 | 显存 | 速度 |
|---|---|---|
| 原始 FP16 | 14 GB | 1× |
| + Wanda 50% (稀疏存储) | 7 GB | 1× (没真加速) |
| + INT4 量化 | 4 GB | 1× |
| + Dynamic KV prune | 4 GB | 1.3× |
| + Early-exit (CALM) | 4 GB | 1.7× |

```python
    model,
    sparsity=0.5,
    method='wanda',
    calib_dataset='c4',
    n_calib_samples=128,
)

quantize(
    model,
    format='int4',
    scheme='gptq',  # 或 'awq'
)
```

### 8.5 常见生产问题

**问题 1: 剪枝后下游任务掉点**
- 现象: 通用 MMLU 几乎不掉,但**特定领域任务** (金融 / 医疗) 大幅掉。
- 解决: **领域数据** 微调 (LoRA) 几百步,即可恢复。

**问题 2: 推理速度没提升**
- 现象: Wanda 50% 剪完,LLM 速度没变。
- 原因: GPU dense 计算,**稀疏反而慢了** (不规则访存)。
- 解决: 配合 **GPTQ 量化**让 weight 变小,或上 **DeepSparse**。

**问题 3: 显存没省**
- 现象: 剪 50% 后显存几乎不变。
- 原因: PyTorch 默认 dense 存储,0 也占位。
- 解决: 用 **bnb 稀疏存储** 或 **SparseTensor** (PyTorch 2.1+)。

**问题 4: 长文本掉点**
- 现象: short context 几乎不掉,long context (>4k) 掉点严重。
- 原因: 剪枝没考虑**注意力分布**。
- 解决: **SparseGPT** (用 Hessian) 比 Wanda 更适合长上下文。

- **AWQ 比 GPTQ + Wanda 略好**: AWQ 自带剪枝和 outlier 保护。

## 9. 性能 vs 精度权衡

### 9.1 理论加速 vs 实际加速

**理论 FLOPs 下降 ≠ 实际加速**:
- 50% Wanda 剪枝,理论 FLOPs -50%。
- **实际**: GPU dense kernel 跑,**速度不变甚至变慢** (-5%~0%)。
- 唯一例外: **2:4 半结构化稀疏 + NVIDIA Ampere 稀疏 Tensor Core**,真加速 1.5-2×。

**为什么**:
- GPU 计算单元 (Tensor Core) 按 tile (16×16 或 8×32) 算。
- 稀疏矩阵填充不齐 → tile 内无效计算 → 没加速。
- 还要付**索引 / mask** 开销,反而变慢。

### 9.2 加速的真实场景

**稀疏真加速 (需要硬件支持)**:

| 硬件 | 稀疏模式 | 加速比 |
|---|---|---|
| NVIDIA A100 / H100 | 2:4 稀疏 (Sparse Tensor Core) | 1.5-2× |
| NVIDIA A100 | 4:8 稀疏 (extended) | 1.3-1.7× |
| Qualcomm Hexagon | NPU 稀疏 | 2-4× |
| Apple ANE | 4-bit + 稀疏 | 1.5× |

**LLM 用稀疏加速**:
- 必须**重新训练**让权重按 2:4 模式排列 → 不简单。
- 训练成本 = 原训练 30-50%。
- 工业实践: 很少用,**量化更划算**。

### 9.3 精度损失的边界

**剪枝率 vs 困惑度 (LLaMA-7B, WikiText)**:
```text
sparsity = 0%   →  perplexity 5.68
sparsity = 20%  →  perplexity 5.85
sparsity = 40%  →  perplexity 6.30
sparsity = 50%  →  perplexity 6.66  (Wanda)
sparsity = 60%  →  perplexity 8.5   (质量明显掉)
sparsity = 70%  →  perplexity 25+   (基本废了)
```

**关键阈值**:
- **≤ 40%**: 几乎无损。
- **40-60%**: 轻度损失,可接受。
- **60-70%**: 严重掉点,要微调。
- **> 70%**: 必崩,基本需要重训。

### 9.4 下游任务的精度损失

**通用 perplexity 和下游任务不直接挂钩**:
- 困惑度 (perplexity) 衡量语言建模能力。
- **下游任务** (MMLU, HumanEval, GSM8K) 敏感度不同。

**经验**:
- **MMLU** (多任务): 50% Wanda 掉 1-3 个百分点。
- **HumanEval** (代码): 50% Wanda 掉 5-10 个百分点 (代码任务对剪枝敏感)。
- **GSM8K** (数学推理): 掉得最厉害, 5-15 个百分点。

**为什么推理任务敏感**:
- 推理任务依赖**精确的多步计算**, 剪枝破坏"小但关键"的权重。
- 多选题 (MMLU) 主要靠**模式匹配**,容忍度高。

### 9.5 缓解精度损失的 4 个手段

**1. 稀疏微调 (Sparse Fine-tuning)**:
```python
# 剪完后做 LoRA 微调 (PEFT 库)
from peft import LoraConfig, get_peft_model

config = LoraConfig(
    r=8, lora_alpha=16,
    target_modules=['q_proj', 'v_proj'],
    modules_to_save=[],  # 不更新 dense weight
)
model = get_peft_model(model, config)

# 训练 200-1000 步
trainer = Trainer(model=model, ...)
trainer.train()
```

**2. 渐进式剪枝 (Gradual Pruning)**:
- 不一次剪 50%,而是**每训练 1k 步剪 10%**,共 5 次。
- 每次训练恢复一些精度。
- 比一次性剪 50% + 微调**损失小**。

**3. 混合精度 (Mixed Sparsity)**:
- **不重要层剪 70%**,**重要层剪 30%**。
- 按层 importance 分配剪枝率。
- LLM-Pruner 的核心做法。

**4. 敏感度分析 (Sensitivity Analysis)**:
- 逐层做"剪枝 + 验证"。
- 找**剪枝敏感度低**的层,大力剪。
- 找**敏感度高**的层,少剪或不剪。

```python
# 敏感度分析伪代码
for sparsity in [0.1, 0.2, ..., 0.7]:
    for layer_idx in range(n_layers):
        # 只剪这一层
        local_model = copy_model(original)
        only_prune_layer(local_model, layer_idx, sparsity)

        # 验证困惑度变化
        ppl = evaluate_ppl(local_model, calib_data)
        sensitivity[layer_idx].append(ppl)
```

### 9.6 量化 vs 剪枝的精度对比

| 压缩方式 | 显存减少 | 精度影响 | 速度 |
|---|---|---|---|
| FP16 → INT8 (SmoothQuant) | 2× | <1% | +30% |
| FP16 → INT4 (GPTQ) | 4× | 1-3% | +30% |
| Wanda 50% | **无 (dense 存)** | 5-15% | **不变** |
| Wanda 50% + INT4 | 4× | 5-15% | +30% |
| Wanda 70% + INT4 | 5-6× | 10-30% | +30% |

**关键洞察**:
- **量化的"性价比"远高于剪枝**: INT4 省 4× 显存 + 提速 30%, 精度损失极小。
- **剪枝的核心价值**: 配合量化,把模型压到极致 (5-8×)。
- **不结合量化的剪枝**: 工业上几乎没用 (除非需要稀疏加速)。

### 9.7 总体推荐策略

**决策树**:
```text
需要压缩 LLM?
├── 显存不是问题 → 用 FP16/BF16,不剪枝
├── 想省 2× 显存 → SmoothQuant INT8 (无需剪枝)
├── 想省 4× 显存 → GPTQ/AWQ INT4 (无需剪枝)
├── 想省 6× + 极致压缩 → Wanda 50% + INT4 (dense 重排)
├── 想省 6× + 端侧 → LLM-Pruner 20% + INT4 + 蒸馏
└── 极限 1.5GB 部署 → Wanda 50% + INT3 + LLM-Pruner
```

### 9.8 速度-精度曲线 (Pareto Front)

```text
Pareto 最优点:
  - Wanda 50% + INT4  (6× 压缩, 精度中)
  - AWQ INT4           (4× 压缩, 精度高)
  - LLM-Pruner 20% + INT4  (5× 压缩, 精度中)
```

在 A100 / RTX 4090 上,**INT4 + Wanda 50%** 是工业标准的最优点。

## 10. 面试题

### Q1. 非结构化剪枝为什么 GPU 难加速?

**答**:
非结构化剪枝把单个权重置 0,理论 FLOPs 下降,但 GPU 按 tile (16×16 等) 计算,**稀疏不规则** → tile 内有 0 也要算,**无效计算**。还要付**索引开销**(CSR 存储需要查找表)。结果是: **理论 FLOPs 降,实际 wall-clock 不变甚至变慢**。

只有**2:4 半结构化**(每 4 权重保留 2)在 NVIDIA Ampere 的稀疏 Tensor Core 上**真有 1.5-2× 加速**,因为它对齐到硬件。

**根本解决**: 用**结构化剪枝**(整头 / 整通道),模型**真变小**,shape 变小,GPU 自然加速。

### Q2. Wanda 的 |W| × |X| 为什么比纯 |W| 好?

**答**:
- 纯 |W|: 认为**权重大**就重要,忽略激活。
- 但若某权重很大,但对应激活一直很小,**实际贡献小**。
- |W| × |X|: 权重×激活,**只有两者都大**才"重要贡献"。这与**量化里 AWQ / SmoothQuant 看激活**的思路一致。

**数学**: 输出 y_i = Σ_j W_ij · X_j,W_ij × X_j 是对 y_i 的贡献,wanda 把这个乘积作为 importance。

### Q3. 为什么 LLM 难做结构化剪枝?

**答**:
- LLM 每层 (block) 都关键,任一层删除掉点 5-15%。
- 7B 模型 32 层,极限剪 4-6 层 (15-20%),再多就崩。
- 删神经元 / 头相对宽松,但要**重新索引 weight**,实现复杂。
- 真正有效的结构化剪枝压缩比 10-30%,比非结构化的 50% 低很多。

**为什么**: Transformer 每层做一次信息整合,层数不能太短。视觉 ResNet 可以剪 50% layer,因为结构冗余大。

### Q4. SparseGPT vs Wanda 的核心差异?

**答**:
| | Wanda | SparseGPT |
|---|---|---|
| 重要性准则 | \|W\| × \|X\| (局部启发式) | **Hessian 加权** (全局最优) |
| 是否更新剩余权重 | 否 | **是**(逐列 Cholesky 更新) |
| 精度 | 中 | **优** |
| 耗时 | 15 min | 2-3 h |

**核心**: Wanda 是**简单启发式**,SparseGPT 是**基于二阶信息的精确剪枝**(用 Hessian 看到每个权重对输出的全局影响)。SparseGPT 还能**补偿剪枝误差**(用 Cholesky 分解,把被剪掉的列的影响补偿到剩余列)。

### Q5. 什么场景该用哪种剪枝?

**答**:

| 场景 | 推荐 |
|---|---|
| LLM 云端部署 | **AWQ / GPTQ INT4**(不剪枝) |
| 消费级 GPU 跑大模型 | **Wanda 50% + GPTQ INT4** |
| 端侧 / 手机 | **LLM-Pruner 20% + INT4 + 蒸馏** |
| 需要真加速 | **2:4 半结构化**(需重训)或**结构化剪枝** |
| 学术研究 | **Wanda / SparseGPT**(复用性强) |
| 上线生产 | **SparseGPT + 量化 + 微调** |

### Q6. 剪枝、量化、蒸馏的优先级?

**答**:
1. **量化**(性价比最高): INT4 省 4× 显存,精度掉 1-3%。**首选**。
2. **结构化剪枝**(模型真变小): 再省 20-30% 显存,但需微调。
3. **非结构化剪枝**: 主要用于研究 / 配合量化,单独价值小。
4. **蒸馏**: 最贵,但能恢复或超越原模型精度。**质量关键时用**。

**实战组合**: 量化 (优先) → 结构化剪枝 → 蒸馏恢复。

### Q7. 什么是彩票假设? 对 LLM 剪枝有什么指导?

**答**:
**彩票假设** (Frankle & Carlin 2019): 随机初始化的大网络里,存在一个**稀疏子网络**(中奖彩票),**单独从原始初始化训练也能达到大网络的精度**。

**对 LLM 剪枝的指导**:
- 证明了大网络存在**高质量稀疏子结构**,剪枝有效。
- 但 LLM 重新训练成本太高,**不能从随机初始化训练稀疏子网络**。
- 所以 LLM 转向 **one-shot 剪枝** (Wanda / SparseGPT),用校准数据**不训练**直接剪。
- 实际上是**妥协**: 不能严格遵循彩票假设,但用了它的直觉 (大网络含冗余)。

### Q8. 为什么剪枝后要做微调? 什么时候可以不做?

**答**:
- **必须微调**: **结构化剪枝** (>20%)、**非结构化 > 60%**、**下游任务特定领域**。
- **可不做**: **Wanda 50%**(通用任务)、**SmoothQuant INT8** 量化后的精度掉点很小。

**为什么需要微调**: 剪枝改变了权重分布,**模型"忘记"了一些能力**,微调让权重在新稀疏结构下重新对齐到任务。

**微调强度**:
- LoRA 200-1000 步: Wanda 50% 通用任务,够用。
- LoRA 1000-5000 步: 结构化剪枝 20%+,或领域适配。
- 全量 finetune: 极端情况 (>60% 稀疏) 才需要。

### Q9. 解释 Wanda 的逐行剪枝 (per-output pruning)

**答**:
Wanda 不是**整个矩阵**排序剪,而是**逐输出通道**剪:
- 每个 output channel i 独立排序,保留 top-k。
- 这样**每行有相同保留数** → 输出分布不偏。
- 比整层排序 (largest global) 困惑度更优。

**为什么**: 整层排序会让某些输出通道**几乎全剪**而另一些**全留**,输出分布剧烈偏移。逐行保证每行至少保留 n_keep 个,**输出维度分布不变**。

### Q10. 2:4 稀疏怎么训练?

**答**:
**2:4 模式**: 每 4 个连续权重中保留 2 个非零。
- NVIDIA A100 / H100 稀疏 Tensor Core **硬件加速 1.5-2×**。
- 训练通常用 **SR-STE (Sparse-Refined Straight-Through Estimator)** 或 **Mask Gradient**。
- 大致流程:
  1. 训练 dense 模型 (几百到几千步)。
  2. 按 2:4 模式 mask,finetune。
  3. 推理时用 **SparseTensorCore**。

**工程难点**:
- 训练框架支持差 (PyTorch 有限支持)。
- 精度损失 ~1-3%。
- 重训练成本 = 原训练 30-50%。

### Q11. 推理框架如何处理剪枝模型?

**答**:
- **vLLM**: 不支持通用 Wanda 稀疏,只支持 GPTQ/AWQ/INT4/INT8 量化。
- **llama.cpp**: 支持 GGUF,内置 INT4/INT5/INT8 量化,**部分支持稀疏**。
- **DeepSparse** (Neural Magic): **专为稀疏推理**设计,GPU/CPU 都支持。
- **MLX / CoreML** (Apple): 支持 4-bit + 稀疏。

**实战**: 多数工业部署**不用稀疏推理框架**,而是把 Wanda 剪完的模型**重排为 dense + 量化**,然后用通用框架跑。

### Q12. 蒸馏 vs 剪枝的核心区别?

**答**:

| 维度 | 剪枝 | 蒸馏 |
|---|---|---|
| **做什么** | 删冗余权重 | 用小模型学大模型行为 |
| **模型结构** | 同 (或子结构) | **完全不同的新模型** |
| **显存** | 模型变小 | **新模型本身小** |
| **质量上限** | 原模型 (≤100%) | **可超原模型** (用大数据) |
| **成本** | 低 (一次性) | 高 (需训练新模型) |
| **适用** | 显存受限 | 极致压缩 + 质量保持 |

**蒸馏更深**: LLaMA-2-7B → 蒸馏 → LLaMA-2-3B (Zipformer),质量接近 7B,但**结构是新的 3B 模型**。

### Q13. 半结构化 (2:4) 和非结构化 (50%) 的本质区别?

**答**:
- **非结构化 50%**: 任意位置 50% 权重 = 0,**模式不固定**。
  - GPU 难加速 (不规则)。
  - **理论 FLOPs -50%**。
- **半结构化 2:4**: 每 4 个里 2 个 0,**模式固定**。
  - NVIDIA Sparse Tensor Core **真加速 1.5-2×**。
  - 稀疏度**固定 50%** (2/4 = 50%)。

**差异**: 半结构化是**对齐硬件**(模式固定 → SIMD 友好),非结构化是**自由稀疏** → 软件灵活但硬件不友好。

### Q14. 为什么 SmoothQuant 不需要剪枝?

**答**:
SmoothQuant 是**纯量化方案**,核心是把"激活里少数大 outlier"在数学上**等价地迁移到权重里**,然后用 **INT8** (W8A8) 量化,**精度几乎不掉**。

不需要剪枝:
- **量化**: FP16 → INT8 = 2× 压缩,精度 -1%。
- **剪枝**: 不需要,**模型大小不变**。
- **组合**: SmoothQuant + 结构化剪枝 20% = **2.5× 综合压缩**。

### Q15. 一个 7B 模型最终能压到多小? 极限是多少?

**答**:
**LLaMA-7B FP16 = 14 GB**,逐步压缩:

| 步骤 | 显存 | 累计 | 质量 |
|---|---|---|---|
| FP16 原始 | 14 GB | 14 GB | 100% |
| SmoothQuant INT8 | 7 GB | 7 GB | 99% |
| + GPTQ INT4 | 4 GB | 4 GB | 97% |
| + Wanda 50% (dense 重排) | 2 GB | 2 GB | 92% |
| + LLM-Pruner 20% | 1.7 GB | 1.7 GB | 91% |
| + 蒸馏 + INT3 极端 | 1 GB | 1 GB | 88% |

**极限**: 在质量保留 85%+ 下,**7B 可以压到 1-1.5 GB**;继续压 (<1GB) 必崩。

**工程标杆**:
- **MobileLLM** (Apple, 2024): 1B 模型压到 < 1 GB,手机端跑。
- **Phi-3-mini** (Microsoft, 2024): 3.8B 量化到 ~2 GB。

### Q16. 如何评估一个剪枝方法的好坏?

**答**:
**3 个核心指标**:
1. **困惑度 (Perplexity)**: 语言建模能力,WikiText / C4 上测。
2. **下游任务精度**: MMLU、HumanEval、GSM8K、HellaSwag 等 6+ 任务平均。
3. **推理速度 (wall-clock)**: 端到端吞吐量 (tok/s),不是理论 FLOPs。

**次要指标**:
- **延迟**: p99 延迟,生产关键。
- **显存峰值**: 推理时最大 GPU 显存。
- **能耗**: 每 token 的焦耳数。

**工业**: 在**至少 5 个下游任务**上不掉点超过 3%,才是"可用"剪枝方案。

### Q17. 解释 SparseGPT 的 Cholesky 分解为什么快?

**答**:
**问题**: 剪枝时需要解线性方程组 (W - Ŵ) × X ≈ 0,如果朴素求逆需要 **O(d³)**,单层 (4096×4096) 可接受,但**多层 + 多次更新**的总成本爆炸。

**Cholesky 分解**: 用 H = LL^T (L 下三角),把"求 H 的逆"变成"求 L 的逆",**O(d³/3)** 时间,O(d²) 内存。

**优势**:
- L 是三角矩阵,逆矩阵是**三角矩阵**(容易更新)。
- 逐列剪枝时,只需要更新 L 的一列,而不是整个逆矩阵。
- 实际加速 3-5×。

### Q18. 解释为什么剪 embedding 层危险

**答**:
- **embedding 层** 把 token ID (e.g., 32000) → hidden_dim (e.g., 4096)。占 LLM 5-10% 显存,但**信息密度极高**。
- 剪掉某个 embedding 维度 → **部分 token 无法表达** (输出向量残缺)。
- 影响所有后续层,**不可恢复**。

**所以**:**不剪 embedding 和 lm_head**。这是行业共识 (Wanda / SparseGPT 都默认跳过)。

**例外**: 如果 tokenizer 里有大量**未用 token** (很多 LLM 是这样),可以裁剪 tokenizer,顺便减少 embedding 维度。

### Q19. 为什么 LLM 主流不用结构化剪枝?

**答**:
1. **压缩比低**: 结构化剪枝最多 20-30%, 远不如 Wanda 50%。
2. **微调贵**: 结构化剪枝必微调 (LoRA 1k+ 步),工业上嫌麻烦。
3. **Wanda 更简单**: 一次性,无需训练,质量损失可接受。
4. **配合量化**: Wanda + INT4 比结构化剪枝 + INT4 压缩比更高。

**什么时候用结构化**:**端侧 / 嵌入式**,必须真减小模型 (shape 变小)。

### Q20. 总结: LLM 压缩技术的选择流程

**答**:
```text
1. 显存需求是什么?
   ├── 充裕 (≥14GB for 7B)  →  FP16,不动
   ├── 中等 (4-8 GB)         →  GPTQ/AWQ INT4,不剪枝
   ├── 紧张 (2-4 GB)         →  Wanda 50% + GPTQ INT4
   └── 极限 (<2 GB)          →  Wanda 50% + LLM-Pruner 20% + INT3 + 蒸馏
2. 是否在意延迟?
   ├── 普通    →  默认 dense 推理
   └── 极致    →  2:4 半结构化 (重训) 或 vLLM int4 + early-exit
3. 是否要恢复质量?
   ├── 不在意  →  直接上线
   └── 在意    →  LoRA 微调 200-1000 步
4. 端侧?
   ├── 是      →  LLM-Pruner + INT4 + llama.cpp
   └── 否      →  云端推理,标准 vLLM + 量化
```

**实战金句**: **量化是基础,剪枝是补充,蒸馏是兜底**。

- GPTQ 4-bit 量化 → 显存再降 4×。
- LoRA 微调 → 质量恢复 (补偿 Wanda + 量化损失)。

### 11.2 模型密度的工程经验

**"Layer-wise 密度" 概念**:
- LLM 内部**不同层稀疏容忍度不同**。
- 通常**前 1/4 层**密集,**中间稀疏更友好**,**后 1/4 层**重要。

**经验密度配置** (LLaMA-7B 32 层):
```text
layer 0-7:  sparsity 0.3  (前层重要, 少剪)
layer 8-23: sparsity 0.5  (中间层, 可猛剪)
layer 24-31: sparsity 0.3  (后层重要, 少剪)
平均 sparsity: 0.42, 比均匀 0.5 效果更好
```

实现:
```python
def layer_wise_wanda(model, calib_data, sparsity_pattern):
    """
    sparsity_pattern: list of length n_layers
    e.g. [0.3]*8 + [0.5]*16 + [0.3]*8
    """
    for layer_idx, layer in enumerate(model.layers):
        sparsity = sparsity_pattern[layer_idx]
        wanda_prune_single_layer(layer, calib_data, sparsity)
```

### 11.3 稀疏 vs 量化: 哪个先做?

**选项 A: 先量化后剪枝**
- INT4 量化后 weight 值域小,稀疏阈值更难定。
- 量化+剪枝**叠加精度损失**。

**选项 B: 先剪枝后量化** (推荐)
- Wanda 先剪 50%,剩下一半再 GPTQ 量化为 INT4。
- 剪枝 + 量化**可以独立恢复** (稀疏结构稳定 → 量化更好做)。
- **主流选 B**。

### 11.4 Outlier-aware 剪枝 (OWL)

**为什么需要 OWL**:
LLM 里有少数 activation 维度是"outlier",值域 ~50-100× 普通维度。
- **Wanda 公式** 等权看所有维度 → outlier 维度**掩盖**正常维度。
- 剪枝时正常维度被错误认为"不重要",outlier 被保留 → 实际是反的。

**OWL 解决**:
```text
1. 统计每层 activation 的分布
2. 识别 outlier 维度 (top 1-2% 的 max-value 维度)
3. 剪枝时**跳过** outlier 维度
4. 只在 "non-outlier" 维度上做 Wanda
```

```python
def owl_prune(W, X_calib, outlier_threshold=3.0):
    # 1. 找 outlier
    col_max = X_calib.abs().max(dim=0).values  # (d_in,)
    threshold = col_max.mean() + outlier_threshold * col_max.std()
    outlier_mask = col_max > threshold  # (d_in,)

    # 2. 非 outlier 维度做 Wanda
    normal_X = X_calib[:, ~outlier_mask]
    normal_W = W[:, ~outlier_mask]
    importance = normal_W.abs() * normal_X.norm(dim=0)
    # 只对 normal 部分剪枝

    # 3. outlier 维度保留 (剪枝率 0)
    return pruned_W
```

**优势**: LLaMA-2 / Mistral 这种 outlier 多的模型,OWL 比 Wanda 好 10-15%。

### 11.5 稀疏模型的恢复技术 (Post-Pruning Recovery)

**1. Sparse LoRA (重训剪枝后的)**
```python
# 关键: 训练时 mask 必须和剪枝 mask 对齐
def sparse_lora_step(W, grad, prune_mask):
    W.grad = grad * prune_mask  # 被剪掉的梯度为 0
    optimizer.step()
```

**2. Knowledge Distillation (KD)**
```python
# Teacher = 原 dense 模型, Student = 剪枝后模型
def kd_loss(student_logits, teacher_logits, T=2.0):
    soft_student = F.log_softmax(student_logits / T, dim=-1)
    soft_teacher = F.softmax(teacher_logits / T, dim=-1)
    return F.kl_div(soft_student, soft_teacher, reduction='batchmean') * (T ** 2)
```

**3. Magnitude Growth (重训时 0 weight 可恢复)**
- 初始剪枝时掩码为 0 的位置,**允许在微调中激活**。
- 训练期用**重要性梯度** 触发"生长"。
- 比"固定剪枝"恢复更好。

### 11.6 模型压缩的 Pareto 探索

**实际工程**:
```text
                    精度 (PPL)
                     ↑
              ● 原始
            ·
          ·  AWQ INT4      (4× 压缩)
        ·
      ·  GPTQ INT4 + Wanda 50%   (8× 压缩)
    ·
  ·  Wanda 70% + INT3   (10× 压缩)
●
──────────────────────────→  压缩比
```

**Pareto 最优点** (质量 × 压缩比最优):
- **AWQ INT4**: 4× 压缩, ⭐⭐⭐⭐⭐ 质量
- **Wanda 50% + GPTQ INT4**: 8× 压缩, ⭐⭐⭐⭐ 质量
- **LLM-Pruner 20% + INT4**: 5× 压缩, ⭐⭐⭐⭐ 质量

### 11.7 评估指标的陷阱

**陷阱 1: 困惑度不能完全代表质量**
- WikiText PPL 5.68 → 6.66 看着只掉 1,但**下游任务**可能掉 10%。
- 必须**多任务评估** (MMLU + HumanEval + GSM8K)。

**陷阱 2: 速度测试要实测**
- 不要信理论 FLOPs,**必须 end-to-end tok/s 测**。
- A100 vs RTX 4090 vs Apple M2 结果差异巨大。

**陷阱 3: 校准数据的偏置**
- 校准数据决定 importance,**影响剪枝选择**。
- 领域数据 (医疗) 校准 → 模型**保留领域能力**,通用能力掉。
- 用**多样校准集** (C4 + Wikipedia + 领域) 平衡。

### 11.8 剪枝 vs 知识蒸馏的 "经验法则"

| 压缩目标 | 推荐 |
|---|---|
| < 2× 压缩 | **只量化** (SmoothQuant / AWQ INT4) |
| 2-4× 压缩 | **只量化** + INT4 |
| 4-8× 压缩 | **Wanda + 量化** (性价比最高) |
| > 8× 压缩 | **蒸馏 + 量化** + 结构化剪枝 |

**经验**: **剪枝叠加量化** 是 <10× 压缩的最优解。**蒸馏**只在 <2B 等需要"重新设计"时用。

```python
# 1. 准备模型
```

### 11.11 排查清单: 剪枝后掉点严重怎么办?

按顺序排查:

1. **校准数据** 是否合适?
   - 太少 (<32 条) → 加到 128+。
   - 太偏 (单一领域) → 用 C4 多样数据。

2. **剪枝率** 是否过高?
   - 50% 掉 → 降到 30-40%。
   - 30% 还掉 → 检查重要性评估是否正确。

3. **微调是否做了**?
   - 结构化剪枝必做 LoRA (200+ 步)。
   - 50% Wanda 强烈建议 200 步 LoRA。

4. **验证集是否有代表性**?
   - 测试数据应覆盖**多领域** (MMLU + HumanEval + 自己的数据)。

5. **outlier** 是否被错误剪了?
   - LLaMA-2 / Mistral 有 outlier。
   - 加 OWL 保护。

6. **是否有更差的地方**?
   - **逐层评估**: 看哪层掉得最厉害。
   - **回滚**: 把那层恢复不剪。

### 11.12 工程补充: 显存计算速查

```text
LLM-7B 显存 = (12 × n_layers × h² + 6 × n_layers × h × i) bytes  (FP16)
              │                  │                  │
              │                  │                  FFN: 4*h*i (LLaMA: i≈3.5h)
              │                  attn Q,K,V,O (4 mat)
              per-layer

实际:
  n_layers=32, h=4096, i=11008
  = 12 × 32 × 4096² + 6 × 32 × 4096 × 11008
  = 6.4 GB + 8.6 GB = 15 GB ≈ 14 GB (LLaMA-7B)

  + embedding (32k × 4096 × 2) = 256 MB
  + lm_head = 256 MB
  = 14.5 GB (官方报告 14 GB)
```

**剪枝 50% + INT4 的估算**:
```text
FP16 14 GB → 50% Wanda (dense 存) = 14 GB (不省!)
        → + INT4 = 3.5 GB (省 4×)
        → + 结构化剪 20% = 2.8 GB (省 5×)
        → + 重排 dense = 2.8 GB (直接可用)
最终: 2.5-3 GB / LLaMA-7B
```
