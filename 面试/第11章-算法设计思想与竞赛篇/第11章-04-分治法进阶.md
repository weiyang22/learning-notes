## 1. 从逆序对到 CDQ 分治

归并排序求逆序对: 分治时"左半贡献右半"。CDQ 把这一思想推广到**多维偏序**。

**三维偏序问题**: 给 $n$ 个点 $(a,b,c)$, 求每个点被多少个点在三维都不大于它。

**CDQ 思路**:
1. 按第一维 $a$ 排序 (消掉一维)。
2. 分治操作序列: `solve(l,r)` 先递归左右, 再算**左半对右半**的贡献。
3. 左右各自按第二维 $b$ 有序 (归并), 用树状数组维护第三维 $c$。

```python
class BIT:
    def __init__(self, n):
        self.t = [0]*(n+1)
    def add(self, i, v):
        while i < len(self.t): self.t[i] += v; i += i & -i
    def qry(self, i):
        s = 0
        while i > 0: s += self.t[i]; i -= i & -i
        return s

def cdq(points):
    """points: [(a,b,c)], 返回每点被支配数. 假设已按 a 排序、去重合并"""
    n = len(points)
    ans = [0]*n
    bit = BIT(max(p[2] for p in points) + 1)

    def solve(l, r):
        if r - l <= 1: return
        m = (l + r)//2
        solve(l, m); solve(m, r)
        # 左半 [l,m) 对右半 [m,r) 贡献: 双指针按 b 归并, 用 BIT 统计 c
        i = l
        for j in range(m, r):
            while i < m and points[i][1] <= points[j][1]:
                bit.add(points[i][2], 1); i += 1
            ans[j] += bit.qry(points[j][2])       # c 不大于的个数
        for k in range(l, i):                     # 回滚 BIT
            bit.add(points[k][2], -1)
        # 按 b 归并使 [l,r) 有序 (供上层使用)
        points[l:r] = sorted(points[l:r], key=lambda p: p[1])

    solve(0, n)
    return ans
```

**复杂度**: $O(n \log^2 n)$ (分治 $\log n$ 层 × 每层 BIT $\log n$)。这是"CDQ 降维打击"——把三维数据结构问题降成一维 BIT。

**7. 实践建议**

结合 "分治法进阶 (CDQ / 整体二分)" 的特点,实践中有以下建议:

1. **数据优先**: 数据质量决定上限,模型只是逼近这个上限。把 50% 的时间投入到数据理解和清洗上,这条经验被无数实践证明。数据问题往往比模型问题更关键,但也更容易被忽视。

2. **基线先行**: 先用最简单的方法(如逻辑回归、规则)做基线,确认增益是来自方法还是数据。没有强基线的"创新"往往不靠谱。很多看似 fancy 的方法,在强基线面前提升有限。

3. **迭代式改进**: 不要追求一步到位,而是 baseline → 简单改进 → 高级方法 → 调优。每一步都用验证集确认有提升。每一步的提升幅度通常递减,要预期边际收益下降。

4. **失败案例分析**: 重点看模型做错的样本,往往能发现系统性问题。错误样本里藏着模型没学会的知识。把这些样本按错误类型分类,可以发现模型的薄弱点。

5. **A/B 测试**: 在生产环境做对照实验,用业务指标而非离线指标评估。离线指标只是手段,业务指标才是目的。指标可以被优化,但业务目标很难直接优化。

6. **监控与回滚**: 上线后持续监控关键指标,异常时快速回滚。任何线上系统都必须考虑"最坏情况",并预先设计好应对方案。

**8. 常见误解**

对 "分治法进阶 (CDQ / 整体二分)" 常见的误解包括:

1. **"模型越复杂越好"**: 实际上,简单模型 + 好数据往往优于复杂模型 + 烂数据。这条法则在实践中反复被验证。

2. **"训练 loss 越低越好"**: 训练 loss 低不代表泛化好,可能过拟合。要看验证集表现,做误差分析。

3. **"指标好就等于业务好"**: 离线指标与在线业务有 gap,必须做 A/B 测试。指标可以被优化,但业务目标很难直接优化。

4. **"新方法一定比旧方法好"**: 新方法通常针对特定场景,在你的场景未必更好。要谨慎评估,先复现,再改进。

5. **"开源即用"**: 开源代码与你的数据/工程栈往往有 gap,需要适配。盲目复用经常踩坑,要理解代码再做改动。
