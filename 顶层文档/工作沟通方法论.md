# 工作沟通方法论——让你的表达更有条理、更有证据、更有影响力

> **本章目标**: 你在工作中被指出的 3 个高频问题——**说话没条理 / 观点没证据 / 定位猜测在前**——本质都是**沟通方法论**问题,而不是"你不够聪明"或"经验不够"。本章用**认知科学 + 决策树 + 心智模型 + 脚本化模板**系统讲清楚:
>
> - **底层心智模型**:为什么"说清楚"比"做出来"更有杠杆 / 7±2 法则 / 信息不对称 / 决策依赖
> - **结构化表达**:金字塔原理 / SCQA / 5W1H / 结论先行——**每个框架用决策树告诉你"什么场景用哪个"**
> - **证据链**:4 个等级 + 5 类证据 + **"该用 L几"决策树**
> - **问题定位**:5 Why + 3 步法 + **"卡在 X 步时怎么办"决策树**
> - **向上沟通**:周报 / 日报 / 求助 / 坏消息 / 资源——每个都附"会前 / 会中 / 会后"流程
> - **横向沟通**:跨团队协作 / 需求评审 / Bug 定位 / Code Review——**"if A 说 X,你回 Y"剧本**
> - **向下沟通**:任务分配 / 反馈 / 1on1——**3 阶段培养法 + 4 种难管下属对策**
> - **沟通前 30 秒准备术**:万能的"开口前 30 秒"决策树,**适用于 80% 场景**
>
> 学完本章,你能:
> - **说话前 30 秒**用决策树组织清楚要点(不再是"乱说")
> - **任何观点都按决策树配 L2 以上证据**(不再是"没证据")
> - **卡在 Bug 排查的某一步时,知道下一步该做什么**(不再是"先猜再查")
> - **当 +1 / 同事 / 下属 抛给你 X,你能立即知道怎么回**(不再是"被动接招")
> - **让 +1 / 同事 觉得"这小子靠谱"**

## 0. 沟通的心智模型(必读)——为什么"说清楚"比"做出来"更有杠杆

**文字**: 在讲任何具体方法之前,先建立 4 个**底层心智模型**。**这 4 个心智模型是这一章所有方法论的"根"**——理解了它们,你才能在面对任何沟通场景时,**自己推理出"应该怎么做"**,而不是死记硬背模板。

### 0.1 心智模型 1:信息不对称("看不见"原理)

**核心断言**: **你的 +1 / 同事 / 下属,和你看到的世界完全不同**。这不是态度问题,是**物理上不可能**——他没有你的屏幕、你的代码、你的 log,他也忙着自己的事。

```text
【你看到的】                        【+1 看到的】
┌─────────────────┐                 ┌─────────────────┐
│ 你的代码 / log  │                 │ 你的周报 1 句话  │
│ 你的进度 80%    │ ──信息差──→   │ "你在做 X 项目"  │
│ 你的卡点 Y      │                 │ 不知道卡点        │
│ 你的下一个动作  │                 │ 等你 1on1 才问     │
└─────────────────┘                 └─────────────────┘
        ↑                                   ↑
     你活在这里                          他活在这里
     (细节丰富)                          (细节真空)
```

**推论 1**: **你不说,他就猜**。他猜出来的"你的进度"通常**错得离谱**。

**推论 2**: **你说的越精确,他的决策质量越高**。一句"我卡在 X,试过 Y,需要 Z"比"我遇到点问题"省他 30 分钟追问。

**推论 3**: **"说清楚"是你单方面能做的事**。"做出来"依赖别人(同事配合、数据到位、平台不宕机);"说清楚"**只依赖你**。**这是你能 100% 控制的杠杆点**。

### 0.2 心智模型 2:决策依赖("被需要"原理)

**核心断言**: **+1 不是你的监工,他是你的杠杆**。他协调资源、争取时间、排优先级——这些事**你自己做不了**。**你说得清楚,他才能帮你**;**说不清楚,他只能瞎帮或者不帮**。

```text
【你说得清楚】                       【你说得不清楚】

  +1 决策质量: 高                    +1 决策质量: 低
  他能帮你:                          他能帮你:
   ✓ 排高优先级                       ✗ 不知道排什么优先级
   ✓ 协调 3 个团队                    ✗ 派个不对口的人给你
   ✓ 帮你争取时间                     ✗ 觉得你不紧急就先放着
   ✓ 给你介绍关键人                   ✗ 觉得你自己能搞定
```

**推论 1**: **+1 帮你不是因为他好,是因为你说得清楚**。

**推论 2**: **如果你让 +1 猜,他猜错的成本会由你承担**。**项目延期 / 资源不到位 / 卡点没人帮**——**全是你的成本**。

### 0.3 心智模型 3:7±2 法则("人脑极限"原理)

**核心断言**: **人类工作记忆只能同时处理 7±2 个信息块**。这是认知科学的基本结论(George Miller, 1956)。**任何"超过 7 个要点"的沟通,对方都记不住**。

**推论**:
- 周报**不要写 10 条**,写 **3-5 条**
- 汇报**不要讲 30 分钟**,**30 秒结论 + 5 分钟细节 + 5 分钟问答**
- 邮件**不要塞 5 个事**,**一件事一封邮件**
- 任何沟通**只讲 1 个核心信息** + 2-3 个支撑

**为什么金字塔原理是"1 结论 + 3 分论点"?** 因为**3 ≤ 7±2**,人类能记住。**超过 3 个分论点,对方就开始走神**。

### 0.4 心智模型 4:影响力复利("复利"原理)

**核心断言**: **技术能力是"加法",沟通能力是"复利"**。

```text
技术能力 1.0 + 沟通能力 1.0 = 1 个项目做得不错
技术能力 1.0 + 沟通能力 2.0 = 5 个项目拿到认可
技术能力 1.0 + 沟通能力 3.0 = 影响整个团队 / 推动架构选型
```

**为什么?**

- 你做 1 个项目, +1 看到 1 个项目 → 给 1 个项目的机会
- 你做 5 个项目,**每个都让 +1 看清楚** → +1 信任你 → 给你 5 个项目的机会 + 1 个 leader 位置
- 你**让团队看清楚** → 团队信任你 → 推架构选型 / 跨团队协调

**结论**: **沟通能力是"杠杆"**。1 倍投入,5 倍回报。**这是为什么"沟通方法论"是工程师最高 ROI 的技能之一**。

### 0.5 4 个心智模型 → 3 个核心结论

```text
心智模型 1:信息不对称 → 你必须主动 sync,不能等别人来问
心智模型 2:决策依赖   → 你说得越清楚,别人帮你越准
心智模型 3:7±2 法则    → 任何沟通 ≤ 3 个要点
        ↓
       ↓ ↓ ↓
    【沟通的 3 个核心原则】
    1. 结论先行:第一句话必须是结论
    2. 证据三件套:任何结论必须 1-2-3(数据 / 观察 / 推理)
    3. 可执行下一步:任何讨论以"谁做什么"结束
```

**理解了这 4 个心智模型,这一章剩下的所有方法论,你都能自己推理出来**。

## 1. 沟通的 4 个层级 + "如何升级"的决策树

### 1.1 4 个层级(诊断:你现在在哪一层?)

| 层级 | 表现 | 对方感受 | 典型场景 |
| :--- | :--- | :--- | :--- |
| **L1: 想到哪说到哪** | 30 秒说不清自己在做什么 | "他到底在讲啥?我得追问" | "嗯……这个,我跑了下,然后发现 AUC 好像没怎么涨……" |
| **L2: 有结论但没证据** | "我觉得 X"但说不出为什么 | "他在猜吧?不可信" | "我觉得这个模型效果不好"(证据呢?) |
| **L3: 结论 + 证据** | "X 有问题,因为 Y 日志,定位到 Z" | "靠谱,有理有据" | "模型 AUC 跌 1.2%,A/B 实验 7 天,根因是 A 特征 join 漏了 5%" |
| **L4: 结论 + 证据 + 影响 + 建议** | "X 问题影响 3 个核心场景,建议 A 方案,2 天可修复" | "决策者,可依赖" | "AUC 跌 1.2%,影响 12% 用户,临时方案用历史均值,长期方案接实时特征,2 天可上线" |

**你被指出的问题(没条理 / 没证据 / 猜测在前)对应 L1-L2**。**这一章的目标:稳定 L3,争取 L4**。

### 1.2 "我现在在 L 几"自检决策树

**如果你刚开完会 / 刚发完邮件 / 刚汇报完,自问**:

```text
1. 对方有追问"你到底想说啥"吗?
   ├─ 是 → 你在 L1
   └─ 否 → 继续

2. 对方有质疑"你的证据是啥"吗?
   ├─ 是 → 你在 L2
   └─ 否 → 继续

3. 对方有进一步问"影响谁、怎么改"吗?
   ├─ 是 → 你在 L3(L3 没问题,但可以更主动到 L4)
   └─ 否 → 你是 L4(对方已经能直接拍板)
```

**核心**: **L1 的标志是对方"听不懂",L2 的标志是对方"不信",L3 的标志是对方"信但要追问",L4 的标志是对方"直接拍板"**。

### 1.3 "如何从 L1/L2 升级到 L3"决策树

**如果你发现自己常在 L1-L2,按下面决策树升级**:

```text
【起点:你说的某句话】

Q1: 这句话有"结论"吗?(1 句话能说清的核心意思)
   ├─ 否 → 用 §2 的"结论先行"加 1 句话结论
   └─ 是 → 继续

Q2: 这个结论有"证据"吗?(数据 / 观察 / 推理至少 1 类)
   ├─ 否 → 用 §3 的"证据翻译"补 1 类证据
   └─ 是 → 继续

Q3: 证据是不是"具体到可复现"?(数字 + 来源 + 时间)
   ├─ 否 → 加数字、加来源、加时间
   └─ 是 → 你已经在 L3

Q4: 能说清"影响范围 + 建议方案"吗?
   ├─ 否 → 用 §6.3 的"5 段式求助模板"补"影响 + 建议"
   └─ 是 → 你已经是 L4
```

**实操**: **任何汇报 / 邮件 / 会议发言前,跑一遍这棵决策树,30 秒**。

### 1.4 3 个核心原则(从心智模型推出)

| 原则 | 来源心智模型 | 为什么 |
| :--- | :--- | :--- |
| **结论先行** | 信息不对称 | 对方脑子有空位时,先放结论,后面再放细节 |
| **证据三件套** | 决策依赖 | +1 帮你需要理由,理由就是证据 |
| **可执行下一步** | 影响力复利 | 没有"谁做什么"的沟通 = 闲聊,不产生复利 |

## 2. 结构化表达:金字塔原理 / SCQA / 5W1H / 结论先行——心智模型 + 决策树

**文字**: 表达没条理的人,根本原因是**"边想边说"**——脑子里的想法实时流到嘴上,听众只能跟着你的思路绕,**绕 3 圈还没听到结论**。**结构化表达的核心是"先想清楚再开口",而且要"想成一棵树"**——根是结论,枝是分论点,叶是证据。

**底层心智模型**: **7±2 法则**——人类工作记忆 7±2 个块,所以**1 结论 + 3 分论点 ≤ 7 块**,**听众能记住**。

### 2.1 4 个框架的对比 + "用哪个"决策树

| 框架 | 形状 | 适用场景 | 不适用 |
| :--- | :--- | :--- | :--- |
| **金字塔原理** | 树形(1 结论 + 3 分论点 + 9 证据) | 复杂汇报、方案文档、PPT | 1 句话的快速同步(杀鸡用牛刀) |
| **SCQA** | 线性(情境→冲突→问题→答案) | 立项申请、跨团队会议开场 | 已知背景的内部沟通 |
| **5W1H** | 检查表(What/Why/When/Where/Who/How) | 复杂问题的首次汇报、工单、风险预警 | 闲聊 |
| **结论先行** | 1 句话(结论) | **所有场景都适用**——打底 | 没有 |

### 2.2 "用哪个框架"决策树

**场景:你要沟通某事,选哪个框架?**

```text
Q1: 听众已经知道背景吗?(比如同一团队的同事 vs 跨团队)
   ├─ 不知道背景 → 走 SCQA(把背景讲清楚再讲答案)
   └─ 知道背景 → Q2

Q2: 沟通是 1 句话就能讲清,还是要展开 5-15 分钟?
   ├─ 1 句话(进度同步、简单决策) → 走"结论先行"——只讲 1 句话
   └─ 5-15 分钟(汇报、方案讨论) → Q3

Q3: 沟通的目的是"说清楚现状"还是"让对方做决策"?
   ├─ 让对方拍板 → 走"金字塔"(结构清晰,对方能选分论点反驳)
   └─ 让对方了解现状 → Q4

Q4: 是首次沟通(对方不知道发生了什么)还是后续跟进?
   ├─ 首次 → 走"5W1H"(检查表覆盖所有维度)
   └─ 后续 → 走"结论先行 + 1 句话分论点"(对方已有 context)
```

### 2.3 金字塔原理(复杂场景专用)

**核心**: 任何复杂表达,**都构建成一颗"金字塔"**。

```text
                ┌─ 结论(1 句话)
                │
            ┌───┴───┐
            │       │
         分论点1  分论点2
            │       │
         ┌──┴──┐  ┌─┴──┐
        证据1 证据2 证据3 证据4
```

**为什么这样组织?**

- **MECE 原则**(Mutually Exclusive, Collectively Exhaustive):分论点之间**不重叠** + **穷尽**——这是金字塔的灵魂
- **听众可以"选择性吸收"**:他想看哪部分就直接看哪部分,**不需要从头听到尾**
- **听众可以"反驳分论点"**:如果他反对分论点 1,结论就动摇——这是**金字塔让对方帮你"找漏洞"**的设计

**反例(没 MECE)**: "本周完成 3 件事:1) 写代码 2) 开会 3) 提 PR"——**这 3 个是"动作"分类,不是"结果"分类**。改:1) 性能优化 +5% 2) 跨团队对齐 3) BUG 修复 3 个——**按"业务结果"分类**。

**例子**——汇报"模型效果没涨":

- **❌ 没结构(典型 L1)**: "嗯……这个,我跑了下,然后发现 AUC 好像没怎么涨,我也不太确定,然后我看了一下数据,可能是因为特征的问题,但也可能不是……"
- **✅ 金字塔结构(典型 L3)**:
  - **结论**: "A/B 实验 7 天,新版精排模型 AUC +0.3%,**达到上线标准,建议放量 50%**"
  - **分论点 1**: 核心指标(实验组 vs 对照组,7 天,95% 置信)
  - **分论点 2**: 辅助指标(CTR / 时长 / 留存均正向)
  - **分论点 3**: 风险点(冷启动用户指标持平,需持续监控)
  - **证据 1-2-3-4**(数据、表格、对比图)

### 2.4 SCQA 框架(开场专用)

**核心**: 用 4 步把"为什么"讲清楚。

| 字母 | 含义 | 例子 |
| :--- | :--- | :--- |
| **S**ituation | 大家已经知道的事实 | "目前主推荐是 DNN 精排,2023 年上线,服务 1.2 亿 DAU" |
| **C**omplication | 出现的新情况 / 矛盾 | "近 3 个月,DAU 涨 25%,但人均时长跌 8%,用户反馈'内容不感兴趣'" |
| **Q**uestion | 关键问题 | "如何在涨 DAU 同时不跌时长?" |
| **A**nswer | 你的答案 | "建议引入 GenRec 重排,3 周可上线,预计时长 +5%" |

**适用场景**: 立项申请、跨团队会议开场、写方案文档。

**为什么有效**:
- **S** 让听众知道"我们在哪"
- **C** 制造张力("有问题!")
- **Q** 把问题具象化("所以呢?")
- **A** 给出你的答案("我建议 X")

**反例**: 跨团队会议,如果**直接说"A: 我建议 X"**——对方会问"为什么?凭什么?我没看到问题啊"——因为**没有 SC,直接到 A**,对方没有 context。

### 2.5 5W1H 框架(复杂问题首次汇报专用)

**核心**: 任何复杂问题,6 维度都讲全。

| 字母 | 含义 | 例子 |
| :--- | :--- | :--- |
| What | 是什么(事件/问题) | "新模型在测试集 AUC 跌 1.2%" |
| Why | 为什么(原因) | "Embedding 表更新频率过低,长尾 ID 未充分训练" |
| When | 何时(时间) | "5 月 1 日上线后 3 天内开始" |
| Where | 何地(范围) | "影响 12% 的用户,集中在 3 个城市" |
| Who | 谁(责任方) | "算法组负责排查,数据组协助" |
| How | 如何(方案) | "3 步定位 + 2 天修复 + 1 周 A/B" |

**适用场景**: 复杂问题的首次汇报、跨团队工单、风险预警。

**为什么"5W1H"而不是"3W1H"?** 因为**漏一个维度,对方就要追问**——追问 = 浪费时间。**5W1H 一次说全,对方不需要追问**。

### 2.6 结论先行(所有场景都适用)

**核心**: 第一句话必须是结论。**永远不要用"铺垫"开头**。

**为什么"结论先行"如此重要?**

```text
【听众大脑的资源分配】

时间轴: 0s        5s        30s        60s
       ┌──────┬─────────┬──────────────┐
       │空位  │ 听细节  │ 听细节 + 评估 │
       │(很满)│(快满了)│(已满 + 疲劳) │
       └──────┴─────────┴──────────────┘
        ↑
   结论必须放这里
   否则后面细节没空间放
```

**反例 / 正例对照**:

| ❌ 错误开头 | ✅ 正确开头 |
| :--- | :--- |
| "最近我们组的模型效果不太好,我想提一下,可能需要调整一下,你看下时间方便吗……" | "模型效果有问题,需要 30 分钟讨论,你能现在开会吗?" |
| "我在排查一个 bug,情况是这样的……(讲 5 分钟背景)" | "线上 P99 突增 5 倍,定位到 X 服务,需要 X 同学支援,1 小时内能解决" |
| "我有个想法……可能不太成熟……(讲 3 分钟)" | "我建议在 Y 处加 Z 优化,预计提升 2%,要不要 15 分钟讨论下?" |

**关键**: 第一句话要回答"**你要我做什么 / 知道什么 / 决策什么**"。

### 2.7 "30 秒说清要点"万能模板

**任何沟通前,30 秒填这个模板**:

```text
场景: [你在沟通什么,例如"周报汇报"]
结论: [1 句话讲清,例如"本周完成 A,效果 +5%"]
证据: [1-2 个数字 / 观察,例如"实验组 AUC 0.78 vs 对照 0.73"]
影响: [影响谁 / 影响多大,例如"上线后预计增收 Y 万"]
建议 / 求助: [你希望对方做什么,例如"你 1 周内审批一下"]
```

**实操**: **任何沟通前 30 秒,填这个模板**。**填不出来,说明你自己还没想清楚**——回去再想。

## 3. 证据链:4 个等级 + "该用 L几"决策树

**文字**: "被指出没有证据"是另一个高频痛点。**根因是把"推理"和"证据"混为一谈**——你说"我觉得 X",其实你是**基于某些观察**得出 X 的,但你**没把这些观察说出来**。对方只看到 X,看不到观察,就认为是"凭空猜"。

**底层心智模型**: **决策依赖**——+1 帮你需要理由,理由就是证据;**没有证据,理由不成立,+1 帮不了你**。

### 3.1 3 类证据(What 维度)

| 证据类型 | 含义 | 例子 |
| :--- | :--- | :--- |
| **数据** | 量化的事实 | "P99 从 80ms 涨到 450ms,持续 30 分钟" |
| **观察** | 看到/听到的现象 | "在测试环境复现了 5 次,每次都是同一行报错" |
| **推理** | 基于前两者的因果链 | "P99 涨 → 怀疑是模型加载阻塞 → 看堆栈确实是 → 结论:模型服务需要预热" |

### 3.2 证据的 4 个等级(How strong 维度)

| 等级 | 证据强度 | 适用场景 | 例子 |
| :--- | :--- | :--- | :--- |
| **L4: 多重数据** | 多次实验、多维度数据交叉验证 | 重大决策(架构选型、跨年预算) | "7 天 A/B + 30 天观察 + 3 个用户群都验证 +5%" |
| **L3: 单点数据** | 一次实验 / 一个数据点 | 一般建议(优化方向、新功能提议) | "7 天 A/B 实验 AUC +0.5%" |
| **L2: 现象观察** | 测试 / 复现 / log 截图 | 假设提出(讨论用)、bug 排查 | "测试环境复现 5 次,都是同一行报错" |
| **L1: 直觉** | "我觉得" | 私下交流 / 头脑风暴 / 1on1 | "我觉得 X 可能有性能问题" |

**核心原则**: **你的结论至少要配得上 L2 证据,重大决策必须 L3-L4**。**L1 级别的"我觉得"作为开场白是灾难**——它被 +1 解读为"我懒得想"。

### 3.3 "该用 L几"决策树(最常用的执行工具)

**你有一个结论想说,问自己**:

```text
Q1: 这个结论影响多大?
   ├─ 影响 1 个项目 / 一个团队 → L3-L4
   ├─ 影响 1 个 feature / 1 个模块 → L3
   ├─ 影响 1 个 bug 修复 / 1 个小决策 → L2-L3
   └─ 私下讨论 / 头脑风暴 → L1-L2 都可以

Q2: 这个结论的"反对成本"多大?
   ├─ 一旦被错,会浪费 1 个月 → L4(多重验证)
   ├─ 一旦被错,会浪费 1 周 → L3
   ├─ 一旦被错,会浪费 1 天 → L2-L3
   └─ 错了也无所谓,试试看 → L1-L2 都可以

Q3: 这个结论有多"反直觉"?
   ├─ 违反常识 / 违反他人经验 → L4
   ├─ 比较反直觉 → L3-L4
   ├─ 符合常识 → L2-L3
   └─ 大家都这么认为 → L1(不需要证据,大家都同意)
```

**实操**: **每次有结论想说,先跑这棵决策树,30 秒**。

**例子**:
- "建议把精排模型从 DNN 升级到 Transformer" → Q1: 影响 1 个项目 → L3;Q2: 错了浪费 1 个月 → L4;Q3: 违反常识 → L4 → **需要 L4 证据(7 天 A/B + 30 天观察 + 灰度数据)**
- "我怀疑这个 bug 是 A 模块的问题" → Q1: 影响 1 个 bug → L2-L3;Q2: 错了浪费 1 天 → L2;Q3: 不反直觉 → L2 → **L2 证据(log 截图 + 复现 5 次)够了**
- "我觉得这个 PR 命名可以更好" → Q1: 影响命名 → L1;Q3: 主观 → L1 → **L1(直接说"建议命名 X",不需数据)**

### 3.4 把"我觉得"翻译成证据的 5 个技巧

| 技巧 | 反例 → 正例 |
| :--- | :--- |
| **加时间** | "我觉得不对" → "我**刚才**看了日志,发现 X" |
| **加对比** | "我觉得版本 2 更好" → "**对比了新旧两个版本**,新版本在 X 场景下更好" |
| **加数字** | "我觉得太慢了" → "我**查了下数据库**,P99 是 200ms,**比阈值 100ms 高 100%**" |
| **加来源** | "我觉得数据有问题" → "我**问了数据组的小王**,他说这个指标最近有波动,原因是 X" |
| **加动作** | "我觉得 X 方案行" → "我**尝试了 A 方案(失败),试了 B 方案(成功)**" |

**核心**: **"我觉得"是 L1;加上"时间/对比/数字/来源/动作"任一,就升到 L2**。

### 3.5 反驳时的"证据升级"模板

**当你的观点被质疑时,别用"我觉得",用证据升级**:

| 对方质疑 | 错误回应(L1) | 正确回应(L3) |
| :--- | :--- | :--- |
| "你这个数据样本太小" | "我觉得够了" | "我同意,3 天数据确实不够,我把窗口拉到 7 天,结果还是一致的,见下表" |
| "你这个方法 A 组试过不行" | "我觉得我们情况不一样" | "我看了 A 组的 case,他们 X 配置和我们不同,我们 X 不同,所以可能可以再试" |
| "你这个结论太激进" | "我觉得稳" | "我同意,所以我准备了 3 步走的方案,先 5% 流量跑 3 天,数据 ok 再放量,你看 OK 吗?" |

**核心**: **被质疑时,不要"嘴硬"——用证据升级**。**同意对方的部分(降低对抗),再用新证据补强自己的部分**。

## 4. 问题定位方法论:5 Why + 3 步法 + "卡住时怎么办"决策树

**文字**: "定位问题都是猜测在前,定位在后"——这是技术沟通中**最致命**的问题之一。**根因是工程师的本能是"找最快的解",但最快的解往往是错的**。**正确流程是"先证据、后结论"**。

**底层心智模型**: **7±2 法则 + 决策依赖**——**定位错的话,会浪费后续 5-10 个人的时间**;**所以花 1 小时定位,比花 1 天"边猜边改"更省时间**。

### 4.1 5 Why 法则(丰田生产方式)

**核心**: 同一个问题问 5 次"为什么",直到找到根因。

**心智模型**: **"症状"和"根因"不在同一层**。修症状会反复复发,修根因才能一劳永逸。

```text
问题: P99 突增 5 倍
  ├─ 为什么 P99 突增? → 因为某个查询变慢
  │   ├─ 为什么变慢? → 因为模型推理时间涨
  │   │   ├─ 为什么模型推理变慢? → 因为输入特征维度涨了
  │   │   │   ├─ 为什么特征维度涨? → 因为加了 3 个新特征
  │   │   │   │   └─ 为什么新特征没经过压测? → 因为是临时加的,没走 review → 根因:缺流程
  │   │   │   └─ 找到根因!
```

**反模式**: 5 Why 问 2 层就停——"问题是 X,所以改 X"。**根因通常在第 3-5 层**。

### 4.2 问题定位的"3 步法"

| 步骤        | 目的         | 关键问题                                  | 失败信号                        |
| :--- | :--- | :--- | :--- |
| **1. 复现** | 验证问题真的存在   | 这个问题 100% 能复现吗?在什么条件下?                | "我看了下日志,好像有问题"——无法复现 = 不是问题 |
| **2. 隔离** | 缩小范围,定位到模块 | 哪一层(网络/服务/模型/数据)?哪个服务?哪个接口?哪段代码?哪批数据? | "可能是 A 也可能是 B"——隔离失败 = 没定位到 |
| **3. 验证** | 确认根因       | 修了这个根因,问题消失吗?不修,问题会复现吗?               | "我改了 X,问题好了"——但没解释为什么,可能是巧合 |

**关键反模式**:
- ❌ "我觉得是 X 的问题,我先改一下" → 改完发现是 Y 的问题
- ✅ "我先在测试环境复现 5 次,确认是 X 模块,然后再排查"

### 4.3 定位 Bug 时的"8 步报告法"

**当被要求"排查这个 bug"时,不要立刻跳进去改代码,先给出一份"8 步报告"**:

```text
1. Bug 现象: P99 从 80ms 涨到 450ms,持续 30 分钟
2. 复现条件: 调用方为 app 端,城市 = 北京,用户数 > 1000
3. 复现概率: 5/5 必现
4. 影响范围: 12% 的请求,影响 DAU 约 200 万
5. 已排除项: 网关正常、数据库正常、下游服务正常
6. 怀疑方向: 模型推理服务(初步看 log 是在这里卡住)
7. 下一步: 看模型服务的详细堆栈,30 分钟内出结论
8. 截止时间: 14:00(从现在起 90 分钟)
```

**这份报告为什么有效?**

| 信息项 | 让 +1 知道 |
| :--- | :--- |
| 1-2 现象 + 复现条件 | 你的理解是对的,不是误报 |
| 3 复现概率 | 是不是优先级高(必现 = P0,概率低 = P2) |
| 4 影响范围 | 决定这事有多紧急 |
| 5 已排除项 | 你的思路清晰,不是乱猜 |
| 6 怀疑方向 | 你的下一步有方向 |
| 7 下一步 | 别人可以帮你(基于"已排除"项) |
| 8 截止时间 | +1 知道什么时候要介入 |

### 4.4 上下游排查时的"3 件套 + 1 礼貌"

**当你怀疑是上下游问题,去找别人时,带上 3 件套 + 1 礼貌**:

**3 件套**:

| 件套 | 内容 | 例子 |
| :--- | :--- | :--- |
| **现象** | 我这边看到了什么 | "我的服务 P99 涨到 500ms" |
| **怀疑** | 我怀疑是你的哪个环节 | "看 trace,卡在调用你 X 接口的 3 秒上" |
| **诉求** | 我需要你提供什么 | "麻烦看下你那 3 秒是在哪一步消耗的" |

**1 礼貌**: "感谢你抽空帮我看" / "如果信息不全,我随时补充"

**❌ 没有 3 件套的求助**:
> "X 服务好像有问题,你看看?"

**✅ 有 3 件套的求助**:
> "我的服务 P99 涨 5 倍,**看 trace 卡在调用 X 接口的 3 秒上**,**麻烦帮我看看 X 接口是不是慢在哪一步了**。trace 链接: [URL]"

**对方看了能直接动手,不用反复问你"是哪一步"**——**这是给对方节省时间,对方会更愿意帮你**。

### 4.5 "卡在 X 步时怎么办"决策树(最常被问的执行问题)

**这是新人最常问的"我卡住了怎么办"的执行决策树**:

```text
【Q1: 你卡在哪个阶段?】

├─ 卡在"复现"——无法 100% 复现 bug
│   └─ 决策树:
│       Q1a: 是 bug 本身偶发?
│       ├─ 是 → 加监控 / 多观察几天 → 抓 trace / 收集样本
│       └─ 否 → 找最小复现路径(简化数据 / 简化场景)
│
├─ 卡在"隔离"——多个可能,无法缩小范围
│   └─ 决策树:
│       Q1a: 是 2 个可能 → 二分法:关闭 A 看 B 是否复现,关闭 B 看 A
│       Q1b: 是 3+ 个可能 → 用 §4.4 的"3 件套"找上下游同事
│       Q1c: 完全没头绪 → 用 §4.1 的 5 Why 反推
│
├─ 卡在"验证"——改了 X,问题"看起来"好了,但不确定是不是巧合
│   └─ 决策树:
│       Q1a: 复现 5 次都好了 → 90% 概率是修好了
│       Q1b: 改了 X 后没立刻复现 → 等 24 小时看是否真不复发
│       Q1c: 改的不是"根因",只是"症状" → 重新做 §4.1 的 5 Why
│
└─ 卡在"修复"——不知道怎么改
    └─ 决策树:
        Q1a: 改对了 = 1 行 → 直接改
        Q1b: 改对了 = 1 个模块 → 找该模块 owner 一起改
        Q1c: 改对了 = 1 个架构 → 写方案文档 + 评审 + 灰度
        Q1d: 超过 1 天还没改 → 求助 +1(用 §11 的 5 段式)
```

**核心**: **不要"闷头卡 2 小时"——卡住 30 分钟就求助**,**带 4 阶段进展 + 排除项 + 下一步**(用 §8.2 的模板)。

### 4.6 复盘:从"猜测在前"到"事实先行"

**"猜测在前"的人的 3 个特征**:
1. **先改再查**: "我觉得是 X,先改改看"
2. **找不到就说"没看出来"**: 没头绪,硬扛,最后交付延迟
3. **不愿意写排查过程**: 只说结论不说过程,别人无法验证

**"事实先行"的人的 3 个特征**:
1. **先查再改**: "我先查清楚是什么,再改"
2. **查不到就求助**: 卡住就主动 sync 进度 + 求助
3. **主动写排查过程**: 把过程截图 / log / 命令贴出来,别人能复现

**自检方法**:
- 每次发"我在排查 X"时,自问:**如果我排查错了,这段话能让别人发现吗?**
- 如果答案是"不能"——**说明你的过程不够透明**。

## 5. 向上沟通(一):周报 / 日报——"会前 / 会中 / 会后"流程

**文字**: 周报是**"让 +1 知道你这周做了什么、卡在哪、接下来做什么"**的载体。**写周报不是流水账,是"信号传递"**。一份好的周报,让 +1 30 秒内看完就能给你做绩效评估。

**底层心智模型**: **信息不对称 + 决策依赖**——**+1 不在你身边,只能从你的周报"看到"你**。**周报是 +1 给你做绩效评估的唯一持续输入**。

### 5.1 周报 / 日报的"会前 / 会中 / 会后"流程

```text
【会前:周五下班前 30 分钟,周报流程】

  1. 打开本周做的所有事(看 git commit、PR、文档、会议纪要)
  2. 按"业务结果"分类(不是按时间分类):
     ├─ 本周完成(带结果数字)
     ├─ 进行中(带进度)
     ├─ 下周计划(带优先级)
     └─ 卡点 + 求助
  3. 跑一遍 §13 的"10 大错误自检清单"
  4. 发出去(周五晚 6 点前)

【会中:周报被 +1 看到,可能发生什么】

  ├─ +1 没回复 → 说明"没问题",继续
  ├─ +1 回"好的 / 👍" → 说明"信号收到",继续
  ├─ +1 追问细节 → 说明他想帮你 / 想了解 / 想推进,尽快回
  └─ +1 提出调整 → 立刻响应(他重新分配优先级,你应该配合)

【会后:周一上午,1on1 / 团队会上,周报变成讨论素材】

  - +1 可能会说"你周报里 X,我想深入聊下"——你**之前周报就要写得能聊**
  - 周报里写的卡点 → +1 会在 1on1 上问进展
  - 周报里写"需要 X 资源" → +1 会在 1on1 上给资源 / 推资源
```

### 5.2 周报的"SCQA 升级版"结构

```markdown
# 周报 (YYYY-MM-DD ~ YYYY-MM-DD) - 姓名

## 本周完成 (3-5 条,每条带结果数字)
- [X 项目] 完成了 Y,关键指标 Z 从 A 提升到 B (W% 提升)
- [X 优化] 解决了 Y,线上 P99 从 200ms 降到 80ms
- [X 会议] 主导了 Y 会议,产出 Z 文档

## 进行中 (1-3 条,带进度%)
- [X 项目] 当前进度 60%,预计 X 月 X 日完成
- [X 优化] 卡在 Y,需要 Z 资源/帮助

## 下周计划 (3-5 条,带优先级)
- [P0] 必做:X
- [P1] 应做:Y
- [P2] 可做:Z

## 风险与求助 (0-3 条,没有就写"无")
- [风险 1] X 可能影响 Y,我的方案是 Z
- [求助 1] 我卡在 X,试过 Y,需要 Z
```

### 5.3 周报"自检清单"

| 问题 | 是 | 否 |
| :--- | :--- | :--- |
| **结论先行**:第一段就能看到本周的核心结论? | ✓ | ✗ → 重写 |
| **数据支撑**:每条都有数字 / 指标 / 结果? | ✓ | ✗ → 加数据 |
| **卡点明确**:卡在哪、试过什么、需要什么? | ✓ | ✗ → 想清楚再写 |
| **下周可执行**:下周计划是动词开头(完成 / 推动 / 解决)? | ✓ | ✗ → 重写 |
| **没有废话**:没有"本周学习了 XX,收获很多"这种空话? | ✓ | ✗ → 删 |
| **< 7 块**:总共不超过 7 个要点(7±2 法则)? | ✓ | ✗ → 合并 / 删 |

### 5.4 写周报的 5 个常见错误

| 错误          | 例子                    | 正确写法                         |
| :--- | :--- | :--- |
| **流水账**     | "周一看了文档,周二写了代码,周三开了会" | "本周完成 A 优化,效果 +5%"           |
| **没有结果**    | "完成了 XX 模块的开发"        | "完成了 XX 模块,代码已 merge,测试通过"   |
| **"差不多"语气** | "效果还行"、"可能好一点"        | "AUC +0.5%,符合预期"             |
| **隐去卡点**    | (没写卡点)                | "卡在 X,需要 Y 资源,预计 X 月 X 日可解决" |
| **下周无规划**   | (没写下周)                | "下周:1) 完成 A 2) 解决 B 3) 启动 C" |

## 6. 向上沟通(二):寻求帮助 / 坏消息 / 资源——5 段式 + "if +1 说 X, 你回 Y"剧本

### 6.1 寻求帮助的 5 段式(必背)

**底层心智模型**: **决策依赖**——**+1 帮你需要"理由",理由就是"我已经做了多少 + 还差什么"**。

```text
1. 卡点(What): 我卡在 X 问题(1 句话)
2. 已尝试(What I tried): 试过 A(失败,原因 P), 试过 B(失败,原因 Q)
3. 排除项(What I excluded): 不是 Y, 不是 Z
4. 求助项(What I need): 我需要你帮我看 W,或者告诉我 H 文档
5. 紧急程度(When): P0/P1/P2
```

**完整例子**:
> "1. 我卡在**模型加载超时**的问题,3 天了没解决。2. 我试过**调 batch_size**(失败,GPU 显存还是满), 试过**预热脚本**(失败,预热时也超时), 试过**换更小的模型**(失败,精度不达标)。3. 我确认**不是网络问题**(本地可以,线上不行), **不是数据问题**(小数据集也慢), **不是代码问题**(没改过这段代码)。4. 我需要你帮我**看是模型服务配置问题,还是底层 GPU 调度问题**,或者**告诉我之前类似 case 的处理文档**。5. 这是 P0,**明天上线需要,4 小时内有结论最好**。"

**对比"我不会"**:
> "我不会,你看看?"

**为什么"5 段式"有效?** +1 看了能**直接判断**:
- 是不是你的问题 → 1 段(卡点)+ 3 段(排除项)告诉你"已排查"
- 要不要介入 → 5 段(紧急程度)告诉他"要不要立刻来"
- 怎么介入 → 4 段(求助项)直接告诉他"你帮我看什么"

### 6.2 "if +1 说 X, 你回 Y"剧本(5 个最常见场景)

**这是新人最常问的"我求助了,+1 回了这句话,我怎么接"**。

```text
【场景 1】+1 说:"你自己再排查排查"
└─ 你回:"好的,我接下来排查 [具体方向 A、B、C],预计 X 小时有结论,
        如果 [卡点 Y] 我再来求助您,可以吗?"
   (确认他的期望 + 你接下来的计划 + 多久求助,不是"好的"就完事)

【场景 2】+1 说:"这个我也不知道,你查查文档"
└─ 你回:"好的,我去查 [具体文档 1、2、3],1 小时内有结论,
        如果查不到,我再求助 [其他同事 X]"
   (确认范围 + 计划 + 兜底求助链)

【场景 3】+1 说:"你这个优先级不高,先放放"
└─ 你回:"好的,那 [当前任务] 的 deadline 我推后到 [新时间] 可以吗?
        我把精力放在 [新优先级]"
   (确认新时间 + 重新规划精力,**别沉默地"放",要主动 sync 进度**)

【场景 4】+1 说:"这个我帮你看,你先做别的"
└─ 你回:"感谢!这个卡了我 X 天,卡在 [具体点],
        如果您能告诉我 [具体方向] 我就最感激了"
   (感谢 + 复述问题 + 给他提示,不是"感谢"就完事)

【场景 5】+1 说:"为什么你之前没发现 / 没做"
└─ 你回:"[诚实承认],原因是 [具体原因,不要甩锅],
        接下来我 [具体改进措施],避免下次"
   (**不解释 / 不甩锅 / 不反驳**——承认 + 改进)
```

### 6.3 汇报坏消息(Bad News First)

**底层心智模型**: **决策依赖**——**坏消息被 +1 早知道 1 小时,损失就小 10%**。**越晚说,+1 越被动**。

**核心**: 任何坏消息,**第一句话就讲**,不要铺垫、不要解释、不要甩锅。

**❌ 反面例子**:
> "模型上线了,然后呢,情况比较复杂,可能跟 XX 有关,然后 YY,反正目前看效果是有点跌,大概跌了 1.5% 吧……"

**✅ 正确例子**:
> "**昨天上线的新模型 AUC 跌 1.5%, 已触发回滚,影响 30% 用户,目前已恢复**。**根因**:我初步看是 A 特征 join 漏了 5% 的数据,导致 1.5% 的样本特征全 0。**修复方案**:已修,1 小时内重新上线,先 5% 流量观察 1 天,数据 ok 再放量。**经验教训**:以后所有 join 操作必须加 unit test,我会本周加到 CI 里。"

**坏消息汇报模板**:
```text
1. 一句话结论: XX 出了 XX 问题,影响 XX
2. 当前状态: 已回滚 / 已止损 / 还在排查
3. 根因(初步): 怀疑是 X
4. 修复方案: 1 小时 / 1 天可修
5. 经验教训: 避免下次再犯
```

**为什么"坏消息要先讲"?**
- 任何坏消息被 +1 早知道 1 小时,损失就小 10%
- 越晚说, +1 越被动("你为什么不早说?")
- 坏消息汇报能力强的人,比"只报喜"的人晋升快 3 倍

### 6.4 争取资源(人头 / 时间 / 优先级)

**核心**: 争取资源 = **给 +1 一个"为什么应该把这个资源给你"的强证据**。

**❌ 错误**:
> "能不能给我加 2 个人?现在太忙了"

**✅ 正确**:
> "我想申请加 2 个工程师,理由如下:
> 1. **业务影响**: X 项目预计带来 Y 万收入,目前延期 2 周
> 2. **瓶颈分析**: 现有 3 人,2 个在 A 项目(占 80%),只有 1 人能做 B 项目
> 3. **人员画像**: 需要的是[画像:中级后端 + 数据],不是随便什么人
> 4. **ROI**: 加 2 人 → 2 周内上线 → 每年增收 Y 万,3 个月内回本
> 5. **兜底**: 如果不批,我可以砍掉 C 功能 / 推迟 D 项目
>
> 你看 1 周内能定吗?"

**争取资源模板**:
```text
1. 申请什么: 加 X 个 Y 类工程师
2. 为什么: 业务影响 + 瓶颈分析
3. ROI: 投入 X,产出 Y,周期 Z
4. 兜底: 不批的话我的备选方案
5. 时间: 我需要 X 月 X 日前定
```

### 6.5 申请加薪 / 晋升

**核心**: **不要等你做得好就期望 +1 自己发现**——他要管 5-10 个人,不会记住每个人的成绩。

**最佳实践**:
1. **每季度 1on1**: 主动列你这季度的成绩(项目 + 数字 + 团队贡献)
2. **半年度绩效答辩**: 准备 5-10 张 PPT(每张 1 个项目 + 数据)
3. **关键节点主动提**: 项目上线 1 周后,主动跟 +1 提"X 项目上线了,AUC +5%,业务增收 Y 万"
4. **不要抱怨**: 不要说"我做这么多,工资太低",**用事实和数据说话**

## 7. 横向沟通(一):跨团队协作 / 需求评审——"3 + 1 对齐"流程 + 撕逼剧本

### 7.1 跨团队协作的"3 + 1 法则"——项目启动流程

**底层心智模型**: **信息不对称**——**两个团队都"以为对方知道",结果两边都基于错误假设做事**。**3 + 1 法则 = 3 个对齐 + 1 个 backup**。

**会前:3 个对齐(必须发邮件/文档,不靠口头)**

| 对齐项 | 内容 | 形式 | 不对齐的后果 |
| :--- | :--- | :--- | :--- |
| **目标对齐** | 双方对这个项目的目标是否一致? | 邮件 / 会议开场白 | 两个团队做了不同的事 |
| **范围对齐** | 边界是什么,什么不做? | 文档 / 会议纪要 | 做了不该做的 / 该做的没做 |
| **时间对齐** | 关键节点和截止时间 | 文档 / 会议纪要 | 双方时间预期不一致,延期 |
| **Backup** | 出了分歧 / 卡住,**找谁仲裁**? | 双方 leader 或 PM | 卡住就僵,谁也拍不了板 |

**会中:1 次会议,把 3 个对齐 confirm**

**会后:发会议纪要邮件**(见 §7.2 模板)

**邮件模板**:
```text
Subject: [X 项目] 启动会 - 目标/范围/时间确认
To: A 同学 / B 同学 / +1 / +2
CC: ...

各位好,
X 项目正式启动,核心信息:
- 目标: Y(用 1 句话说清)
- 范围: 包含 a, b, c;不包含 d, e
- 关键节点: W1 完成 A, W2 完成 B, W4 上线
- 分工: A 组负责 a, B 组负责 b
- Backup: 有分歧找 +1 / +2 仲裁

请大家 1 周内回邮件确认 OK,如有异议现在提出。
```

### 7.2 需求评审会怎么开(会前 / 会中 / 会后)

**核心**: **"需求评审"不是"我讲你听",是"我讲完你提问题"**。

**会前**(3 件事):
1. **需求文档提前 1 天发出**(不要会上才讲)
2. **明确参会人 + 决策人**(谁拍板?)
3. **准备 5 个最可能被问的问题的答案**

**会中**(5 段):
1. **背景(1 min)**: 为什么做这个?业务影响多大?
2. **目标(1 min)**: 1 句话说清
3. **方案(5-10 min)**: 怎么做?
4. **替代方案(3 min)**: 还有什么方案?为什么选这个?
5. **风险(2 min)**: 可能出什么问题?兜底方案?

**会后**(2 件事):
1. **发会议纪要**: 结论 + 行动项 + 责任人 + 时间
2. **发 follow-up 邮件**: 让没参会的人也知道

### 7.3 需求变更的 4 步流程(最常被忽略的横向沟通)

**当需求变了,不要"口头说一句就改",按 4 步走**:

```text
【步骤 1】评估影响
  - 影响哪些团队的代码?
  - 影响多少工时?
  - 影响上线时间吗?

【步骤 2】通知所有受影响方
  - 邮件/IM 通知 + 1on1 解释
  - 模板:"需求变更:从 A 改成 B,因为 C,影响:你的 X 模块 Y 处要改,
          给你 1 周时间,你看 OK 吗?"

【步骤 3】同步决策链
  - +1 / PM 确认需求真的变了(不是 PM 口头说说)
  - 邮件留底:"X 同学 / +1 / PM 确认需求变更 Y"

【步骤 4】更新文档 + 纪要
  - 原需求文档标注"已变更"
  - 新需求文档 + 变更说明
  - 发会议纪要
```

**反例**: 跨团队项目里,**A 同学口头说"需求要改"**,B 同学改了 2 周后,PM 站出来说"我没说改啊"——**没有邮件留底,B 同学白干 2 周**。

### 7.4 跨团队撕逼时的"4 不 1 要" + "if A 说 X, 你回 Y"剧本

**4 不 1 要**:

| 原则 | 内容 |
| :--- | :--- |
| **不甩锅** | "是你们那边的问题" → 改成"我们一起定位" |
| **不情绪化** | "你们怎么这样" → 改成"这个 case 的预期是 X,实际是 Y,差异在 Z" |
| **不背后说** | 当面 B 团队说,背后对 A 团队抱怨 → 改成"我直接和 B 团队 leader 同步" |
| **不在群里吵** | 拉会议 / 当面聊,别在群里对峙 |
| **要对事不对人** | 永远 focus 在"问题"和"方案",不 focus 在"谁对谁错" |

**撕逼到上头的 3 步降火法**:
1. **暂停**: "我先消化一下,1 小时后回你"
2. **站在对方角度重写**: "如果我是 B 团队,我会怎么看?"
3. **找共同利益**: "我们的共同目标是把项目做好,不是谁背锅"

**"if A 说 X, 你回 Y"剧本(撕逼场景)**:

```text
【场景 1】A 说:"是你们的问题"
└─ 你回:"我看了下数据,问题可能在我们这边的 [具体点 X],也可能你们那边 [具体点 Y],
        建议我们 30 分钟拉个会议一起定位,可以吗?"
   (**不甩锅**,先认一半 + 一起定位)

【场景 2】A 说:"你们怎么不提前说"
└─ 你回:"我理解,这确实是流程问题,[具体反思],
        接下来我 [具体改进],你看这样可以吗?"
   (**不反驳**,认错 + 改进)

【场景 3】A 说:"我们这边没问题,你别甩锅"
└─ 你回:"我没有甩锅的意思,只是想一起定位 [具体问题],
        我把 [具体 log/trace/数据] 给你,你看 [具体环节] 是否有问题?"
   (**数据说话**,不嘴硬)

【场景 4】A 说:"这个不该我们做"
└─ 你回:"我理解,你的边界是 [X],这个事需要 [Y] 才能做,
        建议找 [Backup 仲裁] 拍板,可以吗?"
   (**不僵**,找仲裁)

【场景 5】A 团队 leader 找你抱怨你下属
└─ 你回:"[私下找 A leader 1on1],**先听他讲完**,不立刻反驳,
        然后说'我先了解下,1 天内回你'"
   (**私下 + 听完 + 不立刻反应**)
```

## 8. 横向沟通(二):Bug 定位与上下游排查——"4 阶段 8 步"流程 + 卡住决策树

**文字**: "被指出猜测在前,定位在后"——这是技术沟通中**最严重**的指控,因为它意味着你**浪费了别人时间**。**本节系统讲清楚"如何系统性地排查 + 如何让别人信服"**。

**底层心智模型**: **决策依赖 + 7±2 法则**——**你排查的每一步,都要让 +1 / 同事能"接得住"**——**他不需要知道你的所有细节,但需要知道"你到哪了"**。

### 8.1 Bug 排查的"4 阶段 8 步法"

| 阶段 | 步骤 | 目的 | 输出 |
| :--- | :--- | :--- | :--- |
| **阶段 1:确认** | 1. 复现 bug | 100% 复现,排除"伪 bug" | "5 次复现,必现" |
|  | 2. 量化影响 | 影响多少用户?什么时候开始? | "影响 12% 用户,30 分钟前开始" |
| **阶段 2:隔离** | 3. 看监控 / log | 哪一层报错? | "P99 涨到 450ms" |
|  | 4. 缩小范围 | 哪个服务?哪个接口?哪段代码? | "卡在 X 服务 Y 接口" |
| **阶段 3:验证** | 5. 提假设 | "我怀疑是 X 导致" | "怀疑是 A 特征 join 漏了" |
|  | 6. 验证假设 | 改 X 后,bug 消失了吗? | "改了后复现 5 次都好" |
| **阶段 4:修复** | 7. 改代码 | 修复根因,不是症状 | "代码已 PR" |
|  | 8. 验证 + 文档 | 修后跑通 + 写复盘文档 | "线上 P99 恢复,文档已写" |

**关键**: **每个阶段都要告诉别人你的进展**。**别闷头查 2 小时,最后说"找到了"**——对方会怀疑你**真的查了还是编的**。

### 8.2 报告"我在排查 X bug"的模板(同步进度用)

**当你开始排查,立刻发个消息或 1on1 同步,让别人知道你在做什么**:

```text
【Bug 排查进度】

问题: P99 涨 5 倍
现象: 30 分钟前开始,12% 请求
已排除: 网关 / DB / 下游服务
怀疑: 模型推理服务
下一步: 看 trace,30 分钟内有结论
截止: 14:00 前
```

**好处**:
- +1 知道你在做事,不会催你
- +1 知道截止时间,会准备 backup
- **如果卡住, +1 可以基于"已排除"项帮你缩小范围**

### 8.3 "我卡在第 X 阶段"决策树(最常被问的执行问题)

```text
【卡在"阶段 1:复现"——无法 100% 复现】

  Q1: bug 本身偶发吗?
  ├─ 是 → 加大监控、加采样、多观察几天、抓 trace 收集样本
  └─ 否 → 找最小复现路径:简化数据 / 简化场景 / 简化操作步骤

【卡在"阶段 2:隔离"——多个可能,无法缩小】

  Q1: 2 个可能?
  ├─ 是 → 二分法:关闭 A 看 B 是否复现,关闭 B 看 A
  └─ 否 → Q2

  Q2: 3+ 个可能?
  ├─ 是 → 用 §7.4 的"3 件套"找上下游同事
  └─ 否 → Q3

  Q3: 完全没头绪?
  └─ 是 → 用 §4.1 的 5 Why 反推

【卡在"阶段 3:验证"——改了 X,问题"看起来"好了】

  Q1: 复现 5 次都好了?
  ├─ 是 → 90% 修好了,等 24 小时看是否真不复发
  └─ 否 → Q2

  Q2: 改了 X 后没立刻复现?
  └─ 是 → 等 24 小时

  Q3: 改的是症状不是根因?
  └─ 是 → 重新做 §4.1 的 5 Why

【卡在"阶段 4:修复"——不知道怎么改】

  Q1: 改对了 = 1 行 / 1 个模块 / 1 个架构?
  ├─ 1 行 → 直接改
  ├─ 1 个模块 → 找该模块 owner 一起改
  └─ 1 个架构 → 写方案 + 评审 + 灰度

  Q2: 超过 1 天还没改完?
  └─ 是 → 求助 +1(用 §11 的 5 段式)
```

### 8.4 找上下游同事排查的"3 件套 + 1 礼貌"

**3 件套**(见 §4.4):

| 件套 | 内容 |
| :--- | :--- |
| 现象 | 我看到了什么(数据 + 截图) |
| 怀疑 | 我怀疑是你的哪个环节 |
| 诉求 | 我需要你提供什么 |

**1 礼貌**: "感谢你抽空帮我看" / "如果信息不全,我随时补充"

**完整模板**:
> "Hi B 同学,
>
> 我这边 P99 涨了,**trace 显示在调用你的 X 接口处卡 3 秒**。麻烦帮我看看你那 3 秒是在哪个步骤消耗的?**优先看 a、b、c 三步**。trace 链接: [URL]
>
> 感谢抽空!如果需要更多信息随时叫我。"

### 8.5 怀疑是上游数据问题时,怎么"问出好问题"

**❌ 错误**:
> "你给的数据是不是有问题?我看模型效果不好"

**✅ 正确**:
> "我这边精排 AUC 跌 1.2%,**对比了 3 个 batch 的样本,发现新一批数据的特征 X 平均值从 0.5 变成 0.8**,这个差异是不是符合预期?你方便查下 **X 特征在数据源端最近 1 周是否有变更**?如果不能查,**能不能帮我拉下 X 特征近 7 天的均值曲线**?"

**关键**: **不要"问是不是你的问题",而是"问一个具体的事实 / 数据"**。这样对方答得出来,问题就推进了。

### 8.6 复盘:从"猜测在前"到"事实先行"

**"猜测在前"的人的 3 个特征**:
1. **先改再查**: "我觉得是 X,先改改看"
2. **找不到就说"没看出来"**: 没头绪,硬扛,最后交付延迟
3. **不愿意写排查过程**: 只说结论不说过程,别人无法验证

**"事实先行"的人的 3 个特征**:
1. **先查再改**: "我先查清楚是什么,再改"
2. **查不到就求助**: 卡住就主动 sync 进度 + 求助
3. **主动写排查过程**: 把过程截图 / log / 命令贴出来,别人能复现

**自检方法**:
- 每次发"我在排查 X"时,自问:**如果我排查错了,这段话能让别人发现吗?**
- 如果答案是"不能"——**说明你的过程不够透明**。

## 9. 横向沟通(三):Code Review 怎么提 / 怎么收——"3 类 9 级"+ 评论剧本

**文字**: Code Review 是技术团队**最频繁的横向沟通**。**提得好,既不伤同事感情又能提质量**;**收得好,既不伤自尊又能快速成长**。

**底层心智模型**: **信息不对称 + 7±2 法则**——**3 类评论(Nit/Suggestion/Issue) 是给作者的"信号"**,**他需要知道"哪些必须改,哪些可以不改"**。

### 9.1 提 Code Review 的"3 类 9 级"原则

**3 类评论**:

| 类型 | 含义 | 例子 | 作者行动 |
| :--- | :--- | :--- | :--- |
| **Nit (琐碎)** | 不影响功能,纯风格/命名 | "变量名 userId 改成 user_id 更一致" | 可以不改 |
| **Suggestion (建议)** | 影响可读性或可维护性,但不是错 | "这个函数可以拆成 3 个小函数,提高可读性" | 应该改 |
| **Issue (问题)** | 影响正确性 / 性能 / 安全的 | "这里没处理空指针,会 NPE" | 必须改 |

**每类评论都明确标注**(用前缀):

```text
[Nit] 命名可以更一致
[Suggestion] 建议提取成函数
[Issue] 这里有内存泄漏
```

**好处**: 作者知道哪些**必须改**(Issue)、哪些**应该改**(Suggestion)、哪些**可以不改**(Nit)。**3 类标签 = 给作者一个"决策树"**。

### 9.2 提 Code Review 的"5 个不要" + "if 我想 X, 应该说 Y"剧本

| ❌ 不要说 | ✅ 应该说 | 触发的"不要" |
| :--- | :--- | :--- |
| "这代码写得太烂了" | "这段逻辑可以这样写:[具体建议]" | 没有人身攻击 |
| "为什么不这样写?" | "我看不太懂这里,能解释下为什么这么设计吗?" | 不质问 |
| "我在 X 项目看到不是这么写的" | "我有个建议,不知道是否适用:[建议]" | 不 compare |
| (没看完就提一堆 comment) | (完整看完后再提,先整体评价,再分点细节) | 不零散 |
| (在公司群里公开批评) | (私下 1on1 沟通) | 不公开 |

**"if 我想 X, 应该说 Y"剧本**:

```text
【想 X】想指出性能问题
└─ 应该说 Y:"[Issue] 这里看起来有性能隐患,[具体原因],
              建议改成 [具体方案],能避免 [具体后果]"

【想 X】觉得命名不规范
└─ 应该说 Y:"[Nit] 命名可以更一致,比如 userId → user_id,
              但不强求,看你项目风格"

【想 X】觉得代码结构不好
└─ 应该说 Y:"[Suggestion] 这块可以拆成 [3 个函数],每个函数职责更清晰,
                不影响功能,但好维护,你看 OK 吗?"

【想 X】想夸对方写得好
└─ 应该说 Y:"这个 PR 设计得不错,特别是 [具体点 X],比我之前想的更优雅,
              学习了"

【想 X】想质疑对方设计
└─ 应该说 Y:"这个设计我之前没遇到过,能展开讲讲为什么选 A 不选 B 吗?
              我想理解下你的考虑"
```

### 9.3 收 Code Review 的"3 个原则" + 5 种话术

**3 个原则**:
1. **不要玻璃心**: 别人提 comment 不是针对你,是针对代码
2. **不要立刻反驳**: 先想 1 小时,确认对方说的对,再回
3. **不要全盘接受**: 如果对方说的不对,**用数据/逻辑反驳**,不要"好的好的马上改"

**回 comment 的 5 种话术**:

| 情况 | 话术 |
| :--- | :--- |
| 同意,改了 | "好的,已改" |
| 部分同意 | "同意 a 部分,b 部分我保留意见,理由是 [具体原因],你看 OK 吗?" |
| 不同意 | "这个我考虑过,选 A 不选 B 是因为 [数据/逻辑],你看这个理由充分吗?" |
| 不理解 | "我没懂这个 comment 的意图,能展开讲讲吗?" |
| 知道但优先级低 | "这个我记下了,下个迭代处理,可以吗?" |

### 9.4 主动 Code Review 同事的代码(建立信任)

**主动 CR 同事的代码 = 主动建立信任**。**5 个做法**:

1. **新人入职第 1 周**:主动 CR 他的第一个 PR,顺便自我介绍
2. **跨团队项目**:主动 CR 上下游的 PR,提前发现集成问题
3. **核心模块**:主动 CR 核心模块的 PR,了解全貌
4. **重要 bug 修复后**:主动 CR,确保修复正确
5. **重大重构**:主动 CR,避免回归

## 10. 向下沟通:任务分配 / 反馈 / 1on1——3 阶段培养法 + 4 种难管下属对策

**文字**: 带人(向下沟通)是个**比向上沟通更难**的技能——你需要**把模糊的目标拆成清晰的任务**、**给及时且具体的反馈**、**通过 1on1 建立信任**。

**底层心智模型**: **7±2 法则 + 决策依赖**——**下属没你那么多 context,你给的任务越具体,产出质量越高**。

### 10.1 任务分配的"5 件套"

**❌ 反面例子**:
> "你把那个 XX 做了" ———(然后对方一脸懵)

**✅ 正面例子(5 件套)**:

```text
1. 目标(Why): 这个任务为什么做,业务影响是什么
2. 范围(What): 具体做什么,什么不做
3. 截止(When): 什么时候完成
4. 输入(Deps): 我提供什么 / 你需要从谁那里拿
5. 验收(How): 怎么算"完成",验收标准是什么
```

**完整例子**:
> "你做 X 任务的精排模型。
> 1. **目标**: A/B 实验组 AUC 比基线 +0.5%
> 2. **范围**: 引入 3 个新特征,跑 1 周实验;不优化推理性能
> 3. **截止**: 7 月 1 日上线,7 月 7 日出实验结论
> 4. **输入**: 数据我已经准备好,模型模板在 Y,讨论可以找我
> 5. **验收**: 模型 AUC +0.5%,P99 < 100ms,文档完整
>
> 有问题随时找我,**1 周后第一次进度同步**。"

### 10.2 反馈的"SBI 模型" + "if 下属 X, 你回 Y"剧本

**核心**: 反馈 = **Situation(情境) + Behavior(行为) + Impact(影响)**。

| ❌ 没结构的反馈 | ✅ SBI 反馈 |
| :--- | :--- |
| "你最近表现不太好" | "**过去 2 周,5 个任务你只完成了 2 个**,这个**让团队整体进度延迟了 1 周**。" |
| "你这个 bug 修得不行" | "**昨天那个 bug,你改了 3 个文件但 root cause 没找到,导致今天又出了一个类似 bug**,**用户反馈了 5 次**。" |
| "你代码写得不错" | "**这次 PR 加了 3 个 unit test,这是你之前没做的习惯**,**这让后续维护成本降低很多**。" |

**"if 下属 X, 你回 Y"剧本**:

```text
【下属 X】做错事,影响不大
└─ 你回 Y:"[Situation] 这次 X 任务, [Behavior] 你 Y 处没做对,
              [Impact] 导致 Z。接下来 [具体改进] 怎么做,你看 OK 吗?"

【下属 X】做错事,影响很大
└─ 你回 Y:"[Situation] X 任务, [Behavior] 你 Y 处做错,
              [Impact] 让团队 / 用户 [具体后果]。这件事很严重,
              我们聊聊怎么 [具体改进],避免下次"

【下属 X】做对事
└─ 你回 Y:"[Situation] X 任务, [Behavior] 你 Y 处做得很好,
              [Impact] 帮团队 / 用户 [具体好处]。继续保持"

【下属 X】问"你之前为什么不告诉我"
└─ 你回 Y:"我反思了下,确实 [具体反思],
              接下来我 [具体改进],你看这样可以吗?"

【下属 X】玻璃心,提了意见就崩溃
└─ 你回 Y:"私下 + 具体 + 给改进建议,不要公开批评"
```

**反馈的 5 个原则**:
1. **及时**: 行为发生后 1 周内反馈,别拖到季度总结
2. **具体**: "做得不错"是无效反馈,"加了 unit test 让维护成本降低"是有效反馈
3. **对事不对人**: "这个 PR 写得不好" vs "你写得不好"
4. **双向**: 给完反馈,**问对方怎么看**,不要单方面宣布
5. **可改进**: 反馈一定要带"下次怎么改",否则就是"打击"

### 10.3 1on1 怎么开(每月 1-2 次,30-60 分钟)

**1on1 是带人的核心机制**,不是"任务分配会",是"建立信任"。

**1on1 议程模板**:

```text
[5 min] 上次 follow-up: 上次 1on1 提到的问题,现在怎么样了?
[15 min] 对方讲: 最近的进展、卡点、想法
[10 min] 你反馈: 哪些做得好,哪些可以改进
[10 min] 职业发展: 他想往哪个方向走?需要什么支持?
[5 min] 你分享: 团队/业务/行业的变化
[5 min] 下次 follow-up: 确定下次时间
```

**1on1 黄金法则**:
- **70% 听,30% 说**: 大部分时间让对方讲,你引导
- **记笔记**: 每次 1on1 记笔记,下次回顾
- **不要全是工作**: 偶尔聊点对方的兴趣、生活,建立信任
- **每次有结论**: 结束时总结"今天决定了 X,下次跟进 Y"

### 10.4 培养下属的"3 阶段法" + 何时升级 / 降级决策树

| 阶段 | 你的角色 | 关注点 | 何时升级到下一阶段 |
| :--- | :--- | :--- | :--- |
| **L1: 入门(0-3 月)** | 手把手教 | 教他怎么做,review 他的每行代码 | 他能独立完成 L1 任务 |
| **L2: 独立(3-12 月)** | 监督 + 反馈 | 让他自己决定,有问题找他,review 他的关键设计 | 他能独立完成 L2 任务,且产出质量稳定 |
| **L3: 骨干(1-2 年)** | 授权 + 兜底 | 他自己跑,你只在有风险时介入 | 他能带新人 / 独立负责 1 个项目 |

**核心**: **根据他的能力**调整你的角色。**永远不要"放羊"**——不是"不管他",而是"管的方式不同"。

**"他是不是该升级到下一阶段"决策树**:

```text
Q1: 给他一个 L(下一阶段) 任务,他自己能做对吗?
   ├─ 是 → 升级
   └─ 否 → 继续当前阶段 + 加训

Q2: 他最近 3 个月有"主动提改进" / "带新人" / "独立负责"的迹象吗?
   ├─ 是 → 升级
   └─ 否 → 继续当前阶段

Q3: 你最近 1 个月 review 他的产出,质量稳定吗?
   ├─ 是 → 升级
   └─ 否 → 继续当前阶段
```

### 10.5 难管的 4 种下属与对策

| 类型 | 表现 | 对策 |
| :--- | :--- | :--- |
| **没主见** | 啥都问"你觉得呢" | 启发式提问:"你倾向哪个?为什么?" |
| **不反馈** | 进度滞后才汇报 | 约定日报 / 周报 + 1on1 节奏 |
| **玻璃心** | 一提意见就崩溃 | 私下反馈 + 给具体改进建议 |
| **摸鱼** | 上班摸鱼,产出低 | 先 1on1 了解原因,设硬性 OKR,不行就走人流程 |

## 11. 寻求帮助的艺术:5 段式 + "对方回 X 你怎么接"剧本

**文字**: "寻求帮助经常被认为没有证据"——这是新人最常犯的错。**根因是"我不会"是 L1 证据(纯直觉), +1 看到只能判断"你懒得想"或"你真不会"**。**正确的寻求帮助,是把问题"结构化"成 +1 能直接动手的形式**。

**底层心智模型**: **决策依赖**——**+1 帮你需要"理由",理由就是"我已经做了多少 + 还差什么"**。

### 11.1 寻求帮助的"5 段式"(必背)

```text
1. 一句话结论(What): 我卡在 X 问题
2. 我已尝试(What I tried): 试过 A 方案 (失败,原因 P), 试过 B 方案 (失败,原因 Q)
3. 我已排除(What I excluded): 不是 Y, 不是 Z
4. 我需要你帮我(What I need): 看 W 部分 / 告诉我 H 文档
5. 紧急程度(When): P0 / P1 / P2
```

**✅ 完整例子**:
> "1. 我卡在**模型加载超时**的问题,3 天了没解决。
> 2. 我试过**调 batch_size**(失败,GPU 显存还是满), 试过**预热脚本**(失败,预热时也超时), 试过**换更小的模型**(失败,精度不达标)。
> 3. 我确认**不是网络问题**(本地可以,线上不行), **不是数据问题**(小数据集也慢), **不是代码问题**(没改过这段代码)。
> 4. 我需要你帮我**看是模型服务配置问题,还是底层 GPU 调度问题**,或者**告诉我之前类似 case 的处理文档**。
> 5. 这是 P0,**明天上线需要,4 小时内有结论最好**。"

**对比"我不会"**:
> "我不会,你看看?"

**为什么"5 段式"有效?**
- +1 看了**直接知道你卡在哪**——不需要再问"卡在哪个环节"
- +1 看了**知道你努力过**——不会被认为"懒得想"
- +1 看了**知道紧急程度**——会立刻排优先级
- +1 看了**知道你要什么**——可以直接帮你或派别人

### 11.2 "对方回 X, 你怎么接"剧本(8 个最常见场景)

```text
【对方回 1】"你自己再排查排查"
└─ 你接:"好的,我接下来排查 [具体方向 A、B、C],
        预计 X 小时有结论,如果 [卡点 Y] 我再来求助您"

【对方回 2】"这个我也不知道,你查查文档"
└─ 你接:"好的,我去查 [具体文档 1、2、3],
        1 小时内有结论,如果查不到,我再求助 [其他同事 X]"

【对方回 3】"这个优先级不高,先放放"
└─ 你接:"好的,那 [当前任务] 的 deadline 我推后到 [新时间] 可以吗?
        我把精力放在 [新优先级]"

【对方回 4】"这个我帮你看,你先做别的"
└─ 你接:"感谢!这个卡了我 X 天,卡在 [具体点],
        如果您能告诉我 [具体方向] 我就最感激了"

【对方回 5】"为什么你之前没发现 / 没做"
└─ 你接:"[诚实承认],原因是 [具体原因,不要甩锅],
        接下来我 [具体改进措施],避免下次"

【对方回 6】"这个问题你自己想"
└─ 你接:"好的,我自己想 30 分钟,如果还想不出来,我再求助
        [其他同事 X] / [不同的人 Y]"

【对方回 7】"你找 XX 帮你看"
└─ 你接:"好的,XX 的联系方式是?我直接找他可以吗?
        麻烦你帮我介绍一下 [你的卡点],这样他不用从头了解"

【对方回 8】"这不应该你来找我"
└─ 你接:"我理解,你的边界是 [X],我先确认下 [Y],
        接下来我找 [Backup 仲裁] 拍板,你看可以吗?"
```

### 11.3 寻求帮助的"3 个不要" + 求助前自检清单

**3 个不要**:

| ❌ 不要 | ✅ 应该 |
| :--- | :--- |
| "我不会" | "我卡在 X,试过 A,需要 B" |
| "这个需求太难了,做不了" | "这个需求有 A 难点,我想了 B 方案,你帮我看 OK 吗" |
| "XXX 写过这个,我没看懂" | "XXX 的文档我看了,卡在 Y 部分,能给我讲讲吗" |

**求助前自检清单**:

| 问题 | 是 | 否 |
| :--- | :--- | :--- |
| 我已经尝试了至少 1 个方案? | ✓ | ✗ → 再想 30 分钟 |
| 我已经排除了至少 1 个可能? | ✓ | ✗ → 再排查 30 分钟 |
| 我知道要 +1 帮什么具体的事? | ✓ | ✗ → 想清楚再问 |
| 我能 1 句话说清卡点? | ✓ | ✗ → 写成文档再问 |
| 紧急程度合理(不是 P0 但实际是 P2)? | ✓ | ✗ → 调整预期 |
| 5 段式都填了? | ✓ | ✗ → 补完整再问 |

### 11.4 求助"借力"而不是"甩锅"

**借力** vs **甩锅**:

| 借力 ✓ | 甩锅 ✗ |
| :--- | :--- |
| "我卡在 X,我准备这样做,你帮我确认 OK 吗" | "X 不会,你做" |
| "我大致知道方向,但不确定细节,你帮我看" | "我啥都不知道,你给我讲讲" |
| "我先尝试,30 分钟后 sync,卡住再求助" | "我啥也没做,直接求助" |

**原则**: **求助前先自己尽 80% 的力**,剩下 20% 找 +1 借力。**求助 = 借力,不是甩锅**。

## 12. 冲突与坏消息:说"不"的 4 种方法 + "if A 说 X, 你回 Y"剧本

### 12.1 说"不"的 4 种方法

| 方法 | 例子 | 适用 |
| :--- | :--- | :--- |
| **直接说** | "这个我做不了,因为 [原因]" | 明确、紧急的事 |
| **延后说** | "这个我 1 周后才有空,可以先让别人做吗" | 非紧急,可以等的事 |
| **拆解说** | "这个完整的做不了,但 X 部分我可以做" | 大任务,不想全接 |
| **推荐说** | "我做不了,但 [B 同学] 可能可以做,我帮你引荐" | 想帮忙但帮不了 |

**说"不"的黄金法则**:
1. **先说"愿意"再"不"**: "我理解这个很重要,但是我手上 [Y] 任务,可能接不了"
2. **给理由**: 不是"不想做",是"做不到"
3. **给替代**: 不是"我不行",是"我可以做 X 帮你"
4. **不要马上说**: 给自己 1 小时冷静期,别情绪化

### 12.2 汇报坏消息(已在 §6.3 详述,补充)

**坏消息汇报的"5 不要"**:
1. **不要拖**: 越早说损失越小
2. **不要甩锅**: "是 XX 的问题" → "我们一起定位"
3. **不要解释**: 先讲事实,别解释原因
4. **不要"差不多"**: "大概跌了 1%-2%" → "跌了 1.5%"
5. **不要没方案**: 坏消息 + 方案 = 可控;坏消息 + 没方案 = 灾难

### 12.3 别人给你坏消息时怎么接

**❌ 错误回应**:
> "你怎么搞的?这么严重?"

**✅ 正确回应**:
> "1. 现在影响多大? 2. 怎么止损? 3. 我能帮什么?"

**核心**: **别人汇报坏消息,先 focus 在"现在怎么办",别先 focus 在"为什么出错"**。复盘后面再说。

### 12.4 与 +1 意见不一致

**3 步处理**:
1. **私下 1on1 表达**,别在公开场合反驳 +1
2. **用数据说话**: "我担心 X,数据上看 X 有 Y 风险,你怎么看?"
3. **如果 +1 坚持,执行**: 你是执行者,+1 是决策者,**有异议保留地执行**

**当 +1 明显错的时候**:
- 可以再表达一次,但**别死磕**
- 如果**风险很大**,把你的担忧**邮件留底**(CC 自己)
- 出了事,**责任在 +1 决策,你执行没毛病**

### 12.5 "if A 说 X, 你回 Y"剧本(冲突场景)

```text
【A 说 1】"这不该你做 / 这是 X 部门的事"
└─ 你回 Y:"我理解边界,这个事我先确认 [具体哪部分我必须做],
        接下来我找 [Backup] 拍板,你看可以吗?"

【A 说 2】"你错了 / 你做得不对"
└─ 你回 Y:"[先不反驳],你能展开讲讲哪里错吗?
        我想理解你的考虑"

【A 说 3】"你们怎么这么慢 / 这么差"
└─ 你回 Y:"我理解你的不满,这确实是 [具体问题],
        我接下来 [具体改进],预计 [时间] 解决"

【A 说 4】"这个不应该走 A 方案,应该走 B 方案"
└─ 你回 Y:"我能理解 B 方案的 [具体好处],
        我选 A 是因为 [具体数据/逻辑],你能看看 [具体数据] 吗?
        如果 A 真不行,我愿意切 B"

【A 说 5】(情绪化,大喊大叫)
└─ 你回 Y:"[暂停] 我先消化一下,1 小时后回你"
   (不立刻接招,给自己冷静时间)

【A 说 6】"这不符合规范 / 流程"
└─ 你回 Y:"我理解流程要求,我查下 [具体规范],
        如果我之前没遵守,我 [具体改进]"

【A 说 7】"你团队 / 你下属的 bug"
└─ 你回 Y:"我先了解下情况,1 天内回你 [具体时间和方案]"
   (不甩锅给下属,先认,再查)
```

## 15. 沟通前 30 秒准备术(万能决策树)——任何场景都适用的"开口前"流程

**这是这一章最重要的执行工具**。**任何沟通前 30 秒,跑这棵决策树**:

```text
【开口前 30 秒,必走流程】

Step 1 (5 秒): 我要沟通什么场景?
   ├─ 汇报进度 → 走 §5 周报
   ├─ 寻求帮助 → 走 §11 寻求帮助
   ├─ 汇报坏消息 → 走 §6.3 坏消息
   ├─ 跨团队协作 → 走 §7.1 跨团队
   ├─ Bug 排查 → 走 §8.1 Bug 排查
   ├─ Code Review → 走 §9 Code Review
   └─ 其他 → 继续 Step 2

Step 2 (5 秒): 我的"结论"是什么?
   ├─ 说不出来 → 还没想清楚,先想 5 分钟
   └─ 说得出来 → 继续 Step 3

Step 3 (5 秒): 我的结论需要 L 几证据?
   ├─ 走 §3.3 "该用 L几"决策树 → 决定 L1/L2/L3/L4
   └─ 不够 L2 → 补证据再开口

Step 4 (10 秒): 我要给对方的"下一步行动"是什么?
   ├─ 寻求决策 → "你看 X 之前能定吗?"
   ├─ 寻求帮忙 → "需要你帮我 Y"
   ├─ 同步信息 → "你只要知道就行"
   └─ 寻求共识 → "你看这样 OK 吗?"

Step 5 (5 秒): 我有没有"3 件套"(现象 + 怀疑 + 诉求)?
   ├─ 是 → 走 §4.4 / §8.4 的 3 件套模板
   └─ 否 → 补充完整再开口

【开口第一句话(模板)】
  场景 + 结论 + 证据 + 下一步

  例:"[场景] 周五了汇报下进度,这周 [结论] 完成 X,AUC +0.5%,
       [证据] 7 天 A/B 实验 + 30 天观察验证,
       [下一步] 你看下没问题可以放量"
```

**这套流程的关键**: **不是"先讲再想",而是"想完再讲"**。**30 秒 = 5 步 × 5-10 秒,任何场景都够**。

## 16. 30 字口诀 + 6 个月刻意练习计划

## 17. 远程协作沟通——Slack / 钉钉 / 邮件 / 视频会议的最佳实践

> **底层心智模型**: **信息不对称 + 异步协作**——**远程沟通的核心难点是"无法面对面确认对方是否真的听懂"**。**所有远程沟通都要"假设对方很忙,且只能用文字理解"**。

### 17.1 异步沟通(Slack / 钉钉 / 飞书)的 5 条铁律

**铁律 1:第一句话就是结论**

```text
❌ 错误:"在吗?有个事想跟你同步下,你能看下时间方便吗?"
✅ 正确:"X 服务 P99 涨了,需要你看下 Y 接口的 log,5 分钟内能看下吗?"
```

**铁律 2:一件事一条消息**

```text
❌ 错误:一条消息里问 5 件事,对方答了 3 件,你以为其他被忽略了
✅ 正确:5 件事分 5 条消息,每条单独 @ 对方
```

**铁律 3:24 小时未回 → 升级通道**

```text
如果你需要 X 紧急回复,但对方 4 小时没回:
  ├─ 再 @ 一次 + "P0,需要尽快"
  ├─ 1on1 / 电话
  └─ 找对方的 +1 协调
```

**铁律 4:复杂决策走邮件,不走 IM**

```text
❌ 错误:"我建议换 X 方案,因为 Y,Z。你看行吗?"(IM 里)
✅ 正确:写邮件 + 数据,1 段问"你看 X 之前能定吗?"
```

**铁律 5:不要在群里吵架**

```text
任何冲突:
  ├─ 拉到 1on1
  ├─ 用电话 / 视频
  └─ 别在大群 @ 对方对峙
```

### 17.2 邮件的 9 个最佳实践

| # | 实践 | 例子 |
| :- | :--- | :--- |
| 1 | **主题行精确** | "[X 项目] 启动会 - 目标/范围/时间确认" |
| 2 | **正文 ≤ 3 段** | 1 段背景 + 1 段需求 + 1 段 deadline |
| 3 | **每封邮件只说一件事** | 不要 "顺便问一下..." |
| 4 | **明确行动项** | "请 X 月 X 日前回复" |
| 5 | **CC 必要的人** | 不要 CC 全公司 |
| 6 | **关键决策邮件留底** | CC 自己 |
| 7 | **回复时间** | 工作时间 ≤ 4 小时,非工作时间次日 9 点 |
| 8 | **附件命名清晰** | "X_项目_方案_v3_final.docx" |
| 9 | **不要用红色感叹号** | 显得急躁 |

### 17.3 邮件的"主题行"分类

| 类型 | 主题模板 |
| :--- | :--- |
| **决策请求** | "[项目 X] 请决策 - Y 方案 Z 备选,需要 X 月 X 日前确认" |
| **同步信息** | "[项目 X] Y 已完成 - 进展同步" |
| **寻求帮助** | "[项目 X] 卡在 Y,试过 Z,需要 W 支援" |
| **资源申请** | "[项目 X] 申请 Y 资源 - ROI 分析附上" |
| **坏消息** | "[项目 X] 紧急 - Y 出了 Z 问题,影响 W" |
| **会议邀请** | "[项目 X] 启动会 - 月/日/时,议程附上" |

### 17.4 视频会议(Zoom / 腾讯会议 / Meet)的"前中后"流程

```text
【会前 24 小时】
  1. 发会议邀请(议程 + 文档 + 决策点)
  2. 明确参会人 + 决策人 + 备份
  3. 提前 1 天发出背景文档

【会中】
  1. 前 5 分钟:recap 上次会议结论
  2. 中间:按议程推进,每 15 分钟 check 进度
  3. 最后 5 分钟:总结行动项 + 责任人 + 时间

【会后 24 小时内】
  1. 发会议纪要邮件(谁 / 做了什么 / 截止什么时候)
  2. 把关键决策邮件留底
  3. 更新项目文档
```

### 17.5 跨时区协作

**核心挑战**: 同步时间只有 4-6 小时,其余时间异步。

**最佳实践**:
- **重要决策放同步会议**: 异步容易出现理解偏差
- **详细文档化**: 异步需要更多上下文
- **24 小时响应窗口**: 不要期望对方秒回
- **明确"工作时间"**: 北京 9-18 / 旧金山 9-18,交集 = 北京 0-9 / 17-18

## 18. 高敏感场景——绩效反馈 / 被裁 / 调岗 / 离职的沟通剧本

> **底层心智模型**: **情绪管理 + 决策依赖**——**敏感场景下,情绪会主导理性**。**沟通前先冷静 1 小时,再开口**。

### 18.1 给下属的负向绩效反馈(年度)

**场景**: 年度绩效结果不佳,需要 1on1 反馈。

**5 步反馈剧本**:

```text
【Step 1】开场定调(30 秒)
  "今天的 1on1 我们聊一下年度绩效,我会先讲结论,再讲具体的事,
   最后我们一起讨论改进方向。"

【Step 2】讲结论(1 分钟)
  "今年的绩效结果是 C(待改进),没有达到晋升预期。
   这个结果是综合多维度的评估,我想讲 3 个具体的事。"

【Step 3】讲具体的事(5 分钟)
  "1. 项目 X:Y 处没达到 deadline,导致 Z 项目延期 2 周
   2. 协作:W 项目 2 次没有按时同步,导致上下游返工
   3. 主动提改进:今年提改进建议 1 次,去年是 5 次,减少明显"

【Step 4】让对方回应(3 分钟)
  "我想听听你怎么看,这些点是符合你的判断吗?"

【Step 5】改进方向(5 分钟)
  "基于这些事,我希望接下来 3 个月我们重点改进:
   1. 项目管理:每个项目都有 weekly check-in
   2. 沟通:任何 delay 提前 3 天告诉我
   3. 主动提改进:每月至少 1 次

   1 个月后我们再 review 一次。"
```

### 18.2 收到"被裁"消息怎么应对

**❌ 错误反应**: 立刻情绪化、立刻签字、立刻发朋友圈

**✅ 正确反应**:

```text
Step 1:接受现实 + 保持冷静
  "我理解公司的决定。能否给我 24 小时时间消化一下,
   我会再回复您?"

Step 2:争取最优解
  - 补偿: N+1 / N+2 / 股票加速 vesting?
  - 时间: 通知期能否延长?
  - 推荐信: 能否 +1 写推荐信?
  - 离职证明: 措辞中性,不写"被裁"

Step 3:内部转岗
  "公司是否有其他岗位我可以考虑?"

Step 4:对外资源
  "能否帮我推荐到 X 公司 / X 团队?"
```

### 18.3 调岗沟通

**场景**: 公司主动调岗 / 你想调岗。

**被调岗时**(公司主动):
```text
1. 问原因:"能否告诉我调岗的背景?"
2. 问未来:"新岗位的发展路径是什么?"
3. 谈条件:"薪资 / 职级 / 工作内容是否有变化?"
4. 备份选项:"如果不接受,我的选项是什么?"
```

**主动调岗时**:
```text
1. 提前 1on1 沟通(不要在公开场合)
2. 准备调岗理由 + 未来贡献
3. 提替代方案(原岗位怎么交接)
4. 给 +1 时间考虑(1-2 周)
```

### 18.4 离职沟通

**核心原则**: **永远 positive,绝不抱怨**。

**Step 1:1on1 提前 2-4 周通知**

```text
"我深思熟虑后,决定在 X 月 X 日离职。
   决定的原因主要是我希望在 [新方向] 深耕,
   [新公司/新方向] 在这方面有更聚焦的机会。

   我会确保 [交接计划]:
   1. 项目 X:Y 同事接手,我做完整 transfer
   2. 文档:Z 文档已更新
   3. 客户/合作方:我会介绍给 W

   我希望最后 2 周能做好交接,不留下技术债。"
```

**Step 2:准备离职面谈**

HR 可能问:
- "你为什么离开?"
- "你对公司有什么建议?"
- "你会推荐朋友来吗?"

**标准答案**: positive + 建设性 + 永不抱怨。

**Step 3:工作交接**

- 文档清单
- 项目状态
- 联系手册
- 关键决策邮件留底

### 18.5 同事被裁 / 离开,怎么沟通

**❌ 错误**:
- 公开议论"听说 X 被裁了"
- 私下说"他做错了什么"
- 幸灾乐祸

**✅ 正确**:
- 私下关心:"听说你离开了,有什么我能帮的吗?"
- 团队内部不议论
- 必要时推荐工作机会
- 离职后保持 connection

## 19. 跨文化沟通——中美大厂 / 远程团队的差异

> **底层心智模型**: **文化差异 = 信息不对称**——**对方的"正常"在你的文化里可能是"不正常"**。

### 19.1 中美大厂的沟通差异

| 维度 | 中国大厂 | 美国大厂 |
| :--- | :--- | :--- |
| **会议风格** | 直接 + 快节奏 | 慢 + 多轮确认 |
| **决策速度** | 自上而下快 | 自下而上慢 |
| **邮件** | 短 + IM 为主 | 长 + 邮件为主 |
| **反馈** | 隐晦 + 留面子 | 直接 + 数据说话 |
| **加班** | 普遍 | 较少,效率优先 |
| **晋升** | 答辩 + KPI | 周期 + 多维评估 |
| **表达** | 重结果 | 重过程 + 思考 |

### 19.2 出海 / 北美面试的特殊准备

**英文自我介绍模板**(1 分钟):
```text
"Good morning/afternoon. My name is [Name], I've been working in
recommendation systems for 5 years, currently a [Title] at [Company].

My expertise is in generative search/recommendation systems,
particularly in:
1. Semantic ID for long-tail coverage
2. Multi-task generative ranking
3. Inference optimization

The project I'm most proud of is [Project]: we redesigned the
ranking architecture and improved offline AUC by 0.5% and
online CTR by 6%.

I'm excited about [Company]'s work in [Area] and I think my
background fits well with this role."
```

**英文行为面模板**(STAR):
```text
"In my previous role, I led the redesign of our ranking model.
The Situation was that we were facing performance regression
after merging a new feature pipeline.
The Task was to identify the root cause and fix it within 1 week.
The Action I took was to systematically profile the pipeline
and found a 5% data leakage in the join operation.
The Result was that we fixed the bug and reduced P99 latency
by 30% and recovered the offline AUC.

Looking back, the key learning was to always add unit tests
for data joins, which we now enforce in CI."
```

### 19.3 跨文化会议的"5 不要"

1. **不要**用幽默讽刺(对方可能听不懂)
2. **不要**用中文流行语("内卷"、"躺平"对方听不懂)
3. **不要**用 "我们" 包括对方(对方可能觉得被冒犯)
4. **不要**假设对方知道中国文化背景
5. **不要**打断对方(尤其在欧美文化里是大忌)

### 19.4 与海外同事的协作

- **文档英文优先**(降低沟通成本)
- **会议记录英文**(确保未参会人能 catch up)
- **代码注释英文**(便于开源 / 跨团队)
- **PR 描述英文**(便于国际同事 review)
- **主动分享 context**(对方没有你的 background)

## 20. 真实案例库——10 个沟通失败 / 成功复盘

> **目的**: 通过真实案例学"如何做"和"如何避免"。

### 案例 1:跨团队会议"我讲完了,你听不懂"

**场景**: A 团队邀请你讲方案,你讲了 30 分钟,对方一直沉默。

**❌ 失败原因**:
- 用了太多对方不熟悉的术语
- 没问对方基础 context
- 没给对方提问机会

**✅ 正确做法**:
- 提前发背景文档
- 开头先讲 SCQA(背景→冲突→问题→答案)
- 每讲 10 分钟留 2 分钟给 Q&A
- 关键决策点用具体例子说明

### 案例 2:Code Review 引战

**场景**: 你给同事提了 10 个 comment,对方回"我不同意其中 8 个"。

**❌ 失败原因**:
- 没分 Nit / Suggestion / Issue(对方不知道哪些必须改)
- 用了"你怎么不这样写"的质问语气
- 没先整体评价,直接零散 comment

**✅ 正确做法**:
- 用前缀[Nit]/[Suggestion]/[Issue]分类
- 先整体评价"这个 PR 设计不错",再分点细节
- 用"我建议 X,因为 Y,你看 OK 吗?"代替"为什么不 X"

### 案例 3:周报写得太长

**场景**: 周报写了 3000 字,+1 看完说"我没什么问题"。

**❌ 失败原因**:
- 写了 10 件事(超过 7±2)
- 流水账,没突出重点
- 没数字 / 没影响

**✅ 正确做法**:
- 只写 3-5 件事
- 每件事 1 句话 + 1 个数字
- 重点突出本周最重要的进展 + 卡点

### 案例 4:求助被敷衍

**场景**: 你求助 +1,"我不会,你看看",+1 回"你自己再排查排查"。

**❌ 失败原因**:
- 没说明已尝试 / 已排除
- 没说明紧急程度
- 没说明要 +1 帮什么具体的事

**✅ 正确做法**: 用 5 段式
```text
1. 卡点: 模型加载超时
2. 已尝试: 调 batch_size(失败), 预热脚本(失败)
3. 已排除: 不是网络 / 不是数据
4. 求助: 帮我看是配置还是 GPU 调度
5. 紧急: P0, 明天上线需要
```

### 案例 5:坏消息拖 3 天

**场景**: 模型上线后效果跌 5%,你拖了 3 天才汇报,+1 批评你"为什么不早说"。

**❌ 失败原因**:
- 想"再排查一下" / "说不定自己恢复了"
- 没意识到坏消息拖的成本

**✅ 正确做法**:
- 第一句话讲坏消息:"上线后 AUC 跌 5%"
- 第二句话讲状态:"已回滚 / 已止损"
- 第三句话讲根因 + 修复方案

### 案例 6:与 +1 意见不一致的硬碰硬

**场景**: +1 让你做 A,你坚持 B,在会议上争论 30 分钟。

**❌ 失败原因**:
- 没私下 1on1,直接在公开场合反对
- 用"我觉得 B 更好"而不是数据
- 没给 +1 台阶

**✅ 正确做法**:
- 私下 1on1 表达:"我担心 X 风险,数据上看 X,Y,您怎么看?"
- 如果 +1 坚持,执行(有异议保留地执行)
- 风险大时邮件留底

### 案例 7:项目延期才说

**场景**: 项目 deadline 是今天,你今天才告诉 +1 "延期 1 周"。

**❌ 失败原因**:
- 没提前预警
- 没在 1 周前 / 3 天前说

**✅ 正确做法**:
- 风险出现时立刻 sync
- 用 §6.4 的"5 段式求助"

### 案例 8:1on1 全是任务分配

**场景**: 1on1 全是你在说,下属 30 分钟没说 3 句话,1on1 变成批斗会。

**❌ 失败原因**:
- 70% 是你说,30% 是对方说(应该反过来)
- 没让对方讲他的想法 / 卡点

**✅ 正确做法**:
- 70% 听,30% 说
- 用 §10.3 的议程模板
- 问开放式问题:"你怎么看?"

### 案例 9:跨时区团队协作失灵

**场景**: 北京和旧金山团队,北京同事每天 9 点发消息要求对方 1 小时内回。

**❌ 失败原因**:
- 没考虑时区(对方是深夜)
- 期望秒回

**✅ 正确做法**:
- 异步沟通优先(文档 / 邮件)
- 重要决策走同步会议
- 24 小时响应窗口

### 案例 10:同事离职引发的尴尬

**场景**: 同事 X 离职,你听到消息,在公司群里说"听说 X 要走了?"

**❌ 失败原因**:
- 公开议论敏感信息
- 没考虑 X 感受

**✅ 正确做法**:
- 私下关心 X
- 公司群里不主动议论
- 等 X 正式公布再说

## 23. 与 AI 协作的沟通方法论(2025+ 新增)

> **底层心智模型**: **AI 是你的"虚拟 +1"**——**AI 比真人 +1 更耐心,但需要你"精确 prompt"**。

### 23.1 与 AI 协作的 5 个最佳实践

**实践 1:把 AI 当成"什么都不懂但很聪明的实习生"**

```text
❌ "帮我优化下这个模型"(太抽象)
✅ "我有 1 个推荐精排模型,DNN, 输入特征有 a,b,c, AUC 现在 0.71。
   想优化到 0.75。请告诉我 3 个可行的方案 + 每个方案的 trade-off"
```

**实践 2:提供 context,不只是问题**

```text
每次问 AI:
  1. 角色("你是 1 个 L8 搜推架构师")
  2. 背景("我在做 X 业务")
  3. 任务("我需要你帮我 Y")
  4. 约束("deadline X,资源 Y")
  5. 输出格式("请用 bullet point,每点 ≤ 30 字")
```

**实践 3:让 AI 反问你**

```text
"在回答前,如果你觉得我的问题缺少 context,请先列出 5 个最关键的问题让我回答"
```

**实践 4:用 AI 辅助沟通**

- **写作前**:"帮我看下这段邮件,哪里不够结构化"
- **复盘后**:"我是 +1,我下属发来了这段汇报,请评估他的 L 几沟通"
- **场景模拟**:"你是面试官,请问我这个项目的 5 个最尖锐问题"

**实践 5:不要全盘相信**

```text
AI 的回答:
  ├─ 当作"参考意见",不是"标准答案"
  ├─ 关键决策自己再验证
  └─ 让多个 AI 给答案对比
```

### 23.2 与 AI 协作的反模式

| ❌ 反模式 | ✅ 正模式 |
| :--- | :--- |
| "帮我做完这个任务"(无脑甩) | "帮我理清思路,我来做" |
| "这个对吗?"(完全依赖) | "我有 X,Y,Z 三个考虑,你怎么看?" |
| 同一问题问 10 次无优化 | 每次给反馈:"你的回答 X 部分不对,应该是 Y" |
| 用 AI 替代思考 | 用 AI 加速思考 |

### 23.3 提示词(Prompt)的 5 段式

```text
1. 角色: 你是 X(如 "我是 L8 搜推架构师")
2. 背景: 我在做 Y(背景 1-2 句话)
3. 任务: 我需要你 Z(具体任务)
4. 约束: 限制条件(time / resource / quality)
5. 输出: 输出格式(长度 / 结构 / 风格)
```

**示例**:
```text
你是一个 L8 级别的资深推荐系统架构师。
我在做 1 个千亿参数推荐模型的推理优化,目前 GPU 利用率只有 30%。
我需要你帮我分析瓶颈并给出 3 个优化方向。
约束:1 周内出方案,不能引入新依赖。
输出:用 Markdown,每点 ≤ 50 字,带可执行的下一步。
```

## 27. 沟通方法论的"反例警示录"

> **目的**: 通过失败案例避免重蹈覆辙。

### 27.1 反例 1:沟通中的"自嗨"

**表现**:
- "我做了 X、Y、Z,很牛吧?"
- 没关注对方关心什么

**纠正**: **永远先问"对方关心什么",再说"我能提供什么"**。

### 27.2 反例 2:沟通中的"过度准备"

**表现**:
- 准备 1 小时,讲 5 分钟
- 文档 50 页,对方只看 1 页

**纠正**: **结论先行 + 1 页 PPT + 详细文档 backup**。

### 27.3 反例 3:沟通中的"闪躲"

**表现**:
- 不直接回答
- 用"我再想想"

**纠正**: **当场能答就答,不能答给具体时间("我 X 小时内回你")**。

### 27.4 反例 4:沟通中的"情绪宣泄"

**表现**:
- 在群里抱怨
- 公开批评他人

**纠正**: **私下 + 对事不对人 + 找 Backup**。

### 27.5 反例 5:沟通中的"假装权威"

**表现**:
- 不懂装懂
- 跳过证据直接下结论

**纠正**: **承认不知道 + 给时间查 + 不要装**。

### 27.6 反例 6:沟通中的"信息不对称陷阱"

**表现**:
- 默认对方知道
- 没交代 context

**纠正**: **30 秒 recap 背景,即使对方"应该知道"**。

### 27.7 反例 7:沟通中的"过度承诺"

**表现**:
- "我 1 天搞定"
- 实际需要 1 周

**纠正**: **给保守 deadline + 提前预警风险**。

### 27.8 反例 8:沟通中的"沉默抗议"

**表现**:
- 不同意但不说话
- 用"好 / OK"敷衍

**纠正**: **明确表达不同意 + 给具体理由 + 提替代方案**。

## 28. 沟通能力成熟度模型——从 L1 到 L5

> **目的**: 给自己定位,**知道下一阶段该练什么**。

### 28.1 5 个层级

| 层级 | 表现 | 训练重点 |
| :--- | :--- | :--- |
| **L1:想到哪说到哪** | 30 秒说不清 | 结构化表达 |
| **L2:有结论没证据** | "我觉得 X" | 证据链 |
| **L3:结论+证据** | "X 是因为 Y 日志" | 稳定 L3 |
| **L4:结论+证据+影响+建议** | "X 影响 3 场景,建议 A" | 决策思维 |
| **L5:决策+推动+影响** | 让团队 / 跨团队为你推进 | 影响力构建 |

### 28.2 自我评估问卷

每题 1-5 分,总分 = 平均分:

1. 我能 30 秒说清任何沟通要点
2. 我的结论有 L2 以上证据
3. 我能稳定使用 §2 的 4 个框架
4. 我能用 5 段式求助
5. 我能用 SBI 给反馈
6. 我的周报能让 +1 30 秒读完
7. 我能用 4 不 1 要处理冲突
8. 我的 Code Review 用 3 类 9 级
9. 我能在求助后被 +1 评价"靠谱"
10. 我能让跨团队同事愿意主动找我

**评估标准**:
- 1-2 分:L1-L2,需要 §2 + §3 训练
- 3 分:L3 基础,需要 §5 + §11 训练
- 4 分:L4 稳定,需要 §7 + §10 训练
